# Boost 官方文档管理机制（源格式 → 构建链 → 归档发布）

> 元数据
> 生成日期：2026-11-14 ｜ 版本基线：Boost 1.92.0（2026-11-14 冻结；期间官网版本选择器已出现 1.93.0.beta1，见 §5.1 注）
> 调研方式：GitHub API / raw.githubusercontent 抽查 13 个库的 doc/ 目录与 Jamfile 原文；boost.org 各 URL 全部 curl/WebFetch 实测（直连失败时用代理 `http://127.0.0.1:10808`），核实日期统一为 2026-11-14
> 上游约束：术语表（`docs/glossary_术语表.md`）——b2、BoostBook、QuickBook、Doxygen、AsciiDoc、Antora、MrDocs、docca 等工具名一律不译
> 对应总纲：P7 → R8 文档管理机制

## 0. 快速结论（TL;DR）

1. **源格式碎片化是现状**：抽查 13 个库，QuickBook（含 +Doxygen 混合）仍是绝对主流（9/13）；AsciiDoc/asciidoctor 3/13；Antora+MrDocs 1/13（url）；另有 1/13（multi_index）直接手写 HTML。官方未强制统一格式。
2. **构建契约已经明确**：库作者只需在 `doc/` 放一个 b2 Jamfile（或 `doc/antora.yml`），定义 `boostrelease` 别名；发布脚本按此构建并把产物"原样拷贝"进发布树。整合进全站 BoostBook 一本书的 `boostdoc` 目标已被官方标注为**遗留（legacy），新库应避免**。
3. **归档机制确认**：`/doc/libs/{版本}/`（含 beta，如 `1_93_0_beta1`）为按版本冻结的静态树；`/doc/libs/latest/` 与 `/doc/libs/release/` 为别名，指向**当前发布快照**（实测与 1.92.0 内容不一致——处于 1.93 开发周期，见 §5.3）。库列表页在新官网会 302 到 Django 动态页 `/libraries/{v}/list/`。
4. **2023+ 官网改版**：新官网是 Django 应用（boostorg/website-v2），静态文档树存于 AWS S3、由 Django 兜底视图输出；库/版本数据从 GitHub 自动同步（`.gitmodules` + `meta/libraries.json`）；统一文档门户（用户指南/贡献者指南/正式评审）由 **Antora** 生成（boostorg/website-v2-docs）。
5. **新动向**：C++20 modules 文档化走"逐库增量 + 官方原型公告"路线（1.87 PFR 起步，1.89 扩至 Any/TypeIndex，PFR 按"官方推荐实践"重写）；参考文档生成新工具 MrDocs（cppalliance/mrdocs）已在 url 库落地；发布说明正向 AsciiDoc（S3 托管）迁移。

- **QuickBook 路线**（9/13）内部又分两类：纯手写 .qbk（stacktrace、regex、test 主体）与"QuickBook 叙述 + Doxygen 生成 API 引用"混合（filesystem、asio、geometry、log、beast、test）。

- **Antora 组件路线**目前样本最少（url），但它是新官网统一门户的原生格式，官方贡献者指南已把它列为受支持的两种布局之一（见 §3.2）。
- boostorg/docca 仓库自述："Boost.Book XSLT C++ documentation system"；cppalliance/mrdocs 自述："A Clang/LLVM tool for building reference documentation from C++ code and javadoc comments"（均为 2026-11-14 实测）。

## 3. 构建链：从源格式到 HTML

### 3.1 三条管线一览（源格式 → 工具链 → 产物）

| # | 源格式 | 工具链（依序） | 中间产物 | 最终产物 | 实测示例 |
|---|---|---|---|---|---|
| A | QuickBook (.qbk) | b2（`using quickbook`）→ quickbook 可执行 | BoostBook XML（.xml） | DocBook XSL（xsltproc + DocBook XSL 样式表 + DocBook DTD）→ 分块 HTML；可选 Apache FOP 出 PDF | filesystem `doc/html/`、stacktrace |
| B | C++ 源码注释 | Doxygen（`using doxygen`） | Doxygen XML | ① asio 式：doxy2qbk.pl → .qbk → 接 A 线；② json 式：docca → entities.adoc → 接 C 线；③ hana 式：Doxygen 直接出 HTML | asio、json、hana |
| C | AsciiDoc (.adoc) | asciidoctor（b2 `import asciidoctor` 或独立工具） | — | HTML（+PDF，如 compat）；Antora 线则由 Antora 汇总成多页文档站（Node.js ≥16，playbook + 自定义 UI bundle） | compat、json（叙述页）、url（Antora） |
| D | C++ 源码 + javadoc 注释 | MrDocs（Clang/LLVM） | MrDocs 输出 | Antora 站点内嵌参考页（`mrdocs.yml` 配置） | url |

### 3.2 官方构建契约（库作者必读）

来源：新官网贡献者指南（boostorg/website-v2-docs，2024 版，实测 2026-11-14）：

1. **文档入口**：发布树中每个库的文档入口必须是 `libs/<库名>/index.html`，通常用 `<meta http-equiv="refresh">` 重定向到真正的文档页（如 `doc/html/index.html` 或 `../../doc/antora/<库名>/index.html`）。实测 1.92.0 中：
   - `libs/filesystem/index.html` → `libs/filesystem/doc/index.htm`
   - `libs/asio/index.html` → `doc/html/boost_asio.html`（全站级 doc/html 树）
   - `libs/json/index.html` → `libs/json/doc/html/index.html`
   - `libs/url/` → `doc/antora/url/index.html`；`libs/msm/` → `doc/antora/msm/index.html`
   - 旧惯例 `libs/<库名>/doc/html.html` 已 **404**（实测），新规入口是 `index.html`。
2. **两种受支持的布局**（官方《Documentation Guidelines》原文口径）：
   - **Antora 组件文档**：库仓库放 `doc/antora.yml` + `doc/modules/ROOT/pages/`（AsciiDoc），再到 boostorg/website-v2-docs 的 `libs.playbook.yml` 注册组件；发布时由 Antora 统一构建，产物写入发布树 `doc/antora/<库名>/`。1.92.0 发布树中实测生效的 Antora 组件为 **msm 与 url** 两个。
   - **独立文档（standalone）**：库仓库放 `doc/Jamfile`（b2 工程），常用工具为 AsciiDoc、Doxygen、QuickBook；构建在库目录内"就地"产出（通常 `doc/html/`），发布脚本**原样拷贝**进发布树。
3. **`boostrelease` / `boostdoc` 契约**（组织要求 `Building Documentation` 节原文要点）：
   - `doc/` 工程必须定义 `boostrelease` 目标（别名）；发布脚本只认 `doc/` 这一个位置。
   - `boostdoc`（把库文档整合进全站 BoostBook"一本书"）**已被官方标注为遗留做法，新库应避免**（实测 compat 的 Jamfile 中 `alias boostdoc ;` 为空别名、`boostrelease` 指向 html，即此口径的落地实例）。
4. **超级项目聚合构建**：boostorg/boost 的 `doc/Jamfile.v2` 用 `path.glob libs/*/doc 与 tools/*/doc` 收集各库 Jamfile，构建全站聚合文档（这正是历史 `doc/html/` 一书树的来源；因 `boostdoc` 转遗留，新书树增长已停滞）。

### 3.3 本地构建实操（开发者）

```bash
# 前置：b2 可执行 + 以下外部工具（BoostBook/A 线必需，官方 Getting Started 实测口径）：
#   xsltproc、DocBook XSL 样式表、DocBook DTD（PDF 另需 Apache FOP）
# quickbook 可执行通常由 b2 按 "using quickbook" 自动从 tools/quickbook 源码构建

cd libs/<mylib>/doc          # 或 tools/<tool>/doc
b2                           # 构建 Jamfile 默认目标
b2 html                      # 常见显式目标名（如 compat: b2 html / b2 pdf）
```

注意事项（均实测或官方文档口径）：
- 各库 Jamfile 顶部 `using quickbook ;` `using boostbook ;` `using doxygen ;` `using xsltproc ;` 声明所依赖工具（filesystem 实例）。
- Antora 线不依赖 b2：需 Node.js ≥16 + `npx antora`（website-v2-docs 的 `libdoc.sh`/`build.sh`；url 库自带 `build_antora.sh`）。
- docca 线依赖 `tools/docca`（以 b2 `import-search /boost/docca` 引入）+ Doxygen。
- 历史教训：QuickBook/BoostBook 工具链外部依赖（xsltproc/DocBook XSL 版本匹配）是库作者常见的构建门槛，这也是官方把"新格式"引向 AsciiDoc/Antora 的现实原因之一（官方 Antora 指南明示动机）。

## 4. 工具链要点补充（各格式简介/优缺点/适用场景）

### 4.1 QuickBook + BoostBook（Boost 传统的第一格式）

- **简介**：Wiki 式轻量标记（.qbk）→ BoostBook XML（DocBook 的 Boost 定制子集）→ DocBook → HTML/PDF。支持 `[import]` 抽取源码片段、与 Doxygen 生成物拼装。
- **优点**：Boost 全家桶内建（b2 自动编译 quickbook）；与回归测试/发布脚本深度集成；20+ 年存量模板与先例极多；Doxygen 混合管线成熟。
- **缺点**：外部依赖链重（xsltproc + DocBook XSL/DTD）；语法封闭、生态小；错误信息不友好；新官网统一门户（Antora）并不以它为原生格式。
- **适用场景**：维护既有 Boost 库；需要与老式全站 BoostBook 一书树共存；叙述文+大 API 参考混合的大型库。
- **实测样本**：filesystem、asio、geometry、regex、stacktrace、beast、log、test（8 库纯 QBK 主体）+ hana 之外的其余样本均含 .qbk 成分。

### 4.2 Doxygen（及 docca 变体）

- **简介**：从源码注释生成参考文档。Boost 内三种用法：Doxygen XML→QuickBook（asio/geometry/log）；Doxygen XML→docca→AsciiDoc（json）；Doxygen 直出 HTML（hana）。
- **优点**：注释即文档，单一事实来源，改接口不用手改手册；docca 产物可进 asciidoctor/Antora 新管线。
- **缺点**：输出质量取决于注释纪律；直出 HTML 风格与 Boost 站点不一致（hana 例）；XML→中间格式转换脚本各自维护（doxy2qbk.pl/docca 双轨）。
- **适用场景**：API 面大的库，凡"参考手册"部分都建议注释化；叙述/教程部分仍需独立格式。
- **实测样本**：asio、json、geometry、hana、log、test、filesystem（参考部分）。

### 4.3 AsciiDoc / asciidoctor

- **简介**：现代轻量标记（GitHub 原生渲染），asciidoctor 工具链出 HTML/PDF；也是 Antora 的页面语言。b2 有内建 `asciidoctor` 模块（compat 实测）。
- **优点**：工具链极轻（无 xsltproc/DocBook 依赖）；可读性接近 Markdown；与 Antora 统一门户同语言；可出 PDF。
- **缺点**：Boost 存量模板少；参考文档仍需 docca/MrDocs 等生成器配合；b2 集成模块不如 quickbook/boostbook 文档化程度高。
- **适用场景**：新库叙述文档、小型库全套文档、准备接入 Antora 门户的库。
- **实测样本**：compat（独立）、json（docca 产物）、url（Antora 页面）。

### 4.4 Antora + MrDocs（新官网原生组合）

- **简介**：Antora 是多组件文档站生成器（Node.js），Boost 用它构建统一门户（用户指南/贡献者指南/正式评审，实测门户页 `user-guide/index.html` 标注 "Antora 3.1.15"）；MrDocs 是 C++ Alliance 开发的 Clang/LLVM 参考文档生成器，输出接 Antora。
- **优点**：版本化/多分支/跨库导航原生支持；站内搜索与统一 UI；MrDocs 直接解析真实源码（含 javadoc），无需 Doxygen 中转；这是官方新门户的主航道。
- **缺点**：需要 Node.js 工具链（与 Boost 传统 C++ 构建链分离）；目前接入 libs.playbook.yml 的库极少（实测 develop 名单仅 msm、url）；MrDocs 尚在快速演进期。
- **适用场景**：新库愿意长期跟进官方门户演进、或需要跨版本文档站的库。
- **实测样本**：url（全链路）；msm（已注册组件）。

### 4.5 新库作者选型建议（选择策略矩阵）

| 你的情况 | 推荐格式 | 理由 |
|---|---|---|
| 新库、API 面大、希望"注释即参考" | 源码注释 + **docca→AsciiDoc**（或跟进 MrDocs 成熟后切 MrDocs） | 单一事实来源；产物可直接被 asciidoctor/Antora 消费 |
| 新库、叙述文档为主、想上官方统一门户 | **AsciiDoc + Antora 组件**（`doc/antora.yml`） | 官方两种受支持布局之一；门户原生格式；工具链最轻 |
| 新库、最小可用文档、暂不接门户 | **AsciiDoc 独立文档**（`doc/Jamfile` + `import asciidoctor`，参照 compat） | 官方认可；b2 一条命令出 HTML/PDF；日后迁 Antora 成本低 |
| 接手/维护既有 QBK 库 | **维持 QuickBook**，不迁移 | 迁移无官方强制；存量 Jamfile/模板成熟；破坏性风险大于收益 |
| 极小库（几个函数） | 手写 HTML + `libs/<库名>/index.html` 入口 | multi_index 先例；契约只要求入口与 `boostrelease`，格式自由 |

一句话结论：**新库默认 AsciiDoc（独立或 Antora 组件）+ 注释化参考（docca/MrDocs）；旧库维持 QuickBook 不折腾。**

## 5. 归档与发布机制

### 5.1 官网 URL 体系（2026-11-14 实测）

| URL | 实测行为 | 说明 |
|---|---|---|
| `https://www.boost.org/doc/libs/` | 301 → `/libraries/` | 库总列表页已迁新应用 |
| `https://www.boost.org/doc/libs/latest/` | 302 → `/libraries/latest/list/` | 列表页是 Django 动态页；其版本选择器显示 Latest=1.93.0.beta1（基线冻结时点已进入 1.93 周期） |
| `https://www.boost.org/doc/libs/1_92_0/` | 302 → `/libraries/1-92-0/list/` | 版本列表页同样动态化，URL 用连字符版本号 |
| `https://www.boost.org/doc/libs/1_92_0/libs/filesystem/index.html` | 200 → `.../doc/index.htm` | **静态归档树仍在原域名按版本提供** |
| `https://www.boost.org/doc/libs/1_92_0/libs/asio/index.html` | 200 → `.../doc/html/boost_asio.html` | asio 文档位于全站级 `doc/html/` |
| `https://www.boost.org/doc/libs/1_92_0/libs/url/` | 200 → `.../doc/antora/url/index.html` | Antora 组件产物进发布树 `doc/antora/<库名>/` |
| `https://www.boost.org/doc/libs/latest/libs/regex/index.html` | 200 → `.../doc/html/index.html` | `latest` 对静态深层路径同样有效 |

| `https://www.boost.org/doc/libs/1_93_0_beta1/libs/filesystem/doc/html/index.html` | 200 | **beta 版本同样按版本归档** |
| `https://www.boost.org/doc/libs/1_92_0/doc/html/quickbook.html` | 200 | QuickBook 自身文档随发布树分发 |
| `https://www.boost.org/doc/tools/quickbook/`（发布说明中仍引用） | 404 | 旧站独立工具文档路径已在改版中失效（遗留断链实例） |

### 5.2 latest/release 别名语义（实测细节）

- `/doc/libs/latest/` 与 `/doc/libs/release/` 为同一内容的两个别名（实测同一路径返回字节一致：filesystem `doc/index.htm` 均为 20284 字节、md5 相同）。
- 该别名内容**不等于** 1.92.0 冻结树：同名文件（filesystem `doc/index.htm`）在 latest 为 20284 字节、在 1.92.0 为 20382 字节，md5 不同；asio `doc/html/boost_asio.html` 同样不一致。结合旧站 `doc/.htaccess`（`/doc/html → libs/release/doc/html` 的 rewrite 规则，boostorg/website 仓库实测）可判定：**release/latest = 当前发布分支（master）的文档快照，随开发周期滚动更新**，而 `/doc/libs/{版本}/` 为发布时冻结的静态副本。开发者引用文档时，**要"稳定引用"就用带版本号 URL，要"跟最新"才用 latest**。
- beta 亦有独立版本树（`1_93_0_beta1`），但实测其树内个别旧路径（如 filesystem `doc/index.htm`）与稳定版布局存在差异（beta 下该文件 404、`doc/html/index.html` 存在）——按版本的树以该版本实际构建产物为准，跨版本路径不可假设一致。

### 5.3 新官网架构与发布流程（2023+ 改版）

三仓库分工（全部 2026-11-14 实测）：

| 仓库 | 分支 | 角色 |
|---|---|---|
| boostorg/website | master | **旧官网**（PHP/静态 HTML 生成），README 称 master 自动同步上线；现已非现役前台，存量发布说明 HTML 停留在 1.89.0 前后 |
| boostorg/website-v2 | develop | **新官网**（Django 应用，Python 3.13 + Docker；stage.boost.org 预发、www.boost.org 生产） |
| boostorg/website-v2-docs | develop | **统一文档门户的 Antora 源仓库**（contributor-guide / user-guide / formal-reviews / site-pages / release-notes / history 组件 + `libs.playbook.yml` + `libdoc.sh` 构建脚本 + antora-ui 定制主题） |

关键机制（均出自 website-v2 仓库 docs/ 目录原文，实测）：
- **静态文档托管**：`docs/static_content.md`——发布文档树存放在 AWS S3；Django 的 `StaticContentTemplateView` 是 URL 兜底视图，按 `{env}_static_config.json` 映射 + S3 key 探测返回内容（Redis/DB 缓存加速）。这解释了 §5.1 中"列表页 302 到 Django、深层静态路径直接 200"的混合行为。
- **数据同步**：`docs/syncing_data_with_github.md`——版本数据取自 boostorg/boost 的 tags/releases（`import_versions`）；库数据每月从 `.gitmodules` + 各库 `meta/libraries.json` 刷新（`update_libraries`）；**各库-版本的文档 URL 由后台任务扫描 S3 发布树自动发现**（`import_library_version_docs_urls`）。
- **发布说明**：`import_release_notes` 优先取 **S3 上的 AsciiDoc 源**渲染，回退到 boostorg/website 仓库的遗留 HTML；发布说明源文件历史上即 website 仓库 `feed/history/boost_X_YZ_0.qbk`（QuickBook，本次实测 1.84–1.90 共 7 个 qbk 原文用于 C++20 modules 检索）。
- **下载分发**：下载元数据来自 Artifactory（`import_archives_release_data`）；文件实体在 `https://archives.boost.io/release/{版本}/source/`（实测 1.92.0 提供 7z / tar.bz2 / tar.gz / zip 及 rc 变体）。
- **发布节奏**：官方贡献者指南《Release Process》——每年 3 次（4 月、8 月、12 月第二周），master 分支按"提前 7/6/5/4/1 周、4 天"阶梯冻结，beta 与 RC 先行，必要时出补丁版本（如 1.91.0-1，官网版本选择器实测可见）。

### 5.4 旧站（boostorg/website）的 doc/libs 来源

旧体系（2024 年前）中 `/doc/libs/{版本}/` 不在 website 仓库内，而是发布时由发布管理者把发布包 `doc/` 树上传到服务器（website 仓库 `doc/.htaccess` 实测含 `/doc/html → libs/release/doc/html`、CSS/图片统一指向 `libs/common` 等 rewrite 规则，可佐证 `libs/release`、`libs/common` 的目录约定）。新站把这套静态树搬进了 S3，并保留了对外 URL 兼容（§5.1 重定向行为）。

## 6. 新动向（2024–2026）

### 6.1 C++20 modules 的文档化（逐库增量，非一步到位）

- **事实基线（以发布说明 qbk 原文为准，2026-11-14 实测）**：
  - 1.84.0/1.85.0/1.86.0 发布说明**无** C++20 modules 内容（常见"1.84 起 modules"的说法不成立）；
  - **1.87.0**：PFR "Initial support for C++20 Modules"（首个）；
  - **1.89.0**：Any、TypeIndex 新增 initial support；PFR "按新的官方推荐实践重写 C++20 module"；另有库 "Add support for modular build structure with b2"；
  - （注：`modular build structure` 一词在 1.87 发布说明中另指 b2 对**超级项目模块化 git 结构**的构建支持，勿与 C++20 modules 混淆——与术语表 §1 的"模块/module 分译"约定一致。）
- **文档形态（PFR 实测）**：库仓库新增 `modules/boost_pfr.cppm`（模块接口单元）+ `doc/pfr.qbk` 内 "PFR as a C++20 module" 章节：CMake 选项 `-DBOOST_USE_MODULES=1`、`import boost.pfr;` 用法、手工 clang 预编译命令、早期阶段警示（caution）。
- **官方公告**：boost.org 新闻《C++20 modules and Boost: a prototype》（2025-01-29，实测 200）：`BOOST_USE_MODULES` 宏让头文件在 `#include` 与 `import` 间切换；原型阶段、逐库推进。截至目前**没有**统一的"推荐实践"总册，规范散落在该公告 + 逐库文档 + CMake 集成中。
- **官网旧路径**：`/docs/modular-boost`、`/development/modular-boost.html` 均 404（实测）；git 模块化（2013）的说明现归属新门户贡献者指南 superproject 章节。

### 6.2 文档体系统一化（Antora 门户 + MrDocs）

- 统一门户已上线：`https://www.boost.org/docs/`（实测 200）聚合 **User Guide / Contributor Guide / Formal Reviews** 三大 Antora 组件；门户页实测标注 Antora 3.1.15；"Edit this Page" 直链 GitHub `boostorg/website-v2-docs`。
- 官方《Documentation Guidelines》明确 Antora 组件与 standalone 两种布局并列受支持，并给出库接入门户的步骤（antora.yml → 注册 libs.playbook.yml → 发布树 `doc/antora/<库名>/`）。
- 实际接入进度缓慢：develop playbook 实测仅 **msm、url** 两库；1.92.0 发布树 `doc/antora/` 下同样只有这两个组件——"门户已就绪、库迁移刚起步"是当前格局。
- MrDocs（cppalliance/mrdocs）作为下一参考文档生成器在 url 库全链路落地；Antora 生态配套扩展（`@cppalliance/antora-cpp-reference-extension`、`antora-cpp-tagfiles-extension`、`asciidoctor-boost-links` 等）已在 libs.playbook.yml 实测可见，跨库引用通过 Doxygen tagfile 互联（url 的 tagfiles 指向 system/core/filesystem 的 `doc/libs/master/` 页面）。
- 发布说明 AsciiDoc 化：website-v2 已按"S3 AsciiDoc 源优先、遗留 HTML 兜底"取数（§5.3），说明官方内容生产在整体向 AsciiDoc 收敛。

### 6.3 遗留断链与治理缺口（实测发现）

- `/doc/tools/quickbook/` 等 1.90 发布说明中引用的旧工具文档路径 404；QuickBook 文档现只能经发布树 `/doc/libs/{v}/doc/html/quickbook.html` 获取。
- 旧站库文档入口 `doc/html.html` 惯例废弃（404），未在所有旧版本树上补齐重定向。
- 旧 website 仓库发布说明 HTML 停更于 1.89 前后，1.90+ 依赖新站管线——跨仓库检索历史发布说明时需注意分界。

## 7. 文档获取方式总结（开发者实用结论）

| 场景 | 推荐方式 | 说明 |
|---|---|---|
| 日常查 API（要稳定链接） | `https://www.boost.org/doc/libs/{版本}/libs/{库名}/index.html` | 带版本号=冻结树；入口页会重定向到该版本真实文档位置（doc/html/ 或 doc/antora/） |
| 查最新文档 | `https://www.boost.org/doc/libs/latest/libs/{库名}/index.html` | 注意 latest 是当前发布分支快照，开发期内可能与上一个正式版不一致（§5.2） |
| 浏览/搜索全库 | `https://www.boost.org/libraries/`（或旧 `/doc/libs/` 自动跳转） | 新站动态列表页，支持按版本/分类/关键词筛选 |
| 离线阅读（推荐） | 发布包自带完整文档：下载 `boost_1_92_0.tar.gz`（或 7z/zip）解压后看 `libs/<库名>/doc/html/`、顶层 `doc/html/`（含 boost_asio 等）、`doc/antora/`；QuickBook 自身手册在 `doc/html/quickbook.html` | 文档树与源码同包分发，无需另下；archives.boost.io 可取任意历史版本（1.92.0 提供 7z/tar.bz2/tar.gz/zip） |
| 系统包管理器安装的用户 | 文档通常不在运行时包内 | Debian/Fedora 等将 doc 拆分为 `-doc` 子包或仅提供在线版（与 P4 主流版本调研结论衔接） |
| 从源码重建文档 | 库目录 `doc/` 下 `b2`（需 xsltproc+DocBook XSL 等）；Antora 组件库用 Node.js + `npx antora`（参照 url/build_antora.sh 或 website-v2-docs/libdoc.sh） | 见 §3.3 |
| 查历史发布说明 | 新站 `/releases/{版本}/`（聚合页）或 boostorg/website `feed/history/boost_X_YZ_0.qbk` 原文（1.89 前后为 HTML） | 本项目 P3 翻译主数据源即此 |

**核心结论**：Boost 文档"源在各库仓库、构建有契约（doc/ + boostrelease 或 antora.yml）、发布树按版本冻结 + latest 滚动别名、托管已从自管服务器迁至 S3+Django"。开发者最可靠的离线文档来源始终是**发布包自带的 doc/ 树**；在线引用时优先带版本号 URL。
