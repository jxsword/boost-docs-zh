引言

Boost 不要求任何特定的文档结构. 但是, 有一些影响内容与结构的重要因素. 例如, 许多 Boost 库最终会被提案纳入 C++ 标准, 因此最初就使用适合写入标准的文字来编写可能有所帮助. 另外, Boost 库文档通常经由万维网访问, 包括通过搜索引擎, 因此每个页面的上下文往往很重要. 最后, Boost 库还应提供额外的文档, 如入门、教程、示例和设计理由内容. 考虑到这些因素, 我们对 Boost 库文档建议以下指南.

符合标准的文档

C++ 标准所要求的文档结构是描述库技术规范的一种有效方式. 这种格式虽然简洁, 却为许多 Boost 用户所熟悉, 而且比大多数临时拼凑的格式精确得多. 以下描述基于标准的 §17.3. (注意, 最终的标准提案必须包含完整的标准措辞, 这是委员会不会替你完成的; 但 Boost 库文档不需要达到那样的详细程度.)

文档元素

每份文档视情况包含以下元素(1):

  • 摘要
  • 要求
  • 详细规范
  • 对标准 C++ 库的引用
  • 对标准 C 库的引用

摘要

摘要提供该分类的概要, 并介绍一级子条款. 每个子条款也提供摘要, 列出该子条款中规定的头文件以及每个头文件中提供的库实体.

标记为 "Note(s):" 或 "Example(s):" 的段落是说明性的, 其他段落是规范性的.

摘要和详细规范按以下顺序呈现:

  • 宏
  • 取值
  • 类型
  • 类
  • 函数
  • 对象

要求

C++ 程序可以对该库进行扩展. 每一条款视情况描述此类扩展必须满足的要求. 这类扩展通常属于以下几类之一:

  • 模板实参
  • 派生类
  • 满足某种接口约定的容器、迭代器和/或算法

接口约定要求尽可能一般化地表述. 接口不陈述 "class X 必须定义一个成员函数 operator++()", 而是要求 "对任意对象 x (属于 class X), ++x 有定义". 也就是说, 该运算符是否为成员并未指明.

要求以定义良好的表达式来表述, 这些表达式定义了满足要求的类型的有效用法. 针对每一组要求都有一个表格, 规定一组初始的有效表达式及其语义. 任何使用这些要求的泛型算法, 都依据其形式类型参数的有效表达式来描述.

模板实参要求有时会按名称引用.

在某些情况下, 语义要求以 C++ 代码的形式给出. 这样的代码旨在说明一个结构与另一结构的等价性, 而不一定是该结构必须采用的实现方式.(2)

详细规范

详细规范各包含以下元素:

  • 名称与简要说明
  • 概要 (视情况为类定义或函数原型)
  • 模板实参的限制 (如有)
  • 类不变式的说明
  • 函数语义的说明

类成员函数的说明按如下顺序排列 (视情况)(3):

  • 构造函数与析构函数
  • 复制与赋值函数
  • 比较函数
  • 修改器函数
  • 观察器函数
  • 运算符及其他非成员函数

函数语义的说明包含以下 元素 (视情况)(4):

要求: 调用该函数的前置条件
效果: 该函数执行的动作
后置条件: 该函数建立的可观察结果
返回: 对该函数返回值的说明
抛出: 该函数抛出的任何异常, 以及导致异常的条件
复杂度: 该函数的时间及/或空间复杂度
设计理由: 该函数的设计依据或存在理由

库条款中规定的复杂度要求是上限; 提供更好复杂度保证的实现同样满足要求.

函数语义元素说明

上面的函数语义元素说明直接取自 C++ 标准, 相当简洁. 下面对每个元素给出更详细的解释.

注意 <code> ... </code> 字体标签的用法, 它用于把实际的 C++ 用法与英文散文区分开来.

要求

调用该函数的前置条件, 通常以谓词形式表达. 最常见的前置条件是对实参值的要求, 常以 C++ 表达式的形式给出. 例如,

 
void limit( int * p, int min, int max );
要求: p != 0 && min <= max

C++ 语言规则已强制的要求 (如实参的类型) 不会在"要求"段落中重复.

效果

该函数执行的动作, 可用散文或 C++ 描述. 散文描述通常对实现者的限制更少, 但往往不如 C++ 代码精确.

如果某一效果已在其他元素中说明, 特别是 后置条件、返回或抛出, 就不要再在 效果段落中描述. 只保留单一描述可确保有且仅有一份规范, 从而消除分歧的风险.

后置条件

该函数的可观察结果, 例如变量的值. 后置条件通常表述为函数完成后为真的谓词, 采用 C++ 表达式的形式. 例如:

 
void make_zero_if_negative( int & x );
后置条件: x >= 0

返回

该函数返回的值, 通常以 C++ 表达式的形式给出. 例如:

int sum( int x, int y );
返回: x + y

只需指明返回值; 类型已由 C++ 语言规则确定.

抛出

既要指明抛出异常的类型, 也要指明导致抛出异常的条件. 例如, std::basic_string 类规定:

 
void resize(size_type n, charT c);
抛出: length_error 如果 n > max_size().

复杂度

指明函数的时间及/或空间复杂度往往并不可取, 因为它会过度约束实现者, 而且很难正确指明. 因此, 复杂度通常最好留作实现的品质问题.

不过, 如果符合规范的各实现之间性能差异很大, 库组件实际上可能变得不可移植. 容器就是一个典型的例子. 在这些情况下, 指明复杂度就变得值得.

复杂度常用广义的 "大 O" 表示法来指明.

设计理由

指明函数设计或存在的设计理由, 往往能让用户深入了解库为何如此设计. 更重要的是, 它有助于避免在库成熟过程中"修复"其实没有坏的东西.

Web 参考文档

Boost 库文档经常经由万维网访问. 通过搜索引擎, 参考内容深处的页面可能在没有任何上下文的情况下被查看. 因此, 为每个页面添加额外的上下文信息会有所帮助, 例如:

  • 说明所在的命名空间, 或使用全限定标识符.
  • 为每个类型或函数记载所需的头文件.
  • 链接到相关的教程信息.
  • 链接到相关的示例代码.
  • 包含库名.
  • 包含导航到文档开头的导航元素.

还应考虑描述在搜索引擎中的效果. 简略或晦涩的描述不太可能帮助好奇的读者找到相关的函数或类型.

脚注

(1) 为节省篇幅, 不适用于某一条款的条目将被省略. 例如, 如果某条款没有规定任何要求, 就不会有"要求"子条款.
(2) 尽管在某些情况下, 代码无疑是最佳实现.
(3) 为节省篇幅, 不适用于某个类的条目将被省略. 例如, 如果某个类没有规定任何比较函数, 就不会有"比较函数"子条款.
(4) 为节省篇幅, 不适用于某个函数的条目将被省略. 例如, 如果某个函数没有规定任何前置条件, 就不会有"要求"段落.
