概述

bcp 工具是用于提取 Boost 子集的工具, 对希望将其库与 Boost 分开发布的 Boost 库作者, 以及希望随应用程序分发 Boost 子集的 Boost 用户都很有用.

bcp 还可以报告你的代码依赖 Boost 的哪些部分, 以及这些依赖使用了哪些许可证.

示例 

bcp scoped_ptr /foo

把 boost/scoped_ptr.hpp 及其依赖复制到 /foo.

bcp boost/regex.hpp /foo

把 boost/regex.hpp 及其所有依赖 (包括正则表达式源码 (位于 libs/regex/src) 和构建文件 (位于 libs/regex/build)) 复制到 /foo. 不复制 regex 的文档、测试或示例代码, 也不复制 Boost.Build 系统.

bcp regex /foo

把完整的 regex 库 (位于 libs/regex) 连同其依赖 (例如 regex 测试程序所需的 boost.test 源码) 复制到 /foo. 不复制 Boost.Build 系统.

bcp --namespace=myboost --namespace-alias regex config build /foo

把完整的 regex 库 (位于 libs/regex) 加上 config 库 (libs/config) 和构建系统 (tools/build) 连同所有依赖复制到 /foo. 同时把 boost 命名空间重命名为 myboost, 并把二进制库的文件名前缀从 "boost" 改为 "myboost". --namespace-alias 选项使 namespace boost 成为新名称的别名.

bcp --scan --boost=/boost foo.cpp bar.cpp boost

扫描 [非 Boost] 文件 foo.cpp 和 bar.cpp 的 boost 依赖, 并把这些依赖复制到子目录 boost 中.

bcp --report regex.hpp boost-regex-report.html

为 boost 模块 regex.hpp 创建名为 boost-regex-report.html 的 HTML 报告. 报告包含许可证信息、作者详情和文件依赖.

行为选择 

bcp --list [options] module-list

输出 module-list 中所有文件 (含依赖) 的列表.

bcp [options] module-list output-path

把 module-list 中找到的所有文件复制到 output-path

bcp --report [options] module-list html-file

输出一个包含以下内容的 html 报告文件:

  • 所有生效的许可证, 以及使用每种许可证的文件和使用每种许可证的版权持有人.
  • 任何没有可识别许可证的文件 (请把这些报告给 boost 邮件列表).
  • 任何没有可识别版权持有人的文件 (请把这些报告给 boost 邮件列表).
  • 所有版权持有人及其持有版权的文件.
  • 文件依赖信息——指出任何特定文件被包含在所发现的依赖中的原因.

选项 

--boost=path

把 boost 树的位置设置为 path. 若未提供此选项, 则假定当前路径是 Boost 树的根目录.

--namespace=newname

复制文件时, boost 命名空间的所有出现都会被重命名为 "newname". 同时把 Boost 二进制文件重命名为使用 "newname" 而非 "boost" 作为前缀.

该选项常与 --namespace-alias 选项配合使用, 允许在同一个程序中使用两个不同的 Boost 版本, 但不能在同一个编译单元中使用.

--namespace-alias

与 --namespace 选项配合使用时, namespace boost 将被声明为新命名空间名称的别名. 这使得依赖 namespace boost 中 Boost 代码的现有代码无需改动即可编译, 同时保留通过更改命名空间可实现的"强版本控制".

--scan

把模块列表视为要扫描 boost 依赖的 (可能非 Boost 的) 文件列表, 模块列表中列出的文件不会被复制 (或列出), 只会复制它们所依赖的 boost 文件.

--svn

仅复制处于 svn 版本控制之下的文件.

--unix-lines

确保所有被复制的文件使用 Unix 风格的行尾.

module-list

未使用 --scan 选项时, 这是要复制的 boost 文件或库名称的列表, 可以是:

  1. 工具名: 例如 "build" 会找到 "tools/build".
  2. 库名: 例如 "regex".
  3. 头文件标题: 例如 "scoped_ptr" 会找到 "boost/scoped_ptr.hpp".
  4. 头文件名: 例如 "scoped_ptr.hpp" 会找到 "boost/scoped_ptr.hpp".
  5. 文件名: 例如 "boost/regex.hpp".

使用 --scan 选项时, 这是要扫描 boost 依赖的 (可能非 Boost 的) 文件列表, 因此模块列表中的文件不会被复制/列出.

output-path

文件将被复制到的路径 (该路径必须存在).

依赖

文件依赖按如下方式发现:

  • 扫描 C++ 源文件中的 #include, 然后扫描 boost 源码树中出现的所有 #include 的依赖, 依此类推.
  • C++ 源文件会与某个库的名称关联, 如果该库有源码 (可能还有构建数据), 则把这些源码包含进依赖.
  • 检查 C++ 源文件对 Boost.test 的依赖 (例如查看它们是否使用 cpp_main 作为入口点).
  • 扫描 HTML 文件的直接依赖 (图像和样式表, 但不包括链接).

应当注意, 实际使用中 bcp 可能产生相当"庞大"的依赖列表, 原因包括:

  • 它首先搜索库名, 因此使用 "regex" 作为名称会得到 libs/regex 目录中的所有内容以及依赖于它的所有内容. 这可能是一个很长的列表, 因为所有 regex 测试和示例程序都会被扫描依赖. 如果你想要更精简的列表, 请尝试使用你实际包含的头文件名, 或使用 --scan 选项扫描你的源码.
  • 如果你包含一个带有独立源码的库的头文件, 那么你会得到该库的源码及其所有依赖. 这是有意为之, 通常这些额外的依赖都是必需的.
  • 包含头文件时, bcp 并不知道你使用的是哪个编译器, 因此它会跟踪所有可能的预处理器路径. 如果你随应用程序分发 Boost 子集, 通常这正是你想要的结果.

上述最后一点会导致找到的头文件数量比大多数人的预期多得多. 例如, bcp 为 boost/shared_ptr.hpp 找到 274 个头文件依赖: 以报告模式运行 bcp 可以看出这些头文件为何都被发现为依赖:

  • Config 库的所有头文件都被包含进来 (52 个头文件, 若只针对一个编译器则约为 6 个).
  • 大量 MPL 和 type traits 代码包含针对有缺陷编译器的变通方案, 你可能需要也可能不需要. 追溯代码可以发现, 其中大多数并非必需, 除非用户定义了 BOOST_SP_USE_QUICK_ALLOCATOR; 但 bcp 无法知道该预处理器路径是否会被执行, 所以这些头文件被以防万一地包含进来. 这增加了约 48 个头文件 (type traits), 外加来自 MPL 的另外 49 个.
  • Preprocessor 库被 MPL 大量使用: 这又增加了 96 个头文件.
  • Shared Pointer 库包含大量平台特定代码, 分拆在大约 22 个头文件中: 通常你的编译器只需要其中少数几个文件.

如你所见, 发现的依赖数量远大于任何单个编译器实际使用的数量; 但如果你想分发一个可在任何配置、任何编译器、任何平台下都可用的 Boost 子集, 那这正是你需要的. 如果你想弄清楚你的特定编译器使用了哪些 Boost 头文件, 最好的办法是对代码进行预处理, 然后扫描输出中的 boost 头文件包含. 你应当意识到, 结果将高度依赖平台和编译器, 而且哪怕只是改一个编译器开关 (例如打开线程支持), 结果也可能缺少所需的全部头文件.
