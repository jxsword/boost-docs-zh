我的意思是, 为什么我需要这个半成品 property_tree 作为又一种数据结构? property_tree 本身什么也不支持, 它只是一种数据结构. 你有解析器可以从不同的来源生成 property tree. 但你同样可以生成 map 或其他东西. 下面举个例子, 为了“实现”与你的 property tree 类似的功能, 我需要做的只是: 

// Data structure itself
template<typename ValueType,typename KeyType>
struct Node;
template<typename ValueType,typename KeyType>
struct ptree_gen {
    typedef std::pair<KeyType,Node<ValueType,KeyType> > mi_value;
    typedef multi_index_container<mi_value, indexed_by<...> > type;
};
template<typename ValueType,typename KeyType>
struct Node {
    ValueType v;
    ptree_gen<ValueType,KeyType>::type children;
};
// serialization support
template<class Archive,typename ValueType,typename KeyType>
void serialize(Archive & ar, Node<ValueType,KeyType>& n,
               const unsigned int version)
{
    ar & n.v;
    ar & n.children;
}
// some access methods
template<typename ValueType,typename KeyType>
ValueType const&
get( string const& keys, ptree_gen<ValueType,KeyType>::type const& src )
{
    std::pait<string,string> sk = split( keys, "." );
    Node const& N = src.find( sk.first );
    return sk.second.empty() ? N.v : get( sk.second, N.children );
}

像这样使用它: 

ptree_gen<string,string>::type PT;
boost::archive::text_iarchive ia( std::ifstream ifs("filename") );
ia >> PT;
string value = get( "a.b.c.d", PT );

现在告诉我, property_tree 的接口何以更简单? 以及实现这种数据结构所需的 5 万行代码有什么价值.

Marcin

你刚才实现的只是一个精简的、骨架级的 property_tree 版本, 其中一个缺陷是无法生成人类可编辑的 XML 文件. 现在请加入更多接口 (也就是 get 函数) , 为序列化库加入更多档案类型, 加入定制能力, 加入从字符串到任意类型 (以及反向) 的透明转换. 花几个星期把所有边角情况都处理正确, 再花几个星期打磨接口中的粗糙之处. 然后编写测试, 编写文档. 到最后, 我相信你写出的代码不会比库中现有的代码少多少. 也许用 multi_index 代替手工索引能省下一些代码.

ptree 不使用 multi index 的原因是, 其实现早在考虑提交给 boost 之前就已经存在了, 可能在知道 multi index 存在之前就有了. 它运行良好. 后来, 在评审前的改进过程中, 我认真考虑过使用 multi-index, 但我决定不值得把一切推倒重来.

尽管 ptree 拥有大量修改树状态的函数接口, 但它采用“单一修改点”的方式. 每次插入最终都会经过同一个函数, 由它负责异常安全性并使索引与数据保持同步. erase 也是如此. 这个函数在插入的情况下只有 9 行代码, 巧的是 erase 也是 9 行. 使用 multi index 显然能把这些函数简化, 也许各减到 4 行. 净收益: 10 行代码 (而 ptree_implementation.hpp 有数百行) .

我知道在性能方面也有收益可图, 但那时我更专注于把接口做对.

使用 Boost.MultiIndex 的专用容器

引言

Boost.MultiIndex 允许在同一个元素集合上构建涉及两种或多种索引机制的复杂数据结构. 在 Boost.MultiIndex 可指定的无限多样的数据结构中, 有几种特定配置反复出现:

a. 双向映射 (bimap) 是由 pair<T,Q> 类型元素组成的容器, 对 T 和 Q 两个字段都提供快速查找; 相比之下, 常规的 STL map 只允许对 T 进行快速查找.

b. MRU (最近使用) 列表保存最近引用的 n 个元素: 当插入新条目且列表已达最大长度时, 最老的元素被擦除; 而如果试图插入一个已存在的元素, 该元素会被提升到第一位. MRU 列表可用于实现动态缓存, 以及带有“最近文件”菜单命令的程序所表现的那种行为, 例如.

尽管 Boost.MultiIndex 提供了构建这些常见结构的机制, 但与专注于此类特定结构的专用容器相比, 得到的接口可能繁琐且过于通用.

目标

编写一个由上述专用容器组成的库, 使用 Boost.MultiIndex 作为实现核心. 除了 bimap 和 MRU 列表之外, 学生也可以提议社区感兴趣的其他专用容器. 预期该库要达到 Boost 对最终纳入本项目所要求的质量标准, 这意味着要高度重视接口设计、文档和单元测试; 导师将指导学生完成从规范与需求收集到文档编写和实际编码的完整周期. 项目的最终成果必须包含:

a. 遵循 Boost 编程规范 的源代码.

b. 用户文档. 对格式的要求较为宽松, 不过 QuickBook 格式正在 Boost 内获得越来越多的认可.

c. 由 Boost Build System V2 驱动的完整单元测试集.

要求

a. 中高级 C++ 水平, 侧重泛型编程 (模板) .

b. 了解 STL 框架及其设计原则. 当然, 总体上了解 Boost、特别是了解 Boost.MultiIndex 是很大的加分项.

c. 熟悉至少两种不同的 C++ 编程环境.

d. 英语具备一定流利度; 不过后续对文档的评审可以帮助打磨这方面的粗糙之处.

e. 有数学天赋并且此前修过正式的算法课程会大有帮助.

f. 对极致质量工作的渴望.

学生的收益

承担本项目的学生将有机会在一家享有盛誉的 C++ 开源机构内学习软件生产的完整流程, 甚至最终看到自己的成果被纳入 Boost. 完成本项目涉及 C++ 接口设计和所谓现代 C++ 编程中的非平凡问题、高质量用户文档以及单元测试. 学生还将 (也许会令她惊讶地) 学到: 大部分时间将花在收集和尝试各种想法上, 总的来说是在思考, 而不是在编写实际代码.
