提示

最好先阅读最初的 Boost.Misc SoC 提案.

- The discussion starts with Joaquin trying to strip out the "misc" name out of the library -

Joaquin

细想之下, MISC 容器的统一原则也许有些误导: 当然所有 misc 在内部都使用多索引, 但这在外部接口上并没有太多体现 (不过这也理应如此) . 所以, 从用户的角度看, 各个 misc 完全是异构的兽类. 此外, 你的提案中没有任何一种对所有 misc 通用的全局设施. 那么, 何不放弃 misc 原则, 把每个容器当作独立的库来做呢? 那样你会有 boost::bimap、boost::mru 等, 并且没有它们的共同介绍. 这也打开了向这套组件添加其他不基于 B.MI 的容器的可能性. 你对此持什么立场? 你认为把 misc 在概念上保持在一起有价值吗?

Matias

正如最初的提案所述, 只有两个容器 (bimap 和 mru 集合) , 而且都以 B.MI 为基础, 所以把它们归到一起是很自然的. 当我写 SoC 提案时, 随着两个家族开始壮大, 我也有过类似的感受. 正如你所说, 唯一的共同点是它们的内部实现. 我稍微想过用一个更通用的框架来联合这两个家族 (以及其他内部相关的家族) , 最后想出的答案是: Boost.MultiIndex! 所以我认为试图统一这两个家族不是个好主意, 我投票赞成去掉 boost::misc::bimap 和 boost::misc::mru 中的 misc 部分. 不过, 对我的 SoC 申请来说, 把两个家族放进同一个项目似乎没问题, 因为尽管从外部看它们毫不相关, 我构建这些库要做的工作是一致的, 而且我编写 bimap 家族时学到的东西在我开始编写 mru 家族时也会派上用场. 等 mru 家族就位后, 我肯定还会学到其他可以用来改进 bimap 组的东西.

另一方面, 我认为至少在 B.MI 文档中链接一份文档对普通用户是有用的, 这份文档列举最常见的用例 (例如 bimap 和 mru 集合) , 并指出在哪里可以找到这些有用容器的干净实现. 眼下, 一个指向 boost::bimap 的链接和一个指向 boost::mru 的链接就足够了. 如果你想想这样一份文档的标题, 你很可能想出类似这样的名字: Common Multi Index Specialized Containers (常见的多索引专用容器) , 于是我们又回到了 misc 提案. 所以, 梳理一下思路:

- 将创建一个可以通过两个键访问的新容器家族. (boost::bimap)

- 一个新的时间感知容器家族将问世. (boost::mru)

- 可以在 B.MI 文档中添加一页, 标题为 misc, 链接到这些新库.

这对用户来说是一个更清晰的框架. 他们完全可以使用 mru 容器而根本不用听说 Boost.MultiIndex. B.MI 的用户也会看到他们的一些常用容器已经在其他库中以对 STL 友好的接口实现出来. 而且正如你所说, 这更具可扩展性, 因为它为 bimap 和 mru 家族使用 Boost.MultiIndex 之外的库打开了大门, 而不损害更广泛的 boost 框架. “misc”这个词将从 bimap 和 mru 的代码和文档中消失. 从现在起, 它的唯一用途就是标识我们的 SoC 项目. 我正在为 bimap 库想一个名字. Boost.BidirectionalMap 怎么样? 有什么想法吗?

Joaquin

是的, Boost.Bimap. 在我看来, bimap 在 Boost 社区甚至整个 C++ 社区都是一个广为人知的名字. 它听起来简洁, 也确实简短. 为什么不把自己正名为这个名字的拥有者呢?

- Then after a week of work -

Matias

现在 Boost.Bimap 逐渐成形, 我明白你跟我说过的了, 我们必须在库中提供 “one_to_many_map” 和 “multi_bimap”. 我目前正在编写的框架允许构造这类双向映射, 并且从用户角度来看容易理解.

Joaquin

好, 我很高兴我们在这一点上达成一致.

Matias

关于键访问名称的对称性, 我不得不承认下面这几对之间没有太大差别:

- to - from

- to - b

- 0 - 1

- left - right

在我看来这是品味问题, 但 left/right 听起来比其他几对更对称.

Joaquin

我非常喜欢 left/right 记法, 它非常容易记住, 而且比 to/from 对称得多.

Matias

起初我的想法是通过隐藏 B.MI 核心来获得易用性, 使其更符合 STL 直觉. 然而我意识到 B.MI 比我想象的要连贯和易用得多. 这让我重新思考这个问题. 在我现在正在编写的设计中, bimap is-a 一个用非常舒适的称为 bipair 的数据类型特化过的 multi_index_container, 通过 map 视图可以看到它所整合的两个 map 中的任意一个. 这种方案对用户有极大的好处:

- 如果用户已经了解 B.MI, 他就可以利用它提供而 STL 容器所没有的工具. 此外, 在某些情况下, 使用索引来查看数据会非常有用.

- 如果用户对 B.MI 一无所知但熟悉 STL 框架, 学习曲线就缩减为理解 bimap 的实例化以及如何得到所需的 map 视图.

另一个非常重要的好处依然成立: 为 B.MI 编写的所有算法都能继续用于 Boost.Bimap, 而且如果 B.MI 继续成长, bimap 会自动随之成长.

Joaquin

嗯……这是一个有趣的设计决定, 但在我看来有争议. 基本上你决定暴露 bimap 的实现; 正如你所说, 这有好处, 但也有一个不小的缺点: 一旦 你已将其文档化, 实现就再也无法更改了. 这是与 B.MI 的联姻, 没有离婚的可能. 另一种可能性——隐藏实现, 并把所提供的功能 (无论是显式地还是由于实现的相同特征而隐式地) 复制并编写文档——维护起来当然更重, 但它给了你一种自由度, 可以在需要时更改软件的内脏. 不要把这当作正面的反对意见, 但我认为这是一个相当重要的设计决定, 不仅在 bimap 的语境中, 在一般意义上也是如此.

Matias

你说得很对. 我想我们必须选择更艰难的道路, 向用户隐藏 B.MI 核心. 我正把 bimap 的第一稿连同一些文档发给你.

- This completes the second week, the documentation was basically the first section of this rationale -

Joaquin

我必须承认, 我开始喜欢我看到的东西了. 我天生是学数学的, 当我在一个表述中看到对称性时, 我相信它走对了路.

Matias

那么我们是两个天生学数学的人了.

Joaquin

我认为 std::set 理论那一部分非常清楚. 对我而言, 把 map 的秩 (值 X) 当作 std::set 来考虑有点奇怪, 但当然这个表述是自洽的.

Matias

我非常喜欢它. 起初可能有点奇怪, 但现在我已经习惯了, 用代码表达我对数据的约束非常容易, 而且我相信如果有人读代码时看到 bimap 的实例化, 他理解起来不会有问题. 如果我们使用你的记法 (ordered_nonunique、unordered_unique) , 也许更容易理解, 但这与我们的 STL 门面相悖. 在我看来, 来自 STL 的用户必须尽量少学新东西.

Joaquin

把关系看作 struct {left, right} 是干净而清晰的. 如果我理解得对, 一个关系拥有类型为 pair{first, second}, 这样理解对吗?

Matias

是的, 我相信用 left/right 记法表达对称性太棒了. 我相信人们会喜欢它的.

Joaquin

好, 完美. 我非常喜欢这一点:

- bm.left 与 std::map<A,B> 兼容

- bm.right 与 std::map<B,A> 兼容

- bm 与 std::set<relation<A,B>> 兼容

它优雅而对称. 我在这里感受到了良好的预兆.

Matias

太好了!

Joaquin

继续往下说, 对 N-1、N-N 和哈希索引的支持非常容易理解, 而且很好地融入了框架. 然而我还是没有完全理解 “set<relation> 约束”一节. 你会举一些例子来说明你所列举的不同情形的含义吗?

Matias -

是的, 我的意思是:

- 基于左侧

- 基于右侧

bimap 核心必须基于 multi index 的某个索引. 如果左侧索引是哈希类型, 那么实际上主视图将是一个 unordered_set< relation<A,B> >. 也许这不是用户想要的, 他可能想把主视图建立在右侧索引之上.

- set_of_relation

- multiset_of_relation

- unordered_set_of_relation

- unordered_multiset_of_relation

然而, 如果两者都是哈希索引, 用户可能希望主视图是有序的. 既然我们有一个 B.MI 核心, 这非常容易支持, 我们只需为其添加另一个索引.

Joaquin

我现在理解了. 好, 我不知道我们是否必须把它纳入第一版, 这将是一场功能雪崩!

Matias

添加这一功能不会影响用户, 因为默认情况下它将基于左侧索引, 这是非常自然的行为. 我不认为这是功能膨胀, 但我同意你的说法, 这是一场功能雪崩.

Joaquin

左侧和右侧集合类型与可能的主视图集合类型之间存在约束. 例如, 如果某个索引是唯一类型, 那么主视图就不能是 multiset_of_relation 类型. 反过来说, 如果主视图是 set_of_relation 类型, 那么左侧和右侧索引就不能是 multi_set 类型. 所有这个唯一性约束以及索引之间由此产生的相互作用问题, 是 B.MI 中比较微妙的主题之一.

Matias

这可以在编译期进行检查, 并作为编译期错误报告.

Joaquin

这可能挺有意思.

- And right when everything seems to be perfect... -

Joaquin

关于 mutant 我有一个更坏的消息, 它是一个非常精心设计且易于管理的类, 遗憾的是, C++ 几乎在任何情况下都不保证布局兼容. 例如, C++ 标准不保证类 struct{T1 a; T2 b;} 和 struct{T1 b; T2 a;} 是布局兼容的, 因此 reinterpret_cast 的技巧是一种未定义行为. 我同意你的看法, 在 100% 的情况下这个方案确实会奏效, 但标准就是标准. 你可以在标准中查看布局兼容这一主题 (http://www.kuzbass.ru/docs/isocpp/) . 如你所见, 标准有时是残酷的. 虽然 mutant 看起来像是没救了, 但请不要急着把它删掉. 我们再看看能为它做点什么.

Matias

我读了标准, 你是对的. Mutant 只是一个实现细节. 很遗憾, 因为我确信它在任何编译器上都会完美工作. 也许某天标准变得更严格, mutant 就能复活……到那时我们可以尝试围绕一个 relation<A,B> 写一个包装, 它带有名为 first 和 second 的两个引用, 分别绑定到 A 和 B, 或者 B 和 A. 

relation<TA,TB> r;
const_reference_pair<A,B> pba(r);
const_reference_pair<B,A> pbb(r);

用这种方式编写 relation 类并不困难, 但每次访问都会初始化两个引用, 而且在大多数编译器上, 使用 pba.first 会比 r.left 慢. 很难对这类引用进行优化.

Joaquin

这个变通方案行不通, 原因在于迭代器预期行为方面的技术问题. 如果 bm.left 的迭代器是双向类型, 那么标准规定解引用时必须返回 const value_type& 类型的对象. 你将不得不返回一个临时创建的 const_reference_pair, 这就无法返回引用.

Matias

我明白了……对此我也有一个变通方案, 但标准肯定又会来攻击我! 我们必须设法创建一个按我们的意愿响应的 relation 类, 其余的代码都将从这个点自然展开. relation 类与库其余部分之间的这种清晰分离, 将帮助我们分离问题并更好地解决它们.

Joaquin

什么变通方案? 已经勾起我的好奇心了, 我在这个主题上花了很长时间, 除了允许 relation 类占用更多内存之外, 我没有找到任何解决办法.

Matias

如果我们想让这个库真正有用, 就必须使 relation<A,B> 的大小等于 pair<A,B> 的大小. 我正要写下我的变通方案时, 意识到它行不通. 看看这个: http://www.boost.org/libs/iterator/doc/new-iter-concepts.html 基本上, 如果我们把迭代器建立在这个提案之上, 我们正在处理的问题就迎刃而解了. 现行的标准迫使双向迭代器同时也是输入和输出类型. 使用新概念, 把我们的迭代器做成“Readable Writable Swappable Bidirectional Traversal”没有任何妨碍. 这样一来 const_reference_pair 又变得有效了.

Joaquin

从某种意义上说这是正确的: 你只是声明你的迭代器不如 std::map 的强大. 这不是错误, 只是你没有解决问题, 而是坦白了它.

Matias

好吧, 但在我们这个特定的情形中: 提供 LValue 迭代器相对于 Read Write 迭代器有什么好处? 在我看来在这种情况下它并不更弱.

Joaquin

ReadWrite 的主要问题是下面这一点: value_type * p=&(*it); 会失败, 或者在 p 中存储一个临时地址. 这在现实生活中重要吗? 我不知道. 你存储 map 元素的地址有多频繁? 也许并不常见, 因为合乎逻辑的做法是存储迭代器而不是元素的地址. 让我们回顾一下我们的选项:

1. 我们使用 mutant, 明知它不合标准, 但当然它在 100% 的情况下都受支持.

2. 我们使用 const_reference_pair, 并声明迭代器不是 LValue 的.

3. 我们找到某个我们还不知道的技巧. 我一直在玩联合之类的花样, 运气不佳.

4. 我们利用“视图必须支持 first、second 记法”这一限制. 如果我们做出这个决定, 有几种可能:

a. 左 map 具有标准的 first/second 语义, 而右 map 具有相反的语义.

b. 我们不提供 first 和 second, 而是提供 first() 和 second(), 这样问题就变得微不足道了.

c. map 视图不支持 first/second, 而是像父关系那样支持 left/right

5. 我们用比 sizeof(pair<A,B>) 更多的内存来解决这个问题.

无论如何, 我要说唯一真正不可接受的选项是最后一个.

Matias

让我们看看.

1. 我要库带上“符合标准”的标签.

2. 这是自然的选择, 但明知存在另一个总是有效而且更高效的选项, 感觉很糟糕.

3. 我也试过玩联合, 问题是联合成员必须是 POD 类型.

4. 这个选项意味着库的重大损失.

5. 完全同意.

我想在这个清单上再增加一个选项. 利用元编程, relation 类检查编译器是否支持 mutant 习语. 如果支持, 就使用它, 获得零开销外加 LValue 迭代器; 如果不支持, 就使用 const_reference_pair, 以 ReadWrite 迭代器获得最小开销. 这可能引起争议, 但 mutant 提供的好处非常大, 而且说实话, 我不相信有任何现役编译器不支持这个习语. 这个方案可以完美贴合现行标准, 因为我们没有做任何假设. 这里唯一的缺点是: 尽管 mutant 方案允许制作 LValue 迭代器, 但在这两种情况下我们都必须把它们降级为 Read Write, 因为我们希望同一段代码能在任何符合标准的编译器上编译.

- Hopefully we find our way out of the problem -

Joaquin

换个话题, 我认为挂钩数据的一般概念是好的, 但我不喜欢你实现它的方式. 它必须易于迁移到 B.MI, 以预防 Boost.Bimap 变得不够用的情况. 对 B.MI 用户来说, 更自然的是不经由 .data 的间接来访问数据. 我不知道如何在你的框架中组织这一点.

Matias

用这种方式实现 data_hook 我有一个技术难题. 如果标准允许我们直接使用 mutant 习语, 我可以用多重继承来实现它. 但由于我们还必须使用 const_reference_pair, 这就变得不可能支持了. 这里有三个选项:

1) relation { left, right, data } 和 pair_view { first, second, data }

- 这在 bimap 框架内更直观, 因为它不像数据库中的表那样把数据与索引混在一起, 而是更侧重索引.

- 用户不必在数据类的每个成员上都写 mutable 关键字.

- 这与 B.MI 稍有偏离, 因为 B.MI 的模型类似于一张表, 但仍然存在一条清晰的迁移路径.

2) relation { left,right, d1,d2... dn } 和 pair_view { first, second, data }

- 迁移到 B.MI 的路径就是你提议的那样.

- 这非常不对称. 有必要解释视图的处理方式与 relation 不同.

- 用户必须在数据类中放置 mutable 关键字.

3) 只要 relation { left,right, d1,d2... dn }

- 迁移到 B.MI 的路径简单.

- 你无法从视图访问挂钩的数据.

我投票给第一个提案.

Joaquin

是的, 第一个选项给用户带来的意外最少. 我也投 1.

- The third week was over -

Matias

还有一个我必须解决的问题. 我需要知道是否有必要创建一个不关联任何东西的 map_view. 如果有必要, 有两个选项: 让它表现为一个空容器, 或者在使用它时抛出异常或断言失败. 如果没有必要, map_view 将保存一个引用而不是指针. 对我而言, map_view 必须始终在查看某个东西. 对于迭代器, 允许创建空的迭代器使它们易于在需要默认构造函数的上下文中使用, 比如作为容器的 value_type, 但我不认为 map_view 属于这种情况.

Joaquin

一个空的 map_view 有什么用处呢? 我的直觉与你相同: map_view 应当始终关联到某个东西. 如果我们想获得“已关联或未关联”的语义, 可以使用指向 map_view 的指针.

Matias

好, 那么你同意 map_view 保存引用而不是指针吗?

Joaquin

这取决于你想给 map_view 什么样的语义, 特别是 map_view 的拷贝语义. 

map_view x=...;
map_view y=...;
x=y;

最后这一行应该做什么?

1. x 的重绑定, 也就是说, x 指向与 y 相同的容器.

2. 底层容器的拷贝.

如果你想实现 1, 就不能在内部使用引用. 如果你想实现 2, 使用引用和指针几乎是一样的.

Matias

如果我要它们的行为与 std::maps 完全一样, 那我必须选 2. 但如果我把它们看作某个东西的“视图”, 我喜欢 1. 这个问题很复杂. 我再增加一个选项:

3. 错误: operator= 在 boost::bimap::map_view std_container 中被声明为 private
