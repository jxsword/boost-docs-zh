附加特性

N-1、N-N、哈希映射

这是设计中非常有趣的一点. 在 std::set 理论 中引入的框架允许以一种非常简单且概念化的方式来管理不同的约束. 它既容易记住又容易学会. 这里的想法是让用户直接指定每个键的集合类型. 为了实现这一特性, 我们必须解决两个问题:

  • multi_index_container 核心的索引类型现在取决于每个键所使用的集合类型.
  • map 视图现在会根据所选的集合类型改变其语义.

Boost.Bimap 在很大程度上依赖 Boost.MPL 来实现使这个框架得以工作所需的全部元编程. 默认情况下, 如果用户没有指定集合的类型, 将使用 std::set 类型.

关系的集合类型约束

bimap 集合视图的约束是另一个非常重要的特性. 一般来说, Boost.Bimap 用户会基于其两个键的集合类型之一来确定集合视图类型. 然而, 为这个集合指定其他约束, 或者只是以不同的方式排序, 可能也是有用的. 默认情况下, Boost.Bimap 将关系的集合类型建立在左侧集合类型之上, 但用户可以在以下选项之间选择:

  • left_based
  • right_based
  • set_of_relation<>
  • multiset_of_relation<>
  • unordered_set_of_relation<>
  • unordered_multiset_of_relation<>
  • list_of
  • vector_of

在前两种情况下, multi_index_core 中只有两个索引, 因此这些是首选选项. 必要时, 实现会使用进一步的元编程来定义一个新索引.

标签

使用标签而不是 member_at::side 习语的想法非常有吸引力, 因为使用它的代码更具可读性. 唯一的代价是编译时间. boost/bimap/tagged 是一种非侵入式标签习语的实现. relation 类的构建方式使得即使用户使用标签, member_at::side 习语也继续有效. 这很好, 因为用户甚至可以在算法编码完成之前就开始加标签, 而未加标签的代码仍能继续工作. 当引入用户自定义标签时, 开发会变得稍微复杂一些, 但 tagged 习语中定义的许多顺手的元函数有助于让事情保持足够简单.
