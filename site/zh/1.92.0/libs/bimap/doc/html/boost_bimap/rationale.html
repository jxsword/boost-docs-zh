总体设计

最初的解释只包含少量特性. 本节旨在描述库的总体设计, 不涉及那些较不重要的特性的细节; 这些特性将在后面介绍.

库的设计分为两部分. 第一部分是构造一个 relation 类. 这将是由 multi_index_container 核心存储和管理的对象. 我们的想法是让这个类尽可能易于使用, 同时在内存和访问时间方面保持高效. 这是 Boost.Bimap 设计中的一块基石, 而且正如你在本设计理由中将看到的, 设计的其余部分就水到渠成了.

relation 类需要以下接口:

typedef -unspecified- TA; typedef -unspecified- TB;

TA a, ai; TB b, bi;

typedef relation< TA, TB > rel;
STATIC_ASSERT( is_same< rel::left_type , TA >::value );
STATIC_ASSERT( is_same< rel::right_type, TB >::value );

rel r(ai,bi);
assert( r.left == ai && r.right == bi );

r.left  = a; r.right = b;
assert( r.left  == a && r.right == b );

typedef pair_type_by< member_at::left , rel >::type pba_type;
STATIC_ASSERT( is_same< pba_type::first_type , TA >::value );
STATIC_ASSERT( is_same< pba_type::second_type, TB >::value );

typedef pair_type_by< member_at::right, rel >::type pbb_type;
STATIC_ASSERT( is_same< pbb_type::first_type , TB >::value );
STATIC_ASSERT( is_same< pbb_type::second_type, TA >::value );

pba_type pba = pair_by< member_at::left  >(r);
assert( pba.first == r.left  && pba.second == r.right );

pbb_type pbb = pair_by< member_at::right >(r);
assert( pbb.first == r.right && pbb.second == r.left  );

虽然这看起来很直接, 但正如稍后将看到的, 这是本库中最难啃的代码. 如果我们放松一些效率约束, 它确实非常容易. 例如, 如果我们允许一个关系的大小大于其各组成部分大小之和, 那就是显而易见的. 如果访问速度不重要, 也同样简单. 然而, 关于 Boost.Bimap 做出的最初决定之一却是: 为了有用, 它必须相对于被包装的 Boost.MultiIndex 容器实现零开销. 最后, 还有另一个可以放松的约束: 符合 C++ 标准, 但这是完全不可接受的. 现在让我们假设我们已经编写了这个类, 并且它符合要求.

第二部分基于这个 relation 类. 现在我们可以用三种方式中的任意一种来查看数据: pair<A,B>、relation<A,B> 和 pair<B,A>. 假设我们的 bimap 只支持一对一关系. (其他关系类型在本设计中被视为附加特性. ) 提议的接口非常简单, 并且在很大程度上基于 STL 的概念. 给定一个 bimap<A,B> bm:

  1. bm.left 与一个 std::map<A,B> 签名兼容
  2. bm.right 与一个 std::map<B,A> 签名兼容
  3. bm 与一个 std::set<relation<A,B> > 签名兼容

这个接口对于有 STL 背景的用户来说很容易学会, 既简单又强大. 这就是总体设计.

关系的实现

本节解释relation 类的具体实现细节.

我们能想象到的第一件事就是使用一个 union. 遗憾的是, 当前的 C++ 标准只允许 POD 类型的联合. 对于视图, 我们可以尝试围绕一个 relation<A,B> 写一个包装, 它带有名为 first 和 second 的两个引用, 分别绑定到 A 和 B, 或者绑定到 B 和 A.

relation<TA,TB> r;

const_reference_pair<A,B> pba(r);
const_reference_pair<B,A> pbb(r);

用它来编写 relation 类并不困难, 但每次访问都会初始化两个引用, 而且在大多数编译器上, 使用 pba.first 会比直接使用 r.left 更慢. 这种方案还有另一个隐藏的缺点: 它对迭代器不友好, 因为 map 视图的迭代器必须降级为 读写 而不是 LValue. 这一点稍后解释.

起初, 这似乎是我们在当前 C++ 标准下所能做到的最好方案. 然而, 这个问题存在一种解决方案, 它不太符合 C++ 标准, 但在访问时间和内存方面确实实现了零开销, 并且还允许将视图迭代器重新升级为 LValue.

为了使用它, 编译器必须符合一条布局兼容性条款, 该条款目前不在标准中, 但非常自然. 这条附加条款规定, 如果我们有两个类:

struct class_a_b
{
    Type1 name_a;
    Type2 name_b;
};

struct class_b_a
{
    Type1 name_b;
    Type2 name_a;
};

那么 class_a_b 的存储布局与 class_b_a 的存储布局相同. 如果你惊讶于这在符合标准的 C++ 编译器上并不成立, 欢迎加入俱乐部. 从编译器厂商的角度来看, 这是实现它的自然方式, 并且对开发者非常有用. 也许某天它会被纳入标准. 当前的每一个编译器都符合这一点.

如果我们能够指望这一点, 那么我们就可以实现一种称为 mutant 的习语. 这个想法是围绕 reinterpret_cast 提供一个安全的包装. 一个类可以声明它可以用与它存储兼容的不同视图类来查看. 然后我们使用自由函数 mutate<view>(mutant) 来获取视图. mutate 函数在编译期检查所请求的视图是否已在 mutant 视图列表中声明. 我们实现一个名为 structured_pair 的类, 它与某个 std::pair 签名兼容, 而存储布局由第三个模板参数配置. 这个模板类的两个实例将提供这个关系的视图.

问题在于, 如果我们想符合标准, 就不能使用这种方法. 明知它能在每个编译器上工作、远优于其他备选方案却不能用, 实在令人恼火. 所以——这是一个重要的决定——我们必须找到一种既能使用它、又能让库符合标准的方法.

这个想法非常简单. 我们把两种方案都写出来: 基于 const_reference_pair 的和基于 mutant 的, 并在编译器符合我们新的布局兼容条款时使用 mutant 方案. 如果编译器真的把事情搞砸了, 我们就稍微降低 bimap 的性能. 这里唯一的缺点是, 虽然 mutant 方案允许制作 LValue 迭代器, 但在这两种情况下我们都必须把它们降级为 读写, 因为我们要求同一段代码能被任何符合标准的编译器编译.

注释

在所有受支持的编译器上测试这种方法表明, mutant 习语总是受支持. 严格符合标准的版本因为从未被使用而从代码中移除了.

Bimap 的实现

bimap 的核心显然将是一个 multi_index_container. 实现 bimap 类的基本思路是使用 iterator_adaptor 将 Boost.MultiIndex 的迭代器转换为 std::map 和 std::set 的行为. map_view 和 set_view 可以直接用这些新的转换后迭代器以及围绕核心容器每个索引的一个包装来实现. 然而, 这里隐藏着一种习语, 一旦编写出来, 对本库的其他部分以及 Boost.MRU 库都会非常有用. 借鉴 iterator_adaptor 的思想, Boost.Bimap 的视图用 container_adaptor 来实现. 有几个模板类 (例如 map_adaptor 和 set_adaptor) 接受一个与 std::map 签名兼容的类以及新的迭代器, 并对容器进行适配, 让它改用这些新迭代器而不是原来的迭代器. 例如, 如果你有一个 std::set<int*>, 你就可以构建另一个行为与 std::set<int> 完全相同的容器, 方法是使用 set_adaptor 和 iterator_adaptor. 这两种工具的组合使用非常强大. container_adaptor 可以接受不完全满足被适配容器全部要求的类. 新容器必须定义这些缺失的函数.
