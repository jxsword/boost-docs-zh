1.

这真的有必要吗? 如果我以必要的细心和能力编写程序, 引言中指出的问题将永远不会出现. 如果出现了, 应该 "从源头" 修正, 而不是用 "创可贴" 来掩盖不良实践.

这个问题刚被提出时让我惊讶. 但我收到的一些反馈让我认为这是一种普遍看法. 最好的答案是考虑本库文档的 教程与动机示例 一节中的示例. 我相信它们令人信服地表明, 任何不使用本库的程序都必须被假定包含算术错误.

2.

safe 类型可以用作内建类型的直接替代品吗?

几乎可以. 把所有内建类型替换为其 safe 对应类型, 应该能得到按预期编译和运行的程序. 偶尔会出现编译期错误, 需要调整源代码. 通常这会产生更正确的代码.

3.

为什么要有诸如 safe_signed_literal<42> 这样的字面量专用类型? 为什么不直接使用 std::integral_const<int, 42>?

通过定义我们自己的 "特殊" 类型可以简化接口. 使用 std::integral_const 需要同时指定类型 和 值. 使用 safe_signed_literal<42> 则不需要类型参数. 因此库可以选择容纳指定值的最佳类型. 这也意味着不会有机会指定不一致的类型-值对.

4.

为什么根本需要 safe...literal? const safe<int>(42) 有什么问题?

const safe<int>(42) 看起来可能正是我们想要的: 一个不可变的值, 在表达式中使用时调用 "safe" 运算符. 但有一个问题. std::numeric_limits<safe<int>> 的范围是从 INTMIN 到 INTMAX, 即使该值在编译期固定为 42. 编译期正是用这个范围来计算运算结果的范围.

因此执行运算时, 结果的范围是根据 [INTMIN, INTMAX] 而不是 [42,42] 计算的.

5.

safe 类型运算是 constexpr 吗? 也就是说, 可以在编译期调用吗?

是的. safe 类型的构造和计算都是 constexpr . 注意, 要获得最大收益, 你必须使用 safe...literal 在编译期指定原始值.

6.

为什么要定义 safe_literal ? 它实际上不是与 std::integral_constant

几乎相同, 但仍有充分理由创建不同的类型.

  • std::integral_constant<int, 42> 需要同时指定类型和值, 所以它不如 safe_signed_literal 方便, 后者映射到容纳该值所需的最小类型.

  • std::numeric_limits<std::integral_constant<int, 42>>::is_integer 返回 false . 这会使本库的实现复杂化

  • 类型特征 is_safe<std::integral_constant<int, 42>> 必须定义为返回 true.

  • 但在全局修改 std::integral_constant 的特征可能会产生与其它代码相关的意外副作用. 这些很可能成为难以发现、难以绕开的错误.

7.

为什么不使用 Boost.Convert?

我无法从文档弄清楚如何使用它.

8.

为什么库命名为 "safe ..." 而不是 "checked ..." 之类的名字?

我使用 "safe" 很大程度上是因为其他类似库也这样用. 也许更好的词是 "correct", 但那会引发类似的疑虑. 我不打算改变这一点. 我已尽力在文档中阐明本库所解决的问题是什么.

9.

既然库叫 "numerics", 为什么不处理浮点算术?

实际上, 我认为这可以/应该应用于任何满足文档中定义的类型要求 Numeric 的类型 T. 因此应该有特化 safe<float> 及相关类型, 以及诸如 safe<fixed_decimal> 等新类型. 但本库当前版本只处理整数类型. 希望本库能演进到符合其名称所暗示的承诺.

10.

在任何潜在未定义行为之前放置防御性检查难道不常被视为不良实践吗?

由谁? 让能产生不正确结果的代码留着更好吗? 注意, 文档引用了多个正好推荐用这种方法来缓解这种 C/C++ 行为所造成问题的来源. 参见 [Seacord]

11.

看起来实现假定硬件层采用二进制补码算术. 所以本库不可移植 - 对吗? 其他硬件架构怎么办?

就撰写本文时所知, 本库并不假定底层硬件是二进制补码. 不过, 这尚未以任何严格的方式得到验证.

12.

根据 C/C++ 标准, unsigned integers 不会溢出 - 它们是会 "回绕" 的模整数. 但 safe numerics 库却检测并拦截这种行为视为错误. 为什么?

本库的指导目的是捕获不正确的算术行为 - 而不仅是未定义行为. 尽管精明的用户可能理解并牢记无符号整数实际上是模类型, 但算术表达式的直观解读传达的观念是所有操作数都是普通整数. 而且在许多情况下, unsigned integers 被用于并非有意进行模运算的场景, 例如数组索引. 最后, 此类整数的模随机器架构而异. 出于这些原因, 在本库的语境中, unsigned integer 被视为整数子集的一种表示. 注意, 这一决定与 CERT C 安全编码标准中的 [INT30-C] "确保无符号整数运算不回绕" 一致 [Seacord].

13.

为什么本库要求 C++14?

本库最初版本使用 C++11. 来自 CPPCon、Boost Library Incubator 和 Boost 开发者邮件列表的反馈让我确信, 必须更加严肃地对待运行期开销问题. 我决心消除或最小化它. 这带来了更精细的元编程. 但这还不够. 显然, 真正最小化运行期开销的唯一方法是实现编译期整数范围算术 - 一个相当精细的子库. 通过在编译期做范围算术, 我可以对许多/大多数整数运算跳过运行期检查. 虽然 C++11 的 constexpr 能力还不足以完成这项工作, 但 C++14 的 constexpr 可以. 本库目前非常依赖 C++14 的 constexpr . 我认为深入钻研本库的人会对以下程度感到非常惊讶: 用户代码的微小改动就能产生零运行期开销且保证正确的整数代码.

14.

这是一个 C++ 库 - 但你提到 C/C++. 到底是哪个?

C++ 已经远超最初的 C 语言. 但 C++ 仍 (在大多数情况下) 与 C 兼容. 因此大多数 C 程序都可以用 C++ 编译器编译. 不正确算术的问题同时困扰 C 和 C++. 假设我们有一个为某嵌入式系统设计的遗留 C 程序.

  • 把所有 int 声明替换为 int16_t , 并把所有 long 声明替换为 int32_t .

  • 创建一个包含类似以下内容的文件, 并在每个源文件的开头包含它.

    #ifdef TEST
// using C++ on test platform
#include  <cstdint>
#include <boost/numeric/safe_numerics/safe_integer.hpp>
#include <cpp.hpp>
using pic16_promotion = boost::numeric::cpp<
    8,  // char
    8,  // short
    8,  // int
    16, // long
    32  // long long
>;
// define safe types used in the desktop version of the program.
template <typename T> // T is char, int, etc data type
using safe_t = boost::numeric::safe<
    T,
    pic16_promotion,
    boost::numeric::default_exception_policy // use for compiling and running tests
>;
typedef safe_t<std::int_least16_t> int16_t;
typedef safe_t<std::int_least32_t> int32_t;
#else
/* using C on embedded platform */
typedef int int_least16_t;
typedef long int_least16_t;
#endif

  • 在桌面上用 C++14 编译器编译测试, 并定义宏 TEST.

  • 运行测试, 并修改代码以处理抛出的任何异常.

  • 在宏 TEST 未定义的情况下为目标 C 平台编译.

此示例说明了用 C++14 实现的本库如何有助于为 C 语言编写的程序开发正确的代码.

15.

某些编译器 (包括 gcc 和 clang) 提供用于受检加法、乘法等的内建函数. 本库使用这些内建函数吗?

不. 我尝试过使用它们, 但它们目前不是 constexpr . 因此若不破坏 safe numerics 原语的 constexpr 兼容性, 就无法使用它们.

16.

某些编译器 (包括 gcc 和 clang) 提供用于检测常量的内建函数. 这似乎很有吸引力, 可以消除对 safe_literal 类型的需求. 遗憾的是, 这些内建函数被定义为宏. 通过函数传入 safe numerics 库的常量无法被检测为常量. 因此, 通过把更多操作移到编译期来使本库更高效的机会并不存在 - 与我的希望和预期相反.
