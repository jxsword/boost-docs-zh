设计目标

四个准则塑造了 Boost.Iostreams 的设计:

  1. 简单性: 库应易于学习、使用和扩展.
  2. 灵活性: 库应足够灵活, 能够生成具有几乎任意所需特性的流和流缓冲.
  3. 效率: 在大多数情况下, 使用该库生成的流和流缓冲应与手写组件一样高效.
  4. 互操作性: 库应能轻松融入 C++ 标准库的框架. 特别是,
    1. 用于构造流和流缓冲的组件 — Source、汇、InputFilter 与 OutputFilter — 不应要求比标准库流和流缓冲更丰富的接口.
    2. 使用该库构造的流和流缓冲不应要求比标准库流和流缓冲更丰富的接口.

本质上, 4a 表示凡可用源和汇之处都应能使用标准库流和流缓冲, 而 4b 表示凡可用标准库流和流缓冲之处都应能使用 (本库的) 流和流缓冲. 两条准则都旨在让 Boost.Iostreams 易于集成到现有代码中.

简单性

许多用户反映本库易于学习和使用, 事实证明它也相对易于扩展. 不过, 对灵活性和效率的需求使设计变得复杂. 一个很好的例子是表示流和流缓冲全部范围所需的数量庞大的 模式. 另一个例子是: 需要优化对表示内存中字符序列的 设备 (例如 内存映射文件) 的处理; 这导致引入了 Direct 设备, 它们比其他设备更难使用一些.

灵活性

尽管 Boost.Iostreams 极其灵活, 但它有一些局限. 例如, 无法自定义 stream_buffer 所用的缓冲策略: 用户要么选择默认缓冲策略, 要么请求无缓冲 I/O. 让用户完全控制缓冲策略会大幅复杂化库的接口和实现.

效率

初步测量表明, 使用 Boost.Iostreams 构建的流和流缓冲的性能与手写组件相当. 进一步的测量 — 以及对库实现的相应调整 — 有待建立一整套全面的基准测试.

互操作性

目前, 凡允许使用设备之处都可以使用标准库流和流缓冲; 但随着对 异步与非阻塞 I/O 支持的增多, 这一点将会改变, 因为流和流缓冲无法区分满足读或写请求的暂时失败与永久失败. 此外, 使用 Boost.Iostreams 定义的流和流缓冲可在需要标准库流或流缓冲之处使用, 但前提是流或流缓冲已被正确初始化. 例如, filtering_stream 的用户必须先将一系列过滤器和设备推入底层 过滤链, 然后 filtering_stream 才能被现有代码使用. 不过这一局限无法避免, 因为所有流和流缓冲都需要一些专门的初始化, 包括 std::fstream 与 std::stringstream.

设计决策

泛型设计

泛型设计的好处众所周知. 例如,

  • 现有组件 — 例如流、流缓冲和迭代器 — 可以轻松集成到库中.
  • 库可以轻松扩展以处理新的过滤器和设备概念.
  • 库的内部 — 例如将 过滤链 实现为流缓冲列表 — 可以重新设计而不影响用户代码.

泛型设计的一个典型好处在本例中可以忽略: 当虚函数调用被内联代码取代时带来的性能提升. 因为 std::basic_streambuf 使用虚函数作为定制点, 库无法合理期望消除虚函数调用. 不过, 这些调用的开销在很大程度上被缓冲所缓解.

模式

支持的 模式 数量大大增加了库的复杂性. 遗憾的是, 为满足灵活性准则, 所有模式似乎都是必要的. 此处的示例表明, 除一种模式外, 其余模式都有重要用例. 例外是 双向可寻位; 不过, 一旦实现了其他模式, 这种模式基本上是免费的.

I/O 库往往以以下两种方式之一处理这种情况:

  • 它们只支持 input 与 output, 或者
  • 它们支持额外的模式, 但允许不同模式的组件自由混合. 为避免运行期故障, 用户必须研读各组件的文档, 以确定它们是否兼容.

第二种选择显然不可接受. 第一种选择因其简单而有吸引力, 但遗漏了关键用例. Boost.Iostreams 试图两全其美: 建议新用户忽略 input 与 output 之外的所有模式.

生命期管理

过滤器 和 设备 必须要么满足 CopyConstructible, 要么使用 boost::ref 传递给流和流缓冲. 这一要求会使过滤器和设备的设计复杂化, 因为某些原本可以不可复制的组件必须使用引用计数. 模板 basic_file 就是一个很好的例证. Boost.Iostreams 的一个预发布版本允许将动态分配的过滤器和设备以指针形式传递给流和流缓冲, 并可由用户选择让 Iostreams 库取得其所有权. 这一设计因两个原因被否决: 它不是异常安全的, 且它需要一个额外的函数参数来指示对象是否要归库所有.

链接口

Boost.Iostreams 的某些预发布版本为 过滤链 提供了丰富的接口, 允许链在任意位置断开和重新连接, 与 std::list 十分类似. 为使库更易学习, 这一功能已被移除; 如果用户发现需要它, 可以轻松恢复.

异步与非阻塞 I/O

Boost.Iostreams 提供的 Filter 概念经过设计, 以适应 异步与非阻塞 I/O. 设备 概念可以适应非阻塞 I/O, 但对异步 I/O 的支持将需要引入新的设备概念. 添加这一有限的支持是为了向前兼容: 当引入更多概念和组件时, 用户不应需要重新设计其现有组件. 此外, 如果异步与非阻塞 I/O 最终被证明不够有用, 可以移除库的内部支持而不影响现有接口.
