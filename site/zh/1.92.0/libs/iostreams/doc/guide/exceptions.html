标准 Iostreams 库

public 成员函数 — std::basic_streambuf 中执行 I/O 的那些 — 即 sgetn()、sputn()、pubsync(), etc. — 是使用 protected virtual 接口实现的, 该接口属于 std::basic_streambuf — 即 underflow()、overflow()、sync()、等. 这些 protected virtual 函数中的大多数允许通过抛出异常或返回错误指示符 (通常是 traits_type::eof()) 来报告失败. 抛出的所有异常都会由 public 成员函数传播, 因此原始流缓冲的用户原则上必须准备好处理异常. 不过, 大多数标准库实现自带的流缓冲并不抛出异常.

相比之下, 标准流默认不抛出异常: 用户必须设置异常掩码, 才能请求使用异常报告异常状况. 若流的异常掩码中设置了 ios_base::badbit, 则底层流缓冲抛出的所有异常都会被捕获并重新抛出.

因此, 对于流, 用户可以选择是否启用异常; 对于流缓冲, 实现者有选择权, 而用户没有.

Boost Iostreams 库

策略

Boost Iostreams 库中的基本流缓冲模板 stream_buffer 实现了 protected virtual (std::basic_streambuf 的成员函数), 方式是委托给 I/O 函数 read、write、put、get、等, 而这些函数又委托给过滤器和设备的成员函数. 这些成员函数抛出异常来报告错误. 异常由 protected virtual — stream_buffer 的成员 — 以及 std::basic_streambuf 的公有成员传播.

建议用户定义的过滤器和设备抛出的所有异常都派生自 std::ios_base::failure.[1]

设计理由

另一种可能的表述是: 要求返回类型为 std::streamsize 的过滤器和设备成员函数返回 -1 以指示错误, 并修改返回 void 的函数的规范, 使其返回表示成功的 bool. 决定依靠异常报告错误, 是为了让实现者能够传达关于错误原因的额外信息, 并让他们不必记住哪些返回值被指定为错误指示符.

第三种可能是仿照 std::basic_streambuf 的做法, 允许过滤器和设备的成员函数通过抛出异常或返回指定的错误指示符来报告错误. 这一方案被否决, 因为它会复杂化各种 Filter 与 Device 概念的规范, 并使 stream_buffer 的内部更难理解和维护.[2]

异常安全

Iostreams 库旨在在 I/O 操作期间抛出异常时提供以下保证:
  1. 酌情通过调用析构函数或 close 来释放资源.
  2. C++ 标准库为流和流缓冲规定的不变式得到维持. 允许尝试执行更多 I/O, 但可能引发更多异常.
  3. Boost Iostreams 库为流和流缓冲规定的不变式得到维持. 具体而言,
    1. 可以关闭并重新打开 stream_buffer 或 stream, 以使用底层 过滤器 或 设备 类型的新实例执行更多 I/O.
    2. filtering_streambuf 或 filtering_stream 的过滤器和设备链处于一致状态. 如果从链中移除当前设备并添加新设备, 用户即可像流或流缓冲是新构造的那样执行 I/O.

条件 2. 与 3. 依赖于 Filter 与 Device 概念的规范. 注意, 并不保证流或流缓冲的字符序列处于一致状态, 即数据未被破坏, 而且一般无法在异常发生后确定这些序列的状态.

这些条件等同于通常所说的异常安全的基本保证 (参见 [Abrahams1].)

致谢

感谢 Angelika Langer 与 John Torjo 就异常问题进行的讨论.

[1]C++ 标准将 std::ios_base::failure 描述为"Iostreams 库中的函数在流缓冲操作期间检测到错误时抛出的所有异常对象类型"的基类 ([ISO], 27.4.2.1.1 节). 对于这是否意味着流缓冲成员函数抛出的所有异常都必须是 failure 类型, 各家解说存在分歧.

一本关于 C++ iostreams 的权威著作将标准中的措辞解读为: 异常"可以是任何类型", 但"如果异常是由任何 IOStreams 操作发现的错误情形引发的, 则其类型为 failure" ([Langer], p. 36, 着重号为引者所加). 例如, 该书作者指出, 在缓冲区分配期间产生的 std::bad_alloc 无需捕获后再以 failure 重新抛出.

然而, 另一本权威著作认为所有异常都必须派生自 failure. ([Josuttis1], p. 602.)

Iostreams 库在此问题上持中立立场: 库内部抛出的所有异常都是 failure 类型或其派生类, 但用户自定义类型抛出的异常会原样传播.

[2]正如 Herb Sutter 所写: "允许一个操作以两种不同方式报告同一错误始终是糟糕的设计……它使接口和语义变得复杂, 也让调用者更难堪, 因为调用者必须能够处理两种风格的错误报告." ([Sutter], p. 130.)
