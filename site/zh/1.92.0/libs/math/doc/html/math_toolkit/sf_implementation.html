补充实现说明

大多数实现说明包含在每个函数或分布的文档中. 这里的说明更具一般性, 更多地反映了所采用的总体实现理念.

实现理念

"先求正确, 再求快速."

在速度与精度之间总有可能需要权衡. 或许可以找到更快的方法, 特别是针对某些受限的参数范围; 但对于数学函数和分布的大多数应用, 我们判断速度很少像精度那样重要.

因此我们把精度放在首位.

为了能够评估特殊函数的精度, 生成极其精确的测试值表投入了相当多的精力.

(这也需要大量 CPU 算力, JM 的笔记本电脑底部一度有滴落熔化塑料的危险, 于是改用 PAB 的双核台式机, 让它保持 50% 的占用率连转 数天 来计算部分测试值表!)

对于特定的 RealType (比如 float 或 double), 或许能为某些函数找到更简单因而更快的近似, 但精度较低 (例如在计算反函数时, 可能因为没有精化迭代).

如果这些近似被证明足够精确, 达到"符合其目的"的程度, 用户就可以替换为自己的定制特化.

例如, 有一些近似可以追溯到计算代价 高昂得多 的年代:

H Goldberg and H Levine, t 与卡方的百分点及正规化近似公式, Ann. Math. Stat., 17(4), 216 - 225 (Dec 1946).

A H Carter, Approximations to percentage points of the z-distribution, Biometrika 34(2), 352 - 358 (Dec 1947).

对于某些对速度敏感的应用, 它们仍可提供足够的精度.

测试值的精度与表示

为了让常量值对尽可能多的实数类型足够精确, 在可获得的范围内它们被给出 50 位十进制数字 (尽管许多来源经证明只在接近 64 位 double 精度处是精确的). 数值通过追加 L 指定为 long double 类型, 除非它们可以被精确表示, 例如整数, 或像 0.125 这样的二进制分数. 这避免了从默认类型 double 转换时丢失精度的风险. 数值在 static_cast<RealType>(1.2345L) 之后使用, 为抽点测试提供相应的 RealType.

返回常量值的函数 (例如峰度) 写作

static_cast<RealType>(-3) / 5;

以提供编译器能为该实数类型计算出的最精确值. (分母是整数, 因此会被精确提升).

因此, 对三分之一这样的数 (用基数为 2 的浮点数 无法 精确表示) 的测试应当 (例如) 使用:

static_cast<RealType>(1) / 3;

如果函数对输入的变化非常敏感, 指定一个不精确的值作为输入 (比如 0.1) 可能使结果产生明显偏差: 例如 0.1f 会"错"约 1e-7 (因为 0.1 没有精确的二进制表示). 这就是为什么测试代码中使用精确的二进制值 (二分之一、四分之一、八分之一等), 偶尔配合形如 a/b 的分数, 其中 b 是 2 的幂 (以确保结果是可精确表示的二进制值).

测试的容差

容差需要设置为以下各项的最大值:

  • 某个 epsilon 值.
  • 数据的精度 (通常只接近 64 位 double).

否则, 当 long double 的位数多于测试数据时, 无论怎样调整基于 epsilon 的容差都无济于事.

一个常见问题是: 容差适用于 Microsoft VS.NET 这类 double 与 long double 大小相同的实现, 但在 long double 比 double 更精确的其他系统上测试会失败. 请先检查后缀 L 是否存在, 然后检查容差是否足够大.

处理不合适的参数

在 J. Marraffino 和 M. Paterno 的 Errors in Mathematical Special Functions 中, 作者提议: 当参数会导致数学上未定义的结果时, 必须发出定义域错误信号.

  • 准则 1

如果当 x = (x1, x2, . . .) '从所有方向逼近 a' 时各极限一致, 则称数学函数在点 a = (a1, a2, . . .) 处有定义. 该定义值可以是任何数, 也可以是 +infinity 或 -infinity.

粗略地说, 如果函数趋于 +infinity, 然后又从'背后'以 -infinity 出现, 那么它是没有定义的.

逼近某个数学函数的库函数, 凡在数学函数未定义的参数值处求值, 都应当发出定义域错误信号.

  • 准则 2

逼近某个数学函数的库函数, 凡在数学函数取得非实数值的参数值处求值, 都应当发出定义域错误信号.

本实现被认为遵循了这些提议, 并且有助于与 ISO/IEC 9899:1999 Programming languages - C 以及 Draft Technical Report on C++ Library Extensions, 2005-06-24, section 5.2.1, paragraph 5 保持兼容. 另参见 domain_error.

参见 policy reference 了解错误处理策略的细节, 它们应能让用户遵循上述任一建议以及其他行为.

机制的详细说明参见 error handling, 示例参见 error_handling example 和 error_handling_example.cpp

注意

如果你启用了抛出却没有 try & catch 块, 程序将因未捕获的异常而终止并很可能中止. 因此, 为了获得有益的错误信息, 建议所有应用程序启用 全部 异常 并 使用 try&catch. 不过为了简单起见, 大多数示例并未这样做.

对数学上未定义的函数的处理

数学上未定义的函数 (如柯西分布的均值) 默认无法通过编译. policy 允许对此进行控制.

如果策略允许未定义的函数, 那么调用它们默认会抛出定义域错误. 但错误策略可以设置为不抛出, 而是返回 NaN. 例如,

#define BOOST_MATH_DOMAIN_ERROR_POLICY ignore_error

出现在第一个 Boost include 之前, 那么调用未实现的函数时, mean(cauchy<>()) 将返回 std::numeric_limits<T>::quiet_NaN().

警告

如果 std::numeric_limits<T>::has_quiet_NaN 为 false (例如, T 是不支持 NaN 的用户自定义类型), 那么发生定义域错误时将总是抛出异常. 因此强烈建议捕获异常.

分布的中位数

有许多分布我们一直无法找到解析公式, 这让我们迟迟没有实现 median functions, 即一列值的中点.

不过, 正如通常那样, 分布 dist 有一个有用的数值近似, 以访问器非成员函数 median 的形式提供, 使用 median(dist), 它可以 (在缺少解析公式的情况下) 通过调用下式求值

quantile(dist, 0.5) (这当然是 数学 定义).

Mean, Median, and Skew, Paul T von Hippel

Descriptive Statistics,

与

Mathematica Basic Statistics. 提供了更多细节, 尤其是针对离散分布.

对浮点无穷大的处理

有些函数和分布在以 +infinity 或 -infinity 作为参数时是有良好定义的, 但在尝试把无穷参数作为特殊情形处理之后, 我们得出结论: 禁止这种做法通常更有用, 改为返回 domain_error 的结果.

把无穷大作为特殊情形处理还带来额外的复杂性, 因为与大多数 (但非全部) 平台上的内置类型不同, 并非所有用户自定义类型都特化以提供 std::numeric_limits<RealType>::infinity(), 它们会返回零而不是任何无穷大的表示.

理由是: 非有限值可能因用户代码中的错误或上溢而发生, 及时诊断它比继续运行更有帮助. 此外, 代码也变得更加复杂、更容易出错、测试工作量大得多, 可读性也差得多.

不过在少数我们觉得显而易见的情形下 (例如正态分布), 我们允许参数为无穷大, 条件是该实现为 RealType 实现了无穷大, 并且该分布支持并测试了这一点.

这些分布的范围在平台支持时被设为无穷大 (通过测试 std::numeric_limits<RealType>::has_infinity), 否则设为 Boost.Math 为 RealType 提供的最大值.

对 has_infinity 的测试显然很重要, 对于任意精度类型, 无穷大的意义远不如 IEEE754 浮点数.

到目前为止, 我们尚未设置 support() 函数 (只设置了范围), 理由是无穷处的 PDF 无意义/为零.

需要对无穷大 (或其他特定值) 进行特殊处理的用户当然总可以在调用分布或函数之前拦截它, 返回自己选择的值或其他行为. 这通常比试图处理错误策略的后果更简单.

上溢、下溢和非规格化数可以使用 error handling policies 处理.

我们还尝试捕获数学规格会导致除以零或上溢的边界情形, 并以类似方式发出信号. 极点处 (及其附近) 发生的情况可以通过 error handling policies 控制.

尺度、形状与位置

我们曾考虑把位置和尺度加入函数列表, 例如:

template <class RealType>
inline RealType scale(const triangular_distribution<RealType>& dist)
{
  RealType lower = dist.lower();
  RealType mode = dist.mode();
  RealType upper = dist.upper();
  RealType result;  // of checks.
  if(false == detail::check_triangular(BOOST_CURRENT_FUNCTION, lower, mode, upper, &result))
  {
    return result;
  }
  return (upper - lower);
}

但发现这些概念对太多分布没有定义 (或其定义争议太大), 因而不具备普遍适用性. 由于它们是非成员函数, 需要时可以随时添加.

特定函数与分布的实现说明
  • 三角分布的默认参数. 我们不确定最佳的默认参数是什么. 一些资料认为标准三角分布取 lower = 0、mode = half 和 upper = 1. 然而, 作为最常见用法即对正态分布的近似, lower = -1、mode = 0 和 upper = 1 会更合适.
所使用的有理近似

本库中的一些特殊函数通过有理近似实现. 这些近似要么取自文献, 要么由 John Maddock 使用 我们的 Remez 代码 设计.

使用有理近似而非多项式近似是为了确保精度: 多项式近似在一定精度水平上往往表现出色, 但无论再添加多少项, 都常常无法提供高得多的精度.

我们自己的近似要么是为了更高的精度而设计 (例如支持 128 位 long double), 要么是因为文献方法不可用或其许可证与 BSL 不兼容. 已知我们的 Remez 代码在相当简单的"玩具"情形中能与文献结果良好吻合. 所有近似都检查过收敛性, 并确保它们不是病态的 (系数可以给出理论上良好的解, 但在固定精度下, 所得到的有理函数可能是无法计算的).

用不同的 Remez 实现重新计算很可能产生不同的系数: 大家都知道该问题一般而言是病态的, 我们的 Remez 实现对其中许多近似常常找到一个宽泛且界定不清的极小值 (当然, 对于像逼近 exp 这样简单的"玩具"例子, 极小值是明确界定的, 无论使用谁的 Remez 实现, 系数都应当一致). 一般而言, 这不应影响近似的有效性: 有很好的文献支持这样一种观点, 即系数可以"有误差"而不必然对结果产生不利影响. 注意, "有误差"在此语境中具有特殊含义, 参见 "Approximate construction of rational approximations and the effect of error autocorrection.", Grigori Litvinov, eprint arXiv:math/0101042. 因此, 系数仍然需要被精确计算, 即使它们相对于"真正的"极小极大解可能有误差.

数学常量的表示

constants.hpp 中的宏 BOOST_DEFINE_MATH_CONSTANT 用于向数学函数和分布提供高精度常量, 因为必须统一地为内置的 float、double 和 long double 类型, 以及 Boost.Multiprecision 中 cpp_dec_float 之类的用户自定义类型, 还有 NTL::quad_float 和 NTL::RR 等, 提供数值.

为了允许在本 Math ToolKit 及其测试 (以及其他地方) 中使用 NTL::RR 类型以约 100 位十进制数字进行计算, 显然有必要按这一精度定义常量.

然而, 一些编译器不接受这么长的十进制数字字符串. 因此常量被拆分成两部分: 第一部分至少包含 long double 精度, 第二部分在不需要或未知时为零. 第三部分允许在必要时提供指数 (若无则用零); 另外两个参数只能包含十进制数字 (以及符号和小数点), 不能包含像 1.234E99 这样的指数 (也不能有结尾的 F 或 L). 第二个数字字符串只在 T 是用户自定义类型时使用, 此时常量被转换为长字符串字面量并 lexical_cast 到类型 T. (这是必要的, 因为你不能使用数值常量, 即使是 long double 也可能没有足够的位数).

例如, pi 定义如下:

BOOST_DEFINE_MATH_CONSTANT(pi,
  3.141592653589793238462643383279502884197169399375105820974944,
  5923078164062862089986280348253421170679821480865132823066470938446095505,
  0)

并这样使用:

using namespace boost::math::constants;

double diameter = 1.;
double radius = diameter * pi<double>();

or boost::math::constants::pi<NTL::RR>()

注意, 必须显式指定类型 (尽管这不太方便).

因此你不能写

double p = boost::math::constants::pi<>();  // could not deduce template argument for 'T'

也不能写:

double p = boost::math::constants::pi; // Context does not allow for disambiguation of overloaded function
double p = boost::math::constants::pi(); // Context does not allow for disambiguation of overloaded function
线程安全

通过设置 errno 报告错误应当已经是线程安全的 (否则标准库的数学函数就都不是线程安全的了?). 如果你启用通过异常报告错误, errno 反正会被弃置不用.

对于常规的 C++ 用法, Boost.Math 的 static const 常量现在是线程安全的, 因此对于内置实数类型: float、double 和 long double 都是线程安全的.

对于用户自定义类型 (例如 cpp_dec_float), Boost.Math 也应当是线程安全的 (尽管我们不确定如何严格证明这一点).

(线程安全在 C++11 标准修订中受到了关注, 所以希望所有编译器最终都能在这方面做对.)

测试数据的来源

我们找到了大量测试数据来源. 如果它们与我们的测试结果一致, 我们就假定它们是 "已知良好" 的; 只有在严重分歧的情况下, 才会参考其他来源, 听取它们的 '投票'. 精度 (无论是实际的还是声称的) 差异极大. 只有 Wolfram Mathematica functions 提供了高于 C++ double (64 位浮点) 的精度, 并被视为迄今为止最可信的来源. The R Project for Statistical Computing 提供了最广的分布范围, 但通常的 Intel X86 发行版使用 64 位 double, 因此我们的使用局限于 15 到 17 位十进制数字的精度.

一个有用的来源索引是: Web-oriented Teaching Resources in Probability and Statistics

Statlet: 一个 Javascript 应用程序, 用于计算和绘制概率分布, 提供了最完整的分布种类:

伯努利、二项、离散均匀、几何、超几何、负二项、泊松、贝塔、柯西-洛伦兹、卡方、埃尔朗、指数、极值、费希尔、伽马、拉普拉斯、逻辑斯蒂、对数正态、正态、帕累托、学生 t、三角、均匀与威布尔。

它计算 pdf、cdf、survivor、log survivor、hazard、尾部面积以及 5 个尾值的关键值.

它也是找到的 Weibull 分布唯一独立来源; 遗憾的是, 在底层特殊函数公认难以实现的区域, 它的精度似乎非常差.

对传给函数和构造函数的无效参数的测试

在发现一些'坏'参数 (如 NaN) 没有像应当的那样抛出 domain_error 异常之后, 设计了一个函数

check_out_of_range (位于 test_out_of_range.hpp 中) 由 JM 设计, 用于检查 (使用 Boost.Test 的 BOOST_CHECK_THROW 宏) 传给构造函数和函数的坏参数是否会抛出 domain_error 异常.

用法为 check_out_of_range< DistributionType >(list-of-params);, 其中 list-of-params 是一个 有效 参数的列表, 分布可以由它们构造, 即传给函数的参数个数与传给分布构造函数的相同.

参数的取值并不重要, 但必须是 有效 的, 以通过构造函数的检查; 默认值是合适的, 但必须显式提供, 例如:

check_out_of_range<extreme_value_distribution<RealType> >(1, 2);

所做的检查包括:

  • 在每个有效参数的位置传入 Infinity 或 NaN (如果可用).
  • 以 Infinity 或 NaN (如果可用) 作为随机变量.
  • 把超出范围的随机变量传给 pdf 和 cdf (即在 "range(DistributionType)" 之外).
  • 把超出范围的概率传给分位数函数及其补.

但 不会 检查传给构造函数的有限但超出范围的参数, 因为这些是每个分布特有的, 例如:

BOOST_CHECK_THROW(pdf(pareto_distribution<RealType>(0, 1), 0), std::domain_error);
BOOST_CHECK_THROW(pdf(pareto_distribution<RealType>(1, 0), 0), std::domain_error);

它检查 scale 和 shape 参数都 > 0, 其方式是检查当任一参数 == 0 时会抛出 domain_error 异常.

(使用 check_out_of_range 函数可能意味着之前的一些测试现在是多余的).

还注意到, 如果有不止一个参数是坏的, 那么错误消息只报告第一个被检测到的.

$for file in *.mml; do

必要时可以用以下命令移除 XHTML 包装器:

cat filename | tr -d "\r\n" | sed -e 's/.*\(<math[^>]*>.*</math>\).*/\1/' > newfile

PDF 生成到 \pdf\math.pdf, 所用命令在当前目录为 \math_toolkit\libs\math\doc\sf_and_dist 的 shell 或命令窗口中执行, 通常是:

bjam -a pdf >math_pdf.log

注意, 必须配置 XEP 以 使用并嵌入 SVG 公式所用的字体 (几乎肯定要编辑 XEP 安装提供的示例 xep.xml). 如果不这样做, 你会在日志文件中看到如下 XEP 警告

[warning]could not find any font family matching "Times New Roman"; replaced by Helvetica

(html 是默认格式, 因此它生成在 libs\math\doc\html\index.html, 使用命令行 >bjam -a > math_toolkit.docs.log).

<!-- Sample configuration for Windows TrueType fonts.  -->

XZ 使用久经考验的 Latex 编写他的公式, JM 使用 mxlatex 把它们转换为 MathML. 这一过程目前不可靠, 需要一些人工干预: 因此, Latex 源不被认为是自动生成公式 SVG 版本的可行途径.

公式通过 math.qbk 中定义的 equation 模板嵌入 quickbook 源. 这会输出类似下面这样的 Docbook XML:

<inlinemediaobject>
<imageobject role="html">
<imagedata fileref="../equations/myfile.png"></imagedata>
</imageobject>
<imageobject role="print">
<imagedata fileref="../equations/myfile.svg"></imagedata>
</imageobject>
</inlinemediaobject>

Docbook 输出和生成的 HTML 中目前都没有 MathML: 这需要进一步调查.
