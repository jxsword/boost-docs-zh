Boost.Atomic 最常见的用途是实现自定义线程同步协议: 目标是协调线程对共享变量的访问, 以避免 "冲突". 程序员必须意识到, 编译器、CPU 与缓存层次结构通常可以随意重排内存引用. 因此, 诸如以下的程序:

int x = 0, int y = 0;

thread1:
  x = 1;
  y = 1;

thread2:
  if (y == 1) {
    assert(x == 1);
  }

确实可能失败, 因为不保证 thread2 对 x 的读取能 "看见" thread1 的写入.

Boost.Atomic 使用基于 happens-before 关系的同步概念来描述在哪些情形下可确保上述情况不会发生.

本节余下部分将以 "上手" 的方式讨论 happens-before, 而不是给出完全形式化的定义. 鼓励读者另外查看后面对若干 示例正确性的讨论.

通过互斥实施 happens-before

作为理解如何用 happens-before 进行推理的入门示例, 考虑两个线程使用共同的互斥量进行同步:

mutex m;

thread1:
  m.lock();
  ... /* A */
  m.unlock();

thread2:
  m.lock();
  ... /* B */
  m.unlock();

"基于锁集合的直觉" 会论证: A 与 B 不能并发执行, 因为代码路径要求持有共同的锁.

然而也可以用 happens-before 得出同样的结论: 要么 thread1 要么 thread2 会在 m.lock() 处率先成功. 若是 thread1, 则作为结果, thread2 不能在 m.lock() 处成功, 直到 thread1 执行了 m.unlock(), 因此在此情形下 A happens-before B. 由对称性, 若 thread2 在 m.lock() 处率先成功, 我们可得出 B happens-before A.

由于这已穷尽所有可能, 我们可以得出: A happens-before B 或 B happens-before A 两者必有其一始终成立. 显然我们无法断言两个关系中 哪一个 成立, 但任意一个都足以得出 A 与 B 不能冲突的结论.

比较 自旋锁实现, 以了解互斥概念如何映射到 Boost.Atomic.

happens-before 通过 release 与 acquire

通过 Boost.Atomic 协调线程的最基本模式, 是在一个原子变量上使用 release 与 acquire 进行协调: 如果 ...

  • ... thread1 执行操作 A,
  • ... thread1 随后以 release 语义写入 (或原子地修改) 一个原子变量,
  • ... thread2 随后以 acquire 语义从同一个原子变量读取 (或原子地读-改) 该值, 并且
  • ... thread2 随后执行操作 B,

... 那么 A happens-before B.

考虑以下示例

atomic<int> a(0);

thread1:
  ... /* A */
  a.fetch_add(1, memory_order::release);

thread2:
  int tmp = a.load(memory_order::acquire);
  if (tmp == 1) {
    ... /* B */
  } else {
    ... /* C */
  }

在此示例中, 有两种可能的执行路径:

  • thread1 的 store 操作先于 thread2 的 load: 此时 thread2 将执行 B, 且 "A happens-before B" 成立, 因为上述所有条件都满足.
  • thread2 的 load 操作先于 thread1 的 store: 此时 thread2 将执行 C, 但 "A happens-before C" 不 成立: thread2 没有通过 a 读取 thread1 写入的值.

因此, A 与 B 不能冲突, 但 A 与 C 可能 冲突.

栅栏

排序约束通常与对原子变量的访问一起指定. 不过也可以单独发出 "栅栏" 操作, 此时栅栏与先前 (对 acquire、consume 或 seq_cst 操作) 或随后 (对 release 或 seq_cst) 的原子操作配合起作用.

上一节的示例也可以写成如下形式:

atomic<int> a(0);

thread1:
  ... /* A */
  atomic_thread_fence(memory_order::release);
  a.fetch_add(1, memory_order::relaxed);

thread2:
  int tmp = a.load(memory_order::relaxed);
  if (tmp == 1) {
    atomic_thread_fence(memory_order::acquire);
    ... /* B */
  } else {
    ... /* C */
  }

这提供与之前相同的排序保证, 但在执行 C 的情形下省去了一次 (可能昂贵的) 内存序操作.

注释

原子栅栏仅用于为线程同步目的约束常规与原子加载和存储的排序. atomic_thread_fence 并不用于为某些体系结构特定的内存访问排序, 如 x86 上的非临时加载与存储或写合并内存访问. 请为这些目的使用专用指令.

happens-before 通过 release 与 consume

通过 Boost.Atomic 协调线程的第二种模式, 是在一个原子变量上使用 release 与 consume 进行协调: 如果 ...

  • ... thread1 执行操作 A,
  • ... thread1 随后以 release 语义写入 (或原子地修改) 一个原子变量,
  • ... thread2 随后以 consume 语义从同一个原子变量读取 (或原子地读-改) 该值, 并且
  • ... thread2 随后执行操作 B, 且该操作 在计算上依赖于原子变量的值,

... 那么 A happens-before B.

考虑以下示例

atomic<int> a(0);
complex_data_structure data[2];

thread1:
  data[1] = ...; /* A */
  a.store(1, memory_order::release);

thread2:
  int index = a.load(memory_order::consume);
  complex_data_structure tmp = data[index]; /* B */

在此示例中, 有两种可能的执行路径:

  • thread1 的 store 操作先于 thread2 的 load: 此时 thread2 将读取 data[1], 且 "A happens-before B" 成立, 因为上述所有条件都满足.
  • thread2 的 load 操作先于 thread1 的 store: 此时 thread2 将读取 data[0], 但 "A happens-before B" 不 成立: thread2 没有通过 a 读取 thread1 写入的值.

此处, happens-before 关系有助于确保 thread1 对 data[1] 的任何访问 (推测为写入) 都发生在 thread2 对 data[1] 的访问 (推测为读取) 之前: 若缺少该关系, thread2 可能读到过时/不一致的数据.

注意, 在此示例中, 操作 B 在计算上依赖于该原子变量; 因此以下程序将是错误的:

atomic<int> a(0);
complex_data_structure data[2];

thread1:
  data[1] = ...; /* A */
  a.store(1, memory_order::release);

thread2:
  int index = a.load(memory_order::consume);
  complex_data_structure tmp;
  if (index == 0)
    tmp = data[0];
  else
    tmp = data[1];

consume 最常见 (也最安全! 见 限制) 的用法是与指针配合, 例如比较 双重检查锁定的单例.

顺序一致性

通过 Boost.Atomic 协调线程的第三种模式, 是使用 seq_cst 进行协调: 如果 ...

  • ... thread1 执行操作 A,
  • ... thread1 随后以 seq_cst 执行任何操作,
  • ... thread1 随后执行操作 B,
  • ... thread2 执行操作 C,
  • ... thread2 随后以 seq_cst 执行任何操作,
  • ... thread2 随后执行操作 D,

则要么 "A happens-before D" 成立, 要么 "C happens-before B" 成立.

在此情形下, thread1 与 thread2 操作的是相同还是不同的原子变量, 或是否使用 "独立" 的 atomic_thread_fence 操作, 都无关紧要.
