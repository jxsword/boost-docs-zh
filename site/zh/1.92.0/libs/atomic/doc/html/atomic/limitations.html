局限

虽然 Boost.Atomic 力求尽可能忠实地实现 C++11 及后续标准的原子操作, 但仍有一些没有编译器支持就无法消除的限制:

  • 不支持聚合初始化语法: 由于 Boost.Atomic 有时使用不同于值类型的存储类型, atomic<> 模板需要一个执行必要转换的初始化构造函数. 这使 atomic<> 成为非聚合类型, 并禁止聚合初始化语法 (atomic<int> a = {10}). 不过 Boost.Atomic 确实支持直接初始化与统一初始化语法. 建议: 始终使用直接初始化 (atomic<int> a(10)) 或统一初始化 (atomic<int> a{10}) 语法.
  • 某些类型的初始化构造函数不是 constexpr : 对于整数类型、bool、枚举、浮点类型以及无填充的类之外的值类型, atomic<> 初始化构造函数需要在运行期转换到存储类型, 并可能清除填充位. 这一限制未来可能对更多类别类型解除.
  • 编译器可能把计算依赖转换为控制依赖: 关键在于, memory_order::consume 只影响计算上依赖的操作, 但一般而言没有什么能阻止编译器把计算依赖转换为控制依赖. 一个完全符合 C++11 的编译器会被禁止做这种转换, 但实际上, 即使不是全部、也是大多数编译器选择将 memory_order::consume 提升为 memory_order::acquire (例如参见 此 gcc 缺陷). 在当前实现中, Boost.Atomic 遵循这一趋势, 但未来可能改变. 建议: 一般应避免 memory_order::consume, 改用 memory_order::acquire. 仅在与指针值配合时使用 memory_order::consume, 且仅当你能确保编译器无法推测并将其转换为控制依赖时.
  • 栅栏操作可能强制实施 "过强" 的编译器排序: 语义上, memory_order::acquire/memory_order::consume 和 memory_order::release 只需在一个方向上约束内存操作的重排. 由于某些编译器无法表达该约束, 这些操作可能充当 "完全编译器屏障". 在极端情形下, 这可能产生比能力更强的编译器所能生成的代码效率略低的代码. 若可能, Boost.Atomic 会使用编译器内置函数来表达恰当的排序约束.
  • 调试模式下原子操作可能强制实施 "过强" 的内存序: 在某些编译器上, 禁用优化使得无法以编译期常量形式向编译器内置函数提供内存序约束. 这会导致编译器静默忽略所提供的约束并选择 "最强" 的内存序 (memory_order::seq_cst) 来生成代码. 这不仅降低性能, 还可能掩盖用户代码中的缺陷 (例如用户使用了错误的内存序约束从而导致数据竞争的情形). 建议: 始终在启用优化的情况下测试你的代码.
  • 无进程间回退: 在共享内存中使用 atomic<T> 只有在 atomic<T>::is_lock_free() == true 时才能正确工作. atomic_ref<T> 亦然. 建议: 进程间通信请使用 IPC 原子类型.
  • 内存类型要求: 原子对象不能放置在只读内存中, 即使只从中读取. 此处只读指的是内存区域被操作系统以只读权限映射, 与 const 限定无关. 在某些目标上, Boost.Atomic 可能使用读-改-写指令实现加载操作, 如 x86 上的 CMPXCHG16B. 加载操作不改变对象值, 但该指令仍会向内存位置发出写入, 因此内存必须可写. 对可与原子指令一起使用的内存类型, 还可能存在其他硬件特定的限制. 此外, 为正确实现等待与通知操作, 操作系统可能对内存类型及其上允许的操作集有额外限制. 这些要求因系统而异. 例如, 在 Mac OS 上, IPC 原子对象不能放置在栈内存中, 因为通知操作可能伪失败而无法唤醒被阻塞的线程. Boost.Atomic 的目标是原生支持更多原子类型与操作, 即使这意味着不支持某些很少有用的极端情形. 建议: 非 IPC 原子对象可以安全地在常规的进程本地读写内存中使用 (如栈或通过 malloc 或 new 获得的内存), 而 IPC 原子对象可用于进程共享的读写内存 (如通过 shm_open+ mmap 获得的内存). 任何特殊内存类型, 如映射的设备内存或以特殊缓存策略 (即回写以外的策略) 映射的内存, 不保证可用, 并受系统特定限制约束.
  • 带符号整数必须使用 二进制补码表示: Boost.Atomic 提出该要求是为了在内部实现带符号与无符号整数之间的转换. C++11 要求所有对整数的原子算术运算都按二进制补码算术良定义, 这意味着 Boost.Atomic 必须在内部对无符号整数进行操作, 以避免带符号整数溢出导致的未定义行为. 不支持采用其他带符号整数表示的平台. 注意, C++20 将带符号整数的二进制补码表示定为强制.
  • 对带填充位类型的支持有限: 没有可移植的方法清除对象的填充位. 这样做需要编译器支持, 通常在支持 C++20 的编译器上可用. 不清除填充时, compare_exchange_strong/compare_exchange_weak 无法按预期工作, 因为填充内容不匹配它们会伪失败. 注意, 其他操作可能在内部以 compare_exchange_* 实现. 若编译器不提供清除填充位的方法, Boost.Atomic 在编译期已知填充位位置的平台上的确支持浮点类型的填充位, 但除此之外无法支持带填充的类型. 注意, 如 atomic 描述中所讨论的, 即使在提供清除填充方法的编译器上, 带填充位的联合体也无法被可靠支持.
