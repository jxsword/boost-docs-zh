配置与构建

本库包含仅头文件部分和需编译部分. 在无锁情形下本库是仅头文件库, 但在部分平台上需要单独的二进制文件来实现基于锁的模拟以及等待与通知操作. 用户可通过检查 特性宏 来检测是否需要链接需编译部分.

以下宏会影响本库的行为:

宏

说明

BOOST_ATOMIC_LOCK_POOL_SIZE_LOG2

Boost.Atomic 在部分平台上用于实现基于锁的原子操作以及等待与通知操作的内部锁池中锁数量的以 2 为底的对数. 必须是 0 到 16 范围内的整数, 默认值为 8. 仅在构建 Boost.Atomic 时生效.

BOOST_ATOMIC_NO_CMPXCHG8B

影响 32 位 x86 的 Oracle Studio 构建. 定义该宏时, 本库假定目标 CPU 不支持用于实现 64 位原子操作的 cmpxchg8b 指令. 非常古老的 CPU (早于 Pentium) 就是这种情况. 本库不会在运行期检测该指令, 因此除非定义该宏, 否则在此类 CPU 上运行使用 64 位原子类型的代码将导致崩溃. 注意, 该宏不影响 MSVC、GCC 及兼容编译器, 因为本库会从编译器定义的宏推断该信息.

BOOST_ATOMIC_NO_CMPXCHG16B

影响 64 位 x86 的 MSVC 和 Oracle Studio 构建. 定义该宏时, 本库假定目标 CPU 不支持用于实现 128 位原子操作的 cmpxchg16b 指令. 某些早期 64 位 AMD CPU 就是这种情况; 所有 Intel CPU 和当前的 AMD CPU 都支持该指令. 本库不会在运行期检测该指令, 因此除非定义该宏, 否则在此类 CPU 上运行使用 128 位原子类型的代码将导致崩溃. 注意, 该宏不影响 GCC 及兼容编译器, 因为本库会从编译器定义的宏推断该信息.

BOOST_ATOMIC_NO_FLOATING_POINT

定义该宏时, 浮点操作支持被禁用. 浮点类型应被视为类似于平凡可复制 (trivially copyable) 的结构体, 且不会定义任何能力宏.

BOOST_ATOMIC_NO_DARWIN_ULOCK

影响 Darwin 系统 (Mac OS、iOS、tvOS、watchOS) 上的编译. 定义该宏时, 禁用 ulock API 来实现等待与通知操作. 这有助于满足 Apple App Store 的要求.

BOOST_ATOMIC_FORCE_FALLBACK

定义该宏时, 所有操作都以锁实现. 这主要用于测试, 不应在实际项目中使用.

BOOST_ATOMIC_DYN_LINK 和 BOOST_ALL_DYN_LINK

控制本库的链接方式. 定义前者时, 本库假定动态链接, 否则为静态链接. 其中后一个宏影响所有 Boost 库, 而不仅是 Boost.Atomic.

BOOST_ATOMIC_NO_LIB 和 BOOST_ALL_NO_LIB

控制本库在 Windows 上的自动链接. 定义该宏时, 禁用自动链接. 其中后一个宏影响所有 Boost 库, 而不仅是 Boost.Atomic.

除宏之外, 为目标 CPU 指定正确的编译器选项也很重要. 对于 GCC 及兼容编译器, 这会影响特定的原子操作是否无锁.

Boost 的构建过程在 入门指南中描述. 例如, 你可以用以下命令行构建 Boost.Atomic:

b2 --with-atomic variant=release instruction-set=core2 stage

内存序 

#include <boost/memory_order.hpp>

作用域枚举 boost::memory_order 定义了以下值, 用于表示内存排序约束:

常量时间

说明

relaxed

无排序约束. 非正式地说, 后续操作可以重排到该原子操作之前, 先前的操作可以重排到其后. 仅在以下情形下该约束才适用: a) 后续操作不依赖于原子操作的结果; 或 b) 排序通过独立的 atomic_thread_fence 操作强制实施. 不过, 对原子值本身的操作仍是原子的.

release

执行 release 操作. 非正式地说, 防止所有先前的内存操作被重排越过此点.

acquire

执行 acquire 操作. 非正式地说, 防止后续的内存操作被重排到该点之前.

consume

执行 consume 操作. 比 memory_order::acquire 更宽松 (且在某些体系结构上可能更高效), 因为它只影响在计算上依赖于从原子变量读取的值的后续操作. 目前在所有受支持的体系结构上等价于 memory_order::acquire (说明见 限制一节).

acq_rel

同时执行 release 和 acquire 操作

seq_cst

强制顺序一致性. 蕴含 acq_rel, 但额外为所有经此限定的操作强制全序.

注意, 默认构造函数 atomic_flag() 不同于 C++11 的 std::atomic_flag, 后者会使默认构造的对象保持未初始化. C++20 将 std::atomic_flag 的默认构造函数改为把标志初始化为清除状态, 与 Boost.Atomic 类似. 这可能需要在程序启动期间进行动态初始化来执行对象初始化, 这使得创建全局 boost::atomic_flag 对象变得不安全, 如果这些对象可在进入 main() 之前被使用. 不过, 一些编译器 (尤其是支持 C++11 constexpr 的编译器) 可能足够聪明, 能够静态地执行标志初始化 (用 C++11 的术语说, 这是常量初始化).

C++11 定义了 ATOMIC_FLAG_INIT 宏, 可用于像这样将 std::atomic_flag 静态初始化为清除状态:

std::atomic_flag flag = ATOMIC_FLAG_INIT; // constant initialization

使用 Boost.Atomic, 若编译器支持 C++11 constexpr, 则下面的简单声明会有相同的效果:

boost::atomic_flag flag; // constant initialization

不过, 为了与 std::atomic_flag 保持接口一致, 若可能, 本库也定义了 BOOST_ATOMIC_FLAG_INIT 宏, 它等价于 ATOMIC_FLAG_INIT:

boost::atomic_flag flag = BOOST_ATOMIC_FLAG_INIT; // constant initialization

boost::atomic<T> 便捷类型别名
#include <boost/atomic/atomic.hpp>

boost::atomic<T> 提供了对适当类型 T 的变量进行原子访问的方法. 若该类型是 平凡可复制 (3.9/9 [basic.types]), 则它是适当的. 以下是与该要求兼容的类型的示例:

  • 标量类型 (如整数、布尔、枚举或指针类型)
  • 一个 class 或 struct, 其没有非平凡的复制或移动构造函数或赋值运算符, 拥有平凡析构函数, 并且可通过 memcmp 在忽略任何填充位的情况下进行比较 (但见下文).

注意, 带虚函数或虚基类的类不满足这些要求.

另请注意, 对带填充位类型的支持在很大程度上取决于编译器是否提供将填充位设置为已知状态 (如零) 的方法. 此特性通常存在于支持 C++20 的编译器中. 当编译器不支持该特性时, 会定义 BOOST_ATOMIC_NO_CLEAR_PADDING 能力宏, 且带填充位的类型通过 memcmp 比较时可能不相等, 即使所有成员都相等. 某些本身包含填充位的浮点类型也可能出现这种情况. 此时, Boost.Atomic 会尝试支持填充位位置已知的某些浮点类型 (一个著名的例子是 x86 目标上的 80 位扩展精度 long double 类型), 但除此之外不支持带填充位的类型.

注释

即使在支持清除填充位的编译器上, 带填充的联合体也可能不按预期工作. 编译器对联合体的处理行为各不相同. 特别是, gcc 11 会清除构成所有联合体成员填充的字节 (这是 C++20 在 [atomics.types.operations]/28 中所要求的), 而 MSVC 19.27 完全不清除任何填充. 另外, 考虑到联合体表示中的某些位可能在一个联合体成员中构成填充, 但对另一个成员则参与构成值. 当前编译器无法可靠地追踪联合体的活跃成员, 因此无法就清除这些位实现合理的行为. 结果是, 当前活跃联合体成员的填充位可能保持未初始化, 这将妨碍原子操作可靠工作. C++20 标准明确允许 compare_exchange_* 操作在这种情形下总是失败.

boost::atomic<T> 的默认构造函数不同于 C++11 的 std::atomic<T>, 而与 C++20 一致. 在 C++11 (以及更早的 Boost.Atomic 版本) 中, 默认构造函数对类型为 T 的所含对象执行默认初始化, 若 T 没有用户定义的构造函数, 这会导致未指明的值. C++20 与当前的 Boost.Atomic 版本执行值初始化, 这意味着在此情形下为零初始化.

等待与通知操作在 此处一节中有详细描述.

value 操作是 Boost.Atomic 的扩展. 返回的引用可用于对原子值调用不属于 Boost.Atomic 但在目标体系结构上与其兼容的外部操作. 典型例子是某些系统上可用的 futex 及类似操作. 返回的引用不得用于以非原子方式读取或修改原子对象的值, 也不得用于构造 原子引用. 否则不保证原子性或内存序.

注释

即使给定类型的 boost::atomic 是无锁的, 该类型的原子引用也未必如此. 因此, 对同一对象操作的 boost::atomic 和 boost::atomic_ref 可能使用彼此不兼容的不同线程同步原语.

带四个参数的 compare_exchange_weak/compare_exchange_strong 变体与三参数变体的区别在于: 它们允许在操作失败的情形下指定不同的内存序约束.

需要注意, compare_exchange_weak/compare_exchange_strong 在 Boost.Atomic 中不同于 C++11 的 std::atomic<T>: boost::atomic<T> 被允许向 expected 实参写入, 即使操作返回 true; 而 std::atomic<T> 仅当操作返回 false 时才向该实参写入. 若调用者向 expected 实参传入的是必须由 compare_exchange_* 操作保护的数据的引用, 该差异可能是重大的, 因为对 expected 的写入可能发生在以 success_order 约束进行原子更新之后, 并构成数据竞争. 建议用户避免将受保护数据的引用作为 expected 实参传入.

除这些显式操作外, 每个 atomic<T> 对象还支持隐式 store 与 load, 通过使用 "赋值" 运算符与 "转换为 T" 运算符实现. 应避免使用这些运算符, 因为它们不允许指定内存序约束, 而总是默认为 memory_order::seq_cst.

提示

若枚举被用于实现位掩码或一组标志, 位运算会很有用.

原子操作的效果是: 枚举类型的输入值先被转换为该枚举的底层类型, 然后在底层类型的值上执行运算, 之后在适用时把运算结果转换回枚举类型.

警告

严格来说, 其中一些操作可能产生超出该枚举有效值范围的值, 如 C++ 标准所定义. 特别地, 对于底层类型不固定的枚举 (即未指定基类型说明的非作用域 enum), C++ 标准将枚举支持的取值范围定义为能够装入该枚举全部具名常量所用最小位数的一组值. 例如, 原子取补操作可能产生超出此范围的值. 尽管大多数编译器可能会按预期处理这类值, 仍建议用户避免将底层类型不固定的枚举用于这些操作, 或确保操作不产生超出有效范围的值.

上述内容意味着不会调用任何用户定义的运算符来实现原子操作. 这类似于 compare_exchange_weak/compare_exchange_strong 操作, 它们同样不调用任何用户定义的 operator== 来比较值. 若为枚举定义了用户定义的运算符, 其行为可能与原子操作不同. 若用户定义运算符的行为更可取, 可以用比较交换循环来实现.

enum class flags : std::uint32_t
{
    none = 0u,
    one = 1u,
    two = 1u << 1u,
    four = 1u << 2u,
    all = (1u << 3u) - 1u
};

flags operator~ (flags value)
{
    // Only invert bits that are named in the enum
    return static_cast<flags>(static_cast<std::uint32_t>(value) ^ static_cast<std::uint32_t>(flags::all));
}

atomic<flags> atomic_flags(flags::none);

// bitwise_complement() operates on the value of the underlying type
assert(atomic_flags.bitwise_complement() == (flags)0xFFFFFFFF);

atomic_flags.store(flags::none);

// Enforce behavior of the user-defined operator~
{
    flags old_val = atomic_flags.load(), new_val;
    do
    {
        new_val = ~old_val;
    }
    while (!atomic_flags.compare_exchange_weak(old_val, new_val));

    assert(new_val == flags::all);
}

atomic_flags.store(flags::none);

// Achieve the behavior similar to the user-defined operator~ through other atomic operations
assert(atomic_flags.bitwise_xor(flags::all) == flags::all);

操作的 opaque_op 与 op_and_test 变体在一些体系结构上可能产生更高效的代码, 因为不保留原子变量的原值. 在 bit_test_and_op 操作中, 比特编号 n 从 0 开始 (即最低有效位), 且对底层类型固定的枚举不得超过 std::numeric_limits<std::underlying_type<E>::type>::digits - 1, 对底层类型不固定的枚举则不得超过参与构成值的最高有效位的编号.

除这些显式操作外, 每个 boost::atomic<E> 对象还支持运算符 &=、|= 和 ^=. 应避免使用这些运算符, 因为它们不允许指定内存序约束, 而总是默认为 memory_order::seq_cst.

原子引用

注意事项
#include <boost/atomic/atomic_ref.hpp>

boost::atomic_ref<T> 还提供了对类型为 T 的外部变量进行原子访问的方法. 对类型 T 的要求与 boost::atomic 所施加的要求相同. 与 boost::atomic 不同, boost::atomic_ref 不在内部存储值, 而只引用类型为 T 的外部对象.

与 boost::atomic_ref 兼容的对象有若干要求:

  • 被引用对象的生命期不得在引用它的最后一个 boost::atomic_ref 被销毁之前结束.
  • 被引用对象的对齐不得低于 boost::atomic_ref<T>::required_alignment 常量所指示的对齐. 该常量可能大于类型 T 的自然对齐. 在 Boost.Atomic 中, required_alignment 表示使对该对象的操作成为无锁的对齐; 否则, 若无锁操作不可能, required_alignment 不得低于 T 的自然对齐.
  • 被引用对象不得是 潜在重叠对象. 它必须是 最派生对象 (即不得是派生类对象的基类子对象), 且不得以 [[no_unique_address]] 属性标记. 
    struct Base
{
    short a;
    char b;
};

struct Derived : public Base
{
    char c;
};

Derived x;
boost::atomic_ref<Base> ref(x); // bad
    在上面的示例中, ref 可能悄悄破坏 x.c 的值, 因为它可能位于 Base 基类子对象 (属于 x) 的尾部填充中.
  • 被引用对象不得位于只读内存中. 即使对于非修改性操作, 如 load(), boost::atomic_ref 也可能发出需要写访问的读-改-写 CPU 指令.
  • 只要存在至少一个引用某对象的 boost::atomic_ref, 该对象就不得以 boost::atomic_ref 之外的任何其他方式访问.

允许多个引用同一对象的 boost::atomic_ref, 并且通过任何此类引用执行的操作都是原子的, 且按内存序实参彼此有序. boost::atomic_ref<T> 支持 boost::atomic<T> 所支持的同一组属性与操作 (取决于类型 T), 但有以下例外:

注意事项

使用 boost::atomic_ref 与 boost::atomic 相比存在若干缺点.

首先, 用户需要维护被引用对象的正确对齐. 这意味着用户必须预先规划程序中哪些变量需要原子访问. 在 C++11 及更高版本中, 用户可通过应用 alignas 说明符来确保所需的对齐:

alignas(boost::atomic_ref<int>::required_alignment)
int atomic_int;

在不支持 alignas 的编译器上, 用户必须使用编译器特定的属性或手动填充来实现所需对齐. BOOST_ALIGNMENT 宏 (来自 Boost.Config) 可能有用.

注释

不要指望编译器为基本类型强制自然对齐, 也不要指望默认对齐会满足 atomic_ref<T>::required_alignment 约束. 现实中确实存在默认对齐低于原子引用所需对齐的案例. 例如, 在 32 位 x86 目标上, 64 位整数和浮点数的对齐通常是 4, 这对 atomic_ref 来说不够高. 用户必须始终显式确保被引用对象按 atomic_ref<T>::required_alignment 对齐.

其次, 某些类型可能带有填充位, 即对象表示中不参与构成对象值的位. 填充位通常用于对齐目的. 填充位给 Boost.Atomic 带来问题, 因为它们可能破坏对象的二进制比较 (如同通过 memcmp 进行的比较), 而该比较被用于 compare_exchange_weak/compare_exchange_strong 操作. boost::atomic 管理内部对象表示, 并且在编译器恰当支持的情况下, 能够初始化填充位, 使二进制比较产生预期结果. 这对 boost::atomic_ref 是不可能的, 因为被引用对象由外部方式初始化, 无法保证填充位中的任何特定内容. 这要求 boost::atomic_ref 在构造时初始化被引用对象的填充位. 结果是, boost::atomic_ref 的构造可能相对昂贵, 并可能潜在地干扰正在通过其他原子引用对同一对象执行的原子操作. 建议避免在紧凑循环或热点路径中构造 boost::atomic_ref.

最后, 目标平台可能不具备对某些大小的对象实现原子操作的必要手段. 例如, 在许多硬件体系结构上, 对以下结构的原子操作是不可能的:

struct rgb
{
    unsigned char r, g, b; // 3 bytes
};

boost::atomic<rgb> 能够实现无锁操作, 若目标 CPU 支持 32 位原子指令, 它会在内部将 rgb 结构填充到 4 字节大小. 这对 boost::atomic_ref<rgb> 是不可能的, 因为它必须操作外部对象. 因此, boost::atomic_ref<rgb> 不会提供无锁操作, 而会退回到加锁.

一般而言, 建议尽可能使用 boost::atomic, 因为它更易用且更高效. 仅在绝对必要时才使用 boost::atomic_ref.

改进 POSIX 系统上自定义时钟的性能

boost::atomic_flag、boost::atomic<T> 和 boost::atomic_ref<T> 支持 C++20 中引入的 等待 与 通知 操作. 等待操作有以下形式:

  • T wait(T old_val, memory_order order)
  • template<typename Clock, typename Duration> wait_result<T> wait_until(T old_val, std::chrono::time_point<Clock, Duration> timeout, memory_order order)
  • template<typename Rep, typename Period> wait_result<T> wait_for(T old_val, std::chrono::duration<Rep, Period> timeout, memory_order order)

对于 boost::atomic_flag, T 是 bool. 此处 order 不得是 memory_order::release 或 memory_order::acq_rel. 注意, 与 C++20 不同, wait 操作返回 T 而非 void. 这是 Boost.Atomic 的扩展. wait_until 和 wait_for 是 定时等待操作, 也是 Boost.Atomic 的扩展.

等待操作反复执行以下步骤:

  • 加载原子对象的当前值 new_val, 所用内存序约束为 order. 对于 boost::atomic_flag, 该加载如同通过 test(order) 执行; 对于其他原子对象, 如同通过 load(order) 执行.
  • 若 new_val 表示与 old_val 不同 (即如同通过 memcmp 比较时不相等), 则返回. 对于 wait, 返回值为 new_val. 对于定时等待操作, 返回值是一个 wait_result<T> 对象 r, 其中 r.value 是 new_val, 而 t.timeout 可按语境转换为 false.
  • 对于定时等待操作, 若 timeout 已到期, 则返回一个 wait_result<T> 对象 r, 其中 r.value 是 new_val, 而 t.timeout 可按语境转换为 true. wait_for 以某个未指明的稳定时钟度量 timeout.
  • 阻塞调用线程, 直到被某个通知操作解除阻塞, 或发生伪唤醒, 或 (对定时等待操作而言) timeout 到期.

注意, 等待操作被允许伪返回, 即在没有对应通知操作的情况下返回. 它也被允许 不 返回, 若原子对象的值只是瞬时地不同于 old_val (这被称为 ABA 问题). 对于定时等待操作, 超时追踪的精度取决于硬件与底层操作系统, 且对不同时钟类型可能不同. 对于支持时间调整的时钟, 时间调整是否解除等待线程的阻塞是未指明的 (例如, 若在线程等待期间时钟被向前调整, 该线程可能直到超时到期后才解除阻塞, 就像没有进行调整一样).

通知操作有以下形式:

  • void notify_one()
  • void notify_all()

notify_one 操作解除在同一个原子对象的等待操作中被阻塞的至少一个线程, notify_all 则解除所有此类线程的阻塞. 通知操作不强制内存序, 通常应在其之前执行一个带适当内存序约束的存储操作或栅栏.

等待与通知操作需要操作系统的特殊支持, 这未必普遍可用. 操作系统是否原生支持这些操作, 由给定原子类型的 always_has_native_wait_notify 静态常量和 has_native_wait_notify() 成员函数指示.

即使对于支持无锁操作的原子对象 (如 is_always_lock_free 属性或相应 宏所示), 等待与通知操作也可能涉及加锁, 并需要链接 Boost.Atomic 的需编译库.

等待与通知操作不是地址无关的, 即实现可能使用进程本地状态和原子对象的进程本地地址来实现这些操作. 特别地, 这意味着这些操作不能用于进程间通信 (当原子对象位于共享内存中时), 也不能用于原子对象在同一进程内被映射到不同内存地址的情形.

改进 POSIX 系统上自定义时钟的性能

尽管定时等待操作对任何时钟类型默认都能工作 (受 前一节所述注意事项约束), 实现会在内部针对某个已知且可用的时钟类型追踪超时, 在 POSIX 系统上通常是 CLOCK_MONOTONIC 或 CLOCK_REALTIME. 在用户指定时钟与内部时钟之间协调会产生性能开销, 因为等待操作必须查询时钟时间戳, 并可能在耗尽分配的超时期间时执行多次阻塞操作与唤醒.

当用户使用可映射到某个 POSIX 时钟的自定义时钟类型时 (参见例如 clock_gettime), 若操作系统支持该时钟用于阻塞超时, 用户可通过提供 posix_clock_traits 类模板的如下特化来改进性能:

#include <boost/atomic/posix_clock_traits_fwd.hpp>

namespace boost {
namespace atomics {

template< >
struct posix_clock_traits<my_clock>
{
    // POSIX clock identifier (e.g. CLOCK_MONOTONIC) onto which my_clock maps
    static constexpr clockid_t clock_id = ...;

    // Function that converts a my_clock time point to a POSIX timespec structure that corresponds to clock_id
    static timespec to_timespec(my_clock::time_point time_point) noexcept;
};

} // namespace atomics
} // namespace boost

此处 my_clock 是满足 C++11 chrono 时钟要求 (20.11.3, [time.clock.req]) 的用户定义时钟类型. 注意, posix_clock_traits 必须在命名空间 boost::atomics 中特化. to_timespec 函数必须能够把任何有效时间点转换为 timespec 结构, 因此不得抛出异常.

当提供了该特化, 且底层操作系统支持 posix_clock_traits<my_clock>::clock_id 时, 等待操作将能够把传入的 my_clock 时间点转换为操作系统支持的原生格式并直接使用.

注释

用户无需特化 posix_clock_traits 类模板来适配 std::chrono 时钟. Boost.Atomic 已包含对标准库时钟的必要支持.

高级用户可以使用 posix_clock_traits 的第二个模板参数 (默认为 void 的类型) 来利用 SFINAE, 并定义 posix_clock_traits 模板偏特化, 使其适用于满足特定条件的时钟类型子集. 例如, 若存在若干个时钟类型都派生自 my_clock_base, 则可以用 std::is_base_of 作为限定条件为它们提供一个单一特化.

#include <type_traits>
#include <boost/atomic/posix_clock_traits_fwd.hpp>

namespace boost {
namespace atomics {

template<typename MyClock>
struct posix_clock_traits<MyClock, typename std::enable_if<std::is_base_of<my_clock_base, MyClock>::value>::type>
{
    // POSIX clock identifier onto which MyClock maps
    static constexpr clockid_t clock_id = MyClock::clock_id;

    // Function that converts a MyClock time point to a POSIX timespec structure that corresponds to clock_id
    static timespec to_timespec(typename MyClock::time_point time_point) noexcept;
};

} // namespace atomics
} // namespace boost

用于进程间通信的原子类型 

#include <boost/atomic/ipc_atomic.hpp>
#include <boost/atomic/ipc_atomic_ref.hpp>
#include <boost/atomic/ipc_atomic_flag.hpp>

Boost.Atomic 提供了一组专用于进程间通信的类型: boost::ipc_atomic_flag、boost::ipc_atomic<T> 和 boost::ipc_atomic_ref<T>. 这些类型统称为进程间通信原子类型 (IPC 原子类型), 而不带 ipc_ 前缀的对应类型则称为非 IPC 原子类型.

每个 IPC 原子类型对其值类型的要求与其非 IPC 对应物相同, 并提供相同的操作与属性集. 所有操作具有相同的签名、要求与效果, 但有以下修订:

  • 除构造函数、析构函数、is_lock_free() 和 has_native_wait_notify() 之外, 所有操作都有一个额外前置条件: 对该原子对象, is_lock_free() 返回 true. (实现注记: 当前实现在编译期检测原子指令的可用性, 不满足该要求的代码将无法编译.)
  • has_native_wait_notify() 方法与 always_has_native_wait_notify 静态常量指示操作系统是否对进程间等待与通知操作有原生支持. 这可能与非 IPC 原子类型不同, 因为操作系统对线程间通信和进程间通信可能具有不同能力.
  • 对 IPC 原子类型对象的全部操作都是地址无关的, 这允许把此类对象 (对于 boost::ipc_atomic_ref<T> 则是 ipc_atomic_ref 引用的对象) 放置在进程间共享的内存区域, 或在同一进程内映射到不同地址.
注释

无锁非 IPC 原子对象上的操作 (等待与通知操作除外) 也是地址无关的, 因此 boost::atomic_flag、boost::atomic<T> 和 boost::atomic_ref<T> 也可以用于进程间通信. 不过, 用户必须确保给定原子对象确实支持无锁操作. 否则可能导致程序行为异常. IPC 原子类型强制实施该要求, 并增加对地址无关等待与通知操作的支持.

需要注意, IPC 原子类型上的某些操作可能比非 IPC 的更昂贵. 这主要涉及等待与通知操作, 因为操作系统可能必须把原子对象的进程映射地址转换为物理地址. 此外, 当没有对进程间等待与通知操作的原生支持时 (如 has_native_wait_notify() 所示), 等待操作以忙循环模拟, 这可能影响系统的性能与功耗. 等待与通知操作的原生支持也可用 能力宏检测.

用户不得同时在同一个被引用对象上创建并使用 IPC 与非 IPC 原子引用. IPC 与非 IPC 原子引用不要求彼此通信. 例如, 非 IPC 原子引用上的等待操作可能不会被引用同一对象的 IPC 原子引用上的通知操作中断.

此外, 用户不得在栈上 (以及可能的其他非共享内存) 创建 IPC 原子对象. 若原子对象被放置在不受支持的内存类型中, 等待与通知操作在某些系统上可能不按预期工作. 例如, 在 Mac OS 上, 若 IPC 原子对象位于栈中, 通知操作已知会发生伪失败. 请在进程本地内存中使用常规原子对象. 用户还应避免在 IPC 原子操作运行期间修改内存属性. 例如, 在线程阻塞于等待操作时调整共享内存段大小, 可能会阻止后续通知操作唤醒被阻塞的线程.

栅栏 

#include <boost/atomic/fences.hpp>

栅栏通过以下操作实现:

语法

说明

void atomic_thread_fence(memory_order order)

发出用于与其他线程协调的栅栏.

void atomic_signal_fence(memory_order order)

发出用于与信号处理器协调的栅栏 (仅在同一线程内).

注意, atomic_signal_fence 不实现线程同步, 只充当阻止编译器 (而非 CPU) 重排代码的屏障. 此处的 order 实参指定栅栏阻止编译器重排代码的方向.

SMT 暂停提示 

#include <boost/atomic/thread_pause.hpp>

原子操作常用于紧凑循环 (也称为自旋循环), 其中反复尝试同一操作序列, 直到原子对象被成功更新. 在带 SMT 的现代处理器上, 这类紧凑循环可能导致次优性能, 因为它们可能占用本可由同一核心的兄弟线程使用的 CPU 核心资源. 本节描述的 thread_pause 操作在这种情况下可能有帮助:

语法

说明

void thread_pause()

提示 CPU 核心重新分配硬件资源, 以偏向其当前正在运行的其他兄弟线程.

thread_pause 的预期用例是在自旋循环内、某次迭代失败之后作为退避手段调用它. 该提示的效果取决于 CPU 体系结构, 并可能因 CPU 型号和制造商而异. 它也可能是空操作. 当不是空操作时, 它通常会将调用线程的执行暂停若干 CPU 时钟周期, 让兄弟线程有机会使用被释放的硬件资源继续推进, 并可能让调用线程在下一次自旋循环迭代中取得成功. 从操作系统的角度看, thread_pause 不会阻塞线程.
