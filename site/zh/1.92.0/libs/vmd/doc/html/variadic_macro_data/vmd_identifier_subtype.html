标识符子类型

标识符是宏程序员最常用来传递预处理数据的低级数据类型. 我们已经看到, VMD 有一套注册和检测标识符的系统, 使得它们可以作为预处理数据的一部分被解析. 该系统还包括使用 BOOST_VMD_EQUAL/BOOST_VMD_NOT_EQUAL 比较标识符的相等或不等, 以及在 BOOST_VMD_IS_IDENTIFIER 和 BOOST_VMD_ELEM 中使用标识符修饰符来匹配标识符. 这些设施共同为在宏中处理标识符提供了丰富的功能.

数和 v-type 都是标识符的子类型, 它们既可以作为各自独立的数据类型被单独识别, 也可以使用前面提到的标识符设施作为标识符来处理. 其中数在 Boost PP 库内还拥有一整套丰富的功能. 作为子类型, 数和 v-type 可以用作过滤修饰符, 并且在调用 BOOST_VMD_GET_TYPE 或使用返回类型修饰符时可以作为特定类型返回. 此外, VMD 在解析序列时会把它们各自的 v-type, 即 BOOST_VMD_TYPE_NUMBER 和 BOOST_VMD_TYPE_TYPE, 识别为 VMD 数据.

最终用户也可以定义自己的标识符子类型. 这被称为"用户定义子类型". 一旦创建了用户定义子类型, VMD 中数或 v-type 等子类型所拥有的所有通用类型设施都会自动适用于该用户定义子类型.

定义子类型

要定义一个用户定义子类型, 需要遵循若干步骤. 这些步骤将在下文详细说明:

  1. 注册并预先检测该子类型的所有标识符.
  2. 注册并预先检测该子类型的一个 v-type 名称.
  3. 对该子类型的所有标识符做子类型注册.
  4. 对该子类型的 v-type 名称做子类型注册.

在执行上述操作时, 最好把所有宏放在单个头文件中, 并且在我们以通用方式使用用户定义子类型时始终包含该头文件.

注册并预先检测该子类型的所有标识符

注册并预先检测子类型的所有标识符, 与注册并预先检测任何标识符完全相同.

让我们为虚构的 "udef" 库创建一些要使用的标识符. 我们将把所有宏放在头文件 udef_vmd_macros.hpp 中.

我们库中的标识符需要有独特的名称, 因此我们将在标识符名称后面附加 UDEF_ 使它们唯一. 我们的 udef 库处理几何图形, 因此我们将创建一个用户定义子类型, 它由我们的 udef 库可以在其宏中操纵的各种图形的标识符组成. 于是, 放在头文件中的标识符注册与预先检测将是:

#define BOOST_VMD_REGISTER_UDEF_CIRCLE (UDEF_CIRCLE)
#define BOOST_VMD_REGISTER_UDEF_SQUARE (UDEF_SQUARE)
#define BOOST_VMD_REGISTER_UDEF_TRIANGLE (UDEF_TRIANGLE)
#define BOOST_VMD_REGISTER_UDEF_HEXAGON (UDEF_HEXAGON)

#define BOOST_VMD_DETECT_UDEF_CIRCLE_UDEF_CIRCLE
#define BOOST_VMD_DETECT_UDEF_SQUARE_UDEF_SQUARE
#define BOOST_VMD_DETECT_UDEF_TRIANGLE_UDEF_TRIANGLE
#define BOOST_VMD_DETECT_UDEF_HEXAGON_UDEF_HEXAGON

注册并预先检测该子类型的一个 v-type 名称

我们需要为用户定义子类型创建一个唯一的 v-type 名称. 该名称不必以 BOOST_VMD_TYPE_ 开头, 但应该是唯一的. 由于 BOOST_VMD_TYPE_ 是所有 v-type 的共同开头, 为了保持一致性我们也将使用它, 并在其后附加 UDEF_SHAPES, 赋予它不应被重复的唯一性:

#define BOOST_VMD_REGISTER_BOOST_VMD_TYPE_UDEF_SHAPES (BOOST_VMD_TYPE_UDEF_SHAPES)

#define BOOST_VMD_DETECT_BOOST_VMD_TYPE_UDEF_SHAPES_BOOST_VMD_TYPE_UDEF_SHAPES

对该子类型的所有标识符做子类型注册

注册标识符子集的宏以 BOOST_VMD_SUBTYPE_REGISTER_ 开头, 然后在其后附加子集中的每个标识符. 这与使用 BOOST_VMD_REGISTER_ 宏的方式非常相似. 区别在于: BOOST_VMD_REGISTER_ 宏展开为一个其单个元素是该标识符的元组, 而 BOOST_VMD_SUBTYPE_REGISTER_ 展开为一个含两个元素的元组, 其中第一个元素是子类型的 v-type, 第二个元素是标识符.

对于我们的 udef 用户定义子类型, 这将是:

#define BOOST_VMD_SUBTYPE_REGISTER_UDEF_CIRCLE (BOOST_VMD_TYPE_UDEF_SHAPES,UDEF_CIRCLE)
#define BOOST_VMD_SUBTYPE_REGISTER_UDEF_SQUARE (BOOST_VMD_TYPE_UDEF_SHAPES,UDEF_SQUARE)
#define BOOST_VMD_SUBTYPE_REGISTER_UDEF_TRIANGLE (BOOST_VMD_TYPE_UDEF_SHAPES,UDEF_TRIANGLE)
#define BOOST_VMD_SUBTYPE_REGISTER_UDEF_HEXAGON (BOOST_VMD_TYPE_UDEF_SHAPES,UDEF_HEXAGON)

对该子类型的 v-type 名称做子类型注册

一旦理解了如何注册标识符子集, 对实际的 udef v-type 做子类型注册就相当容易了. 唯一需要认识到的是: 任何 v-type 的类型都是 v-type BOOST_VMD_TYPE_TYPE. 因此, 对我们的新 v-type BOOST_VMD_TYPE_UDEF_SHAPES 的子类型注册是:

#define BOOST_VMD_SUBTYPE_REGISTER_BOOST_VMD_TYPE_UDEF_SHAPES (BOOST_VMD_TYPE_TYPE,BOOST_VMD_TYPE_UDEF_SHAPES)

使用我们的标识符子集

一旦把上述用于定义用户定义子类型的所有对象式宏添加到 udef_vmd_macros.hpp 头文件中, 我们就拥有了一个新的数据类型, 可以像以通用方式使用数或 v-type 那样以通用方式使用它. 重要的是, 每当需要针对新数据类型的 VMD 功能时, 都要在某个翻译单元中包含头文件 udef_vmd_macros.hpp. 因此在示例中我们假定每个示例之前都有 '#include udef_vmd_macros.hpp'.

#include <boost/vmd/get_type.hpp>

#define A_SEQUENCE UDEF_SQUARE
#define A_SEQUENCE2 217
#define A_SEQUENCE3 BOOST_VMD_TYPE_UDEF_SHAPES
#define A_SEQUENCE4 BOOST_VMD_TYPE_NUMBER

BOOST_VMD_GET_TYPE(A_SEQUENCE) will return 'BOOST_VMD_TYPE_UDEF_SHAPES'
BOOST_VMD_GET_TYPE(A_SEQUENCE2) will return 'BOOST_VMD_TYPE_NUMBER'
BOOST_VMD_GET_TYPE(A_SEQUENCE3) will return 'BOOST_VMD_TYPE_TYPE'
BOOST_VMD_GET_TYPE(A_SEQUENCE4) will return 'BOOST_VMD_TYPE_TYPE'

这里我们看到, 当我们对一个属于用户定义子类型值的单元素序列使用 BOOST_VMD_GET_TYPE 宏时, 会正确地得到用户定义子类型的 v-type, 就像我们询问某个数的类型时那样. 同样, 当我们对用户定义子类型的 v-type 本身使用 BOOST_VMD_GET_TYPE 宏时, 会正确地得到所有 v-type 的类型, 即 BOOST_VMD_TYPE_TYPE, 就像我们询问某个数的 v-type 的类型时那样.

#include <boost/vmd/elem.hpp>

#define A_SEQUENCE5 (1,2) UDEF_TRIANGLE

BOOST_VMD_ELEM(1,A_SEQUENCE5,BOOST_VMD_RETURN_TYPE) will return '(BOOST_VMD_TYPE_UDEF_SHAPES,UDEF_TRIANGLE)'
BOOST_VMD_ELEM(0,A_SEQUENCE5,BOOST_VMD_RETURN_TYPE) will return '(BOOST_VMD_TYPE_TUPLE,(1,2))'

这里我们看到, 我们可以使用返回类型修饰符, 以二元组的形式同时得到用户定义子类型的类型和值, 就像对任何其他类型所做的那样.

#include <boost/vmd/equal.hpp>

#define A_SEQUENCE6 UDEF_CIRCLE
#define A_SEQUENCE7 168

BOOST_VMD_EQUAL(A_SEQUENCE6,UDEF_CIRCLE,BOOST_VMD_TYPE_UDEF_SHAPES) will return '1'
BOOST_VMD_EQUAL(A_SEQUENCE6,UDEF_CIRCLE,BOOST_VMD_TYPE_LIST) will return '0'
BOOST_VMD_EQUAL(A_SEQUENCE7,168,BOOST_VMD_TYPE_NUMBER) will return '1'
BOOST_VMD_EQUAL(A_SEQUENCE7,168,BOOST_VMD_TYPE_SEQ) will return '0'

这里可以看到, 我们可以对用户定义子类型的 v-type 使用过滤修饰符, 就像对任何其他 v-type (例如数的 v-type) 所做的那样.

无论从哪方面看, 一旦我们定义了子类型并在头文件中提供这些定义, 用户定义子类型在我们系统中的行为就与任何其他 v-type 一样. 由于 VMD 功能在很大程度上依赖于识别宏输入中数据的类型, 因此能够定义另一种 VMD 可以理解的"类型" (作为标识符子类型) 对宏程序员而言是有价值的.

标识符子类型值与 v-type 的唯一性

当我们定义一个新的标识符子类型时, 需要小心确保该子类型的值及其实际 v-type 在任何翻译单元内都是唯一的标识符. 这就是仅定义标识符与定义标识符子类型之间的主要区别.

回想一下, 当我们仅注册和预先检测标识符时, 即使相同的标识符已经在同一个翻译单元中注册和预先检测过, 也不会有问题. 因为在这种情况下我们只是重新定义完全相同的宏.

但对于标识符子类型, 当我们使用 BOOST_VMD_SUBTYPE_REGISTER_ 宏把子类型的 v-type 与子类型标识符关联起来时, 如果别人也使用与我们相同的标识符定义了一个标识符子类型, 我们就会遇到问题, 因为我们将以不同的展开重定义同一个对象式宏名. 即便别人只是注册/预先检测了我们要用于子类型的标识符而没有基于该标识符定义子类型, 我们定义子类型也会造成问题, 因为以通用方式返回序列或序列元素类型的 VMD 宏会把我们的子类型作为类型返回, 而不是某些程序员可能期望的 BOOST_VMD_TYPE_IDENTIFIER.

这一问题的要旨在于: 如果我们定义一个用户定义子类型, 其标识符需要在给定翻译单元内唯一, 而唯一的名称又让最终用户更难自然地使用宏. 在我们这个虚构 udef 库的示例中, 我们使用了 'UDEF_CIRCLE' 等标识符, 而不是听起来更自然的 CIRCLE. 因此, 使用用户定义标识符子类型存在权衡: 为了不与可能正在使用标识符子类型的其他人冲突, 我们的子类型标识符和子类型的 v-type 都需要唯一的标识符名称, 但这些唯一名称可能让宏的使用变得不那么"自然". 另一方面, 仅注册/预先检测标识符则没有这样的问题. 任何希望借助 VMD 定义用户定义子类型来创建自己数据类型的用户, 都应当意识到这个问题.
