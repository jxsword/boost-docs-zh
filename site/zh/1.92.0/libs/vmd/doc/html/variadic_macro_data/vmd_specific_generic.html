通用宏小结

VMD 用于处理其所能理解的数据类型的宏可以分为特定宏和通用宏.

特定宏询问某些输入数据是否是特定数据类型. 通用宏将输入数据当作任意数据类型处理, 同时也允许程序员单独查询数据的类型.

特定宏和通用宏各有其用武之地, 宏程序员可以根据具体情况决定使用哪一种.

VMD 有许多用于解析数据类型的特定宏. 这些宏各自询问某个输入是否是特定的 VMD 数据类型.

空

传递空参数

可以向宏传递一个空参数. C++ 标准中对这一情况的官方术语是"由零个预处理记号组成的"参数. 向宏传递空参数是 C++11 标准的正式组成部分, 但许多编译器在不严格遵循标准的条件下也支持在 C++98/C++03 模式下向宏传递空参数.

让我们考虑若干情形, 而不必太在意宏输出代表什么.

考虑这两个类函数宏:

#define SMACRO() someoutput
#define EMACRO(x) otheroutput x

第一个宏不接受任何参数, 因此调用它必须始终采用如下方式

SMACRO()

向它传递任何参数都是无效的.

第二个宏接受单个参数. 它可以按如下方式调用

EMACRO(somedata)

但也可以按如下方式调用

EMACRO()

在第二次调用 EMACRO 时, 我们向该宏传递了一个空参数. 类似地, 对于任何拥有 1 个或多个参数的宏, 都可以为其中任意参数有效地传递空参数, 如下所示:

#define MMACRO(x,y,z) x y z

MMACRO(1,,2)

即使我们没有传递任何内容, 空参数也是一个参数.

能够为宏的某个给定参数传递空参数, 并不意味着就应该这么做. 任何给定的宏都会规定其每个参数应当代表什么, 而且通常极少遇到明确规定可以为某个参数传递空参数的宏. 但从标准 C++ 的角度看, 为宏参数传递空参数是完全有效的.

传递空参数的概念可以扩展到在略微复杂的情况下传递"由零个预处理记号组成的"空数据. 可以以变参宏数据的形式把空数据作为参数传递给变参宏, 如下所示:

#define VMACRO(x,...) x __VA_ARGS__

调用方式如下:

VMACRO(somedata,)

这里我们把空数据作为变参宏数据传递, 这是完全有效的 C++. 请注意, 这不同于

VMACRO(somedata)

后者在 C++20 之前不是有效的 C++, 因为必须为变参参数传递某些内容. 在 C++20 中, 上面的调用是有效的, 并且与我们前一个示例 'VMACRO(somedata,)' (把空数据作为变参宏数据传递) 完全相同. 类似地, 也可以按如下方式调用该宏:

VMACRO(somedata,vdata1,,vdata3)

其中传递了变参宏数据, 但变参宏数据中的一个元素是空.

此外, 如果我们调用的宏期望一个 Boost PP 数据类型 (例如元组), 我们也可以有效地为元组中的全部或部分数据传递空数据, 如下所示:

#define TMACRO(x,atuple) x atuple

TMACRO(somedata,())

在这种情况下, 我们传递的是一个 1 元素的元组, 其中的单个元素本身是空.

或者

TMACRO(somedata,(telem1,,telem2,teleem3))

在这种情况下, 我们传递的是一个 4 元素的元组, 其中的第二个元素是空.

这两种调用同样是有效的 C++, 但并不一定是宏设计者所期望的, 即使在这两种情况下宏设计者都规定第二个参数必须是元组宏才能正常工作.

返回空

与以各种方式向宏传递空参数类似, 宏返回的数据 (或者用"生成"这个词可能更贴切) 也可以以各种方式为空. 同样, 我并非在提倡把这种做法作为宏设计的常见形态, 而只是指出它是有效的 C++ 预处理.

#define RMACRO(x,y,z)

RMACRO(data1,data2,data3)

从宏调用中返回 "nothing" 是完全有效的 C++. 实际上 Boost PP 中的许多宏都会基于宏的预处理元编程逻辑这样做, 并且在文档中也如此说明.

类似地, 可以返回空作为 Boost PP 数据类型的一部分或全部, 甚至作为变参宏数据的一部分.

#define TRETMACRO(x,y,z) ()
#define TRETMACRO1(x,y,z) (x,,y,,z)
#define VRETMACRO(x,y,z) x,,y,,z

这里我们同样返回了某些内容, 但就 Boost PP 元组或变参数据而言, 其中有些元素是空.

预处理元编程中的空

在上面给出的示例中, 某种形式的"空"被作为参数传递给宏或从宏返回, 我给出的这些示例都尽可能简化以说明我的观点. 在使用 Boost PP 的实际预处理元编程中, 如果使用复杂的逻辑基于宏的参数生成宏输出, 那么在能够测试数据确实为空的前提下, 允许并处理空数据可能会很有用.

测试空数据

目前 Boost PP 有一个未写入文档的宏, 用于测试参数是否为空. 该宏名为 BOOST_PP_IS_EMPTY. 该宏天生有缺陷, 因为在 C++20 之前, 使用 C++ 预处理器没有通用的方法来判断参数是否为空. 但该宏对几乎所有非空输入, 或输入确实为空的情况, 都能正确工作.

Boost PP 的开发者 Paul Mensonides 编写了 BOOST_PP_IS_EMPTY 宏的代码, 使用变参宏来判断参数是否为空, 他最初将其发布在互联网上以回应一场关于空的讨论. 我为 Boost PP 库改编了他的代码, 并为 VMD 基于他的原始示例开发了自己的略有不同的代码.

该宏名为 BOOST_VMD_IS_EMPTY, 如果输入为空则返回 1, 输入不为空则返回 0. 该宏是一个变参宏, 可以接受任意输入 [1].

标准 C++ 编译器下的宏缺陷

在 C++20 之前, 该宏不能正常工作的唯一情形是: 其输入解析为一个类函数宏的名字, 或解析为一个以类函数宏名字结尾的预处理记号序列, 且该类函数宏接受两个或更多参数.

下面是一个简单的示例:

#include <boost/vmd/is_empty.hpp>

#define FMACRO(x,y) any_output

BOOST_VMD_IS_EMPTY(FMACRO)
BOOST_VMD_IS_EMPTY(some_input FMACRO)

第一种情况是向 BOOST_VMD_IS_EMPTY 传递一个类函数宏的名字, 第二种情况是向 BOOST_VMD_IS_EMPTY 传递一个以类函数宏名字结尾的预处理记号序列. 该类函数宏还有两个 (或更多) 参数. 在上述两种情况下, 使用 BOOST_VMD_IS_EMPTY 都会产生编译器错误.

请注意, 这两种有问题的情形不同于向 BOOST_VMD_IS_EMPTY 传递一个类函数宏的调用, 如下所示:

#include <boost/vmd/is_empty.hpp>

BOOST_VMD_IS_EMPTY(FMACRO(arg1,arg2))
BOOST_VMD_IS_EMPTY(someinput FMACRO(arg1,arg2))

这种方式总能正确工作, 当然除非某个特定的类函数宏调用解析成了前面两种情形之一.

该宏可能无法正常工作的另一种情形是: 前面提到的类函数宏只接受单个参数, 但在传递的参数为空时会产生错误. 例如:

#define FMACRO(x) BOOST_PP_CAT(+,x C);

当什么都没传给 FMACRO 时会发生未定义行为, 因为在 C++ 预处理器术语中, 将 '+' 拼接到 ' C' 上是未定义行为.

因此对于 C++20 之前符合标准的编译器, 我们基本上有两个让 BOOST_VMD_IS_EMPTY 不起作用的边角情况, 而当它不起作用时, 产生的是编译器错误而不是错误的结果. 从最大安全性的角度出发, 我们本质上应该做到: 在测试空时永远不要传递以类函数宏名字结尾的输入.

Visual C++ 下的宏缺陷

在与我们讨论空相关的至少两种情形下, VC++ 默认预处理器并不是符合标准 C++ 的预处理器. 这些情形共同造成了一个单一的边角情况, 使得当输入解析为类函数宏名字时, 使用带默认预处理器的 VC++, BOOST_VMD_IS_EMPTY 宏无法正常工作.

与我们讨论空相关的第一种情形 (VC++ 默认预处理器不是符合标准 C++ 的预处理器) 是: 如果一个接受 'n' 个参数的宏以 0 到 'n-1' 个参数被调用, 编译器不报错, 而只给出警告.

#define FMACRO(x,y) x + y

FMACRO(1)

这本应产生编译器错误 (使用符合 C++ 标准的编译器时确实如此), 但使用带默认预处理器的 VC++ 调用时只给出警告, VC++ 继续进行宏替换, 'y' 成为一个占位符预处理记号. 这种不符合标准的做法实际上消除了 BOOST_VMD_IS_EMPTY 在符合标准 C++ 的编译器上无法正常工作的情形. 但当然, 在其他与 BOOST_VMD_IS_EMPTY 调用无关的宏处理情形中, 本应产生编译器错误的地方, 它有可能产生错误的输出.

与我们讨论空相关的第二种一般情形 (VC++ 默认预处理器不是符合标准 C++ 的预处理器) 是: 当被展开的宏是一个类函数宏名字后跟一个类函数宏调用时, 宏的展开会出错, 此时宏的重复展开会被错误地执行不止一次. 后一种情形可以通过这个示例看到:

#define FMACRO1(parameter) FMACRO3 parameter()
#define FMACRO2() ()
#define FMACRO3() 1

FMACRO1(FMACRO2)

should expand to:

FMACRO3()

but in VC++ with its default preprocessor it expands to:

1

在最初将宏展开为:

FMACRO3 FMACRO2()

之后, VC++ 错误地对预处理记号序列重新扫描了不止一次, 而不是只为寻找更多宏名字再重新扫描一次.

VC++ 编译器带默认预处理器时存在的这两个特定的预处理器缺陷意味着: 尽管 BOOST_VMD_IS_EMPTY 在与前面给定的符合标准 C++ 编译器相同的情形下不会以编译器错误的方式失败, 但它会在另一种情形下以给出错误结果的方式失败.

失败的情形是:

当 BOOST_VMD_IS_EMPTY 的输入只解析为一个类函数宏的名字, 且该类函数宏在传入单个空参数时会展开为一个 Boost PP 元组时, 使用 Visual C++ 编译器时 BOOST_VMD_IS_EMPTY 会错误地返回 1, 而不是给出预处理错误或返回 0.

下面是这种失败的一个示例:

#include <boost/vmd/is_empty.hpp>

#define FMACRO4() ( any_number_of_tuple_elements )
#define FMACRO5(param) ( any_number_of_tuple_elements )
#define FMACRO6(param1,param2) ( any_number_of_tuple_elements )

BOOST_VMD_IS_EMPTY(FMACRO4) // erroneously returns 1, instead of 0
BOOST_VMD_IS_EMPTY(FMACRO5) // erroneously returns 1, instead of 0
BOOST_VMD_IS_EMPTY(FMACRO6) // erroneously returns 1, instead of generating a preprocessing error

与 C++20 之前符合标准的编译器一样, 我们遇到了 BOOST_VMD_IS_EMPTY 无法正常工作的罕见边角情况, 但不幸的是, 在这个非常相似却更为罕见的、使用带默认预处理器的 VC++ 的边角情况中, 我们会悄无声息地得到错误的结果, 而不是编译器错误.

我想重申, 对于 C++20 之前的所有编译器, C++ 中不存在检测空的完美解决方案, 即使预处理器的预处理完全符合标准的 C++ 编译器也不行, 而带默认预处理器的 VC++ 显然不符合标准.

在 C++20 模式下测试空

目前一些编译器可以以 C++20 模式运行, 我的意思是可以在使用这类编译器编译时传入一个编译器标志来强制即将到来的 C++20 标准. C++20 标准的特性之一是增加了名为 __VA_OPT__ 的预处理器构造. 由于 __VA_OPT__ 构造在 C++20 中的规范工作方式, 现在可以让 BOOST_VMD_IS_EMPTY 宏完美地测试空, 而没有该宏在 C++20 之前各级 C++ 标准中存在的任何缺陷. 但该宏只有在编译器以 C++20 模式编译时才能进行 100% 可靠的空测试. 对于 C++20 之前的各级 C++ 标准 (如 C++98, C++03, C++11, C++14 和 C++17), 空测试存在前面已经讨论过的阻碍其完美工作的边角情况.

此外, 在 C++20 模式下, 编译器仍有可能尚未支持 __VA_OPT__ 构造, 即使它是 C++20 标准的一部分. 幸运的是, 可以测试编译器在 C++20 模式下是否支持 __VA_OPT__ 构造, 而 BOOST_VMD_IS_EMPTY 的宏实现在使用该构造之前就会进行这种测试, 以提供完全可靠的空测试实现.

所有这些的结果是: 当编译器使用 C++20 标准编译源代码, 并且支持 C++20 的 __VA_OPT__ 预处理器构造时, 该实现提供了一种使用 BOOST_VMD_IS_EMPTY 宏测试空的完全可靠的方式. 否则, BOOST_VMD_IS_EMPTY 宏具有前面讨论过的边角情况, 使其在测试空时达不到 100% 可靠. 好消息当然是, 会有更多编译器实现 C++20 标准, 更多 C++ 程序员会使用 C++20 标准来编译他们的代码.

程序员可以通过传递给编译器的命令行参数知道编译器是否以 C++20 模式使用, 也可以从编译器的文档了解 C++20 模式下的编译器是否支持 C++20 的 __VA_OPT__ 构造. 但从预处理器编程的角度来看, 最好能用一个宏查明当前是否正在使用带 __VA_OPT__ 构造的 C++20 模式, 这样 BOOST_VMD_IS_EMPTY 宏在测试空时就可以被认为是完全可靠的. 这样的宏已经存在于 Boost Preprocessor 库中, 名为 BOOST_PP_VARIADIC_HAS_OPT. 你可以在 Boost Preprocessor 库文档中阅读该宏的文档, 但我在这里会快速概述它的工作方式. 该宏是一个不接受参数的类函数宏, 如果编译器处于 C++20 模式且支持 __VA_OPT__ 则返回 1, 否则返回 0. 以 BOOST_PP_VARIADIC_HAS_OPT() 形式调用该宏所需的头文件包含如下:

#include <boost/preprocessor/variadic/has_opt.hpp>

程序员不必处于 C++20 编译模式也可以调用 BOOST_PP_VARIADIC_HAS_OPT 宏. 当程序员不在 C++20 模式时, 调用该宏总是返回 0. 当程序员处于 C++20 模式时, 调用该宏在支持 __VA_OPT__ 构造时返回 1, 在不支持 __VA_OPT__ 构造时返回 0. 后一种判断是通过巧妙的预处理器编程实现的.

宏缺陷小结

综上所述, BOOST_VMD_IS_EMPTY 工作不正确的情形非常少, 即使在使用有缺陷的 VC++ 默认预处理器时也是如此. 我认为该宏值得使用, 因为它对绝大多数可能的预处理输入都能正确工作, 并且在 C++20 模式下 (带 __VA_OPT__ 预处理器支持) 总能正确工作.

它无法工作的情形 (无论在符合 C++ 标准的预处理器下还是在 Visual C++ 下) 是: 类函数宏的名字成为 BOOST_VMD_IS_EMPTY 输入的一部分. 显然, 当输入可能的范围经过约束而排除了出错情形时, 预处理元程序员才应当使用该宏.

由于空几乎在每种情况下都能被正确测试, 当预处理元程序员想从宏返回数据且该数据的全部或一部分可能为空时, 可以在内部使用 BOOST_VMD_IS_EMPTY 宏.

因此我认为 BOOST_VMD_IS_EMPTY 宏相当有用, 尽管使其不完美的边角情况缺陷依然存在. 因此我认为预处理元程序员可以在自己的宏设计中使用空预处理数据的概念.

使用该宏

宏 BOOST_VMD_IS_EMPTY 在 VMD 内部被广泛使用, 尽管它在 C++20 之前模式下的工作方式略有缺陷, 宏程序员仍可能在自己的编程工作中发现该宏很有用.

你可以使用通用头文件:

#include <boost/vmd/vmd.hpp>

或者你也可以使用独立头文件:

#include <boost/vmd/is_empty.hpp>

用于 BOOST_VMD_IS_EMPTY 宏.

宏约束

在讨论 BOOST_VMD_IS_EMPTY 宏时, 我提到过对该宏输入的约束. 现在我将讨论这对于预处理元编程以及一般宏输入意味着什么.

受约束的输入

当程序员在 C++ 中设计任何类型的可调用对象 (函数, 成员函数等) 时, 他会规定输入的类型和返回值的类型. C++ 编译器会在编译期强制执行这一规定. 类似地, 在运行期, 可调用对象可以检查其输入是否落在某些已文档化、已定义的边界之内, 并在越界时做出相应反应. 这都是 C++ 中任何可调用对象约束的一部分, 任何优秀的程序员都应当将其文档化.

C++ 预处理器比 C++ 编译器"笨"得多, 即使有了 Paul Mensonides 在 Boost PP 中创建的预处理元编程构造, 预处理元程序员在预处理期对宏参数输入施加约束的能力, 也远少于程序员在编译期和/或运行期对 C++ 可调用对象的参数输入施加约束的能力. 尽管如此, 把宏期望的参数输入文档化是完全有效的, 而且如果程序员不遵守约束, 宏将无法正常工作. 在预处理元编程的理想情况下, 宏能够判断约束是否被满足, 并在未满足时发出某种可理解的预处理错误, 但即便在基于 Boost PP 的预处理元编程的现实条件下, 这也并非总是可行. 尽管如此, 如果宏的使用者没有遵守所调用特定宏文档中规定的宏参数约束, 发生的任何错误都是该使用者的责任. 我意识到这可能与一个根深蒂固的观念相冲突, 即编程错误必须总是以某种编译期或运行期的现象呈现出来, 让程序员能够纠正错误, 而不是以掩盖错误的静默失败呈现. 由于预处理器比较"笨", 无法在所有情况下提供这样的现象, 不幸的是错误可能被掩盖, 即使文档规定了正确的输入约束. 对于前面已经讨论过的 BOOST_VMD_IS_EMPTY 宏而言, 这种错误掩盖只可能发生在不符合 C++ 标准的预处理器 (Visual C++) 上.

Boost PP 库确实有一种在不产生预处理器输出的情况下生成预处理错误的方法, 但这种方法同样不能用于 Visual C++ 不符合标准的预处理器. 使用 Boost PP 的手段是 BOOST_PP_ASSERT 宏. 正如后面将要看到和讨论的, VMD 有一个等效的宏, 它可以通过产生错误的 C++ 输出而不是预处理错误来与 Visual C++ 配合工作, 但即便如此也不是完整的解决方案, 因为产生的错误 C++ 输出可能被隐藏.

即使努力产生预处理错误, 或产生引发编译期错误的错误输出, 也解决不了预处理元编程中受约束输入的问题. 通常无法确定输入是否满足预处理元程序员对其施加并文档化的约束. 某些预处理记号无法在不使检查机制本身产生预处理错误或未定义行为的情况下, 可靠地检查特定值或值范围.

这并不意味着应该放弃检查宏输入约束的尝试. 如果可以做到, 我认为这样的检查是有价值的, 后面要讨论的一些 VMD 宏就被设计为预处理输入约束检查宏. 但处理宏输入约束时最重要的事情是: 应当仔细地将约束文档化, 并且程序员应当知道, 如果不满足约束, 结果可能是预处理错误或不正确的宏结果.

VMD 库为了提供更多的预处理器编程功能和灵活性, 允许在某些输入约束不满足时出现错误结果, 无论是预处理错误还是 VMD 宏的不正确输出. 与此同时, VMD 尽预处理器所能做的一切来检查输入约束, 并为库中的每个宏仔细文档化各自的输入可能是什么, 以避免错误输出.

在预处理器中, 已文档化的宏输入约束与 C++ 中编译期/运行期约束同样有效, 即使此类约束的检测和/或对未满足约束的处理, 在预处理器中比在 C++ 的编译期/运行期处理中要困难得多, 甚至不可能.

VMD 库对其大多数宏使用约束, 这些宏的文档提到了使用该宏所适用的约束.

  • 作为整数字面量记号的预处理记号 'pp-number'.

测试任意标识符的问题

预处理元编程中标识符的一个难点是安全地测试某个特定标识符. VMD 提供了一种在特定约束下做到这一点的方法, 该约束针对作为测试输入的字符.

该约束是: 输入必须为空, 或者作为测试输入传递的开头输入字符 (忽略任何空白) 必须是以下之一:

  • 一个标识符字符, 即字母数字字符或下划线
  • 元组的左括号

并且如果第一个字符不是元组的左括号, 那么其余字符必须直到出现空格字符或输入结束为止都是字母数字字符或下划线

如果不是这样, 行为是未定义的, 并且很可能发生预处理错误.

给定输入:

's_anything' : can be tested
'S_anything' : can be tested
's_anYthiNg' : can be tested
'_anything' : can be tested
'_Anything' : can be tested
'_anytHIng' : can be tested
'24' : can be tested
'245e2' : can be tested
'(anything)' : can be tested, tuple
'(anything) anything' : can be tested, tuple and further input
'anything anything' : can be tested, identifier followed by space character

'%_anything' : undefined behavior and most likely a preprocessing error due to the constraint
'(_anything' : undefined behavior and most likely a preprocessing error due to the constraint, since a single '(' does not form a tuple
'44.3' : undefined behavior and most likely a preprocessing error due to the constraint since '.' is not alphanumeric
识别标识符

VMD 中有三个层级的标识符测试.

  1. 你可以测试任何匹配标识符语法的一般标识符
  2. 你可以测试某个特定标识符
  3. 你可以测试某个特定标识符是否等于另一个特定标识符
测试任意一般标识符

用于测试任意标识符的宏名为 BOOST_VMD_IS_GENERAL_IDENTIFIER.

你按上面给出的规则用可能为标识符的输入调用它, 如果输入具有标识符的形式则返回 1, 如果输入不具有标识符的形式则返回 0. 请注意, 不遵循上述约束的输入很可能导致未定义行为. 此外, 传给 BOOST_VMD_IS_GENERAL_IDENTIFIER 的输入应当是单个标识符, 而不是由预处理记号组成的 VMD 序列, 否则返回值可能不正确. 示例代码:

#include <boost/vmd/is_generaL_identifier.hpp>

BOOST_VMD_IS_GENERAL_IDENTIFIER(some_input) // returns 1 if 'some_input' is in the form of an identifier, else returns 0

这种遵循标识符语法的标识符形式被称为"一般"标识符. 一般标识符可以使用 VMD 特定宏成功测试, 但不能使用 VMD 通用宏成功测试. 对于后者, 你需要特定标识符.

测试特定标识符

尽管测试宏输入是否为上述任意一般标识符的形式有时很有用, 但查明宏输入是否是你特别感兴趣的一组特定标识符之一也很有价值. 为此, 你首先创建一个"注册"特定标识符的用户定义宏. 该用户定义宏是一个对象式宏, 其形式为:

#define BOOST_VMD_REGISTER_identifier (identifier)

其中 'identifier' 是我们希望识别的特定标识符. 在 VMD 中这被称为注册宏.

用于测试特定标识符的宏名为 BOOST_VMD_IS_IDENTIFIER.

#include <boost/vmd/is_identifier.hpp>

#define BOOST_VMD_REGISTER_yellow (yellow)
#define BOOST_VMD_REGISTER_green  (green)
#define BOOST_VMD_REGISTER_blue   (blue)

BOOST_VMD_IS_IDENTIFIER(some_input) // returns 1 if 'some_input' is 'yellow','green', or 'blue'
BOOST_VMD_IS_IDENTIFIER(some_input) // returns 0 if 'some_input' is 'purple'

建议在头文件中创建注册宏, 并在最终用户使用 VMD 的标识符宏之前包含该头文件; 当然如果你愿意, 也可以直接在源文件中创建注册宏. 如果某个特定注册宏出现了不止一次, 这并不是预处理错误, 因此重复注册宏不会导致任何问题, 因为同名注册宏的对象式宏展开完全相同. 在给定的翻译单元内, 可能会出现注册宏已被某个 VMD 最终用户并未创建的头文件包含的情况. 这同样不应导致特定的问题, 因为注册是为任何特定翻译单元添加特定标识符的过程.

正如我们将在文档后面进一步看到的, 只有特定标识符才能在使用 VMD 通用宏和解析 VMD 序列时被测试, 因此在 VMD 中, 一个不是特定标识符而只是一般标识符的标识符用途有限.

测试标识符相等

尽管注册一个标识符可以让 VMD 在使用 BOOST_VMD_IS_IDENTIFIER 时把该字符串识别为特定的 VMD 标识符, 但要检测某个特定标识符是否与另一个特定标识符完全相同, 需要最终用户定义另一个宏:

#define BOOST_VMD_DETECT_identifier_identifier

其中 'identifier' 是我们希望检测的特定标识符. 这个对象式宏必须展开为空输出.

与注册宏一样, 同一标识符在翻译单元中出现多个检测宏不会引起编译器问题, 因为出现的对象式宏完全相同.

创建该宏的术语是我们可能已经"预先检测"了该标识符. 我将把创建 BOOST_VMD_DETECT 宏的过程称为预先检测 (pre-detected), 把查明某个特定标识符是否与另一个特定标识符相同的能力称为检测 (detect).

检测 VMD 标识符是否为某个特定标识符的能力, 用于 VMD 宏在使用宏 BOOST_VMD_EQUAL 和 BOOST_VMD_NOT_EQUAL 比较预处理数据的相等/不等时, 以及当我们想使用宏 BOOST_VMD_IS_IDENTIFIER 并传入多于上述单个变参参数, 将一个标识符与一组特定的其他已注册标识符进行匹配时.

这些情形将在文档后面讨论 VMD 宏功能的其他主题中说明. 如果程序员从不使用这些情形所涵盖的功能, 即把一个特定标识符与另一个标识符匹配以查看它们是否相等, 那么对已注册标识符就不需要做预先检测. 然而, 一旦你提供了注册宏以便在预处理输入中测试某个特定标识符, 再为该标识符提供一个预先检测宏, 在宏记法方面的代价极小, 在预处理器时间方面则毫无代价. 因此, 即使最终用户最初不认为他可能想测试该标识符与另一个标识符的相等性, 也可以在创建相应注册宏的同一位置或头文件中为特定标识符添加预先检测宏.

总结一下标识符功能的三个层级:

  • 一般标识符可以与 VMD 特定宏一起使用并返回正确结果, 但不能与 VMD 通用宏一起使用.
  • 特定标识符 (即已注册的标识符) 可以与 VMD 特定宏以及几乎所有 VMD 通用宏一起使用.
  • 经过预先检测的特定标识符可以与所有 VMD 宏一起使用, 无论特定宏还是通用宏.
解析标识符的约束与未定义行为

上面提到的标识符约束之所以存在, 是因为解析标识符的技术 (在确定被解析的输入不为空或不以一组括号开头之后) 在解析中使用了预处理器拼接. 该技术涉及使用预处理器 '##' 运算符拼接输入, 并检查拼接的结果. 使用预处理器拼接时, 拼接的结果必须是有效的预处理记号, 否则预处理器的行为是未定义的. 在 C++ 中, "未定义行为"通常意味着任何事情都可能发生. 在实际使用中, 当预处理器拼接没有产生有效的预处理记号时, 编译器最有可能产生预处理错误. 如果编译器选择在拼接没有产生有效预处理记号时不发出预处理错误, VMD 宏的结果将总是正确的, 并且解析标识符会失败. 但由于结果是未定义行为, 当使用预处理器拼接且被解析的输入不满足本主题开头提到的解析标识符约束时, 程序员没有绝对的方法确定结果会是什么.

在本文档中, 我将使用缩写 'UB' 作为 'undefined behavior' (未定义行为) 的简写, 表示 VMD 尝试使用预处理器拼接解析预处理输入时会发生未定义行为的特定情形.

用法

要使用 BOOST_VMD_IS_GENERAL_IDENTIFIER 宏和/或 BOOST_VMD_IS_IDENTIFIER 宏, 你可以包含通用头文件:

#include <boost/vmd/vmd.hpp>

或者包含特定头文件:

#include <boost/vmd/is_general_identifier.hpp>
#include <boost/vmd/is_identifier.hpp>

但不包括:

测试任意数的问题

从标识符的解释可以看出, 数只是所有可能标识符的一个小子集, VMD 在内部为它的使用提供了注册宏和预先检测宏. 因此对测试输入的特定约束与标识符完全相同.

该约束是: 作为测试输入传递的开头输入字符 (忽略任何空白) 必须是以下之一:

  • 一个标识符字符, 即字母数字字符或下划线
  • 元组的左括号

并且如果第一个字符不是元组的左括号, 那么其余字符必须直到出现空格字符或输入结束为止都是字母数字字符或下划线.

如果不是这样, 行为是未定义的, 并且很可能发生预处理错误.

数的测试宏

在 VMD 中用于测试任意数的宏名为 BOOST_VMD_IS_NUMBER. 该宏接受单个变参参数, 即要对照测试的输入.

如果该参数是 Boost PP 数, 宏返回 1, 否则宏返回 0.

Boost PP 库拥有大量处理数的功能, 因此一旦你使用 VMD 解析/测试一个数, 就可以使用 Boost PP 以各种方式处理该数. VMD 库不会尝试复制 Boost PP 库中数的功能.

任何数同时也是经过注册和预先检测的标识符, 因此如果你愿意, 也可以使用 VMD 处理标识符的功能, 把数当作标识符来处理.

示例

让我们看一个如何使用 BOOST_VMD_IS_NUMBER 的示例.

#include <boost/vmd/is_number.hpp>

BOOST_VMD_IS_NUMBER(input)

returns:

if input = 0, 1
if input = 44, 1
if input = SQUARE, 0
if input = 44 DATA, 0 since there are tokens after the number
if input = 044, 0 since no leading zeros are allowed for our Boost PP numbers
if input = 256, 1
if input = 1025, 0 since it falls outside the Boost PP number range of 0-BOOST_PP_LIMIT_MAG
if input = %44, does not meet the constraint therefore undefined behavior
if input = 44.0, does not meet the constraint therefore undefined behavior
if input = ( 44 ), 0 since the macro begins with a tuple and this can be tested for
用法

要使用 BOOST_VMD_IS_NUMBER 宏, 要么包含通用头文件:

#include <boost/vmd/vmd.hpp>

要么包含特定头文件:

#include <boost/vmd/is_number.hpp>

类型宏

标识符的一个子集是 VMD 类型, 称为 'v-type'. 这些是代表 VMD 可以解析的所有预处理数据类型的标识符. 这个标识符子集由 VMD 自动注册和预先检测. 每个标识符类型都以唯一的前缀 'BOOST_VMD_TYPE_' 开头.

实际的类型有:

  • BOOST_VMD_TYPE_EMPTY, 表示空, 即"空数据"
  • BOOST_VMD_TYPE_ARRAY, 一个 Boost PP 数组
  • BOOST_VMD_TYPE_LIST, 一个 Boost PP 列表
  • BOOST_VMD_TYPE_SEQ, 一个 Boost PP seq
  • BOOST_VMD_TYPE_TUPLE, 一个 Boost PP 元组
  • BOOST_VMD_TYPE_IDENTIFIER, 标识符
  • BOOST_BMD_TYPE_NUMBER, 一个数
  • BOOST_VMD_TYPE_TYPE, 类型本身
  • BOOST_VMD_TYPE_SEQUENCE, 一个序列
  • BOOST_VMD_TYPE_UNKNOWN, 未知类型

由于 v-type 本身是一个标识符, 对测试输入的特定约束与标识符完全相同.

该约束是: 作为测试输入传递的开头输入字符 (忽略任何空白) 必须是以下之一:

  • 一个标识符字符, 即字母数字字符或下划线
  • 元组的左括号

并且如果第一个字符不是元组的左括号, 那么其余字符必须直到出现空格字符或输入结束为止都是字母数字字符或下划线.

如果不是这样, 行为是未定义的, 并且很可能发生预处理错误.

在 VMD 中用于测试特定类型的宏名为 BOOST_VMD_IS_TYPE. 该宏接受单个变参参数, 即要对照测试的输入.

如果该参数是 v-type, 宏返回 1, 否则宏返回 0.

v-type 同样是经过注册和预先检测的标识符, 因此如果你愿意, 也可以使用 VMD 处理标识符的功能, 把 v-type 当作标识符来处理.

示例

让我们看一个如何使用 BOOST_VMD_IS_TYPE 的示例.

#include <boost/vmd/is_type.hpp>

BOOST_VMD_IS_TYPE(input)

returns:

if input = BOOST_VMD_TYPE_SEQ, 1
if input = BOOST_VMD_TYPE_NUMBER, 1
if input = SQUARE, 0
if input = BOOST_VMD_TYPE_IDENTIFIER DATA, 0 since there are tokens after the type
if input = %44, does not meet the constraint therefore undefined behavior
if input = ( BOOST_VMD_TYPE_EMPTY ), 0 since the macro begins with a tuple and this can be tested for
用法

要使用 BOOST_VMD_IS_TYPE 宏, 要么包含通用头文件:

#include <boost/vmd/vmd.hpp>

要么包含特定头文件:

#include <boost/vmd/is_type.hpp>

VMD 与 Boost PP 数据类型

VMD 能够判断预处理输入是否是给定的 Boost PP 数据类型. 用于此目的的 VMD 宏是:

  • BOOST_VMD_IS_ARRAY 用于数组
  • BOOST_VMD_IS_LIST 用于列表
  • BOOST_VMD_IS_SEQ 用于 seq
  • BOOST_VMD_IS_TUPLE 用于元组

这些宏各自接受单个变参参数作为输入, 如果该参数是对应的数据类型则返回 1, 否则返回 0.

语法上的特异之处

数组和非空列表同时也是元组. 因此如果拥有:

#define ANARRAY (3,(a,b,c))
#define ALIST (a,(b,(c,BOOST_PP_NIL)))
#define ATUPLE (a,b,c)
#define ASEQ (a)(b)(c)

then 

#include <boost/vmd/is_tuple.hpp>

BOOST_VMD_IS_TUPLE(ANARRAY) returns 1
BOOST_VMD_IS_TUPLE(ALIST) returns 1
BOOST_VMD_IS_TUPLE(ATUPLE) returns 1
BOOST_VMD_IS_TUPLE(ASEQ) returns 0

第一个元素为数 2 且第二个元素不是列表结束标记 BOOST_PP_NIL 的列表同时也是数组. 因此如果拥有:

#define ALIST (2,(3,BOOST_PP_NIL))
#define ALIST2 (2,(3,(4,BOOST_PP_NIL)))
#define ALIST3 (2,BOOST_PP_NIL)

#include <boost/vmd/is_array.hpp>
#include <boost/vmd/is_list.hpp>

BOOST_VMD_IS_LIST(ALIST) returns 1
BOOST_VMD_IS_LIST(ALIST2) returns 1
BOOST_VMD_IS_LIST(ALIST3) returns 1
BOOST_VMD_IS_ARRAY(ALIST) returns 1
BOOST_VMD_IS_ARRAY(ALIST2) returns 1
BOOST_VMD_IS_ARRAY(ALIST3) returns 0

单元素元组同时也是单元素 seq. 因此如果拥有:

#define ASE_TUPLE (a)

then 

#include <boost/vmd/is_seq.hpp>
#include <boost/vmd/is_tuple.hpp>

BOOST_VMD_IS_TUPLE(ASE_TUPLE) returns 1
BOOST_VMD_IS_SEQ(ASE_TUPLE) returns 1

然而如果我们的数据由多于一个连续的单元素元组组成, 该数据总是 seq:

#include <boost/vmd/is_seq.hpp>
#include <boost/vmd/is_tuple.hpp>

#define ST_DATA (somedata)(some_other_data)

BOOST_VMD_IS_SEQ(ST_DATA) will return 1
BOOST_VMD_IS_TUPLE(ST_DATA) will return 0
测试数组时的问题

数组的形式是一个二元组, 其中第一个元素是一个数, 第二个元素是一个元组. 该数规定元组的大小. 由于使用变参宏时从不需要规定元组的大小, 数组在很大程度上已经过时. 不过 VMD 仍然支持它.

测试数组时的问题在于: 如果第一个元素不遵守测试数的约束, 你会得到未定义行为.

#include <boost/vmd/is_array.hpp>
#include <boost/vmd/is_tuple.hpp>

#define A_TUPLE (&anything,(1,2))

BOOST_VMD_IS_ARRAY(A_TUPLE) will give UB due to the constraint
BOOST_VMD_IS_TUPLE(A_TUPLE) will return 1

当 VMD 尝试解析数组时 (使用 BOOST_VMD_IS_ARRAY 时就是如此), 它首先查看语法是否表示一个含两个元素的元组. 接着查看第二个元素本身是否是一个元组. 最后, 如果确认前面的检查都有效, 它会测试第一个元素是否为数. 正是在这最后的测试中 (第一个元素不是有效的数), 可能发生未定义行为, 如"数"主题中所解释的那样.

测试列表时的问题

非空列表的形式是一个二元组, 其中第一个元素是列表的头, 可以是任何内容, 第二个元素本身是一个列表或列表结束标识符 BOOST_PP_NIL.

测试列表时的问题在于: 如果第二个元素不遵守测试标识符的约束 (因为 BOOST_PP_NIL 是一个标识符并按此测试), 你会得到未定义行为.

#include <boost/vmd/is_list.hpp>
#include <boost/vmd/is_tuple.hpp>

#define A_TUPLE (element,&anything)

BOOST_VMD_IS_LIST(A_TUPLE) will give UB due to the constraint
BOOST_VMD_IS_TUPLE(A_TUPLE) will return 1

空列表的形式是标识符 BOOST_PP_NIL. 因此:

#include <boost/vmd/is_identifier.hpp>
#include <boost/vmd/is_list.hpp>

#define A_BAD_EMPTY_LIST &BOOST_PP_NIL

BOOST_VMD_IS_LIST(A_BAD_EMPTY_LIST) will give UB due to the constraint
BOOST_VMD_IS_IDENTIFIER(A_BAD_EMPTY_LIST) will give UB due to the constraint

当 VMD 尝试解析列表时 (使用 BOOST_VMD_IS_LIST 时就是如此), 它首先查看语法是否表示一个含两个元素的元组. 如果它不是含两个元素的元组, 则检查列表结束. 如果它是含两个元素的元组, 则查看第二个元素是否是一个列表. 在这两条路径上, 它最终都必须检查列表结束记法 BOOST_PP_NIL, 它在 VMD 中是一个标识符. 正是在这最后的测试中 (列表结束记法作为 VMD 标识符存在), 可能发生未定义行为, 如"标识符"主题中所解释的那样.

空的 Boost PP 数据类型

数组和列表可以为空.

空数组的形式是 '(0,())', 是一个完全有效的数组.

你可以使用宏 BOOST_VMD_IS_EMPTY_ARRAY 测试空数组.

#include <boost/vmd/is_array.hpp>
#include <boost/vmd/is_empty_array.hpp>

#define AN_ARRAY (1,(1))
#define AN_EMPTY_ARRAY (0,())

BOOST_VMD_IS_ARRAY(AN_ARRAY) will return 1
BOOST_VMD_IS_ARRAY(AN_EMPTY_ARRAY) will return 1

BOOST_VMD_IS_EMPTY_ARRAY(AN_EMPTY_ARRAY) will return 1
BOOST_VMD_IS_EMPTY_ARRAY() will return 0
BOOST_VMD_IS_EMPTY_ARRAY(AN_ARRAY) will return 0

空列表的形式是 'BOOST_PP_NIL', 是一个完全有效的列表.

你可以使用宏 BOOST_VMD_IS_EMPTY_LIST 测试空列表.

#include <boost/vmd/is_empty_list.hpp>
#include <boost/vmd/is_list.hpp>

#define A_LIST (1,BOOST_PP_NIL)
#define AN_EMPTY_LIST BOOST_PP_NIL

BOOST_VMD_IS_LIST(A_LIST) will return 1
BOOST_VMD_IS_LIST(AN_EMPTY_LIST) will return 1

BOOST_VMD_IS_EMPTY_LIST(AN_EMPTY_LIST) will return 1
BOOST_VMD_IS_EMPTY_LIST() will return 0
BOOST_VMD_IS_EMPTY_LIST(A_LIST) will return 0

使用 Boost PP 时, seq 和元组都不能为空. 因此, 如果你使用 Boost PP 宏把空数组或空列表转换为 seq 或元组, 会得到未定义行为.

语法 '()' 被称为空括号, 它既不是零元素的 seq, 也不是不含元素的元组. 它要么是一个内容为空的单元素 seq, 要么是一个内容为空的单元素元组.

VMD 支持空括号的语法. 你可以使用宏 BOOST_VMD_IS_PARENS_EMPTY 测试它.

#include <boost/vmd/is_parens_empty.hpp>
#include <boost/vmd/is_seq.hpp>
#include <boost/vmd/is_tuple.hpp>

#define EMPTY_PARENS ()
#define TUPLE (0)
#define SEQ (0)(1)

BOOST_VMD_IS_TUPLE(EMPTY_PARENS) will return 1
BOOST_VMD_IS_SEQ(EMPTY_PARENS) will return 1

BOOST_VMD_IS_PARENS_EMPTY(EMPTY_PARENS) will return 1
BOOST_VMD_IS_PARENS_EMPTY() will return 0
BOOST_VMD_IS_PARENS_EMPTY(TUPLE) will return 0
BOOST_VMD_IS_PARENS_EMPTY(SEQ) will return 0

VC++8 编译器 (Visual Studio 2005) 是 VMD 支持的最老的 VC++ 版本, 它在处理空括号语法时有问题. 因此如果你必须使用 VC++8, 请避免使用该语法, 否则只要你愿意就可以放心使用.

用元组代替数组

在使用变参宏时, 数组相对元组的唯一优势是数组可以为空. 否则使用元组总是更容易, 因为语法更简单; 你永远不必标注元组的大小.

由于 VMD 完全支持传递和返回空, 你可以在所有情况下用元组代替数组, 只需传递或返回空来表示"空"元组, 作为空数组的等价物.

用空表示"空"元组的想法也可以扩展为用空表示"空" seq. 然而 Boost PP 中的功能不会把空识别为空元组或空 seq, 你也无法使用 Boost PP 中针对元组或 seq 的功能来处理表示空元组或空 seq 的空. 作为用空表示"空"元组或"空" seq 的解决方案, VMD 提供了相应的功能, 将在我们查看 VMD 最后一个功能领域 (Boost PP 之外有用的变参宏) 时加以说明.

用法

你可以使用通用头文件:

#include <boost/vmd/vmd.hpp>

或者你也可以为这些宏使用各自的独立头文件. 这些独立头文件是:

#include <boost/vmd/is_array.hpp> //  for the BOOST_VMD_IS_ARRAY macro
#include <boost/vmd/is_list.hpp> //  for the BOOST_VMD_IS_LIST macro
#include <boost/vmd/is_seq.hpp> //  for the BOOST_VMD_IS_SEQ macro
#include <boost/vmd/is_tuple.hpp> // for the BOOST_VMD_IS_TUPLE macro.

#include <boost/vmd/is_empty_array.hpp> // for the BOOST_VMD_IS_EMPTY_ARRAY macro.
#include <boost/vmd/is_empty_list.hpp> // for the BOOST_VMD_IS_EMPTY_LIST macro.
#include <boost/vmd/is_parens_empty.hpp> // for the BOOST_VMD_IS_PARENS_EMPTY macro.

识别宏与 BOOST_VMD_IS_EMPTY

各种识别 VMD 数据类型的宏与使用 BOOST_VMD_IS_EMPTY 识别空的能力互为补充. 在本文档中我将把这些特定宏统称为"识别宏". 识别宏还与 BOOST_VMD_IS_EMPTY 共享在 C++20 标准之前讨论 BOOST_VMD_IS_EMPTY 时提到过的固有缺陷, 因为它们自己就是使用 BOOST_VMD_IS_EMPTY 来确定输入已经结束的.

回顾一下 C++20 之前 BOOST_VMD_IS_EMPTY 的缺陷:

  • 使用标准 C++ 编译器时, 如果输入以类函数宏的名字结尾, 且该宏接受两个或更多参数, 会发生预处理错误.
  • 使用带默认预处理器的 VC++ 编译器时, 如果输入由类函数宏的名字组成, 且该宏在无参数调用时返回一个元组, 该宏会错误地返回 1, 意味着输入为空.
  • 即使类函数宏只接受一个参数, 向该宏传递空也可能导致预处理错误.

避免识别宏的 BOOST_VMD_IS_EMPTY 问题的显而易见的方法, 是把输入设计成永远不把类函数宏的名字作为参数传递. 如果使用 VMD 并且输入可能包含类函数宏名字, 可以通过把该类函数宏名字放入一个 Boost PP 数据类型 (例如元组) 中, 而不尝试用 VMD 识别该元组元素的类型来实现. 换句话说, 如果输入是:

( SOME_FUNCTION_MACRO_NAME )

并且我们有宏定义:

#define SOME_FUNCTION_MACRO_NAME(x,y) some_output

如果需要, VMD 仍然可以使用 BOOST_VMD_IS_TUPLE 把输入解析为元组, 而不会遇到 BOOST_VMD_IS_EMPTY 问题. 然而, 如果输入是:

SOME_FUNCTION_MACRO_NAME

无论是直接给出, 还是通过访问上述元组的第一个元素得到, 并且程序员试图对这一输入使用 BOOST_VMD_IS_IDENTIFIER, 那么 BOOST_VMD_IS_EMPTY 问题就会发生.
