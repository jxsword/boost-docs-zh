与官方连接器对比的基准测试

MySQL 和 MariaDB 自带官方 C 连接器: libmysqlclient 和 libmariadb. 两者都实现了客户端/服务器协议, Boost.MySQL 也是如此. 由此产生一个问题: Boost.MySQL 与官方驱动一样快吗?

注释

简而言之: Boost.MySQL 与官方 C API 一样快, 在某些情况下甚至可能更快.

设计决策

这些基准测试聚焦于 协议实现的速度, 以尝试回答上面的问题. 这至少应将 (反) 序列化和缓冲考虑在内. 它不应考虑 Boost.MySQL 特有的功能, 例如静态接口或连接池.

libmysqlclient 和 libmariadb 都提供了一种连接类型, 类似于 any_connection, 同时具有同步和异步原语. 同步函数与 Boost.MySQL 中的类似 (尽管带有 C 语言风格). 异步函数则低级得多, 往往需要集成到某个框架 (如 Asio 或 libuv) 中, 或者手写 poll/epoll 代码. 这些选项都不简单. 此外, 同步函数的开销更小, 因此最适合用来回答我们的问题. 出于这个原因, 基准测试中 只使用同步函数.

基准测试 只使用预处理语句. 官方驱动对文本查询 (通过 mysql_real_query 发出) 和预处理语句的处理方式不同. 文本查询生成的行以字符串形式返回, 需要用户自行解析. Boost.MySQL 会自动为你完成这一解析. 因此, 比较文本查询没有太大意义. 预处理语句的处理方式相似, 并且更适合大行和大数据集.

所有测试都使用真实数据库. Boost.MySQL 和官方 C 客户端都不暴露 (反) 序列化函数. 缓冲和优化系统调用次数对效率也至关重要, 只能通过真实通信来衡量. 缺点是数据库处理会引入延迟, 并可能最终成为瓶颈.

基准测试尝试 通过使用 UNIX 套接字将通信开销降到最低.

基准测试流程

基准测试源码位于仓库的 bench/ 目录中. 执行的基准测试如下:

  • 单个小行. 执行一条语句, 生成一个包含 15 个字段的小行, 涵盖大多数可能的类型. 每行约 500 字节. 执行重复 10000 次. Boost.MySQL 版本使用 any_connection::execute.
  • 单个大行. 与上面类似, 但行有 17 个字段, 每行大小在 72 到 108 KB 之间. Boost.MySQL 版本使用 any_connection::start_execution, 允许零拷贝.
  • 多行. 执行一条语句, 生成 5000 行上述“大行”. 该语句只执行一次. Boost.MySQL 版本使用 any_connection::start_execution, 因为结果集很大.
  • 带参数的语句. 执行一条包含 17 个参数的语句, 大致对应上述“大行”结构. 用于衡量序列化速度. 该语句执行 1000 次.

基准测试条件:

  • 数据库: MySQL 8.4.1, 运行在 localhost 的 Docker 容器中.
  • 操作系统: Ubuntu 24.04
  • CPU: Intel(R) Core(TM) i7-10510U CPU @ 1.80GHz, 8 核.
  • 编译器: g++-14, 使用 CMake 的 Release 配置, C++23.
  • MySQL C API: libmysqlclient24 (官方 MySQL 8.4.4 发布版所含版本).
  • MariaDB C API: libmariadb3 1:10.11.11-0ubuntu0.24.04.2 (Ubuntu 官方包).
  • Boost.MySQL: Boost 1.87.0. 使用仅头文件版本 (不定义 BOOST_MYSQL_SEPARATE_COMPILATION), 因为它稍快一些.

结果

三个库表现出相近的性能水平, 这对于正确实现的二进制协议是符合预期的. Boost.MySQL 在单行基准测试中优于 libmysqlclient, 并与 libmariadb 持平. 其他基准测试中的差异似乎在统计上不显著.

在这些基准测试期间, 发现了一些潜在的性能改进方向. 详见 [https://github.com/boostorg/mysql/issues/458 该 issue].

请记住, 协议只是整个拼图中的一块. 正确使用 connection_pool、with_params、多函数操作和多查询等特性, 可以为你的应用带来巨大的性能差异. 永远不要想当然, 始终要进行测量!
