文本查询与客户端侧 SQL 格式化

文本查询 是使用 MySQL 文本协议执行的查询. 普通字符串和 with_params 使用此协议. 这与 预处理语句 不同, 后者先准备再单独执行, 并使用二进制协议.

警告

切勿使用原始字符串拼接来组合 SQL 查询. 这不安全, 会导致 SQL 注入漏洞. 请使用本节介绍的客户端侧 SQL 格式化设施来避免漏洞.

使用文本查询可以执行 多条以分号分隔的查询 , 从而提高效率.

将 with_params 用于简单查询

with_params 是使用客户端侧 SQL 格式化最简单的方式. 它可作为预处理语句更简单、更灵活的替代品. 预处理语句在服务器侧展开查询, 而 SQL 格式化在客户端侧进行. 更多信息请阅读 与预处理语句的对比 和 安全注意事项 章节.

with_params 接受一个带占位符的 SQL 查询字符串和一组参数. 传递给 execute 或 async_execute 时, 查询会在客户端用提供的参数展开并发送到服务器执行:

std::string employee_name = get_name();  // employee_name is an untrusted string
mysql::results result;

// Expand the query and execute it. The expansion happens client-side.
// If employee_name is "John", the executed query would be:
// "SELECT id, salary FROM employee WHERE last_name = 'John'"
co_await conn.async_execute(
    mysql::with_params("SELECT id, salary FROM employee WHERE last_name = {}", employee_name),
    result
);

花括号 ({}) 表示占位符 (技术上称为 替换字段). 记法和语义与 std::format 类似.

所有基本类型都可用作查询参数. 包括整数、浮点类型、字符串、blob、日期和时间:

// Will execute "SELECT id FROM employee WHERE salary > 42000"
mysql::results result;
co_await conn.async_execute(
    mysql::with_params("SELECT id FROM employee WHERE salary > {}", 42000),
    result
);

std::optional<T> 与 boost::optional<T> 也可使用:

std::optional<std::int64_t> salary;  // get salary from a possibly untrusted source
mysql::results result;

// Depending on whether salary has a value or not, executes:
// "UPDATE employee SET salary = 42000 WHERE id = 1"
// "UPDATE employee SET salary = NULL WHERE id = 1"
co_await conn.async_execute(
    mysql::with_params("UPDATE employee SET salary = {} WHERE id = {}", salary, 1),
    result
);

支持集合和范围, 只要其元素可格式化:

mysql::results result;
std::vector<long> ids{1, 5, 20};

// Executes "SELECT * FROM employee WHERE id IN (1, 5, 20)"
// std::ref saves a copy
co_await conn.async_execute(
    mysql::with_params("SELECT * FROM employee WHERE id IN ({})", std::ref(ids)),
    result
);

关于格式化范围的更多内容参见 本节 , 内置支持 SQL 格式化的类型参考参见 此表.

注释

与 std::format 一样, 传给 with_params 的查询字符串必须在编译期已知. 可以使用 runtime 函数跳过此检查.

与 std::format 一样, 可以使用带显式索引的实参:

// Recall that you need to set connect_params::multi_queries to true when connecting
// before running semicolon-separated queries. Executes:
// "UPDATE employee SET first_name = 'John' WHERE id = 42; SELECT * FROM employee WHERE id = 42"
mysql::results result;
co_await conn.async_execute(
    mysql::with_params(
        "UPDATE employee SET first_name = {1} WHERE id = {0}; SELECT * FROM employee WHERE id = {0}",
        42,
        "John"
    ),
    result
);

常见错误及修复方法

并非所有值都能被格式化. 若库发现格式化某个值可能导致安全问题的歧义, 会报错且查询不会发送到服务器. 以下是最常见的错误:

  • client_errc::invalid_encoding
    • 原因: 你的某个字符串参数包含无效码位. 使用默认字符集时, 这意味着它包含 无效的 UTF-8.
    • 解决方法: 所有字符串值必须按连接的字符集 (通常为 UTF-8) 编码. 请净化或拒绝此类值. 对不表示字符串而是任意二进制值的值, 请使用 blob 和 blob_view 类型.
  • client_errc::unformattable_value
    • 原因: 你的某个参数包含无效值. 例如 double 包含 MySQL 不支持的 NaN 或 Inf.
    • 解决方法: 拒绝此类值, 或在传给客户端侧 SQL 格式化之前将其替换为 NULL.
  • client_errc::unknown_character_set
    • 原因: 你的连接不知道你正在使用的字符集. 安全地生成查询需要知道所用字符集. 调用 reset_connection 之后, 或在连接时使用了自定义 connect_params::connection_collation 时, 可能出现这种情况.
    • 解决方法: 使用 connection_pool 而非手动重置连接. 若无法做到, 连接时请使用默认的 connection_collation , 并在重置连接后使用 set_character_set 或 async_set_character_set.
    • 了解更多 关于字符集跟踪的工作原理.

例如:

try
{
    // If the connection is using UTF-8 (the default), this will throw an error,
    // because the string to be formatted is not valid UTF-8.
    // The query never reaches the server.
    mysql::results result;
    co_await conn.async_execute(mysql::with_params("SELECT {}", "bad\xff UTF-8"), result);
}
catch (const boost::system::system_error& err)
{
    BOOST_TEST(err.code() == mysql::client_errc::invalid_encoding);
}

预处理语句与客户端侧 SQL 格式化的对比

虽然二者用途相似, 但它们有根本区别. 预处理语句由服务器解析和展开. 客户端侧 SQL 在客户端展开查询, 并将其作为字符串发送到服务器.

这意味着 客户端侧 SQL 并不理解你的查询. 它只知道如何将 MySQL 类型格式化为字符串而不产生漏洞, 其他情况下将你的查询视为不透明的字符串. 客户端侧 SQL 带来 更大的灵活性 (你可以动态组合任何查询), 而语句则有更多限制. 这也意味着 你需要更加注意组合有效的查询 , 尤其是处理复杂条件逻辑时. 逻辑错误可能导致漏洞利用. 更多信息请阅读 安全注意事项章节.

相比语句, 客户端侧 SQL 有 更少的服务器往返 , 对轻量级查询通常更高效. 然而, 它使用较不紧凑的文本协议, 对检索大量数据的查询可能更慢. 更多信息参见 效率注意事项章节.

总体而言, 以下情况 使用客户端侧 SQL 格式化:

  • 不检索大量数据的简单查询. 默认使用 with_params , 只有当性能测量表明有必要时才切换到语句.
  • 涉及语句无法实现的动态 SQL 的查询. 典型情况包括:
    • 动态过滤 (示例).
    • 批量插入. 逐行插入可能导致效率低下. 可以使用客户端侧 SQL 格式化组合一条 INSERT , 一次插入多行 (见 示例 1 和 示例 2).
    • 类似 PATCH 的更新, 其中 UPDATE 的字段列表必须是动态的 (示例).
    • 涉及动态标识符的查询, 如表名和字段名.
    • 条件排序.
    • 由多条带动态字段的分号分隔查询组成的管道.

另一方面, 若出现以下情况, 优先使用预处理语句:

  • 你在反复执行同一查询. 可以一次准备语句, 多次执行.
  • 你的查询检索大量数据, 且你已经完成相关的性能测量.
效率注意事项

客户端侧 SQL 格式化和预处理语句在效率上各有优劣:

  • 客户端格式化的 SQL 有 更少的服务器往返. 对于预处理语句, 通常需要一次准备语句的调用、一次执行调用, 可能还需要最后一次关闭调用. 客户端格式化的 SQL 只需执行往返. 随着网络延迟增大以及使用 TLS, 此性能收益会更加明显.
  • 预处理语句总是涉及 会话状态的变更 , 而客户端格式化的 SQL 则未必. 若你将 connection_pool 与预处理语句配合使用, 则不能使用 pooled_connection::return_without_reset , 因为这会泄漏语句. 对于客户端格式化的查询, 若你的 SQL 不变更会话状态, 则可能无需重置.
  • 客户端格式化的 SQL 查询使用通常 效率较低的文本协议 , 而预处理语句使用更紧凑的二进制协议. 当你检索大量难以与文本互相转换的数据 (如 double) 时, 这一点很重要.
  • 预处理语句可以复用. 若需要多次执行同一查询, 预处理语句只需解析一次.
  • 相比预处理语句, 客户端格式化的 SQL 支持 更高效的模式 , 如批量插入和分号分隔查询.
安全注意事项

客户端侧 SQL 格式化和预处理语句都能 防御 SQL 注入. 语句通过在执行参数替换之前由服务器解析带占位符的查询来做到这一点. 客户端侧 SQL 通过给值加引号和转义来避免注入, 但 并不理解你的查询.

这意味着你需要 确保你的查询始终展开为有效的 SQL. 对简单查询来说这很容易, 但对涉及范围或动态标识符的更复杂查询可能是问题. 例如, 若提供的范围为空, 以下查询可能展开为无效 SQL:

// If ids.empty(), generates "SELECT * FROM employee WHERE id IN ()", which is a syntax error.
// This is not a security issue for this query, but may be exploitable in more involved scenarios.
// Queries involving only scalar values (as opposed to ranges) are not affected by this.
// It is your responsibility to check for conditions like ids.empty(), as client-side SQL
// formatting does not understand your queries.
std::vector<int> ids;
mysql::results r;
co_await conn.async_execute(
    mysql::with_params("SELECT * FROM employee WHERE id IN ({})", ids),
    r
);

若你使用 format_sql_to 分段构建查询, 风险会更高.

总结:

  • 客户端侧 SQL 可防御 SQL 注入.
  • 客户端侧 SQL 不能防御逻辑错误. 该风险仅存在于复杂查询中. 我们建议遵循以下建议:
    • 尽量避免复杂的查询生成逻辑. 使用单个格式字符串而非 format_sql_to , 除非别无选择.
    • 使用范围时, 考虑空范围是否会导致有效的 SQL.
    • 对复杂的查询生成逻辑进行充分测试.
  • 客户端侧 SQL 需要知道连接的当前字符集. 这通常开箱即用, 否则会导致 受控错误. 一些推荐做法:
    • 若有疑问, 始终使用默认字符集 (utf8mb4).
    • 绝不要直接发出 SET NAMES 或 SET CHARACTER SET 语句 — 请改用 any_connection::set_character_set 或 async_set_character_set.
    • 若你使用 format_sql 或 format_sql_to , 绝不要手工构造 format_options 值. 请改用 any_connection::format_opts.
