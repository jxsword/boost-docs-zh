连接池

连接池是一种将多个长生命周期连接复用于独立逻辑操作的技术. 与建立单独连接相比, 它有以下好处:

  • 它提供更好的性能. 更多信息请查阅 我们的基准测试.
  • 它简化了连接管理. 连接池开箱即用地提供建立会话、执行重试和应用超时等功能.

下面是创建连接池的方法:

// pool_params contains configuration for the pool.
// You must specify enough information to establish a connection,
// including the server address and credentials.
// You can configure a lot of other things, like pool limits
mysql::pool_params params;
params.server_address.emplace_host_and_port(server_hostname);
params.username = mysql_username;
params.password = mysql_password;
params.database = "boost_mysql_examples";

// The I/O context, required by all I/O operations
asio::io_context ctx;

// Construct a pool of connections. The context will be used internally
// to create the connections and other I/O objects
mysql::connection_pool pool(ctx, std::move(params));

// You need to call async_run on the pool before doing anything useful with it.
// async_run creates connections and keeps them healthy. It must be called
// only once per pool.
// The detached completion token means that we don't want to be notified when
// the operation ends. It's similar to a no-op callback.
pool.async_run(asio::detached);

connection_pool 是一个管理连接的 I/O 对象. 它可以由执行器或执行上下文 (与所有 I/O 对象一样) 以及一个 pool_params 对象构造.

每个池必须恰好调用一次 connection_pool::async_run. 该函数负责实际保持连接的健康状态.

现在可以使用 connection_pool::async_get_connection 获取连接了. 我们将使用 C++20 协程让异步代码更简单:

// Use connection pools for functions that will be called
// repeatedly during the application lifetime.
// An HTTP server handler function is a good candidate.
asio::awaitable<std::int64_t> get_num_employees(mysql::connection_pool& pool)
{
    // Get a fresh connection from the pool.
    // pooled_connection is a proxy to an any_connection object.
    mysql::pooled_connection conn = co_await pool.async_get_connection();

    // Use pooled_connection::operator-> to access the underlying any_connection.
    // Let's use the connection
    mysql::results result;
    co_await conn->async_execute("SELECT COUNT(*) FROM employee", result);
    co_return result.rows().at(0).at(0).as_int64();

    // When conn is destroyed, the connection is returned to the pool
}

默认情况下, connection_pool::async_run 会一直运行. 当应用退出时, 你会希望使用 connection_pool::cancel 停止它. 这在信号处理函数中很常见, 用于保证干净的关闭.

注意, 池化只适用于 any_connection.

注释

connection_pool仅提供异步函数. 这与效率以及 Boost.Asio 执行器模型的一些特殊之处有关. 如果需要从同步代码中使用它, 请参见 本节.

池大小

池以固定的初始大小启动, 并会在需要时动态扩展到上限. 可以使用 pool_params::initial_size 和 pool_params::max_size 配置这些大小.

调整大小的算法如下:

  • 池创建时, 会创建并连接 pool_params::initial_size 数量的连接 (默认情况下 initial_size为 1).
  • 如果请求连接但所有可用连接都在使用中, 会创建一个新连接, 直到达到 max_size.
  • 如果请求连接且已有 max_size个连接在使用中, connection_pool::async_get_connection 会等待连接变为可用.
  • 连接一旦创建, 就永远不会被释放.

默认情况下, pool_params::max_size 为 151, 这是 MySQL 中 max_connections 系统变量的默认值, 控制服务器允许的最大并发连接数.

注释

在增大 pool_params::max_size 之前, 请确保同时增大服务器中 max_connections的值. 否则, 你的连接将因连接数限制而被拒绝.

下面是配置池大小的方法:

mysql::pool_params params;

// Set the usual params
params.server_address.emplace_host_and_port(server_hostname);
params.username = mysql_username;
params.password = mysql_password;
params.database = "boost_mysql_examples";

// Create 10 connections at startup, and allow up to 1000 connections
params.initial_size = 10;
params.max_size = 1000;

mysql::connection_pool pool(ctx, std::move(params));

为 async_get_connection 应用超时

默认情况下, connection_pool::async_get_connection 会一直等待直到有连接可用. 这意味着, 如果服务器不可用, async_get_connection可能会永远等待.

因此, 可以考虑为 async_get_connection设置超时. 可以使用 asio::cancel_after 来实现, 它利用了 Asio 的逐操作取消机制:

// Get a connection from the pool, but don't wait more than 5 seconds
auto conn = co_await pool.async_get_connection(asio::cancel_after(std::chrono::seconds(5)));

你也可以考虑在更高的层级设置超时. 例如, 如果你在处理 HTTP 请求, 可以使用 cancel_after为整个请求设置超时. 连接池示例就采用了这种方法.

会话状态

MySQL 连接持有状态. 在预处理语句、创建临时表、开启事务或设置会话变量时, 你会改变会话状态. 使用池化连接时, 会话状态可能成为问题: 如果未正确重置, 前一个操作的状态可能影响后续操作.

将连接归还到池后, 会使用等效于 any_connection::async_reset_connection 和 async_set_character_set 的操作来清除会话状态, 之后该连接才能再次被获取. 这会释放预处理语句、回滚未提交的事务、清除变量并将连接的字符集恢复为 utf8mb4. 特别是, 你无需调用 any_connection::async_close_statement 来释放语句.

重置连接开销很小, 但仍有成本 (一次到服务器的往返). 如果你使用过某个连接并且确定没有改变会话状态, 可以使用 pooled_connection::return_without_reset 跳过重置. 例如:

// Get a connection from the pool
mysql::pooled_connection conn = co_await pool.async_get_connection();

// Use the connection in a way that doesn't mutate session state.
// We're not setting variables, preparing statements or starting transactions,
// so it's safe to skip reset
mysql::results result;
co_await conn->async_execute("SELECT COUNT(*) FROM employee", result);

// Explicitly return the connection to the pool, skipping reset
conn.return_without_reset();

连接重置在连接归还后的后台进行, 因此不会影响延迟. 如果不确定某个操作是否会影响状态, 请假定它会影响.

字符集

默认情况下, 池化连接使用 utf8mb4作为其字符集. 连接重置时, 会使用等效于 any_connection::async_set_character_set 的操作将字符集恢复为 utf8mb4 (注意, 直接调用 async_reset_connection 会清除字符集数据). 这意味着, 使用默认配置时, any_connection::format_opts 和 current_character_set 总是成功.

我们建议始终使用 utf8mb4. 如果确实需要使用其他字符集, 请在从池中取出连接后, 对其使用 async_set_character_set.

在现代服务器上避免 SET NAMES 语句

每次重置连接时, async_reset_connection 都会导致发出一条 SET NAMES语句. 由于该语句与重置请求一起以管道方式发送, 性能影响极小, 但它仍可能出现在你的性能数据中.

现代服务器 (MySQL 8.0+ 和 MariaDB 11.6+) 默认使用 utf8mb4字符集. 如果你完全确定服务器已配置为使用 utf8mb4, 可以避免发出 SET NAMES, 方法是设置 pool_params::charset_strategy:

mysql::pool_params params;

// Connections will no longer issue SET NAMES statements when reset.
// Instead, they rely on the server's default character set being the one
// passed here. You must verify yourself that the server's default matches
// what you pass! Use this as an optimization, and only if you know what you are doing.
params.charset_strategy = mysql::pool_charset_strategy::use_server_default(mysql::utf8mb4_charset);
警告

使用 pool_charset_strategy::use_server_default 时, 作为用户, 你是在向库承诺你的服务器已正确配置. 运行时不会检查这一点. 仅在你清楚自己在做什么时, 才将其用作优化手段.

可以通过运行以下语句获取服务器的默认字符集:

SELECT @@GLOBAL.character_set_client;

连接生命周期

上面已解释的行为可以用如下状态模型来概括:

简而言之:

  • 连接创建后, 进入 pending_connect状态.
  • 尝试建立连接. 如果成功, 连接变为 idle. 否则, 它保持 pending_connect状态, 并在 pool_params::retry_interval 经过之后再次尝试.
  • idle连接可以通过 connection_pool::async_get_connection 获取, 并变为 in_use.
  • 如果连接通过 pooled_connection::return_without_reset 归还, 它会再次变为 idle.
  • 如果连接通过 pooled_connection 的析构函数归还, 它会变为 pending_reset.
  • any_connection::async_reset_connection 会应用于 pending_reset连接. 成功时, 它们再次变为 idle. 否则, 它们变为 pending_connect并将被重新连接.
  • 如果连接保持 idle状态达 pool_params::ping_interval, 它会变为 pending_ping. 此时会对连接进行探测. 如果它仍然存活, 将恢复为 idle. 否则, 它变为 pending_connect以等待重连. 将 pool_params::ping_interval 设置为零可以禁用 ping.

线程安全

默认情况下, connection_pool 不是线程安全的, 但通过设置 pool_params::thread_safe 可以轻松使其线程安全:

// The I/O context, required by all I/O operations.
// This is like an io_context, but with 5 threads running it.
asio::thread_pool ctx(5);

// The usual pool configuration params
mysql::pool_params params;
params.server_address.emplace_host_and_port(server_hostname);
params.username = mysql_username;
params.password = mysql_password;
params.database = "boost_mysql_examples";
params.thread_safe = true;  // enable thread safety

// Construct a thread-safe pool
mysql::connection_pool pool(ctx, std::move(params));
pool.async_run(asio::detached);

// We can now pass a reference to pool to other threads,
// and call async_get_connection concurrently without problem.
// Individual connections are still not thread-safe.

要正确理解 pool_params::thread_safe 保护了什么、未保护什么, 需要了解池的实现方式. connection_pool 和各个 pooled_connection 都持有指向共享状态对象的指针, 该对象包含池所需的全部数据:

线程安全的连接池会在内部创建一个 asio::strand 来保护连接池的状态. 像 async_get_connection、async_run 和 pooled_connection 的析构函数这类操作会通过 strand 运行, 因此可以安全地从任何线程调用. 更改状态句柄 (内部的 std::shared_ptr) 的操作, 例如 赋值运算符, 不是线程安全的.

池状态之外的数据不受保护. 特别是, asio::cancel_after会创建一个内部定时器, 可能引发无意中的竞态条件. 例如:

// A function that handles a user session in a server
asio::awaitable<void> handle_session(mysql::connection_pool& pool)
{
    // CAUTION: asio::cancel_after creates a timer that is *not* part of the pool's state.
    // The timer is not protected by the pool's strand.
    // This coroutine must be run within a strand for this to be safe
    using namespace std::chrono_literals;
    co_await pool.async_get_connection(asio::cancel_after(30s));

    // Use the connection
}

该协程必须在 strand 中运行:

// OK: the entire coroutine runs within a strand.
// In a typical server setup, each request usually gets its own strand,
// so it can run in parallel with other requests.
asio::co_spawn(
    asio::make_strand(ctx),  // If we removed this make_strand, we would have a race condition
    [&pool] { return handle_session(pool); },
    asio::detached
);

如果不使用 asio::make_shared, 就会出现以下竞态条件:

  • 调用 async_get_connection的线程设置了 asio::cancel_after所需的定时器.
  • 与此同时, 运行执行上下文的线程发现有健康的连接, 并完成 async_get_connection操作. 结果, 定时器被取消. 于是, 定时器在两个线程中被并发访问而没有保护.

如果使用回调, 代码会稍微复杂一些. 上面的协程可以改写为:

// Holds per-session state
class session_handler : public std::enable_shared_from_this<session_handler>
{
    // The connection pool
    mysql::connection_pool& pool_;

    // A strand object, unique to this session
    asio::strand<asio::any_io_executor> strand_;

public:
    // pool.get_executor() points to the execution context that was used
    // to create the pool, and never to the pool's internal strand
    session_handler(mysql::connection_pool& pool)
        : pool_(pool), strand_(asio::make_strand(pool.get_executor()))
    {
    }

    void start()
    {
        // Enters the strand. The passed function will be executed through the strand.
        // If the initiation is run outside the strand, a race condition will occur.
        asio::dispatch(asio::bind_executor(strand_, [self = shared_from_this()] { self->get_connection(); }));
    }

    void get_connection()
    {
        // This function will run within the strand. Binding the passed callback to
        // the strand will make async_get_connection run it within the strand, too.
        pool_.async_get_connection(
            asio::cancel_after(
                std::chrono::seconds(30),
                asio::bind_executor(
                    strand_,
                    [self = shared_from_this()](boost::system::error_code, mysql::pooled_connection) {
                        // Use the connection as required
                    }
                )
            )
        );
    }
};

void handle_session_v2(mysql::connection_pool& pool)
{
    // Start the callback chain
    std::make_shared<session_handler>(pool)->start();
}

线程安全默认禁用, 因为 strand 会带来性能损失, 而在单线程程序中这种损失是可以避免的.

传输类型与 TLS

可以使用与 any_connection 相同的一组传输方式: 明文 TCP、基于 TCP 的 TLS 或 UNIX 套接字. 可以使用 pool_params::server_address 和 pool_params::ssl 配置它们. 默认情况下, 若服务器支持则使用基于 TCP 的 TLS, 否则回退到明文 TCP.

可以使用 pool_params::ssl_ctx 为池创建的连接配置 TLS 选项. 如果未提供上下文, 会在内部为你创建一个.

基准测试

已进行了一项吞吐量基准测试, 以评估 connection_pool提供的性能提升. 基准测试代码位于 bench/connection_pool.cpp. 测试流程如下:

  • 测试由 N = 10000 个逻辑上独立的会话组成. 在 webserver 这类应用中, 这相当于处理 N 个 HTTP 请求.
  • 每个逻辑会话预处理一条 SELECT语句并执行它. 该语句按主键匹配单行, 并检索单个短字符串字段 (轻量查询).
  • num_parallel = 100 个异步代理并行运行. 这意味着, 在任一时刻, 与 MySQL 的并行连接数不超过 100.
  • 测试测量从启动第一个异步代理到收到最后一个查询响应 (ellapsed_time) 之间经过的时间.
  • 每种不同的配置重复测试 10 次并取平均值. 该时间用于测量吞吐量, 单位为“connections/s” (由 N/ellapsed_time给出).
  • 连接池场景使用 pooled_connection::~pooled_connection, 这会导致发出一次连接重置. 原始连接场景对每个会话使用 any_connection::async_connect 和 any_connection::async_close. 所有测试均为单线程.
  • 服务器在与基准测试相同的机器上、以 Docker 容器方式运行 MySQL v8.0.33.
  • 基准测试使用 clang-18 编译, 采用 CMake 的 Release 构建类型和 C++20. 它们在配备 8 核 i7-10510U 和 32GB 内存、运行 Ubuntu 22.04 的机器上执行.

可以看到, 池化显著提升了吞吐量. 在与服务器通信开销较大时尤其如此 (例如使用基于 TCP 的 TLS 时). 在高延迟网络上性能提升可能更大, 而对于重量级查询则可能减小, 因为此时建立连接所占的整体比重更小.

提示

使用 TLS 或运行频繁的小查询时, 池化可以帮到你.
