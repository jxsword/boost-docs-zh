多函数操作

多函数操作允许将操作作为一系列独立步骤运行, 从而让你对执行过程有更好的控制. 它们的工作原理是将部分读写拆分为多次函数调用.

可以通过动态接口或静态接口, 使用多函数操作来执行文本查询和预处理语句.

协议入门

要善用多函数操作, 你应当对底层协议有基本的了解.

该协议使用 消息进行通信. 消息由包含消息长度的头部定界. 所有操作都由客户端通过发送单个 请求消息发起, 服务器则以一组 响应消息作为回应.

下图展示了文本查询和语句执行时客户端与服务器之间的消息交换. 每个箭头代表一条消息.

有两种不同的情况:

  • 如果你的查询检索了至少一列 (即使没有生成任何行), 我们就处于 情况 1. 服务器发送:
    • 一个初始包, 通知查询已正确执行, 并且我们处于 情况 1.
    • 若干描述查询检索到的列的元数据包. 它们对用户可用, 并且是解析行所必需的.
    • 实际的行.
    • 一个 OK 包, 它标记结果集的结束, 并包含 last_insert_id 和 affected_rows 等信息.
  • 如果你的查询没有检索任何列, 我们就处于 情况 2. 服务器只会发送一个 OK 包, 其信息与 情况 1相同.

connection::execute 处理完整的消息交换. 相比之下, connection::start_execution 不会读取行 (如果有的话).

几点要点:

  • 单函数操作与多函数操作的区别只存在于客户端. 两者在线路上交换的消息是相同的.
  • 无法预先知道一个结果集有多少行. 你需要逐行读取, 直到找到标记结果集结束的 OK 包.
  • 当服务器处理请求消息时, 它会立即发送所有响应消息. 这些响应会等待在客户端处以供读取. 如果你不读取 全部响应, 后续操作会错误地将它们当作自己的响应读取, 导致包不匹配. 请小心, 不要让这种情况发生!

通过动态接口使用多函数操作

execution_state 是动态接口进行多函数操作的主类. 执行状态保存推进执行操作所需的信息, 如元数据 (解析行所必需) 和协议状态. 与 results不同, 它不包含行.

给定以下表定义:

const char* table_definition = R"%(
    CREATE TEMPORARY TABLE posts (
        id INT PRIMARY KEY AUTO_INCREMENT,
        title VARCHAR (256) NOT NULL,
        body TEXT NOT NULL
    )
)%";

可以使用 connection::start_execution 启动多函数操作:

// st will hold information about the operation being executed.
// It must be passed to any successive operations for this execution
execution_state st;

// Sends the query and reads response and meta, but not the rows
conn.start_execution("SELECT title, body FROM posts", st);

现在, 我们 必须通过调用 connection::read_some_rows 来读取所有生成的行, 它会返回一批大小不确定的行:

// st.complete() returns true once the OK packet is received
while (!st.complete())
{
    // row_batch will be valid until conn performs the next network operation
    rows_view row_batch = conn.read_some_rows(st);

    for (row_view post : row_batch)
    {
        // Process post as required
        std::cout << "Title:" << post.at(0) << std::endl;
    }
}

几点说明:

  • 如果还有行待读取, read_some_rows 会至少返回一行, 但可能返回更多.
  • execution_state::complete 在我们读取完此操作的最终 OK 包后返回 true.
  • 最终的 row_batch 可能为空也可能不为空, 取决于行数及其大小.
  • 在读取最终 OK 包之后调用 read_some_rows 会返回一个空批次.

read_some_rows 返回一个指向连接内部缓冲区的 rows_view 对象. 该视图在连接执行任何其他涉及网络传输的操作之前一直有效.

注意, 在代码中无需区分上图中的 情况 1 和 情况 2, 因为读取完整操作的行是明确定义的.

通过静态接口使用多函数操作

机制与上面介绍的类似. 静态接口使用 static_execution_state 来承载状态. 与 static_results一样, 我们必须定义并传递一个描述行的类型:

// We can use a plain struct with ints and strings to describe our rows.
// This must be placed at the namespace level
struct post
{
    int id;
    std::string title;
    std::string body;
};

// We use BOOST_DESCRIBE_STRUCT to add reflection capabilities to post.
// We must list all the fields that should be populated by Boost.MySQL
BOOST_DESCRIBE_STRUCT(post, (), (id, title, body))

现在可以使用相同的 connection::start_execution 启动我们的操作:

// st will hold information about the operation being executed.
// It must be passed to any successive operations for this execution
static_execution_state<post> st;

// Sends the query and reads response and meta, but not the rows.
// If there is any schema mismatch between the declared row type and
// what the server returned, start_execution will detect it and fail
conn.start_execution("SELECT id, title, body FROM posts", st);

现在, 我们 必须通过调用 connection::read_some_rows 来读取所有生成的行:

// storage will be filled with the read rows. You can use any other contiguous range.
std::array<post, 20> posts;

// st.complete() returns true once the OK packet is received
while (!st.complete())
{
    std::size_t read_rows = conn.read_some_rows(st, boost::span<post>(posts));
    for (const post& p : boost::span<post>(posts.data(), read_rows))
    {
        // Process post as required
        std::cout << "Title " << p.title << std::endl;
    }
}

几点说明:

  • static_execution_state 不以任何方式存储行. 它使用作为模板参数传入的行类型来验证服务器返回的元数据, 并确保其与将与 read_some_rows 一起使用的 C++ 数据结构兼容.
  • 我们必须向 read_some_rows 传递一个适当行类型的 boost::span. 我们使用 std::array 将行放置在栈上, 但你可以使用任何其他连续范围.
  • read_some_rows 返回读取的行数. 最多为 span 的大小, 但可能更少, 取决于行大小和网络缓冲区大小.
  • 如果还有行待读取, read_some_rows 会至少返回一行, 但可能返回更多.
  • execution_state::complete 在我们读取完此操作的最终 OK 包后返回 true.
  • 最后一次读取可能返回行, 也可能不返回, 取决于行数及其大小.
  • 在读取最终 OK 包之后调用 read_some_rows 总是读取零行.

访问元数据与 OK 包数据

可以在任意时刻使用 execution_state::meta 或 static_execution_state::meta 访问元数据. 该函数返回一个 metadata 对象集合. 更多信息请参见 本节.

可以使用 last_insert_id 和 affected_rows 等函数在 execution_state 和 static_execution_state 中访问 OK 包数据. 由于这些信息包含在 OK 包中, 只有当 complete 函数返回 true 后才能访问.

将多函数操作用于存储过程与多查询

使用返回多于一个结果集的操作时 (例如调用存储过程), 协议会稍微复杂一些:

消息交换如下:

  • 向服务器发送单个执行请求.
  • 服务器发送第一个结果集, 与单结果集情况相同. OK 包中包含一个标志, 指示后面还有另一个结果集.
  • 然后发送另一个结果集, 其结构与前一个相同. 该过程不断重复, 直到某个 OK 包指示没有更多结果集.

例如, 给定以下存储过程:

CREATE PROCEDURE get_company(IN pin_company_id CHAR(10))
BEGIN
    START TRANSACTION READ ONLY;
    SELECT id, name, tax_id FROM company WHERE id = pin_company_id;
    SELECT first_name, last_name, salary FROM employee WHERE company_id = pin_company_id;
    COMMIT;
END

我们可以这样写:

动态接口

静态接口

 
// Get the company ID to retrieve, possibly from the user
std::string company_id = get_company_id();

// Call the procedure
execution_state st;
statement stmt = conn.prepare_statement("CALL get_employees(?)");
conn.start_execution(stmt.bind(company_id), st);

// The above code will generate 3 resultsets
// Read the 1st one, which contains the matched companies
while (st.should_read_rows())
{
    rows_view company_batch = conn.read_some_rows(st);

    // Use the retrieved companies as required
    for (row_view company : company_batch)
    {
        std::cout << "Company: " << company.at(1).as_string() << "\n";
    }
}

// Move on to the 2nd one, containing the employees for these companies
conn.read_resultset_head(st);
while (st.should_read_rows())
{
    rows_view employee_batch = conn.read_some_rows(st);

    // Use the retrieved employees as required
    for (row_view employee : employee_batch)
    {
        std::cout << "Employee " << employee.at(0).as_string() << " " << employee.at(1).as_string()
                  << "\n";
    }
}

// The last one is an empty resultset containing information about the
// CALL statement itself. We're not interested in this
conn.read_resultset_head(st);
assert(st.complete());

// Get the company ID to retrieve, possibly from the user
std::string company_id = get_company_id();

// Our procedure generates three resultsets. We must pass each row type
// to static_execution_state as template parameters
using empty = std::tuple<>;
static_execution_state<company, employee, empty> st;

// Call the procedure
statement stmt = conn.prepare_statement("CALL get_employees(?)");
conn.start_execution(stmt.bind(company_id), st);

// Read the 1st one, which contains the matched companies
std::array<company, 5> companies;
while (st.should_read_rows())
{
    std::size_t read_rows = conn.read_some_rows(st, boost::span<company>(companies));

    // Use the retrieved companies as required
    for (const company& c : boost::span<company>(companies.data(), read_rows))
    {
        std::cout << "Company: " << c.name << "\n";
    }
}

// Move on to the 2nd one, containing the employees for these companies
conn.read_resultset_head(st);
std::array<employee, 20> employees;
while (st.should_read_rows())
{
    std::size_t read_rows = conn.read_some_rows(st, boost::span<employee>(employees));

    // Use the retrieved companies as required
    for (const employee& emp : boost::span<employee>(employees.data(), read_rows))
    {
        std::cout << "Employee " << emp.first_name << " " << emp.last_name << "\n";
    }
}

// The last one is an empty resultset containing information about the
// CALL statement itself. We're not interested in this
conn.read_resultset_head(st);
assert(st.complete());

注意, 我们使用 should_read_rows 而不是 complete 作为循环终止条件. complete() 在所有结果集都被读取后返回 true, 而 should_read_rows() 在单个结果被完整读取后即返回 false.

将静态接口用于多函数操作时, 并非所有模式不匹配都能被 start_execution 函数发现, 因为此时并非所有信息都可用. 错误也可能由 read_some_rows 和 read_resultset_head 报告. 总体上, 执行的检查与使用 connection::execute 时相同, 只是发生在不同的时间点.

一般情况下的多结果集

execution_state 和 static_execution_state 可以看作具有四个状态的状态机. 每个状态描述下一步应调用哪个读取函数:

  • should_start_op: 初始状态, 即默认构造 execution_state 之后. 此时应调用 connection::start_execution 或 connection::async_start_execution 来启动操作.
  • should_read_rows: 下一个操作应为 connection::read_some_rows, 以读取生成的行.
  • should_read_head: 下一个操作应为 connection::read_resultset_head, 以读取下一个结果集的元数据. 只有生成多个结果集的操作才会进入此状态.
  • complete: 无需更多操作.

对于多函数操作, 每当一个结果集被完整读取时 (即 should_read_head 返回 true 时), 你也可以访问 OK 包数据.

该示例展示了这种一般情况. 它使用多查询来运行任意 SQL 脚本文件.

关于 read_some_rows 的更多内容

要正确理解 read_some_rows, 我们需要知道每个 connection 拥有一个 内部缓冲区, 服务器发送的数据包存储在其中. 它是一个单一的平坦缓冲区, 你可以在创建 connection 时配置其初始大小, 方法是将一个 buffer_params 对象作为第一个参数传给 connection 的构造函数. 在某些情况下, 读缓冲区可能会增长以容纳大消息.

read_some_rows 会通过对流执行单次 read_some 操作 (或使用缓存数据), 获取内部缓冲区 (在不增长的前提下) 能容纳的最大行数. 如果有行待读取, read_some_rows 保证至少读取一行. 这意味着, 如果按上述方式执行后没有得到任何行 (例如由于某行过大而无法放入缓冲区), read_some_rows 将增长缓冲区或执行更多读取, 直到至少读取到一行. 如果使用静态接口, 读取的行数还受传入的 span 大小限制.

如果想充分发挥 read_some_rows 的性能, 可以自定义初始缓冲区大小, 以最大化每批读取的行数.
