字符集与排序规则

根据 MySQL 文档, 字符集是 一组符号及其各自的编码. utf8mb4、utf16 和 ascii 是 MySQL 支持的字符集. 排序规则是一组比较字符的规则, 并与单个字符集相关联. 例如, utf8mb4_spanish_ci以不区分大小写的方式比较 utf8mb4字符.

连接的字符集与排序规则

每个客户端会话都有一个关联的字符集和排序规则. 连接的字符集决定了发送到服务器以及从服务器获取的字符串的编码. 这包括 SQL 查询字符串、字符串字段以及元数据中的列名. 连接的排序规则用于字符串字面值比较. 连接的字符集和排序规则可以使用 SQL 动态更改.

默认情况下, Boost.MySQL 连接使用 utf8mb4_general_ci, 因此 所有字符串都使用 UTF-8. 我们建议使用此默认值, 因为 MySQL 的字符集很容易出错.

连接的字符集与为数据库、表和列指定的字符集没有关联. 考虑以下声明:

CREATE TABLE test_table(
    col1 TEXT CHARACTER SET utf16 COLLATE utf16_spanish_ci
);

存储在 col1中的数据将使用 UTF-16 编码, 并使用 utf16_spanish_ci进行比较. 但是, 当发送到客户端时, 它将被转换为连接的字符集.

注释

utf8mb4是 MySQL 对标准 UTF-8 的称呼. 容易混淆的是, MySQL 有一个名为 utf8的字符集, 它并不符合 UTF-8 标准.

连接字符集的影响

连接的字符集至关重要, 因为它影响大多数字符串字段的编码. 以下是受影响内容的摘要:

  • 传递给 async_execute 和 async_prepare_statement 的 SQL 查询字符串必须使用连接的字符集发送. 否则, 可能出现服务器端解析错误.
  • 传递给 with_params 和 format_sql 的 SQL 模板和字符串值必须使用连接的字符集编码. 否则, 值在组合查询时会被 Boost.MySQL 拒绝. 连接会 跟踪当前使用的字符集以检测这些错误. 如果绕过字符集跟踪 (例如使用 SET NAMES 而不是 async_set_character_set), 可能会遇到安全漏洞.
  • 传递给 statement::bind 的语句字符串参数应使用连接的字符集. 否则, MySQL 可能会拒绝这些值.
  • 从服务器获取的行和元数据中的字符串值使用连接的字符集.
  • 服务器提供的诊断消息 (diagnostics::server_message) 也使用连接的字符集.

总而言之, 要正确使用连接, 关键是要了解它所使用的字符集.

字符集建议

以下几节深入解释了 MySQL 中字符集的工作原理. 如果没有时间阅读, 请遵循以下建议:

  • 始终使用默认的 UTF-8. MySQL 中的字符集非常复杂且充满陷阱. 如果你的应用需要使用其他编码, 请在与服务器交互时将数据与 UTF-8 相互转换. 默认的 connect_params 确保使用 UTF-8, 无需运行任何 SQL.
  • 不要执行 SET NAMES语句, 也不要更改 character_set_client 和 character_set_results 会话变量 (例如通过 async_execute 语句). 这会破坏字符集跟踪, 从而可能导致安全漏洞.
  • 除非你清楚自己在做什么, 否则不要使用 async_reset_connection. 如果需要重用连接, 请改用 connection_pool.
  • 从 connection_pool 获取的连接始终使用 utf8mb4. 当连接归还到池中时, 其字符集会被重置为 utf8mb4.

字符集跟踪

有多种操作可能改变连接的字符集:

  • 使用 async_connect 连接时, 会向服务器提供一个数字形式的排序规则 ID. 可以使用 connect_params::connection_collation 更改它. <boost/mysql/mysql_collations.hpp> 和 <boost/mysql/mariadb_collations.hpp> 头文件包含可用的排序规则 ID. 如果服务器识别传入的排序规则, 连接的字符集将是与该排序规则关联的字符集. 如果不能识别, 连接将 静默回退到服务器的默认字符集 (旧服务器中为 latin1, 不是 Unicode; 现代服务器中为 utf8mb4). 在旧的 MySQL 5.7 服务器上尝试使用较新的排序规则 (例如 utf8mb4_0900_ai_ci) 时可能发生这种情况. 默认情况下, Boost.MySQL 使用所有服务器都支持的 utf8mb4_general_ci.
  • 使用 async_reset_connection 会将连接的字符集重置 为服务器的默认字符集.
  • 使用 async_set_character_set 会执行一条 SET NAMES语句来设置连接的字符集. 执行带有设置字符集阶段的管道具有相同的效果.
  • 手动执行 SET NAMES、SET CHARACTER SET或修改 character_set_client和 character_set_results会改变连接的字符集. 请不要这样做, 因为这会使字符集跟踪陷入混乱.

any_connection 会尝试跟踪连接当前的字符集, 因为安全地执行客户端 SQL 格式化需要它. 可以通过 any_connection::current_character_set 获取该信息, 它返回一个 character_set 对象. 当前字符集也被 async_execute使用 (当传入 with_params_t 对象时), 以及被 any_connection::format_opts 使用.

MySQL 协议对字符集跟踪的支持有限, 因此这项任务需要用户的一些配合. 某些情况可能导致当前字符集未知. 如果发生这种情况, 执行 with_params_t 将失败并报 client_errc::unknown_character_set. any_connection::current_character_set 和 any_connection::format_opts 也会返回此错误.

按照上述要点, 跟踪的工作方式如下:

  • 在建立连接之前, 当前字符集始终是未知的.
  • async_connect 成功后, 会使用保守的启发式方法来确定当前字符集. 如果传入的 connect_params::connection_collation 已知会被所有受支持的服务器接受, 其关联的字符集将成为当前字符集. 如果库不能确定, 当前字符集将保持未知 (这是避免安全漏洞的稳妥选择). 注意, 将 connection_collation 保留为其默认值总是会将当前字符集设置为 utf8mb4_charset.
  • 成功执行 async_set_character_set 会将当前字符集设置为传入的字符集. 成功执行设置字符集管道阶段也是如此.
  • 调用 async_reset_connection 会使当前字符集变为未知.
警告

不要执行 SET NAMES、SET CHARACTER SET或任何其他修改 character_set_client的 async_execute 等 SQL 语句. 这会使客户端中存储的字符集信息失效.

现代服务器 (MySQL 8.0+ 和 MariaDB 11.6+) 的默认字符集是 utf8mb4. 如果你确定服务器的默认字符集, 可以在 connect_params::server_default_charset 中设置它. 这会改变跟踪算法:

  • 如果将 connect_params::connection_collation 设置为 invalid_collation_id, 则 async_connect 成功后, 当前字符集就是 connect_params::server_default_charset 中传入的字符集.
  • 调用 async_reset_connection 会将当前字符集设置为连接时作为 connect_params::server_default_charset 传入的值.
警告

设置 connect_params::server_default_charset 时, 作为用户, 你是在向库承诺你的服务器已配置为使用该字符集作为默认字符集. 运行时不会检查这一点. 若未能履行此承诺, 可能导致安全漏洞. 仅在你清楚自己在做什么时, 才将其用作一种优化手段.

添加对字符集的支持

本库为 utf8mb4 (utf8mb4_charset) 和 ascii (ascii_charset) 提供了内置支持. 我们强烈建议你始终使用 utf8mb4. 注意, MySQL 不支持将连接的字符集设置为 UTF-16 或 UTF-32.

如果确实需要使用其他字符集, 可以通过创建 character_set 对象来实现. 之后可以像使用内置字符集一样, 将它们传递给 set_character_set 等函数.

注释

这是一种高级技术. 除非你清楚自己在做什么, 否则不要使用它.

该结构具有以下成员:

  • character_set::name 必须与你在 SET NAMES中使用的名称一致.
  • character_set::next_char 用于遍历字符串. 它必须返回字符串中第一个码点的字节长度; 若码点无效, 则返回 0.

例如, 下面展示了如何实现 utf8mb4字符集. 为简洁起见, 这里只展示了实现的一小部分 - 完整实现请参见 utf8mb4_charset 的定义.

// next_char must interpret input as a string encoded according to the
// utf8mb4 character set and return the size of the first character,
// or 0 if the byte sequence does not represent a valid character.
// It must not throw exceptions.
std::size_t utf8mb4_next_char(boost::span<const unsigned char> input)
{
    // Input strings are never empty - they always have 1 byte, at least.
    assert(!input.empty());

    // In UTF8, we need to look at the first byte to know the character's length
    auto first_char = input[0];

    if (first_char < 0x80)
    {
        // 0x00 to 0x7F: ASCII range. The character is 1 byte long
        return 1;
    }
    else if (first_char <= 0xc1)
    {
        // 0x80 to 0xc1: invalid. No UTF8 character starts with such a byte
        return 0;
    }
    else if (first_char <= 0xdf)
    {
        // 0xc2 to 0xdf: two byte characters.
        // It's vital that we check that the characters are valid. Otherwise, vulnerabilities can arise.

        // Check that the string has enough bytes
        if (input.size() < 2u)
            return 0;

        // The second byte must be between 0x80 and 0xbf. Otherwise, the character is invalid
        // Do not skip this check - otherwise escaping will yield invalid results
        if (input[1] < 0x80 || input[1] > 0xbf)
            return 0;

        // Valid, 2 byte character
        return 2;
    }
    // Omitted: 3 and 4 byte long characters
    else
    {
        return 0;
    }
}

character_set_results 与 character_set_client

在建立连接期间或通过 async_set_character_set 设置连接的字符集, 最终效果是更改一些会话变量. 本节列出这些变量以供参考. 我们 强烈建议不要手动修改它们, 因为这会使字符集跟踪陷入混乱.

  • character_set_client 决定了发送到服务器的 SQL 语句应使用的编码. 这包括传递给 async_execute 和 async_prepare_statement 的 SQL 字符串, 以及传递给 statement::bind 的字符串参数. character_set_client并不允许所有字符集. 例如, 基于 UTF-16 和 UTF-32 的字符集不会被接受.
  • character_set_results 决定了服务器发送任何类型结果时使用的编码, 包括由 connection::execute 获取的字符串字段、metadata::column_name 等元数据以及错误消息. 注意, metadata::column_collation 反映的是服务器在将列发送给客户端之前将其转换到的字符集和排序规则. 在上面的例子中, metadata::column_collation将是 UTF16 的默认排序规则, 而不是 latin1_swedish_ci.
