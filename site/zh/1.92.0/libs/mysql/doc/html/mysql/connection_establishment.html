建立与终止连接

本节讨论与客户端连接的创建、建立和终止相关的几个方面.

身份认证

connect_params::username 和 connect_params::password 包含认证过程中使用的凭据. 按照协议要求, 密码要么以哈希形式发送, 要么通过 TLS 等安全通道发送到服务器.

MySQL 实现了多种可用于认证用户的身份认证插件 (参见 MySQL 可插拔认证文档). 每个 MySQL 用户都关联到单个身份认证插件, 在创建用户时指定. 此外, 服务器还定义了一个默认身份认证插件 (参见 authentication_policy 和 default_authentication_plugin). 默认插件将用于新创建的用户, 并可能影响握手的工作方式.

本库实现了两种最常用的身份认证插件:

  • mysql_native_password. 除非另行配置, 这是 MySQL 5.7 和 MariaDB 的默认插件. 它既可用于 TLS 连接, 也可用于明文连接. 它发送经过哈希处理的密码, 并使用随机数 (nonce) 加盐.
  • caching_sha2_password. 这是 MySQL 8.0+ 的默认插件. 该插件过去要求使用 TLS. 自 Boost 1.89 起, 情况不再如此, 它也可以用于明文连接.

尚不支持多因素认证. 如果你需要支持上面未列出的插件或 MFA, 请在 GitHub 仓库中提交功能请求.

注释

不支持将默认身份认证插件配置为 Boost.MySQL 未实现插件的服务器, 无论具体用户实际使用的插件是什么. 这一限制将来可能会解除.

连接并指定数据库

connect_params::database 包含要连接的数据库名. 如果指定了它, 连接将默认使用该数据库, 就像发出过一条 USE 语句一样. 可以将其留空以不选择任何数据库. 建立连接后, 始终可以发出一条 USE 语句 (使用 async_execute) 来选择其他数据库.

TLS 支持

Boost.MySQL 完全支持 TLS 加密连接. 使用 any_connection 建立的 TCP 连接默认使用 TLS.

TLS 握手与终止

TLS 握手由 any_connection::async_connect 执行. 这与 Boost.Beast 等库形成对比, 在那些库中 TLS 握手必须由用户显式调用. 我们选择这种方式, 是因为 TLS 握手是 MySQL 协议握手的一部分: 客户端和服务器先交换若干未加密的消息, 然后执行 TLS 握手并继续交换加密的消息, 直到连接成功或失败. 这种方案使 TLS 协商功能成为可能 (更多信息见下文).

如果 TLS 握手失败, 整个 async_connect 操作也将失败.

TLS 关闭由 any_connection::async_close 执行. MySQL 并不总是优雅地关闭 TLS 连接, 因此 TLS 关闭产生的错误会被忽略.

TLS 协商

在建立连接期间, 客户端和服务器会协商是否使用 TLS. Boost.MySQL 通过 connect_params::ssl 支持这种协商. 这是一个 ssl_mode 枚举, 具有以下选项:

  • ssl_mode::enable 会在服务器支持时让连接使用 TLS, 否则回退到明文连接. 这是默认值, 适用于使用 TCP 时的 any_connection.
  • ssl_mode::require 确保连接使用 TLS. 如果服务器不支持, async_connect 将失败.
  • ssl_mode::disable 无条件禁用 TLS.

UNIX 套接字被视为安全通道, 并且 从不使用 TLS. 使用 UNIX 套接字连接时, connect_params::ssl 会被忽略.

连接建立成功后, 可以使用 any_connection::uses_ssl 查询连接是否已加密.

禁用 TLS

如上所述, 将 connect_params::ssl 设置为 ssl_mode::disable将禁用 TLS:

// The server host, username, password and database to use.
// Passing ssl_mode::disable will disable the use of TLS.
mysql::connect_params params;
params.server_address.emplace_host_and_port(std::string(server_hostname));
params.username = std::move(username);
params.password = std::move(password);
params.database = "boost_mysql_examples";
params.ssl = mysql::ssl_mode::disable;

完整示例见 此处.

证书验证与其他 TLS 选项

可以将一个可选的 asio::ssl::context 传递给 any_connection 的构造函数. 通过这种方式可以设置许多 TLS 参数, 包括受信任的 CA、证书验证回调和 TLS 扩展.

any_connection_params 包含一个可用于此目的的 ssl_context 成员. 例如, TLS 证书验证默认是禁用的. 要启用它:

// Create a SSL context, which contains TLS configuration options
asio::ssl::context ssl_ctx(asio::ssl::context::tls_client);

// Enable certificate verification. If the server's certificate
// is not valid or not signed by a trusted CA, async_connect will error.
ssl_ctx.set_verify_mode(asio::ssl::verify_peer);

// Load a trusted CA, which was used to sign the server's certificate.
// This will allow the signature verification to succeed in our example.
// If you want to use your system's trusted CAs, use
// ssl::context::set_default_verify_paths() instead of this function.
ssl_ctx.load_verify_file(std::string(ca_cert_path));

// We expect the server certificate's common name to be "mysql".
// If it's not, the certificate will be rejected and handshake or connect will fail.
// Replace "mysql" by the common name you expect.
ssl_ctx.set_verify_callback(asio::ssl::host_name_verification("mysql"));

// Create a connection.
// We pass the context as the second argument to the connection's constructor.
// Other TLS options can be also configured using this approach.
// We need to keep ssl_ctx alive as long as we use the connection.
mysql::any_connection conn(co_await asio::this_coro::executor, mysql::any_connection_params{&ssl_ctx});

// The hostname, username, password and database to use
mysql::connect_params params;
params.server_address.emplace_host_and_port(std::string(server_hostname));
params.username = username;
params.password = password;
params.database = "boost_mysql_examples";

// Connect to the server. If certificate verification fails,
// async_connect will fail.
co_await conn.async_connect(params);

可以在多个连接之间安全地共享单个 asio::ssl::context.

如果未传入 ssl::context, 连接会在需要时于内部创建一个. 默认上下文不执行证书验证.

上述示例的完整源码见 此处.

connection_pool 中的 TLS

由于 connection_pool 会创建 any_connection 实例, TLS 的机制是类似的. 与 TLS 相关的参数在构造池时指定, 作为 pool_params 的成员:

  • pool_params::ssl 控制 TLS 协商. 它是一个 ssl_mode 值, 其语义已在 上文中说明.
  • pool_params::ssl_ctx 是一个传递给池所创建连接的 asio::ssl::context. 它可用于配置证书验证等 TLS 选项. 池会取得传入的 ssl::context的所有权, 这与 any_connection不同.

UNIX 套接字

connect_params::server_address 是一个 any_address, 即一种类似 variant 的类型, 可以容纳 (主机名, 端口) 对或 UNIX 套接字路径. 要使用 UNIX 套接字连接 MySQL, 请将 server_address设置为 UNIX 域路径:

// Create a connection.
// Will use the same executor as the coroutine.
mysql::any_connection conn(co_await asio::this_coro::executor);

// The socket path, username, password and database to use.
// server_address is a variant-like type. Using emplace_unix_path,
// we can specify a UNIX socket path, instead of a hostname and a port.
// UNIX socket connections never use TLS.
mysql::connect_params params;
params.server_address.emplace_unix_path(std::string(unix_socket_path));
params.username = username;
params.password = password;
params.database = "boost_mysql_examples";

// Connect to the server
co_await conn.async_connect(params);

注意, 无论 connect_params::ssl 的值如何, UNIX 套接字从不使用 TLS.

更改网络缓冲区大小限制

any_connection 拥有一个内部网络缓冲区, 用于存储待写入或已从服务器读取的消息. 其初始大小由 any_connection_params::initial_buffer_size 给定. 每条协议消息都必须能放入内存, 因此缓冲区会按需扩展. 读取数据时, 每一行都作为单独的消息发送.

缓冲区永远不会扩展超过 any_connection_params::max_buffer_size. 如果操作需要更大的缓冲区, 将以 client_errc::max_buffer_size_exceeded错误码失败. 默认大小为 64MB.

如果需要读取或写入超过默认限制的单行数据, 可以在构造连接时增大该限制:

// Increase the max buffer size to 512MB.
// This allows reading individual rows as big as 512MB.
// This is only required if each individual row is extremely big,
// and is not required for many smaller rows.
mysql::any_connection_params conn_params;
conn_params.max_buffer_size = 0x20000000;

// Create the connection
mysql::any_connection conn(ctx, conn_params);

// Connect and use the connection normally

注意, 只要单行小于上述限制, 读取大于 64MB 的数据集 并不需要增大该限制.

调整 any_connection_params::initial_buffer_size 可能会影响 any_connection::async_read_some_rows 的性能, 如 本节所述.

启用多查询

可以使用 any_connection::async_execute 一次运行多条以分号分隔的查询. 这是默认禁用的一项协议特性. 可以在连接前将 connect_params::multi_queries 设置为 true 来启用它:

// The server host, username, password and database to use.
// Setting multi_queries to true makes it possible to run several
// semicolon-separated queries with async_execute.
mysql::connect_params params;
params.server_address.emplace_host_and_port(std::string(server_hostname));
params.username = std::move(username);
params.password = std::move(password);
params.database = "boost_mysql_examples";
params.multi_queries = true;

// Connect to the server
co_await conn.async_connect(params);

如 教程中所述, 多条分隔查询在许多情况下都很有用, 例如使用事务时. 本节包含关于如何使用多查询的更多信息.

这项协议特性默认禁用, 作为一种安全加固措施. 如果你的应用存在 SQL 注入漏洞, 该特性可能使利用漏洞变得更容易. 不需要该特性的应用应将其保持关闭, 这是最佳实践.

注释

正确使用多查询是安全的. 只需确保使用恰当的客户端 SQL 格式化工具来安全地生成查询.

关闭连接

可以通过调用 any_connection::async_close 来干净地关闭连接. 这会向服务器发送一个 quit packet, 通知即将结束连接, 然后执行 TLS 关闭并关闭底层传输层. 干净关闭涉及 I/O, 因此可能失败.

销毁连接而不执行干净关闭只会关闭底层传输层. 这不会泄漏任何资源, 但你可能会在服务器日志中看到警告. 尽可能尝试干净地关闭连接.

重连与长生命周期连接

any_connection 自身不会执行任何重连. 如果在操作期间遇到致命错误 (如网络错误), 需要显式重新建立连接.

按照设计, any_connection::async_connect 始终可以用于重新建立连接. 即使连接曾遇到网络错误或取消, 它也能工作. 为实现这一点, async_connect会在继续之前清除所有先前的连接状态.

如果需要可靠的长生命周期连接, 请考虑 使用连接池, 而不是自己实现策略. connection_pool会为你处理连接的重连和复用.
