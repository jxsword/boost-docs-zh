设计理由

错误处理设计理由

在出错的情况下, 本库不会定义类模板所需的成员. 这种技术使编译器在客户代码中、即错误实际所在之处停止显示诊断信息, 而不是沿着模板实例化一路追溯进库的实现.

本库组件的错误条件有限, 因此问题输入很容易被发现.

为什么使用 MPL 序列?

MPL 提供了对序列的算法, 因此变换 (例如为优化转发而把按值传递的参数类型变为 const 引用, 或者计算一个签名来特化 boost::function, 即在应用 boost::bind 之后) 可以更容易地表达. MPL 序列概念与多个其他 Boost 库兼容 (最重要的是 Fusion), 因此另一个原因是互操作性.

成员对象指针类型

尽管其语法如此, 成员对象指针类型仍可被视为进行解引用的函数对象.

ClassTransform 模板参数

This 指针、this 引用或仅对象本身 (或者甚至是对象的智能指针), 再加上 cv 限定的调整 - 所有这些情形都有其适用之处, 并不存在唯一最佳答案.

在序列内部对类类型作特殊处理会显著增加客户代码的复杂度. 通过自定义 ClassTransform 实参, 客户可以在序列形成之前调整类类型, 然后统一处理所有参数.

为什么使用标签类型?

让我们考虑一下替代方案.

第一种是仅仅使用更多模板, 使每个属性都必须显式询问. 如果需要检查的属性不止一个, 这种做法会导致客户代码更复杂, 库接口也会呈指数级增大.

第二种替代方案是让客户通过非类型模板参数传入位模式. 逻辑必须由客户执行, 而且错误条件要多得多. 此外, 带非类型模板参数的类模板在 MPL lambda 表达式中无法工作, 并且可能在较老的编译器上引发问题.

让合成模板把可调用体内建类型或 MPL 序列作为第一个模板参数是否安全?

是安全的, 但这一点并非一目了然, 因为可能的 MPL 序列集合与可调用体内建类型集合并不是天然不相交的.

然而, 任何试图让内建类型充当 MPL 序列的做法都是个坏主意, 因为在使类型成为序列的头文件被包含之前, 内建类型就已可用, 这很容易违反 ODR.

为什么成员函数的隐藏 this 参数要计入函数参数个数?

人们发现以下条件成立更为可取:

mpl::size< parameter_types<T> >::value == function_arity<T>::value

为什么忽略指针的顶层 cv 限定符?

带 cv 限定的指针仍然是指针. 这通常无关紧要, 即使有影响, 那也是 Boost.TypeTraits 的工作.
