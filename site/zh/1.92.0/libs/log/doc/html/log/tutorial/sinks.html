设置接收器

有时简单日志提供的灵活性不够. 例如, 您可能想要比简单打印到控制台更精细的日志处理逻辑. 要实现定制, 必须构造日志接收器并将其注册到日志核心. 这通常只需在应用程序的启动代码中做一次.

注释

必须提到, 前面的章节中我们并没有初始化任何接收器, 而简单日志不知怎么仍然可以工作. 这是因为库包含一个 默认接收器, 在用户未设置任何接收器时作为后备使用. 该接收器总是以固定格式将日志记录打印到控制台, 即前面示例中看到的格式. 提供默认接收器主要是为了让简单日志无需任何库初始化即可立即使用. 一旦您向日志核心添加了任何接收器, 默认接收器将不再使用. 不过您仍然可以使用简单日志宏.

解锁文件日志

作为起点, 下面是将日志初始化到文件的方法:

void init()
{
    logging::add_file_log("sample.log");

    logging::core::get()->set_filter
    (
        logging::trivial::severity >= logging::trivial::info
    );
}

新增的部分是对 add_file_log 函数的调用. 顾名思义, 该函数初始化一个将日志记录存储到文本文件的日志接收器. 该函数还接受若干定制选项, 例如文件轮转间隔和大小限制. 例如:

void init()
{
    logging::add_file_log
    (
        keywords::file_name = "sample_%N.log",                                        
        keywords::rotation_size = 10 * 1024 * 1024,                                   
        keywords::time_based_rotation = sinks::file::rotation_at_time_point(0, 0, 0), 
        keywords::format = "[%TimeStamp%]: %Message%"                                 
    );

    logging::core::get()->set_filter
    (
        logging::trivial::severity >= logging::trivial::info
    );
}

提示

您可以注册多个接收器. 每个接收器都会独立于其他接收器, 接收并处理您发出的日志记录.

深入了解接收器: 更多接收器

如果您不想深入了解细节, 可以跳过本节, 直接阅读下一节. 否则, 如果您需要对接收器配置更全面的控制, 或想使用便捷函数提供的接收器之外的其他接收器, 可以手动注册接收器.

在最简单的形式下, 上一节中对 add_file_log 函数的调用几乎等价于以下代码:

void init()
{
    // Construct the sink
    typedef sinks::synchronous_sink< sinks::text_ostream_backend > text_sink;
    boost::shared_ptr< text_sink > sink = boost::make_shared< text_sink >();

    // Add a stream to write log to
    sink->locked_backend()->add_stream(
        boost::make_shared< std::ofstream >("sample.log"));

    // Register the sink in the logging core
    logging::core::get()->add_sink(sink);
}

查看完整代码.

好, 关于接收器, 您首先可能注意到的是它们由两个类组成: 前端和后端. 前端 (即上面代码片段中的 synchronous_sink 类模板) 负责所有接收器的各种公共任务, 例如线程同步模型、过滤, 以及对基于文本的接收器而言的格式化. 后端 (上面的 text_ostream_backend 类) 实现接收器的所有特有功能, 例如本例中写入文件. 库提供了许多可以开箱即用相互配合的前端和后端.

上面的 synchronous_sink 类模板表明该接收器是同步的, 即它允许多个线程同时记录日志, 并在争用情况下阻塞. 这意味着后端 text_ostream_backend 完全不必操心多线程. 还有其他可用的接收器前端, 您可以在 此处 阅读更多内容.

text_ostream_backend 类将格式化后的日志记录写入与标准库兼容的流. 上面我们使用了文件流, 但也可以使用任何类型的流. 例如, 添加输出到控制台的方式如下:

#include <boost/core/null_deleter.hpp>

// We have to provide an empty deleter to avoid destroying the global stream object
boost::shared_ptr< std::ostream > stream(&std::clog, boost::null_deleter());
sink->locked_backend()->add_stream(stream);

text_ostream_backend 支持添加多个流. 此时其输出会被复制到所有添加的流. 将输出同时复制到控制台和文件可能很有用, 因为对于该接收器, 所有过滤、格式化和库的其他开销对每条记录只发生一次.

注释

请注意注册多个独立接收器与注册一个带多个目标流的接收器之间的区别. 前者允许对每个接收器的输出独立定制, 而后者在不需要这种定制时工作速度快得多. 该特性是这个特定后端独有的.

库提供了许多 后端, 提供不同的日志处理逻辑. 例如, 指定 syslog 后端可以将日志记录通过网络发送到 syslog 服务器, 或设置 Windows NT 事件日志 后端可以用标准 Windows 工具监视应用程序的运行期.

这里最后值得注意的一点是对 locked_backend 成员函数的调用, 用于访问接收器后端. 它用于获得对后端的线程安全排他访问, 由所有接收器前端提供. 该函数返回指向后端的智能指针, 只要该指针存在, 后端就处于锁定状态 (这意味着即使另一个线程尝试记录日志且日志记录被传递给该接收器, 在您释放后端之前它也不会被记录). 唯一的例外是 unlocked_sink 前端, 它完全不做同步, 只是返回一个未锁定的后端指针.
