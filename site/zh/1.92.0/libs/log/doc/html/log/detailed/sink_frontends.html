接收器前端是库提供的接收器的一部分, 实现所有接收器共享的公共功能. 这包括对过滤、异常处理和线程同步的支持. 此外, 由于格式化是基于文本的接收器的典型需求, 它也由前端实现. 每个接收器前端从日志核心接收日志记录, 然后将其传递给关联的接收器后端. 前端不定义如何处理记录, 而是定义核心应以何种方式与后端交互. 定义日志记录处理规则的是后端. 当您需要创建新类型的接收器时, 大概率不必编写自己的前端, 因为库提供了覆盖大多数用例的多种前端.

接收器前端派生自 sink 类模板, 日志核心使用该模板供给日志记录. 从技术上讲, 可以从 sink 模板派生自己的类, 从而得到新的接收器, 但使用接收器前端可以省去相当多的例行工作. 由于每个接收器前端都关联一个后端, 相应的后端也会在前端构造时由前端构造 (除非用户自己提供后端实例), 从而构成完整的接收器. 因此, 前端构造完成后即可注册到日志核心, 开始处理记录. 有关前端与后端交互的更多细节, 参见 接收器后端 一节.

下面是接收器前端所提供服务的更详细概述.

接收器前端基本服务

所有接收器前端都提供若干基本功能.

过滤

所有接收器前端都支持过滤. 用户可以指定自定义过滤函数对象, 或使用 库提供的工具 构造的过滤器. 过滤器可以通过 set_filter 方法设置, 或通过 reset_filter 方法清除. 过滤器在日志核心发出的 will_consume 方法调用期间被调用. 如果未设置过滤器, 则假定接收器会接受任何日志记录.

注释

与日志核心一样, 所有接收器前端都假定从多个线程并发调用过滤器是安全的. 库提供的过滤器满足这一要求.

格式化

对于基于文本的接收器后端, 前端实现记录格式化. 与过滤器一样, 可以使用 lambda 表达式 构造格式化器. 对于基于文本的接收器, 可以通过调用 set_formatter 方法设置格式化器, 或通过调用 reset_formatter 清除.

异常处理

所有接收器前端都允许设置异常处理器, 以便按接收器逐一自定义错误处理. 可以通过 set_exception_handler 方法安装异常处理函数; 当在后端的记录处理过程中或接收器专属过滤期间发生异常时, 该函数将从 catch 块中以无参数方式调用. 异常处理器可以自由地重新抛出异常或抑制它. 在前一种情况下, 异常会传播到核心, 在那里可以有另一层异常处理发挥作用.

提示

日志核心 和 日志器 也支持安装异常处理器.

库提供了一个 便捷工具, 用于将异常分派到一元多态函数对象.

注释

异常处理器不允许返回值. 这意味着一旦发生异常, 您无法改变过滤结果, 因此过滤将始终失败.

注释

所有接收器前端都假定从多个线程并发调用异常处理器是安全的. 库提供的异常分派器满足这一要求.

无锁接收器前端 

#include <boost/log/sinks/unlocked_frontend.hpp>

无锁接收器前端以 unlocked_sink 类模板实现. 该前端为后端提供最基本的服务. unlocked_sink 前端在访问后端时不执行线程同步, 假定同步要么不需要, 要么已由后端实现. 尽管如此, 设置过滤器仍然是线程安全的 (即当其他线程正在通过该接收器写日志时, 可以安全地更改 unlocked_sink 前端的过滤器). 这是单线程环境中唯一可用的接收器前端. 用法示例如下:

enum severity_level
{
    normal,
    warning,
    error
};

// A trivial sink backend that requires no thread synchronization
class my_backend :
    public sinks::basic_sink_backend< sinks::concurrent_feeding >
{
public:
    // The function is called for every log record to be written to log
    void consume(logging::record_view const& rec)
    {
        // We skip the actual synchronization code for brevity
        std::cout << rec[expr::smessage] << std::endl;
    }
};

// Complete sink type
typedef sinks::unlocked_sink< my_backend > sink_t;

void init_logging()
{
    boost::shared_ptr< logging::core > core = logging::core::get();

    // The simplest way, the backend is default-constructed
    boost::shared_ptr< sink_t > sink1(new sink_t());
    core->add_sink(sink1);

    // One can construct backend separately and pass it to the frontend
    boost::shared_ptr< my_backend > backend(new my_backend());
    boost::shared_ptr< sink_t > sink2(new sink_t(backend));
    core->add_sink(sink2);

    // You can manage filtering through the sink interface
    sink1->set_filter(expr::attr< severity_level >("Severity") >= warning);
    sink2->set_filter(expr::attr< std::string >("Channel") == "net");
}

库提供的所有接收器后端都要求前端部分进行线程同步. 如果我们尝试在需要比前端所提供更严格线程保证的后端上实例化该前端, 代码将无法编译. 因此, 该前端主要用于单线程环境和自定义后端.

同步接收器前端 

#include <boost/log/sinks/sync_frontend.hpp>

同步接收器前端以 synchronous_sink 类模板实现. 它与 unlocked_sink 类似, 但额外在将日志记录传递给后端之前使用互斥量进行线程同步. 当前所有支持格式化的接收器后端都要求前端进行线程同步.

同步接收器还引入了获取已锁定后端指针的能力. 只要该指针存在, 就保证后端不会被其他线程访问, 除非访问是通过另一个前端或对后端的直接引用进行的. 如果需要在其他线程可能正在写日志的同时对接收器后端执行某些更新, 此功能会很有用. 但要注意, 当后端被锁定时, 任何其他试图向该接收器写日志记录的线程都会被阻塞, 直到后端被释放.

用法与 unlocked_sink 类似.

enum severity_level
{
    normal,
    warning,
    error
};

// Complete sink type
typedef sinks::synchronous_sink< sinks::text_ostream_backend > sink_t;

void init_logging()
{
    boost::shared_ptr< logging::core > core = logging::core::get();

    // Create a backend and initialize it with a stream
    boost::shared_ptr< sinks::text_ostream_backend > backend =
        boost::make_shared< sinks::text_ostream_backend >();
    backend->add_stream(
        boost::shared_ptr< std::ostream >(&std::clog, boost::null_deleter()));

    // Wrap it into the frontend and register in the core
    boost::shared_ptr< sink_t > sink(new sink_t(backend));
    core->add_sink(sink);

    // You can manage filtering and formatting through the sink interface
    sink->set_filter(expr::attr< severity_level >("Severity") >= warning);
    sink->set_formatter
    (
        expr::stream
            << "Level: " << expr::attr< severity_level >("Severity")
            << " Message: " << expr::smessage
    );

    // You can also manage backend in a thread-safe manner
    {
        sink_t::locked_backend_ptr p = sink->locked_backend();
        p->add_stream(boost::make_shared< std::ofstream >("sample.log"));
    } // the backend gets released here
}

异步接收器前端 

#include <boost/log/sinks/async_frontend.hpp>

// Related headers
#include <boost/log/sinks/unbounded_fifo_queue.hpp>
#include <boost/log/sinks/unbounded_ordering_queue.hpp>
#include <boost/log/sinks/bounded_fifo_queue.hpp>
#include <boost/log/sinks/bounded_ordering_queue.hpp>
#include <boost/log/sinks/drop_on_overflow.hpp>
#include <boost/log/sinks/block_on_overflow.hpp>

该前端以 asynchronous_sink 类模板实现. 与同步前端一样, 异步接收器前端提供了一种同步访问后端的方式. 所有日志记录都在专用线程中传递给后端, 这使它适合于可能长时间阻塞的后端 (例如网络和其他与硬件设备相关的接收器). 前端的内部线程在前端构造函数中创建, 并在其析构函数中汇合 (这意味着前端析构可能会阻塞).

注释

异步接收器前端的当前实现使用记录排队. 这在记录发出与其实际处理 (例如写入文件) 之间引入了一定的延迟. 在某些场景下, 这种行为可能不合适, 例如调试容易崩溃的应用程序时.

enum severity_level
{
    normal,
    warning,
    error
};

// Complete sink type
typedef sinks::asynchronous_sink< sinks::text_ostream_backend > sink_t;

boost::shared_ptr< sink_t > init_logging()
{
    boost::shared_ptr< logging::core > core = logging::core::get();

    // Create a backend and initialize it with a stream
    boost::shared_ptr< sinks::text_ostream_backend > backend =
        boost::make_shared< sinks::text_ostream_backend >();
    backend->add_stream(
        boost::shared_ptr< std::ostream >(&std::clog, boost::null_deleter()));

    // Wrap it into the frontend and register in the core
    boost::shared_ptr< sink_t > sink(new sink_t(backend));
    core->add_sink(sink);

    // You can manage filtering and formatting through the sink interface
    sink->set_filter(expr::attr< severity_level >("Severity") >= warning);
    sink->set_formatter
    (
        expr::stream
            << "Level: " << expr::attr< severity_level >("Severity")
            << " Message: " << expr::message
    );

    // You can also manage backend in a thread-safe manner
    {
        sink_t::locked_backend_ptr p = sink->locked_backend();
        p->add_stream(boost::make_shared< std::ofstream >("sample.log"));
    } // the backend gets released here

    return sink;
}

重要

如果在多模块应用程序中使用异步日志, 应谨慎决定何时卸载写日志的动态加载模块. 库中有很多地方可能最终会使用位于动态加载模块中的资源, 例如虚函数表、字符串字面量和函数. 如果当这些资源所在的模块被卸载时, 库仍在使用其中任何资源, 应用程序极有可能崩溃. 严格来说, 这个问题存在于任何接收器类型 (而且首先并不仅限于接收器), 但异步接收器引入了一个额外的问题: 无法得知异步接收器正在使用哪些资源, 因为它在专用线程中工作并使用缓冲的日志记录. 这一问题没有通用解决方案. 建议用户要么避免在应用程序运行期间动态卸载模块, 要么避免使用异步日志. 作为应对该问题的补充手段, 可以尝试在卸载任何模块之前关闭所有异步接收器, 卸载后再重新创建它们. 不过, 避免动态卸载才是彻底解决该问题的唯一途径.

要停止向后端馈送日志记录的专用线程, 可以调用前端的 stop 方法. 该方法会在前端析构函数中自动调用. 与线程中断不同, stop 方法只会在正在馈送的日志记录被后端处理完毕后终止馈送循环 (即不会中断已经开始的记录处理). 不过, 从 stop 方法返回后, 队列中可能仍有剩余记录. 要将这些记录刷入后端, 需要额外调用一次 feed_records 方法. 这在应用程序终止阶段很有用.

void stop_logging(boost::shared_ptr< sink_t >& sink)
{
    boost::shared_ptr< logging::core > core = logging::core::get();

    // Remove the sink from the core, so that no records are passed to it
    core->remove_sink(sink);

    // Break the feeding loop
    sink->stop();

    // Flush all log records that may have left buffered
    sink->flush();

    sink.reset();
}

查看完整代码.

可以通过前端可选的布尔型 start_thread 命名参数抑制创建馈送日志记录的专用线程. 在这种情况下, 用户可以选择以下任一方式处理记录:

  • 调用前端的 run 方法. 该调用会在馈送循环中阻塞. 该循环可以通过调用 stop 中断.
  • 定期调用 feed_records. 该方法会处理发出调用时前端队列中的所有日志记录, 然后返回.
注释

用户应注意不要并发混用这两种方式. 此外, 如果专用馈送线程正在运行 (即构造时未指定 start_thread 或其值为 true), 则不应调用这些方法中的任何一个.

自定义记录排队策略

asynchronous_sink 类模板可以用记录排队策略进行定制. 库提供了以下几种策略:

  • unbounded_fifo_queue. 该策略是默认策略. 顾名思义, 队列深度不受限制, 也不对日志记录排序.
  • unbounded_ordering_queue. 与 unbounded_fifo_queue 一样, 队列深度不受限制, 但会对排队的记录应用排序. 我们稍后会回到排序队列.
  • bounded_fifo_queue. 队列具有在模板参数中指定的有限深度, 以及溢出处理策略. 不应用记录排序.
  • bounded_ordering_queue. 与 bounded_fifo_queue 类似, 但还会应用日志记录排序.
警告

使用无界排队策略时要小心. 由于队列深度不受限制, 如果日志记录持续生成的速度快于后端处理的速度, 队列将不受控制地增长, 表现为内存泄漏.

有界队列支持以下溢出策略:

  • drop_on_overflow. 队列已满时, 静默丢弃多余的日志记录.
  • block_on_overflow. 队列已满时, 阻塞日志线程, 直到后端馈送线程处理掉一些排队记录.

例如, 我们可以这样修改前面的示例, 将记录队列限制为 100 个元素:

// Complete sink type
typedef sinks::asynchronous_sink<
    sinks::text_ostream_backend,
    sinks::bounded_fifo_queue<                                                   
        100,                                                                     
        sinks::drop_on_overflow                                                  
    >
> sink_t;

boost::shared_ptr< sink_t > init_logging()
{
    boost::shared_ptr< logging::core > core = logging::core::get();

    // Create a backend and initialize it with a stream
    boost::shared_ptr< sinks::text_ostream_backend > backend =
        boost::make_shared< sinks::text_ostream_backend >();
    backend->add_stream(
        boost::shared_ptr< std::ostream >(&std::clog, boost::null_deleter()));

    // Wrap it into the frontend and register in the core
    boost::shared_ptr< sink_t > sink(new sink_t(backend));
    core->add_sink(sink);

    // ...

    return sink;
}

日志记录排序

记录排序可用于缓解多线程应用程序中存在的 记录弱序 问题.

排序排队策略会给记录处理引入少量延迟. 延迟时长和排序谓词可以在前端构造时指定. 使用 日志记录排序工具 实现排序谓词可能会很有用.

// Complete sink type
typedef sinks::asynchronous_sink<
    sinks::text_ostream_backend,
    sinks::unbounded_ordering_queue<                                             
        logging::attribute_value_ordering<                                       
            unsigned int,                                                        
            std::less< unsigned int >                                            
        >
    >
> sink_t;

boost::shared_ptr< sink_t > init_logging()
{
    boost::shared_ptr< logging::core > core = logging::core::get();

    // Create a backend and initialize it with a stream
    boost::shared_ptr< sinks::text_ostream_backend > backend =
        boost::make_shared< sinks::text_ostream_backend >();
    backend->add_stream(
        boost::shared_ptr< std::ostream >(&std::clog, boost::null_deleter()));

    // Wrap it into the frontend and register in the core
    boost::shared_ptr< sink_t > sink(new sink_t(
        backend,                                                                 
        keywords::order = logging::make_attr_ordering< unsigned int >(           
            "LineID", std::less< unsigned int >()),
        keywords::ordering_window = std::chrono::seconds(1)                      
    ));
    core->add_sink(sink);

    // You can manage filtering and formatting through the sink interface
    sink->set_filter(expr::attr< severity_level >("Severity") >= warning);
    sink->set_formatter
    (
        expr::stream
            << "Level: " << expr::attr< severity_level >("Severity")
            << " Message: " << expr::smessage
    );

    // You can also manage backend in a thread-safe manner
    {
        sink_t::locked_backend_ptr p = sink->locked_backend();
        p->add_stream(boost::make_shared< std::ofstream >("sample.log"));
    } // the backend gets released here

    return sink;
}

在上面的代码示例中, 接收器前端会将日志记录保留在内部队列中最多一秒, 并基于 unsigned int 类型的日志记录计数器进行排序. ordering_window 参数是可选的, 默认为某个足够小的系统特定值, 足以维持日志记录按时间顺序流向后端.

即使停止了内部馈送循环, 前端也会保持排序窗口, 因此可以重新进入循环而不破坏记录排序. 另一方面, 为了确保所有日志记录都被刷入后端, 必须在应用程序结束时调用 flush 方法.

void stop_logging(boost::shared_ptr< sink_t >& sink)
{
    boost::shared_ptr< logging::core > core = logging::core::get();

    // Remove the sink from the core, so that no records are passed to it
    core->remove_sink(sink);

    // Break the feeding loop
    sink->stop();

    // Flush all log records that may have left buffered
    sink->flush();

    sink.reset();
}
