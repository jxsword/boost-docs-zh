再谈过滤

前面的章节已经触及过滤, 但只是浅尝辄止. 既然我们能够向日志记录添加属性并设置接收器, 我们可以构建任意复杂的过滤. 我们来看这个示例:

BOOST_LOG_ATTRIBUTE_KEYWORD(line_id, "LineID", unsigned int)
BOOST_LOG_ATTRIBUTE_KEYWORD(severity, "Severity", severity_level)
BOOST_LOG_ATTRIBUTE_KEYWORD(tag_attr, "Tag", std::string)

void init()
{
    // Setup the common formatter for all sinks
    logging::formatter fmt = expr::stream
        << std::setw(6) << std::setfill('0') << line_id << std::setfill(' ')
        << ": <" << severity << ">\t"
        << expr::if_(expr::has_attr(tag_attr))
           [
               expr::stream << "[" << tag_attr << "] "
           ]
        << expr::smessage;

    // Initialize sinks
    typedef sinks::synchronous_sink< sinks::text_ostream_backend > text_sink;
    boost::shared_ptr< text_sink > sink = boost::make_shared< text_sink >();

    sink->locked_backend()->add_stream(
        boost::make_shared< std::ofstream >("full.log"));

    sink->set_formatter(fmt);

    logging::core::get()->add_sink(sink);

    sink = boost::make_shared< text_sink >();

    sink->locked_backend()->add_stream(
        boost::make_shared< std::ofstream >("important.log"));

    sink->set_formatter(fmt);

    sink->set_filter(severity >= warning || (expr::has_attr(tag_attr) && tag_attr == "IMPORTANT_MESSAGE"));

    logging::core::get()->add_sink(sink);

    // Add attributes
    logging::add_common_attributes();
}

查看完整代码.

在此示例中, 我们初始化两个接收器 —— 一个用于完整的日志文件, 另一个只用于重要消息. 两个接收器都将以相同的日志记录格式写入文本文件, 我们先初始化该格式并保存到 fmt 变量中. formatter 类型是一个类型擦除的函数对象, 具有格式化器的调用签名; 在很多方面可以将其视为类似于 boost::function 或 std::function, 只是它永远不会为空. 过滤器也有对应的 a similar function object.

值得注意的是, 这里的格式化器本身包含一个过滤器. 可以看到, 格式中包含一个条件部分, 仅当日志记录含有 "Tag" 属性时才会出现. has_attr 谓词检查记录是否包含 "Tag" 属性值, 并控制它是否写入文件. 我们用属性关键字为谓词指定属性的名称和类型, 但也可以在 has_attr 调用处指定它们. 条件格式化器在 此处 有更详细的解释.

接下来是两个接收器的初始化. 第一个接收器没有任何过滤器, 这意味着它会把每条日志记录都保存到文件. 我们对第二个接收器调用 set_filter, 使其只保存严重级别不低于 warning 或具有值为 "IMPORTANT_MESSAGE" 的 "Tag" 属性的日志记录. 可以看到, 过滤器语法非常像常规的 C++, 尤其是使用属性关键字时.

与格式化器一样, 也可以使用自定义函数作为过滤器. 从根本上说, 过滤器函数必须支持以下签名:

bool (logging::attribute_value_set const& attrs);

过滤器被调用时, attrs 将包含完整的属性值集, 可用于决定日志记录应被传递还是被抑制. 如果过滤器返回 true, 日志记录将被构造并由接收器进一步处理. 否则, 记录将被丢弃.

Boost.Phoenix 在构造过滤器时非常有用. 它可以自动从 attrs 集中提取属性值, 因为其 bind 实现与属性占位符兼容. 前面的示例可以这样修改:

bool my_filter(logging::value_ref< severity_level, tag::severity > const& level,
               logging::value_ref< std::string, tag::tag_attr > const& tag)
{
    return level >= warning || tag == "IMPORTANT_MESSAGE";
}

void init()
{
    // ...

    namespace phoenix = boost::phoenix;
    sink->set_filter(phoenix::bind(&my_filter, severity.or_none(), tag_attr.or_none()));

    // ...
}

如上所示, 自定义过滤器以单独实参的方式接收属性值, 包装在 value_ref 模板中. 该包装器包含对指定类型属性值的可选引用; 若日志记录包含所需类型的属性值, 引用有效. my_filter 中使用的关系运算符可以无条件应用, 因为如果引用无效, 它们会自动返回 false. 其余工作由 bind 表达式完成, 它会识别 severity 和 tag_attr 关键字, 提取相应的值后再传递给 my_filter.

注释

由于与 Boost.Phoenix 集成相关的限制 (参见 #7996), 当属性关键字与 phoenix::bind 或 phoenix::function 一起使用时, 必须显式指定属性值缺失时的回退策略. 在上面的示例中, 这是通过调用 or_none 实现的, 若值未找到, 结果是一个空的 value_ref. 在其他上下文中, 该策略是默认的. 还有 其他策略 可以代替使用.

您可以编译并运行 测试 来尝试其工作方式.
