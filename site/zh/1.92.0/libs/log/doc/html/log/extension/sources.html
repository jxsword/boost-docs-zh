编写自己的日志源 

#include <boost/log/sources/threading_models.hpp>
#include <boost/log/sources/basic_logger.hpp>

您可以通过开发自己的日志源来扩展库, 并就此扩展收集日志数据的方式. 基本上有两种起步选择: 要么开发一个新的日志器特性, 要么设计一种全新的日志源类型. 如果您只需要微调现有日志器的功能, 第一种方式很好; 如果库提供的日志器收集日志的整个机制不适合您的需求, 第二种方式是合理的.

创建新的日志器特性

库提供的每个日志器都由若干可以相互组合的特性组成. 每个特性负责日志器功能中单一且独立的一个方面. 例如, 提供为日志记录分配严重级别能力的日志器包含 severity 特性. 您可以实现自己的特性, 并与库提供的特性一起使用.

日志器特性应遵循以下基本要求:

  • 日志特性应当是类模板. 它应至少有一个模板参数类型 (不妨命名为 BaseT).
  • 该特性必须公开派生自 BaseT 模板参数.
  • 该特性必须可默认构造且可复制构造.
  • 该特性必须可以用一个模板化类型的单个实参构造. 特性本身可以不使用该实参, 但应将该实参传递给 BaseT 构造函数.

这些要求允许由多个相互派生的特性组合出一个日志器. 特性层次结构的根类将是 basic_logger 类模板实例. 该类实现日志器的大部分基本功能, 例如存储日志器专属属性, 以及提供日志消息格式化接口. 层次结构的组合由 basic_composite_logger 类模板完成, 它以特性序列实例化 (别担心, 稍后会用一个示例展示). 带模板化实参的构造函数允许使用 Boost.Parameter 库通过命名参数初始化特性.

日志特性也可以包含内部数据. 在这种情况下, 为了维护日志器的线程安全, 特性应遵循以下附加准则:

  1. 通常不需要在每个特性中引入互斥量或其他同步机制. 而且, 建议不要这样做, 因为同一特性既可能用于线程安全的日志器, 也可能用于非线程安全的日志器. 相反, 特性应使用日志器的线程模型作为同步原语, 类似于使用互斥量的方式. 线程模型可通过 get_threading_model 方法访问, 该方法定义在 basic_logger 类模板中.
  2. 如果特性必须重写 *_unlocked 方法 (属于 basic_logger 类模板的受保护接口, 或基特性接口的同一部分), 关于这类方法应考虑以下几点:
    • 最终调用这些方法的公开方法由 basic_composite_logger 类模板实现. 这些实现会进行必要的加锁, 然后将控制传递给基特性的对应 _unlocked 方法.
    • 这些方法的线程安全要求用锁类型表示. 这些类型作为 typedef 在每个特性以及 basic_logger 类模板中提供. 如果特性暴露受保护函数 foo_unlocked, 它也会暴露类型 foo_lock, 该类型表达 foo_unlocked 的加锁要求. foo 方法 (位于 basic_composite_logger 类模板中) 会使用该 typedef, 在调用 foo_unlocked 之前锁定线程模型.
    • 特性构造函数不需要加锁, 因此不需要为它们定义锁类型.
  3. 特性可以实现复制构造函数. 调用构造函数时, 构造函数的参数已被共享锁锁定. 自然, 特性应将复制构造调用转发给 BaseT 类.
  4. 特性无需实现赋值运算符. 赋值将由 basic_composite_logger 类实例自动提供. 不过, 特性可以提供 swap_unlocked 方法, 交换本特性与方法实参的内容, 并调用 BaseT 类中的类似方法. 自动生成的赋值运算符将连同复制构造函数一起使用该方法.

为了说明这些冗长的建议, 我们来实现一个简单的日志器特性. 假设我们希望日志器能够为单条日志记录打标记. 换句话说, 日志器必须临时向其属性集添加一个属性, 发出日志记录, 然后自动移除该属性. 使用作用域属性可以实现类似功能, 尽管语法可能使把它包装成一个整洁的宏变得复杂:

// We want something equivalent to this
{
    BOOST_LOG_SCOPED_LOGGER_TAG(logger, "Tag", "[GUI]");
    BOOST_LOG(logger) << "The user has confirmed his choice";
}

我们来声明日志器特性:

template< typename BaseT >
class record_tagger_feature :
    public BaseT                        
{
public:
    // Let's import some types that we will need. These imports should be public,
    // in order to allow other features that may derive from record_tagger to do the same.
    typedef typename BaseT::char_type char_type;
    typedef typename BaseT::threading_model threading_model;

public:
    // Default constructor. Initializes m_Tag to an invalid value.
    record_tagger_feature();
    // Copy constructor. Initializes m_Tag to a value, equivalent to that.m_Tag.
    record_tagger_feature(record_tagger_feature const& that);
    // Forwarding constructor with named parameters
    template< typename ArgsT >
    record_tagger_feature(ArgsT const& args);

    // The method will require locking, so we have to define locking requirements for it.
    // We use the strictest_lock trait in order to choose the most restricting lock type.
    typedef typename logging::strictest_lock<
        std::lock_guard< threading_model >,
        typename BaseT::open_record_lock,
        typename BaseT::add_attribute_lock,
        typename BaseT::remove_attribute_lock
    >::type open_record_lock;

protected:
    // Lock-less implementation of operations
    template< typename ArgsT >
    logging::record open_record_unlocked(ArgsT const& args);
};

// A convenience metafunction to specify the feature
// in the list of features of the final logger later
struct record_tagger :
    public boost::mpl::quote1< record_tagger_feature >
{
};

特性应派生自其他特性或 basic_logger 类

可以看到, 我们使用 strictest_lock 模板来定义锁类型, 使其满足基类的线程安全要求, 供将从 record_tagger_feature 的对应方法调用的方法使用. open_record_lock 定义表明, open_record_unlocked 实现 (属于 record_tagger_feature 特性) 需要日志器的排他锁 (lock_guard 正是这种锁), 但它也考虑了基类 open_record_unlocked、add_attribute_unlocked 和 remove_attribute_unlocked 方法的加锁要求, 因为它必须调用这些方法. 最终日志器类生成的 open_record 方法将利用该 typedef, 在转发到 open_record_unlocked 方法之前自动获取相应的锁类型.

实际上, 在这个特定示例中, 并不需要使用 strictest_lock 特征, 因为我们所有的方法都需要排他锁, 而这已经是最严格的了. 不过, 如果您使用共享锁, 该模板可能会派上用场.

公开接口的实现变得相当简单:

template< typename BaseT >
record_tagger_feature< BaseT >::record_tagger_feature()
{
}

template< typename BaseT >
record_tagger_feature< BaseT >::record_tagger_feature(record_tagger_feature const& that) :
    BaseT(static_cast< BaseT const& >(that))
{
}

template< typename BaseT >
template< typename ArgsT >
record_tagger_feature< BaseT >::record_tagger_feature(ArgsT const& args) : BaseT(args)
{
}

现在, 由于所有加锁都提取到了公开接口中, 特性逻辑的大部分需要在接口的受保护部分实现. 为了在日志器中设置标记值, 我们必须引入一个新的 Boost.Parameter 关键字. 按照该库文档的建议, 最好在专用命名空间中引入该关键字:

namespace my_keywords {

    BOOST_PARAMETER_KEYWORD(tag_ns, tag)

}

打开新记录现在大致如下:

template< typename BaseT >
template< typename ArgsT >
logging::record record_tagger_feature< BaseT >::open_record_unlocked(ArgsT const& args)
{
    // Extract the named argument from the parameters pack
    std::string tag_value = args[my_keywords::tag | std::string()];

    logging::attribute_set& attrs = BaseT::attributes();
    logging::attribute_set::iterator tag = attrs.end();
    if (!tag_value.empty())
    {
        // Add the tag as a new attribute
        std::pair<
            logging::attribute_set::iterator,
            bool
        > res = BaseT::add_attribute_unlocked("Tag",
            attrs::constant< std::string >(tag_value));
        if (res.second)
            tag = res.first;
    }

    // In any case, after opening a record remove the tag from the attributes
    BOOST_SCOPE_EXIT_TPL((&tag)(&attrs))
    {
        if (tag != attrs.end())
            attrs.erase(tag);
    }
    BOOST_SCOPE_EXIT_END

    // Forward the call to the base feature
    return BaseT::open_record_unlocked(args);
}

这里, 如果调用 open_record 时指定了标记值, 我们就添加一个带有该标记值的新属性. 打开日志记录时, 所有属性值都会被获取并随记录一起锁定, 因此我们用 Boost.ScopeExit 块从属性集中移除该标记.

好了, 我们得到了自己的特性, 现在是把它注入日志器的时候了. 假设我们想把它与标准严重级别日志组合起来. 没问题:

template< typename LevelT = int >
class my_logger :
    public src::basic_composite_logger<
        char,                           
        my_logger< LevelT >,            
        src::single_thread_model,       
        src::features<                  
            src::severity< LevelT >,
            record_tagger
        >
    >
{
    // The following line will automatically generate forwarding constructors that
    // will call to the corresponding constructors of the base class
    BOOST_LOG_FORWARD_LOGGER_MEMBERS_TEMPLATE(my_logger)
};

如上所示, 创建日志器是相当简单的过程. 这里看到的 BOOST_LOG_FORWARD_LOGGER_MEMBERS_TEMPLATE 宏只是为了方便: 它展开为默认构造函数、复制构造函数、赋值运算符, 以及若干支持命名实参的构造函数. 对于非模板日志器, 有一个类似的 BOOST_LOG_FORWARD_LOGGER_MEMBERS 宏.

假设我们像这样定义了严重级别:

enum severity_level
{
    normal,
    warning,
    error
};

现在我们可以这样使用日志器:

void manual_logging()
{
    my_logger< severity_level > logger;

    logging::record rec = logger.open_record((keywords::severity = normal, my_keywords::tag = "GUI"));
    if (rec)
    {
        logging::record_ostream strm(rec);
        strm << "The user has confirmed his choice";
        strm.flush();
        logger.push_record(boost::move(rec));
    }
}

所有这些繁琐的写法通常并不需要. 可以定义一个特殊宏使代码更简洁:

#define LOG_WITH_TAG(lg, sev, tg) \
    BOOST_LOG_WITH_PARAMS((lg), (keywords::severity = (sev))(my_keywords::tag = (tg)))

void logging_function()
{
    my_logger< severity_level > logger;

    LOG_WITH_TAG(logger, normal, "GUI") << "The user has confirmed his choice";
}

面向独立日志源设计者的准则

一般而言, 您可以按自己喜欢的方式实现新的日志源, 库不强制对日志源提出任何设计要求. 不过, 关于日志源应如何与日志核心交互, 有一些注意事项.

  1. 每当日志源准备好发出日志记录时, 它应调用核心中的 open_record. 日志源专属属性应传入该调用. 在该调用期间, 核心为正在创建的记录分配资源并执行过滤.
  2. 如果对 open_record 的调用返回了有效的日志记录, 则该记录已通过过滤, 被视为已打开. 记录随后既可以由日志源通过后续调用 push_record 确认, 也可以通过销毁它而撤回.
  3. 如果对 open_record 的调用返回了无效 (空) 的日志记录, 则说明记录未被打开 (很可能因过滤被拒绝). 此时日志核心不持有与该记录关联的任何资源, 因此日志源不得为这次日志尝试调用 push_record.
  4. 日志源随后可以打开不止一条记录. 已打开的日志记录彼此独立存在.
