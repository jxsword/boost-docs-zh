支持的编译器与平台

库应能在相当符合标准的 C++11 编译器下构建和运行. 库已在以下平台上成功构建和测试:

  • Windows 10. MSVC 14.0 及更新版本. gcc 5.x 的 MinGW32, 以及 gcc 6.x 及更新版本的 MinGW-w64.
  • gcc 7.x 及更新版本的 Cygwin 和 Cygwin64.
  • Linux. GCC 5.x 及更新版本.
  • Linux. Clang 3.5 及更新版本.

以下编译器/平台不受支持, 编译该库很可能失败:

  • 不支持 C++11 的编译器.
  • 搭配非 C++11 标准库的 C++11 编译器 (例如搭配 GCC 4.2 的 libstdc++ 的 Clang). 请在 C++11 模式下使用 C++11 标准库.
  • MSVC 12.0 及更早版本.
  • GCC 4.4 及更早版本.
  • Borland C++ 5.5.1 (免费版). 较新版本可能可用也可能不可用.
  • Solaris Studio 12.3 及更早版本.
  • 不支持 Windows 9x、ME、NT4、2000 及更早版本.

Boost.Log 应与 Boost 支持的所有硬件架构兼容. 不过, 对于 32 位 x86 架构, 库至少需要 i586 级别的 CPU 才能运行.

GCC 用户须知

GCC 4.5 起支持链接时优化 (LTO), 此时大部分优化和二进制代码生成在链接阶段进行. 这可以进行更高级的优化并生成更快的代码. 遗憾的是, 它与包含需要以不同编译器选项编译的源文件的项目配合不佳. Boost.Log 就是这样的项目之一, 其部分源码包含针对现代 CPU 的优化, 无法在较旧的 CPU 上运行. 为 Boost.Log 启用 LTO 会产生与较旧 CPU 不兼容的二进制文件 (GCC 缺陷 61043、77845), 很可能导致运行期崩溃. 因此 Boost.Log 不支持 LTO.

存在一个 GCC 缺陷, 使用 -march=native 命令行参数时可能导致编译失败. 建议避免使用 -march=native 参数 (或 instruction-set=native b2 属性), 而是显式指定目标 CPU (例如 instruction-set=sandy-bridge).

MinGW、Cygwin 和 Visual Studio Express 版用户须知

要用这些编译器编译库, 需要一些特殊准备. 首先, 对于 MinGW 或 Cygwin, 请确保安装了最新版本的 GCC. 库在 GCC 3.x 下很可能无法编译.

其次, 库在某个阶段会需要 Message Compiler 工具 (mc.exe), 而 MinGW、Cygwin 和某些版本的 MSVC Express 版没有该工具. 通常, 库构建脚本会自动检测系统中是否存在消息编译器, 如果没有, 则禁用库中与事件日志相关的部分. 如果需要事件日志支持但系统中未找到消息编译器, 有三种解决方案. 推荐的方案是获取原版 mc.exe. 该工具可在 Windows SDK 中找到, Windows SDK 可从 Microsoft 网站免费下载 (例如 此处). 此外, 该工具应也包含在 Visual Studio 2010 Express 版中. 编译期间, mc.exe 必须能通过 PATH 环境变量所列目录之一访问到.

另一种方式是尝试使用 MinGW 和 Cygwin 随附的 windmc.exe 工具, 它是原版 mc.exe 的等价物. 为此, 您必须修补 Boost.Build 文件 (特别是 tools/build/tools/mc.jam), 如 此 工单所述 文件). 之后, 您就可以在 b2 中指定 mc-compiler=windmc 选项来构建库.

如果消息编译器检测因某种原因失败, 可以在构建库时定义 BOOST_LOG_WITHOUT_EVENT_LOG 配置宏, 显式禁用事件日志后端支持. 这样就不再需要消息编译器. 更多配置选项参见 本节.

Windows XP 上的 MinGW 用户可能受到操作系统附带的 msvcrt.dll 中 缺陷 的影响. 该缺陷表现为库格式化日志记录时崩溃. 该问题并非 Boost.Log 特有, 也可能在与 locale 和 IO 流管理相关的其他场景中出现.

Cygwin 用户补充说明

对 Cygwin 的支持非常初步. Cygwin 中可用的默认 GCC 版本 (截至撰写时为 4.5.3) 因编译器错误而无法编译该库. 您必须从源码构建较新的 GCC. 即便如此, 某些 Boost.Log 功能也不可用. 特别是, 基于套接字的 syslog 后端 不受支持, 因为它基于 Boost.Asio, 后者在该平台上无法编译. 不过, 原生 syslog 支持仍然可用.
