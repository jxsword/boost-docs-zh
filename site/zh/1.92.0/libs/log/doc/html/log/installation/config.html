库的配置与构建

库有一个单独编译的部分, 应按 入门指南 中的描述构建. 不过有一点需要注意. 如果您的应用程序由多个使用 Boost.Log 的模块组成 (例如一个 exe 和一个或多个 dll), 库 必须 构建为共享对象. 如果您只有单个可执行文件或单个使用 Boost.Log 的模块, 则可以将库构建为静态库.

库支持若干配置宏:

表 1.1. 配置宏

宏名

效果

CMake 说明

BOOST_LOG_DYN_LINK

如果在用户代码中定义, 库将假定二进制文件构建为动态加载库 ("dll" 或 "so"). 否则假定库以静态模式构建. 对于使用日志功能的用户应用程序的所有翻译单元, 该宏必须一致地定义或不定义. 在支持自动链接的平台上, 该宏可帮助自动链接.

根据 BUILD_SHARED_LIBS CMake 选项自动定义.

BOOST_ALL_DYN_LINK

与 BOOST_LOG_DYN_LINK 相同, 但以同样的方式影响其他 Boost 库.

BOOST_USE_WINAPI_VERSION

同时影响库和用户代码的编译. 该宏是 Windows 专属的. 为包括 Boost.Log 在内的各种 Boost 库选择目标 Windows 版本. 为特定 Windows 版本编译的代码很可能无法在较旧的 Windows 版本上运行, 但由于使用较新的 OS 特性, 可能会提升性能. 该宏应具有等同于 _WIN32_WINNT 的整数值.

BOOST_LOG_NO_THREADS

如果定义, 则禁用多线程支持. 同时影响库和用户代码的编译. 未检测到线程支持时, 该宏会被自动定义.

BOOST_LOG_WITHOUT_CHAR

如果定义, 则禁用窄字符日志支持. 同时影响库和用户代码的编译.

BOOST_LOG_WITHOUT_WCHAR_T

如果定义, 则禁用宽字符日志支持. 同时影响库和用户代码的编译.

BOOST_LOG_NO_QUERY_PERFORMANCE_COUNTER

该宏只在 Windows 上有用. 它同时影响库和用户代码的编译. 如果定义, 则禁用 QueryPerformanceCounter API 在 timer 属性中的支持. 这将导致时间读数的精度显著下降. 该宏旨在解决早期版本 AMD Athlon CPU 的可能问题, 相关描述见 此处 和 此处. 还存在已知的芯片组硬件故障, 可能导致该 API 无法正常工作 (参见 此处).

BOOST_LOG_USE_NATIVE_SYSLOG

只影响库的编译. 如果由于某种原因未自动检测到对原生 SysLog API 的支持, 请定义该宏以强制启用它.

BOOST_LOG_WITHOUT_DEFAULT_FACTORIES

只影响库的编译. 如果定义, settings 解析器将在构建时不包含过滤器和格式化器的任何默认工厂. 在从字符串解析任何过滤器或格式化器之前, 用户必须在库中注册所有属性. 这可以显著减小二进制体积.

BOOST_LOG_WITHOUT_SETTINGS_PARSERS

只影响库的编译. 如果定义, 与 settings 解析器相关的任何设施都不会构建. 这可以显著减小二进制体积.

禁用 boost_log_setup 库的编译.

BOOST_LOG_WITHOUT_DEBUG_OUTPUT

只影响库的编译. 如果定义, 将不构建 Windows 调试器输出支持.

BOOST_LOG_WITHOUT_EVENT_LOG

只影响库的编译. 如果定义, 将不构建 Windows 事件日志支持. 定义该宏也使 Message Compiler 工具链不再必要.

BOOST_LOG_WITHOUT_SYSLOG

只影响库的编译. 如果定义, 将不构建 syslog 后端 支持.

BOOST_LOG_WITHOUT_IPC

只影响库的编译. 如果定义, 将不构建 进程间队列 及相关 后端 支持.

BOOST_LOG_WITHOUT_ASIO

同时影响库和用户代码的编译. 如果定义, 将不构建依赖 Boost.ASIO 的功能. 特别是, 这会禁用基于套接字的 syslog 后端 实现.

BOOST_LOG_NO_SHORTHAND_NAMES

只影响用户代码的编译. 如果定义, 某些已弃用的简写宏名将不可用.

不是 CMake 配置选项.

BOOST_LOG_USE_COMPILER_TLS

只影响库的编译. 该宏启用对线程局部存储的编译器内建函数支持. 定义它可以提升 Boost.Log 的性能, 但前提是接受某些使用上的限制. 更多说明见下文.

BOOST_LOG_USE_STD_REGEX、BOOST_LOG_USE_BOOST_REGEX 或 BOOST_LOG_USE_BOOST_XPRESSIVE

只影响库的编译. 通过定义这些宏之一, 用户可以指示 Boost.Log 内部使用 std::regex、Boost.Regex 或 Boost.Xpressive 来处理从字符串和设置解析的字符串匹配过滤器. 如果这些宏都未定义, Boost.Log 默认使用 Boost.Regex. 使用 std::regex 或 Boost.Regex 通常产生更小的可执行文件, 其中 Boost.Regex 通常运行期也最快. 使用 Boost.Xpressive 可以消除对 Boost.Regex 编译后二进制文件的依赖. 注意, 这些宏不影响用户创建的 过滤表达式.

请勿定义这些宏之一, 而应使用 BOOST_LOG_USE_REGEX_BACKEND 字符串选项并取以下值之一: "std::regex"、"Boost.Regex" 或 "Boost.Xpressive". CMake 会相应地定义这些宏.

您可以在 b2 命令行中定义配置宏, 如下所示:

b2 --with-log variant=release define=BOOST_LOG_WITHOUT_EVENT_LOG define=BOOST_USE_WINAPI_VERSION=0x0600 stage

使用 CMake 时, 配置宏可以在命令行中作为 CMake 选项指定, 如下所示:

cmake .. -DCMAKE_BUILD_TYPE=Release -DBOOST_LOG_WITHOUT_EVENT_LOG=On

不过, 在 "boost/config/user.hpp" 文件中定义配置宏可能更方便, 这样可以同时为库和用户项目自动定义它们. 如果未指定任何选项, 库将尝试支持尽可能全面的配置, 包括对目标平台可用的所有字符类型和功能的支持.

日志库使用其他几个也需要构建的 Boost 库. 它们是 Boost.Filesystem、Boost.System、Boost.DateTime、Boost.Thread, 以及在某些配置下的 Boost.Regex. 有关构建过程的详细说明, 请参阅它们的文档.

最后还需要补充一点. 库要求在库编译和用户代码编译中都启用运行期类型信息 (RTTI). 通常, 这不需要您做任何事情, 只需确认项目中没有禁用 RTTI 支持即可.

关于编译器 TLS 内建函数的说明

许多广泛使用的编译器支持管理线程局部存储的内建函数, 库的多个部分都用到了它. C++11 标准也包含该特性. 一般而言, 与任何替代实现相比 (无论是 Boost.Thread 还是原生操作系统 API), 这些内建函数能更高效地访问存储. 不过, 该特性有几个注意事项:

  • 某些操作系统不支持在应用程序运行期动态加载的共享库中定义的 TLS 使用这些内建函数. 这些系统包括 Linux 和 Vista 之前的 Windows. Windows Vista 及更高版本没有此问题.
  • 可能无法从全局构造函数和析构函数可靠地访问 TLS. 已知 Windows 上的 MSVC 8.0 至少存在此问题.

库提供 BOOST_LOG_USE_COMPILER_TLS 配置宏, 允许启用该特性, 这将以接受以下限制为代价提升库的性能:

  • 应用程序可执行文件必须与 Boost.Log 库链接. 它不应在运行期动态加载.
  • 应用程序不得在全局构造函数或析构函数中使用日志.

注意, BOOST_LOG_USE_COMPILER_TLS 宏只控制 Boost.Log 中 TLS 的使用, 而不控制 Boost.Log 所用其他库中的 TLS. 例如, Boost.Asio 默认使用编译器提供的 TLS. 要构建完全不用编译器提供 TLS 的 Boost.Log 二进制文件, 还必须在这些其他库中禁用该特性 (对 Boost.Asio 而言, 可以在构建和使用 Boost 时定义 BOOST_ASIO_DISABLE_THREAD_KEYWORD_EXTENSION 来实现).

另请注意, 启用编译器对 TLS 的内建支持并不会移除对 Boost.Thread 或更低层 OS 线程原语 (包括实现 TLS 的那些) 的依赖. 使用编译器 TLS 内建函数的目的是获得更好的性能, 而不是减少依赖.

关于原生 wchar_t 支持的说明

一些编译器 (最著名的是 MSVC) 提供禁用原生 wchar_t 类型的选项, 用某个标准整型类型的 typedef 模拟它. 从 C++ 语言的角度看, 这种行为不符合标准, 但对于某些难以更新的遗留代码, 这可能有助于兼容.

默认情况下, Boost (以及作为其一部分的 Boost.Log) 在启用原生 wchar_t 的情况下构建. 截至撰写本文时, 用户必须修改 Boost.Build 才能启用模拟模式. 在此模式下构建 Boost.Log 是可能的, 但必须牢记几个注意事项:

  • 编译出的 Boost.Log 二进制文件将导出与构建时所选配置对应的符号. 用户代码必须使用与构建 Boost.Log 时相同的设置, 否则会出现链接错误.
  • 由于在模拟模式中 wchar_t 与某个整型类型无法区分, 库的某些部分的行为可能与启用原生 wchar_t 的正常模式不同. 特别是, 宽字符字面量可能被拒绝或以不同方式格式化.
  • 模拟模式未经测试, 因此可能出现意外的故障.

因此不建议使用模拟模式, 应予以避免. 在库的未来版本中, 对其支持可能被完全移除.

Windows 上的 CMake 用户须知

要在 Windows 上使用 CMake 编译带事件日志支持的 Boost.Log, 初始 CMake 配置应在资源 (rc.exe 或 windres.exe) 和消息编译器工具 (mc.exe 或 windmc.exe) 可通过 PATH 环境变量访问的情况下执行. 对于 MSVC, 建议在 Visual Studio 命令行中运行 CMake, 或以其他方式确保已设置 Windows SDK 环境变量.

或者, 用户可以将 RC 和 MC 环境变量分别设置为资源编译器和消息编译器可执行文件的路径, 或在命令行中将 CMAKE_RC_COMPILER 和 CMAKE_MC_COMPILER CMake 选项设置为相应路径.
