后续版本中的待办事项

本节中的条目不一定会实现. 这些主要是关于进一步改进库的一些想法.

  • 优化单线程配置. 在许多地方, 如果禁用多线程支持, 可以避免动态内存分配.
  • SNMP 支持. 想法是实现一个接收器后端, 作为处理日志记录的结果发出 SNMP 陷阱. 这需要大量的研究和思考.
  • 提供一个编译期选项, 从应用程序中移除所有日志 (编译出的二进制文件内部应不包含任何日志痕迹). 提出这一需求有两个原因: 追求最大性能, 以及在不带日志的构建中隐藏函数名称和内部消息等内部信息, 以防逆向工程. 实际上, 这不仅要求将所有库宏重定义为空, 还要为许多库组件提供占位实现. 需要更多考虑. 也许, 只抑制宏就足够了.
  • 提供一个类似 BOOST_LOG_FUNCTION 的宏, 但具有自动记录所有函数实参的能力.
  • 考虑仅头文件配置. 也许以减少功能为代价.
  • 将 syslog 支持更新到 RFC 5424.
  • 提供某种共享格式化器. 想法是多个接收器可以使用同一格式化器. 如果一条日志记录通过过滤到达多个此类接收器, 则对所有共享该格式化器的接收器只做一次格式化. 也许这需要重构接收器架构, 将它们转变为管道, 格式化器和后端只是日志记录处理中的步骤.
  • 允许在文本文件后端中更改文件流的 locale. 在宽字符日志中, locale 可以改变字符编码转换.
  • 改进文件接收器中的文件收集. 使其可以 (i) 重命名被收集的文件, 以及 (ii) 在专用线程中收集文件.
  • 提供包含库组件前向声明的头文件.
  • 使从文件加载设置后能够更新库配置. 也许这需要一个新的配置实体, 能够检测并应用设置之间的变更.
  • 开发一个统计信息收集框架. 基本思路是提供一个特定的日志源和一个 pin. 用户可以 pin 他的数据, 或通过调用日志源显式指示事件. 日志源会自动从被 pin 的变量收集数据. 该日志源应与过滤器有更好的集成, 以便能够确定哪些 pin 应被收集, 哪些不应.
  • 允许在基于文件的接收器的文件名模式中指定进程 ID.
  • 改进对 format 格式化器的支持, 实现占位符格式标志.
