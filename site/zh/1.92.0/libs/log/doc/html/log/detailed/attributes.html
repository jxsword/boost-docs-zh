#include <boost/log/attributes/attribute.hpp>
#include <boost/log/attributes/attribute_cast.hpp>
#include <boost/log/attributes/attribute_value.hpp>

如 设计概述 所述, Boost.Log 中的属性表示要与日志记录关联的信息. 属性本质上是一个函数, 被调用时产生一个属性值. 该函数每次调用可能产生不同的值, 也可能每次调用都产生相同的值. 例如, local_clock 属性根据本地挂钟时钟产生时间戳值, 而 constant 每次都产生相同的值.

库中的所有属性都使用 pimpl 惯用法 实现, 更具体地说是共享 pimpl 惯用法. 每个属性提供一个派生自 attribute 类的接口类, 以及一个派生自 impl 的实现类. 接口类只持有指向属性实际实现的引用计数指针; 该指针是 attribute 类的成员, 因此派生的接口类没有任何数据成员. 接口类默认构造时, 会创建相应的实现对象, 并用指向实现的指针初始化 attribute 基类. 因此, 在典型工作流中, 属性的 pimpl 特性对用户是透明的.

不过, 共享 pimpl 设计在少数情况下很重要. 一种情况是复制属性. 复制操作是浅层的, 因此多个接口对象可能引用同一个实现对象. 无法对属性进行深拷贝. 另一种情况是 attribute 的默认构造, 它创建一个不引用任何实现的空对象. 处于这种空状态的属性不应传递给库, 但在某些情况下可能有用, 例如需要延迟变量初始化时.

可以将属性接口从 attribute 向上转换为实际的接口类. 为此需要应用 attribute_cast:

logging::attribute attr = ...;
attrs::constant< int > const_attr = logging::attribute_cast< attrs::constant< int > >(attr);

在此示例中, 转换将成功 (即 const_attr 将为非空) 的条件是: 属性 attr 最初创建为 attrs::constant< int >. 由于所有数据都存储在实现对象中, 转换过程中不会丢失任何数据.

如前所述, 属性的主要目的是生成属性值. 值在语义上与属性不同. 这种分离使得可以实现可在不同时间返回不同值的属性, 另一方面也允许独立地使用同一属性的不同值. attribute 接口有一个名为 get_value 的方法, 返回实际的属性值. 属性值也使用共享 pimpl 方式实现, 接口类是 attribute_value, 实现类派生自 impl.

属性值对象用于存储实际的属性值, 并实现类型分派, 以便能够提取存储的值. 不应混淆属性值实现类型与存储值类型. 前者在大多数情况下对用户并不重要, 它提供类型擦除; 而后者是提取值所必需的. 在上面的示例中, constant< int > 类型是属性类型, 其 get_value() 方法产生一个 attribute_value 类型的对象, 它是 attribute_value_impl< int > 实现类型的 pimpl 包装器. 这里实际存储的属性值类型是 int, 它是属性生成的内容, 也是用户从 attribute_value 中提取值所需要的. 为简洁起见, 本文档将存储的属性值类型简称为属性值类型.

常量 

#include <boost/log/attributes/constant.hpp>

最简单也最常用的属性类型是某个类型的常量值. 这类属性用 constant 类模板实现. 该模板以属性值类型为参数. 常量值应传递给属性构造函数. 下面是一个示例:

void foo()
{
    src::logger lg;

    // Register a constant attribute that always yields value -5
    lg.add_attribute("MyInteger", attrs::constant< int >(-5));

    // Register another constant attribute. Make it a string this time.
    lg.add_attribute("MyString", attrs::constant< std::string >("Hello world!"));

    // There is also a convenience generator function. "MyInteger2" is constant< int > here.
    lg.add_attribute("MyInteger2", attrs::make_constant(10));
}

就是这样, 常量属性没有太多可操作之处. 当想要突出显示某些日志记录, 或只是想向接收器后端传递一些数据 (例如向收集器传递统计参数) 时, 常量非常有用.

可变常量 

#include <boost/log/attributes/mutable_constant.hpp>

这类属性是 常量属性 的扩展. 除了能够存储某个值之外, mutable_constant 类模板还有两个特点:

  • 它允许在不重新注册属性的情况下修改存储的值
  • 它允许对存储值的写入和读取进行同步

要更改属性存储的值, 必须调用 set 方法:

void foo()
{
    src::logger lg;

    // Register a mutable constant attribute that always yields value -5
    attrs::mutable_constant< int > attr(-5);
    lg.add_attribute("MyInteger", attr);
    BOOST_LOG(lg) << "This record has MyInteger == -5";

    // Change the attribute value
    attr.set(100);
    BOOST_LOG(lg) << "This record has MyInteger == 100";
}

在多线程应用程序中, set 方法调用必须与 get_value 调用串行化 (一般来说, 后者在每条日志记录创建时都会发生). 默认情况下, mutable_constant 不以任何方式串行化调用, 假定用户会在外部进行串行化. 不过, mutable_constant 模板提供了三个额外的模板参数: 同步原语类型、作用域排他锁类型和作用域共享锁类型. 如果指定了同步原语类型, 则作用域排他锁类型是必选参数. 如果未指定作用域共享锁类型, 属性将退回使用排他锁而不是共享锁. 例如:

// This mutable constant will always lock exclusively
// either for reading or storing the value
typedef attrs::mutable_constant<
    int,                                        // attribute value type
    boost::mutex,                               // synchronization primitive
    boost::lock_guard< boost::mutex >           // exclusive lock type
> exclusive_mc;
exclusive_mc my_int1(10);

// This mutable constant will use shared clocking for reading the value
// and exclusive locking for storing
typedef attrs::mutable_constant<
    int,                                        // attribute value type
    boost::shared_mutex,                        // synchronization primitive
    boost::unique_lock< boost::shared_mutex >,  // exclusive lock type
    boost::shared_lock< boost::shared_mutex >   // shared lock type
> shared_mc;
shared_mc my_int2(20);

BOOST_LOG_INLINE_GLOBAL_LOGGER_INIT(my_logger, src::logger_mt)
{
    src::logger_mt lg;
    lg.add_attribute("MyInteger1", my_int1);
    lg.add_attribute("MyInteger2", my_int2);

    return lg;
}

void foo()
{
    src::logger_mt& lg = get_my_logger();

    // This is safe, even if executed in multiple threads
    my_int1.set(200);
    BOOST_LOG(lg) << "This record has MyInteger1 == 200";

    my_int2.set(300);
    BOOST_LOG(lg) << "This record has MyInteger2 == 300";
}

可变常量常用作日志器内部的辅助属性, 用于存储可能随某些事件而变化的属性. 与普通常量不同 (值修改时需要重新注册), 可变常量允许就地修改值.

计数器 

#include <boost/log/attributes/counter.hpp>

计数器是最简单的属性之一, 每次被请求时都会生成新值. 计数器常用于标识日志记录或统计某些事件, 例如已接受的网络连接. 类模板 counter 提供了这种功能. 该模板以计数器值类型为参数, 该类型应支持算术运算, 例如 operator + 和 operator -. 计数器属性允许在构造时指定初始值和步长 (可以为负).

BOOST_LOG_INLINE_GLOBAL_LOGGER_INIT(my_logger, src::logger_mt)
{
    src::logger_mt lg;

    // This counter will count lines, starting from 0
    lg.add_attribute("LineCounter", attrs::counter< unsigned int >());

    // This counter will count backwards, starting from 100 with step -5
    lg.add_attribute("CountDown", attrs::counter< int >(100, -5));

    return lg;
}

void foo()
{
    src::logger_mt& lg = get_my_logger();
    BOOST_LOG(lg) << "This record has LineCounter == 0, CountDown == 100";
    BOOST_LOG(lg) << "This record has LineCounter == 1, CountDown == 95";
    BOOST_LOG(lg) << "This record has LineCounter == 2, CountDown == 90";
}
注释

不要期望带有 counter 属性的日志记录在最终日志中总是具有升序或降序的计数值. 在多线程应用程序中, 不同线程获取的计数值可能以任意顺序到达接收器. 为什么会出现这种情况, 详见 设计理由. 因此, 更准确的说法是 counter 属性按升序或降序生成标识符, 而不是按任一顺序统计日志记录.

挂钟时钟 

#include <boost/log/attributes/clock.hpp>

任何日志库的 "必备" 特性之一, 是支持为每条日志记录附加时间戳. 库为此提供了两个属性: utc_clock 和 local_clock. 前者返回当前 UTC 时间, 后者返回当前本地时间. 无论哪种情况, 返回的时间戳都以目标平台可达到的最高精度获取. 属性值是 boost::posix_time::ptime (参见 Boost.DateTime). 用法非常直接:

BOOST_LOG_DECLARE_GLOBAL_LOGGER(my_logger, src::logger_mt)

void foo()
{
    logging::core::get()->add_global_attribute(
        "TimeStamp",
        attrs::local_clock());

    // Now every log record ever made will have a time stamp attached
    src::logger_mt& lg = get_my_logger();
    BOOST_LOG(lg) << "This record has a time stamp";
}
注释

与其他属性一样, 挂钟时钟属性的值是在日志记录创建时获取的, 而不是在接收器处理它时. 这意味着: (a) 附加到日志记录的时间戳总是反映事件发生的时间点, 而不是存储日志记录的时间; (b) 如果同一日志记录被多个接收器处理, 即使在不同时间点, 这些接收器处理的 (例如存储到各自文件中的) 也是同一时间戳. 这是挂钟时钟属性的一个有用特性, 尽管它可能导致输出中 日志记录的弱序.

计时器 (stop watch) 

#include <boost/log/attributes/timer.hpp>

当需要估算某个较长过程的持续时间时, timer 属性非常有用. 该属性返回自属性构造以来经过的时间. 属性值类型是 boost::posix_time::ptime::time_duration_type (参见 Boost.DateTime).

// The class represents a single peer-to-peer connection
class network_connection
{
    src::logger m_logger;

public:
    network_connection()
    {
        m_logger.add_attribute("Duration", attrs::timer());
        BOOST_LOG(m_logger) << "Connection established";
    }
    ~network_connection()
    {
        // This log record will show the whole life time duration of the connection
        BOOST_LOG(m_logger) << "Connection closed";
    }
};

该属性提供高精度的时间估算, 甚至可以用作简单的就地性能分析工具.

提示

timer 属性甚至可以在不重新编译不同模块的情况下分析其中的代码. 技巧是用线程专属的 timer 作用域属性 包装对外部模块的高开销调用, 它会用时间读数标记从该模块内部产生的所有日志记录.

命名作用域 

#include <boost/log/attributes/named_scope.hpp>

// Supporting headers
#include <boost/log/support/exception.hpp>

日志库支持在应用程序执行期间维护作用域栈跟踪. 该栈可以写入日志, 也可以用于其他需求 (例如, 在抛出异常时保存导致该异常的确切调用序列). 每个栈元素包含以下信息 (参见 named_scope_entry 结构模板的定义):

  • 作用域名称. 它可以由用户定义或由编译器生成, 但无论如何 必须是常量字符串字面量 (参见 设计理由).
  • 作用域开始处的源文件名. 它通常是标准 __FILE__ 宏展开的结果. 与作用域名称一样, 文件名 必须是常量字符串字面量.
  • 源文件中的行号. 通常它是标准 __LINE__ 宏展开的结果.

作用域栈内部实现为线程专属的全局存储. 有一个 named_scope 属性允许将该栈挂接到日志管道中. 该属性生成嵌套类型 named_scope::scope_stack 的值, 即作用域栈的实例. 该属性可以按以下方式注册:

logging::core::get()->add_global_attribute("Scope", attrs::named_scope());

请注意, 全局注册该属性是完全有效的, 因为作用域栈本来就是线程局部的. 这还会隐式地为应用程序的所有线程添加作用域跟踪, 而这通常正是所需要的.

现在我们可以用宏 BOOST_LOG_FUNCTION 和 BOOST_LOG_NAMED_SCOPE (后者接受作用域名称作为其参数) 标记执行作用域. 这些宏会自动向每个作用域条目添加源位置信息. 示例如下:

void foo(int n)
{
    // Mark the scope of the function foo
    BOOST_LOG_FUNCTION();

    switch (n)
    {
    case 0:
        {
            // Mark the current scope
            BOOST_LOG_NAMED_SCOPE("case 0");
            BOOST_LOG(lg) << "Some log record";
            bar(); // call some function
        }
        break;

    case 1:
        {
            // Mark the current scope
            BOOST_LOG_NAMED_SCOPE("case 1");
            BOOST_LOG(lg) << "Some log record";
            bar(); // call some function
        }
        break;

    default:
        {
            // Mark the current scope
            BOOST_LOG_NAMED_SCOPE("default");
            BOOST_LOG(lg) << "Some log record";
            bar(); // call some function
        }
        break;
    }
}

执行 foo 之后, 我们将能够在日志中看到 bar 函数是从 foo 调用的, 更准确地说, 是从与 n 的值对应的 case 语句调用的. 这在排查只在从特定位置调用 bar 时才出现的微妙缺陷时可能非常有用 (例如, 在该特定位置 bar 被传入了无效参数).

注释

BOOST_LOG_FUNCTION 宏使用编译器特定的扩展从外围函数生成作用域名称. C++11 为此定义了标准宏 __func__, 但它并未得到普遍支持. 此外, 该字符串的格式没有标准化, 可能因编译器而异. 因此, 通常建议使用 BOOST_LOG_NAMED_SCOPE 而不是 BOOST_LOG_FUNCTION, 以确保一致且可移植的行为.

警告

BOOST_LOG_FUNCTION 和 BOOST_LOG_NAMED_SCOPE 宏实际上在栈上形成一个作用域描述符链表, 随着控制以 LIFO (后进先出) 顺序进入和离开作用域, 该链表会被自动维护. 属性实现依赖于这种 LIFO 顺序. 当执行在任意点切换到另一个栈再切回来时, 这种顺序会被打破, 此时控制可以按任意顺序进入和离开作用域. 线程上下文切换时就会发生这种情况, 例如使用协程或 ucontext、fibers 等底层系统 API 时. 在使用这类上下文切换设施的代码中使用命名作用域, 需要谨慎编程, 以维护用命名作用域宏标记的作用域进入/离开的 LIFO 顺序. 否则, 使用命名作用域将导致未定义行为, 应予避免. 注意, 在任意上下文切换的情况下, 作用域列表无论如何也不会提供有意义的信息.

另一个好的用例是将作用域栈信息附加到异常上. 借助 Boost.Exception, 这是可行的:

void bar(int x)
{
    BOOST_LOG_FUNCTION();

    if (x < 0)
    {
        // Attach a copy of the current scope stack to the exception
        throw boost::enable_error_info(std::range_error("x must not be negative"))
            << logging::current_scope();
    }
}

void foo()
{
    BOOST_LOG_FUNCTION();

    try
    {
        bar(-1);
    }
    catch (std::range_error& e)
    {
        // Acquire the scope stack from the exception object
        BOOST_LOG(lg) << "bar call failed: " << e.what() << ", scopes stack:\n"
            << *boost::get_error_info< logging::current_scope_info >(e);
    }
}
注释

为了使这段代码能够编译, 必须包含 Boost.Exception 支持头文件.

注释

我们不会将 named_scope 属性注入异常. 由于作用域栈是全局维护的, 抛出异常会导致栈展开, 从而截断全局栈. 相反, 我们在抛出点通过调用 current_scope 创建作用域栈的副本. 即使全局栈实例在栈展开期间发生变化, 该副本也将保持不变.

当前进程标识符 

#include <boost/log/attributes/current_process_id.hpp>

了解产生日志的进程标识符通常很有用, 特别是当日志最终可能合并不同进程的输出时. current_process_id 属性是一个常量, 会格式化为当前进程标识符. 属性的值类型可通过 current_process_id::value_type typedef 确定.

void foo()
{
    logging::core::get()->add_global_attribute(
        "ProcessID",
        attrs::current_process_id());
}

当前进程名称 

#include <boost/log/attributes/current_process_name.hpp>

current_process_name 产生 std::string 值, 其中包含当前进程的可执行文件名.

注释

该属性并非在所有平台都可移植, 但支持 Windows、Linux 和 OS X. 该属性在其他 POSIX 系统上可能也能工作, 但未经测试. 如果无法获取进程名称, 该属性将生成一个包含进程 id 的字符串.

void foo()
{
    logging::core::get()->add_global_attribute(
        "Process",
        attrs::current_process_name());
}

当前线程标识符 

#include <boost/log/attributes/current_thread_id.hpp>

库的多线程构建还支持 current_thread_id 属性, 其值类型为 current_thread_id::value_type. 该属性将生成特定于调用线程的值. 用法与进程 id 类似.

void foo()
{
    logging::core::get()->add_global_attribute(
        "ThreadID",
        attrs::current_thread_id());
}
提示

您可能已经注意到, 该属性是全局注册的. 这不会导致所有线程在日志记录中具有相同的 ThreadID, 因为该属性总是返回线程专属的值. 额外的好处是, 您无需在线程初始化例程中做任何事, 就能让日志记录中包含线程专属的属性值.

函数对象作为属性 

#include <boost/log/attributes/function.hpp>

该属性是用户自定义函数对象的简单包装. 每次尝试获取属性值都会导致函数对象被调用. 调用的结果作为属性值返回 (这意味着该函数不得返回 void). 函数对象属性可以用 make_function 辅助函数构造, 如下所示:

void foo()
{
    logging::core::get()->add_global_attribute("MyRandomAttr", attrs::make_function(&std::rand));
}

自动生成的函数对象 (例如 Boost.Bind 或 C++ 标准库中定义的函数对象) 也受支持.

注释

某些有缺陷的编译器可能无法正确支持 result_of 构造. 该元函数在 make_function 函数中用于自动检测函数对象的返回类型. 如果 result_of 出错或检测到错误的类型, 可以尝试将函数对象的返回类型显式指定为 make_function 函数的模板实参.

属性名称 
#include <boost/log/attributes/attribute_name.hpp>

属性名称用 attribute_name 对象表示, 这些对象用作库所使用的属性关联容器中的键. attribute_name 对象可以从字符串创建, 因此大多数时候其使用是透明的.

名称并不以字符串形式存储在 attribute_name 对象中. 相反, 会生成一个进程内唯一的标识符并与特定名称关联. 该关联会一直保留到进程终止, 因此每次为同一名称创建 attribute_name 对象时, 它都会获得相同的标识符. 不过, 该关联在应用程序的不同次运行之间并不稳定.

警告

由于字符串名称与标识符之间的关联涉及一些状态分配, 不建议使用外部提供或已知会变化的字符串作为属性名称. 即使该名称未在任何日志记录中使用, 关联仍会被保留. 持续构造带有唯一字符串名称的 attribute_name 对象可能表现为内存泄漏.

使用标识符比使用字符串高效得多. 例如, 复制不涉及动态内存分配, 比较运算符也非常轻量. 另一方面, 如果需要, 很容易获得人类可读的属性名称用于展示.

attribute_name 类支持默认构造时的空 (未初始化) 状态. 在这种状态下, 名称对象不等于任何其他已初始化的名称对象. 未初始化的属性名称不应传递给库, 但在某些上下文中可能有用 (例如需要延迟初始化时).

属性集 
#include <boost/log/attributes/attribute_set.hpp>

属性集是一个无序关联容器, 将 属性名称 映射到 属性. 它用于 日志器 和 日志核心 中, 存储日志源专属、线程专属和全局属性. 其接口与标准库关联容器非常相似, 在 attribute_set 类参考中有描述.

属性值集 
#include <boost/log/attributes/attribute_value_set.hpp>

属性值集是一个无序关联容器, 将 属性名称 映射到 属性值. 该容器用于日志 记录 中表示属性值. 与常规容器不同, attribute_value_set 不支持在插入后移除或修改元素. 这保证了参与过滤的属性值不会在处理过程中从日志记录中消失.

此外, 该集合可以由三个 属性集 构造, 它们分别被解释为日志源专属、线程专属和全局属性的集合. 构造函数将三个属性集中的属性值收纳为一个单一的属性值集. 构造之后, attribute_value_set 被视为处于未冻结状态. 这意味着容器可能保留对用作值集构造来源的属性集元素的引用. 在此状态下, 属性集和值集都不得以任何方式修改, 否则可能损坏值集. 此状态下值集可用于读取, 其查找操作将照常执行. 可以通过调用 freeze 方法冻结值集; 此调用之后, 该集合将不再依附于原始属性集, 并可用于进一步的插入. 库会确保从日志核心返回日志记录时值集总是已冻结; 但在过滤期间该集合 并未 冻结.

提示

在未冻结状态下, 值集可能尚未从属性获取所有属性值. 它只会按过滤器的请求获取值. 冻结之后, 容器拥有全部属性值. 这种转换使库得以优化, 只在需要时才获取属性值.

有关容器接口的更多细节, 请查阅 attribute_value_set 参考.

属性值提取与访问

由于属性值不在接口中暴露存储的值, 需要一个 API 来获取存储的值. 库为此提供了两个 API: 值访问 (visitation) 和提取 (extraction).

值访问 
#include <boost/log/attributes/value_visitation_fwd.hpp>
#include <boost/log/attributes/value_visitation.hpp>

属性值访问实现了访问者设计模式, 因此得名. 用户必须提供一个一元函数对象 (访问器), 它将在存储的属性值上被调用. 调用方还必须提供存储值的预期类型或可能的类型集合. 显然, 访问器必须能够接受预期类型的实参. 只有存储类型与预期匹配时, 访问才会成功.

要应用访问器, 应对属性值调用 visit 函数. 我们来看一个示例:

// Our attribute value visitor
struct print_visitor
{
    typedef void result_type;

    result_type operator() (int val) const
    {
        std::cout << "Visited value is int: " << val << std::endl;
    }

    result_type operator() (std::string const& val) const
    {
        std::cout << "Visited value is string: " << val << std::endl;
    }
};

void print_value(logging::attribute_value const& attr)
{
    // Define the set of expected types of the stored value
    typedef boost::mpl::vector< int, std::string > types;

    // Apply our visitor
    logging::visitation_result result = logging::visit< types >(attr, print_visitor());

    // Check the result
    if (result)
        std::cout << "Visitation succeeded" << std::endl;
    else
        std::cout << "Visitation failed" << std::endl;
}

查看完整代码.

在此示例中, 我们在 print_visitor 中打印存储的属性值. 我们期望属性值的存储类型为 int 或 std::string; 只有在这种情况下访问器才会被调用, 且访问结果为肯定. 失败时, visitation_result 类提供关于失败原因的额外信息. 该类有一个名为 code 的方法, 返回访问错误码. 可能的错误码如下:

  • ok - 访问成功, 访问器已被调用; 使用此错误码时访问结果为肯定
  • value_not_found - 访问失败, 因为未找到请求的值; 当访问应用于日志记录或属性值集而非单个值时使用此错误码
  • value_has_invalid_type - 访问失败, 因为值的类型与任何预期类型都不同

默认情况下, 访问器函数的结果会被忽略, 但也可以获取它. 为此, 应为访问器使用特殊的 save_result 包装器; 该包装器会将访问器的结果值保存到按引用捕获的外部变量中. 当返回的 visitation_result 为肯定时, 访问器结果会被初始化. 参见下面的示例, 我们对存储的值计算哈希值.

struct hash_visitor
{
    typedef std::size_t result_type;

    result_type operator() (int val) const
    {
        std::size_t h = val;
        h = (h << 15) + h;
        h ^= (h >> 6) + (h << 7);
        return h;
    }

    result_type operator() (std::string const& val) const
    {
        std::size_t h = 0;
        for (std::string::const_iterator it = val.begin(), end = val.end(); it != end; ++it)
            h += *it;

        h = (h << 15) + h;
        h ^= (h >> 6) + (h << 7);
        return h;
    }
};

void hash_value(logging::attribute_value const& attr)
{
    // Define the set of expected types of the stored value
    typedef boost::mpl::vector< int, std::string > types;

    // Apply our visitor
    std::size_t h = 0;
    logging::visitation_result result = logging::visit< types >(attr, logging::save_result(hash_visitor(), h));

    // Check the result
    if (result)
        std::cout << "Visitation succeeded, hash value: " << h << std::endl;
    else
        std::cout << "Visitation failed" << std::endl;
}

查看完整代码.

提示

当访问器结果没有默认状态时, 使用 Boost.Optional 包装返回值会很方便. 如果访问成功, optional 将用访问器结果初始化. 如果访问器是多态的 (即根据其参数类型有不同的结果类型), 可以使用 Boost.Variant 接收结果值. 使用空类型 (例如 boost::blank) 来指示 variant 的未初始化状态也是值得的.

如前所述, 访问也可以应用于日志记录和属性值集. 语法相同, 只是还必须指定属性名称. visit 算法将尝试按名称查找属性值, 然后将访问器应用于找到的元素.

void hash_value(logging::record_view const& rec, logging::attribute_name name)
{
    // Define the set of expected types of the stored value
    typedef boost::mpl::vector< int, std::string > types;

    // Apply our visitor
    std::size_t h = 0;
    logging::visitation_result result = logging::visit< types >(name, rec, logging::save_result(hash_visitor(), h));

    // Check the result
    if (result)
        std::cout << "Visitation succeeded, hash value: " << h << std::endl;
    else
        std::cout << "Visitation failed" << std::endl;
}

此外, 为方便起见, attribute_value 有一个名为 visit 的方法, 其含义与应用于属性值的自由函数相同.

值提取 
#include <boost/log/attributes/value_extraction_fwd.hpp>
#include <boost/log/attributes/value_extraction.hpp>

属性值提取 API 允许获取对存储值的引用. 它不需要访问器函数对象, 但用户仍须提供存储值可能具有的预期类型或类型集合.

void print_value(logging::attribute_value const& attr)
{
    // Extract a reference to the stored value
    logging::value_ref< int > val = logging::extract< int >(attr);

    // Check the result
    if (val)
        std::cout << "Extraction succeeded: " << val.get() << std::endl;
    else
        std::cout << "Extraction failed" << std::endl;
}

查看完整代码.

在此示例中, 我们期望属性值的存储类型为 int. extract 函数尝试提取对存储值的引用, 成功时返回已填充的 value_ref 对象.

值提取也可以与一组预期存储类型一起使用. 下面的代码片段演示了这一点:

void print_value_multiple_types(logging::attribute_value const& attr)
{
    // Define the set of expected types of the stored value
    typedef boost::mpl::vector< int, std::string > types;

    // Extract a reference to the stored value
    logging::value_ref< types > val = logging::extract< types >(attr);

    // Check the result
    if (val)
    {
        std::cout << "Extraction succeeded" << std::endl;
        switch (val.which())
        {
        case 0:
            std::cout << "int: " << val.get< int >() << std::endl;
            break;

        case 1:
            std::cout << "string: " << val.get< std::string >() << std::endl;
            break;
        }
    }
    else
        std::cout << "Extraction failed" << std::endl;
}

注意, 我们使用了返回引用的 which 方法在可能的类型之间分派. 该方法返回该类型在 types 序列中的索引. 另请注意, get 方法现在接受显式模板参数来选择要获取的引用类型; 自然, 该类型必须与实际被引用的类型一致, 在我们的示例中这由 switch/case 语句保证.

value_ref 对象也支持值访问. 下面是我们从提取的值计算哈希值的方法:

struct hash_visitor
{
    typedef std::size_t result_type;

    result_type operator() (int val) const
    {
        std::size_t h = val;
        h = (h << 15) + h;
        h ^= (h >> 6) + (h << 7);
        return h;
    }

    result_type operator() (std::string const& val) const
    {
        std::size_t h = 0;
        for (std::string::const_iterator it = val.begin(), end = val.end(); it != end; ++it)
            h += *it;

        h = (h << 15) + h;
        h ^= (h >> 6) + (h << 7);
        return h;
    }
};

void hash_value(logging::attribute_value const& attr)
{
    // Define the set of expected types of the stored value
    typedef boost::mpl::vector< int, std::string > types;

    // Extract the stored value
    logging::value_ref< types > val = logging::extract< types >(attr);

    // Check the result
    if (val)
        std::cout << "Extraction succeeded, hash value: " << val.apply_visitor(hash_visitor()) << std::endl;
    else
        std::cout << "Extraction failed" << std::endl;
}

最后, 与值访问一样, 值提取也可以应用于日志记录和属性值集.

void hash_value(logging::record_view const& rec, logging::attribute_name name)
{
    // Define the set of expected types of the stored value
    typedef boost::mpl::vector< int, std::string > types;

    // Extract the stored value
    logging::value_ref< types > val = logging::extract< types >(name, rec);

    // Check the result
    if (val)
        std::cout << "Extraction succeeded, hash value: " << val.apply_visitor(hash_visitor()) << std::endl;
    else
        std::cout << "Extraction failed" << std::endl;
}

此外, 库提供了 extract 函数的两个特殊变体: extract_or_throw 和 extract_or_default. 顾名思义, 当无法提取属性值时, 这些函数提供不同的行为. 前者在无法提取值时抛出异常, 后者返回默认值.

警告

使用 extract_or_default 函数时必须小心. 该函数以常量引用接受默认值, 而该引用最终可能从 extract_or_default 返回. 如果使用临时对象作为默认值, 用户必须确保 extract_or_default 的结果按值保存而不是按引用保存. 否则, 临时对象销毁时保存的引用可能变成悬空引用.

与 visit 类似, attribute_value 类有名为 extract、extract_or_throw 和 extract_or_default 的方法, 其含义与应用于属性值的对应自由函数相同.

作用域属性 
#include <boost/log/attributes/scoped_attribute.hpp>

作用域属性是一种强大的日志记录标记机制, 可用于不同目的. 顾名思义, 作用域属性在作用域开始时注册, 在作用域结束时注销. 该机制包括以下宏:

BOOST_LOG_SCOPED_LOGGER_ATTR(logger, attr_name, attr);
BOOST_LOG_SCOPED_THREAD_ATTR(attr_name, attr);

第一个宏在 logger 日志器对象中注册一个日志源专属属性. 属性名称和属性本身分别在 attr_name 和 attr 参数中给出. 第二个宏做的完全相同, 但属性是在日志核心中为当前线程注册的 (这不需要日志器).

注释

如果日志器/日志核心中已经注册了同名属性, 这些宏不会覆盖现有属性, 最终将不起作用. 有关这种行为原因的更详细解释, 参见 设计理由.

使用示例如下:

BOOST_LOG_DECLARE_GLOBAL_LOGGER(my_logger, src::logger_mt)

void foo()
{
    // This log record will also be marked with the "Tag" attribute,
    // whenever it is called from the A::bar function.
    // It will not be marked when called from other places.
    BOOST_LOG(get_my_logger()) << "A log message from foo";
}

struct A
{
    src::logger m_Logger;

    void bar()
    {
        // Set a thread-wide markup tag.
        // Note the additional parentheses to form a Boost.PP sequence.
        BOOST_LOG_SCOPED_THREAD_ATTR("Tag",
            attrs::constant< std::string >("Called from A::bar"));

        // This log record will be marked
        BOOST_LOG(m_Logger) << "A log message from A::bar";

        foo();
    }
};

int main(int, char*[])
{
    src::logger lg;

    // Let's measure our application run time
    BOOST_LOG_SCOPED_LOGGER_ATTR(lg, "RunTime", attrs::timer());

    // Mark application start.
    // The "RunTime" attribute should be nearly 0 at this point.
    BOOST_LOG(lg) << "Application started";

    // Note that no other log records are affected by the "RunTime" attribute.
    foo();

    A a;
    a.bar();

    // Mark application ending.
    // The "RunTime" attribute will show the execution time elapsed.
    BOOST_LOG(lg) << "Application ended";

    return 0;
}

用常量值标记一组日志记录常常很方便, 以便之后能够过滤这些记录. 库专门为此提供了两个便捷宏:

BOOST_LOG_SCOPED_LOGGER_TAG(logger, tag_name, tag_value);
BOOST_LOG_SCOPED_THREAD_TAG(tag_name, tag_value);

这些宏实际上分别是 BOOST_LOG_SCOPED_LOGGER_ATTR 和 BOOST_LOG_SCOPED_THREAD_ATTR 的包装. 例如, 上例中的 "Tag" 作用域属性可以这样注册:

BOOST_LOG_SCOPED_THREAD_TAG("Tag", "Called from A::bar");
警告

使用作用域属性时, 请确保作用域属性在其注册的属性集中不被改动. 例如, 如果日志器中注册了日志器专属的作用域属性, 就不应清空或重新安装日志器的属性集. 否则程序很可能崩溃. 在多线程应用程序中, 这个问题尤其严重, 因为一个线程可能不知道日志器中是否有作用域属性. 未来的版本可能会解决这一限制, 但目前作用域属性必须保持完好, 直到离开作用域时被注销.

虽然上述宏旨在作为该功能的主要接口, 但也有可用的 C++ 接口. 如果用户决定开发无法基于现有宏的自定义宏, 这可能有用.

任何作用域属性都附加到一个 scoped_attribute 类型的通用哨兵对象上. 只要哨兵存在, 属性就处于注册状态. 有几个函数可以为日志源专属或线程专属属性创建哨兵:

// Source-specific scoped attribute registration
template< typename LoggerT >
[unspecified] add_scoped_logger_attribute(
    LoggerT& l,
    attribute_name const& name,
    attribute const& attr);

// Thread-specific scoped attribute registration
template< typename CharT >
[unspecified] add_scoped_thread_attribute(
    attribute_name const& name,
    attribute const& attr);

scoped_attribute 类型的对象在构造时能够附加这些函数中每一个的结果. 例如, BOOST_LOG_SCOPED_LOGGER_ATTR(lg, "RunTime", attrs::timer()) 大致可以展开为:

attrs::scoped_attribute sentry =
    attrs::add_scoped_logger_attribute(lg, "RunTime", attrs::timer());
