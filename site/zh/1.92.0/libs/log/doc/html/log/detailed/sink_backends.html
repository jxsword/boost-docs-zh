文本流后端 

#include <boost/log/sinks/text_ostream_backend.hpp>

文本输出流接收器后端是库开箱即用提供的最通用的后端. 该后端以 basic_text_ostream_backend 类模板实现 (为窄字符和宽字符支持提供了 text_ostream_backend 和 wtext_ostream_backend 便捷 typedef). 它支持将日志记录格式化为字符串并写入一个或多个流. 每个附着的流都会得到相同的格式化结果, 因此如果需要为不同的流以不同方式格式化日志记录, 就需要创建多个接收器 —— 每个接收器有自己的格式化器.

该后端还提供一个在调试应用程序时可能有用的功能. 通过 auto_flush 方法, 可以让接收器在每条日志记录写入后自动刷新所有附着流的缓冲区. 这当然会降低日志性能, 但在应用程序崩溃时, 最后的日志记录很有可能不会丢失.

void init_logging()
{
    boost::shared_ptr< logging::core > core = logging::core::get();

    // Create a backend and attach a couple of streams to it
    boost::shared_ptr< sinks::text_ostream_backend > backend =
        boost::make_shared< sinks::text_ostream_backend >();
    backend->add_stream(
        boost::shared_ptr< std::ostream >(&std::clog, boost::null_deleter()));
    backend->add_stream(
        boost::shared_ptr< std::ostream >(new std::ofstream("sample.log")));

    // Enable auto-flushing after each log record written
    backend->auto_flush(true);

    // Wrap it into the frontend and register in the core.
    // The backend requires synchronization in the frontend.
    typedef sinks::synchronous_sink< sinks::text_ostream_backend > sink_t;
    boost::shared_ptr< sink_t > sink(new sink_t(backend));
    core->add_sink(sink);
}

#include <boost/log/sinks/text_file_backend.hpp>

尽管可以使用 文本流后端 将日志写入文件, 库还提供了一个特殊的接收器后端, 具有适合基于文件的日志的扩展功能集. 这些功能包括:

  • 基于文件大小和/或时间的日志文件轮转
  • 灵活的日志文件命名
  • 将轮转文件放入文件系统中的特定位置
  • 删除最旧的文件以在文件系统上腾出更多空间
  • 与 文本流后端 类似, 文件接收器后端也支持自动刷新功能

该后端名为 text_file_backend.

警告

该接收器内部使用 Boost.Filesystem, 在进程终止时可能引发问题. 更多细节参见 此处.

文件轮转

当接收器检测到一个或多个轮转条件满足且需要创建新文件时, 就会发生文件轮转. 它由接收器后端实现, 包括以下步骤:

  1. 如果日志文件当前处于打开状态, 调用 文件关闭处理器 并关闭文件.
  2. 如果设置了目标文件名模式, 则生成新的目标文件名, 并将日志文件重命名为该名称.
  3. 如果配置了 文件收集器, 则将日志文件交给它进行收集. 此时, 文件收集器可能会移除较旧的日志文件以腾出空间, 并将新文件移入目标存储.
  4. 当需要写入新的日志记录时, 为新文件生成新的文件名并以此名称创建文件. 如果启用了 文件追加 且同名文件已存在, 则以追加模式打开该文件而不是覆盖.

需要特别注意的是, 此过程涉及三类文件名或路径:

  • 用于创建或打开活动写入的日志文件的文件名. 这称为 活动 文件名, 通过接收器后端构造函数的 file_name 命名参数或调用 set_file_name_pattern 方法指定.
  • 在日志文件关闭并即将被收集时生成的文件名. 这称为 目标 文件名, 因为它定义了日志文件在目标存储中的命名方式. 目标文件名是可选的, 可通过 target_file_name 命名参数或调用 set_target_file_name_pattern 方法指定.
  • 目标存储位置, 即由 文件收集器 管理的、存放先前轮转日志文件的目录. 多个接收器可以共享同一目标存储.

文件名模式和轮转条件可以在构造 text_file_backend 后端时指定.

void init_logging()
{
    boost::shared_ptr< logging::core > core = logging::core::get();

    boost::shared_ptr< sinks::text_file_backend > backend =
        boost::make_shared< sinks::text_file_backend >(
            keywords::file_name = "file.log",                                              
            keywords::target_file_name = "file_%5N.log",                                   
            keywords::rotation_size = 5 * 1024 * 1024,                                     
            keywords::time_based_rotation = sinks::file::rotation_at_time_point(12, 0, 0)  
        );

    // Wrap it into the frontend and register in the core.
    // The backend requires synchronization in the frontend.
    typedef sinks::synchronous_sink< sinks::text_file_backend > sink_t;
    boost::shared_ptr< sink_t > sink(new sink_t(backend));

    core->add_sink(sink);
}

注释

轮转时的文件大小可能不精确. 实现统计的是写入文件的字节数, 但底层 API 可能引入额外的辅助数据, 从而增加日志文件在磁盘上的实际大小. 例如, 众所周知, Windows 和 DOS 操作系统对换行字符有特殊处理: 每个换行字符都写成两字节序列 0x0D 0x0A, 而不是单个 0x0A. 也存在其他平台特定的字符转换. 在压缩文件系统上, 磁盘上的实际大小也可能小于写入的字符数.

基于时间的轮转不限于时间点. 开箱即用提供了以下选项:

  1. 时间点轮转: rotation_at_time_point 类. 只要到达指定时间点就会进行这种轮转. 可用的变体如下:
    • 每天在指定时间轮转. 这就是上面代码片段中展示的方式: 
      sinks::file::rotation_at_time_point(12, 0, 0)
    • 每周指定日期在指定时间轮转. 例如, 这将使文件轮转在每周二午夜发生: 
      sinks::file::rotation_at_time_point(date_time::Tuesday, 0, 0, 0)
      对于午夜, 时间可以省略: 
      sinks::file::rotation_at_time_point(date_time::Tuesday)
    • 每月指定日期在指定时间轮转. 例如, 每月 1 日轮转文件的方式如下: 
      sinks::file::rotation_at_time_point(gregorian::greg_day(1), 0, 0, 0)
      与星期几一样, 默认为午夜: 
      sinks::file::rotation_at_time_point(gregorian::greg_day(1))
  2. 时间间隔轮转: rotation_at_time_interval 类. 使用该谓词时, 轮转不与任何时间点绑定, 而是在距上次轮转经过指定时间间隔后立即发生. 每小时轮转的写法如下: 
    sinks::file::rotation_at_time_interval(posix_time::hours(1))

如果以上都不适用, 可以为基于时间的轮转指定自己的谓词. 该谓词应不接收参数并返回 bool (true 值表示应进行轮转). 该谓词会在每条写入文件的日志记录时被调用.

bool is_it_time_to_rotate();

void init_logging()
{
    // ...

    boost::shared_ptr< sinks::text_file_backend > backend =
        boost::make_shared< sinks::text_file_backend >(
            keywords::file_name = "file.log",
            keywords::target_file_name = "file_%5N.log",
            keywords::time_based_rotation = &is_it_time_to_rotate
        );

    // ...
}
注释

日志文件轮转发生在尝试向文件写入新日志记录之时. 因此, 基于时间的轮转也不是严格的阈值. 只要库检测到应当轮转, 轮转就会发生.

除了基于时间和大小的文件轮转外, 后端默认还会在其销毁时执行轮转. 这样做是为了在程序终止后保持目标目录中收集的所有日志文件, 并确保临时日志文件不会堆积在接收器后端写入的目录中. 可以通过后端构造函数的 enable_final_rotation 参数或后端的同名方法禁用此行为:

void init_logging()
{
    // ...

    boost::shared_ptr< sinks::text_file_backend > backend =
        boost::make_shared< sinks::text_file_backend >(
            keywords::file_name = "file.log",
            keywords::target_file_name = "file_%5N.log",
            keywords::enable_final_rotation = false
        );

    // ...
}

活动文件名模式和目标文件名模式都可以包含若干通配符, 例如上例中所见. 支持的占位符如下:

  • 当前日期和时间组成部分. 占位符与 Boost.DateTime 库规定的占位符一致.
  • 文件计数器 (%N), 可按 printf 风格的格式可选地指定宽度. 文件计数器始终为十进制, 按指定宽度以零填充.
  • 百分号 (%%).

几个简单示例:

模板

展开为

file_%N.log

file_1.log, file_2.log...

file_%Y%m%d.log

file_2008-07-05_13-44-23.1.log, file_2008-07-06_16-00-10.2.log...

重要

虽然所有 Boost.DateTime 格式说明符都可用, 但如果您打算扫描旧日志文件, 其中一些会受到限制. 该功能在 此处 讨论.

注意, 如上所述, 活动文件名和目标文件名是在不同时间点生成的. 具体而言, 活动文件名在日志文件最初创建时生成, 而目标文件名在文件关闭时生成. 用于构造这些文件名的时间戳会反映这一差异.

提示

当需要 文件追加 时, 建议避免在活动文件名模式中使用任何占位符. 否则, 由于活动日志文件名不同, 追加不会发生. 可以使用目标文件名模式在轮转后为日志文件添加时间戳或计数器.

文件打开和关闭处理器

接收器后端允许挂接到文件轮转过程, 以执行轮转前和轮转后的操作. 这对于通过写入文件头和文件尾来维持日志文件的有效性很有用. 例如, 我们可以这样修改前面示例中的 init_logging 函数, 以便将日志写入 XML 文件:

// Complete file sink type
typedef sinks::synchronous_sink< sinks::text_file_backend > file_sink;

void write_header(sinks::text_file_backend::stream_type& file)
{
    file << "<?xml version=\"1.0\"?>\n<log>\n";
}

void write_footer(sinks::text_file_backend::stream_type& file)
{
    file << "</log>\n";
}

void init_logging()
{
    // Create a text file sink
    boost::shared_ptr< file_sink > sink(new file_sink(
        keywords::file_name = "%Y%m%d_%H%M%S_%5N.xml",  
        keywords::rotation_size = 16384                 
    ));

    sink->set_formatter
    (
        expr::format("\t<record id=\"%1%\" timestamp=\"%2%\">%3%</record>")
            % expr::attr< unsigned int >("RecordID")
            % expr::attr< boost::posix_time::ptime >("TimeStamp")
            % expr::xml_decor[ expr::stream << expr::smessage ]            
    );

    // Set header and footer writing functors
    sink->locked_backend()->set_open_handler(&write_header);
    sink->locked_backend()->set_close_handler(&write_footer);

    // Add the sink to the core
    logging::core::get()->add_sink(sink);
}

管理轮转文件

关闭后, 轮转的文件可以被收集. 为此, 必须设置文件收集器, 指定收集轮转文件的目标目录, 以及可选的大小阈值. 例如, 我们可以修改 init_logging 函数, 将轮转文件放入一个单独的目录并限制文件总大小. 假设 init_logging 以构造好的接收器调用以下函数:

void init_file_collecting(boost::shared_ptr< file_sink > sink)
{
    sink->locked_backend()->set_file_collector(sinks::file::make_collector(
        keywords::target = "logs",                      
        keywords::max_size = 16 * 1024 * 1024,          
        keywords::min_free_space = 100 * 1024 * 1024,   
        keywords::max_files = 512                       
    ));
}

max_size、min_free_space 和 max_files 参数是可选的, 如果未指定参数, 相应的阈值将不被考虑.

可以创建多个将文件收集到同一目标目录的文件接收器后端. 在这种情况下, 该目标目录会合并应用最严格的阈值. 从该目录删除文件时不考虑是哪个接收器后端写入的, 即按严格的时间顺序删除.

警告

收集器不解决不同接收器后端之间的日志文件名冲突, 因此一般而言, 如果发生冲突, 行为是未定义的. 视具体情况, 文件可能相互覆盖, 或操作完全失败.

扫描轮转文件

文件收集器还提供了另一个有用的功能. 假设您运行应用程序 5 次, 在 "logs" 目录中有 5 个日志文件. 文件接收器后端和文件收集器提供了 scan_for_files 方法, 在目标目录中搜索这些文件并将其纳入考虑. 这样, 在删除文件时, 这些文件不会被遗忘. 此外, 如果后端中的文件名模式包含文件计数器, 扫描旧文件可以将计数器更新为最新值. 下面是 init_logging 函数的最终版本:

void init_logging()
{
    // Create a text file sink
    boost::shared_ptr< file_sink > sink(new file_sink(
        keywords::file_name = "%Y%m%d_%H%M%S_%5N.xml",
        keywords::rotation_size = 16384
    ));

    // Set up where the rotated files will be stored
    init_file_collecting(sink);

    // Upon restart, scan the directory for files matching the file_name pattern
    sink->locked_backend()->scan_for_files();

    sink->set_formatter
    (
        expr::format("\t<record id=\"%1%\" timestamp=\"%2%\">%3%</record>")
            % expr::attr< unsigned int >("RecordID")
            % expr::attr< boost::posix_time::ptime >("TimeStamp")
            % expr::xml_decor[ expr::stream << expr::smessage ]
    );

    // Set header and footer writing functors
    namespace bll = boost::lambda;

    sink->locked_backend()->set_open_handler
    (
        bll::_1 << "<?xml version=\"1.0\"?>\n<log>\n"
    );
    sink->locked_backend()->set_close_handler
    (
        bll::_1 << "</log>\n"
    );

    // Add the sink to the core
    logging::core::get()->add_sink(sink);
}

文件扫描有两种方法: 一种是基于文件名与目标文件名模式匹配的扫描 (默认), 另一种是假定目标目录中的所有文件都是日志文件的扫描. 前者对文件名模式中可使用的占位符施加了某些限制: 特别是只支持文件计数器占位符和 Boost.DateTime 的这些占位符: %y、%Y、%m、%d、%H、%M、%S、%f. 而后一种扫描方法也有自身的缺点: 它不允许在后端中更新文件计数器. 它还被认为更加危险, 因为可能导致意外删除文件, 所以要谨慎. 全文件扫描方法可以通过将其作为附加参数传递给 scan_for_files 调用来启用:

// Look for all files in the target directory
backend->scan_for_files(sinks::file::scan_all);

扫描匹配文件名时, 如果未设置目标文件名, 则使用活动文件名模式代替.

追加写入先前已写的文件

接收器后端支持追加写入先前已写的文件 (例如应用程序上次运行留下的文件). 要启用此模式, 必须在后端使用的文件打开模式中添加 std::ios_base::app. 这可以通过后端构造函数的 open_mode 命名参数或 set_open_mode 方法完成.

void init_logging()
{
    // ...

    boost::shared_ptr< sinks::text_file_backend > backend =
        boost::make_shared< sinks::text_file_backend >(
            keywords::file_name = "file.log",
            keywords::target_file_name = "file_%5N.log",
            keywords::open_mode = std::ios_base::out | std::ios_base::app,
            keywords::enable_final_rotation = false
        );

    // ...
}

从 settings 初始化时, "TextFile" 接收器的 "Append" 参数用于启用追加.

要使文件追加真正发生, 新打开的日志文件的名称必须与先前写入的文件匹配, 这一点很重要. 否则, 接收器只会以新名称创建一个新文件. 希望进行文件追加时, 应遵循以下建议:

  • 不要在活动文件名模式中使用占位符. 这将确保接收器每次打开文件进行写入时, 该文件都具有相同的名称.
  • 使用有区分的目标文件名模式, 最好包含日期、时间或计数器占位符. 这将确保文件轮转并被收集时不会与先前写入的文件冲突, 且新打开的文件与上一个文件名称不同.
  • 禁用接收器销毁时的文件轮转. 这将使最后的活动写入日志文件保留在原位置并使用原名称, 以便应用程序下次运行时能够找到它.
  • 活动写入的日志文件最好使用稳定的位置和文件名. 如果文件名或目录在应用程序两次运行之间发生变化, 库将找不到先前写入的文件.

文本多文件后端 

#include <boost/log/sinks/text_multifile_backend.hpp>

文本流后端和文件后端旨在将所有日志记录存储到单个文件/流中, 而该后端的用途不同. 假设我们有一个银行请求处理应用程序, 希望将与每个请求相关的日志放入单独的文件. 如果我们可以将某个属性与请求标识关联, 那么 text_multifile_backend 后端就是合适的选择.

注释

多文件后端在运行期间会频繁打开和关闭日志文件, 这意味着这些操作在特定系统上的开销将显著影响日志性能. Windows (尤其是在运行杀毒软件时) 的文件打开和关闭操作开销极高. 例如, 与 Linux 相比, 关闭文件可能慢 数百 倍 (见 一些 报告). 如果您受到影响, 请考虑创建多个带有相应过滤器的 text_file_backend 接收器, 或将 text_multifile_backend 作为 异步 接收器运行.

void init_logging()
{
    boost::shared_ptr< logging::core > core = logging::core::get();

    boost::shared_ptr< sinks::text_multifile_backend > backend =
        boost::make_shared< sinks::text_multifile_backend >();

    // Set up the file naming pattern
    backend->set_file_name_composer
    (
        sinks::file::as_file_name_composer(expr::stream << "logs/" << expr::attr< std::string >("RequestID") << ".log")
    );

    // Wrap it into the frontend and register in the core.
    // The backend requires synchronization in the frontend.
    typedef sinks::synchronous_sink< sinks::text_multifile_backend > sink_t;
    boost::shared_ptr< sink_t > sink(new sink_t(backend));

    // Set the formatter
    sink->set_formatter
    (
        expr::stream
            << "[RequestID: " << expr::attr< std::string >("RequestID")
            << "] " << expr::smessage
    );

    core->add_sink(sink);
}

可以看到, 我们使用常规的 格式化器 来指定文件命名模式. 现在, 每条具有不同 "RequestID" 属性值的日志记录都将存储在单独的文件中, 无论应用程序并发处理多少个不同请求. 库发行版中还可以找到 multiple_files 示例, 它展示了类似的技术来分离应用程序不同线程产生的日志.

如果出于某种原因不适合使用格式化器, 您可以提供自己的文件名组合器. 组合器只是一个函数对象, 接受日志记录作为单个参数, 并返回 text_multifile_backend::path_type 类型的值.

注释

多文件后端无法得知某个特定文件是否还会被使用. 也就是说, 如果一条日志记录已写入文件 A, 库无法判断是否还会有更多记录写入文件 A. 这使得无法实现文件轮转和删除不再使用的文件以释放文件系统空间. 用户必须自行实现这类功能.

文本 IPC 消息队列后端 

#include <boost/log/sinks/text_ipc_message_queue_backend.hpp>

有时, 在本地机器上的不同进程之间传递日志记录会很方便. 例如, 可以将多个进程的日志收集到一个公共的日志进程; 或者创建一个能够监视运行进程的日志查看器. 要实现这一想法, 需要一个跨进程发送日志的接收器后端. 文本进程间接收器后端将格式化后的日志消息放入 进程间消息队列, 随后可由另一个进程取出并处理. 特别地, 可以选择将带有各种属性值的日志记录编码为 JSON 或 XML 格式的文本消息, 然后在接收端解码该消息进行处理, 例如过滤和显示.

该后端由 text_ipc_message_queue_backend 类模板实现, 应使用进程间消息队列 (例如 reliable_message_queue) 实例化. 下面的示例程序演示了一个日志进程.

BOOST_LOG_ATTRIBUTE_KEYWORD(a_timestamp, "TimeStamp", attrs::local_clock::value_type)
BOOST_LOG_ATTRIBUTE_KEYWORD(a_process_id, "ProcessID", attrs::current_process_id::value_type)
BOOST_LOG_ATTRIBUTE_KEYWORD(a_thread_id, "ThreadID", attrs::current_thread_id::value_type)

int main()
{
    try
    {
        typedef logging::ipc::reliable_message_queue queue_t;
        typedef sinks::text_ipc_message_queue_backend< queue_t > backend_t;
        typedef sinks::synchronous_sink< backend_t > sink_t;

        // Create a sink that is associated with the interprocess message queue
        // named "ipc_message_queue".
        boost::shared_ptr< sink_t > sink = boost::make_shared< sink_t >
        (
            keywords::name = logging::ipc::object_name(logging::ipc::object_name::user, "ipc_message_queue"),
            keywords::open_mode = logging::open_mode::open_or_create,
            keywords::capacity = 256,
            keywords::block_size = 1024,
            keywords::overflow_policy = queue_t::block_on_overflow
        );

        // Set the formatter
        sink->set_formatter
        (
            expr::stream << "[" << a_timestamp << "] [" << a_process_id << ":" << a_thread_id << "] " << expr::smessage
        );

        logging::core::get()->add_sink(sink);

        // Add the commonly used attributes, including TimeStamp, ProcessID and ThreadID
        logging::add_common_attributes();

        // Do some logging
        src::logger logger;
        for (unsigned int i = 1; i <= 10; ++i)
        {
            BOOST_LOG(logger) << "Message #" << i;
        }
    }
    catch (std::exception& e)
    {
        std::cout << "Failure: " << e.what() << std::endl;
    }

    return 0;
}

同一个进程间队列也可用于实现接收端. 以下代码将接收到的日志消息显示在控制台上.

int main()
{
    try
    {
        typedef logging::ipc::reliable_message_queue queue_t;

        // Create a message_queue_type object that is associated with the interprocess
        // message queue named "ipc_message_queue".
        queue_t queue
        (
            keywords::name = logging::ipc::object_name(logging::ipc::object_name::user, "ipc_message_queue"),
            keywords::open_mode = logging::open_mode::open_or_create,
            keywords::capacity = 256,
            keywords::block_size = 1024,
            keywords::overflow_policy = queue_t::block_on_overflow
        );

        std::cout << "Viewer process running..." << std::endl;

        // Keep reading log messages from the associated message queue and print them on the console.
        // queue.receive() will block if the queue is empty.
        std::string message;
        while (queue.receive(message) == queue_t::succeeded)
        {
            std::cout << message << std::endl;

            // Clear the buffer for the next message
            message.clear();
        }
    }
    catch (std::exception& e)
    {
        std::cout << "Failure: " << e.what() << std::endl;
    }

    return 0;
}

syslog 后端 

#include <boost/log/sinks/syslog_backend.hpp>

顾名思义, syslog 后端为几乎所有类 UNIX 平台上都可用的 syslog API 提供支持. 在 Windows 上至少存在 一个 公开的 syslog 客户端 API 实现. 不过, 为了提供最大限度的灵活性和更好的可移植性, 库内置支持 RFC 3164 中描述的 syslog 协议. 因此在 Windows 上仅支持内置实现, 而在类 UNIX 系统上同时支持内置实现和基于系统 API 的实现.

该后端以 syslog_backend 类实现. 该后端支持日志记录格式化, 因此前端需要线程同步. 该后端还支持将严重级别从应用程序特定的值转换为 syslog 定义的值. 这是通过一个额外的函数对象 (级别映射器) 实现的, 它接收每条日志记录的属性值集, 并返回相应的 syslog 级别值. 该值被后端用于构造 syslog 记录的最终优先级值. syslog 优先级值的另一组成部分 (facility) 对每个后端对象是常量, 可以在后端构造函数参数中指定.

级别映射器可由库用户编写, 以最佳方式将应用程序日志级别转换为 syslog 级别. 不过, 库提供了两个映射器, 在显而易见的情况下可以满足此需求. direct_severity_mapping 类模板提供了一种将某个整型属性值直接映射到 syslog 级别的方式, 无需任何值转换. custom_severity_mapping 类模板增加了一些灵活性, 允许将某个属性的任意值映射到 syslog 级别.

无论如何, 一个例子胜过千言万语.

// Complete sink type
typedef sinks::synchronous_sink< sinks::syslog_backend > sink_t;

void init_native_syslog()
{
    boost::shared_ptr< logging::core > core = logging::core::get();

    // Create a backend
    boost::shared_ptr< sinks::syslog_backend > backend(new sinks::syslog_backend(
        keywords::facility = sinks::syslog::user,               
        keywords::use_impl = sinks::syslog::native              
    ));

    // Set the straightforward level translator for the "Severity" attribute of type int
    backend->set_severity_mapper(sinks::syslog::direct_severity_mapping< int >("Severity"));

    // Wrap it into the frontend and register in the core.
    // The backend requires synchronization in the frontend.
    core->add_sink(boost::make_shared< sink_t >(backend));
}

void init_builtin_syslog()
{
    boost::shared_ptr< logging::core > core = logging::core::get();

    // Create a new backend
    boost::shared_ptr< sinks::syslog_backend > backend(new sinks::syslog_backend(
        keywords::facility = sinks::syslog::local0,             
        keywords::use_impl = sinks::syslog::udp_socket_based    
    ));

    // Setup the target address and port to send syslog messages to
    backend->set_target_address("192.164.1.10", 514);

    // Create and fill in another level translator for "MyLevel" attribute of type string
    sinks::syslog::custom_severity_mapping< std::string > mapping("MyLevel");
    mapping["debug"] = sinks::syslog::debug;
    mapping["normal"] = sinks::syslog::info;
    mapping["warning"] = sinks::syslog::warning;
    mapping["failure"] = sinks::syslog::critical;
    backend->set_severity_mapper(mapping);

    // Wrap it into the frontend and register in the core.
    core->add_sink(boost::make_shared< sink_t >(backend));
}

Windows 调试器输出后端 

#include <boost/log/sinks/debug_output_backend.hpp>

Windows API 有一个有趣的特性: 在调试器下运行的进程能够发出消息, 这些消息会被拦截并显示在调试器窗口中. 例如, 如果应用程序在 Visual Studio IDE 下运行, 它能够将调试消息写入 IDE 窗口. basic_debug_output_backend 后端提供了一种发出此类消息的简单方式. 此外, 为了优化应用程序性能, 还提供了一个 特殊过滤器, 用于检查应用程序是否在调试器下运行. 与许多其他接收器后端一样, 该后端也支持设置格式化器来组织消息文本.

用法非常简单直接:

// Complete sink type
typedef sinks::synchronous_sink< sinks::debug_output_backend > sink_t;

void init_logging()
{
    boost::shared_ptr< logging::core > core = logging::core::get();

    // Create the sink. The backend requires synchronization in the frontend.
    boost::shared_ptr< sink_t > sink(new sink_t());

    // Set the special filter to the frontend
    // in order to skip the sink when no debugger is available
    sink->set_filter(expr::is_debugger_present());

    core->add_sink(sink);
}

注意, 该接收器后端以字符类型为模板参数. 该类型定义了用于发出消息的 Windows API 版本. 此外, 还提供了 debug_output_backend 和 wdebug_output_backend 便捷 typedef.

Windows 事件日志后端 

#include <boost/log/sinks/event_log_backend.hpp>

Windows 操作系统提供了一个特殊 API, 用于发布与应用程序执行相关的事件. 大量应用程序 (包括 Windows 组件) 使用该设施, 在一个地方 —— 事件日志 —— 向用户提供关于计算机健康状况的所有关键信息. 事件日志可以有多个. 不过, 通常所有用户态应用程序都使用公共的 Application 日志. 不同应用程序或其组成部分的记录可以通过记录源名称从日志中筛选出来. 事件日志可以用 Windows 自带的标准工具事件查看器 (Event Viewer) 读取.

虽然看起来很诱人, 但该 API 相当复杂且具有侵入性, 难以支持. 应用程序需要提供一个带有特殊资源的动态库, 这些资源描述应用程序支持的所有事件. 该库必须在 Windows 注册表中注册, 注册会将库的位置固定在文件系统中. 事件查看器使用该注册信息查找资源, 并组成和显示消息. 这种方法的优点是, 由于事件资源可以针对不同语言以不同方式描述事件, 它允许应用程序以相当透明的方式支持事件国际化: 应用程序只需向 API 提供事件标识符和不可本地化的事件参数, 其余工作由 API 完成.

为了同时支持简单的"开箱即用"方式和更精细的事件组合 (包括国际化支持), 库提供了两个与事件日志 API 配合工作的接收器后端.

简单事件日志后端

basic_simple_event_log_backend 后端旨在尽可能多地封装事件日志 API, 使接口和使用模型与其他接收器后端非常相似. 它包含事件查看器正常工作所需的全部资源, 并在 Windows 注册表中注册 Boost.Log 库, 以便将自身注册为这些资源的容器.

重要

为了完美使用该后端, 库必须构建为动态库. 否则, 事件描述资源不会链接到可执行文件中, 事件查看器将无法正确显示事件.

用户要为应用程序添加 Windows 事件日志支持, 唯一需要做的就是提供事件源和日志名称 (它们是可选的, 库可以自动建议), 并设置适当的过滤器、格式化器和事件严重级别映射.

// Complete sink type
typedef sinks::synchronous_sink< sinks::simple_event_log_backend > sink_t;

// Define application-specific severity levels
enum severity_level
{
    normal,
    warning,
    error
};

void init_logging()
{
    // Create an event log sink
    boost::shared_ptr< sink_t > sink(new sink_t());

    sink->set_formatter
    (
        expr::format("%1%: [%2%] - %3%")
            % expr::attr< unsigned int >("LineID")
            % expr::attr< boost::posix_time::ptime >("TimeStamp")
            % expr::smessage
    );

    // We'll have to map our custom levels to the event log event types
    sinks::event_log::custom_event_type_mapping< severity_level > mapping("Severity");
    mapping[normal] = sinks::event_log::info;
    mapping[warning] = sinks::event_log::warning;
    mapping[error] = sinks::event_log::error;

    sink->locked_backend()->set_event_type_mapper(mapping);

    // Add the sink to the core
    logging::core::get()->add_sink(sink);
}

完成这些之后, 所有传递到该接收器的日志记录都将按照与其他接收器相同的方式进行格式化. 格式化后的消息将作为事件描述显示在事件查看器中.

高级事件日志后端

basic_event_log_backend 允许对日志 API 进行更细致的控制, 但在初始化和使用过程中需要多得多的准备工作.

首先, 用户必须构建带有事件资源的自己的库 (该过程在 MSDN 中有描述). 作为此过程的一部分, 必须创建一个描述所有事件的消息文件. 为便于示例, 假设以下内容用作消息文件:

; /* --------------------------------------------------------
; HEADER SECTION
; */
SeverityNames=(Debug=0x0:MY_SEVERITY_DEBUG
            Info=0x1:MY_SEVERITY_INFO
            Warning=0x2:MY_SEVERITY_WARNING
            Error=0x3:MY_SEVERITY_ERROR
            )

; /* --------------------------------------------------------
; MESSAGE DEFINITION SECTION
; */

MessageIdTypedef=WORD

MessageId=0x1
SymbolicName=MY_CATEGORY_1
Language=English
Category 1
.

MessageId=0x2
SymbolicName=MY_CATEGORY_2
Language=English
Category 2
.

MessageId=0x3
SymbolicName=MY_CATEGORY_3
Language=English
Category 3
.

MessageIdTypedef=DWORD

MessageId=0x100
Severity=Warning
Facility=Application
SymbolicName=LOW_DISK_SPACE_MSG
Language=English
The drive %1 has low free disk space. At least %2 Mb of free space is recommended.
.

MessageId=0x101
Severity=Error
Facility=Application
SymbolicName=DEVICE_INACCESSIBLE_MSG
Language=English
The drive %1 is not accessible.
.

MessageId=0x102
Severity=Info
Facility=Application
SymbolicName=SUCCEEDED_MSG
Language=English
Operation finished successfully in %1 seconds.
.

编译资源库之后, 必须将该库的路径提供给接收器后端构造函数, 连同简单后端使用的其他参数. 该路径可以包含占位符, 它们将用相应的环境变量展开.

// Create an event log sink
boost::shared_ptr< sinks::event_log_backend > backend(
    new sinks::event_log_backend((
        keywords::message_file = "%SystemDir%\\event_log_messages.dll",
        keywords::log_name = "My Application",
        keywords::log_source = "My Source"
    ))
);

与简单后端一样, basic_event_log_backend 会在 Windows 注册表中注册自身, 使事件查看器能够显示发出的事件.

接下来, 用户必须提供应用程序日志属性与事件标识符之间的映射. 这些标识符在编译消息文件时由消息编译器输出提供. 可以使用 basic_event_composer 和事件 ID 映射之一, 如下例所示:

// Create an event composer. It is initialized with the event identifier mapping.
sinks::event_log::event_composer composer(
    sinks::event_log::direct_event_id_mapping< int >("EventID"));

// For each event described in the message file, set up the insertion string formatters
composer[LOW_DISK_SPACE_MSG]
    // the first placeholder in the message
    // will be replaced with contents of the "Drive" attribute
    % expr::attr< std::string >("Drive")
    // the second placeholder in the message
    // will be replaced with contents of the "Size" attribute
    % expr::attr< boost::uintmax_t >("Size");

composer[DEVICE_INACCESSIBLE_MSG]
    % expr::attr< std::string >("Drive");

composer[SUCCEEDED_MSG]
    % expr::attr< unsigned int >("Duration");

// Then put the composer to the backend
backend->set_event_composer(composer);

如上所示, 可以使用常规的 格式化器 来指定哪些属性将插入最终事件消息中的占位符位置. 除此之外, 还可以指定属性值到事件类型和类别的映射. 假设我们的应用程序有以下严重级别:

// Define application-specific severity levels
enum severity_level
{
    normal,
    warning,
    error
};

然后可以将这些级别映射到消息描述文件中的值:

// We'll have to map our custom levels to the event log event types
sinks::event_log::custom_event_type_mapping< severity_level > type_mapping("Severity");
type_mapping[normal] = sinks::event_log::make_event_type(MY_SEVERITY_INFO);
type_mapping[warning] = sinks::event_log::make_event_type(MY_SEVERITY_WARNING);
type_mapping[error] = sinks::event_log::make_event_type(MY_SEVERITY_ERROR);

backend->set_event_type_mapper(type_mapping);

// Same for event categories.
// Usually event categories can be restored by the event identifier.
sinks::event_log::custom_event_category_mapping< int > cat_mapping("EventID");
cat_mapping[LOW_DISK_SPACE_MSG] = sinks::event_log::make_event_category(MY_CATEGORY_1);
cat_mapping[DEVICE_INACCESSIBLE_MSG] = sinks::event_log::make_event_category(MY_CATEGORY_2);
cat_mapping[SUCCEEDED_MSG] = sinks::event_log::make_event_category(MY_CATEGORY_3);

backend->set_event_category_mapper(cat_mapping);

提示

自 Windows NT 6 (Vista、Server 2008) 起, 不再需要指定事件类型映射. 该信息在消息定义资源中提供, 无需在 API 调用中重复.

初始化完成后, 可以将接收器注册到核心中.

// Create the frontend for the sink
boost::shared_ptr< sinks::synchronous_sink< sinks::event_log_backend > > sink(
    new sinks::synchronous_sink< sinks::event_log_backend >(backend));

// Set up filter to pass only records that have the necessary attribute
sink->set_filter(expr::has_attr< int >("EventID"));

logging::core::get()->add_sink(sink);

为了发出事件, 方便的做法是创建一组函数, 接受相应事件所需的全部参数, 并宣告事件已经发生.

BOOST_LOG_INLINE_GLOBAL_LOGGER_DEFAULT(event_logger, src::severity_logger_mt< severity_level >)

// The function raises an event of the disk space depletion
void announce_low_disk_space(std::string const& drive, boost::uintmax_t size)
{
    BOOST_LOG_SCOPED_THREAD_TAG("EventID", (int)LOW_DISK_SPACE_MSG);
    BOOST_LOG_SCOPED_THREAD_TAG("Drive", drive);
    BOOST_LOG_SCOPED_THREAD_TAG("Size", size);
    // Since this record may get accepted by other sinks,
    // this message is not completely useless
    BOOST_LOG_SEV(event_logger::get(), warning) << "Low disk " << drive
        << " space, " << size << " Mb is recommended";
}

// The function raises an event of inaccessible disk drive
void announce_device_inaccessible(std::string const& drive)
{
    BOOST_LOG_SCOPED_THREAD_TAG("EventID", (int)DEVICE_INACCESSIBLE_MSG);
    BOOST_LOG_SCOPED_THREAD_TAG("Drive", drive);
    BOOST_LOG_SEV(event_logger::get(), error) << "Cannot access drive " << drive;
}

// The structure is an activity guard that will emit an event upon the activity completion
struct activity_guard
{
    activity_guard()
    {
        // Add a stop watch attribute to measure the activity duration
        m_it = event_logger::get().add_attribute("Duration", attrs::timer()).first;
    }
    ~activity_guard()
    {
        BOOST_LOG_SCOPED_THREAD_TAG("EventID", (int)SUCCEEDED_MSG);
        BOOST_LOG_SEV(event_logger::get(), normal) << "Activity ended";
        event_logger::get().remove_attribute(m_it);
    }

private:
    logging::attribute_set::iterator m_it;
};
