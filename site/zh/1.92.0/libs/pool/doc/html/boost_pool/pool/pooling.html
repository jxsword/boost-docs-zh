池化的基本思想

自大约 1960 年以来, 动态内存分配一直是大多数计算机系统的基本组成部分... 1

每个人都使用动态内存分配. 如果你曾经调用过 malloc 或 new, 那么你就使用过动态内存分配. 大多数程序员倾向于把堆当作一个 “魔法袋"”: 我们向它要内存, 它就神奇地为我们创造一些. 有时我们会遇到问题, 因为堆并不神奇.

堆是有限的. 即使在拥有大量虚拟内存的大型系统 (即非嵌入式系统) 上, 也存在限制. 人人都知道物理限制, 但还有一个更微妙的"虚拟"限制: 达到该限制时, 你的程序 (或整个系统) 会因使用虚拟内存而变慢. 这个虚拟限制比物理限制离你的程序更近, 尤其是在多任务系统上运行时. 因此, 在大型系统上运行时, 让程序尽可能少地使用资源并尽快释放它们被认为是 友好的 做法. 在嵌入式系统上工作时, 程序员通常没有可以浪费的内存.

堆是复杂的. 它必须满足任何类型、任何大小的内存请求, 并且要快速完成. 常见的内存管理方法是把内存分割成若干部分, 并按大小以某种树或列表结构保持其有序. 再加上其他因素, 如局部性和生存期估计, 堆很快变得非常复杂. 复杂到事实上, 对于如何进行动态内存分配这一问题, 并没有已知的 完美 答案. 下图展示了大多数常见内存管理器的工作方式: 对于每块内存, 它使用其中一部分来维护其内部树或列表结构. 即使在一块内存被 malloc 出给程序之后, 内存管理器也必须在其中 保存 一些信息 - 通常只是它的大小. 然后, 当该块被 free 时, 内存管理器就可以轻松知道它有多大.

动态内存分配往往效率低下

由于动态内存分配的复杂性, 它在时间和/或空间上往往效率低下. 大多数内存分配算法会随每个内存块存储某种形式的信息, 或者是块大小, 或者是某种关系信息, 例如其在内部树或列表结构中的位置. 这类 头字段 通常会在程序正在使用的块中占用一个机器字. 明显的缺点是动态分配小对象时. 例如, 如果动态分配 int, 那么算法会自动为头字段保留空间, 我们最终会浪费 50% 的内存. 当然, 这是最坏的情形. 然而, 更现代的程序越来越多地使用堆上的小对象, 这使该问题越来越明显. Wilson 等人指出, 平均情况下内存开销约为百分之十到二十2. 随着更多程序使用更多更小的对象, 这一内存开销还会增长. 正是这一内存开销使程序更接近虚拟限制.

在较大的系统中, 内存开销不是那么大的问题 (相比于绕过它所需的时间), 因此常常被忽略. 但是, 存在这样的情形: 作为时间关键算法的一部分, 对较小对象的大量分配和/或释放不断发生; 在这些情形下, 系统提供的内存分配器往往太慢.

简单分隔存储同时解决了这两个问题. 几乎所有的内存开销都被消除, 且所有分配都可以在少量 (摊还) 常数时间内完成. 但是, 这是以牺牲通用性为代价的; 简单分隔存储只能分配单一大小的内存块.

简单分隔存储

简单分隔存储是 Boost Pool 库背后的基本思想. 简单分隔存储是最简单、也可能是最快的内存分配/释放算法. 它首先把一个内存区块划分为固定大小的内存块. 在实现之前, 区块来自哪里并不重要. 池就是以这种方式使用简单分隔存储的某个对象. 举例说明:

任何给定区块中的所有内存块的大小总是相同的. 这是简单分隔存储的基本限制: 你不能请求不同大小的内存块. 例如, 你不能向整数池请求一个字符, 也不能向字符池请求一个整数 (假定字符和整数的大小不同).

简单分隔存储的工作方式是把空闲列表交错地放入未使用的内存块中. 例如:

通过把空闲列表交错放入内存块内部, 每个简单分隔存储只有一个指针的开销 (指向列表第一个元素的指针). 对于进程正在使用的内存块, 它没有内存开销.

简单分隔存储也非常快. 在最简单的情形下, 内存分配仅仅是从空闲列表中移除第一个内存块, 这是一个 O(1) 操作. 在空闲列表为空的情形下, 可能需要获取并划分另一个区块, 这将产生摊还 O(1) 的时间. 内存释放可以简单到把该内存块加到空闲列表的前端, 这是一个 O(1) 操作. 但是, 简单分隔存储的更复杂用法可能要求有序空闲列表, 这会使释放变为 O(N).

与系统提供的分配器相比, 简单分隔存储执行更快、内存开销更小, 但以牺牲通用性为代价. 使用池的一个好场合是: 可能要在堆上分配许多 (非连续的) 小对象, 或者对相同大小对象的分配与释放反复发生.

保证对齐 - 我们如何以可移植的方式保证对齐.

如何处理连续内存块
Terminology

如果你还不熟悉 concepts 一节, 请先阅读它. 记住, 区块是内存的一段连续区域, 被划分或分隔为固定大小的内存块. 这些内存块就是用户分配和释放的对象.

概述

每个池都有一个可以跨越多个内存区块的空闲列表. 因此, 池也有一个已分配内存区块的链表. 默认情况下, 每个内存区块都是使用 new[] 分配的, 且所有内存区块都在销毁时释放. 正是 new[] 的使用使我们能够保证对齐.

概念证明: 保证对齐

每块内存都是通过 operator new[] 作为一个 POD 类型 (具体地说, 是一个字符数组) 分配的. 设 POD_size 为所分配的字符数.

谓词 1: 数组不得含有填充

这来自以下引文:

[5.3.3/2] (Expressions::Unary expressions::Sizeof) ... 当应用于数组时, 结果是数组中的总字节数. 这意味着 n 个元素的数组的大小是元素大小的 n 倍.

因此, 数组不能包含填充, 尽管数组内的元素可以包含填充.

谓词 2: 通过 operator new[] 作为字符数组分配的任何内存区块 (以下简称区块) 对该大小或更小大小的任何对象都是正确对齐的

这来自:

  • [3.7.3.1/2] (Basic concepts::Storage duration::Dynamic storage duration::Allocation functions) "... 返回的指针应适当对齐, 以便它可以转换为指向任何完整对象类型的指针, 并随后用于访问所分配存储中的对象或数组 ..."
  • [5.3.4/10] (Expressions::Unary expressions::New) "... 对于 char 和 unsigned char 数组, new 表达式的结果与分配函数返回的地址之间的差应为大小不超过所创建数组大小的任何对象类型的最严格对齐要求 (3.9) 的整数倍. [注: 由于假定分配函数返回的指针所指向的存储对任何类型的对象都是适当对齐的, 这一数组分配开销约束允许把字符数组分配出来、以后再在其中放置其他类型对象的常见惯用法."
考虑: 大小为某个实际对象大小倍数的假想对象类型 Element; 假定 sizeof(Element) > POD_size

注意, 该大小的对象可以存在. 这种大小的一个对象就是一个由"实际"对象组成的数组.

注意, 该区块对 Element 是正确对齐的. 这直接来自谓词 2.

推论 1: 该区块对 Element 数组是正确对齐的

这来自谓词 1 与谓词 2, 以及以下引文:

[3.9/9] (Basic concepts::Types) "对象类型是 (可能带 cv 限定的) 不是函数类型、不是引用类型且不是 void 类型的类型."

(具体而言, 数组类型是对象类型.)

推论 2: 对任何指针 p 与整数 i, 如果 p 对其指向的类型是正确对齐的, 则 p + i (在良定义时) 对该类型也是正确对齐的; 换言之, 如果一个数组是正确对齐的, 那么该数组中的每个元素都是正确对齐的

标准中没有任何引文直接支持这一论证, 但它符合关于"对齐"含义的通常理解.

注意, p + i 良定义的条件在 [5.7/5] 中有概述. 我们不在此引用它, 只注明当 p 与 p + i 都指向同一数组的内部或其后一位置时, 它是良定义的.

设: sizeof(Element) 为若干实际对象 (T1, T2, T3, ...) 大小的最小公倍数
设: block 为指向该内存区块的指针, pe 为 (Element *) block, pn 为 (Tn *) block
推论 3: 对每个整数 i, 只要 pe + i 良定义, 则对每个 n, 都存在某个整数 jn 使得 pn + jn 良定义且所引用的内存地址即 pe + i

这自然成立, 因为该内存区块是一个 Element 数组, 且对每个 n, sizeof(Element) % sizeof(Tn) == 0; 因此, Element 数组中每个元素的边界也是每个 Tn 数组中每个元素的边界.

定理: 对每个整数 i, 只要 pe + i 良定义, 该地址 (pe + i) 对每个类型 Tn 都是正确对齐的

由于 pe + i 是良定义的, 根据推论 3, pn + jn 是良定义的. 由谓词 2 以及推论 1 和推论 2, 它是正确对齐的.

定理的使用

上述证明涵盖了从区块中切分内存块的对齐要求. 实现使用以下实际对象大小:

  • 所请求的对象大小 (requested_size); 这是用户请求的内存块大小
  • void* (指向 void 的指针); 这是因为我们让空闲列表穿过内存块交错存放
  • size_type; 这是因为我们在每个内存区块中保存下一个区块的大小

每个区块还包含一个指向下一个区块的指针; 但它以指向 void 的指针形式存储并在需要时转换, 从而把对齐要求简化为上述三种类型.

因此, alloc_size 被定义为上述大小中的最大者, 并向上取整为所有三个大小的公倍数. 只要所有对齐都是 2 的幂, 这就保证了对齐: 在所有已知平台上这似乎都成立.

内存区块一览

每个内存区块由三个主要部分组成. 第一部分是切分内存块的部分, 包含交错的空闲列表. 第二部分是指向下一个区块的指针, 第三部分是下一个区块的大小.

这些部分中的每一部分都可能包含填充, 以保证对后续每一部分的对齐. 第一部分的大小是 number_of_chunks * lcm(requested_size, sizeof(void *), sizeof(size_type));, 第二部分的大小是 lcm(sizeof(void *), sizeof(size_type);, 第三部分的大小是 sizeof(size_type).

如何处理连续内存块

上述定理保证了分配内存块的所有对齐要求, 也保证了诸如交错空闲列表之类的实现细节. 但是, 它通过在必要时添加填充来做到这一点; 因此, 我们必须以不同的方式处理连续内存块的分配.

使用与上面类似的数组论证, 我们可以把对 n 个大小为 requested_size 的对象的连续内存请求转换为对 m 个连续内存块的请求. m 就是 ceil(n * requested_size / alloc_size), 其中 alloc_size 是内存块的实际大小.

注意, 所提供的分配连续内存块的实现使用线性而非平方算法. 这意味着如果空闲列表不是有序的, 它可能找不到连续的空闲内存块. 因此, 建议在处理内存块的连续分配时始终使用有序空闲列表. (在上面的示例中, 如果内存块 1 指向内存块 3、内存块 3 指向内存块 2、内存块 2 指向内存块 4, 而不是按顺序排列, 那么连续分配算法将无法找到任何连续内存块).

简单分隔存储 (不适合胆小者 - 仅限嵌入式程序员!)

引言

simple_segregated_storage.hpp 提供了一个模板类 simple_segregated_storage, 用于控制对内存块空闲列表的访问.

注意, 这是一个非常简单的类, 其几乎所有函数都带有未检查的前置条件. 它旨在成为最快且最小的快速内存分配器, 例如可用于嵌入式系统. 该类把许多困难的前置条件交由用户处理 (尤其是对齐问题). 有关更一般的用法, 请参见其他 Pool 接口.

概要 
template <typename SizeType = std::size_t>
class simple_segregated_storage
{
  private:
    simple_segregated_storage(const simple_segregated_storage &);
    void operator=(const simple_segregated_storage &);

  public:
    typedef SizeType size_type;

    simple_segregated_storage();
    ~simple_segregated_storage();

    static void * segregate(void * block,
        size_type nsz, size_type npartition_sz,
        void * end = 0);
    void add_block(void * block,
        size_type nsz, size_type npartition_sz);
    void add_ordered_block(void * block,
        size_type nsz, size_type npartition_sz);

    bool empty() const;

    void * malloc();
    void free(void * chunk);
    void ordered_free(void * chunk);
    void * malloc_n(size_type n, size_type partition_sz);
    void free_n(void * chunks, size_type n,
        size_type partition_sz);
    void ordered_free_n(void * chunks, size_type n,
        size_type partition_sz);
};
语义

类型为 simple_segregated_storage<SizeType> 的对象在其空闲列表为空时是空的. 若它不为空, 则当其空闲列表有序时它是有序的. 如果对 malloc() 的重复调用会产生按 std::less<void *> 判定的不断递增的值序列, 则该空闲列表是有序的. 如果空闲列表保持其顺序方向 (即有序空闲列表在成员函数调用后仍然有序), 则该成员函数是保持顺序的.
