Concepts

说明

Foldable 概念表示可以归约为单一值的数据结构.

一般而言, 折叠指的是把复杂结构概括为单一值的概念, 办法是连续应用一个二元运算, 把结构中的两个元素归约为单个值. 折叠有多种形式: 左折叠、右折叠, 带与不带初始归约状态的折叠, 以及它们的单子变体. 本概念能够表达所有这些折叠变体.

看待 Foldable 的另一种角度是: 支持内部迭代并能够累积结果的数据结构. 所谓内部迭代, 是指循环控制掌握在结构而非调用者手中. 因此, 由结构自己决定迭代何时停止, 通常即整个结构被消费完毕之时. 由于 C++ 是急切求值的语言, 这要求 Foldable 结构必须是有限的, 否则将需要无限循环才能消费整个结构.

注释
虽然 Foldable 只能处理有限结构这一点, 与 Haskell 中 Foldable 的定义相比似乎限制过严, 但概念的更细粒度划分应能缓解这个问题. 对可能无限的数据结构进行迭代, 参见 Iterable 概念. 对可能无限的数据结构进行搜索, 参见 Searchable 概念.

最小完整定义

fold_left or unpack

但请注意, 通过 unpack 提供的最小完整定义, 其编译期效率将远高于通过 fold_left 提供的定义.

具体模型

hana::map, hana::optional, hana::pair, hana::set, hana::range, hana::tuple

<tt>Foldable</tt> 的线性化

直观地说, 对 Foldable 结构 xs 而言, 其线性化 (即 xs 的线性化) 就是把 xs 中的所有元素如同放进一个列表中那样的序列:

linearization(xs) = [x1, x2, ..., xn]

注意, 对有限的 Foldable 而言, 总可以通过设置

linearization(xs) = fold_left(xs, [], flip(prepend))

编译期 Foldable

编译期 Foldable 是总长度在编译期已知的 Foldable. 换言之, 它是一个 Foldable, 其 length 方法返回一个无符号整型的 Constant. 对编译期 Foldable 进行折叠时, 折叠过程可以展开, 因为算法的最终步数在编译期已知.

此外, unpack 方法只对编译期 Foldable 可用. 这是因为其返回类型 (即 unpack 的返回类型) 依赖于结构中对象的个数. 要在编译期解析 unpack 的返回类型, 就要求结构的长度同样在编译期已知.

在本库当前版本中, 只支持编译期 Foldable. 虽然理论上也可以支持运行期 Foldable, 但要高效地做到这一点还需更多研究.

提供到 <tt>Sequence</tt> 的转换

给定标签 S (它是一个 Sequence), 标签建模 Foldable 概念的对象可以转换为标签为 S 的对象. 换言之, Foldable 可以转换为 Sequence S, 只需取 Foldable 的线性化并用它创建序列. 更具体地说, 给定一个 Foldable xs (线性化为 [x1, ..., xn]) 和 Sequence 标签 S, to<S>(xs) 等价于 make<S>(x1, ..., xn).

内建数组的自由模型

大小已知的内建数组可以像同质元组一样折叠. 但请注意, 内建数组至多只能做成 Foldable (例如 Iterable), 因为它们不能为空, 也不能从函数返回.

单子折叠入门

单子折叠 (monadic fold) 是指对二元函数的后续调用都通过相应 Monad 的单子 chain 运算符串接起来的折叠. 这使得可以在自定义的单子上下文中折叠结构. 例如, 用 hana::optional 单子执行单子折叠, 就要求二元函数把结果作为 hana::optional 返回, 并且折叠会中止并返回 nothing — 每当某个累积步骤失败 (即返回 nothing). 反之, 如果所有归约步骤都成功, 则会返回 just 结果. 不同的单子当然会产生不同的效果.

计算结构中数值的乘积.

更一般地, product 会取任何包含构成 Ring 的对象的可折叠结构, 并用 Ring 的二元运算归约它们. 折叠的初始状态是 Ring 运算的单位元. 有时需要指定所用的 Ring; 这可通过 product<R> 完成. 若未指定 Ring, 结构会使用由其包含元素构成的 Ring (若它知道的话), 否则使用 integral_constant_tag<int>. 因此,

product<R>(xs) = fold_left(xs, one<R or inferred Ring>(), mult)
product<> = product<integral_constant_tag<int>>
boost::hana::mult
constexpr auto mult

定义: mult.hpp:47

对数值而言, 这只是计算 xs 结构中数值的乘积.

注释
结构的元素实际上并不要求属于同一个 Ring, 但必须能对结构中任意两个相邻元素执行 mult, 这要求每对相邻元素至少共享一个 Ring 嵌入. 此处"相邻"的含义是: 结构的两个元素 x 与 y 相邻当且仅当它们在该结构的线性化中相邻, 如 Iterable 概念所记载.

constexpr

#include <boost/hana/fwd/sum.hpp>

计算结构中数值的总和.

更一般地, sum 会取任何包含构成 Monoid 的对象的可折叠结构, 并用 Monoid 的二元运算归约它们. 折叠的初始状态是 Monoid 的单位元. 有时需要指定所用的 Monoid; 这可通过 sum<M> 完成. 若未指定 Monoid, 结构会使用由其包含元素构成的 Monoid (若它知道的话), 否则使用 integral_constant_tag<int>. 因此,

sum<M>(xs) = fold_left(xs, zero<M or inferred Monoid>(), plus)
sum<> = sum<integral_constant_tag<int>>
boost::hana::plus
constexpr auto plus
Monoid 上的结合二元运算.
定义: plus.hpp:47

对数值而言, 这只是计算 xs 结构中数值的总和.

注释
结构的元素实际上并不要求属于同一个 Monoid, 但必须能对结构中任意两个相邻元素执行 plus, 这要求每对相邻元素至少共享一个 Monoid 嵌入. 此处"相邻"的含义是: 结构的两个元素 x 与 y 相邻当且仅当它们在该结构的线性化中相邻, 如 Iterable 概念所记载.

为什么有时必须用 <tt>sum<M></tt> 指定 <tt>Monoid</tt>?

这是因为像 tuple_tag 这样的序列标签 (出于设计) 没有参数化. 因此, 我们不知道序列中是什么类型的对象, 也就无法知道序列为空时应返回哪种类型的 0 值. 所以, 空情形下要返回的 0 的类型必须显式指定. 像 hana::range 这样的其他可折叠结构会忽略所建议的 Monoid, 因为它们知道自己包含对象的标签. 这种不一致行为是当前非参数化标签设计的局限, 但我们暂时没有好的解决方案.

以 Foldable 的元素作为实参调用函数.

给定一个函数和一个长度可在编译期确定的可折叠结构, unpack 以该结构的内容调用函数. 换言之, unpack(xs, f) 等价于 f(x...), 其中 x... 是结构的元素. 结构的长度必须在编译期已知, 因为将要编译的 f 的 operator() 版本取决于调用时的实参个数, 而这必须在编译期已知.

要创建接受可折叠结构而非可变参数的函数, 参见 fuse.

参数
xs要展开进函数的结构.
f要以 f(x...) 形式调用的函数, 其中 x... 是结构的元素, 就如同它们已用 to<tuple_tag> 线性化过一样.

设计理由: <tt>unpack</tt> 的命名与参数顺序

已有人多次建议把 unpack 改名为 apply, 并反转参数顺序以匹配提案中的 std::apply 函数. 然而, apply 这个名字已被用于表示普通函数应用, 这一用法与 Boost MPL 库乃至全世界 (尤其是函数式编程社群) 一致. 此外, 本库作者认为提案中的 std::apply 名字与参数顺序都不理想. 的确, 把函数作为第一个实参意味着对 lambda 使用 std::apply 时看起来像

std::apply([](auto ...args) {
use(args...);
}, tuple);
boost::hana::apply
constexpr auto apply
以给定实参调用 Callable.
定义: apply.hpp:40

由于最后一行末尾的 , tuple) 部分, 这无疑很丑陋. 相反, 把函数作为第二个实参则可以写成

hana::unpack(tuple, [](auto ...args) {
use(args...);
});

看起来美观得多. 基于这些考虑, 本库作者认为使用 unpack 而非 apply, 并采用合理的参数顺序, 是有充分理由的.
