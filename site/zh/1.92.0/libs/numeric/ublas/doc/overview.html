uBLAS 概述

设计理由

如果每一种数值软件都能用 C++ 编写而不损失效率, 那将非常好; 但除非能找到一种在不损害 C++ 类型系统的前提下实现这一目标的方法, 否则依赖 Fortran、汇编或体系结构特定的扩展可能更可取 (Bjarne Stroustrup).

这个 C++ 库面向科学计算, 侧重于矩阵和向量层面的基本线性代数构造及其对应的抽象运算. 主要设计目标是:

  • 数学记法
  • 效率
  • 功能性
  • 兼容性

另一个意图是评估: 使用这类矩阵和向量类所带来的抽象惩罚是否可以接受.

资源

本库的开发受到几个类似工作的指导:

  • BLAS , 作者 Jack Dongarra 等
  • Blitz++ , 作者 Todd Veldhuizen
  • POOMA , 作者 Scott Haney 等
  • MTL , 作者 Jeremy Siek 等

BLAS 似乎是使用最广泛的基本线性代数构造库, 可以称之为事实标准. 它的接口是过程式的, 各个函数在某种程度上从简单的线性代数运算中抽象出来. 由于它是用 Fortran 实现并做了优化, 它似乎也是现有最快的库之一. 因为我们决定以面向对象的方式设计和实现我们的库, 所以技术途径不同. 不过, 任何人都应该能够用我们库的运算符表达 BLAS 抽象, 并比较实现的效率.

Blitz++ 是一个用 C++ 实现的令人印象深刻的库. 它的主要设计似乎面向多维数组及其相关运算符, 包括张量. Blitz++ 的作者声称, 由于其使用表达式模板和模板元程序的实现技术, 该库达到了与相应 Fortran 代码相当或更好的性能. 然而, 我们有几个理由去发展自己的设计和实现途径. 我们不知道是否有人尝试用 Blitz++ 实现传统线性代数和其他数值算法. 我们还推测, 由于其实现习惯用法, 即使在今天 Blitz++ 仍需要最先进的 C++ 编译器技术. 另一方面, Blitz++ 使我们确信: 使用表达式模板对于把抽象惩罚降到可接受的限度是必不可少的.

POOMA 的设计目标在许多方面与 Blitz++ 相似. 它用偏微分方程和理论物理领域的类扩展了 Blitz++ 的概念. 其实现甚至支持并行体系结构.

MTL 是在 C++ 中支持基本线性代数运算的另一种途径. 它的设计似乎主要受 BLAS 和 C++ 标准模板库的影响. 我们赞同这样的见解: 线性代数库必须提供与 BLAS 相当的功能. 另一方面我们认为, C++ 标准库的概念尚未被证明能够按需要支持数值计算. 另一个不同点是, MTL 目前似乎不使用表达式模板. 这可能导致两种后果之一: 可能丧失表达力, 或可能丧失性能.

效率

为了达到数值计算的效率目标, 必须克服用 C++ 构造抽象时的两个困难, 即临时对象和虚函数调用. 表达式模板解决了这些问题, 但往往会拖慢编译时间.

消除临时对象

向量与矩阵上的抽象公式通常由若干一元和二元运算复合而成. 求值这种公式的传统方法是: 先把复合式的每个叶运算求值到一个临时对象, 再对复合式求值得到另一个临时对象. 这种方法在时间上很昂贵 (尤其是对小向量和小矩阵), 在空间上也很昂贵 (尤其是大向量和大矩阵). 解决这一问题的途径是使用现代函数式编程语言中已知的惰性求值. 这种方法的原理是逐元素求值复杂表达式, 并把它直接赋给目标.

由此产生两个有趣而危险的事实:

别名

对向量或矩阵使用逐元素求值可能会带来严重的副作用. 考虑矩阵向量乘 x = A x. 求 A1x 的值并赋给 x1 会改变右侧, 使得 A2x 的求值返回错误结果. 在这种情况下, 赋值的左边和右边都存在 别名, 涉及元素 xn.

我们对这个问题的解决方案是: 先把赋值的右侧求值到一个临时对象, 再把这个临时对象赋给左侧. 为了允许进一步优化, 我们为每个赋值运算符提供了相应的成员函数, 还提供了 noalias 语法. 使用这种语法, 程序员可以确认赋值的左边和右边相互独立, 从而逐元素求值并直接赋给目标是安全的.

复杂度

在某些情况下, 计算复杂度可能出乎意料地大. 考虑链式矩阵向量乘 A (B x). A (B x) 的常规求值是平方级的. B xi 的延迟求值是线性的. 由于每个元素 B xi 都需要以线性于大小的方式求值, 完全延迟求值的链式矩阵向量乘 A (B x) 是立方级的. 在这种情况下, 需要在表达式中重新引入临时对象.

消除虚函数调用

惰性表达式求值通常会导致定义一个项 (term) 的类层次结构. 这会导致使用动态多态来访问向量和矩阵的单个元素, 而这在时间上同样是昂贵的. 几年前 David Vandervoorde 和 Todd Veldhuizen 各自独立地找到了一个解决方案, 通常称为表达式模板 (expression templates). 表达式模板包含惰性求值, 并用静态多态 (即编译期多态) 取代动态多态. 表达式模板严重依赖著名的 Barton-Nackman 技巧, Jim Coplien 也将其称为 "奇异递归模板模式" (curiously defined recursive templates).

表达式模板是我们实现的基础.

编译时间

一个众所周知的事实是: 表达式模板对现有编译器是很大的挑战. 通过坚持使用 Barton-Nackman 技巧, 我们得以显著减少所需表达式模板的数量.

我们还决定支持一种双重的常规实现 (即不使用表达式模板), 并对向量与矩阵运算进行广泛的边界和类型检查, 以支持开发周期. 从 debug 模式切换到 release 模式由 NDEBUG 的 <cassert> 预处理符号控制.

存储布局

uBLAS 支持许多不同的存储布局. 完整细节见 类型概览. 大多数类型 (如 vector<double> 和 matrix<double>) 默认与 C 数组兼容, 但也可以配置为包含与 FORTRAN 兼容的数据.

兼容性

出于兼容性考虑, 我们为向量和矩阵提供了类似数组的索引. 对于某些类型 (厄米、稀疏等), 由于需要临时代理对象, 这对矩阵来说可能开销很大.

uBLAS 使用与 STL 兼容的分配器来分配其容器所需的存储.
