舍入策略

为了尽可能通用, 库使用一个类来计算所有向上或向下舍入的必要函数. 该类是 policies 的第一个参数, 也是 rounding 策略定义中名为 interval 的类型.

默认情况下它是 interval_lib::rounded_math<T>. 类 interval_lib::rounded_math 已针对标准浮点类型 (float、double 和 long double) 特化. 因此, 若你的区间的基础类型不是其中之一, 一个好的解决方案很可能是提供该类的特化. 但若 rounded_math<T> 针对 float、double 或 long double 的默认特化不合你的需求, 或者你不想特化 interval_lib::rounded_math<T> (比如说因为你更愿意在自己的命名空间中工作), 你也可以定义自己的舍入策略并直接传给 interval_lib::policies.

要求

下面是该类应当提供的内容. 定义域写在其对应函数旁边 (如你所见, 这些函数不必担心无效值, 但必须处理无穷参数).

  T tanh_up  (T);   // [-∞;+∞]

  T int_up  (T);    // [-∞;+∞]
  // conversion functions
  T conv_down(U);
  T conv_up  (U);
  // unprotected rounding class
  typedef ... unprotected_rounding;

舍入类的构造函数与析构函数有一条非常重要的语义要求: 它们负责设置和复位 T 上计算的舍入模式. 例如, 若 T 是标准浮点类型且浮点计算按 IEEE 754 标准执行, 构造函数可以保存当前舍入状态, 每个 _up (相应地 _down) 函数将向上 (相应地向下) 舍入, 而析构函数会恢复保存的舍入状态. 这正是默认舍入策略的行为.

直到 atanh_up 为止的所有数学函数的含义都很清楚: 每个函数返回类型 T 中可表示的数, 它是对应函数真实数学结果的下界 (对应 _down) 或上界 (对应 _up). 函数 median 计算其两个参数的平均值并舍入到最近的可表示数. 函数 int_down 和 int_up 计算小于或大于其参数的最近整数. 最后, conv_down 和 conv_up 负责把其他类型的值转换为基础数类型: 第一个必须把值向下舍入, 第二个必须把值向上舍入.

类型 unprotected_rounding 允许移除所有控制. 至于为什么要这样做, 请参见下文的保护段落.

所提供类的概览

库提供了大量的类. 这些类按层次组织. 最底层是类 rounding_control. 上一层是 rounded_arith_exact、rounded_arith_std 和 rounded_arith_opp. 然后是 rounded_transc_dummy、rounded_transc_exact、rounded_transc_std 和 rounded_transc_opp. 最后是 save_state 和 save_state_nothing. 这些类各自提供一组下一层类所需的成员. 例如, 一个 rounded_transc_... 类需要 rounded_arith_... 类的成员.

当它们存在两个版本 _std 和 _opp 时, 前者每次都切换舍入模式, 后者则尽量使舍入模式保持朝向正无穷. _opp 版本的主要目的是通过 \"opposite trick\" 加速计算 (参见性能说明). 该版本要求在进入该类的任何计算函数之前舍入模式已为向上. 它保证在函数退出时舍入模式仍然向上.

请注意: 把 _opp 版本与 _std 混用是非常糟糕的主意, 因为它们的性质互不兼容.

还有第三个版本名为 _exact, 它在不改变舍入模式的情况下计算这些函数. 这是一个 \"exact\" 版本, 因为它面向产生精确结果的基础类型.

最后一个版本是 _dummy 版本. 它不做任何计算, 但仍产生兼容的结果.

请注意: 对不精确的基础类型 (例如 float 或 double) 也可以使用 \"exact\" 版本. 在这种情况下, 包含性质不再得到保证, 但在不严格要求包含性质时, 这有助于加速计算. 例如, 在计算机图形学中, 只要包含性质的近似版本成立, 浮点舍入带来的小误差是可以接受的.

所提供类的描述

下面按舍入策略定义中出现的顺序描述各个类 (这种从外到内的顺序与概要中的顺序相反).

保护控制

保护 (protection) 指的是区间运算会被舍入模式控制所包围. 解除类的保护意味着移除所有舍入控制. 每个舍入策略都提供一个类型 unprotected_rounding. 所需的类型 unprotected_rounding 给出另一个舍入类, 使得它能在嵌套于 rounding 内部时工作. 例如, 下面前三行都应产生相同的结果 (因为第一个操作是 rounding 的构造函数, 最后一个操作是其析构函数, 它们负责设置舍入模式); 而最后一行允许有未定义行为 (因为从不调用任何 rounding 构造函数或析构函数).

T c; { rounding rnd; c = rnd.add_down(a, b); }
T c; { rounding rnd1; { rounding rnd2; c = rnd2.add_down(a, b); } }
T c; { rounding rnd1; { rounding::unprotected_rounding rnd2; c = rnd2.add_down(a, b); } }
T d; { rounding::unprotected_rounding rnd; d = rnd.add_down(a, b); }

自然地, rounding::unprotected_rounding 可以就是 rounding 本身. 但若它是一个带空构造函数和析构函数的简化版本, 则可以提升性能. 为了避免未定义行为, 库中保证: 类型为 rounding::unprotected_rounding 的对象只会在类型为 rounding 的对象已经存活时才被创建. 更多细节参见性能说明.

支持库定义了一个元编程类模板 unprotect, 它接受区间类型 I 并返回舍入策略已被解除保护的区间类型 unprotect<I>::type. 关于这些类型的信息: interval<T, interval_lib::policies<Rounding, _> >::traits_type::rounding is 与 Rounding 是相同的类型, 而 unprotect<interval<T, interval_lib::policies<Rounding, _> > >::type is 与 interval<T, interval_lib::policies<Rounding::unprotected, _> > 是相同的类型.

状态保存

首先是 save_state. 该类负责在其构造函数中保存当前舍入模式并调用 init, 并在其析构函数中恢复保存的舍入模式. 该类还定义 unprotected_rounding 类型.

若舍入模式不需要任何状态保存或初始化, 可以用 save_state_nothing 代替 save_state.

超越函数

类 rounded_transc_exact、rounded_transc_std 和 rounded_transc_opp 要求 std 命名空间提供函数 exp、log、cos、tan、acos、asin、atan、cosh、sinh、tanh、acosh、asinh、atanh. 对于 _std 和 _opp 版本, 所有这些函数都应遵守由 downward 或 upward 调用所设定的当前舍入模式.

请注意: 遗憾的是, 后一种情况很少成立. 正因如此, 库提供了一个不依赖 std 命名空间函数的类 rounded_transc_dummy. 但这并没有什么魔法: rounded_transc_dummy 的函数不做任何计算, 只返回有效的值. 例如, cos_down 总是返回 -1. 这样, 默认实现仍然验证了包含性质, 尽管这对用户毫无实际价值. 要想得到有用的值, 必须显式使用另一种策略, 而这多半会导致包含性质被破坏. 这样我们就确保该破坏被明确地告知用户, 让用户清楚自己面对的是什么. 这个类本可以用作默认的超越舍入类, 但最终决定: 宁可让编译因缺少声明而失败, 也不愿因函数有效却不可用而"成功".

基本算术函数

类 rounded_arith_std 和 rounded_arith_opp 要求运算符 + - * / 和函数 std::sqrt 遵守当前舍入模式.

类 rounded_arith_exact 要求定义了 std::floor 和 std::ceil, 因为它不能依赖 to_int.

舍入控制

前面各类定义的函数无需解释. 例如, add_down 的行为就是计算两个数之和并向下舍入. 而 rounding_control 的情况则复杂一些.

基本函数是 force_rounding, 它在参数尚未按当前舍入模式舍入时, 将其正确舍入后返回. 该函数对处理延迟舍入必不可少. 的确, 视计算方式不同, 中间结果可能在内部以更精确的格式保存, 从而导致错误的舍入. 因此该函数强制执行舍入. 这里是一个未强制舍入时会发生什么的例子.

函数 get_rounding_mode 返回当前舍入模式; set_rounding_mode 把舍入模式恢复为 get_rounding_mode 早前返回的某个值. downward、upward 和 to_nearest 把舍入模式设为三个方向之一. 该舍入模式对所有使用类型 T 的函数应是全局的. 例如, 调用 downward 之后, force_rounding(x+y) 应返回朝 -∞ 舍入的和.

函数 to_int 按当前舍入模式计算最近的整数.

类 rounding_control 的非特化版本什么也不做. 舍入模式相关函数为空, to_int 和 force_rounding 是恒等函数. pi_ 系常量函数返回合适的整数 (例如 pi_up 返回 T(4)).

类模板 rounding_control 针对 float、double 和 long double 做了特化, 以便充分利用计算机的浮点单元.

模板类 rounded_math

默认策略 (又名 rounded_math<T>) 简单地定义为:

template <class T> struct rounded_math<T> : save_state_nothing<rounded_arith_exact<T> > {};

而针对 float、double 和 long double 的特化使用 rounded_arith_opp, 如下所示:

template <> struct rounded_math<float>       : save_state<rounded_arith_opp<float> >       {};
template <> struct rounded_math<double>      : save_state<rounded_arith_opp<double> >      {};
template <> struct rounded_math<long double> : save_state<rounded_arith_opp<long double> > {};

性能问题

本段主要讨论库在使用计算机浮点单元 (FPU) 的区间上的性能. 以 [a,b] 与 [c,d] 之和为例. 结果是 [down(a+c), up(b+d)], 其中 down 和 up 表示所需的舍入模式.

舍入模式切换

若 FPU 能为每次运算使用不同的舍入模式, 则没有任何问题. 例如 Alpha 处理器就是如此: 每条浮点指令都可以指定不同的舍入模式. 然而, IEEE-754 标准并不要求这种行为. 因此大多数 FPU 只提供一些指令, 用于为后续所有运算设置舍入模式. 而且, 这些指令通常需要清空 FPU 的流水线.

在这种情况下, 计算 [a,b] 与 [c,d] 之和所需的时间远差于计算 a+b 和 c+d 所需的时间, 因为两次加法无法并行. 因此, 目标就是减少舍入模式切换的次数.

若使用本库不是为了提供精确计算, 而只是做数对算术, 解决方案非常简单: 不使用舍入. 此时计算 [a,b] 与 [c,d] 之和将与计算 a+b 和 c+d 一样快. 一切完美.

然而, 若要求精确计算, 这种方案完全不可想象. 那么, 我们就一筹莫展了吗? 不, 还有一个技巧可用. 的确, 若一元负号是精确运算, 则 down(a+c) = -up(-a-c). 这样就可以用同一舍入模式计算整个和. 一般来说, 模式切换的代价高于变号的代价.

加速连续运算

区间加法并不是唯一的运算; 大多数区间运算都可以只设置一次 FPU 的舍入方向来计算. 因此浮点舍入策略的各个运算都假定方向已被正确设置. 这个假定在程序中通常不成立 (用户和标准库都期望舍入方向为就近舍入), 所以这些运算必须被包裹在一个设置浮点环境的外壳中. 这种保护由舍入策略的构造函数和析构函数完成.

现在来考虑两次连续区间加法的情形: [a,b] + [c,d] + [e,f]. 生成的代码应当形如:

init_rounding_mode();    // rounding object construction during the first addition
t1 = -(-a - c);
t2 = b + d;
restore_rounding_mode(); // rounding object destruction
init_rounding_mode();    // rounding object construction during the second addition
x = -(-t1 - e);
y = t2 + f;
restore_rounding_mode(); // rounding object destruction
// the result is the interval [x,y]

在两次运算之间, 舍入方向被恢复, 然后又被重新初始化. 理想情况下, 编译器应能优化掉这些无用代码. 但遗憾的是它们做不到, 这会使代码慢一个数量级. 为了避免这个瓶颈, 用户可以告知区间运算: 它们不再需要被保护. 之后保护区间计算就成了用户自己的责任. 编译器将能生成如下代码:

init_rounding_mode();    // done by the user
x = -(-a - c - e);
y = b + d + f;
restore_rounding_mode(); // done by the user

用户需要创建一个舍入对象. 只要该对象存活, 就可以使用区间运算的非保护版本. 它们通过使用带有特定舍入策略的区间类型来选择. 若初始区间类型是 I, 则 I::traits_type::rounding 是舍入对象的类型, 而 interval_lib::unprotect<I>::type 是非保护区间类型的类型.

由于舍入对象存活期间 FPU 的舍入模式会被改变, 任何不涉及区间库的浮点算术运算都可能产生意外的结果. 反过来, 在没有舍入对象存活时使用非保护区间运算, 所产生的区间将不再保证包含真实结果.

示例

下面是一个用 Horner 方案计算多项式值的示例. 整个计算过程禁用了舍入模式切换.

// I is an interval class, the polynom is a simple array
template<class I>
I horner(const I& x, const I p[], int n) {

  // save and initialize the rounding mode
  typename I::traits_type::rounding rnd;

  // define the unprotected version of the interval type
  typedef typename boost::numeric::interval_lib::unprotect<I>::type R;

  const R& a = x;
  R y = p[n - 1];
  for(int i = n - 2; i >= 0; i--) {
    y = y * a + (const R&)(p[i]);
  }
  return y;

  // restore the rounding mode with the destruction of rnd
}

请注意: 系统专门创建了一个舍入对象来保护所有区间计算. 每个类型为 I 的区间在任何运算之前都会被转换为类型 R 的区间. 若不做这种转换, 结果仍然正确, 但整个优化的意义就消失了. 只要可能, 最好转换为 const R& 而不是 R: 的确, 该函数可能已经在某个解除保护的块内被调用, 此时类型 R 与 I 是同一个区间, 无需转换.

无关紧要的说明

开头曾说过, Alpha 处理器可以为每次运算使用特定的舍入模式. 然而, 由于指令格式的限制, 朝正无穷舍入不可用, 只能使用朝负无穷舍入. 因此借助变号的技巧变得必不可少, 但无需在每次运算两侧保存和恢复舍入模式.

扩展寄存器

除了舍入模式切换的代价之外还有另一个问题. 一些 FPU 使用扩展寄存器 (例如 float 计算用 double 寄存器完成, 或 double 计算用 long double 寄存器完成). 由此会产生许多问题.

第一个问题源于尾数的扩展精度. 舍入也在这种扩展精度上进行. 因此在扩展寄存器中, 我们仍然有 down(a+b) = -up(-a-b). 但回到标准精度后, 我们得到的将是 down(a+b) < -up(-a-b) 而非等式. 一种解决方案是不使用这种方法. 但仍有其他问题, 例如数与数之间的比较.

自然地, 指数的扩展精度也会带来问题. 为说明这个问题, 设 m 是 +inf 之前最大的数. 若我们计算 2*[m,m], 答案应当是 [m,inf]. 但由于扩展寄存器的存在, FPU 会先存储 [2m,2m], 然后在计算结束时 (当舍入模式朝向 +inf 时) 把它转换为 [inf,inf]. 于是答案不再准确.

只有一种解决方案: 强制 FPU 在每次运算之后把扩展值转回标准精度. 一些 FPU 提供能完成这种转换的指令 (例如 PowerPC 处理器). 但对于不提供它的 FPU (x86 处理器), 唯一的解决方案是把值写入内存再读回来. 这种操作显然非常昂贵.

一些示例

下面给出几种情况:

  • 若你需要对 float 或 double 类型进行精确计算, 使用默认的 rounded_math<T>;
  • 若要快速宽区间, 不用任何舍入也不管精度, 使用 save_state_nothing<rounded_transc_exact<T> >;
  • 对于精确类型 (如 int 或 rational, 辅以对无穷和 NaN 值的少量支持) 且不需要超越函数支持的情况, 解决方案可以是 save_state_nothing<rounded_transc_dummy<T, rounded_arith_exact<T> > > 或直接用 save_state_nothing<rounded_arith_exact<T> >;
  • 若情况比上述几种更复杂, 最好的办法多半是直接定义你自己的策略.
