检查策略

检查策略控制 interval 类如何处理特殊情况, 例如: 空区间、无穷数、无效值.

例如, 考虑 operator+(interval, T). 第二个参数可能是一个无效值 (对浮点数而言即 NaN). 这种情况下该怎么办? 首先, 可以规定第二个参数绝不可能是无效数. 其次, 也可以规定这种情况可能出现但被禁止. 第三, 还可以允许这类值, 并在遇到时生成空区间. 此外还有许多其他可能性.

这正是使用这种策略的原因: 存在许多有趣的行为, 若武断地选定其中一种未免可惜.

要求

检查类应满足下列要求 (以接口的形式给出):

/* requirements for checking policy */
struct checking
{
  static T pos_inf();
  static T neg_inf();
  static T nan();
  static bool is_nan(const T&);
  static T empty_lower();
  static T empty_upper();
  static bool is_empty(const T&, const T&);
};

前两个函数 pos_inf 和 neg_inf 会在库需要创建区间的无穷边界时被调用. 例如, interval::whole 计算 interval(checking::neg_inf(), checking::pos_inf()). 若允许无穷值且 std::numeric_limits<T>::infinity() 返回正确的值, 则可使用该值.

接下来是 nan. 每当某个函数需要返回 T 类型的值却无法计算时, 就会使用该函数. 这种情况只发生在函数的某个参数无效时. 例如, 若询问空区间的中位值, 就会使用 nan. 但请记住: lower 和 upper 直接返回存储在区间中的值; 因此若区间为空, lower 不会经由 (by) by 对 checking::nan 的调用来作答 (但将返回与 checking::empty_lower 可能返回的值相同的值).

empty_lower 和 empty_upper 分别返回空区间的下边界和上边界. 并不要求 empty_lower 和 empty_upper 返回与 checking::nan 相同的值. 例如, 若类型 T 没有任何无效值, 则 empty_ 函数可以返回 [1;0] 区间.

is_nan 用于测试 T 类型的值是否无效. is_empty 测试由两个参数构成的区间是否为空. 这类测试通常位于每个涉及 T 类型参数的函数的开头. 若某个输入被判定为无效, 函数将尝试产生一个无效值或一个输入区间.

概要

namespace boost {
namespace numeric {
namespace interval_lib {

template<class T>
struct checking_base;
template<class T, class Checking = checking_base<T>, class Exception = exception_create_empty<T> >
struct checking_no_empty;
template<class T, class Checking = checking_base<T> >
struct checking_no_nan;
template<class T, class Checking = checking_base<T>, class Exception = exception_invalid_number<T> >
struct checking_catch_nan;

template<class T> struct exception_create_empty { T operator()(); };
template<class T> struct exception_invalid_number { void operator()(); };

} // namespace numeric
} // namespace interval_lib
} // namespace boost

预定义类

为简化策略的定制, 库中已定义了一些模板.

首先, 库中提供了 checking_base. 得益于 std::numeric_limits<T> 提供的信息, 该类能够为策略生成一个基础. 若 T 具有 quiet NaN (如 numeric_limits::has_quiet_NaN 所示), 则该值用于 nan, empty_lower, empty_upper; 并对 is_nan 使用一个基本测试 (即 x!=x). 若 T 不具有 quiet NaN, 则 nan 为 assert(false), 空区间为 [1,0], 且 is_nan 总是返回 false. 至于 nan, pos_inf 返回 numeric_limits::infinity() (若可能), 否则为 assert(false). neg_inf 返回相反的值. 最后, is_empty(T l,T u) 总是定义为 !(l<=u).

接下来是 checking_no_empty. 使用它意味着: 每当需要产生空区间时 (通过 empty_lower 和 empty_upper), 将调用由模板的 Exception 参数给出的函数对象, 并传播其返回值. 因此, 若 Exception 定义得当 (例如它可以抛出异常, 这也是该参数名字的由来), 就可以确保绝不会创建空区间. 于是 is_empty 将总是返回 false (因为无需再测试空区间). 并且如前所述, 此时还可以把 nan 替换为 assert(false); 这样可以确保绝不会产生无效数. 若不使用该模板, 则隐含意味着所有函数都可能产生空区间, 并且它们能正确处理空区间参数.

最后还有 checking_no_nan 和 checking_catch_nan. 前者表示库的函数绝不会收到无效数作为参数. 因此 is_nan 将只返回 false. 后者表示参数可以是无效数, 但在这种情况下, is_nan 会调用函数对象 Exception 并返回 false. 的确, 该模板的含义是: 无效数绝不应进入函数体. 若这两个模板都未使用, 则隐含意味着所有函数都可能收到无效数参数, 并且它们会正确地处理这些参数.

exception_create_empty 抛出 std::runtime_error, 消息为 "boost::interval: empty interval created"; 而 exception_invalid_number 抛出 std::invalid_argument, 消息为 "boost::interval: invalid number".

自定义你自己的检查策略

要定义合适的策略, 你需要准确说明你希望区间类提供什么行为. 首先, 你是否关心在计算结束后得到空区间? 若你不希望得到空区间, 则 empty_lower 和 empty_upper 在被调用时必须失败 (它们可以抛出异常、设置标志等). 然而, 若没有任何函数能产生空区间, 就无需再做该测试, 此时 is_empty 可以总是返回 false. 在这种情况下, 一个好的编译器会做大量优化.

你也可能希望在计算结束后得到空区间. 例如, 若你需要把一个由不确定值 (或区间) 组成的数组转换成一个新的区间数组, 你可能不希望在遇到第一个问题时就停止转换. 此时 empty_lower 和 empty_upper 需要返回合适的值以定义空区间 (例如可以使用一个不大于等于下边界的上边界); 并且 is_empty 必须能够区分空区间和有效区间.

另一个重要问题是: 某些基础数 (类型为 T 的对象) 是否可能无效? 若可能, 它们是被允许还是被禁止? 若不可能, 则无需任何测试; is_nan 可以总是返回 false. 这种情况下, 一个好的编译器同样会做大量优化. 若函数参数可能携带无效数, 则根据其被允许与否需要考虑两种情况. 若允许, is_nan 只需测试其是否无效即可. 若禁止, is_nan 在遇到无效参数时应失败 (异常、断言等), 否则返回 false. nan 返回的值没有任何意义, 因为除非用户向构造函数传入无效数, 否则可以保证区间函数不会产生无效的区间边界. 所以若你不信任本库, 可以在其中放一个断言. :-)

最后, 你需要决定如何处理 nan (若开始时尚未决定), 以及 pos_inf 和 neg_inf. 这些函数应返回一个值, 或启动异常行为 (尤其当基础类型没有对应值时).

一些示例

  • 若你需要一种检查策略, 使库能够正确处理数据 (即使其中包含无效数和空区间), 那么 checking_base<T> 是一种可行选择.
  • 若你不希望创建空区间, 又不确定所有数都有效, 那么 checking_catch_nan<T, checking_no_empty<T> > 可以帮到你.
  • 若所有数都有效, 且按预期不会创建空区间 (或者你不希望创建它们), 那么可以使用 checking_no_nan<T, checking_no_empty<T> >. 请注意: 若 T 无法表示无效数, 则该策略的行为与 checking_no_empty<T> 相同. 这是默认策略, 也称为 interval_lib::checking_strict.
  • 若所有数值数据都有效, 但算法可能产生并处理空区间, 则应使用 checking_no_nan<T>.
  • 类似地, 若无效数据必须被报告, 且算法可能处理空区间, 则 checking_catch_nan<T> 是一种解决方案.
  • 若你不介意在产生空区间或无效区间数时得到未定义的结果, 最好的办法是通过重载 checking_base 创建自己的策略, 并修改 is_nan 和 is_empty 使其总是返回 false. 这可能是现有最快的检查策略; 但其安全性不足.
