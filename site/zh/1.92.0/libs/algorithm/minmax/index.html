动机

minmax 库由两个头文件组成: <boost/algorithm/minmax.hpp> 和 <boost/algorithm/minmax_element.hpp>.(见 设计理由.) 该库解决的问题在于: 同时计算 min 和 max 只需要一次比较, 但使用 std::min 和 std::max会强制进行两次比较. 更糟的是, 计算一个含 n 个元素的范围的最小与最大元素本只需 3n/2+1 次比较, 而 std::min_element 与 std::max_element却强制 2n 次(两次遍历). 我一直觉得, 计算一个范围的大小本来一次就够, 却要调用两个函数, 对输入进行两遍遍历, 是一种浪费. 本库同时解决了这两个问题.

第一个文件实现了函数模板 minmax, 作为对 C++ 标准的直接扩展. 由于它返回一个由 const& 组成的 pair, 我们必须使用 Boost.tuple 库来构造这样的 pair.(请注意: 其意图并不是修复 std::min 与 std::max 的已知缺陷, 而是新增一个把两者结合起来的算法; 见 设计理由.)

第二个文件实现了函数模板 minmax_element. 在第二部分中, 它还提出了一些通常无法由 minmax 算法计算, 且在元素相等时更为灵活的变体. 这些变体本也可以用基于策略的设计来提供, 但我否决了这种做法(见 设计理由).

如果你对 性能感兴趣, 你会看到 minmax_element 只比单独的 min_element 或 max_element 略低效, 因而比分别调用 min_element 和 max_element 高效一倍. 从理论角度看, 所有 minmax_element 函数至多执行 3n/2+1 次比较, 且恰好对 ForwardIterator 递增 n 次.

概要: <boost/algorithm/minmax.hpp>

#include <boost/tuple/tuple.hpp>

namespace boost {

  template <class T>
  tuple<T const&, T const&>
  minmax(const T& a, const T& b);

  template <class T, class BinaryPredicate>
  tuple<T const&, T const&>
  minmax(const T& a, const T& b, BinaryPredicate comp);

}

概要: <boost/algorithm/minmax_element.hpp>

#include <utility> // for std::pair

namespace boost {

  template <class ForwardIterator>
  std::pair<ForwardIterator,ForwardIterator>
  minmax_element(ForwardIterator first, ForwardIterator last);

  template <class ForwardIterator, class BinaryPredicate>
  std::pair<ForwardIterator,ForwardIterator>
  minmax_element(ForwardIterator first, ForwardIterator last,
                 BinaryPredicate comp);

}
此外, 还有一批扩展, 用于在元素相等时指定你想选取哪个(哪些)元素. 它们是:
  • first_min_element 与 last_min_element
  • first_max_element 与 last_max_element
  • first_min_first_max_element, first_min_last_max_element, last_min_first_max_element 和 last_min_last_max_element
我不打算用完整的概要来烦你, 它们的声明与对应的 _element 函数完全相同. 不过, 你可以在 此处找到完整概要.

函数模板说明

minmax 算法返回一个 pair p, 其中包含 (a,b) 或 (b,a), 使得第一个版本中 p.first<p.second, 或第二个版本中 comp(p.first,p.second). 若两元素等价, 则返回 pair (a,b) . [1]

minmax_element 在语义上等价于 first_min_first_max_element.

First_min_element 与 first_max_element 在范围 [first, last) 中查找最小和最大元素. 若存在多个这样的元素实例, 则返回第一个. 它们与 std::min_element 和 std::max_element完全相同, 仅出于对称性才收入本库.

Last_min_element 与 last_max_element 在范围 [first, last) 中查找最小和最大元素. 它们与 std::min_element 和 std::max_element几乎相同, 区别在于它们返回最大元素的最后一个实例(而非像 first_min_element 与 last_max_element那样返回第一个).

由 first_min_first_max_element, first_min_last_max_element, last_min_first_max_element 和 last_min_last_max_element 组成的算法家族可以概括如下(用 which 与 what 表示 first 或 last): which_min_what_max_element 按 which取第一个或最后一个地查找最小元素, 并按 what取第一个或最后一个地查找最大元素, 范围为 [first, last). 第一个版本在语义上等价于: 

  std::make_pair(boost::which_min_element(first,last),
                 boost::what_max_element(first,last)),
第二个版本等价于: 
  std::make_pair(boost::which_min_element(first,last,comp),
                 boost::what_max_element(first,last,comp)).


注释: first_min_last_max_element 也可以描述为: 在范围被稳定排序的情况下, 找到其中的第一个和最后一个元素.

定义

定义于 minmax.hpp 与 minmax_element.hpp.

对类型的要求

对 minmax 而言, T 必须是 LessThan Comparable 的一个模型.

对于所有其他函数模板, 带有两个模板参数的版本:

  • ForwardIterator 是 Forward Iterator 的一个模型.
  • ForwardIterator 的值类型是 LessThan Comparable.
对带三个模板参数的版本:
  • ForwardIterator 是 Forward Iterator 的一个模型.
  • BinaryPredicate 是 Binary Predicate 的一个模型.
  • ForwardIterator 的值类型可转换为 BinaryPredicate 的第一实参类型与第二实参类型.

前置条件

  • [first, last) 是一个有效范围.

后置条件

除上述语义说明之外, 对 minmax_element 与所有 which_min_what_max_element 变体, 当且仅当 [first, last) 是空范围时, 返回值为 last 或 std::make_pair(last,last). 否则, 返回值或结果 pair 的两个成员都是范围 [first, last) 中的迭代器.

复杂度

Minmax 只执行一次比较, 除此之外复杂度为常量. 使用 boost::tuple<T const&> 避免了在实参按引用传递时调用拷贝构造函数.

所有其他算法的复杂度都是线性的. 它们都恰好执行 n 次递增操作; 若 [first,last) 为空则比较次数为零, 否则:

  • 所有 min_element 与 max_element 变体恰好执行 (n-1) 次比较,
  • minmax_element, first_min_first_max_element 和 last_min_last_max_element 在 n 为偶数且非零时至多执行 3(n/2)-1 次比较, 在 n 为奇数时至多执行 3(n/2)+1 次, [2]
  • first_min_last_max_element 和 last_min_first_max_element 在 n 为偶数且非零时恰好执行 3n/2-2 次比较, 在 n 为奇数时至多执行 3(n/2) 次, [3]
其中 n 是 [first,last) 中元素的个数.

示例

该示例已收入发行包中, 位于本库的示例部分: minmax_ex.cpp. 
int main()
{
  using namespace std;
  boost::tuple<int const&, int const&> result1 = boost::minmax(1, 0);

  assert( result1.get<0>() == 0 );
  assert( result1.get<1>() == 1 );

  list<int> L;
  generate_n(front_inserter(L), 1000, rand);

  typedef list<int>::const_iterator iterator;
  pair< iterator, iterator > result2 = boost::minmax_element(L.begin(), L.end());
  cout << "The smallest element is " << *(result2.first) << endl;
  cout << "The largest element is  " << *(result2.second) << endl;

  assert( result2.first  == std::min_element(L.begin(), L.end());
  assert( result2.second == std::max_element(L.begin(), L.end());
}

注释

[1] 我们不支持诸如 tie(a,b)=minmax(a,b) 这样给两个元素 a, b 排序的惯用法, 尽管如果我们返回引用而非常量引用, 它会具有期望的效果. 原因是: 若 a 和 b 本来有序, 就会执行两次多余的赋值. 要达到该效果, 更好的做法是坚持用 if (b<a) swap(a,b).

[2] 这些算法总是至少执行 3n/2-2 次比较, 这是任何情况下比较次数的下界(Cormen, Leiserson, Rivest: "Introduction to Algorithms", 9.1 节, 练习 9.1-). 这些算法基本上成对比较元素: 对头两个元素做 1 次比较, 然后对其余每一对元素做 3 次比较(一次用于排序这两个元素, 一次用于更新最小值, 一次用于更新最大值). 当元素个数为奇数时, 最后一个元素需要与当前最小值以及当前最大值各比较一次. 此外, 对于 minmax, 在 pair 的两个成员可能相等, 且更新动作保存第二个元素的情况下, 我们会保存第一个元素, 以便最后检查更新是否本应保存第一个元素(在相等的情况下). 很难预测最后一次比较是否执行, 因此两种情况下都用了"至多".

[3] 这些算法总是至少执行 3n/2-2 次比较, 这是任何情况下比较次数的下界. 方法与上文注释 [2]相同, 且与上文一样, 当元素个数为奇数时, 最后一个元素需要与当前最小值以及当前最大值各比较一次. 若前一次比较成功, 我们可以省去后一次比较, 因此奇数情形下用 至多而非 恰好.

设计理由:

为什么不只用一个头文件 <boost/algorithm/minmax.hpp>?

这是在正式评审中最初提出并获批准的设计. 随着 Boost.tuple 的需求变得明朗(由于 std::pair 的局限), 要求不需要它的 minmax_element 也依赖另一个库就变得讨厌起来. 因此拆分为两个头文件.

你的 minmax 与 std::min 和 std::max 存在同样的问题.

我了解 std::min 与 std::max 的问题, 以及围绕它们进行的一切争论(请参阅 Alexandrescu 的论文及其中的链接). 但我不认为本库的目的是修复属于 C++ 标准的东西. 我谦卑地认为这超出了本库的范围. 相反, 我遵循标准的方式, 只是提供同一家族的又一个函数. 如果有人想修复 std::min, 他们的修复多半也同样适用于 boost::minmax.

为什么没有 min/max_element_if?

在本库的第一个版本中, 我曾提议所有算法的 _if 版本(嗯, 不是全部, 因为那会太多). 然而, 根本没有理由这样做, 我手头的所有版本用优秀的 <boost/iterator_adaptors.hpp> 库实现起来同样快. 也就是说, 对 min_element_if(first, last, pred) 的调用可以同样好地用如下方式实现: 

     // equivalent to min_element_if(first, last, pred)
     min_element(boost::make_filter_iterator(first, last, pred),
                 boost::make_filter_iterator(last, last, pred));
可以说, min_element_if 版本要短一些, 但迭代器适配器的开销并不大, 而且它们省去了大量代码(想想 first/last 之间的所有组合, 再用 _if 变体把它们翻倍!).

讨论: 关于 std::max_element

这条设计理由带有一定的历史色彩, 但它解释了为什么会有这么多 first/last_min/max_element 函数.

C++ 标准规定 std::min_element 与 std::max_element 返回最小和最大元素的第一个实例(而不是, 比如说, 最后一个). 这一任意的选择有其一致性: 例如, 对类型为 vector<int> 的 v 来说, std::min_element(v.begin(),v.end(),std::less<int>()) == std::max_element(v.begin(),v.end(),std::greater<int>()) 成立.

这当然没有什么错: 这只是一个选择问题. 指定 min_element 和 max_element 的另一种方式, 是把它们定义为: 若范围被稳定排序, 则分别为其第一个和最后一个元素.(稳定排序是必要的, 用于区分具有相同值的迭代器.) 在那种情况下, min 应返回第一个实例, max 应返回最后一个. 于是, 两个函数通过 reverse_iterator(std::first_min_element(v.begin(),v.end(),std::less<int>())) == std::last_max_element(v.rbegin(),v.rend(),std::greater<int>()) 相互关联. 这一定义与前一判断有微妙的不同.

当人们尝试按照(Cormen, Leiserson, Rivest: "Introduction to Algorithms", 9.1 节)中提出的过程设计一个 minmax_element 时, 定义问题就浮出水面. 本 应当有可能推导出一个只用 3n/2 次比较的算法 —— 若 [first,last) 有 n 个元素的话 —— 但若有人尝试编写一个名为 first_min_first_max_element() 的函数, 在一个 pair 中同时返回 std::min_element 与 std::max_element, 平凡的实现却行不通. 问题相当微妙地出在相等元素上: 我花了相当一段时间才找到每对只做三次比较并返回第一个最小与第一个最大元素的办法. 有很长一段时间, 任何这样的尝试在最坏情形下似乎都要消耗每对四次比较. 这个实现做到了三次.

改变 max_element 的含义是不可能的(甚至是不可取的), 但提供一个名为 minmax_element, 返回 min_element 与 max_element 组成的 pair 的函数仍然是有益的. 尽管调用 min_element 与 max_element 足够容易, 但这会执行 2(n-1) 次比较, 并且需要对输入进行 两次遍历. 相比之下, minmax_element 将执行更少的比较, 并对输入只做 单次遍历. 当迭代器类型不是裸指针, 甚至只是 InputIterator 概念的一个模型时, 节省可能很可观(不过那种情况下接口将不得不改变, 因为返回类型无法被拷贝, 比如可以改为返回一个值).

为了从该算法的所有变体中获益, 我提议同时引入 first_min_element 与 last_min_element, 以及它们的对应物 first_max_element 与 last_max_element. 然后我还提议所有的变体算法: first_min_last_max_element 与 last_min_first_max_element, 它们至多只执行 3n/2 次比较, 且对输入只做单次遍历. 事实上, 可以证明, 在该问题的任何实例上, 计算 minmax 至少需要 3(n/2)-2 次比较(Cormen, Leiserson, Rivest, 第 2 版, 9.1 节). 我给出的实现不会执行多余的比较(其结果本可以由之前比较的传递性推得).

看起来 first_min_last_max_element 可能只比单独的 first_min_element 略慢一点, 仍然远低于分别调用 first_min_element 与 last_max_element. [2]

为什么是算法而不是累加器(accumulator)?

minmax 算法可用于计算一个范围的大小. 在计算机图形学中, 我们需要一组对象的包围盒. 那种情况下对单次遍历的需求更加严苛, 因为三个方向必须一次完成. 值得思考的是: 有潜力做一个漂亮的泛型编程库, 它带有可堆叠的 update_min 与 update_max 函数对象 —— 它们保存对 min_result与 max_result 变量的引用 —— 并与 for_each 算法配合使用).

我相信许多标准顺序算法都可以用累加器重新表述(还有许多其他算法, 如统计学中的期望/方差/等). 看起来还有容纳另一个库的空间, 但我不认为它会与 minmax 竞争, 相反, 它会把若干算法(包括 minmax)扩展到累加器框架. 不过, 我觉得提供这样的累加器超出了本库的范围.

这种 first/last 是基于策略的设计的完美应用场景.

没错, 我本可以走那条路, 让 min_element 与 max_element 的默认策略选取结果的第一次出现. 这本可以减少 minmax_element 变体的组合数量. 但那也意味着要改变 boost::minmax_element 的接口. minmax_element 算法的目标之一是最终加入 C++ 标准, 与 std::min_element 和 std::max_element 并列(我觉得考虑到实现的简短, 以及把它做对所需的那些并非微不足道的细节, 这会很自然). 因此, 通过添加策略来改变接口, 遗憾的是将意味着背离标准, 并给那个目标制造障碍. 此外, 不用策略时代码仍然相当易读且简单. 所以我很乐意保持现状.

关于性能

致谢

 Generic: Min and Max Redivivus, by Andrei Alexandrescu Dr. Dobbs, 2001 年 4 月

我 CS903(Polytechnic Univ., http://photon.poly.edu/~hbr/cs903/)的学生们把 minmax_element 作为作业, 他们帮助澄清了问题, 还得出了 first_min_last_max_element 的最优比较次数. 围绕 max_element 的问题的辨识则完全归功于我个人.

最后, Matthew Wilson 与 Jeremy Siek 提供了评审前的意见, 而 Gennadiy Rozental, John Maddock, Craig Henderson, Gary Powell 参与了本库的评审, 评审由 Thomas Witt 主持. 特别是, Gennadiy 建议对代码做因式分解; 虽然我没有完全照做, 他的建议确实让代码更易读, 并且仍能在较老的编译器上工作. 评审之后很久, 当我终于勉强为本库的发布做准备时, Eric Niebler 注意到了 std::pair 用于 minmax 的不良行为, 并建议改用 Boost.tuple. 对所有人出色的建议与评审, 我深表感谢.
