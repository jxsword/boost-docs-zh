引言

智能指针是存储指向动态分配 (堆) 对象的指针的对象. 其行为与 C++ 内置指针非常相似, 区别在于它们会在恰当的时机自动删除所指向的对象. 在可能出现异常的场合, 智能指针尤其有用, 因为它们能确保动态分配的对象被正确销毁. 它们还可用于跟踪由多个所有者共享的动态分配对象.

从概念上讲, 智能指针被视为拥有其所指向的对象, 因而在对象不再需要时负责将其删除. 因此, 它们是"资源获取即初始化" (resource acquisition is initialization) 惯用法的实例; 该惯用法在 Bjarne Stroustrup 所著《The C++ Programming Language》第 3 版第 14.4 节 Resource Management 中有描述.

本库提供六个智能指针类模板:

  • scoped_ptr, 用于将动态分配对象的所有权包含在当前作用域内;

  • scoped_array, 为动态分配的数组提供作用域所有权;

  • shared_ptr, 管理对象或数组共享所有权的多功能工具;

  • weak_ptr, 指向 shared_ptr 所管理对象的非所有权观察者, 可临时提升为 shared_ptr;

  • intrusive_ptr, 指向内嵌引用计数对象的指针;

  • local_shared_ptr, 提供单线程内的共享所有权.

shared_ptr 和 weak_ptr 自 2011 年版起成为 C++ 标准的一部分.

此外, 本库还包含以下辅助工具函数和类:

  • make_shared 和 allocate_shared, 用于创建对象的工厂函数, 返回 shared_ptr;

  • make_unique, 返回 std::unique_ptr 的工厂函数;

  • allocate_unique, 使用分配器创建对象的工厂函数, 返回 std::unique_ptr;

  • enable_shared_from_this, 辅助基类, 用于获得 shared_ptr, 其指向 this;

  • enable_shared_from, enable_shared_from_this 的更新且更好的替代品;

  • pointer_to_other, 用于将一种智能指针类型转换为另一种的辅助特征 (trait) ;

  • static_pointer_cast 及其同类, 通用智能指针转换;

  • intrusive_ref_counter, 包含引用计数的辅助基类.

  • atomic_shared_ptr, 一个辅助类, 实现 std::atomic 的接口, 用于 shared_ptr 类型的值.

一般规则是: 由本库中的指针所管理对象的析构函数或 operator delete 不允许抛出异常.

scoped_ptr: 作用域对象所有权

说明

scoped_ptr 类模板存储指向动态分配对象的指针. (动态分配对象通过 C++ new 表达式分配. ) 所指向的对象保证会被删除: 或者在 scoped_ptr 析构时, 或者通过显式调用 reset. 参见示例.

scoped_ptr 是针对简单需求的简单解决方案. 它提供基本的"资源获取即初始化"设施, 不具有共享所有权或所有权转移语义. 其名称以及对语义的强制执行 (通过不可复制) 都表明, 它打算将所有权仅保留在当前作用域内. 由于它不可复制, 对于不应被复制的指针而言, 它比 shared_ptr 更安全.

由于 scoped_ptr 很简单, 在通常的实现中, 其每个操作的速度都与内置指针一样快, 且空间开销不超过内置指针.

scoped_ptr 不能用于 C++ 标准库容器. 如果需要能用于标准库容器的智能指针, 请使用 shared_ptr 或 std::unique_ptr.

scoped_ptr 无法正确持有指向动态分配数组的指针. 该用法请参见 scoped_array.

该类模板以 T (即所指向对象的类型) 为参数. 销毁 T 不得抛出异常, 并且 T 必须是完整类型 (在 scoped_ptr<T>::~scoped_ptr 被实例化之处) .

概要

scoped_ptr 定义于 <boost/smart_ptr/scoped_ptr.hpp>.

namespace boost {

  template<class T> class scoped_ptr {
  private:

    scoped_ptr(scoped_ptr const&);
    scoped_ptr& operator=(scoped_ptr const&);

    void operator==(scoped_ptr const&) const;
    void operator!=(scoped_ptr const&) const;

  public:

    typedef T element_type;

    explicit scoped_ptr(T * p = 0) noexcept;
    ~scoped_ptr() noexcept;

    void reset(T * p = 0) noexcept;

    T & operator*() const noexcept;
    T * operator->() const noexcept;
    T * get() const noexcept;

    explicit operator bool() const noexcept;

    void swap(scoped_ptr & b) noexcept;
  };

  template<class T> void swap(scoped_ptr<T> & a, scoped_ptr<T> & b) noexcept;

  template<class T>
    bool operator==( scoped_ptr<T> const & p, std::nullptr_t ) noexcept;
  template<class T>
    bool operator==( std::nullptr_t, scoped_ptr<T> const & p ) noexcept;

  template<class T>
    bool operator!=( scoped_ptr<T> const & p, std::nullptr_t ) noexcept;
  template<class T>
    bool operator!=( std::nullptr_t, scoped_ptr<T> const & p ) noexcept;
}

构造一个 scoped_ptr, 存储 p 的副本, 该副本必须是通过 C++ new 表达式分配的, 或为 0. T 不要求是完整类型.

析构函数

删除所存储指针指向的对象, 然后存储 p 的副本, 该副本必须是通过 C++ new 表达式分配的, 或为 0.

由于前一个对象需要被删除, T 必须是完整类型.

get

转换

swap

交换两个智能指针的内容. T 不必是完整类型.

template<class T> bool operator!=( std::nullptr_t, scoped_ptr<T> const & p ) noexcept;

示例

下面是一个使用 scoped_ptr 的示例.

#include <boost/scoped_ptr.hpp>
#include <iostream>

struct Shoe { ~Shoe() { std::cout << "Buckle my shoe\n"; } };

class MyClass {
    boost::scoped_ptr<int> ptr;
  public:
    MyClass() : ptr(new int) { *ptr = 0; }
    int add_one() { return ++*ptr; }
};

int main()
{
    boost::scoped_ptr<Shoe> x(new Shoe);
    MyClass my_instance;
    std::cout << my_instance.add_one() << '\n';
    std::cout << my_instance.add_one() << '\n';
}

该示例程序输出一首童谣的开头:

1
2
Buckle my shoe

设计理由

使用 scoped_ptr 而非 std::auto_ptr 或 std::unique_ptr 的主要原因, 是让代码的读者知道: 你打算只把"资源获取即初始化"应用于当前作用域, 而没有转移所有权的意图.

使用 scoped_ptr 的另一个次要原因是, 防止后来的维护者添加一个通过返回 auto_ptr 来转移所有权的函数, 因为维护者看到了 auto_ptr, 便以为所有权可以安全转移.

想想 bool 与 int 的对比. 我们都知道, 在底层 bool 通常只是一个 int. 事实上, 正因如此, 一些人曾反对将 bool 纳入 C++ 标准. 但是, 编写 bool 而不是 int, 就能告诉读者你的意图. scoped_ptr 也是同样道理; 使用它就是在表明意图.

有人认为 scoped_ptr<T> 等价于 std::auto_ptr<T> const. 然而 Ed Brey 指出, reset 在 std::auto_ptr<T> const 上行不通.

Handle/Body 惯用法

scoped_ptr 的一个常见用法是实现 handle/body (也称为 pimpl) 惯用法, 以避免在头文件中暴露 body (实现) .

scoped_ptr_example_test.cpp 示例程序包含一个头文件 scoped_ptr_example.hpp, 它使用指向不完整类型的 scoped_ptr<> 来隐藏实现. 需要完整类型的成员函数的实例化则发生在 scoped_ptr_example.cpp 实现文件中.

常见问题

  1. 为什么 scoped_ptr 没有 release() 成员?

    阅读源代码时, 能够根据所使用的类型推断程序行为是很有价值的. 如果 scoped_ptr 拥有 release() 成员, 就可以转移所持有指针的所有权, 从而削弱其将资源生命周期限制在特定上下文中的作用. 需要转移所有权时请使用 std::auto_ptr. (由 Dave Abrahams 提供)

scoped_array: 作用域数组所有权

说明

scoped_array 类模板存储指向动态分配数组的指针. (动态分配的数组通过 C++ new[] 表达式分配. ) 所指向的数组保证会被删除: 或者在 scoped_array 析构时, 或者通过显式调用 reset.

scoped_array 模板是针对简单需求的简单解决方案. 它提供基本的"资源获取即初始化"设施, 不具有共享所有权或所有权转移语义. 其名称以及对语义的强制执行 (通过不可复制) 都表明, 它打算将所有权仅保留在当前作用域内. 由于它不可复制, 对于不应被复制的指针而言, 它比 shared_ptr<T[]> 更安全.

由于 scoped_array 非常简单, 在通常的实现中, 其每个操作的速度都与内置数组指针一样快, 且空间开销不超过内置数组指针.

它不能用于 C++ 标准库容器. 请参见 shared_ptr<T[]>——如果 scoped_array 不能满足你的需求.

它无法正确持有指向单个对象的指针. 该用法请参见 scoped_ptr.

std::vector 是 scoped_array 的替代品, 稍重一些, 但灵活得多. boost::array 则是不使用动态分配的替代方案.

该类模板以 T (即所指向对象的类型) 为参数.

概要

scoped_array 定义于 <boost/smart_ptr/scoped_array.hpp>.

namespace boost {

  template<class T> class scoped_array {
  private:

    scoped_array(scoped_array const &);
    scoped_array & operator=(scoped_array const &);

    void operator==( scoped_array const& ) const;
    void operator!=( scoped_array const& ) const;

  public:

    typedef T element_type;

    explicit scoped_array(T * p = 0) noexcept;
    ~scoped_array() noexcept;

    void reset(T * p = 0) noexcept;

    T & operator[](std::ptrdiff_t i) const noexcept;
    T * get() const noexcept;

    explicit operator bool () const noexcept;

    void swap(scoped_array & b) noexcept;
  };

  template<class T> void swap(scoped_array<T> & a, scoped_array<T> & b) noexcept;

  template<class T>
    bool operator==( scoped_array<T> const & p, std::nullptr_t ) noexcept;
  template<class T>
    bool operator==( std::nullptr_t, scoped_array<T> const & p ) noexcept;

  template<class T>
    bool operator!=( scoped_array<T> const & p, std::nullptr_t ) noexcept;
  template<class T>
    bool operator!=( std::nullptr_t, scoped_array<T> const & p ) noexcept;
}

shared_ptr: 共享所有权

说明

shared_ptr 类模板存储指向动态分配对象的指针, 该对象通常通过 C++ new 表达式分配. 当最后一个指向该对象的 shared_ptr 被销毁或重置时, 所指向的对象保证会被删除.

代码示例 1. 使用 shared_ptr
shared_ptr<X> p1( new X );
shared_ptr<void> p2( new int(5) );

shared_ptr 删除的正是构造时传入的那个指针, 并保留其原始类型, 而与模板参数无关. 在上面的第二个示例中, 当 p2 被销毁或重置时, 它会调用 delete——作用于传入构造函数的那个原始 int*——即使 p2 本身的类型是 shared_ptr<void>, 存储的指针类型是 void*.

每个 shared_ptr 都满足 C++ 标准库的 CopyConstructible、MoveConstructible、CopyAssignable 和 MoveAssignable 要求, 并可用于标准库容器. 库中提供了比较运算符, 使 shared_ptr 可用于标准库的关联容器.

由于实现使用引用计数, shared_ptr 实例构成的环不会被回收. 例如, 如果 main() 持有 shared_ptr (指向 A) , 而后者直接或间接持有 shared_ptr (回指 A) , 那么 A’s use count will be 2. Destruction of the original `shared_ptr 会使 A 悬空, 使用计数为 1. 请使用 weak_ptr 来"打破环".

该类模板以 T (即所指向对象的类型) 为参数. shared_ptr 及其大多数成员函数对 T 不作要求; 它允许是不完整类型, 或为 void. 带有额外要求的成员函数 (构造函数、reset) 在下文有明确说明.

shared_ptr<T> 可隐式转换为 shared_ptr<U>, 只要 T* 可隐式转换为 U*. 特别是, shared_ptr<T> 可隐式转换为 shared_ptr<T const>, 可转换为 shared_ptr<U> (其中 U 是 T 的可访问基类) , 还可转换为 shared_ptr<void>.

shared_ptr 现已作为 std::shared_ptr 成为 C++11 标准的一部分.

从 Boost 1.53 发布版开始, shared_ptr 可用于持有指向动态分配数组的指针. 做法是使用数组类型 (T[] 或 T[N]) 作为模板参数. 使用不带大小的数组 T[] 与带大小的数组 T[N] 几乎没有区别; 后者只是使 operator[] 能够对索引执行范围检查.

代码示例 2. 将 shared_ptr 用于数组
shared_ptr<double[1024]> p1( new double[1024] );
shared_ptr<double[]> p2( new double[n] );

最佳实践

一条几乎可以消除内存泄漏可能性的简单准则是: 始终使用命名的智能指针变量来保存 new 的结果. 代码中每次出现 new 关键字都应采用如下形式:

shared_ptr<T> p(new Y);

当然, 用其他智能指针代替上面的 shared_ptr 也是可以接受的; 让 T 与 Y 为同一类型, 或者向 Y 的构造函数传递实参, 也都可以.

如果遵守这条准则, 自然就不会有显式的 delete 语句; try/catch 结构也会很少见.

请避免为省事而使用未命名的 shared_ptr 临时对象; 想知道为什么这样做危险, 请看这个示例:

代码示例 3. shared_ptr 的异常安全与非异常安全用法
void f(shared_ptr<int>, int);
int g();

void ok()
{
    shared_ptr<int> p( new int(2) );
    f( p, g() );
}

void bad()
{
    f( shared_ptr<int>( new int(2) ), g() );
}

函数 ok 严格遵循该准则, 而 bad 就地构造临时对象 shared_ptr, 从而存在内存泄漏的可能. 由于函数实参的求值顺序是不确定的, new int(2) 可能先求值, g() 后求值; shared_ptr 的构造函数可能永远不会被执行, 只要 g 抛出异常. 更多信息参见 Herb Sutter 对此问题的论述 .

上述异常安全问题也可以通过使用 make_shared 或 allocate_shared 工厂函数 (定义于 <boost/smart_ptr/make_shared.hpp>) 来消除. 这些工厂函数还通过合并分配带来了效率上的好处.

指针构造函数

template<class Y> explicit shared_ptr(Y * p);

  • 要求

    Y 必须是完整类型. 表达式 delete[] p (当 T 是数组类型时) 或 delete p (当 T 不是数组类型时) 必须是良构的、有良好定义的, 且不抛出异常. 当 T 为 U[N] 时, Y(*)[N] 必须可转换为 T*; 当 T 为 U[] 时, Y(*)[] 必须可转换为 T*; 否则, Y* 必须可转换为 T*.

    效果

    当 T 不是数组类型时, 构造一个 shared_ptr, 拥有指针 p; 否则, 构造一个 shared_ptr, 拥有 p 以及一个调用 delete[] p 的未指定类型删除器.

    后置条件

    use_count() == 1 && get() == p. 如果 T 不是数组类型, 并且 p 可无歧义地转换为 enable_shared_from_this<V>* (对某个 V 而言) , 那么 p->shared_from_this() 返回 *this 的副本.

    抛出

    std::bad_alloc; 当无法获得内存以外的资源时, 则抛出由实现定义的异常.

    异常安全

    如果抛出异常, 构造函数会调用 delete[] p (当 T 是数组类型时) , 或调用 delete p (当 T 不是数组类型时) .

注释
 p 必须是指向通过 C++ new 表达式分配的对象的指针, 或为 0. 即使 p 为 0, 使用计数为 1 这一后置条件也成立; 对值为 0 的指针调用 delete 是无害的.
注释
 此构造函数是模板, 以便记住所传入的实际指针类型. 析构函数将使用同一个指针 (保留其原始类型) 调用 delete, 即使 T 没有虚析构函数, 或者它是 void.

  • 要求

    D 必须为 CopyConstructible. D 的复制构造函数和析构函数不得抛出异常. 表达式 d(p) 必须是良构的、有良好定义的, 且不抛出异常. A 必须是 Allocator, 如 C++ 标准的 Allocator Requirements [allocator.requirements] 一节所述. 当 T 为 U[N] 时, Y(*)[N] 必须可转换为 T*; 当 T 为 U[] 时, Y(*)[] 必须可转换为 T*; 否则, Y* 必须可转换为 T*.

    效果

    构造一个 shared_ptr, 拥有指针 p 和删除器 d. 接受分配器 a 的构造函数使用 a 的副本来分配内存.

    后置条件

    use_count() == 1 && get() == p. 如果 T 不是数组类型, 并且 p 可无歧义地转换为 enable_shared_from_this<V>* (对某个 V 而言) , 那么 p->shared_from_this() 返回 *this 的副本.

    如果抛出异常, 则会调用 d(p).

注释
 当需要删除 p 所指向的对象时, 将调用所存储的 d 副本, 并以所存储的 p 副本作为实参.
注释
 自定义释放器使返回 shared_ptr 的工厂函数能够把用户与其内存分配策略隔离开. 由于释放器不是类型的一部分, 改变分配策略不会破坏源代码或二进制兼容性, 也不需要客户端重新编译. 例如, "空操作" (no-op) 释放器在返回指向静态分配对象的 shared_ptr 时很有用; 其他变体则允许将 shared_ptr 用作另一个智能指针的包装器, 从而简化互操作.
注释
 要求 D 的复制构造函数不抛出异常, 这一点源于按值传递. 如果复制构造函数抛出异常, 指针就会泄漏.

线程安全

shared_ptr 对象提供与内置类型相同级别的线程安全. 一个 shared_ptr 实例可以同时被多个线程"读取" (仅使用 const 操作访问) . 不同的 shared_ptr 实例可以同时被多个线程"写入" (使用 operator= 或 reset 等可变操作访问) (即使这些实例是副本, 且在底层共享同一个引用计数) .

任何其他形式的并发访问都会导致未定义行为.

从 Boost 1.33.0 发布版开始, shared_ptr 在大多数常见平台上使用无锁实现.

常见问题

  1. 共享指针有多种变体, 各有不同的权衡; 为什么智能指针库只提供单一实现? 能够对每种类型进行试验以找出最适合当前任务的一种, 应该会很有用?

    shared_ptr 的一个重要目标是提供标准的共享所有权指针. 单一的指针类型对稳定的库接口很重要, 因为不同的共享指针通常无法互操作, 即引用计数指针 (库 A 使用) 无法与链接指针 (库 B 使用) 共享所有权.

  2. 为什么 shared_ptr 没有提供特征 (traits) 或策略 (policy) 之类的模板参数, 以允许用户进行大量定制?

    参数化会让用户望而却步. shared_ptr 模板经过精心设计, 无需大量参数化即可满足常见需求.

  3. 我不信服. 可以在适当的地方使用默认参数来隐藏复杂性. 再说一次, 为什么不用策略?

    模板参数会影响类型. 参见上面对第一个问题的回答.

  4. 为什么 shared_ptr 不使用链表实现?

    链表实现提供的优势不足以抵消额外一个指针带来的开销. 此外, 使链表实现线程安全的代价也很高.

  5. 为什么 shared_ptr (以及其他任何 Boost 智能指针) 不提供到 T* 的自动转换?

    人们认为自动转换太容易出错.

  6. 为什么 shared_ptr 提供 use_count()?

    作为编写测试用例和调试显示的辅助手段. 该功能的一位缔造者拥有 use_count(), 它在一个最终被证明存在循环依赖的复杂项目中帮助定位了缺陷.

  7. 为什么 shared_ptr 不规定复杂度要求?

    因为复杂度要求会限制实现者并使规范复杂化, 而对 shared_ptr 用户没有明显好处. 例如, 如果必须满足严格的复杂度要求, 带错误检查的实现可能就不合规了.

  8. 为什么 shared_ptr 不提供 release() 函数?

    shared_ptr 无法交出所有权, 除非它是 unique(), 因为另一份副本仍会销毁该对象.

    考虑如下情形:

    shared_ptr<int> a(new int);
shared_ptr<int> b(a); // a.use_count() == b.use_count() == 2

int * p = a.release();

// Who owns p now? b will still call delete on it in its destructor.

    此外, release() 返回的指针将难以可靠地释放, 因为源 shared_ptr 可能是用自定义删除器创建的, 或者可能指向不同类型的对象.

  9. 为什么 operator->() 是 const 的, 但其返回值是指向元素类型的非 const 指针?

    浅拷贝指针 (包括裸指针) 通常不传播 const 性. 让它们这样做意义不大, 因为你总能从 const 指针获得非 const 指针, 然后通过它修改对象. shared_ptr 的设计是"尽可能接近裸指针, 但不过分接近".

weak_ptr: 非所有权观察者

说明

weak_ptr 类模板存储对已被 shared_ptr 管理的对象的"弱引用". 要访问该对象, 可以把 weak_ptr 转换为 shared_ptr: 使用 shared_ptr 构造函数 (接受 weak_ptr) , 或 weak_ptr 成员函数 lock. 当最后一个指向该对象的 shared_ptr 消失且对象被删除后, 获得 shared_ptr 的尝试将失败 (从引用已删除对象的 weak_ptr 实例出发) : 构造函数会抛出 boost::bad_weak_ptr 类型的异常, weak_ptr::lock 会返回空的 shared_ptr.

每个 weak_ptr 都满足 C++ 标准库的 CopyConstructible 和 Assignable 要求, 因此可用于标准库容器. 库中提供了比较运算符, 使 weak_ptr 可用于标准库的关联容器.

weak_ptr 操作从不抛出异常.

该类模板以 T (即所指向对象的类型) 为参数.

与 shared_ptr 相比, weak_ptr 只提供非常有限的操作子集, 因为访问其存储的指针在多线程程序中往往很危险, 即使在单线程内有时也不安全 (即可能引发未定义行为) . 不妨假设 weak_ptr 有一个返回裸指针的 get 成员函数, 并考虑这段看似无害的代码:

shared_ptr<int> p(new int(5));
weak_ptr<int> q(p);

// some time later

if(int * r = q.get())
{
    // use *r
}

设想在 if 之后、r 尚未被使用之前, 另一个线程执行了语句 p.reset(). 此时 r 就成了悬空指针.

解决办法是创建一个临时 shared_ptr, 来源为 q:

shared_ptr<int> p(new int(5));
weak_ptr<int> q(p);

// some time later

if(shared_ptr<int> r = q.lock())
{
    // use *r
}

此时 r 持有对 q 原先所指对象的引用. 即使 p.reset() 在另一个线程中执行, 该对象也会保持存活, 直到 r 离开作用域或被重置. 通过获得指向该对象的 shared_ptr, 我们实际上已将其锁定以防销毁.

    不能. weak_ptr 只能从 shared_ptr 创建, 而在对象构造时, 指向该对象的 shared_ptr 尚不存在. 即使你能创建一个临时 shared_ptr 指向 this, 它也会在构造函数结束时离开作用域, 所有 weak_ptr 实例都会立即失效.

    解决办法是把构造函数设为私有, 并提供一个返回 shared_ptr 的工厂函数:

    class X
{
private:

    X();

public:

    static shared_ptr<X> create()
    {
        shared_ptr<X> px(new X);
        // create weak pointers from px here
        return px;
    }
};

make_shared: 创建 shared_ptr

说明

函数模板 make_shared 和 allocate_shared 提供便捷、安全且高效的方式来创建 shared_ptr 对象.

设计理由

始终如一地使用 shared_ptr 可以消除使用显式 delete 的需要, 但仅靠它并不能帮助避免显式 new. 用户曾反复要求提供一个工厂函数, 创建给定类型的对象并返回指向它的 shared_ptr. 除了便利和风格之外, 这样的函数还是异常安全的, 而且快得多, 因为它可以对对象及其对应的控制块使用单次分配, 从而消除了 shared_ptr 构造开销的很大一部分. 这消除了针对 shared_ptr 的主要效率抱怨之一.

重载函数模板族 make_shared 和 allocate_shared 就是为满足这一需求而提供的. make_shared 使用全局的 operator new 来分配内存, 而 allocate_shared 使用用户提供的分配器, 可实现更精细的控制.

选择名称 make_shared 的理由是: 表达式 make_shared<Widget>() 可以朗读出来, 并能传达预期的含义.

最初, Boost 函数模板 allocate_shared 和 make_shared 仅为标量对象提供. 当时需要高效地分配数组对象. 对类模板 shared_array 的一个批评始终是缺少像 make_shared 这样只使用单次分配的工具. 当 shared_ptr 被增强以支持数组类型后, 又为数组类型提供了 allocate_shared 和 make_shared 的额外重载.

概要

make_shared 和 allocate_shared 定义于 <boost/smart_ptr/make_shared.hpp>.

通用要求

下面描述适用于所有 make_shared 和 allocate_shared 重载的通用要求, 除非另有说明.

要求

A 应当是一个分配器. A 的复制构造函数和析构函数不应抛出异常.

效果

为类型为 T 的对象或 n 个 U 对象分配内存 (如果 T 是形如 U[] 的数组类型, 且 n 由实参确定, 具体由对应重载规定) . 对象由实参初始化, 具体方式由对应重载规定. 使用 a 的重绑定副本 (针对某个未指定的 value_type) 分配内存. 如果抛出异常, 这些函数不产生任何效果.

返回

一个 shared_ptr 实例, 存储并拥有新构造对象的地址.

后置条件

r.get() != 0 和 r.use_count() == 1, 其中 r 是返回值.

抛出

std::bad_alloc, 或从 A::allocate 或对象初始化过程中抛出的异常.

备注

  • 至多执行一次内存分配. 这提供了与侵入式智能指针相当的效率.

  • 当数组类型的对象被指定为初始化为同类型的值 v 时, 应将其解释为: 该对象的每个数组元素都初始化为 v 中对应的元素.

  • 当数组类型的对象被指定为值初始化时, 应将其解释为: 该对象的每个数组元素都被值初始化.

  • 当非数组类型 U 的 (子) 对象被指定为初始化为值 v, 或从 args... 构造时, make_shared 应通过表达式 ::new(p) U(expr) 执行该初始化 (其中 expr 分别为 v 或 std::forward<Args>(args)...)) , 且 p 的类型为 void*, 指向适合容纳 U 类型对象的存储.

  • 当非数组类型 U 的 (子) 对象被指定为初始化为值 v, 或从 args... 构造时, allocate_shared 应通过表达式 std::allocator_traits<A2>::construct(a2, p, expr) 执行该初始化 (其中 expr 分别为 v 或 std::forward<Args>(args)...)) , p 指向适合容纳 U 类型对象的存储, 且类型为 a2 的 A2 是 a 的可能重绑定副本.

  • 当非数组类型 U 的 (子) 对象被指定为默认初始化时, make_shared_noinit 和 allocate_shared_noinit 应通过表达式 ::new(p) U 执行该初始化, 其中 p 的类型为 void*, 指向适合容纳 U 类型对象的存储.

  • 当非数组类型 U 的 (子) 对象被指定为值初始化时, make_shared 应通过表达式 ::new(p) U() 执行该初始化, 其中 p 的类型为 void*, 指向适合容纳 U 类型对象的存储.

  • 当非数组类型 U 的 (子) 对象被指定为值初始化时, allocate_shared 应通过表达式 std::allocator_traits<A2>::construct(a2, p) 执行该初始化, 其中 p 指向适合容纳 U 类型对象的存储, 且类型为 a2 的 A2 是 a 的可能重绑定副本.

  • 数组元素按其地址升序初始化.

  • 当返回值所管理对象的生命周期结束, 或某个数组元素的初始化抛出异常时, 已初始化的元素应按其构造的逆序销毁.

注释
 这些函数分配的内存通常会多于元素对象的总大小, 以便容纳引用计数等内部簿记结构.

enable_shared_from_this

说明

类模板 enable_shared_from_this 用作基类, 允许在成员函数内部获得指向当前对象的 shared_ptr 或 weak_ptr.

enable_shared_from_this<T> 定义了两个名为 shared_from_this 的成员函数, 返回 shared_ptr<T> 和 shared_ptr<T const> (取决于常量性) , 指向 this. 它还定义了两个名为 weak_from_this 的成员函数, 返回相应的 weak_ptr.

示例

#include <boost/enable_shared_from_this.hpp>
#include <boost/shared_ptr.hpp>
#include <cassert>

class Y: public boost::enable_shared_from_this<Y>
{
public:

    boost::shared_ptr<Y> f()
    {
        return shared_from_this();
    }
};

int main()
{
    boost::shared_ptr<Y> p(new Y);
    boost::shared_ptr<Y> q = p->f();
    assert(p == q);
    assert(!(p < q || q < p)); // p and q must share ownership
}

make_unique: 创建 unique_ptr

说明

make_unique 函数模板提供便捷且安全的方式来创建 std::unique_ptr 对象.

设计理由

C++11 标准引入了 std::unique_ptr, 但没有提供任何 make_unique 工具——像 std::make_shared 那样提供同样的异常安全性以及避免编写 new 表达式的便利. 在某些标准库厂商实现它之前 (也早于引入 std::make_unique 的 C++14 标准) , 应用户的要求, 本库提供了它.

本库还为默认初始化提供了 make_unique 的额外重载, 供用户不需要或不想承担值初始化开销时使用. C++20 标准现在通过 std::make_unique_for_overwrite 提供了该特性.

说明

allocate_unique 函数模板族提供便捷且安全的方式, 获得一个管理使用分配器创建的新对象的 std::unique_ptr.

  • 数组元素按其地址升序初始化.

  • 当返回值所管理对象的生命周期结束, 或某个数组元素的初始化抛出异常时, 已初始化的元素应按其构造的逆序销毁.

intrusive_ptr: 管理内嵌引用计数的对象

说明

intrusive_ptr 类模板存储指向内嵌引用计数对象的指针. 每个新的 intrusive_ptr 实例都会通过非限定调用函数 intrusive_ptr_add_ref (以指针作为实参) 来递增引用计数. 类似地, 当一个 intrusive_ptr 被销毁时, 它会调用 intrusive_ptr_release; 当引用计数降为零时, 该函数负责销毁对象. 用户应当提供这两个函数的适当定义. 在支持实参依赖查找的编译器上, intrusive_ptr_add_ref 和 intrusive_ptr_release 应定义在其形参对应的命名空间中; 否则, 这些定义需要放在命名空间 boost 中. 本库提供一个辅助基类模板 intrusive_ref_counter, 可帮助为用户类型添加对 intrusive_ptr 的支持.

该类模板以 T (即所指向对象的类型) 为参数. intrusive_ptr<T> 可隐式转换为 intrusive_ptr<U>, 只要 T* 可隐式转换为 U*.

使用 intrusive_ptr 的主要原因有:

  • 一些现有框架或操作系统提供内嵌引用计数的对象;

  • intrusive_ptr 的内存占用与相应的裸指针相同;

  • intrusive_ptr<T> 可以从类型为 T* 的任意裸指针构造.

一般而言, 如果 intrusive_ptr 与 shared_ptr 哪个更适合你的需求并不明显, 请先尝试基于 shared_ptr 的设计.

说明

intrusive_ref_counter 类模板为派生用户类实现引用计数器, 该类预期与 intrusive_ptr 一起使用. 基类关联了 intrusive_ptr_add_ref 和 intrusive_ptr_release 函数, 它们按需修改引用计数器, 并在计数降为零时销毁用户对象.

该类模板以 Derived 和 CounterPolicy 两个参数. 第一个参数是从 intrusive_ref_counter 派生的用户类. 需要该类型是为了在没有引用剩下时正确销毁对象.

第二个参数是定义引用计数器性质的策略. 本库提供两种这样的策略: thread_unsafe_counter 和 thread_safe_counter. 前者指示 intrusive_ref_counter 基类使用只适用于单线程的计数器. 指向使用这种引用计数器的单个对象的指针不得在不同线程中使用. 后者使引用计数器线程安全, 除非目标平台不支持线程. 由于现代系统普遍支持线程, 默认计数策略是 thread_safe_counter.

local_shared_ptr: 单线程内的共享所有权

说明

local_shared_ptr 与 shared_ptr 几乎完全相同, 唯一值得注意的区别是它的引用计数用非原子操作更新. 因此, 一个 local_shared_ptr 及其所有副本必须驻留于 (局部于) 单个线程中 (名称由此而来) .

local_shared_ptr 可以与 shared_ptr 相互转换. local_shared_ptr 若由 shared_ptr 创建, 会产生一个新的局部引用计数; 这意味着两个 local_shared_ptr 实例 (都从同一个 shared_ptr 创建) 指向同一对象但不共享同一计数, 因此可以被两个不同线程安全使用.

代码示例 9. 从 shared_ptr 创建的两个 local_shared_ptr 实例
shared_ptr<X> p1( new X );

local_shared_ptr<X> p2( p1 ); // p2.local_use_count() == 1
local_shared_ptr<X> p3( p1 ); // p3.local_use_count() also 1

然而, 从第一个实例创建第二个 local_shared_ptr, 确实会使两者共享同一计数:

代码示例 10. 从另一个 local_shared_ptr 创建的 local_shared_ptr
shared_ptr<X> p1( new X );

local_shared_ptr<X> p2( p1 ); // p2.local_use_count() == 1
local_shared_ptr<X> p3( p2 ); // p3.local_use_count() == 2

两个 shared_ptr 实例 (从同一个 local_shared_ptr 创建) 确实共享所有权:

代码示例 11. 从 local_shared_ptr 创建的两个 shared_ptr 实例
local_shared_ptr<X> p1( new X );

shared_ptr<X> p2( p1 ); // p2.use_count() == 2
shared_ptr<X> p3( p1 ); // p3.use_count() == 3

这里 p2.use_count() 为 2, 因为 p1 也持有一个引用.

可以把 local_shared_ptr<T> 想象成 shared_ptr<shared_ptr<T>>, 其中外层 shared_ptr 对其计数使用非原子操作. 从 local_shared_ptr 转换为 shared_ptr 会得到内层 shared_ptr 的一个副本; 从 shared_ptr 转换则会把它包装进一个具有非原子使用计数的外层 shared_ptr 中 (从概念上讲) , 并返回结果.

概要

  public:

make_local_shared: 创建 local_shared_ptr

说明

函数模板 make_local_shared 和 allocate_local_shared 提供便捷、安全且高效的方式来创建 local_shared_ptr 对象. 它们类似于 make_shared 和 allocate_shared (用于 shared_ptr) .

概要

make_local_shared 和 allocate_local_shared 定义于 <boost/smart_ptr/make_local_shared.hpp>.

namespace boost {
  // T is not an array
  template<class T, class... Args>
    local_shared_ptr<T> make_local_shared(Args&&... args);
  template<class T, class A, class... Args>
    local_shared_ptr<T> allocate_local_shared(const A& a, Args&&... args);

  // T is an array of unknown bounds
  template<class T>
    local_shared_ptr<T> make_local_shared(std::size_t n);
  template<class T, class A>
    local_shared_ptr<T> allocate_local_shared(const A& a, std::size_t n);

  // T is an array of known bounds
  template<class T>
    local_shared_ptr<T> make_local_shared();
  template<class T, class A>
    local_shared_ptr<T> allocate_local_shared(const A& a);

  // T is an array of unknown bounds
  template<class T>
    local_shared_ptr<T> make_local_shared(std::size_t n,
      const remove_extent_t<T>& v);
  template<class T, class A>
    local_shared_ptr<T> allocate_local_shared(const A& a, std::size_t n,
      const remove_extent_t<T>& v);

  // T is an array of known bounds
  template<class T>
    local_shared_ptr<T> make_local_shared(const remove_extent_t<T>& v);
  template<class T, class A>
    local_shared_ptr<T> allocate_local_shared(const A& a,
      const remove_extent_t<T>& v);

  // T is not an array of known bounds
  template<class T>
    local_shared_ptr<T> make_local_shared_noinit();
  template<class T, class A>
    local_shared_ptr<T> allocate_local_shared_noinit(const A& a);

  // T is an array of unknown bounds
  template<class T>
    local_shared_ptr<T> make_local_shared_noinit(std::size_t n);
  template<class T, class A>
    local_shared_ptr<T> allocate_local_shared_noinit(const A& a,
      std::size_t n);
}

说明

这些函数的要求和效果与 make_shared 和 allocate_shared 相同, 只是返回 local_shared_ptr.

通用指针转换

说明

指针转换函数模板 (static_pointer_cast、dynamic_pointer_cast、const_pointer_cast 和 reinterpret_pointer_cast) 提供了一种为裸指针、std::shared_ptr 和 std::unique_ptr 编写通用指针转换的方式.

测试和示例代码见 pointer_cast_test.cpp

设计理由

Boost 智能指针通常重载这些函数, 以提供模拟指针转换的机制. 例如, shared_ptr<T> 就是这样实现静态指针转换的:

template<class T, class U>
  shared_ptr<T> static_pointer_cast(const shared_ptr<U>& p);

指针转换函数模板是 static_pointer_cast、dynamic_pointer_cast、const_pointer_cast 和 reinterpret_pointer_cast 针对裸指针、std::shared_ptr 和 std::unique_ptr 的重载. 这样, 在开发与指针类型无关的类 (例如内存管理器或共享内存兼容类) 时, 同一代码既可用于裸指针, 也可用于智能指针.

概要

通用指针转换定义于 <boost/pointer_cast.hpp>.

namespace boost {
  template<class T, class U> T* static_pointer_cast(U* p) noexcept;
  template<class T, class U> T* dynamic_pointer_cast(U* p) noexcept;
  template<class T, class U> T* const_pointer_cast(U* p) noexcept;
  template<class T, class U> T* reinterpret_pointer_cast(U* p) noexcept;

  template<class T, class U> std::shared_ptr<T>
    static_pointer_cast(const std::shared_ptr<U>& p) noexcept;
  template<class T, class U> std::shared_ptr<T>
    dynamic_pointer_cast(const std::shared_ptr<U>& p) noexcept;
  template<class T, class U> std::shared_ptr<T>
    const_pointer_cast(const std::shared_ptr<U>& p) noexcept;
  template<class T, class U> std::shared_ptr<T>
    reinterpret_pointer_cast(const std::shared_ptr<U>& p) noexcept;

  template<class T, class U> std::unique_ptr<T>
    static_pointer_cast(std::unique_ptr<U>&& p) noexcept;
  template<class T, class U> std::unique_ptr<T>
    dynamic_pointer_cast(std::unique_ptr<U>&& p) noexcept;
  template<class T, class U> std::unique_ptr<T>
    const_pointer_cast(std::unique_ptr<U>&& p) noexcept;
  template<class T, class U> std::unique_ptr<T>
    reinterpret_pointer_cast(std::unique_ptr<U>&& p) noexcept;
}

使用不完整类隐藏实现

一种经过验证的 (在 C 中也适用) 分离接口与实现的技术, 是使用指向不完整类的指针作为不透明句柄:

class FILE;

FILE * fopen(char const * name, char const * mode);
void fread(FILE * f, void * data, size_t size);
void fclose(FILE * f);

可以用 shared_ptr 表达上述接口, 从而无需手动调用 fclose:

class FILE;

shared_ptr<FILE> fopen(char const * name, char const * mode);
void fread(shared_ptr<FILE> f, void * data, size_t size);

该技术依赖于 shared_ptr 执行自定义删除器的能力 (从而省去对 fclose 的显式调用) , 以及 shared_ptr<X> 在 X 不完整时仍可被复制和销毁这一事实.

"Pimpl" 惯用法

不完整类模式的一个 C++ 特有变体是"Pimpl"惯用法. 不完整类不暴露给用户; 它隐藏在一个转发门面之后. shared_ptr 可用于实现"Pimpl":

// file.hpp:

class file
{
private:

    class impl;
    shared_ptr<impl> pimpl_;

public:

    file(char const * name, char const * mode);

    // compiler generated members are fine and useful

    void read(void * data, size_t size);
};

// file.cpp:

#include "file.hpp"

class file::impl
{
private:

    impl(impl const &);
    impl & operator=(impl const &);

    // private data

public:

    impl(char const * name, char const * mode) { ... }
    ~impl() { ... }
    void read(void * data, size_t size) { ... }
};

file::file(char const * name, char const * mode): pimpl_(new impl(name, mode))
{
}

void file::read(void * data, size_t size)
{
    pimpl_->read(data, size);
}

这里需要注意的关键是: 编译器生成的复制构造函数、赋值运算符和析构函数都有合理的含义. 因此, file 是 CopyConstructible 且 Assignable, 可用于标准容器.

使用抽象类隐藏实现

另一个广泛使用的分离接口与实现的 C++ 惯用法, 是使用抽象基类和工厂函数. 抽象类有时被称为"接口", 该模式被称为"基于接口的编程". 同样, shared_ptr 可以用作工厂函数的返回类型:

// X.hpp:

class X
{
public:

    virtual void f() = 0;
    virtual void g() = 0;

protected:

    ~X() {}
};

shared_ptr<X> createX();

// X.cpp:

class X_impl: public X
{
private:

    X_impl(X_impl const &);
    X_impl & operator=(X_impl const &);

public:

    virtual void f()
    {
      // ...
    }

    virtual void g()
    {
      // ...
    }
};

shared_ptr<X> createX()
{
    shared_ptr<X> px(new X_impl);
    return px;
}

shared_ptr 的一个关键特性是: 分配、构造、释放和销毁的细节都在构造点 (工厂函数内部) 被捕获.

注意上例中受保护且非虚的析构函数. 客户端代码不能、也不需要 delete 指向 X 的指针; shared_ptr<X> 实例 (由 createX 返回) 会正确调用 ~X_impl.

防止 delete px.get()

通常希望防止客户端代码 delete 一个正由 shared_ptr 管理的指针. 前面的技术展示了一种可行方法: 使用受保护的析构函数. 另一种替代方案是使用私有删除器:

class X
{
private:

    ~X();

    class deleter;
    friend class deleter;

    class deleter
    {
    public:

        void operator()(X * p) { delete p; }
    };

public:

    static shared_ptr<X> create()
    {
        shared_ptr<X> px(new X, X::deleter());
        return px;
    }
};

封装分配细节, 包装工厂函数

shared_ptr 可用于在现有 C 风格库接口之上创建 C++ 包装器 (这些接口的工厂函数返回裸指针) , 以封装分配细节. 例如, 考虑这个接口, 其中 CreateX 可能从自己的私有堆分配 X, ~X 可能不可访问, 或者 X 可能不完整:

X * CreateX();
void DestroyX(X *);

可靠销毁 CreateX 返回指针的唯一方式是调用 DestroyX.

下面是基于 shared_ptr 的包装器的可能样子:

shared_ptr<X> createX()
{
    shared_ptr<X> px(CreateX(), DestroyX);
    return px;
}

调用 createX 的客户端代码仍然不需要知道对象是如何分配的, 但现在销毁是自动的.

使用 shared_ptr 持有指向静态分配对象的指针

有时希望为已存在的对象创建 shared_ptr, 使得 shared_ptr 在没有引用剩下时不会尝试销毁该对象. 例如, 工厂函数:

shared_ptr<X> createX();

在某些情况下可能需要返回指向静态分配的 X 实例的指针.

解决办法是使用一个什么也不做的自定义删除器:

struct null_deleter
{
    void operator()(void const *) const
    {
    }
};

static X x;

shared_ptr<X> createX()
{
    shared_ptr<X> px(&x, null_deleter());
    return px;
}

同样的技术适用于任何已知会比指针存续更久的对象.

使用 shared_ptr 持有指向 COM 对象的指针

背景: COM 对象有内嵌的引用计数和两个操作它的成员函数. AddRef() 递增计数. Release() 递减计数, 并在计数降为零时销毁自身.

可以在 shared_ptr 中持有指向 COM 对象的指针:

shared_ptr<IWhatever> make_shared_from_COM(IWhatever * p)
{
    p->AddRef();
    shared_ptr<IWhatever> pw(p, mem_fn(&IWhatever::Release));
    return pw;
}

但请注意, shared_ptr 副本 (从 pw 创建) 不会在 COM 对象的内嵌计数中"注册"; 它们会共享 make_shared_from_COM 中创建的那个单一引用. 从 pw 创建的弱指针会在最后一个 shared_ptr 被销毁时失效, 无论 COM 对象本身是否仍然存活.

如所解释的 (见 mem_fn 文档) , 你需要先 #define BOOST_MEM_FN_ENABLE_STDCALL.

使用 shared_ptr 持有指向内嵌引用计数对象的指针

这是上述技术的推广. 该示例假定对象实现了 intrusive_ptr 所要求的两个函数: intrusive_ptr_add_ref 和 intrusive_ptr_release:

template<class T> struct intrusive_deleter
{
    void operator()(T * p)
    {
        if(p) intrusive_ptr_release(p);
    }
};

shared_ptr<X> make_shared_from_intrusive(X * p)
{
    if(p) intrusive_ptr_add_ref(p);
    shared_ptr<X> px(p, intrusive_deleter<X>());
    return px;
}

使用 shared_ptr 持有另一个共享所有权智能指针

shared_ptr 的设计目标之一是用于库接口. 可能遇到这样的情况: 库接受 shared_ptr 实参, 但手头的对象正由另一种引用计数或链接式智能指针管理.

可以利用 shared_ptr 的自定义删除器特性, 把这个现有智能指针包装在 shared_ptr 门面之后:

template<class P> struct smart_pointer_deleter
{
private:

    P p_;

public:

    smart_pointer_deleter(P const & p): p_(p)
    {
    }

    void operator()(void const *)
    {
        p_.reset();
    }

    P const & get() const
    {
        return p_;
    }
};

shared_ptr<X> make_shared_from_another(another_ptr<X> qx)
{
    shared_ptr<X> px(qx.get(), smart_pointer_deleter< another_ptr<X> >(qx));
    return px;
}

一个微妙之处是删除器不允许抛出异常, 而上面示例的写法假定 p_.reset() 不抛出异常. 如果不是这样, p_.reset(); 应包装在一个忽略异常的 try {} catch(…​) {} 块中. 在 (通常不太可能) 抛出并忽略异常的情况下, p_ 会在删除器的生命周期结束时被释放. 这发生在所有引用 (包括弱指针) 都被销毁或重置之时.

另一个变化是: 给定上面的 shared_ptr 实例, 可以使用 get_deleter 恢复原来的智能指针:

void extract_another_from_shared(shared_ptr<X> px)
{
    typedef smart_pointer_deleter< another_ptr<X> > deleter;

    if(deleter const * pd = get_deleter<deleter>(px))
    {
        another_ptr<X> qx = pd->get();
    }
    else
    {
        // not one of ours
    }
}

从裸指针获得 shared_ptr

有时需要在给定裸指针的情况下获得 shared_ptr, 而该对象已被另一个 shared_ptr 实例管理. 示例:

void f(X * p)
{
    shared_ptr<X> px(???);
}

在 f 内部, 我们想创建一个 shared_ptr, 指向 *p.

一般情况下, 这个问题无解. 一种方法是把 f 改为接受 shared_ptr (如果可能的话) :

void f(shared_ptr<X> px);

同样的转换也可用于非虚成员函数, 把隐式的 this:

void X::f(int m);

将变成一个以 shared_ptr 为第一个实参的自由函数:

void f(shared_ptr<X> this_, int m);

如果 f 不能修改, 但 X 使用侵入式计数, 请使用上文所述的 make_shared_from_intrusive. 或者, 如果已知 shared_ptr (在 f 中创建) 不会比对象存续更久, 请使用空删除器.

在构造函数中获得指向 this 的 shared_ptr (weak_ptr)

有些设计要求对象在构造时向中央机构注册自己. 当注册例程接受 shared_ptr 时, 就会引出这样的问题: 构造函数如何能获得 shared_ptr (指向 this) :

class X
{
public:

    X()
    {
        shared_ptr<X> this_(???);
    }
};

一般情况下, 该问题无法解决. 正在构造的 X 实例可以是自动变量或静态变量; 也可以在堆上创建:

shared_ptr<X> px(new X);

但在构造时, px 尚不存在, 因而不可能创建另一个与之共享所有权的 shared_ptr 实例.

视上下文而定, 如果内层 shared_ptr this_ 不需要让对象保持存活, 请使用 null_deleter, 如此处和此处所解释. 如果 X 应当始终位于堆上并由 shared_ptr 管理, 请使用静态工厂函数:

class X
{
private:

    X() { ... }

public:

    static shared_ptr<X> create()
    {
        shared_ptr<X> px(new X);
        // use px as 'this_'
        return px;
    }
};

获得指向 this 的 shared_ptr

有时需要在虚成员函数中获取 shared_ptr——从 this 出发, 并假定 this 已由某个 shared_ptr 管理. 前一技术中描述的转换无法应用.

一个典型示例:

class X
{
public:

    virtual void f() = 0;

protected:

    ~X() {}
};

class Y
{
public:

    virtual shared_ptr<X> getX() = 0;

protected:

    ~Y() {}
};

// --

class impl: public X, public Y
{
public:

    impl() { ... }

    virtual void f() { ... }

    virtual shared_ptr<X> getX()
    {
        shared_ptr<X> px(???);
        return px;
    }
};

解决办法是保存一个指向 this 的弱指针, 作为 impl 中的成员:

class impl: public X, public Y
{
private:

    weak_ptr<impl> weak_this;

    impl(impl const &);
    impl & operator=(impl const &);

    impl() { ... }

public:

    static shared_ptr<impl> create()
    {
        shared_ptr<impl> pi(new impl);
        pi->weak_this = pi;
        return pi;
    }

    virtual void f() { ... }

    virtual shared_ptr<X> getX()
    {
        shared_ptr<X> px(weak_this);
        return px;
    }
};

本库现在包含一个辅助类模板 enable_shared_from_this, 可用于封装该解决方案:

class impl: public X, public Y, public enable_shared_from_this<impl>
{
public:

    impl(impl const &);
    impl & operator=(impl const &);

public:

    virtual void f() { ... }

    virtual shared_ptr<X> getX()
    {
        return shared_from_this();
    }
}

注意, 你不再需要手动初始化 weak_ptr 成员 (位于 enable_shared_from_this 中) . 构造一个 shared_ptr (指向 impl) 会处理好这件事.

将 shared_ptr 用作智能计数句柄

一些库接口使用不透明句柄, 是上文所述不完整类技术的一个变体. 示例:

typedef void * HANDLE;

HANDLE CreateProcess();
void CloseHandle(HANDLE);

可以不使用裸指针, 而用 shared_ptr 作为句柄, 免费获得引用计数和自动资源管理:

typedef shared_ptr<void> handle;

handle createProcess()
{
    shared_ptr<void> pv(CreateProcess(), CloseHandle);
    return pv;
}

使用 shared_ptr 在代码块退出时执行代码

shared_ptr<void> 可以在控制流离开作用域时自动执行清理代码.

  • 执行 f(p), 其中 p 是一个指针:

    shared_ptr<void> guard(p, f);

  • 执行任意代码: f(x, y):

    shared_ptr<void> guard(static_cast<void*>(0), bind(f, x, y));

使用 shared_ptr<void> 持有任意对象

shared_ptr<void> 可以充当类似 void* 的通用对象指针. 当按如下方式构造的 shared_ptr<void> 实例:

shared_ptr<void> pv(new X);

被销毁时, 它会正确处置 X 对象——通过执行 ~X.

该特性可以以与裸 void* 大致相同的方式使用: 暂时剥离对象指针的类型信息. shared_ptr<void> 之后可以使用 static_pointer_cast 转换回正确的类型.

将任意数据与异构 shared_ptr 实例关联

shared_ptr 和 weak_ptr 支持 operator< 比较 (std::map 等标准关联容器所需) . 这可以用来以非侵入方式将任意数据与 shared_ptr 管理的对象关联:

typedef int Data;

std::map<shared_ptr<void>, Data> userData;
// or std::map<weak_ptr<void>, Data> userData; to not affect the lifetime

shared_ptr<X> px(new X);
shared_ptr<int> pi(new int(3));

userData[px] = 42;
userData[pi] = 91;

使用 shared_ptr 作为 CopyConstructible 互斥锁

有时需要从函数返回互斥锁, 而不可复制的锁无法按值返回. 可以使用 shared_ptr 作为互斥锁:

class mutex
{
public:

    void lock();
    void unlock();
};

shared_ptr<mutex> lock(mutex & m)
{
    m.lock();
    return shared_ptr<mutex>(&m, mem_fn(&mutex::unlock));
}

更好的做法是, 把充当锁的 shared_ptr 实例封装在一个专用的 shared_lock 类中:

class shared_lock
{
private:

    shared_ptr<void> pv;

public:

    template<class Mutex> explicit shared_lock(Mutex & m): pv((m.lock(), &m), mem_fn(&Mutex::unlock)) {}
};

shared_lock 现在可以这样使用:

shared_lock lock(m);

注意, shared_lock 并没有以互斥类型为模板参数, 这要归功于 shared_ptr<void> 隐藏类型信息的能力.

使用 shared_ptr 包装成员函数调用

shared_ptr 实现了 Wrap/CallProxy 方案所需的所有权语义, 该方案在 Bjarne Stroustrup 的文章"Wrapping C++ Member Function Calls" (在线可见于 http://www.stroustrup.com/wrapper.pdf ) 中描述. 下面给出一个实现:

template<class T> class pointer
{
private:

    T * p_;

public:

    explicit pointer(T * p): p_(p)
    {
    }

    shared_ptr<T> operator->() const
    {
        p_->prefix();
        return shared_ptr<T>(p_, mem_fn(&T::suffix));
    }
};

class X
{
private:

    void prefix();
    void suffix();
    friend class pointer<X>;

public:

    void f();
    void g();
};

int main()
{
    X x;

    pointer<X> px(&x);

    px->f();
    px->g();
}

延迟释放

在某些情况下, 单个 px.reset() 可能会在性能关键区域触发一次昂贵的释放操作:

class X; // ~X is expensive

class Y
{
    shared_ptr<X> px;

public:

    void f()
    {
        px.reset();
    }
};

解决办法是推迟潜在的释放: 把 px 移入一个专用空闲列表, 在性能和响应时间不成问题的时机周期性地清空它:

vector< shared_ptr<void> > free_list;

class Y
{
    shared_ptr<X> px;

public:

    void f()
    {
        free_list.push_back(px);
        px.reset();
    }
};

// periodically invoke free_list.clear() when convenient

另一种变体是使用延迟删除器把空闲列表逻辑移到构造点:

struct delayed_deleter
{
    template<class T> void operator()(T * p)
    {
        try
        {
            shared_ptr<void> pv(p);
            free_list.push_back(pv);
        }
        catch(...)
        {
        }
    }
};

指向不受 shared_ptr 管理的对象的弱指针

让对象持有一个指向自身的 shared_ptr, 使用 null_deleter:

class X
{
private:

    shared_ptr<X> this_;
    int i_;

public:

    explicit X(int i): this_(this, null_deleter()), i_(i)
    {
    }

    // repeat in all constructors (including the copy constructor!)

    X(X const & rhs): this_(this, null_deleter()), i_(rhs.i_)
    {
    }

    // do not forget to not assign this_ in the copy assignment

    X & operator=(X const & rhs)
    {
        i_ = rhs.i_;
    }

    weak_ptr<X> get_weak_ptr() const { return this_; }
};

当对象生命周期结束时, X::this_ 会被销毁, 所有弱指针都会自动失效.

附录 B: 历史与致谢

1994 年夏

Greg Colvin 向 C++ 标准委员会提议了名为 auto_ptr 和 counted_ptr 的类, 它们与我们如今所称的 scoped_ptr 和 shared_ptr 非常相似. 在库工作组建议极少几次未被全体委员会采纳的情形之一中, counted_ptr 被否决, 且令人意外的所有权转移语义被加进了 auto_ptr.

1998 年 10 月

Beman Dawes 提议以 safe_ptr 和 counted_ptr 之名恢复原始语义, 出席会议的有 Per Andersson, Matt Austern, Greg Colvin, Sean Corfield, Pete Becker, Nico Josuttis, Dietmar Kühl, Nathan Myers, Chichiang Wan 和 Judy Ward. 讨论期间, 四个新类名被确定下来, 与会者决定无需严格遵循 std::auto_ptr 接口, 各种函数签名和语义也得以敲定.

在接下来的三个月里, 为 shared_ptr 考虑了几种实现, 并在 boost.org 邮件列表上讨论. 实现问题围绕必须保存的引用计数展开: 要么附着在被指向对象上, 要么分离存放在别处. 这些变体各自又各有两个主要变体:

  • 直接分离式: shared_ptr 包含一个指向对象的指针和一个指向计数的指针.

  • 间接分离式: shared_ptr 包含一个指向辅助对象的指针, 而该辅助对象又包含指向对象和计数的指针.

  • 内嵌附着式: 计数是被指向对象的成员.

  • 定位附着式: 计数通过 operator new 操作附着.

每种实现技术各有优劣. 我们甚至对直接和间接两种方法进行了各种计时测试, 发现至少在 Intel Pentium 芯片上几乎没有可测量的差异. Kevlin Henney 提供了他撰写的一篇关于"Counted Body Techniques"的论文. Dietmar Kühl 提出了一种优雅的偏特化技术, 允许用户选择自己偏好的实现, 我们也对此进行了试验.

但 Greg Colvin 和 Jerry Schwarz 认为"参数化会让用户望而却步", 最终我们选择只提供直接实现.

1999 年 4 月和 5 月, Valentin Bonnard 和 David Abrahams 提出了许多建议, 带来了大量改进.

1999 年 9 月

Luis Coelho 提供了 shared_ptr::swap 和 shared_array::swap.

1999 年 11 月

Darin Adler 提供了 operator ==、operator !=, 以及 std::swap 和 std::less 针对 shared 类型的特化.

2001 年 5 月

Vladimir Prus 建议要求在销毁时类型必须是完整的. 相关细化在包括 Dave Abrahams, Greg Colvin, Beman Dawes, Rainer Deyke, Peter Dimov, John Maddock, Vladimir Prus, Shankar Sai 等人的讨论中逐步成形.

2002 年 1 月

Peter Dimov 重构了全部四个类, 增加特性、修复缺陷、把它们拆分为四个独立的头文件, 并添加了 weak_ptr.

Peter Dimov 和 Glen Fernandes 分别更新了标量和数组实现, 以解决 C++ 标准库缺陷 2070.

附录 C: shared_array (已弃用)

注释
 该设施已弃用, 因为 shared_ptr (指向 T[] 或 T[N]) 现已可用, 且各方面都更优越.

说明

shared_array 类模板存储指向动态分配数组的指针. (动态分配的数组通过 C++ new[] 表达式分配. ) 当最后一个指向它的 shared_array 被销毁或重置时, 所指向的对象保证会被删除.

每个 shared_array 都满足 C++ 标准库的 CopyConstructible 和 Assignable 要求, 因此可用于标准库容器. 库中提供了比较运算符, 使 shared_array 可用于标准库的关联容器.

通常, shared_array 无法正确持有用 new 的非数组形式分配的对象的指针. 该用法请参见 shared_ptr.

由于实现使用引用计数, shared_array 实例构成的环不会被回收. 例如, 如果 main 持有一个指向 A 的 shared_array, 而后者直接或间接持有回指 A 的 shared_array, 那么 A 的使用计数将是 2. 原始 shared_array 的销毁会使 A 悬空, 使用计数为 1.

shared_ptr (指向 std::vector) 是 shared_array 的替代品, 稍重一些, 但灵活得多.

该类模板以 T (即所指向对象的类型) 为参数. shared_array 及其大多数成员函数对 T 不作要求; 它允许是不完整类型, 或为 void. 带有额外要求的成员函数 (构造函数、reset) 在下文有明确说明.

概要

namespace boost {

  template<class T> class shared_array {
  public:
    typedef T element_type;

    explicit shared_array(T* p = 0);
    template<class D> shared_array(T* p, D d);
    shared_array(const shared_array& v) noexcept;

    ~shared_array() noexcept;

    shared_array& operator=(const shared_array& v) noexcept;

    void reset(T* p = 0);
    template<class D> void reset(T* p, D d);

    T& operator[](std::ptrdiff_t n) const noexcept;
    T* get() const noexcept;

    bool unique() const noexcept;
    long use_count() const noexcept;

    explicit operator bool() const noexcept;

    void swap(shared_array<T>& v) noexcept;
  };

  template<class T> bool
    operator==(const shared_array<T>& a, const shared_array<T>& b) noexcept;
  template<class T> bool
    operator!=(const shared_array<T>& a, const shared_array<T>& b) noexcept;
  template<class T> bool
    operator<(const shared_array<T>& a, const shared_array<T>& b) noexcept;

  template<class T>
    void swap(shared_array<T>& a, shared_array<T>& b) noexcept;
}
