用户接口签名

为满足用户要求, 第一次尝试可能产生如下相当常规的接口:

template<typename Out, typename In> Out  convert (In const&); //#1
template<typename Out, typename In> Out  convert (In const&, Out const& fallback); //#2
template<typename Out, typename In> bool convert (Out& result_out, In const&); //#3
template<typename Out, typename In> bool convert (Out& result_out, In const&, Out const& fallback); //#4

其行为如下:

  1. 返回结果, 失败时抛出异常 (R3a, R4);
  2. 不抛异常, 返回结果或所提供的回退值 (R3b, R5, R5c, 但不满足 R5a);
  3. 不抛异常, (成功时) 把结果写入 result_out, 返回成功或失败的指示 (R3b, R5, R5a, 但不满足 R5c);
  4. 不抛异常, (成功时) 把结果写入 result_out 或写入所提供的回退值, 返回成功或失败的指示 (R3b, R5, R5c 与 R5a).

#3 与 #4 签名比较特殊, 因为它们实际上返回两样东西——实际结果 (写入 result_out) 和成功或失败的指示 (由函数返回). 鉴于传入了指向 result_out 的引用, 实际的 result_out 实例在函数调用之外构造 (分配并初始化存储).

类似 转换器签名一节所述的场景, 这会导致额外且不必要的开销. 的确, 若转换操作成功, 初始化值会被覆盖 (为实际结果); 若失败, 该值要么仍被覆盖 (为回退值), 要么毫无意义.

为避免该开销, 我们可以再次 (如 转换器签名一节) 部署 boost::optional 并把签名改为

bool convert (boost::optional<Out>&, In const&); //#3
bool convert (boost::optional<Out>&, In const&, Out const&); //#4

现在看 #3, 可以发现成功或失败的指示是重复的. 即, 它既从函数返回, 又封装在 boost::optional<Out> 中. 因此 #3 可以进一步简化为

void convert (boost::optional<Out>&, In const&); //#3

或用 (C++ 中) 更符合习惯的方式表达为:

boost::optional<Out> convert (In const&); //#3

到目前为止, 我们得到了以下集合

Out                  convert (In const&); //#1
Out                  convert (In const&, Out const&); //#2
boost::optional<Out> convert (In const&); //#3
bool                 convert (boost::optional<Out>&, In const&, Out const&); //#4

整体看起来相当难看, 而且实际上甚至无法编译, 因为 #1 与 #3 冲突. 不过好消息是, 功能上 已不再需要 #1 和 #2, 因为它们是以下 #3 部署的重复:

Out out1 = boost::convert(in).value(); // #3 with #1 behavior
Out out2 = boost::convert(in).value_or(fallback); // #3 with #2 behavior

再说一遍, 我们不是在讨论接口的美学方面 (或者有人会说, 语法糖——这可能非常主观). 相反, 我们关注的是 功能完备性, 到目前为止我们设法以 更少 维持了同样的 功能完备性.

事实证明, 稍加努力, 我们也可以不用最复杂的那一个——#4:

boost::optional<Out> out = boost::convert(in);
bool         out_success = out ? true : false;
Out            out_value = out.value_or(fallback);

于是, 我们最终得到独一无二的一个

boost::optional<Out> convert(In const&);

该 API 的重要特质是: 它是 功能完备 的, 并且是部署所选转换器签名的 最高效方式 (见 转换器签名一节). 即, 当按如下方式部署时, boost::convert() 接口通常会被优化掉 (省略):

boost::optional<Out> out = boost::convert(in);

该 API 有若干与部署相关的优点. 首先, 它确切地说明自己做什么. 鉴于转换请求只是一个 请求, 该 API 返回 boost::optional, 实际上是在说 "我会尝试, 但可能会失败. 请自行酌情处理.". 诚实而简单. 相比 "我会尝试. 我可能会失败, 但你不会想知道." 或 "我会尝试. 若我失败, 你就完了." 以及诸如此类的变体, 我更喜欢它. :-)

更认真地说, 该接口允许批量传送带式的转换. 即, 按顺序尝试转换若干值, 存储 boost::optional 结果, 然后以某种半自动的方式分析/验证它们 (不丢失各次单独转换是否成功的信息).

再说一遍, 该 API 不必是 Boost.Convert 提供的唯一 API. 然而, 该 API 是唯一 本质性 的 API. 其他 API 可以相对容易地从它派生. 例如,

template<typename Out, typename In>
Out
convert(In const& in, Out const& fallback) //#2
{
   return convert(in).value_or(fallback);
}

鉴于想出一个能让所有人都满意的库 API 极其困难 (若非不可能), 我们不妨定格在 本质性 API 上, 让用户构建他们自己的 API (如上例) 来满足其美学偏好.

尽管如此, 需要承认 boost::optional 是一个相当新的概念, 有些人不愿使用它, 或觉得其部署不必要地复杂化. 因此, Boost.Convert 提供了一个替代 (更常规) 的接口:

Out convert(In const&, Converter const&, Out const& fallback_value);
Out convert(In const&, Converter const&, Functor const& fallback_functor);
Out convert(In const&, Converter const&, boost::throw_on_failure);
