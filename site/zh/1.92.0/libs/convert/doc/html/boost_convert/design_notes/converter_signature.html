转换器签名

考虑过以下转换器签名:

bool operator()(TypeIn const&, TypeOut&); //#1
void operator()(TypeIn const&, boost::optional<TypeOut>&); //#2
boost::optional<TypeOut> operator()(TypeIn const&); //#3

从设计角度看, 签名 #1 的优点是提供了最佳的 关注点分离. 即, 它让相应的转换器只承担一个任务——实际转换任务. 不过在实践中, 这可能导致不必要的性能开销. 即, 由于从外部提供了 TypeOut 类型的实例, 需要为该实例分配存储, 而最重要的是初始化它. 该初始化阶段 (可能开销很大) 是不必要的开销: 若转换操作成功, 初始值会被实际结果覆盖; 若失败, TypeOut 实例的值要么毫无意义, 要么更具误导性.

签名 #2 通过部署 boost::optional 不初始化而分配存储 的能力来避免初始化开销. 此时 TypeOut 的存储仍在 (函数) 外部分配, 但不被初始化. 现在, 知道 如何 初始化 TypeOut 实例, 并在 需要时 真正初始化它, 就是转换器的责任. 在实践中, 这通常比听起来容易. 例如, 基于 strtol() 的转换器可能会有类似如下的代码:

void operator()(char const* str_in, boost::optional<int>& result_out) const
{
   char const* str_end = str_in + strlen(str_in);
   char*       cnv_end = 0;
   long int     result = ::strtol(str_in, &cnv_end, base_);

   if (INT_MIN <= result && result <= INT_MAX && cnv_end == str_end)
       result_out = int(result);
}

签名 #3 因美学优势、更符合习惯用法而被简要考虑过. 遗憾的是, 它缺少 TypeOut 的自动推导, 因而必须显式指定之. 对于不同类型的受支持转换器 (基于类的、普通老式函数、lambda), 这会显著复杂化 Boost.Convert 基础设施的实现, 并限制相应转换器的实现.
