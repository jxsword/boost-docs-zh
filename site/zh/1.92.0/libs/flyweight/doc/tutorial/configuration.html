Boost.Flyweight 的可配置方面

多数时候, flyweight 的默认配置已经足够好, 用户无需进一步调整其 flyweight 实例化; 然而, 当需要对 Boost.Flyweight 行为施加更多控制时, 库提供了全面的机制来选择、配置甚至扩展以下实现方面:

  • 类型标签.
  • 工厂, 用于存储 flyweight 对象所引用的共享值.
  • 实例化机制, 即享元工厂的实例化方式.
  • 多线程环境中访问内部工厂的内部同步机制.
  • 跟踪策略, 控制当与工厂中存储的值相关联的所有享元对象都被销毁时如何处理该值.

自由顺序模板参数接口

flyweight 类模板具有一种 "智能" 的指定接口, 配置方面可以作为可选模板实参以用户喜欢的任意顺序提供. 例如, 一个带标签的 flyweight (值为 std::string)、使用基于 set 的工厂和无跟踪可以这样指定:

flyweight<std::string, tag<label_t>,  set_factory<>, no_tracking   >

或者这样:

flyweight<std::string, no_tracking,   tag<label_t>,  set_factory<> >

或以任何其他顺序; 只有 std::string 要求占据指定中的第一位.

头文件包含

引言一节中的示例代码使用了 "boost/flyweight.hpp" 便利头文件, 它只包含类模板 flyweight 及其默认配置组件的头文件:

#include <boost/flyweight/flyweight.hpp>      // class template flyweight
#include <boost/flyweight/hashed_factory.hpp> // hashed flyweight factory
#include <boost/flyweight/static_holder.hpp>  // regular factory instantiation
#include <boost/flyweight/simple_locking.hpp> // simple locking policy
#include <boost/flyweight/refcounted.hpp>     // refcounting tracking policy

使用这些以外的组件时, 必须显式包含它们各自的头文件.

打标签

考虑以下两个类型:

typedef flyweight<std::string> name_t;
typedef flyweight<std::string> ip_address_t;

虽然从技术上讲这两个类型完全相同, 但这只是巧合, 因为名称与 IP 地址之间没有合理的关联. 在内部, name_t 和 ip_address_t 是同一个享元类型这一事实导致两个类的值被一起存储在同一个享元工厂中, 尽管它们各自的取值范围预计不会重叠.打标签可用于把它们变成真正不同的类型:

struct name_tag{};
typedef flyweight<std::string,tag<name_tag> > name_t;

struct ip_address_tag{};
typedef flyweight<std::string,tag<ip_address_tag> > ip_address_t;

现在, name_t 和 ip_address_t 是不同的享元类, 各自拥有独立的工厂. 标签是一种纯粹的语法构件: 在 tag 构造中可以使用任何类型来打标签, 不过良好的风格建议使用名称具有描述性且局部于定义享元类型所在上下文的标签类.

工厂指定

flyweight 使用一种称为工厂的内部组件类型, 其用途是存储和取回享元对象在给定时刻所引用的不同值. 默认使用基于哈希容器的工厂, 因此 flyweight<T> 实际上等价于

flyweight<T,hashed_factory<> >

其中 hashed_factory 是一个所谓的工厂指定器. Boost.Flyweight 提供了若干预定义的工厂指定器, 它们不仅让用户选择所使用的具体工厂类型, 还接受各自的模板实参来定制每个工厂.

工厂配置涉及的类型

一个给定的 flyweight 实例化关联有 flyweight::key_type 和 flyweight::value_type 类型 (对于常规享元两者相等, 若使用键值享元则不同). 此外还有一个内部 Entry 类型, 对应于实际存储在工厂中的对象的类型: Entry 包含 value_type 对象 (其类型为 flyweight) 的共享实例以及一些内部簿记信息; 而且 Entry 可隐式转换为 const key_type&, 因此工厂可以依靠 key_type 来查找 Entrie. 由于 Entry 是 flyweight 实现的内部细节, 用户无法在配置工厂时直接引用它. 作为替代, 可以使用代理占位符类型 boost::mpl::_1.

hashed_factory

头文件: "boost/flyweight/hashed_factory.hpp"
语法: hashed_factory<[Hash[,Pred[,Allocator]]]>

该指定器是 Boost.Flyweight 的默认选择, 控制内部基于哈希容器的工厂的使用. 值的等价性通过 BinaryPredicate Pred 判定, 并使用 Hash 索引到工厂容器中; 该实参被假定为一个Hash 函数对象, 适用于 Key 类型的实参. Allocator 参数由工厂容器用于其内存分配需求. 这些参数的默认类型使得表达式

flyweight<T,hashed_factory<> >

等价于

flyweight<
  T,
  hashed_factory<
    boost::hash<key_value>,
    std::equal_to<key_value>,
    std::allocator<boost::mpl::_1>
  >
>

其中 key_type 是享元的键类型, 而 boost::mpl::_1 如上文所解释, 表示工厂中所存元素的内部 Entry 类型. 假设我们想配置 hashed_factory, 用于 std::string 享元, 使用特殊的哈希谓词 special_hash 和自定义分配器 custom_allocator; 可按如下方式指定:

flyweight<
  std::string,
  hashed_factory<
    special_hash<std::string>,
    std::equal_to<key_value>,
    custom_allocator<boost::mpl::_1>
  >
>

concurrent_factory

头文件: "boost/flyweight/concurrent_factory.hpp"
语法: concurrent_factory<[Hash[,Pred[,Allocator]]]>

该指定器提供基于 Boost.Unordered 并发容器的工厂. 该工厂特别适合多线程场景下的享元创建, 因为它不需要外部同步或跟踪; 因此通常应与 no_locking 和 no_tracking 配合使用:

typedef flyweight<
  std::string,
  concurrent_factory<>,
  no_locking,
  no_tracking
> concurrent_string_flyweight;

不再被使用 (即不再被任何享元引用) 的值, 会由内置的垃圾收集器从工厂中周期性地擦除.

concurrent_factory 参数的默认类型使得表达式

flyweight<T,concurrent_factory<> >

等价于

flyweight<
  T,
  concurrent_factory<
    boost::hash<key_value>,
    std::equal_to<key_value>,
    std::allocator<boost::mpl::_1>
  >
>

与 hashed_factory 中的含义相同.

set_factory

头文件: "boost/flyweight/set_factory.hpp"
语法: set_factory<[Compare[,Allocator]]>

set_factory 借助一个类似 std::set 的有序容器来实现享元工厂. Compare 必须是一个BinaryPredicate, 在 flyweight 所作用的值类型上诱导一个严格弱序; 按照 STL 有序容器的惯例, 若两个值根据 Pred 互不小于, 则视为等价. Allocator 是传递给工厂内部容器、用于内存相关任务的分配器类型. 使用默认参数时, 表达式

flyweight<T,set_factory<> >

等价于

flyweight<
  T,
  set_factory<std::less<key_type>,std::allocator<boost::mpl::_1> >
>

在有序容器与哈希容器的比较中出现的常见权衡, 同样适用于在 set_factory 和 hashed_factory 之间做选择: 基于 set 的值查找和插入通常比基于哈希的慢, 但后者可能受到病态最坏情形的影响, 性能极差.

assoc_container_factory

头文件: "boost/flyweight/assoc_container_factory.hpp"
语法: assoc_container_factory<ContainerSpecifier>

该指定器可以看作 hashed_factory 和 set_factory 的推广, 用户在其中提供工厂所基于容器的确切类型. 对不熟悉Boost MPL Library的人来说, 指定容器的方式起初可能有点令人生畏: ContainerSpecifier 必须是一个MPL Lambda Expression, 当以 Entry 和 key_type 类型调用时 — 如前文所解释 — 它产生满足以下要求的 Entry 元素容器类型:

  1. 容器类型必须是AssociativeContainer或UnorderedAssociativeContainer (带唯一键) 的模型, 其中 Entry 的等价性由条目可转换到的 key_type 值决定.
  2. 容器必须是稳定的, 即其迭代器在插入和擦除操作后必须保持有效. 注意, 许多现有的哈希容器实现不满足这一条件, 它们会在再哈希操作时使迭代器失效.

让我们通过一个例子看看容器指定器是什么样子. 假设我们有如下自定义的有序容器:

template<
  typename Elem,
  typename Compare=std::less<Elem>,
  typename Allocator=std::allocator<Elem>
>
class ultrafast_set
{
  ...
};

于是 ultrafast_set 可以像这样接入 assoc_container_factory:

typedef flyweight<
  std::string,
  assoc_container_factory<
    // MPL lambda expression follows
    ultrafast_set<mpl::_1,std::less<std::string> >
  >
> flyweight_string;

如前所述, mpl::_1 是所谓的 MPL 占位符, 它充当一个 "槽位", 由 Boost.Flyweight 的内部机制替换为 Entry. 注意, 我们没有依赖 ultrafast_set 的默认实参 (针对 Compare), 而是为 std::string 提供了一个固定的实例化: 这是因为要求规定, ContainerSpecifier 内部将被填充的类型必须可转换为 const key_type& (此处为 const std::string&), 并且条目的查找与等价性应基于 key_type 来确定. 另一方面, Allocator 参数的默认实参工作良好, 若显式写出会更明显:

typedef flyweight<
  std::string,
  assoc_container_factory<
    ultrafast_set<
      mpl::_1,
      std::less<std::string>,
      std::allocator<mpl::_1>
    >
  >
> flyweight_string;

持有器指定

每个享元类型 — 即类模板 flyweight 的每个不同实例化 — 都恰好与一个工厂对象相关联. 在大多数情况下, 该工厂对象如何创建对 Boost.Flyweight 的用户无关紧要, 但存在需要控制这一方面的特殊情况. 一个称为持有器的内部组件负责实例化工厂类和其他一些内部信息; 该组件通过持有器指定器来规定, static_holder 是默认的那个.

static_holder

头文件: "boost/flyweight/static_holder.hpp"
语法: static_holder

这是 Boost.Flyweight 的默认持有器指定器, 它产生的持有器中, 唯一的工厂以程序局部静态变量的形式存在.

intermodule_holder

头文件: "boost/flyweight/intermodule_holder.hpp"
语法: intermodule_holder

在大多数 C++ 环境中, 静态变量与动态加载模块配合不佳, 表现为同一个静态变量的实例可能在不同模块间出现多份, 尽管按定义该变量应当唯一. 在许多情况下, 如果模块之间不使用受影响的类型互相通信, 这种重复不会被察觉; 但考虑一下确实发生这种通信的情形:

// module 1

typedef flyweight<std::string> flyweight_string;

// produce_string is exported so that it can be dynamically
// linked

flyweight_string produce_string()
{
  return flyweight_string("boost");
}

// main program

typedef flyweight<std::string> flyweight_string;

int main()
{
  ... // import module 1

  flyweight_string str1=produce_string();
  flyweight_string str2("boost");
  assert(str1==str2);
}

在许多环境中, 该程序会导致断言失败, 因为模块 1 内所见 flyweight_string 使用的享元工厂对象与主程序内所见的不是同一个工厂对象: 因此 str1 和 str2 内部指向的值表示将不同, 并会被误判为不相等. 工厂重复还可能引发许多其他问题, 包括未定义行为.

intermodule_holder 指定一种工厂持有器, 它能够避免重复问题, 并确保程序的所有模块使用同一个工厂实例. 要修复上例, 只需在两个模块中都把 flyweight_string 重新定义为:

typedef flyweight<std::string,intermodule_holder> flyweight_string;

就编译时间而言, intermodule_holder 比 static_holder 昂贵得多, 并且在程序启动时引入不可忽视的开销, 因此应只在真正必要时使用它.

锁定策略

与每个 flyweight 类型关联的内部工厂是一个共享资源, 因此在多线程环境中对它的访问必须恰当地同步. 一个锁定策略规定为此目的要使用的同步机制.

simple_locking

头文件: "boost/flyweight/simple_locking.hpp"
语法: simple_locking

这是默认的锁定策略. 只要可用, 它就指定操作系统提供的最简单的原生同步原语.

no_locking

头文件: "boost/flyweight/no_locking.hpp"
语法: no_locking

不强制任何同步, 从而允许对实现共享资源的不受限内部访问. 选择 no_locking 会比默认的 simple_locking 稍微快一些, 但它使该类型线程不安全, 这可能带来灾难性后果. 除非在单线程环境中, 或绝对保证特定 flyweight 类型不会用于并发场景, 否则不应使用该策略.

跟踪策略

一个跟踪策略控制 flyweight 对象的生命期, 并可以基于这一信息采取行动. 例如, 合适的跟踪机制可以判定工厂中存储的给定值何时可以安全擦除, 因为它不再被任何 flyweight 引用; 默认跟踪策略 refcounted 做的正是这件事.

refcounted

头文件: "boost/flyweight/refcounted.hpp"
语法: refcounted

该跟踪策略规定, 存储在工厂中的值配备引用计数机制, 使得当最后一个与之关联的 flyweight 对象被销毁时, 工厂条目即被擦除.

no_tracking

头文件: "boost/flyweight/no_tracking.hpp"
语法: no_tracking

选择该策略时不做任何享元跟踪, 这意味着存储在工厂中的值会一直保留到程序终止. 与 refcounted 相比, no_tracking 各有优劣. 其优点是:

  • 未跟踪的享元对象比带引用计数的传递起来更快.
  • 由于没有引用计数器, 内存使用有所减少.
而使用 no_tracking 的潜在缺点包括:
  • 工厂中存储的未使用条目的数量在程序运行期间可能持续增长, 对于活动值集合随时间 "漂移" 的某些享元创建模式, 这可能成为问题.
  • 程序终止期间可能有潜在延迟, 因为所有工厂条目会在那时被一次性销毁.
