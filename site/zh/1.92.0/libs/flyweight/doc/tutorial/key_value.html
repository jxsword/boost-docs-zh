键值享元

继续我们的在线游戏示例, 假设我们有一个用于处理渲染纹理的庞大类:

class texture
{
public:
  texture(const std::string& filename){/* loads texture file */}

  const std::string& get_filename()const;

  // rest of the interface
};

并且我们决定使用 flyweight<texture> 来简化这些对象的操纵. 现在考虑这个看似无害的表达式:

flyweight<texture> fw("grass.texture");

注意, 为了构造 fw, 我们隐式地构造了一个完整的草地纹理对象. 该表达式基本上等价于

flyweight<texture> fw(texture("grass.texture"));

这是不可接受的昂贵: 我们构造了一个庞大的临时对象, 只是为了在大多数情况下把它丢弃, 因为 Boost.Flyweight 极可能已经拥有 fw 将绑定到的内部等价对象 — 毕竟值共享正是享元模式背后的关键特性. 在这个特定例子中, 纹理文件名充当实际纹理对象的键: 由同一文件名构造的两个纹理对象是等价的. 因此, 我们希望用文件名来做纹理查找, 并以某种方式确保昂贵的纹理构造只在未找到等价值时才执行.

flyweight<T> 使键与值之间的这种区分变得模糊, 因为它把 T 同时用作键类型及其关联值类型. 当这效率低下时 — 如我们的纹理示例 — 可以使用 key_value 构造显式指定这两个类型:

#include <boost/flyweight.hpp>
#include <boost/flyweight/key_value.hpp>
...
flyweight<key_value<std::string,texture> > fw("grass.texture");

所谓键值享元于是具有形式 flyweight<key_value<K,T> >: 键类型 K 用于对类型为 T 的关联值做内部查找. 键值享元保证: 除非不存在其他等价值, 否则不会构造 T 值; 这种构造由关联的 K 值完成.

键提取器

除了构造时基于键的语义之外, 键值享元的行为与常规享元非常相似, 不过仍存在一些差异. 考虑以下代码 — 它对常规享元没有任何问题:

const texture& get_texture(const object&);
...
flyweight<key_value<std::string,texture> > fw;
...
fw=get_texture(obj);

这个赋值不可能工作, 因为内部查找需要一个 std::string 类型的键, 而我们传入的却是完整的纹理对象. 事实上, 这段代码会产生类似这样的编译错误:

error: 'boost::mpl::assertion_failed' : cannot convert parameter 1 from
'boost::mpl::failed ************(__thiscall boost::flyweights::detail::
regular_key_value<Key,Value>::rep_type::no_key_from_value_failure::
NO_KEY_FROM_VALUE_CONVERSION_PROVIDED::* ***********)(std::string,texture)'
to 'boost::mpl::assert<false>::type'...

事实证明, 只要提供一种从值取回键的手段, 就能让这个赋值工作. 这并非总是可行, 但在我们的特定例子中, 纹理类确实保存了构造时所用的文件名, 如 texture::get_filename 成员函数所示. 我们利用这一点, 在享元类型定义中指定一个合适的键提取器:

struct texture_filename_extractor
{
  const std::string& operator()(const texture& x)const
  {
    return x.get_filename();
  }
};

flyweight<key_value<std::string,texture,texture_filename_extractor> > fw;
...
fw=get_texture(obj); // OK now

在键值享元的定义中指定键提取器会带来内部空间优化, 因为键无需与值一起存储, 而是从值中取回. 因此, 只要可能就提供键提取器总是好主意, 即使你的程序不包含像上面那样的赋值语句.

示例一节中的示例 2 和 5 使用了键值享元.

类型要求

对 T 施加的许多要求 — 那些针对常规享元的要求 — 在键值 flyweight<key_value<K,T> > 的情形转移到键类型上. 现在必须是 K 满足 MoveConstructible 与 EqualityComparable, 并与 Boost.ContainerHash 互操作; 其中相等性与哈希兼容性是 Boost.Flyweight 默认内部工厂施加的要求, 若用户进一步配置或替换该工厂, 这些要求可以改变. T 唯一保留的要求是它必须可从 K 构造; 仅当享元被直接赋以一个 T 对象时, 还要求 T 是CopyConstructible (或为MoveConstructible, 当赋以 T&& 时). 要序列化 flyweight<key_value<K,T> > 类型的对象, 只有 K 需要可序列化.
