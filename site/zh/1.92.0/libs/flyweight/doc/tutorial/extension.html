引言

Boost.Flyweight 为其可配置方面提供公开接口规约, 使用户能够通过实现自己的组件并把它们提供给 flyweight 类模板的实例化来扩展本库.

在大多数情况下, 扩展 Boost.Flyweight 的给定方面涉及两类实体:

  • 组件本身 (例如, 一个工厂类模板).
  • 关联的组件指定器, 即作为 flyweight 实例化的模板实参提供的类型.
例如, 类型 static_holder 是一个持有器指定器, 由 flyweight 用来生成实际的持有器类, 此处即类模板 static_holder_class 的实例化. 注意, static_holder 是具体类型, 而 static_holder_class 是类模板, 因此指定器可以看作一种便捷手段, 用于提供对一族相关具体组件 (该类模板的各种可能实例化) 的访问: flyweight 在内部选择符合其内部需要的特定组件.

自定义工厂

在某种程度上, 工厂类似于 std::set 这样的唯一键关联容器, 不过它们期望的接口要简洁得多:

// example of a possible factory class template

template<typename Entry,typename Key>
class custom_factory_class
{
  public:
  typedef ... handle_type;
  
  handle_type  insert(Entry&& x);
  void         erase(handle_type h);
  const Entry& entry(handle_type h);
};

工厂由 Entry 和 Key 参数化: 第一个是所存对象的类型, 第二个是 flyweight 所操作的公开键类型 (例如 std::string 之于 flyweight<std::string>, 或 flyweight<key_value<std::string,texture> >). 条目持有一个共享值, 享元对象与之关联, 同时还有内部簿记信息; 但从工厂的视角来看, 关于 Entry 唯一已知的事实是它可隐式转换为 const Key&, 并且条目是否等价要依据其关联的 Key 来判定. 工厂的 insert() 成员函数定位先前存储的条目 — 其关联 Key 与所传入 Entry 对象的等价 (就与该工厂密切相关的 Key 上的某种等价关系而言) — 若未找到等价条目则存储新条目. 返回指向等价或新插入条目的一个 handle_type; 该 handle_type 是经由 erase() 和 entry() 进一步访问条目的凭据. 参考中给出了 Factory 概念的正式定义.

让我们看一个自定义工厂类实现的实际例子. 假设我们想跟踪 Boost.Flyweight 对 insert() 和 erase() 成员函数的不同调用: 这可以通过使用一个自定义工厂来完成, 其成员方法向程序控制台输出跟踪消息. 我们把仓库功能的实现基于一个常规的 std::set:

template<typename Entry,typename Key>
class verbose_factory_class
{ 
  typedef std::set<Entry,std::less<Key> > store_type;

  store_type store;

public:
  typedef typename store_type::iterator handle_type;

  handle_type insert(Entry&& x)
  {
    std::pair<handle_type, bool> p=store.insert(std::move(x));
    if(p.second){ /* new entry */
      std::cout<<"new: "<<(const Key&)x<<std::endl;
    }
    else{         /* existing entry */
      std::cout<<"hit: "<<(const Key&)x<<std::endl;
    }
    return p.first;
  }

  void erase(handle_type h)
  {
    std::cout<<"del: "<<(const Key&)*h<<std::endl;
    store.erase(h);
  }

  const Entry& entry(handle_type h)
  {
    return *h;
  }
};

这段代码值得一些解说:

  • 注意, 工厂由 Entry 和 Key 参数化, 因为当工厂作为 flyeight 机制的一部分被实例化时, 这些类型由 Boost.Flyweight 在内部提供; 但没有任何东西阻止我们增加更多模板参数以对工厂类型做更精细的配置: 例如, 我们可以扩展 verbose_factory_class 使其接受某个比较谓词而非默认的 std::less<Key>, 或指定内部 std::set 所使用的分配器.
  • Entry 可转换为 const Key& (这几乎是我们对 Entry 唯一已知的性质) 这一事实, 被用于把 std::less<Key> 指定为比较谓词, 用于 std::set — 即用作内部仓库的 Entry 之条目类型.
  • 作为公开的 handle_type, 我们只是使用指向内部 std::set 的迭代器.

为了把自定义工厂接入 flyweight 类型的指定, 我们需要一个关联的构造, 称为工厂指定器. 工厂指定器是一个Lambda Expression, 接受两个实参类型 Entry 和 Key 并返回对应的工厂类:

// Factory specifier (metafunction class version)

struct custom_factory_specifier
{
  template<typename Entry,Key>
  struct apply
  {
    typedef custom_factory_class<Entry,Key> type;
  } 
};

// Factory specifier (placeholder version)

typedef custom_factory_class<
  boost::mpl::_1,
  boost::mpl::_2
> custom_factory_specifier;

还有最后一个细节: 为了实现 flyweight 的 自由顺序模板参数接口, 必须显式地把工厂指定器标记为工厂指定器, 以便与其他类型的指定器区分. Boost.Flyweight 提供三种不同的机制来做这种标记:

  1. 让指定器派生自哑类型 factory_marker. 注意, 该机制不能用于占位符表达式. 
    #include <boost/flyweight/factory_tag.hpp>

struct custom_factory_specifier: factory_marker
{
  template<typename Entry,Key>
  struct apply
  {
    typedef custom_factory_class<Entry,Key> type;
  } 
};
  2. 特化一个名为 is_factory 的特殊类模板: 
    #include <boost/flyweight/factory_tag.hpp>

struct custom_factory_specifier{};

namespace boost{
namespace flyweights{

template<> struct is_factory<custom_factory_specifier>: boost::mpl::true_{};

}
}
  3. 第三种机制侵入性最小, 它把指定器包装在 factory 构造中: 
    #include <boost/flyweight/factory_tag.hpp>

typedef flyweight<
  std::string,
  factory<custom_factory_specifier>
> flyweight_string;

示例一节中的 示例 8 完整展开了上面概述的 verbose_factory_class 案例.

自定义持有器

持有器是一个类, 它带有静态成员函数 get(), 提供对给定类型 C 的唯一实例的访问:

// example of a possible holder class template

template<typename C>
class custom_holder_class
{
public:
  static C& get();
};

flyweight 在内部使用一个持有器来创建其关联的工厂以及一些其他全局数据. 持有器指定器是一个Lambda Expression, 接受关联持有器类所操作的类型 C:

// Holder specifier (metafunction class version)

struct custom_holder_specifier
{
  template<typename C>
  struct apply
  {
    typedef custom_holder_class<C> type;
  } 
};

// Holder specifier (placeholder version)

typedef custom_holder_class<boost::mpl::_1> custom_factory_specifier;

与工厂指定器一样, 持有器指定器必须被标记, 以便在提供给 flyweight 时被正确识别. 有三种可用机制:

// Alternatives for tagging a holder specifier

#include <boost/flyweight/holder_tag.hpp>

// 1: Have the specifier derive from holder_marker

struct custom_holder_specifier: holder_marker
{
  ...
};

// 2: Specialize the is_holder class template

namespace boost{
namespace flyweights{

template<> struct is_holder<custom_holder_specifier>: boost::mpl::true_{};

}}

// 3: use the holder<> wrapper when passing the specifier
// to flyweight

typedef flyweight<
  std::string,
  holder<custom_holder_specifier>
> flyweight_string;

自定义锁定策略

自定义锁定策略呈现如下简单接口:

// example of a custom policy

class custom_locking
{
  typedef ... mutex_type;
  typedef ... lock_type;
};

其中 lock_type 依照作用域锁惯用法用于获取/释放互斥量:

mutex_type m;
...
{
  lock_type lk(m); // acquire the mutex
  // zone of mutual exclusion, no other thread can acquire the mutex
  ...
} // m released at lk destruction

概念 Mutex 和 Scoped Lock 的正式定义见参考部分. 要把锁定策略作为 flyweight 的模板实参传入, 该类必须被恰当地标记:

// Alternatives for tagging a locking policy

#include <boost/flyweight/locking_tag.hpp>

// 1: Have the policy derive from locking_marker

struct custom_locking: locking_marker
{
  ...
};

// 2: Specialize the is_locking class template

namespace boost{
namespace flyweights{

template<> struct is_locking<custom_locking>: boost::mpl::true_{};

}}

// 3: use the locking<> wrapper when passing the policy
// to flyweight

typedef flyweight<
  std::string,
  locking<custom_locking>
> flyweight_string;

注意, 锁定策略就是它自己的指定器, 也就是说, 不像工厂和持有器那样需要额外的类来作为真实组件的代理.

自定义跟踪策略

跟踪策略为内部享元工厂的定义过程贡献一些类型信息, 并被授予对该工厂的访问权, 以便实现跟踪代码. 跟踪策略 Tracking 定义为具有以下嵌套元素的类:

  • 一个类型 Tracking::entry_type.
  • 一个类型 Tracking::handle_type.
这些元素逐级递进: Boost.Flyweight 的内部机制把一个元素产生的结果汇入下一个元素:
  • Tracking::entry_type 是一个Lambda Expression, 接受两个名为 Value 和 Key 的不同类型, 且 Value 可隐式转换为 const Key&. 该表达式预期返回一个可隐式转换为 const Value& 和 const Key& 两者的类型. Tracking::entry_type 对应于享元工厂中所存条目的实际类型: 允许跟踪策略参与该类型的定义, 使得策略可以在需要时向条目数据添加内部跟踪信息. 如果不需要附加信息, 跟踪策略可以简单地返回 Value 作为其 Tracking::entry_type 类型.
  • 二元 Lambda Expression Tracking::handle_type 以 InternalHandle 和 TrackingHandler 类型调用, 产生一个类型 Handle, 它将用作享元工厂的句柄类型. TrackingHandler 作为模板实参传给 Tracking::handle_type, 以提供支持跟踪代码实现的功能.
于是, 为了定义某个 fw_t 实例化 (属于 flyweight) 的工厂, Tracking::entry_type 会以内部类型 Value 被调用 — 该类型可隐式转换为 const fw_t::key_type& — 以获得工厂的条目类型, 该类型必须可转换为 const Value& 和 const fw_t::key_type& 两者. 然后, 向 Tracking::handle_type 传入一个内部句柄类型和一个跟踪策略辅助器, 以产生工厂句柄类型. 观察敏锐的读者可能已经发现了一个明显的循环: Tracking::handle_type 产生享元工厂的句柄类型, 同时却又被传入一个授予对正在定义中的工厂之访问权的跟踪辅助器! 这个谜题的答案来自如下认识: TrackingHandler 是一个不完整类型 — 在它被传给 Tracking::handle_type 的时刻; 只有在稍后阶段 Handle 被实例化时, 该类型才是完整的.

为了把跟踪策略传给 flyweight, 必须像其他指定器一样对它打标签.

// Alternatives for tagging a tracking policy

#include <boost/flyweight/tracking_tag.hpp>

// 1: Have the policy derive from tracking_marker

struct custom_tracking: tracking_marker
{
  ...
};

// 2: Specialize the is_tracking class template

namespace boost{
namespace flyweights{

template<> struct is_tracking<custom_tracking>: boost::mpl::true_{};

}}

// 3: use the tracking<> wrapper when passing the policy
// to flyweight

typedef flyweight<
  std::string,
  tracking<custom_tracking>
> flyweight_string;

跟踪策略就是它们自己的指定器, 也就是说, 它们直接作为模板实参提供给 flyweight 类模板.
