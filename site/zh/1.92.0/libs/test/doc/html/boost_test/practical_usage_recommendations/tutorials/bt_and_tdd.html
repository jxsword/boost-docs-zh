用 Boost.Test 进行测试驱动开发

今天是一个值得纪念的日子 - 新年的第一天. 今天我要开始新的生活. 我打算不再吃油腻的食物, 开始去健身俱乐部, 而且......今天我要开始测试我写的程序. 我可以在程序最后一行完成之后立即开始, 或者更好, 我可以边编码边写测试. 也许下次我会在编码之前, 即设计阶段就先写测试. 我已经阅读了大量关于如何编写测试的文献, 手头有单元测试框架, 还有一个新类的构想. 那么, 开始吧.

假设我想把一段带长度的不可变 C 字符缓冲区封装进一个简单的类const_string. 理由: 一个不分配内存、并为预先分配的字符缓冲区提供便捷只读访问的字符串类. 我可能希望const_string具有与 std::string 类似的接口. 我首先会做什么? 在我的新生活里, 我会从为未来的类const_string编写测试模块开始. 它看起来像这样:

#define BOOST_TEST_MODULE const_string test
#include <boost/test/unit_test.hpp>

现在我可以编译它并与单元测试框架链接. 完成! 我有了一个可运行的测试程序. 它是空的, 所以运行程序时产生如下输出:

*** No errors detected

好了, 现在可以开始着手实现const_string了. 我设想第一件好事是拥有构造函数和简单的访问方法. 于是这个类的初始版本如下:

class const_string {
public:
  // Constructors
  const_string();
  const_string( std::string const& s )
  const_string( char const* s );
  const_string( char const* s, size_t length );
  const_string( char const* begin, char const* end );

  // Access methods
  char const* data() const;
  size_t      length() const;
  bool        is_empty() const;

  // ...
};

现在我可以编写第一个测试用例 - 构造函数测试 - 并把它添加到测试套件中. 我的测试程序变成了这样:

#define BOOST_TEST_MODULE const_string test
#include <boost/test/unit_test.hpp>

BOOST_AUTO_TEST_CASE( constructors_test )
{
  const_string cs0( "" );                                                 // 1 //
  BOOST_TEST( cs0.length() == (size_t)0 );
  BOOST_TEST( cs0.is_empty() );

  const_string cs01( NULL );                                              // 2 //
  BOOST_TEST( cs01.length() == (size_t)0 );
  BOOST_TEST( cs01.is_empty() );

  const_string cs1( "test_string" );                                      // 3 //
  BOOST_TEST( std::strcmp( cs1.data(), "test_string" ) == 0 );
  BOOST_TEST( cs1.length() == std::strlen("test_string") );

  std::string s( "test_string" );                                         // 4 //
  const_string cs2( s );
  BOOST_TEST( std::strcmp( cs2.data(), "test_string" ) == 0 );

  const_string cs3( cs1 );                                                // 5 //
  BOOST_TEST( std::strcmp( cs3.data(), "test_string" ) == 0 );

  const_string cs4( "test_string", 4 );                                   // 6 //
  BOOST_TEST( std::strncmp( cs4.data(), "test", cs4.length() ) == 0 );

  const_string cs5( s.data(), s.data() + s.length() );                    // 7 //
  BOOST_TEST( std::strncmp( cs5.data(), "test_string", cs5.length() ) == 0 );

  const_string cs_array[] = { "str1", "str2" };                           // 8 //
  BOOST_TEST( cs_array[0] == "str1" );
  BOOST_TEST( cs_array[1] == "str2" );
}

constructors_test 测试用例旨在检查类const_string的一个简单特性: 基于不同参数正确构造自身的能力. 为测试这一特性, 我使用被构造对象的若干特征, 如它包含的数据和长度. 类const_string的规范不包含任何预期失败, 因此, 虽然构造函数在传入指向无效内存的指针时可能失败, 错误检查控制并未执行(不能要求未曾承诺的东西 :-)). 但对任何有效输入它都应当工作. 于是我尝试检查以下构造: 空字符串(1)、NULL 字符串(2)、常规 C 字符串(3)、STL 字符串(4)、复制构造(5)等等. 好了, 在修完实现中的全部错误之后(你能从零开始写出没有错误的程序吗?), 我可以通过这个测试用例, 单元测试框架给我如下报告:

Running 1 test case...

*** No errors detected

受到鼓舞, 我继续添加更多访问方法:

class const_string {
public:
  //...
  char operator[]( size_t index ) const;
  char at( size_t index ) const;
  //...
};

我添加了新特性 - 需要一个新测试用例来检查它. 于是我的测试套件变成了这样:

#define BOOST_TEST_MODULE const_string test
#include <boost/test/unit_test.hpp>

BOOST_AUTO_TEST_CASE( constructors_test )
{
  //...
}

BOOST_AUTO_TEST_CASE( data_access_test )
{
  const_string cs1( "test_string" );                                // 1 //
  BOOST_TEST( cs1[(size_t)0] == 't' );
  BOOST_TEST( cs1[(size_t)4] == '_' );
  BOOST_TEST( cs1[cs1.length()-1] == 'g' );

  BOOST_TEST( cs1[(size_t)0] == cs1.at( 0 ) );                      // 2 //
  BOOST_TEST( cs1[(size_t)2] == cs1.at( 5 ) );
  BOOST_TEST( cs1.at( cs1.length() - 1 ) == 'g' );

  BOOST_CHECK_THROW( cs1.at( cs1.length() ), std::out_of_range );   // 3 //
}

在 data_access_test 测试用例中, 我尝试检查类const_string字符访问的正确性. 测试(1)用const_string::operator[]检查有效访问, 测试(2)用方法const_string::at()检查有效访问, 但还有一件事要测试. 方法const_string::at()的规范包含对越界访问的校验. 测试(3)正是为此而设: 检查校验是否生效. 对校验和错误处理代码的测试是单元测试的重要组成部分, 不应留到生产阶段. data_access_test 测试用例通过了, 我准备好进行下一步.

继续努力, 我完成了类const_string(见清单 1 const_string.hpp)和针对它的测试模块(见清单 2 const_string_test.cpp), 后者检查类const_string规范中呈现的所有特性.

好了, 我离实现新年计划又近了一步(健身俱乐部嘛......下次再说的). 你呢? 你的测试习惯可能略有不同. 你可以从类/库的开发开始, 然后在某个时间点开始按特性编写测试用例. 或者, 给定未来产品的详细规范(包括预期接口), 你可以立即开始编写全部测试用例(也可能是另一个人在写测试, 而你同时在实现). 无论哪种情况, 使用 Boost.Test 单元测试框架提供的设施都不应遇到任何问题, 而且但愿你能写出稳定、坚如磐石的代码. 更重要的是, 你将有信心对任何复杂度的代码做出修改, 而无需对整个产品进行冗长的回归测试. 你的测试模块和单元测试框架会在背后支持你, 帮助你应对偶发错误.
