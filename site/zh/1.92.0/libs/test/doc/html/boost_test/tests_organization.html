声明与组织测试的 API 汇总

如果你查看许多遗留测试模块, 很可能它们被实现为一个大测试函数, 由检查语句和输出语句混合而成. 这有什么问题吗? 有. 单一测试函数方式有各种缺点:

  • 一个大函数在检查数量超过合理上限时会变得非常难以管理(对任何大函数都是如此). 测试了什么、在哪里测试 - 谁知道?
  • 许多检查需要类似的准备工作. 这导致测试函数内部代码重复.
  • 如果测试函数内的任何检查引发致命错误或异常, 其余测试会被跳过, 且无法阻止这一点.
  • 无法只对被测单元的特定子系统执行检查.
  • 没有关于被测单元各子系统在测试中表现的汇总.

上述几点应已说明, 把测试模块拆分成更小的单元更为可取. 这些单元就是测试用例、测试套件和夹具.

本节涵盖的主题

声明

单元测试框架支持多种声明测试用例的方法. 测试用例可以用类似自由函数的语法实现, 或基于实际的自由函数或函数对象, 可带参数/数据定义, 也可以实现为针对各种类型运行的模板函数.

组织

单元测试框架提供了把若干测试用例分组为测试套件的设施. 测试套件可以嵌套, 测试套件和测试用例的集合定义了测试树, 其中叶节点是测试用例. 除层次结构外, 单元测试框架还允许你用逻辑分组和依赖来组织测试树, 并为你提供按你想要的方式利用已定义测试树组织的控制手段(例如从命令行).

属性

可以指定测试单元的属性, 方法是使用装饰器. 属性用于对测试模块执行的各个方面进行细粒度控制, 如逻辑分组、依赖、预期失败等.

测试单元的建立/拆除动作

当多个测试共享同一套建立步骤(环境、测试数据准备等)时, 准备和清理代码可以因式分解到夹具中. 在单元测试框架中, 夹具可以关联到测试用例、测试套件, 或全局关联到测试模块.
