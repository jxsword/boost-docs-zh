一般建议

优先使用离线编译的库, 而非内联包含的组件

如果你只是想在一个从未用过 Boost.Test 的环境中快速写一个简单测试 - 是的, 可以用内联包含的组件. 但如果你计划长期使用 Boost.Test, 构建(如果尚未构建)、安装并修改 makefile/工程设置所需的小额时间投入, 很快就会以更短编译时间的形式回馈给你. 为什么要让你的编译器一遍又一遍地做同样的工作?

如果只使用基于自由函数的测试用例, 请改用自动注册设施

切换到自动注册真的很容易. 而且你不必担心遗忘某个测试用例.

要在被复用的模板函数内定位测试工具报告的第一个错误的位置, 请使用框架头文件中的特殊钩子

有些情况下, 你会在一个测试用例内复用同一份基于模板的代码(实际上, 我们在这种情形下推荐更好的方案 - 见下文). 此时, 如果测试工具在这份复用代码内报告了错误, 你可能难以确定错误究竟发生在哪里. 要解决这个问题, 你要么在模板化代码中添加BOOST_TEST_MESSAGE语句来记录模板参数的当前类型 id, 要么使用unit_test_result.hpp中名为first_failed_assertion()的特殊钩子. 如果你在定义该函数的那一行上设置断点, 就能展开调用栈并看到错误实际发生的位置.

要用不同的模板参数测试可复用的模板基础组件, 请使用测试用例模板设施

如果你在为通用的可复用组件编写单元测试, 可能需要针对一组不同的模板参数类型对它进行测试. 最可能的情况是, 你最终会写出类似这样的代码:

template<typename TestType>
void specific_type_test( TestType* = 0 )
{
  MyComponent<TestType> c;
  // ... here we perform actual testing
}

void my_component_test()
{
  specific_type_test( (int*)0 );
  specific_type_test( (float*)0 );
  specific_type_test( (UDT*)0 );
  // ...
}

这正是应该使用测试用例模板设施的情形. 它不仅通过自动化部分工作简化了这类单元测试, 而且每个参数类型都会在单元测试监视器下被单独测试. 这样一来, 如果某个类型产生异常或非致命错误, 你仍可以继续并用其他类型完成测试并获得结果.
