设计理由

单元测试任务出现在软件开发的许多不同阶段: 从最初的项目实现到其维护及后续修订. 这些任务的复杂度和目的各不相同, 因而不同开发者会以不同方式应对. 问题领域中任务的广泛谱系给单元测试框架提出了许多(有时相互冲突的)要求, 其中包括:

  • 对新手用户而言, 编写单元测试模块应当简单明了.
  • 框架应允许高级用户执行非平凡的测试.
  • 测试模块应能包含许多小测试用例, 且开发者应能把它们组织成测试套件.
  • 开发初期, 用户希望看到详细且具描述性的错误消息.
  • 回归测试期间, 用户只想知道是否有测试失败.
  • 对小测试模块而言, 其执行时间应优先于编译时间: 用户不想为了编译一个只需一秒运行的测试而等上一分钟.
  • 对于长而复杂的测试, 用户希望能看到测试进度.
  • 最简单的测试不应需要外部库.
  • 对单元测试框架的长期用户而言, 应能把它构建为独立库.

单元测试框架满足上述要求, 并提供多种多样的设施来:

  • 轻松指定被测代码中的所有期望.
  • 把这些期望组织成测试用例和测试套件.
  • 检测不同种类的错误、失败和超时, 并以统一且可定制的方式报告它们.
为什么需要一个框架?

虽然你可以从零开始自己编写测试程序, 但框架能带来以下好处:

  • 你得到文本格式的错误报告. 错误报告是统一的, 便于机器分析.
  • 错误报告与测试代码分离. 你可以轻松更改错误报告格式而不影响测试代码.
  • 框架自动检测被测组件抛出的异常和超时, 并把它们与其他错误一起报告.
  • 你可以轻松过滤测试用例, 只调用所需的那几个. 这不需要改动测试代码.
