测试单元过滤

单元测试框架提供了多种方式, 只运行测试树中注册的全部测试用例的一个子集.

默认运行状态

每个测试单元(测试用例或测试套件)都有一个关联的默认运行状态. 它可以取三个值之一:

  1. true -- 这意味着, 除非某些运行期参数另有规定, 该测试单元被指定为要运行.
  2. false -- 这意味着, 除非某些运行期参数另有规定, 该测试单元被指定为不运行.
  3. inherit -- 这意味着测试单元的默认运行状态与其直接父测试单元相同. 此规则递归适用.

初始时, 主测试套件的默认运行状态被设为true. 所有其他测试单元的默认运行状态被设为inherit. 这意味着, 除非施加任何额外配置, 所有测试都被指定为要运行.

你可以用装饰器为任何测试单元设置不同的默认运行状态: disabled、enabled和enable_if. 默认运行状态只在测试程序初始化时设置一次, 之后不可更改. 被禁用的测试默认不执行, 但仍存在于测试树中, 且在你使用命令行参数list_content时会与其他测试一起列出.

示例: 默认运行状态

代码

 
#define BOOST_TEST_MODULE decorator_20
#include <boost/test/included/unit_test.hpp>

namespace utf = boost::unit_test;

const bool io_implemented = true;
const bool db_implemented = false;

BOOST_AUTO_TEST_SUITE(suite1, * utf::disabled())

  BOOST_AUTO_TEST_CASE(test_1)
  {
    BOOST_TEST(1 != 1);
  }

  BOOST_AUTO_TEST_CASE(test_2, * utf::enabled())
  {
    BOOST_TEST(2 != 2);
  }

  BOOST_AUTO_TEST_CASE(test_io,
    * utf::enable_if<io_implemented>())
  {
    BOOST_TEST(3 != 3);
  }

  BOOST_AUTO_TEST_CASE(test_db,
    * utf::enable_if<db_implemented>())
  {
    BOOST_TEST(4 != 4);
  }

BOOST_AUTO_TEST_SUITE_END()

输出

 
> decorator_20
Running 2 test cases...
test.cpp(18): error: in "suite1/test_2": check 2 != 2 has failed [2 == 2]
test.cpp(24): error: in "suite1/test_io": check 3 != 3 has failed [3 == 3]

*** 2 failures are detected in the test module "decorator_20"

> decorator_20 --list_content
suite1*
    test_1
    test_2*
    test_io*
    test_db

动态测试依赖

此外, 还可以把测试单元与一个条件静态关联. 该关联条件会在执行测试单元之前立即求值. 条件满足则执行该测试单元; 否则测试单元被跳过. 可以添加两类依赖:

  1. 依赖于另一个测试单元. 此时, 若依赖中指定的测试单元处于失败、跳过或禁用状态, 被装饰的测试用例将被跳过. 可用装饰器depends_on声明.
  2. 依赖于任意谓词. 可用装饰器precondition声明.

命令行控制

除非施加命令行过滤, 否则默认使用测试用例过滤的静态配置. 通过命令行参数run_test, 可以用多种方式改变静态预设:

  1. 忽略静态配置, 手动指定要运行的测试用例.
  2. 通过启用被禁用的测试用例来扩充静态定义的集合.
  3. 通过禁用某些已启用的测试用例来收缩静态定义的集合.
绝对指定

此处"绝对"一词的意思是: 静态设置的测试单元默认运行状态被完全忽略, 要运行的测试从头手动指定. 首先, 为了了解测试树中注册了哪些测试单元, 用户需要使用命令行参数list_content. 接着, 为了指定一组测试用例, 用户需要使用带绝对值的命令行参数run_test:

> test_program --run_test=<test_set>

<test_set>的值可以采用多种形式. 给定以下程序:

#define BOOST_TEST_MODULE example
#include <boost/test/included/unit_test.hpp>

using boost::unit_test::label;

BOOST_AUTO_TEST_CASE(test_1, *label("L1")) {}
BOOST_AUTO_TEST_CASE(test_2, *label("L1")) {}

BOOST_AUTO_TEST_SUITE(suite_1)

  BOOST_AUTO_TEST_SUITE(suite_1)
    BOOST_AUTO_TEST_CASE(test_1) {}
    BOOST_AUTO_TEST_CASE(test_2) {}
  BOOST_AUTO_TEST_SUITE_END()

  BOOST_AUTO_TEST_SUITE(suite_2)
    BOOST_AUTO_TEST_CASE(test_1, *label("L2")) {}
    BOOST_AUTO_TEST_CASE(test_2, *label("L2")) {}
  BOOST_AUTO_TEST_SUITE_END()

  BOOST_AUTO_TEST_CASE(test_1, *label("L1")) {}
  BOOST_AUTO_TEST_CASE(test_2) {}
  BOOST_AUTO_TEST_CASE(test_2A) {}

BOOST_AUTO_TEST_SUITE_END()

下表展示了<test_set>的不同值如何控制运行哪些测试用例.

关于描述<test_set>值结构的语法产生式, 见此处.

虽然使用手动绝对测试用例指定会忽略默认运行状态, 但它不会忽略动态测试依赖. 如果测试单元B依赖测试单元A, 且测试B被run_test指定为要运行, 那么A也会运行, 即使它未被指定, 而且它的失败可能导致B的执行被跳过. 类似地, precondition的检查失败也可能导致被选中的测试被跳过.

示例: run_test 与动态依赖

代码

 
#define BOOST_TEST_MODULE decorator_21
#include <boost/test/included/unit_test.hpp>

namespace utf = boost::unit_test;
namespace tt = boost::test_tools;

tt::assertion_result fail(utf::test_unit_id)
{
  tt::assertion_result ans(false);
  ans.message() << "precondition failed";
  return ans;
}

BOOST_AUTO_TEST_CASE(test_1)
{
  BOOST_TEST(false);
}

BOOST_AUTO_TEST_CASE(test_2,
  * utf::depends_on("test_1"))
{
  BOOST_TEST(true);
}

BOOST_AUTO_TEST_CASE(test_3,
  * utf::precondition(fail))
{
  BOOST_TEST(true);
}

输出

 
> decorator_21 --log_level=test_suite --run_test=test_2,test_3

Running 3 test cases...
Entering test module "decorator_21"
test.cpp(14): Entering test case "test_1"
test.cpp(16): error: in "test_1": check false has failed
test.cpp(14): Leaving test case "test_1"; testing time: 3ms
test.cpp(26): Test case "test_3" is skipped because precondition failed
test.cpp(20): Test case "test_2" is skipped because dependency test case "test_1" has failed

相对指定

此处"相对"一词的意思是: 配置基于测试单元的默认运行状态, 或由绝对指定给出的命令行覆盖; 在此之上, 我们再额外启用一些被禁用的测试单元, 或禁用一些已启用的测试单元. 相对指定由命令行参数run_test控制, 其值采用与绝对指定相似的语法, 但前面要加上字符'!'表示禁用已启用的测试单元, 或字符'+'表示启用被禁用的测试单元. 可用下表概括:

命令

指定类型

语义

 
> test_program --run_test=!<absolute_spec>

禁用器(disabler)

与<absolute_spec>匹配的已启用测试单元变为禁用.

 
> test_program --run_test=+<absolute_spec>

启用器(enabler)

与<absolute_spec>匹配的被禁用测试单元及其上游依赖变为启用.

启用器指定用于启用初始被禁用的一组测试单元.

示例: 命令行启用器

代码

 
#define BOOST_TEST_MODULE decorator_22
#include <boost/test/included/unit_test.hpp>

namespace utf = boost::unit_test;

BOOST_AUTO_TEST_CASE(test_1)
{
  BOOST_TEST(true);
}

BOOST_AUTO_TEST_CASE(test_net,
  * utf::disabled()
  * utf::description("requires network"))
{
  BOOST_TEST(true);
}

输出

> decorator_22 --log_level=test_suite

反过来, 禁用器指定用于禁用初始已启用的一组测试单元.

示例: 命令行禁用器

代码

 
#define BOOST_TEST_MODULE decorator_23
#include <boost/test/included/unit_test.hpp>

namespace utf = boost::unit_test;

BOOST_AUTO_TEST_CASE(test_1)
{
  BOOST_TEST(true);
}

BOOST_AUTO_TEST_CASE(test_net,
  * utf::description("requires network"))
{
  BOOST_TEST(true);
}

如果同一命令行上同时存在指定同一测试的启用器和禁用器, 该测试将变为禁用. 即, 禁用器优先于启用器.

注释

启用器会额外启用上游依赖(通过装饰器depends_on引入), 而禁用器不会禁用它们. 因此, 当你先启用再禁用同一个测试时, 其上游依赖不会被禁用.
