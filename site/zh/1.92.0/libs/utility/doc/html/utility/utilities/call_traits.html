引言

<boost/call_traits.hpp> 的全部内容都定义在 namespace boost 内部.

模板类 call_traits<T> 封装了把某个类型 T 的形参传入或传出函数的"最佳"方式, 由下表所定义的 typedef 集合组成. call_traits 的目的是确保 "引用的引用" 之类的问题绝不会发生, 并以最高效的方式传递形参, 如 示例 所示. 在每种情形下, 如果你现有的做法是使用左列定义的类型, 则应将其替换为右列的 call_traits 定义类型.

注意, 对于既不支持部分特化也不支持成员模板的编译器, 使用 call_traits 不会带来任何好处: 此时 call_traits 定义的类型总是与现有做法相同. 此外, 如果编译器只支持成员模板而不支持部分模板特化 (例如 Visual C++ 6), 则 call_traits 不能用于数组类型, 但仍可用于解决引用的引用问题.

  1. 如果 T 已经是引用类型, 则 call_traits 的定义会确保不出现 "引用的引用" (需要部分特化).
  2. 如果 T 是数组类型, 则 call_traits 把 value_type 定义为"类型的常量指针"而不是"类型的数组" (需要部分特化). 注意, 如果你把 value_type 用作存储值, 那么这将导致存储一个"指向数组的常量指针"而不是数组本身. 这是否是好事取决于你的实际需要 (换言之, 请务必小心!).
  3. 如果 T 是小的内置类型或指针, 则 param_type 被定义为 T const, 而不是 T const&. 如果函数体内的循环依赖于所传递的形参, 这可以提高编译器优化循环的能力, 否则所传递形参的语义不变 (需要部分特化).

示例 1:

下面的类是一个平凡的类, 它按值存储某个类型 T (参见 call_traits_test.cpp 文件). 目的是说明如何使用各个可用的 call_traits typedef:

template <class T>
struct contained
{
   // define our typedefs first, arrays are stored by value
   // so value_type is not the same as result_type:
   typedef typename boost::call_traits<T>::param_type       param_type;
   typedef typename boost::call_traits<T>::reference        reference;
   typedef typename boost::call_traits<T>::const_reference  const_reference;
   typedef T                                                value_type;
   typedef typename boost::call_traits<T>::value_type       result_type;

   // stored value:
   value_type v_;

   // constructors:
   contained() {}
   contained(param_type p) : v_(p){}
   // return byval:
   result_type value() { return v_; }
   // return by_ref:
   reference get() { return v_; }
   const_reference const_get()const { return v_; }
   // pass value:
   void call(param_type p){}

};
示例 2 (引用的引用问题):

考虑 std::binder1st 的定义:

template <class Operation>
class binder1st :
   public std::unary_function<typename Operation::second_argument_type, typename Operation::result_type>
{
protected:
   Operation op;
   typename Operation::first_argument_type value;
public:
   binder1st(const Operation& x, const typename Operation::first_argument_type& y);
   typename Operation::result_type operator()(const typename Operation::second_argument_type& x) const;
};

现在考虑相对常见的情况: 函子以其第二个实参作为引用, 这意味着 Operation::second_argument_type 是引用类型, operator() 最终将接受对引用的引用作为实参, 而这目前是不合法的. 这里的解决办法是修改 operator() 以使用 call_traits:

typename Operation::result_type operator()(typename call_traits<typename Operation::second_argument_type>::param_type x) const;

现在, 在 Operation::second_argument_type 是引用类型的情况下, 实参以引用方式传递, 且不会出现"引用的引用".

示例 3 (make_pair 问题):

如果我们将数组名作为一个 (或两个) 实参传给 std::make_pair, 那么模板实参推导会把传递的形参推导为"对 T 数组的 const 引用", 这也适用于字符串字面量 (它们实际上是数组字面量). 因此, 它不会返回一对指针, 而是尝试返回一对数组, 且由于数组类型不可拷贝构造, 代码将无法编译. 一种解决办法是把实参显式转换为 std::make_pair 的指针, 但 call_traits 提供了更好的自动解决方案, 即使在转换可能出错的泛型代码中也能安全工作.

template <class T1, class T2>
std::pair<
   typename boost::call_traits<T1>::value_type,
   typename boost::call_traits<T2>::value_type>
      make_pair(const T1& t1, const T2& t2)
{
   return std::pair<
      typename boost::call_traits<T1>::value_type,
      typename boost::call_traits<T2>::value_type>(t1, t2);
}

这里, 若推导出的类型是数组, 推导出的实参类型会自动退化为指针; 标准绑定器与适配器中也会出现类似情况: 原则上, 在任何"包装"类型被推导的临时对象的函数中都会出现. 注意, std::make_pair 的函数实参没有以 call_traits 的形式表示: 否则会妨碍模板实参推导的正常工作.

示例 4 (优化填充):

call_traits 模板会"优化"小型内置类型作为函数形参的传递方式. 这主要在形参在循环体内使用时才有效果.

在下面的示例中 (参见 fill_example.cpp), std::fill 的一个版本以两种方式进行了优化: 如果传入的类型是单字节内置类型, 则使用 std::memset 完成填充; 否则使用常规的 C++ 实现, 但使用 call_traits 对传入的形参进行了"优化":

template <bool opt>
struct filler
{
   template <typename I, typename T>
   static void do_fill(I first, I last, typename boost::call_traits<T>::param_type val)
   {
      while(first != last)
      {
         *first = val;
         ++first;
      }
   }
};

template <>
struct filler<true>
{
   template <typename I, typename T>
   static void do_fill(I first, I last, T val)
   {
      std::memset(first, val, last-first);
   }
};

template <class I, class T>
inline void fill(I first, I last, const T& val)
{
   enum { can_opt = boost::is_pointer<I>::value
                   && boost::is_arithmetic<T>::value
                   && (sizeof(T) == 1) };
   typedef filler<can_opt> filler_t;
   filler_t::template do_fill<I,T>(first, last, val);
}

对小型内置类型而言这样做"最优"的原因是: 当值以 T const 而不是 const T& 传递时, 编译器能够断定该值既是常量又无别名. 有了这一信息, 编译器可以把传入的值缓存到寄存器中、展开循环, 或使用显式并行指令 (如果支持其中任何一种). 你能从中获得多少好处取决于你的编译器 - 我们确实需要一些精确的基准测试软件作为 boost 的组成部分来应对这类情形.

注意, fill 的函数实参没有以 call_traits 的形式表示: 否则会妨碍模板实参推导的正常工作. 相反, fill 充当用于执行模板实参推导的"薄包装", 编译器会把对 fill 的调用完全优化掉, 代之以对 filler<>::do_fill 的调用, 后者确实使用了 call_traits.

设计理由

以下注释旨在简要说明 call_traits 中所做选择背后的理由.

所有用户定义类型遵循"现有做法", 无需评述.

小型内置类型 (标准称之为 基本类型) 仅在 param_type typedef 方面与现有做法不同. 在这种情况下, 传递 T const 与现有做法兼容, 但在某些情况下可能提高性能 (参见 示例 4). 无论如何, 这绝不会比现有做法更差.

指针遵循与小型内置类型相同的理由.

对于引用类型, 其理由遵循 示例 2 - 不允许引用的引用, 因此 call_traits 成员的定义必须确保这些问题不会发生. 曾有一项修改语言的提案, 使"引用的引用即是引用" (issue #106, 由 Bjarne Stroustrup 提交). call_traits<T>::value_type 与 call_traits<T>::param_type 都提供了与该提案相同的效果, 而无需修改语言. 换言之, 这是一种变通办法.

对于数组类型, 接受数组作为实参的函数会把数组类型退化为指针类型: 这意味着实际形参的类型与其声明类型不同, 这在依赖形参声明类型的模板代码中可能引起无穷的问题.

例如:

template <class T>
struct A
{
   void foo(T t);
};

在这种情况下, 如果我们实例化 A<int[2]>, 那么传递给成员函数 foo 的形参的声明类型是 int[2], 但其实际类型是 const int*. 如果我们尝试在函数体内使用类型 T, 那么代码很有可能无法编译:

template <class T>
void A<T>::foo(T t)
{
   T dup(t); // doesn't compile for case that T is an array.
}

通过使用 call_traits, 从数组到指针的退化是显式的, 且形参的类型与其声明类型相同:

template <class T>
struct A
{
   void foo(typename call_traits<T>::value_type t);
};

template <class T>
void A<T>::foo(typename call_traits<T>::value_type t)
{
   typename call_traits<T>::value_type dup(t); // OK even if T is an array type.
}

对于 value_type (按值返回), 同样只能返回指针, 而不能返回整个数组的拷贝; 同样, call_traits 使这种退化成为显式的. 每当必须把数组显式退化为指针时, value_type 成员就很有用 - 示例 3 提供了测试用例.

脚注: call_traits 的数组特化是所有 call_traits 特化中最难被理解的. 如果给定的语义给你带来了具体问题, 或未能解决某个特定的数组相关问题, 我很乐意听到反馈. 不过, 大多数人可能永远不需要使用这个特化.
