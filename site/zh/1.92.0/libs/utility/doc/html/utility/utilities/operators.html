引言

头文件 <boost/operators.hpp> 在 namespace boost 中提供了几组类模板. 这些模板基于类提供的最少基本运算符, 在命名空间作用域定义运算符.

设计理由

类类型的重载运算符通常成组出现. 如果你能写 x + y, 你可能还希望能写 x += y. 如果你能写 x < y,, 你还会想要 x > y、x >= y, 和 x <= y.

此外, 除非你的类有真正令人意外的行为, 否则其中一些相关运算符可以由其他运算符定义 (例如 x >= y 等价于 !(x < y)).

为多个类复制这些样板代码既繁琐又容易出错. <boost/operators.hpp> 模板可以提供帮助: 它基于你在类中定义的其他运算符, 在命名空间作用域为你生成运算符.

例如, 如果你声明一个这样的类:

class MyInt
    : boost::operators<MyInt>
{
    bool operator<(const MyInt& x) const;
    bool operator==(const MyInt& x) const;
    MyInt& operator+=(const MyInt& x);
    MyInt& operator-=(const MyInt& x);
    MyInt& operator*=(const MyInt& x);
    MyInt& operator/=(const MyInt& x);
    MyInt& operator%=(const MyInt& x);
    MyInt& operator|=(const MyInt& x);
    MyInt& operator&=(const MyInt& x);
    MyInt& operator^=(const MyInt& x);
    MyInt& operator++();
    MyInt& operator--();
};

那么 operators<> 模板会添加十多个附加运算符, 例如 operator>、operator<=、operator>= 以及二元 operator+.

还提供了模板的 双实参形式, 以允许与其他类型交互.

以下是一个 模板语义摘要:

  1. 每个运算符模板通过为其目标类定义重载运算符来补全它所描述的概念.
  2. 运算符类模板的名称表明其目标类将建模的 概念.
  3. 通常, 目标类把运算符类模板的一个实例用作基类. 某些运算符模板支持 替代方法.
  4. 该概念可以是复合的, 即它可以表示其他更简单概念的常见组合.
  5. 大多数运算符模板要求其目标类支持与模板所提供运算符相关的操作. 遵循广为接受的 编码风格建议, 目标类通常被要求提供该概念"主运算符"的赋值对应运算符. 例如, addable 模板要求 operator+=(T const&), 并相应地提供 operator+(T const&, T const&).

关于概念使用的说明: 这里讨论的概念不一定是标准库的概念 (例如 CopyConstructible), 尽管其中一些可能与之对应; 它们是我们所说的 小写 'c' 的概念. 特别地, 它们与前者的不同之处在于, 它们 不 描述其要求定义的运算符的精确语义, 除以下要求外: (a) 归入同一概念的各运算符的语义应当一致 (例如, 求值 a += b 与 a = a + b 表达式的效果应当相同); 以及 (b) 运算符的返回类型应遵循内置类型相应运算符返回类型的语义 (例如, operator< 应返回可转换为 bool 的类型, 而 T::operator-= 应返回可转换为 T 的类型). 这类"宽松"的要求使得 operators 库可适用于来自不同领域的更广泛的目标类集合, 即最终更为有用.

示例

该示例展示了如何将一些 算术运算符模板 用于几何点类模板.

template <class T>
class point    // note: private inheritance is OK here!
    : boost::addable< point<T>          // point + point
    , boost::subtractable< point<T>     // point - point
    , boost::dividable2< point<T>, T    // point / T
    , boost::multipliable2< point<T>, T // point * T, T * point
      > > > >
{
public:
    point(T, T);
    T x() const;
    T y() const;

    point operator+=(const point&);
    // point operator+(point, const point&) automatically
    // generated by addable.

    point operator-=(const point&);
    // point operator-(point, const point&) automatically
    // generated by subtractable.

    point operator*=(T);
    // point operator*(point, const T&) and
    // point operator*(const T&, point) auto-generated
    // by multipliable.

    point operator/=(T);
    // point operator/(point, const T&) auto-generated
    // by dividable.
private:
    T x_;
    T y_;
};

// now use the point<> class:
template <class T>
T length(const point<T> p)
{
    return sqrt(p.x()*p.x() + p.y()*p.y());
}

const point<float> right(0, 1);
const point<float> up(1, 0);
const point<float> pi_over_4 = up + right;
const point<float> pi_over_4_normalized = pi_over_4 / length(pi_over_4);

用法

双实参模板形式

二元运算符的实参通常具有相同类型, 但定义组合不同类型的运算符并不罕见. 例如, 可能希望把数学向量乘以标量. 算术运算符模板的双实参模板形式就是为此目的而提供的. 应用模板的双实参形式时, 运算符的期望返回类型通常决定了两个相关类型中应由哪一个派生自该运算符模板.

例如, 如果 T + U 的结果的类型为 T, 那么 T (而不是 U) 应当派生自 addable<T, U>. 比较模板 less_than_comparable<T,U>、equality_comparable<T, U>、equivalent<T, U> 和 partially_ordered<T, U> 是该准则的例外, 因为它们所定义运算符的返回类型是 bool.

在不支持部分特化的编译器上, 双实参形式必须使用下面所示、带尾部 '2' 的名称来指定. 带尾部 '1' 的单实参形式是为了对称性而提供的, 同时也为了支持 基类链接 技术的某些应用.

混合算术: 双实参模板形式的另一个应用是类型 T 与可转换为 U 的类型 T 之间的混合算术. 在这种情况下, 双实参模板形式有两个用武之地: 一是为运算符重载提供相应的签名, 二是性能.

就运算符重载而言, 假设例如 U 是 int, T 是用户定义的无限精度整数类型, 并且存在 double operator-(double, const T&).

如果想计算 int - T 而没有提供 T operator-(int, const T&), 编译器会认为 double operator-(double, const T&) 比 T operator-(const T&, const T&) 更匹配, 这可能与用户的意图不同.

为了定义完整的运算符签名集合, 还提供了双实参模板形式的附加 '左' 形式: subtractable2_left<T, U>、dividable2_left<T, U> 和 modable2_left<T, U>, 它们为 U 出现在左侧的非交换运算符定义签名 (operator-(const U&, const T&)、operator/(const U&, const T&)、operator%(const U&, const T&)).

就性能而言, 注意当人们使用单类型二元运算符进行混合类型算术时, 类型 U 的实参必须转换为类型 T. 然而在实践中, 比如 T::operator-=(const U&) 往往存在避免从 U 到 T 的不必要转换的更高效实现.

算术运算符的双实参模板形式创建了使用这些更高效实现的附加运算符接口. 但是, '左' 形式没有性能提升: 它们仍然需要从 U 到 T 的转换, 其实现等价于编译器在认为单类型二元运算符是最佳匹配时会自动生成的代码.

基类链接与对象大小

除 算术示例 与 迭代器辅助类 之外, 每个运算符类模板都有一个额外的但可选的模板类型参数 B. 该参数将成为实例化模板的公开派生基类. 这意味着它必须是类类型. 它可用于避免通常与从多个空基类多重继承相关的对象大小膨胀. 更多细节参见 旧版本用户须知.

为了支持一组运算符, 使用 B 参数把运算符模板链接成单基类层次结构, 在 用法示例 中有演示. 复合运算符模板也使用这一技术来组合运算符定义. 如果链接对编译器而言过长, 可以尝试用单个把旧模板链接在一起的分组运算符模板替换其中一些运算符模板; 长度限制只适用于链中直接的模板数量, 不适用于隐藏在分组模板中的模板.

注意: 当链接到 不是 Boost 运算符模板的基类, 而使用的是 Boost 运算符模板的 单实参形式 时, 必须在名称中带尾部 '1' 指定该运算符模板. 否则, 本库会假定你的意思是定义一个组合你要用作基类的类与你的派生类的二元运算.

单独显式实例化

在某些编译器 (例如 Borland、GCC) 上, 即使单继承在某些情况下似乎也会导致对象大小增加. 如果你定义的不是类模板, 通过完全避免派生、改为如下显式实例化运算符模板, 可能获得更好的对象大小性能:

class my_class // lose the inheritance...
{
    //...
};

// explicitly instantiate the operators I need.
template struct less_than_comparable<my_class>;
template struct equality_comparable<my_class>;
template struct incrementable<my_class>;
template struct decrementable<my_class>;
template struct addable<my_class,long>;
template struct subtractable<my_class,long>;

注意, 某些运算符模板不能使用这一变通办法, 而必须是其主操作数类型的基类. 这些模板定义的运算符必须是成员函数, 而变通办法需要这些运算符是独立的 friend 函数. 相关模板有:

  • dereferenceable<>
  • indexable<>
  • 任何包含上述至少一个的复合运算符模板

正如 Daniel Krugler 指出的, 这一技术违反 C++11 §14.6.5/2 [temp.inject], 因而是不可移植的. 理由是: 实例化例如 less_than_comparable<my_class> 所注入的运算符无法按照 C++11 §3.4.2/2 [basic.lookup.argdep] 给出的规则通过 ADL 找到, 因为 my_class 不是 less_than_comparable<my_class> 的关联类. 因此, 仅在其他所有办法都失败时才使用这一技术.

要求的可移植性

许多编译器 (例如 MSVC 6.3、GCC 2.95.2) 在依赖于运算符模板表中要求的操作真正被使用之前, 不会强制执行这些要求. 这是不符合标准的行为. 特别是, 尽管把所有需要二元运算符的类都从 operators<> 与 operators2<> 模板派生会很方便 (无论它们是否实现这些模板的全部要求), 这种捷径是不可移植的. 即使它目前在你的编译器上可行, 以后也可能不行.

算术运算符

算术运算符模板简化了创建自定义数值类型的任务. 给定一组核心运算符, 这些模板会向数值类添加相关运算符. 这些操作类似于标准算术类型所具有的操作, 可能包括比较、加法、递增、逻辑与按位操作等. 此外, 由于大多数数值类型需要不止一个这样的运算符, 某些模板被提供用于在一条声明中组合多个基本运算符模板.

用于实例化简单运算符模板的类型的要求以必须有效的表达式及该表达式的返回类型来指定. 复合运算符模板只列出它们所使用的其他模板. 复合运算符模板所提供的操作和要求可以从所列组件的操作和要求推断出来.

排序说明: less_than_comparable<T> 与 partially_ordered<T> 模板提供相同的运算集合. 但是, less_than_comparable<T> 的工作方式假定类型 T 的所有值都可以置于全序中. 如果情况并非如此 (例如 IEEE 浮点算术中的非数值 NaN), 则应当使用 partially_ordered<T>. partially_ordered<T> 模板可用于全序类型, 但它不如 less_than_comparable<T> 高效. less_than_comparable<T, U> 与 partially_ordered<T,U> 对于所有 T 值与 U 值的排序也适用同样的规则; equivalent<> 的两个版本亦是如此. 对 equivalent<> 的解决办法是为目标类编写自定义的 operator==.

对称性说明: 在讨论对称性之前, 我们需要先讨论优化, 以理解运算符采用不同实现方式的原因. 以 operator+ 为例来考察类 T:

T operator+( const T& lhs, const T& rhs )
{
    return T( lhs ) += rhs;
}

这会是 operator+ 的一种常规实现, 但它不是高效的实现. 会创建 lhs 的一个未命名局部拷贝, 对它调用 operator+=, 然后把它拷贝到函数返回值中 (返回值是另一个类型为 T 的未命名对象). 标准通常不允许把中间对象优化掉:

C++11 §3.7.3/3 [basic.stc.auto]: 自动存储期: 如果具有自动存储期的变量有带副作用的初始化或析构函数, 则它不得在其块结束之前被销毁, 也不得作为优化而被消除, 即使它看起来未被使用; 除非按照 12.8 的规定可以消除类对象或其拷贝/移动.

对 §12.8 的引用对我们很重要:

C++11 §12.8/31 [class.copy]: 类对象的拷贝与移动: 当满足某些条件时, 实现允许省略类对象的拷贝/移动构造, 即使该对象的拷贝/移动构造函数和/或析构函数具有副作用. (...) 这种拷贝/移动操作的省略称为 拷贝消除, 在以下情况下是允许的 (这些情况可以组合起来以消除多次拷贝):

— 在返回类型为类类型的函数中的 return 语句中, 当表达式是一个与函数返回类型具有相同 cv 非限定类型的非 volatile 自动对象 (函数形参或 catch 子句形参除外) 的名字时, 可以通过把该自动对象直接构造到函数返回值中来省略拷贝/移动操作

(…)

这一优化被称为具名返回值优化 (NRVO), 由此我们得到 operator+ 的如下实现:

T operator+( const T& lhs, const T& rhs )
{
    T nrv( lhs );
    nrv += rhs;
    return nrv;
}

有了这一实现, 编译器就被允许移除中间对象. 遗憾的是, 并非所有编译器都实现了 NRVO, 有些甚至以不正确的方式实现它, 使其在这里毫无用处. 在没有 NRVO 的情况下, NRVO 友好的代码并不比上面给出的原始代码差, 但还有一种可能的实现, 它有一些非常特殊的性质:

T operator+( T lhs, const T& rhs )
{
    return lhs += rhs;
}

与第一个实现的区别在于, lhs 不是作为用于创建拷贝的常量引用; 相反, lhs 是按值传递的形参, 因此它已经是所需的拷贝. 这在某些情况下允许另一种优化 (C++11 §12.2/2 [class.temporary]).

考虑 a + b + c, 其中 a + b 的结果在用作 lhs 加上 c 时不会被拷贝. 这比原始代码更高效, 但不如使用 NRVO 的编译器高效. 对大多数人而言, 对于未实现 NRVO 的编译器, 这仍然是更好的选择, 但 operator+ 现在有了不同的函数签名. 此外, (a + b) + c 与 a + (b + c) 创建的对象数量也不同.

很可能这不会对你造成问题, 但如果你的代码依赖函数签名或严格的对称行为, 你应该在 user-config 中设置 BOOST_FORCE_SYMMETRIC_OPERATORS. 这将强制使用 NRVO 友好的实现, 即使编译器没有实现 NRVO.

解引用运算符与迭代器辅助类

迭代器辅助 模板简化了创建自定义迭代器的任务. 与算术类型类似, 一个完整的迭代器有许多"冗余"运算符, 它们可以基于核心运算符集合来实现.

解引用运算符 的动机来自 迭代器辅助类, 但它们在非迭代器环境中也常常有用. 许多冗余的迭代器运算符同时也是算术运算符, 因此迭代器辅助类借用了上面定义的许多运算符. 事实上, 只需要定义两个新运算符: 指向成员的 operator-> 和下标 operator[].

迭代器辅助类说明:

  1. 与其他迭代器辅助类模板不同, output_iterator_helper 只接受一个模板参数 - 其目标类的类型. 尽管对某些人来说这似乎是不必要的限制, 但标准要求任何输出迭代器的 difference_type 与 value_type 必须是 void (C++11 §24.4.1 [lib.iterator.traits]), 而 output_iterator_helper 模板遵循这一要求. 此外, 标准中的输出迭代器具有 void 的 pointer 与 reference 类型, 因此 output_iterator_helper 也这样做.
  2. 由于自代理是实现输出迭代器最简单且最常见的方式 (例如, 标准库中的 insert (C++11 §24.5.2 [insert.iterators]) 与流迭代器 (C++11 §24.6 [stream.iterators])), output_iterator_helper 通过定义 operator* 与 operator++ 成员函数 (它们只返回对迭代器自身的非 const 引用) 来支持这一惯用法. 在许多情况下, 对自代理的支持使我们能够把编写输出迭代器的任务简化为只编写两个成员函数 - 一个合适的构造函数和一个拷贝赋值运算符. 例如, 下面是 boost::function_output_iterator 适配器的一个可能实现:
template<class UnaryFunction>
struct function_output_iterator
    : boost::output_iterator_helper< function_output_iterator<UnaryFunction> >
{
    explicit function_output_iterator(UnaryFunction const& f = UnaryFunction())
        : func(f) {}

    template<typename T>
    function_output_iterator& operator=(T const& value)
    {
        this->func(value);
        return *this;
    }

private:
    UnaryFunction func;
};

注意, 对自代理的支持并不会妨碍你使用 output_iterator_helper 来简化其他不同类型输出迭代器的实现. 如果 output_iterator_helper 的目标类型自行提供了 operator* 和/或 operator++ 的定义, 那么将使用这些运算符, 而 output_iterator_helper 提供的运算符将永远不会被实例化.

迭代器演示与测试程序

iterators_test.cpp 程序演示了迭代器模板的使用, 也可用于验证操作的正确性. 下面是测试程序中定义的自定义迭代器. 它演示了核心操作的一个正确 (尽管平凡) 的实现, 只有定义了这些核心操作, 迭代器辅助类才能"填充"其余的迭代器操作.

template <class T, class R, class P>
struct test_iter
    : public boost::random_access_iterator_helper<
                test_iter<T, R, P>, T, std::ptrdiff_t, P, R
             >
{
    typedef test_iter self;
    typedef R Reference;
    typedef std::ptrdiff_t Distance;

public:
    explicit test_iter(T* i =0);
    test_iter(const self& x);
    self& operator=(const self& x);
    Reference operator*() const;
    self& operator++();
    self& operator--();
    self& operator+=(Distance n);
    self& operator-=(Distance n);
    bool operator==(const self& x) const;
    bool operator<(const self& x) const;
    friend Distance operator-(const self& x, const self& y);
};

旧版本用户须知

库接口的变更与推荐用法 源于下文所述的一些实际问题. 新版本的库仍然向后兼容旧版本, 因此你 不被强制 更改任何现有代码, 但旧用法已被弃用.

虽然它可以说比使用 基类链接 更简单直观, 但人们发现, 从多个运算符模板派生的旧做法可能导致生成的类远大于应有的大小. 大多数现代 C++ 编译器会显著膨胀从多个空基类派生的类的大小, 即使基类本身没有状态. 例如, point<int> 的大小 (参见上面的 示例) 在 Win32 平台的各个编译器上是 12-24 字节, 而不是预期的 8 字节.

严格来说, 这并不是库的错 - 语言规则允许编译器在这种情况下应用 空基类优化. 原则上, 任意数量的空基类都可以分配在相同的偏移处, 只要它们没有共同的祖先 (参见 C++11 标准 §10 [class.derived] 第 8 段).

但语言定义也 不要求 实现去做这一优化, 而当今的编译器在涉及多重继承时几乎都没有实现它. 更糟糕的是, 实现者极不可能把它作为对未来编译器的增强而采纳, 因为这会破坏同一编译器的两个不同版本生成的代码之间的二进制兼容性. 正如 Matt Austern 所说, "你有自由做这类事情的时候屈指可数, 其中之一就是面向新架构的时候…". 另一方面, 许多常见的编译器会对单继承层次结构使用空基优化.

考虑到这一问题对本库用户的重要性 (本库旨在用于编写像 MyInt 或 point<> 这样的轻量级类), 以及上述种种因素, 我们决定更改库接口, 使得即使在只支持最简单形式的空基类优化的编译器上, 对象大小的膨胀也能被消除. 当前的库接口就是这些更改的结果. 虽然新用法比旧用法稍微复杂一些, 我们认为让库在真实世界中更有用是值得的. Alexy Gurtovoy 贡献了支持新用法的代码, 同时保持库向后兼容.
