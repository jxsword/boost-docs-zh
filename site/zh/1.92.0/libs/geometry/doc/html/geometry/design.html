设计理由

假设你需要一个计算两点间距离的 C++ 程序. 你可能会定义一个结构体:

struct mypoint
{
    double x, y;
};

以及一个包含该算法的函数:

double distance(mypoint const& a, mypoint const& b)
{
    double dx = a.x - b.x;
    double dy = a.y - b.y;
    return sqrt(dx * dx + dy * dy);
}

相当简单, 也能用, 但并不通用. 作为库, 其设计必须走得更远. 上面的设计只能用于笛卡尔坐标系中的二维点, 且仅适用于结构体 mypoint (不能用于其他结构体). 一个通用库应当能够计算以下情形的距离:

  • 针对任意点类或结构体, 而不只是 mypoint 这一类型
  • 在二维以上的维度中
  • 针对其他坐标系, 例如地球表面或球面
  • 点与线之间, 或其他几何组合之间
  • 以高于 double 的精度
  • 避免开平方: 我们通常不想这么做, 因为它是相对昂贵的函数, 而且比较距离时也没有必要

在本节及后续各节中, 我们将逐步使这一设计更加通用.

使用模板

距离函数可以改写为模板函数. 这很简单, 使得除 mypoint 之外的其他点类型也能计算距离. 我们增加两个模板参数, 以允许输入两种不同的点类型.

template <typename P1, typename P2>
double distance(P1 const& a, P2 const& b)
{
    double dx = a.x - b.x;
    double dy = a.y - b.y;
    return std::sqrt(dx * dx + dy * dy);
}

这个模板版本稍好一些, 但好得不多.

考虑一个成员变量受保护的 C++ 类... 这样的类不允许直接访问 x 与 y 成员. 所以, 本节内容很短, 我们直接继续.

使用特征

我们需要采用一种通用方法, 允许任何点类型作为距离函数的输入. 不直接访问 x 与 y 成员, 而是利用特征 (traits) 系统增加几层间接. 该函数于是变为:

template <typename P1, typename P2>
double distance(P1 const& a, P2 const& b)
{
    double dx = get<0>(a) - get<0>(b);
    double dy = get<1>(a) - get<1>(b);
    return std::sqrt(dx * dx + dy * dy);
}

改造后的距离函数使用一个泛型 get 函数 (以维度作为模板参数) 来访问点的坐标. 该 get 转发到特征系统, 其定义如下:

namespace traits
{
    template <typename P, int D>
    struct access {};
}

随后为我们的 mypoint 类型对其进行特化, 实现一个名为 get 的静态方法:

namespace traits
{
    template <>
    struct access<mypoint, 0>
    {
        static double get(mypoint const& p)
        {
            return p.x;
        }
    };
    // same for 1: p.y
    ...
}

调用 traits::access<mypoint, 0>::get(a) 现在即可返回我们的 x 坐标. 很妙, 不是吗? 对于库中如此常用的函数而言, 这样写太啰嗦了. 我们可以增加一个额外的自由函数来缩短语法:

template <int D, typename P>
inline double get(P const& p)
{
    return traits::access<P, D>::get(p);
}

这使得我们可以调用 get<0>(a), 对任何具有 traits::access 特化的点均可, 正如本节开头的距离算法所示. 因此我们希望支持拥有形如 x() 方法的类, 只要存在对访问特征 struct 的特化, 并提供一个静态函数 get 返回 x() (对应维度 0), 对维度 1 和 y() 也是如此.

维度无关性

现在我们可以计算二维点之间、任意结构体或类的点之间的距离了. 不过, 我们还想支持三维. 因此必须使其与维度无关. 这会让距离函数变得复杂. 我们可以用 for 循环遍历各维度, 但循环的性能与最初那种直接的坐标相加并不相同. 不过, 我们可以进一步利用模板, 把距离算法写成如下形式——更复杂, 但对模板爱好者很有吸引力:

template <typename P1, typename P2, int D>
struct pythagoras
{
    static double apply(P1 const& a, P2 const& b)
    {
        double d = get<D-1>(a) - get<D-1>(b);
        return d * d + pythagoras<P1, P2, D-1>::apply(a, b);
    }
};

template <typename P1, typename P2 >
struct pythagoras<P1, P2, 0>
{
    static double apply(P1 const&, P2 const&)
    {
        return 0;
    }
};

距离函数会调用该 pythagoras 结构, 并指定维度数:

template <typename P1, typename P2>
double distance(P1 const& a, P2 const& b)
{
    static_assert(dimension<P1>::value == dimension<P2>::value,
        "Distance can only be computed for points of same dimension.");

    return sqrt(pythagoras<P1, P2, dimension<P1>::value>::apply(a, b));
}

所引用的维度由另一个特征类定义:

namespace traits
{
    template <typename P>
    struct dimension {};
}

它同样需要针对 struct mypoint 再次特化.

由于它只需要发布一个值, 我们干脆让它派生自 Boost.MPL 的 class boost::mpl::int_:

namespace traits
{
    template <>
    struct dimension<mypoint> : boost::mpl::int_<2>
    {};
}

与自由 get 函数一样, 库中也包含一个维度元函数 (meta-function).

template <typename P>
struct dimension : traits::dimension<P>
{};

后文会解释为什么这个额外的声明有用. 现在我们实现了维度数量上的无关性. 更通用的距离函数现在可以接受三维或更多维的点. 编译期断言会阻止点 a 为二维而点 b 为三维的情况.

坐标类型

上文我们假定坐标是 double. 如果我们的点是整数呢?

我们可以轻松增加一个特征类, 后面就会这么做. 不过, 两个整数坐标之间的距离仍可能是分数值. 此外, 设计目标之一是避免开平方. 这些情况会在下面另一节中处理. 目前我们仍返回 double, 但允许点类型使用整数坐标. 为定义坐标类型, 我们再增加一个特征类 coordinate_type, 它应由库用户特化:

namespace traits
{
    template <typename P>
    struct coordinate_type{};

    // specialization for our mypoint
    template <>
    struct coordinate_type<mypoint>
    {
        typedef double type;
    };
}

与访问函数的情形类似 (我们有一个自由 get 函数), 这里也增加一个代理. 后文会给出更长的版本, 短版本函数如下:

template <typename P>
struct coordinate_type :    traits::coordinate_type<P> {};

现在可以再次修改距离算法. 由于它仍返回 double, 我们只需修改 pythagoras 计算类. 它应当返回其输入的坐标类型. 但它有两个可能不同的输入点类型, 两者的坐标类型也可能不同. 虽然这种情况不太可能发生, 但我们设计的是通用库, 应当处理这些奇怪的情况. 我们必须在两种坐标类型中做出选择, 当然选择精度最高的那种. 这里不展开实现, 那会太长, 而且与几何无关. 我们只假设存在一个元函数 select_most_precise 来选出最佳类型.

于是我们的计算类变为:

template <typename P1, typename P2, int D>
struct pythagoras
{
    typedef typename select_most_precise
        <
            typename coordinate_type<P1>::type,
            typename coordinate_type<P2>::type
        >::type computation_type;

    static computation_type apply(P1 const& a, P2 const& b)
    {
        computation_type d = get<D-1>(a) - get<D-1>(b);
        return d * d + pythagoras <P1, P2, D-1> ::apply(a, b);
    }
};

不同几何类型

我们已经设计出一个维度无关的系统, 支持任意坐标类型的任意点类型. 还有一些细节待调整, 留待以后处理. 现在来看如何计算点到多边形、点到线段之间的距离. 这些公式更复杂, 对设计的影响也更大. 我们不想再增加一个用别的名字命名的函数:

template <typename P, typename S>
double distance_point_segment(P const& p, S const& s)

我们希望保持通用, 距离函数必须能被不了解其所处理几何类型的代码调用, 因此它必须命名为 distance. 我们也不能创建重载, 因为模板签名相同会产生歧义. 有两种解决方案:

  • 标签分派 (tag dispatching)
  • SFINAE

我们选择标签分派, 因为它契合特征系统. Boost.Geometry 的早期版本 (预览版) 曾使用 SFINAE, 但我们发现对于如此庞大的设计它有若干缺点, 于是改用了标签分派.

借助标签分派, 距离算法会检查输入参数的几何类型. 距离函数将改成这样:

template <typename G1, typename G2>
double distance(G1 const& g1, G2 const& g2)
{
    return dispatch::distance
        <
            typename tag<G1>::type,
            typename tag<G2>::type,
            G1, G2
        >::apply(g1, g2);
}

它引用 tag 元函数, 并把调用转发给 apply 方法, 该方法属于 dispatch::distance 结构. tag 元函数是另一个特征类, 应针对每种点类型进行特化, 两者如下所示:

namespace traits
{
    template <typename G>
    struct tag {};

    // specialization
    template <>
    struct tag<mypoint>
    {
        typedef point_tag type;
    };
}

自由元函数, 如 coordinate_system 与 get:

template <typename G>
struct tag : traits::tag<G> {};

标签 (point_tag, segment_tag 等) 是空结构体, 用途是为分派结构体提供特化依据. distance 的分派结构体及其各特化都定义在一个单独的命名空间中, 形式如下:

namespace dispatch {
    template < typename Tag1, typename Tag2, typename G1, typename G2 >
    struct distance
    {};

    template <typename P1, typename P2>
    struct distance < point_tag, point_tag, P1, P2 >
    {
        static double apply(P1 const& a, P2 const& b)
        {
            // here we call pythagoras
            // exactly like we did before
            ...
        }
    };

    template <typename P, typename S>
    struct distance
    <
        point_tag, segment_tag, P, S
    >
    {
        static double apply(P const& p, S const& s)
        {
            // here we refer to another function
            // implementing point-segment
            // calculations in 2 or 3
            // dimensions...
            ...
        }
    };

    // here we might have many more
    // specializations,
    // for point-polygon, box-circle, etc.

} // namespace

所以, 这是可行的; 距离算法现在已经通用, 意义在于它也支持不同的几何类型. 一个缺点是: 我们必须分别为 point - segment 与 segment - point 定义两个分派特化. 这也会在下面的“可逆性”一节中解决. 下面的示例展示了我们目前的成果: 不同的点类型、几何类型与维度.

point a(1,1);
point b(2,2);
std::cout << distance(a,b) << std::endl;
segment s1(0,0,5,3);
std::cout << distance(a, s1) << std::endl;
rgb red(255, 0, 0);
rbc orange(255, 128, 0);
std::cout << "color distance: " << distance(red, orange) << std::endl;

再谈内核

上文提到我们有一个特征类 coordinate_type, 定义在 traits 命名空间中, 同时还定义了一个单独的 coordinate_type 类. 在此之前这其实并不真正必要, 因为二者唯一的区别就是命名空间子句. 但现在我们有了另一种几何类型 (此处是线段), 这就必不可少了. 我们可以对任何几何类型 (点、线段、多边形等) 调用 coordinate_type 元函数, 它同样通过标签分派实现:

template <typename G>
struct coordinate_type
{
    typedef typename dispatch::coordinate_type
        <
            typename tag<G>::type, G
        >::type type;
};

在 dispatch 命名空间内部, 该元函数有两个实现: 泛型版本和针对点的特化. 针对点的特化调用特征类. 泛型版本调用点的特化, 有点像递归的元函数定义:

namespace dispatch
{

    // Version for any geometry:
    template <typename GeometryTag, typename G>
    struct coordinate_type
    {
        typedef typename point_type
            <
                GeometryTag, G
            >::type point_type;

        // Call specialization on point-tag
        typedef typename coordinate_type < point_tag, point_type >::type type;
    };

    // Specialization for point-type:
    template <typename P>
    struct coordinate_type<point_tag, P>
    {
        typedef typename
            traits::coordinate_type<P>::type
            type;
    };
}

因此它调用另一个元函数 point_type. 这里不展开细讲, 但要知道它对所有几何类型都可用, 它会 typedef 出构成该几何的点类型, 命名为 type.

元函数 dimension 以及后面将出现的坐标系元函数也是如此.

坐标系

到目前为止我们假定的都是笛卡尔坐标系. 但我们知道地球并不是平的. 用上面的系统计算两个 GPS 点之间的距离会得出毫无意义的结果. 于是我们再次扩展设计. 我们再次利用特征系统为每种点类型定义一个坐标系类型, 然后让计算依赖于该坐标系.

坐标系与坐标类型类似, 也是一个元函数, 通过调用分派函数使之适用于任何几何类型, 再转发到其点的特化, 最后调用特征类, 在其中用 typedef 定义 type 为一个坐标系. 这些就不再全部展示了. 我们只给出几个坐标系的定义:

struct cartesian {};

template<typename DegreeOrRadian>
struct geographic
{
    typedef DegreeOrRadian units;
};

可见笛卡尔坐标系很简单; 对于地理坐标系, 还可以选择坐标以度还是以弧度存储.

距离函数现在要变了: 它会为相应的坐标系选择计算方法, 然后调用 distance 的分派结构体. 我们把针对坐标系特化的计算方法称为策略 (strategy). 于是距离函数的新版本是:

template <typename G1, typename G2>
double distance(G1 const& g1, G2 const& g2)
{
    typedef typename strategy_distance
        <
            typename coordinate_system<G1>::type,
            typename coordinate_system<G2>::type,
            typename point_type<G1>::type,
            typename point_type<G2>::type,
            dimension<G1>::value
        >::type strategy;

    return dispatch::distance
        <
            typename tag<G1>::type,
            typename tag<G2>::type,
            G1, G2, strategy
        >::apply(g1, g2, strategy());
}

这里提到的 strategy_distance 是一个结构体, 针对不同的坐标系有不同特化.

template <typename T1, typename T2, typename P1, typename P2, int D>
struct strategy_distance
{
    typedef void type;
};

template <typename P1, typename P2, int D>
struct strategy_distance<cartesian, cartesian, P1, P2, D>
{
    typedef pythagoras<P1, P2, D> type;
};

于是, 我们的 pythagoras 又出现了, 这次定义为策略. distance 的分派函数只调用其 apply 方法.

这是重要的一步: 对于球面或地理坐标系, 可以实现另一种策略 (计算方法). 球面坐标系有半正矢 (haversine) 公式. 于是分派特征结构体的特化如下

template <typename P1, typename P2, int D = 2>
struct strategy_distance<spherical, spherical, P1, P2, D>
{
    typedef haversine<P1, P2> type;
};

// struct haversine with apply function
// is omitted here

对于地理坐标系, 距离计算有若干选择: Andoyer 方法快速而精确, Vincenty 方法较慢但更精确, 还有一些精度较低的方法.

每个坐标系都有一个策略被定义为默认策略. 为了也能使用其他策略, 我们再次修改设计, 为 distance 算法增加一个重载, 将策略对象作为第三个参数.

这个新的重载 distance 函数还有个好处: 策略可以在 distance 函数之外构造. 由于上文策略是在函数内部构造的, 它无法拥有构造参数. 但对 Andoyer、Vincenty 或半正矢公式而言, 提供一个以地球半径为参数的构造函数显然很有意义.

于是, distance 的重载函数为:

template <typename G1, typename G2, typename S>
double distance(G1 const& g1, G2 const& g2, S const& strategy)
{
    return dispatch::distance
        <
            typename tag<G1>::type,
            typename tag<G2>::type,
            G1, G2, S
        >::apply(g1, g2, strategy);
}

策略必须有一个 apply 方法, 以两个点作为参数 (针对点的情况). 它不必须是静态方法. 策略可以定义一个构造函数, 传入配置值并保存为成员变量. 在这种情况下静态方法会不方便. 它可以实现为普通方法 (带 const 限定符).

我们这里不列出全部实现——Vincenty 会占半页数学推导, 但你能理解其思想. 我们可以这样调用 distance:

distance(c1, c2)

其中 c1 与 c2 是笛卡尔点, 或者这样调用:

distance(g1, g2)

其中 g1 与 g2 是地理点, 调用针对地理点的默认策略 (如 Andoyer), 或者这样调用:

distance(g1, g2, vincenty<G1, G2>(6275))

其中显式指定了策略, 并用半径构造.

点概念

前几节提到的五个特征类共同构成点概念 (Point Concept). 任何在 traits 命名空间中实现了特化的点类型都应被接受为有效类型. 因此点概念由以下部分组成:

  • traits::tag 的一个特化
  • traits::coordinate_system 的一个特化
  • traits::coordinate_type 的一个特化
  • traits::dimension 的一个特化
  • traits::access 的一个特化

最后一个是类, 包含 get 方法和 (可选的) set 方法; 前四个是元函数, 或定义 type 或声明一个值 (遵循 MPL 惯例).

至此我们实现了维度数量无关和坐标系无关; 该设计可以处理任何坐标类型, 也能处理不同的几何类型. 此外我们还可以指定自己的策略; 两个点维度不同时代码无法编译 (因为断言), 两个点坐标系不同时也无法编译 (因为没有特化). 库可以检查点类型是否满足概念所施加的要求. 这将在后面的概念检查 (Concept Checking) 一节中介绍.

返回类型

我们曾承诺, 调用 std::sqrt 并非总是必要. 因此我们定义一个距离结果 struct, 它包含平方值且可转换为 double 值. 不过, 只需要对 pythagoras 这样做. 球面距离函数不做开平方, 因此无需避免昂贵的开平方调用, 可以直接返回距离.

因此距离结果结构体依赖于策略, 于是被做成策略的成员类型. 结果结构体如下:

template<typename T = double>
struct cartesian_distance
{
    T sq;
    explicit cartesian_distance(T const& v) : sq (v) {}

    inline operator T() const
    {
        return std::sqrt(sq);
    }
};

它还定义了运算符, 可以在不开平方的情况下与其他结果比较.

每个策略都应在策略类内部定义其返回类型, 例如:

typedef cartesian_distance<T> return_type;

或者:

typedef double return_type;

分别对应笛卡尔 (毕达哥拉斯) 与球面.

同样如预期, 我们的 distance 函数将再次修改以体现新的返回类型. 对于带策略的重载, 并不复杂:

template < typename G1, typename G2, typename Strategy >
typename Strategy::return_type distance( G1 const& G1 , G2 const& G2 , S const& strategy)

但对于不带策略的版本, 我们必须选择策略、坐标类型等. 一行代码写不下, 所以我们增加一个单独的元函数:

template <typename G1, typename G2 = G1>
struct distance_result
{
    typedef typename point_type<G1>::type P1;
    typedef typename point_type<G2>::type P2;
    typedef typename strategy_distance
        <
            typename cs_tag<P1>::type,
            typename cs_tag<P2>::type,
            P1, P2
        >::type S;

    typedef typename S::return_type type;
};

并修改我们的 distance 函数:

template <typename G1, typename G2>
inline typename distance_result<G1, G2>::type distance(G1 const& g1, G2 const& g2)
{
    // ...
}

当然, 分派特化中的 apply 函数也将返回这样的结果. 它们到处都以策略作为模板参数, 这使得更简洁的版本成为可能.

轴顺序

对开发 GIS 应用、要求符合 OGC 标准或使用多种坐标参考系统 (CRS) 的用户来说, 这是一条重要提示.

Boost.Geometry 的约定是: 二维元组的坐标值始终按数学轴顺序给出, 即 X,Y. 对 GIS 应用而言, 这总是意味着东坐标,北坐标; 用地理坐标系的术语说就是经度,纬度. Boost.Geometry 不允许也不遵循坐标参考系统 (CRS) 所指定的轴顺序来排列坐标值.

在实践中, 用户可以轻松适配采用其他轴顺序的点类型, 并按 Boost.Geometry 期望的顺序指定坐标访问.

小结

在本设计原理中, 我们使用标签分派、概念、特征与元编程逐步设计了 Boost.Geometry. 我们用广为人知的 distance 函数来展示这一设计.

Boost.Geometry 的设计如上文所述, 此外还运用了一些别的技术: 自动反转模板参数、标签转换 (tag casting), 以及在其他分派类中把实现类或分派类复用为策略.
