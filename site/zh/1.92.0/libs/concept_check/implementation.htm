警告

本文档已过时; 现在使用的是类似但更新的实现技术. 本文档还引用了库旧接口中的组件和协议, 例如 BOOST_CLASS_REQUIRES 和 constraints() 函数, 它们仍受支持但已弃用.

实现

理想情况下, 我们希望在实例化点捕获并指明概念违规. 如 D&E[2] 中所述, 可以通过练习函数模板所需的全部要求来捕获错误. 具体如何练习这些要求 (尤其是有效表达式) 是个棘手的问题, 因为我们希望代码被编译——而不是被执行. 我们的做法是: 把练习要求的过程放在一个单独的函数中, 并把它赋给一个函数指针. 这样, 编译器会实例化该函数, 但不会真正调用它. 此外, 优化编译器会把该指针赋值当作 "死代码" 移除 (不过无论如何, 该赋值增加的运行期开销都可以忽略不计). 可以设想, 编译器或许会一开始就跳过约束函数的语义分析和编译, 从而使我们的函数指针技术失效. 然而, 这不太可能, 因为移除不必要的代码和函数通常是编译器后期阶段的工作. 我们已在 GNU C++、Microsoft Visual C++ 以及若干基于 EDG 的编译器 (KAI C++、SGI MIPSpro) 上成功使用了函数指针技术. 下面的代码展示了如何把该技术应用于 std::stable_sort() 函数:

  template <class RandomAccessIterator>
  void stable_sort_constraints(RandomAccessIterator i)
  {
    typename std::iterator_traits<RandomAccessIterator>
      ::difference_type n;
    i += n;  // exercise the requirements for RandomAccessIterator
    ...
  }
  template <class RandomAccessIterator>
  void stable_sort(RandomAccessIterator first, RandomAccessIterator last)
  {
    typedef void (*fptr_type)(RandomAccessIterator);
    fptr_type x = &stable_sort_constraints;
    ...
  }

通常需要检查的要求集合很大, 让库实现者为每个公开函数编写像 stable_sort_constraints() 这样的约束函数会很繁琐. 因此, 我们按照相应概念的定义, 把若干有效表达式组合成组. 对每个概念, 我们定义一个概念检查类模板, 其模板参数是被检查的类型. 该类包含一个 constraints() 成员函数, 练习该概念的所有有效表达式. 约束函数中使用的对象 (如 n 和 i) 被声明为概念检查类的数据成员.

  template <class Iter>
  struct RandomAccessIteratorConcept
  {
    void constraints()
    {
      i += n;
      ...
    }
    typename std::iterator_traits<RandomAccessIterator>
      ::difference_type n;
    Iter i;
    ...
  };

我们仍然可以用函数指针机制来促使约束函数被实例化, 只不过现在它是成员函数指针. 为了让库实现者方便地调用概念检查, 我们把成员函数指针机制包装在一个名为 function_requires() 的函数中. 下面的代码片段展示了如何使用 function_requires() 来确保迭代器是 RandomAccessIterator.

  template <class Iter>
  void stable_sort(Iter first, Iter last)
  {
    function_requires< RandomAccessIteratorConcept<Iter> >();
    ...
  }

function_requires() 的定义如下. Concept 是已经用建模类型实例化的概念检查类. 我们把 constraints 成员函数的地址赋给函数指针 x, 这会促使约束函数被实例化, 并检查该概念的有效表达式. 然后我们把 x 赋给 x 以避免未使用变量的编译器警告, 并把所有内容包在一个 do-while 循环中以防止名字冲突.

  template <class Concept>
  void function_requires()
  {
    void (Concept::*x)() = BOOST_FPTR Concept::constraints;
    ignore_unused_variable_warning(x);
  }

为了检查类模板的类型参数, 我们提供了 BOOST_CLASS_REQUIRE 宏, 它可以用在类定义体内 (而 function_requires() 只能用在函数体内). 该宏声明一个嵌套类模板, 其模板参数是一个函数指针. 然后我们在一个 typedef 中使用该嵌套类类型, 以约束函数的函数指针类型作为模板实参. 我们在嵌套类和 typedef 的名字中使用 type_var 和 concept 名称, 以帮助防止名字冲突.

#define BOOST_CLASS_REQUIRE(type_var, ns, concept) \
  typedef void (ns::concept <type_var>::* func##type_var##concept)(); \
  template <func##type_var##concept _Tp1> \
  struct concept_checking_##type_var##concept { }; \
  typedef concept_checking_##type_var##concept< \
    BOOST_FPTR ns::concept<type_var>::constraints> \
    concept_checking_typedef_##type_var##concept

此外, 还有接受更多参数的 BOOST_CLASS_REQUIRE 版本, 用于处理包含两个或更多类型之间交互的概念. BCCL 概念检查的实现中没有使用 BOOST_CLASS_REQUIRE, 因为有些编译器不实现函数指针类型的模板参数.
