一般配置

引言

本库使用了 <boost/config.hpp> 中的若干配置宏, 以及两个需要由应用程序提供的配置宏. 此外, 两个常用的编译器选项也会影响可用特性.

调试模式编译选项

  • 必须开启 C++ RTTI (各种断言会用到)
  • 可以开启或关闭 C++ 异常处理. 关闭后, 库的 错误处理支持显然就不再可用

发布模式编译选项

  • 可以开启或关闭 C++ RTTI. 关闭后, 使用 state_cast<>() 会导致编译期错误 (state_downcast<>() 仍然可用). 此外, 不得同时定义 BOOST_STATECHART_USE_NATIVE_RTTI
  • 可以开启或关闭 C++ 异常处理. 关闭后, 库的 错误处理支持显然就不再可用

应用定义的宏

使用本库的应用程序可以定义以下宏:

宏 含义
BOOST_STATECHART_USE_NATIVE_RTTI 定义此宏后, 库不再使用自己那套速度优化的 RTTI 实现, 而是改用原生 C++ RTTI (更多信息参见性能文档中的 RTTI 定制). 这会带来以下影响:
  • state_machine::state_base_type 变成多态类型. 也就是说, 将 typeid 作用于某个 state_machine::state_base_type 引用时, 结果引用的是一个 type_info 对象, 表示最派生状态类型 (most derived state type) 的类型
  • 自定义状态类型信息不再可用
  • 所有状态都少存一个指针, 使状态机内存占用量在最佳情况下减少约 15%
  • 在大多数情况下, 分派速度会下降. 这是因为在几乎所有平台上, 原生 C++ RTTI 值都要经过一次额外的间接寻址才能取得. 耗时数据参见性能文档中的 速度与可扩展性权衡
BOOST_STATECHART_RELAX_TRANSITION_CONTEXT 定义此宏后, 转换期间调用的动作序列会放宽. 也就是说, 在调用转换动作之前, 不再要求先退出直到最内层公共上下文 (innermost common context) 的所有状态 (UML 标准的要求). 相反, 转换动作可以是转换源状态或任何直接或间接外层上下文的成员, 并且一旦所有可能处于活动的内层状态都已退出, 就立即调用它. 随后, 在进入直至转换目标的所有状态之前, 先退出直至最内层公共上下文的所有剩余活动状态

对于之后要链接进同一可执行文件的所有翻译单元, 这两个宏必须一致地定义或一致地不定义. 否则将不可避免地导致 ODR 违规. 依据编译器与链接器技术的不同, 此类违规在链接期报错中可能有所体现, 也可能没有.
