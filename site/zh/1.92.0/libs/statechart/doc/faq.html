状态局部存储 (state-local storage) 到底好在哪里?

最好用一个例子来解释:

struct Active;
struct Stopped;
struct Running;
struct StopWatch : sc::state_machine< StopWatch, Active >
{
  // startTime_ remains uninitialized, because there is no reasonable default
  StopWatch() : elapsedTime_( 0.0 ) {}
  ~StopWatch()
  {
    terminate();
  }

  double ElapsedTime() const
  {
    // Ugly switch over the current state.
    if ( state_cast< const Stopped * >() != 0 )
    {
      return elapsedTime_;
    }
    else if ( state_cast< const Running * >() != 0 )
    {
      return elapsedTime_ + std::difftime( std::time( 0 ), startTime_ );
    }
    else // we're terminated
    {
      throw std::bad_cast();
    }
  }

  // elapsedTime_ is only meaningful when the machine is not terminated
  double elapsedTime_;
  // startTime_ is only meaningful when the machine is in Running
  std::time_t startTime_;
};

struct Active : sc::state< Active, StopWatch, Stopped >
{
  typedef sc::transition< EvReset, Active > reactions;

  Active( my_context ctx ) : my_base( ctx )
  {
    outermost_context().elapsedTime_ = 0.0;
  }
};

  struct Running : sc::state< Running, Active >
  {
    typedef sc::transition< EvStartStop, Stopped > reactions;

    Running( my_context ctx ) : my_base( ctx )
    {
      outermost_context().startTime_ = std::time( 0 );
    }

    ~Running()
    {
      outermost_context().elapsedTime_ +=
        std::difftime( std::time( 0 ), outermost_context().startTime_ );
    }
  };

  struct Stopped : sc::simple_state< Stopped, Active >
  {
    typedef sc::transition< EvStartStop, Running > reactions;
  };

这个 StopWatch 没有使用任何状态局部存储, 却实现了与 教程 StopWatch 相同的行为. 虽然对不熟悉的人来说这段代码可能更易读, 但它有一些原版没有的问题:

  • 这个 StopWatch 类的数据成员只有在状态机恰好处于某个特定状态时才有意义. 也就是说, 这些变量的生存期与包含它们的 StopWatch 对象的生存期并不一致. 由于这些生存期由状态的进入与退出动作管理, 所以当我们要在当前状态不明确的上下文中访问它们时, 就不得不使用一个丑陋的 switch 语句对当前状态进行分派 (见 StopWatch::ElapsedTime()). 这实质上复制了 FSM 的部分状态逻辑. 因此, 每当我们需要更改状态机的布局时, 很可能也必须修改这个丑陋的 switch. 更糟的是, 如果忘记修改 switch, 代码可能仍然能编译通过, 甚至可能悄无声息地做错事. 注意, 教程中的版本不可能出现这种情况, 它至少会抛出异常, 而且往往直接拒绝编译. 此外, 对于教程中的 StopWatch, 程序员第一次修改就能改对的概率要高得多, 因为计算流逝时间的代码就在更新这些变量的代码附近
  • 每当要引入新变量或修改既有变量的类型时, 我们都必须修改 StopWatch 类. 也就是说, FSM 中的许多改动很可能都会连带修改 StopWatch 类. 因此, 在所有不采用状态局部存储的 FSM 中, state_machine<> 子类型都会成为改动热点 (change hotspot), 而这几乎可以肯定是糟糕设计的征兆

对于这样一个由单个程序员在单个翻译单元中轻松实现的小例子, 上述两点算不上什么问题. 然而, 对于一个分布在多个翻译单元 (甚至可能由不同程序员维护) 的大型复杂状态机, 它们很快就会成为大问题.

如何向客户端隐藏状态机的内部运作?

要理解这为什么可能以及如何做到, 关键是回顾以下事实:

  • C++ 类模板的成员函数在其被实际调用的位置实例化. 如果函数从未被调用, 它就不会被实例化, 也就不会生成哪怕一条汇编指令
  • InitialState 作为 sc::state_machine 的模板参数, 可以是不完整类型 (即仅前向声明)

类模板成员函数 state_machine<>::initiate() 会创建初始状态的对象. 因此, 在编译器到达调用 initiate() 的位置之前, 必须已知该状态的定义. 为了能够把状态机的初始状态隐藏在 .cpp 文件中, 我们必须不再让客户端调用 initiate(), 而是改为在 .cpp 文件中初始状态完整定义已知的位置调用它.

示例:

StopWatch.hpp:

// define events ...

struct Active; // the only visible forward
struct StopWatch : sc::state_machine< StopWatch, Active >
{
  StopWatch();
};

StopWatch.cpp:

struct Stopped;
struct Active : sc::simple_state< Active, StopWatch, Stopped >
{
  typedef sc::transition< EvReset, Active > reactions;
};

  struct Running : sc::simple_state< Running, Active >
  {
    typedef sc::transition< EvStartStop, Stopped > reactions;
  };

  struct Stopped : sc::simple_state< Stopped, Active >
  {
    typedef sc::transition< EvStartStop, Running > reactions;
  };

StopWatch::StopWatch()
{
  // For example, we might want to ensure that the state
  // machine is already started after construction.
  // Alternatively, we could add our own initiate() function
  // to StopWatch and call the base class initiate() in the
  // implementation.
  initiate();
}

能否继承一个既有的状态机, 并在子类中修改其布局?

可以, 但与某些 FSM 代码生成器允许的做法不同, Boost.Statechart 状态机只能以基状态机设计者预见的方式进行:

struct EvStart : sc::event< EvStart > {};

struct Idle;
struct PumpBase : sc::state_machine< PumpBase, Idle >
{
  virtual sc::result react(
    Idle & idle, const EvStart & ) const;
};

struct Idle : sc::simple_state< Idle, PumpBase >
{
  typedef sc::custom_reaction< EvStart > reactions;

  sc::result react( const EvStart & evt )
  {
    return context< PumpBase >().react( *this, evt );
  }
};

struct Running : sc::simple_state< Running, PumpBase > {};

sc::result PumpBase::react(
  Idle & idle, const EvStart & ) const
{
  return idle.transit< Running >();
}


struct MyRunning : sc::simple_state< MyRunning, PumpBase > {};

struct MyPump : PumpBase
{
  virtual sc::result react(
    Idle & idle, const EvStart & ) const
  {
    return idle.transit< MyRunning >();
  }
};

UML 2.0 特性怎么样?

本库在 2.0 出现之前就已设计完成. 因此, 除非明确说明, 库实现的是 UML1.5 标准规定的行为. 下面列出 2.0 语义与 Boost.Statechart 语义之间的部分差异:

  • 所有转换始终都是外部转换. 完全不支持局部转换 (local transition). 遗憾的是, UML2.0 规范对局部转换应如何工作并未完全说清, 更多信息见 此处
  • 没有直接支持 UML2.0 中的入口点 (entry point) 和出口点 (exit point) 元素. 不过, 两者都很容易模拟: 前者用一个 typedef, 后者用一个模板状态 (以转换目标作为模板参数)

为什么从状态析构函数访问状态机会触发断言?

在 NDEBUG 未定义的情况下编译时, 运行以下程序会导致断言失败:

#include <boost/statechart/state_machine.hpp>
#include <boost/statechart/simple_state.hpp>
#include <iostream>

struct Initial;
struct Machine : boost::statechart::state_machine< Machine, Initial >
{
  Machine() { someMember_ = 42; }
  int someMember_;
};

struct Initial : boost::statechart::simple_state< Initial, Machine >
{
  ~Initial() { std::cout << outermost_context().someMember_; }
};

int main()
{
  Machine().initiate();
  return 0;
}

问题的起因是 state_machine<>::~state_machine 不可避免地析构所有剩余的活动状态. 此时 Machine::~Machine 已经执行完毕, 再访问任何 Machine 成员都是非法的. 定义如下析构函数可以避免这个问题:

~Machine() { terminate(); }

Boost.Statechart 适合嵌入式应用吗?

视情况而定. 正如 Performance 页面 速度与可扩展性权衡 一节所解释的, 本库提供的近乎无限的可扩展性是有代价的. 尤其是小而简单的 FSM, 完全可以另行实现得更省周期、更省内存, 并在可执行文件中占据更少的代码空间. 下面是一些显然 非常粗略的估计:

  • 对于最多只有一个同时活动状态 (即机器是扁平的, 没有正交区域)、动作简单、使用了定制内存管理、并用优化良好的编译器编译的状态机, Pentium 4 级别的 CPU 在 state_machine<>::process_event() 内部花费的周期不应超过 1000 个. 对更复杂的状态机而言, 这一处理单个事件的最坏情况耗时与同时活动状态的数量大致呈线性关系, 而典型平均值远低于该值. 因此, 一个最多有 10 个同时活动状态的相当复杂的机器, 在 100MHz CPU 上每秒应能处理超过 10'000 个事件
  • 单个状态机对象通常使用不到 1KB 内存, 即便它实现的是一个非常复杂的机器
  • 关于代码大小, 很难给出具体准则, 但用 BitMachine 示例所做的测试表明, 代码大小与状态数量大致呈线性关系 (转换的影响似乎很小). 在 Windows 上用 MSVC7.1 编译时, 32 个状态和 224 个转换似乎可以放进约 108KB 的可执行代码中 (开启全部优化).
    此外, 本库可以在关闭 C++ RTTI 和异常处理的情况下编译, 在大多数平台上能显著节省开销

如上所述, 这些只是基于在桌面 PC 上使用本库的经验得出的非常粗略的估计, 仅可用于判断是否有必要在目标平台上自行做性能测试.

本库适合有硬实时要求的应用吗?

是. 开箱即用时, 本库执行的唯一可能具有非确定性耗时的操作, 是对 std::allocator<> 成员函数和 dynamic_cast 的调用. 避免 std::allocator<> 成员函数调用的办法, 是把自定义分配器传给 event<>、state_machine<>、asynchronous_state_machine<>、fifo_scheduler<> 和 fifo_worker<>. 避免 dynamic_cast 的办法, 则是不调用 state_cast<> 成员函数 (它们属于 state_machine<>、simple_state<> 和 state<>), 而改用确定性的变体 state_downcast<>.

使用模板化状态时我收到 'inner_context_type' 未定义的错误. 这是怎么回事?

下面的代码会产生这样的错误:

#include <boost/statechart/state_machine.hpp>
#include <boost/statechart/simple_state.hpp>

namespace sc = boost::statechart;

template< typename X > struct A;
struct Machine : sc::state_machine< Machine, A< int > > {};

template< typename X > struct B;
template< typename X >
struct A : sc::simple_state< A< X >, Machine, B< X > > {};

  template< typename X >
  struct B : sc::simple_state< B< X >, A< X > > {};

int main()
{
  Machine machine;
  machine.initiate();
  return 0;
}

如果将模板 A 和 B 替换为普通类型, 上面的代码就能编译通过. 其根源在于, C++ 对前向声明的模板与对前向声明的类型的处理方式不同: 编译器会在模板尚未定义的位置尝试访问 B< X > 的成员 typedef. 幸运的是, 只要把所有内层初始状态实参放进一个 mpl::list<>, 就能轻松避免, 如下:

struct A : sc::simple_state<
  A< X >, Machine, mpl::list< B< X > > > {};

技术细节见 此帖.

能否在运行期禁用某个状态的历史 (history)?

可以, 见 simple_state::clear_shallow_history() 与 simple_state::clear_deep_history(). 在以下情况下, 调用这些函数通常比引入额外的普通转换更为可取:

  • 带历史 (history) 的状态是许多转换的目标, 和/或
  • 忽略历史的决定与到带历史状态的转换发生在不同的位置

如何把状态机编译成动态链接库 (DLL)?

库在用户不可见的情况下, 使用静态数据成员为 event<> 和 simple_state<> 子类型实现自己的速度优化 RTTI 机制. 只要这类子类型定义在头文件中、随后又被多个翻译单元 (TU) 包含, 链接器之后就需要消除静态数据成员的重复定义. 只要所有这些翻译单元都 静态链接到同一个二进制文件中, 这通常都能完美运作. 一旦涉及 DLL, 情况就复杂得多. TuTest*.?pp 文件说明了这一点:

  • TuTest.hpp: 实例化一个含静态数据成员的类模板
  • TuTest.cpp: 包含 TuTest.hpp, 编译成一个 DLL
  • TuTestMain.cpp: 包含 TuTest.hpp, 编译成一个可执行文件

若不做任何预防措施 (例如在兼容 MSVC 的编译器上使用 __declspec(dllexport)), 在大多数平台上, 两个二进制文件 (exe 与 dll) 现在都会各自包含该静态数据成员的一份实例. 由于 RTTI 机制假定运行期该成员恰好只有一个对象, 当运行 exe 的进程又加载 dll 时, 该机制就会彻底失效. 不同平台对这个问题有不同的处理方式:

  • 在某些平台 (如 MinGW) 上, 似乎根本没有办法强制这种成员在运行期只存在一份. 因此, 内部 RTTI 机制无法与 DLL 可靠地配合使用. 在所有翻译单元中定义 BOOST_STATECHART_USE_NATIVE_RTTI 来禁用它, 通常可以绕过这个问题
  • 兼容 MSVC 的编译器支持 __declspec(dllimport) 和 __declspec(dllexport), 可精确指定需要从 DLL 加载什么 (具体做法参见 TuTest 示例). 因此可以使用内部 RTTI 机制, 但必须注意, 对定义在编译进多个二进制文件的头文件中的所有 event<> 和 simple_state<> 子类型, 都要正确地导出和导入. 当然, 也可以使用 BOOST_STATECHART_USE_NATIVE_RTTI 来省去导入导出的工作

Boost.Statechart 支持多态事件吗?

不支持. 虽然事件可以相互派生以只写一次公共代码, 但 反应只能为最派生事件 (most-derived event) 定义.

示例:

template< class MostDerived >
struct EvButtonPressed : sc::event< MostDerived >
{
  // common code
};

struct EvPlayButtonPressed :
  EvButtonPressed< EvPlayButtonPressed > {};
struct EvStopButtonPressed :
  EvButtonPressed< EvStopButtonPressed > {};
struct EvForwardButtonPressed :
  EvButtonPressed< EvForwardButtonPressed > {};

/* ... */

// We want to turn the player on, no matter what button we
// press in the Off state. Although we can write the reaction
// code only once, we must mention all most-derived events in
// the reaction list.
struct Off : sc::simple_state< Off, Mp3Player >
{
  typedef mpl::list<
    sc::custom_reaction< EvPlayButtonPressed >,
    sc::custom_reaction< EvStopButtonPressed >,
    sc::custom_reaction< EvForwardButtonPressed >
  > reactions;

  template< class MostDerived >
  sc::result react( const EvButtonPressed< MostDerived > & )
  {
    // ...
  }
};

为什么使用多重继承时退出动作 (exit-action) 的调用顺序不对?

更新: 这方面的实现已有很大变化. 在少数情况下仍可能出现这种行为 (当动作在带正交区域的状态机中传播异常 并且状态图布局满足特定条件时), 但已无法用下面的示例程序演示. 不过, 所述的变通方法仍然有效, 可确保这种行为永远不会出现.

对 simple_state<> 和 state<> 子类型来说肯定不会, 但附加基类的析构函数可能按构造顺序 (而非构造的逆序) 被调用:

#include <boost/statechart/state_machine.hpp>
#include <boost/statechart/simple_state.hpp>

namespace sc = boost::statechart;

class EntryExitDisplayer
{
  protected:
    EntryExitDisplayer( const char * pName ) :
      pName_( pName )
    {
      std::cout << pName_ << " entered\n";
    }

    ~EntryExitDisplayer()
    {
      std::cout << pName_ << " exited\n";
    }

  private:
    const char * const pName_;
};

struct Outer;
struct Machine : sc::state_machine< Machine, Outer > {};
struct Inner;
struct Outer : EntryExitDisplayer, sc::simple_state<
  Outer, Machine, Inner >
{
  Outer() : EntryExitDisplayer( "Outer" ) {}
};

struct Inner : EntryExitDisplayer,
  sc::simple_state< Inner, Outer >
{
  Inner() : EntryExitDisplayer( "Inner" ) {}
};

int main()
{
  Machine myMachine;
  myMachine.initiate();
  return 0;
}

这个程序将产生如下输出:

Outer entered
Inner entered
Outer exited
Inner exited

也就是说, EntryExitDisplayer 基类部分 (Outer 的) 先于 Inner 的被析构, 尽管 Inner::~Inner() 在 Outer::~Outer() 之前被调用. 这种有违直觉的行为由以下事实导致:

  • simple_state<> 基类部分 (属于 Inner) 负责析构 Outer
  • 基类部分的析构函数按构造的逆序调用

因此, 当 Outer 的析构函数被调用时, 调用栈如下:

Outer::~Outer()
simple_state< Inner, ... >::~simple_state()
Inner::~Inner()

注意, Inner::~Inner() 还没有机会销毁自己的 EntryExitDisplayer 基类部分, 因为它必须先调用 第二个基类的析构函数. 接下来 Outer::~Outer() 会先析构自己的 simple_state< Outer, ... > 基类部分, 再对 EntryExitDisplayer 基类部分做同样的事. 然后栈回退到 Inner::~Inner(), 它最终通过调用 EntryExitDisplayer::~EntryExitDisplayer() 完成.

幸运的是, 有一个简单的变通方法: 始终让 simple_state<> 和 state<> 作为状态的第一基类. 这可确保附加基类的析构函数会在状态基类析构函数所采用的递归能够改变析构顺序之前被调用.
