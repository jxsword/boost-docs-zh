为什么选择 spreadsort?

本库使用的 spreadsort 算法旨在提供尽可能好的最坏情况性能, 同时保持缓存友好. 它提供 𝑶(N*log(K/S + S)) 与 𝑶(N*log(N)) 最坏情况时间中较优者, 其中 K 是范围的对数. 范围的对数通常是数据类型的比特长度; 对 32 位整数为 32.

相比之下, flash_sort (另一种混合算法) 对均匀分布的列表为 𝑶(N). 问题在于, flash_sort 只是 MSD 基数排序 与 𝑶(N*N) 插入排序的组合, 后者用于处理 MSD 基数排序低效的小子集, 因此对于大小接近其切换到 insertion_sort 的数据块, 它效率不高, 最终表现为一个增强版的 MSD 基数排序. 对不均匀分布, 这使得它尤其低效.

integer_sort 与 float_sort 改用 introsort, 它对这些中等大小的数据块提供 𝑶(N*log(N)) 性能. 此外, flash_sort 对均匀分布的 𝑶(N) 性能以缓存未命中为代价, 而这在现代架构上极其昂贵; 在现代系统上的测试表明, 它最终比以多个缓存友好的步骤切分数据更慢. 还值得注意的是, 在大多数现代计算机上, log2(available RAM)/log2(L1 cache size) 约为 3, 即一次缓存未命中所耗时间超过缓存内随机访问的 3 倍, 而 max_splits 的大小就是按缓存大小调优的. 在缓存未命中没有这么昂贵的计算机上, 可以把 max_splits 增大到很大的值, 或完全去掉, 此时 integer_sort/float_sort 在均匀分布下也会有同样的 𝑶(N) 性能.

Adaptive Left Radix (ALR) 与 flash_sort 相似, 但更缓存友好. 它仍然使用 insertion_sort. 由于 ALR 使用 𝑶(N*N) 的 insertion_sort, 在大型列表上使用基于比较的回退排序并不高效; 如果数据聚集成略大于回退大小的小块并夹杂少量离群值, 基于基数的排序会反复迭代, 只做很少的排序却带来高开销. 渐近意义上 ALR 仍为 𝑶(N*log(K/S + S)), 但 S 非常小 (最坏情况下约为 2), 与 Spreadsort 的 max_splits 默认值 11 相比处于劣势.

ALR 也没有 𝑶(N*log(N)) 回退, 因此对不均匀分布的小列表极其低效. 示例见 alrbreaker 与 binaryalrbreaker 测试用例; 既可以把对 sort 的调用替换为对 ALR 的调用并更新顶部的 ALR_THRESHOLD, 也可以作为快速比较而设置 get_max_count return ALR_THRESHOLD (依据论文默认为 20). 在作者的测试中, 这些小测试使用 ALR 所需时间是 std::sort 的 4-10 倍 (取决于测试系统), 因为它们要排序高度不均匀的分布. 普通 Spreadsort 处理它们要好得多, 因为 get_max_count 的设计目标就是最小化最坏情况运行时间.

burst_sort 是一种针对字符串的高效混合算法, 但使用大量额外内存.

相比之下, string_sort 使用极少的额外内存. 二者尚未进行速度比较, 但更好的内存效率使 string_sort 更为通用.

postal_sort 与 string_sort 相似. 若能做直接的性能比较将更有说服力, 但在源码检索中未找到高效的 postal_sort 版本.

string_sort 与 美国国旗排序 算法最为相似. 主要区别在于它不费心优化空桶/堆的处理方式, 而是只检查当前索引处的所有字符是否相等. 其他区别包括使用 std::sort 作为回退算法, 以及更大的回退规模 (256 对 16), 这使得空堆处理不那么重要.

另一个区别是不施加栈大小限制. 由于 string_sort 中的相等性检查, 需要 m*m 内存量级的字符串才能迫使 string_sort 创建深度为 m 的栈. 在现代具有数兆字节栈大小限制的系统上, 这不是一个现实问题——为超过栈大小限制所需的长字符串本身就会耗尽主存. string_sort 可以看作是对 美国国旗排序 的现代化改造, 以利用 introsort 作为回退算法. 在作者的测试中, 美国国旗排序 (基于 std::strings) 的运行时间与 introsort 相当, 但把二者混合可以降低开销并获得显著更优的性能.
