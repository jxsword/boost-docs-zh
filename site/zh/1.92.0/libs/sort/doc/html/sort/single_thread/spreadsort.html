2.1.-Spreadsort

概述

引言

Spreadsort 组合了多种高速排序算法的通用实现, 当待排序列表元素超过 1000 个时, 其平均与最坏情况性能均优于 C++ 标准中的算法.

在小数据集上它们回退到 STL std::sort.

警告

这些算法都只能用于 随机访问迭代器.

它们是混合算法, 同时使用基数排序与基于比较的排序, 并针对常见数据类型 (如整数、浮点数和字符串) 做了特化.

这些算法以通用方式编码并接受仿函数, 因此能够对任何可以像这些基本数据类型一样处理的对象排序. 就 string_sort 而言, 这包括 std::sort 能排序的、定义了严格弱序的任何类型; 但为某些复杂键类型编写高效仿函数相对于直接使用 std::sort 可能不值得付出额外精力, 这取决于速度对你的应用有多重要. 示例用法可在 example 目录中找到.

与许多基于基数的算法不同, spreadsort 底层算法是围绕 最坏情况性能设计的. 它在成块的数据 (分布不广的数据) 上表现更好, 因此在真实数据上的性能可能显著优于随机数据. 从概念上讲, spreadsort 可以对任何能确定绝对顺序的数据排序, 而 string_sort 具有足够的灵活性, 这应当是可行的.

spreadsort 相对于 std::sort 最快的情形:

  1. 待排序元素数量巨大 (N >= 10000).
  2. 比较函数缓慢 (如 x86 处理器上的浮点数或字符串).
  3. 数据元素较大 (如按键排序的键 + 数据).
  4. 完全有序的数据, 此时 spreadsort 有提前退出的优化.

spreadsort 比 std::sort 慢的情形:

  1. 逆序数据. std::sort 与 spreadsort 在逆序数据上都比随机数据快, 但 std::sort 在这一特殊情况下提速更多.
  2. 极小的数据量 (< 1000 个元素). 因此 spreadsort 在输入规模小于 1000 时回退到 std::sort, 所以实际上对少量数据二者性能相同.

这些函数定义于 namespace boost::sort::spreadsort.

重载
提示

在 Boost.Sort C++ 参考一节中, 点击相应的重载, 例如 float_sort(RandomAccessIter, RandomAccessIter, Right_shift, Compare);, 即可查看该重载的完整细节.

integer_sort、float_sort 与 string_sort 各有 3 个主要版本: 基础版本接受首迭代器与尾迭代器, 与 std::sort 相同:

integer_sort(array.begin(), array.end());
float_sort(array.begin(), array.end());
string_sort(array.begin(), array.end());

重载了移位仿函数的版本, 在 operator>> 已经做的不是普通位右移时提供灵活性. 右移仿函数接受两个参数: 第一个是数据类型, 第二个是要右移的自然数位数.

对 string_sort 而言, 该变体稍有不同: 它需要一个等价于 operator[] 的下标仿函数, 接收与字符偏移对应的数字, 以及第二个 getlength 仿函数来获取字符串长度 (以字符计). 在所有情况下, 该运算符都必须返回一个整数类型, 用于与 operator< 比较以提供预期的顺序 (整数可以取负来反转其顺序).

换句话说 (负浮点数除外, 它们作为整数时是反转的):

rightshift(A, n) < rightshift(B, n) -> A < B
A < B -> rightshift(A, 0) < rightshift(B, 0)

integer_sort(array.begin(), array.end(), rightshift());

string_sort(array.begin(), array.end(), bracket(), getsize());

带右移仿函数的整数排序的可运行示例见 rightshiftsample.cpp.

还有一个带比较仿函数的版本, 可提供最大灵活性. 该仿函数必须提供与右移返回的整数相同的排序顺序 (负浮点数除外):

rightshift(A, n) < rightshift(B, n) -> compare(A, B)
compare(A, B) -> rightshift(A, 0) < rightshift(B, 0)

integer_sort(array.begin(), array.end(), negrightshift(), std::greater<DATA_TYPE>());

仿函数的示例如下:

struct lessthan {
  inline bool operator()(const DATA_TYPE &x, const DATA_TYPE &y) const {
    return x.a < y.a;
  }
};

struct bracket {
  inline unsigned char operator()(const DATA_TYPE &x, size_t offset) const {
    return x.a[offset];
  }
};

struct getsize {
  inline size_t operator()(const DATA_TYPE &x) const{ return x.a.size(); }
};

这些仿函数的用法如下:

string_sort(array.begin(), array.end(), bracket(), getsize(), lessthan());

使用全部仿函数对字符串排序的可运行示例见 stringfunctorsample.cpp.

性能

spreadsort 算法是一种混合算法: 当待排序元素数量低于某一数值时使用基于比较的排序, 高于该数值时使用基数排序. 因此, 基于基数的算法会把问题切分成小块: 如果数据聚集, 就完全基于基数对数据排序; 否则用基于比较的排序完成切分后小块的排序.

Spreadsort 算法在递归时动态选择基于比较或基于基数的排序, 选择最坏情况性能更优者. 这样, 最坏情况性能保证是 𝑶(N⋅log2(N)) 次比较与 𝑶(N⋅log2(K/S + S)) 次操作中较好的一方, 其中

  • N 是待排序元素数量,
  • K 是键的比特长度, 而
  • S 是一个常数.

这使得大 N 下的性能大幅提升: integer_sort 通常比 std::sort 快 50% 到 2 倍, 而 float_sort 与 _string_sort 约比 std::sort 快 2 倍.

integer_sort、float_sort 与 string_sort 的说明中提供了性能图.

float_sort 的耗时与 integer_sort 非常接近.

使用固定最大分裂数的直方图统计, 因为它能减少缓存未命中的次数, 从而相对 原始 SpreadSort 论文中详述的方法提高性能.

缓存友好直方图统计的重要性在 Arne Maus, Adaptive Left Reflex 中有描述, 但没有下文所述的最坏情况处理.

每轮基数迭代所需的时间为:

对数据 𝑶(N) 次迭代

𝑶(N) 次整数类型比较 (即使对于 _float_sort 和 string_sort 也是如此)

𝑶(N) 次交换

𝑶(2S) 次桶操作.

为获得每轮迭代 𝑶(N) 的最坏情况性能, 施加 S <= log2(N) 的限制, 𝑶(2S) 即变为 𝑶(N). 在每轮这样的迭代中, 每个元素未排序比特数 log2(range) (记作 K) 减少 S. S 会随待排序元素数量而减小, 可以从最大值 Smax 降到最小值 Smin.

假设: 假定 std::sort 为 𝑶(N*log2(N)), 因为 introsort 存在且被普遍使用. (如果你对此有异议, 请与你的 std::sort 的实现者讨论; 如果你的 std::sort 库调用实现不佳, 欢迎把对 std::sort 的递归调用替换为对 introsort 的调用).

为简单起见, 本算法不包含 Introsort, 并且假定 std::sort 调用的实现者知道自己在做什么.

为保持 S (Smin) 的最小值, 当 n <= log2(meanbinsize) 时必须使用基于比较的排序, 其中 log2(meanbinsize) (lbs) 是一个小常数 (通常在 0 到 4 之间), 用于最小化每元素的桶开销. 存在一个小的边角情形: 若 K < Smin 且 n >= 2^K, 则数据可以在 S = K 的单轮基于基数的迭代中完成排序 (这种桶排序特例默认只应用于 float_sort). 因此最后一轮递归的最坏情况性能为:

若 K <= Smin, 则为 1 轮基于基数的迭代,

或进行 Smin + lbs 轮基于比较的迭代 (若 K > Smin 且 n <= 2(Smin + lbs)).

因此最后一轮迭代的最坏情况运行时间为 𝑶(N*(Smin + lbs)), 但如果 K > Smin 且 N > 2(Smin + lbs), 则需要多于 1 轮的基数递归.

对于倒数第二轮, 可以处理 K <= Smin * 2 + 1 (若数据被划分为 2(Smin + 1) 份); 若 N < 2(Smin + lbs + 1), 则回退到 std::sort 更快.

在基于基数的排序加递归的情形下, 最坏情况耗时为 𝑶(N*(Smin + lbs)) + 𝑶(N) = 𝑶(N*(Smin + lbs + 1)), 因为 K_remaining = K_start - (Smin + 1), 且 K_start <= Smin * 2 + 1.

另外, 若 N < 2(Smin + lbs + 1), 则改用基于比较的排序, 耗时为 𝑶(N*(Smin + lbs + 1)).

因此无论哪种方式, 𝑶(N*(Smin + lbs + 1)) 都是倒数第二轮的最坏情况耗时, 发生条件为 K <= Smin * 2 + 1 或 N < 2(Smin + lbs + 1).

只要 Smin <= S <= Smax 这一过程就会持续, 因此当 K_m <= K_(m-1) + Smin + m (其中 m 是本轮结束后剩余的最大迭代次数), 或 N < 2(Smin + lbs + m) 时, 最坏情况运行时间为 𝑶(N*(Smin + lbs + m)).

   K_m 在 m <= (Smax - Smin) 时可推得:

   K_1 <= (Smin) + Smin + 1 <= 2Smin + 1

   K_2 <= (2Smin + 1) + Smin + 2

因为从 0 到 m 的和为 m(m + 1)/2

   K_m <= (m + 1)Smin + m(m + 1)/2 <= (Smin + m/2)(m + 1)

把 Smax - Smin 代入 m

   K_(Smax - Smin) <= (Smin + (Smax - Smin)/2)*(Smax - Smin + 1)

   K_(Smax - Smin) <= (Smin + Smax) * (Smax - Smin + 1)/2

由于这涉及 Smax - Smin + 1 轮迭代, 推得每轮迭代把 K 平均分成 (Smin + Smax)/2 份.

从此点完成该问题需要 𝑶(N * (Smax - Smin)) 的 m 轮迭代, 加上最后一轮最坏情况的 𝑶(N*(Smin + lbs)), 总计耗时 𝑶(N *(Smax + lbs)).

当 m > Smax - Smin 时, 问题每轮被划分为 Smax 份, 或者调用 std::sort (若 N < 2^(m + Smin + lbs)). 对于此范围:

   K_m <= K_(m - 1) + Smax, 由此得到运行时间

若递归, 则为 𝑶(N *((K - K_(Smax - Smin))/Smax + Smax + lbs)),

若基于比较, 则为 𝑶(N * log(2^(m + Smin + lbs))),

化简为 𝑶(N * (m + Smin + lbs)), 代入得 𝑶(N * ((m - (Smax - Smin)) + Smax + lbs)), 考虑到 m - (Smax - Smin) <= (K - K_(Smax - Smin))/Smax (否则会使用更少的基于基数的迭代)

同样得出 𝑶(N *((K - K_(Smax - Smin))/Smax + Smax + lbs)).

渐近地, 对于大 N 与大 K, 上式化简为:

   𝑶(N * (K/Smax + Smax + lbs)),

化简掉与 Smax - Smin 范围相关的常数后, 提供 𝑶(N * (Smax + lbs)) 的额外运行时间, 叠加在 𝑶(N * (K/S)) 性能的 LSD 基数排序 之上, 但没有 𝑶(N) 的内存开销. 为简单起见, 由于 lbs 是一个小常数 (可以使用 0, 表现也还可以), 在后续讨论总结性能时将其忽略. 通过检查基于比较的排序是否更优, Spreadsort 也是 𝑶(N*log(N)) (取二者较优者), 并且与 LSD 基数排序 不同, 若数据均匀分布或高度聚集, 其表现可以远好于最坏情况.

以上分析针对 integer_sort 与 float_sort. string_sort 的不同之处在于 Smin = Smax = sizeof(Char_type) * 8、lbs 为 0, 且 std::sort 的比较不是常数时间操作, 所以严格来说 string_sort 的运行时间为

   𝑶(N * (K/Smax + (Smax 次比较))).

最坏情况下, 最终为 𝑶(N * K) (其中 K 是字符串平均长度, 以字节计), 如 美国国旗排序 所述, 这优于

   𝑶(N * K * log(N))

基于比较排序的最坏情况.

调优

integer_sort 与 float_sort 有一些调优常数, 控制这些算法中基数排序部分的工作方式. integer_sort 与 float_sort 的理想常数值随平台、编译器和待排序数据而变化. 目前为止最重要的常数是 max_splits, 它定义基数排序部分每轮迭代把数据分成多少份.

max_splits 的理想值取决于处理器 L1 缓存的大小, 在许多系统上介于 10 到 13 之间. 默认值取 11. 对于大部分有序的数据, 更大的值更好, 因为交换 (以及由此产生的缓存未命中) 很少发生; 但这对无序数据的运行时间损害严重, 因此不推荐.

在某些 x86 系统上, 当待排序元素总数较少 (约小于 100 万) 时, 理想的 max_splits 可以大得多, 例如 17. 据推测这是因为所有数据都能放入 L2 缓存, L1 缓存到 L2 缓存的未命中不像对主存的未命中那样严重影响性能. 不建议修改 max_splits 以外的调优常数, 因为更改其他常数带来的性能提升通常很小.

如果你能让它运行一天, 并且至少有 1GB 空闲内存, 可以使用 perl 命令: ./tune.pl -large -tune (UNIX) 或 perl tune.pl -large -tune -windows (Windows) 来自动调优这些常数. 应当在 boost 主目录内的 libs/sort directory 下运行. 它会在 2000 万元素 (80MB) 文件的各种分布上进行测试, 为你系统确定 ideal constants.hpp 设置, 并额外验证所有排序例程在各种数据分布下都能正确排序. 另外, 你也可以用最关心的文件大小来测试: ./tune.pl number -tune (UNIX) 或 perl tune.pl number -tune -windows (Windows), 把 number 替换为想测试的元素数量. 否则, 直接使用它自带的选项即可, 它们已经不错. 使用默认设置 ./tune.pl -tune (UNIX) perl tune.pl -tune -windows (Windows) 时, 脚本要运行数小时 (不到一天), 但若 max_splits 超过 10, 可能选不出正确的值. 另外, 可以加上 -small 选项, 让它只用几分钟, 针对较小的 vector 大小 (十万元素) 调优, 但得到的常数可能不适合大文件 (参见上文关于 Windows 上 max_splits 的说明).

通过省略 "-tune" 选项, 调优脚本也可以只用于验证排序在你的系统上是否正确工作, 并查看能获得多少提速. 这会在调优运行的最后执行. 默认参数运行约需一小时, 并在规模可观的测试向量上给出准确结果. ./tune.pl -small (UNIX) perl tune.pl -small -windows (Windows) 是更快的选项, 在更小的向量上测试, 但不够准确.

如果调优期间遇到任何差异, 请调用 tune.pl 并带上 -debug > log_file_name. 如果生成的日志文件包含编译或权限问题, 那可能是你的环境配置问题. 如果遇到其他类型的错误 (或结果差异), 请把它们发送给库作者: spreadsort@gmail.com. 附上所用 input.txt 的压缩包也会有帮助.
