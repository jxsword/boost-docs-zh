rational 类概要

#include <boost/rational.hpp>

namespace boost {

class bad_rational;

template<typename I> class rational {
    typedef implementation-defined bool_type;

public:
    typedef I int_type;

    // Constructors
    rational();          // Zero;               constexpr since C++11
    rational(I n);       // Equal to n/1;       constexpr since C++11
    rational(I n, I d);  // General case (n/d); constexpr since C++14
    template<typename J>
    explicit rational(const rational<J> &r);  // Cross-instantiation; constexpr since C++11

    // Normal copy constructors and assignment operators

    // Assignment from I
    rational& operator=(I n); // constexpr since C++14

    // Assign in place
    rational& assign(I n, I d); // constexpr since C++14

    // Representation
    I numerator() const;   // constexpr since C++11
    I denominator() const; // constexpr since C++11

    // In addition to the following operators, all of the "obvious" derived
    // operators are available - see operators.hpp

    // Arithmetic operators
    rational& operator+= (const rational& r); // constexpr since C++14
    rational& operator-= (const rational& r); // constexpr since C++14
    rational& operator*= (const rational& r); // constexpr since C++14
    rational& operator/= (const rational& r); // constexpr since C++14

    // Arithmetic with integers
    rational& operator+= (I i); // constexpr since C++14
    rational& operator-= (I i); // constexpr since C++14
    rational& operator*= (I i); // constexpr since C++14
    rational& operator/= (I i); // constexpr since C++14

    // Increment and decrement
    const rational& operator++(); // constexpr since C++14
    const rational& operator--(); // constexpr since C++14

    // Operator not
    bool operator!() const; // constexpr since C++11

    // Boolean conversion
    operator bool_type() const; // constexpr since C++11

    // Comparison operators
    bool operator< (const rational& r) const;  // constexpr since C++14
    bool operator== (const rational& r) const; // constexpr since C++11

    // Comparison with integers
    bool operator< (I i) const;  // constexpr since C++14
    bool operator> (I i) const;  // constexpr since C++14
    bool operator== (I i) const; // constexpr since C++11
};

// Unary operators
template <typename I> rational<I> operator+ (const rational<I>& r); // constexpr since C++11
template <typename I> rational<I> operator- (const rational<I>& r); // constexpr since C++14

// Reversed order operators for - and / between (types convertible to) I and rational
template <typename I, typename II> inline rational<I> operator- (II i, const rational<I>& r); // constexpr since C++14
template <typename I, typename II> inline rational<I> operator/ (II i, const rational<I>& r); // constexpr since C++14

// Absolute value
template <typename I> rational<I> abs (const rational<I>& r); // constexpr since C++14

// Input and output
template <typename I> std::istream& operator>> (std::istream& is, rational<I>& r);
template <typename I> std::ostream& operator<< (std::ostream& os, const rational<I>& r);

// Type conversion
template <typename T, typename I> T rational_cast (const rational<I>& r); // constexpr since C++11

设计理由

数有多种不同的形式. 最基本的形式是自然数 (非负的 "整数")、整数与实数. 这些类型由 C++ 内建类型 unsigned int、int 与 float (以及各种不同大小的等价类型) 近似.

C++ 标准库通过提供 complex 类型扩展了可用数值类型的范围.

本库提供了又一个数值类型: rational (有理数).

rational 类实际上实现为一个模板, 方式与标准 complex 类类似.

背景

有理数的数学概念是人们通常所想的分数 - 即可以表示为两个整数之比的数. 这一概念不同于实数, 实数可取的值多得多 (例如 2 的平方根, 它不能表示为分数).

计算机无法精确表示数学概念 - 总要做出妥协. 机器整数的取值范围有限 (通常 32 位), 机器对实数的近似精度有限. 这些妥协各有动机 - 机器整数支持精确计算但范围有限, 而机器实数范围大得多, 却牺牲了精确性.

有理数类提供了另一种妥协. 有理数计算是精确的, 但可用范围有限. 确切地说, 只要分子与分母 (始终以无公因子的规范化形式保存) 在底层整数类型的范围之内, 有理数就是精确的. 当值超出这些界限时, 会发生溢出, 结果未定义.

有理数类是一个模板, 让程序员能在一定程度上控制溢出行为. 如果有无限精度整数类型可用, 基于它的有理数将永不溢出 (资源限制除外), 并在任何情况下提供精确计算.

整数类型要求

rational 类型接受单个模板类型参数 I. 它是 rational 类型的 底层整数类型. C++ 实现提供的任何内建整数类型都可作为 I 的值. 用户自定义类型也可使用, 但用户应注意 rational 类的性能特征高度依赖底层整数类型的性能特征 (往往以复杂的方式 - 具体说明参见下文 性能 一节). 注: 如果 boost 库将来支持无限精度整数类型, 该类型将作为 rational 类的底层整数类型获得完整支持.

要用作 rational 类型底层整数类型的用户自定义整数类型, 必须是以下概念的模型.

  • Assignable
  • Default Constructible
  • Equality Comparable
  • LessThan Comparable

此外, I 必须是 类整数 类型, 即以下表达式对 I 类型的任意两个值 n 和 m 必须有效, 且具有 "预期" 语义.

  • n + m
  • n - m
  • n * m
  • n / m (必须截断; 若 n 与 m 为正则必须非负)
  • n % m (若 n 与 m 为正则必须非负)
  • 以上各表达式的赋值版本
  • +n, -n
  • !n (必须为 true, 当且仅当 n 为零)

I 必须有可用的 零值 与 一值. 应当能够分别以 I(0) 与 I(1) 生成它们. 注: 这并不意味着 I 需要能从整数隐式转换 - 一个 explicit 构造函数即可.

I 为无符号类型是合法的. 此时, 派生的 rational 类也将是无符号的. 这种情况下, 当减法结果本应为负时的下溢行为不可预测.

  • rational_cast<T>(rational<I>) 的实现依赖于从类型 I 到类型 T 的 static_cast 能力, 以及表达式 x/y 对 T 类型的任意两个值有效.
  • 输入与输出运算符依赖于类型 I 存在对应的输入与输出运算符.

std::numeric_limits<I> 特化必须存在 (且在需要指定 boost::rational<I> 之前必须可见). 其 is_specialized 静态数据成员的值必须为 true, 且其 is_signed 静态数据成员的值必须准确.

接口

实用函数

可提供两个实用函数模板, 它们应能配合 任何可用于 boost::rational<> 类模板的类型工作.

gcd(n, m) n 与 m 的最大公约数
lcm(n, m) n 与 m 的最小公倍数

这些函数模板现在把调用转发给 Boost.Integer 库 中的对应函数. 其存在与否可在编译期用 BOOST_CONTROL_RATIONAL_HAS_GCD 预处理器常量控制.

构造函数

有理数可由零个、一个或两个整数实参构造; 分别表示: 默认构造为零, 由作为分子的整数转换 (隐含分母为一), 或按该顺序给出的一对分子与分母. 整数实参应为 rational 的整数类型, 或可隐式转换为该类型. (对于双实参构造函数, 所需的转换当然是各自独立求值的.) 各分量以规范化形式存储.

有理数也可由另一个有理数构造. 当源与目标的底层整数类型一致时, 使用自动定义的拷贝或移动构造函数. 否则, 使用转换构造函数模板. 该构造函数对分子与分母逐成员初始化. 标记为 explicit 的分量级转换没有问题. 当转换最终保值时, 结果已是规范化的; 但仍会执行规范化检查, 以防保值性被破坏.

这些意味着以下语句是有效的: 

    I n, d;
    rational<I> zero;
    rational<I> r1(n);
    rational<I> r2(n, d);
    rational<J> r3(r2);  // assuming J(n) and J(d) are well-formed

在 C++11 中, 无实参构造函数、单实参构造函数与跨版本构造函数模板均标记为 constexpr, 使得当初始化器 (如有) 也是常量表达式 (且底层整数类型所需的运算支持 constexpr) 时, 它们可用于常量表达式. 自 C++14 起, 所有构造函数均支持 constexpr.

单实参构造函数 并未 声明为 explicit, 因此存在从底层整数类型到 rational 类型的隐式转换. 双实参构造函数可视为 C++11 统一初始化语法下的隐式转换, 因为它同样未声明为 explicit. 跨版本构造函数模板声明为 explicit, 因此两个 rational 实例化之间的转换方向必须显式指定.

算术运算

标准数值运算符都为 rational 类作了定义. 包括: 
    +    +=
    -    -=
    *    *=
    /    /=
    ++   --    (both prefix and postfix)
    ==   !=
    <    >
    <=   >=

    Unary: + - !

自 C++14 起, 所有这些运算均已启用 constexpr. 在 C++11 中, 仅 operator==、operator!=、一元 operator+ 与 operator! 如此.

输入与输出

输入与输出运算符 << 和 >> 均已提供. 有理数的外部表示是两个整数, 以斜线 (/) 分隔. 输入时, 格式必须恰好是一个整数, 后随无空白间隔的斜线, 再后随 (同样无空白间隔) 第二个整数. 整数的外部表示由底层整数类型定义.

就地赋值

对任意 rational<I> r, r.assign(n, m) 提供了 r = rational<I>(n, m); 的替代方案, 无需用户指定的临时对象构造. 虽然这对基于机器整数类型的有理数来说可能并无必要, 但对基于无限精度整数的有理数等情形可以节省开销.

若给定的分量无法组成有效的有理数, 该函数将抛出异常. 否则, 只有当分量级的移动赋值 (C++11; 更早的 C++ 版本为拷贝赋值) 可能抛出时它才可能抛出. 若抛出发生在第一部分, 则保持强保证; 但若在分量赋值期间抛出异常, 则强保证与基本保证都可能无法保持.

转换

存在一个到未指定布尔类型 (很可能是成员指针) 的转换运算符. 该运算符在有理数表示零时将其转换为 false, 否则转换为 true. 该转换允许有理数用作运算符 ?: 的第一个实参; 用作运算符 && 或 || 的任一实参而不丧失短路求值; 用作 do、if、while 或 for 语句的条件; 以及用作 if、while 或 for 语句的条件声明. 所用类型的性质, 以及该性质的任何名称都保持私有, 应能防止不当的非布尔使用, 如数值或指针运算, 或用作 switch 条件.

存在 再无其他 从 rational 类型的隐式转换. 除显式跨版本构造函数模板外, 还有一个显式类型转换函数 rational_cast<T>(r). 其用法如下: 

    rational<int> r(22,7);
    double nearly_pi = boost::rational_cast<double>(r);

若源有理数的分子或分母无法安全地转换为适当的浮点类型, 或分子与分母的除法 (在目标浮点类型下) 求值不正确, rational_cast<T> 函数的行为未定义. 此外, 由于该函数具有自定义名称, 它不能像跨版本构造函数那样在泛型代码中调用, 以在同一类模板的两个实例化之间进行交换.

本质上, 所有必需的转换都应保值, 且所有运算的行为都应 "合理". 若无法满足这些约束, 单独的用户自定义转换将更为合适.

布尔转换与 rational_cast 均已启用 constexpr.

实现说明:

rational_cast 函数的实现曾如下

    template <typename Float, typename Int>
    Float rational_cast(const rational<Int>& src)
    {
        return static_cast<Float>(src.numerator()) / src.denominator();
    }
但是, 程序不应依赖于该实现, 尤其是该实现现已过时. (它要求类型 Float 与 Int 之间的混合模式除法, 这与 整数类型要求 相悖.)

分子与分母

最后, 通过两个成员函数 numerator() 与 denominator() 提供对有理数内部表示的访问. 这些函数已启用 constexpr.

这些函数允许用户代码实现任何额外所需的功能. 特别应注意, 在某些情况下上述 rational_cast 运算可能不合适 - 尤其当 rational 类型基于无限精度整数类型时. 此时, 专门编写的用户自定义到浮点数的转换将更为合适.

性能

rational 类的设计隐含假定底层整数类型的行为 "类似" 内建整数类型. 该假设的行为方面已在上文 整数类型要求 一节中明确描述. 但除行为假定外, 还有隐含的性能假定.

不会尝试为 rational 类的可用运算提供详细的性能保证. 尽管可以提供此类保证 (以类似于许多标准库类的性能规范的方式), 但此类保证对 rational 类的用户是否有重大价值并不明确. 本节转而对 rational 类的性能特征作一般性讨论.

下面列出 <boost/rational.hpp> 头文件中定义的基本运算, 并对其性能特征作非正式描述. 注意: 这些描述基于当前实现, 因此应视为可能变更.

  • 有理数的构造本质上就是底层整数类型的两次构造, 外加一次规范化.
  • 自增与自减运算本质上与底层整数类型上的加法和减法一样廉价.
  • (不) 相等比较本质上与底层整数类型上的两次相等运算一样廉价.
  • I/O 运算并不廉价, 但其性能基本上由 I/O 时间本身主导.
  • (隐式) GCD 例程调用本质上是一次反复的取模运算. 其他的重要运算包括 IntType 值的构造、赋值与和零的比较. 假定这些运算与取模运算相比可以忽略.
  • (隐式) LCM 运算本质上是一次 GCD 外加一次乘法、除法与比较.
  • 加法与减法运算比较复杂. 它们大约需要底层整数类型上的两次 gcd 运算、3 次除法、3 次乘法和一次加法.
  • 乘法与除法运算需要两次 gcd 运算、两次乘法和四次除法.
  • 与整数比较的运算执行一次整数除法与取模对、至多一次额外的整数加法与自减, 以及至多三次整数比较.
  • 与有理数比较的运算在最坏情况下执行两次双倍大小的 GCD 运算、两次额外的加法与自减, 以及三次比较. (GCD 运算之所以是双倍大小, 是因为它们分段进行, 且中间商数被保留并比较, 而直接的 GCD 函数只保留并比较余数.)
  • 最后一项基本运算是规范化有理数. 每当构造有理数 (以及就地赋值) 时都会执行该运算. 所有其他运算都注意使有理数保持规范化状态. 规范化的代价相当于一次 gcd 加两次除法.

注意: 这里隐含假定 IntType 上的运算具有 "常规" 性能特征 - 具体而言, 昂贵的运算是乘法、除法与取模, 而加法与减法则显著更廉价. 假定构造 (从整数字面量 0 与 1 构造, 以及拷贝构造) 与赋值相对廉价, 尽管实现中也尽力减少不必要的构造与拷贝. 还假定比较 (尤其是与零的比较) 是廉价的.

不符合这些假定的整数类型作为 rational 类的底层整数类型不会特别有效. 具体而言, 性能很可能严重欠佳.

异常

有理数的分母永不为零. (本库不支持无穷大或 NaN 的表示). 若有理数运算结果产生了零分母, 或在规范化期间失败, 则抛出异常 boost::bad_rational (std::domain_error 的子类). 这只应在用户试图显式构造分母为零的有理数、用零值除以有理数、或产生过大而无法规范化的负分母时发生. 在跨实例化转换期间, 当至少一个分量最终未保值且新组合不被视为规范化时, 也可能抛出该异常.

此外, 如果底层整数类型上的运算可能产生异常, 这些异常会从 rational 类的运算中传播出来. 不应作任何特定假定 - 唯一安全的假定是: 整数类可能抛出的任何异常, 都可能由任何 rational 运算抛出. 特别是, rational 构造函数可能因规范化步骤而从底层整数类型抛出异常. 该规则的唯一例外是: rational 析构函数只会抛出底层整数类型析构函数可能抛出的异常 (通常没有).

如果分量级赋值运算符可能抛出, 那么当第二个分量的赋值期间发生异常时, rational 对象的不变式可能被破坏. (assign 成员函数也属此列.) 这同时违反强保证与基本保证.

内部表示

注: 此信息仅供参考. 程序不应编写为依赖这些实现细节.

在内部, 有理数存储为整数对 (分子, 分母) (其类型指定为 rational 类型的模板参数). 有理数始终以完全规范化形式存储 (即 gcd(numerator,denominator) = 1, 且分母恒为正).

设计说明

最小实现

有理数类的设计恪守基础. 它提供了数值类所需的最小运算集, 以及以 numerator() 和 denominator() 成员函数形式访问底层表示的能力. 有了这些构件, 就可以实现所需的任何附加功能.

这一最小化考量有所放宽的地方是提供输入/输出运算符以及 rational_cast. 前者通常没有争议. 然而, 在不少情况下, rational_cast 并不是把有理数转换为浮点值的最佳方法 (尤其是涉及用户自定义类型时). 在这些情况下, 可以且应当实现用户自定义转换. 这类运算无需命名为 rational_cast, 因此 rational_cast 函数 并不 提供允许特化/重载的必要基础设施.

有限范围整数类型

有理数类设计为与无限精度整数类配合使用. 有了这样的类, 有理数总是精确的, 不会出现精度损失、上溢或下溢问题.

遗憾的是, C++ 标准并未提供这样的类 (boost 目前的版本也没有). 因此, 有理数类在很多情况下很可能与有限精度整数类型一起使用, 例如内建的 int 类型.

当与有限精度整数类型一起使用时, rational 类会遇到许多导致浮点类型困难的精度问题. 虽然精度问题很可能不会影响 rational 类的简单用法, 用户仍应意识到此类问题的存在.

作为与有限精度整数相关问题的简单说明, 考虑 C++ int 类型为 32 位有符号表示的情形. 此时, 最小的正 rational<int> 是 1/0x7FFFFFFF. 换言之, rational<int> 表示在零附近的 "粒度" 约为 4.66e-10. 在可表示范围的另一端, 可表示的最大 rational<int> 是 0x7FFFFFFF/1, 而次小的可表示 rational<int> 是 0x7FFFFFFE/1. 因此, 在可表示范围的这一端, 粒度为 1. 这种依赖于数量级的粒度是浮点表示的典型特征. 然而, 在使用有理数类时它并不会让人感觉 "自然".

有限精度整数类型可能在其允许的负值与正值范围大小方面引发问题. 若负值范围更大, 则极端负数在正范围内将没有加法逆元, 使它们无法用作分母值, 因为它们无法规范化为正值 (除非用户碰上好运, 输入分量在规范化前恰好不互素).

基于有限精度整数类型的 rational 类型的使用者应自行了解并预先在代码中考虑此类问题.

从浮点数转换

本库不提供从浮点数到有理数的转换函数. 曾收到许多对此类转换的请求, 但 boost 邮件列表上的广泛讨论得出的结论是: 该问题不存在 "最佳方案". 由于库用户没有理由不能自行编写满足其特定需求的转换函数, 因此决定不选取任何算法作为 "标准".

任何从浮点值转换的转换函数, 关键问题都在于如何处理浮点运算涉及的精度损失. 举一个具体例子, 考虑以下代码: 

    // These two values could in practice be obtained from user input,
    // or from some form of measuring instrument.
    double x = 1.0;
    double y = 3.0;

    double z = x/y;

    rational<I> r = rational_from_double(z);

根本问题是: r 究竟应为何值? 一个天真的答案是 r 应等于 1/3. 然而, 这忽略了大量问题.

首先, z 并不精确等于 1/3. 由于浮点表示的限制, 1/3 无法在任何常见的 double 类型表示中精确表示. 那么, r 是否因此不应包含 z 所表示的实际值的 (精确) 表示? 但用户会对 r 取值 33333333333333331/100000000000000000 感到满意吗?

在考虑上述问题之前, 我们还必须考虑原始值 x 和 y 的准确性. 例如, 若它们来自模拟测量仪器, 则无论如何都不可能无限精确. 在这种情况下, 上述那样的有理数表示所承诺的精度远超任何合理的依据.

凡此种种都表明, 我们应当寻找某种 "最近简单分数". 确实存在确定此类数值的算法. 然而, 并非所有应用都希望这样工作. 在其他情况下, 转换为有理数的全部意义在于获得精确表示, 以防止一系列计算过程中的精度损失. 此时需要的是完全精确的表示, 无论分数看起来多么 "不自然".

鉴于这些相互冲突的要求, 显然不存在能让所有用户都满意的单一方案. 此外, 相关算法相对复杂且专用, 最好在对应用需求有充分理解的前提下实现. 所有这些因素使得此类函数不适合像本库这样的通用库.

绝对值

首先, 用 abs(IntType) 实现 abs(rational<IntType>) 似乎合乎逻辑. 然而, 这样做会引发许多问题.

第一个问题是, 当 IntType 是用户命名空间中的用户自定义类型时, 要找到 abs(IntType) 的适当实现就需要 Koenig 查找. 目前并非所有编译器都支持对函数的 Koenig 查找. 对于这类编译器, 需要笨拙的变通方案 (需要 rational 类用户配合) 才能使其工作.

第二个 (也可能更严重的) 问题是, 对于非标准的内建整数类型 (例如 long long 或 __int64 这样的 64 位整数类型), 无法保证厂商为这些类型提供了内建的 abs() 函数. 这是实现质量问题, 但实际上, 厂商对 long long 等类型的支持仍然很不完整.

由于这些问题, 用 abs(IntType) 实现 abs(rational<IntType>) 似乎并不值得. 于是改用带有内联 abs() 实现的简单实现: 

    template <typename IntType>
    inline rational<IntType> abs(const rational<IntType>& r)
    {
        if (r.numerator() >= IntType(0))
            return r;

            return rational<IntType>(-r.numerator(), r.denominator());
    }

同样的理由意味着, 在其他需要 IntType 绝对值的地方, 计算以内联方式进行.

历史与致谢

1999 年 12 月, 我实现了有理数类的初始版本, 并提交到 boost.org 邮件列表. 邮件列表上对该实现进行了一些讨论. 特别是 Andrew D. Jewell 指出了把溢出风险降至最低的重要性, 并为大多数基本运算提供了无溢出实现. rational_cast 这个名字由 Kevlin Henney 建议. Ed Brey 提供了宝贵的意见 - 尤其是指出了原始代码中一些相当愚蠢的键入错误!

David Abrahams 对文档提供了有益的反馈.

2000 年 11 月, boost 邮件列表上就提供从浮点数到有理数转换的利弊进行了长时间讨论. 主要贡献者包括 Reggie Seagraves、Lutz Kettner 与 Daniel Frey (尽管 boost 邮件列表上的大多数人似乎都在某个时刻参与了讨论!). 尽管最终决定 不 实现任何内容, 这场讨论对理解相关问题非常宝贵.

Stephen Silver 贡献了在有理数类中使用用户自定义整数类型的实用经验.

Nickolay Mladenov 提供了 operator+= 与 operator-= 的当前实现.

2001 年 1 月, boost 邮件列表上讨论了 Koenig 查找与 std::swap 的相关问题.

Daryle Walker 于 2005 年 12 月提供了布尔转换运算符, 使有理数可以像内建数值类型一样用于相同的布尔语境. 他于 2013 年 8 月添加了跨实例化构造函数模板.

2014 年 7 月: 更新 numerator/denominator 访问器以按常量引用返回值: 在与多精度 (类) 类型一起使用时带来性能提升.

2014 年 7 月: 全面更新为统一使用 BOOST_THROW_EXCEPTION.

2014 年 7 月: 添加对 C++11 constexpr 构造函数的支持, 以及相应测试.

2014 年 11 月: 添加对有理数的 gcd 与 lcm 的支持.

2016 年 12 月: 重构构造函数与运算符以禁止收窄的隐式转换, 尤其是来自浮点类型的意外转换.

2018 年 10/11 月: 增加更多 constexpr.
