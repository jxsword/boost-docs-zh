对 lambda 表达式的支持不完整

经验丰富的 MPL 用户会同意我们的看法: 如果 MPL 中有什么在威力和本质上都显得近乎神奇, 那就是 MPL lambda 表达式. 实际上, 使之成为现实的机制非常直白, 对任何大体熟悉 C++ 模板的人, 恐怕用不了 10 分钟就能讲清楚.

遗憾的是, 这一机制恰好依赖于对偏特化和模板模板参数的支持. 在所谓的残缺编译器中——基本上是 2000 年之前发布的大多数编译器——找到对这两个特性都有完整支持的希望渺茫. 属于此类的产品清单请参见我们的兼容性表.

虽然没有这两个特性就无法实现完全透明的 lambda 表达式, 但一种稍受限、需要元函数作者提供一些手动协助的实现是可能的. 本节描述所需的手工工作以及结果的局限.

The Problem

如果你的编译器属于 "残缺" 类别, 下面这个有效的 MPL 元程序将无法通过编译:

#include <boost/mpl/apply.hpp>

using namespace boost::mpl;

template< typename T > struct add_const
{
    typedef T const type;
};

typedef apply1< add_const<_1>,int >::type t; // t == int const

更糟的是, 它很可能会带着指向库内部、并可能给人造成库本身有问题的印象的诊断回溯而失败. 事实是, 程序和库都无缺陷 (就这个特定演示而言), 该责怪的是你的编译器.

解决办法

如前所述, 解决方案需要元函数作者做一些工作, 但对这些元函数的用户而言, 结果是相对透明的. 以下是我们对前面的例子需要做的修改:

#include <boost/mpl/apply.hpp>
#include <boost/mpl/aux_/lambda_support.hpp>

using namespace boost::mpl;

template< typename T > struct add_const
{
    typedef T const type;
    BOOST_MPL_AUX_LAMBDA_SUPPORT(1, add_const, (T))
};

typedef apply1< add_const<_1>,int >::type t; // t == int const

有了这两处修改, 刚才还冲我们汪汪叫的编译器现在欣然接受了它. "嘿, 这也没那么糟嘛!" 你可能会说. 放个小宏进去, 又能开开心心了.

限制

遗憾的是, 故事还没完. 仍有一些情形会使上述方法失效, 我们将不得不求助于编写非内联的元函数类. 细节如下:

为了在没有偏特化和模板模板参数的情况下让 lambda 表达式工作, MPL 必须实现某种其他方式来拆解模板实例化的表达式树, 而唯一的办法是通过侵入式的元函数内省机制. 这就是我们前面看到的 BOOST_MPL_AUX_LAMBDA_SUPPORT 宏背后所隐藏的东西.

但随后, 在把所需的信息 (元函数的元数及其确切的模板实参) 存入元函数自身之后, 库访问它的唯一办法就是查看元函数内部. 而后者又意味着在实际调用之前、过早地以一个或多个占位符实参实例化该元函数. 这最后一点是一个潜在问题.

换言之, 只要你的元函数是 "占位符安全的" (可以安全地以占位符实参实例化), 该机制就能工作, 这归结为以下两条判据:

  1. 该元函数不访问其实参的嵌套成员, 或者
  2. 所访问的成员只有名为 ::tag 或 ::type 的类型 (占位符确实包含这些).

如果这两条成立, 你就可以放心地把 BOOST_MPL_AUX_LAMBDA_SUPPORT 放进你的元函数, 不再操心此事. 如果不成立, 那你运气不佳, 恐怕得改写一个元函数类.

好消息是, MPL 自身的大多数元函数和 Boost.Type Traits 模板都是 "占位符安全的", 并已应用了该变通办法, 因此即使在破损的编译器上, 约 90% 的用例也能 "直接工作".

请参阅 MPL 参考手册, 了解 BOOST_MPL_AUX_LAMBDA_SUPPORT 宏的细节.
