资源受限最短路径

使用基于动态规划的标号设置算法(label-setting), 在有向图上求解带资源约束的最短路径问题(SPPRC).

复杂度: 取决于具体问题; 对非初等或无环情形为多项式, 对含负环的初等情形为指数级
定义于: <boost/graph/r_c_shortest_paths.hpp>

示例

#include <boost/graph/adjacency_list.hpp>
#include <boost/graph/r_c_shortest_paths.hpp>
#include <iostream>
#include <vector>

using namespace boost;

// Bundled edge fields replace `property<edge_index_t, int, property<edge_weight_t, int>>`.
struct Edge { int idx; int weight; };

using Graph = adjacency_list<vecS, vecS, directedS, no_property, Edge>;
using Descriptor = graph_traits<Graph>::edge_descriptor;

// Resource container: (cost, time)
struct Res { int cost; int time; };
bool operator==(const Res& a, const Res& b) { return a.cost == b.cost && a.time == b.time; }
bool operator<(const Res& a, const Res& b) { return a.cost < b.cost; }

struct ResExt {
    bool operator()(const Graph& g, Res& new_r, const Res& old_r, Descriptor e) const {
        new_r.cost = old_r.cost + g[e].weight;
        new_r.time = old_r.time + 1;
        return new_r.time <= 5; // hop-count constraint
    }
};

struct Dom {
    bool operator()(const Res& r1, const Res& r2) const {
        return r1.cost <= r2.cost && r1.time <= r2.time;
    }
};

int main() {
    Graph g(4);
    int i = 0;
    auto ae = [&](int u, int v, int w) {
        auto e = add_edge(u, v, g).first;
        g[e].idx = i++;
        g[e].weight = w;
    };
    ae(0, 1, 2); ae(0, 2, 5); ae(1, 3, 3); ae(2, 3, 2);

    std::vector<Descriptor> path;
    Res result{0, 0};
    r_c_shortest_paths(g, get(vertex_index, g), get(&Edge::idx, g),
        vertex(0, g), vertex(3, g), path, result,
        Res{0, 0}, ResExt{}, Dom{});

    std::cout << "Cost: " << result.cost << ", hops: " << result.time << "\n";
    std::cout << "Path edges: " << path.size() << "\n";
}
Cost: 5, hops: 2
Path edges: 2

template <class Graph,
          class VertexIndexMap,
          class EdgeIndexMap,
          class Resource_Container,
          class Resource_Extension_Function,
          class Dominance_Function,
          class Label_Allocator,
          class Visitor>
void r_c_shortest_paths(
    const Graph& g,
    const VertexIndexMap& vertex_index_map,
    const EdgeIndexMap& edge_index_map,
    typename graph_traits<Graph>::vertex_descriptor s,
    typename graph_traits<Graph>::vertex_descriptor t,
    std::vector<std::vector<typename graph_traits<Graph>::edge_descriptor>>& pareto_optimal_solutions,
    std::vector<Resource_Container>& pareto_optimal_resource_containers,
    const Resource_Container& rc,
    const Resource_Extension_Function& ref,
    const Dominance_Function& dominance,
    Label_Allocator la,
    Visitor vis)
方向 参数 说明

IN

const Graph& g

算法所作用的图对象. 类型 Graph 必须是有向的, 且必须是 关联图 和 属性图 的模型.

IN

const VertexIndexMap& vertex_index_map

一个 ReadablePropertyMap, 将顶点描述符映射到 [0, num_vertices(g)) 内的整数.

IN

const EdgeIndexMap& edge_index_map

一个 ReadablePropertyMap, 将边描述符映射到 [0, num_edges(g)) 内的整数.

IN

vertex_descriptor s

路径的起始顶点.

IN

vertex_descriptor t

路径的结束顶点.

OUT

std::vector<std::vector<edge_descriptor>>& pareto_optimal_solutions

用于存储所有 Pareto 最优(未被支配)的 s-t 路径的容器. 路径以边描述符序列的形式按逆序返回(从 t 到 s).

OUT

std::vector<Resource_Container>& pareto_optimal_resource_containers

用于存储与所有 Pareto 最优解对应的 Pareto 最优资源容器的容器.

IN

const Resource_Container& rc

指定顶点 s 处初始资源消耗的对象. 类型 Resource_Container 必须是 ResourceContainer 概念的模型.

IN

const Resource_Extension_Function& ref

指定标号如何沿一条弧扩展的函数对象、函数指针或函数. 类型 Resource_Extension_Function 必须是 ResourceExtensionFunction 概念的模型.

IN

const Dominance_Function& dominance

指定两个标号之间支配关系的函数对象、函数指针或函数. 类型 Dominance_Function 必须是 DominanceFunction 概念的模型.

IN

Label_Allocator la

指定标号内存管理策略的对象. 它必须提供与 std::allocator<r_c_shortest_paths_label<Graph, Resource_Container>> 相同的接口. 此参数有默认类型 default_r_c_shortest_paths_allocator, 使用 STL 标准分配器. 若想使用特制的分配器, 可为分配器的值类型模板参数指定任意类型; 该参数会被重绑定到正确的类型.

IN

Visitor vis

指定在算法的各事件点执行何种操作的访问器对象. 类型 Visitor 必须是 ResourceConstrainedShortestPathsVisitor 概念的模型. 此参数有默认类型 default_r_c_shortest_paths_visitor, 其函数体为空.

引言与问题描述

带资源约束的最短路径问题(SPPRC)是在有向图中求从起点到终点的一条最短(最省、最快)路径, 弧长(行程时间、费用)任意, 且受一个或多个资源约束限制. 例如, 可以在下列约束条件下求从 s 到 t 的最短路径:

  • 总行程时间不得超过某个上界, 并且/或者

  • 沿路径在各顶点必须取走某种货物的总量小于等于某个容量上限, 并且/或者

  • 若路径上访问了两个顶点 i 和 j, 则必须先访问 i, 再访问 j

  • 等等.

该问题在强意义下是 NP 难的. 若路径不必是初等的(即允许顶点被多次访问), 问题可以在伪多项式时间内求解. 与不带资源约束的 SPP 不同, SPPRC 中两条(部分)路径可能互不可比, 这一点至关重要. 这使得 SPPRC 类似于多准则决策问题.
关于该问题的近期综述如下:
Irnich, S.; Desaulniers, G. (2005):
Shortest Path Problems with Resource Constraints
, 载于:
Desaulniers, G.; Desrosiers, J.; Solomon, M. (eds.) (2005):
Column Generation
, Springer, New York, pp. 33-65
(在线阅读见 此处)

本文档无法对 SPPRC 作完整介绍. 要透彻理解该问题, 请读者参阅上述论文. 不过, 为了理解该算法及其实现, 有必要解释一些基本思想, 并指出它与不带资源约束的最短路径问题(SPP)的标号算法之间的差异.

SPPRC 的标准求解技术是基于动态规划的标号算法. 该方法使用 资源 和 资源扩展函数 的概念. 资源是在图的有向行走的各顶点处可以确定或测量的一维信息, 其刻度可以任意. 例如费用、时间、载重, 或“当前路径上是否访问过顶点 i”这类信息. 若图中存在至少一个顶点, 资源在该顶点处不得取所有可能的值, 则该资源是 受约束的. 资源在某顶点处的 资源窗口 是该资源在此顶点处允许取值的集合.

对图中每条弧上的每种所考虑的资源, 都定义一个资源扩展函数. 某资源的资源扩展函数将该弧源点处资源值的所有可能向量(数学意义上的向量, 不要与 std::vector 混淆)映射为该弧目标点处该资源的可能值集合. 这意味着一个资源在某顶点处的值可能依赖于前一顶点处一个或多个其他资源的值.

标号 用于存储部分路径的资源值信息. SPPRC 标号算法中的标号不像 SPP 标号算法中那样只是驻留顶点、当前费用和前驱顶点的三元组. SPPRC 标号算法的标号存储其驻留顶点、其被扩展时所经的前驱 弧、其前驱标号, 以及其当前的资源值向量. 待最小化的准则(费用、行程时间、行程距离等)也被当作一种(可能不受约束的)资源. 必须存储前驱弧而非前驱顶点, 因为由于资源约束的存在, 不能假定底层图是简单图. 标号驻留在顶点上, 当标号沿一条弧被扩展时, 通过资源扩展函数传播. 标号沿弧 (i, j) 的 扩展 是 可行的, 当且仅当所得标号 l(位于 j)是可行的, 也就是 l 的所有资源值都位于其资源窗口之内.

为使标号数量尽可能少, 关键在于执行 支配步骤 以消除不必要的标号. 标号 l1 支配 标号 l2, 如果两者驻留在同一顶点, 并且对 l2 的每个可行扩展, l1 也存在一个可行扩展, 使得每个基数刻度资源的值小于等于 l2 的扩展中该资源的值, 且每个名义刻度资源的值等于 l2 的扩展中该资源的值. 被支配的标号无需再扩展. 不被任何其他标号支配的标号称为未支配标号或 Pareto 最优标号. 支配原理的应用是可选的 — 至少从理论上如此.

本实现是标号设置(label-setting)算法. 这意味着必须存在一个或多个资源, 其在扩展后的累计消耗总是不低于扩展前. 这类似于不带资源约束的 SPP 中的 Dijkstra 算法, 其中距离度量必须非负. 只要存在一个资源在所有弧上的资源消耗均非负(例如非负的弧长或非负的弧行程时间)即可.

概念

ResourceContainer

用于建模 ResourceContainer 概念的类型, 用来存储标号的当前资源消耗.

细化自
可默认构造、可复制构造、可赋值、可小于比较、可相等比较

有效表达式
见 ResourceExtensionFunction 概念.

标号

此概念定义 r_c_shortest_paths 函数中标号的接口. 设计上决定不对函数按标号类型进行参数化. 类型 template<class Graph, class Resource_Container> struct r_c_shortest_paths_label 用于建模此概念.

有效表达式
若 label 是类型 r_c_shortest_paths_label 的对象, 则以下表达式有效:

表达式 说明

label.num

返回一个无符号整数值, 指定该标号的编号. 标号按其创建顺序连续编号.

label.cumulated_resource_consumption

返回与 label 关联的、建模 ResourceContainer 概念的对象.

label.p_pred_label

返回指向前驱标号的 const 指针, 即指向沿 label.pred_edge 扩展而得到 label 对象的那个标号.

label.pred_edge

返回 label.p_pred_label 被扩展而得到 label 对象时所沿弧的边描述符.

label.resident_vertex

返回 label 对象所驻留顶点的顶点描述符.

label.b_is_dominated

返回一个布尔值, 指示 label 对象是否被驻留在顶点 label.resident_vertex 处的某个其他标号所支配. 仅在执行过支配检查之后有用, 即仅在访问器函数 on_label_dominated 和 on_label_not_dominated 中有用(见 下文).

不变式
除第一个标号外, 每个 r_c_shortest_paths_label 对象都具有有效的(非空) p_pred_label 指针和有效的 pred_edge 成员. p_pred_label 指针为空指针的标号正是 num 成员等于零的那个标号, 其 pred_edge 成员是默认构造的边描述符.

ResourceExtensionFunction

ResourceExtensionFunction 概念的模型用于指定标号如何沿一条弧扩展.

有效表达式
若 ref 建模 ResourceExtensionFunction 概念, 且类型 Resource_Container 建模 ResourceContainer 概念, 则以下表达式有效:

bool b = ref( const Graph& g,
              Resource_Container& new_cont,
              const Resource_Container& old_cont,
              graph_traits<Graph>::edge_descriptor ed )

ref 必须返回 true, 当且仅当扩展可行, 即 new_cont 在 ed 的目标顶点处满足所有资源约束.

此外, 建模 ResourceExtensionFunction 概念的类型的引用可以作为参数传给 r_c_shortest_paths, 见上文.

因此, 建模 ResourceExtensionFunction 概念的类型很可能是函数或 函数对象.

不变式
若 ref 建模 ResourceExtensionFunction 概念, 且类型 Resource_Container 建模 ResourceContainer 概念, 则经过如下调用后

ref( const Graph& g,
     Resource_Container& new_cont,
     const Resource_Container& old_cont,
     graph_traits<Graph>::edge_descriptor )

表达式 old_cont <= new_cont 的求值结果为 true.
其原因在于, 如上所述, 本实现是标号设置(label-setting)算法. 因此, 为使算法正常工作, ResourceContainer 的小于运算符必须比较在任意弧上消耗均非递减的一个或多个资源.

DominanceFunction

DominanceFunction 的模型用于指定两个标号之间的支配关系.

细化自
二元谓词

有效表达式
若 dominance 建模 DominanceFunction 概念, 且类型 Resource_Container 建模 ResourceContainer 概念, 则以下表达式有效:

bool b = dominance(const Resource_Container& rc1, const Resource_Container& rc2)

dominance 必须返回 true, 当且仅当 rc1 支配 rc2.

此外, 建模 DominanceFunction 概念的类型的引用可以作为参数传给 r_c_shortest_paths, 见上文.

不变式
建模 DominanceFunction 概念的类型必须返回 true, 当且仅当 rc1<=rc2. 它必须 不 返回 false, 如果 rc1==rc2. 由此保证, 任何两个资源消耗完全相同的标号不会互相支配, 也不会都被 r_c_shortest_paths 函数视为已支配.

ResourceConstrainedShortestPathsVisitor

此概念为 r_c_shortest_paths 定义访问器接口. 用户可以定义具有此接口的类型, 并把该类型的对象传给 r_c_shortest_paths, 以在算法的事件点执行用户自定义动作. 注意, 该对象按值传递.

细化自
可默认构造、可复制构造

有效表达式
若 vis 是建模 ResourceConstrainedShortestPathsVisitor 概念的类型的对象, 且 g 是类型 Graph 的对象, 该类型建模 IncidenceGraph 与 PropertyGraph 概念且为有向图, 且 l 是建模 Label 概念的类型 Label 的对象, 则以下表达式有效:

vis.on_enter_loop(const Queue& queue, const Graph& g)

vis.on_label_popped(const Label& l, const Graph& g)

vis.on_label_feasible(const Label& l, const Graph& g)

vis.on_label_not_feasible(const Label& l, const Graph& g)

vis.on_label_dominated(const Label& l, const Graph& g)

vis.on_label_not_dominated(const Label& l, const Graph& g)

注意, on_enter_loop 返回一个布尔值, 指示主循环是否应继续(参见 default_r_c_shortest_paths_visitor, 位于 source code 中, 可资借鉴). Label 的接口见 Label 概念的说明. 这些函数何时被调用见 算法说明.

算法描述

这些函数是基于优先队列的标号设置算法的实现. 每次迭代中, 算法从优先队列(未处理标号的集合)中取出一个标号 l, 并针对 l 所驻留顶点 i 处的当前标号集合检查其是否被支配. 若 l 被驻留在 i 处的某个其他标号支配, 则将 l 从 i 处的标号集合中删除. 若 l 未被支配, 则沿 i 的所有出边扩展它. 得到的每个新标号都要检查可行性, 若可行, 则加入未处理标号集合, 并加入 i 的相应后继顶点处的标号集合. 若新标号不可行, 则丢弃. 当没有更多未处理标号时算法停止. 随后算法检查是否可达目标顶点(由于资源约束, 即使是强连通图也可能不可达), 构造一条或全部 Pareto 最优(即未被支配)的 s-t 路径并返回. 算法伪代码如下.

r_c_shortest_paths( g,
                    vertex_index_map,
                    edge_index_map,
                    s,
                    t,
                    pareto_optimal_solutions,
                    pareto_optimal_resource_containers,
                    rc,
                    ref,
                    dominance,
                    la,
                    vis )
{
  Label first_label, cur_label, new_label
  Set of Labels unprocessed_labels, labels_cur_vertex
  initialize first_label with rc
  INSERT(unprocessed_labels, first_label)
  while(unprocessed_labels != Ø)
    cur_label := EXTRACTMIN(unprocessed_labels)                      ◁ vis.on_label_popped(cur_label)
    if(cur_label is not dominated)
      vertex i = ResidentVertex(cur_label)
      perform pairwise dominance check over labels resident at i
      mark all dominated labels as dominated
      DELETE all labels which are dominated AND processed
    if(cur_label is not dominated)                                   ◁ vis.on_label_not_dominated(cur_label)
      mark cur_label as processed
      for each arc (i, j) in the forward star of i
        new_label := ref(cur_label)
        if(new_label is not feasible)                                ◁ vis.on_label_not_feasible(new_label)
          DELETE(new_label)
        else                                                         ◁ vis.on_label_feasible(new_label)
          INSERT(unprocessed_labels, new_label)
          INSERT(set of labels resident at j,new_label)
    else                                                             ◁ vis.on_label_dominated(cur_label)
      DELETE(cur_label)
  if(t could be reached from s)
    for each label resident at t
      INSERT(pareto_optimal_resource_containers, label.resource_container)
      recursively construct pareto_optimal_path
      INSERT(pareto_optimal_solutions, pareto_optimal_path)
      if(only one Pareto-optimal solution is sought)
        BREAK
}

前置条件

  • s 和 t 是 g 的有效顶点描述符.

  • rc 位于 s 的资源窗口之内, 即它构成一个可行的 Resource_Container 对象, 存在于 s 处(见 讨论).

抛出

函数本身不抛出任何异常. 但是, 视模板参数而定, 函数内部可能抛出异常.

注释

讨论

该函数把大量工作留给用户, 几乎就是一个 SPPRC 的小框架. 不过, 这是问题本身固有的属性. 用户完全需要自行确保: 在资源容器对象中保存“正确”的资源, 资源扩展函数按期望的方式扩展标号, 以及支配函数把“正确”的标号声明为已支配或未支配. 特别是, 提供给函数的初始 ResourceContainer 对象必须可行这一前置条件, 既重要又令人不快. 本实现不检查这一点, 因此在这里为了通用性而牺牲了易用性. 这是一个设计决策: 不对建模 ResourceContainer 的类型与图类型的顶点属性之间的关系作任何假设.

若底层图不含负环(即待最小化的无约束资源(如费用或距离)总消耗为负的环), 所得路径将总是初等的, 即不重复顶点. 若存在负环, 则只要存在至少一个严格递增的资源, 即在所有弧上资源消耗严格为正的资源(这是充分条件), 算法就是有限的. 否则, 必须为 ResourceContainer 概念提供定制的类型以保证有限性. 例如可参见
Feillet, D.; Dejax, P.; Gendreau, M.; Gueguen, C. (2004):
An Exact Algorithm for the Elementary Shortest Path Problem with Resource Constraints: Application to Some Vehicle Routing Problems
, Networks, vol. 44, pp. 216-229.

经验表明, 对“较小”的资源容器, 尝试专用的小对象分配器可能有用, 例如 Boost Pool 库中的分配器. 对较大的资源容器(即资源数量很多时), 默认分配器是正确的选择.

分配器与访问器的默认值

若使用该函数的第三个或第四个重载, 则类型 default_r_c_shortest_paths_allocator 和 default_r_c_shortest_paths_visitor 的对象分别用作 Label_Allocator 和 Visitor 参数. 若使用第一个或第二个重载, 则必须同时指定 Label_Allocator 和 Visitor 参数. 若只想为 Visitor 开发用户自定义类型, 可以使用 default_r_c_shortest_paths_allocator 作为 Label_Allocator 参数. 若只想使用专用分配器, 可以使用 default_r_c_shortest_paths_visitor 作为 Visitor 参数.

实用函数: check_r_c_path

有一个名为 check_r_c_path 的实用函数可用于调试, 适用情形是: r_c_shortest_paths 把某条路径判定为可行且 Pareto 最优, 而用户认为该路径不可行或非最优:

template <class Graph,
          class Resource_Container,
          class Resource_Extension_Function>
void check_r_c_path(
    const Graph& g,
    const std::vector<typename graph_traits<Graph>::edge_descriptor>& ed_vec_path,
    const Resource_Container& initial_resource_levels,
    bool b_result_must_be_equal_to_desired_final_resource_levels,
    const Resource_Container& desired_final_resource_levels,
    Resource_Container& actual_final_resource_levels,
    const Resource_Extension_Function& ref,
    bool& b_is_a_path_at_all,
    bool& b_feasible,
    bool& b_correctly_extended,
    typename graph_traits<Graph>::edge_descriptor& ed_last_extended_arc)

布尔参数的含义如下:

  • 若 b_result_must_be_equal_to_desired_final_resource_levels==true, 则计算出的累计最终资源水平必须等于 desired_final_resource_levels.

  • 若 b_result_must_be_equal_to_desired_final_resource_levels==false, 则计算出的累计最终资源水平必须小于等于 desired_final_resource_levels.

  • b_is_a_path_at_all==true, 当且仅当 ed_vec_path 指定图论意义下的一条行走(walk), 即一个弧序列, 其中每条弧的目标点是下一条弧的源点; 或者一条反向行走, 其中一条弧的源点是下一条弧的目标点. 注意, 在资源受限最短路径的领域里, 路径不必是初等的: 允许重复顶点或弧. 当图中没有任何负费用环(行程费用、行程时间等)时, r_c_shortest_paths 返回的路径将是初等的. 否则, 必须使用恰当的资源容器以及资源扩展函数和支配函数(见上述文献).

  • b_feasible==true, 当且仅当 b_is_a_path_at_all==true, 且路径上所有顶点处的所有资源窗口均得到维持.

  • 当 b_result_must_be_equal_to_desired_final_resource_levels==true(false)时, b_correctly_extended==true, 当且仅当 b_feasible==true, 且路径终点处计算出的资源水平等于(小于等于) desired_final_resource_levels 中指定的期望最终资源水平.

ed_last_extended_arc 存储最后被扩展的弧的边描述符. 若 ed_vec_path 是一条长度为正的路径且 b_feasible==false, 则 ed_last_extended_arc 是其目标顶点处首次违反资源窗口的那条弧的边描述符.

文件 example/r_c_shortest_paths_example.cpp 提供了如何用 r_c_shortest_paths 函数求解 SPPRC 的更多示例. 其中有一个不带资源约束的 SPP 示例和一个带时间窗的最短路径问题示例.
显然, 人们不会把该算法用于不带资源约束的 SPP, 因为对此问题已有更快的算法, 但人们会期望带资源约束的 SPP 代码能够处理这种情形.
