保持稳定连接

本章深入介绍 mqtt_client 用于与代理服务器保持稳定连接的策略.

理解保持连接与服务器保持连接

首先, 需要理解 Keep Alive 与 Server Keep Alive 及其在维持稳定连接中的作用.

MQTT 协议定义了 Keep Alive 值, 它是从客户端完成发送一个报文到开始发送下一个报文之间允许经过的最大时间间隔. 在某些情况下, 代理服务器可能会提议一个 Server Keep Alive 间隔, 客户端应采用该间隔而非先前设置的 Keep Alive 间隔 (下文称为协商后的 Keep Alive 间隔).

如果客户端在等于协商后的 1.5 倍 Keep Alive 间隔的时间内未传输任何报文, 代理服务器必须关闭与客户端的连接.

客户端负责确保发送报文的间隔不超过协商后的 Keep Alive 间隔. mqtt_client 会自动完成这一点: 它向代理服务器发送 PINGREQ, 每次间隔为协商后的 Keep Alive 秒, 与连接上的任何进行中的活动无关.

若协商后的 Keep Alive 间隔为 0, 保持连接机制将停用, mqtt_client 将 不会 发送任何 PINGREQ 报文. 这使得维护与代理服务器连接的责任落在用户身上.

使用 mqtt_client::keep_alive 函数, 在 mqtt_client 的配置阶段以秒为单位指定你偏好的 Keep Alive 时间. 否则, mqtt_client 将默认采用 Keep Alive 时间为 60 seconds.

注释

MQTT 协议不使用 TCP 内置的保持连接 (keep-alive) 机制, 因为该机制不灵活且受限, 只能在操作系统层面配置. 在发送第一个保持连接报文之前, 连接必须空闲的默认时间通常设为 2 小时, 超出了大多数 MQTT 应用的容忍范围.

检测与处理半开连接

鉴于软件异常、硬件故障、信号丢失、路由器问题、连接路径中断等诸多潜在干扰, 确保网络连接的完整性与稳定性是一项复杂任务. 尽管识别这些干扰本身就很困难, 健壮的客户端实现仍必须准确检测并解决此类问题.

正常情况下, 当一方想要关闭 TCP 连接时, 会发起 TCP 终止过程, 即四次握手. 发起方发送一个指示数据传输结束的 TCP 报文来完成 TCP 连接, 接收方对此进行确认. 接着接收方发送相同的终止报文, 并等待发起方的确认以结束整个过程. 这确保双方都已完成全部数据的收发, 并一致同意优雅地关闭连接.

然而, 连接可能因外部干扰而突然终止. 例如, 设想客户端正与代理服务器通信, 却突然遭遇意外的信号丢失. 由于双方都没有发起四次握手来关闭连接, 客户端没有任何理由认为连接不是打开状态. 因此, 它会继续向代理服务器发送报文并等待响应, 浑然不知这些报文永远无法到达另一端的代理服务器. 这导致半开 TCP 连接场景: 连接在一端实际已终止, 在另一端却仍然存活.

若没有任何识别半开连接的机制, 客户端就有无限期停留在半开状态的风险. 处理半开状态的常见策略是引入超时机制. 在此策略下, 客户端预期在预定义的超时区间内从代理服务器收到一些数据. 在该区间内成功收到数据即证明连接活跃且稳定. 若在超时区间内未收到任何数据, 客户端将假定网络故障并关闭连接. 因此, 若客户端处于半开状态, 则不会有数据送达, 连接将超时. 这一条件触发客户端发起重连过程, 尝试恢复被切断的连接.

为避免在空闲连接上误检半开状态, 客户端必须确保持续的数据交换. 这通过客户端周期性地向代理服务器发送 PINGREQ 报文实现, 代理服务器则以 PINGRESP 报文回应, 确认其运行状态.

mqtt_client 会发送 PINGREQ, 间隔为协商后的 Keep Alive 秒, 并预期从代理服务器收到一些数据 [1], 时间为 1.5 倍协商后的 Keep Alive 秒. 若在此时间内未收到任何数据, mqtt_client 将认定处于半开状态, 并发起 内置自动重连与重试机制 中所述的重连过程.

重要

若协商后的 Keep Alive 值被设为 0, 检测半开连接的超时机制将被禁用. 于是 mqtt_client 将失去识别并妥善应对半开场景的能力.


[1] mqtt_client 并不要求必须收到 PINGRESP 才能确认其 PINGREQ. 来自代理服务器的任何数据都足以确认其状态.
