按操作取消

在 Boost.Asio 中, 套接字和定时器等各类对象可通过其 close 或 cancel 成员函数全局终止所有正在进行的异步操作. 除这种全局取消能力外, Boost.Asio 还提供逐个取消特定异步操作的机制. 这种逐操作取消通过为完成处理器指定关联取消槽来实现. 若异步操作支持取消, 它会在关联槽中安装一个取消处理器. 当用户向取消槽发出取消信号时, 该取消处理器将被调用. 更多信息请参见 逐操作取消.

在使用 boost::asio::experimental::parallel_group 并行启动多个工作并等待其中一个或全部操作完成时, 逐操作取消的作用尤为明显. 例如, 在并行组中等待若干操作中任意一个完成时, 某个操作完成将触发对其余所有操作的逐个取消. 同样的概念也适用于 awaitable operator ||, 它并行运行两个 awaitable, 等待其中一个完成后随即取消另一个. 更多信息请参见 协调并行操作.

在 mqtt_client 中, 每个异步函数都设计为支持逐操作取消. 这允许为任何 async_xxx 函数调用关联取消槽, 从而按需发出取消信号. 取消信号如何影响每个 async_xxx 函数的详细说明, 见其相应章节中的 逐操作取消 段落, 载于 mqtt_client 参考文档.

示例: 将取消槽与异步操作关联

此示例演示将取消槽与 mqtt_client::async_publish 操作关联并发出 terminal 取消信号. 执行这一序列实际上会立即取消整个客户端操作, 效果等同于直接调用 mqtt_client::cancel.

若发出的不是 terminal 而是 total 或 partial 取消信号, 影响则较轻. 此时取消仅针对 PUBLISH 报文的重发, 防止在操作进行期间客户端重连时该报文被重传.

boost::mqtt5::mqtt_client<boost::asio::ip::tcp::socket> client(ioc);

client.brokers("<your-mqtt-broker>", 1883)
    .async_run(boost::asio::detached);

boost::asio::cancellation_signal signal;

client.async_publish<boost::mqtt5::qos_e::at_least_once>(
    "<topic>", "Hello world!",
    boost::mqtt5::retain_e::no, boost::mqtt5::publish_props {},
    boost::asio::bind_cancellation_slot(
        signal.slot(),
        [&client](boost::mqtt5::error_code ec, boost::mqtt5::reason_code rc, boost::mqtt5::puback_props props ) {
            std::cout << ec.message() << std::endl;
        }
    )
);

signal.emit(boost::asio::cancellation_type_t::terminal);

mqtt_client 中的 parallel_group/operator || 与异步函数

由于支持逐操作取消, mqtt_client 的所有异步函数都可用于 parallel_group 或配合 awaitable operator || 使用. 这一特性对执行需要超时机制的操作尤为有益.

关于协议级取消

在 mqtt_client 中, 不同异步操作对取消信号的处理方式各不相同. 除 mqtt_client::async_receive 外, 其余所有 async_xxx 操作都会通过调用 mqtt_client::cancel 来响应 terminal 取消信号. 对于 total 与 partial 取消信号, 这些操作将停止重发某些报文.

值得注意的是, 出于防止违反协议的设计考虑, 未实现在协议交换进行过程中取消 async_xxx 操作. 例如, 若 QoS 2 的 mqtt_client::async_publish 正在与代理服务器 [6] 通信的中途被尝试取消, 可能导致违反协议. 比如, 若在从代理服务器收到 PUBREC 报文之后、发送 PUBREL 报文之前取消了操作, 就会因未能发送必要报文而违反 MQTT 协议, 并使与代理服务器的连接处于无效状态.

因此, mqtt_client 的取消策略设计经过慎重考虑, 避免了这些陷阱, 以确保始终符合协议.


[6] 以 QoS 2 发布包括: 发送 PUBLISH 报文, 从代理服务器接收 PUBREC 确认, 发送 PUBREL 报文, 最后接收 PUBCOMP 报文.
