优化通信

本章详细剖析 mqtt_client 如何通过多重在途模式 (同时处理消息) 及高效带宽使用策略来优化与代理服务器的通信. 这些技术是在要求快速可靠消息投递的场景中充分发挥 MQTT 效能的关键, 同时满足协议的服务质量要求和网络效率标准.

多重在途模式

Boost.MQTT5 库引入了多重在途 (multiflight) 特性. 它允许同时发起多个异步请求, 而无需等待先前请求完成. 有了这一特性, 你可以反复调用 mqtt_client::async_publish 或任何类似的 async_xxx 函数, 而无需等待先前 async_xxx 调用的处理器被调用.

这一特性在配合回调使用 mqtt_client 时尤为有用, 因为它让你可以一个接一个地快速派发多个请求, 而不是将它们嵌套在回调中.

考虑下面的示例: 以 QoS 2 调用 mqtt_client::async_publish 5 次, 处于一个 for 循环中. QoS 等级 2 确保每条消息恰好投递一次, 并涉及四步通信过程: 发送 PUBLISH 报文, 从代理服务器接收 PUBREC 确认, 传输 PUBREL 报文, 最后接收 PUBCOMP 报文以确认消息成功投递.

尽管连续发起多个这样的消息交换序列十分复杂, mqtt_client 仍会正确管理 mqtt_client 与代理服务器之间的所有中间报文交换, 并完成消息投递.

值得注意的是, 无法保证最终处理器按相应 async_xxx 调用发起的相同顺序被调用.

来源: multiflight_client.cpp 

#include <boost/mqtt5/logger.hpp>
#include <boost/mqtt5/mqtt_client.hpp>
#include <boost/mqtt5/reason_codes.hpp>
#include <boost/mqtt5/types.hpp>

#include <boost/asio/detached.hpp>
#include <boost/asio/io_context.hpp>
#include <boost/asio/ip/tcp.hpp>
#include <boost/asio/signal_set.hpp>

#include <iostream>
#include <string>

struct config {
    std::string brokers = "broker.hivemq.com";
    uint16_t port = 1883;
    std::string client_id = "boost_mqtt5_tester";
};

int main(int argc, char** argv) {
    config cfg;

    if (argc == 4) {
        cfg.brokers = argv[1];
        cfg.port = uint16_t(std::stoi(argv[2]));
        cfg.client_id = argv[3];
    }

    boost::asio::io_context ioc;

    // Construct the Client with boost::asio::ip::tcp::socket as the underlying stream and enabled logging.
    // Since we are not establishing a secure connection, set the TlsContext template parameter to std::monostate.
    boost::mqtt5::mqtt_client<
        boost::asio::ip::tcp::socket, std::monostate /* TlsContext */, boost::mqtt5::logger
    > client(ioc, {} /* tls_context */, boost::mqtt5::logger(boost::mqtt5::log_level::info));

    client.brokers(cfg.brokers, cfg.port) // Broker that we want to connect to.
        .credentials(cfg.client_id) // Set the Client Identifier. (optional)
        .async_run(boost::asio::detached); // Start the client.

    // Publish with QoS 2 five times in a row without waiting for the handler
    // of the previous async_publish call to be invoked.
    for (auto i = 1; i <= 5; ++i)
        client.async_publish<boost::mqtt5::qos_e::exactly_once>(
            "boost-mqtt5/test", "Hello world!",
            boost::mqtt5::retain_e::no, boost::mqtt5::publish_props {},
            [i](boost::mqtt5::error_code ec, boost::mqtt5::reason_code rc, boost::mqtt5::pubcomp_props) {
                std::cout << "Publish number " << i << " completed with: " << std::endl;
                std::cout << "\t ec: " << ec.message() << std::endl;
                std::cout << "\t rc: " << rc.message() << std::endl;
            }
        );

    // We can stop the Client by using signals.
    boost::asio::signal_set signals(ioc, SIGINT, SIGTERM);
    signals.async_wait([&client](boost::mqtt5::error_code, int) {
        client.async_disconnect(boost::asio::detached);
    });

    ioc.run();
}

通过数据包排队高效利用带宽

mqtt_client 采用一种战略性排队机制, 对优化用户请求的网络使用与性能至关重要. 只要可行 [2], 该机制就会将多个 MQTT 报文打包到一个 TCP 报文内传输. 这显著降低了性能开销, 提升了数据吞吐, 并减少了单个报文传输带来的延迟. 其结果是快速的性能和高效的网络资源利用.

此外, 排队机制确保 mqtt_client 遵守代理服务器设置的 Receive Maximum 值. 该值用于实现发送配额, 限制尚未收到确认的 QoS > 0 PUBLISH 报文数量 (QoS 1 为 PUBACK, QoS 2 为 PUBCOMP) (参见 Flow Control). 当以 QoS > 0 调用 mqtt_client::async_publish 时, mqtt_client 会将当前未确认 PUBLISH 报文的数量与代理服务器的 Receive Maximum 阈值进行比较. 若数量低于该阈值, mqtt_client 将派发 PUBLISH 报文; 否则报文将留在队列中, 直到数量降到阈值以下.

因此, 在 multiflight_client.cpp 示例中, mqtt_client 将把所有 5 个 PUBLISH 报文打包到单个 TCP 报文中传输 (若有可能) [3].

数据包排序

mqtt_client 使用报文排序机制来管理等待派发到代理服务器的排队报文. 最重要的排序规则如下:

- PUBLISH 报文按其通过 mqtt_client::async_publish 调用发起的顺序传输. 即使在需要重传报文的情况下, 这种顺序完整性也会得到保持, 确保消息投递顺序一致. 但需要注意, 当代理服务器设置了 Receive Maximum 值时, QoS 0 与 QoS > 0 报文之间不保持顺序. 代理服务器可以设置该值来限制其能同时处理的 QoS > 0 消息数量, 这可能导致 QoS 0 消息在投递顺序中被提前于 QoS > 0 消息传输.

- DISCONNECT 报文会 以单个 TCP 报文、先于队列中任何其他报文 发送. 有关断开的更多信息请参见 断开客户端连接.


[2] 当 mqtt_client 正在将先前的请求写入传输层时, 请求会被排队并打包.

[3] 代理服务器的 Receive Maximum 等于或大于 5.
