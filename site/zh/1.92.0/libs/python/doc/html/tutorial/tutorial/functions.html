调用策略

在 C++ 中, 我们经常处理指针和引用之类的参数与返回类型. 这些原始类型相当——呃——底层, 它们并不能告诉我们太多信息. 至少, 我们不知道指针或被引用对象的所有者是谁. 难怪 Java 和 Python 这样的语言从不与这种底层实体打交道. 在 C++ 中, 使用能准确描述所有权语义的智能指针通常被视为良好实践. 尽管如此, 即使是好的 C++ 接口有时也会使用裸引用和指针, 所以 Boost.Python 必须处理它们. 为此, 它可能需要你的帮助. 考虑以下 C++ 函数:

X& f(Y& y, Z* z);

库应当如何包装这个函数? 一种天真的做法是把 result 引用包进一个 Python X 对象. 这种策略可能行得通, 也可能行不通. 下面就是一个行不通的例子

>>> x = f(y, z) # x refers to some C++ X
>>> del y
>>> x.some_method() # CRASH!

问题在哪里?

嗯, 如果 f() 的实现如下所示呢:

X& f(Y& y, Z* z)
{
    y.z = z;
    return y.x;
}

问题在于 result X& 的生存期与 y 的生存期绑定在一起, 因为 f() 返回的是对 y 对象成员的引用. 这种习语并不罕见, 在 C++ 语境中也完全可接受. 然而, Python 用户不应仅仅使用我们的 C++ 接口就能使系统崩溃. 在这个例子里, 删除 y 会使对 X 的引用失效. 我们遇到了悬空引用.

事情的经过是:

  1. 调用 f, 传入对 y 的引用和指向 z 的指针
  2. 返回对 y.x 的引用
  3. y 被删除. x 是悬空引用
  4. 调用 x.some_method()
  5. 轰!

我们可以把 result 复制到一个新对象中:

>>> f(y, z).set(42) # Result disappears
>>> y.x.get()       # No crash, but still bad
3.14

这并不是我们 C++ 接口的本意. 我们违背了 Python 接口应尽可能贴近 C++ 接口的承诺.

我们的问题还没完. 假设 Y 的实现如下:

struct Y
{
    X x; Z* z;
    int z_value() { return z->value(); }
};

注意, 数据成员 z 由类 Y 用裸指针持有. 现在我们在 Y 内部有一个潜在的悬空指针问题:

>>> x = f(y, z) # y refers to z
>>> del z       # Kill the z object
>>> y.z_value() # CRASH!

作为参考, 这里再次给出 f 的实现:

X& f(Y& y, Z* z)
{
    y.z = z;
    return y.x;
}

事情的经过是:

  1. 调用 f, 传入对 y 的引用和指向 z 的指针
  2. 指向 z 的指针由 y 持有
  3. 返回对 y.x 的引用
  4. z 被删除. y.z 是悬空指针
  5. 调用 y.z_value()
  6. 调用 z->value()
  7. 轰!

调用策略

调用策略可用于类似上面详述例子的情形. 在我们的例子中, return_internal_reference 和 with_custodian_and_ward 是我们的朋友:

def("f", f,
    return_internal_reference<1,
        with_custodian_and_ward<1, 2> >());

你要问 1 和 2 参数是什么?

return_internal_reference<1

告知 Boost.Python 第一个参数 (在我们的例子里是 Y& y) 是返回引用的所有者: X&. "1" 只是指定第一个参数. 简言之: "返回一个内部引用 X&, 由第 1 个参数 Y& y 所拥有".

with_custodian_and_ward<1, 2>

告知 Boost.Python, ward 所指示参数 (即第 2 个参数: Z* z) 的生存期依赖于 custodian 所指示参数 (即第 1 个参数: Y& y) 的生存期.

同样重要的是, 我们在上面定义了两个策略. 两个或更多策略可以通过链式组合. 一般语法如下:

policy1<args...,
    policy2<args...,
        policy3<args...> > >

以下是预定义调用策略的清单. 详细说明这些策略的完整参考可在此处找到.

  • with_custodian_and_ward: 绑定参数的生存期
  • with_custodian_and_ward_postcall: 绑定参数与结果的生存期
  • return_internal_reference: 把一个参数的生存期绑定到结果的生存期
  • return_value_policy<T>, 其中 T 为:
    • reference_existing_object: 朴素 (危险) 做法
    • copy_const_reference: Boost.Python v1 做法
    • copy_non_const_reference:
    • manage_new_object: 接管指针并持有实例

Overloading

下面示例展示了手动包装重载成员函数的一种方案. 当然, 同样的技术也可用于包装重载的非成员函数.

这里是我们的 C++ 类:

struct X
{
    bool f(int a)
    {
        return true;
    }

    bool f(int a, double b)
    {
        return true;
    }

    bool f(int a, double b, char c)
    {
        return true;
    }

    int f(int a, int b, int c)
    {
        return a + b + c;
    };
};

类 X 有 4 个重载函数. 我们先引入一些成员函数指针变量:

bool    (X::*fx1)(int)              = &X::f;
bool    (X::*fx2)(int, double)      = &X::f;
bool    (X::*fx3)(int, double, char)= &X::f;
int     (X::*fx4)(int, int, int)    = &X::f;

有了这些, 我们就可以着手为 Python 定义并包装它:

.def("f", fx1)
.def("f", fx2)
.def("f", fx3)
.def("f", fx4)

默认参数

Boost.Python 包装 (成员) 函数指针. 遗憾的是, C++ 函数指针不携带默认参数信息. 看一个带默认参数的函数 f:

int f(int, double = 3.14, char const* = "hello");

但指向函数 f 的指针的类型没有关于其默认参数的信息:

int(*g)(int,double,char const*) = f;    // defaults lost!

当我们把这个函数指针传给 def 函数时, 没有办法取回默认参数:

def("f", f);                            // defaults lost!

因此, 在包装 C++ 代码时, 我们不得不像前一节所述的那样求助于手动包装, 或编写薄包装器:

// write "thin wrappers"
int f1(int x) { return f(x); }
int f2(int x, double y) { return f(x,y); }

/*...*/

    // in module init
    def("f", f);  // all arguments
    def("f", f2); // two arguments
    def("f", f1); // one argument

当你想包装的函数 (或成员函数) 满足以下任一条件时:

  • 带默认参数, 或
  • 以共同的初始参数序列重载

BOOST_PYTHON_FUNCTION_OVERLOADS

Boost.Python 现在有一种让它更简单的办法. 例如, 给定函数:

int foo(int a, char b = 1, unsigned c = 2, double d = 3)
{
    /*...*/
}

宏调用:

BOOST_PYTHON_FUNCTION_OVERLOADS(foo_overloads, foo, 1, 4)

会自动为我们创建薄包装器. 这个宏会创建一个类 foo_overloads, 它可以传给 def(...). 宏的第三和第四个参数分别是最小参数个数和最大参数个数. 在我们的 foo 函数中, 参数最少 1 个, 最多 4 个. def(...) 函数会自动为我们添加所有 foo 变体:

def("foo", foo, foo_overloads());

BOOST_PYTHON_MEMBER_FUNCTION_OVERLOADS

对象这里, 对象那里, 到处都是对象. 比什么都更频繁的是, 我们需要把类的成员函数暴露给 Python. 同样, 当默认参数或以共同初始参数序列重载登场时, 我们会遇到与之前相同的不便. 提供了另一个宏使这变得轻而易举.

与 BOOST_PYTHON_FUNCTION_OVERLOADS 一样, BOOST_PYTHON_MEMBER_FUNCTION_OVERLOADS 可用于自动创建包装成员函数的薄包装器. 来看一个例子:

struct george
{
    void
    wack_em(int a, int b = 0, char c = 'x')
    {
        /*...*/
    }
};

宏调用:

BOOST_PYTHON_MEMBER_FUNCTION_OVERLOADS(george_overloads, wack_em, 1, 3)

会为 george 的 wack_em 成员函数生成一组薄包装器, 接受最少 1 个、最多 3 个参数 (即宏的第三和第四个参数). 这些薄包装器全部封装在一个名为 george_overloads 的类中, 该类随后可用作 def(...) 的参数:

.def("wack_em", &george::wack_em, george_overloads());

详情参见overloads 参考.

init 与 optional

为类构造函数提供了类似的设施, 同样是针对默认参数或重载序列. 还记得 init<...> 吗? 例如, 给定一个带构造函数的类 X:

struct X
{
    X(int a, char b = 'D', std::string c = "constructor", double d = 0.0);
    /*...*/
}

你可以一次性轻松地把这个构造函数加入 Boost.Python:

.def(init<int, optional<char, std::string, double> >())

注意用 init<...> 和 optional<...> 表示默认 (可选参数).

自动重载

前一节顺带提到, BOOST_PYTHON_FUNCTION_OVERLOADS 和 BOOST_PYTHON_MEMBER_FUNCTION_OVERLOADS 也可用于带共同初始参数序列的重载函数和成员函数. 下面是一个例子:

void foo()
{
   /*...*/
}

void foo(bool a)
{
   /*...*/
}

void foo(bool a, int b)
{
   /*...*/
}

void foo(bool a, int b, char c)
{
   /*...*/
}

与前一节一样, 我们可以一次性为这些重载函数生成薄包装器:

BOOST_PYTHON_FUNCTION_OVERLOADS(foo_overloads, foo, 0, 3)

然后……

.def("foo", (void(*)(bool, int, char))0, foo_overloads());

不过要注意, 我们现在的情形是最少零 (0) 个参数、最多 3 个参数.

手动包装

但需要强调的是, 重载函数必须具有共同的初始参数序列. 否则, 我们上面的方案行不通. 如果情况并非如此, 我们就得手动包装函数.

实际上, 我们可以混合搭配重载函数的手动包装与通过 BOOST_PYTHON_MEMBER_FUNCTION_OVERLOADS 及其姐妹 BOOST_PYTHON_FUNCTION_OVERLOADS 的自动包装. 接着关于重载一节给出的例子, 由于前 4 个重载函数具有共同的初始参数序列, 我们可以用 BOOST_PYTHON_MEMBER_FUNCTION_OVERLOADS 自动包装 def 的前三个, 并只手动包装最后一个. 我们的做法如下:

BOOST_PYTHON_MEMBER_FUNCTION_OVERLOADS(xf_overloads, f, 1, 4)

像上面那样为两个 X::f 重载创建成员函数指针:

bool    (X::*fx1)(int, double, char)    = &X::f;
int     (X::*fx2)(int, int, int)        = &X::f;

然后……

.def("f", fx1, xf_overloads());
.def("f", fx2)
