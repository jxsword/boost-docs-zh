引言

在已有持有该函数的 object 实例 f 的情况下, 从 C++ 调用 Python 函数最简单的方式就是直接调用其函数调用运算符.

f("tea", 4, 2) // In Python: f('tea', 4, 2)

当然, object 实例 x 的方法可以通过使用相应属性的函数调用运算符来调用:

x.attr("tea")(4, 2); // In Python: x.tea(4, 2)

如果你没有 object 实例, Boost.Python 提供两族函数模板 call 和 call_method, 分别用于在 PyObject* 上调用 Python 函数和方法. 调用 Python 函数对象 (或任何 Python 可调用对象) 的接口形如:

call<ResultType>(callable_object, a1, a2... aN);

调用 Python 对象的方法同样简单:

call_method<ResultType>(self_object, "method-name", a1, a2... aN);

这个相对底层的接口就是你实现可在 Python 中改写的 C++ 虚函数时要用的接口.

参数处理

参数按其类型转换为 Python. 默认情况下, 参数 a1...aN 会被复制到新的 Python 对象中, 但可以通过使用 ptr() 和 ref() 覆盖这一行为:

class X : boost::noncopyable
{
   ...
};

void apply(PyObject* callable, X& x)
{
   // Invoke callable, passing a Python object which holds a reference to x
   boost::python::call<void>(callable, boost::ref(x));
}

在下表中, x 表示实际的参数对象, cv 表示可选的 cv 限定: "const"、"volatile" 或 "const volatile".

参数类型

行为

T cv & T cv

Python 参数以与包装的返回 T 的 C++ 函数的返回值相同的方式创建. 当 T 是类类型时, 这通常意味着 *x 被复制构造到新的 Python 对象中.

T*

如果 x == 0, Python 参数将是 None. 否则, Python 参数以与包装的返回 T 的 C++ 函数的返回值相同的方式创建. 当 T 是类类型时, 这通常意味着 *x 被复制构造到新的 Python 对象中.

boost::reference_wrapper<T>

Python 参数包含指向 x.get() 的指针, 而不是其副本. 注意: 若未能确保没有 Python 代码在 *x.get() 的生命期之外持有对所得对象的引用, 可能导致崩溃!

pointer_wrapper<T>

如果 x.get() == 0, Python 参数将是 None. 否则, Python 参数包含指向 *x.get() 的指针, 而不是其副本. 注意: 若未能确保没有 Python 代码在 *x.get() 的生命期之外持有对所得对象的引用, 可能导致崩溃!

结果处理

一般而言, call<ResultType>() 和 call_method<ResultType>() 通过利用为 ResultType 注册的所有左值与右值 from_python 转换器并返回结果的副本来返回 ResultType. 然而, 当 ResultType 是指针或引用类型时, Boost.Python 只搜索左值转换器. 为防止悬空指针和引用, 如果 Python 结果对象的引用计数只有 1, 将抛出异常.

设计理由

一般而言, 要得到与 a1...aN 对应的 Python 参数, 必须为每一个创建新的 Python 对象; 是应当把 C++ 对象复制到那个 Python 对象中, 还是让 Python 对象仅仅持有一个指向 C++ 对象的引用/指针? 总的说来, 后一种做法不安全, 因为被调用的函数可能在某处存储对 Python 对象的引用. 如果在 C++ 对象销毁之后使用该 Python 对象, 我们会让 Python 崩溃.

本着 Python 侧用户不必担心使解释器崩溃的理念, 默认行为是复制 C++ 对象, 只有当用户写 boost::ref(a1) 而不是直接写 a1 时才允许不复制行为. 至少这样, 用户不会 "意外" 得到危险行为. 还值得注意, 不复制 ("按引用") 行为一般只对类类型可用, 否则使用时会在运行期以 Python 异常失败[1].

然而, 指针类型带来一个问题: 一种做法是当任何 aN 具有指针类型时拒绝编译: 毕竟, 用户总是可以传 *aN 来 "按值" 传递, 或传 ref(*aN) 来表示按引用传递的行为. 然而, 这给预期的空指针到 None 的转换制造了麻烦: 对空指针值解引用是非法的.

我最终采取的折中方案是:

  1. 默认行为是按值传递. 如果传入非空指针, 所指对象会被复制到新的 Python 对象中; 否则相应的 Python 参数将是 None.
  2. 如果你想要按引用行为, 当 aN 是指针时使用 ptr(aN), 否则使用 ref(aN). 如果传给 ptr(aN) 的是空指针, 相应的 Python 参数将是 None.

至于结果, 我们有类似的问题: 如果允许 ResultType 是指针或引用类型, 它所指对象的生存期很可能正由某个 Python 对象管理. 当那个 Python 对象销毁时, 我们的指针就悬空了. 当 ResultType 是 char const* 时问题尤为严重——相应的 Python 字符串对象通常是唯一引用的, 这意味着 call<char const*>(...) 一返回指针就悬空.

旧的 Boost.Python v1 处理这个问题的办法是拒绝编译任何 call<char const*>() 的使用, 但这既走得太远又走得不够远. 说它走得太远, 是因为存在拥有它的 Python 字符串对象在调用之后仍然存活的情形 (举例来说, 当它是某个 Python 类的名字时); 说它走得不够远, 是因为对返回的任何其他类型的指针或引用, 我们同样可能有这个问题.

在 Boost.Python 中, 这个问题通过以下方式处理:

  1. 解除对 char const * 回调返回的编译期限制
  2. 检测结果 Python 对象引用计数为 1 的情形, 并在 call<U>(...) 内部抛出异常——当 U 是指针或引用类型时.

这应当是可以接受的安全, 因为用户必须为 U 在 call<U> 中显式指定指针/引用, 并且在运行期他们会受到悬空保护, 至少足以撑过 call<U>(...) 的调用.
