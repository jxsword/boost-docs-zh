Complex - 完全集成

到目前为止, 我们一直在绕开 std::complex<> 不是原生 Boost.Fusion 序列这一事实. 我们一直无法像使用 fusion::tuple<> 或类似的 Boost.Fusion 数据结构那样简单自然地使用它. 幸运的是, 从 Boost V1.43 开始, 可以把任何数据结构 (不仅是以前那样只有公开可访问成员的结构)适配为 Boost.Fusion 序列. 我们要做的只是使用新的 BOOST_FUSION_ADAPT_ADT 宏之一.

把类适配为 Fusion 序列

让我们再次从代码开始, 随后给出解释.

如果我们能把 std::complex<> 的实例直接传递给 Karma 的 generate() 函数, 岂不是最优?

template <typename OutputIterator>
bool generate_complex(OutputIterator sink, std::complex<double> const& c)
{
    using boost::spirit::karma::double_;
    using boost::spirit::karma::bool_;
    using boost::spirit::karma::true_;
    using boost::spirit::karma::omit;
    using boost::spirit::karma::generate;

    return generate(sink,

        //  Begin grammar
        (
           &true_ << '(' << double_ << ", " << double_ << ')'
        |   omit[bool_]  << double_ << omit[double_]
        ),
        //  End grammar

        c     //  Data to output
    );
}

确实, 这是可能的! 要使其工作, 我们只需提供一句魔法咒语 (在全局命名空间的某处):

// We can leave off the setters as Karma does not need them.
BOOST_FUSION_ADAPT_ADT(
    std::complex<double>,
    (bool, bool, obj.imag() != 0, /**/)
    (double, double, obj.real(), /**/)
    (double, double, obj.imag(), /**/)
)

格式化文法本身的大部分内容与上一节相比没有变化. 我们仍使用非常类似的方案. 我们有一个备选, 为我们的两个用例提供格式化规则: 一个用于完整复数格式, 一个用于虚部为零的复数. 但与在文法中通过比较虚部与零来选择所需的备选不同, 我们假定接收一个携带此信息的布尔属性:

&true_ << "(" << double_ << ", " << double_ << ")"

这读作: '如果所提供 fusion 序列的第一个 (布尔)元素为 true, 则按指定的方式进行, 否则选择下一个备选'. 下一个备选现在也考虑了布尔元素, 但其他方面与上一节的示例 (几乎)相同.

现在应当清楚了, 为什么上面我们的适配构造暴露一个三元素 Boost.Fusion 序列: 一个布尔值和两个 double 值 (复数的实部和虚部). 我们希望它匹配格式化文法的要求, 后者期望的正是这些值. BOOST_FUSION_ADAPT_ADT 宏允许我们指定任意的访问器构造, 不必仅限于调用对象实例的成员函数 (在此宏的上下文中由 obj 表示). 这使我们能够把决策逻辑漂亮地封装到类适配中.

这是最后一条新信息. 如果仔细观察, 你会发现第二个备选比第一个"更短". 它只消耗所提供 fusion 序列的两个元素: 它忽略布尔值, 并使用复数的实部来生成其输出. 如果我们的属性中的元素多于所需, 现在可以安全地从文法中省略它们 (这也是 V1.43 中加入 Spirit 的新"特性"). 注意, 我们本可以把备选写成

&false_ << double_

但这样效率会略低, 因为我们需要再次比较布尔值, 而所提供的最终方案只会忽略它.
