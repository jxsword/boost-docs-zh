快速上手 3 - 使用解析器统计单词

把 Spirit.Lex 集成为 Spirit 库一部分的全部目的, 就是增加一个允许把词法分析与 Spirit 文法定义的解析过程合并起来的库. Spirit 解析器从由迭代器访问的输入序列读取其输入. 因此自然而然地, 我们选择迭代器作为词法分析器与解析器之间的接口. 词法分析器/解析器集成的第二个目标是能够使用不同的词法分析器库. 从这个角度看, 使用迭代器似乎也是正确的选择, 主要因为它们可以用作抽象层, 隐藏所用词法分析器库的实现细节. 下面的 插图 展示了解析与词法分析相结合时实现的常见流程控制.

图 7. 解析与词法分析相结合时实现的常见流程控制


与词法分析器和解析器集成相关的另一个问题, 是找到一种方法, 使定义的记号在语法上能够与 Spirit 的文法定义语法相融合. 对于定义为 token_def<> 类实例的记号, 最自然的集成方式是允许把它们直接用作解析器组件. 在语义上, 只要词法分析器匹配到相应的记号类型, 这些解析器组件就成功匹配其输入. 本快速上手示例将再次通过统计单词来演示这一点 (以及更多内容), 做法只是把解析器语义动作内部的数字累加起来 (完整示例代码见此处: word_count.cpp).

前置条件

本示例使用了 Spirit 库的两个组件: Spirit.Lex 和 Spirit.Qi, 因此我们必须 #include 相应的头文件. 同样, 我们还需要包含 Boost.Phoenix 库中的几个头文件. 该示例展示了如何把仿函数附加到解析器组件上; 这可以通过任何产生可调用对象的 C++ 技术来完成. 使用 Boost.Phoenix 完成此任务可以简化工作, 并避免向其他库添加依赖 (反正 Spirit 已经在使用 Boost.Phoenix).

#include <boost/spirit/include/qi.hpp>
#include <boost/spirit/include/lex_lexertl.hpp>
#include <boost/phoenix/operator.hpp>
#include <boost/phoenix/statement.hpp>
#include <boost/phoenix/stl/container.hpp>

为了让下面的代码更易读, 我们引入以下命名空间.

using namespace boost::spirit;
using namespace boost::spirit::ascii;

定义记号

与前两个快速上手示例 (Lex 快速上手 1 - 单词计数器: 使用 Spirit.Lex 和 Lex 快速上手 2 - 更佳单词计数器: 使用 Spirit.Lex) 相比, 本示例的记号定义类没有任何意外之处. 不过, 它使用了词法分析器记号定义宏来简化正则表达式的组合, 这将在 FIXME 一节中更详细地描述. 一般而言, 任何记号定义都无需修改即可用于独立的词法分析器, 或者与解析器配合使用.

template <typename Lexer>
struct word_count_tokens : lex::lexer<Lexer>
{
    word_count_tokens()
    {
        // define patterns (lexer macros) to be used during token definition 
        // below
        this->self.add_pattern
            ("WORD", "[^ \t\n]+")
        ;

        // define tokens and associate them with the lexer
        word = "{WORD}";    // reference the pattern 'WORD' as defined above

        // this lexer will recognize 3 token types: words, newlines, and 
        // everything else
        this->self.add
            (word)          // no token id is needed here
            ('\n')          // characters are usable as tokens as well
            (".", IDANY)    // string literals will not be escaped by the library
        ;
    }

    // the token 'word' exposes the matched string as its parser attribute
    lex::token_def<std::string> word;
};

把记号定义实例用作解析器

虽然词法分析器与解析器在控制流中的集成是通过使用包装词法分析器的特殊迭代器实现的, 我们仍然需要一种方式在文法中表达匹配什么记号以及在何处匹配. 上面的记号定义类使用了三种不同的记号定义方式:

  • 使用 token_def<> 的实例, 每当你需要指定记号属性时它都很方便 (有关词法分析器相关属性的更多信息请参见此处: Lexer Attributes).
  • 使用单个字符作为记号; 此时该字符自身就表示一个记号, 记号 id 即该字符的 ASCII 值.
  • 使用以字符串表示的正则表达式; 此时需要显式指定记号 id, 以便从文法层级访问该记号.

这三种记号定义方法都需要不同的文法集成方式. 但正如你从下面的代码片段中所看到的, 每种方法都很直接, 能把相应的记号实例自然地融入周围的 Spirit.Qi 文法语法.

记号定义

解析器集成

token_def<>

token_def<> 实例可直接用作解析器组件. 如果用于定义它的正则表达式被成功匹配, 对该组件的解析就会成功.

单个字符

单个字符可在文法中直接使用. 但在某些情况下, 它需要被 char_() 解析器组件包装. 如果该单个字符被匹配, 对此组件的解析就会成功.

显式记号 id

要在 Spirit.Qi 文法中使用显式记号 id, 必须用特殊的 token() 解析器组件包装它. 如果当前记号具有与表达式 token(<id>) 中指定的记号 id 相同的记号 id, 对此组件的解析就会成功.

下面的文法定义使用了全部三种类型, 以演示它们的用法.

template <typename Iterator>
struct word_count_grammar : qi::grammar<Iterator>
{
    template <typename TokenDef>
    word_count_grammar(TokenDef const& tok)
      : word_count_grammar::base_type(start)
      , c(0), w(0), l(0)
    {
        using boost::phoenix::ref;
        using boost::phoenix::size;

        start =  *(   tok.word          [++ref(w), ref(c) += size(_1)]
                  |   lit('\n')         [++ref(c), ++ref(l)]
                  |   qi::token(IDANY)  [++ref(c)]
                  )
              ;
    }

    std::size_t c, w, l;
    qi::rule<Iterator> start;
};

如前所述 (参见: Attributes), Spirit.Qi 解析器库构建在一组完全属性化的解析器组件之上. 因此, 所有记号定义也都支持这种属性模型. 实现这一点的最自然方式, 是把记号值用作与该记号定义对应的解析器组件所暴露的属性 (关于此主题的更多信息可在此处阅读: About Tokens and Token Values). 上面的示例充分利用了记号值作为 token_def<> 解析器属性的完整集成: 记号定义 word 被声明为 token_def<std::string>, 使 word 记号的每个实例都携带被匹配输入序列的字符串表示作为其值. 附加到 tok.word 的语义动作接收此字符串 (由 _1 占位符表示), 并用它来计算被匹配的字符数: ref(c) += size(_1).

整合所有内容

主函数现在需要实现稍多一些的逻辑, 因为我们不仅要初始化和启动词法分析, 还要初始化和启动解析过程. 三个类型定义 (typedef 语句) 简化了词法分析器和文法的创建. 在把给定文件的内容读入内存后, 它调用函数 tokenize_and_parse() 来初始化词法分析和解析过程.

int main(int argc, char* argv[])
{
  typedef lex::lexertl::token<
        char const*, boost::mpl::vector<std::string>
    > token_type;

  typedef lex::lexertl::lexer<token_type> lexer_type;

  typedef word_count_tokens<lexer_type>::iterator_type iterator_type;

    // now we use the types defined above to create the lexer and grammar
    // object instances needed to invoke the parsing process
    word_count_tokens<lexer_type> word_count;          // Our lexer
    word_count_grammar<iterator_type> g (word_count);  // Our parser 

    // read in the file int memory
    std::string str (read_from_file(1 == argc ? "word_count.input" : argv[1]));
    char const* first = str.c_str();
    char const* last = &first[str.size()];

  bool r = lex::tokenize_and_parse(first, last, word_count, g);

    if (r) {
        std::cout << "lines: " << g.l << ", words: " << g.w
                  << ", characters: " << g.c << "\n";
    }
    else {
        std::string rest(first, last);
        std::cerr << "Parsing failed\n" << "stopped at: \""
                  << rest << "\"\n";
    }
    return 0;
}
