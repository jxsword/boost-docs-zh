多遍 (multi_pass) 迭代器

Spirit.Qi 中的回溯要求使用以下类型的迭代器: 前向、双向或随机访问. 由于回溯, 不能使用输入迭代器. 因此, 属于输入迭代器类别的标准库类 std::istreambuf_iterator 和 std::istream_iterator 无法使用. 另一个值得关注的输入迭代器是包装词法分析器 (如 LEX) 的迭代器.

注释

一般来说, Spirit.Qi 生成的递归下降解析器在设计上需要回溯. 因此, 我们需要向 Spirit.Qi 的任何 API 函数至少提供前向迭代器. 不过这不是绝对要求. 将来我们会看到更多只需要至多 1 个字符 (记号) 前瞻的确定性解析器. 这类解析器允许我们按原样使用 std::istream_iterator 这样的输入迭代器.

只有当我们被允许保存迭代器位置 (即复制当前迭代器) 时, 才能实现回溯. 遗憾的是, 对于输入迭代器, 无法这样做, 因此输入迭代器无法在 Spirit.Qi 中配合回溯使用. 此问题的一种解决方案是把所有待解析数据简单地加载到一个容器 (例如 vector 或 deque) 中, 然后把容器的 begin 和 end 传给 Spirit.Qi. 这种方法对某些应用来说内存开销过大, 这就是创建 multi_pass 迭代器的原因.

使用 multi_pass

multi_pass 迭代器会把任何输入迭代器转换为适合与 Spirit.Qi 一起使用的前向迭代器. multi_pass 会在需要时缓冲数据, 并在其内容不再需要时丢弃缓冲区. 这发生在只有一个迭代器副本或不可能发生回溯的情况下.

如果使用 multi_pass 迭代器, 文法必须谨慎设计. 任何可能需要回溯的 rule (例如含有备选项的 rule) 都会导致数据被缓冲. 最适宜使用的 rule 是重复构造 (如 kleene 和 plus).

形如 a >> b 的序列也会缓冲数据. 这与 Spirit.Classic 的行为不同, 但有充分理由. 如果序列的某个组件匹配失败, 序列需要把当前迭代器重置到其初始状态. 为了补偿这种行为, 我们为 expect 解析器增加了功能 (即 a > b 这样的构造). 期望点在文法中引入确定性点, 确保它们匹配时不会发生回溯. 因此, 我们在每个期望点清空所有 multi_pass 迭代器的缓冲区, 即使对于大型文法也能保证最小的缓冲内容.

重要

如果你在 expect 解析器中配合使用错误处理器, 同时使用 multi_pass 迭代器, 并且打算用错误处理器强制 retry 或 fail (参见错误处理器的说明 -- FIXME: 插入链接), 那么你需要使用 retry 或 fail 来实例化错误处理器, 例如:

rule r<iterator_type> r;
on_error<retry>(r, std::cout << phoenix::val("Error!"));

如果不这样做, 生成的代码将在运行时触发断言语句.

任何重复的 rule, 例如 kleene_star (*a) 或正闭包 (+a), 只会为当前重复缓冲数据.

在典型文法中, 歧义以及因此产生的前瞻通常是局部的. 实际上, 许多设计良好的语言是完全确定性的, 完全不需要前瞻. 查看输入的第一个字符即可立即确定要走的备选分支. 而且, 即使是高度歧义的文法, 备选项也常常形如 *(a | b | c | d). 输入迭代器不断前进, 从不会卡在开头. 让我们看一个 Pascal 代码片段:

program =
        programHeading >> block >> '.'
    ;

block =
       *(   labelDeclarationPart
        |   constantDefinitionPart
        |   typeDefinitionPart
        |   variableDeclarationPart
        |   procedureAndFunctionDeclarationPart
        )
    >>  statementPart
    ;

注意 rule block 中 Kleene 星号内部的备选项. 该 rule 以线性方式吞掉输入, 并在每次迭代时丢弃过去的历史. 由于这是完全确定性的 LL(1) 文法, 每个失败的备选项只需查看 1 个字符 (记号). 消耗超过 1 个字符 (记号) 的备选项肯定是成功者. 之后, Kleene 星号继续下一个.

在听完使用 multi_pass 时需要小心的特性讲解之后, 你可能觉得 multi_pass 用起来限制太多. 事实并非如此. 如果你的文法是确定性的, 你可以在文法中使用 flush_multi_pass 伪解析器来确保数据不会在不必要的时候被缓冲 (flush_multi_pass 可从 Spirit.Qi 解析器 仓库 获得).

这里我们给出一个展示最小用例的极简示例. multi_pass 迭代器是高度可配置的, 但默认策略经过选择, 使其能轻松与 std::istreambuf_iterator 这样的输入迭代器一起使用. 此示例的完整源代码请参见 multi_pass.cpp.

int main()
{
    namespace spirit = boost::spirit;
    using spirit::ascii::space;
    using spirit::ascii::char_;
    using spirit::qi::double_;
    using spirit::qi::eol;

    std::ifstream in("multi_pass.txt");    // we get our input from this file
    if (!in.is_open()) {
        std::cout << "Could not open input file: 'multi_pass.txt'" << std::endl;
        return -1;
    }

    typedef std::istreambuf_iterator<char> base_iterator_type;
    spirit::multi_pass<base_iterator_type> first =
        spirit::make_default_multi_pass(base_iterator_type(in));

    std::vector<double> v;
    bool result = spirit::qi::phrase_parse(first
      , spirit::make_default_multi_pass(base_iterator_type())
      , double_ >> *(',' >> double_)              // recognize list of doubles
      , space | '#' >> *(char_ - eol) >> eol      // comment skipper
      , v);                                       // data read from file

    if (!result) {
        std::cout << "Failed parsing input file!" << std::endl;
        return -2;
    }

    std::cout << "Successfully parsed input file!" << std::endl;
    return 0;
}

使用 flush_multi_pass 解析器

Spirit 仓库 包含 flush_multi_pass 解析器组件. 它可以与 multi_pass 迭代器配合使用以最小化缓冲. 它允许在文法中插入显式同步点, 在这些点清除任何已存储的输入是安全的, 因为可以确保此时不会再发生回溯.

当 flush_multi_pass 解析器与 multi_pass 一起使用时, 它会调用 multi_pass::clear_queue(). 这会导致所有缓冲数据被擦除. 这也将使 multi_pass 的所有其他副本失效, 它们不应再被使用. 如果使用, 将抛出 boost::illegal_backtracking 异常.

multi_pass 策略

multi_pass 迭代器是一个可使用策略配置的模板类. 上面关于 multi_pass 的描述是它最初 (在使用策略之前) 的实现方式, 也是现在的默认配置. 但 multi_pass 能做的远不止这些. 由于策略的开放性, 你可以编写自己的策略, 使 multi_pass 以我们从未想象过的方式工作.

multi_pass 类有两个模板参数:

multi_pass 模板参数

Input

multi_pass 获取其输入所用的类型. 这通常是一个输入迭代器或仿函数.

Policies

用于创建 multi_pass 迭代器实例的组合策略. 这个组合策略类型在下文描述

可以在单个类中实现组合策略所需的全部功能. 但实践表明, 把它拆分为四组不同的函数, 即四个独立但协调良好的策略, 会更方便. 因此, multi_pass 库实现了一个模板 iterator_policies::default_policy, 允许组合多个不同策略, 每个策略实现其中一个功能组:

表 12. default_policy 模板所需的策略

模板参数

说明

OwnershipPolicy

该策略决定 multi_pass 如何处理其共享组件.

CheckingPolicy

该策略决定如何检查无效迭代器.

InputPolicy

定义 multi_pass 如何获取其输入的类. InputPolicy 由 Input (multi_pass 的模板参数) 进行参数化.

StoragePolicy

multi_pass 使用的缓冲方案由 StoragePolicy 决定和管理.

multi_pass 库为上述每种策略类型包含若干预定义策略实现. 我们先描述这些预定义类型, 然后给出一些如何编写自己的策略实现的指导.

预定义策略

所有预定义的 multi_pass 策略都定义在命名空间 boost::spirit::iterator_policies 中.

表 13. 预定义策略类

类名

说明

InputPolicy 类

  

input_iterator

该策略指示 multi_pass 从类型为 Input 的输入迭代器读取.

buffering_input_iterator

该策略指示 multi_pass 从类型为 Input 的输入迭代器读取. 另外它会缓冲从底层迭代器接收的最后一个字符. 这允许包装那些自身不缓冲最后一个字符的迭代器 (例如 std::istreambuf_iterator).

istream

该策略指示 multi_pass 从类型为 Input 的输入流读取 (通常是 std::basic_istream).

lex_input

该策略通过调用 yylex() 获取输入, 该函数通常由 Flex 生成的扫描器提供. 如果你使用此策略, 你的代码必须链接一个 Flex 生成的扫描器.

functor_input

该输入策略通过调用类型为 Input 的仿函数获取数据. 该仿函数必须满足特定要求. 它必须有一个名为 result_type 的 typedef, 应当是 operator() 返回的类型. 另外, 由于输入策略需要一种确定输入何时结束的方法, 仿函数必须包含一个名为 eof 的静态变量, 它可与 result_type 类型的变量比较.

split_functor_input

这与 functor_input 策略基本相同, 只是 (用户提供的) 函数对象暴露独立的 unique 和 shared 子类, 允许把仿函数的 unique 数据成员与每个实例持有的 multi_pass 数据项集成, 其 shared 数据成员将与所有副本共享的 multi_pass 成员集成.

OwnershipPolicy 类

  

ref_counted

该类使用引用计数方案. 当计数到达零时, multi_pass 会删除其共享组件.

first_owner

使用该策略时, 创建的第一个 multi_pass 将是删除共享数据的那个. 每个副本不获取共享数据的所有权. 这对 Spirit 很有效, 因为不对迭代器做动态分配. 所有副本都在栈上创建, 因此原始迭代器寿命最长.

CheckingPolicy 类

  

no_check

该策略完全不进行检查.

buf_id_check

该策略保存一个缓冲区 id 或缓冲区寿命 (age). 每当在 clear_queue() 迭代器上调用 multi_pass 时, 所有其他迭代器都可能失效. 当调用 clear_queue() 时, buf_id_check 会递增缓冲区 id. 当迭代器被解引用时, 该策略检查该迭代器的缓冲区 id 是否与共享缓冲区 id 匹配. 该策略与 split_std_deque StoragePolicy 一起使用时最有效. 它不应与 fixed_size_queue StoragePolicy 一起使用, 因为它无法检测超出范围的迭代器解引用.

full_check

该策略尚未实现. 实现后将跟踪所有迭代器并确保它们都有效. 这主要用于调试目的, 因为它会产生显著开销.

StoragePolicy 类

  

split_std_deque

尽管名字如此, 该策略把所有缓冲数据保存在 std::vector 中. 只要存在多于一个迭代器, 所有数据都会保存. 一旦迭代器数量降到一且不再需要队列, 队列就会被清除以释放内存. 也可以通过调用 multi_pass::clear_queue() 强制清除队列.

fixed_size_queue<N>

该策略维护一个大小为 N+1、保存 N 元素的环形缓冲区. fixed_size_queue 是一个模板, 带有指定队列大小的 std::size_t 参数. 你有责任确保 N 对你的解析器足够大. 每当最前面的迭代器递增时, 缓冲区的最后一个字符会被自动擦除. 目前无法判断某个迭代器是否落后太远而已经失效. 在正常迭代器操作期间, 该策略不做动态分配, 只在初始构造时进行. 这个 StoragePolicy 的内存用量固定为 N+1 字节, 而不像 split_std_deque 那样无上限.

组合: 如何指定你自己的自定义 multi_pass

基于策略的设计之美在于, 你可以通过选择想要的策略来混合搭配, 创建自己的自定义迭代器. 下面是一个如何指定自定义 multi_pass 的示例, 它包装 std::istream_iterator<char>, 并且比默认的 multi_pass (由 make_default_multi_pass() API 函数生成) 稍微高效, 因为它使用 iterator_policies::first_owner OwnershipPolicy 和 iterator_policies::no_check CheckingPolicy:

typedef multi_pass<
    std::istream_iterator<char>
  , iterator_policies::default_policy<
        iterator_policies::first_owner
      , iterator_policies::no_check
      , iterator_policies::buffering_input_iterator
      , iterator_policies::split_std_deque
    >
> first_owner_multi_pass_type;

iterator_policies::default_policy 的默认模板参数为:

  • iterator_policies::ref_counted OwnershipPolicy
  • iterator_policies::no_check CheckingPolicy; 如果定义了 BOOST_SPIRIT_DEBUG, 则为 iterator_policies::buf_id_check CheckingPolicy
  • iterator_policies::buffering_input_iterator InputPolicy, 以及
  • iterator_policies::split_std_deque StoragePolicy.

所以如果你使用 multi_pass<std::istream_iterator<char> >, 在包装 std::istream_iterator<char> 的同时, 你将获得这些预定义行为.

处理恒定前瞻

还有一个预定义类, 名为 look_ahead. 类 look_ahead 是另一个预定义的 multi_pass 迭代器类型. 它有两个模板参数: Input (要包装的输入迭代器的类型) 和 std::size_t N, 后者为 fixed_size_queue 策略指定缓冲区大小. 默认 multi_pass 配置为安全而设计, 而 look_ahead 为速度而设计. look_ahead 派生自已配置如下策略的 multi_pass: input_iterator InputPolicy、first_owner OwnershipPolicy、no_check CheckingPolicy 和 fixed_size_queue<N> StoragePolicy.

该迭代器通过包含以下文件定义:

// forwards to <boost/spirit/home/support/look_ahead.hpp>
#include <boost/spirit/include/support_look_ahead.hpp>

另请参见 包含结构.

从标准输入流读取

另一个用于包装标准输入流 (通常是 std::basic_istream<>) 的预定义迭代器称为 basic_istream_iterator<Char, Traits>. 该类可用作 std::istream_iterator<Char, Traits> 的直接替代品. 其唯一区别是它是前向迭代器 (而 std::istream_iterator 是输入迭代器). basic_istream_iterator 派生自已配置如下策略的 multi_pass: istream InputPolicy、ref_counted OwnershipPolicy、no_check CheckingPolicy 和 split_std_deque StoragePolicy.

还有一个附加的预定义 typedef:

typedef basic_istream_iterator<char, std::char_traits<char> > istream_iterator;

该迭代器通过包含以下文件定义:

// forwards to <boost/spirit/home/support/istream_iterator.hpp>
#include <boost/spirit/include/support_istream_iterator.hpp>

另请参见 包含结构.

如何为 functor_input InputPolicy 编写仿函数

如果你想使用 functor_input InputPolicy, 可以编写自己的函数对象来为 multi_pass 提供输入. 函数对象必须满足若干要求. 它必须有一个 typedef result_type, 指定其 operator() 的返回类型. 这是 STL 的标准做法. 另外, 它必须提供一个名为 eof 的静态变量, 通过与之比较来判断输入是否已到末尾. 最后同样重要的是, 函数对象必须可默认构造. 下面是一个示例:

#include <iostream>
#include <boost/spirit/home/qi.hpp>
#include <boost/spirit/home/support.hpp>
#include <boost/spirit/home/support/multi_pass.hpp>
#include <boost/spirit/home/support/iterators/detail/functor_input_policy.hpp>

// define the function object
class iterate_a2m
{
public:
    typedef char result_type;

    iterate_a2m() : c_('A') {}
    iterate_a2m(char c) : c_(c) {}

    result_type operator()()
    {
        if (c_ == 'M')
            return eof;
        return c_++;
    }

    static result_type eof;

private:
    char c_;
};

iterate_a2m::result_type iterate_a2m::eof = iterate_a2m::result_type('M');

using namespace boost::spirit;

// create two iterators using the define function object, one of which is 
// an end iterator
typedef multi_pass<iterate_a2m
  , iterator_policies::first_owner
  , iterator_policies::no_check
  , iterator_policies::functor_input
  , iterator_policies::split_std_deque>
functor_multi_pass_type;

int main()
{
    functor_multi_pass_type first = functor_multi_pass_type(iterate_a2m());
    functor_multi_pass_type last;

    // use the iterators: this will print "ABCDEFGHIJKL"
    while (first != last) {
        std::cout << *first;
        ++first;
    }
    std::cout << std::endl;
    return 0;
}
如何编写与 multi_pass 配合使用的策略

所有与 default_policy 模板配合使用的策略都需要有两个内嵌类: unique 和 shared. unique 类需要实现特定策略类型所需的全部函数. 此外, 它可以保存 唯一 于特定 multi_pass 实例的所有成员数据项 (名称由此而来). shared 类不暴露任何成员函数 (有时构造函数除外), 但它可以保存要 共享 于特定 multi_pass 的所有副本之间的成员数据项.

InputPolicy

InputPolicy 必须具有以下接口:

struct input_policy
{
    // Input is the same type used as the first template parameter
    // while instantiating the multi_pass
    template <typename Input>
    struct unique
    {
        // these typedef's will be exposed as the multi_pass iterator
        // properties
        typedef __unspecified_type__ value_type;
        typedef __unspecified_type__ difference_type;
        typedef __unspecified_type__ distance_type;
        typedef __unspecified_type__ pointer;
        typedef __unspecified_type__ reference;

        unique() {}
        explicit unique(Input) {}

        // destroy is called whenever the last copy of a multi_pass is
        // destructed (ownership_policy::release() returned true)
        //
        //   mp:    is a reference to the whole multi_pass instance
        template <typename MultiPass>
        static void destroy(MultiPass& mp);

        // swap is called by multi_pass::swap()
        void swap(unique&);

        // get_input is called whenever the next input character/token
        // should be fetched. 
        //
        //   mp:    is a reference to the whole multi_pass instance
        //
        // This method is expected to return a reference to the next 
        // character/token
        template <typename MultiPass>
        static typename MultiPass::reference get_input(MultiPass& mp);

        // advance_input is called whenever the underlying input stream 
        // should be advanced so that the next call to get_input will be 
        // able to return the next input character/token
        //
        //   mp:    is a reference to the whole multi_pass instance
        template <typename MultiPass>
        static void advance_input(MultiPass& mp);

        // input_at_eof is called to test whether this instance is a 
        // end of input iterator.
        //
        //   mp:    is a reference to the whole multi_pass instance
        //
        // This method is expected to return true if the end of input is 
        // reached. It is often used in the implementation of the function
        // storage_policy::is_eof.
        template <typename MultiPass>
        static bool input_at_eof(MultiPass const& mp);

        // input_is_valid is called to verify if the parameter t represents 
        // a valid input character/token
        //
        //   mp:    is a reference to the whole multi_pass instance
        //   t:     is the character/token to test for validity
        // 
        // This method is expected to return true if the parameter t 
        // represents a valid character/token.
        template <typename MultiPass>
        static bool input_is_valid(MultiPass const& mp, value_type const& t);
    };

    // Input is the same type used as the first template parameter passed
    // while instantiating the multi_pass
    template <typename Input>
    struct shared
    {
        explicit shared(Input) {}
    };
};

可以派生出 struct unique, 其基类型为 boost::spirit::detail::default_input_policy. 该类型为部分所需函数实现了一个最小充分接口, 简化了编写新输入策略的任务.

该类可以实现一个函数 destroy(), 它在 multi_pass 的最后一个副本销毁期间被调用. 该函数应当用于释放策略在其 shared 部分构造期间可能分配的任何共享数据项. 由于 multi_pass 的实现方式, shared 中任何已分配的数据成员不应在 shared 的拷贝构造函数中被深拷贝.

OwnershipPolicy

OwnershipPolicy 必须具有以下接口:

struct ownership_policy
{
    struct unique
    {
        // destroy is called whenever the last copy of a multi_pass is
        // destructed (ownership_policy::release() returned true)
        //
        //   mp:    is a reference to the whole multi_pass instance
        template <typename MultiPass>
        static void destroy(MultiPass& mp);

        // swap is called by multi_pass::swap()
        void swap(unique&);

        // clone is called whenever a multi_pass is copied
        //
        //   mp:    is a reference to the whole multi_pass instance
        template <typename MultiPass>
        static void clone(MultiPass& mp);

        // release is called whenever a multi_pass is destroyed
        //
        //   mp:    is a reference to the whole multi_pass instance
        //
        // The method is expected to return true if the destructed 
        // instance is the last copy of a particular multi_pass. 
        template <typename MultiPass>
        static bool release(MultiPass& mp);

        // is_unique is called to test whether this instance is the only 
        // existing copy of a particular multi_pass
        //
        //   mp:    is a reference to the whole multi_pass instance
        //
        // The method is expected to return true if this instance is unique
        // (no other copies of this multi_pass exist).
        template <typename MultiPass>
        static bool is_unique(MultiPass const& mp);
    };

    struct shared {};
};

可以派生出 struct unique, 其基类型为 boost::spirit::detail::default_ownership_policy. 该类型为部分所需函数实现了一个最小充分接口, 简化了编写新所有权策略的任务.

该类可以实现一个函数 destroy(), 它在 multi_pass 的最后一个副本销毁期间被调用. 该函数应当用于释放策略在其 shared 部分构造期间可能分配的任何共享数据项. 由于 multi_pass 的实现方式, shared 中任何已分配的数据成员不应在 shared 的拷贝构造函数中被深拷贝.

struct checking_policy
{
    struct unique
    {

        //   mp:    is a reference to the whole multi_pass instance

StoragePolicy

StoragePolicy 必须具有以下接口:

struct storage_policy
{
    // Value is the same type as typename MultiPass::value_type
    template <typename Value>
    struct unique
    {
        // destroy is called whenever the last copy of a multi_pass is
        // destructed (ownership_policy::release() returned true)
        //
        //   mp:    is a reference to the whole multi_pass instance
        template <typename MultiPass>
        static void destroy(MultiPass& mp);

        // swap is called by multi_pass::swap()
        void swap(unique&);

        // dereference is called whenever multi_pass::operator*() is invoked
        //
        //   mp:    is a reference to the whole multi_pass instance
        //
        // This function is expected to return a reference to the current
        // character/token.
        template <typename MultiPass>
        static typename MultiPass::reference dereference(MultiPass const& mp);

        // increment is called whenever multi_pass::operator++ is invoked
        //
        //   mp:    is a reference to the whole multi_pass instance
        template <typename MultiPass>
        static void increment(MultiPass& mp);

        //
        //   mp:    is a reference to the whole multi_pass instance
        template <typename MultiPass>
        static void clear_queue(MultiPass& mp);

        // is_eof is called to test whether this instance is a end of input 
        // iterator.
        //
        //   mp:    is a reference to the whole multi_pass instance
        //
        // This method is expected to return true if the end of input is 
        // reached. 
        template <typename MultiPass>
        static bool is_eof(MultiPass const& mp);

        // less_than is called whenever multi_pass::operator==() is invoked
        //
        //   mp:    is a reference to the whole multi_pass instance
        //   rhs:   is the multi_pass reference this instance is compared 
        //          to
        //
        // This function is expected to return true if the current instance
        // is equal to the right hand side multi_pass instance
        template <typename MultiPass>
        static bool equal_to(MultiPass const& mp, MultiPass const& rhs);

        // less_than is called whenever multi_pass::operator<() is invoked
        //
        //   mp:    is a reference to the whole multi_pass instance
        //   rhs:   is the multi_pass reference this instance is compared 
        //          to
        //
        // This function is expected to return true if the current instance
        // is less than the right hand side multi_pass instance
        template <typename MultiPass>
        static bool less_than(MultiPass const& mp, MultiPass const& rhs);
    };

    // Value is the same type as typename MultiPass::value_type
    template <typename Value>
    struct shared {};
};

可以派生出 struct unique, 其基类型为 boost::spirit::detail::default_storage_policy. 该类型为部分所需函数实现了一个最小充分接口, 简化了编写新存储策略的任务.

该类可以实现一个函数 destroy(), 它在 multi_pass 的最后一个副本销毁期间被调用. 该函数应当用于释放策略在其 shared 部分构造期间可能分配的任何共享数据项. 由于 multi_pass 的实现方式, shared 中任何已分配的数据成员不应在 shared 的拷贝构造函数中被深拷贝.

一般来说, StoragePolicy 是最难实现的策略. 在尝试编写自己的实现之前, 你应当研究并理解现有的 StoragePolicy 类.
