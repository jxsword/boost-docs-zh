Spirit 常见问题(FAQ)

使用 Visual C++ 时出现多个符号定义错误, 我能做些什么?

你是否看到了奇怪的多个符号定义链接器错误, 其中提到 boost::mpl::failed 和 boost::spirit::qi::rule? 那么这条 FAQ 可能正是为你准备的.

Boost.Mpl 实现了宏 BOOST_MPL_ASSERT_MSG(), 它本质上是一个更强大的 static_assert 版本. 遗憾的是, 在某些情况下使用这个宏可能导致上述链接器错误.

Spirit 允许你定义一个预处理器常量来禁用 BOOST_MPL_ASSERT_MSG() 的使用, 改用 BOOST_STATIC_ASSERT(). 为此你需要定义 BOOST_SPIRIT_DONT_USE_MPL_ASSERT_MSG=1. 方法是添加

-DBOOST_SPIRIT_DONT_USE_MPL_ASSERT_MSG=1

到编译器命令行, 或者插入一个

#define BOOST_SPIRIT_DONT_USE_MPL_ASSERT_MSG 1

到你的代码中, 位于包含任何 Spirit 头文件之前.

使用这个技巧对 Spirit 的任何功能都没有不利影响. 使用这一变通方法时, 你可能看到的唯一变化是 static_assert 生成的错误消息不再那么冗长.

我对 boost/spirit 目录中的头文件地狱感到非常困惑, 这是怎么回事?

boost/spirit 目录目前保存着 Spirit 库的两个版本: Spirit.Classic (即以前的 V1.8.x)和 SpiritV2. 两者完全独立, 通常不会同时使用. 不要在同一个 grammar 中混用这两者.

Spirit.Classic 经过多年演化, 形成了相当复杂的目录结构:

boost/spirit/actor
boost/spirit/attribute
boost/spirit/core
boost/spirit/debug
boost/spirit/dynamic
boost/spirit/error_handling
boost/spirit/iterator
boost/spirit/meta
boost/spirit/symbols
boost/spirit/tree
boost/spirit/utility

在引入 Spirit V2 时, 我们重构了目录结构, 以便同时容纳两个版本. Spirit.Classic 的全部内容现在位于目录

boost/spirit/home/classic

其中上面的目录包含指向新位置的转发头文件, 以保持应用程序兼容性. 转发头文件会发出警告(从 Boost V1.38 开始), 告诉用户修改其包含路径. 请预期上述目录/转发头文件很快会被移除.

这解释了为什么需要目录

boost/spirit/include

它同样包含转发头文件. 但这一次这些头文件不会被移除. 我们鼓励应用程序编写者只使用该目录中包含的头文件. 这样, 如果需要, 我们可以重构其下的目录, 而不必担心应用程序兼容性. 请在你的应用程序中只使用这些文件. 如果发现缺少某个转发文件, 请报告缺陷.

Spirit V2 不再只关于解析(不像 Spirit.Classic). 它现在由 3 个部分(子库)组成: Spirit.Qi, Spirit.Karma 和 Spirit.Lex. 它们的头文件位于

boost/spirit/home/qi
boost/spirit/home/karma
boost/spirit/home/lex

并在以下位置有转发头文件:

boost/spirit/include

Spirit.Qi 是 Spirit.Classic 的直接后继, 它实现了一种 DSEL(领域特定嵌入式语言), 允许使用 C++ 自身的语法编写解析器(这里的解析器指把字节序列转换为内部数据结构). 它与 Spirit.Classic 不兼容, 但主要概念是相似的.

Spirit.Karma 是 Spirit.Qi 的对偶. 它实现了一个类似的 DSEL, 但用于编写生成器(即把内部数据结构转换为字节序列--通常是字符串--的东西). 如果说 Spirit.Qi 是阴, 那么 Spirit.Karma 就是阳, 二者几乎互为镜像.

Spirit.Lex (顾名思义)是一个允许编写词法分析器的库. 它们既可以独立使用, 也可以用作 Spirit.Qi 解析器的前端. 如果你了解 flex, 理解 Spirit.Lex 应当不成问题. 这个库实际上并不实现词法分析器本身, 它只是为既有的词法分析器提供一个接口. 目前它使用 Ben Hanson 出色的 Lexertl 库(顺带一提, 已提议进行 Boost 评审)作为其底层主力.

再次强调, 不要直接使用 boost/spirit/home 目录下的任何头文件, 应当始终包含 boost/spirit/include 目录中的文件.

为什么我的符号表在 no_case 指令中不起作用?

要执行不区分大小写的解析(使用 no_case), 并配合符号表(即把 symbols<> 解析器用在 no_case 指令中), 该符号表需要全部以小写内容填充. 含有一个或多个大写字符的条目将无法匹配任何输入.

我得到一个提到 boost::function 和/或 boost::function4 的编译错误, 这是什么意思?

如果你使用 Visual C++ 并遇到如下错误:

error C2664: 'bool boost::function4<R,T0,T1,T2,T3>::operator ()(T0,T1,T2,T3) const' :
    cannot convert parameter 4 from '...' to '...'

或者你使用 GCC 并遇到如下错误:

error: no match for call to '(const boost::function<bool ()(...)>) (...)'
note: candidates are: ... boost::function4<R,T1,T2,T3,T4>::operator()(T0,T1,T2,T3) const [with ...]

那么这条 FAQ 可能会帮到你.

Rule 或 Grammar 的定义可以包含跳过器类型. 如果包含, 则意味着该非终结符只能与兼容类型的跳过器一起使用. 当情况并非如此时, 就会出现上述错误, 即:

  • 以跳过器类型定义的非终结符在没有跳过器的情况下被使用; 例如, 带有跳过器类型的 rule 被用在 lexeme 指令内部, 或者带有跳过器类型的 grammar 被用于 parse 而不是 phrase_parse,
  • 或者非终结符与不兼容类型的跳过器一起使用; 例如, 以一种跳过器类型定义的 rule 调用了以另一种不兼容跳过器类型定义的第二个 rule.
注释

同样的情况也适用于 Spirit.Karma, 把"跳过器"和 lexeme 替换为"分隔生成器"和 verbatim. 类似地, Spirit.Karma 中相应的错误消息会引用 boost::function3 和第 3 个参数(而不是第 4 个).
