深入解析器

本节不适合胆小者. 这里提炼了 Spirit.Qi 解析器的内部工作机制, 使用 Spirit 库的真实代码作为示例. 不过, 也不必害怕继续读下去. 我们尽力循序渐进地解释各种内容, 同时突出重要的洞见.

Parser 类是所有解析器的基类.

template <typename Derived>
struct parser
{
    struct parser_id;
    typedef Derived derived_type;
    typedef qi::domain domain;

    // Requirement: p.parse(f, l, context, skip, attr) -> bool
    //
    //  p:          a parser
    //  f, l:       first/last iterator pair
    //  context:    enclosing rule context (can be unused_type)
    //  skip:       skipper (can be unused_type)
    //  attr:       attribute (can be unused_type)

    // Requirement: p.what(context) -> info
    //
    //  p:          a parser
    //  context:    enclosing rule context (can be unused_type)

    // Requirement: P::template attribute<Ctx, Iter>::type
    //
    //  P:          a parser type
    //  Ctx:        A context type (can be unused_type)
    //  Iter:       An iterator type (can be unused_type)

    Derived const& derived() const
    {
        return *static_cast<Derived const*>(this);
    }
};

Parser 类本身并不知道如何解析任何东西, 而是依赖模板参数 Derived 来进行实际的解析. 这种技术在模板元编程圈子里被称为"奇异递归模板模式". 这种继承策略为我们提供了多态的能力, 而没有虚函数的开销. 从本质上讲, 这是实现编译期多态的一种方式.

派生解析器 PrimitiveParser, UnaryParser, BinaryParser 和 NaryParser 提供了解析器检测, 自省, 变换和访问所需的必要设施.

派生解析器必须支持以下内容:

bool parse(f, l, context, skip, attr)

f, l

first/last 迭代器对

context

外围 rule 上下文(可以是 unused_type)

skip

跳过器(可以是 unused_type)

attr

属性(可以是 unused_type)

parse 是主要的解析器入口点. skipper 可以是一个 unused_type. 它是 Spirit 中到处使用的一种类型, 表示"不关心". skip 有一个针对 unused_type 的重载, 它只是一个空操作. 这样, 我们就不必为短语级和字符级解析编写多个 parse 函数.

以下是解析的基本规则:

  • 解析器成功时返回 true, 否则返回 false.
  • 成功时, first 会被递增 N 次, 其中 N 是解析的字符数. N 可以为零 --即空(epsilon)匹配.
  • 成功时, 解析得到的属性被赋给 attr
  • 失败时, first 会被重置为进入解析器函数之前的位置. attr 保持不变.

void what(context)

context

外围 rule 上下文(可以是 unused_type)

what 函数应当显而易见. 它提供一些关于解析器"什么" 的信息. 例如, 它可以用作调试辅助.

P::template attribute<context>::type

P

解析器类型

context

上下文类型(可以是 unused_type)

attribute 元函数返回解析器期望的属性类型. 在某些情况下, 它依赖于上下文.

在本节中, 我们将剖析两种解析器类型:

解析器

PrimitiveParser

用于原始数据的解析器(例如整数解析).

UnaryParser

具有单一主体(subject)的解析器(例如 kleene star).

原语解析器

在剖析研究中, 我们将使用 Spirit 的一个原语: boost::spirit::qi 命名空间中的 any_int_parser.

[primitive_parsers_any_int_parser]

any_int_parser 派生自 PrimitiveParser<Derived>, 而后者又派生自 parser<Derived>. 因此, 它支持以下要求:

  • parse 成员函数
  • what 成员函数
  • 内嵌的 attribute 元函数

parse 是主入口点. 对于原语解析器, 我们要做的第一件事是调用:

qi::skip(first, last, skipper);

以执行预跳过. 预跳过之后, 解析器继续做自己的事情. 实际的解析代码位于 extract_int<T, Radix, MinDigits, MaxDigits>::call(first, last, attr);

这个简单而不花哨的协议是 Spirit 快速的原因之一. 如果你了解 Spirit.Classic 的内部机制, 甚至可能用它写过一些解析器, 那么这个简单的 Spirit 机制用起来会是一种享受. 没有 scanner 和那些乱七八糟的东西.

what 函数只是告诉我们它是一个整数解析器. 很简单.

attribute 元函数返回 T 模板参数. 我们把 any_int_parser 关联到用于 short_, int_, long_ 和 long_long 类型的一些占位符. 但首先, 我们在命名空间 boost::spirit 中启用这些占位符:

template <> // enables short_
struct use_terminal<qi::domain, tag::short_> : mpl::true_ {};


template <> // enables int_
struct use_terminal<qi::domain, tag::int_> : mpl::true_ {};


template <> // enables long_
struct use_terminal<qi::domain, tag::long_> : mpl::true_ {};


template <> // enables long_long
struct use_terminal<qi::domain, tag::long_long> : mpl::true_ {};

注意 any_int_parser 位于命名空间 boost::spirit::qi 中, 而这些 启用器 位于命名空间 boost::spirit 中. 原因是这些占位符被 Spirit 的其他 域 共享. 解析器 Spirit.Qi 是一个域, 生成器 Spirit.Karma 是另一个域. 其他解析器技术也可能被开发出来并放入另一个域. 尽管如此, 为了互操作性, 所有这些域都可能共享相同的占位符. 这些占位符的解释是特定于域的.

既然已经启用了占位符, 我们必须为它们编写生成器. make_xxx 之类的代码(在 boost::spirit::qi 命名空间中):

template <
    typename T
  , unsigned Radix = 10
  , unsigned MinDigits = 1
  , int MaxDigits = -1>
struct make_int
{
    typedef any_int_parser<T, Radix, MinDigits, MaxDigits> result_type;
    result_type operator()(unused_type, unused_type) const
    {
        return result_type();
    }
};

上面这个是我们的主生成器. 它是一个带有 2 个(未使用的)实参的简单函数对象. 这些实参是

  1. 由 proto 获得的实际终结符值. 在这里, 是 short_, int_, long_ 或 long_long 之一. 我们不关心它.
  2. 修饰符. 我们也不关心它. 它允许诸如 no_case[p] 之类的指令向内层解析器节点传递信息. 稍后我们会看到这是如何工作的.

现在:

template <typename Modifiers>
struct make_primitive<tag::short_, Modifiers>
  : make_int<short> {};


template <typename Modifiers>
struct make_primitive<tag::int_, Modifiers>
  : make_int<int> {};


template <typename Modifiers>
struct make_primitive<tag::long_, Modifiers>
  : make_int<long> {};


template <typename Modifiers>
struct make_primitive<tag::long_long, Modifiers>
  : make_int<boost::long_long_type> {};

这些代码为特定的标签特化了 qi:make_primitive. 它们都继承自 make_int, 由后者完成实际工作.

复合解析器

让我介绍一下 kleene star (同样位于命名空间 spirit::qi 中):

template <typename Subject>
struct kleene : unary_parser<kleene<Subject> >
{
    typedef Subject subject_type;

    template <typename Context, typename Iterator>
    struct attribute
    {
        // Build a std::vector from the subject's attribute. Note
        // that build_std_vector may return unused_type if the
        // subject's attribute is an unused_type.
        typedef typename
            traits::build_std_vector<
                typename traits::
                    attribute_of<Subject, Context, Iterator>::type
            >::type
        type;
    };

    kleene(Subject const& subject_)
      : subject(subject_) {}

    template <typename F>
    bool parse_container(F f) const
    {
        while (!f (subject))
            ;
        return true;
    }

    template <typename Iterator, typename Context
      , typename Skipper, typename Attribute>
    bool parse(Iterator& first, Iterator const& last
      , Context& context, Skipper const& skipper
      , Attribute& attr_) const
    {
        // ensure the attribute is actually a container type
        traits::make_container(attr_);

        typedef detail::fail_function<Iterator, Context, Skipper>
            fail_function;

        Iterator iter = first;
        fail_function f(iter, last, context, skipper);
        parse_container(detail::make_pass_container(f, attr_));

        first = f.first;
        return true;
    }

    template <typename Context>
    info what(Context& context) const
    {
        return info("kleene", subject.what(context));
    }

    Subject subject;
};

在形式上, 它看起来与其原语近亲 int_parser 相似. 同样, 它具有 Derived 所要求的相同基本要素.

  • 内嵌的 attribute 元函数
  • parse 成员函数
  • what 成员函数

kleene 是一个复合解析器. 它是组合另一个解析器的解析器, 即其 "主体". 它是一个 UnaryParser 并从其派生子类. 与 PrimitiveParser 一样, UnaryParser<Derived> 派生自 parser<Derived>.

unary_parser<Derived> 对 Derived 有以下表达式要求:

  • p.subject -> 主体解析器 ( p 是一个 UnaryParser 解析器.)
  • P::subject_type -> 主体解析器类型 ( P 是一个 UnaryParser 类型.)

parse 是主要的解析器入口点. 由于这不是一个原语解析器, 我们不需要调用 qi::skip(first, last, skipper). subject 如果是原语, 会执行预跳过; 如果它是另一个复合解析器, 它最终会沿调用链在某个位置调用一个原语解析器, 由后者执行预跳过. 这使得它比 Spirit.Classic 高效得多. Spirit.Classic 把跳过的工作交给了所谓的"scanner", 后者在每次递增迭代器时都盲目地尝试预跳过.

kleene 的 attribute 是什么? 一般来说, 它是一个 std::vector<T>, 其中 T 是主体的属性. 不过有一种特殊情况. 如果 T 是一个 unused_type, 那么 kleene 的属性也是 unused_type. traits::build_std_vector 会处理这个细节.

好, 让我们来解析. 首先, 我们需要为主体提供一个局部属性:

typename traits::attribute_of<Subject, Context>::type val;

traits::attribute_of<Subject, Context> 只是调用主体的 struct attribute<Context> 内嵌元函数.

val 初始为默认初始化. 这个 val 就是我们要传递给主体的 parse 函数的那个.

只要主体解析器成功, kleene 就会无限重复. 每次成功解析时, 我们把解析得到的属性 push_back 到 kleene 的属性中, 后者至少应当与一个 std::vector 兼容. 换句话说, 尽管我们说我们希望属性是一个 std::vector, 我们还是尽量宽容一些. kleene 的 parse 的调用者可以传递不同的属性类型. 只要它也是具有 push_back 的合规 STL 容器, 就没有问题. 下面是 kleene 的循环:

while (subject.parse(first, last, context, skipper, val))
{
    // push the parsed value into our attribute
    traits::push_back(attr, val);
    traits::clear(val);
}
return true;

请注意, 我们没有调用 attr.push_back(val), 而是调用了一个 Spirit 提供的函数:

traits::push_back(attr, val);

这是一种反复出现的模式. 我们这样做的原因是 attr 可以 是 unused_type. traits::push_back 会处理这个细节. 针对 unused_type 的重载是空操作. 现在, 你可以想象 Spirit 为什么这么快了! 解析器非常简单, 生成的代码与手工编写的循环一样高效. 所有这些解析器组合和递归 parse 调用都会被现代 C++ 编译器大量内联. 最终, 使用 kleene 时你得到的是一个紧凑的循环. 没有多余的负担. 如果属性未使用, 就不会为它生成代码. Spirit 就是这样设计的.

what 函数只是把主体的输出包装成 "kleene"... "".

好, 现在, 与 int_parser 一样, 我们必须把解析器挂接到 qi 引擎. 方法如下:

首先, 我们启用前缀星号运算符. 在 proto 中, 它被称为"dereference":

template <>
struct use_operator<qi::domain, proto::tag::dereference> // enables *p
  : mpl::true_ {};

这在命名空间 boost::spirit 中完成, 类似于它的伙伴: 即 use_terminal 特化, 对应我们的 int_parser. 显然, 我们使用 use_operator 来为 qi::domain 启用解引用.

然后, 我们需要编写生成器(在 qi 命名空间中):

template <typename Elements, typename Modifiers>
struct make_composite<proto::tag::dereference, Elements, Modifiers>
  : make_unary_composite<Elements, kleene>
{};

这实际上是说: 对于所有形如 *p 的表达式, 构建一个 kleene 解析器. Elements 是一个 Boost.Fusion 序列. kleene 是一元运算符, 因此预期序列中只有一个元素. 该元素就是 kleene 的主体.

我们仍然不关心 Modifiers. 等讲到深入指令时, 我们再看修饰符是怎么回事.
