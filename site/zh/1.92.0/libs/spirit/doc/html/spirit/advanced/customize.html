为什么需要属性定制点
重要

在继续阅读之前, 请注意本节描述的接口尚未最终定稿, 将来可能发生变化, 且不保证向后兼容. 尽管如此, 我们仍然记录了这些定制点接口, 因为我们认为它们很重要. 理解定制点有助于理解 Spirit. 此外, 它们已被证明是强大的工具, 能够将用户的数据结构与 Qi 的 解析器和 Karma 的 生成器完全集成.

Spirit 在设计时就考虑了可扩展性. 它提供了许多不同的属性定制点, 使得自定义数据类型能够与 Spirit.Qi 的解析过程或 Spirit.Karma 的输出生成过程集成. 所有属性定制点都用类似的技术暴露: 模板的完全特化或部分特化. Spirit 通常实现主模板, 提供默认实现. 作为用户, 你必须为想要与库集成的数据类型提供该模板的部分或完全特化. 事实上, 库自身也使用这些定制点, 例如处理 unused_type 属性类型的魔力.

下面的示例展示了 traits::container_value 定制点, 不同的解析器(例如 Kleene, Plus 等)用它来查找要存储到所提供 STL 容器中的属性类型:

template <typename Container, typename Enable/* = void*/>
struct container_value
  : detail::remove_value_const<typename Container::value_type>
{};

库会在适当的位置实例化此模板, 并把所提供的容器类型用作模板实参. 在解析要存入该容器的元素时, 内嵌的 type 被用作属性类型.

下面的示例展示了 unused_type 的预定义特化:

template <>
struct container_value<unused_type>
{
    typedef unused_type type;
};

它把内嵌的 type 同样定义为 unused_type, 以这种方式将"无关"属性状态传播给内嵌解析器.

所有属性定制点都遵循相同的模式. 最后一个模板参数总是 typename Enable = void, 允许利用 SFINAE 对模板特化过程进行细粒度控制. 但大多数时候你可以放心地忽略它的存在.

以下各节将描述所有定制点, 并说明需要为达到什么目的而特化哪一个.

定制点的使用

不同的定制点由库的不同部分使用. 部分定制点同时被 Spirit.Qi 和 Spirit.Karma 使用, 而另一些则专门用于其中一个子库. 我们将说明何时需要实现某个特定的定制点, 以及同样重要的: 哪些定制点需要同时实现. 仅仅为一个定制点提供特化通常是不够的; 在这种情况下, 作为用户, 你必须为想要与库集成的数据类型提供所有必要的定制.
