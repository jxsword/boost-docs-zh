引言: Spirit.Lex

词法扫描是分析输入字符流并将其分隔为被称为记号的字符串的过程, 这些字符串由空白字符分隔. 大多数编译器著作都从这里开始, 并用几章的篇幅讨论构建扫描器的各种方法. Spirit.Lex 是一个库, 用于消除为你的文法创建词法分析器的复杂性 (在本文档中, 我们将交替使用 'lexical analyzer'、'lexer' 和 'scanner' 这几个术语). 创建词法分析器所需要的一切, 就是知道描述你想在输入中识别的不同记号的模式集合. 为了更正式一些, 这里给出一些定义:

  • 记号是具有整体意义的连续字符序列. 记号可以拥有特定于记号类型的属性, 这些属性携带关于所匹配字符序列的附加信息.
  • 模式是以正则表达式形式表达、描述特定记号如何构成的规则. 例如, [A-Za-z][A-Za-z_0-9]* 就是匹配 C++ 标识符的规则的一个模式.
  • 记号之间的字符被称为空白字符; 包括空格、制表符、换行符和换页符. 很多人也把注释算作空白字符, 不过由于 lint 等某些工具会查看注释, 这种做法并不完美.
为什么要使用单独的词法分析器?

通常, 词法扫描在与解析器分离的模块中完成, 只向解析器提供输入记号流. 从理论上讲, 这种分离并非必需, 因为归根结底定义语言的语法规则只有一套, 所以理论上我们可以把整个解析器写在一个模块里. 事实上, Spirit.Qi 允许你在不使用词法分析器的情况下编写解析器, 直接解析输入的字符流, 而且自诞生以来, Spirit 在大多数情况下正是这样使用的.

然而, 这种分离既有实用基础也有理论基础, 并且在实际应用中被证明非常有用. 1956 年, Noam Chomsky 定义了文法的 "Chomsky Hierarchy" (乔姆斯基层次):

  • 0 型: 无限制文法 (例如自然语言)
  • 1 型: 上下文有关文法
  • 2 型: 上下文无关文法
  • 3 型: 正则文法

这些文法的复杂度依次递增, 正则文法最简单, 无限制文法最复杂. 类似地, 针对这些文法的模式识别复杂度也随之增加. 虽然某些编程语言 (如 C++) 的少数特性属于 1 型, 但所幸编程语言在绝大多数情况下只用 2 型和 3 型就可以描述. 这两种类型的妙处在于它们广为人知, 其解析方法也已被充分理解. 已经证明, 任何正则文法都可以用状态机 (有限自动机) 来解析; 类似地, 上下文无关文法总是可以用下推自动机 (本质上是一个增加了栈的状态机) 来解析.

在真实的编程语言和实用文法中, 能够当作正则表达式处理的部分往往是较低层次的部分, 例如标识符或整数值的定义:

letter     := [a-zA-Z]
digit      := [0-9]

identifier := letter [ letter | digit ]*
integer    := digit+

实用文法中更高层次的部分往往更复杂, 无法用纯正则表达式实现. 在递归文法层次时, 我们需要把信息存储在内建的硬件栈上, 而这正是自顶向下解析所偏好的方法. 由于解析这两类文法需要不同种类的抽象机, 把词法扫描器分离成围绕状态机思想构建的独立模块被证明是高效的. 这里的目标是使用完成工作所需的最简单的解析技术.

把扫描器从解析器中分离出来的另一个更实际的原因, 是解析期间需要回溯. 输入数据是字符流, 通常被认为从左到右处理而不做任何回溯. 遗憾的是, 实践中大多数时候这并不可行. 几乎每种语言都有某些关键字, 例如 IF、FOR 和 WHILE. 某个字符序列究竟构成关键字还是只是标识符, 这一判定往往要在看到它 之后 的第一个分隔符之后才能做出. 事实上, 这使得该过程变成回溯式的, 因为我们必须把字符串保存足够久才能做出判定. 对于更粗粒度的语言特性, 例如嵌套的 IF/ELSE 语句, 也是如此: 关于最后一个 ELSE 语句属于哪个 IF 的判定, 只有在看到整个结构之后才能做出.

因此, 传统编译器的结构通常会把低层与高层解析的职能分开. 词法扫描器在字符层面处理事务, 把字符收集成字符串, 把字符序列转换成整数等不同表示, 然后把它们作为不可再分的记号传递给解析器本体. 让扫描器承担额外的工作, 例如识别关键字、把标识符存入表中等等, 也被视为正常做法.

Spirit 正是遵循这一结构, 其中 Spirit.Lex 可用于实现基于状态机的识别器, 而 Spirit.Qi 可用于为上下文无关文法构建识别器. 由于这两个模块彼此无缝集成, 并且都与 C++ 目标语言无缝集成, 甚至可以利用所提供的功能来构建更复杂的文法识别器.

优点: 使用 Spirit.Lex

使用 Spirit.Lex 创建词法分析器, 相比使用 Flex 等更传统的工具, 其优势在于它与 Spirit 库和 C++ 宿主语言的精心集成. 你不需要任何外部工具来生成代码, 你的词法分析器将与程序的其他部分完美集成, 从而可以自由访问任何上下文信息和数据结构. 由于 C++ 编译器能看到全部代码, 无论用户选择了哪些配置选项, 它都会生成最优代码. Spirit.Lex 为你提供类似的 Flex 程序所能获得的绝大多数特性, 而无需离开 C++ 这一宿主语言:

  • 记号的定义通过正则表达式 (模式) 完成
  • 记号定义可以引用特殊的替换字符串 (模式宏), 从而简化模式定义
  • 生成的词法扫描器可以有多个起始状态
  • 可以为任意记号定义附加代码; 每当匹配到相应的记号模式时, 这段代码就会被执行

尽管也可以使用 Spirit.Lex 生成代表词法分析器的 C++ 代码 (我们将其称为 静态模型, 在 静态模型 一节中有更详细的描述) - 这种模型与 Flex 的工作方式非常相似 - 但我们将主要关注与之相反的 动态模型. 你可以把记号定义直接集成到你的 C++ 程序中, 在运行期动态构建词法分析器. 这种动态模型是 Flex 或其他词法扫描器生成器 (如 re2c、Ragel 等) 所不支持的. 这种动态灵活性使你能够加快应用程序的开发.

库结构: Spirit.Lex

下面的 插图 展示了在应用程序中如何使用 Spirit.Lex 库的概览. Spirit.Lex 允许基于模式创建词法分析器. 这些模式是基于正则表达式的规则, 用于定义要在字符输入序列中识别的不同记号. 输入序列应当以任意标准前向迭代器的形式提供给词法分析器. 词法分析器本身也暴露一个标准前向迭代器. 区别在于: 暴露的迭代器提供对记号序列 (而非字符序列) 的访问. 该序列中的记号是在分析底层字符序列并将其与应用程序定义的模式进行匹配时动态构造的.
