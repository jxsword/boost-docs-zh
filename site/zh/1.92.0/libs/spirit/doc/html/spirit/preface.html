前言

“满足 'goodness' (易于理解、灵活、高效) 大部分标准的设计示例有: 递归下降解析器, 它是传统的过程式代码; 另一个示例是 STL, 它是一个泛型的容器与算法库, 关键地依赖于传统过程式代码和参数多态两者. ” --Bjarne Stroustrup

历史

80 年代

80 年代中期, Joel 用 Pascal 编写了他的第一个计算器. 那是一次难忘的编码经历, 他惊叹于一组相互递归的函数竟能为文法规范建模. 随着时间推移, 他从那段学术经历中习得的技能变得非常实用, 因为他被委派去做一些解析工作. 例如, 每当他需要执行任何形式的二进制或文本 I/O 时, 他都尝试以较为正式的方式处理每个任务: 先用类 Pascal 的语法图编写一个文法, 然后编写相应的递归下降解析器. 这一过程效果很好.

90 年代

互联网和万维网的到来使解析需求放大了千倍. 有一段时间, Joel 必须为一个 Web 浏览器项目编写 HTML 解析器. 借助 W3C 的正式规范, 他轻松地编写了一个递归下降 HTML 解析器. 在互联网的影响下, RFC 规范非常丰富. SGML、HTML、XML、电子邮件地址, 甚至那些看似平凡的 URL, 都使用小型 EBNF 风格的文法规范进行了正式定义. Joel 有更多解析工作要做, 他希望有一个类似于 YACC 和 ANTLR 等大型解析器生成器的工具, 能从文法规范自动构建解析器.

这种理想工具应能解析从电子邮件地址、命令行到 XML 和脚本语言的任何东西. 可伸缩性是首要目标. 该工具应能在不带来沉重开发负担的情况下做到这一点, 而这是上述解析器生成器所做不到的. 其结果就是 Spirit.

Spirit 是一个个人项目, 构思于 Joel 在日本从事研发工作期间. 受 GoF 的组合模式和解释器模式启发, 他意识到可以用基础组件 (终结符) 与组合组件 (产生式) 的层次化对象组合来为递归下降解析器建模. 最初的版本用运行期多态类实现. 解析器在运行期通过喂入如下产生式规则字符串来生成:

"prod ::= {'A' | 'B'} 'C';"

一个 compile 函数编译该解析器, 动态创建对象层次结构并即时链接语义动作. 非常早期的文献可在此处找到: pre-Spirit.

2001 至 2006 年

1.0 到 1.8 版是对原始 Spirit 解析器的完全重写, 使用了表达式模板和静态多态, 灵感来自 Todd Veldhuizen 的工作 (Expression Templates, C++ Report, 1995 年 6 月). 最初, static-Spirit 版本只打算替换原始 dynamic-Spirit 的核心. dynamic-Spirit 反正需要一个解析器来实现自身. 原始版本使用手写的递归下降解析器来解析输入的文法规范字符串. 正是在这个时候, Hartmut Kaiser 加入了 Spirit 的开发.

2001 年 5 月首次以 "开源" 形式亮相后, static-Spirit 获得了成功. 大约在 2001 年 11 月, Spirit 网站的活动百分位达到 98%, 成为当时 Source Forge 上排名第一的解析器工具. 对于一个解析器库这样的小众项目来说, 这相当不错. Spirit 的 "static" 部分被淡忘, static-Spirit 干脆就成为了 Spirit. 该库很快演进, 获得了更多动态特性.

2002 年 10 月, Spirit 正式被 Boost 接受. Boost 是一项围绕免费开源 C++ 库集合的、经同行评审的开放协作开发计划, 覆盖广泛的领域. Boost 库作为设计和实现质量、健壮性与可复用性的行业标准而广为人知.

2007

多年来, 特别是在 Spirit 被 Boost 接受之后, Spirit 出色地完成了它的使命. Classic-Spirit (2.0 之前的版本) 专注于转换解析 (transduction parsing), 即把输入字符串仅仅翻译为输出字符串. 许多解析器都属于转换类型. 当需要为解析器库添加属性时, 采用的是相当临时的方式, 目标是与 Classic Spirit 100% 向后兼容. 结果就是: 有些解析器有属性, 有些没有.

Spirit V2 是另一次重大重写. Spirit V2 文法是完全属性化的 (参见 Attribute Grammar), 这意味着所有解析器组件都有属性. 为了高效而优雅地做到这一点, 我们不得不使用几个基础设施库. 其中一些当时并不存在, 一些在 Spirit 亮相时还很新, 还有一些需要改进. Boost.Mpl 是一个重要的基础设施库, 但不足以实现 Spirit V2. 还必须编写另一个库: Boost.Fusion. Fusion 介于 MPL 和 STL 之间 -- 介于编译期和运行期之间 -- 把类型映射到值. Fusion 是 MPL 和 Boost.Tuples 两者的直系后裔. Fusion 现在是一个成熟的 Boost 库. Boost.Phoenix 也必须加强以支持 Spirit V2, 其成果就是 Boost.Phoenix. 最后同样重要的是, Spirit V2 使用了一个名为 Boost.Proto 的 Expression Templates 库.

尽管 Spirit 已经演化成熟, 成为一个多模块库, 它仍然被用于微型解析任务以及脚本语言. 与 C++ 一样, 你只需为你需要的特性付出代价. Spirit 的力量来自其模块化和可扩展性. 它不是直接给你一把大锤, 而是给你合适的原料, 让你轻松打造一把大锤.

新思想: Spirit V2

就在 Spirit V2 的开发开始之前, Hartmut 接触到了 StringTemplate 库, 它是 ANTLR 解析器框架的一部分. [1] 该库中提出的概念把 Hartmut 引向了 Spirit 演进的下一步. 解析与生成紧密关联于一种形式记法, 即文法. 文法同时描述输入和输出, 因此, 解析器库应当具有由文法驱动的输出. 这种对偶性在 Spirit 中体现为解析器库 Spirit.Qi 和生成器库 Spirit.Karma, 二者使用相同的组件基础设施.

创建一个与 Spirit 解析器良好集成的词法分析器库的想法并不新鲜. 几乎从 Classic-Spirit (V2 之前) 最初亮相起就有人讨论过. 人们已多次尝试把现有的词法分析器库和框架与 Spirit 集成, 并作为概念和可用性的证明 (例如参见 Wave: Boost C/C++ 预处理器库, 以及 SLex: 用 Spirit 实现的完全动态 C++ 词法分析器). 基于这些经验, 我们添加了 Spirit.Lex: 一个完全集成的词法分析器库, 让用户能够利用正则表达式的强大能力进行记号匹配, 为解析器组件减轻压力, 并简化解析器文法. 再次地, Spirit 的模块化结构使我们能够复用与解析器库和生成器库相同的底层组件库.

如何使用本手册

每个主要部分 (共 3 个: Qi、Karma 和 Lex) 大致分为 3 个部分:

  1. 教程: 带有大量注释代码的分步指南. 旨在让用户尽快熟悉该库. 目标是通过丰富的示例和详细的说明建立用户使用该库的信心. 示例胜过千言万语, 而我们有大量的示例!
  2. 摘要: 关键主题的高层次总结. 目标是让用户对该库、关键概念、背景和理论有一个高层次的认识.
  3. 参考: 详细的正式技术参考. 我们从快速参考开始 -- 一个易于使用的表, 映射到参考正文. 参考正文从 C++ 概念开始, 随后是这些概念的模型.
