从 Spirit 1.8.x 迁移

当前版本的 Spirit 是对早期版本的完全重写 (我们把早期版本称为 Spirit.Classic). 解析器生成器现在只是整个库的一部分. Spirit 的解析器子模块现在称为 Spirit.Qi. 它在概念上有所不同, 并暴露了一个完全不同的接口. 一般来说, 把为 Spirit.Classic 编写的解析器转换为 Spirit.Qi 没有简单 (或自动化) 的方法. 因此, 本节只能就如何把你的旧解析器迁移到当前版本的 Spirit 给出指导.

包含文件

Spirit 目录的总体目录结构在 包含文件结构 一节和常见问题条目 头文件地狱 中描述. 这应当能让你很好地了解如何为新解析器找到所需的头文件. 此外, Qi 参考 中的每一节都列出了任何特定组件所需的包含文件.

从头文件的名称就能判断它属于哪个版本. Spirit.Classic 的所有主要包含文件名称中都含有字符串 'classic_', 例如:

#include <boost/spirit/include/classic_core.hpp>

我们把 Spirit.Qi 的所有主要包含文件命名为名称中含有字符串 'qi_', 例如:

#include <boost/spirit/include/qi_core.hpp>

下表粗略列出了 Spirit.Classic 与 Spirit.Qi 之间对应的头文件, 但这只能作为起点, 因为若干组件要么已被移到不同的子模块, 要么在新版本中可能已不存在. 我们只列出最顶层子模块的包含文件. 对于更低层组件所需的头文件, 请参阅该组件相应的参考文档.

自由解析函数

自由解析函数 (即主要解析器 API) 已经改变. 这包括自由函数的名称及其接口. 在 Spirit.Classic 中, 所有自由函数都命名为 parse. 在 Spirit.Qi 中, 它们要么命名为 qi::parse, 要么命名为 qi::phrase_parse, 取决于解析是否应使用跳过器 (qi::phrase_parse) 进行 (qi::parse 则不使用). 所有自由函数现在都返回一个简单的 bool. 返回 true 表示成功 (即解析器已匹配), 返回 false 则表示未匹配 (即解析器未匹配). 这等价于以前 parse_info 的成员 hit. Spirit.Qi 不再支持跟踪被匹配输入的长度. 旧的 parse_info 成员 full 可以通过在 qi::parse 返回后比较迭代器来模拟.

本节的所有代码示例都假定插入了以下 include 语句和 using 指令. 对于 Spirit.Classic:

#include <boost/spirit/include/classic.hpp>
#include <boost/spirit/include/phoenix1.hpp>
#include <iostream>
#include <string>


using namespace boost::spirit::classic;

而对于 Spirit.Qi:

#include <boost/spirit/include/qi.hpp>
#include <boost/phoenix/operator.hpp>
#include <iostream>
#include <string>
#include <algorithm>


using namespace boost::spirit;

下面相似的示例应当能阐明这些差异. 首先是 Spirit.Classic 中的基础示例:

std::string input("1,1");
parse_info<std::string::iterator> pi = parse(input.begin(), input.end(), int_p);

if (pi.hit)
    std::cout << "successful match!\n";

if (pi.full)
    std::cout << "full match!\n";
else
    std::cout << "stopped at: " << std::string(pi.stop, input.end()) << "\n";

std::cout << "matched length: " << pi.length << "\n";

下面是使用 Spirit.Qi 的等价代码:

std::string input("1,1");
std::string::iterator it = input.begin();
bool result = qi::parse(it, input.end(), qi::int_);

if (result)
    std::cout << "successful match!\n";

if (it == input.end())
    std::cout << "full match!\n";
else
    std::cout << "stopped at: " << std::string(it, input.end()) << "\n";

// seldomly needed: use std::distance to calculate the length of the match
std::cout << "matched length: " << std::distance(input.begin(), it) << "\n";

短语解析 (即使用跳过器的解析) 所需的修改类似. 下面是 Spirit.Classic 中短语解析的工作方式:

std::string input(" 1, 1");
parse_info<std::string::iterator> pi = parse(input.begin(), input.end(), int_p, space_p);

if (pi.hit)
    std::cout << "successful match!\n";

if (pi.full)
    std::cout << "full match!\n";
else
    std::cout << "stopped at: " << std::string(pi.stop, input.end()) << "\n";

std::cout << "matched length: " << pi.length << "\n";

下面是 Spirit.Qi 中的等价示例:

std::string input(" 1, 1");
std::string::iterator it = input.begin();
bool result = qi::phrase_parse(it, input.end(), qi::int_, ascii::space);

if (result)
    std::cout << "successful match!\n";

if (it == input.end())
    std::cout << "full match!\n";
else
    std::cout << "stopped at: " << std::string(it, input.end()) << "\n";

// seldomly needed: use std::distance to calculate the length of the match
std::cout << "matched length: " << std::distance(input.begin(), it) << "\n";

注意字符解析器位于一个单独的命名空间中 (此处为 boost::spirit::ascii::space), 因为 Spirit.Qi 现在支持使用不同的字符集. 更多信息参见 字符编码命名空间 一节.

命名约定

在 Spirit.Classic 中, 所有解析器基础组件的名称都带有后缀, 用于编码其类型: 解析器用 "_p", 惰性动作用 "_a", 指令用 "_d" 等等. 在 Spirit.Qi 中没有类似的东西. 唯一的后缀是单个下划线字母 "_", 应用于名称会与关键字或预定义名称冲突的地方 (例如整数解析器的 int_). 总体而言, 大部分 (即使不是全部) 基础解析器和指令都被重命名了. 请参阅 Qi 快速参考 以概览可用的各种解析器基础组件、指令和运算符的名称.

解析器属性

在 Spirit.Classic 中, 大多数解析器基础组件不暴露特定的属性类型. 大多数解析器暴露指向被匹配输入序列的一对迭代器. 由于 Spirit.Qi 中所有解析器都暴露解析器特定的属性类型, 它引入了一个特殊指令 raw[], 允许实现与 Spirit.Classic 中类似的效果. raw[] 指令暴露指向其内嵌解析器匹配序列的一对迭代器. 尽管我们非常鼓励你重写解析器以利用生成的解析器特定属性, 但有时访问底层被匹配的输入序列仍然有帮助.

文法与 rule

grammar<> 和 rule<> 类型对 Spirit.Qi 的重要性, 与它们对 Spirit.Classic 的重要性相同. 它们的主要目的仍然一样: 允许定义非终结符, 并且它们是构建更复杂解析器的主要构件. 尽管如此, 两种类型都经过了重新设计, 其接口也已改变. 让我们先看两个示例, 之后再解释差异. 下面是 Spirit.Classic 中的一个简单文法及其用法:

struct roman : public grammar<roman>
{
    template <typename ScannerT>
    struct definition
    {
        definition(roman const& self)
        {
            hundreds.add
                ("C"  , 100)("CC"  , 200)("CCC"  , 300)("CD" , 400)("D" , 500)
                ("DC" , 600)("DCC" , 700)("DCCC" , 800)("CM" , 900) ;

            tens.add
                ("X"  , 10)("XX"  , 20)("XXX"  , 30)("XL" , 40)("L" , 50)
                ("LX" , 60)("LXX" , 70)("LXXX" , 80)("XC" , 90) ;

            ones.add
                ("I"  , 1)("II"  , 2)("III"  , 3)("IV" , 4)("V" , 5)
                ("VI" , 6)("VII" , 7)("VIII" , 8)("IX" , 9) ;

            first = eps_p         [phoenix::var(self.r) = phoenix::val(0)]
                >>  (  +ch_p('M') [phoenix::var(self.r) += phoenix::val(1000)]
                    ||  hundreds  [phoenix::var(self.r) += phoenix::_1]
                    ||  tens      [phoenix::var(self.r) += phoenix::_1]
                    ||  ones      [phoenix::var(self.r) += phoenix::_1]
                    ) ;
        }

        rule<ScannerT> first;
        symbols<unsigned> hundreds;
        symbols<unsigned> tens;
        symbols<unsigned> ones;

        rule<ScannerT> const& start() const { return first; }
    };

    roman(unsigned& r_) : r(r_) {}
    unsigned& r;
};


std::string input("MMIX");        // MMIX == 2009
unsigned value = 0;
roman r(value);
parse_info<std::string::iterator> pi = parse(input.begin(), input.end(), r);
if (pi.hit)
    std::cout << "successfully matched: " << value << "\n";

下面是 Spirit.Qi 中一个类似的文法及其用法:

template <typename Iterator>
struct roman : qi::grammar<Iterator, unsigned()>
{
    roman() : roman::base_type(first)
    {
        hundreds.add
            ("C"  , 100)("CC"  , 200)("CCC"  , 300)("CD" , 400)("D" , 500)
            ("DC" , 600)("DCC" , 700)("DCCC" , 800)("CM" , 900) ;

        tens.add
            ("X"  , 10)("XX"  , 20)("XXX"  , 30)("XL" , 40)("L" , 50)
            ("LX" , 60)("LXX" , 70)("LXXX" , 80)("XC" , 90) ;

        ones.add
            ("I"  , 1)("II"  , 2)("III"  , 3)("IV" , 4)("V" , 5)
            ("VI" , 6)("VII" , 7)("VIII" , 8)("IX" , 9) ;

        // qi::_val refers to the attribute of the rule on the left hand side 
        first = eps          [qi::_val = 0]
            >>  (  +lit('M') [qi::_val += 1000]
                ||  hundreds [qi::_val += qi::_1]
                ||  tens     [qi::_val += qi::_1]
                ||  ones     [qi::_val += qi::_1]
                ) ;
    }

    qi::rule<Iterator, unsigned()> first;
    qi::symbols<char, unsigned> hundreds;
    qi::symbols<char, unsigned> tens;
    qi::symbols<char, unsigned> ones;
};


std::string input("MMIX");        // MMIX == 2009
std::string::iterator it = input.begin();
unsigned value = 0;
roman<std::string::iterator> r;
if (qi::parse(it, input.end(), r, value))
    std::cout << "successfully matched: " << value << "\n";

两个版本看起来足够相似, 但我们可以看到几处差异 (下面将更详细地逐一讨论):

  • 文法和 rule 都不再依赖于扫描器类型, 二者只依赖于底层迭代器类型. 这意味着令人畏惧的 scanner business (扫描器问题) 不再是问题!
  • 文法不再有内嵌类 definition
  • 文法和 rule 可以在其定义中显式指定属性类型
  • 文法不再有任何显式起始 rule. 相反, 默认使用所包含的某个 rule 作为起始 rule.

前两点紧密相关. scanner business 问题 (Spirit.Classic 的常见问题第一条, 见此处: The Scanner Business) 长期以来一直是个难题. 文法和 rule 类型经过了专门重新设计, 以避免将来出现此问题. 这也意味着我们不再需要文法内部定义类的任何延迟实例化. 因此, 这次重新设计不仅帮助修复了一个长期存在的设计问题, 还大大简化了事物.

所有 Spirit.Qi 解析器组件都有良定义的属性类型. 文法和 rule 也不例外. 但由于二者都需要足够通用以便用于任何解析器, 其属性类型必须显式指定. 在上面的示例中, 文法 roman 和 rule first 都有一个 unsigned 属性:

// grammar definition
template <typename Iterator>
struct roman : qi::grammar<Iterator, unsigned()> {...};

// rule definition
qi::rule<Iterator, unsigned()> first;

所使用的记法类似于函数类型的定义. 这非常自然, 因为你可以把文法和 rule 的合成属性看作其 '返回值'. 事实上, rule 和文法都 '返回' 一个无符号值 —— 即它们匹配到的值.

注释

函数类型记法还允许指定参数. 这些参数被解释为 rule 或文法期望在解析期间传入的继承属性的类型. 更多信息请参阅关于 rule 和文法的继承属性与合成属性的一节 (Attributes).

如果不需要属性, 则无需指定. 文法和 rule 二者的默认属性类型都是 unused_type, 它是一个特殊的占位符类型. 一般而言, 使用 unused_type 作为解析器的属性被解释为 '此解析器没有属性'. 这主要用于应用于输入中不携带任何重要信息部分的解析器, 这些部分其实是正确解释输入所需的分隔符或结构元素.

最后一个差异可能看起来相当表面且无关紧要. 但事实证明, 不必指定文法中的哪个 rule 是起始 rule (即不必从函数 start() 返回它), 也意味着文法中的任何 rule 都可以直接用作起始 rule. 尽管如此, 当文法实例被直接用作解析器时, 文法基类仍会用它必须用作起始 rule 的那个 rule 进行初始化.
