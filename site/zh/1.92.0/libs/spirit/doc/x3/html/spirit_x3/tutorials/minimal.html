X3 程序结构

作为理解本教程的先决条件, 请先回顾前面的 employee 示例. 本示例正是在该示例的基础上构建的.

到目前为止, 为了保持简单, 本教程的所有程序都自包含在一个 cpp 文件中. 实际应用中, 你会希望把解析器的各个逻辑模块拆分到不同的 cpp 和头文件中, 使接口与实现解耦.

组织 X3 解析器结构的方式有很多, 但本教程的 “minimal” 示例展示的是首选方式. 为了便于对照, 本示例基本沿用了与 employee 示例 相同的解析器, 但在结构上允许实际的解析器在其自己的定义文件和 cpp 文件中单独编译. 包括 main 在内的各 cpp 文件只看到头文件, 即接口. 这是关于 X3 解析器在 C++ 应用程序中如何组织的一个好示例.

这些文件的内容应当已经熟悉了. 它本质上就是同一个 employee 示例. 因此我将略去解析器工作原理的细节, 只关注把程序重构为适合实际部署的模块化结构所需的特性.

AST

我们把 AST 声明放在这里:

namespace client { namespace ast
{
    struct employee
    {
        int age;
        std::string forename;
        std::string surname;
        double salary;
    };

    using boost::fusion::operator<<;
}}
Fusion 适配器

在这里, 我们把 AST 适配到 Fusion, 使其成为一等 fusion 公民:

BOOST_FUSION_ADAPT_STRUCT(client::ast::employee,
   age, forename, surname, salary
)
主解析器 API

这是所有其他 cpp 文件都需要包含的主头文件.

BOOST_SPIRIT_DECLARE

还记得 BOOST_SPIRIT_DEFINE 吗? 如果不记得, 那么你或许应该回头复习那一节, 以便更好地理解这里发生了什么.

我们没有使用 BOOST_SPIRIT_DEFINE, 而是使用 BOOST_SPIRIT_DECLARE 作用于顶层规则. 在幕后, 实际发生的事情是: 我们在客户端命名空间中声明了一个 parse_rule 函数.

如果你回头复习了 BOOST_SPIRIT_DEFINE, 你就会明白为什么它正是我们在头文件中需要使用的东西. BOOST_SPIRIT_DECLARE 生成函数声明, 应放在 hpp(头)文件中; 而 BOOST_SPIRIT_DEFINE 生成函数定义, 应放在 cpp 文件中.

注释

BOOST_SPIRIT_DECLARE 是可变参数的, 可用于一条或多条规则. 示例: BOOST_SPIRIT_DECLARE(r1, r2, r3);

在本示例中, 顶层规则是 employee. 我们在这个头文件中声明 employee:

namespace client
{
    namespace parser
    {
        namespace x3 = boost::spirit::x3;
        using employee_type = x3::rule<class employee, ast::employee>;
        BOOST_SPIRIT_DECLARE(employee_type);
    }

    parser::employee_type employee();
}

我们还提供了一个返回 employee 对象的函数. 这就是我们将在任何需要之处使用的解析器. X3 解析器对象非常轻量, 它们基本上是简单的标签, 除了规则名(如 “employee”)之外不携带任何数据. 注意, 我们按值传递它.

解析器定义

这里放置构成我们文法的实际规则:

namespace parser
{
    namespace x3 = boost::spirit::x3;
    namespace ascii = boost::spirit::x3::ascii;

    using x3::int_;
    using x3::lit;
    using x3::double_;
    using x3::lexeme;
    using ascii::char_;

    x3::rule<class employee, ast::employee> const employee = "employee";

    auto const quoted_string = lexeme['"' >> +(char_ - '"') >> '"'];

    auto const employee_def =
        lit("employee")
        >> '{'
        >>  int_ >> ','
        >>  quoted_string >> ','
        >>  quoted_string >> ','
        >>  double_
        >>  '}'
        ;

    BOOST_SPIRIT_DEFINE(employee);
}

parser::employee_type employee()
{
    return parser::employee;
}

在解析器定义中, 我们使用 BOOST_SPIRIT_DEFINE, 就像我们在 employee 示例 中所做的那样.

虽然这是另一个头文件, 但它并不是供客户端包含的. 它的用途是被实例化用的 cpp 文件包含(见下文). 为了保持灵活性, 我们把它放在一个 .hpp 文件中, 这样我们就可以自由地用不同的迭代器类型实例化解析器.

配置

在这里, 我们声明一些类型, 用于实例化 X3 解析器. 请记住, Spirit 解析器可以使用任何 ForwardIterator 工作. 我们还需要提供初始上下文类型, 即 X3 用来发起解析的上下文. 要调用 phrase_parse, 你需要 phrase_parse_context, 如下文所示, 传入 skipper 类型.

using iterator_type = std::string::const_iterator;
using context_type = x3::phrase_parse_context<x3::ascii::space_type>::type;

对于普通的 parse, 我们直接使用 x3::unused_type.

解析器实例化

现在我们在这里为我们的特定配置实例化解析器:

namespace client { namespace parser
{
    BOOST_SPIRIT_INSTANTIATE(employee_type, iterator_type, context_type);
}}

为此, 我们使用 BOOST_SPIRIT_INSTANTIATE, 传入解析器类型、迭代器类型和上下文类型.

BOOST_SPIRIT_INSTANTIATE

回头复习 BOOST_SPIRIT_DEFINE 和 BOOST_SPIRIT_DECLARE, 以便更好地掌握 BOOST_SPIRIT_INSTANTIATE 在做什么以及为什么需要它.

那么 BOOST_SPIRIT_INSTANTIATE 到底是什么? 我们想要的是把解析器的实例化(规则之类)隔离到单独的翻译单元(或者可以说是 cpp 文件)中. 在本示例中, 我们想把 x3 employee 相关内容放到 employee.cpp 中. 这样, 我们就实现了分离编译. 每次更新 employee 解析器源代码时, 我们只需构建 employee.cpp 文件, 其余部分不受影响. 只在一个翻译单元中编译一次, 既节省构建时间, 又避免代码膨胀. 不存在代码重复——否则, 如果你只是在各处包含 employee 解析器(employee.hpp), 就可能出现重复.

但该怎么做呢? 请记住, 出于灵活性考虑, 我们的解析器定义也放在它自己的头文件中, 这样我们就可以自由地用不同的迭代器类型实例化解析器.

我们需要做的是显式实例化 parse_rule 函数, 它分别通过 BOOST_SPIRIT_DECLARE 和 BOOST_SPIRIT_DEFINE 进行声明和定义, 实例化时使用 BOOST_SPIRIT_INSTANTIATE. 对于我们这个具体示例, BOOST_SPIRIT_INSTANTIATE 展开为如下代码:

template bool parse_rule<iterator_type, context_type>(
    employee_type rule_
  , iterator_type& first, iterator_type const& last
  , context_type const& context, employee_type::attribute_type& attr);
主程序

最后是我们的主程序. 代码与单 cpp 文件的 employee 示例 相同, 只不过在这里我们只包含三个头文件:

#include "ast.hpp"
#include "ast_adapted.hpp"
#include "employee.hpp"
  1. ast.hpp 用于 AST 声明
  2. ast_adapted.hpp 如果你需要用 fusion 遍历 AST
  3. employee.hpp 主解析器 API
