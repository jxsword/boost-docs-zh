规则

规则(rule)是一个多态解析器, 充当命名占位符, 捕获赋给它的 EBNF 表达式的行为. 为 EBNF 表达式命名, 使它可以在日后被引用. rule 是一个模板类, 由扫描器的类型(ScannerT), 规则的 上下文及其 标签参数化. 框架提供了默认模板参数, 使规则易于使用.

    template<
        typename ScannerT = scanner<>,
        typename ContextT = parser_context<>,
        typename TagT = parser_address_tag>
    class rule;

框架提供默认模板参数以处理最常见的情况. ScannerT 默认为 scanner<>, 一个普通的原生扫描器, 作用于 char const* 迭代器, 除逐个遍历以空字符结尾的输入中的所有字符之外别无特别之处. 规则标签 TagT 通常与 AST一起使用, 用于标识一条规则; 它在 此处解释. 在平凡的情况下, 把规则声明为 rule<> 就足够了. 除非你想要调整规则的底层行为, 否则完全无需关心 ContextT 模板参数. 有关 ContextT 模板参数的详细信息在 其他地方提供.

参数顺序

自 v1.8.0 起, ScannerT, ContextT 和 TagT 可以以任意顺序指定. 若缺少某个模板参数, 则采用默认值. 示例:

    rule<> rx1;
    rule<scanner<> > rx2;
    rule<parser_context<> > rx3;
    rule<parser_context<>, parser_address_tag> rx4;
    rule<parser_address_tag> rx5;
    rule<parser_address_tag, scanner<>, parser_context<> > rx6;
    rule<parser_context<>, scanner<>, parser_address_tag> rx7;

多个扫描器

自 v1.8.0 起, 规则可以使用一个或多个扫描器类型. 例如, 有些情况下我们需要一条既能在短语层面又能在字符层面工作的规则. 规则/扫描器不匹配一直是令人困惑的根源, 是排名第一的 FAQ. 为解决这一问题, 我们现在有了多扫描器支持. 示例:

    typedef scanner_list<scanner<>, phrase_scanner_t> scanners;

    rule<scanners>  r = +anychar_p;
    assert(parse("abcdefghijk", r).full);
    assert(parse("a b c d e f g h i j k", r, space_p).full);

注意规则 r 如何同时在短语层面与字符层面使用.

默认情况下, 多扫描器支持是禁用的. 必须把宏 BOOST_SPIRIT_RULE_SCANNERTYPE_LIMIT 定义为 scanner_list 中允许的最大扫描器数. 该值必须大于 1 才能启用多扫描器. 以上面的示例为例, 要把列表的扫描器上限定义为两个, 必须在包含 Spirit 头文件之前把以下行插入源文件:

    #define BOOST_SPIRIT_RULE_SCANNERTYPE_LIMIT 2
techniques 一节给出了一个 示例, 其中的 文法 使用了启用多扫描器的规则, lexeme_scanner 与 as_lower_scanner.

规则声明

rule 类建模 EBNF 的产生式规则. 示例:

    rule<> a_rule = *(a | b) & +(c | d | e);

右侧(rhs) EBNF 表达式的类型与行为(可以是任意复杂的)被编码在名为 a_rule 的规则中. a_rule 现在可以在文法的其他地方被引用:

    rule<> another_rule = f >> g >> h >> a_rule;
引用规则

当规则在 EBNF 表达式右侧的任何地方被引用时, 表达式以引用方式持有该规则. 使用者有责任确保被引用的规则保持在作用域内, 在其被引用期间不被销毁.		 
    a = int_p;
    b = a;
    c = int_p >> b;

复制规则

规则是一个怪异的 C++ 公民, 不同于任何其他 C++ 对象. 它不具备正确的拷贝与赋值语义, 不能按值存储与传递. 如果你需要拷贝一条规则, 必须显式调用其成员函数 copy():

    r.copy();

然而, 要当心: 拷贝一条规则并不会深拷贝被拷贝源规则所引用的其他规则. 这可能导致悬垂引用. 再说一次, 使用者有责任确保所有被引用的规则保持在作用域内, 在其被引用期间不被销毁. 谨慎使用.

如果你拷贝了一条规则, 那你会想把它放到某个存储里. 问题是: 怎么放? 存储不能是另一条规则:

    rule<> r2 = r.copy(); // BAD!

因为规则很怪异, 不具备预期的 C++ 拷贝构造与赋值语义! 作为一般准则: 不要把拷贝出的规则放进另一条规则! 为此请改用 stored_rule.

前向声明

rule 可以在定义之前先行声明, 以允许 BNF 声明中常见的循环结构. 示例:

    rule<> a, b, c;

    a = b | a;
    b = c | a;

递归

规则的右侧可以引用其他规则, 包括它自身. 限制是不允许直接或间接的左递归(这是一个未检查的运行期错误, 会导致无限循环). 这是自顶向下解析器的典型特征. 示例:

    a = a | b; // infinite loop!
什么是左递归?

当你有一条规则在做任何其他事情之前就调用自身时, 就发生了左递归. 这种情况下, 自顶向下的解析器会陷入无限循环. 有关如何消除左递归的详情, 见 FAQ.

未定义规则

未定义的规则不匹配任何内容, 在语义上等价于 nothing_p.

重复声明

与任何其他 C++ 赋值一样, 对规则的第二次赋值是破坏性的, 会重定义它. 旧的定义丢失. 规则是动态的. 规则可以随时改变其定义:

    r = a_definition;
    r = another_definition;

进行第二次赋值时, 规则 r 失去了旧定义. 如前所述, 未定义的规则不匹配任何内容, 在语义上等价于 nothing_p.

动态解析器

在命令式 C++ 中承载声明式 EBNF 产生了有趣的融合. 我们兼得两个世界之长. 我们能够使用 if, else 语句等命令式结构在运行期便捷地修改文法. 示例:

    if (feature_is_available)
        r = add_this_feature;

规则本质上是动态解析器. 动态解析器的特征是能够在运行期修改自身行为. 起初, 未定义的规则不匹配任何内容. 规则可以随时被定义与重定义, 从而动态地改变其行为.

没有开始规则

通常, 解析器有所谓的开始符号, 它被选作文法的根, 解析从那里开始. Spirit 解析器框架没有开始符号的概念. 任何规则都可以是开始符号. 这一特性促进了分步创建解析器. 我们可以自底向上构建解析器, 同时充分测试每一层或模块, 直到抵达最顶层.

解析器标签

规则可以打上标签以供标识. 这是必要的, 尤其是在处理 解析树与 AST时, 用于查看是哪条规则创建了特定的 AST/解析树节点. 每条规则有一个 parser_id 类型的 ID. 该 ID 可以通过规则的 id() 成员函数获得:

    my_rule.id(); //  get my_rule's id

parser_id 类声明为:

    class parser_id
    {
    public:
                    parser_id();
        explicit    parser_id(void const* p);
                    parser_id(std::size_t l);
    
        bool        operator==(parser_id const& x) const;
        bool        operator!=(parser_id const& x) const;
        bool        operator<(parser_id const& x) const;
        std::size_t to_long() const;
    };

parser_address_tag

规则的 TagT 模板参数提供这个 ID. 其默认值为 parser_address_tag. parser_address_tag 使用规则的地址作为其 ID. 这通常不是最方便的, 因为并不总是能够取得规则的地址来进行比较.

parser_tag

可以用特定的常量整数来标识一条规则. 为此, 我们可以使用 parser_tag<N>, 其中 N 是一个常量整数:

    rule<parser_tag<123> > my_rule; //  set my_rule's id to 123

dynamic_parser_tag

parser_tag<N> 只能指定在编译期定义的 静态 ID. 如果你需要 ID 是 动态的(可在运行期改变), 可以使用 dynamic_parser_tag 类作为 TagT 模板参数. 该模板参数启用了 set_id() 函数, 它可用于在运行期设置所需的 id:

    rule<dynamic_parser_tag> my_dynrule;
    my_dynrule.set_id(1234);    // set my_dynrule's id to 1234

若未调用 set_id() 函数, 解析器 id 默认使用规则的地址作为其 ID, 就像 parser_address_tag 模板参数那样.
