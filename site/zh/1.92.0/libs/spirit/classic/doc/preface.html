前言


"满足大部分"优良"标准(易于理解, 灵活, 高效)的设计范例, 一是递归下降解析器, 它是传统的纯过程式代码. 另一个例子是 STL, 它是一个容器与算法的泛型库, 关键性地同时依赖于传统过程式代码与参数多态."

Bjarne Stroustrup

历史

十五年前, 我用 Pascal 写了我的第一个计算器. 那是我最难忘的编码经历之一. 我惊讶于一组相互递归的函数竟然能为文法规范建模. 随着时间推移, 我从那次学术经历中习得的技能变得非常实用. 我不时被安排做一些解析工作. 例如, 每当我需要执行任何形式的 I/O 时, 哪怕是二进制的, 我都会尝试以比较正式的方式来处理任务: 先用类 Pascal 的语法图编写一个文法, 然后编写相应的递归下降解析器. 这非常有效.

互联网与万维网的到来把这一点放大了千倍. 有一次, 我必须为一个 Web 浏览器项目编写 HTML 解析器. 我基于 W3C 的正式规范轻松地写出了一个可工作的递归下降 HTML 解析器. HTML 拥有正式的文法规范, 这着实让我庆幸. 由于互联网的影响, 我随后要做更多的解析. RFC 规范无处不在. SGML, HTML, XML, 甚至电子邮件地址和那些看似微不足道的 URL, 都是用小型 EBNF 风格的文法规范正式定义的. 这让我盼望有一个类似 YACC 和 ANTLR 这样重量级解析器生成器的工具, 由文法规范自动构建解析器. 但我又希望它极其小巧; 小到能装进口袋, 却又可扩展.

它必须能够实际解析从电子邮件地址这样的简单文法到 XML 这样中等复杂的文法, 或许还有一些小型到中型的脚本语言. 可扩展性是首要目标. 你应当能够把它用于解析命令行这样的小任务, 而不必像使用 YACC 或 PCCTS 那样背负沉重的包袱. 即使现在它已演进成熟为一个多模块库, 忠于其初衷, Spirit 仍可用于极端微型的解析任务. 你只需为所需的功能付费. Spirit 的力量来自其模块化与可扩展性. 它不是直接递给你一把大锤, 而是给你合适的原料, 让你轻松地打造一把大锤. 例如, 它实际上并没有词法分析器, 但如果你需要一个, 你拥有编写一个所需的全部原始原料.

结果便是 Spirit. Spirit 是我在日本做研发时构思的个人项目. 受 GoF 的组合模式与解释器模式启发, 我意识到可以用原语(终结符)与组合器(产生式)的层次化对象组合来为递归下降解析器建模. 最初的版本以运行期多态类实现. 解析器在运行时通过喂入产生式规则字符串(如 "prod ::= {‘A’ | ‘B’} ‘C’;)生成. 一个 compile 函数编译该解析器, 动态创建对象层次并即时挂接语义动作. 早期的文字可 在此找到.

我们今天拥有的版本是对原始 Spirit 解析器的完全重写, 使用了表达式模板与静态多态, 灵感来自 Todd Veldhuizen 的工作(" Expression Templates", C++ Report, 1995 年 6 月). 最初, static-Spirit 版本只打算替换原始 dynamic-Spirit 的核心. 反正 dynamic-spirit 也需要一个解析器来实现自身. 原来的实现使用手写的递归下降解析器来解析输入的文法规范字符串.

在 2001 年 5 月初次"开源"亮相之后, static-Spirit 获得了成功. 大约在 2001 年 11 月, Spirit 网站的活动百分位达到 98%, 使其成为当时 SourceForge 上排名第一的解析器工具. 对于解析器库这样一个小众项目来说, 已属不俗. Spirit 的"静态"部分被淡忘, static-Spirit 简直就成了 Spirit. 该框架很快演化, 获得了更多动态特性.

如何使用本手册

Spirit 框架从核心出发, 按逻辑模块组织. 本文档为框架中的每个模块提供用户指南与参考. 一个简单清晰的代码示例抵得上一百行文档; 因此, 用户指南以大量示例呈现, 并以渐进的方式加以注解和解释. 用户指南建立在示例之上 —— 大量的示例.

在每个模块的用户手册部分, 我们尽量避免前向引用信息(即引用尚未讨论过的特定信息). 不过在很多情况下, 高级但相关的主题不可避免地穿插在正常的讨论流程中. 为缓解这一问题, 归类为"进阶"的主题在初读时可以跳过.

一些图标用于标记某些主题, 表明其相关性. 这些图标出现在某些文字之前, 表示:

图标
Note 所提供的信息比较重要, 读者应当留意.
Alert 所提供的信息至关重要.
Detail 所提供的信息是辅助性的, 但会让读者对特定主题有更深入的理解. 可以跳过.
Tip 一条潜在有用且有益的信息.
