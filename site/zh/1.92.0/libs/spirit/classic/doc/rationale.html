设计理由

虚函数: 从静态 C++ 到动态 C++

rule 跨越了静态 C++ 与动态 C++ 的边界. 实际上, rule 把编译期多态 (使用模板) 转换为运行期多态 (使用虚函数). 这是必要的, 因为 C++ 无法自动声明一个变量, 其类型由赋值表达式右侧 (rhs) 的任意复杂表达式推导得出. 基本上, 我们想这样做:

    T rule = an_arbitrarily_complex_expression;

而不必知道或关心赋值表达式右侧(rhs)的结果类型. 除此之外, 我们还需要一个设施来前向声明未知类型:

    T rule;
    ...
    rule = a | b;

这些限制把我们引向规则的这一实现. 其代价是虚函数调用的开销, 每次调用规则都会经过一次.

多重声明

某些 BNF 变体允许对 rule 的多重声明. 这些声明被视为候选. 示例:

   r = a;    
   r = b;

等价于:

   r = a | b;

Spirit v1.3 允许这种行为. 然而, 当前版本的 Spirit 不再允许, 因为经验表明这种行为会导致不想要的陷阱(例如, 它不允许把规则存放在容器中). 在当前版本的 Spirit 中, 对规则的第二次赋值只会简单地重定义它. 旧的定义被销毁. 这更贴近 C++ 语义, 也更符合用户对规则行为的预期.

顺序衔接语法

像 a, b 这样的逗号运算符, 从语法上看似乎是更好的候选. 但问题在于它的优先级. 它在 C/C++ 中优先级最低, 这使它几乎无用.

Bjarne Stroustrup 在其文章 "Generalizing Overloading for C++2000" 中谈到了重载空白. 这样的特性将允许像我们在 (E)BNF 中那样把解析器对象并置(例如用 a b | c 代替 a >> b | c). 遗憾的是, 那篇文章的日期是 1998 年 4 月 1 日. 唉.

前向迭代器

一般而言, 扫描器期望至少一个符合标准的前向迭代器. 回溯需要前向迭代器, 因为迭代器位置需要被保存以便日后恢复. 总的来说, Spirit 是带回溯的解析器. 这意味着在某些时刻, 必须保存迭代器位置, 以允许解析器回溯到之前的某个点. 因此, 要使回溯工作, 框架至少需要前向迭代器.

某些解析器可能需要更特化的迭代器(双向甚至随机访问). 也许将来, 确定性解析器加入框架后, 将不执行回溯, 只需要单个记号的向前看, 因此将只需要输入迭代器.

子规则为何重要?

子规则还开启了进行激进元编程的机会, 因为它们不依赖虚函数. 虚函数是元程序员的炼狱. 它不仅因虚函数的间接调用而拖慢程序, 还是一堵不透明的墙, 任何元程序都无法越过. 它杀死了虚函数调用之外的所有元信息. 更糟的是, 虚函数不能被模板化. 这意味着它的实参必须绑定到实际类型. 许多问题都源于这一限制.

虽然 Spirit 目前被归类为非确定性递归下降解析器, Doug Gregor 最先指出, 除自顶向下递归下降之外的其他解析技术也可以应用. 例如, 除非确定性递归下降之外, 确定性的 LL(1) 与 LR(1) 理论上也可以用同一个表达式模板前端实现. Spirit 规则使用虚函数把 RHS 解析器表达式编码在一个不透明的抽象解析器类型中. 虽然它很好地实现了自己的目的, 但规则的虚函数是更高级元编程的绊脚石. 子规则没有虚函数.

穷尽回溯与贪婪 RD

Spirit 不像正则表达式那样做穷尽回溯. 例如:

    *chlit_p('a') >> chlit_p('a');

将总是无法匹配, 因为当 rule 的其余部分匹配失败时, Spirit 的 Kleene 星号不会回退.

实际上, 这个贪婪 RD 问题有一个解决方案. 这种方案在 Parsing Techniques: A Practical Guide 的 6.6.2 节中有讨论. 其技巧涉及向每个解析器传递一个 tail(尾部)解析器(除扫描器之外). 开始解析器于是简单地是: start >> end_p;(end_p 是 start 的尾部).

Spirit 是贪婪的 -- 使用直接的、朴素的递归下降 (RD). 实现上面给出的完全回溯方案当然是可能的, 但肯定会有性能损失. 该方案总是会尝试匹配所有可能的解析器路径 (完整解析器层次遍历), 直到达到确定的点: 整体匹配或不匹配.

回溯与贪婪 RD

Spirit 对于何时回溯以及回溯到何处相当一致且直观, 尽管对来自不同背景的人来说这可能不那么明显. 一般来说, 任何(子)解析器在给定相同输入时, 总是匹配输入的相同部分(或完全不匹配输入). 这意味着 Spirit 天生是贪婪的. Spirit 只在(子)解析器未能匹配输入时才回溯, 且它总是回溯到解析器结构中向上(而非向后)的下一个选择点. 换句话说, abb|ab 将匹配 "ab", a(bb|b) 也将匹配 "ab", 但 (ab|a)b 不会, 因为若 'a' 之后有 'b', (ab|a) 子解析器总是会匹配这个 'b'.

--Rainer Deyke

目前, 强烈倾向于 "简单, 需要时提供所有旋钮" 的做法. 另一方面, Spirit 的灵活性使得可以提供不同的可选方案. 将来或许可以把穷尽回溯的 RD 方案实现为可选特性.
