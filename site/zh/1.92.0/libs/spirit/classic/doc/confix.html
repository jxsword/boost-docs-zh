Confix 解析器

Confix 解析器

Confix 解析器从三个独立元素中识别出一个序列: 开头(opening), 表达式(expression)和结尾(closing). 一个简单的例子是 C 注释:

    /* This is a C comment */

它可以通过以下规则定义来解析: 

    rule<> c_comment_rule
        =   confix_p("/*", *anychar_p, "*/")
        ;

应当使用 confix_p 解析器生成器来生成所需的 Confix 解析器. confix_p 的三个参数可以是单个字符(如上), 字符串, 或者在需要更复杂解析逻辑时的辅助解析器, 每一个都会被自动转换为成功解析所需的对应解析器类型.

生成的解析器等价于以下规则:

    open >> (expr - close) >> close

若 expr 解析器是 action_parser_category 类型的解析器(挂接了语义动作的解析器), 我们就得做一些特殊处理. 当用户写出如下代码时就会发生这种情况:

    confix_p(open, expr[func], close)

其中 expr 是匹配 confix 序列 expr 部分的解析器, func 是在匹配 expr 之后要调用的函数对象. 如果我们什么都不做, 生成的代码将按如下方式解析该序列:

    open >> (expr[func] - close) >> close

这在大多数情况下并非用户所期望的.(如果这 正是你所期望的, 请使用 confix_p 生成函数的 direct(), 它会抑制解析器重构.) 为使 confix 解析器按预期行为工作:

    open >> (expr - close)[func] >> close

挂接在 expr 解析器上的 actor 必须重新挂接到 (expr - close) 解析器构造上, 这将使生成的 confix 解析器 "做正确的事". 这一重构借助 重构解析器完成. 此外, 若 expr 解析器是 unary_parser_category 类型的解析器, 还须特别小心, 如

    confix_p(open, *anychar_p, close)

若不做任何重构, 将得到

    open >> (*anychar_p - close) >> close

这不会给出预期的结果(*anychar_p 会吃掉直到输入流末尾的所有输入). 因此我们必须将其重构为: 

    open >> *(anychar_p - close) >> close

这样将给出正确的结果.

expr 解析器同时兼具上述两类问题的情况(即 expr 解析器是挂接了动作的一元解析器)也会得到相应处理, 因此:

    confix_p(open, (*anychar_p)[func], close)

将按预期被解析为:

    open >> (*(anychar_p - end))[func] >> close

这里同样借助 重构解析器实现了所需的重构.

Confix 解析器重构小结
你这样写: It is refactored to:
confix_p(open, expr, close)

open >> (expr - close) >> close
confix_p(open, expr[func], close)

open >> (expr - close)[func] >> close
confix_p(open, *expr, close)

open >> *(expr - close) >> close
confix_p(open, (*expr)[func], close)

open >> (*(expr - close))[func] >> close

注释解析器(Comment Parsers)

注释解析器生成器模板 comment_p 是一个辅助工具, 用于从辅助参数生成一个正确的 Confix 解析器, 它能够解析如下形式的注释构造:

    StartCommentToken >> Comment text >> EndCommentToken

可用作参数的类型有: 解析器, 单个字符和字符串(见 as_parser). 若只使用一个参数, 则匹配从给定的第一个解析器参数开始直到行尾的注释. 例如, 下面的解析器匹配 C++ 风格的注释:

    comment_p("//")

若使用两个参数, 则匹配从第一个解析器参数开始直到第二个解析器参数的注释. 例如, C 风格的注释解析器可以这样构造:

    comment_p("/*", "*/")

comment_p 解析器生成器允许生成匹配非嵌套注释的解析器(如 C/C++ 注释). 有时则需要解析嵌套注释, 例如 Pascal 中允许的嵌套注释.

    { This is a { nested } PASCAL-comment }

这类嵌套注释可通过 comment_nest_p 生成器模板函数子生成的解析器来解析. 下例展示了一个可用于解析两种不同(可嵌套)Pascal 注释风格的解析器:

    rule<> pascal_comment
        =   comment_nest_p("(*", "*)")
        |   comment_nest_p('{', '}')
        ;

请注意, 注释是隐式解析的, 就好像整个 comment_p(...) 语句被嵌入 lexeme_d[] 指令中一样, 即在解析注释期间不会发生任何跳词, 即便你已为整个解析过程定义了跳过解析器.

comments.cpp 演示了多种注释解析方案:

  1. 解析不同的注释风格
    • 解析 C/C++ 风格注释
    • 解析 C++ 风格注释
    • 解析 PASCAL 风格注释
  2. 借助 confix_parser 解析带标签的数据
  3. 借助 confix_parser 解析带标签的数据, 但语义
    动作直接挂接到正文序列解析器上

它是 Spirit 发行包的一部分.
