指令

解析器指令的形式为: directive[expression]

指令会修改其所包围表达式的行为, 本质上是对它的修饰. 框架预定义了若干指令. 框架的使用者可以按需自由定义自己的指令. 有关如何做到这一点的内容稍后提供. 目前, 我们只讨论预定义指令.

lexeme_d

关闭空白跳过. 在短语(phrase)层面, 解析器会忽略空白, 可能还包括注释. 当我们想在字符层面而非短语层面工作时, 请使用 lexeme_d. 通过将相关部分包围在 lexeme_d 指令内, 可以让解析器在字符层面工作. 例如, 让我们完成 引言中给出的示例. 在那里, 我们略过了 integer 规则的定义. 它的实际定义如下:

    integer = lexeme_d[ !(ch_p('+') | '-') >> +digit ];

lexeme_d 指令指示解析器在字符层面工作. 若没有它, integer 规则将允许诸如 "1 2 345" 这类输入中存在错误的内嵌空白, 而它们会被解析为 "12345".

as_lower_d

有时我们希望禁用大小写敏感性. as_lower_d 指令将输入中的所有字符转换为小写.

as_lower_d 行为

需要特别注意的是, 只有输入会被转换为小写. 包围在 as_lower_d 内、期望大写字符的解析器将解析失败. 示例: as_lower_d['X'] 永远不会成功, 因为它期望一个大写 'X', 而 as_lower_d 指令永远不会提供大写字母.

例如, 在 Pascal 中, 关键字和标识符不区分大小写. Pascal 忽略标识符和关键字中字母的大小写. 标识符 Id, ID 和 id 在 Pascal 中无法区分. 若没有 as_lower_d 指令, 定义一个能识别这一点的规则会很别扭. 下面是一种可能的做法:

    r = str_p("id") | "Id" | "iD" | "ID";

现在, 试试对不区分大小写的 Pascal 关键字 "BEGIN" 做同样的事. as_lower_d 指令使之变得简单:

    r = as_lower_d["begin"];
原语实参

敏锐的读者会注意到, 我们没有显式地把 "begin" 包裹在 str_p 中. 只要合适, 指令应当能够接受 char, int, wchar_t, char const*, wchar_t const* 等原语类型. 示例:

as_lower_d["hello"] // same as as_lower_d[str_p("hello")]
as_lower_d['x'] // same as as_lower_d[ch_p('x')]

no_actions_d

有些情况下, 你希望 语义动作不被触发. 通过将解析器包围在 no_actions_d 指令中, 直接或间接挂接到该解析器上的所有语义动作都不会触发.

    no_actions_d[expression]

调整扫描器类型

lexeme_d, as_lower_d 和 no_actions_d 是如何工作的? 这些指令通过调整扫描器策略来施展魔法. 嗯, 你现在还不需要知道这意味着什么. 扫描器策略将在 稍后讨论. 不过, 需要特别注意的是, 一旦扫描器策略被调整, 得到的就是一个不同的扫描器. 为什么这一点很重要? 规则与特定扫描器绑定(准确地说, 是一个或多个扫描器). 如果你把一条规则包裹在 lexeme_d, as_lower_d 或 no_actions_d,中, 编译器将报 扫描器不匹配错误, 除非你把所需的扫描器与该规则关联起来.

lexeme_scanner, as_lower_scanner 和 no_actions_scanner 会在你需要把规则包裹进这些指令时助你一臂之力. 请在下一章 The Scanner and Parsing 中了解这些家伙.

longest_d

Spirit 解析器编译器中的候选分支是短路求值的(见 运算符). 有时这并非所需. longest_d 指令指示解析器不要对该指令包围的候选分支短路, 而是让解析器尝试所有可能的候选分支, 并选择匹配输入流最长部分的那一个.

考虑对整数和实数的解析:

    number = real | integer;

一个数可以是实数或整数. 这个文法是有歧义的. 像 "1234" 这样的输入本应既能匹配实数也能匹配整数. 但请记住, 候选分支是短路的. 因此, 对于上述输入, 实数分支总是胜出. 然而, 如果我们交换候选分支的顺序:

    number = integer | real;

仍然有问题. 现在, 输入 "123.456" 会被 integer 匹配到小数点为止. 这不是我们想要的. 这里的解决方案是, 或者通过提取 real 和 integer 的公共前缀来消除歧义, 或者在这既不可行也不合意时, 使用 longest_d 指令:

    number = longest_d[ integer | real ];

shortest_d

与 longest_d 指令相反.

多个候选分支

longest_d 和 shortest_d 指令可以接受两个或更多候选分支. 示例:

longest[ a | b | c ];
shortest[ a | b | c | d ];

limit_d

确保解析器的结果被约束在给定的 min..max 范围内(含边界). 若不满足, 则解析器失败并返回不匹配.

用法:

    limit_d(min, max)[expression]

该指令与解析特定标量范围的解析器(例如 数值解析器)配合使用时尤为有用. 下面是一个实际例子. 尽管数值解析器可以配置为只接受有限的位数(比如 0..2), 却没有办法把结果限制到一个范围内(比如 -1.0..1.0). 这一设计是深思熟虑的结果. 若不然, 就会违背 Spirit 的设计准则 "the client should not pay for features that she does not use". 我们将不得不把 min, max 值存储在数值解析器自身中, 无论用还是不用. 嗯, 我们本可以用由非类型模板参数配置的静态常量来应付, 但那不可接受, 因为那样只能容纳整数. 那实数或用户自定义的数(如 big-int)怎么办?

示例, 解析 HH:MM:SS 形式的时间:

    uint_parser<int, 10, 2, 2> uint2_p;

    r = lexeme_d
        [
                limit_d(0u, 23u)[uint2_p] >> ':'    //  Hours 00..23
            >>  limit_d(0u, 59u)[uint2_p] >> ':'    //  Minutes 00..59
            >>  limit_d(0u, 59u)[uint2_p]           //  Seconds 00..59
        ];

min_limit_d

有时, 只解除上限的约束会很有用. 这将允许一个在单一方向上无界的区间. min_limit_d 指令确保解析器的结果不小于 minimum. 若不满足, 则解析器失败并返回不匹配.

用法:

    min_limit_d(min)[expression]

示例, 确保日期不小于 1900

    min_limit_d(1900u)[uint_p]

max_limit_d

与 min_limit_d 相反. 注意 limit_d[p] 等价于:

    min_limit_d(min)[max_limit_d(max)[p]]
