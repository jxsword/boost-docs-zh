惰性解析器

闭包很酷. 它允许我们把基于栈的局部变量注入解析下降层次的任何位置. 通常, 我们把由语义动作生成的临时变量存储在闭包变量中, 作为在递归下降中上下传递信息的手段.

现在想象一下... 鉴于闭包变量几乎可以是任何类型, 我们可以把一个解析器, 一条规则, 或者指向解析器或规则的指针存储在闭包变量中. 是啊, 然后呢?... 好, 稍安勿躁... 如果我们能用这个闭包变量发起一次解析呢? 想一秒钟. 突然我们就拥有了一些强大的动态解析器! 突然我们在 Phoenix 与 Spirit 之间有了完整的往返! Phoenix 语义动作选择正确的 Spirit 解析器, 而 Spirit 解析器选择正确的 Phoenix 语义动作. 天哪, 我得说, 这主意酷毙了!!

lazy_p

这就是 lazy_p 解析器背后的想法. lazy_p 的语法为:

    lazy_p(actor)

其中 actor 是一个返回 Spirit 解析器的 Phoenix 表达式. 该返回的解析器被用于解析过程.

示例:

    lazy_p(phoenix::val(int_p))[assign_a(result)]

挂接到 lazy_p 解析器的语义动作期望的签名与返回解析器的签名相同(在我们上面的例子中是 int_p).

lazy_p 示例

为了让你看得更清楚(见 lazy_parser.cpp), 假设你想解析如下输入:

    dec 
    {
        1 2 3
        bin 
        {
            1 10 11
        }
        4 5 6
    }

其中 bin {...} 和 dec {...} 指定我们期望读取的数值格式(二进制或十进制). 如果我们分析该输入, 我们想要一个这样的文法:

    base = "bin" | "dec";
    block = base >> '{' >> *block_line >> '}';
    block_line = number | block;

我们有意略去了 number 规则. 棘手之处在于 number 规则的行为方式取决于 base 规则的结果. 若 base 得到了 "bin", 则 number 应解析二进制数. 若 base 得到了 "dec", 则 number 应解析十进制数. 通常, 我们必须重写文法以容纳不同的解析行为:

    block = 
            "bin" >> '{' >> *bin_line >> '}'
        |   "dec" >> '{' >> *dec_line >> '}'
        ;
    bin_line = bin_p | block;
    dec_line = int_p | block;

虽然这样可以, 但冗余使我们想寻找更好的解决方案; 毕竟, 我们希望充分利用 Spirit 的动态解析能力. 除此之外, 还会有这样的情况: 编写文法时, number 规则的解析行为集合尚不可知. 我们只会拿到一个由字符串描述符与对应规则组成的映射 [例如 (("dec", int_p), ("bin", bin_p) ... 等等...)].

基本思路是为二进制数和十进制数各设一条规则. 这很容易做到(见 numerics). 当解析 base 时, 在你的语义动作中, 把指向所选基的指针存入一个闭包变量(如 block.int_rule). 下面是一个示例:

    base 
        = str_p("bin")[block.int_rule = &var(bin_rule)] 
        | str_p("dec")[block.int_rule = &var(dec_rule)]
        ;

有了这种设置, 你的 number 规则看起来会像这样:

    number = lazy_p(*block.int_rule);

lazy_parser.cpp 的做法稍有不同, 巧妙地使用 符号表来分派正确的规则, 但本质上两种策略是相似的. 这种使用符号表的技术在 Techniques 一节中有详述: nabialek_trick. 诚然, 把所有规则加起来, 得到的文法比上面硬编码的文法更复杂. 然而, 对于带有更多待选规则的更复杂文法模式, 额外的设置是非常值得的.
