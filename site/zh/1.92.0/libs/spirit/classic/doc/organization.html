Spirit 有四层, 外加一个独立的顶层. 这个独立的层由 actor 与 iterator 组成, 不依赖其他层. 框架的架构是完全正交的. 各层之间的关系是无环的. 低层不依赖也不知道高层的存在. 同一层中的模块不依赖同层中的其他模块.

使用者可以只使用她想要的模块, 而不产生任何编译期或运行期开销. 一种极简方案是按原样只使用核心. 高度精简的核心本身即可使用. 对于微解析之类的任务, 核心已经完全足够.

iterator 模块独立于 Spirit, 可用于其他非 Spirit 应用程序. 该模块汇集了与 Spirit 兼容的独立迭代器和迭代器封装. 随着时间推移, 人们发现这些迭代器对使用 Spirit 进行解析最为有用.

actor 模块同样独立于 Spirit, 它汇集了预定义的语义动作, 覆盖最常见的语义处理任务.

debug 模块提供库范围的解析器调试. 该模块以非侵入方式, 仅在必要时把自身透明地挂接进核心.

attribute 模块引入了先进的语义动作机制, 重点是通过继承属性与综合属性在解析器层次中向上和向下提取与传递数据. 属性还可以实际用于控制解析. 参数化解析器是动态解析器的一种形式, 它在运行期根据某些属性或数据改变自身行为.

dynamic 模块聚焦于行为可在运行期修改的解析器.

error_handling. 没有错误处理的框架是不完整的. C++ 的异常处理机制与 Spirit 是天作之合, 因为 Spirit 具有高度递归的函数式特性. C++ 异常被该模块广泛用于处理错误.

symbols模块聚焦于符号表管理. 该模块目前还相当基础. 其目标是构建一个能够容纳 C++ 风格多作用域机制的子框架. C++ 是作用域复杂性的绝佳模型, 也许没有任何其他语言能与之相比. 其中有类与继承, private, protected 和 public 访问限制, 友元, 命名空间, using 声明, using 指令, Koenig 查找(实参依赖查找)等等. 我们现在拥有的符号表功能, 将成为尝试对这一切建模的完整设施的基础.

I wish that I could ever see, a structure as lovely as a tree...

解析树与抽象语法树(AST)的生成由 Tree 模块处理. 相比语义动作, 解析树和抽象语法树有其优势. 你可以对数据做多遍处理而不必重新解析输入. 你可以对树执行变换. 你可以按任意想要的顺序求值, 而属性方案则必须从头到尾处理. 你不必担心歧义文法中可能出现的回溯与动作副作用.

utility 模块是一组常见且有用的解析器与支持类, 人们发现它们在处理列表处理, 注释, confix 表达式等常见任务时很有用.

meta, 为高级 Spirit 开发者提供元编程设施. 该模块便利了对 Spirit 解析器的编译期与运行期内省.
