扫描器问题

问: 为什么这段代码无法编译?

    rule<> r = /*...*/;
    parse("hello world", r, space_p); // BAD [attempts phrase level parsing]

但如果我 移除跳过解析器, 一切又恢复正常:

    rule<> r = *anychar_p;
    parse("hello world", r); // OK [character level parsing]

有时你会想把一个规则传给 Spirit 提供的某个 parse 函数. 问题在于规则是一个以扫描器类型为参数的模板类. 这虽然别扭但不可避免: 规则与扫描器绑定. 不太明显的是, 该扫描器必须与最终传给规则的 parse 成员函数的扫描器兼容. 否则, 编译器会抱怨.

为什么第一次调用 parse 无法编译? 因为扫描器不兼容. 在幕后, 自由 parse 函数根据传入的迭代器创建扫描器. 在第一次 parse 调用中, 创建的扫描器是普通原味的 scanner<>. 它与 rule<> 的默认扫描器类型兼容 [参见 规则 的默认模板参数]. 第二次调用创建的是 phrase_scanner_t 类型的扫描器. 因此, 要让第二次调用成功, 规则必须参数化为 rule<phrase_scanner_t>:

    rule<phrase_scanner_t> r = *anychar_p;
    parse("hello world", r, space_p);       //  OK [phrase level parsing]

但请注意: 只有当你使用 char const* 迭代器且以 space_p 作为跳过解析器时, phrase_scanner_t 才是兼容的. 其他情况下, 你必须自己找到正确的扫描器类型, 而要做对相当繁琐. 有鉴于此, 最好避免把规则作为 parse 函数的实参. 请记住, 这一问题只发生在规则上. 规则是唯一必须绑定到特定扫描器类型的解析器. 例如:

    parse("hello world", *anychar_p);           //  OK  [character level parsing]
    parse("hello world", *anychar_p, space_p);  //  OK  [phrase level parsing]

从 v1.8.0 起, 规则可以使用一个或多个扫描器类型. 例如, 有些情况下我们需要一个既能在短语层又能在字符层工作的规则. 规则/扫描器不匹配一直是困惑之源, 也是头号的 FAQ. 为解决这一问题, 我们现在有了 多扫描器支持.

消除左递归

问: 我从 YACC 移植了一个文法. 它 "勉强" 能工作 - 解析器本身编译无错误. 但当我尝试解析时, 它给我一个 "无效页故障". 我把问题定位到了这段文法片段:

    or_expr = xor_expr | (or_expr >> VBAR >> xor_expr);

你应当做的是消除直接与间接左递归. 之所以会出现无效页故障, 是因为程序进入了无限循环. 上面的代码适用于 YACC 这类自底向上的解析器, 但不适用于 Spirit 这类 LL 解析器.

这类似于 Hartmut Kaiser 的 C 解析器中的一条规则 (读到本文时, 它应该可以从 Spirit 网站 下载).

    inclusive_or_expression
    = exclusive_or_expression
    | inclusive_or_expression >> OR >> exclusive_or_expression
    ;

把左递归转换为右递归, 可得:

    inclusive_or_expression
    = exclusive_or_expression >> inclusive_or_expression_helper
    ;

    inclusive_or_expression_helper
    = OR >> exclusive_or_expression >> inclusive_or_expression_helper
    | epsilon_p
    ;

我想更进一步. 既然:

    r = a | epsilon_p;

等价于:

    r = !a;

我们可以这样简化 inclusive_or_expression_helper:

    inclusive_or_expression_helper
    = !(OR >> exclusive_or_expression >> inclusive_or_expression_helper)
    ;

现在, 既然:

    r = !(a >> r);

等价于:

    r = *a;

可得:

    inclusive_or_expression_helper
    = *(OR >> exclusive_or_expression)
    ;

现在完全简化 inclusive_or_expression, 可得:

    inclusive_or_expression
    = exclusive_or_expression >> *(OR >> exclusive_or_expression)
    ;

这让我想起了那些计算器. 简而言之:

    a = b | a >> op >> b;

在 伪 YACC 中:

    a = b >> *(op >> b);

在 Spirit 中. 还能更简单吗? 看哪, 没有递归, 只有迭代.

实现右结合

问: 我尝试把 '^' 作为计算幂的运算符加入一个计算器文法. 以下代码

    pow_expression 
    = pow_operand >> *( '^' >> pow_operand [ & do_pow ]
                      )
    ;

可以正确解析输入, 但我希望该运算符从右向左求值. 换句话说, 表达式 2^3^4 应当与 2^(3^4) 具有相同的语义, 而不是 (2^3)^4. 该怎么做?

右结合的 "教科书配方" 是右递归. 用 BNF 表示即: 

    <pow_expression> ::=  <pow_operand> '^' <pow_expression> | <pow_operand>

但这里最好不要把理论太当真, 因为如果第一个候选分支失败, pow_operand 内的语义动作可能已经执行过, 并且在尝试第二个候选分支时会再次执行. 所以让我们应用左因子提取来把 pow_operand 因子化: 

    <pow_expression> ::=  <pow_operand> <pow_expression_helper>
    <pow_expression_helper> ::= '^' <pow_expression> | ε

产生式 pow_expression_helper 匹配空串 ε, 因此在 Spirit 代码中我们可以用可选运算符替换该候选分支.

    pow_expression 
    = pow_operand >> !( '^' >> pow_expression [ & do_pow ]
                      )
    ;

现在 pow_operand 内的任何语义动作都可以安全执行. 对于基于栈的求值, 这意味着 pow_operand 的每次匹配都会在栈上留下一个值, 而递归确保当 do_pow 触发以把这两个值归约为它们的幂时, 栈上已有 (至少) 两个值.

在这种技术不适用的情况下, 例如 C 风格赋值 

    assignment
    = lvalue >> '=' >> assignment 
    | ternary_conditional 
    ;

你可以向解析器追加 | epsilon_p [ action ] >> nothing_p, 以便在发生回溯时修正语义上下文 (在示例情形中, 即把 lvalue 压入求值栈的地址弹出):

    assignment
    = lvalue >> ( '=' >> assignment    [ & do_store ]
                | epsilon_p            [ & do_drop  ]
                  >> nothing_p
                ) 
    | ternary_conditional 
    ;

然而, 这一技巧损害了语法与语义的清晰分离, 因此你也可以考虑改用 AST 而不是语义动作, 这样你就可以直接使用 assignment 的第一个定义.

lexeme_d 指令与规则

问: lexeme_d 不支持包含规则的表达式吗? 在下面的示例中, atomicRule 的定义可以编译,

    rule<phrase_scanner_t> atomicRule
        = lexeme_d[(alpha_p | '_') >> *(alnum_p | '.' | '-' | '_')];

但如果我把 alnum_p | '.' | '-' | '_' 移到它自己的规则中, 编译器会抱怨从 const scanner<...> 到 const phrase_scaner_t& 的转换.

    rule<phrase_scanner_t> ch 
        = alnum_p | '.' | '-' | '_';

    rule<phrase_scanner_t> compositeRule
        = lexeme_d[(alpha_p | '_') >> *(ch)]; // <- error source

你可能会觉得 lexeme_d 指令与规则不能混用. 实际上, 这个问题与第一个 FAQ 条目相关: 扫描器问题. 更准确地说, 是 lexeme_d 指令与具有不兼容扫描器类型的规则不能混用. 这个问题更加隐蔽. 造成扫描器不兼容的是指令本身. lexeme_d 指令把它收到的扫描器变换为禁用跳过解析器的东西. 遗憾的是, 这种非跳过扫描器与变换发生前的原始扫描器不兼容.

最简单的解决方案是不要在 lexeme_d 中使用规则. 不过, 如果你确实需要在 lexeme_d 内使用更复杂的解析器, 完全可以把 lexeme_d 应用于子规则 (subrules) 和文法. 如果确实必须使用规则, 你需要知道该指令使用的确切扫描器. lexeme_scanner 元函数在此可以帮到你. 只要给 ch 规则一个正确的扫描器类型, 上面的示例就会按预期工作:

    rule<lexeme_scanner<phrase_scanner_t>::type> ch 
        = alnum_p | '.' | '-' | '_';

注: 当在模板类或模板函数内部使用时, 请确保在 lexeme_scanner 前加上 "typename".

在 as_lower_d 指令内部使用规则时也会发生同样的事情. 此时你可以使用 as_lower_scanner. 参见 lexeme_scanner 与 as_lower_scanner.

请参见技巧一节中的一个 示例 : 一个 文法 - 使用了 启用多扫描器的规则, lexeme_scanner 与 as_lower_scanner.

Kleene 星号无限循环

问: 为什么它永远循环?

    rule<> optional = !(str_p("optional"));
    rule<> list_of_optional = *optional;

问题在于 kleene 星号会一直循环, 直到它所包裹的解析器返回不匹配. 由于 optional 规则是可选的, 它总会返回匹配. 即使输入不匹配 "optional", 它也会返回零长度匹配. list_of_optional 会永远调用 optional, 因为 optional 永远不会返回不匹配. 所以一般来说, 任何可能 "可空" (nullable, 即可以返回零长度匹配) 的规则都不得放入 kleene 星号内.

Boost CVS 与 Spirit CVS

问: 存在 Boost CVS 与 Spirit CVS. Spirit 的后续开发使用哪一个?

一般来说, 开发在 Spirit 的 CVS 中进行. 但不时会有新版本的 Spirit 集成到 Boost 中. 此时开发便在 Boost CVS 中进行. Spirit CVS 的状态每次变化都会在 Spirit 邮件列表上公告.

在开发 Spirit v1.8.1 (作为 boost-1.32.0 的一部分发布) 与 v1.6.2 期间, Spirit 的开发者决定停止维护 BRANCH_1_8 与 BRANCH_1_6 的 Spirit CVS. 这是为了减少维护和同步两个仓库的额外工作. 这些分支的维护将在 Boost CVS 上进行. 此时, 面向 Spirit v2 的新开发及其他实验性开发预计将在 Spirit CVS 中进行.

如何用复杂的 Spirit 文法减少编译时间

问: 有没有使用 spirit 时尽量缩短编译时间的技巧? 对于简单解析器, 编译时间似乎不是大问题, 但最近我创建了一个约有 78 条规则的解析器, 编译花了大约 2 小时. 我想把文法拆成更小的块, 但这不像我想的那么容易, 因为两个文法胶囊 (grammar capsules) 中的规则是相互定义的. 有什么想法吗?

缩短编译时间的唯一办法是

  • 把文法拆分成更小的块
  • 防止编译器同时看到所有文法定义 (在同一个编译单元中)

第一个任务是纯事务性的, 第二个则偏技术性.

JCAB 编写的 Spirit cpp_lexer 示例给出了解决第一个任务的好例子 (你可以在 应用程序仓库 找到它).

交叉引用问题可以通过某种前向声明解决; 如果行不通, 可以向非模板文法引入某个哑模板实参. 这样可以把实例化时机推迟到编译器看到全部定义之后:

    template <typename T = int>
    grammar2;


    template <typename T = int>
    struct grammar1 : public grammar<grammar1>
    {
    // refers to grammar2<>
    };

    template <typename T>
    struct grammar2 : public grammar<grammar2>
    {
    // refers to grammar1<>
    };

    //...
    grammar1<> g; // both grammars instantiated here

第二个任务稍微复杂一些. 你必须确保在第一个编译单元中编译器只看到某些函数/模板 声明, 而在第二个编译单元中看到函数/模板的 定义. 如果不涉及模板, 这仍然没有问题. 若涉及模板, 你需要在一个单独的编译单元内用正确的模板参数手动 (显式) 实例化这些模板. 这样编译时间被分摊到多个编译单元, 从而也大幅减少所需的总体时间.

有关展示如何做到这一点的示例, 你可以看看 Wave 预处理器库, 该技术在那里被广泛使用. (读到本文时, 它应该可以从 Spirit 网站 下载).

闭包帧断言

问: 运行解析器时我得到断言 "frame.get() != 0 in file closures.hpp". 我做错了什么?

基本上, 当你访问一个尚未构造的闭包变量时就会触发该断言. 举个例子. 我们有三条规则 a、b 和 c. 设规则 a 有一个闭包成员 m. 现在:

    a = b;
    b = int_p[a.m = 123];
    c = b;

当规则 a 被调用时, 它的帧连同其成员 m 一同被设置. 因此, 当从 a 调用 b 时, 语义动作 [a.m = 123] 会把 123 存入 a 的闭包成员 m. 另一方面, 当 c 被调用且 c 尝试调用 b 时, a 的帧未被设置. 于是, 当从 c 调用 b 时, 语义动作 [a.m = 123] 会触发 "frame.get() != 0 in file closures.hpp" 断言.

贪婪 RD

问: 我想知道为什么下面这段代码解析时不工作:

    a = +anychar_p;
    b = '(' >> a >> ')';

试试这个:

    a = +(anychar_p - ')');
    b = '(' >> a >> ')';

David Held 写道: 这是因为它像 langoliers 一样 - 会吃掉一切. 你通常需要通过从解析器中减去终止字符来说明它不应吃掉什么. 寓意是: 单独使用 *anychar_p 或 +anychar_p 通常是一件 坏事™.

换句话说: 递归下降天生是贪婪的 (不过参见 穷尽回溯与贪婪 RD).

在构造时引用规则

问: 下面的代码以段错误 (segmentation fault) 终止, 但我 (显然) 对自己错在哪里感到困惑.

    rule<ScannerT, clos::context_t> id = int_p[id.i = arg1];

你有一条正在被构造的规则 id. 在它构造完成之前, 你在构造函数的右侧引用了 id.i. 这是先有鸡还是先有蛋的问题. 闭包成员 id.i 在那时还未构造. 使用赋值将解决该问题. 试试这样:

    rule<ScannerT, clos::context_t> id;
    id = int_p[id.i = arg1];

存储规则

问: 为什么我不能把规则存入 STL 容器以备后用, 为什么不能按值把规则传入函数或从函数返回?

EBNF 本质上是声明式的. 与函数式编程一样, 它是一份静态配方, 没有 "先做这个再做那个" 的概念. 然而, 在 Spirit 中, 我们成功地说服了命令式 C++ 接受声明式 EBNF. 哈! 有趣!... 我们做到这一点的方式之一是伪装 C++ 赋值运算符来模仿 EBNF 的 ::= (还有 >>、|、& 等). 我们通过赋予 rule 类的赋值运算符 (和拷贝构造函数) 不同的含义与语义来实现这一点. 这样做使得 rule 类与任何其他 C++ 对象都不同. 你不能复制它. 不能对它赋值. 不能把它放入容器 (vector、stack 等). 见鬼, 你甚至不能 *按值* 从函数返回它.

rule 是一个怪异的对象, 与任何其他 C++ 对象都不同. 它不具备适当的拷贝与赋值语义, 不能按值存储和传递.

无论声明式 EBNF 多么优雅, C++ 的动态特性都可能成为优势. 我们已经在各处看到它的实际应用. 使用 Spirit 的动态解析器确实有一些有趣的应用. 然而, 除非 (!) 我们拥有一个不那么 "异类" 的规则 (即表现为一个良好的 C++ 对象), 否则我们尚未充分利用动态解析的能力. 有了这样的东西, 我们就可以编写在运行期 (而非编译期) 定义的解析器.

既然我开始专注于规则了 (嘿, 看看那些漂亮的新规则特性), 现在也许是实现规则持有者 (rule-holder) 的好时机. 它基本上就是一个规则, 但具有 C++ 对象语义. 然而它并不那么简单. 没有真正的垃圾回收, 实现会有点棘手. 我们不能简单地使用引用计数, 因为规则持有者 (嘿, 有人有更好的名字吗?) *是一种* 规则, 而规则通常是递归的, 因而是循环的. 问题在于谁拥有谁.

好吧... 目前就先到这里. 接下来几天你肯定会看到更多关于规则持有者的内容.

解析整数与实数

问: 我尝试用 longest_d 指令解析 int 或 float 值, 并在各个候选分支上放置一些动作以显示结果. 当我解析 "123.456" 时, 输出报告:

  1. (int) 已匹配: full match = false
  2. (double) 已匹配: full match = true

这不是我所期望的. 我遗漏了什么?

实际上, 问题在于 int 分支与 real 分支的语义动作都会被触发, 因为两个分支都会被尝试. 这没有带来多少好处. 最终胜出的其实是你所期望的那个. 但没有简便方法知道哪个胜出. 问题源于歧义.

情形 1: 考虑输入 "2". 它是 int 还是 real? 两者都是 (严格按 real 的文法).

情形 2: 那么 "1.0" 呢? 它是 int 还是 real? 两者都是, 尽管 int 部分只得到部分匹配: "1". 这就是为什么你的 int 规则得到一个 (部分) 匹配 (full match = false).

与其使用 longest_d 来解析整数和实数, 我的建议是消除歧义并使用普通的短路候选分支. 第一步是使用 strict_real_p 使第一种情形无歧义. 与 real_p 不同, strict_real_p 要求必须存在小数点, 数字才算成功匹配. 你的文法可以无歧义地写作:

    strict_real_p | int_p

注意: 由于歧义已消除, 在两个分支上都附加动作是安全的. 只有一个会被触发:

    strict_real_p[R] | int_p[I]

"1.0" ---> 触发 R
"2" ---> 触发 I

再次强调, 根据经验, 最好尽可能消除歧义. 最好的文法是完全不需要回溯的文法: LL(1) 文法. 回溯与语义动作并不合拍.

BOOST_SPIRIT_DEBUG 与缺失的 operator<<

问: 我的代码在发布模式下编译良好, 但当我尝试定义 BOOST_SPIRIT_DEBUG 时, 编译器抱怨缺少 operator<<.

定义 BOOST_SPIRIT_DEBUG 后, 会为 spirit 解析器生成调试输出. 为此, 期望每个闭包成员都定义了默认的输出运算符.

你可以把运算符重载提供在声明该类的命名空间中 (会通过实参依赖查找找到), 或者让它在被使用处可见, 即 namespace boost::spirit. 下面是 std::pair 的一个示例:


    #include <iosfwd>
    #include <utility>

    namespace std {

        template <
            typename C,
            typename E,
            typename T1,
            typename T2
        >
        basic_ostream<C, E> & operator<<(
            basic_ostream<C, E> & out,
            pair<T1, T2> const & what)
        {
            return out << '(' << what.first << ", "
                << what.second << ')';
        }

    }
