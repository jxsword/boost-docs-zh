调试

Spirit 自顶向下的特性使得可以使用我们所用 C++ 编译器自带的标准调试器对生成的解析器进行微观调试. 采用递归下降时, 解析遍历通过 C++ 函数调用机制利用硬件栈. 不存在难以调试、会遮蔽解析逻辑流程的表或状态机. 我们在调试器中看到的栈跟踪忠实于层次化的文法结构.

由于任何产生式规则都可以发起一次解析遍历, 通过聚焦于一条或少数几条规则来定位缺陷要容易得多. 对于相对复杂的解析任务, 与编写健壮的 C++ 程序一样, 建议以每个模块一个子集的方式迭代地开发文法, 其中每个模块是完整文法的一个小子集. 这样, 我们可以逐块地对各个模块进行压力测试, 直至抵达最顶层模块. 例如, 在开发一门脚本语言时, 可以从表达式开始, 然后转向语句, 再到函数, 逐层向上直至获得完整文法.

当文法变得相当复杂时, 就希望将解析遍历可视化, 观察正在发生的事情. 框架中提供了一些设施, 可用于将解析遍历可视化以辅助调试. 以下宏可启用这些特性.

调试宏

BOOST_SPIRIT_ASSERT_EXCEPTION

Spirit 包含一些断言, 当 Spirit 被不正确使用时它们可能被激活. 默认情况下, 这些断言使用标准库的 assert 宏. 如果你希望 Spirit 改为抛出异常, 请将 BOOST_SPIRIT_ASSERT_EXCEPTION 定义为你希望抛出的类的名称. 抛出时, 该类的构造函数会接收一个 const char* 形式的文件, 行号与断言条件的字符串化版本. 如果要完全禁用断言, 请 #define NDEBUG.

BOOST_SPIRIT_DEBUG

定义此宏以启用调试.

启用调试后, 会在解析过程的关键节点生成特殊输出, 使用标准输出运算符(operator<<), 以 BOOST_SPIRIT_DEBUG_OUT(默认为 std::cout, 见下文)作为其左操作数.

要使用 Spirit 的调试支持, 必须确保存在 operator<< 的相应重载, 且以 BOOST_SPIRIT_DEBUG_OUT 为左操作数, 其预期语义与标准输出运算符相同.

这些重载既可以提供在声明相应类的命名空间内(可通过实参依赖查找找到), 也可以[在匿名命名空间内]提供于 namespace boost::spirit 中, 使其在调用处可见.

特别要注意, 当设置了 BOOST_SPIRIT_DEBUG_FLAGS_CLOSURES 时, 还需要有 operator<< 的重载, 其以闭包中使用的类型实例为右操作数.

为 std::pair 重载输出运算符的示例可参见 相关 FAQ 条目.

默认情况下, 若定义了 BOOST_SPIRIT_DEBUG 宏, 将生成所有可用的调试输出. 要微调生成文本的数量, 可以将 BOOST_SPIRIT_DEBUG_FLAGS 常量定义为以下标志的组合:

可用于微调调试输出的标志
BOOST_SPIRIT_DEBUG_FLAGS_NODES

打印关于节点的信息(适用于所有解析器)
BOOST_SPIRIT_DEBUG_FLAGS_TREES

打印关于解析树与 AST 的信息(适用于所有树解析器)
BOOST_SPIRIT_DEBUG_FLAGS_CLOSURES 打印关于闭包的信息(适用于所有带闭包的解析器)
BOOST_SPIRIT_DEBUG_FLAGS_ESCAPE_CHAR

打印 esc_char_parser
BOOST_SPIRIT_DEBUG_FLAGS_SLEX 输出 SLEX 解析器的信息

BOOST_SPIRIT_DEBUG_OUT

定义此宏可将调试诊断输出重定向到其他地方(如文件或流). 默认为 std::cout.

BOOST_SPIRIT_DEBUG_TOKEN_PRINTER

BOOST_SPIRIT_DEBUG_TOKEN_PRINTER 宏允许你重新定义字符打印到流上的方式.

若 BOOST_SPIRIT_DEBUG_OUT 的类型为 StreamT, 字符类型为 CharT, 且 BOOST_SPIRIT_DEBUG_TOKEN_PRINTER 被定义为 foo, 则它必须与以下用法兼容:

    foo(StreamT, CharT)

默认的打印器要求定义 operator<<(StreamT, CharT). 此外, 若 CharT 可转换为普通字符类型(char, wchar_t 或 int), 它会以友好的方式打印控制字符(例如, 当它收到 '\n' 时, 实际打印 \ 和 n 两个字符, 而非换行).

BOOST_SPIRIT_DEBUG_PRINT_SOME

BOOST_SPIRIT_DEBUG_PRINT_SOME 常量定义了为诊断而从流中打印的字符数. 默认为前 20 个字符.

BOOST_SPIRIT_DEBUG_TRACENODE

默认跟踪所有解析器节点. 此常量可用于重定义这一默认行为. 若其为 1(true), 则默认启用跟踪; 若为 0(false), 则默认禁用跟踪. 该预处理器常量默认设为 1 (true).

请注意, 以下 BOOST_SPIRIT_DEBUG_...() 宏只能在函数作用域内使用.

BOOST_SPIRIT_DEBUG_NODE(p)

定义此宏可为解析器 p 打印一些调试诊断信息. 此宏

  • 注册解析器名称以供调试
  • 是否启用/禁用对解析器的跟踪取决于 BOOST_SPIRIT_DEBUG_TRACENODE

解析前: 在进入规则之前, 打印规则名, 后跟对当前迭代器位置数据的预览.

解析后: 在解析规则之后, 打印规则名, 后跟对当前迭代器位置数据的预览. 此处, 规则名前的 '/' 表示匹配成功, 而 '#' 表示匹配失败.

以下各项同义于 BOOST_SPIRIT_DEBUG_NODE

  1. BOOST_SPIRIT_DEBUG_RULE
  2. BOOST_SPIRIT_DEBUG_GRAMMAR

BOOST_SPIRIT_DEBUG_TRACE_NODE(p, flag)

与 BOOST_SPIRIT_DEBUG_NODE 类似. 另外允许选择性调试. 这在我们只想调试精选的一组节点时非常有用.

以下各项同义于 BOOST_SPIRIT_DEBUG_TRACE_NODE

  1. BOOST_SPIRIT_DEBUG_TRACE_RULE
  2. BOOST_SPIRIT_DEBUG_TRACE_GRAMMAR

BOOST_SPIRIT_DEBUG_TRACE_NODE_NAME(p, name, flag)

与 BOOST_SPIRIT_DEBUG_NODE 类似. 另外允许选择性调试, 并允许指定调试打印时使用的名称. 这在我们只想调试精选的一组节点时非常有用. 当解析器实参不能体现待调试解析器的名称时, 可以重定义 name.

以下各项同义于 BOOST_SPIRIT_DEBUG_TRACE_NODE

  1. BOOST_SPIRIT_DEBUG_TRACE_RULE_NAME
  2. BOOST_SPIRIT_DEBUG_TRACE_GRAMMAR_NAME

下面是启用了调试特性的原始计算器:

    #define BOOST_SPIRIT_DEBUG  ///$$$ DEFINE THIS BEFORE ANYTHING ELSE $$$///
    #include "boost/spirit/include/classic.hpp"

    /***/

    /*** CALCULATOR GRAMMAR DEFINITIONS HERE ***/

    BOOST_SPIRIT_DEBUG_RULE(integer);
    BOOST_SPIRIT_DEBUG_RULE(group);
    BOOST_SPIRIT_DEBUG_RULE(factor);
    BOOST_SPIRIT_DEBUG_RULE(term);
    BOOST_SPIRIT_DEBUG_RULE(expr);

务必要把宏添加到文法定义构造函数的内部. 下面是与该计算器的一次示例会话.

    Type an expression...or [q or Q] to quit

    1 + 2

    grammar(calc):	"1 + 2"
      rule(expression):	"1 + 2"
        rule(term):	"1 + 2"
          rule(factor):	"1 + 2"
            rule(integer):	"1 + 2"
    push	1
            /rule(integer):	" + 2"
          /rule(factor):	" + 2"
        /rule(term):	" + 2"
        rule(term):	"2"
          rule(factor):	"2"
            rule(integer):	"2"
    push	2
            /rule(integer):	""
          /rule(factor):	""
        /rule(term):	""
    popped 1 and 2 from the stack. pushing 3 onto the stack.
      /rule(expression):	""
    /grammar(calc):	""
    -------------------------
    Parsing succeeded
    result = 3
    -------------------------

我们输入了 "1 + 2". 注意, 从顶层规则 expr 有两个成功的分支. 红色文本由解析器的语义动作生成, 其余文本由规则的调试诊断生成. 注意第一条 integer 规则取走了 "1", 第一条 term 规则取走了 "+", 最后第二条 integer 规则取走了 "2".

请注意打印行首字符的特殊含义:

  • 单个 '/' 开头的行包含关于成功匹配的解析器节点(rule<>, grammar<> 或 subrule<>)的信息
  • 单个 '#' 开头的行包含关于匹配失败的解析器节点的信息
  • 单个 '^' 开头的行包含成功匹配的解析器节点闭包的第一个成员(返回值/综合属性).
