multi_pass


Spirit 中的回溯要求使用以下类型的迭代器: 前向, 双向或随机访问. 由于回溯的存在, 输入迭代器无法使用. 因此, 属于输入迭代器类别的标准库类 istreambuf_iterator 和 istream_iterator 无法使用. 另一个值得关注的输入迭代器是包装词法分析器的迭代器, 例如 LEX.

输入迭代器

一般而言, Spirit 是带回溯的解析器. 但这并非绝对要求. 将来我们会看到更多只需要 1 个字符(记号)向前看的确定性解析器. 这样的解析器使我们能够原样使用 istream_iterator 这样的输入迭代器.

遗憾的是, 对于输入迭代器, 无法保存迭代器位置, 因此输入迭代器无法与 Spirit 中的回溯配合工作. 该问题的一种解决方案是把所有要解析的数据简单地装载到一个容器(如 vector 或 deque)中, 然后把容器的 begin 和 end 传给 Spirit. 这种方法对某些应用程序来说可能过于消耗内存, 这正是创建 multi_pass 迭代器的原因.

multi_pass 迭代器会把任何输入迭代器转换为适合与 Spirit 一起使用的前向迭代器. multi_pass 会在需要时缓冲数据, 并且当迭代器只存在一份拷贝时丢弃缓冲.

若使用 multi_pass 迭代器, 文法必须经过精心设计. 任何可能需要回溯的规则, 例如包含候选分支的规则, 都会导致数据被缓冲. 最适合使用的规则是顺序与重复. 形如 a >> b 的序列完全不缓冲数据. 任何重复的规则, 如 kleene_star(*a)或正闭包(+a), 只会为当前这一次重复缓冲数据.

在典型的文法中, 歧义及因此产生的向前看往往是局部的. 事实上, 许多设计良好的语言是完全确定的, 完全不需要向前看. 从输入中预看第一个字符即可立即确定应走的候选分支. 而且, 即使在歧义度很高的文法中, 候选分支通常也形如 *(a | b | c | d). 输入迭代器不断前进, 绝不会卡在开头. 举例来看一个 Pascal 片段:

    program =
        programHeading >> block >> '.'
        ;

    block =
       *(    labelDeclarationPart
        |    constantDefinitionPart
        |    typeDefinitionPart
        |    variableDeclarationPart
        |    procedureAndFunctionDeclarationPart
        )
        >>   statementPart
        ;

注意 rule block 中 Kleene 星号内部的备选项. 该 rule 以线性方式吞掉输入, 并在每次迭代时丢弃过去的历史. 由于这是完全确定性的 LL(1) 文法, 每个失败的备选项只需查看 1 个字符 (记号). 消耗超过 1 个字符 (记号) 的备选项肯定是成功者. 之后, Kleene 星号继续下一个.

使用自由 parse 函数时要留心. 所有这些函数都会对其接收的迭代器做一份拷贝.

现在, 在听完关于使用 multi_pass 时须小心之处的讲座之后, 你可能会认为 multi_pass 用起来限制太多了. 情况并非如此. 如果你的文法是确定性的, 你可以在文法中使用 flush_multi_pass 来确保不会缓冲不必要的数据.

接着我们在扫描器一节中开始使用的例子. 下面是一个使用 multi_pass 的示例: 这一次我们使用 istreambuf_iterator 从输入流中提取输入.

    #include <boost/spirit/core.hpp>    
    #include <boost/spirit/iterator/multi_pass.hpp>

    using namespace boost::spirit;
    using namespace std;
    
    ifstream in("input_file.txt"); // we get our input from this file

    typedef char char_type;
    typedef multi_pass<istreambuf_iterator<char_type> > iterator_type;

    typedef skip_parser_iteration_policy<space_parser> iter_policy_type;
    typedef scanner_policies<iter_policy_type> scanner_policies_type;
    typedef scanner<iterator_type, scanner_policies_type> scanner_type;

    typedef rule<scanner_type> rule_type;

    iter_policy_type iter_policy(space_p);
    scanner_policies_type policies(iter_policy);
    iterator_type first(
        make_multi_pass(std::istreambuf_iterator<char_type>(in)));

    scanner_type scan(
        first, make_multi_pass(std::istreambuf_iterator<char_type>()),
        policies);

    rule_type   n_list = real_p >> *(',' >> real_p);
    match<>     m = n_list.parse(scan);

flush_multi_pass

有一个预定义的伪解析器叫做 flush_multi_pass. 当该解析器与 multi_pass 一起使用时, 它会调用 multi_pass::clear_queue(). 这将导致所有被缓冲的数据被擦除. 这也会使 multi_pass 的所有其他拷贝失效, 它们不应再被使用. 若使用了它们, 将抛出 boost::illegal_backtracking 异常.

multi_pass 策略

multi_pass 是一个以策略驱动的模板类. 上文对 multi_pass 的描述是它最初的实现方式(在使用策略之前), 也是现在的默认配置. 但是, multi_pass 的能力远不止于此. 由于策略的开放性, 你可以编写自己的策略, 让 multi_pass 表现出我们以前从未设想过的行为.

multi_pass 类有五个模板参数:

  • InputT —— multi_pass 用于获取输入的类型. 它通常是一个输入迭代器或函数对象.
  • InputPolicy —— 定义 multi_pass 如何获取输入的类. InputPolicy 以 InputT 为参数.
  • OwnershipPolicy —— 该策略决定 multi_pass 如何处理其共享组件.
  • CheckingPolicy —— 该策略决定如何检查无效迭代器.
  • StoragePolicy —— multi_pass 使用的缓冲方案由 StoragePolicy 决定和管理.

预定义策略

所有预定义的 multi_pass 策略都位于命名空间 boost::spirit::multi_pass_policies 中.

预定义 InputPolicy 类

input_iterator

该策略指示 multi_pass 从 InputT 类型的输入迭代器读取.

lex_input

该策略通过调用 yylex() 获取输入, yylex() 通常由 LEX 生成的扫描器提供. 若使用该策略, 你的代码必须与 LEX 生成的扫描器链接.

functor_input

该输入策略通过调用 InputT 类型的函数对象获取数据. 该函数对象必须满足特定要求. 它必须有一个名为 result_type 的 typedef, 应当是 operator() 的返回类型. 此外, 由于输入策略需要一种确定输入是否已到达末尾的方法, 该函数对象必须包含一个名为 eof 的静态变量, 它可与 result_type 类型的变量比较.

预定义 OwnershipPolicy 类

ref_counted

该类使用引用计数方案. 当计数减到零时, multi_pass 将删除其共享组件.

first_owner

使用该策略时, 第一个创建的 multi_pass 将是删除共享数据的那个. 每个拷贝都不取得共享数据的所有权. 这对 spirit 很有效, 因为迭代器没有动态分配. 所有拷贝都在栈上创建, 因此最初的迭代器拥有最长的寿命.

预定义 CheckingPolicy 类

no_check

该策略完全不进行检查.

buf_id_check

buf_id_check 保存一个缓冲区 id, 即缓冲区年龄. 每次对 multi_pass 迭代器调用 clear_queue() 时, 所有其他迭代器都有可能失效. 当调用 clear_queue() 时, buf_id_check 递增缓冲区 id. 当迭代器被解引用时, 该策略检查迭代器的缓冲区 id 是否与共享缓冲区 id 匹配. 该策略与 std_deque StoragePolicy 配合使用时最为有效. 它不应与 fixed_size_queue StoragePolicy 一起使用, 因为它检测不到越界的迭代器解引用.

full_check

该策略尚未实现. 实现之后, 它将跟踪所有迭代器并确保它们全部有效.

预定义 StoragePolicy 类

std_deque

该策略把所有缓冲数据保存在 std::deque 中. 只要存在多于一个迭代器, 所有数据都会被存储. 一旦迭代器计数降为一, 且队列不再需要, 就会清空它, 释放内存. 也可以通过调用 multi_pass::clear_queue() 强制清空队列.

fixed_size_queue<N>

fixed_size_queue 维护一个大小为 N+1 的环形缓冲区, 存储 N 个元素. fixed_size_queue 是一个带 std::size_t 参数的模板, 该参数指定队列大小. 确保 N 对你的解析器足够大是你自己的责任. 每当最前方的迭代器递增时, 缓冲区的最后一个字符会被自动擦除. 目前没有办法判断某个迭代器是否落后太远而已经失效. 该策略在正常的迭代器操作期间不做任何动态分配, 只在初始构造时分配. 这个 StoragePolicy 的内存用量固定为 N+1 字节, 不像 std_deque 那样无界.

组合: 如何指定你自己的定制 multi_pass

基于策略的设计之美在于: 通过挑选想要的策略, 你可以混合搭配它们来创建自己的定制类. 下面这个例子演示如何指定一个包装 istream_iterator<char> 的定制 multi_pass, 它比默认版本略有效率优势, 因为它使用了 first_owner OwnershipPolicy 和 no_check CheckingPolicy:

    typedef multi_pass<
        istream_iterator<char>,
        multi_pass_policies::input_iterator,
        multi_pass_policies::first_owner,
        multi_pass_policies::no_check,
        multi_pass_policies::std_deque
    > first_owner_multi_pass_type;

multi_pass 的默认模板参数是: input_iterator InputPolicy, ref_counted OwnershipPolicy, buf_id_check CheckingPolicy 和 std_deque StoragePolicy. 因此, 如果你使用 multi_pass<istream_iterator<char> >, 你在包装 istream_iterator<char> 的同时会得到那些预定义行为.

还有一个预定义类叫做 look_ahead. look_ahead 有两个模板参数: InputT, 要包装的输入迭代器的类型; 以及 std::size_t N, 它为 fixed_size_queue 策略指定缓冲区大小. 默认的 multi_pass 配置为安全而设计, 而 look_ahead 为速度而设计. look_ahead 派生自具有以下策略的 multi_pass: input_iterator InputPolicy, first_owner OwnershipPolicy, no_check CheckingPolicy 和 fixed_size_queue<N> StoragePolicy.

如何为 functor_input InputPolicy 编写函数对象

如果你想使用 functor_input InputPolicy, 可以编写自己的函数对象来向 multi_pass 提供输入. 该函数对象必须满足两个要求. 它必须有一个 typedef result_type, 指定 operator() 的返回类型. 这是 STL 的标准做法. 此外, 它必须提供一个名为 eof 的静态变量, 通过与之比较来获知输入是否已到达末尾. 下面是一个示例:

    class my_functor
    {
    public:

        typedef char result_type;

        my_functor()
        : c('A') {}

        char operator()() const
        {
            if (c == 'M')
                return eof;
            else
                return c++;
        }

        static result_type eof;

    private:

        char c;
    };

    my_functor::result_type my_functor::eof = '\0';

    typedef multi_pass<
        my_functor,
        multi_pass_policies::functor_input,
        multi_pass_policies::first_owner,
        multi_pass_policies::no_check,
        multi_pass_policies::std_deque
    > functor_multi_pass_type;

    functor_multi_pass_type first = functor_multi_pass_type(my_functor());
    functor_multi_pass_type last;

如何为 multi_pass 编写策略

InputPolicy

InputPolicy 必须具有以下接口:

    class my_input_policy // your policy name
    {
    public:

    //  class inner will be instantiated with the type given
    //  as the InputT parameter to multi_pass.

        template <typename InputT>
        class inner
        {
        public:

            // these typedefs determine the iterator_traits for multi_pass
            typedef x value_type;
            typedef x difference_type;
            typedef x pointer;
            typedef x reference;

        protected:

            inner();
            inner(InputT x);
            inner(inner const& x);
            // delete or clean up any state
            void destroy();
            // return true if *this and x have the same input
            bool same_input(inner const& x) const;
            void swap(inner& x);

        public:

            // get an instance from the input
            result_type get_input() const;
            // advance the input
            void advance_input();
            // return true if the input is at the end
            bool input_at_eof() const;
        };
    };

由于 multi_pass 在多份拷贝之间共享缓冲区和输入的方式, inner 类应保持一个指向其输入的指针. 拷贝构造函数应当只拷贝该指针. destroy() 应删除它. same_input 应比较这些指针. 更多细节请参见各 InputPolicy 类的各种实现.

OwnershipPolicy

OwnershipPolicy 必须具有以下接口:

    class my_ownership_policy
    {
    protected:

        my_ownership_policy();
        my_ownership_policy(my_ownership_policy const& x);
        // clone is called when a copy of the iterator is made
        void clone();
        // called when a copy is deleted. Return true to indicate
        // resources should be released
        bool release();
        void swap(my_ownership_policy& x);

    public:
        // returns true if there is only one iterator in existence.
        // std_dequeue StoragePolicy will free it's buffered data if this
        // returns true.
        bool unique() const;
    };

CheckingPolicy

CheckingPolicy 必须具有以下接口:

    class my_check
    {
    protected:

        my_check();
        my_check(my_check const& x);
        void destroy();
        void swap(my_check& x);
        // check should make sure that this iterator is valid
        void check_if_valid() const;
        void clear_queue();
    };

StoragePolicy

StoragePolicy 必须具有以下接口:

    class my_storage_policy
    {
    public:

    // class inner will be instantiated with the value_type from the InputPolicy

        template <typename ValueT>
        class inner
        {
        protected:

            inner();
            inner(inner const& x);
            // will be called from the destructor of the last iterator.
            void destroy();
            void swap(inner& x);
            // This is called when the iterator is dereferenced. It's a template
            // method so we can recover the type of the multi_pass iterator
            // and access it.
            template <typename MultiPassT>
            static ValueT dereference(MultiPassT const& mp);
            // This is called when the iterator is incremented. It's a template
            // method so we can recover the type of the multi_pass iterator
            // and access it.
            template <typename MultiPassT>
            static void increment(MultiPassT& mp);
            void clear_queue();
            // called to determine whether the iterator is an eof iterator
            template <typename MultiPassT>
            static bool is_eof(MultiPassT const& mp);
            // called by operator==
            bool equal_to(inner const& x) const;
            // called by operator<
            bool less_than(inner const& x) const;
        };  // class inner
    };

StoragePolicy 是最难编写的策略. 在尝试编写自己的策略之前, 你应当研究并理解现有的 StoragePolicy 类.
