库编译期配置

C++ 预处理迭代器库可以通过在编译期指定不同的预处理常量来配置, 以包含不同的附加特性. 可能的预处理常量在下表中描述.

库配置可能的预处理常量汇总
BOOST_WAVE_SUPPORT_WARNING_DIRECTIVE

支持#warning 指令
BOOST_WAVE_SUPPORT_MS_EXTENSIONS

支持若干 MS 特有的语言扩展 (即__int8 等)
BOOST_WAVE_PREPROCESS_ERROR_MESSAGE_BODY

启用对#error 和#warning 指令消息体的预处理.
BOOST_WAVE_EMIT_PRAGMA_DIRECTIVES

如果已定义, #pragma 指令会作为记号序列返回给调用者; 如果未定义, 整条#pragma 指令会被跳过.
BOOST_WAVE_PREPROCESS_PRAGMA_BODY

启用对所有 #pragma 指令体的预处理.
但请注意, operator _Pragma() 的体总是会被预处理, 因为这是 C99 标准[2]的要求.
BOOST_WAVE_ENABLE_COMMANDLINE_MACROS

启用以命令行语法定义宏 (-DMACRO(x)=definition) 所需的功能
BOOST_WAVE_STRINGTYPE

Wave 库生成的记号包含记号数据和该记号在输入流中被发现时的文件位置.
该常量可用于重新定义用于保存记号数据和对应文件名的数据类型. 如果未定义, 它默认为 std::string. (这里定义的数据类型应当与 std::string 类型兼容)
BOOST_WAVE_SUPPORT_VARIADICS_PLACEMARKERS

如果已定义, 预处理库支持变参宏和 placemarker 记号. 注意, 要支持 C99 模式, 也必须定义该常量.
BOOST_WAVE_SUPPORT_CPP0X

如果已定义, 预处理库支持 C++0x 关键字和 C++0x 特有特性, 例如变参宏、placemarker 记号、扩展的字符和字符串字面量. 这意味着必须定义BOOST_WAVE_SUPPORT_VARIADICS_PLACEMARKERS 常量.
BOOST_WAVE_SUPPORT_CPP1Z

如果已定义, 预处理库支持 C++17 关键字——目前只有__has_include. 它隐含BOOST_WAVE_SUPPORT_CPP0X.
BOOST_WAVE_SUPPORT_CPP2A

如果已定义, 预处理库支持 C++20 关键字, 特别是__VA_OPT__. 它隐含BOOST_WAVE_SUPPORT_CPP1Z.
BOOST_WAVE_MAX_INCLUDE_LEVEL_DEPTH

如果已定义, 它将确定支持的初始最大包含文件嵌套深度. 默认为 1024.
BOOST_WAVE_SUPPORT_PRAGMA_ONCE

如果已定义, #pragma once 指令受Wave 支持. 它规定 pragma 所在的文件在一次构建中只被编译器包含 (打开) 一次.
BOOST_WAVE_SUPPORT_PRAGMA_MESSAGE

如果已定义, #pragma message("") 指令受Wave 支持. 该 pragma 只是生成一条包含消息文本的备注. 当BOOST_WAVE_PREPROCESS_PRAGMA_BODY 常量也被定义时, #pragma message 的体会被预处理.
BOOST_WAVE_SUPPORT_INCLUDE_NEXT

如果已定义, #include_next 指令受Wave 支持. 它在语法上等价于#include 指令, 但可用于继承一个头文件 (即包含一个与包含#include_next 的当前文件同名的文件) .
BOOST_WAVE_USE_STRICT_LEXER

如果它被定义为非零值, C/C++ 词法分析器将识别严格的 C99/C++ 基本源字符集. 如果未定义或定义为零, 词法分析器会把'$' 字符识别为标识符的一部分.
BOOST_WAVE_PRAGMA_KEYWORD

如果它被定义为一个字符串字面量, 它将用作 pragma 关键字, 库据此识别特定的 Wave pragma. 该常量默认为"wave", 即库识别所有#pragma wave option [(argument)] 指令并把处理分派给 interpret_pragma() 预处理钩子函数 (见:预处理钩子) . pragma 的参数部分是可选的.

BOOST_WAVE_SUPPORT_LONGLONG_INTEGER_LITERALS

C++ 标准要求预处理器对整数字面量使用以下类型之一: long 或unsigned long, 取决于可选的后缀 ('u'、'l'、'ul' 或'lu') . 有时需要对更大的整数字面量进行预处理 (即long long 或unsigned long long) . 定义这个预处理常量即可识别 long long 整数, 即使它们没有'll' 后缀.

该预处理常量仅在目标平台支持 long long 整数 (即定义了BOOST_HAS_LONG_LONG) 时有效. 请注意, 该设置与 Wave 支持选项support_option_long_long无关, 后者只启用对'll' 后缀的识别.
BOOST_WAVE_SUPPORT_THREADING

该预处理常量允许配置 Wave 库构建时是否启用线程支持. 该值 (如果定义) 在需要禁用线程时应设为零 ('0') , 在需要显式启用线程时应设为非零的数值.

如果未定义该常量, Wave 库将使用从 Boost 构建环境中选取的线程设置进行构建 (见 Boost 配置文档中的BOOST_HAS_THREADS) .

配合 Wave 使用不同的记号类型或词法分析器类型

可以配合自己的记号类型和/或词法分析器类型来使用Wave 库. 这可以通过在实例化boost::wave::context<> 对象时把你的词法分析器类型作为第二个模板参数提供来实现. 库使用的记号类型由词法分析器类型需要提供的token_type typedef 派生. 如果你只想提供自己的记号类型, 可以使用库自带的boost::wave::lex_iterator<> 类型. 该类型需要用要使用的记号类型进行参数化.

Wave 库包含若干示例来说明这些可能性. cpp_tokens 示例展示了自定义词法分析器和自定义记号类型的用法. 所用的词法分析器类型在功能上与默认使用的基于re2c [3] 的词法分析器完全兼容. 它基于 Dan Nuffer 编写的SLex [5] 词法分析器示例实现. 其中使用的记号类型在功能上与默认记号类型等价, 只是额外实现了一个operator<<, 用于转储记号携带的信息.

分离编译模型与包含编译模型

Wave C++ 预处理迭代器库几乎完全构建为仅头文件库 (基于 re2c 的词法分析器除外) . 如果你试图一次性包含所有必需的文件, 你会注意到 resulting 编译时间非常长 (最长可达一小时——取决于你的系统配置) . 这种直接的方式我们称之为包含编译模型 (inclusion compilation model) . 如果你不在乎编译时间, 这就是可行之道, 无需特殊处理.

如果你希望缩短编译时间, 则应使用下面的方法. 我们称之为分离编译模型 (separation compilation model) . 技巧是把不同的对象分隔开来, 使它们可以单独编译. 实例化相关模板对象的函数被分解出来, 使其定义只对一个翻译单元可见. 为进一步简化, 这个创建函数被封装成一个小型的生成器模板结构.

实现了两个层次的分离: C++ 词法分析器编译的分离, 以及所用的不同 Spirit 文法编译的分离. 要使用这些分离, 你必须在编译整个应用程序时定义两个预处理常量, 并且必须显式实例化一些辅助模板. 下表详细列出了这些常量.

要看一个示例, 可以查看Wave 驱动程序, 它作为 C++ 预处理迭代器库的配套示例提供. 相应的文件名显而易见是"instantiate_...something.cpp", 其中'...somthing' 提示了其中显式实例化了哪些文法. 使用分离模型后, 构建Wave 示例所需的编译时间最多可降低 90%.

编译器要求

从 1.77 版开始, Wave 将要求用 C++11 特性构建, 并不再支持旧编译器. 不过, Wave 将继续无限期地模拟旧预处理器的特性.
