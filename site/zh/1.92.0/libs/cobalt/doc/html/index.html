动机

许多编程语言 (如 node.js 和 python) 都提供易于使用的单线程并发框架. 虽然比同步代码更复杂, 但单线程异步性避免了多线程的诸多陷阱与开销.

也就是说, 一个协程可以工作, 而其他协程等待事件 (例如服务器的响应). 这让我们能够在单线程上编写同时做多个事情的应用程序.

本库旨在为 C++ 提供这种能力: 简单的单线程异步性, 类似 node.js 和 python 的 asyncio, 并且可与 boost.beast、boost.mysql 或 boost.redis 等既有库配合使用. 它基于 boost.asio 构建.

它借用其他语言中的一组概念, 并基于 C++20 协程提供这些概念.

  • 易用的异步基础函数, 例如异步的 main 与 threads

  • Promise 与 generator 类型

  • 操作封装器

  • 一个异步作用域

  • race

  • channel

与 asio::awaitable 和 asio::experimental::coro 不同, cobalt 协程是开放的. 也就是说, 一个 asio::awaitable 只能等待以及被其他 asio::awaitable 等待, 且不提供协程特有的同步机制.

cobalt 则相反, 提供了协程特有的 channel 以及多种针对协程和 awaitable 优化过的等待类型 (race、gather 等).

协程入门

异步编程

异步编程通常指一种允许任务在后台运行、同时继续执行其他工作的编程风格.

设想一个执行完整 http 请求 (包括连接与 SSL 握手等) 的 get 请求函数.

std::string http_get(std:string_view url);

int main(int argc, char * argv[])
{
    auto res = http_get("https://boost.org");
    printf("%s", res.c_str());
    return 0;
}

上面的代码是传统的同步编程. 如果要并行执行两个请求, 就需要另创一个线程来运行另一段同步代码.

std::string http_get(std:string_view url);

int main(int argc, char * argv[])
{
    std::string other_res;

    std::thread thr{[&]{ other_res = http_get("https://cppalliance.org"); }};
    auto res = http_get("https://boost.org");
    thr.join();

    printf("%s", res.c_str());
    printf("%s", other_res.c_str());
    return 0;
}

这可行, 但程序大部分时间将耗费在等待输入上. 操作系统提供了允许异步执行 IO 的 API, 而 boost.asio 之类的库提供了管理异步操作的可移植方式. Asio 本身并不规定处理完成的方式. 本库 (boost.cobalt) 提供了通过协程/awaitable 管理这一切的方法.

cobalt::promise<std::string> http_cobalt_get(std:string_view url);

cobalt::main co_main(int argc, char * argv[])
{
    auto [res, other_res] =
            cobalt::join(
                http_cobalt_get("https://boost.org"),
                http_cobalt_get("https://cppalliance.org")
            );

    printf("%s", res.c_str());
    printf("%s", other_res.c_str());
    return 0;
}

在上面的代码中, 执行请求的异步函数利用操作系统 API, 使实际 IO 不阻塞. 这意味着在我们等待两个函数完成期间, 各操作是交错且非阻塞的. 与此同时, cobalt 提供的协程原语让我们远离回调地狱.

协程

协程是可恢复的函数. "可恢复"意味着函数可以挂起, 即多次把控制权交还给调用者.

普通函数通过 return 把控制权交还调用者, 同时返回值.

而协程则可能把控制权交给调用者, 并被多次恢复.

协程有三个类似 co_return 的控制关键字 (其中只有 co_return 必须支持).

  • co_return

  • co_yield

  • co_await

co_return

这类似于 return, 但将函数标记为协程.

co_await

co_await 表达式为一个 Awaitable 挂起, 即停止执行, 直到 awaitable 恢复它.

例如:

cobalt::promise<void> delay(std::chrono::milliseconds);

cobalt::task<void> example()
{
  co_await delay(std::chrono::milliseconds(50));
}

co_await 表达式可以产出一个值, 具体取决于它在等待什么.

cobalt::promise<std::string> read_some();

cobalt::task<void> example()
{
  std::string res = co_await read_some();
}
在 cobalt 中, 大多数协程原语也是 Awaitables.

co_yield

co_yield 表达式类似于 co_await, 但它把控制权交给调用者并携带一个值.

例如:

cobalt::generator<int> iota(int max)
{
  int i = 0;
  while (i < max)
    co_yield i++;

  co_return i;
}

co_yield 表达式也可以产生一个值, 这让让出 (yield) 协程的使用者能够向其推送值.

cobalt::generator<int> iota()
{
  int i = 0;
  bool more = false;
  do
  {
    more = co_yield i++;
  }
  while(more);
  co_return -1;
}
无栈

C++ 协程是无栈的, 这意味着它们只分配自己的函数帧.

详见无栈.

Awaitables

awaitable 是可以在 co_await 表达式中使用的类型.

struct awaitable_prototype
{
    bool await_ready();

    template<typename T>
    see_below await_suspend(std::coroutine_handle<T>);

    return_type  await_resume();
};
若存在可用的 operator co_await 调用, 类型将被隐式转换为 awaitable. 本文档将用 awaitable 涵盖这些类型, 并用 "actual_awaitable" 指代符合上述原型的类型.

在 co_await 表达式中, 等待中的协程会首先调用 await_ready 来检查协程是否需要挂起. 若已就绪, 则直接进入 await_resume 获取值, 因为无需挂起; 否则, 它将挂起自身, 并调用 await_suspend, 传入指向自身 promise 的 std::coroutine_handle.

std::coroutine_handle<void> 可用于类型擦除.

return_type 是 co_await expression 的结果类型, 例如 int:

int i = co_await awaitable_with_int_result();

await_suspend 的返回类型可以是三种情况:

  • void

  • bool

  • std::coroutine_handle<U>

若为 void, 等待中的协程保持挂起. 若为 bool, 将检查该值, 若为 false, 等待中的协程立即恢复.

若返回一个 std::coroutine_handle, 该协程将被恢复. 后一种情况允许 await_suspend 返回传入的句柄, 实际上等同于返回 false.

若等待中的协程被立即重新恢复 (即在调用 await_resume 之后), 在本库中称为"立即完成". 这不要与非挂起的 awaitable (即返回 true (来自 await_ready) 的 awaitable) 混为一谈.

事件循环

由于 cobalt 中的协程可以 co_await 事件, 它们需要运行在事件循环上. 也就是说, 由另一段代码负责跟踪未决事件, 并恢复等待这些事件的协程. 这种模式非常常见, node.js 和 python 的 asyncio 都以类似方式使用它.

cobalt 使用 asio::io_context 作为默认事件循环. 也就是说, thread 类、main 类以及 run 函数都在内部使用它.

任何能产生 asio::any_io_executor 的事件循环都可以与本库配合使用. 最简单的方式是使用 spawn.

事件循环通过执行器访问 (沿用 asio 的术语), 并可以使用 set_executor 手动设置.

导览

进入 cobalt 环境

要使用 awaitable, 我们需要能够 co_await 它们, 即处于协程之内.

实现这一点有四种方式:

cobalt/main.hpp

用协程替换 int main 

cobalt::main co_main(int argc, char* argv[])
{
    // co_await things here
    co_return 0;
}
cobalt/thread.hpp

为异步环境创建一个线程

cobalt::thread my_thread()
{
    // co_await things here
    co_return;
}

int main(int argc, char * argv[])
{
    auto t = my_thread();
    t.join();
    return 0;
}
cobalt/task.hpp

创建一个 task 并运行或 spawn 它

cobalt::task<void> my_thread()
{
   // co_await things here
   co_return;
}

int main(int argc, char * argv[])
{
    cobalt::run(my_task()); // sync
    asio::io_context ctx;
    cobalt::spawn(ctx, my_task(), asio::detached);
    ctx.run();
    return 0;
}

promise

Promises 是推荐的默认协程类型. 它们是急切的, 因此很容易用于临时并发.

cobalt::promise<int> my_promise()
{
   co_await do_the_thing();
   co_return 0;
}

cobalt::main co_main(int argc, char * argv[])
{
    // start the promise here
    auto p = my_promise();
    // do something else here
    co_await do_the_other_thing();
    // wait for the promise to complete
    auto res = co_await p;

    co_return res;
}

Tasks

Tasks 是惰性的, 这意味着在被等待或 spawn 之前不会做任何事.

cobalt::task<int> my_task()
{
   co_await do_the_thing();
   co_return 0;
}

cobalt::main co_main(int argc, char * argv[])
{
    // create the task here
    auto t = my_task();
    // do something else here first
    co_await do_the_other_thing();
    // start and wait for the task to complete
    auto res = co_await t;
    co_return res;
}

Generator

generator 是 cobalt 中唯一可以 co_yield 值的类型.

Generator 默认是急切的. 与 std::generator 不同, cobalt::generator 可以 co_await, 因而是异步的.

cobalt::generator<int> my_generator()
{
   for (int i = 0; i < 10; i++)
    co_yield i;
   co_return 10;
}

cobalt::main co_main(int argc, char * argv[])
{
    // create the generator
    auto g = my_generator();
    while (g)
        printf("Generator %d\n", co_await g);
    co_return 0;
}

值可以被推送进 generator, 并从 co_yield 返回.

急切的 generator 会在被等待之前就产生第一个结果. 也就是说, 当我们调用 co_await g(4) 时, 初始 co_yield 的结果已就绪. 随后 generator 接收作为 co_yield 返回传入的值 4, 并处理它.

cobalt::generator<std::string, int> my_eager_push_generator(int value)
{
   while (value != 0)
       value = co_yield std::to_string(value);
   co_return "";
}

cobalt::main co_main(int argc, char * argv[])
{
    // create the generator
    auto g = my_generator(5);

    assert("5" == co_await g(4)); // result of 5
    assert("4" == co_await g(3)); // result of 4
    assert("3" == co_await g(2)); // result of 3
    assert("2" == co_await g(1)); // result of 2
    assert("1" == co_await g(0)); // result of 1

    // we let the coroutine go out of scope while suspended
    // no need for another co_await of `g`

    co_return 0;
}

协程也可以使用 this_coro::initial 变为惰性.

惰性 generator 会等待第一个 co_await 才开始工作, 即当 initial 被等待时它才挂起. 数据处理不会先行一步, 而是在被 co_await 时发生.

cobalt::generator<std::string, int> my_eager_push_generator()
{
    auto value = co_await this_coro::initial;
    while (value != 0)
       value = co_yield std::to_string(value);
    co_return "";
}

cobalt::main co_main(int argc, char * argv[])
{
    // create the generator
    auto g = my_generator(); // lazy, so the generator waits for the first pushed value
    assert("5" == co_await g(5)); // result of 5
    assert("4" == co_await g(4)); // result of 4
    assert("3" == co_await g(3)); // result of 3
    assert("2" == co_await g(2)); // result of 2
    assert("1" == co_await g(1)); // result of 1

    // we let the coroutine go out of scope while suspended
    // no need for another co_await of `g`

    co_return 0;
}

join

如果多个 awaitable 并行工作, 可以用 join 同时等待它们.

cobalt::promise<int> some_work();
cobalt::promise<double> more_work();

cobalt::main co_main(int argc, char * argv[])
{
    std::tuple<int, double> res = cobalt::join(some_work(), more_work());
    co_return 0;
}

race

如果多个 awaitable 并行工作, 但我们希望在其中任一完成时得到通知, 应使用 race.

cobalt::generator<int> some_data_source();
cobalt::generator<double> another_data_source();

cobalt::main co_main(int argc, char * argv[])
{
    auto g1 = some_data_source();
    auto g2 = another_data_source();

    int res1    = co_await g1;
    double res2 = co_await g2;

    printf("Result: %f", res1 * res2);

    while (g1 && g2)
    {
        switch(variant2::variant<int, double> nx = co_await cobalt::race(g1, g2))
        {
            case 0:
                res1 = variant2::get<0>(nx);
                break;
            case 1:
                res2 = variant2::get<1>(nx);
                break;
        }
        printf("New result: %f", res1 * res2);
    }

    co_return 0;
}
此语境下的 race 不会造成任何数据丢失.

教程

延迟

我们从最简单的示例开始: 一个简单的延迟.

example/delay.cpp
cobalt::main co_main(int argc, char * argv[]) (1)
{
  asio::steady_timer tim{co_await asio::this_coro::executor, (2)
                         std::chrono::milliseconds(std::stoi(argv[1]))}; (3)
  co_await tim.async_wait(cobalt::use_op); (4)
  co_return 0; (5)
}
1 co_main 函数在使用时会定义一个隐式的 main, 是搭建运行异步代码环境的最简单方式.
2 从当前协程的 promise 获取执行器.
3 用实参设置超时
4 使用 cobalt::use_op 执行等待.
5 返回一个值, 它将作为隐式 main 的返回值.

本示例使用 cobalt/main.hpp 头文件, 若 co_main 按上文定义, 它会为我们提供 main 协程. 这有几个优点:

  • 环境被正确设置 (executor 与 memory)

  • asio 得到通知: 该上下文是单线程的

  • asio::signal_set (带 SIGINT 与 SIGTERM) 自动连接到取消机制 (即 Ctrl+C 会引发取消)

该协程的 promise 中有一个执行器 (promise 是 C++ 对协程状态的称呼, 不要与 cobalt/promise.hpp 混淆), 我们可以通过 this_coro 命名空间中的伪 awaitable 获取它.

然后我们可以构造一个定时器, 并发起 async_wait (使用 use_op). cobalt 提供了多种与 asio 交互的 co_await 方式, 其中最简单的是 use_op.

echo 服务器

我们将处处使用 use_op (asio 完成) 标记, 因此使用的是 默认完成标记, 从而可以省略最后的参数.

example/echo_server.cpp 声明部分
namespace cobalt = boost::cobalt;
namespace this_coro = boost::cobalt::this_coro;

我们把 echo 函数写成 promise 协程. 它是急切协程, 推荐作为默认选择; 若需要惰性协程, 可以使用 task.

example/echo_server.cpp echo 函数部分
cobalt::promise<void> echo(cobalt::io::stream_socket socket)
{
  try (1)
  {
    char data[4096];
    while (socket.is_open()) (2)
    {
      std::size_t n = co_await socket.read_some(boost::asio::buffer(data)); (3)
      co_await cobalt::io::write(socket, boost::asio::buffer(data, n)); (4)
    }
  }
  catch (std::exception& e)
  {
    std::printf("echo: exception: %s\n", e.what());
  }
}

    co_yield std::move(sock); (3)
  }

有了这两个函数, 我们现在可以编写服务器:

example/echo_server.cpp run_server 函数部分
cobalt::promise<void> run_server(cobalt::wait_group & workers)
{
  auto l = listen(); (1)
  while (true)
  {
    if (workers.size() == 10u)
      co_await workers.wait_one();  (2)
    else
      workers.push_back(echo(co_await l)); (3)
  }
}

延迟操作

到目前为止我们使用 use_op, 以利用基于 asio 完成标记机制的隐式操作.

但我们也可以实现自己的操作 (op), 它们同样可以利用 await_ready 优化. 与立即完成不同, 当 await_ready 返回 true 时协程绝不会挂起.

为了利用这一协程特性, cobalt 提供了一种创建可跳过操作的简便方式:

example/delay_op.cpp
struct wait_op final : cobalt::op<system::error_code> (1)
{
  asio::steady_timer & tim;
  wait_op(asio::steady_timer & tim) : tim(tim) {}
  void ready(cobalt::handler<system::error_code> h ) override (2)
  {
    if (tim.expiry() < std::chrono::steady_clock::now())
      h(system::error_code{});
  }
  void initiate(cobalt::completion_handler<system::error_code> complete) override (3)
  {
    tim.async_wait(std::move(complete));
  }
};


cobalt::main co_main(int argc, char * argv[])
{
  asio::steady_timer tim{co_await asio::this_coro::executor,
                         std::chrono::milliseconds(std::stoi(argv[1]))};
  co_await wait_op(tim); (4)
  co_return 0; //
}
1 声明该操作. 我们继承 op 使其成为 awaitable.
2 挂起前检查在此实现
3 必要时执行等待
4 像使用其他 awaitable 一样使用 op.

这样我们可以把协程挂起的次数降到最少.

虽然上面是与 asio 一起使用的, 但这些处理器也可以用于任何其他基于回调的代码.

设计

概念

本库有两个基本概念:

  • awaitable

  • coroutine

awaitable 是可以在协程内与 co_await 一起使用的表达式, 例如:

co_await delay(50ms);

但是, 协程的 promise 可以定义 await_transform, 也就是说, 实际能与 co_await 表达式一起使用的内容取决于协程.

因此, 我们应当重新定义什么是 awaitable: awaitable 是可以在协程内被 co_await 的类型, 且其 promise 未定义 await_transform.

pseudo-keyword 是一种可在协程中使用的类型, 它凭借其 promise 的 await_transform 为协程添加特殊功能.

this_coro 命名空间中的所有动词都是这种伪关键字.

auto exec = co_await this_coro::executor;
本库公开了一组供 promise 使用的 enable_* 基类, 使自定义协程易于创建. 其中包括 enable_awaitables, 它提供的 await_transform 仅用于转发 awaitable.

在本文档的语境中, 协程指异步协程, 即不考虑 std::generator 之类的同步协程.

除 main 之外的所有协程也都是实际的 awaitable.

执行器

由于一切都是异步的, 本库需要使用事件循环. 又因为一切都是单线程的, 可以假定每个线程恰好有一个执行器, 这足以覆盖 97% 的用例. 因此, 本库提供一个 thread_local 执行器, 作为协程对象的默认执行器 (尽管协程 promise 中存的是其副本).

同样, 本库只使用一种 executor 类型, 默认为 asio::any_io_executor.

如果你编写自己的协程, 它应持有执行器的一个副本, 并提供一个以 const 引用返回它的 get_executor 函数.

使用 strand

虽然可以使用 strand, 但它与 thread_local 执行器不兼容. 这是因为 strand 可能切换线程, 因而无法 thread_local.

如果想使用 strand (例如通过 spawn), 任何 promise、generator 或 channel 的执行器都必须手动指定.

对 channel 而言这是构造函数实参; 而对其他协程类型, 需要使用 asio::executor_arg. 具体做法是在协程的实参列表中让 asio::executor_arg_t (位于某处) 之后直接跟要使用的执行器, 例如:

cobalt::promise<void> example_with_executor(int some_arg, asio::executor_arg_t, cobalt::executor);

这样协程 promise 就能从第三个实参获取执行器, 而不是默认使用 thread_local 执行器.

当然, 这些实参可以提供默认值以减少不便, 尤其当它们有时使用 thread_local 执行器时.

cobalt::promise<void> example_with_executor(int some_arg,
                                           asio::executor_arg_t = asio::executor_arg,
                                           cobalt::executor = cobalt::this_thread::get_executor());

若在 strand 上省略这一点, 将抛出 asio::bad_allocator 类型的异常, 或者更糟, 使用错误的执行器.

多态内存资源

类似地, 本库使用 thread_local 的 pmr::memory_resource 来分配协程帧, 并在异步操作中用作分配器.

原因在于用户可能想自定义分配行为, 例如避免锁、限制内存使用或监控用量. pmr 使我们无需引入不必要的模板参数即可做到这一点, 即不带来 promise<T, Allocator> 复杂度. 但使用 pmr 确实会引入一些最小开销, 因此用户可以通过定义 BOOST_COBALT_NO_PMR 来禁用它.

op 使用针对 asio 分配器用法优化过的内部资源, 而 gather、race 和 join 使用单调资源以尽量减少分配. 在定义了 BOOST_COBALT_NO_PMR 的情况下二者仍然可用, 此时它们会使用 new/delete 作为上游分配器.

main 与 thread 在启用 PMR 时每线程一个 pmr::unsynchronized_pool_resource.

如果你编写自己的协程, 它应提供一个返回 pmr::polymorphic_allocator<void> 的 get_allocator 函数.

取消

cobalt 使用基于 asio::cancellation_signal 的隐式取消. 它大多被隐式使用 (例如配合 race), 因此示例中很少显式使用.

如果编写自定义协程, 它必须返回一个 cancellation_slot (来自 get_cancellation_slot 函数), 才能取消其他操作.
如果编写自定义 awaitable, 它可以在 await_suspend 中使用该函数来接收取消信号.

Promise

主要的协程类型是 promise, 它是急切的. 默认采用它的原因是: 编译器可以把不挂起的 promise 优化掉, 如下:

cobalt::promise<void> noop()
{
  co_return;
}

等待上述操作理论上是无操作 (noop), 但实际上, 截至 2023 年编译器还没做到这一点.

Race

最重要的同步机制是 race 函数.

它以伪随机顺序等待多个 awaitable, 并在第一个完成后返回其结果, 而忽略其余的.

也就是说, 它以伪随机顺序发起 co_await, 一旦发现某个 awaitable 已就绪或立即完成就停止.

cobalt::generator<int> gen1();
cobalt::generator<double> gen2();

cobalt::promise<void> p()
{
  auto g1 = gen1();
  auto g2 = gen2();
  while (!co_await cobalt::this_coro::cancelled)
  {
    switch(auto v = co_await race(g1, g2); v.index())
    {
    case 0:
      printf("Got int %d\n", get<0>(v));
      break;
    case 1:
      printf("Got double %f\n", get<1>(v));
      break;
    }
  }
}

不过, race 一旦发起 co_await, 就必须在内部等待所有 awaitable 完成. 因此, 当第一个 awaitable 完成后, 它会尝试中断其余的, 若失败则取消它们.

race 是触发取消的首选方式, 例如:

cobalt::promise<void> timeout();
cobalt::promise<void> work();

race(timeout(), work());

interrupt_await

但如果直接取消就会丢失数据. 因此引入了 interrupt_await 的概念: 它告诉支持该机制的 awaitable 立即恢复等待者, 并返回或抛出一个将被忽略的值.

可中断 awaitable 的示例
struct awaitable
{
   bool await_ready() const;

   template<typename Promise>
   std::coroutine_handle<void> await_suspend(std::coroutine_handle<Promise> h);

   T await_resume();

   void interrupt_await() &;
};

若 interrupt_await 未导致 (h 的) 立即恢复, race 将发送取消信号.

race 会以正确的引用限定应用这些:

auto g = gen1();
race(g, gen2());

上面的代码会调用 interrupt_await() & 函数 (为 g1) 以及 interrupt_await() && (为 g2), 若可用.

一般而言, cobalt 中的协程支持左值中断, 即 interrupt_await() &. channel 操作则不带限定, 即两种情况都可用.

关联器

cobalt 使用 asio 的 associator 概念, 但做了简化. 也就是说, 它有三个关联器, 都是等待方 promise 的成员函数.

  • const executor_type & get_executor() (始终为 executor, 必须以 const 引用返回)

  • allocator_type get_allocator() (始终为 pmr::polymorphic_allocator<void>)

  • cancellation_slot_type get_cancellation_slot() (必须与 asio::cancellation_slot 具有相同的 IF)

cobalt 使用 concept 来检查这些是否存在于其 await_suspend 函数中.

这样自定义协程就能支持取消、执行器和分配器.

在自定义 awaitable 中可以这样获取它们:

struct my_awaitable
{
    bool await_ready();
    template<typename T>
    void await_suspend(std::corutine_handle<P> h)
    {
        if constexpr (requires  (Promise p) {p.get_executor();})
            handle_executor(h.promise().get_executor();

        if constexpr (requires (Promise p) {p.get_cancellation_slot();})
            if ((cl = h.promise().get_cancellation_slot()).is_connected())
                cl.emplace<my_cancellation>();
    }

    void await_resume();
};

取消会在 co_await 表达式中被连接 (若协程与 awaitable 均支持), 包括 race 之类的同步机制.

线程

本库在设计上是单线程的, 因为这简化了恢复过程, 从而能更高效地处理 race 之类的同步. 若非如此, race 将需要锁住每个参与竞争的 awaitable 以避免数据丢失, 这需要阻塞, 且每增加一个元素都会变得更糟.

任何协程都不能在与创建时不同的线程上恢复, task 除外 (例如使用 spawn).

主要的技术原因是: 切换协程最高效的方式是从 await_suspend 返回新协程的句柄, 如下:

struct my_awaitable
{
    bool await_ready();
    std::coroutine_handle<T> await_suspend(std::coroutine_handle<U>);
    void await_resume();
};

在这种情况下, 等待中的协程会在调用 await_suspend 之前被挂起, 而返回的协程被恢复. 当然, 如果需要经过执行器, 这就行不通了.

这不仅适用于被等待的协程, 也适用于 channel. 本库的 channel 使用 awaitable 的侵入式列表, 写操作的 await_suspend 可能返回正在读取 (因而已挂起) 的协程的句柄.

cobalt/channel.hpp

channel 可用于在单线程上的不同协程之间交换数据.

概要

channel 概要
template<typename T>
struct channel
{
  // create a channel with a buffer limit, executor & resource.
  explicit
  channel(std::size_t limit = 0u,
          executor executor = this_thread::get_executor(),
          pmr::memory_resource * resource = this_thread::get_default_resource());
  // not movable.
  channel(channel && rhs) noexcept = delete;
  channel & operator=(channel && lhs) noexcept = delete;

  using executor_type = executor;
  const executor_type & get_executor();

  // Closes the channel
  ~channel();
  bool is_open() const;
  // close the operation, will cancel all pending ops, too
  void close();

  // an awaitable that yields T
  using read_op = unspecified;

  // an awaitable that yields void
  using write_op = unspecified;

  // read a value to a channel
  read_op  read();

  // write a value to the channel
  write_op write(const T  && value);
  write_op write(const T  &  value);
  write_op write(      T &&  value);
  write_op write(      T  &  value);

  // write a value to the channel if T is void

};

说明

channel 是两个协程之间通信与同步的工具.

const std::size_t buffer_size = 2;
channel<int> ch{exec, buffer_size};

// in coroutine (1)
co_await ch.write(42);

// in coroutine (2)
auto val = co_await ch.read();
1 向 channel 发送一个值, 会阻塞直到可以发送
2 从 channel 读取一个值, 会阻塞直到有值可读.

两种操作都可能阻塞, 取决于 channel 的缓冲区大小.

若缓冲区大小为零, read 与 write 必须同时发生, 即如同会合 (rendezvous).

若缓冲区未满, 写操作不会挂起协程; 同样, 若缓冲区非空, 读操作不会挂起.

若两个操作同时完成 (缓冲区为空时总是如此), 第二个操作会被投递到执行器稍后完成.

channel 类型可以是 void 的, 此时 write 不接受参数.

channel 操作可以被取消而不丢失数据. 这使它们可与 race 配合使用.

generator<variant2::variant<int, double>> merge(
    channel<int> & c1,
    channel<double> & c2)
{
    while (c1 && c2)
       co_yield co_await race(c1.read(), c2.read());
}

示例

cobalt::promise<void> producer(cobalt::channel<int> & chan)
{
  for (int i = 0; i < 4; i++)
    co_await chan.write(i);

  chan.close();
}

cobalt::main co_main(int argc, char * argv[])
{
  cobalt::channel<int> c;

  auto p = producer(c);
  while (c.is_open())
    std::cout << co_await c.read() << std::endl;

  co_await p;
  co_return 0;
}

此外, 还提供了一个 channel_reader, 使读取 channel 更方便, 并可与 BOOST_COBALT_FOR 配合使用.

cobalt::main co_main(int argc, char * argv[])
{
  cobalt::channel<int> c;

  auto p = producer(c);
  BOOST_COBALT_FOR(int value, cobalt::channel_reader(c))
    std::cout << value << std::endl;

  co_await p;
  co_return 0;
}

cobalt/race.hpp

race 函数可用于 co_await 一组 awaitable 中的一个.

它既可以作为变参函数以多个 awaitable 调用, 也可以作用于 awaitable 的范围.

cobalt::promise<void> task1();
cobalt::promise<void> task2();

cobalt::promise<void> do_wait()
{
  co_await cobalt::race(task1(), task2()); (1)
  std::vector<cobalt::promise<void>> aws {task1(), task2()};
  co_await cobalt::race(aws); (2)
}
1 等待变参的一组 awaitable
2 以 vector 形式等待 awaitable

第一个参数 race 可以是 均匀随机位生成器.

race 的签名
extern promise<void> pv1, pv2;
std::vector<promise<void>> pvv;

std::default_random_engine rdm{1};
// if everything returns void race returns the index
std::size_t r1 = co_await race(pv1, pv2);
std::size_t r2 = co_await race(rdm, pv1, pv2);
std::size_t r3 = co_await race(pvv);
std::size_t r4 = co_await race(rdm, pvv);

// variant if not everything is void. void become monostate
extern promise<int> pi1, pi2;
variant2::variant<monostate, int, int> r5 = co_await race(pv1, pi1, pi2);
variant2::variant<monostate, int, int> r6 = co_await race(rdm, pv1, pi1, pi2);

// a range returns a pair of the index and the result if non-void
std::vector<promise<int>> piv;
std::pair<std::size_t, int> r7 = co_await race(piv);
std::pair<std::size_t, int> r8 = co_await race(rdm, piv);

中断等待

当实参以右值引用传入时, race 会尝试使用 .interrupt_await (作用于 awaitable) 来通知该 awaitable 立即完成且结果将被忽略. 若支持此机制, Awaitable 必须在 interrupt_await 返回之前恢复等待中的协程. 若 race 未检测到该函数, 则会发送取消.

这意味着可以这样复用 race:

cobalt::promise<void> do_wait()
{
  auto t1 = task1();
  auto t2 = task2();
  co_await cobalt::race(t1, t2); (1)
  co_await cobalt::race(t1, t2); (2)
}
1 等待第一个任务完成
2 等待另一个任务完成

promise、generator 和 gather 都支持此机制.

race 会调用 awaitable 的函数, 如同在 co_await 表达式中使用一样, 或者完全不对其求值.

left_race

left_race 函数类似于 race, 但遵循严格的从左到右扫描. 这可能导致饥饿问题, 因此它不是推荐的默认选择; 但若加以小心, 可用于优先级控制.

概要

// Concept for the random number generator.
template<typename G>
  concept uniform_random_bit_generator =
    requires ( G & g)
    {
      {typename std::decay_t<G>::result_type() } -> std::unsigned_integral; // is an unsigned integer type
      // T	Returns the smallest value that G's operator() may return. The value is strictly less than G::max(). The function must be constexpr.
      {std::decay_t<G>::min()} -> std::same_as<typename std::decay_t<G>::result_type>;
      // T	Returns the largest value that G's operator() may return. The value is strictly greater than G::min(). The function must be constexpr.
      {std::decay_t<G>::max()} -> std::same_as<typename std::decay_t<G>::result_type>;
      {g()} -> std::same_as<typename std::decay_t<G>::result_type>;
    } && (std::decay_t<G>::max() > std::decay_t<G>::min());


// Variadic race with a custom random number generator

         uniform_random_bit_generator URBG, awaitable ... Promise>

// Ranged race with a custom random number generator
template<asio::cancellation_type Ct = asio::cancellation_type::all,
         uniform_random_bit_generator URBG, range<awaitable> PromiseRange>
awaitable race(URBG && g, PromiseRange && p);

// Variadic race with the default random number generator
template<asio::cancellation_type Ct = asio::cancellation_type::all, awaitable... Promise>
awaitable race(Promise && ... p);

// Ranged race with the default random number generator
template<asio::cancellation_type Ct = asio::cancellation_type::all, range<awaitable>>
awaitable race(PromiseRange && p);

// Variadic left race
template<asio::cancellation_type Ct = asio::cancellation_type::all, awaitable... Promise>
awaitable left_race(Promise && ... p);

// Ranged left race
template<asio::cancellation_type Ct = asio::cancellation_type::all, range<awaitable>>
awaitable left_race(PromiseRange && p);

cobalt/wait_group.hpp

cobalt/spawn.hpp

spawn 函数允许运行 task 于 asio executor/execution_context 之上, 并用 完成标记 消费结果.

auto spawn(Context & context, task<T> && t, CompletionToken&& token);
auto spawn(Executor executor, task<T> && t, CompletionToken&& token);

spawn 会投递其发起并提交完成. 这使得用 task 在另一个执行器上运行任务, 并用 use_op 在当前执行器上消费结果是安全的. 也就是说, spawn 可用于跨线程.

  auto f = spawn(ctx, work(), asio::use_future);
  ctx.run();

  return f.get();
}
调用者需要确保执行器不会在多个线程上并发运行, 例如使用单线程的 asio::io_context.

cobalt/composition.hpp

包含 cobalt/composition.hpp 会提供一些定义, 用于把任何以 cobalt::completion_handler 作为最后一个实参的函数转换为组合操作. 这使组合操作的创建变得简单.

co_await 语句的结果会自动转换为元组 (类似于使用 as_tuple), 以避免异常.

结果需要被 co_return. 传入协程的处理器不得被改动.

struct echo_op final : op<system::error_code>
{
  echo_op(cobalt::io::stream & str) : stream(str) {}
  void initiate(completion_handler<system::error_code>) final;
  cobalt::io::stream & str;
};

void echo_op::initiate(completion_handler<system::error_code, std::size_t>)
{
  char buf[4096];
  auto [ec, n] = co_await str.read_some(buf);

  auto buf = asio::buffer(buf, n);

  while (!ec && !buf.empty() && !!co_await this_coro::cancelled)
  {
    std::tie(ec, n) = co_await str.write_some(buf);
    buf += n;
  }

  if (!!co_await this_coro::cancelled)
    co_return {asio::error::operation_aborted, m};
  else
    co_return {system::error_code{}, m};
}

深入细节

自定义执行器

cobalt 默认使用 asio::any_io_executor 的原因之一是它是类型擦除的执行器, 即你可以提供自己的事件循环, 而无需重新编译 cobalt.

然而, 在 Executor TS 的开发过程中, 执行器概念变得有点不直观, 说得客气一点.

Ruben Perez 写过一篇出色的博客文章, 我将毫不客气地从中取材.

定义

执行器是指向实际事件循环的类型, 可以 (廉价) 拷贝, 支持属性 (见下文), 可比较相等, 并拥有一个 execute 函数.

execute
struct example_executor
{
  template<typename Fn>
  void execute(Fn && fn) const;
};

上述函数会按照其属性执行 fn.

属性

属性可以被查询、偏好或要求, 例如:

struct example_executor
{
  // get a property by querying it.
  asio::execution::relationship_t &query(asio::execution::relationship_t) const
  {
    return asio::execution::relationship.fork;
  }

  // require an executor with a new property
  never_blocking_executor require(const execution::blocking_t::never_t);

  // prefer an executor with a new property. the executor may or may not support it.
  never_blocking_executor prefer(const execution::blocking_t::never_t);
  // not supported
  example_executor prefer(const execution::blocking_t::always_t);
};
属性: asio::any_io_executor

要把执行器封装进 asio::any_io_executor, 需要两个属性:

  • execution::context_t

  • execution::blocking_t::never_t

这意味着我们要么让它们可被 require (这对 context 而言没有意义), 要么从 query 返回期望的值.

execution::context_t 查询应当返回 asio::execution_context&, 如下:

struct example_executor
{
  asio::execution_context &query(asio::execution::context_t) const;
};

执行上下文用于管理那些管理 io 对象 (如 asio 的定时器与套接字) 生命周期的服务的生命周期. 也就是说, 提供该上下文后, asio 的所有 io 都能与它配合.

在执行器被销毁之后, execution_context 必须仍然存活.

以下属性可以被偏好 (preferred):

  • execution::blocking_t::possibly_t

  • execution::outstanding_work_t::tracked_t

  • execution::outstanding_work_t::untracked_t

  • execution::relationship_t::fork_t

  • execution::relationship_t::continuation_

这意味着你可能想在执行器中支持它们以进行优化.

blocking 属性

如前所述, 该属性控制传给 execute() 的函数能否作为 execute() 的一部分立即运行, 还是必须排队稍后执行. 可能的取值有:

  • asio::execution::blocking.never: 绝不作为 execute() 的一部分运行函数. 这就是 asio::post() 的行为.

  • asio::execution::blocking.possibly: 函数可能作为 execute() 的一部分运行, 也可能不. 这是默认值 (调用 io_context::get_executor 时得到的行为).

  • asio::execution::blocking.always: 函数总是作为 execute() 的一部分运行. io_context::executor 不支持此行为.

relationship 属性

relationship 可以取两个值:

  • asio::execution::relationship.continuation: 表示传给 execute() 的函数是调用 execute() 的函数的延续 (continuation).

  • asio::execution::relationship.fork: 与上述相反. 这是默认值 (调用 io_context::get_executor() 时得到的行为).

把该属性设为 continuation 会启用一些函数调度方面的优化. 它只在函数被排队 (而非立即运行) 时生效. 对于 io_context, 设置后函数会被调度到更快的线程局部队列中运行, 而不是上下文全局队列.

outstanding_work_t 属性

outstanding_work 可以取两个值:

  • asio::execution::outstanding_work.tracked: 表示只要执行器还存活, 就仍有工作要做.

  • asio::execution::outstanding_work.untracked: 与上述相反. 这是默认值 (调用 io_context::get_executor() 时得到的行为).

把该属性设为 tracked 意味着只要 executor 存活, 事件循环就不会返回.

无栈

C++20 协程是无栈的, 这意味着它们没有自己的栈.

C++ 中的栈指调用栈, 即堆叠的所有函数帧. 函数帧是函数运行所需的内存, 即用于存储其变量以及返回地址等信息的一块内存.

函数帧的大小在编译期是已知的, 但在包含其定义的编译单元之外不可知. 
int bar() {return 0;} // the deepest point of the stack
int foo() {return bar();}

int main()
{
    return foo();
}

上面示例中的调用栈是:

main()
  foo()
    bar()

协程可以实现为有栈的, 即分配一块固定大小的内存, 并像线程一样堆叠函数帧. C++20 协程是无栈的, 即它们只分配自己的帧, 并在恢复时使用调用者的栈. 使用之前的示例:

fictional_eager_coro_type<int> example()
{
    co_yield 0;
    co_yield 1;
}

void nested_resume(fictional_eager_coro_type<int>& f)
{
    f.resume();
}

int main()
{
    auto f = example();
    nested_resume(f);
    f.reenter();
    return 0;
}

这将产生类似这样的调用栈:

main()
  f$example()
  nested_resume()
    f$example()
  f$example()

若协程被移动到其他线程, 情况亦然.

惰性与急切

若协程只有在被恢复之后才开始执行其代码, 则它是惰性的; 而急切的协程会立即执行到第一个挂起点 (即 co_await、co_yield 或 co_return 表达式) 为止.

lazy_coro co_example()
{
    printf("Entered coro\n");
    co_yield 0;
    printf("Coro done\n");
}

int main()
{
    printf("enter main\n");
    auto lazy = co_example();
    printf("constructed coro\n");
    lazy.resume();
    printf("resumed once\n");
    lazy.resume();
    printf("resumed twice\n");
    return 0;
}

这将产生如下输出:

enter main
constructed coro
Entered coro
resumed once
Coro Done
resumed twice

而急切的协程则如下所示:

eager_coro co_example()
{
    printf("Entered coro\n");
    co_yield 0;
    printf("Coro done\n");
}

int main()
{
    printf("enter main\n");
    auto lazy = co_example();
    printf("constructed coro\n");
    lazy.resume();
    printf("resumed once\n");
    return 0;
}

这将产生如下输出:

enter main
Entered coro
constructed coro
resume once
Coro Done

要求

库

Boost.cobalt 需要 C++20 编译器, 并直接依赖以下 boost 库:

  • boost.asio

  • boost.system

  • boost.circular_buffer

  • boost.intrusive

  • boost.smart_ptr

  • boost.container (clang < 16 时使用)

编译器

本库自 Clang 14、Gcc 10 与 MSVC 19.30 (Visual Studio 2022) 起受支持.

Gcc 12.1 与 12.2 版本对包含外部栈变量的协程似乎有缺陷, 如此处所示, 协程场景应避免使用.

Clang 直到 16 才加入 std::pmr 支持, 因此较旧的 clang 版本使用 boost::container::pmr 作为直接替代品.

即使不是全部, 至少某些 MSVC 版本的协程实现是有缺陷的, 本库需要绕过这些问题. 这可能导致非确定性行为和开销.

协程延续可以在 final_suspend 返回的 awaitable 中完成, 如下:

// in promise
auto final_suspend() noexcept
{
    struct final_awaitable
    {
      std::coroutine_handle<void> continuation{std::noop_coroutine()}; (1)
      bool await_ready() const noexcept;
      std::coroutine_handle<void> await_suspend(std::coroutine_handle<void> h) noexcept
      {
        auto cc = continuation;
        h.destroy(); (2)
        return cc;
      }

      void await_resume() noexcept {}
    };
    return final_awaitable{my_continuation};
};
1 延续
2 在延续之前自毁协程

在 MSVC 上 final_suspend 不能正确挂起协程, 导致 h.destroy() 会使协程帧上的元素被双重销毁. 因此 msvc 需要把销毁投递出去, 在线外执行. 这会带来开销, 并使实际的内存释放变得不确定.
