实现原理

封闭寻址容器

boost::unordered_[multi]set 和 boost::unordered_[multi]map 遵循无序关联容器的标准要求, 因此接口是固定的. 但仍有一些实现决策要做. 优先考虑的是符合标准和可移植性.

Wikipedia 上关于哈希表的文章 对一般哈希表的实现问题有很好的总结.

数据结构

标准通过规定访问容器桶的接口, 实际上要求哈希表使用封闭寻址.

可以设想编写一个使用其他方法的哈希表. 例如, 它可以使用开放寻址, 并让查找链充当桶, 但这样做存在一些严重问题:

  • 标准要求指向元素的指针不得失效, 因此元素不能存储在单个数组中, 而需要一层间接——这失去了开放寻址的主要优势: 效率和大部分内存收益.

  • 局部迭代器会非常低效, 并且可能无法满足复杂度要求.

  • 还有迭代器何时失效的限制. 由于开放寻址在大量冲突时性能急剧恶化, 这些限制可能阻止真正需要的重新哈希. 可以把最大负载因子设置得相当低来绕开这个问题——但标准要求其初始值为 1.0.

  • 而且, 由于标准是以封闭寻址为导向编写的, 如果性能表现与此不符, 用户会感到意外.

因此使用封闭寻址.

桶的数量

为哈希表选择桶数量有两种流行的方法. 一种是使用质数数量的桶, 另一种是使用 2 的幂.

使用质数数量的桶, 并用哈希函数结果的模来选择桶, 通常会给出不错的结果. 缺点是所需的模运算相当昂贵. 过去这些容器在大多数情况下就是这样做的.

使用 2 的幂可以更快地选择要使用的桶, 但代价是丢失哈希值的高位. 对于某些专门设计的哈希函数, 这样做仍能得到好结果, 但由于容器可以接受任意哈希函数, 这一点不能依赖.

为避免这一点, 可以对哈希函数施加一个变换, 例如参见 Thomas Wang 关于整数哈希函数的文章. 遗憾的是, Wang 式的变换需要知道哈希值的位宽, 因此过去只在 size_t 为 64 位时才使用.

从 1.79.0 发布起, 改用 斐波那契哈希. 在这一实现中, 桶编号通过 (h * m) >> (w - k) 确定, 其中 h 是哈希值, m 是 2^w 除以黄金分割比, w 是机器字长 (32 或 64), 2^k 是桶数量. 这在速度和分布之间提供了很好的折中.

从 1.80.0 发布起, 桶数量选择质数, 并配合精细的模运算. 这免除了 1.79.0 发布中所采用的对用户哈希函数结果进行 "混合" 的需要.

开放寻址容器

C++ 标准对无序关联容器的规范对允许的实现施加了严格限制, 其中最重要的是隐式假定封闭寻址. 稍微放宽这一规范, 就有可能提供充分利用开放寻址技术的容器变体.

boost::unordered_flat_set/unordered_node_set 和 boost::unordered_flat_map/unordered_node_map 的设计以 Peter Dimov 的 Boost.Unordered 开发计划 为指导. 这里讨论其中最相关的原则.

哈希函数

鉴于其丰富的功能和跨平台互操作性, boost::hash 仍是开放寻址容器的默认哈希函数. 然而, boost::hash 对整数及其他基本类型的处理并不具备开放寻址所需的统计特性; 为应对这一点, 我们实现了一个后混合阶段:

     a ← h mul C,
     h ← high(a) xor low(a),

其中 mul 是一种 扩展乘法 (64 位架构下为 128 位, 32 位环境下为 64 位), 而 high 和 low 分别是扩展字的高半部分和低半部分. 在 64 位架构中, C 是 264∕φ 的整数部分; 而在 32 位下, C = 0xE817FB2Du 来自 Steele and Vigna (2021).

当使用的哈希函数直接适合开放寻址时, 可以通过专门的 hash_is_avalanching 特征选择不做后混合. boost::hash 针对字符串类型的特化已被标记为雪崩式.

平台互操作性

boost::unordered_flat_set/unordered_node_set 和 boost::unordered_flat_map/unordered_node_map 的可观察行为在不同编译器之间是确定性地相同的, 只要它们的 std::size_t 大小相同, 且用户提供的哈希函数和相等谓词也可互操作——这包括对于相同的操作序列, 元素的排列方式完全一致.

尽管实现在可用时会内部使用 SIMD 技术 (如 SSE2 和 Neon), 但这不影响互操作性. 例如, 在支持 SSE2 的 x64 模式 Intel CPU 上使用 Visual Studio, 与在不支持任何 SIMD 技术的 IBM s390x 上使用 GCC, 行为是相同的.

并发容器

Boost.Unordered 开放寻址容器所用的同一数据结构也被选作 boost::concurrent_flat_set/boost::concurrent_node_set 和 boost::concurrent_flat_map/boost::concurrent_node_map 的基础:

  • 与非并发和并发场景中封闭寻址的替代方案相比, 开放寻址都更快.

  • 开放寻址布局非常适合以最小的锁定进行并发访问和修改. 特别是, 元数据数组可用于实现查找, 直到实际元素比较的最后一步都无锁.

  • 与 Boost.Unordered 平坦容器的布局兼容性, 使得所有元素可以在并发容器与其对应的非并发容器之间 快速转移, 反之亦然.

哈希函数与平台互操作性

在 哈希函数默认值 和 平台互操作性 方面, 并发容器做出与 Boost.Unordered 开放寻址容器相同的决策并提供相同的保证.
