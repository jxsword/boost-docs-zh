并发容器

Boost.Unordered 提供 boost::concurrent_node_set、boost::concurrent_node_map、boost::concurrent_flat_set 和 boost::concurrent_flat_map, 这些哈希表允许来自不同线程的并发写/读访问, 而无需用户侧实现任何同步机制.

std::vector<int>                    input;
boost::concurrent_flat_map<int,int> m;

...

// process input in parallel
const int                 num_threads = 8;
std::vector<std::jthread> threads;
std::size_t               chunk = input.size() / num_threads; // how many elements per thread

for (int i = 0; i < num_threads; ++i) {
  threads.emplace_back([&,i] {
    // calculate the portion of input this thread takes care of
    std::size_t start = i * chunk;
    std::size_t end = (i == num_threads - 1)? input.size(): (i + 1) * chunk;

    for (std::size_t n = start; n < end; ++n) {
      m.emplace(input[n], calculation(input[n]));
    }
  });
}

在上面的示例中, 线程无需同步即可访问 m, 就像单线程场景中那样. 在理想情况下, 如果给定的工作负载分布在 N 个线程上, 执行速度会比单线程快 N 倍——由于同步开销和 争用 (一个线程等待另一个线程离开 map 中被锁定的部分), 这一上限在实践中永远无法达到, 但 Boost.Unordered 并发容器的设计目标是开销极小, 通常能够实现 线性扩展 (即性能与线程数成正比, 上限为 CPU 的逻辑核心数).

基于访问的 API

Boost.Unordered 并发容器的新用户首先会注意到, 这些类 不提供迭代器 (从 C++ 标准的意义上讲, 这使它们在技术上不是 Container). 原因在于迭代器天生是线程不安全的. 考虑这段假想的代码:

auto it = m.find(k);  // A: get an iterator pointing to the element with key k
if (it != m.end() ) {
  some_function(*it); // B: use the value of the element
}

在多线程场景中, 迭代器 it 在 B 点可能已失效——如果其他线程在 A 和 B 之间发出了 m.erase(k) 操作. 有一些设计可以让迭代器锁定其指向的元素来弥补这一问题, 但这种方式容易导致高争用, 并可能在程序中轻易产生死锁. operator[] 也有类似的并发问题, boost::concurrent_flat_map/boost::concurrent_node_map 同样不提供它. 元素访问改为通过所谓的 访问函数 完成:

m.visit(k, [](const auto& x) { // x is the element with key k (if it exists)
  some_function(x);            // use it
});

用户传入的访问函数 (本例中为 lambda 函数) 由 Boost.Unordered 在内部以线程安全的方式执行, 因此它可以访问元素, 而不必担心其他线程干扰这一过程.

另一方面, 访问函数 不能 访问容器本身:

m.visit(k, [&](const auto& x) {
  some_function(x, m.size()); // forbidden: m can't be accessed inside visitation
});

不过, 访问其他容器是允许的:

m.visit(k, [&](const auto& x) {
  if (some_function(x)) {
    m2.insert(x); // OK, m2 is a different boost::concurrent_flat_map
  }
});

但总体而言, 访问函数应尽可能轻量, 以减少争用并提高并行度. 在某些情况下, 将繁重的工作移到访问之外可能更有益:

std::optional<value_type> o;
bool found = m.visit(k, [&](const auto& x) {
  o = x;
});
if (found) {
  some_heavy_duty_function(*o);
}

访问在并发容器提供的 API 中十分突出, 许多经典操作都有支持访问的变体:

m.insert_or_visit(x, [](auto& y) {
  // if insertion failed because of an equivalent element y,
  // do something with it, for instance:
  ++y.second; // increment the mapped part of the element
});

注意, 在最后一个示例中, 访问函数实际上可以 修改 元素: 作为一般规则, 对于并发 map m, 其操作会根据 m 是 const 还是非 const, 授予访问函数对元素的 const/非 const 访问. 始终可以通过使用 cvisit 重载 (例如 insert_or_cvisit) 显式请求 const 访问, 这可能带来更高的并行度. 而对于并发 set, 访问始终是 const 访问.

尽管预计使用频率要低得多, 并发容器也提供这样的插入操作: 在元素创建之后即可立即访问该元素 (除了在已存在等价元素时的常规访问之外):

  m.insert_and_cvisit(x,
    [](const auto& y) {
      std::cout<< "(" << y.first << ", " << y.second <<") inserted\n";
    },
    [](const auto& y) {
      std::cout<< "(" << y.first << ", " << y.second << ") already exists\n";
    });

有关支持访问的操作的完整列表, 请查阅 boost::concurrent_node_set、boost::concurrent_node_map、boost::concurrent_flat_set 和 boost::concurrent_flat_map 的参考.

整表访问

在没有迭代器的情况下, 提供 visit_all 作为处理容器中所有元素的替代方式:

m.visit_all([](auto& x) {
  x.second = 0; // reset the mapped part of the element
});

在实现标准并行算法的 C++17 编译器中, 整表访问可以并行化:

m.visit_all(std::execution::par, [](auto& x) { // run in parallel
  x.second = 0; // reset the mapped part of the element
});

遍历可以中途打断:

// finds the key to a given (unique) value

int  key = 0;
int  value = ...;
bool found = !m.visit_while([&](const auto& x) {
  if(x.second == value) {
    key = x.first;
    return false; // finish
  }
  else {
    return true;  // keep on visiting
  }
});

if(found) { ... }

还有最后一个整表访问操作 erase_if:

m.erase_if([](auto& x) {
  return x.second == 0; // erase the elements whose mapped value is zero
});

visit_while 和 erase_if 也可以并行化. 注意, 为了提高效率, 整表访问操作在执行期间不会阻塞表: 这意味着在访问期间, 其他线程可能插入、修改或擦除元素. 建议不要在程序的任何时点对并发容器的确切全局状态做过多假设.

批量访问

假设你有一个 std::array, 其中存放着想在并发 map 中查找的键:

std::array<int, N> keys;
...
for(const auto& key: keys) {
  m.visit(key, [](auto& x) { ++x.second; });
}

批量访问 允许我们在一次操作中传入所有键:

m.visit(keys.begin(), keys.end(), [](auto& x) { ++x.second; });

不过, 提供这一功能并非仅仅为了语法上的便利: 通过一次性处理所有键, 可以应用一些内部优化, 使性能高于常规的一次一个的情形 (参见 基准测试). 实际上, 缓冲传入的键以便分块批量访问可能更有益:

static constexpr auto bulk_visit_size = boost::concurrent_flat_map<int,int>::bulk_visit_size;
std::array<int, bulk_visit_size> buffer;
std::size_t                      i=0;
while(...) { // processing loop
  ...
  buffer[i++] = k;
  if(i == bulk_visit_size) {
    map.visit(buffer.begin(), buffer.end(), [](auto& x) { ++x.second; });
    i = 0;
  }
  ...
}
// flush remaining keys
map.visit(buffer.begin(), buffer.begin() + i, [](auto& x) { ++x.second; });

这里存在延迟/吞吐量的权衡: 传入的键需要更长时间才能被处理 (因为它们先被缓冲), 但每秒处理的键数量更高. bulk_visit_size 是推荐的分块大小——更小的缓冲区可能带来更差的性能.

阻塞操作

并发容器可以像任何其他 Boost.Unordered 容器一样被复制、赋值、清空和合并. 与大多数其他操作不同, 这些操作是 阻塞 的, 即在复制、赋值、清空或合并操作进行期间, 所有其他线程都被阻止访问所涉及的表. 阻塞由库自动处理, 用户无需采取任何特殊预防措施, 但整体性能可能受到影响.

另一个阻塞操作是 重新哈希, 它或者通过 rehash/reserve 显式发生, 或者在插入期间当表的负载达到 max_load() 时发生. 与非并发容器一样, 在批量插入之前预留空间通常可以加快这一过程.

与非并发容器的互操作性

由于开放寻址容器和并发容器基于相同的内部数据结构, 它们可以从对应的非并发容器高效地移动构造, 反之亦然.

表 1. 并发/非并发互操作性

boost::concurrent_node_set

boost::unordered_node_set

boost::concurrent_node_map

boost::unordered_node_map

boost::concurrent_flat_set

boost::unordered_flat_set

boost::concurrent_flat_map

boost::unordered_flat_map

这种互操作性在多阶段场景中非常方便: 数据处理的一部分并行进行, 而其他步骤是非并发 (或非修改) 的. 在下面的示例中, 我们想从一个巨大的输入单词 vector 构建直方图: 填充阶段可以用 boost::concurrent_flat_map 并行完成, 然后把结果转移到最终容器中.

std::vector<std::string> words = ...;

// Insert words in parallel
boost::concurrent_flat_map<std::string_view, std::size_t> m0;
std::for_each(
  std::execution::par, words.begin(), words.end(),
  [&](const auto& word) {
    m0.try_emplace_or_visit(word, 1, [](auto& x) { ++x.second; });
  });

// Transfer to a regular unordered_flat_map
boost::unordered_flat_map m=std::move(m0);
