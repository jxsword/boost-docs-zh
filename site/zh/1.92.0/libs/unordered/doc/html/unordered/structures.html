数据结构

封闭寻址容器

Boost.Unordered 拥有最快的封闭寻址实现之一, 该方法也通常被称为 链地址法 (separate chaining). 表示该数据结构的示例如下图:

图 1. 简单桶组方法

分配一个 "桶" 数组, 每个桶又指向自己的独立链表. 这使得满足标准的桶迭代要求变得简单. 遗憾的是, 使用这种布局遍历整个容器通常很慢, 因为必须检查每个桶的占用情况, 导致时间复杂度为 O(bucket_count() + size()), 而标准要求的复杂度是 O(size()).

典型的标准实现最终会如下图所示:

图 2. 典型标准方法

值得注意的是, 这种方法只有 libc++ 和 libstdc++ 使用; MSVC Dinkumware 实现采用不同的方法. 关于标准容器的更详细分析可在 此处 找到.

选择这种布局不寻常的数据结构, 是为了通过把所有节点互连成单链表来使整个容器的遍历高效. 你可能还注意到, 桶指向桶元素开始 之前 的节点. 这样做是为了能高效地从链表中移除元素, 而无需引入双向链表. 遗憾的是, 这种数据结构引入了一个必然存在的额外间接层. 例如, 要访问桶的第一个元素, 必须执行类似这样的操作:

auto const idx = get_bucket_idx(hash_function(key));
node* p = buckets[idx]; // first load
node* n = p->next; // second load
if (n && is_in_bucket(n, idx)) {
  value_type const& v = *n; // third load
  // ...
}

采用简单桶组布局时, 只需这样做:

auto const idx = get_bucket_idx(hash_function(key));
node* n = buckets[idx]; // first load
if (n) {
  value_type const& v = *n; // second load
  // ...
}

在实践中, 额外的间接层会对 insert、find 和 erase 等常见操作产生显著的性能影响. 但为了保持容器遍历的快速, Boost.Unordered 引入了一种新颖的数据结构: "桶组". 桶组是桶数组某个子段的固定宽度视图. 它包含一个位掩码 (一个 std::size_t), 用于跟踪桶的占用情况, 还包含两个指针, 使其能与非空组构成双向链表. 示例如下图:

图 3. Boost 采用的新布局

这样, 容器级遍历就变成了遍历非空桶组 (常量时间复杂度的操作), 从而把时间复杂度降回 O(size()). 总的来说, 一个桶组只有 4 个字 (word) 的大小, 它查看 sizeof(std::size_t) * CHAR_BIT 个桶, 这意味着对所有常见实现而言, 桶组为每个桶引入的空间开销只有 4 个位.

开放寻址容器

图中展示了 boost::unordered_flat_set/unordered_node_set 和 boost:unordered_flat_map/unordered_node_map 的基本内部布局.

图 4. Boost.Unordered 使用的开放寻址布局.

与所有开放寻址容器一样, 元素 (对于 boost::unordered_node_set 和 boost::unordered_node_map, 则是指向元素节点的指针) 直接存储在桶数组中. 该数组在逻辑上被划分为 2n 个 组, 每组 15 个元素. 除桶数组外, 还有一个关联的 元数据数组, 含 2n 个 16 字节的字.

图 5. 元数据字的分解.

一个元数据字被划分为 15 个 hi 字节 (每个关联桶一个), 以及一个 溢出字节 (图中为 ofw). hi 的值为:

  • 0, 如果对应的桶为空.

  • 1, 用于编码一种称为 哨兵 的特殊空桶, 它在内部用于在容器被完全遍历后停止迭代.

  • 如果桶被占用, 则为从元素的哈希值得到的 缩减哈希值.

在查找哈希值为 h 的元素时, SSE2 和 Neon 等 SIMD 技术让我们只需少量 CPU 指令就能非常快速地检查完整的元数据字, 并在全部 15 个桶中寻找 h 的缩减值: 不匹配的桶可以被立即丢弃, 而缩减哈希值匹配的桶则需要通过与对应元素的完整比较来检查. 如果要找的元素不存在, 则检查溢出字节:

  • 如果 h mod 8 位置上的位为零, 则查找终止 (且元素不存在).

  • 如果该位被置为 1 (该组已发生 溢出), 则使用 二次探测 检查后续的组, 并重复此过程.

插入在算法上类似: 使用 SIMD 定位空桶, 当越过已满的组时, 将其对应的溢出位设置为 1.

在不支持 SIMD 的架构中, 逻辑布局保持不变, 但元数据字采用我们称为 位交错 的技术进行编码: 这种布局让我们仅使用标准算术和逻辑运算就能以相当不错的性能模拟 SIMD.

图 6. 位交错的元数据字.

并发容器

boost::concurrent_flat_set/boost::concurrent_node_set 和 boost::concurrent_flat_map/boost::concurrent_node_map 使用上述基本 开放寻址布局, 并辅以同步机制.

图 7. Boost.Unordered 使用的并发开放寻址布局.

使用两级同步:

  • 容器级: 使用读写互斥量来控制任何操作对容器的访问. 通常, 即使是修改操作, 这种访问也处于读模式 (即并发模式), 因此就大多数实际用途而言, 此级别不存在线程争用. 仅在重新哈希或执行交换、赋值等容器级操作时, 访问才处于写模式 (阻塞).

  • 组级: 每个 15 槽的组配备一个 8 字节的字, 其中包含:

    • 一个读写自旋锁, 用于对组内任何元素的同步访问.

    • 一个原子 插入计数器, 用于下文所述的乐观插入.

通过使用原子操作访问组元数据, 查找在 (组级) 无锁状态下进行, 直到需要与先前经 SIMD 匹配的元素进行实际比较为止: 只有在那时才使用组的自旋锁.

插入使用以下 乐观算法:

  • 探测序列中初始组的插入计数器的值会在本地记录 (我们把这个值称为 c0).

  • 查找如上所述. 如果查找未找到等价元素, 则为插入寻找可用槽的过程会依次锁定/解锁探测序列中的每个组.

  • 当找到一个可用槽时, 先抢占式地占用它 (设置其缩减哈希值), 并原子地递增插入计数器: 如果在整个操作期间没有其他线程递增该计数器 (通过与 c0 比较来检查), 那么就可以继续完成插入; 否则, 我们回滚并重新开始.

该算法在查找和实际插入两个阶段的争用都非常低, 代价是: 如果其他线程通过从同一个组开始执行成功插入而干扰此过程, 计算可能必须重新开始. 实践中, 重新开始的频率极小, 在我们的一些基准测试中为百万分之几的量级.
