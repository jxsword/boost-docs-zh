哈希表基础

容器由若干 桶 组成, 每个桶可以包含任意数量的元素. 例如, 下图展示了一个 boost::unordered_set, 其 7 个桶中包含 5 个元素: A、B、C、D 和 E (此处仅作说明之用, 容器通常拥有更多的桶).

为了决定将元素放入哪个桶, 容器对元素的键应用哈希函数 Hash (对于 set, 键就是整个元素, 但仍称为键, 以便 set 和 map 使用相同的术语). 该函数返回一个 std::size_t 类型的值. std::size_t 的取值范围远大于桶的数量, 因此容器会对该值再施加一次变换, 以选择放置元素的桶.

获取给定键对应的元素很简单. 对键应用同样的过程即可找到正确的桶. 然后将键与桶中的元素进行比较, 以找出匹配的元素 (使用相等谓词 Pred). 如果哈希函数工作良好, 元素会均匀分布在各个桶中, 因此只需检查少量元素.

还有 更多关于哈希函数与相等谓词的信息, 见下一节.

从图中可以看到, A 和 D 被放入了同一个桶. 在此桶中查找元素时最多需要 2 次比较, 使搜索变慢. 这被称为 冲突. 为了保持速度, 我们尽量将冲突降到最少.

如果我们使用的不是 boost::unordered_set 而是 boost::unordered_flat_set, 则图将如下所示:

在开放寻址容器中, 每个桶最多容纳一个元素; 如果发生冲突 (如示例中的 D), 元素会使用原始位置附近的其他可用桶. 鉴于这种更简单的场景, Boost.Unordered 开放寻址容器为访问桶提供的 API 非常有限.

控制桶的数量

随着向无序关联容器中添加更多元素, 冲突数量会增加, 导致性能下降. 为了应对这一问题, 容器会在插入元素时增加桶数量. 你也可以通过调用 rehash 让容器 (在需要时) 更改桶数量.

标准在如何选择桶数量方面给实现者留下了很大的自由, 但确实基于容器的 负载因子 (元素数除以桶数) 提出了一些要求. 容器还有一个 最大负载因子, 负载因子应尽量保持在它之下.

你无法直接控制桶数量, 但有两种方式可以对其施加影响:

  • 在构造容器时或调用 rehash 时指定桶的最小数量.

  • 通过调用 max_load_factor 建议一个最大负载因子.

max_load_factor 不允许你自行设置最大负载因子, 它只是让你给出一个 提示. 即便如此, 标准实际上也不要求容器太在意这个值. 唯一 要求 负载因子小于最大值的情形是调用 rehash 之后. 但大多数实现都会尽量将元素数量保持在最大负载因子以下, 并把最大负载因子设置为与提示相同或接近的值——除非你的提示小或大到不合理的程度.

size_type max_load() const

返回容器在重新哈希之前允许的最大元素数量.

关于开放寻址容器与并发容器的 max_load 的一点说明: 最大负载将是 (max_load_factor() * bucket_count()), 即紧随 rehash 之后或容器创建之时, 但在高负载情况下擦除元素时可能会略有下降. 例如, 假设我们有一个 boost::unordered_flat_map, 其 size() 几乎处于 max_load() 水平, 然后擦除 1,000 个元素, max_load() 可能会减少大约几十个元素. 这是 Boost.Unordered 在内部为保持性能稳定而采取的做法, 在规划无重新哈希的插入时必须将其考虑在内.
