哈希质量

为了正常工作, 哈希表要求所提供的哈希函数具有 良好的质量, 大致意思是它尽可能均匀地使用其 std::size_t 输出空间, 很像随机数生成器的行为——当然, 哈希函数的值并非随机, 而是严格由其输入参数决定.

Boost.Unordered 的封闭寻址容器对质量欠佳的哈希函数有相当的健壮性, 但开放寻址容器和并发容器对此因素敏感得多, 如果哈希函数不合适, 它们的性能可能急剧下降. 一般来说, 如果你使用 Boost.Hash 提供的或用其生成的函数, 质量是足够的, 但使用其他哈希算法时必须小心.

本节其余内容仅适用于开放寻址容器和并发容器.

哈希后混合与雪崩特性

即使你提供的哈希函数不符合开放寻址所要求的均匀行为, Boost.Unordered 容器的性能也很可能可以接受, 因为库会执行一个内部的 后混合 步骤, 以改善所计算哈希值的统计特性. 这会带来额外的计算开销; 如果不想进行后混合, 请像下面这样注解你的哈希函数:

struct my_string_hash_function
{
  using is_avalanching = std::true_type; // instruct Boost.Unordered to not use post-mixing

  std::size_t operator()(const std::string& x) const
  {
    ...
  }
};

通过设置 hash_is_avalanching 特征, 我们告知 Boost.Unordered: my_string_hash_function 的质量足够好, 可以直接使用而无需任何后混合安全网. 这样做的风险是, 当哈希函数的表现不如我们声明的那样好时, 性能可能下降.

容器统计

如果我们全局定义宏 BOOST_UNORDERED_ENABLE_STATS, 开放寻址容器和并发容器将计算一些与哈希函数质量直接相关的内部统计信息:

#define BOOST_UNORDERED_ENABLE_STATS
#include <boost/unordered/unordered_map.hpp>

...

int main()
{
  boost::unordered_flat_map<std::string, int, my_string_hash> m;
  ... // use m

  auto stats = m.get_stats();
  ... // inspect stats
}

stats 对象提供以下信息:

内部维护三种操作的统计信息: 插入 (不考虑为确定键尚不存在而先做的查找), 成功查找, 以及失败查找 (包括插入元素时内部发出的查找). 探测长度 是每次操作访问的 桶组 数量. 如果哈希函数行为正常:

  • 平均探测长度应接近 1.0.

  • 每次成功查找的平均比较次数应接近 1.0 (即只检查找到的那个元素).

  • 每次失败查找的平均比较次数应接近 0.0.
