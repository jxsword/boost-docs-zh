Boost.Nowide 是什么

Boost.Nowide 是一个最初由 Artyom Beilis 实现的库, 它让跨平台的支持 Unicode 的编程变得更加容易.

本库提供标准 C 与 C++ 库函数的实现, 使它们的输入在 Windows 上支持 UTF-8, 而无需使用 Wide API. 在非 Windows/POSIX 平台上则直接别名为标准库对应物, 因此在那里不做任何转换, 因为那些平台本就普遍使用 UTF-8.

因此, 你可以在所有平台上使用与 std 对应函数同名的 Boost.Nowide 函数来处理窄字符串, 并且它就是能直接工作.

设计理由

问题

考虑一个简单的应用程序, 它把一个大文件切分成多个块, 以便通过电子邮件发送. 它需要完成几个非常简单的任务:

  • 访问命令行参数: int main(int argc,char **argv)
  • 打开一个输入文件, 打开若干输出文件: std::fstream::open(const char*,std::ios::openmode m)
  • 发生故障时删除这些文件: std::remove(const char* file)
  • 在控制台上打印进度报告: std::cout << file_name

遗憾的是, 如果文件名包含非 ASCII 字符, 这个简单的任务在纯 C++ 中是无法实现的.

使用该 API 的简单程序可以在内部使用 UTF-8 的系统上运行 – 这占了绝大多数的类 Unix 操作系统: Linux、Mac OS X、Solaris、BSD. 但在 Microsoft Windows 下, 它对 War and Peace - Война и мир - מלחמה ושלום.zip 这样的文件会失败, 因为 Windows 原生的支持 Unicode 的 API 是 Wide API – UTF-16.

这个极其平常的任务, 要以跨平台的方式实现却非常困难.

解决方案

Boost.Nowide 提供了一组在 Windows 上支持 UTF-8 的标准库函数, 让支持 Unicode 的编程更加容易.

本库提供:

  • 易于使用的 UTF-8 与 UTF-16 互转函数
  • 一个使 argc、argc 与 env 参数在 main 中使用 UTF-8 的类
  • 支持 UTF-8 的函数
    • cstdio 函数:
      • fopen
      • freopen
      • remove
      • rename
    • cstdlib 函数:
      • system
      • getenv
      • setenv
      • unsetenv
      • putenv
    • fstream
      • filebuf
      • fstream/ofstream/ifstream
    • iostream
      • cout
      • cerr
      • clog
      • cin

所有这些函数都在 Boost.Nowide 的同名头文件中提供. 因此, 不必包含 cstdio 并使用 std::fopen, 你只需包含 boost/nowide/cstdio.hpp 并使用 boost::nowide::fopen. 这些函数接受的参数与其 std 对应函数相同; 实际上在非 Windows 构建中它们就是那些函数的别名. 但在 Windows 上, Boost.Nowide 施展它的魔法: 窄字符串参数被解释为 UTF-8, 转换为宽字符串 (UTF-16), 然后传给能正确处理特殊字符的 wide API.

如果传入的字符串含有非 UTF-8 字符, 转换会将其替换为替换字符 (默认: U+FFFD), 与 NT 内核的做法类似. 这意味着无效的 UTF-8 序列无法从 narrow->wide->narrow 完整往返, 例如文件名损坏时会导致无法打开文件.

为什么不既提供窄字符又提供宽字符?

为什么不同时提供 Wide 和 Narrow 两种实现, 让开发者可以选择在类 Unix 平台上使用宽字符?

有以下几个原因:

  • wchar_t 并不真正可移植, 它可能是 2 字节、4 字节甚至 1 字节, 这让支持 Unicode 的编程更加困难
  • C 与 C++ 标准库在与操作系统交互时使用窄字符串. 本库遵循同样的总体规则. 标准库中不存在 fopen(const wchar_t*, const wchar_t*) 这样的东西, 因此与其以 "Microsoft Windows 风格" 重新实现 Wide API, 不如遵循标准

替代方案

自 2019 年 5 月更新起, Windows 10 通过清单 (manifest) 文件为窄字符串支持 UTF-8. 因此, 把 "UTF-8" 设为活动代码页后, 无需任何其他更改即可在窄 API 中使用 UTF-8 编码的字符串. 详见 相关文档.

自 2018 年 4 月起, Windows 10 提供 (测试版) 功能, 允许通过用户设置默认使用 UTF-8 代码页.

两种方法都可行, 但都有一个重大缺陷: 对应用程序开发者而言并非完全可靠. 清单方式设置的代码页在低于 1903 的 Windows 版本上会回退到旧代码页, 因此只有目标系统是 2019 年 5 月之后的 Windows 10 时才可用.
第二种方法依赖用户在启动程序之前的交互操作. 显然, 若代码中只期望 UTF-8, 这并不可靠.

此外, 自 Windows 10 1803 (即 2018 年 4 月) 起, 可以通过编程方式把当前代码页设为 UTF-8, 例如 setlocale(LC_ALL, ".UTF8");. 这使许多函数接受或产生 UTF-8 编码的字符串, 这对 std::filesystem::path 及其 string() 函数尤其有用. 详见 相关文档. 虽然这对大多数函数有效, 但对例如程序参数 (main 的 argv 与 env 参数) 无效.

因此, 在某些情况下 (并且希望将来总能如此), 本库将不再必要, 甚至 Windows I/O 也能直接使用 UTF-8 编码的文本.

使用本库

构建本库

Boost.Nowide 通常作为 Boost 的一部分通过 b2 构建.
它需要 C++11 特性, 若有缺失, 本库将不会构建.

如果意外出现这种情况, 请留意配置检查输出中类似 cxx11_constexpr : no 的内容.
这意味着你的编译器未使用 C++11 (或更高版本), 例如默认使用 C++03. 你可以给 b2 传入 cxxstd=11 以 C++11 模式构建.

也支持使用 Boost CMake 构建系统进行构建.
为此可运行例如 cmake -DBOOST_INCLUDE_LIBRARIES=nowide <path-to-boost-root> <other options>.

标准特性

作为开发者, 你应当使用 boost::nowide 函数, 而不是 std 命名空间中可用的函数.

例如, 下面是一个不支持 Unicode 的行计数器实现:

#include <fstream>
#include <iostream>
int main(int argc,char **argv)
{
if(argc!=2) {
std::cerr << "Usage: file_name" << std::endl;
return 1;
}
std::ifstream f(argv[1]);
if(!f) {
std::cerr << "Can't open " << argv[1] << std::endl;
return 1;
}
int total_lines = 0;
while(f) {
if(f.get() == '\n')
total_lines++;
}
f.close();
std::cout << "File " << argv[1] << " has " << total_lines << " lines" << std::endl;
return 0;
}

为了让这个程序正确处理 Unicode, 我们做如下修改:

#include <boost/nowide/args.hpp>
#include <boost/nowide/fstream.hpp>
#include <boost/nowide/iostream.hpp>
int main(int argc,char **argv)
{
boost::nowide::args a(argc,argv); // 修正参数 - 把它们变成 UTF-8
if(argc!=2) {
boost::nowide::cerr << "Usage: file_name" << std::endl; // 支持 Unicode 的控制台
return 1;
}
boost::nowide::ifstream f(argv[1]); // argv[1] - 是 UTF-8
if(!f) {
// 控制台可以显示 UTF-8
boost::nowide::cerr << "Can't open " << argv[1] << std::endl;
return 1;
}
int total_lines = 0;
while(f) {
if(f.get() == '\n')
total_lines++;
}
f.close();
// 控制台可以显示 UTF-8
boost::nowide::cout << "File " << argv[1] << " has " << total_lines << " lines" << std::endl;
return 0;
}

注意 boost::nowide::args、boost::nowide::ifstream 和 boost::nowide::cerr/cout 的用法. 在非 Windows 平台上它们什么也不做, 但在 Windows 上会发生以下事情:

  • boost::nowide::args 从 Windows API 获取 UTF-16 参数, 把它们转换为 UTF-8, 并在实例生存期内临时用指向这些内部保存的 UTF-8 字符串的指针替换原始的 argv (以及可选的 env).
  • boost::nowide::ifstream 把传入的文件名 (现在是有效的 UTF-8) 转换为 UTF-16, 并调用 Windows Wide API 打开文件流, 之后即可照常使用.
  • 类似地, boost::nowide::cerr 与 boost::nowide::cout 使用一个底层流缓冲区把 UTF-8 字符串转换为 UTF-16, 并用另一个 Wide API 函数把它写到控制台.

自定义 API

当然, 这组简单的函数并不能满足所有需求. 如果在内部使用 UTF-8 的 Windows 应用程序中需要访问 Wide API, 可以使用函数 boost::nowide::widen 和 boost::nowide::narrow.

例如:

CopyFileW( boost::nowide::widen(existing_file).c_str(),
boost::nowide::widen(new_file).c_str(),
TRUE);

boost::nowide::widen 返回 std::string. 有时避免分配并改用栈上缓冲区会很有用. Boost.Nowide 为此提供了 boost::nowide::basic_stackstring 类.

上面的示例可以改写为:

boost::nowide::basic_stackstring<wchar_t,char,64> wexisting_file(existing_file), wnew_file(new_file);
CopyFileW(wexisting_file.c_str(), wnew_file.c_str(), TRUE);

windows.h 头文件

本库不包含 windows.h, 以避免大量宏定义与类型造成的命名空间污染. 作为替代, 本库自行声明 Win32 API 函数的原型.

不过, 若要使用 windows.h 头文件, 可以在包含任何 Boost.Nowide 头文件之前定义 BOOST_USE_WINDOWS_H

与 Boost.Filesystem 集成

Boost.Filesystem 支持选择窄编码. 遗憾的是 Windows 上默认的窄编码不是 UTF-8. 但你可以在程序开头调用 boost::nowide::nowide_filesystem(), 为 Boost.Filesystem 启用 UTF-8 作为默认编码; 该调用会注入一个带 UTF-8 转换刻面的 locale, 用于在 char 与 wchar_t 之间转换. 这样, 传入和传出 boost::filesystem::path 的所有窄字符串在被转换为宽字符串 (内部存储所需) 时都被解释为 UTF-8. 在 POSIX 上这通常没有效果, 因为窄字符串就是存储格式, 不做转换.

对于 C++17 起可用的 std::filesystem::path, 无法注入 locale. 不过 u8string() 成员函数可用于从 path 获取 UTF-8 编码的字符串. 而要从 UTF-8 编码的字符串获得 path, 可以使用 std::filesystem::u8path, 或从 C++20 起使用接受 char8_t 类型输入的某个 path 构造函数.

从流中读/写 std::filesystem::path 实例时, 通常会使用例如 os << path. 但这实际上相当于执行 os << std::quoted(path.string()), 意味着可能转换为未必是 UTF-8 编码的窄字符串. 为此可以使用 quoted:

#include <boost/nowide/quoted.hpp>
#include <filesystem>
#include <sstream>
std::string write(const std::filesystem::path& path)
{
std::ostringstream s;
s << boost::nowide::quoted(path);
return s.str();
}
std::experimental::path read(std::istream& is)
{
std::filesystem::path path;
is >> boost::nowide::quoted(path);
return path;
}

技术细节

Windows 与 POSIX

对于 Microsoft Windows, 本库为 std: 的一部分 (即 boost::nowide 命名空间中的函数) 提供支持 UTF-8 的变体. 例如, std::fopen 变为 boost::nowide::fopen.

在 POSIX 平台下, boost::nowide 中的函数是其标准库对应物的别名:

namespace boost {
namespace nowide {
#ifdef BOOST_WINDOWS
inline FILE *fopen(const char* name, const char* mode)
{
...
}
#else
using std::fopen
#endif
} // nowide
} // boost
boost::nowide::fopen
FILE * fopen(const char *file_name, const char *mode)
与 fopen 相同, 但 file_name 和 mode 是 UTF-8 字符串.

Windows 上还提供了一个 std::filebuf 兼容的实现, 为 open 支持 UTF-8 文件路径, 其余行为 (API 层面) 完全相同.

在所有系统上, 都以自定义实现的方式提供 std::fstream 类及相关类, 支持 std::string 与 *::filesystem::path, 以及 wchar_t* (仅 Windows) 的构造函数与 open 重载. 这样, 用户无需依赖 C++17 支持即可使用例如 boost::filesystem::path 配合 boost::nowide::fstream. 此外, 任何路径类只要与 std::filesystem::path 的接口匹配得 "足够" 好, 就受支持.

注意, path 与 std::string 在 boost::nowide::filebuf 中并没有普遍支持. 原因是在非 Windows 系统上使用的是 std 变体, 它在某些情况下可能更快. 由于用户代码很少直接使用 filebuf, 而是经由 fstream 间接使用, 不提供 string 或 path 支持似乎代价不大, 尤其是 C++11 增加了 std::string 支持, C++17 增加了 path 支持, 且经由 string_or_path.c_str() 使用仍然可行且可移植.

控制台输入输出

当流连接到 "真实" 控制台时, 控制台输入输出通过封装 ReadConsoleW/WriteConsoleW 实现. 当流被管道化/重定向时, 则改用标准 cin/cout.

这种方法免去了手动处理代码页的必要. 若使用 TrueType 字体, 支持 Unicode 的输入输出可按预期工作.

问答 (Q & A)

问: 传经 Boost.Nowide 的无效 UTF 会怎样? 例如 Windows 使用 UCS-2 而不是 UTF-16.

答: Boost.Nowide 的策略是始终产出有效的 UTF 编码字符串. 因此无效的 UTF 字符会被替换字符 U+FFFD 取代.

这在两个方向上都会发生:
向 Boost.Nowide 传入 (假定的) UTF-8 编码字符串时, 它会将其转换为 UTF-16, 并在传给操作系统之前替换每个无效字符.
从操作系统获取值时 (例如 boost::nowide::getenv 或经由 boost::nowide::args 的命令行参数), 该值被假定为 UTF-16 并被转换为 UTF-8, 同时替换任何无效字符.

这意味着, 如果有人设法在 Windows 中创建了一个无效的 UTF-16 文件名, 那么 Boost.Nowide 将无法处理它. 但由于 Microsoft 在 Windows 2000 中已从 UCS-2 (即任意 2 字节值的字符串) 切换到 UTF-16, 在大多数环境中这不会成为问题.

问: 使用何种错误报告方式?

答: 实际上有 3 种:

  • 无效的 UTF 编码字符串的处理方式是把无效字符替换为替换字符 U+FFFD
  • 镜像标准 API 的 API 调用采用与之相同的错误报告方式, 例如失败时返回非零值
  • 不可继续的错误通过标准异常报告. 最主要的例子是经由 WinAPI 获取命令行参数失败

问: 在 POSIX 系统上, 为什么本库不在字符串与 locale 编码之间进行转换 (而使用 UTF-8)?

答: 在 POSIX 平台上, 在字符串与本地化编码之间来回转换本身就是不正确的做法.

你可以创建一个名为 "\xFF\xFF.txt" 的文件 (无效 UTF-8), 删除它, 把它的名字作为参数传给某个程序, 无论当前 locale 是否是 UTF-8 都能正常工作. 而且, 把 locale 从比如 en_US.UTF-8 改为 en_US.ISO-8859-1, 也不会神奇地改变操作系统中的所有文件或用户可能传给程序的字符串 (这在 Windows 上则不同)

POSIX 操作系统把字符串当作以 NULL 结尾的不透明数据块.

因此按 locale 修改其内容实际上会导致不正确的行为.

例如, 下面是标准程序 "rm" 的一个朴素实现:

#include <cstdio>
int main(int argc,char **argv)
{
for(int i=1;i<argc;i++)
std::remove(argv[i]);
return 0;
}

它在任何 locale 下都能工作, 而修改这些字符串会导致不正确的行为.

locale 在 POSIX 与 Windows 平台上的含义不同, 效果也大相径庭.

独立版

可以不依赖庞大的 Boost 工程来使用 Nowide 库. 有一个独立版本, 它在 nowide 命名空间 (而非 boost::nowide) 中提供全部功能.

上面的示例将如下所示:

#include <nowide/args.hpp>
#include <nowide/fstream.hpp>
#include <nowide/iostream.hpp>
int main(int argc,char **argv)
{
nowide::args a(argc,argv); // 修正参数 - 把它们变成 UTF-8
if(argc!=2) {
nowide::cerr << "Usage: file_name" << std::endl; // 支持 Unicode 的控制台
return 1;
}
nowide::ifstream f(argv[1]); // argv[1] - 是 UTF-8
if(!f) {
// 控制台可以显示 UTF-8
nowide::cerr << "Can't open a file " << argv[1] << std::endl;
return 1;
}
int total_lines = 0;
while(f) {
if(f.get() == '\n')
total_lines++;
}
f.close();
// 控制台可以显示 UTF-8
nowide::cout << "File " << argv[1] << " has " << total_lines << " lines" << std::endl;
return 0;
}

独立版本仅支持用 CMake 构建. CMake 选项以 NOWIDE_ 为前缀, 即 -DNOWIDE_INSTALL=ON/OFF 与 -DNOWIDE_WERROR=ON/OFF.
