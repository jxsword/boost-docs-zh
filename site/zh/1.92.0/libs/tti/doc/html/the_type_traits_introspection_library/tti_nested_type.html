嵌套类型

除了查询类型中是否存在具有给定名称的内部元素这一 TTI 库功能之外, 该库还包含生成嵌套类型的功能 — 若嵌套类型存在则生成它, 否则生成标记类型. 标记类型指由库内部创建的、没有任何功能的类型, 或由最终用户指定来表示同一概念的类型.

我将先解释该功能的语法和用法, 然后解释它存在于库中的原因.

该功能是由宏 BOOST_TTI_MEMBER_TYPE 创建的元函数. 该宏接受单个参数, 即一个嵌套类型的名称. 我们将其称为 “已命名类型” (named type). 该宏生成一个名为 member_type_'named_type' 的元函数, 传入外围类型后, 若该命名类型存在则返回它, 否则返回标记类型.

与我们的其他宏一样, 可以使用宏的替代形式 BOOST_TTI_TRAIT_MEMBER_TYPE 先传入要生成的元函数的名称, 再传入 “已命名类型” 的名称. 此后生成的元函数功能完全相同.

它的一般解释如下:

该功能的一个简单示例是:

#include <boost/tti/member_type.hpp>

BOOST_TTI_MEMBER_TYPE(ANamedType)

typedef typename member_type_ANamedType<EnclosingType>::type AType;

如果类型 'ANamedType' 是 'EnclosingType' 的嵌套类型, 则 AType 与 'ANamedType' 是相同的类型; 否则 AType 是 TTI 库内部的标记类型.

既然已经解释了 BOOST_TTI_MEMBER_TYPE 的语法, 我们现在可以回答这个问题: 为什么在查找外围类型的嵌套类型时, 需要有创建 'type' 的这一功能.

问题所在

TTI 宏生成的元函数都要使用各种类型 — 无论是指定外围类型, 还是指定某个内部元素的类型 (这可能还涉及该元素签名中的类型, 例如函数的参数或返回类型). 给定外围类型 'T' 和内部类型 'InnerType', C++ 表示嵌套类型的记法是 'T::InnerType'. 如果外围类型 'T' 不存在, 或者内部类型 'InnerType' 不存在于 'T' 中, 那么当我们在 TTI 某个宏元函数的模板实例化中试图使用表达式 'T::InnerType' 时, 它会产生编译器错误.

如果我们希望能够在不产生编译器错误的情况下内省外围类型内部元素的存在性, 这就是一个问题. 当然, 如果我们确切知道自己拥有的类型且嵌套类型存在, 并且这些声明在我们的作用域内, 我们总是可以不出错地使用 'T::InnerType' 这样的表达式. 但在模板编程中往往不是这样, 因为编译期传给我们的类型 (在类或函数模板中) 是在实例化时才确定的, 由模板的使用者创建.

库本身提供了一种解决方案. 给定一个我们知道必然存在的外围类型 'T' (或者因为它是我们知道的顶层类型, 或者因为它以 'class T' 或 'typename T' 的形式从某个模板传给我们), 以及一个我们希望确认其存在性的名为 'InnerType' 的内部类型, 我们可以使用 BOOST_TTI_HAS_TYPE(InnerType) 宏及其相关的 has_type_InnerType 元函数来确定嵌套类型 'InnerType' 是否存在. 这个方案完全有效, 并且配合 Boost MPL 的选择元函数, 我们可以进行编译期选择来生成正确的模板代码.

然而, 如果我们需要从顶层外围类型继续深入到深层的嵌套类型, 甚至查找某个深层嵌套类型的内部元素, 这种方案在语法上的伸缩性并不好. 我们将不得不生成大量 boost::mpl::if_ 和/或 boost::mpl::eval_if 类型选择语句, 才能到达某个最终条件, 在那里我们才能确定可以生成想要的编译期代码.

解决方案

BOOST_TTI_MEMBER_TYPE 给出的解决方案是: 我们可以把元函数的返回创建为一个类型, 若嵌套类型存在则它与该嵌套类型相同, 否则为某个其他标记类型, 然后在不产生编译器错误的情况下使用该返回的类型. 如果我们必须使用 'T::InnerType' 语法来指定我们的类型 (其中 'T' 代表外围类型, 'InnerType' 代表嵌套类型), 而外围类型 'T' 中并不存在嵌套类型 'InnerType', 编译器会立即报错.

使用 BOOST_TTI_MEMBER_TYPE 后, 即使这样的类型实际上并不存在, 我们也有一个可以使用的类型. 自然, 如果类型不存在, 我们拿到的类型 (标记类型) 通常不会满足我们想要的任何进一步功能. 这很好, 在进行元函数编程时对该类型的后续使用通常会给出正确结果. 偶尔, 当嵌套类型不存在时, TTI 生成的标记类型不足以进行进一步的元函数编程. 在这种罕见情况下, 最终用户可以提供自己的标记类型, 以便在嵌套类型不存在时使用. 无论如何, 无论嵌套类型存在与否, 无论使用的是 TTI 默认提供的标记类型还是最终用户的标记类型, 模板元编程都可以继续进行而没有编译问题. 此外, 这比在复杂的模板元编程代码中不得不通过 BOOST_TTI_HAS_TYPE 反复检查嵌套类型的存在性有更好的伸缩性.

检查成员类型是否存在

一旦使用 BOOST_TTI_MEMBER_TYPE 生成了嵌套类型 (如果它存在), 我们通常会在进一步的元函数编程中使用该类型. 偶尔, 对于生成的类型, 我们会想问它究竟是我们的嵌套类型还是标记类型. 本质上, 我们是在问生成的类型是否为标记类型. 如果是标记类型, 那么生成的类型就不是我们希望的嵌套类型; 如果不是标记类型, 那么生成的类型就是我们希望的嵌套类型. 对模板元编程者来说这不难做到, 但 TTI 通过提供两个元函数之一来简化这一计算. 这两个元函数是 'boost::tti::valid_member_type' 和 'boost::tti::valid_member_metafunction':

在第一个元函数 'boost::tti::valid_member_type' 中, 第一个参数是调用 BOOST_TTI_MEMBER_TYPE 生成的元函数所返回的 'type'. 如果调用该元函数时指定了用户自定义标记类型, 那么第二个可选参数就是该标记类型, 否则无需指定可选的第二个模板参数. 由于标记类型被保存为嵌套类型 boost::tti::marker_type, 一旦我们调用了 BOOST_TTI_MEMBER_TYPE 生成的元函数, 我们始终可以把它作为 'boost::tti::valid_member_type' 的第二个模板参数 (如果我们愿意).

第二个元函数 boost::tti::valid_member_metafunction 让传递嵌套 'type' 和标记类型的过程更容易一些. 这里唯一的模板参数就是 BOOST_TTI_MEMBER_TYPE 生成的被调用元函数本身. 它会从被调用元函数中同时取出返回的 'type' 和嵌套的 boost::tti::marker_type 来完成正确的计算.

该功能的一个简单示例是:

#include <boost/tti/member_type.hpp>

struct UDMarkerType { };

BOOST_TTI_MEMBER_TYPE(ANamedType)

typedef member_type_ANamedType<EnclosingType> IMType;
typedef member_type_ANamedType<EnclosingType,UDMarkerType> IMTypeWithMarkerType;

then 

boost::tti::valid_member_type<IMType::type>::value
boost::tti::valid_member_type<IMTypeWithMarkerType::type,IMTypeWithMarkerType::boost_tti_marker_type>::value

或者

boost::tti::valid_member_metafunction<IMType>::value
boost::tti::valid_member_metafunction<IMTypeWithMarkerType>::value

给出我们的编译期结果.

一个扩展的嵌套类型示例

作为一个扩展示例, 给定类型 T, 让我们创建一个元函数, 其中存在一个嵌套类型 FindType, 其外围类型最终是 T, 如以下结构所示:

struct T
  {
  struct AType
    {
    struct BType
      {
      struct CType
        {
        struct FindType
          {
          };
        }
      };
    };
  };

在我们的 TTI 代码中, 首先为每个嵌套类型创建一系列成员类型宏:

BOOST_TTI_MEMBER_TYPE(AType)
BOOST_TTI_MEMBER_TYPE(BType)
BOOST_TTI_MEMBER_TYPE(CType)
BOOST_TTI_MEMBER_TYPE(FindType)

接下来, 通过实例化我们的宏元函数, 可以创建一个反映名为 FindType 的嵌套类型 (具有上述关系) 的 typedef. 我们必须按与上面假想的 'struct T' 相反的顺序来做, 因为元函数 BOOST_TTI_MEMBER_TYPE 把外围类型作为其模板参数.

typedef typename
member_type_FindType
  <
  typename member_type_CType
    <
    typename member_type_BType
      <
      typename member_type_AType
        <
        T
        >::type
      >::type
    >::type
  >::type MyFindType;

我们可以使用上面的 typedef 把类型作为 FindType 传给我们的某个宏元函数. FindType 可能实际上并不存在, 但我们使用它时不会产生编译器错误. 如果它不存在, 只会导致使用该类型的任何元函数在编译期返回 false 值的最终失败.

举个例子, 让我们问 FindType 是否拥有名为 MyData、类型为 'int' 的静态成员数据. 我们加上:

BOOST_TTI_HAS_STATIC_MEMBER_DATA(MyData)

接下来创建我们的元函数:

has_static_member_data_MyData
  <
  MyFindType,
  int
  >

并在元编程代码中使用它. 我们的元函数现在告诉我们嵌套类型 FindType 是否拥有名为 MyData、类型为 'int' 的静态成员数据, 即使 FindType 并未按我们指定为类型的方式实际存在. 如果我们尝试用普通 C++ 嵌套类型记法来做, 上面的元函数代码将是:

has_static_member_data_MyData
  <
  typename T::AType::BType::CType::FindType,
  int
  >

但如果没有这样的嵌套类型, 这会因编译器错误而失败, 而这正是我们在编译期元编程代码中不希望发生的.

在上面的元函数中, 我们在询问 FindType 是否拥有名为 'MyData' 的静态成员数据元素; 若 FindType 不存在, 或者它存在但没有名为 'MyData' 的 'int' 类型静态成员数据, 结果将是 'false'. 两种情况都不会产生编译器错误.

我们可能还想确认深层嵌套类型 'FindType' 是否实际存在. 使用 BOOST_TTI_MEMBER_TYPE 并重复上面的宏, 我们的元函数可以是:

BOOST_TTI_MEMBER_TYPE(FindType)
BOOST_TTI_MEMBER_TYPE(AType)
BOOST_TTI_MEMBER_TYPE(BType)
BOOST_TTI_MEMBER_TYPE(CType)

BOOST_TTI_HAS_TYPE(FindType)

has_type_FindType
  <
  typename
  member_type_CType
    <
    typename
    member_type_BType
      <
      typename
      member_type_AType
        <
        T
        >::type
      >::type
    >::type
  >

但这会在生成 'MyFindType' typedef 时重复我们的大量代码. 因此我们改用 'boost::tti::valid_member_type' 已经提供的功能. 对上面的 'MyFindType' 类型使用该功能, 我们创建无参元函数:

boost::tti::valid_member_type
  <
  MyFindType
  >

而不是用我们的 'has_type_FindType' 元函数复刻相同的功能.
