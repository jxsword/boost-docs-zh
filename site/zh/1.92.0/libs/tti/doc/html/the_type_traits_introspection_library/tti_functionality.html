宏元函数名称生成的注意事项

模板元编程者可能在编译期想要了解的类型元素包括:

  • 它是否拥有具有特定名称的嵌套类型 ?
  • 它是否拥有具有特定名称、且满足该嵌套类型某种其他可能性的嵌套类型.
  • 它是否拥有具有特定名称的特定用户自定义嵌套类型 (结构体/类、联合体或枚举) ?
  • 它是否拥有具有特定名称、且满足该嵌套类型某种其他可能性的特定用户自定义嵌套类型.
  • 它是否拥有具有特定名称的嵌套类模板 ?
  • 它是否拥有具有特定名称和特定签名的嵌套类模板 ?
  • 它是否拥有具有特定名称和特定实例化签名的嵌套成员函数模板 ?
  • 它是否拥有具有特定名称和特定实例化签名的嵌套静态函数模板 ?
  • 它是否拥有具有特定名称和特定签名的成员函数 ?
  • 它是否拥有具有特定名称和特定类型的成员数据 ?
  • 它是否拥有具有特定名称和特定签名的静态成员函数 ?
  • 它是否拥有具有特定名称和特定类型的静态成员数据 ?
  • 它是否拥有具有特定名称和特定类型的成员数据或静态成员数据 ?
  • 它是否拥有具有特定名称和特定类型的成员函数或静态成员函数 ?

这些是 TTI 库所回答的一部分编译期问题. 它通过使用 C++ 宏创建可在编译期使用的元函数来做到这一点. 创建的每个元函数都返回一个编译期常量布尔值, 在编译期回答上述问题之一. 当上述特定元素存在时, 该值为 'true' — 更准确地说是 boost::mpl::true_; 若元素不存在, 该值为 'false' — 更准确地说是 boost::mpl::false_. 无论哪种情况, 该值的类型都是 boost::mpl::bool_.

按照 Boost MPL 库的术语, 这个常量布尔值称为 “整型常量包装器” (integral constant wrapper), 生成的元函数称为 “数值元函数” (numerical metafunction). 调用元函数得到的结果可以传给其他元函数用于类型选择, 其中最常用的是 Boost MPL 库中的布尔值运算符.

上述所有问题都试图对具有特定名称的内部元素找到答案. 为了用模板元编程做到这一点, 需要使用宏, 以便内部元素的名称可以传给宏. 宏随后会生成相应的元函数, 模板元编程者可以用它来内省所需的信息. 内部元素本身的名称总是作为宏参数传给宏, 但在某些情况下可能还需要其他宏参数.

所有宏都以 BOOST_TTI_ 前缀开头, 在用户调用宏的任何作用域中把元函数创建为类模板, 并有以下两种形式:

  1. 在最简单的宏形式 (我称之为简单宏形式) 中, 内部元素的 'name' 直接用于生成元函数的名称, 同时也作为要内省的 'name'. 在从宏名生成元函数名时, 会去掉 BOOST_TTI_ 前缀, 将宏名的其余部分改为小写, 并追加一个下划线 ( '_' ) 加上 'name'. 例如, 对于宏 BOOST_TTI_HAS_TYPE(MyType), 元函数的名称是 has_type_MyType, 它将查找名为 'MyType' 的内部类型.
  2. 在更复杂的宏形式 (我称之为复杂宏形式) 中, 宏以 BOOST_TTI_TRAIT_ 开头, 第一个参数传入 'trait' 名称, 第二个参数传入内部元素的 'name'. 'trait' 名称的唯一作用是在宏被调用的作用域中完整命名元函数. 例如, 对于宏 BOOST_TTI_TRAIT_HAS_TYPE(MyTrait,MyType), 元函数的名称是 MyTrait, 它将查找名为 MyType 的内部类型.

每个宏元函数都有简单宏形式和对应的复杂宏形式. 一旦对特定类型的内部元素使用了这两种宏形式中的任何一种, 对应的宏元函数的工作方式就完全相同, 功能也完全一致.

在后续文档中, 所有宏元函数都将以其简单形式名称来指代, 但请记住, 复杂形式始终可以作为替代使用. 当使用简单形式可能在同一命名空间中造成重名、从而违反 C++ 单一定义规则时, 复杂形式非常有用.

宏元函数名称的生成

对于简单宏形式, 尽管记住生成元函数命名的算法相当容易, TTI 还为每个宏元函数提供了一个相应的 “命名” 宏供最终用户使用, 其唯一目的就是展开为元函数名. 每个宏元函数的命名宏形式为: 'corresponding-macro'_GEN(name).

例如, BOOST_TTI_HAS_TYPE(MyType) 创建一个在某个外围类型中查找名为 'MyType' 的嵌套类型的元函数. 根据上面的规则, 生成的元函数名为 'has_type_MyType'. 相应的宏 BOOST_TTI_HAS_TYPE_GEN (在我们的例子中以 BOOST_TTI_HAS_TYPE_GEN(MyType) 调用) 展开为同样的 'has_type_MyType' 名称. 对于每个生成元函数的宏都有这样的名称生成宏, 对觉得使用它们比记住上述命名规则更容易的最终用户来说纯属便利.

宏元函数名称生成的注意事项

由于名称中含有双下划线 ( __ ) 被 C++ 实现保留, 最终用户应避免创建带双下划线的 C++ 标识符. 使用 TTI 宏以简单宏形式生成元函数时, TTI 会在被内省元素的名称之前为宏名追加一个下划线. 这样做的原因是: Boost 不鼓励使用大小写字母混合的不可移植 C++ 标识符, 下划线于是成为分隔标识符名称各部分、使其看起来可理解的常规方式. 由于决定使用下划线从宏名生成元函数名, 任何以下划线开头的内部元素都会导致生成的元函数名标识符包含双下划线.

避免这一问题的规则是:

  • 当要内省的内部元素名称以下划线开头时, 请使用复杂宏形式, 其中明确给出元函数的名称.

此外, 由于 TTI 经常不仅为最终用户生成一个元函数, 还会生成一些辅助性细节元函数 — 出于编程清晰性的考虑, 这些辅助元函数的标识符与主元函数相同, 只是追加了以下划线分隔的其他字母 — 因此还有另一条规则:

  • 使用复杂宏形式 (它完整给出所生成宏元函数的名称) 时, 该名称不应以下划线结尾.

遵循这两条简单规则将避免 TTI 生成带双下划线的名称.

复用已命名的元函数

当最终用户使用 TTI 宏生成用于内省特定类型内部元素的元函数时, 该元函数可以在涉及同名同类型内部元素的任何有效模板参数组合下复用.

举一个例子, 考虑两个不同的用户自定义类型 'AType' 和 'BType', 对每个类型我们都想确定名为 'InnerType' 的内部类型是否存在. 对这两个类型, 我们只需在当前作用域中使用以下代码生成一个宏元函数:

BOOST_TTI_HAS_TYPE(InnerType)

现在我们在当前作用域中有了一个元函数 (它是一个 C++ 类模板), 其 C++ 标识符是 'has_type_InnerType'. 我们可以用同一个元函数在编译期内省 'AType' 或 'BType' 中嵌套类型 'InnerType' 的存在性. 虽然尚未解释这样做的语法, 我还是在这里给出, 以便你看到 'has_type_InnerType' 是如何被复用的:

  1. 'has_type_InnerType<AType>::value' 是一个编译期常量, 告诉我们 'InnerType' 是否是嵌套在 'AType' 中的类型.
  2. 'has_type_InnerType<BType>::value' 是一个编译期常量, 告诉我们 'InnerType' 是否是嵌套在 'BType' 中的类型.

作为元函数复用的另一个例子, 考虑单一用户自定义类型 'CType', 我们想确定它是否拥有两个名为 'AMemberFunction' 的重载成员函数之一, 二者函数签名不同, 分别为 'int (int)' 和 'double (long)'. 对这两个成员函数, 我们只需在当前作用域中使用以下代码生成一个宏元函数:

BOOST_TTI_HAS_MEMBER_FUNCTION(AMemberFunction)

现在我们在当前作用域中有了一个元函数 (它是一个 C++ 类模板), 其 C++ 标识符是 'has_member_function_AMemberFunction'. 我们可以用同一个元函数在编译期内省 'CType' 中成员函数 'AMemberFunction' 以函数签名 'int (int)' 或 'double (long)' 的存在性. 虽然尚未解释这样做的语法, 我还是在这里给出, 以便你看到 'has_type_InnerType' 是如何被复用的:

  1. 'has_member_function_AMemberFunction<CType,int,boost::mpl::vector<int> >::value' 是一个编译期常量, 告诉我们 'AMemberFunction' 是否是类型 'CType' 的函数签名为 'int (int)' 的成员函数.
  2. 'has_member_function_AMemberFunction<CType,double,boost::mpl::vector<long> >::value' 是一个编译期常量, 告诉我们 'AMemberFunction' 是否是类型 'CType' 的函数签名为 'double (long)' 的成员函数.

这些只是特定宏元函数可被复用的方式中的两个例子. 生成宏元函数时的两个 “常量” 是 'name' 和 '内部元素的类型'. 一旦为特定名称和内部元素类型生成了宏元函数, 它就可以复用于内省任何拥有与该名称和内部元素类型对应内部元素的外围类型.

避免 ODR 违规

TTI 宏元函数直接生成在调用相应宏的外围作用域中. 该外围作用域可以是任何可以指定类模板的 C++ 作用域. 在该外围作用域内, 正在生成的元函数的名称必须唯一, 否则会发生 C++ ODR (单一定义规则) 违规. 记住这一点极其重要, 尤其是当外围作用域可能出现在多个翻译单元中时 — 命名空间和全局作用域就是这种情况.

由于 ODR 以及简单宏形式元函数名称直接依赖于被内省元素及其名称这一事实, 使用 TTI 宏生成元函数的程序员有责任在一个模块 (应用程序或库) 内避免 ODR. 有几种一般方法可以做到:

  1. 创建唯一的命名空间名称来生成宏元函数, 和/或在不跨翻译单元扩展的 C++ 作用域中生成宏元函数. 后者最明显的例子是在 C++ 类中.
  2. 使用复杂宏形式明确命名生成的元函数, 以提供唯一名称.
  3. 避免在全局作用域中使用 TTI 宏.

对于在库中使用 TTI 并将被他人使用的人而言, 生成对该库唯一的元函数名称非常重要.

TTI 还保留的不仅是宏元函数生成的名称, 还包括以该名称开头的任何 C++ 标识符序列. 换句话说, 如果使用复杂宏形式生成的元函数名为 'MyMetafunction', 请不要在同一作用域中创建任何以 'MyMetaFunction' 开头的 C++ 构造, 例如 'MyMetaFunction_Enumeration' 或 'MyMetaFunctionHelper'. 当前作用域中所有以元函数名开头的名称都应被视为使用 TTI 的程序员不可触及的范围.
