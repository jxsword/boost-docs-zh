调度

线程中的纤程由纤程管理器协调. 纤程以协作方式而非抢占方式交接控制权: 当前运行的纤程保持控制权, 直到它调用某个把控制权交给管理器的操作. 每当纤程挂起 (或让出) 时, 纤程管理器会咨询调度器以确定下一个运行的纤程.

Boost.Fiber 提供纤程管理器, 但调度器是一个定制点. (参见 定制.)

每个线程都有自己的调度器. 进程中的不同线程可以使用不同的调度器. 默认情况下, Boost.Fiber 会为每个线程隐式实例化 round_robin 作为调度器.

明确允许你编写自己的 algorithm 子类. 在大多数情况下, 你的 algorithm 子类无需防御跨线程调用: 纤程管理器会拦截并推迟这类调用. 大多数 algorithm 方法只会从其管理的纤程所在线程被直接调用——例外情况见下文说明.

你的 algorithm 子类通过调用 use_scheduling_algorithm() 在特定线程上启用:

void thread_fn() {
    boost::fibers::use_scheduling_algorithm< my_fiber_scheduler >();
    ...
}

调度器类必须实现接口 algorithm. Boost.Fiber 提供的调度器有: round_robin, work_stealing, numa::work_stealing 和 shared_work.

void thread( std::uint32_t thread_count) {
    // thread registers itself at work-stealing scheduler
    boost::fibers::use_scheduling_algorithm< boost::fibers::algo::work_stealing >( thread_count);
    ...
}

// count of logical cpus
std::uint32_t thread_count = std::thread::hardware_concurrency();
// start worker-threads first
std::vector< std::thread > threads;
for ( std::uint32_t i = 1 /* count start-thread */; i < thread_count; ++i) {
    // spawn thread
    threads.emplace_back( thread, thread_count);
}
// start-thread registers itself at work-stealing scheduler
boost::fibers::use_scheduling_algorithm< boost::fibers::algo::work_stealing >( thread_count);
...

该示例生成与 std::thread::hardware_concurrency() 返回值一样多的线程. 每个线程运行一个 work_stealing 调度器. 该调度器的每个实例都需要知道程序中有多少个线程运行工作窃取调度器. 如果某个线程的本地队列耗尽了就绪纤程, 该线程会尝试从运行此调度器的另一个线程窃取就绪纤程.

algorithm 类

algorithm 是定义纤程调度器必须实现的接口的抽象基类.

#include <boost/fiber/algo/algorithm.hpp>

namespace boost {
namespace fibers {
namespace algo {

struct algorithm {
    virtual ~algorithm();

    virtual void awakened( context *) noexcept = 0;

    virtual context * pick_next() noexcept = 0;

    virtual bool has_ready_fibers() const noexcept = 0;

    virtual void suspend_until( std::chrono::steady_clock::time_point const&) noexcept = 0;

    virtual void notify() noexcept = 0;
};

}}}

Member function awakened() 

virtual void awakened( context * f) noexcept = 0;

效果:

告知调度器纤程 f 已就绪可运行. 纤程 f 可能是新启动的, 也可能曾被阻塞但刚刚被唤醒, 还可能调用了 this_fiber::yield().

注释:

此方法建议调度器把纤程 f 加入其就绪可运行纤程的集合. 典型的调度器实现会把 f 放入队列.

参见:

round_robin

Member function pick_next() 

virtual context * pick_next() noexcept = 0;

返回:

下一个要恢复的纤程; 若没有就绪纤程则为 nullptr.

注释:

调度器在此实际指定下一个要运行的纤程. 典型的调度器实现会选择就绪队列的队首.

参见:

round_robin

Member function has_ready_fibers() 

virtual bool has_ready_fibers() const noexcept = 0;

返回:

如果调度器有就绪可运行的纤程, 则为 true.

Member function suspend_until() 

virtual void suspend_until( std::chrono::steady_clock::time_point const& abs_time) noexcept = 0;

效果:

告知调度器: 在时间点 abs_time 之前不会有纤程就绪.

注释:

此方法允许自定义调度器以任何合理的方式把控制权让给其所处的环境. 纤程管理器表示 suspend_until() 直到 abs_time——或调用了 algorithm::notify()——之前无需返回, 以先到者为准. 与 notify() 的交互意味着, 例如, 调用 std::this_thread::sleep_until(abs_time) 会过于简单. round_robin::suspend_until() 使用 std::condition_variable 与 round_robin::notify() 协调.

注释:

鉴于 notify() 可能从另一个线程被调用, 你的 suspend_until() 实现——与你的 algorithm 实现的其余部分一样——必须保护它与你的 notify() 实现共享的任何数据.

Member function notify() 

virtual void notify() noexcept = 0;

效果:

请求调度器从对 algorithm::suspend_until() 的挂起调用中返回.

注释:

在所有 algorithm 方法中, 唯有 notify() 可以从另一个线程调用. 你的 notify() 实现必须保护它与你的 algorithm 实现的其余部分共享的任何数据.

    virtual void notify() noexcept;
};

}}}

work_stealing 类

该类实现 algorithm; 如果本地就绪队列耗尽了就绪纤程, 就会从其他调度器窃取就绪纤程.
受害调度器 (从中窃取就绪纤程的调度器) 是随机选取的.

注释

工作线程存储在静态变量中, 不支持动态添加/移除工作线程, 也不支持同时存在多个不同的工作线程域.

#include <boost/fiber/algo/work_stealing.hpp>

namespace boost {
namespace fibers {
namespace algo {

class work_stealing : public algorithm {
public:
    work_stealing( std::uint32_t thread_count, bool suspend = false);

    work_stealing( work_stealing const&) = delete;
    work_stealing( work_stealing &&) = delete;

    work_stealing & operator=( work_stealing const&) = delete;
    work_stealing & operator=( work_stealing &&) = delete;

    virtual void awakened( context *) noexcept;

    virtual context * pick_next() noexcept;

    virtual bool has_ready_fibers() const noexcept;

    virtual void suspend_until( std::chrono::steady_clock::time_point const&) noexcept;

    virtual void notify() noexcept;
};

}}}

shared_work 类

注释

由于数据的非局部性, shared_work 的性能不如 work_stealing.

该类实现 algorithm, 以轮转方式调度纤程. 就绪纤程在 shared_work 的所有实例 (运行在不同线程上) 之间共享, 因此工作被均匀分布到所有线程上.

注释

工作线程存储在静态变量中, 不支持动态添加/移除工作线程, 也不支持同时存在多个不同的工作线程域.

    virtual void notify() noexcept;
};

}}}

自定义调度器纤程属性

直接从 algorithm 派生的调度器类可以使用 context 提供的任何信息来实现 algorithm 接口. 但自定义调度器可能需要为纤程跟踪额外的属性. 例如, 基于优先级的调度器需要跟踪纤程的优先级.

Boost.Fiber 提供了一种机制, 使你的自定义调度器可以为每个纤程关联自定义属性.

fiber_properties 类

自定义纤程属性类必须从 fiber_properties 派生.

#include <boost/fiber/properties.hpp>

namespace boost {
namespace fibers {

class fiber_properties {
public:
    fiber_properties( context *) noexcept;

    virtual ~fiber_properties();

protected:
    void notify() noexcept;
};

}}

构造函数 

fiber_properties( context * f) noexcept;

效果:

构造自定义子类的基类组件.

抛出:

无.

注释:

你的子类构造函数必须接受一个 context*, 并把它传给基类的 fiber_properties 构造函数.

Member function notify() 

void notify() noexcept;

效果:

把控制权交给自定义 algorithm_with_properties<> 子类的 algorithm_with_properties::property_change() 方法.

抛出:

无.

注释:

自定义调度器的 algorithm_with_properties::pick_next() 方法可以从就绪纤程中动态选取, 或者 algorithm_with_properties::awakened() 也可以把每个就绪纤程插入某种形式的就绪队列, 供 pick_next() 使用. 在后一种情况下, 如果应用程序代码修改了某个纤程属性 (例如优先级), 而该属性会影响该纤程与其他就绪纤程的关系, 则必须给自定义调度器机会重新排列其就绪队列. 自定义属性子类应当实现一个访问方法来修改此类属性; 在存储新属性值之后, 该访问方法应调用 notify(). 这会把控制权交给自定义调度器的 property_change() 方法, 使自定义调度器能够恰当地重新排列其就绪队列. 是否使用由你自行决定. 当然, 如果你定义的属性不影响 pick_next() 方法的行为, 那么在该属性被修改时无需调用 notify().

模板 algorithm_with_properties<>

依赖于自定义属性类 PROPS 的自定义调度器应当从 algorithm_with_properties<PROPS> 派生. PROPS 应当从 fiber_properties 派生.

#include <boost/fiber/algorithm.hpp>

namespace boost {
namespace fibers {
namespace algo {

template< typename PROPS >
struct algorithm_with_properties {
    virtual void awakened( context *, PROPS &) noexcept = 0;

    virtual context * pick_next() noexcept;

    virtual bool has_ready_fibers() const noexcept;

    virtual void suspend_until( std::chrono::steady_clock::time_point const&) noexcept = 0;

    virtual void notify() noexcept = 0;

    PROPS & properties( context *) noexcept;

    virtual void property_change( context *, PROPS &) noexcept;

    virtual fiber_properties * new_properties( context *);
};

}}}

context 类

尽管你可以自由地把 context* 当作不透明令牌, 但某些 context 成员可能对自定义调度器实现有用.

特别值得注意的是, context 包含一个挂钩 (hook), 用于参与 boost::intrusive::list typedef'ed as boost::fibers::scheduler::ready_queue_t. 该挂钩保留给 algorithm 实现使用. (例如, round_robin 包含一个 ready_queue_t 实例来管理其就绪纤程.) 参见 context::ready_is_linked(), context::ready_link(), context::ready_unlink().

你的 algorithm 实现可以使用你想要的任何容器来管理传入的 context 实例. ready_queue_t 可以避免典型 STL 容器的一部分开销.

#include <boost/fiber/context.hpp>

namespace boost {
namespace fibers {

enum class type {
  none               = unspecified,
  main_context       = unspecified, // fiber associated with thread's stack
  dispatcher_context = unspecified, // special fiber for maintenance operations
  worker_context     = unspecified, // fiber not special to the library
  pinned_context     = unspecified  // fiber must not be migrated to another thread
};

class context {
public:
    class id;

    static context * active() noexcept;

    context( context const&) = delete;
    context & operator=( context const&) = delete;

    id get_id() const noexcept;

    void detach() noexcept;
    void attach( context *) noexcept;

    bool is_context( type) const noexcept;

    bool is_terminated() const noexcept;

    bool ready_is_linked() const noexcept;
    bool remote_ready_is_linked() const noexcept;
    bool wait_is_linked() const noexcept;

    template< typename List >
    void ready_link( List &) noexcept;
    template< typename List >
    void remote_ready_link( List &) noexcept;
    template< typename List >
    void wait_link( List &) noexcept;

    void ready_unlink() noexcept;
    void remote_ready_unlink() noexcept;
    void wait_unlink() noexcept;

    void suspend() noexcept;
    void schedule( context *) noexcept;
};

bool operator<( context const& l, context const& r) noexcept;

}}

Member function attach() 

void attach( context * f) noexcept;

前置条件:

this->get_scheduler() == nullptr

效果:

把纤程 f 附加到运行 *this 的调度器.

后置条件:

this->get_scheduler() != nullptr

抛出:

无

注释:

典型的调用: boost::fibers::context::active()->attach(f);

注释:

f 不得是正在运行纤程的上下文. 它不得处于 blocked 状态或已终止. 它不得是 pinned_context. 它当前必须是分离的. 它当前不得已链接进某个 algorithm 实现的就绪队列. 这些条件大多由 f 被某个 algorithm 实现所拥有这一事实所蕴含: 即它已被传给 algorithm::awakened() 但尚未被 algorithm::pick_next() 返回. 通常, 一个 pick_next() 实现会在调用 attach() 时, 传入它即将返回的 context*. 它必须先从其就绪队列中移除 f. 你绝不应把一个 pinned_context 传给 attach(), 因为首先你根本不应调用其 detach() 方法.

Member function detach() 

void detach() noexcept;

前置条件:

(this->get_scheduler() != nullptr) && ! this->is_context(pinned_context)

效果:

把纤程 *this 从运行 *this 的调度器中分离.

抛出:

无

后置条件:

this->get_scheduler() == nullptr

注释:

必须在当前与该纤程关联的线程上调用此方法. *this 不得是正在运行纤程的上下文. 它不得处于 blocked 状态或已终止. 它不得是 pinned_context. 它不得已经被分离. 它当前不得已链接进某个 algorithm 实现的就绪队列. 这些条件大多由 *this 被传给 algorithm::awakened() 这一事实所蕴含; 不过, awakened() 实现仍必须测试 pinned_context. 它必须调用 detach(), 早于 把 *this 链接进其就绪队列的操作.

注释:

特别要指出的是, 同时调用 detach() 和 attach() (在 algorithm::pick_next() 方法中) 以把纤程从一个线程迁移到另一个线程是错误的. pick_next() 在预期的目标线程上调用. detach() 必须在该纤程的原始线程上调用. 你必须调用 detach()——位置在对应的 awakened() 方法中.

注释:

除非你打算让某个纤程可供潜在迁移到不同线程, 否则不应调用 detach() 或 attach() 中的任何一个——即不要带着它的 context 调用.

Member function is_context()

返回:

true——若 *this 属于指定类型.

抛出:

无

注释:

type::worker_context 在此指任何对库而言非特殊的纤程. 对于 type::main_context, context 与线程的 "main" 纤程关联: 即由线程自身隐式创建的那个纤程, 而不是 Boost.Fiber 显式创建的纤程. 对于 type::dispatcher_context, context 与一个 "dispatching" 纤程关联, 该纤程负责把被唤醒的纤程分派到调度器的就绪队列. "dispatching" 纤程是纤程管理器的一个实现细节. "main" 纤程或 "dispatching" 纤程的上下文——任何满足 is_context(pinned_context) 为 true 的纤程——绝不能传给 context::detach().

Member function suspend() 

void suspend() noexcept;

效果:

挂起正在运行的纤程 (与 *this 关联的纤程), 直到其他某个纤程把 this 传给 context::schedule(). *this 被标记为非就绪, 控制权交给调度器以选择另一个纤程运行.

抛出:

无

注释:

这是一个可能对与其他框架集成有用的低层 API. 它并非供典型应用程序直接调用.

注释:

调用方需要负担起如下责任: 安排在将来某个时刻调用 schedule(), 并传入指向 this 的指针.

Member function schedule() 

void schedule( context * ctx ) noexcept;

效果:

把与上下文 *ctx 关联的纤程标记为就绪可运行. 这不会立即恢复该纤程; 而是把该纤程交给调度器以便后续恢复. 如果调度器处于空闲状态 (尚未从对 algorithm::suspend_until() 的调用中返回), 则调用 algorithm::notify() 唤醒它.

抛出:

无

注释:

这是一个可能对与其他框架集成有用的低层 API. 它并非供典型应用程序直接调用.

注释:

明确支持调用 schedule(ctx)——即便 *ctx 当前挂起在另一个线程上. 对应的纤程届时会在其原始线程上恢复.
