定制

概述

如 调度 一节所述, 默认情况下 Boost.Fiber 会为每个线程使用其自身的 round_robin 调度器. 要控制 Boost.Fiber 在特定线程上调度就绪纤程的方式, 通常必须遵循若干步骤. 本节讨论这些步骤, 而 调度 一节则可作为所涉类的参考.

库的纤程管理器会跟踪被挂起 (阻塞) 的纤程. 只有当纤程变为可运行时才会被传递给调度器. 当然, 如果就绪纤程少于两个, 调度器的工作无关紧要. 只有两个或更多就绪纤程时, 特定的调度器实现才会开始影响纤程执行的整体顺序.

本节将演示一个遵循整数纤程优先级的简单自定义调度器. 我们将把它实现为: 优先级较高的纤程优先于优先级较低的纤程; 优先级值相同的纤程则按轮转方式获得服务.

下面示例的完整源代码位于 priority.cpp 中.

自定义属性类

第一个要点是, 我们必须为每个纤程关联一个整数优先级.[11]

有人可能会建议派生一个自定义的 fiber 子类来存储这类属性. 采用现行机制有以下几个原因.

  1. Boost.Fiber 提供了多种不同的方式来启动纤程. (参见 fibers::async().) 更上层的库可能会引入其他这类封装函数. 自定义调度器必须把其自定义属性与线程中的 每一个 纤程关联起来, 而不仅仅是那些通过实例化自定义 fiber 子类显式启动的纤程.
  2. 设想一个大型现有程序, 它在代码中许多不同的地方启动纤程. 我们发现需要为某个特定线程引入自定义调度器. 如果支持该调度器的自定义属性需要某个特定的 fiber 子类, 我们将不得不找出并修改该线程上启动纤程的每一处代码.
  3. fiber 类实际上只是内部 context 数据的一个句柄. fiber 的子类不会给 context 添加数据.

现行机制允许你 "直接插入" 一个自定义调度器及其配套的自定义属性, 而 无需 更改应用程序的其余部分.

自定义调度器纤程属性子类不应从 fiber 派生, 而必须改为从 fiber_properties 派生.

class priority_props : public boost::fibers::fiber_properties {
public:
    priority_props( boost::fibers::context * ctx):
        fiber_properties( ctx), 
        priority_( 0) {
    }

    int get_priority() const {
        return priority_; 
    }

    // Call this method to alter priority, because we must notify
    // priority_scheduler of any change.
    void set_priority( int p) { 
        // Of course, it's only worth reshuffling the queue and all if we're
        // actually changing the priority.
        if ( p != priority_) {
            priority_ = p;
            notify();
        }
    }

    // The fiber name of course is solely for purposes of this example
    // program; it has nothing to do with implementing scheduler priority.
    // This is a public data member -- not requiring set/get access methods --
    // because we need not inform the scheduler of any change.
    std::string name; 
private:
    int priority_;
};

你的子类构造函数必须接受一个 context*, 并把它传给 fiber_properties 构造函数.

可自行决定是否提供读取访问方法.

对任何可能影响调度器行为的属性做出更改时, 都要调用 notify(), 这一点很重要. 因此, 此类修改只应通过访问方法进行.

不影响调度器的属性无需访问方法.

自定义调度器类

现在我们可以从 algorithm_with_properties<> 派生一个自定义调度器, 并把我们的自定义属性类 priority_props 指定为模板参数.

class priority_scheduler :
    public boost::fibers::algo::algorithm_with_properties< priority_props > {
private:
    typedef boost::fibers::scheduler::ready_queue_type   rqueue_t;

    rqueue_t                                rqueue_;
    std::mutex                  mtx_{};
    std::condition_variable     cnd_{};
    bool                        flag_{ false };

public:
    priority_scheduler() :
        rqueue_() {
    }

    // For a subclass of algorithm_with_properties<>, it's important to
    // override the correct awakened() overload.
    virtual void awakened( boost::fibers::context * ctx, priority_props & props) noexcept {
        int ctx_priority = props.get_priority(); 
        // With this scheduler, fibers with higher priority values are
        // preferred over fibers with lower priority values. But fibers with
        // equal priority values are processed in round-robin fashion. So when
        // we're handed a new context*, put it at the end of the fibers
        // with that same priority. In other words: search for the first fiber
        // in the queue with LOWER priority, and insert before that one.
        rqueue_t::iterator i( std::find_if( rqueue_.begin(), rqueue_.end(),
            [ctx_priority,this]( boost::fibers::context & c)
            { return properties( &c ).get_priority() < ctx_priority; }));
        // Now, whether or not we found a fiber with lower priority,
        // insert this new fiber here.
        rqueue_.insert( i, * ctx);
    }

    virtual boost::fibers::context * pick_next() noexcept {
        // if ready queue is empty, just tell caller
        if ( rqueue_.empty() ) {
            return nullptr;
        }
        boost::fibers::context * ctx( & rqueue_.front() );
        rqueue_.pop_front();
        return ctx;
    }

    virtual bool has_ready_fibers() const noexcept {
        return ! rqueue_.empty();
    }

    virtual void property_change( boost::fibers::context * ctx, priority_props & props) noexcept {
        // Although our priority_props class defines multiple properties, only
        // one of them (priority) actually calls notify() when changed. The
        // point of a property_change() override is to reshuffle the ready
        // queue according to the updated priority value.

        // 'ctx' might not be in our queue at all, if caller is changing the
        // priority of (say) the running fiber. If it's not there, no need to
        // move it: we'll handle it next time it hits awakened().
        if ( ! ctx->ready_is_linked()) { 
            return;
        }

        // Found ctx: unlink it
        ctx->ready_unlink();

        // Here we know that ctx was in our ready queue, but we've unlinked
        // it. We happen to have a method that will (re-)add a context* to the
        // right place in the ready queue.
        awakened( ctx, props);
    }

    void suspend_until( std::chrono::steady_clock::time_point const& time_point) noexcept {
        if ( (std::chrono::steady_clock::time_point::max)() == time_point) {
            std::unique_lock< std::mutex > lk( mtx_);
            cnd_.wait( lk, [this](){ return flag_; });
            flag_ = false;
        } else {
            std::unique_lock< std::mutex > lk( mtx_);
            cnd_.wait_until( lk, time_point, [this](){ return flag_; });
            flag_ = false;
        }
    }

    void notify() noexcept {
        std::unique_lock< std::mutex > lk( mtx_);
        flag_ = true;
        lk.unlock();
        cnd_.notify_all();
    }
};

参见 ready_queue_t.

你必须重写 algorithm_with_properties::awakened() 方法. 你的调度器正是通过它接收纤程变为可运行的通知的.

props 是与传入纤程 ctx 关联的 priority_props 实例.

你必须重写 algorithm_with_properties::pick_next() 方法. 你的调度器正是通过它实际告知纤程管理器下一个要运行的纤程.

你必须重写 algorithm_with_properties::has_ready_fibers(), 以便向纤程管理器告知你的就绪队列的状态.

重写 algorithm_with_properties::property_change() 是可选的. 该重写处理运行中纤程更改另一个就绪纤程优先级的情况: 即已在队列中的纤程. 此时, 应在队列内移动被更新的纤程.

你的 property_change() 重写必须能够处理传入的 ctx 不在你的就绪队列中的情况. 它可能正在运行, 也可能已被阻塞.

我们的示例 priority_scheduler 没有重写 algorithm_with_properties::new_properties(): 我们满足于在堆上分配 priority_props 实例.

替换默认调度器

你必须在每个线程的开始处调用 use_scheduling_algorithm(), 只要你希望 Boost.Fiber 在该线程上使用你的自定义调度器而非其自身默认的 round_robin. 具体而言, 你必须先调用 use_scheduling_algorithm(), 然后才能在该线程上执行任何其他 Boost.Fiber 操作.

int main( int argc, char *argv[]) {
    // make sure we use our priority_scheduler rather than default round_robin
    boost::fibers::use_scheduling_algorithm< priority_scheduler >();
    ...
}

使用属性

运行中的纤程能够访问其自身的 fiber_properties 子类实例, 方法是调用 this_fiber::properties(). 尽管 properties<>() 是一个无参函数, 你仍必须以模板参数的形式传入 fiber_properties 子类.

boost::this_fiber::properties< priority_props >().name = "main";

对于一个仍与运行中纤程关联的 fiber 实例 (即尚未被 fiber::detach()), 你可以使用 fiber::properties() 访问该纤程的属性. 与 boost::this_fiber::properties<>() 一样, 你必须把你的 fiber_properties 子类作为模板参数传入.

template< typename Fn >
boost::fibers::fiber launch( Fn && func, std::string const& name, int priority) {
    boost::fibers::fiber fiber( func);
    priority_props & props( fiber.properties< priority_props >() );
    props.name = name;
    props.set_priority( priority);
    return fiber;
}

启动新纤程会把它按就绪状态调度, 但 不会 立即进入其 纤程函数. 当前纤程会保持控制权, 直到它因其他原因阻塞 (或让出, 或终止). 如上面的 launch() 函数所示, 启动纤程后立即设置相关属性是合理的——例如设置其优先级. 下次纤程管理器调用 algorithm_with_properties::pick_next() 时, 你的自定义调度器便可利用这一信息.


[11] Fiber 库的先前版本会为每个纤程隐式跟踪一个 int 优先级, 尽管默认调度器忽略了它. 由于该库现在支持任意的调度器特定纤程属性, 这一做法已被取消.
