调优

禁用同步

若在编译器命令行上定义了 BOOST_FIBERS_NO_ATOMICS, 则纤程之间 (在不同线程中) 的同步将被禁用. 若应用程序是单线程的, 和/或纤程不跨线程同步, 这是可以接受的.

内存分配

内存分配算法对多线程环境下的性能影响重大, 对 Boost.Fiber 尤其如此, 因为纤程栈是在堆上分配的. glibc 的默认用户级内存分配器 (UMA) 是 ptmalloc2, 但可以将其替换为更适合具体工作负载的其他 UMA. 例如, Google 的 TCmalloc 在 skynet 微基准测试中就比 glibc 的默认内存分配器表现更好.

调度策略

一个线程中的纤程由纤程管理器协调. 纤程以协作方式而非抢占方式交换控制权. 根据工作负载, 可采用多种纤程调度策略 [10], 它们可以基于 algorithm 实现.

  • 工作窃取 (work-stealing): 就绪纤程保存在本地队列中; 当纤程调度器的本地队列中就绪纤程耗尽时, 它随机选择另一个纤程调度器, 并尝试从受害者那里窃取一个就绪纤程 (实现于 work_stealing 和 numa::work_stealing)
  • 工作请求 (work-requesting): 就绪纤程保存在本地队列中; 当纤程调度器的本地队列中就绪纤程耗尽时, 它随机选择另一个纤程调度器并请求就绪纤程, 受害者纤程调度器回送一个就绪纤程
  • 工作共享 (work-sharing): 就绪纤程保存在全局队列中, 纤程调度器并发地向全局队列推入和弹出就绪纤程 (实现于 shared_work)
  • 工作分发 (work-distribution): 变为就绪的纤程会被主动分发到空闲的纤程调度器或负载较低的纤程调度器
  • 工作均衡 (work-balancing): 一个专用的 (辅助) 纤程调度器周期性地收集其他线程中运行的所有纤程调度器的信息, 并在它们之间重新分发就绪纤程

TTAS 锁

当不同线程上运行的纤程交互时, Boost.Fiber 在内部使用自旋锁保护临界区. 自旋锁实现为 TTAS (test-test-and-set) 锁, 即自旋锁在调用原子交换之前先测试锁. 这一策略有助于减少获取/释放锁所触发的缓存行失效.

自旋等待循环

如果一个线程由于其他线程抢先而反复未能获得锁, 则认为该锁处于争用状态. 短暂等待片刻, 让其他线程先完成, 再尝试重新进入临界区. 在忙等锁时, 放松 CPU (通过 pause/yield 助记符) 会给 CPU 一个提示, 表明代码正处于自旋等待循环中.

  • 避免昂贵的流水线冲刷 (推测执行的加载和比较指令不会被推入流水线)
  • 另一个硬件线程 (同步多线程) 可以获得时间片
  • 它确实会延迟几个 CPU 周期, 但这是防止饥饿所必需的

显然, 这一策略在单核系统上毫无用处, 因为只有当线程放弃其时间片以让其他线程运行时, 锁才能被释放. 宏 BOOST_FIBERS_SPIN_SINGLE_CORE 会把 CPU 提示 (pause/yield 助记符) 替换为通知操作系统 (通过 std::this_thread_yield()), 表明线程放弃其时间片, 操作系统随即切换到另一个线程.

指数退避

宏 BOOST_FIBERS_RETRY_THRESHOLD 决定 CPU 在让出线程或阻塞于 futex 等待之前, 在自旋等待循环中迭代的次数. 自旋锁会记录线程未能获取锁的次数. 争用越激烈, 线程就应当退避得越久. 为此采用了 “二进制指数退避” 算法, 并辅以随机化的争用窗口. BOOST_FIBERS_CONTENTION_WINDOW_THRESHOLD 决定争用窗口的上限 (以 2 为底的指数表示).

推测执行 (硬件事务内存)

Boost.Fiber 使用自旋锁保护临界区, 这些自旋锁可与事务内存配合使用 (参见 推测执行 一节).

注释

如果在 b2 命令行指定了特性 htm=tsx 并且对编译器应用了 BOOST_USE_TSX, 则启用 TXS.

注释

如果在临界区内修改了浮点状态, TSX 事务将被中止. 因此, 浮点操作——例如在纤程 (上下文) 切换期间对浮点相关寄存器的存储/加载——被禁用.

NUMA 系统

现代多插槽系统通常被设计为 NUMA 系统. 诸如 numa::work_stealing 这样的合适纤程调度器可以减少远程内存访问 (延迟).
