设计理由

预处理器定义

表 1.6. 预处理器定义

BOOST_FIBERS_NO_ATOMICS

不使用 std::atomic<>, 禁用线程间同步

BOOST_FIBERS_SPINLOCK_STD_MUTEX

使用 std::mutex 作为自旋锁, 而不是默认的带退避的 XCHG 自旋锁

BOOST_FIBERS_SPIN_BACKOFF

该上限决定在忙等待期间何时使用 std::this_thread::yield() 而非助记 pause/yield (仅适用于 XCHG 自旋锁)

BOOST_FIBERS_SINGLE_CORE

在忙等待期间始终不带退避地调用 std::this_thread::yield() (仅适用于 XCHG 自旋锁)

协程与纤程的区别

fiber 库在 coroutine 库的基础上增加了一个调度器和同步机制.

  • 协程让出
  • 纤程阻塞

当协程让出时, 它把控制权直接传给其调用者 (或, 对于对称协程, 传给指定的另一个协程). 当纤程阻塞时, 它隐式地把控制权传给纤程调度器. 协程没有调度器, 因为它们不需要调度器.[12].

事务内存怎么办

GCC 自 4.7 版起支持事务内存. 不幸的是, 测试表明事务内存比使用原子操作的自旋锁更慢 (约 4 倍). 一旦事务内存得到改进 (支持混合 TM), 自旋锁将被包围临界区的 __transaction_atomic{} 语句取代.

运行在不同线程中的纤程之间的同步

Boost.Thread 的同步类会阻塞整个线程. 相比之下, Boost.Fiber 的同步类只阻塞特定纤程, 因此调度器仍能让线程忙于运行其他纤程. Boost.Fiber 的同步类被设计为线程安全的, 也就是说, 既可以同步运行在不同线程中的纤程, 也可以同步运行在同一线程中的纤程. (不过, 有一个构建选项可以禁用跨线程纤程同步支持; 参见 此说明.)

虚假唤醒

使用 std::condition_variable 时可能发生虚假唤醒: 条件变量看起来已被通知, 而被等待的条件可能仍为假. 虚假唤醒可能反复发生, 它源于某些多处理器系统——在这些系统上, 使 std::condition_variable 的唤醒完全可预测会拖慢所有 std::condition_variable 操作.[13]

condition_variable 不受虚假唤醒影响. 尽管如此, 在 wait() 循环中测试业务逻辑条件——或等价地, 使用 wait( lock, predicate ) 重载之一——仍是稳妥的做法.

另见 无虚假唤醒.

在线程之间迁移纤程

对在线程之间迁移纤程的支持已经集成进来. 用户自定义调度器必须在源线程上对某个纤程上下文调用 context::detach(), 并在目标线程上调用 context::attach(), 传入要迁移的纤程上下文. (关于自定义调度器的更多信息, 参见 定制.) 示例 work_sharing 和 work_stealing (位于目录 examples 中) 可以用作蓝图.

另见 跨线程迁移纤程.

对 Boost.Asio 的支持

对 Boost.Asio 的 async-result 的支持不属于官方 API. 不过, 要与 boost::asio::io_service 集成, 参见 与另一个主循环共享线程. 要与任意 Asio 异步 I/O 操作顺畅对接, 参见 接下来便是 Boost.Asio.

已测试的编译器

该库已在 c++11 模式下用 GCC-5.1.1、Clang-3.6.0 和 MSVC-14.0 测试.
