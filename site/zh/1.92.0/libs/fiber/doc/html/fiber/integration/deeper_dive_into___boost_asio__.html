深入了解 Boost.Asio

至此, 敏锐的读者会想: 尤其是对于 Asio, 我们理应能够做得比周期性的轮询探测好得多!

事实证明这相当棘手. 我们在 examples/asio/round_robin.hpp 中给出了一种可行的方案.

使用 Boost.Asio 的一个后果是, 你必须始终让 Asio 来挂起运行中的线程. 由于 Asio 知晓未完成的 I/O 请求, 它能够以让操作系统在 I/O 完成时唤醒线程的方式安排挂起. 其他任何人都缺乏足够的知识来做这件事.

因此, 纤程调度器必须依赖 Asio 来进行挂起和恢复. 它需要 Asio 处理器调用来唤醒它.

一个令人沮丧的推论是, 我们无法支持多个线程调用 io_service::run(), 哪怕作用于同一个 io_service 实例. 原因在于 Asio 没有提供任何办法把特定的处理器约束为只在指定线程上调用. 纤程调度器实例被锁定到特定线程: 该实例不能管理任何其他线程的纤程. 然而, 若允许多个线程调用 io_service::run(), 且作用于同一个 io_service 实例, 那么需要休眠的纤程调度器就无法保证自己会被及时唤醒. 它可以按上文所述设置一个 Asio 定时器——但该定时器的处理器很可能在另一个线程上执行!

另一个推论是, 由于感知 Asio 的纤程调度器 (更不用说 boost::fibers::asio::yield 了) 依赖于来自 io_service 的处理器调用, 确保 io_service::stop() 直到每个纤程都已终止才被调用, 是应用程序的责任.

对于这里给出的 asio::round_robin 调度器, 如果我们要求在初始设置之后由线程的主纤程来调用 io_service::run(), 其行为会更容易推断, 因此我们就加上这一要求.

自然, 在每个使用自定义纤程调度器的线程上, 我们必须做的第一件事是调用 use_scheduling_algorithm(). 然而, 由于 asio::round_robin 需要一个 io_service 实例, 我们必须先声明它.

std::shared_ptr< boost::asio::io_context > io_ctx = std::make_shared< boost::asio::io_context >();
boost::fibers::use_scheduling_algorithm< boost::fibers::asio::round_robin >( io_ctx);

use_scheduling_algorithm() 实例化了 asio::round_robin, 后者自然会调用其构造函数:

round_robin( std::shared_ptr< boost::asio::io_context > const& io_ctx) :
    io_ctx_( io_ctx),
    suspend_timer_( * io_ctx_) {
    // We use add_service() very deliberately. This will throw
    // service_already_exists if you pass the same io_context instance to
    // more than one round_robin instance.
    boost::asio::add_service( * io_ctx_, new service( * io_ctx_) );
    boost::asio::post( * io_ctx_, [this]() mutable {

asio::round_robin 绑定传入的 io_service 指针, 并初始化一个 boost::asio::steady_timer:

std::shared_ptr< boost::asio::io_context >      io_ctx_;
boost::asio::steady_timer                       suspend_timer_;

然后它会调用 boost::asio::add_service(), 并传入一个嵌套的 service 结构体:

struct service : public boost::asio::io_context::service {
    static boost::asio::io_context::id                  id;

    std::unique_ptr< boost::asio::io_context::work >    work_;

    service( boost::asio::io_context & io_ctx) :
        boost::asio::io_context::service( io_ctx),
        work_{ new boost::asio::io_context::work( io_ctx) } {
    }

    virtual ~service() {}

    service( service const&) = delete;
    service & operator=( service const&) = delete;

    void shutdown_service() override final {
        work_.reset();
    }
};

service 结构体有几个角色.

它最重要的角色是管理一个 std::unique_ptr<boost::asio::io_service::work>. 我们希望 io_service 实例即使在没有待处理的 Asio I/O 时也能继续其主循环.

但是当 boost::asio::io_service::service::shutdown_service() 被调用时, 我们丢弃 io_service::work 实例, 以便 io_service 能够正常关闭.

它的另一个用途是 post() 一个 lambda (尚未展示). 我们先继续走完示例程序的其余部分, 然后再回来解释这个 lambda.

service 构造函数返回到 asio::round_robin 的构造函数, 后者返回到 use_scheduling_algorithm(), 再返回到应用程序代码.

一旦调用了 use_scheduling_algorithm(), 应用程序现在就可以启动若干纤程:

// server
tcp::acceptor a( * io_ctx, tcp::endpoint( tcp::v4(), 9999) );
boost::fibers::fiber( server, io_ctx, std::ref( a) ).detach();
// client
const unsigned iterations = 2;
const unsigned clients = 3;
boost::fibers::barrier b( clients);
for ( unsigned i = 0; i < clients; ++i) {
    boost::fibers::fiber(
            client, io_ctx, std::ref( a), std::ref( b), iterations).detach();
}

由于我们没有指定 launch, 这些纤程已就绪可运行, 但尚未被进入.

一切设置完毕后, 应用程序调用 io_service::run():

io_ctx->run();

接下来会怎样?

因为这个 io_service 实例拥有一个 io_service::work 实例, run() 不会立即返回. 但是——将要执行实际工作的纤程甚至还没有一个被进入!

如果缺少 post() 这个在 service 构造函数中的最初调用, 就 什么都不会 发生. 应用程序会正好卡在这里.

那么, post() 处理器应该执行什么? 仅仅是 this_fiber::yield() 吗?

那会是一个有希望的开端. 但我们无法保证其他纤程会发起任何 Asio 操作来让事情继续. 完全有可能每个其他纤程都先到达类似的 boost::this_fiber::yield() 调用. 控制权将返回到 post() 处理器, 后者返回到 Asio, 然后——应用程序就会卡死.

post() 处理器可以再次 post() 自身. 但正如 上一节 所讨论的, 一旦有实际的 I/O 操作在进行中——一旦到达没有任何纤程就绪的状态——这就会导致线程空转.

当然, 我们可以设置一个 Asio 定时器——同样如 前文所讨论的. 但在这场 "深入探讨" 中, 我们想做得更好一些.

我们可以等待 "某事发生", 办法是调用 io_service::run_one(); 也可以执行已排队的 Asio 处理器, 办法是调用 io_service::poll().

下面是传给 post() 调用的 lambda 的函数体.

 while ( ! io_ctx_->stopped() ) {
     if ( has_ready_fibers() ) {
         // run all pending handlers in round_robin
         while ( io_ctx_->poll() );
         // block this fiber till all pending (ready) fibers are processed
         // == round_robin::suspend_until() has been called
         std::unique_lock< boost::fibers::mutex > lk( mtx_);
         cnd_.wait( lk);
     } else {
         // run one handler inside io_context
         // if no handler available, block this thread
         if ( ! io_ctx_->run_one() ) {
             break;
         }
     }
}

我们希望这个循环在 io_service 实例被 stopped() 之后退出.

只要存在就绪纤程, 我们就把运行就绪的 Asio 处理器与运行就绪的纤程交替进行.

如果没有就绪纤程, 我们就通过调用 run_one() 来等待. 一旦任何 Asio 处理器被调用——无论是哪个——run_one() 就会返回. 该处理器可能已把某个纤程转变为就绪状态, 因此我们回到循环再次检查.

(我们不会描述 awakened(), pick_next() 或 has_ready_fibers(), 因为它们与 round_robin::awakened(), round_robin::pick_next() 和 round_robin::has_ready_fibers() 完全一样.)

这样就剩下 suspend_until() 和 notify() 了.

你无疑一直在问自己: 为什么我们在 lambda 循环中调用 io_service::run_one()? 为什么不在 suspend_until() 中调用它? 后者的 API 正是为此目的而设计的.

正常情况下, 当纤程管理器发现没有就绪纤程时, 它会调用 algorithm::suspend_until(). 为什么要在 lambda 循环中测试 has_ready_fibers()? 为什么不利用正常机制?

答案是: 由谁来问很重要.

考虑上面展示的 lambda 循环. 它涉及的唯一 Boost.Fiber API 是 has_ready_fibers() 和 this_fiber::yield(). yield() 并不会 阻塞 调用方纤程: 调用方纤程不会变为非就绪. 它会立即被传回 algorithm::awakened(), 轮到它在所有其他就绪纤程都有机会运行之后恢复. 换言之: 在 yield() 调用期间, 总是至少有一个就绪纤程.

只要这个 lambda 循环还在运行, 纤程管理器就不会调用 suspend_until(), 因为它总有纤程就绪可运行.

然而, lambda 循环 自身 可以检测到没有 其他 纤程就绪可运行的情况: 正在运行的纤程不是 就绪 而是 运行中.

话虽如此, suspend_until() 和 notify() 实际上会在有序关闭处理期间被调用, 所以让我们尝试一个看似合理的实现.

void suspend_until( std::chrono::steady_clock::time_point const& abs_time) noexcept {
    // Set a timer so at least one handler will eventually fire, causing
    // run_one() to eventually return.
    if ( (std::chrono::steady_clock::time_point::max)() != abs_time) {
        // Each expires_at(time_point) call cancels any previous pending
        // call. We could inadvertently spin like this:
        // dispatcher calls suspend_until() with earliest wake time
        // suspend_until() sets suspend_timer_
        // lambda loop calls run_one()
        // some other asio handler runs before timer expires
        // run_one() returns to lambda loop
        // lambda loop yields to dispatcher
        // dispatcher finds no ready fibers
        // dispatcher calls suspend_until() with SAME wake time
        // suspend_until() sets suspend_timer_ to same time, canceling
        // previous async_wait()
        // lambda loop calls run_one()
        // asio calls suspend_timer_ handler with operation_aborted
        // run_one() returns to lambda loop... etc. etc.
        // So only actually set the timer when we're passed a DIFFERENT
        // abs_time value.
        suspend_timer_.expires_at( abs_time);
        suspend_timer_.async_wait([](boost::system::error_code const&){
                                    this_fiber::yield();
                                  });
    }
    cnd_.notify_one();
}

正如你可能预期的, suspend_until() 会把一个 asio::steady_timer 设置为 expires_at() 所传入的 std::chrono::steady_clock::time_point. 通常如此.

如注释所示, 我们避免把 suspend_timer_ 多次设置为 同一个 time_point 值, 因为每次 expires_at() 调用都会取消之前的 async_wait() 调用. 这有可能导致空转. 到达 suspend_until() 意味着纤程管理器打算把处理器让给 Asio. 取消之前的 async_wait() 调用会触发其处理器, 导致 run_one() 返回, 进而潜在地导致纤程管理器再次调用 suspend_until(), 且带着相同的 time_point 值...

既然我们通过调用 io_service::run_one() 来挂起线程, 重要的是我们的 async_wait() 调用会导致某个处理器运行, 而这会导致 run_one() 返回. 该处理器具体做什么并不那么重要.

void notify() noexcept {
    // Something has happened that should wake one or more fibers BEFORE
    // suspend_timer_ expires. Reset the timer to cause it to fire
    // immediately, causing the run_one() call to return. In theory we
    // could use cancel() because we don't care whether suspend_timer_'s
    // handler is called with operation_aborted or success. However --
    // cancel() doesn't change the expiration time, and we use
    // suspend_timer_'s expiration time to decide whether it's already
    // set. If suspend_until() set some specific wake time, then notify()
    // canceled it, then suspend_until() was called again with the same
    // wake time, it would match suspend_timer_'s expiration time and we'd
    // refrain from setting the timer. So instead of simply calling
    // cancel(), reset the timer, which cancels the pending sleep AND sets
    // a new expiration time. This will cause us to spin the loop twice --
    // once for the operation_aborted handler, once for timer expiration
    // -- but that shouldn't be a big problem.
    suspend_timer_.async_wait([](boost::system::error_code const&){
                                this_fiber::yield();
                              });
    suspend_timer_.expires_at( std::chrono::steady_clock::now() );
}

由于 expires_at() 调用会取消之前的任何 async_wait() 调用, 我们可以让 notify() 直接调用 steady_timer::expires_at(). 这应该会导致 io_service 调用 async_wait() 处理器, 并传入 operation_aborted.

notify() 中的注释解释了我们为什么调用 expires_at() 而不是 cancel().

这个 boost::fibers::asio::round_robin 实现用于 examples/asio/autoecho.cpp.
