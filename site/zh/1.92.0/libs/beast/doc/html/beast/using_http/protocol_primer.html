协议入门

HTTP 协议定义了 客户端与服务器角色: 客户端发送请求, 服务器返回响应. 客户端与服务器建立连接后, 客户端发送一系列请求, 服务器按收到的顺序对每个请求至少返回一个响应.

请求或响应是一个 HTTP 报文 (下文简称 "报文") , 它有两个部分: 带结构化元数据的头部, 以及存放任意数据的可选变长正文. 序列化的头部由一行或多行文本组成, 每行以回车加换行 ("\r\n") 结尾. 空行标志头部的结束. 头部的第一行称为 start-line. 起始行的内容对请求和响应有所不同.

每个报文包含零个或多个字段名/值对, 统称 "字段". 名称和值用文本字符串表示, 并各有要求. 序列化的字段包含字段名, 然后是冒号加空格 (": ") , 最后是字段值并以 CRLF 结尾.

请求

客户端发送请求, 请求包含 method 和 request-target 和 HTTP-version. 方法标识要执行的操作, 目标标识服务器上操作施加的对象. 版本几乎总是 1.1, 但较老的程序有时使用 1.0.

序列化请求

说明

 
GET / HTTP/1.1\r\n
User-Agent: Beast\r\n
\r\n

此请求的方法为 "GET", 目标为 "/", 指示 HTTP 1.1 版本. 它包含单个字段 "User-Agent", 值为 "Beast". 没有报文正文.
响应

服务器发送响应, 响应包含 status-code, reason-phrase 和 HTTP-version. 原因短语是 已废弃: 客户端应当 (SHOULD) 忽略原因短语的内容. 下面是一个包含正文的响应. 特殊字段 Content-Length 告知远程主机其后正文的大小.

序列化响应

说明

 
HTTP/1.1 200 OK\r\n
Server: Beast\r\n
Content-Length: 13\r\n
\r\n
Hello, world!

该响应具有 200 状态码, 表示请求的操作已成功完成. 已废弃的原因短语是 "OK". 它指定 HTTP 1.1 版本, 包含一个 13 八位组大小、内容为 "Hello, world!" 的正文.
Body

报文可以可选地携带正文. 报文正文的大小由报文的语义以及特殊字段 Content-Length 和 Transfer-Encoding 决定. rfc7230 section 3.3 对正文长度的确定方式给出了全面描述.

特殊字段

报文中出现的某些字段是特殊的. 库在执行序列化和解析时理解这些字段: 当字段在报文中被解析时按需采取自动动作, 在调用方要求时也会设置这些字段.

表 1.15. 特殊字段

Field

说明

Connection

Proxy-Connection

此字段允许发送方指示当前连接所需的控制选项. 常见值包括 "close"、"keep-alive" 和 "upgrade".

Content-Length

存在时, 此字段告知接收方报文头之后正文的精确字节大小.

Transfer-Encoding

此可选字段列出已 (或将) 应用于内容载荷以形成报文正文的传输编码序列的名称.

当 "chunked" 编码方案是最后一个 (最外层) 应用的编码时, Beast 能够理解它. 序列化期间内容长度事先未知时, 库会自动应用分块编码; 解析出的报文中存在分块编码时, 库会自动移除.

Upgrade

Upgrade 头字段提供从 HTTP/1.1 过渡到同一连接上另一协议的机制. 例如, WebSocket 的初始 HTTP 握手就用它来建立 WebSocket 连接.
