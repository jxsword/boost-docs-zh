注释

由于读取数据的调用可能返回不定的字节数, 读取数据的接口需要一个满足 DynamicBuffer 分段. 此 concept 建模于 net::streambuf.

实现不对报文做排队或缓冲. 如有需要, 这些特性应由调用方提供. 这一设计的影响是: 库用户完全掌控用于存储数据的分配策略以及施加在底层 TCP/IP 连接读写两侧的背压.

异步操作

所有函数都有异步版本:

flat_buffer buffer;

ws.async_read(buffer,
    [](error_code, std::size_t)
    {
        // Do something with the buffer
    });

对异步发起函数的调用支持 Boost.Asio 作者开发的可扩展异步模型, 允许传统完成处理器、有栈或无栈协程, 甚至 future:

void echo(stream<tcp_stream>& ws,
    multi_buffer& buffer, net::yield_context yield)
{
    ws.async_read(buffer, yield);
    std::future<std::size_t> fut =
        ws.async_write(buffer.data(), net::use_future);
}

库自带的示例程序演示了 websocket 流操作与所有异步形式配合的用法.

io_context

与底层流关联的 net::io_context 的创建与运行由调用方负责, 允许任何实现策略, 包括在线程不可用的环境中不使用线程的策略. Beast WebSocket 本身不使用也不要求线程.

线程安全

如同常规的 Boost.Asio 套接字, stream 不是线程安全的. 调用方须按 Asio 文档的要求, 使用隐式或显式 strand 同步套接字上的操作. websocket 流异步接口支持以下每种操作各有一个同时处于活动状态:

  • async_read 或 async_read_some
  • async_write 或 async_write_some
  • async_ping 或 async_pong
  • async_close

例如, 下面的代码会产生未定义行为, 因为程序试图同时执行两个读取:

ws.async_read(b, [](error_code, std::size_t){});
ws.async_read(b, [](error_code, std::size_t){});

而这段代码是正确的:

ws.async_read(b, [](error_code, std::size_t){});
ws.async_write(b.data(), [](error_code, std::size_t){});
ws.async_ping({}, [](error_code){});
ws.async_close({}, [](error_code){});

实现使用组合异步操作; 尽管某些个别操作可以同时读和写, 这种行为会在内部协调, 以确保底层流以安全方式被操作. 这使得异步读取操作能够在用户发起的异步写调用进行期间响应收到的 ping 帧.
