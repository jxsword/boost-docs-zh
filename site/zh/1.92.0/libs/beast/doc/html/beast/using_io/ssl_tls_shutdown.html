SSL/TLS 关闭

安全的 SSL/TLS 连接需要正确的关闭流程来安全地指示 EOF 条件. 此流程可防范一种称为 截断攻击 的攻击: 攻击者可以关闭底层传输层并控制 SSL/TLS 连接中最后一条报文的长度. 关闭流程由双方交换 close_notify 报文组成. 在 Boost.Asio 中, 这些步骤通过调用 shutdown() 或 async_shutdown() 于 ssl::stream 对象上进行.

error::stream_truncated

有些 SSL/TLS 实现不执行正确的关闭流程, 而是直接关闭底层传输层. 因此这些应用中的 EOF 条件不具有密码学安全性, 不应依赖. 不过, 在某些场景下 HTTPS 客户端或服务器不需要用 EOF 来判断最后一条报文的结束:

  • HTTP 报文带有 Content-Length 头, 且正文已完整接收 (正文长度已知) .
  • HTTP 报文使用分块传输编码, 且已收到最后分块.
  • HTTP 报文不含正文, 例如任何带 1xx (信息性) 、204 (无内容) 或 304 (未修改) 状态码的响应.

在这类场景中, http::read 或 http::async_read 操作会成功, 因为它们不需要 EOF 即可完成. 但流的下一个操作会因 net::ssl::error::stream_truncated 错误.

例如, 假设我们使用 Beast 与一个不执行正确 SSL/TLS 关闭流程的 HTTPS 服务器通信:

// Receive the HTTP response
http::read(stream, buffer, res);

// Gracefully shutdown the SSL/TLS connection
error_code ec;
stream.shutdown(ec);
// Non-compliant servers don't participate in the SSL/TLS shutdown process and
// close the underlying transport layer. This causes the shutdown operation to
// complete with a `stream_truncated` error. One might decide not to log such
// errors as there are many non-compliant servers in the wild.
if(ec != net::ssl::error::stream_truncated)
    log(ec);
不合规对端与未知正文长度

当 HTTPS 服务器不执行正确的 SSL/TLS 关闭流程、且发送依赖 EOF 判断正文结束的 HTTP 响应报文时, 这确实是一个安全问题, 但属于罕见情形. 之所以是安全问题, 是因为没有 SSL/TLS 关闭流程时 EOF 不具密码学安全性, 报文正文容易受到截断攻击.

以下示例可以从这样的服务器读取 HTTP 响应:

// Use an HTTP response parser to have more control
http::response_parser<http::dynamic_body> parser;

error_code ec;
// Receive the HTTP response until the end or until an error occurs
http::read(stream, buffer, parser, ec);

// Try to manually commit the EOF, the resulting message body would be
// vulnerable to truncation attacks.
if(parser.need_eof() && ec == net::ssl::error::stream_truncated)
    parser.put_eof(ec); // Override the error_code

if(ec)
    throw system_error{ec};

// Access the HTTP response inside the parser
std::cout << parser.get() << std::endl;


// Gracefully shutdown the SSL/TLS connection
stream.shutdown(ec); // Override the error_code
// Non-compliant servers don't participate in the SSL/TLS shutdown process and
// close the underlying transport layer. This causes the shutdown operation to
// complete with a `stream_truncated` error. One might decide not to log such
// errors as there are many non-compliant servers in the wild.
if(ec != net::ssl::error::stream_truncated)
    log(ec);
