常见问题 (FAQ)

为建立合理的预期并避免大量重复的评审意见, 这些说明回应了关于 Beast 以及其他经历过正式评审的 HTTP 库的最常见问题与评论.

"Beast 做任何事都需要太多用户代码! "

本库无意为特定的 HTTP 或 WebSocket 用例提供开箱即用的解决方案. 它是构建在 Boost.Asio 之上的一层合理的协议分层, 保留了 Boost.Asio 的内存管理风格与异步模型.

"Beast 不提供 HTTP 服务器? "

Beast 在 example 目录中有一个功能完整的 HTTP 服务器. 该服务器使用同步与异步的共享或专用端口, 同时支持 HTTP 与 WebSocket. 此外, 若 OpenSSL 可用, 服务器还在专用端口上支持加密的 TLS 连接. 而且该服务器带有一个“多端口”——一个灵活的单一端口, 在同一端口上同时支持加密与非加密连接、HTTP 与 WebSocket. 该服务器不是 Beast 公开接口的一部分, 因为该功能超出了本库的范围. 作者认为试图扩大本库的范围会降低它对标准化的吸引力.

"Beast 不提供 HTTP 客户端? "

“我只想用 HTTP 下载一个资源”是用户与评审者常见的呼声. 此类功能超出了 Beast 的范围. 构建一个功能完整的 HTTP 客户端是一项困难且足够庞大的任务, 值得单独成为一个库. 有许多事情要处理: 各种报文正文编码、复杂的头解析、诸如 Range 与 Cache-Control 这类困难的首部语义、重定向、Expect:100-continue、连接重试、域名解析、TLS, 等等等等. 作者的立场是: Boost 首先需要一套在协议层操作 HTTP 的公共名词与动词; Beast 提供的正是这种语言.

"还没有 HTTP/2 支持! "

许多评审者认为 HTTP/2 支持是 HTTP 库的必备特性. 作者同意 HTTP/2 很重要, 但也认为最合理的实现是不复用与 1.0/1.1 相同的网络读写接口来实现 HTTP/2.

Beast HTTP 报文模型在设计时考虑了新协议, 应当在该语境下评价它. 有在未来添加 HTTP/2 的计划, 但不急于求成. 用户现在就可以使用 HTTP/1; 我们不应为了等待明天的新协议而否认他们今天可用的功能. 作者的立场是: Beast 仅支持 HTTP/1 的实现已具有足够的价值, 缺少 HTTP/2 不应成为接受它的障碍.

Beast HTTP 报文模型适用于 HTTP/2 并且可以被复用. IETF HTTP 工作组把与 HTTP/1.x 的报文兼容性作为明确目标. 解析器可以在解码压缩的 HTTP/2 头之后直接产出完整的头. 流 ID 在逻辑上不是报文的一部分, 而是报文元数据, 应当带外传递 (见下文) . HTTP/2 会话以传统的 HTTP/1.1 Upgrade 开始, 方式与 WebSocket 升级类似. HTTP/2 实现可以使用现有的 Beast.HTTP 原语执行此握手.

"这应当能与 standalone-Asio 一起工作! "

Beast 使用的不仅是 Boost.Asio, 它依赖 Boost 的其他多个部分. standalone Asio 目前比 Boost 版本更超前. 以作者目前的资源, 同时维护 Beast 对两个 Asio 版本的支持是不现实的. 与非 Boost 库的兼容性不应作为接受标准. Beast 目前的定位是 Boost 的一部分: 仅此而已. 从更大的图景看, 作者的目标是将本库提案标准化. 实现这一目标的一条合理路径如下:

  1. Boost 库接受.
  2. 移植到 Boost.Asio 版本的 Networking-TS (这必须等 Boost 的 Asio 版本更新) .
  3. 等待 Networking-TS 成为 C++ 的正式组成部分.
  4. 移植到标准库版本的网络设施 (gcc、clang、msvc) .
  5. 开发提案语言 (这可与第 3、4 步同时进行)
"你需要基准测试! "

投入 Beast 的精力用于接口设计, 而非性能. 话虽如此, Beast 中最敏感的部分已被优化或在设计时考虑了优化. WebSocket 处理中较慢的部分已被优化, 而 HTTP 解析器的设计取自另一个以性能为设计目标的极受欢迎的项目 (见 https://github.com/h2o/picohttpparser) .

出自: http://www.boost.org/development/requirements.html

"首先追求清晰与正确; 对大多数 Boost 库而言, 优化只应是次要考虑. "

随着库走向成熟, 它将经历优化迭代; 基准测试自然伴随这一过程. tests 中包含一个小型基准测试程序, 用于比较 Beast 解析器与 NodeJS 参考解析器的性能, 还有一些基准测试用于比较 Beast 各种动态缓冲区实现与 Asio 的性能.

"Beast 是个糟糕的名字! "

"Boost.Http" 或 "Boost.WebSocket" 这样的名字会误导用户, 让他们以为可以用几行代码对 URL 发起 HTTP 请求, 或搭建一个 WebSocket 客户端/服务器. 核心工具放在哪里? 很可能, 把东西放进 boost/asio 目录会踩到 Boost.Asio 所有者的地盘; 至少会给外部仓库带来未被请求的额外工作.

"Beast" 足够模糊, 不暗示任何特定功能, 同时作为一个令人印象深刻总称, 指代一族低层容器与算法. 懂行的人或有低层网络协议操作需求的人不难找到它, 而引诱新手陷入糟糕体验的可能性大大降低. 专有名称有先例: "Hana"、"Fusion"、"Phoenix"、"Spirit". "Beast" 真的比 "mp11" 更糟吗? Beast 也已拥有不断增长的用户群体和开源社区的关注, Beast 这个名字出现在 reddit 帖子和 StackOverflow 上, 作为“该用哪个 HTTP 或 WebSocket 库”之类问题的答案.

"多一些更高级的示例会更有帮助, 例如包含带客户端/服务器证书的 TLS. "

server-framework 示例演示了如何实现一个使用证书支持 TLS 的服务器. 还有使用 TLS 的 websocket 与 HTTP 客户端示例. 此外, 证书的管理超出了本库公开接口的范围. Asio 已经为执行这些任务提供了文档、接口和示例——Beast 不打算重新发明它们, 也不打算冗余地提供这些信息.

"内置的 HTTP 路由器? "

我们假定这指的是把表达式与 HTTP 请求中的 URI 匹配并分派给调用代码的设施. 作者认为这是更高层代码的职责. Beast 不试图提供一个 web 服务器. 话虽如此, server-framework 示例有一个称为 Service 的请求路由概念. 提供了两个 Service: 一个用于提供文件, 另一个用于处理 WebSocket 升级请求.

"HTTP Cookies? 表单/文件上传? "

Cookie, 或一般性地管理这类 HTTP 头, 是更高层次的职责. Beast 只尽力把完整的报文送达调用代码或从调用代码送达. 它对 HTTP 头的处理仅限于处理报文正文所需, 其余留给调用者. 不过, 对于表单和文件上传, 报文类的对称接口允许 HTTP 请求包含任意正文类型, 包括上传文件或填写表单所需的类型.

"……支持 TLS (这算一个特性吗? 如果不是, 这将是致命缺陷) , 等等. "

Beast 与流概念协同工作, 因此它自动与你已通过 Asio 设置好的 boost::asio::ssl::stream 协同工作.

"还应该有更多示例说明如何把 http 服务与从文件系统获取文件、以 CGI 风格生成响应结合起来. "

本库的设计目标是不试图发明一个 web 服务器. 我们认为, 对建模 HTTP 报文并提供通过 Asio 发送和接收报文的函数的基本实现, 存在强烈需求. 这样的实现应当作为构建更高层抽象 (如前述的 HTTP 服务或 cgi 网关) 的基石.

example 目录中有几个提供文件的 HTTP 服务器, 还有一些经过测试和编译的代码片段, 可用作与其他进程交互的起点.

"如果需要, 你应当发送 100-continue 来请求正文的剩余部分. "

决定是否发送 "Expect: 100-continue" 头, 或在服务器端如何处理它, 是调用者的职责; Beast 提供在发送或读取正文之前发送或检查该头的功能.

"我还希望看到本库在生产环境中使用的实例. 这能提供一些证据, 说明该设计在实践中可行. "

Beast 已经在公共服务器上接收流量并处理每天价值数亿美元的金融交易. 这些服务器运行 rippled, 这是实现 repository 的开源软件 (Ripple Consensus Protocol) , 技术由 Ripple 提供.

此外, 该仓库在 2017 年人气显著增长. 有许多用户, 其中一些人直接参与仓库: 报告问题、执行测试, 某些情况下还提交带代码贡献的 pull request.

WebSocket 报文压缩呢?

Beast WebSocket 支持 draft-ietf-hybi-permessage-compression-00 中描述的 permessage-deflate 扩展. 该库自带 ZLib "deflate" 编解码器的仅头文件 C++11 移植, 用于 permessage-deflate 扩展的实现.

WebSocket 的 TLS/SSL 接口在哪里?

websocket::stream 包装你提供的套接字或流 (例如 boost::asio::ip::tcp::socket 或 boost::asio::ssl::stream) . 你像所有 Asio 示例中那样使用 ssl::stream 上的接口建立 TLS 连接, 然后围绕它构造你的 websocket::stream.

WebSocket 实现 does 支持通过 ADL 编译期虚函数 teardown 和 async_teardown 来关闭 TLS 连接. 它们会按照 rfc6455 正确关闭连接, 并且有可用于 TLS 流的重载. 调用者可以为用户自定义的下一层类型提供这些函数的自有重载.

Windows 与 OpenSSL: 在 Microsoft Windows 上如何安装并使用 OpenSSL 构建?

一种简单方法是使用命令行包安装器 chocolatey 或 scoop. 例如: "choco install -y openssl --x86 --version 1.1.1.700" 或 "scoop install openssl@1.1.1g -a 32bit -g"

如果你把 OpenSSL 安装到了名字带空格的目录, 通常更可取的做法是创建符号链接, 以便使用更简单的路径, 例如:

mklink /D "OpenSSL" "Program Files (x86)\\OpenSSL-Win32"

把环境变量 OPENSSL_ROOT 设置为新安装的位置:

set OPENSSL_ROOT=C:/OpenSSL

然后继续构建. 使用 OpenSSL 构建测试用例的示例参见 beast/.dockers/windows-vs-32/Dockerfile.
