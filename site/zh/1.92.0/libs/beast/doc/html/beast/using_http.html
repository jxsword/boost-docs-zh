HTTP

警告

更高层的功能 (例如 Basic 认证、mime/multipart 编码、cookie、重定向自动处理、gzip 传输编码、缓存或代理等) 并未直接提供, 但没有任何东西阻止用户使用 Beast 的 HTTP 报文类型来创建这些功能.

此库为程序员提供了简单而高性能的 HTTP 报文模型及其相关操作, 包括使用 Boost.Asio 对 HTTP/1 线上格式报文进行同步、异步与面向缓冲区的解析和序列化. 具体而言, 该库提供:

报文容器

完整的 HTTP 报文用 message 类建模, 并支持用户自定义.

流读取

函数 read, read_header, read_some, async_read, async_read_header 和 async_read_some 从 stream.

流写入

函数 write, write_header, write_some, async_write, async_write_header 和 async_write_some 向 stream.

序列化

该 serializer 产出一系列符合 rfc7230 线上表示的 message.

解析

该 parser 尝试把一系列八位组缓冲区转换为 message.

操作 HTTP 报文的接口分为多层. 最高层提供易用性, 较低各层则逐步提供更多控制、选项与灵活性. 最底层提供定制点, 用户自定义类型可以在那里替换实现的某些部分. 各层安排如下:

Level

读/写内容

说明

6

message

在最高层, 这些自由函数一次调用即可发送或接收完整的 HTTP 报文. 它们以易用为目标: read, write, async_read 和 async_write.

5

parser, serializer

要获得更多控制, 调用方可以自行负责管理所需的 parser 或 serializer 瞬态状态对象. 这样可以进行额外的配置, 例如在解析时限制报文组成部分的字节数, 或在输出时调节缓冲区的大小. 这些函数使用序列化器或解析器发送或接收完整报文: read, write, async_read 和 async_write.

4

header

有时需要先发送或接收 HTTP 头. 例如, 先读取头部并采取行动, 然后再继续读取正文. 这些函数使用 parser 或 serializer 来读取或写入头部: read_header, write_header, async_read_header 和 async_write_header.

3

部分 message

前述更高层的流操作都作用于完整的头部或报文. 在这一层, 可以增量地发送和接收报文. 这使资源受限的实现能把工作量约束在存储范围之内, 或在设置超时等场景下提供更好的控制. 这些函数读取或写入有界数量的数据, 并返回传输的字节数: read_some, write_some, async_read_some 和 async_write_some.

2

chunked-body

到目前为止, 解析与序列化操作会按需为大小事先未知的报文载荷应用或移除分块传输编码. 对某些特定领域, 需要直接控制分块编码报文载荷的传入或传出的分块. 解析方面可通过使用函数 on_chunk_header 和/或 on_chunk_body 设置钩子来实现. 序列化方面, 调用方可先发出头部, 然后使用这些缓冲区序列适配器控制每个分块的内容, 包括 分块扩展 和 trailer-part: chunk_body, chunk_crlf, chunk_header 和 chunk_last.

1

buffers

要获得最终控制, 可以完全绕过库的流算法, 改为通过调用 parser 或 serializer.

0

user-defined

除了 流 和 DynamicBuffer 的典型定制点之外, 用户自定义类型还可以在最低层替换库实现的部分内容. 这些定制点包括: Fields (创建存储 HTTP 字段的容器) Body (定义 HTTP 报文载荷使用的容器与算法) basic_parser (实现自定义报文表示策略)
注释

本文档假定读者对 Boost.Asio 以及 rfc7230 有一定了解. 本节提到的示例代码和标识符都以下列声明生效为前提书写:

#include <boost/beast/http.hpp>
using namespace boost::beast::http;
