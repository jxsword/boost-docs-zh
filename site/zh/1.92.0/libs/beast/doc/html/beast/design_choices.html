Design Choices设计选择

这些实现最初源于加密货币服务器应用 (例如 rippled, 以 C++ 编写) 的业务需求. 现有方案无法满足这些需求, 因此从头编写了 Beast 作为解决方案. Beast 的设计理念避免其他库表现出的缺陷:

  • 不要试图做太多事情.
  • 不要牺牲性能.
  • 仿效 Boost.Asio; 熟悉带来信心.
  • 角色对称的接口; 客户端与服务器相同 (或接近相同) .
  • 把重要决策 (例如分配内存或管理流量控制) 留给用户.

Beast 使用 DynamicBuffer 概念 (见 Networking TS) , 并严重依赖 ConstBufferSequence 与 MutableBufferSequence 概念向函数传递缓冲区. 作者发现动态缓冲区与缓冲区序列接口是与 Asio 交互以及其他任务 (例如对缓冲区中的数据做增量解析, 比如解析存储在 static_buffer 中的 WebSocket 帧) 的最优接口.

在开发 Beast 的过程中, 作者研究了其他软件包, 特别是评审过程中针对提供类似功能的其他软件包留下的意见. 在本节以及随后的常见问题中, 我们尝试回答那些同样适用于 Beast 的问题.

对于 HTTP, 我们对报文建模以最大化实现策略的灵活性, 同时允许诸如 read 和 write 这类熟悉的操作. HTTP 接口还进一步受 WebSocket 模块的需求驱动, 因为 WebSocket 会话在开始时需要 HTTP Upgrade 握手交换. 其他设计目标:

  • 保持简单.
  • 保持低层; 不要发明一整套 web 服务器或客户端.
  • 在用户需要时允许定制.
