Comparison to Zaphoyd Studios WebSocket++与 Zaphoyd Studios WebSocket++ 的比较

这与 websocketpp (另一种仅头文件的 WebSocket 实现) 相比如何?

1. 同步接口

Beast 通过同步接口为 WebSocket 提供完整支持. 它使用与 Boost.Asio 中相同的接口风格: 抛出异常的版本, 或通过引用参数返回错误码的版本:

websocketpp

void

<not available>

2. 连接模型

websocketpp 利用一个特征支持多种传输方式, 即 config::transport_type (asio 传输示例) . 要了解实现一种传输所涉及的复杂度, 可将 asio 传输与 iostream 传输 (允许在 std::iostream 上进行 websocket 通信的层) .

相比之下, Beast 通过仅定义一个 NextLayer 模板参数来抽象传输. NextLayer 的类型要求对用户来说已很熟悉, 因为它们在 Asio 中有文档: AsyncReadStream、AsyncWriteStream、SyncReadStream、SyncWriteStream.

与 beast::websocket::stream 相比, 用用户自定义类型实例化 websocketpp::connection 的类型要求大幅减少 (18 个函数对 2 个) . 注意 websocketpp 连接以 shared_ptr 传递. Beast 在其公开接口的任何地方都不使用 shared_ptr. beast::websocket::stream 的构造与移动方式与 boost::asio::ip::tcp::socket 完全相同. 调用者可以随意把这样的对象放进 shared_ptr, 但这并非必须.

websocketpp 

template<class NextLayer>
class stream
{
    NextLayer next_layer_;
    ...
}

template <typename config>
class connection
: public config::transport_type::transport_con_type
, public config::connection_base
{
public:
    typedef lib::shared_ptr<type> ptr;
    ...
}
3. 客户端与服务器角色

websocketpp 通过不同类的层次结构提供多角色支持. beast::websocket::stream 与角色无关, 它在同一个类中提供执行客户端与服务器握手的成员函数. 客户端与服务器流使用相同的类型.

4. 线程安全

websocketpp 使用互斥量保护共享数据免受并发访问. 相比之下, Beast 在其实现中不使用互斥量, 而是遵循 Asio 模式: 对异步发起函数的调用, 通过关联执行器机制, 使用与调用最终处理器相同的方法来调用中间处理器.

Beast 中唯一的要求是对异步发起函数的调用都发生在同一个隐式或显式 strand 上. 例如, 若与 io_context 关联的 beast::websocket::stream 是单线程的, 这就算作隐式 strand, 不会产生与互斥量相关的性能开销.

Beast

websocketpp 

mutex_type m_read_mutex;
5. 回调模型

websocketpp 要求对其接口中的每个事件 (例如收到报文) 进行一次性调用以设置处理器. 处理器由一个 std::function 等价物表示. 重要的是要认识到 websocketpp 接口对该处理器执行类型擦除.

相比之下, Beast 处理器的指定方式与 Boost.Asio 完全相同. 它们是可复制或移动的函数对象, 但最重要的是它们不被类型擦除. 编译器可以透过类型直接看到实现, 从而允许优化. 此外, Beast 遵循 Asio 处理器的处理规则. 它通过对 bind_allocaotr 等函数使用参数依赖查找重载, 尊重与处理器关联的任何分配、执行器和取消操作.

Beast 的完成处理器在调用点提供. 对异步发起函数的每次调用, 保证最终恰好调用处理器一次. 这与 Boost.Asio 中的异步发起函数完全相同, 允许组合更高层次的抽象.

7. 报文缓冲

websocketpp 定义了一个报文缓冲区, 以 shared_ptr 作为参数传入, 并有一个关联的报文管理器, 允许内存的聚合与复用. websocketpp::message 的实现使用 std::string 来保存载荷. 若传入的报文被拆分成多个帧, 该字符串可能为每个续帧重新分配内存. std::string 总是使用标准分配器, 无法自定义分配器的选择.

Beast 允许调用者指定接收报文或帧数据的对象, 其类型可以是满足 DynamicBuffer 要求的任意类型 (仿照 boost::asio::streambuf) .

Beast 自带类 basic_multi_buffer, 它是 DynamicBuffer 概念的一种高效实现, 利用多个已分配的八位组数组. 若传入的报文被拆分成多个片段, 不会发生重新分配; 而是在现有分配被填满时, 把新的分配追加到序列中. Beast 不对调用者强加任何特定的内存管理模型. Beast 提供的 basic_multi_buffer 通过模板参数支持标准分配器. 可以使用 Beast 自带的 DynamicBuffer, 按需自定义分配器, 或提供满足要求的自有类型.

Beast

websocketpp 

template<class DynamicBuffer>
read(DynamicBuffer& dynabuf);

template <template<class> class con_msg_manager>
class message {
public:
    typedef lib::shared_ptr<message> ptr;
    ...

    ...

8. 发送报文

发送报文时, websocketpp 要求载荷被封装到一个 websocketpp::message 对象中并使用 std::string 作为存储, 或者通过构造新的报文对象来要求调用者所提供缓冲区的一份副本. 报文被放入发送队列. 异步写操作在后台运行以清空队列. 没有面向用户的处理器可以注册以便在报文或帧发送完成时收到通知.

Beast 在发送数据时不分配内存也不复制缓冲区. 调用者的缓冲区被就地发送. 可以使用满足 __ConstBufferSequence 要求的任意对象, 从而支持高效的分散-聚集 I/O.

ConstBufferSequence 接口允许调用者从内存映射区域发送数据 (websocketpp 无法做到) . 调用者还可以使用相同的缓冲区向多个流发送数据, 例如一次向许多客户端广播公共订阅数据. 对 async_write 的每次调用, 当数据发送完成时完成处理器被调用一次, 方式与 boost::asio::async_write 完全相同.

9. 流式传输报文

websocketpp 要求整个报文能放入内存, 且大小事先已知.

Beast 允许调用者以单独的帧组成报文. 当数据大小事先未知, 或不希望把整个报文一次性缓冲进内存再发送时, 这很有用. 例如, 发送运行在协程上的数据库查询的周期性输出; 或者分片发送文件内容, 而不把它全部载入内存.

10. 流量控制

websocketpp 的读实现持续地从网络异步读取并缓冲报文数据. 为防止无界增长并利用 TCP/IP 的流量控制机制, 调用者可以周期性地把这个“读泵”关闭再打开.

相比之下, beast::websocket::stream 不会独立地开始后台活动, 也不缓冲报文. 只有在存在带关联处理器的异步发起函数调用 (例如 beast::websocket::stream::async_read) 时它才接收数据. 应用无需实现显式逻辑来调节数据流, 而是遵循传统模型: 发起一次读, 收到读完成, 处理报文, 然后发起一次新的读并重复该过程.

Beast

websocketpp

<implicit> 

lib::error_code pause_reading();
lib::error_code resume_reading();
11. 连接建立

websocketpp 提供 endpoint 类, 可以处理端口的绑定与监听, 并生成连接对象.

Beast 在这里不重复造轮子, 调用者使用 boost::asio 中已有的接口来接收传入连接、解析主机名或建立传出连接. 在套接字 (或 boost::asio::ssl::stream) 连接之后, 围绕它构造 beast::websocket::stream, 即可执行 WebSocket 握手.

Beast 用户可以自由实现自己的“连接管理器”, 但没有要求必须这样做.

Beast、also

websocketpp 

#include <boost/asio.hpp>

template <typename config>
class endpoint : public config::socket_type;
12. WebSocket 握手

调用者调用 beast::websocket::accept 来执行 WebSocket 握手, 但没有要求必须使用此函数. 高级用户可以自行执行 WebSocket 握手. Beast WebSocket 提供了组合请求或响应的工具, 而 Beast HTTP 接口提供了发送和接收 HTTP/1 报文 (包括建立 WebSocket 会话所必需的 HTTP Upgrade 请求) 的容器与算法.

Beast 允许调用者传入已收到的 HTTP Upgrade 请求, 适用于调用者已经收到 HTTP 报文的情况. 这种灵活性允许新颖而健壮的实现, 例如能够在同一端口上以多种协议握手的监听套接字.

有时调用者希望在读取 WebSocket HTTP Upgrade 请求之前先在套接字上读取一些字节. Beast 允许把这些已接收的字节提供给接受函数的一个重载, 以支持复杂的功能. 例如, 一个既能接受常规 WebSocket 又能接受安全 WebSocket (SSL) 连接的监听套接字.
