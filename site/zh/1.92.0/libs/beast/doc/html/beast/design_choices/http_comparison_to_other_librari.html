HTTP Comparison to Other Libraries与其他库的 HTTP 比较

有一些已发布的 C++ 库实现了部分 HTTP 协议. 我们分析这些库选择的报文模型, 并讨论其相对于 Beast 的优缺点.

作者评估外部库的一般策略如下:

  • 审查报文模型. 它能表示完整的请求或响应吗? 对分配器的支持程度如何? 可定制的程度有多大?
  • 审查流抽象. 这是可用于解析或序列化 (即读写) 的对象类型, 例如套接字. 可以指定用户自定义类型吗? 与 Asio 或 Networking-TS 概念的符合程度如何?
  • 检查对缓冲区的处理. 是由库管理缓冲区, 还是用户可以提供自己的缓冲区?
  • 库如何处理边角情况, 例如尾随部分 (trailer) 、Expect: 100-continue 或正文类型的延迟承诺?
注释

来自外部库的声明示例经过了编辑: 为简化起见删除了部分内容.

cpp-netlib

cpp-netlib 是一个网络编程库, 曾打算进入 Boost 但未经历正式评审. 截至撰写时, 它仍在使用 Boost 的名称、命名空间和目录结构, 尽管该项目声明 Boost 接受不再是目标. 该库基于 Boost.Asio, 并自诩为 "a collection of network related routines/implementations geared towards providing a robust cross-platform networking library". 它把 "Common Message Type" 列为特性. 在前面链接的分支上, 它使用如下声明:

template <class Tag>
struct basic_message {
 public:
  typedef Tag tag;

  typedef typename headers_container<Tag>::type headers_container_type;
  typedef typename headers_container_type::value_type header_type;
  typedef typename string<Tag>::type string_type;

  headers_container_type& headers() { return headers_; }
  headers_container_type const& headers() const { return headers_; }

  string_type& body() { return body_; }
  string_type const& body() const { return body_; }

  string_type& source() { return source_; }
  string_type const& source() const { return source_; }

  string_type& destination() { return destination_; }
  string_type const& destination() const { return destination_; }

 private:
  friend struct detail::directive_base<Tag>;
  friend struct detail::wrapper_base<Tag, basic_message<Tag> >;

  mutable headers_container_type headers_;
  mutable string_type body_;
  mutable string_type source_;
  mutable string_type destination_;
};

此容器是用于表示 HTTP 报文的基类模板. 它对各种特征类使用“标签类型”风格的特化, 允许对报文的各个部分进行定制. 例如, 用户特化 headers_container<T> 来决定哪个容器类型存放头字段. 我们指出容器声明的一些问题:

  • 头与正文容器只能被默认构造.
  • 不支持有状态分配器.
  • 无法把 body_ 的类型承诺推迟到读入头之后.
  • 报文模型包含“源”与“目的”. 这是与连接相关的额外元数据, 不属于 HTTP 协议规范的一部分, 应属于其他地方.
  • 对 string_type (一个定制点) 用于源、目的和正文, 暗示 string_type 建模了一个 ForwardRange, 其 value_type 为 char. 考虑到该库构建在 Boost.Asio 之上, 这种表示并不理想. 把 DynamicBuffer 适配到所需的前向范围会破坏 ConstBufferSequence 与 MutableBufferSequence 在动态缓冲区中传递的信息. 后果是 cpp-netlib 的实现效率将低于等效的符合 Networking TS 的实现.
  • 该库使用 string<Tag> 的特化来改变各处使用的字符串类型, 包括正文、字段名/值对, 以及源与目的等额外元数据. 用户只能选择单一类型: 字段名、字段值和正文容器都将使用相同的字符串类型. 这限制了该定制点的效用. 该库对字符串特征的使用仅限于在 std::string 和 std::wstring 之间选择. 鉴于这些限制, 我们认为这一用例并不令人信服.
  • 特化的特征类会生成大量小型附加框架类型. 要特化特征, 用户需要退出自己的命名空间并侵入 boost::network::http 命名空间. 特征在库中的使用方式把特征的用途限制在琐碎目的上.
  • `string<Tag> 定制点把用户自定义正文类型限制在少数几种策略上. 无法把 HTTP 报文正文表示为文件名及配套的、从文件系统存取数据的算法.

本库报文容器的设计因使用特征特化进行定制的体系而显得笨重. 由于这些定制在容器声明中的使用方式, 它们的用途极其有限, 使设计过于复杂而没有相应收益.

Boost.HTTP

boost.http 是 2014 年 Google Summer of Code 的成果. 它被提交进行 Boost 正式评审并于 2015 年被拒绝. 它基于 Boost.Asio, 且该库的开发持续至今. 在前面链接的分支上, 它使用如下报文声明:

template<class Headers, class Body>
struct basic_message
{
    typedef Headers headers_type;
    typedef Body body_type;

    headers_type &headers();

    const headers_type &headers() const;

    body_type &body();

    const body_type &body() const;

    headers_type &trailers();

    const headers_type &trailers() const;

private:
    headers_type headers_;
    body_type body_;
    headers_type trailers_;
};

typedef basic_message<boost::http::headers, std::vector<std::uint8_t>> message;

template<class Headers, class Body>
struct is_message<basic_message<Headers, Body>>: public std::true_type {};

  • 此容器无法建模完整的报文. start-line 项 (请求的方法与目标, 响应的原因短语) 以及 http-version 都是带外传递的. 对包含起始行的报文进行操作的函数需要额外的参数. 这在其中一个example programs中很明显. 500 与 "OK" 参数分别表示响应的 status-code 与 reason-phrase:

    ...
http::message reply;
...
self->socket.async_write_response(500, string_ref("OK"), reply, yield);
  • headers_、body_ 和 trailers_ 只能被默认构造, 因为没有显式声明的构造函数.
  • 无法把 Body 类型的承诺推迟到读入头之后. 这与前面关于默认构造的限制相关.
  • 不支持有状态分配器. 这源于前面关于默认构造的限制. 起始行字符串的缓冲区必须在报文对象之外管理, 因为它们不是成员.
  • 尾随部分存储在单独的对象中. 除了为完全支持头、正文和尾随成员各自的任意转发参数列表所需的额外构造函数数量的组合爆炸之外, 还要事先知道某个特定 HTTP 字段将位于头中还是尾随部分中, 这对操作报文的通用函数带来了不必要的复杂化.
  • 这些声明暗示 std::vector 是 Body 的一个模型. 更正式地说, 正文由 ForwardRange 概念表示, 其 value_type 是 8 位整数. 考虑到该库构建在 Boost.Asio 之上, 这种表示并不理想. 把 DynamicBuffer 适配到所需的前向范围会破坏 ConstBufferSequence 与 MutableBufferSequence 在动态缓冲区中传递的信息. 后果是 Boost.HTTP 在处理正文容器时的效率将低于等效的符合 Networking TS 的实现.
  • Body 定制点把用户自定义类型限制在非常有限的实现策略上. 例如, 无法把 HTTP 报文正文表示为文件名及配套的、从文件系统存取数据的算法.

这种表示只覆盖狭窄的用例范围. 它的定制与性能潜力有限. 由于把起始行字段排除在模型之外, 它更难使用.

C++ REST SDK (cpprestsdk)

cpprestsdk 是 Microsoft 的一个项目, 它旨在帮助 C++ 开发者连接服务并与之交互. 在本文评审的库中它提供的功能最多, 包括借助其 websocket++ 依赖对 WebSocket 服务的支持. 构建基于 Windows 的应用时它可以使用 HTTP.SYS 等原生 API, 也可以使用 Boost.Asio. WebSocket 模块只使用 Boost.Asio.

由于 cpprestsdk 由大型公司开发, 它包含相当多的功能, 必然有更多接口. 我们将把用于建模报文的接口拆分成更易管理的部分. 这是用于存储 HTTP 头字段的容器:

class http_headers
{
public:
    ...

private:
    std::map<utility::string_t, utility::string_t, _case_insensitive_cmp> m_headers;
};

这个声明相当简陋. 我们指出大多数字段容器的典型问题:

  • 容器只能被默认构造.
  • 不支持分配器, 无论有状态还是无状态.
  • 完全没有定制点.

现在我们分析更大的报文容器的结构. 该库使用句柄/正文 (handle/body) 惯用法. 有两个公开的报文容器接口, 一个用于请求 (http_request) , 一个用于响应 (http_response) . 每个接口维护指向实现类的私有共享指针. 公开成员函数调用被路由到内部实现. 这是第一个实现类, 它构成请求与响应实现的基类:

namespace details {

class http_msg_base
{
public:
    http_headers &headers() { return m_headers; }

    _ASYNCRTIMP void set_body(const concurrency::streams::istream &instream, const utf8string &contentType);

    /// Set the stream through which the message body could be read
    void set_instream(const concurrency::streams::istream &instream)  { m_inStream = instream; }

    /// Set the stream through which the message body could be written
    void set_outstream(const concurrency::streams::ostream &outstream, bool is_default)  { m_outStream = outstream; m_default_outstream = is_default; }

    const pplx::task_completion_event<utility::size64_t> & _get_data_available() const { return m_data_available; }

protected:
    /// Stream to read the message body.
    concurrency::streams::istream m_inStream;

    /// stream to write the msg body
    concurrency::streams::ostream m_outStream;

    http_headers m_headers;
    bool m_default_outstream;

    /// <summary> The TCE is used to signal the availability of the message body. </summary>
    pplx::task_completion_event<utility::size64_t> m_data_available;
};

要理解这些声明, 首先需要理解 cpprestsdk 使用 Microsoft Concurrency Runtime 定义的异步模型. pplx namespace 中的标识符定义了任务与事件等常见异步模式. concurrency::streams::istream 参数与 m_data_available 数据成员表明缺乏关注点分离. 在报文声明中, HTTP 报文的表示不应与用于序列化或解析这些报文的异步模型混为一谈.

下一个声明构成完整实现类, 由公开接口中的句柄引用 (随后给出) :

/// Internal representation of an HTTP request message.
class _http_request final : public http::details::http_msg_base, public std::enable_shared_from_this<_http_request>
{
public:
    _ASYNCRTIMP _http_request(http::method mtd);

    _ASYNCRTIMP _http_request(std::unique_ptr<http::details::_http_server_context> server_context);

    http::method &method() { return m_method; }

    const pplx::cancellation_token &cancellation_token() const { return m_cancellationToken; }

    _ASYNCRTIMP pplx::task<void> reply(const http_response &response);

private:

    // Actual initiates sending the response, without checking if a response has already been sent.
    pplx::task<void> _reply_impl(http_response response);

    http::method m_method;

    std::shared_ptr<progress_handler> m_progress_handler;
};

} // namespace details

与前面一样, 我们注意到 HTTP 请求的实现类更多关注异步发送报文的机制, 而不是像 rfc7230 所描述的那样真正建模 HTTP 报文:

  • 接受 std::unique_ptr<http::details::_http_server_context 的构造函数破坏了封装与关注点分离. 它无法针对用户自定义的服务器上下文进行扩展.
  • “取消令牌”存储在报文内部. 这破坏了关注点分离.
  • _reply_impl 函数暗示报文实现还分担了发回 HTTP 应答的手段的职责. 如果它与报文容器完全分离会更好.

最后, 这是表示 HTTP 请求的公开类:

class http_request
{
public:
    const http::method &method() const { return _m_impl->method(); }

    void set_method(const http::method &method) const { _m_impl->method() = method; }

    /// Extract the body of the request message as a string value, checking that the content type is a MIME text type.
    /// A body can only be extracted once because in some cases an optimization is made where the data is 'moved' out.
    pplx::task<utility::string_t> extract_string(bool ignore_content_type = false)
    {
        auto impl = _m_impl;
        return pplx::create_task(_m_impl->_get_data_available()).then([impl, ignore_content_type](utility::size64_t) { return impl->extract_string(ignore_content_type); });
    }

    /// Extracts the body of the request message into a json value, checking that the content type is application/json.
    /// A body can only be extracted once because in some cases an optimization is made where the data is 'moved' out.
    pplx::task<json::value> extract_json(bool ignore_content_type = false) const
    {
        auto impl = _m_impl;
        return pplx::create_task(_m_impl->_get_data_available()).then([impl, ignore_content_type](utility::size64_t) { return impl->_extract_json(ignore_content_type); });
    }

    /// Sets the body of the message to the contents of a byte vector. If the 'Content-Type'
    void set_body(const std::vector<unsigned char> &body_data);

    /// Defines a stream that will be relied on to provide the body of the HTTP message when it is
    /// sent.
    void set_body(const concurrency::streams::istream &stream, const utility::string_t &content_type = _XPLATSTR("application/octet-stream"));

    /// Defines a stream that will be relied on to hold the body of the HTTP response message that
    /// results from the request.
    void set_response_stream(const concurrency::streams::ostream &stream);
    {
        return _m_impl->set_response_stream(stream);
    }

    /// Defines a callback function that will be invoked for every chunk of data uploaded or downloaded
    /// as part of the request.
    void set_progress_handler(const progress_handler &handler);

private:
    friend class http::details::_http_request;
    friend class http::client::http_client;

    std::shared_ptr<http::details::_http_request> _m_impl;
};

从这个声明可以清楚地看出, 本库报文模型的目标由其用例 (与 REST 服务器交互) 驱动, 而非通用地建模 HTTP 报文. 我们注意到与其他声明类似的问题:

  • 完全没有编译期定制点. 唯一的定制在 concurrency::streams::istream 与 concurrency::streams::ostream 引用参数中. 推测它们是抽象接口, 用户可以派生子类以实现自定义行为.
  • 正文的提取与异步模型混在一起.
  • 无法为提取正文时使用的容器定义分配器.
  • 正文只能提取一次, 限制了在使用函数式编程风格时对该容器的使用.
  • 设置正文需要 vector 或 concurrency::streams::istream. 无法使用用户自定义类型.
  • HTTP 请求容器混入了 HTTP 响应行为 (参见 set_response_stream 成员) . 这同样可能是用途驱动的, 但关注点分离的缺失把本库限制在作者明确设想的用途上.

cpprestsdk 中 HTTP 报文模型的总体基调是“没有用户可定义的定制”. 没有分配器支持, 也没有关注点分离. 它被设计为执行一组特定的行为. 换句话说, 它不遵循开闭原则.

Concurrency Runtime 中的任务以与 std::future 类似的方式运作, 但有一些改进, 例如 C++ 标准中还没有的续体 (continuation) . 使用基于任务的异步接口而非完成处理器的代价已有充分记录: 组合任务操作调用链上的同步点无法被优化掉. 参见 A Universal Model for Asynchronous Operations (Kohlhoff) .
