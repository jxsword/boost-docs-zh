SSL/TLS 证书

证书颁发机构

证书颁发机构 (CA) 是签署数字证书的可信实体, 使用户能够验证证书的真实性. 与其为每台服务器存储每张单独的证书 (因数量庞大且频繁续期而不可行) , 用户可以存储一组有限的根证书, 按需认证服务器证书.

Boost.Asio 提供多种加载证书颁发机构证书的方法:

  • net::ssl::context::add_certificate_authority
  • net::ssl::context::add_verify_path
  • net::ssl::context::load_verify_file
  • net::ssl::context::set_default_verify_paths

设置对端验证很重要, 这样证书校验不成功时 TLS/SSL 握手就会失败:

// Verify the remote server's certificate
ctx.set_verify_mode(net::ssl::verify_peer);

客户端还必须校验证书中的主机名或 IP 地址与预期相符. net::ssl::host_name_verification 辅助函数对象可以按 RFC 6125 描述的规则执行此校验:

// Verify the remote server's Hostname or IP address
stream.set_verify_callback(
    net::ssl::host_name_verification("host.name"));

服务器还可以请求并校验客户端证书来认证客户端:

// Verify the remote client's certificate
ctx.set_verify_mode(
    net::ssl::verify_peer |
    net::ssl::verify_fail_if_no_peer_cert);
服务器证书

服务器证书是确认服务器作为客户端合法目的端身份的数字证书. 它包含可验证的签名, 确保它由可信的证书颁发机构 (CA) 签发.

当服务器证书由中间证书颁发机构签发, 而客户端缺少这些中间证书时, 服务器应向客户端提供所有相关证书. 这使客户端能够对照根证书校验链中的最终证书.

以下 Boost.Asio 方法可用于加载证书或证书链:

  • net::ssl::context::use_certificate
  • net::ssl::context::use_certificate_file
  • net::ssl::context::use_certificate_chain
  • net::ssl::context::use_certificate_chain_file
客户端证书

服务器可以通过要求并校验客户端证书来认证客户端, 阻止没有有效证书和私钥者访问. 服务器通过修改对端验证设置来实施这一点:

// Verify the remote client's certificate
ctx.set_verify_mode(
    net::ssl::verify_peer |
    net::ssl::verify_fail_if_no_peer_cert);

若使用此方式, 必须把所需的 CA 证书加载到服务器的 SSL 上下文中, 以启用对客户端证书的校验.

Common Name 与 Subject Alternative Name

主体备用名称 (SAN) 是 X.509 证书中的扩展, 允许多个域名、子域或 IP 地址与单个 SSL/TLS 证书关联. 在此之前, 证书主体中的 Common Name 字段只能包含单个主机名.

RFC 6125 建议: 若证书包含 SAN dNSName 字段, 客户端必须忽略主体 CN 字段. 一些现代浏览器 (如 Google Chrome) 只检查 SSL/TLS 证书的 SAN 部分, 拒绝只含 CN 字段的证书.

私钥

SSL/TLS 握手期间需要证书的私钥, 以证明证书的提供者是其合法所有者

以下 Boost.Asio 方法可用于加载私钥:

  • net::ssl::context::use_private_key
  • net::ssl::context::use_private_key_file
  • net::ssl::context::use_rsa_private_key
  • net::ssl::context::use_rsa_private_key_file

如果私钥受密码保护, net::ssl::context::set_password_callback 允许指定可调用对象来获取密码.

自签发与自颁发证书

自颁发证书是签发者与主体为同一实体的证书.

自签名证书是自颁发证书的一种, 其数字签名可以用证书内的公钥验证.

警告

安装不受信任的、自颁发的或自签名的 CA 证书会带来重大安全风险, 因为它签发证书的域不受任何限制. 攻击者可以为任何公共域生成伪造证书, 一旦获得你网络的访问权, 便可实施中间人攻击.

Diffie-Hellman (DH) 参数

Diffie-Hellman (DH) 密钥交换是一种密码学协议, 允许两方在不安全的通信信道上安全地建立共享秘密. 密钥交换过程需要双方就一组参数 (称为 Diffie-Hellman 参数) 达成一致, 这些参数包括大素数 p 和生成元 g. 由于生成这些参数计算开销很大, 用户可能更愿意在启动时提供预计算的值.

以下 Boost.Asio 方法可用于加载 DH 参数:

  • net::ssl::context::use_tmp_dh
  • net::ssl::context::use_tmp_dh_file

如果不提供 DH 参数, OpenSSL 将拒绝执行任何使用基于 DHE 的密码套件的握手, 但仍可使用其他密码套件, 例如基于 ECDHE 的套件.

自颁发证书示例

在下面的示例中, 我们将生成一个自签名的 CA 证书, 并用它签发服务器与客户端证书.

  • 生成 CA 证书:
openssl req -new -newkey rsa:4096 -keyout ca.key -x509 -out ca.crt -subj "/CN=localhost" -days 365
  • 生成服务器 CSR:
openssl req -new -newkey rsa:4096 -keyout server.key -out server.csr -subj "/CN=localhost" -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
  • 使用我们的 CA 签署服务器 CSR:
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -copy_extensions copy -days 365 -out server.crt
  • 生成客户端 CSR:
openssl req -new -newkey rsa:4096 -keyout client.key -out client.csr -subj "/CN=client.1"
  • 使用我们的 CA 签署客户端 CSR:
openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key -days 365 -out client.crt
  • 生成 DH 参数文件:
openssl dhparam -out dh4096.pem 4096
