HTTP Message Container 🎦HTTP 报文容器 🎦

以下视频演讲于 2017 年在 CppCon 上发表. 该演讲简化地解释了 Beast 中所用 HTTP 报文容器的设计过程. 所用的幻灯片与代码可在 GitHub repository 获取.

在本节中, 我们描述建模 HTTP 报文的问题, 并解释本库如何得出其解决方案, 同时讨论设计选择的优缺点. 创建报文模型的目标是创建一个具有值语义、可移动和/或可复制的容器, 它包含序列化所需的全部信息, 或解析期间捕获的全部信息. 更正式地说, 给定:

  • m 是一个 HTTP 报文容器的实例
  • x 是描述 rfc7230 中序列化格式下有效 HTTP 报文的一系列八位组.
  • S(m) 是一个序列化函数, 它从报文容器产出一系列八位组.
  • P(x) 是一个解析函数, 它从一系列八位组产出报文容器.

以下关系成立:

  • S(m) == x
  • P(S(m)) == m

我们还希望报文容器具有允许以下功能的定制点: 分配器感知、表示头字段的用户自定义容器, 以及表示正文的用户自定义类型和算法. 最后, 由于请求与响应在 start-line 中的字段不同, 我们希望请求与响应的容器由不同类型表示, 以便函数重载.

以下是我们声明一些报文容器的第一次尝试:

/// An HTTP request
template<class Fields, class Body>
struct request
{
    int         version;
    std::string method;
    std::string target;
    Fields      fields;

    typename Body::value_type body;
};

/// An HTTP response
template<class Fields, class Body>
struct response
{
    int         version;
    int         status;
    std::string reason;
    Fields      fields;

    typename Body::value_type body;
};

这些容器能够表示 rfc7230 所描述的 HTTP 请求与响应模型中的一切. 请求与响应对象是不同的类型. 用户可以选择表示字段的容器. 用户还可以选择 Body 类型, 它是一个概念, 不仅定义 body 成员的类型, 还定义在执行序列化和解析时在该成员中传入传出信息所用的算法.

然而, 问题出现了. 我们如何编写一个既能接受请求又能接受响应对象的函数? 按现有写法, 唯一显而易见的解决方案是把报文做成模板类型. 随后还需要额外的特征类来确保传入的对象具有满足要求的有效类型. 把每个容器做成偏特化即可绕过这些不必要的复杂化:

/// An HTTP message
template<bool isRequest, class Fields, class Body>
struct message;

/// An HTTP request
template<class Fields, class Body>
struct message<true, Fields, Body>
{
    int         version;
    std::string method;
    std::string target;
    Fields      fields;

    typename Body::value_type body;
};

/// An HTTP response
template<bool isRequest, class Fields, class Body>
struct message<false, Fields, Body>
{
    int         version;
    int         status;
    std::string reason;
    Fields      fields;

    typename Body::value_type body;
};

现在我们可以声明一个以任意报文为参数的函数:

template<bool isRequest, class Fields, class Body>
void f(message<isRequest, Fields, Body>& msg);

该函数可以操作请求与响应共有的字段. 如果它需要访问其他字段, 可以使用带偏特化的重载, 或在 C++17 中使用 constexpr 表达式:

template<bool isRequest, class Fields, class Body>
void f(message<isRequest, Fields, Body>& msg)
{
    if constexpr(isRequest)
    {
        // call msg.method(), msg.target()
    }
    else
    {
        // call msg.result(), msg.reason()
    }
}

在非平凡的 HTTP 应用中, 我们常常希望先读取 HTTP 头并检查其内容, 然后再为 Body 选择类型. 为此, 需要一种方法建模报文的头部分. 而且我们希望以一种允许接受头作为参数的函数同时接受表示整个报文的类型的方式来实现 (函数只会看到头部分) . 这暗示使用继承, 从报文中拆分出一个新的基类:

/// An HTTP message header
template<bool isRequest, class Fields>
struct header;

访问字段的代码必须费力地写出 fields 成员, 所以我们不仅让 header 成为一个基类, 还做一个易用性改进: 为记法方便让头从字段派生. 为了正确支持 Fields 的所有构造形式, 需要一组合适的构造函数重载 (未显示) :

/// An HTTP request header
template<class Fields>
struct header<true, Fields> : Fields
{
    int         version;
    std::string method;
    std::string target;
};

/// An HTTP response header
template<class Fields>
struct header<false, Fields> : Fields
{
    int         version;
    int         status;
    std::string reason;
};

/// An HTTP message
template<bool isRequest, class Fields, class Body>
struct message : header<isRequest, Fields>
{
    typename Body::value_type body;

    /// Construct from a `header`
    message(header<isRequest, Fields>&& h);
};

注意 message 类现在有一个构造函数, 允许从类似类型的 header 构造报文. 这处理了用户已拥有头并想为 Body 作出类型承诺的情况. 可以声明一个接受任意头的函数:

template<bool isRequest, class Fields>
void f(header<isRequest, Fields>& msg);

到目前为止, 我们还没有认真考虑 message 类的构造函数. 但要实现全部目标, 我们需要确保有足够的构造函数重载, 不仅为实例化类型支持时的特殊复制与移动成员提供支持, 还允许字段容器与正文容器用任意可变参数列表构造. 这使容器能够完整支持分配器.

库中使用的方案是, 在构造时把报文当作 std::pair 对待, 只是把 first 与 second 换成 Fields 基类和 message::body 成员. 这意味着这些字段的单参数构造函数应当像 std::pair 一样可访问, 并且应当提供与 pair 对 std::piecewise_construct 的使用完全相同的机制. 这些构造函数太复杂, 此处不再重复, 有兴趣的读者可以查看对应头文件中的声明.

我们的报文容器现在已有重大进展, 但仍有一个绊脚石. 无法控制 std::string 成员的分配器. 我们可以把分配器加入头与报文类的模板参数列表, 将其用于那些字符串. 这并不令人满意, 因为支持该方案所需的构造函数变体会出现组合爆炸. 这也意味着请求报文可能拥有 种不同的分配器: 两个字段与正文各一, 方法与目标字符串各一. 需要更好的方案.

为绕过这一点, 我们做了一处接口修改, 然后给 Fields 类型增加一项要求. 首先, 接口变更:

/// An HTTP request header
template<class Fields>
struct header<true, Fields> : Fields
{
    int         version;

    verb        method() const;
    string_view method_string() const;
    void        method(verb);
    void        method(string_view);

    string_view target(); const;
    void        target(string_view);

private:
    verb method_;
};

/// An HTTP response header
template<class Fields>
struct header<false, Fields> : Fields
{
    int         version;
    int         result;
    string_view reason() const;
    void        reason(string_view);
};

起始行数据成员被传统的访问器取代, 它们使用对字符串缓冲区的非所有权引用. 当方法可以从已知动词字符串集合中识别时, 方法用一个简单的整数存储, 而不是整个字符串.

现在我们给字段类型增加一项要求: 对应字符串的管理被委托给 Fields 容器, 它已经可以分配器感知, 并通过为 message 提供的构造函数重载用必要的分配器参数构造. 委托实现如下 (只显示响应头特化) :

/// An HTTP response header
template<class Fields>
struct header<false, Fields> : Fields
{
    int     version;
    int     status;

    string_view
    reason() const
    {
        return this->reason_impl(); // protected member of Fields
    }

    void
    reason(string_view s)
    {
        this->reason_impl(s);       // protected member of Fields
    }
};

既然我们已经实现了初始目标并且更多, 还有几处易用性改进要做. 用户为 Body 选择不同类型的频率远高于为 Fields 选择. 因此, 我们交换这些类型的顺序并提供默认值. 然后, 我们为请求与响应提供类型别名, 以减轻使用 bool 选择特化的影响:

/// An HTTP header
template<bool isRequest, class Body, class Fields = fields>
struct header;

/// An HTTP message
template<bool isRequest, class Body, class Fields = fields>
struct message;

/// An HTTP request
template<class Body, class Fields = fields>
using request = message<true, Body, Fields>;

/// An HTTP response
template<class Body, class Fields = fields>
using response = message<false, Body, Fields>;

这为常见情形提供了简洁的指定方式, 同时允许对边角情形的最大定制:

request<string_body> req;

response<file_body> res;

该容器还能表示完整的 HTTP/2 报文. 这并非因为它被显式设计为如此, 而是因为 IETF 希望保持与 HTTP/1 的报文兼容性. 除 Connection 等版本特定字段外, HTTP/1 与 HTTP/2 报文的内容相同, 尽管它们的序列化表示差别很大. 本库提出的报文模型已为 HTTP/2 做好准备.

总之, 这种报文容器的表示经过深思熟虑, 提供了全面的灵活性, 避免了定义额外特征类的必要. 用户编写接受头或报文为参数的函数声明时, 可以以多种方式轻松实现不同结果, 而不必到处强加繁琐的 SFINAE 声明.
