未来的 ABI 稳定性保证

2021 年 12 月底, 正如开发之初所预告的那样, 独立版 Outcome v2.2.3 锁定了其 ABI, 使得以本 Outcome 版本构建的任何代码都可以在不重新编译的情况下, 与以任何未来 Outcome 版本构建的代码链接. 这意味着从今以后, 如果你的库从公共 API 返回 outcome::result<T, E = varies, NoValuePolicy = policy::default_policy<T, E, void>> 或 outcome::outcome<T, EC = varies, EP = varies, NoValuePolicy = policy::default_policy<T, EC, EP>>, 可以保证使用任何未来版本 Outcome 的消费方代码与未重新编译的库二进制 100% 兼容.

这对工业界许多大规模生产场景而言是关键用例, 而且据我所知, 在写作本文时, 尚无其他类似 Outcome 的替代方案实现这一保证1. 另请注意, Boost.Outcome 本身不提供 ABI 保证, 因为 Boost 中 Boost.Outcome 所依赖的那些库并不具备稳定的 ABI 保证.

为确保今后持续兑现这一保证, 已加入一项每次提交都会运行的 CI 步骤, 使用以下工具对 Outcome 针对 v2.2.3 ABI 进行测试:

  • The ABI compliance checker (使用其 abi-dumper 模式, 而非其翻译单元解析模式, 后者过于脆弱).
  • Sourceware’s libabigail tooling.

这两个工具彼此独立, 虽然它们使用相同的机制进行测试 (即从未经优化的共享库对象中提取的 DWARF 调试信息), 但它们的实现各不相同.

ABI 测试实现说明

Outcome 是一个仅头文件库, 因此为了把 Outcome 变成适合作为这些工具输入的共享库, 我们编译了一个导出若干使用 Outcome 的 API 的占位共享库. 因此, 实际接受 ABI 测试的是该占位共享库对 Outcome 的覆盖范围, 而非 Outcome 本身. 这个占位库为其锁定 ABI 的内容包括:

  • basic_result<trivial type, std::error_code, all policies> (即 union 存储布局)
  • basic_outcome<trivial type, std::error_code, trivial type, all policies>
  • basic_result<non-trivial type, std::error_code, all policies> (即 struct 存储布局)
  • basic_outcome<non-trivial type, std::error_code, std::exception_ptr, all policies>
  • bad_result_access_with<std::error_code>
  • bad_outcome_access
  • atomic_eager<int>
  • atomic_eager<basic_result<trivial type, std::error_code, all policies>>
  • atomic_eager<basic_result<non-trivial type, std::error_code, all policies>>
  • atomic_lazy<int>
  • atomic_lazy<basic_result<trivial type, std::error_code, all policies>>
  • atomic_lazy<basic_result<non-trivial type, std::error_code, all policies>>
  • eager<int>
  • eager<basic_result<trivial type, std::error_code, all policies>>
  • eager<basic_result<non-trivial type, std::error_code, all policies>>
  • lazy<int>
  • lazy<basic_result<trivial type, std::error_code, all policies>>
  • lazy<basic_result<non-trivial type, std::error_code, all policies>>

显然, 这些类型在实现中触及的任何内容也会被一并锁定 ABI, 其范围以 ABI 工具能推导出的依赖类型为限. 如果你查看这个占位共享库的源代码, 会看到我们特意在模板参数中编码了依赖类型的显式列表, 以确保 ABI 工具一定能发现所有内容.

注释

Outcome.Experimental 不提供 ABI 保证, 因为 WG21 LEWG 在其接近 C++ 标准的过程中仍在积极修改其设计.

以下构建目标针对 ABI 稳定性进行了测试:

  1. GCC 7.5 与 libstdc++, 配置为 C++ 14 标准和 x64 架构.

  2. GCC 9.3 与 libstdc++, 配置为 C++ 17 标准和 x64 架构.

截至写作本文时, 尚无任何 POSIX 实现保证其 C++ 20 标准库 ABI 的稳定性, 因此我们不对此进行测试.

目前尚无针对 MSVC ABI 稳定性的 CI 覆盖. ABI compliance checker 可以测试 MSVC 二进制文件的 ABI 稳定性, 但在 Github Actions 的 Windows 测试运行器上搭建 ABI compliance checker 是相当大的工作量. 欢迎捐赠足够的测试脚本. 注意, 由于 Windows 与 POSIX 的实现几乎相同, POSIX 上的 ABI 稳定性将对 MSVC ABI 稳定性有很强的影响, 即 MSVC ABI 不太可能被破坏, 尽管没有 CI 测试就无法给出保证.

  1. libstdc++ 实现了强 ABI 稳定性保证, 因此它提供的任何未来 std::expected<T, E> 实现都将是 ABI 稳定的. 然而 Expected 仅提供 outcome::result<T, E> 所具功能的一小部分. [return]
