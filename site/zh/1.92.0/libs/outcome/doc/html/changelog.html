v2.2.15 ? (Boost 1.91) [release]

功能增强:

  • 从头开始完整重实现 Experimental Outcome 的工作已启动, 但 100% 用 C 编写. 这一重实现可从任何 ISO C (一直回溯到 1989 年) 使用, 并且与该 C++ 实现 100% ABI 兼容, 即只要你愿意, 就可以把指向某一实现中类型的指针转换为另一实现中的对应类型, 而且虚函数确实能正确调用到 100% C 实现中, 反之亦然.

  • C 重实现要求对 C++ status_code_domain 的虚函数与 thunk 函数进行重构, 使得以 __thiscall 调用它们时, 在所有主流架构与调用约定上以 __cdecl 调用也能工作. 我还让它们能够返回失败而不抛出 C++ 异常. 如果你创建了自己的 status_code_domain, 就需要更新代码 (重构非常轻微), 否则你不会察觉任何变化.

  • C 重实现简化了 atomic_refcounted_string_ref 的实现, C++ 实现已同步更新以保持一致. 最大的变化是输入字符串现在总是被复制, 不再是一个所有权被接管的 malloc 指针. 如果你在自己的代码中用过 atomic_refcounted_string_ref, 就需要把它重构为不再用 malloc 分配输入缓冲区, 而是传入原始的 char 缓冲区.

  • 完整的 C 重实现目前尚不能用于生产环境, 你应当改用当前成熟的、面向 C++ 实现的 C API. 文档目前未提及完整的 C 重实现, 待其达到生产可用时再行更新.

  • 最后, 这一 C 重实现正是提请标准化进入 C 标准库的版本, 因此请预期标准委员会惯常的改名及其他轻微调整. 由于我已不再任职于 WG21 C++ 标准委员会, 我不预期该委员会会再做进一步修改.

缺陷修复:

  • 在 Experimental.Outcome 中, make_status_code() 这个位于 status_code 中的 ADL 定制点勉强支持在不同种类的状态码之间转换, 但又勉强不支持. 现在它确实支持了. 此修复可能引发边角情形下的破坏.

v2.2.11 12th December 2024 (Boost 1.87) [release]

功能增强:

  • Outcome.Experimental 从一开始就支持 C 表示 (representation), 不过其设计初衷主要是: C++ 产生 result, 经由 C 传递, 再回到 C++. 当初并没有真正预期 C 会对 result 做太多事情, 除了检查它们走正常路径还是失败路径.

C 支持的文档已更新以反映这些新设施.

破坏性变更 #247

此前 spare_storage(const basic_result|basic_outcome *) noexcept 的值不会经由 BOOST_OUTCOME_TRY 传播, 这导致在出错的 result 构造点捕获的栈回溯等内容在每个 TRY 点被丢弃. 现已通过添加可选的 spare_storage 至 success_type<T> 与 failure_type<T>, 以及 auto success(T &&, ...) 与 auto failure(T &&, ...) 而修复.

你的代码应当察觉不到这一点, 唯一的例外是: 此前备用存储 (spare storage) 值不会经由 TRY 传播, 而现在会, 这是一个破坏性变更.

缺陷修复:

破坏性变更 #244

得知 BOOST_OUTCOME_TRY 自本库诞生以来对某些边角情形代码一直是坏的, 令人震惊:

outcome::result<Foo>    get_foo();
outcome::result<Foo>    filter1(outcome::result<Foo> &&);
outcome::result<Foo> && filter2(outcome::result<Foo> &&);

// This works fine, and always has
BOOST_OUTCOME_TRY(auto v, filter1(get_foo()))

// This causes UB due to result<Foo> being destructed before move of value into v
BOOST_OUTCOME_TRY(auto v, filter2(get_foo()))

虽然引用透传过滤函数并不常见, 但它们可能出现在高度泛型的代码中, 在那里, 先于拷贝/移动的析构并无帮助.

原因在于 TRY 的工作方式: 它过去把表达式的结果绑定到一个 auto &&unique, 测试该 unique 是否成功, 若成功则从 unique.value() 移动到用户的输出变量. 如果返回的表达式是纯右值 (prvalue), Result 的生存期会因绑定的引用而延长到语句之外, 一切正常. 如果返回的表达式是亡值 (xvalue) 或左值 (lvalue), 那么生存期延长不会超出该语句, Result 会在给 auto &&unique 赋值的那个分号之后被析构.

此缺陷已通过让 TRY 推导其输入表达式的 值类别 修复, 规则如下:

  • prvalue => auto unique = (expr) (破坏性变更)
  • xvalue => auto unique = (expr) (破坏性变更)
  • lvalue => auto unique = (expr) (破坏性变更)

这确保 xvalue 与 lvalue 输入不会导致无益的过早生存期结束, 尽管它确实静默改变了依赖右值与左值被透传的既有代码的行为, 因为在原先没有的地方引入了一个新的构造-移动-析构或构造-拷贝-析构周期. 此外, 在 C++ 17 之前, 纯右值输入现在会额外增加一次拷贝/移动——由于返回值优化 (RVO), 它不影响运行期代码生成, 但会使包含不可拷贝且不可移动类型的 Result 编译失败, 这是与此前相比的破坏性变更.

如果希望右值或左值被透传, 可以使用一种新的基于预处理器重载的 TRY 语法:

  • BOOST_OUTCOME_TRY((refspec, varname), expr)
  • BOOST_OUTCOME_TRYV2(refspec, expr)

此处 refspec 是同时用于内部临时 unique 与 varname 的存储. 因此如果你写:

Foo &&foo;
BOOST_OUTCOME_TRY((auto &&, v), filter2(foo))

……那么内部 unique 声明为 auto &&unique = (filter2(foo)), 输出变量声明为 auto &&v = std::move(unique).assume_value(). 这会透传右值引用, 并完全避免对 Foo 的拷贝与移动. 如果你不想提取值但也要指定 unique 存储, 有一个新的 BOOST_OUTCOME_TRYV2(refspec, expr).

感谢来自 https://stackoverflow.com/questions/66069152/token-detection-within-a-c-preprocessor-macro-argument 的 KamilCuk 为设计新的重载 TRY 语法提供的全部帮助. 也感谢 vasama 报告此问题并与我一起研究最佳修复方案.

#249

在 GCC 上选择何时将 bool 与 concept 配合使用的预处理器逻辑又一次被重构. 这应当能修复那些因选择了错误组合而导致失败的 GCC 配置.

v2.1.5 11th December 2020 (Boost 1.75) [release]

功能增强:

ADL 发现的事件钩子已被策略指定的事件钩子取代
原因在于其脆弱性 (一旦有人改动某些东西, 钩子就会悄然自我禁用)、编译器缺陷 (编译器设置的差异会导致发现错误的钩子, 或只发现部分而非全部钩子), 以及最终用户根本难以使用它们. 策略指定的事件钩子可以被告知默认退回 ADL 发现的钩子以保持向后兼容: 把 BOOST_OUTCOME_ENABLE_LEGACY_SUPPORT_FOR 设为小于 220 即可启用模拟.
改进配置: BOOST_OUTCOME_GCC6_CONCEPT_BOOL
较老的 GCC 使用基于布尔的 concepts 语法, 而较新的 GCC 符合标准. 然而, 何时使用旧式语法与合规语法的确切逻辑此前未被充分理解, 导致 Outcome 是否编译失败取决于你传给 GCC 的选项. 新逻辑在 GCC 8 或更早时总是使用旧式语法; 否则当且仅当 GCC 处于 C++ 20 或更高模式时使用合规语法. 希望这能解决 GCC 上的边角构建失败.

缺陷修复:

Boost.Outcome 现在应当能在定义 BOOST_NO_EXCEPTIONS 的情况下编译
多亏 Boost.Exception 的维护者 Emil 为我做出一项修改, Boost.Outcome 现在应当能在全局禁用 C++ 异常的情况下编译. 你将无法使用 boost::exception_ptr, 因为在全局禁用 C++ 异常时它无法被包含.
#236
在协程支持中, final_suspend() 不是 noexcept, 尽管 C++ 20 标准要求如此. 此问题已修复, 但前提是你的编译器实现了 noop_coroutine. 此外, 如果 noop_coroutine 可用, 我们会使用 await_suspend() 的返回协程句柄的变体, 其效率高得多, 应能显著改善代码生成与上下文切换性能.

功能增强:

破坏性变更 void 的 result 与 outcome 在显式构造时不再默认构造类型
此前, 如果你用 result<T> 从未出错的 result<void> 显式构造, 它会默认构造 T. 这被发现会造成无益的意外, 因此已被禁用.
新宏 BOOST_OUTCOME_ENABLE_LEGACY_SUPPORT_FOR
宏 BOOST_OUTCOME_ENABLE_LEGACY_SUPPORT_FOR 可用于在使用较新版本 Outcome 时, 把旧命名与旧特性别名到新命名与新特性.
concepts 现在采用 snake case 风格命名, 而非 camel case 风格
Outcome 最初实现时, 人们以为 C++ 20 concepts 会采用 camel case 风格. 这在 C++ 20 发布前被改变, Outcome 的 concepts 也相应改名. 这不会破坏 Outcome v2.1 中的任何代码, 因为提供了兼容别名. 然而针对 Outcome v2.2 编译的代码需要升级, 除非把 BOOST_OUTCOME_ENABLE_LEGACY_SUPPORT_FOR 设为小于 220.
concepts 现在位于 BOOST_OUTCOME_V2_NAMESPACE::concepts 命名空间
此前 concepts 位于 convert 命名空间, 现在它们位于自己的命名空间.
新增 concepts basic_result<T> 与 basic_outcome<T>
最终用户发现 is_basic_result<T> 与 value_or_error<T> 之间存在一个无益的空档: 他们想要一个能匹配 basic_result 类型、但又不完全是其中某一者的 concept. 填补该空档的 concepts 已加入.
自 Outcome v2.2 起, 操作 TRY 的工作方式有所不同
这是一项严重破坏代码的变更, 它改变了使用 BOOST_OUTCOME_TRY() 的语法. 在 Outcome v2.1 与 v2.2 之间的变更列表中, 可以找到适用于升级代码的正则表达式.

缺陷修复:

#224
Apple 在 Xcode 11.4 (当前最新) 中附带的 clang 尚未打上 LLVM clang 的修复补丁——那是修复 noexcept(std::is_constructible<T, void>) 编译失败的补丁, 我多年前就已提交. 所以别再等 Apple 修复他们的 clang 了, 在 Outcome 中加入绕过措施.
把 void 用在 T 或 E 中会导致 noexcept(false)
对 void 的直接 traits 检查曾导致 nothrow 检测返回 false, 已修复.
无法在无值策略类内部使用备用存储 (spare storage)
由于当时编写代码时的明显一时糊涂, 备用存储 API 的原型有误, 导致它们无法在策略类内部工作. 抱歉.

v2.1.3 29th April 2020 (Boost 1.73) [release]

功能增强:

clang 编译的基于 Outcome 的代码性能大幅提升

Outcome 状态位域 (status bitfield) 的旧实现会干扰 clang 的优化器, 导致低质量代码生成. 与多数代码生成问题不同, 这一点在实际代码的经验基准测试中相当明显, P1886 Error speed benchmarking 便展示了这一点.

better_optimisation Outcome v2.2.0 未来分支中安全的部分已合并进 Outcome v2.1.3, 其中包含新的状态位域实现. 它似乎不再干扰 clang 的优化器, 在各种固定用例下, clang 9 生成的代码通常胜过 GCC 9 的代码.

对独立版 Outcome, 在足够新的 cmake 上自动启用预编译头

在 cmake 3.16 或更高版本上, 会使用其新的预编译头构建支持, 告知 outcome::hl cmake 目标的消费方预编译 Outcome, 当且仅当 outcome_IS_DEPENDENCY 为 false. outcome_IS_DEPENDENCY 由 Outcome 的 CMakeLists.txt 设置——前提是它检测到自己是通过 add_subdirectory() 被包含的, 因此对绝大多数 Outcome 最终用户而言, 预编译头的使用不会被启用.

导出的目标不会要求预编译头文件, 因为假定 Outcome cmake 目标的导入者会自行配置包含 Outcome 的预编译头.

可安装性现在每次提交都经 CI 测试

由于独立版 Outcome 的可安装性 (例如 make install) 自我破坏的频率高于理想水平, 可安装性现在每次提交都在 CI 上测试.

协程支持已有文档

v2.1.2 加入的协程支持现已得到恰当的文档说明.

缺陷修复:

#214
较新的支持 Concepts 的编译器对过早检查 T 与 E 的可析构性不满意, 因此移除了模板约束, 改用类型实例化序列中较晚执行的 static assert.
#215
对独立版 Outcome, CMAKE_TOOLCHAIN_FILE 现在会在依赖超构建 (superbuild) 期间被透传. 这应当能解决一些嵌入式工具链用户的构建问题.
#220
对 Experimental Outcome 某些使用场景下未定义行为 sanitizer 的误报, 已用绕过措施避免其失败消息.
#221
恢复了与 Windows x86 的兼容性, 此前它会因链接错误而失败. 这个缺陷没有更早被报告相当令人惊讶, 显然几乎没有人会在 Windows 上以 x86 使用 Outcome.
#223
修复仅限 Experimental.Outcome 中克隆 status_code_ptr 时、且仅出现在 Debug 构建中的段错误.

v2.1.2 11th December 2019 (Boost 1.72) [release]

功能增强:

改善与 cmake 工具链的兼容性
独立版 Outcome 现在可以 make install, 且 cmake 的 find_package() 能够找到它. 注意你必须单独安装并 find_package() Outcome 的依赖 quickcpplib, 否则 Outcome 的 find_package() 将失败.
Visual Studio 现在默认使用非宽容解析 (non-permissive parsing)
独立版 Outcome 的 cmake 默认目标现在启用非宽容解析. 这部分是因为 VS2019 16.3 相当多缺陷的 Concepts 实现在宽容解析模式下不可用. 即便如此, 在 VS2019 16.3 中使用 /std:latest 时, 延迟 ADL 两阶段查找仍是坏的, 你可能希望使用较早的语言标准.
破坏性变更!
独立版 Outcome 用于指定依赖库的 git 子模块机制已被 cmake 依赖超构建机制取代. 在 cmake configure 时, 会 git clone 一份内部的 quickcpplib 副本, 构建并安装到构建目录, 内部的 find_package() 从那里使用它. 这破坏了把未配置的 Outcome 仓库直接用作 Outcome 实现的做法, 现在必须选择以下之一:
  1. 把 Outcome 作为子目录加入 cmake 构建.
  2. 使用 cmake 超构建 (即 ExternalProject_Add()) 把 Outcome 构建并安装到本地安装目录.
  3. 使用单一头文件版本之一.
破坏性变更!
对独立版 Outcome, 现在会检查当前编译器是否能编译包含 C++ Concepts 的代码, 如果能, Outcome 的所有 cmake 消费方都会启用 C++ Concepts. 把 cmake 变量 BOOST_OUTCOME_C_CONCEPTS_FLAGS 设为空字符串可阻止自动检测与启用 C++ Concepts 支持.
BOOST_OUTCOME_TRY 操作现在会向编译器暗示该操作将会成功
P1886 Error speed benchmarking 表明, 通过向编译器暗示表达式是否预期成功, 在非常小的函数中可获得可观收益. BOOST_OUTCOME_TRY 此前完全不向编译器暗示, 现在则会了. 新的宏组 BOOST_OUTCOME_TRY_FAILURE_LIKELY 会向编译器暗示预期失败. 如果你希望回到此前无暗示的行为, 把 BOOST_OUTCOME_TRY_LIKELY(expr) 定义为 (!!expr).
#199
已加入对 C++ 协程的支持. 这分为两部分: 第一, 现在有一个 BOOST_OUTCOME_CO_TRY() 操作, 适合在 C++ 协程内执行 TRY 操作. 第二, 头文件 outcome/coroutine_support.hpp 中提供了 eager<OutcomeType> 与 lazy<OutcomeType> 的实现, 让你能在 C++ 协程内更自然、更高效地使用 basic_result 或 basic_outcome——具体而言, 如果 result 或 outcome 能够从 exception pointer 构造, 协程中抛出的异常会返回携带被抛异常的出错或例外 result, 而不是让异常穿过协程机制抛出 (在当前编译器上, 后者极有可能炸掉程序). eager<T> 与 lazy<T> 也都能接受任意 T. 两者都已在 VS2019 与 clang 9 上测试并确认可用.
#210
make_error_code() 与 make_exception_ptr() 现在也被纳入 basic_result<> 的兼容拷贝与移动转换考量. 这让你可以把 basic_result<T, E> 构造到 basic_result<T, error_code> 中, 其中 E 是一个自定义类型, 它实现了经 ADL 发现的自由函数 error_code make_error_code(E), 但此外与 error_code 无关. 同样的可用性也适用于 exception_ptr, 其中 make_exception_ptr() 是经 ADL 发现的自由函数. basic_outcome<> 对此的支持少于 basic_result<>, 以控制构造函数数量, 但它会经由该机制接受来自 basic_result<> 与 failure_type<> 的转换.

缺陷修复:

#184
编译器中 [[nodiscard]] 支持的检测有非常轻微的破损.
