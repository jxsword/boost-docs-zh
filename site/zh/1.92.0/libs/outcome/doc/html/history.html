Outcome 的历史颇为有趣, 值得在此总结, 以展示一个 Boost 库如何诞生. 以下回忆出自 Niall Douglas, 可能因其记忆衰退而有误.

Outcome v1 的起源 (2014 - 2017)

该 git 仓库诞生于 2014 年 6 月, 名为 “Boost.Spinlock”, 是从 Boost.AFIO v1 中分出来的——它此前在那里作为内部库存在了一段时间. 2014 年 10 月, 我把最初的 Boost.Expected 原型参考库作为 git 子模块加入, 并开始开发非分配的 future<T>/promise<T>, 作为 expected<T, std::exception_ptr> 的扩展——一个更快、单子式的 future-promise 正是 AFIO v1 急切需要的东西.

最初的 Boost.Expected 原型库是一个庞大而非常复杂的家伙. 我很幸运在 2014 年末 2015 年初的一份合同工作中, 亲眼见到它被大规模部署进一个既有的大型 C++ 代码库. Expected 确实强大而优秀, 但它对大型 C++ 代码库的编译时间是毁灭性的, 并使 LTO 实际上不可行. 我还发现它的实现不利于以其实现 future-promise, 于是我决心实现一个强大得多的、策略驱动的单子工厂, 能从 option<T> 一路生成到 future-promise 对, 全部使用完全相同的 basic_monad<>, 因此全都具备完整的单子编程 API、C++ 17 continuation/单子 bind, 并且能智能地互相转换. 此外, 这一切都必须对编译时间与运行时开销有绝对最小的影响——而这两者都不是最初原型 Boost.Expected 库的强项.

到 2015 年 8 月, “Boost.Monad” 已兑现上述全部要求甚至更多, 但因缺乏在其他代码中的使用而不够成熟. 2015 年夏天, AFIO v1 的 Boost 同行评审遭到全面否决. 在审视了大量评审反馈之后, 人们意识到 AFIO v2 将是一个截然不同的设计: 不再使用 future、内存分配, 也不使用 C++ 异常. 由于 AFIO v2 从零开始, 并从一开始就重度使用 Outcome (每个 AFIO v2 API 都返回 result<T>), Outcome 开始获得缺陷修复并删减特性: 非分配的 future-promise 实现于 2016 年 5 月被弃用, 一大块基于类型的元程序设计于 6 月被更干净的变量模板元编程取代. 2016 年 9 月 CppCon 之后, 让 Outcome 为 2017 年第一季度 Boost 同行评审做好准备的长过程开始, 其中包括为回应 C++ 社区多轮反馈而反复整套重写教程——截至写作本文时至少已完整重写四次.

在 Outcome 这些开发的同时, Expected 提交给了 LEWG, 进入 C++ 标准轨道. 随着 WG21 会议推进, Expected 经历了一段被精简的时期, 2014-2015 年间严重拖垮编译与链接时间的许多复杂性被剥离, 于是 P0323R1 中提议的 Expected 最终落得与 Outcome 非常接近, 以至于在 2017 年 1 月, 用 Outcome 的核心 basic_monad 基础设施实现 Expected 只需几个小时的工作. 那个让单子式 future-promise 成为可能的高度灵活的基于策略的设计, 同样使实现一个高度符合标准的 Expected 变得容易; 确实, 在 2017 年初, Outcome 的 Expected 比任何其他实现 (包括 LEWG 参考实现) 都更接近 P0323R1. 而且与 LEWG 参考实现不同, Outcome 已积累了十八个月的那种只有被其他代码库使用才能获得的精细调校光泽.

2017 年 2 月, 人们意识到用户群体真正想要的是一个高质量的 expected<T, E> 实现, 而不是 Outcome 自创的任何似是而非的东西. 因此, 刚刚实现的、基于 basic_monad 的 Expected 实现占据了主导地位. 提交同行评审前的最后一次文档重写, 使 Outcome 看起来主要是一个 expected<T, E> 实现, 带有 outcome<T> 与 result<T> 等少数有用扩展. 对这样的转向我感到遗憾, 但显而易见, 作为主要是一个 Expected 实现, Outcome 将获得远更广泛的流行与使用.

在开始近三年后, Outcome v1 终于在 2017 年 5 月提交 Boost 同行评审, 这演变成 Boost 近年所做的时间最长、最详尽的同行评审之一, 提交了超过 800 条评审反馈. 它经共识被否决, 但附有关于应当如何改进的大量反馈.

Outcome v2 (2018)

在非常漫长的同行评审期间, 关于 value|error 传输类应当是什么样子, 大致出现了三类意见:

1. 轻量
一个尽可能简单的 T 和/或 E 传输, 没有任何实现复杂性.
2. 中等
一个 variant, 存储 T 或 E1 …… En, 其中 T 是期望值, E1 ... 是潜在的意外值. 这种实现真正应当用 C++ 17 的 std::variant<...> 来实现, 只是带上更强的 never-empty 保证.
3. 重量级
一个完全参与 C++ 更广泛单子编程框架的全功能 Either 单子.

Peter Dimov 很快实现了一个 expected<T, E1, ...>, 用的是他的 variant2 库, 因此在 Outcome v2 中复刻他的工作似乎意义不大. 轻量选择似乎是最好的前进道路, 于是 2017 年 6 月, 本库所呈现的最低限度的 result<T, E> 与 outcome<T, EC, P> 被构建出来, 使用与 std::variant<...> 相同的构造函数设计. 与 v1 Outcome 代码的大量向后兼容得以保留, 因为评审认为该基本提案设计不错.

随后是一段成熟期: 把一个使用 Outcome v1 的大型既有代码库移植到 v2, 并用 v2 编写大量新代码, 以测试是否存在意料之外的意外与缺陷. 发现了相当多的边角情形并已修复. 2017 年 9 月底, Outcome v2 被认定为 “成熟”, 并提供了由脚本生成的 “Boost 版”.

在它为第二次 Boost 同行评审做好准备之前, 只剩文档了. 撰写文档花了四个月 (与编写库本身所用时间相同!), 2018 年 1 月, Outcome 迎来第二次 Boost 同行评审, 并通过了!

Outcome v2.1 (2019 - 2020)

v2.0 评审期间所要求的修改相当克制: result 与 outcome 将改名为 basic_result 与 basic_outcome, 并在 basic_* 层与 “便利” 层之间建立清晰的关注点分离. 这非常适合 Outcome, 因为 basic_* 层可以拥有尽可能少的头文件依赖, 从而尽可能小的构建时间影响, 这对拥有数百万行 C++ 代码库的大型企业用户非常有利. 这还带来一个不错的副作用: Outcome 与 Boost.Outcome 都能同时支持 Boost 与 std 两种实现.

到 2018 年 4 月, v2.1 功能完备, 并在其已经庞大的用户群下进入为期六个月的成熟与实战淬炼期. 然而 Outcome 在 2018 年 1 月通过评审所带来的后果远超我的预料. 我并不知情的是, 一些 WG21 领导层把 Outcome 的成功——尤其是它相对 WG21 Expected 的分歧, 即成为一个更完整的 C++ 异常处理替代品——解读为 C++ 异常处理机制已不再适用目的的信号. 于是有人提议把标准异常处理机制改造为高效得多的东西, 从而使 Outcome 在未来的 C++ 标准中变得过时 (P0709 Zero overhead exceptions).

与此同时, 就在 Outcome 2.0 评审之前, 我对 <system_error> 提出了若干语义与编译期性能改进, 建议我们以改进温和地破坏 Boost.System, 看看现实世界的代码会因此坏到什么程度. 这在当时未被广泛接受 (尽管这些改进后来被纳入 Boost.System, 并且作为 C++ 23 的 <system_error> 缺陷补救提案). 于是我编写了 改进版 <system_error2>, 修复了 P0824 (SG14 关于 <system_error> 讨论摘要) 中列出的全部问题, 并修好了 Outcome, 使人们可以在没有任何 system error 实现的情况下使用它, 或者用 STL 的实现, 或用提案的改进实现. 这个改进的 <system_error2> 随后被提议为 对零开销异常的标准库支持, 即提案中的 std::error.

随后产生了一连串论文与讨论, 直至 2020 年布拉格 WG21 会议——会上 WG21 喜欢了确定性异常的库部分, 即 std::error, 并希望在进一步推进之前看到一个实现语言部分的编译器的工作实现. 新冠疫情随后使面对面会议停止, 严重影响了 WG21 的生产力, 因此所有尚未获批进入 C++ 23 的大型事项都被暂停.

Outcome v2.2 (2021)

Outcome 足够流行, 并被广泛认为是 C++ 中当前可得的最接近确定性异常的摹本, 以至于更广泛的 C++ 生态中的许多人经常按 “仿佛如此” 的基准对它进行测试, 包括把他们的 ‘更好的 Outcome 替代品’ 与 Outcome 比较, 其中 Outcome 无一例外地在各种人工测试中显得惨败. 虽然现实世界代码中的任何实测从未显示出统计显著的差异, 但 v2.1 在汇编层面的代码生成确实不理想.

受 WG21 委托, Ben Craig 在 P1886 Error speed benchmarking 中对 Outcome v2.1 做了一些基准测试工作, 发现它相比从函数返回简单整数等替代方案的表现不如预期. 这催生了一个 better_optimisation 分支. 这些变更被认为值得作为 v2.2.0 合并进 Outcome——这是 Outcome 于 2019 年初进入 Boost 以来第一个主版本发布. 为了给用户留出足够时间预告这些源码不兼容的变更即将到来, 整个 2020 年都被用于预告破坏性的 v2.2 分支将于 2021 年初合并进 master 分支.

就提案 std::error 代码 (即使用 Outcome experimental 的代码) 的代码生成收益而言, v2.2 实现了对 P1029 move = bitcopies 的基于库的模拟——这是一项提案中的编译器增强, 可以把某些仅可移动类型当作位袋处理. 这极大改善了 experimental Outcome 代码在汇编中的观感.

Outcome v2.2.3 (2022)

Outcome v2.2 颇受欢迎, 在发布一年后报告的问题极少, 因此决定把 v2.2.3 的 Outcome ABI 永久写死. 这就是保证: 用 v2.2.3 发布版编译的二进制, 能与用任何更新版本 Outcome 编译的二进制无碍链接与工作.

这基本上为 Outcome 的进一步重大开发画上了句号——它现在实际上已进入大型跨国公司所谓的 ‘维持 (sustaining)’ 阶段, 即从今往后只预期进行小幅缺陷修复以及面向未来工具链与语言等的维护.
