异常

异常是 C++ 中报告、传播与处理函数失败信息的默认机制. 其主要优点是能够描述函数之间的 “成功依赖”: 如果你想表明调用函数 g() 依赖于函数 f() 的成功执行, 只需把 g() 放在 f() 之下, 如此而已:

int a()
{
  f();
  g();        // don't call g() and further if f() fails
  return h(); // don't call h() if g() fails
}

按 C++ 标准的术语, 这意味着 f() 先序于 g(). 这使失败处理极其容易: 在许多情况下你什么都不必做.

此外, 在后续操作被取消的同时, 包含初始失败信息的异常对象被保存在一旁. 当取消级联在某个点被异常处理器止住时, 可以检查该异常对象. 它可以包含任意大量的关于失败原因的数据, 包括整个调用栈.

缺点

异常处理机制带来两类开销. 第一类与在旁保存异常有关. 栈回退在每个执行线程中独立工作; 每个线程都可能在处理多个异常 (尽管一个线程中同一时刻只能有一个异常处于活动状态). 这要求为每个线程存储任意数量的任意类型异常做好准备. 跳转表之类的额外内容也需要存入程序二进制.

第二类开销出现在抛出异常并寻找处理器时. 由于几乎任何函数都可能在任何时刻抛出异常, 这是一次动态内存分配. 异常的类型被擦除, 需要运行期类型识别 (RTTI) 来判定活动异常对象的类型. 把异常与处理器匹配所需的最坏情形时间难以预测, 因此异常不适合实时或低延迟系统.

与异常相关的另一个问题是: 虽然它们适合具有线性 “成功依赖” 的程序流, 但在这种成功依赖不出现的场合会变得不便. 一个显著的例子是释放已获取的资源——即使先前操作失败也需要执行. 另一个例子是某个函数 c() 依赖于两个函数 a() 与 b() 中至少一个的成功 (例如它们尝试用两种不同手段存储用户数据); 再一个例子是实现强异常安全保证时, 我们可能需要在先前操作失败后采取一些回退动作. 当失败由异常报告时, 取消所有后续操作的语义是妨碍而非帮助; 这些情形需要采用特殊且不简单的惯用法.

由于这些原因, 一些项目禁止使用异常. 编译器提供完全禁用异常的开关 (它们拒绝编译 throw, 并把已编译的 throw 变成对 std::abort() 的调用).
