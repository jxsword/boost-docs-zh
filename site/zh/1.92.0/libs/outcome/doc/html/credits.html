Outcome v2.1 特别致谢

Andrzej Krzemienski 再次脱颖而出: 源源不断的出色问题、各种 '如果……会怎样?'、对边角情形逻辑缺陷的敏锐发现, 以及对设计矛盾的指出. 谢谢你, Andrzej!

感谢 Microsoft Visual C++ 编译器团队把 Outcome 纳入 MSVC 测试套件, 从而发现了许多关于如何最佳解释 C++ 标准的有趣边角怪癖. 某些情况下, Outcome 被重构以减少歧义; 另一些情况下, 由于标准措辞不清晰, 不得不向 WG21 提交缺陷报告. Visual C++ 编译器团队在帮助追查这些问题成因方面格外慷慨地投入时间, 还提交了带缺陷修复的 pull request. 我对他们非常感激.

Outcome v2.0 特别致谢

Charley Bay 第二次挺身而出担任评审管理人. 鉴于 v1 评审工作量之大, 我只能说谢谢.

在 Outcome v2 的开发中, Andrzej Krzemienski 远超其职责本分. 他撰写了首页与教程的开头, 由此奠定了教程的基调、节奏、风格与形式, 而我只是沿续完成了教程的其余部分. 他还自愿投入大量时间, 担任 v2 设计与实现的主要同行评审者, 提出了许多极有价值的 '愚蠢问题', 其中至少一个问题引发了一次重大的重新思考与重构. 如果 Outcome v2 能通过第二次同行评审, 那要归功于 Andrzej. 谢谢你.

Jonathan Müller 在他的 doxygen 替代工具 Standardese (Outcome 用它生成参考 API 文档) 中投入了无数小时, 其中相当不少时间用于为 Outcome 修复问题. 谢谢你.

Outcome v1 特别致谢

感谢 Paul Bristow, 他在 boost-dev 上旷日持久的命名争论之后为本库提议了 'Outcome' 这一名称. 当时命名之争已近乎荒谬, 我一度想让这个库干脆叫 'Boost.Donkey' 好让所有人闭嘴. 但 Outcome 好听得多, 所以谢谢你, Paul.

衷心感谢 Charley Bay 在 2017 年 5 月担任 Outcome 的评审管理人. 如今找到一位 Boost 评审管理人越来越难, 所以谢谢你! 也感谢 CppCast 团队的 Rob Irving 与 Jason Turner 在 Outcome 同行评审期间如此迅速地邀我上 CppCast 讨论 expected<T, E>, 以帮助宣传这次评审.

更广泛的感谢属于 boost-dev、Reddit 与 SG14 上的各位, 从本库诞生之初他们就提供了大量且常常非常细致的反馈. 你们人数众多难以一一记起, 但 Tongari 与 Andrzej Krzemienski 无疑浮现在脑海——他们参与了特别长的讨论串, 提供了大量澄清我思路的有用反馈. Andrzej 还在评审前逐字梳看了文档, 找出许多小勘误与令人困惑的措辞.

最后, 感谢 Vicente 把 Expected 从萌芽一路推进, 有望在 2020 年前实现标准化. 让某样东西标准化需要多年的工作, 比把一个库送进 Boost 花的时间还要多——正如上文历史所示, 后者大约花了三年.
