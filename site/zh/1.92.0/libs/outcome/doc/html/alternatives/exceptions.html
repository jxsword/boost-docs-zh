std 异常抛出

(注意, 我们此处假定基于表的 EH 实现; SJLJ EH 实现连正常路径与失败路径都会有运行时开销. 基于表的 EH 实现在 x64、ARM 与 AArch64 目标上几乎通行).

C++ 异常抛出自最初的 C++ 98 标准引入. 当时并非所有主流编译器都已实现异常, 已实现者中也有几个缺乏高效实现, 而且在早期, 一些编译器厂商还会为 EH 实现技术之类的成果申请专利, 试图以此保持对竞争对手的优势. 与其他 C++ 特性不同, 在一个编写时未考虑异常的代码库上启用 C++ 异常并不安全, 这导致 C++ 生态分裂为启用异常与禁用异常两大阵营.

优点:

  • 正常路径上零运行时开销.

  • 面向成功的语法让代码摆脱失败控制流路径的干扰.

  • 作为内建的语言特性, 在本文讨论的所有失败处理机制中, 它对优化的影响可能是最小的.

  • 随每个标准工具链一同提供 (不过在部分工具链中可能无法工作, 而且对许多代码库而言无法安全启用).

缺点:

  • 失败路径上的运行时开销不可预测.

  • 对实时应用而言, 失败路径上的运行时开销不可接受.

  • 给生成的二进制文件增加可观的体积膨胀, 对某些使用场景 (嵌入式) 来说可能无法接受.

  • 要求启用 RTTI, 否则会产生非标准行为 (这进一步增加二进制体积).

  • 由于传统或惯例, 在 C++ 生态的几个主要领域不可用 (嵌入式、游戏、音频, 金融领域程度较轻).

  • 在 HPC、GPU、DSP 与微控制器等许多小众架构上不可用.

  • 对 C++ 异常抛出代码所导致的失败控制流路径的静默增殖, 大多数代码库都没有投入足够的正确性测试 (异常抛出会静默生成大量略有差异的失败路径控制流).
