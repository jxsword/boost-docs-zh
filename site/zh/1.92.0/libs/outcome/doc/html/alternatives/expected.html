std expected

std::expected<T, E> 最初来自一个 Boost 之外的实验性单子 (monadic) 与泛型编程库, 由 Boost 与 WG21 的开发者于 2013 年前后编写. 在 Outcome v1 之前, 我曾把当时的 Expected 部署到一个大型代码库中, 结果令我沮丧, 尤其是构建时间. 你可以在此阅读这些经历如何促使我开发 Outcome v1.

std::expected<T, E> 是一个受约束的 variant 类型, 强烈偏好成功类型 T, 并像 std::optional<T> 那样对其建模. 但如果不存在 T 值, 它就改为提供一个 'unexpected' 的 E 值. std::expected<T, E> 已在 C++ 23 标准中被标准化.

Outcome 的 Result 类型可以按你的意愿配置得与 Expected 行为一致, 但归根结底Outcome 的 Result 与 Expected 解决的并不是同一个问题, 而且 Outcome 建模的是 std::variant<T, E> 而非 std::optional<T>, 我们认为前者在许多使用场景中要优秀得多, 概括而言:

  • 如果你解析的输入很少包含意外值, 那么 Expected 在这里是正确的选择.

  • 如果你想要 C++ 异常处理的替代品, 即一个泛化的全程序错误处理框架, 那么 Expected 与其他替代方案相比是较差的选择.

Outcome 能够识别类似 Expected 的类型并从它们构造, 这有助于互操作性.

优点:

  • 正常路径上的运行时开销可预期.

  • 失败路径上的运行时开销可预期.

  • 给二进制增加的代码膨胀极少 (不过支持库存在固定的绝对开销).

  • variant 存储意味着存储开销极小, 除非 T 或 E 中某一方具有抛异常的移动构造函数, 这通常导致存储爆炸.

  • 在 C++ 的所有配置下都工作良好, 包括全局禁用 C++ 异常与 RTTI 的配置.

  • 在所有小众架构上工作良好, 例如 HPC、GPU、DSP 与微控制器.

  • 自 C++ 23 起随每个标准库一同提供.

缺点:

  • 面向成功的语法使得用 E 类型做任何事情都笨拙而累赘.

  • 会产生分支繁多的代码, 这对嵌入式控制器 CPU 而言较慢 (尽管这种慢是可预期的).

  • 未检查一个 Expected 会产生编译器诊断, 但未同时处理失败与成功则不会. 这可能意味着失败或成功被意外丢弃.

  • 缺少 try 运算符使得使用起来冗长而啰嗦.

  • variant 存储确实对构建时间有不小的影响, 其方式与广泛使用 std::variant 时相同. 这是因为要在 union 存储中对不可平凡复制的类型执行拷贝与移动时实现异常保证, 每次使用拷贝和移动都会给编译器带来大量工作.
