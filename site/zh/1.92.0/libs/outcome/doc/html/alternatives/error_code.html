std 错误码

std::error_code 最初来自 boost::error_code, 后者在 2008 年前后作为实现 Filesystem 与 Networking 的一部分而设计. 它们是一种简单、可平凡复制的类型, 相比 C 枚举提供了更好的类型安全性与更多功能. 你可以在此阅读更多关于 std::error_code 工作原理的内容. 它们在 C++ 11 标准中被标准化, 并且自 2008 年起就在 Boost 中可用.

优点:

  • 正常路径上的运行时开销可预期.

  • 失败路径上的运行时开销可预期.

  • 对成功与失败采用无偏向的相同语法, 要求显式编写代码来同时处理两者.

  • 给二进制增加的代码膨胀极少 (不过支持库存在固定的绝对开销).

  • 一旦构造完成, 传递 std::error_code 实例的优化效果很好, 常常经由 CPU 寄存器传递.

  • 在 C++ 的所有配置下都工作良好, 包括全局禁用 C++ 异常与 RTTI 的配置.

  • 在所有小众架构上工作良好, 例如 HPC、GPU、DSP 与微控制器.

  • 自 C++ 11 起随每个标准库一同提供.

缺点:

  • 若未为失败编写处理代码, 失败就会被静默丢弃. 这种疏忽极易发生, 令人不安.

  • 会产生分支繁多的代码, 这对嵌入式控制器 CPU 而言较慢 (尽管这种慢是可预期的).

  • 由于构造时使用的 std::error_category 实例来自一个 magic static, 编译器会在每次 std::error_code 构造周围插入一个原子操作 (例如 https://godbolt.org/z/oGaf4qe8a). 在原子操作优化较差的编译器上, 这可能影响优化效果.

  • int 类型的负载 (payload) 有时约束性极强, 尤其是在 64 位平台上. 如果它是 intptr_t 而不是 int, 情况会好得多.

  • 全零位的负载值具有隐式的硬编码语义, 这与许多从零值开始的 C 枚举不兼容. 这可能以极难调试的方式导致失败被静默丢弃.

  • 不同错误类别之间应当如何比较 (即映射) 并不明晰, 连标准库维护者和许多 WG21 成员过去都曾被它搞糊涂.

(注意, 正是这一长串设计上的注意事项导致了取代 std::error_code、改用 std::error 的提案, 该替代方案如今已可在 Outcome.Experimental 中使用. 更多信息参见 本页了解更多).
