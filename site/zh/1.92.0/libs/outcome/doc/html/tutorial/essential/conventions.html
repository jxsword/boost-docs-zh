约定

你现在已了解立即开始使用 Outcome 所需的一切.

大多数初学者的最初冲动, 是针对具体情况使用定制的强类型枚举, 即一次性的自定义 E 类型. 这通常源于在其他语言中和类型上的经验, 例如 Rust、Haskell、Swift 等.

但这是 C++! 不是 Rust, 不是 Swift, 不是 Haskell! 我必须提醒你: 在公共 API 中始终避免使用自定义 E 类型. 原因是: 每当使用自定义 E1 类型的库 A 必须与使用自定义 E2 类型的库 B 交互时, 你都必须在那些 E1 与 E2 类型之间做映射.

这会丢失信息, 即失败的保真度在多次翻译之后丢失. 它涉及编写、然后维护大量恼人的样板代码. 它泄漏内部实现细节, 未能分离关注点. 而且无法使用 BOOST_OUTCOME_TRYV(expr)/BOOST_OUTCOME_TRY(expr)——如果 E 类型之间没有可转换性.

C++ 11 标准库与 Boost 专门提供了 <system_error>, 用于把单个自定义 E 类型包装进一个通用框架, 使互不相干的自定义 E 类型能彼此发现并交互. 它随每个 C++ 编译器一同提供.

出于所有这些原因, 这正是 result 与 outcome 把 EC 类型默认为错误码的原因. 应尽可能保持该默认值不动.

tl;dr;

请把你的库接入 std::error_code 或等价物, 并且不要在任何公共 API 中暴露自定义 E 类型. result 与 outcome 出于充分理由把 EC 默认为错误码.
