挂钩事件

Outcome 提供多种方法让用户代码拦截发生的各类生命周期事件. 最深的方法是直接继承 basic_result 或 basic_outcome 并重写成员函数——你需要研究源码才能这么做, 因为这种定制形式超出了本教程的范围.

另一个选项是提供自定义 NoValuePolicy (见上一节). 从 Outcome v2.2 起, 拦截构造、拷贝与移动需要自定义 NoValuePolicy.

在 Outcome v2.2 之前, 有一个经 ADL 发现的事件钩子机制用于拦截构造、拷贝与移动 (实践中发现它脆弱、易错且令人意外, 因此被替换). 如果把 BOOST_OUTCOME_ENABLE_LEGACY_SUPPORT_FOR 设为小于 220 以启用模拟, 经 ADL 发现的事件钩子在 Outcome v2.2 及以后仍然可用.

你会注意到命名只是 hook_* => on_* 之一, 参数保持完全相同. 这便于把代码从 Outcome v2.1 移植到 v2.2, 通常只需把 ADL 钩子代码复制粘贴进自定义 NoValuePolicy.

策略集事件钩子 (Outcome v2.2 起):

  • 构造了
    • void on_result_construction(T *, U &&) noexcept
    • void on_outcome_construction(T *, U &&) noexcept
  • 原位构造了
    • void on_result_in_place_construction(T *, in_place_type_t<U>, Args &&...) noexcept
    • void on_outcome_in_place_construction(T *, in_place_type_t<U>, Args &&...) noexcept
  • 拷贝了
    • void on_result_copy_construction(T *, U &&) noexcept
    • void on_outcome_copy_construction(T *, U &&) noexcept
  • 移动了
    • void on_result_move_construction(T *, U &&) noexcept
    • void on_outcome_move_construction(T *, U &&) noexcept

ADL 发现的事件钩子 (Outcome v2.2 之前):

  • 构造了
    • void hook_result_construction(T *, U &&) noexcept
    • void hook_outcome_construction(T *, U &&) noexcept
  • 原位构造了
    • void hook_result_in_place_construction(T *, in_place_type_t<U>, Args &&...) noexcept
    • void hook_outcome_in_place_construction(T *, in_place_type_t<U>, Args &&...) noexcept
  • 拷贝了
    • void hook_result_copy_construction(T *, U &&) noexcept
    • void hook_outcome_copy_construction(T *, U &&) noexcept
  • 移动了
    • void hook_result_move_construction(T *, U &&) noexcept
    • void hook_outcome_move_construction(T *, U &&) noexcept

对基于库的异常抛出替代方案的一个常见批评是: 它们提供的一套设施不如 C++ 异常抛出丰富. 本节展示如何利用事件钩子配置 Outcome, 在构造出错的 result<T, error_code> 时捕获栈回溯, 并且如果该 result<T, error_code> 后来被转换为 outcome<T, error_code, std::exception_ptr>, 一个自定义 std::exception_ptr 会被即时合成, 其组成为错误码的 std::system_error, 加上一条包含错误原始发生处栈回溯的扩展消息字符串.

可以看到这种配置的用例: 低层、确定性、固定延迟的代码以 result 构建, 它与以 outcome 构建的高层应用代码衔接——后者不关心执行时间保证, 因此 malloc 是可以接受的. 这实际上构建了一种 “惰性不确定性” 或 “即时不确定性” 机制来处理失败, 同时拥有抛 C++ 异常的全部丰富信息.
