自定义负载

在本教程至此的部分中, EC——位于 result<T, EC> 中——的类型一直是 std::error_code 或 boost::system::error_code. 把 NoValuePolicy 设为 default_policy<T, EC, EP> 时, EC 实际上只需满足 trait is_error_code_available<T>, 即可让 EC 被当作 error_code 对待. Outcome 为 std::error_code 与 boost::system::error_code 特化该 trait, 因此它们 “直接可用”.

如果不存在特化, 只要存在某个经 ADL 发现的自由函数 trait::is_error_code_available<EC>, make_error_code(EC) 即为真.

因此, 我们实际上可以使用任何喜欢的自定义 EC 类型, 包括携带额外信息 (即负载) 的类型. 这个负载可以携带任何东西, 并且你可以告诉 Outcome 在不同情形下对该负载做不同的事情. 例如:

  1. 如果用户试图观察一个不成功的 result, 抛出一个自定义异常, 内含失败原因以及来自负载的伴随上下文.
  2. 如果用户从携带负载的 outcome 构造出 result, 把被构造 outcome 的 exception ptr 设为一个自定义异常, 内含失败原因以及来自负载的伴随上下文.
  3. 传输一个指明失败确切发生点的栈回溯, 并在转换为人类可读文本的那一刻把该回溯符号化为人类可读文本.
  4. 当库 A 的命名空间本地化 result 被拷贝/移动进 C 绑定库 B 的命名空间本地化 result 时, 若错误码与类别能映射到 errno 域, 则设置 C 的 errno.

当然还有许多许多其他选项. 本教程只能覆盖一个合理的子集. 本节讲上面的示例 1: 在观察不成功的 result 时抛出带负载的自定义异常.
