outcome<>

类型 outcome<T, EC = varies, EP = varies, NoValuePolicy = policy::default_policy<T, EC, EP>> 表示: 要么是类型为 T 的成功计算值, 要么是一或两个失败原因. 失败可以由 EC 或 EP 或两者表示, 尽管通常它是 EC 或 EP 之一. 与 result 类似, EC 默认为 std::error_code/boost::system::error_code, EP 默认为 std::exception_ptr/boost::exception_ptr.

区分体现为两个类型 EC 与 EP:

  • EC 表示来自下层函数的可恢复失败, 也许是经由 result<T, E = varies, NoValuePolicy = policy::default_policy<T, E, void>> 返回的.
  • EP 表示不可恢复的失败——本来通常会抛出 C++ 异常的那种. 这通常是一个指向异常抛出的指针.

应当强调, 这种区分只是约定; 如果你显著偏离该约定, 会让你的用户困惑.

遗留代码库

outcome 对跨程序层传输异常很有用——那些层在设计时从未考虑异常安全.

考虑一个由三层组成的程序:

最高层 Layer3 用异常通知失败. 中间层 Layer2_old 设计时未考虑异常安全, 函数需要经返回值返回失败信息. 而在实现细节深处, 即 Layer1, 又使用了另一个会抛异常的库. 目标是能够把 Layer1 中抛出的异常穿过 Layer2_old (它不是异常安全的) 传输, 并能在 Layer3 中重抛.

在 Layer1 中, 我们有两个来自不同库的函数: 一个通过抛异常报告失败, 另一个通过返回 result<> 报告失败:

auto f() -> int;  // throws on failure
auto g() noexcept -> outcome::result<int>;
在 Github 上查看此代码

在 Layer2_old 中我们不能使用异常, 所以其函数 h 使用返回类型 outcome<> 来报告失败. 它使用了函数 f 与 g, 并在 outcome<> 中报告它们的失败:

auto old::h() noexcept -> outcome::outcome<int>
{
  BOOST_OUTCOME_TRY(auto i, (g()));             // #1
    
  try {
    return i + f();
  }
  catch (...) {
    return std::current_exception(); // #2
  }
}
在 Github 上查看此代码

#1. 运算符 TRY 可以把编码在 result<T, EC> 中的失败作为 outcome<T, EC, EP> 转发, 不丢失任何信息. 你也可以使用 TRY 把失败从一个 outcome<> 转发到另一个.

#2. 你可以把当前异常通过 std::exception_ptr 存入 outcome<T, EC, EP>, 不丢失任何信息 (前提是 EP 为 std::exception_ptr).
