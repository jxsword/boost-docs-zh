前置条件

Outcome 是一个仅头文件的 C++ 14 库, 已知在以下编译器-平台组合的最新点版本或更好版本上工作良好:

  • clang 4.0.1 (LLVM) [FreeBSD, Linux, OS X]
  • GCC 6.5 [Linux]
  • Visual Studio 2017.9 [Windows]
  • XCode 9 [MacOS]

对于非 Windows 非 POSIX 平台 (通常是嵌入式系统), Outcome 以其 Outcome.Experimental 形式在定义 BOOST_OUTCOME_SYSTEM_ERROR2_NOT_POSIX 宏时可用.

如果可以, 值得开启 C++ 17 或 C++ 20, 因为有许多易用性与性能改进. 编译器实现的任何 Concepts TS 或 Coroutines TS 会被自动检测并使用.

已知编译器问题 (最后更新于 2023 年 4 月):

  • clang 3.5 - 3.9 能编译测试套件的不同部分, 问题在于缺乏完整且无缺陷的 C++ 14 语言支持.

  • GCC 7 与 8 的较早点版本在 constexpr 实现中存在内部编译器错误缺陷, 往往会在 constexpr 中使用 Outcome 时触发. 如果你不在 constexpr 中使用 Outcome, 就不会看到这些问题. 如果你的 GCC 不想 ICE, 请升级到最新点版本, constexpr ICE 此后已被修复.

  • Visual Studio 2017 的早期版本有许多边角问题. 从 VS2017.9 起仍存在若干通常不碍事的边角问题, 但对大多数用例而言使用应当相对不出意外. 注意, 只有从 Visual Studio 2022 起, 几乎所有边角问题才被修复.

  • GCC 10 的某些点版本配合 libstdc++ 10 可能引发无限模板实例化, 使一些少见用例的构建失败. 更早或更晚的 GCC 或 10 系列的其他点版本没有此问题.

无法工作、且在维护者修复之前也不会工作的 “C++ 14” 编译器:

  • GCC 5, 原因是嵌套模板变量解析中的一个缺陷, 已在 GCC 6 中修复. 我知道这让许多用户不满. 请把你的不满提交到 https://gcc.gnu.org/bugzilla/. 与此同时, 即使是 clang 3.5, 你在 Outcome 中也能走得相当远.
  • 任何使用随 GCC 5 附带的 libstdc++ 版本的编译器, 因为它没有实现足够的 C++ 14 标准库供 Outcome 编译.
