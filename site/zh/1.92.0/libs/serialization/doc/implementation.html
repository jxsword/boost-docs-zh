字符编码

字符编码与宽字符相结合的整个问题比看起来复杂得多. 当前的库定义了 3 种格式 (文本、二进制和 XML) 、宽字符与窄字符, 并尝试在编译器库之间保持可移植性. 对所有这些因素进行相当长时间的考虑之后, 得出了按以下规则设置默认编码的结果.
  • 所有文本档案 (即 text_?archive) 都会按当前流的 locale 产生文本输出. 一般来说这不会改变字符串数据.
  • 要用 Microsoft 编译器产生二进制输出, 必须以 ios::binary 模式打开流. 若不这样做, 当 0x0d 字符 (回车) 后面跟着 0x0a 字符 (换行) 时, 它们会被从输入流中删除. 这可能损坏输入并使文件不可读. 在 UNIX 系统上不需要 ios::binary, 即使使用也会被忽略.
  • 字符 XML 档案 (即 xml_oarchive) 会产生按当前流 locale 编码字符的 XML 输出.
  • 宽字符 XML 档案 (即 xml_woarchive) 会产生以 UTF-8 编码的文件.
这种字符编码的实现方式是: 在构造档案时更改档案所用 i/o 流的 locale; 当流 locale 被改回其原始值时——这一行为可以通过在打开档案时指定 boost::archive::no_codecvt 来禁止. 在这种情况下, 流 locale 不会被序列化库更改.

注意, 为宽字符文本和 XML 档案包含的代码转换可能改变档案中存储的 std::string 数据. 假设把一个普通 (多字节) 字符串写入宽字符流. 我们的系统在写出之前使用当前 locale 把它转换为宽字符串. 读取时再转换回 (多字节) 字符串. 如果读取档案平台上的 locale 与写出该流平台上的 locale 不同, 实际字符串数据可能被序列化过程改变. 为避免这一点, 要么避免使用依赖 locale 的多字节字符串, 要么确保在读取档案之前正确设置 locale.

要产生宽字符文本输出 (即 Win32 系统上的 16 位字符) , 请按以下步骤操作.

  • 打开一个宽字符流.
  • 把流 locale 改为使用 boost::archive::codecvt_null<OStream::char_type>
  • 以 no_codecvt 标志创建档案.
自然, 输入过程必须是对称的.

特定编译器/库问题

GCC 4.X

  • Cygwin 和 MinGW 的 GCC 版本不支持宽字符 I/O. 因此所有使用宽字符 I/O 的测试都会失败. 注意, 如果通过 STLPort 加入宽字符 I/O 支持, 则所有测试都能成功完成.
  • 该编译器会生成与多态类中使用非虚析构函数相关的长篇警告消息. 这些警告已被仔细考虑, 产生这些警告的代码保持未变. 在这种情况下应当忽略这些警告, 因为在本库的某些用法中, 把析构函数设为虚函数可能导致问题. 作为替代, 基类析构函数已被设为"protected", 以回应促成这些警告消息的顾虑. 用 bjam 构建序列化库和测试时, 这些警告被抑制. 构建自己的应用程序时, 可以通过在编译器命令行加入以下内容来抑制这些警告: 
    
    -Wno-non-virtual-dtor
    -Wno-ctor-dtor-privacy

Intel C++ 8.0

没有已知问题. 所有测试都能在 debug 和 release 模式下编译并运行.

Visual C++ 8.0

该编译器会对调用被视为安全风险的标准库函数发出警告. 序列化依赖于进行其中一些调用, 因此使用序列化库的程序会收到警告消息. 这些消息可以在命令行通过包含以下开关来抑制: 

    /wd4996

Visual C++ 7.1

如……中所描述的、从定义在 DLL 中的档案类派生将无法工作. 这是由于 VC++ 处理带有 __decl(dllexport) 和 __decl(dllimport) 说明的模板化代码的方式. 基本上, 该编译器要求所有实例化都具有相同的说明——即使它们有不同的模板实参. 示例 demo_portable_iarchive.cpp 必须改写成类似预定义档案那样的库或 dll 才能工作.

该编译器默认不开启 RTTI 和异常处理. 虽然使用序列化包并不严格需要它们, 但示例和测试程序假定它们已启用. 因此, 如果想构建并运行这些程序, 请确保你的命令行或 IDE 设置启用了这些特性.

该编译器可以把 wchar_t 当作短整数或内建类型. 如果在编译命令行指定 /Zc:wchar_t, wchar_t 将被视为内建类型——否则它会被当作 16 位整数的同义词. 库可以任一方式使用—— 但是 ——库 和 应用程序都必须用相同的开关设置编译. 注意 BJAM 默认包含此开关. 因此如果想使用 BJAM 构建的库, 编译自己的应用程序时应当包含此开关.

使用 Visual C++ IDE
本库包含一个 VC++ 7.1 "Solution"——BoostSerializationLibrary, 以及一组工程文件——每个示例和测试各一个. 如果决定使用这些配置, 请考虑以下几点.
  • 这些工程假定测试已经用 bjam 以默认位置构建. 这会在你的 boost 主目录下产生一个 bin 子目录. 其下有一整套结构, 按构建类型维护对象文件和库文件. 最简单的构建方法是调用 runtest 脚本, 它使用 bjam (见下文) . 如果库不在这些位置, 就必须相应修改这些工程.
  • boost 支持的所有构建变体组合都有对应的工程配置. 即 release、debug、静态、静态多线程等.
  • 如果想使用/调试 DLL 版本的库及相应测试, 请修改工程文件以定义 BOOST_ALL_DYN_LINK=1. 注意, 要运行可执行文件, PATH 环境变量必须包含包含 boost 库 DLL 版本的目录.
  • 如果在构建自己的项目并与 boost 库链接时遇到困难, 请把自己项目的工程设置与这里的设置比较. VC 有时要求项目与其使用的库之间设置一致才能正确链接. 特别要检查对异常、运行期类型 (RTTI) 以及宽字符内建支持的情况. 本库的标准版本假定这些设施已启用. IDE 向导生成的项目默认不启用这些特性.
  • 在尝试构建项目或查看项目属性时, 经常会弹出一个消息为"未指定错误"的消息框. 这似乎发生在更改构建配置选择时. 事实证明, 可以"修复"它: 转到"Build"菜单项, 选择"Configuration Manager", 并为你正在处理的项目选择一个构建配置.
  • 要测试 boost 库是否构建正确, 可以按我们的方式构建并测试它们. 这包括:
    1. 下载一份 bjam.exe
    2. 构建 process_jam_log
    3. 构建 compiler_status
    4. 调用 runtest.bat
    这将构建序列化库并在你的系统上运行测试. 如果有不止几个测试失败, 你很可能无法让自己的项目正常工作. 如果大多数测试通过, 你就可以确信, 一旦把项目设置与这里包含的设置同步, 你自己的项目就能正常工作.

Comeau 4.3.3

  • 该编译器无法在 Windows 下构建带导出的 DLL.
  • 相关的库——libcomo 在使用 codecvt facet 时失败. 这导致所有宽字符档案失败.
  • test_set 因陷入无限的内存泄漏而失败.

Code Warrior 9.x

  • 一些测试和示例失败——仍在调查中

Code Warrior 8.3

Code Warrior 9.x 的上述所有问题, 外加:
  • 该编译器只对静态库版本支持模板化流.
  • 上述问题阻碍了 DLL 版本库的构建.
  • 一些示例失败——仍在调查中

TRU64

除 test_variant 外, 所有测试和示例都通过. Boost Variant 在该编译器上无法工作

Dinkumware 库

多个编译器 (包括 Visual C++ 6.0) 使用较旧的 dinkumware 库. 这些平台有几个问题:
  • 该编译器附带的 dinkumware 库在流打开之前未调用 imbue 函数时, 不会更改 i/o 流的 locale facet. 要在这种环境下使用本库生成 UTF-8 文件, 不能依赖档案实现的"自动" locale 设置. 必须在流上打开档案之前显式设置流 locale. 档案应以 no_codecvt 标志打开. 注意, 所有附带该库的编译器都会出现此问题.
  • 其他问题已在文件中变通解决. dinkumware.hpp

STLPort 4.5.3

  • 当构建为使用 C++ 运行时代码的动态链接版本 (dynamic) 时, 所有测试都无法链接. 这是由于 stlport 库中缺少与自定义 codecvt facet 相关的符号.
  • test_set 无法正确运行. 似乎哈希 set 迭代器没有正确实现 ++ 运算符. 这导致测试耗尽所有可用内存而失败. 鉴于此, 该测试已被注释掉.
