简单档案

Archive 概念规定了一个类为实现 Serializable 类型序列化而必须实现的函数. 我们的讨论将聚焦于用于保存的档案, 因为其层次结构与用于加载数据的档案完全类似.

最低要求

建模 Archive 概念的最简单的类, 其样子如下: 

#include <cstddef> // std::size_t
//////////////////////////////////////////////////////////////
// class trivial_oarchive
class trivial_oarchive {
public:
    //////////////////////////////////////////////////////////
    // public interface used by programs that use the
    // serialization library
    typedef boost::mpl::bool_<true> is_saving; 
    typedef boost::mpl::bool_<false> is_loading;
    template<class T> void register_type(){}
    template<class T> trivial_oarchive & operator<<(const T & t){
        return *this;
    }
    template<class T> trivial_oarchive & operator&(const T & t){
        return *this << t;
    }
    void save_binary(void *address, std::size_t count){};
};
最简单的输入档案类与上面的类似. 在下面的讨论中, 只讨论输出档案. 输入档案与输出档案完全对称.

该档案可以用任何实现了 Serializable 概念的类型编译并执行. 示例参见 demo_trivial_archive.cpp. 当然, 这个程序按原样不会产生任何输出. 但它提供了一个简单类的起点, 可用于记录格式化输出. 参见 简单日志档案 的实现以了解这是如何做到的.

更实用的档案类

上面这个示例就其本身而言没有问题, 但它没有实现指针序列化、类版本控制等实用特性. 本库实现了一个适合多种用途的全功能档案类家族.

我们的档案已被分解为一棵类树, 以尽量减少代码重复. 这显示在随附的 类图 中. 任何满足以下要求的类都能融入这个层次结构, 并实现我们所要求的全部特性. 从基类 common_oarchive.hpp 派生可以提供我们想要的、而上面的 trivial_oarchive 所缺失的全部特性. 



#include <cstddef> // std::size_t
#include <boost/archive/detail/common_oarchive.hpp>

/////////////////////////////////////////////////////////////////////////
// class complete_oarchive
class complete_oarchive : 
    public boost::archive::detail::common_oarchive<complete_oarchive>
{
    // permit serialization system privileged access to permit
    // implementation of inline templates for maximum speed.
    friend class boost::archive::save_access;

    // member template for saving primitive types.
    // Specialize for any types/templates that require special treatment
    template<class T>
    void save(T & t);

public:
    //////////////////////////////////////////////////////////
    // public interface used by programs that use the
    // serialization library

    // archives are expected to support this function
    void save_binary(void *address, std::size_t count);
};
只要给出 save 和 save_binary 的适当定义, 任何使用序列化的程序在符合标准的 C++ 编译器上都应能以此档案类编译并运行.

可选重写

detail::common_oarchive 类包含许多函数, 序列化库的各个部分会用它们来帮助把档案渲染成特定形式.

void save_start(char const *)

默认 : 什么也不做.
目的 : 向档案注入/读取对象名. XML 档案用它来在数据之前注入 "<name>".

void save_end(char const *)

默认 : 什么也不做.
目的 : 向档案注入/读取对象名. XML 档案用它来在数据之后注入 "</name>".

void end_preamble()

默认 : 什么也不做.
目的 : 在每次保存用户数据时被调用. 保存档案簿记数据时不被调用. XML 档案用它来确定何时在 XML 头的末尾注入 ">" 字符. XML 输出档案维护自己的内部标志, 表明当前写出的数据是头数据. 写入对象起始标签时该内部标志被复位. 当调用 void end_preamble() 且该内部标志已设置时, 会向输出追加一个 ">" 字符, 并复位该内部标志. void end_preamble() 的默认实现是空操作 (no-op) , 从而允许在不使用它的档案类中将其优化掉.

template<class T> void save_override(T & t, int);

默认 : 调用 archive::save(Archive & ar, t)
这是进入序列化库的主要入口.
目的 : 当数据需要以某种特殊方式写入档案时, 可以对此进行特化. 例如, XML 档案通过为名值对重写此函数模板来实现对名值对的特殊处理. 这会取代默认的名值对处理 (默认处理只是丢弃名称) , 换成适合 XML 的处理方式, 即写出带有正确对象名的 XML 标签起始部分.

序列化库使用的类型

序列化库向序列化档案注入簿记数据. 这些数据包括对象 id、版本号、类名等. 这些对象各自被包在一个 wrapper 中, 使档案类可以重写 void save_override(T & t, int); 的实现. 例如, 在 XML 档案中, 该类型的重写会把等于 23 的 object_id 渲染为 "object_id=_23". 下表列出了序列化库内部使用的、定义于 boost::archive namespace 中的类型:

类型default
serialized as
version_typeunsigned int
object_id_typeunsigned int
object_id_reference_typeunsigned int
class_id_typeint
class_id_optional_typenothing
class_id_reference_typeint
tracking_typebool
classname_typestring

所有这些类型都有以原始类型定义的默认序列化, 因此不要求为这些类型定义 save_override.

这些类型定义于 basic_archive.hpp. 所有这些类型都被指定了 实现级别 为 primitive, 并可转换为 int、unsigned int 等类型, 因此它们有默认实现. basic_text_iarchive.hpp 说明了这一点, 它依赖于默认实现. 不过在某些情况下, 必须为这些类型显式提供重写. 示例参见 basic_xml_iarchive.hpp.

在实际操作中, 我们可能还没有完全完成. 可能需要解决以下一个或多个问题:

  • 即使使用符合标准的编译器, 我们可能也希望新的档案类可移植到不符合标准的编译器.
  • 我们的档案格式可能需要在其中插入额外信息. 例如, XML 档案需要在所有数据对象周围加上 <name ... >...</name>.
  • 解决上述任何问题都可能产生更多有待解决的问题.
  • 库中包含的档案都是模板, 使用 stream 或 streambuf 作为模板参数, 而不是简单的类. 结合上述情况, 在不符合标准的编译器上会出现更多问题.
随附的 类图 展示了用于实现序列化库的各类之间的关系.

仔细考察库中包含的档案, 可以了解制作一个覆盖所有数据类型的可移植档案需要些什么.

用法

新创建的档案通常存放在自己的头文件模块中. 只需包含该头文件并构造新档案的一个实例即可. 但有一个特例除外.
  • 派生类的实例通过基类指针序列化.
  • 这些实例没有被"注册", 无论隐式还是显式都没有. 也就是说, 宏 BOOST_CLASS_EXPORT 用于为所包含的档案实例化序列化代码.
为使其生效, 应在档案类定义之后包含以下内容. 

BOOST_SERIALIZATION_REGISTER_ARCHIVE(Archive)
不这样做并不会妨碍程序正常编译、链接和执行——除了一种情况. 如果派生类的实例通过指向其基类的指针序列化, 程序将抛出 unregistered_class 异常.

测试

对库的彻底测试要求用每个档案测试对象序列化的不同方面. 有 46 个不同的测试可以在任何档案上运行. 系统包含 5 个"标准档案" (在不支持宽字符 i/o 的系统上是 3 个) .

此外, 还有 28 个与任何特定档案类无关的测试.

默认的 bjam 测试配置会运行上述所有测试. 这将产生多达 46 项档案测试 * 5 个标准档案 + 28 项通用测试 = 258 项测试. 注意, 对库的完整测试还要包括 DLL 与静态库、release 与 debug 的组合, 因此实际总数会更接近 1032 项测试.

对于每个档案, 测试目录中都有一个类似于下面的头文件. 通过把环境变量 BOOST_ARCHIVE_TEST 设置为该头文件的名称, 把档案名传给测试程序. 下面是头文件 test_archive.hpp. 其他档案的测试头文件类似. 


// text_archive test header
// include output archive header
#include <boost/archive/text_oarchive.hpp>
// set name of test output archive
typedef boost::archive::text_oarchive test_oarchive;
// set name of test output stream
typedef std::ofstream test_ostream;

// repeat the above for input archive
#include <boost/archive/text_iarchive.hpp>
typedef boost::archive::text_iarchive test_iarchive;
typedef std::ifstream test_istream;

// define open mode for streams
//   binary archives should use std::ios_base::binary
#define TEST_STREAM_FLAGS (std::ios_base::openmode)0
要用 gcc 编译器测试一个新档案 (例如可移植二进制档案) , 创建一个头文件 portable_binary_archive.hpp, 并调用 bjam (用 
 
-sBOOST_ARCHIVE_LIST=portable_binary_archive.hpp
) . 这个过程封装在 shell 或 cmd 脚本 library_test 中, 其命令行是 

library_test --toolset=gcc -sBOOST_ARCHIVE_LIST=portable_binary_archive.hpp

多态档案

动机

到目前为止描述的所有档案都以模板实现. 向档案保存和加载数据的代码会为档案类与数据类型的每种组合重新生成. 在这种情况下, 一个能将 inline 函数内联到足够深度的优秀优化编译器会生成快速的代码. 但是:
  • 大量内联代码可能被复制.
  • 如果有多个档案类, 每个档案类都会重新生成代码.
  • 如果序列化代码放在一个库里, 每次创建新的档案类都必须重新构建该库.
  • 如果把序列化代码放进 DLL,
    • DLL 将包含每个已知档案类型的代码版本. 这会导致加载包含大量未使用代码的 DLL——基本上违背了当初选择使用 DLL 的主要动机之一.
    • 如果创建了新档案并发布应用程序, 所有 DLL 都必须重新构建, 并随使用新档案的应用程序一起重新发布. 这样, 使用 DLL 的另一个主要动机也被破坏了.

实现

解决方案是 polymorphic_oarchive 与 polymorphic_iarchive 这一对. 它们提供一个由虚函数构成的公共接口——不含模板——等价于标准的模板化接口. 随附的 类图 展示了这一点.

文件 demo_polymorphic.cpp、demo_polymorphic_A.hpp 和 demo_polymorphic_A 中随附的示例程序演示了如何使用多态档案. 注意以下几点:

  • demo_polymorphic_A.hpp 和 demo_polymorphic_A.cpp 不包含模板, 也不引用任何特定的档案实现. 也就是说, 它们只需为所有档案实现编译一次. 这甚至适用于将来创建的档案类.
  • 主程序 demo_polymorphic.cpp 指定一个特定的档案实现.
从 类图 和头文件可以看出, 这个实现只是多态接口与标准模板驱动实现的组合. 该组合由模板 polymorphic_iarchive_route.hpp 和 polymorphic_oarchive_route.hpp 完成, 它们把对多态档案的调用重定向到具体档案. 由于它们不包含特定于具体实现档案的代码, 因此可以用任何可正常工作的模板化档案实现来创建多态档案实现.

为方便起见, 本库包含了一些小头文件, 其中含有多态实现 (对应于各个模板化实现) 的 typedef. 例如, 头文件 polymorphic_text_iarchive.hpp 和 polymorphic_text_oarchive.hpp 分别包含 typedef, 用于标准文本档案类 text_iarchive.hpp 和 text_oarchive.hpp 的多态实现. 所有随附的多态档案都使用相同的命名方案.

用法

多态档案解决了前面提出的有关模板化实现的问题: 即没有重复的代码, 也不需要为新档案重新编译. 这将使使用多种档案类型的程序获得更小的可执行文件和更小的 DLL. 通过虚函数分派表调用档案函数有性能代价, 而且编译器不可能 inline 档案函数. 这会导致保存和加载档案的性能出现可察觉的下降.

注意, 多态档案的概念与用户以如下方式标记为"primitive"的新类型的序列化在根本上不兼容: 

 
BOOST_CLASS_IMPLEMENTATION(my_primitive_type, boost::serialization::primitive_type)
实现这些类型序列化的代码是在用户程序中"即时"实例化的. 但这与多态档案的全部目的相冲突. 尝试序列化这样的原始类型会导致编译错误, 因为公共多态接口是静态的, 无法为新类型实例化代码.

多态档案的主要用途是允许构建类 DLL, 其中包含针对现有及未来档案的序列化代码, 而无需冗余代码.
