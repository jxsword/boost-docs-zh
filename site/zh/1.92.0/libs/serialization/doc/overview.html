这里, 我们用术语 "序列化" 表示把任意一组 C++ 数据结构可逆地解构为字节序列. 这样的系统可用于在另一个程序环境中重构等价的结构. 视上下文而定, 它可以用来实现对象持久化、远程参数传递或其他设施. 在本系统中, 我们用术语 "档案" 指这种字节流的特定呈现形式. 它可以是二进制数据文件、文本数据、XML, 或由本库使用者创建的其他格式.

我们对这样一个系统的目标是:

  1. 代码可移植性——只依赖 ANSI C++ 设施.
  2. 代码经济性——在合适之处利用 C++ 的特性 (如 RTTI、模板、多重继承等) , 使代码更短、更易使用.
  3. 每个类定义独立的版本控制. 也就是说, 当类定义改变时, 旧文件仍可被导入到类的新版本.
  4. 深指针保存与恢复. 也就是说, 保存和恢复指针时会保存和恢复所指向的数据.
  5. 正确恢复指向共享数据的指针.
  6. STL 容器和其他常用模板的序列化.
  7. 数据可移植性——在一个平台上创建的字节流应当可以在任何其他平台上读取.
  8. 类序列化与档案格式的正交规定. 也就是说, 任何文件格式都应当能够存储任意 C++ 数据结构集合的序列化, 而不必改动任何类的序列化.
  9. 非侵入式. 允许对未改动的类应用序列化. 也就是说, 不要求待序列化的类派生自特定基类或实现指定成员函数. 这对于轻松地把序列化应用于那些我们无法或不希望改动的类库中的类是必要的.
  10. 档案 接口必须足够简单, 以便轻松创建新类型的档案.
  11. 档案 接口必须足够丰富, 以便能够创建以实用方式把序列化数据呈现为 XML 的 档案 .

其他实现

在开始之前, 我四处寻找现有的实现. 我找到了几个.
  • MFC 这是我非常熟悉的一种. 我使用它已有数年, 发现它非常有用. 然而它不满足需求 1、2、3、6、7 和 9. 尽管有这么多未满足的需求, 它仍是我找到的最有用的实现. 事实证明, 类版本控制——MFC 中部分实现——对我的应用确实不可或缺. 发布的程序的 1.x 版不可避免地需要在文件中存储比最初预留更多的信息. MFC 是这些实现中唯一支持这一点的——尽管只对最派生的类支持. 不过聊胜于无, 也能完成任务. MFC 不实现 STL 集合的序列化, 但对 MFC 集合实现了.
  • CommonC++ libraries [1] 据我观察, 它紧随 MFC 实现, 但确实解决了其中一些问题. 它是可移植的, 能创建可移植的档案, 但跳过了版本控制. 它确实支持指针和 STL 集合的正确完整恢复. 它也处理了压缩, 尽管不是我最喜欢的方式. 这个包若能有更好的文档会更好. 因此它未满足 2、3、7、8 和 9.
  • Eternity [2] 这是一个非常简陋的包. 它看起来编码良好, 但确实需要文档和示例. 不花时间研究源代码, 就看不出该怎么使用它. 最近的版本支持 XML 格式的文件. 它在 3、6、7?、8 和 9 上不合格.
  • Holub 的实现 [3] 正是这篇文章首次让我思考自己对序列化实现的要求. 如果你能忍受行文中傲慢的语气, 它很有趣、值得一读. 该实现未满足 2、3、4、5 和 6.
  • s11n [13] 该库与本库目标相似. 实现的某些方面也相似. 截至撰写本文时, 看起来:
    • 可移植性(1)仅对较新的 GCC 版本有保证.
    • 类定义的版本控制(3)没有被库显式支持.
    • 它似乎不会自动处理共享指针(5). 我是从文档以及"不支持图状结构的序列化"这一说法得出此结论的.
    它与本实现有很多差异——也有很多共同点.
