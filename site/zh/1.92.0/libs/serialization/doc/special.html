对象跟踪

视类的使用方式和其他因素而定, 被序列化的对象可能按内存地址跟踪. 这防止同一对象被多次写入档案或从档案读出. 这些存储的地址还可用于删除在因抛出异常而中断的加载过程中创建的对象.

在从同一地址保存不同对象的副本的程序中, 这可能引发问题. 


template<class Archive>
void save(boost::basic_oarchive & ar, const unsigned int version) const
{
    for(int i = 0; i < 10; ++i){
        A x = a[i];
        ar << x;
    }
}
在此情况下, 要保存的数据位于栈上. 循环的每次迭代都会更新栈上的值. 因此尽管数据每次迭代都改变, 数据的地址却不变. 如果 a[i] 是按内存地址跟踪的对象数组, 库会跳过存储第一个之后的对象, 因为它会假定同一地址上的对象其实是同一个对象.

为帮助检测这类情况, 输出档案运算符预期接受 const 引用实参.

鉴于此, 上面的代码会触发编译期断言. 本例中显而易见的修复是使用 


template<class Archive>
void save(boost::basic_oarchive & ar, const unsigned int version) const
{
    for(int i = 0; i < 10; ++i){
        ar << a[i];
    }
}
, 它可以毫无问题地编译运行. 输出档案运算符使用 const 将确保序列化过程不改变被序列化对象的状态. 试图这样做等于给"保存状态"的概念掺入某种不明显的副作用. 这几乎肯定是个错误, 并且很可能是极隐蔽缺陷的来源.

遗憾的是, 目前的实现问题导致当数据项被包装为名值对时无法检测这类错误.

当不同的对象被加载到一个与最终位置不同的地址时, 也可能发生类似问题: 


template<class Archive>
void load(boost::basic_oarchive & ar, const unsigned int version) const
{
    for(int i = 0; i < 10; ++i){
        A x;
        ar >> x;
        std::m_set.insert(x);
    }
}
在此情况下, 被跟踪的是 x 的地址, 而不是加入集合的新条目的地址. 若不处理, 这会破坏依赖跟踪的特性, 例如通过指针加载对象. 程序中会被引入隐蔽缺陷. 可以通过这样修改上面的代码来解决: 

template<class Archive>
void load(boost::basic_iarchive & ar, const unsigned int version) const
{
    for(int i = 0; i < 10; ++i){
        A x;
        ar >> x;
        std::pair<std::set::const_iterator, bool> result;
        result = std::m_set.insert(x);
        ar.reset_object_address(& (*result.first), &x);
    }
}
这会调整跟踪信息以反映被移动变量的最终落脚之处, 从而纠正上述问题.

如果事先知道没有指针值重复, 可以通过适当设置对象跟踪类序列化特征来消除与对象跟踪相关的开销.

默认情况下, 被 实现级别 类序列化特征指定为原始的数据类型从不被跟踪. 如果希望通过指针跟踪一个共享的原始对象 (例如用作引用计数的 long) , 应当把它包装在类/结构体中, 使其成为可识别的类型. 改变 long 的实现级别的替代做法会影响整个程序中序列化的所有 long——这可能不是想要的效果.

即使对象从不通过指针序列化, 我们也可能希望跟踪其地址. 例如, 虚基类只需保存/加载一次. 通过把这个序列化特征设为 track_always, 我们可以抑制冗余的保存/加载操作. 


BOOST_CLASS_TRACKING(my_virtual_base_class, boost::serialization::track_always)

辅助对象支持

某些类型, 特别是那些生命周期行为复杂或对其内部状态访问受限的类型, 可能需要或受益于精巧的序列化算法. 最主要的 motivating 例子是 shared_ptr. 随着实例被加载, 它们必须与任何已经加载的其他实例"配对". 因此, 在包含 shared_ptr 实例的档案被加载期间, 必须维护一张先前已加载实例的表. 若不维护这样的表, shared_ptr 将无法成为可序列化类型.

要实现这一设施, 需要声明一个与当前档案关联的 辅助对象 , 用于存储与特定类型序列化算法相关的上下文信息. 


template<class T>
class shared_ptr
{
   ...
};

BOOST_SERIALIZATION_SPLIT_FREE(shared_ptr)

class shared_ptr_serialization_helper
{
  // table of previously loaded shared_ptr
  // lookup a shared_ptr from the object address
  shared_ptr<T> lookup(const T *);
  // insert a new shared_ptr
  void insert<shared_ptr<T> >(const shared_ptr<T> *);
};

namespace boost {
namespace serialization {

template<class Archive>
void save(Archive & ar, const shared_ptr & x, const unsigned int /* version */)
{
    // save shared ptr
    ...
}

template<class Archive>
void load(Archive & ar, shared_ptr & x, const unsigned int /* version */)
{
    // get a unique identifier.  Using a constant means that all shared pointers
    // are held in the same set.  Thus we detect handle multiple pointers to the
    // same value instances in the archive.
    const void * shared_ptr_helper_id = 0;

    shared_ptr_serialization_helper & hlp =
        ar.template get_helper<shared_ptr_serialization_helper>(helper_instance_id);

    // load shared pointer object
    ...

    shared_ptr_serialization_helper & hlp =
        ar.template get_helper<shared_ptr_serialization_helper>(shared_ptr_helper_id);

    // look up object in helper object
    T * shared_object hlp.lookup(...);

    // if found, return the one from the table

    // load the shared_ptr data
    shared_ptr<T> sp = ...

    // and add it to the table
    hlp.insert(sp);
    // implement shared_ptr_serialization_helper load algorithm with the aid of hlp
}

} // namespace serialization
} // namespace boost
get_helper<shared_ptr_serialization_helper>(); 在第一次被调用时创建与档案关联的辅助对象; 后续调用返回对首次创建对象的引用, 因此 hlp 可以有效地用于存储在同一档案上序列化不同 complex_type 对象期间持续存在的上下文信息.

可以为保存档案和加载档案创建辅助对象. 同一个程序可能有多个不同的辅助对象, 或同一个辅助对象从程序的不同部分分别实例化. 这正是需要 helper_instance_id 的原因. 原则上它可以是任何唯一整数. 实践中最简单的做法似乎是使用包含它的序列化函数的地址. 上面的示例就使用了这一技术.

类信息

默认情况下, 对每个被序列化的类, 类信息会写入档案. 此信息包括版本号、实现级别和跟踪行为. 这是必需的, 这样即使程序的后续版本改动了某个类的某些当前特征值, 档案仍能被正确反序列化. 这些数据的空间开销极小. 有一点点运行期开销, 因为必须检查每个类是否已把其类信息包含进档案. 在某些情况下, 甚至这一点也可能被认为太多. 这些额外开销可以通过把 实现级别 类特征设为: boost::serialization::object_serializable 来消除.

关闭跟踪与类信息序列化会得到纯模板内联代码, 原则上可以优化为简单的流写入/读取. 以这种方式消除所有序列化开销是有代价的. 一旦档案交付给用户, 类序列化特征就不能再改动, 否则会使旧档案失效. 把类信息包含在档案中向我们保证: 即使类定义日后被修订, 档案仍然可读. 像显示像素这样的轻量结构可以像这样在头文件中声明: 


#include <boost/serialization/serialization.hpp>
#include <boost/serialization/level.hpp>
#include <boost/serialization/tracking.hpp>

// a pixel is a light weight struct which is used in great numbers.
struct pixel
{
    unsigned char red, green, blue;
    template<class Archive>
    void serialize(Archive & ar, const unsigned int /* version */){
        ar << red << green << blue;
    }
};

// elminate serialization overhead at the cost of
// never being able to increase the version.
BOOST_CLASS_IMPLEMENTATION(pixel, boost::serialization::object_serializable);

// eliminate object tracking (even if serialized through a pointer)
// at the risk of a programming error creating duplicate objects.
BOOST_CLASS_TRACKING(pixel, boost::serialization::track_never)

档案可移植性

若干档案类以文本或可移植二进制格式创建其数据. 应当能够在一个平台上保存这样的类, 在另一个平台上加载. 这受制于两个条件.

数值

读取档案的机器体系结构必须能容纳保存的数据. 例如, gcc 编译器为存储 wchar_t 类型的变量保留 4 字节, 而其他编译器只保留 2 字节. 因此可能写入一个加载程序无法表示的值. 这是相当明显的情形, 通过使用 <boost/cstdint.hpp> 中的数值类型很容易处理.

一种特殊的整数类型是 std::size_t, 它是某种整数类型的 typedef, 保证大到足以容纳任何集合的大小, 但其实际大小可能因平台而异. collection_size_type 包装器的存在是为了使档案能够以可移植方式序列化集合大小. 对集合大小做可移植序列化的推荐选择是使用 64 位整数或变长整数表示.

特征

另一个潜在的问题由以下示例说明: 

template<class T>
struct my_wrapper {
    template<class Archive>
    Archive & serialize ...
};

...

class my_class {
    wchar_t a;
    short unsigned b;
    template<class Archive>
    Archive & serialize(Archive & ar, unsigned int version){
        ar & my_wrapper(a);
        ar & my_wrapper(b);
    }
};
如果 my_wrapper 使用默认序列化特征, 可能出问题. 使用默认特征时, 每向档案加入一个新类型, 就会加入簿记信息. 所以在本例中, 档案会包含 my_wrapper<wchar_t> 和 my_wrapper<short_unsigned> 的此类簿记信息. 真的会吗? 如果把 wchar_t 当作 unsigned short 同义词的编译器呢? 此时只有一个不同类型——而不是两个. 如果档案在对其 wchar_t 处理方式不同的编译器的程序之间传递, 加载操作将以灾难性方式失败.

对此的一种补救方法是为模板 my_template 赋予序列化特征, 使该模板的实例化的类信息从不被序列化. 此过程在 前文 有描述, 并已用于 名值对 . 包装器通常会被赋予这类特征.

避免此问题的另一种方法是为模板 my_wrapper 针对所有原始类型的所有特化赋予序列化特征, 使类信息从不被保存. 我们对 STL 集合序列化的实现就是这样做的.

二进制档案

某些系统上的标准流 i/o 会在输出时把换行符扩展为回车/换行. 这给二进制档案带来问题. 最简单的处理办法是用标志 ios::binary 以"二进制模式"为二进制档案打开流. 若不这样做, 生成的档案将不可读.

遗憾的是, 尚未找到在加载档案之前检测此错误的方法. debug 构建会在检测到时断言, 因此可能有助于捕捉此错误.

XML 档案

XML 档案是一个 somewhat 特殊的情况. XML 格式具有嵌套结构, 与序列化系统使用的"递归类成员访问器"模式映射良好. 然而, XML 与其他格式的不同之处在于它要求每个数据成员都有名称. 我们的目标是在把这一信息加入类序列化规定的同时, 仍允许序列化代码用于任何档案. 实现方式是: 要求所有序列化到 XML 档案的数据都以 名值对 形式序列化. 第一个成员是用作数据项 XML 标签的名称, 第二个是对数据项本身的引用. 任何试图序列化未包装在 名值对 中的数据的行为都会在编译期被拦截. 系统的实现方式使得对其他档案类只序列化数据的值部分. 名称部分在编译期被丢弃. 因此, 始终使用 名值对 将保证所有数据都能以最高效率序列化到所有档案类.

导出类序列化

在本手册的 其他地方 , 我们已经描述了 BOOST_CLASS_EXPORT. 导出意味着两件事:
  • 实例化其他方式不会引用到的代码.
  • 把外部标识符与要序列化的类关联. 类没有被显式引用这一事实隐含了这一要求.
在 C++ 中, 未被显式引用的代码的使用通过虚函数实现. 因此, 导出的必要性由通过指向其基类的指针或引用操纵派生类的用法所隐含.

在包含任何档案类头文件的同一源模块中包含 BOOST_CLASS_EXPORT, 会为所有那些档案类实例化序列化指定类型多态指针所需的代码. 如果没有包含任何档案类头文件, 则不会实例化任何代码.

注意, 此功能的实现要求 BOOST_CLASS_EXPORT 宏出现在 之后 ——在其代码要被实例化的任何档案类头文件的包含之后. 因此, 使用 BOOST_CLASS_EXPORT 的代码看起来会像下面这样: 


#include <boost/archive/text_oarchive.hpp>
#include <boost/archive/text_oarchive.hpp>
... // other archives

#include "a.hpp" // header declaration for class a
BOOST_CLASS_EXPORT(a)
... // other class headers and exports
无论代码是独立可执行文件、静态库还是动态/共享库的一部分, 这都是成立的.

像对待其他序列化特征那样, 把 BOOST_CLASS_EXPORT 包含在"a.hpp"头文件本身中, 会使上述关于在调用 BOOST_CLASS_EXPORT 之前包含档案头文件的规则变得难以遵守甚至无法遵守. 最好的处理办法是在头文件声明中使用 BOOST_CLASS_EXPORT_KEY, 而在类定义文件中使用 BOOST_CLASS_EXPORT_IMPLEMENT.

本系统对把代码放入静态库或共享库有一定影响. 把 BOOST_CLASS_EXPORT 放入库代码中, 除非同时也包含档案类头文件, 否则不会有效果. 因此构建库时, 应当包含预计会使用的所有档案类的所有头文件. 或者, 可以只包含 多态档案 的头文件.

严格来说, 如果所有指针序列化都通过最派生的类进行, 导出应当不是必需的. 然而, 为了检测可能是灾难性的错误, 本库会拦截所有通过指向多态类的指针进行且未导出或未注册的序列化. 所以在实践中, 要做好准备: 为所有带有一个或多个虚函数且通过指针序列化的类注册或导出.

注意, 此功能的实现依赖于 C++ 语言的厂商特定扩展. 因此, 使用此设施的程序不能保证可移植. 不过, 所有用 boost 测试过的 C++ 编译器都提供所需的扩展. 库中包含了每个编译器所需的额外声明. 可以合理预期未来的 C++ 编译器会支持这些扩展或等价物.

静态库与序列化

数据类型的序列化代码可以像类型的其余实现那样保存在库中. 这工作良好, 并可以节省大量编译时间.
  • 只在库中编译序列化定义.
  • 为打算在库中使用的所有档案类显式实例化序列化代码.
  • 对导出类型, 只在头文件中使用 BOOST_CLASS_EXPORT_KEY.
  • 对导出类型, 只在库中编译的定义里使用 BOOST_CLASS_EXPORT_IMPLEMENT. 对任何特定类型, 应当只有一个文件包含该类型的 BOOST_CLASS_EXPORT_IMPLEMENT. 这确保程序中只存在一份序列化代码. 它避免了空间浪费以及同一程序中存在不同版本序列化代码的可能性. 在多个文件中包含 BOOST_CLASS_EXPORT_IMPLEMENT 可能因符号重复而导致链接失败, 或抛出运行期异常.
  • 序列化代码应当只放在库中,
  • 熟悉 PIMPL 惯用法.
这由 demo_pimpl.cpp 、 demo_pimpl_A.cpp 和 demo_pimpl_A.hpp 说明, 其中序列化的实现位于与主程序完全分离的静态库中.

DLL - 序列化与运行期链接

序列化代码可以放在运行期链接的库中. 也就是说, 代码可以放在 DLL(Windows)、共享库(*nix) 或静态库以及主可执行文件中. 最佳技术与上面针对库所描述的相同. 序列化库测试套件包含以下程序来演示其工作方式:

test_dll_simple 和 dll_a.cpp , 其中序列化的实现也与主程序完全分离, 但代码是在运行期加载的. 在此示例中, 这段代码在用到它的程序启动时自动加载, 但它同样可以用依赖 OS 的 API 调用来加载和卸载.

还包括 test_dll_exported.cpp 和 polymorphic_derived2.cpp , 它们与上面类似, 但在 DLL 环境下包含了对导出和 no_rtti 设施的测试.

为获得最佳效果, 请按以下准则编写代码:

  • 不要在 DLL 中使用的类里包含 inline 代码. 这会在 DLL 和主程序中生成重复代码. 这不必要地复制了代码. 更糟的是, 它使同一代码的不同版本可能同时存在. 事实证明, 这类错误极难调试. 最后, 它带来这样的可能: 被引用的模块被显式卸载, 从而 (但愿) 导致运行期错误. 这是另一种并非总能复现或不易发现的缺陷. 对于类成员模板, 在头文件中使用类似 
    
template<class Archive>
void serialize(Archive & ar, const unsigned int version);
    的代码, 并在实现文件中使用 
    
template<class Archive>
void myclass::serialize(Archive & ar, const unsigned int version){
	...
}

BOOST_CLASS_EXPORT_IMPLEMENT(my_class)

#include <boost/archive/text_oarchive>
#include <boost/archive/text_iarchive>
template myclass::serialize(boost::archive::text_oarchive & ar, const unsigned int version);
template myclass::serialize(boost::archive::text_iarchive & ar, const unsigned int version);
... // repeat for each archive class to be used.
    . 这会确保所有所需代码只在一个地方生成. 库不会替你检测这类错误.
  • 如果 DLL 会被显式加载和卸载 (例如在 *nix 上使用 dlopen, 或在 Windows 上使用 LoadLibrary) , 尽量安排它们按相反顺序卸载. 即使没有遵守上述准则, 这也应当能保证避免问题.

插件

为了实现本库, 需要一些在运行期操纵类型的设施. 它们是 extended_type_info——用于把类与外部标识字符串 ( GUID ) 关联——以及 void_cast——用于在相关类型的指针之间转换. 为补全 extended_type_info 的功能, 还加入了构造和销毁对应类型的能力. 要使用此功能, 必须指定每个类型如何创建. 这应当在导出类时完成. 因此, 上面代码的一个更完整的示例是: 

#include <boost/archive/text_oarchive.hpp>
#include <boost/archive/text_oarchive.hpp>
... // other archives

#include "a.hpp" // header declaration for class a

// this class has a default constructor
BOOST_SERIALIZATION_FACTORY_0(a)
// as well as one that takes one integer argument
BOOST_SERIALIZATION_FACTORY_1(a, int)

// specify the GUID for this class
BOOST_CLASS_EXPORT(a)
... // other class headers and exports
有了这些, 就可以构造、序列化和销毁一个只知道 GUID 和一个基类的类.

多线程

序列化的根本目的与多个线程并发地向单个打开的档案实例写入/读取相冲突. 库实现假定应用程序会避免这种情况.

不过, 允许在不同任务中同时写/读不同的档案, 因为每个档案实例 (几乎) 完全独立于其他档案实例. 唯一共享的信息是一些类型表, 它们用本文档其他地方描述的无锁线程安全 singleton 实现.

该单例实现保证所有这些共享信息在包含它的代码模块被加载时完成初始化. 序列化库注意确保这些数据结构此后不被修改. 唯一可能出问题的情况是: 在另一个任务正在序列化数据时加载/卸载代码. 这只可能发生在其序列化实现于动态加载/卸载的 DLL 或共享库中的类型上. 因此如果避免以下情况:

  • 从不同任务访问同一档案实例.
  • 在任何档案实例打开期间加载/卸载 DLL 或共享库.
库应当是线程安全的.

优化

在序列化大量同质类型连续数据的性能关键应用中, 人们希望避免逐个序列化每个元素的开销, 这正是 array 包装器的动机. 包含同质类型连续数组的数据类型 (例如 std::vector、std::valarray 或 boost::multiarray) 的序列化函数应当使用 array 包装器来序列化它们, 以利用这些优化. 能够为同质类型连续数组提供优化序列化的档案类型应当通过重载 array 包装器的序列化来实现, 正如二进制档案所做的那样.
