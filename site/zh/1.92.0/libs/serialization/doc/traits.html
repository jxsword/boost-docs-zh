数据的序列化取决于数据的类型. 例如, 对于 int 这样的原始类型, 在档案中保存版本号没有意义. 同样, 对于从不通过指针序列化的数据类型, 跟踪保存到档案/从档案加载的对象的地址 (几乎) 从来没有意义, 因为无论如何它都不会被保存/加载多次. 特定数据类型的序列化细节会因类型、使用方式和程序员的规格说明而异.

可以通过指定一个或多个 类序列化特征 来改变特定数据类型被序列化的方式. 通常不需要程序员显式为自己的类指定特征, 因为所有特征都有默认值. 如果默认值不合适, 程序员可以自行指定. 用一个模板把类型名与常量关联. 例如参见 version.hpp .

版本

这个头文件包含以下代码: 

namespace boost { 
namespace serialization {
template<class T>
struct version
{
    BOOST_STATIC_CONSTANT(unsigned int, value = 0);
};
} // namespace serialization
} // namespace boost
对任何类 T 而言, boost::serialization::version<T>::value 的默认定义是 0. 如果我们想把 2 指定为类 my_class 的版本, 我们对 version 模板做特化: 

namespace boost { 
namespace serialization {
struct version<my_class>
{
    BOOST_STATIC_CONSTANT(unsigned int, value = 2);
};
} // namespace serialization
} // namespace boost
此后每当需要类 my_class 的版本号时, 返回的将是 2 而不是默认值 0.

为减少输入并增强可读性, 定义了一个宏, 这样我们不用上面那种写法, 而可以写: 


BOOST_CLASS_VERSION(my_class, 2)
它会展开为上面的代码.

实现级别

与上面相同的方式, 指定序列化"实现级别". 头文件 level.hpp 定义了以下内容. 

// names for each level
enum level_type
{
    // Don't serialize this type. An attempt to do so should
    // invoke a compile time assertion.
    not_serializable = 0,
    // write/read this type directly to the archive. In this case
    // serialization code won't be called.  This is the default
    // case for fundamental types.  It presumes a member function or
    // template in the archive class that can handle this type.
    // there is no runtime overhead associated reading/writing
    // instances of this level
    primitive_type = 1,
    // Serialize the objects of this type using the objects "serialize"
    // function or template. This permits values to be written/read
    // to/from archives but includes no class or version information. 
    object_serializable = 2,
    ///////////////////////////////////////////////////////////////////
    // once an object is serialized at one of the above levels, the
    // corresponding archives cannot be read if the implementation level
    // for the archive object is changed.  
    ///////////////////////////////////////////////////////////////////
    // Add class information to the archive.  Class information includes
    // implementation level, class version and class name if available.
    object_class_info = 3,
};
使用 level.hpp 中定义的宏, 我们可以指定 my_class 连同其版本号一起被序列化: 

BOOST_CLASS_IMPLEMENTATION(my_class, boost::serialization::object_class_info)
如果未显式指定实现级别, 系统按以下规则使用默认值.
  • 如果数据类型是 volatile, 则指定 not_serializable
  • 否则, 如果它是 enum 或基本类型, 则指定 primitive_type
  • 否则指定 object_class_info
也就是说, 对大多数用户定义类型, 对象会连同类版本信息一起被序列化. 这使人能够与包含先前版本的档案保持向后兼容. 不过, 这一能力带来少量运行期开销. 对定义"永远不会"改变的类型, 可以通过指定 object_serializable 来覆盖 object_class_info 的默认设置, 从而获得效率. 例如, binary_object 包装器 就是这样做的.

对象跟踪

视类型的使用方式而定, 可能有必要或便于跟踪被保存和加载对象的地址. 例如, 通过指针序列化对象时通常需要这样做, 以确保加载档案时不会创建多个相同的对象. 这种"跟踪行为"由头文件 tracking.hpp 中定义的类型特征控制, 它定义了以下内容: 

// names for each tracking level
enum tracking_type
{
    // never track this type
    track_never = 0,
    // track objects of this type if the object is serialized through a 
    // pointer.
    track_selectively = 1,
    // always track this type
    track_always = 2
};
定义了对应的宏, 以便我们可以使用: 

BOOST_CLASS_TRACKING(my_class, boost::serialization::track_never)
默认跟踪特征为:
  • 对于原始类型, 为 track_never.
  • 对于指针, 为 track_never. 也就是说, 默认不跟踪地址的地址.
  • 所有当前的序列化包装器, 例如 boost::serialization::nvp、track_never.
  • 对于所有其他类型, 为 track_selectively. 也就是说, 被序列化对象的地址当且仅当以下一项或多项为真时才被跟踪:
    • 该类型的对象在程序中任何地方通过指针被序列化.
    • 该类被显式"导出"——见下文.
    • 该类在档案中被显式"注册".

默认行为几乎总是最方便的. 不过, 有少数情况下覆盖默认值会更好. 一种情况是虚基类. 在带虚基类的菱形继承结构中, 对象跟踪可以防止冗余的保存/加载调用. 所以这是覆盖默认跟踪特征可能带来便利的一种情形. (注意: 在未来的版本中, 默认值将被重新实现, 以自动跟踪用作虚基类的类. ) 库中包含的 test_diamond.cpp 演示了这种情况.

导出键

通过虚基类指针序列化派生类时, 可能出现两个问题.
  • 派生类中的代码可能永远不会被显式引用. 这样的代码永远不会被实例化.

    解决办法是在定义 (实现) 类 T 的文件中调用 BOOST_CLASS_EXPORT_IMPLEMENT(T). 这确保派生类 T 的代码会被显式实例化.

  • 需要某种标识符, 用于在加载对象时选择要调用的代码. 标准 C++ 确实实现了 typeid(), 可用于返回类的唯一字符串. 出于以下原因, 它对我们而言并不完全令人满意:
    • 无法保证该字符串在各平台上相同. 这将无法支持可移植档案.
    • 使用来自各种来源的代码模块时, 类在不同程序中可能不得不被包装在不同的命名空间中.
    • 不同代码模块中本地定义的类可能同名.
    • 可能有名字不同、但我们出于序列化目的希望视为等价的类.

    因此在序列化库中, 解决办法是在声明类的头文件中调用 BOOST_CLASS_EXPORT_KEY2(my_class, "my_class_external_identifier"). 在绝大多数应用中, 类名作为外部标识符字符串工作得很好, 因此定义了以下捷径——BOOST_CLASS_EXPORT_KEY(my_class).

对于只由单个模块构成的程序——即不使用 DLL 的程序——可以在声明头文件或定义中指定 BOOST_CLASS_EXPORT(my_class) 或 BOOST_CLASS_EXPORT_GUID(my_class, "my_class_external_identifier"). 这些宏展开为对上述两个宏的调用. ( GUID 代表 G lobally U nique ID entifier. )

(在本手册的 其他地方 , 详细讨论了派生类的序列化. )

头文件 export.hpp 包含这里描述的所有宏定义. 如果出现以下情况, 库会抛出运行期异常:

  • 未被显式引用的类型未被导出.
  • 同一类型的序列化代码在多个模块 (或 DLL) 中被实例化.

抽象

通过指向基类的指针序列化对象时, 库需要确定基类是否是抽象的 (即至少有一个虚函数) . 库使用类型特征宏 BOOST_IS_ABSTRACT(T) 来完成. 并非所有编译器都支持这个类型特征和相应宏. 为解决这一点, 实现了宏 BOOST_SERIALIZATION_ASSUME_ABSTRACT(T), 允许显式指明某个指定类型实际上是抽象的. 这将保证 BOOST_IS_ABSTRACT 对所有编译器都返回正确的值.

类型信息实现

最后一个特征也与通过基类指针序列化对象有关. 实现该设施需要能在运行期确定基类指针所指向对象的真实类型. 不同的序列化系统以不同方式做到这一点. 在我们的系统中, 默认方法是使用函数 typeid(...), 它在支持 RTTI ( R un T ime T ype I nformation) 的系统中可用. 这在几乎所有情况下都令人满意, 本库的大多数用户跳过手册的这一节不会有任何损失.

不过, 在某些情况下, 默认的类型判定系统并不方便. 某些平台可能不支持 RTTI, 或者为了加快执行速度或其他原因而禁用了它. 某些应用 (例如插件模块的运行期链接) 不能依赖 C++ RTTI 来确定真实的派生类. RTTI 只为多态类——至少有一个虚函数的类——返回正确类型. 如果出现上述任一情况, 可以用自己 extended_type_info 的实现来替代.

实现序列化所需设施的接口定义于 extended_type_info.hpp . 基于 typeid(...) 的这些设施的默认实现定义于 extended_type_info_typeid.hpp . 基于导出类标识符的另一种实现定义于 extended_type_info_no_rtti.hpp .

通过调用宏: 


BOOST_CLASS_TYPE_INFO(
    my_class, 
    extended_type_info_no_rtti<my_class>
)
我们可以逐个类地指定类型信息实现. 不要求程序中的所有类都使用相同的 extended_type_info 实现. 这支持了这样一个理念: 每个类的序列化在头文件中"一次性"指定, 可以不加改动地包含进任何项目.

测试程序 test_no_rtti.cpp 说明了这一点. 其他实现是可能的, 某些特殊情况可能需要它们.

包装器

档案需要与其他类型不同地对待包装器, 因为例如它们通常是非 const 对象, 而输出档案要求任何被序列化的对象 (包装器除外) 都是 const. 头文件 wrapper.hpp 包含以下代码: 

namespace boost { 
namespace serialization {
template<class T>
struct is_wrapper
 : public mpl::false_
{};
} // namespace serialization
} // namespace boost
对任何类 T 而言, boost::serialization::is_wrapper<T>::value 的默认定义因此为 false. 如果我们想声明类 my_class 是包装器, 我们对 version 模板做特化: 

namespace boost { 
namespace serialization {
struct is_wrapper<my_class>
 : mpl::true_
{};
} // namespace serialization
} // namespace boost

为减少输入并增强可读性, 定义了一个宏, 这样我们不用上面那种写法, 而可以写: 


BOOST_CLASS_IS_WRAPPER(my_class)
它会展开为上面的代码.

按位序列化

某些简单的类可以仅通过直接复制类的所有位来序列化. 对于不含指针成员、既不版本化也不跟踪的 POD 数据类型尤其如此. 某些档案 (例如非可移植二进制档案) 可以利用这一信息大幅加速序列化. 为表明可按位序列化, 使用头文件 is_bitwise_serializable.hpp 中定义的类型特征: 

namespace boost { namespace serialization {
    template<class T>
    struct is_bitwise_serializable
     : public is_arithmetic<T>
    {};
} }
被使用, 并可为其他类做特化. 借助相应的宏使特化变得容易: 

BOOST_IS_BITWISE_SERIALIZABLE(my_class)

模板序列化特征

在某些情况下, 一次性为整组类指定序列化特征可能很方便. 考虑 XML 档案用来把名称与类型 T 的数据变量关联的名值对包装器 

template<class T>
struct nvp : public std::pair<const char *, T *>
{
    ...
};
. 这些数据类型从不被跟踪也从不版本化. 因此有人可能想指定: 

BOOST_CLASS_IMPLEMENTATION(nvp<T>, boost::serialization::level_type::object_serializable)
BOOST_CLASS_TRACKING(nvp<T>, boost::serialization::track_never)
考察这些宏的定义可以发现, 把它们与模板实参一起使用时不会展开为合理的代码. 所以不要使用便捷宏, 而要使用原始定义 

template<class T>
struct implementation_level<nvp<T> >
{
    typedef mpl::integral_c_tag tag;
    typedef mpl::int_<object_serializable> type;
    BOOST_STATIC_CONSTANT(
        int,
        value = implementation_level::type::value
    );
};

// nvp objects are generally created on the stack and are never tracked
template<class T>
struct tracking_level<nvp<T> >
{
    typedef mpl::integral_c_tag tag;
    typedef mpl::int_<track_never> type;
    BOOST_STATIC_CONSTANT(
        int, 
        value = tracking_level::type::value
    );
};
来为模板 nvp<T> 生成的所有类指定序列化特征

注意, 只有当使用正确支持模板偏特化的编译器时, 才可能用上述方法为模板指定特征. 第一反应可能是做类似这样的事: 


#ifndef BOOST_NO_TEMPLATE_PARTIAL_SPECIALIZATION
template<class T>
struct implementation_level<nvp<T> >
{
   ... // see above
};

// nvp objects are generally created on the stack and are never tracked
template<class T>
struct tracking_level<nvp<T> >
{
   ... // see above
};
#endif
当希望使自己的代码 和档案 可移植到其他平台时, 这可能有问题. 这意味着对象被序列化的方式取决于所用平台. 这暗示从一个平台保存的对象在另一个平台上可能无法正确加载. 换句话说, 档案将不可移植.

这个问题通过创建另一种为用户类指定序列化特征的方法来解决. 名值对 的序列化演示了这一点.

具体而言, 这需要从一个特殊的类 boost::serialization::traits 派生模板, 该类针对特定的序列化特征组合做了特化. 查找序列化特征时, 库首先检查该类是否被用作基类. 如果是, 则使用相应的特征. 否则使用标准默认值. 通过从序列化特征类派生而不是依赖模板偏特化, 可以把序列化特征应用到模板上, 而且这些特征在所有已知平台上都相同.

编译期警告与错误

某些序列化特征可能与其他特征冲突. 有时这些冲突会导致错误行为 (例如创建无法读取的档案) , 有时它们代表库使用者可能存在的误解, 会导致令人意外的行为. 在可能的范围内, 这些冲突会在编译期被检测出来, 并生成错误 (BOOST_STATIC_ASSERT) 或警告 (BOOST_STATIC_WARNING) . 它们以依赖编译器的方式生成, 应能显示到检测到错误/警告之处为止的实例化链. 没有这一能力, 要追查库使用中的错误或意外行为将非常困难. 以下是被拦截的冲突列表:

object_level - 错误

此错误拦截对实现级别被设为 non_serializable 的类型进行序列化的尝试.

object_versioning - 错误

出于效率原因, 可能给某个类型指定一个在档案中不含类型信息的序列化级别. 这会妨碍为该类型分配新版本号. 此错误拦截在这种情况下分配版本号的尝试. 这必定是用户错误.

object_tracking - 警告

以下代码在编译时会显示一条消息: 
T t;
ar << t;
除非跟踪级别序列化特征被设为"track_never". 以下代码则可以毫无问题地编译: 
const T t
ar << t;
同样, 如果跟踪级别序列化特征被设为"track_never", 以下代码会在编译期被拦截: 
T * t;
ar >> t;

以下情形演示了此消息的作用. 它最初由 Peter Dimov 在邮件列表中用作示例. 

class construct_from 
{ 
    ... 
}; 

void main(){ 
    ... 
    Y y; 
    construct_from x(y); 
    ar << x; 
}
假设上面的消息没有显示, 代码按原样使用.
  1. 这个示例编译和执行都没有问题. 没有做跟踪, 因为 construct_from 从未通过指针序列化. 现在过了一段时间, 下一位程序员(2)来了, 做了一个增强. 他想让档案起到某种日志的作用. 
    void main(){ 
    ... 
    Y y; 
    construct_from x(y); 
    ar << x; 
    ... 
    x.f(); // change x in some way 
   ... 
    ar << x 
}

    同样没有问题. 他在档案中得到两个不同的副本, 每个都不同. 也就是说, 他得到的正是他所期望的, 自然非常高兴.

  2. 又过了一段时间, 第三位程序员(3)看到 construct_from, 说——哦, 太好了, 正是我需要的. 他在一个完全不相干的模块里写了一个函数. (项目如此庞大, 他甚至没有意识到原始用法的存在. ) 他写了类似这样的代码: 
    class K { 
    shared_ptr <construct_from> z; 
    template <class Archive> 
    void serialize(Archive & ar, const unsigned version){ 
        ar << z; 
    } 
};

    他构建并运行程序, 测试他的新功能. 一切正常, 他很高兴.

  3. 事情像从前一样顺利进行. 一个月过去了, 人们发现在加载上个月生成的档案 (读取日志) 时出了问题: 第二条日志条目总是与第一条相同. 经过一系列漫长且火药味渐浓的邮件往来, 发现是程序员(3)意外破坏了程序员(2)的代码. 因为通过指针序列化, "日志"对象现在被跟踪了. 这是因为默认跟踪行为是"track_selectively". 这意味着: 只有当类实例在程序中任何地方通过指针被序列化时, 它们才会被跟踪. 现在, 从同一地址的多次保存只有第一次会写入档案. 后续的保存只会加入地址——即使数据可能已经改变. 等到加载数据时, 所有日志记录实例都显示相同的数据. 就这样, 一个原本正常工作的代码的行为, 由于一个不相干模块改动的副作用而改变了. 更糟的是, 数据已经丢失, 无法从档案中恢复. 人们对 boost (至少是序列化系统) 非常恼火和失望.

  4. 经过大量调查, 发现了问题的根源, 并通过包含: 
    BOOST_CLASS_TRACKING(construct_from, track_never)
    把类 construct_from 标记为"track_never".
  5. 现在一切又正常了. 或者——看起来如此.

  6. shared_ptr<construct_from> 不会在各实例之间共享同一个裸指针. 每个加载的 shared_ptr<construct_from> 都会有自己独立的裸指针. 这会破坏 shared_ptr 并导致内存泄漏. 同样, 问题的起因与发现之处相距甚远. 很可能直到档案被加载之后问题才被发现. 现在我们不仅有一个难以发现和修复的程序缺陷, 还有一堆无效的档案和丢失的数据.

现在考虑显示消息时会发生什么:

  1. 程序立刻在 
    ar << x;
    处被拦截

  2. 程序员骂了一句 (又一个 %^&*&* 要跳的圈) . 他很着急 (谁不急呢) , 不愿意 const_cast——因为这看起来不好. 于是他做了以下改动就继续了. 
    Y y; 
const construct_from x(y); 
ar << x;

    一切正常, 他继续做别的事.

  3. 现在程序员(2)想做他的改动——又是一个恼人的 const 问题; 
    Y y; 
const construct_from x(y); 
... 
x.f(); // change x in some way ; compile error f() is not const 
... 
ar << x

    他有些恼火, 接着尝试以下做法:

    • 他考虑把 f() 设为 const——但大概会把 const 错误转移到别处. 他不想为了绕开序列化系统的一个怪癖而摆弄"他自己的"代码

    • 他从上面的 const 中移除了 const construct_from——该死, 现在他遇到了那个拦截. 如果他看看 BOOST_STATIC_ASSERT 出现处的注释代码, 他会做以下两件事之一

      1. 这简直是疯了. 它让我的人生平添不必要的困难, 还标记了本来没问题的代码. 所以我用一个 const_cast 修掉它, 并向邮件列表发一封抱怨信, 也许他们会修复. 在这种情形下, 故事就转到了前一个场景.

      2. 哦, 这个拦截提示默认序列化并不是我想要的. 当然, 在这个特定程序里这无关紧要. 但拦截处的代码无法真正评估其他模块中的代码 (那些代码甚至可能还没写) . 好吧, 我在 construct_from.hpp 中加入以下内容来解决这个问题. 
        BOOST_CLASS_TRACKING(construct_from, track_never)

  4. 现在程序员(3)来了, 做他的改动. 原始 (且遥远) 模块的行为保持不变, 因为 construct_from 特征已被设为"track_never", 所以他总是能得到副本, 日志也应当符合预期.

  5. 但现在他又遇到另一个拦截——试图通过指针保存一个被标记为"track_never"的类的对象. 于是他回到 construct_from.hpp, 把插入的 BOOST_CLASS_TRACKING 注释掉. 现在第二个拦截避免了, 但该死——第一个拦截又冒了出来. 最终, 经过一些代码重构, 序列化 construct_from 的不同需求得到了调和.
注意, 在第二种场景中
  • 所有错误都在编译期被拦截.
  • 不会创建无效的档案.
  • 不会丢失数据.
  • 不会发生运行期错误.
的确, 这些消息有时会标记当前正确的代码, 这可能让一些程序员恼火. 然而, 这个示例说明了我们的看法: 这些消息是有用的, 为避免特别棘手的编程错误, 这种恼火只是很小的代价.

pointer_level - 警告

此拦截针对通过指针序列化时的以下情形:
  • 某个类型不在档案中保存类信息. 也就是说, 序列化特征实现级别 <= object_serializable.
  • 此类型的跟踪被设为"track selectively". 在这种情形下, 对象是否被跟踪的指示不会存储在档案本身中——见 level == object_serializable. 由于类信息不保存在档案中, 程序中其他地方 ar << T * 操作的存在与否被用来推断该类型的对象是否应当被跟踪.

    当读取档案的程序包含 ar >> T * 操作 (以便跟踪信息被包含在档案中) , 而创建档案的程序没有包含 ar << T 时, 会出现问题. 此时会假定档案不包含跟踪信息, 档案将无法加载. 相反的情形也可能触发类似问题.

    尽管由于多种原因这种情况不太可能发生, 但它是可能的——因此有此警告.

因此, 如果你的程序在这里被拦截, 请考虑更改跟踪或实现级别特征——或者不通过指针序列化.

pointer_tracking - 警告

通过指针序列化被标记为"track_never"的类型的对象, 可能导致创建比保存时更多的对象! 在某些情况下用户可能确实想这样做, 所以我们把它留作警告.

const_loading - 错误

不能向"const"对象加载数据, 除非它是围绕某个其他非 const 对象的包装器.
