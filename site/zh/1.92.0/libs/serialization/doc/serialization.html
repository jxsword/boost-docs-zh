类型 T 是 可序列化 的, 当且仅当以下条件之一成立:
  • 它是一个原始类型.
    所谓 原始类型 , 我们指的是 C++ 内建类型, 而且 仅仅是 C++ 内建类型. 算术类型 (包括字符) 、bool、enum 是原始类型. 下文 序列化特征 中, 我们会出于不同目的以不同方式定义"primitive"实现级别. 这可能是混淆的来源.
  • 它是一个类类型, 并且已按下面详述的原型之一声明了以下内容:
    • 一个类成员函数 serialize
    • 一个全局函数 serialize
  • 它是一个指向 可序列化 类型的指针.
  • 它是一个对 可序列化 类型的引用.
  • 它是一个 可序列化 类型的原生 C++ 数组.

原始类型

上文所述档案类的模板运算符 &、<< 和 >> 会生成代码, 把所有原始类型保存到档案/从档案加载. 这些代码通常只是按照档案格式把数据加入档案. 例如, 一个四字节整数以 4 个二进制字节的形式追加到二进制档案, 而在文本档案中它会被渲染为一个空格后跟字符串表示.

类类型

对于类/结构体类型, 模板运算符 &、<< 和 >> 会生成调用程序员为该特定数据类型所写序列化代码的代码. 没有默认实现. 试图序列化一个未显式指定序列化的类/结构体会导致编译期错误. 类的序列化可以通过类成员函数指定, 也可以通过接受该类实例引用作为参数的自由函数指定.

成员函数

序列化库调用以下代码来向档案保存类实例或从档案加载类实例. 

template<class Archive, class T>
inline void serialize(
    Archive & ar, 
    T & t, 
    const unsigned int file_version
){
    // invoke member function for class T
    t.serialize(ar, file_version);
}
也就是说, 模板 serialize 的默认定义假定存在具有如下签名的类成员函数模板: 

template<class Archive>
void serialize(Archive &ar, const unsigned int version){
    ...
}
如果没有声明这样的成员函数, 就会出现编译期错误. 为了使该模板生成的成员函数能被调用来把数据追加到档案, 它要么必须是 public 的, 要么必须通过在类定义中包含: 

friend class boost::serialization::access;
来使该类对序列化库可访问. 后一种方法应当优先于把成员函数设为 public 的做法. 这可以防止从库外部调用序列化函数. 这几乎肯定是个错误. 遗憾的是, 它可能看起来正常工作, 却以一种极难发现的方式失败.

乍看之下可能不明显: 为什么这一个模板既能向档案保存数据、又能从档案加载数据. 关键在于 & 运算符对输出档案定义为 <<, 对输入档案定义为 >>. & 的"多态"行为使同一个模板既可用于保存操作, 也可用于加载操作. 这非常便利: 省去大量输入工作, 并保证类数据成员的保存与加载始终同步. 这是整个序列化系统的关键.

自由函数

当然, 我们并不限于使用上面描述的默认实现. 我们可以用自己的实现覆盖默认实现. 这样做使我们能够在不改动类定义本身的情况下实现类的序列化. 我们称之为 非侵入式 序列化. 假设我们的类名为 my_class, 重写应如下指定: 

// namespace selection

template<class Archive>
inline void serialize(
    Archive & ar, 
    my_class & t, 
    const unsigned int file_version
){
    ...
}
注意, 我们把这个重写称为"非侵入式". 这略微不够准确. 它不要求类具有特殊函数、派生自某个公共基类或做任何其他根本性的设计改动. 但是, 它需要能够访问要保存和加载的类成员. 如果这些成员是 private, 就无法序列化它们. 所以在某些情况下, 即使使用这种"非侵入式"方法, 也需要对被序列化的类做少量修改. 在实践中这也许不算什么问题, 因为许多库 (例如 STL) 暴露了足够的信息, 使得完全不需要改动库就能实现非侵入式序列化.

自由函数重写的命名空间

为获得最大可移植性, 应把所有自由函数模板和定义放在命名空间 boost::serialization 中. 如果可移植性不是考量因素, 且所用编译器支持 ADL (实参依赖查找) , 则自由函数和模板可以放在以下任一命名空间中:
  • boost::serialization
  • 档案类的命名空间
  • 被序列化类型的命名空间

注意, 乍看之下, 这条建议对于实现两阶段查找的编译器似乎是错的. 事实上, 即使对这类编译器, 序列化库也使用了一个或许过于聪明的方法来支持这条规则. 有兴趣深入研究的人可以在 serialization.hpp 中找到更多信息.

类成员的序列化

无论使用上述哪种方法, serialize 函数体都必须通过对类的所有数据成员依次应用档案 operator & 来指定要保存/加载的数据. 

{
    // save/load class member variables
    ar & member1;
    ar & member2;
}

基类

头文件 base_object.hpp 包含模板: 

template<class Base, class Derived>
Base & base_object(Derived &d);
应当使用它来创建对基类对象的引用, 该引用可用作档案序列化运算符的实参. 因此对于 可序列化 类型 T 的类, 基类状态应当这样序列化: 

{
    // invoke serialization of the base class 
    ar & boost::serialization::base_object<base_class_of_T>(*this);
    // save/load class member variables
    ar & member1;
    ar & member2;
}
请抵制直接把 *this 转换为基类的诱惑. 这看似可行, 但可能无法调用正确序列化所需的代码.

注意, 这 不等于 调用基类的 serialize 函数. 这看似可行, 但会绕过用于对象跟踪、注册基类-派生类关系以及序列化系统按设计运作所需的其他簿记的特定代码. 因此, 所有 serialize 成员函数都应当 private.

const 成员

把 const 成员保存到档案不需要特别考虑. 加载 const 成员可以通过使用 const_cast 来解决: 

    ar & const_cast<T &>(t);
注意, 这违背了 const 关键字的精神与意图. const 成员在类实例构造时初始化且此后不再改变. 不过, 在许多情况下这可能是最合适的做法. 归根结底, 这归结为在序列化上下文中 const 意味着什么的问题.

模板

模板的序列化实现与普通类完全相同, 不需要额外考虑. 其中之一是: 如果组件模板的序列化已定义, 模板组合的序列化会在需要时自动生成. 例如, 本库包含 boost::shared_ptr<T> 和 std::list<T> 的序列化定义. 如果我已经为自己的类 my_t 定义了序列化, 那么 std::list< boost::shared_ptr< my_t> > 的序列化就已经可以使用了.

有关如何为自己的类模板实现这一想法的示例, 参见 demo_auto_ptr.cpp . 它展示了如何实现标准库模板 auto_ptr 的非侵入式序列化.

在示例 shared_ptr.hpp 中可以找到为标准模板添加序列化的一个更棘手的例子

在为模板规定序列化时, 通常把 serialize 拆分为 load/save 对. 注意, 前文 所述的便捷宏在这些情况下没有帮助, 因为模板类实参的数量和种类与拆分简单类的 serialize 时所用不相同. 此时应改用重写语法.

版本控制

最终会出现这样的情况: 档案创建之后类定义发生了变化. 保存类实例时, 当前版本会包含在存储于档案中的类信息里. 从档案加载类实例时, 原始版本号作为实参传给加载函数. 这使加载函数可以包含适配该类旧定义并把它们与最新版本协调起来的逻辑. save 函数总是保存当前版本. 因此这会自动把旧格式档案转换为最新版本. 版本号对每个类独立维护. 这形成了一个简单的系统, 可用于访问旧文件并对其进行转换. 类的当前版本作为 类序列化特征 指定, 本手册后文有描述. 

{
    // invoke serialization of the base class 
    ar & boost::serialization::base_object<base_class_of_T>(*this);
    // save/load class member variables
    ar & member1;
    ar & member2;
    // if its a recent version of the class
    if(1 < file_version)
        // save load recently added class members
        ar & member3;
}

把 serialize 拆分为 Save/Load

有时对 save 和 load 函数使用同一个模板并不方便. 例如, 当版本控制变得复杂时可能出现这种情况.

拆分成员函数

对成员函数而言, 可以通过包含头文件 boost/serialization/split_member.hpp 并在类中包含如下代码来解决: 

template<class Archive>
void save(Archive & ar, const unsigned int version) const
{
    // invoke serialization of the base class 
    ar << boost::serialization::base_object<const base_class_of_T>(*this);
    ar << member1;
    ar << member2;
    ar << member3;
}

template<class Archive>
void load(Archive & ar, const unsigned int version)
{
    // invoke serialization of the base class 
    ar >> boost::serialization::base_object<base_class_of_T>(*this);
    ar >> member1;
    ar >> member2;
    if(version > 0)
        ar >> member3;
}

template<class Archive>
void serialize(
    Archive & ar,
    const unsigned int file_version 
){
    boost::serialization::split_member(ar, *this, file_version);
}
这会把序列化拆分为两个独立的函数 save 和 load. 由于新的 serialize 模板总是相同的, 可以通过调用头文件 boost/serialization/split_member.hpp 中定义的宏 BOOST_SERIALIZATION_SPLIT_MEMBER() 来生成它. 因此上面的整个 serialize 函数可以替换为: 

BOOST_SERIALIZATION_SPLIT_MEMBER()

拆分自由函数

对于使用自由 serialize 函数模板的非侵入式序列化, 情况相同. 要使用 save 和 load 函数模板而非 serialize: 

namespace boost { namespace serialization {
template<class Archive>
void save(Archive & ar, const my_class & t, unsigned int version)
{
    ...
}
template<class Archive>
void load(Archive & ar, my_class & t, unsigned int version)
{
    ...
}
}}
包含头文件 boost/serialization/split_free.hpp , 并重写自由 serialize 函数模板: 

namespace boost { namespace serialization {
template<class Archive>
inline void serialize(
    Archive & ar,
    my_class & t,
    const unsigned int file_version
){
    split_free(ar, t, file_version); 
}
}}
为减少输入, 上面的模板可以用宏替换: 

BOOST_SERIALIZATION_SPLIT_FREE(my_class)
注意, 尽管提供了把 serialize 函数拆分为 save/load 的功能, 仍然优先推荐把 serialize 函数与相应的 & 运算符一起使用. 序列化实现的关键在于对象按完全相同的顺序保存和加载. 使用 & 运算符和 serialize 函数保证了这一点始终成立, 并将把与 save 和 load 函数同步相关的难以发现的错误的发生率降到最低.

另请注意, BOOST_SERIALIZATION_SPLIT_FREE 必须在任何命名空间之外使用.

指针

指向任何类实例的指针都可以用任何档案 save/load 运算符序列化.

要通过指针正确保存和恢复对象, 必须处理以下情形:

  1. 如果同一对象通过不同指针被保存多次, 只需保存该对象的一个副本.
  2. 如果同一对象通过不同指针被加载多次, 只应创建一个新对象, 所有返回的指针都应指向它.
  3. 系统必须检测到这种情况: 对象先通过指针保存, 随后对象本身又被保存. 若不采取额外防范措施, 加载时会导致原始对象被创建多个副本. 本系统在保存时检测这种情况并抛出异常——见下文.
  4. 派生类的对象可以通过指向基类的指针存储. 必须确定并保存对象的真实类型. 恢复时必须创建正确的类型, 并把其地址正确转换为基类. 也就是说, 必须考虑多态指针.
  5. 保存时必须检测 NULL 指针, 反序列化时恢复为 NULL.
本序列化库处理了上述所有考量. 通过指针保存和加载对象的过程并不简单. 可以概括如下:

保存一个指针:

  1. 确定被指向对象的真实类型.
  2. 向档案写入一个特殊标签
  3. 如果被指向的对象尚未写入档案, 现在写入
加载一个指针:
  1. 从档案读取一个标签.
  2. 确定要创建的对象类型
  3. 如果对象已经加载, 返回其地址.
  4. 否则, 创建对象的一个新实例
  5. 使用上述运算符把数据读回
  6. 返回新建对象的地址.
鉴于类实例只向档案保存/从档案加载一次, 无论它们用 << 和 >> 运算符序列化多少次
  • 多次加载同一个指针对象只会创建一个对象, 从而复现原有的指针配置.
  • 诸如多态指针集合之类的结构无需本库使用者付出特别的努力即可处理.
通过指向基类的指针序列化派生类型的指针可能需要一点额外的"帮助". 此外, 程序员可能出于自己的原因想修改上述过程. 例如, 可能希望抑制对象跟踪, 因为事先知道相关应用程序绝不会创建重复对象. 指针的序列化可以通过指定 类序列化特征 来"微调", 如 本手册的另一节 所述

非默认构造函数

指针的序列化在库中用类似下面的代码实现: 

// load data required for construction and invoke constructor in place
template<class Archive, class T>
inline void load_construct_data(
    Archive & ar, T * t, const unsigned int file_version
){
    // default just uses the default constructor to initialize
    // previously allocated memory. 
    ::new(t)T();
}
默认的 load_construct_data 会"就地"调用默认构造函数来初始化内存.

如果没有这样的默认构造函数, 则必须重写函数模板 load_construct_data, 可能还有 save_construct_data. 下面是一个简单示例: 


class my_class {
private:
    friend class boost::serialization::access;
    const int m_attribute;  // some immutable aspect of the instance
    int m_state;            // mutable state of this instance
    template<class Archive>
    void serialize(Archive &ar, const unsigned int file_version){
        ar & m_state;
    }
public:
    // no default construct guarantees that no invalid object
    // ever exists
    my_class(int attribute) :
        m_attribute(attribute),
        m_state(0)
    {}
};
重写应为: 

namespace boost { namespace serialization {
template<class Archive>
inline void save_construct_data(
    Archive & ar, const my_class * t, const unsigned int file_version
){
    // save data required to construct instance
    ar << t->m_attribute;
}

template<class Archive>
inline void load_construct_data(
    Archive & ar, my_class * t, const unsigned int file_version
){
    // retrieve data from archive required to construct new instance
    int attribute;
    ar >> attribute;
    // invoke inplace constructor to initialize instance of my_class
    ::new(t)my_class(attribute);
}
}} // namespace ...
除了指针的反序列化之外, 这些重写还用于元素类型没有默认构造函数的 STL 容器的反序列化.

指向派生类对象的指针

注册

考虑以下情形: 

class base {
    ...
};
class derived_one : public base {
    ...
};
class derived_two : public base {
    ...
};
int main(){
    ...
    base *b;
    ...
    ar & b; 
}
保存 b 时应当保存哪种对象? 加载 b 时应当创建哪种对象? 应当是类 derived_one、derived_two, 还是 base 的对象?

事实证明, 序列化的对象类型取决于基类 (此处是 base) 是否多态. 如果 base 不是多态的, 即它没有虚函数, 那么将序列化 base 类型的对象. 任何派生类中的信息都会丢失. 如果这正是所期望的 (通常不是) , 则无需其他工作.

如果基类是多态的, 将序列化最派生类型 (此处是 derived_one 或 derived_two) 的对象. 序列化哪种类型的对象这个问题 (几乎) 由库自动处理.

系统在该类的对象第一次被序列化时在档案中"注册"该类, 并为其分配一个顺序号. 下次在同一档案中序列化该类的对象时, 档案中写入的就是这个号. 这样, 每个类在档案内都被唯一标识. 当档案被读回时, 每个新的顺序号都与正在读取的类重新关联. 注意, 这意味着"注册"必须在保存和加载时都发生, 使加载时构建的类-整数表与保存时构建的完全一致. 事实上, 整个序列化系统的关键在于一切总是按相同顺序保存和加载. "注册"也包括在内.

扩展我们先前的示例: 


int main(){
    derived_one d1;
    derived_two d2:
    ...
    ar & d1;
    ar & d2;
    // A side effect of serialization of objects d1 and d2 is that
    // the classes derived_one and derived_two become known to the archive.
    // So subsequent serialization of those classes by base pointer works
    // without any special considerations.
    base *b;
    ...
    ar & b; 
}
读取 b 时, 它前面有一个唯一的 (对档案而言) 类标识符, 该标识符先前已与类 derived_one 或 derived_two 关联.

如果派生类没有像上文所述那样被自动"注册", 调用序列化时会抛出 unregistered_class 异常.

这可以通过显式注册派生类来解决. 所有档案都派生自一个实现了以下模板的基类: 


template<class T>
register_type(T * = NULL);
因此我们的问题同样可以这样解决: 

int main(){
    ...
    ar.template register_type<derived_one>();
    ar.template register_type<derived_two>();
    base *b;
    ...
    ar & b; 
}
注意, 如果序列化函数在 save 和 load 之间拆分, 两个函数都必须包含注册. 这是保持 save 与对应 load 同步所必需的.

导出

上面的做法可行, 但可能不方便. 在编写通过基类指针序列化的代码时, 我们并不总是知道要序列化哪些派生类. 每编写一个新的派生类, 我们都不得不回到所有序列化基类的地方并更新代码.

所以我们还有另一种方法: 


#include <boost/serialization/export.hpp>
...
BOOST_CLASS_EXPORT_GUID(derived_one, "derived_one")
BOOST_CLASS_EXPORT_GUID(derived_two, "derived_two")

int main(){
    ...
    base *b;
    ...
    ar & b; 
}
宏 BOOST_CLASS_EXPORT_GUID 把字符串字面量与类关联. 在上例中我们使用了类名的字符串形式. 如果这样一个"导出"类的对象通过指针序列化且未以其他方式注册, "导出"字符串就会被包含进档案. 之后读取档案时, 序列化库用该字符串字面量查找应当创建的类. 这使得每个类可以连同其字符串标识符一起放在单独的头文件中. 无需维护可能被序列化的派生类的单独"预注册". 这种注册方式称为"键导出". 有关此主题的更多信息见类特征一节的 导出键 .

实例化

通过上述任一方法进行的注册还实现了另一个作用, 其重要性可能不明显. 本系统依赖于形如 template<class Archive, class T> 的模板化函数. 这意味着对于程序中序列化的每种档案与数据类型的组合, 都必须实例化序列化代码.

派生类的多态指针可能永远不会被程序显式引用, 因此正常情况下序列化这些类的代码永远不会被实例化. 因此, 除了在档案中包含导出键字符串之外, BOOST_CLASS_EXPORT_GUID 还会为程序使用的所有档案类显式实例化类序列化代码.

选择性跟踪

对象是否被跟踪由其 对象跟踪特征 决定. 用户定义类型的默认设置是 track_selectively. 也就是说, 当且仅当对象在程序中任何地方通过指针序列化时才跟踪它. 通过上述任何方式"注册"的任何对象都被假定在程序中某处通过指针序列化, 因此会被跟踪. 在某些情况下这可能导致低效. 假设我们有一个被多个程序使用的类模块. 由于某些程序会序列化指向该类对象的多态指针, 我们通过 导出 一个类标识符——在类头文件中指定 BOOST_CLASS_EXPORT. 当另一个程序包含该模块时, 该类的对象总会被跟踪, 即使可能没有必要. 这种情况可以通过在这些程序中使用 track_never 来解决.

也可能出现这种情况: 即使程序通过指针序列化, 我们更关心效率而不是避免创建重复对象的可能性. 可能我们恰好知道不会有重复. 也可能创建少量重复是无害的、不值得为跟踪重复付出运行期代价. 同样, 可以使用 track_never.

运行期转换

为了在运行期正确地在基类指针与派生类指针之间转换, 系统要求每个基类/派生类对都能在表中找到. 用 boost::serialization::base_object<Base>(Derived &) 序列化基类对象的一个副作用是: 确保在进入 main 函数之前把基类/派生类对加入表中. 这非常方便, 并带来干净的语法. 唯一的问题是可能出现这种情况: 通过指针序列化的派生类无需调用其基类的序列化. 在这种情况下有两个选择. 显而易见的一个是用 base_object 调用基类序列化, 并为基类序列化指定空函数. 另一种选择是通过调用模板 void_cast_register<Derived, Base>(); 显式"注册"基类/派生类关系. 注意, 这里"register"一词的用法与上一节中的用法无关. 下面是一个示例: 

#include <sstream>
#include <boost/serialization/serialization.hpp>
#include <boost/archive/text_iarchive.hpp>
#include <boost/serialization/export.hpp>

class base {
    friend class boost::serialization::access;
    //...
    // only required when using method 1 below
    // no real serialization required - specify a vestigial one
    template<class Archive>
    void serialize(Archive & ar, const unsigned int file_version){}
};

class derived : public base {
    friend class boost::serialization::access;
    template<class Archive>
    void serialize(Archive & ar, const unsigned int file_version){
        // method 1 : invoke base class serialization
        ar & boost::serialization::base_object<base>(*this);
        // method 2 : explicitly register base/derived relationship
        boost::serialization::void_cast_register<derived, base>(
            static_cast<derived *>(NULL),
            static_cast<base *>(NULL)
        )
    }
};

BOOST_CLASS_EXPORT_GUID(derived, "derived")

int main(){
    //...
    std::stringstream ss;
    boost::archive::text_iarchive ar(ss);
    base *b;
    ar >> b; 
}

为了使这个模板能在不合标准编译器编译的代码中被调用, 可以使用以下语法: 


boost::serialization::void_cast_register(
    static_cast<Derived *>(NULL),
    static_cast<Base *>(NULL)
);
更多信息参见 模板调用语法

参考文献

包含引用成员的类通常需要非默认构造函数, 因为引用只能在实例构造时设置. 如果类有引用成员, 上一节的例子会稍微复杂一些. 这引出了被引用对象存储在哪里、如何存储以及如何创建的问题. 还有对多态基类的引用的问题. 基本上, 这些与指针引发的问题相同. 这并不奇怪, 因为引用实际上是一种特殊的指针. 我们通过把引用当作指针一样序列化来解决这些问题. 

class object;
class my_class {
private:
    friend class boost::serialization::access;
    int member1;
    object & member2;
    template<class Archive>
    void serialize(Archive &ar, const unsigned int file_version);
public:
    my_class(int m, object & o) :
        member1(m), 
        member2(o)
    {}
};
重写应为: 

namespace boost { namespace serialization {
template<class Archive>
inline void save_construct_data(
    Archive & ar, const my_class * t, const unsigned int file_version
){
    // save data required to construct instance
    ar << t.member1;
    // serialize reference to object as a pointer
    ar << & t.member2;
}

template<class Archive>
inline void load_construct_data(
    Archive & ar, my_class * t, const unsigned int file_version
){
    // retrieve data from archive required to construct new instance
    int m;
    ar >> m;
    // create and load data through pointer to object
    // tracking handles issues of duplicates.
    object * optr;
    ar >> optr;
    // invoke inplace constructor to initialize instance of my_class
    ::new(t)my_class(m, *optr);
}
}} // namespace ...

数组

如果 T 是可序列化类型, 那么任何类型为 T 的原生 C++ 数组都是可序列化类型. 也就是说, 如果 T 是可序列化类型, 那么以下内容自动可用并按预期工作: 

T t[4];
ar << t;
    ...
ar >> t;
