引言

与执行 I/O 操作的任何其他 C++ 程序一样, 无法保证使用 Boost.Filesystem 的程序在操作系统之间是可移植的. I/O 的关键方面, 例如操作系统如何解释路径, C 和 C++ 标准均未作出规定.

无法得知一个文件或目录名对未知的操作系统是否有效 (因而是可移植的). 总有可能某个操作系统会使用不寻常的名称 (例如小于 4096 的数字), 或长度非常受限的名称 (例如名称最长 6 个字符). 换句话说, 可移植性从来不是绝对的; 它总是相对于特定的操作系统或文件系统而言.

然而, 可以预先得知一个目录或文件名对特定操作系统是否可能有效. 也可以构造出很可能可移植到大量现代与遗留操作系统的名称.

几乎所有现代操作系统都支持多种文件系统. 至少, 它们支持一个原生文件系统加上一个 CD-ROM 文件系统 (通常为 ISO-9669, 常带 Joliet 扩展).

每种文件系统都可能有自己的命名规则. 例如, 现代 Windows 版本支持 NTFS、FAT、FAT32 和 ISO-9660 等文件系统, 而这些文件系统的命名规则各不相同. 每种文件系统对整体路径有效性也可能有不同的规则, 例如最大长度或子目录数量. 某些遗留系统对目录名与普通文件名有不同的规则.

因此, Boost.Filesystem 的 name_check 函数无法保证目录与文件名的可移植性. 它们的意图是通过及早发现常见的命名问题, 给程序员一个争取可移植性的“机会”.

name_check 函数

name_check 函数在其参数对特定操作系统或文件系统而言可作为目录名与普通文件名时返回 true. 库提供了若干这样的函数.

portable_name 函数尤其值得关注, 因为它经过精心设计, 既提供广泛的可移植性, 又不过度限制表达能力.

库提供的 name_check 函数
函数 说明
portable_posix_name(const std::string& name) 返回: true, 若 !name.empty() && name 仅包含 Portable Filename Character Set (由 POSIX 定义, 参见 www.opengroup.org/onlinepubs/007904975/basedefs/xbd_chap03.html) 规则所规定的字符.
允许的字符为 0-9、a-z、A-Z、'.'、'_' 以及 '-'.

用途: 必须可移植到任何 POSIX 系统的应用程序.
windows_name(const std::string& name) 返回: true, 若 !name.empty() && name 仅包含 Windows 平台 SDK 规定为有效 (无论文件系统为何) 的字符, && (name 为 "." 或 "..", 或者不以结尾空格或句点结束). 允许的字符为除 0x0-0x1F、'<'、'>'、':'、'"'、'/'、'\' 以及 '|' 之外的任何字符.

用途: 必须可移植到 Windows 的应用程序.

注意: 保留设备名作为文件名是无效的, 但不会被检测出来, 因为它们作为路径仍然有效. 具体而言, CON、PRN、AUX、CLOCK$、NUL、COM[1-9]、LPT[1-9], 以及这些名称后跟扩展名的形式 (例如 NUL.tx7).
portable_name(const std::string& name) 返回:  windows_name(name) && portable_posix_name(name) && (name 为 "." 或 "..", 且首字符不是句点或连字符).

用途: 必须可移植到各种现代操作系统 (无论大小) 以及部分遗留操作系统的应用程序. 首字符不得为句点或连字符的限制, 是若干较老操作系统的要求.
portable_directory_name(const std::string& name) 返回: portable_name(name) && (name 为 "." 或 "..", 或不包含句点).

用途: 必须可移植到包括 OpenVMS 在内的多种平台的应用程序.
portable_file_name(const std::string& name) 返回: portable_name(name) && 每个句点后面都跟一至三个附加的非句点字符.

用途: 必须可移植到多种平台的应用程序, 包括 OpenVMS 及其他具有“文件扩展名”概念但限制其长度的系统.
native(const std::string& name) 返回: 由实现定义. 对操作系统的原生文件系统认为有效的名称返回 true.

注意: 对于操作系统在所有条件下都不视为有效的某些名称, 也可能返回 true (尤其发生在支持多种文件系统的操作系统上).

文件与目录命名建议

建议 理由
将文件与目录名的字符限制为 A-Z、a-z、0-9、句点、连字符与下划线.

使用任意一个“portable_”开头的名称检查函数来执行这条建议.

 这些是 POSIX 标准为可移植目录名与文件名规定的字符, 对 Windows、Mac 以及许多其他现代文件系统同样有效.
不要用句点或连字符作为名称的首字符. 不要用句点作为名称的末字符.

使用 portable_name、portable_directory_name 或 portable_file_name 来执行这条建议.

 有些操作系统对名称的首字符有特殊规则, 例如 POSIX. Windows 不允许句点作为末字符.
不要在目录名中使用句点.

使用 portable_directory_name 来执行这条建议.

 不带 Juliet 扩展的 ISO-9660、OpenVMS 文件系统及其他遗留系统的要求.
文件名中不要使用多于一个句点, 并将句点之后的部分限制为三个字符.

使用 portable_file_name 来执行这条建议.

 ISO-9660 第 1 级、OpenVMS 文件系统及其他遗留系统的要求.
不要假定名称区分大小写. 例如, 不要指望一个目录能同时容纳名为“Foo”和“foo”的两个不同元素. 有些文件系统不区分大小写. 例如, Windows NTFS 存储名称时保留大小写, 但搜索名称时不区分大小写 (除非运行在 POSIX 子系统下, 那种情况下会区分大小写搜索).
不要假定名称不区分大小写. 例如, 不要指望以名称“Foo”创建的文件能够以名称“foo”成功打开. 有些文件系统区分大小写, 例如 POSIX.
不要在名称中使用连字符. ISO-9660 第 1 级, 以及可能还有某些遗留系统, 不允许连字符.
将 path::string() 返回的字符串长度限制为 255 个字符. 注意, ISO 9660 有明确的目录树深度限制 8, 尽管该深度限制被 Juliet 扩展取消. 有些操作系统对路径总长度有限制. 例如, Windows 2000 将路径限制为总长 260 个字符.
限制路径中任一名称的长度. 根据你希望可移植到的操作系统和/或文件系统选定具体限制:
无需关注: POSIX、Windows、MAC OS X.
31 个字符: Classic Mac OS
8 个字符 + 句点 + 3 个字符: ISO 9660 第 1 级
32 个字符: ISO 9660 第 2、3 级
128 个字符 (Unicode 时为 64): 带 Juliet 扩展的 ISO 9660		 限制名称长度会明显降低文件名的表达能力, 然而只设置很高的长度上限又会妨碍最广泛的可移植性.
