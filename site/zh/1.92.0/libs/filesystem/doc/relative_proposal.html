引言

对 Filesystem 库相对路径函数的请求至少已有十年之久.

所请求的功能看似简单——给定两个具有公共前缀的路径, 返回其中一个路径的非公共后缀部分, 使其相对于另一个路径.

就 Filesystem 库而言,

path p("/a/b/c");
path base("/a/b");
path rel = relative(p, base);  // the requested function
cout << rel << endl;           // outputs "c"
assert(absolute(rel, base) == p);

如果事情仅此而已, Filesystem 库多年前就该有 relative 函数了.

阻碍性问题: 相互冲突的要求、符号链接、目录占位符 (dot、dot-dot)、用户期望、边界情形.

致谢

Jamie Allsop 的论文 Additions to Filesystem supporting Relative Paths 打破了我的思维僵局. 下面的许多内容直接基于 Jamie 的分析与提案. weakly_canonical 函数与语义规范的若干方面是我的贡献. 错误当然归我.

初步实现

初步实现可在 Boost Filesystem Git 仓库的 feature/relative2 分支获得. 参见 github.com/boostorg/filesystem/tree/feature/relative2

要求

要求 1: 某些用途要求跟随符号链接, 即必须在实际文件系统中解析路径.

要求 2: 某些用途要求不跟随符号链接, 即不得在实际文件系统中解析路径.

要求 3: 某些用途要求移除冗余的当前目录 (dot) 或父目录 (dot-dot) 占位符.

要求 4: 某些用途不需要移除冗余的当前目录 (dot) 或父目录 (dot-dot) 占位符, 因为已知路径已处于普通形式.

问题

问题 1: 如果 p 与 base 本身是相对路径会怎样?

问题 2: 如果没有公共前缀会怎样? 这是错误, 还是整个 p 相对于 base, 还是别的什么?

问题 3: 如果 p、base 或两者都为空会怎样?

问题 4: 如果 p 与 base 相同会怎样?

问题 5: “公共前缀”如何确定?

问题 6: 如果 p 或 base 的部分存在但整个路径不存在, 而又需要跟随符号链接, 会怎样?

问题 7: 当路径中已存在部分的符号链接受到路径后面不存在部分中的目录 (dot-dot) 占位符影响时, 会怎样?

问题 8: 初步设计中过于复杂的语义 (因而规范也是如此) 使得对用例的推理变得困难.

问题 9: 某些用途从不会有冗余的当前目录 (dot) 或父目录 (dot-dot) 占位符, 因此移除操作将是不必要的开销, 虽然除此之外无害.

设计决策

分别提供词法与操作的 relative 函数

解决了要求 1与要求 2之间的冲突, 并确保两个要求都得到满足.

处理实际不存在的目录层级的用户需要纯词法函数.

处理实际存在的目录层级的用户需要查询当前文件系统以确认存在性并跟随符号链接的操作函数.

分别提供词法与操作的 proximate 函数

虽然不是唯一的可能, 但当相对路径函数找不到相对路径时, 一个可能的回退做法是返回被相对化的路径. 作为一种便利, proximate 函数正是这样做的.

把词法函数添加为 path 成员函数

Filesystem 库的不同寻常之处在于, 它有几个函数同时具有词法 (即廉价) 与操作 (即因文件系统访问而昂贵) 两种形式, 且语义不同. 用户选择满足其应用特定需求的形式非常重要. 本库一贯通过约定来区分: 词法函数是类 path 的成员, 而操作函数是非成员函数. 这里提议的词法函数还使用名称前缀 lexically_ 来强化这种区分.

相反的论证参见 Sutter 和 Alexandrescu 的 C++ Coding Standards 第 44 条: “优先编写非成员非友元函数”, 以及 Meyers 的 Effective C++ Third Edition 第 23 条: “优先使用非成员非友元函数而不是成员函数. ”

提供 一个非成员函数 lexically_normal, 返回普通形式路径

使得能够以与问题 9一致的方式解决要求 3与要求 4. 对解决问题 8有所贡献.

“规范化”是移除冗余的当前目录 (dot)、父目录 (dot-dot) 与目录分隔符元素的过程.

规范化是当前 canonical 函数的副产品. 但对于提议的 weakly_canonical 函数返回的路径, 只有前导的规范部分处于规范形式. 因此返回路径的任何结尾部分都未经过规范化.

Jamie Allsop 提议添加一个返回路径的独立规范化函数, 我同意他的看法.

Boost.filesystem 有一个已弃用的、修改路径的非 const 规范化函数, 但我同意 Jamie 的看法: 返回路径的函数是更好的解决方案.

提供 一个 weakly_canonical 操作函数

解决了问题 6、问题 7、问题 9, 并对解决问题 8有所贡献.

操作函数 weakly_canonical(p) 返回一个由 canonical(x)/y 组成的路径, 其中 x 是由 p 中存在的最长前导元素序列组成的路径, 而 y 是由 p 其余的结尾不存在元素 (如有) 组成的路径. “weakly”指的是与现有 canonical 函数相比放宽的存在性要求.

  • 把 weakly_canonical 作为独立函数, 然后把操作 relative 参数的处理规定为对 weakly_canonical 的调用, 这使得规定操作函数 relative 并对其进行推理容易得多. 对操作 relative 语义进行推理的困难 (在 weakly_canonical 出现之前) 正是导致其最初开发的原因.
  • 把 weakly_canonical 作为独立函数也使其可在其他上下文中使用.
  • 规定返回值处于普通形式是一项工程权衡, 目的是以一种对大多数用例“直接可用”的方式解决问题 7.
  • 规定以规范性建议的方式不执行不必要的规范化, 是对问题 9的合理解决.

以对用户“直接可用”的方式解决问题

解决了问题 1、2、3、4、6 和 7. 对解决 issue 8 有所贡献.

“直接可用”的方法由 Jamie Allsop 建议. 其实现方式是: 为所有“如果...会怎样?”边界情形问题规定合理的返回值, 而不是把它们当作需要异常或错误码的硬错误.

规定 lexically relative 为基于 std::mismatch

解决了 issue 5. 对解决 issue 8 有所贡献.

规定 操作函数 relative 为基于 weakly_canonical

对解决 issue 8 有所贡献.

  • 覆盖广泛的用例, 因为单一函数即可适用于存在、不存在及部分存在的路径.
  • 对包含符号链接的部分存在的路径正确工作.

规定 操作函数 relative 为基于 lexically relative

对解决 issue 5 和 issue 8 有所贡献.

如果两个函数语义不同, 会使用户困惑, 也难以正确规定:

  • 当一个或两个路径为空时.
  • 当两个路径的所有元素完全匹配时.
  • 因为使用了不同的匹配算法.
  • 因为虽然使用了相同的匹配算法, 但应用方式不同.

通过在预备调用操作函数之后, 把操作函数 relative 规定为基于词法 relative, 可以避免这些问题.

建议措辞

下文的“概览:”部分是非规范性的尝试, 旨在让规范性的参考规范更易于理解.

定义 normal form

路径处于 普通形式, 如果它没有冗余的当前目录 (dot) 或父目录 (dot-dot) 元素. 空路径的普通形式是空路径. 对以一个非根目录的 directory-separator 结尾的路径, 其普通形式是在原路径后追加一个当前目录 (dot) 元素.

上句对类 POSIX 或类 Windows 的操作系统并非必需, 但支持像 OpenVMS 这样对目录名与普通文件名使用不同语法的系统.

新的类 path 成员函数

概要

path lexically_normal() const;
path lexically_relative(const path& base) const;
path lexically_proximate(const path& base) const;

规定

path lexically_normal() const;

概览: 返回 *this, 其中移除了冗余的当前目录 (dot)、父目录 (dot-dot) 和 directory-separator 元素.

返回: *this, 处于普通形式.

备注: 使用 operator/= 来组合返回的路径.

[示例:

assert(path("foo/./bar/..").lexically_normal() == "foo");
assert(path("foo/.///bar/../").lexically_normal() == "foo/.");

以上断言将会成功. 在 Windows 上, 返回路径的 directory-separator 字符将是反斜杠而非斜杠, 但这不影响 path 相等性. —示例结束]

path lexically_relative(const path& base) const;

概览: 返回 *this 相对于 base 的形式. 把空路径或相同路径视为边界情形而非错误. 不解析符号链接. 不预先规范化 *this 或 base.

备注: 使用 std::mismatch(begin(), end(), base.begin(), base.end()) 来确定 *this 与 base 的第一个不匹配元素. 使用 operator== 来判断元素是否匹配.

返回:

  • path(), 如果 *this 的第一个不匹配元素等于 begin(), 或 base 的第一个不匹配元素等于 base.begin(), 或
  • path("."), 如果 *this 的第一个不匹配元素等于 end() 且 base 的第一个不匹配元素等于 base.end(), 或
  • 类 path 的一个对象, 通过将 operator/= path("..") 应用于半开区间 [base 的第一个不匹配元素, base.end()) 中的每个元素而组合成, 然后再将 operator/= 应用于半开区间 [*this 的第一个不匹配元素, end()) 中的每个元素.

[示例:

assert(path("/a/d").lexically_relative("/a/b/c") == "../../d");
assert(path("/a/b/c").lexically_relative("/a/d") == "../b/c");
assert(path("a/b/c").lexically_relative("a") == "b/c");
assert(path("a/b/c").lexically_relative("a/b/c/x/y") == "../..");
assert(path("a/b/c").lexically_relative("a/b/c") == ".");
assert(path("a/b").lexically_relative("c/d") == "");

以上断言将会成功. 在 Windows 上, 返回路径的 directory-separator 将是反斜杠而非正斜杠, 但这不影响 path 相等性. —示例结束]

[注: 如果需要跟随符号链接的语义, 请使用操作函数 relative —注结束]

[注: 如果需要规范化以确保元素的一致匹配, 请应用 lexically_normal() 于 *this、base 或两者. —注结束]

path lexically_proximate(const path& base) const;

返回: 如果 lexically_relative(base) 的值不是空路径, 则返回它. 否则返回 *this.

[注: 如果需要跟随符号链接的语义, 请使用操作函数 proximate —注结束]

[注: 如果需要规范化以确保元素的一致匹配, 请应用 lexically_normal() 于 *this、base 或两者. —注结束]

新的 操作函数

概要

path weakly_canonical(const path& p);
path weakly_canonical(const path& p, system::error_code& ec);
path relative(const path& p, system::error_code& ec);
path relative(const path& p, const path& base=current_path());
path relative(const path& p, const path& base, system::error_code& ec);
path proximate(const path& p, system::error_code& ec);
path proximate(const path& p, const path& base=current_path());
path proximate(const path& p, const path& base, system::error_code& ec);

规定

path weakly_canonical(const path& p);
path weakly_canonical(const path& p, system::error_code& ec);
概览: 返回 p, 其中符号链接已解析且结果已规范化.

返回: 一个路径, 其组成为: 对一个路径调用 canonical 函数的结果; 该路径由 p 中存在的前导元素 (如有) 以及 p 中不存在的后续元素 (如有) 组成.

后置条件: 返回的路径处于普通形式.

备注: 使用 operator/= 组合返回的路径. 使用 status 函数判断存在性.

备注: 鼓励实现避免不必要的规范化, 例如当 canonical 已被调用于 p 的整体时.

抛出: 按“错误报告 (Error reporting)”中的规定.

path relative(const path& p, system::error_code& ec);

返回: relative(p, current_path(), ec).

抛出: 按“错误报告 (Error reporting)”中的规定.

path relative(const path& p, const path& base=current_path());
path relative(const path& p, const path& base, system::error_code& ec);

概览: 返回 p 相对于 base 的形式. 把空路径或相同路径视为边界情形而非错误. 在其他处理之前解析符号链接并对 p 与 base 都进行规范化.

返回: weakly_canonical(p).lexically_relative(weakly_canonical(base)). 第二种形式在发生错误时返回 path().

抛出: 按“错误报告 (Error reporting)”中的规定.

path proximate(const path& p, system::error_code& ec);

返回: proximate(p, current_path(), ec).

抛出: 按“错误报告 (Error reporting)”中的规定.

path proximate(const path& p, const path& base=current_path());
path proximate(const path& p, const path& base, system::error_code& ec);

返回: weakly_canonical(p).lexically_proximate(weakly_canonical(base)). 第二种形式在发生错误时返回 path().

抛出: 按“错误报告 (Error reporting)”中的规定.
