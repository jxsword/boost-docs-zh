常见问题

一般问题

为什么不支持特定种类文件系统的概念, 例如 posix_file_system 或 windows_file_system.

可移植性是该库最重要的要求之一. 特定操作系统或文件系统专有的特性, 始终可以通过该操作系统的 API 来访问.

类 path 相关问题

为什么通用路径名格式要以 POSIX 为基础?

POSIX 是一项 ISO 标准. 它是最为人们熟悉的路径名格式的基础, 不仅适用于基于 POSIX 的操作系统, 也适用于 Windows 以及 URI 的 URL 部分. 它无处不在且为人熟知. 在许多系统上实现起来非常容易, 因为它要么就是操作系统原生的格式 (Unix 和 Windows), 要么可以通过操作系统提供的 POSIX 库来支持 (z/OS、OS/390 等等).

为什么不使用基于完整 URI (Universal Resource Identifier) 的路径?

URI 所承诺的东西超出了 Filesystem 库实际能够交付的范围, 因为 URI 远远超出多数操作系统对文件或目录的理解. 因此, 就 Filesystem 库的首要要求“可移植的脚本风格文件系统操作”而言, 完整的 URI 显得过度规范化了.

为什么不把 path 作为基类, 派生出 directory_path 和 file_path 类?

何必如此? 这三个类的行为本质上完全相同. 早期几个版本确实要求用户把每个路径标识为文件路径或目录路径, 而这似乎增加了编码错误并降低了代码可读性, 却没有明显的收益.

为什么产生单个元素的 path 分解函数返回 path 而不是字符串?

为了接口简单. 如果返回字符串, 就需要为不同的字符串与字符类型提供各种变体.

为什么 path 的成员函数没有带 error_code& 参数的重载?

尚无用户提出这一需求; 通过 error_code 报告错误的需要似乎只限于操作函数失败, 而不是 path 失败.

操作函数问题

为什么不提供一种“句柄”类型, 让文件与目录操作围绕它进行?

尚不清楚这样的机制有任何可行方式能满足“可移植的脚本风格文件系统操作”这一要求. 确实存在通常以某种非字符串句柄类型执行操作的文件系统. 经典的 Mac OS 就被明确提及为以路径进行操作并不总是自然的情形.

对目录迭代器值类型而言, “句柄”(标识文件的不可见数据类型) 风格的理由可能最有说服力. (参见 Jesse Jones 于 Jan 28, 2002 在 Boost 邮件列表的发帖). 不过, 随着类 path 的演进, 即使作为目录迭代器的值类型, path 看来也已足够.

为什么操作函数的层次如此之低?

为了提供一个工具箱, 让更高层的功能可以在其上构建.

曾长期尝试在低层功能之上添加便捷函数, 或以其作为替代, 但都失败了, 因为对所考虑的大多数便捷函数而言, 并不存在一套被广泛接受的简单语义. 通过运行期选项或编译期策略提供替代语义的尝试, 相对其交付的价值而言变得过于复杂, 或者引发争议. 另一方面, 若干试验性应用所需的特定功能, 用户用低层工具箱函数构建起来非常容易. 参见失败的尝试.

那么, 提供少数几个便捷函数是否前后不一?

是的, 但对本库、POSIX 和 Windows 的经验表明, 某些便捷函数确实有用, 而且可以为它们提供简单而又被广泛接受的语义. 例如, remove_all().

为什么 operations.hpp 的谓词函数要提供 directory_iterator 重载? 用两种方法做同一件事难道不是糟糕的设计吗?

是的, 用两种方法做同一件事通常是不良的设计实践. 但迭代器版本往往高效得多. 在对包含 15,000 个文件的目录进行迭代的测试中, 在刚启动的机器上调用 status(): path 重载耗时 6 秒, 迭代器重载耗时 1 秒; 在该目录已被使用过之后的测试中, 耗时分别为 0.90 秒和 0.30 秒. 这一性能提升足以成为偏离首选设计实践的理由. 两种重载单独使用都无法满足所有需要.

为什么操作函数对错误如此挑剔?

安全性. 默认选择宁求稳妥而非事后追悔. 考虑到在许多计算机系统上文件与目录是全局共享的资源、因而会受到竞争条件影响这一现实, 这一点尤为重要.

为什么通过具名函数而不是属性映射来访问属性?

对于常用属性 (存在性、目录还是文件、是否为空), 简单的语法和保证存在比其他考虑更重要. 由于对许多其他属性的访问本质上是系统相关的, 属性映射被视为访问与修改的最大希望所在, 但在单独的库中提供这类功能才是更好的设计. (历史说明: 连看似简单的“只读”属性也因系统相关性太强而被取消“保证存在”操作的资格. )

为什么不提供自动的名称可移植性错误检测?

曾评估过多种 (至少六种) 名称有效性错误检测设计, 其中至少四种有完整实现. 虽然被否决的具体原因各不相同, 但所有功能较强的名称有效性检查设计都会扭曲库中原本简单的其他方面. 即使是先前库版本提供的简单名称检查, 也是用户抱怨的一个持续来源. 名称检查固然有帮助, 但其重要性还不足以证明显著增加额外复杂度的合理性.

为什么路径有时由成员函数处理, 有时由非成员函数处理?

设计规则是: 纯词法操作以 path 类成员函数的形式提供, 而由操作系统执行的操作则以自由函数的形式提供.
