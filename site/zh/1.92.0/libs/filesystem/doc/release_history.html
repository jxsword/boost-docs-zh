Filesystem 发布历史

1.92.0

  • 把 initial_path 的模板版本标记为已弃用, 并从 v4 中移除. 请改用非模板版本.
  • 在更多 POSIX 平台上用 readdir 代替 readdir_r, 具体包括 Mac OS 及其他 Apple 操作系统、FreeBSD、OpenBSD、DragonFly BSD、NetBSD、QNX 6.0 及更高版本、Solaris 10 及更高版本以及基于 Illumos 的系统. 建议使用 gcc 的 Solaris 用户在构建 Boost 时根据目标 Solaris 版本定义 __SunOS_5_x 宏 (例如 __SunOS_5_11). (#349)
  • 对 readdir 非线程安全的平台的支持已弃用, 将在未来的发布中移除. 虽然在 POSIX.1-2024 之前并无此要求, 但在现代系统上, readdir 是线程安全的 (当在不同线程中使用独立的 DIR 对象时), 并且在某些系统上 readdir_r 已被标记为弃用. POSIX.1-2024 已相应更新, 并将 readdir_r 标记为过时 (obsolescent), 计划在规范的未来版本中移除.
  • 在 POSIX 平台上, 处理 EINTR 错误码——由 opendir、readdir 及等价函数返回. 虽然未见于文档, 但据报道该错误码可能在 Apple 操作系统和某些 BSD 系统上返回.

1.91.0

  • Boost.Filesystem 现在定义并使用自己的平台宏 BOOST_FILESYSTEM_POSIX_API 和 BOOST_FILESYSTEM_WINDOWS_API. 旧的 BOOST_POSIX_API 和 BOOST_WINDOWS_API 宏仍由 Boost.System 定义. Boost.Filesystem 会检查这两组宏是否一致, 默认情况下若不一致将编译失败. 把 BOOST_FILESYSTEM_ALLOW_SYSTEM_API_MISMATCH 定义为 1 可把编译错误降级为警告, 定义为 2 可完全禁用该检查. 注意, 这种情况下 Boost.Filesystem 报告的错误码值将与错误类别不匹配.
  • 在不支持 openat 及相关 API 的 POSIX 平台上, 修复了当迭代器遇到悬空符号链接且禁用跟随符号链接时 recursive_directory_iterator 递增报告的错误.
  • 对 Cygwin 用户是破坏性变更. 本库现在把 Cygwin 当作 POSIX 平台. 这有几个面向用户的后果, 特别是:
    • path::value_type 类型已从 wchar_t 变为 char. 与其他 POSIX 平台一样, 宽字符路径将使用由 path::imbue 设置的 locale 转换为窄字符编码. 注意, 由于 Cygwin 运行在 Windows 之上, 它还会在内部执行字符编码转换. 在 Cygwin 环境中正确配置 locale 非常重要.
    • 路径语法现遵循 POSIX 约定, 不支持 Windows 特有的路径 (如 UNC 路径、驱动器名和路径前缀).
    • API 中某些 Windows 特有的部分将变得不可访问. 由于重解析点 (reparse point) 是 Windows 独有特性, file_type::reparse_file 将不会针对文件报告. 重解析点的处理依赖于 Cygwin 运行时行为.
    • Cygwin 有自己的符号链接实现, 与原生 Windows 符号链接不兼容. Boost.Filesystem 现在将创建并操作 Cygwin 符号链接.
    • Boost.Filesystem 报告的错误码现在将使用 POSIX errno 值.
  • 在 DragonFly BSD、NetBSD 和 Solaris 上, Boost.Filesystem 默认 path locale 现在对路径字符编码使用 UTF-8.
  • 在 Linux 上, 对 configfs、securityfs、cgroup 与 cgroup2 文件系统, 除先前已列入黑名单的文件系统外, 现在采用 read/write 循环实现 copy_file 和 copy.

1.90.0

  • 清除传入的 error_code 参数——当 permissions 操作成功完成时. (PR#338)
  • 在 Windows 上, 为 directory_iterator 构造函数在要求 SMB 签名时针对 Samba 3.0.2 共享出现“Invalid Signature”错误而失败的情况添加了一种变通方法. (#334)

1.89.0

  • 修正了 path::append 中关于比较可能不相关对象的指针的 ASAN 警告. (#335)

1.87.0

  • 如 1.84.0 中所公告, 10 之前的 Windows 版本不再受支持.
  • 在 Windows 上, canonical 现在基于 GetFinalPathNameByHandleW WinAPI 函数. 副作用是驱动器号被转换为大写, 这使结果路径更具互操作性. (#325)
  • v4: 如果输入路径带有结尾目录分隔符, canonical 不再在结果路径中产生结尾目录分隔符.
  • 如果调用 path 构造函数或成员函数时传入的参数是用户定义类型, 可转换为 path 以及一个或多个 Source 类型, 现在默认会选择到 path 的转换. 这在某些情况下可以解决参数转换歧义, 但也可能导致较差的转换路径. 如果希望不同的转换路径, 建议用户使用显式类型转换. (#326)
  • 针对 FreeBSD 9 及更早版本上 dirfd 是宏的问题添加了一种变通方法. (#328)

1.86.0

  • is_empty 操作现在对并发的文件系统修改有更好的防护.
  • 在 POSIX 系统上, 对普通文件或目录以外的文件调用 is_empty 现在会指示错误.
  • 在 Windows 上, 修复了 file_size 和 is_empty 作用于符号链接本身而不是符号链接所指文件的问题. (#313)
  • directory_entry::refresh 不再抛出异常——如果条目引用的文件不存在. 这使得 directory_entry::status 和 directory_entry::symlink_status 以及基于它们的方法表现得类似于等价的独立操作. 文件不存在的事实仍会通过 error_code 来指示 (由相应的 directory_entry::refresh 重载返回), 也可以通过测试 directory_entry::status 或 directory_entry::symlink_status 调用返回的文件类型是否为 file_type::file_not_found 来看出. (#314)
  • 修复了 weakly_canonical 的问题: 当输入路径是相对路径时, 它按相对于当前路径而不是调用中指定的基础路径来测试路径元素的存在性.
  • 在 Windows 上, 修复了当输入路径以 ".." 开头时 weakly_canonical 产生错误结果路径的问题. (#311)

1.85.0

  • path::generic_path 和 path::generic_string 方法现在会移除返回路径中重复的目录分隔符.
  • v4: path::generic_path、path::generic_string、path::make_preferred 和 path::lexically_normal 避免在路径根名称中转换反斜杠与正斜杠. 例如, 在 Windows 上, path("\\\\?\\c:\\foo").generic_string() 现在返回 "\\?\c:/foo" 而不是 "//?/c:/foo". 类似地, path("\\\\host/share/foo/..").lexically_normal() 现在返回 "\\host\share".
  • v4: 如果任一路径不存在, equivalent 现在会指示错误.
  • v4: absolute 现在返回一个带结尾目录分隔符的路径, 如果输入路径的 relative_path() 为空. (#301)
  • 添加了一个 unique_path 重载, 接受单个 error_code& ec 参数. 该重载使用默认路径模型生成唯一路径.
  • weakly_canonical 现在会产生绝对路径, 如果输入路径是相对路径且不包含文件系统中存在的元素. (#300)
  • 添加了一个新的 copy_options::ignore_attribute_errors 选项, 用于 copy_file 和 copy 操作. 新选项允许在复制文件属性时忽略可能出现的错误. (#179)
  • 在 Linux 上, copy_file 后端 (基于 sendfile 和 copy_file_range 系统调用) 会尝试为目标文件预分配存储. 这可以减少文件系统碎片, 并在空闲空间不足时提供早期错误指示. 并非所有文件系统都支持此特性; 如果不支持存储预分配, 文件复制仍会继续进行.
  • 在支持 POSIX.1-2008 定义的 fdopendir、openat 及相关 API 的 POSIX 系统上, 以及在 Windows 上, recursive_directory_iterator 现在在迭代期间使用文件描述符/句柄而不是路径来查询文件状态并打开嵌套目录. 这使得目录迭代对文件系统的并发修改更有韧性.
  • 移除了先前声明弃用的 API. 具体而言, 移除了 path 和 recursive_directory_iterator 成员函数、is_regular、copy_directory、symbolic_link_exists、complete、copy_option、symlink_option, 以及 boost/filesystem/convenience.hpp 和 boost/filesystem/path_traits.hpp 头文件. 被移除组件的可能替代方案见已弃用的名称与特性一节.
  • 对 path 从容器类型 (例如 std::vector<char>) 进行构造、赋值与追加的支持现在默认禁用. 用户仍可通过定义 BOOST_FILESYSTEM_DEPRECATED 启用此功能. 此功能仍处于弃用状态, 将在未来的发布中完全移除.

1.84.0

  • 如 Boost 1.82.0 中所公告, C++03 不再受支持. 需要 C++11 或更高版本的编译器.
  • 修复了某些 directory_entry 观察器 (带 error_code& ec 参数) 在成功返回时未清除错误码的问题. (#291)
  • 在 Windows 上, 提高了日期与时间转换的健壮性, 并添加了对 1970 年 1 月 1 日之前日期的支持. (#293)
  • 移除了自 Boost.Filesystem 1.79.0 起弃用的 Windows CE 支持.
  • 移除了 boost/filesystem/string_file.hpp 头文件. 该头文件自 Boost.Filesystem 1.79.0 起已弃用.
  • 弃用: 对早于 Windows 10 的 Windows 版本的支持已弃用, 将在 Boost 1.87 中移除.

1.83.0

  • 添加了 directory_entry::refresh 方法, 用于更新由路径标识的目录项的内部缓存文件状态.
  • v4: 初始化或修改路径的 directory_entry 构造函数与修改器现在会自动调用 refresh. 如果查询文件系统以获取文件状态失败 (例如文件不存在), 这可能产生以前及 v3 中未指示的错误. 这一新行为类似于 std::filesystem.
  • v4: directory_entry 构造函数与方法 (带 file_status 参数) 已被移除. 建议用户移除这些参数, 依赖 directory_entry 在内部调用 refresh.
  • 添加了 directory_entry 成员方法, 用于检查文件的文件类型, 类似于 std::filesystem.
  • 添加了更多测试文件状态的方法: is_block_file、is_character_file、is_fifo、is_socket 和 is_reparse_file.
  • recursive_directory_iterator 现在更可能复用在文件系统迭代期间获得的文件类型信息. 这可能提升性能. (#288)
  • 如果标准库文件流可移动, boost/filesystem/fstream.hpp 中定义的文件流现在也可移动. (#280)
  • 添加了新头文件 boost/filesystem/cstdio.hpp, 其中带有一个可移植的 fopen 重载, 接受 path 作为第一个参数. 该函数等价于 std::fopen, 只是在 Windows 上它对路径使用原生宽字符编码.
  • 通用 path 比较运算符现在受到更多限制, 以避免当用户代码包含 using namespace boost::filesystem; 指示时的潜在歧义. (#285)
  • 修复了用户代码中潜在的重载决议歧义: 来自迭代器的 path 构造函数可能干扰接受 std::initializer_list 参数的函数重载. (#287)
  • 在 Windows 上, 为创建目录迭代器时各种文件系统返回的错误添加了更多变通方法. (#284、#286)
  • 在 Windows 上, 放宽了查询文件时间所需的访问权限. (#290)

1.82.0

  • 由于 Boost.System 及 Boost.Filesystem 所用的其他一些库的变更, 对 C++03 的支持已弃用. 从 Boost.Filesystem 1.84 起, C++11 将成为最低要求.
  • 修复了可能由 path 转换构造函数对所接受参数过于宽松而引起的编译错误. (#273)
  • v4: path::remove_filename 现在保留结尾目录分隔符. (#271)
  • 添加了 path::remove_filename_and_trailing_separators, 它从路径中移除文件名及其前面的目录分隔符. 该行为类似于 path::remove_filename (Filesystem v3 中), 但也可在 v4 中使用.
  • 添加了 path::replace_filename, 用于替换路径中的文件名.
  • 更新了库版本选择的实现以避免 ODR 违规. (#279)
  • 在 Windows 上, 为查询 SMBv1 共享中文件的文件属性添加了一种变通方法. 以前, SMBv1 共享中的目录可能被报告为普通文件. 这不影响 SMBv2 或更高版本. (#282)

1.81.0

  • 弃用: path 从字符容器 (例如 std::vector<char> 或 std::list<wchar_t>) 进行构造、赋值与追加在 v3 中已弃用, 并在 v4 中移除. 请改用字符串类型或迭代器.
  • 弃用: boost/filesystem/path_traits.hpp 头文件已弃用, 将在未来的发布中移除. 该头文件包含 path 的实现细节, 不应在用户代码中使用.
  • 先前弃用的 API 在使用时现在会生成编译警告. 要抑制这些警告, 可以在编译用户代码时定义 BOOST_FILESYSTEM_ALLOW_DEPRECATED 宏.
  • 修复了在不支持 *at API 的 POSIX 系统上因缺少包含而导致的编译问题. (#250)
  • 在 10 之前的 Windows 上, 为构造目录迭代器时产生 ERROR_INVALID_PARAMETER 的网络共享文件系统添加了一种变通方法. (PR#246、#245)
  • 在 Windows 上, 修复了当路径以 "\\?\" 前缀开头时 weakly_canonical 以 ERROR_INVALID_FUNCTION 错误码失败的问题. (#247)
  • 为 std::string_view、boost::string_view 和 boost::container::string (以及相应的 wchar_t 对应物) 在 path 构造函数、赋值与追加操作中添加了支持. (#208)
  • path 构造函数、赋值与追加操作 (接受一对迭代器) 将不再接受值类型不属于受支持路径字符类型的迭代器.
  • 在 Windows 上, 提高了 directory_iterator 与各种挂载文件系统以及 7.21 之前 Wine 版本的兼容性. (#255、#266)
  • 在 Windows 上, 去重文件现在被报告为普通文件而不是重解析文件. (#262)

1.80.0

  • 在 Windows 上, 当文件无法以 ERROR_ACCESS_DENIED 错误打开时, 为查询文件属性添加了一种回退实现. 这可能使 status 和 symlink_status 对非重解析点或符号链接的系统文件与目录成功执行. (#234)
  • 在 Windows 上, 为查询文件属性时产生 ERROR_INVALID_PARAMETER 的 FAT/exFAT 文件系统添加了一种变通方法. 这曾影响 status 和 symlink_status (它们报告文件不存在)、无法构造的目录迭代器以及其他依赖操作. (#236、#237)
  • 绕过了 RTEMS 上的一个编译问题. (#240)
  • 在 Linux 上, 修正了切换到 sendfile copy_file 实现的问题——如果 copy_file_range 在运行时以 ENOSYS 失败. sendfile 回退实现过去会跳过文件系统类型检查, 对某些文件系统可能失败.
  • 在支持 POSIX.1-2008 定义的 openat 及相关 API 的 POSIX 系统上以及 Windows Vista 及更高版本上, 改进了上一发布中对 remove_all 实施的针对 CVE-2022-21658 的防护. 先前的修复在某些条件下仍可能导致移除非预期的文件. 其他系统仍然易受攻击.

1.79.0

  • v3: path::replace_extension 现在按 v3 对 path::extension 的定义而非 v4 的定义工作.
  • 修复了路径追加与拼接运算符在参数类型可转换为 path 或兼容字符串类型时的编译问题. (#223)
  • 在支持 fdopendir 与 O_NOFOLLOW 的 POSIX 系统上以及 Windows 上, remove_all 现在已针对 CVE-2022-21658 实施防护. 该漏洞是一个竞争条件: 第三方进程可以把正在被 remove_all 并发处理的目录替换为目录符号链接, 导致 remove_all 跟随该符号链接并移除链接目录中的文件, 而不是移除符号链接本身. (#224)
  • 在 Windows 上, 在 remove 和 remove_all 实现中, 当操作系统支持时 (Windows 10 1709 及更高版本), 对文件移除使用 POSIX 语义. 当支持 POSIX 语义时, 文件一经标记为删除, 其文件名即从文件系统命名空间中移除, 即使文件仍然打开并处于使用中. 在传统 Windows 语义下, 文件名会一直保留在文件系统命名空间中, 直到该文件的最后一个文件句柄被关闭, 这使得被标记删除的文件仍可被打开, 并阻止创建同名的新文件. (#216)
  • 在 Windows 上, remove 和 remove_all 现在支持删除只读目录. 对移除只读非目录文件的支持先前已添加.
  • 在 Windows 上, directory_iterator 的内部实现经过重做, 以更好地利用现代 Windows API, 这可能提升处理符号链接时的性能.
  • 在 Windows 上, 尽可能早地初始化内部 WinAPI 函数指针, 以允许在全局构造函数中调用 Boost.Filesystem 操作. 仅 MSVC、GCC、Clang 及兼容编译器支持此做法.
  • 在 Windows 上, 如果要调整大小的文件已被打开, resize_file 应不再因错误而失败.
  • 在 11.0 (API 版本 30) 之前的 Android 上禁用 statx 系统调用. 该系统调用被 seccomp 列入黑名单, 会在运行时导致进程终止. (#229)
  • 弃用: boost/filesystem/string_file.hpp 头文件已弃用, 将在未来的发布中移除. 默认情况下 boost/filesystem.hpp 不再包含该头文件. 建议用户自行实现该功能或迁移到其他实现.
  • 弃用: Windows CE 支持已弃用, 将在未来的发布中移除. Windows CE 多年未经测试, 很可能已无法工作.

1.78.0

  • v4: 如果路径以目录分隔符结尾, path::filename 和 path::iterator 不再返回隐式的结尾点号 (".") 元素. 改为返回空路径, 类似于 C++17 std::filesystem. 这也影响以迭代器或文件名定义的其他方法, 例如 path::stem、path::compare 或 lexicographical_compare. 例如, path("a/b/") == path("a/b/.") 不再成立. (#193)
  • v4: path::lexically_normal 不再在规范化路径中产生结尾点号 (".") 元素, 并省略结尾 dot-dot ("..") 元素之后的目录分隔符.
  • v4: path 追加操作现在会考虑被追加路径中的根名称与根目录. 如果被追加路径是绝对路径, 或存在根名称且与源路径不同, 则结果路径等价于被追加的路径. 如果存在根目录, 则结果是重新定基于源路径根名称之上的根目录与相对路径. 否则, 行为类似于 v3. (#214)
  • path::lexically_normal 现在在规范化路径的根名称中把目录分隔符转换为首选分隔符.
  • 优化了 path::assign、path::append、path::concat 及相应运算符的重载, 以避免不必要的路径复制并减少代码冗余.
  • 在 POSIX 系统上, 修复了 absolute(p, base) 的问题: 它会返回带根名称 base.root_name() 的路径, 如果 p 以根目录开头. 在这种情况下 p 已经是绝对路径, 应原样返回.
  • create_directories 不再报告错误, 如果输入路径完全由点号 (".") 与 dot-dot ("..") 元素组成. 实现不再在内部使用递归, 因此在极长路径上更能避免栈溢出.
  • 在 Windows 上, remove 现在支持删除只读文件. 该操作会在移除前尝试重置只读属性. 注意, 如果操作失败且属性原值恢复失败, 这引入了只读属性被留置为未设置的可能性. 这也影响 remove_all. (#216)
  • remove_all 现在在出错时返回 static_cast< uintmax_t >(-1), 类似于 C++17 std::filesystem.
  • 修复了一个链接错误: 当用户代码包含 boost/filesystem/path.hpp 但不包含 boost/container_hash/hash.hpp, 且编译器被设置为保留未使用的内联函数时, 会出现对 Boost.ContainerHash 函数的未解析引用. (#215)
  • 针对 MSVC 及兼容编译器在发布构建中消除路径全局对象清理的问题添加了一种变通方法. 如果 Boost.Filesystem 共享库在进程中反复加载与卸载, 这可能导致内存泄漏. (#217)

1.77.0

  • 推出 Boost.Filesystem v4. 该库的新版本移除了 v3 的所有已弃用特性, 并作出多项破坏性 API 变更, 旨在使 Boost.Filesystem 与 C++17 引入的 std::filesystem 更加兼容. 差异在发布说明与文档中以 v3 和 v4 标签描述, 并在单独章节中汇总. 用户可以在编译代码时把 BOOST_FILESYSTEM_VERSION 宏定义为 3 或 4 来选择 Boost.Filesystem 版本. 无需为每个库版本单独编译 Boost.Filesystem——单个二进制文件同时支持 v3 和 v4. 用户应避免在同一应用中同时使用 v3 与 v4, 因为这可能引入隐蔽的缺陷. 目前默认版本为 v3. 在未来的发布中 v4 将成为默认版本, 最终 v3 将被移除. v4 已可使用, 但仍在开发中, 未来可能有破坏性 API 变更.
  • v4: 如果路径仅由这些组件组成, path::filename、path::stem 和 path::extension 不再把路径的根名称或根目录视为文件名. 例如, 在 Windows 上 path("C:").filename() 过去返回 "C:" 而 path("C:\\").filename() 过去返回 "\", 现在两者都将返回空路径. (#88、#194)
  • v4: path::stem 和 path::extension 不再把以点号开头且没有其他点号的文件名视为扩展名. 以点号开头的文件名通常被视为带空扩展名的文件名. 在多数类 UNIX 系统上, 前导点号用于指示隐藏文件. (#88)
  • 新增: 改进了对 Windows 上各种路径前缀的支持. 添加了对本地设备前缀 ("\\.\") 的支持以及对 NT 路径前缀 ("\??\") 的实验性支持. 这些前缀会被纳入路径的根名称. 注意, 在 Boost.Filesystem v3 中使用这些前缀可能产生意外结果 (例如 path("\\\\.\\").stem() == "\\\\"). 建议只在 Boost.Filesystem v4 中使用这些前缀.
  • 重做了 path::lexically_normal 实现, 以消除规范化路径中某些重复点号 (".") 元素的情形.
  • 新增: 在 Linux 上添加了对 statx 和 getrandom 系统调用的运行期检测. 如果系统调用在编译期存在但在运行期以 ENOSYS 失败 (例如, 在限制该系统调用的 Docker 容器中, 即使宿主机上可用), 这会很有用. (#172)
  • 新增: 添加了在库构建期禁用各种系统 API 使用的支持. 当某个 API 被库配置脚本检测为存在, 但出于某种原因不得使用时 (例如, 运行期检测在目标系统上不起作用), 这会很有用. 更多细节参见配置宏的说明.
  • 新增: 添加了 copy_options::synchronize_data 和 copy_options::synchronize 选项, 用于 copy_file 操作. 这些选项允许把写入的数据与属性同步到永久存储. 这些选项在性能上代价高昂, 但能确保被复制数据的可靠性. 注意, 自 Boost.Filesystem 1.74.0 起, copy_file 在 POSIX 系统上会执行隐式数据同步. 本发布增加了对更多平台的支持, 并默认禁用数据同步, 同时允许调用者显式请求同步. (#186)
  • 在 POSIX 系统上, 为内部发出的某些系统调用添加了对 EINTR 错误码的处理. 特别是, EINTR 在 close 上可能被忽略, 这在 HP-UX 上会导致文件描述符泄漏.
  • 在 copy_file 实现 (基于 Linux sendfile 和 copy_file_range 系统调用) 中, 添加了对表明特定文件系统不支持该系统调用的错误码的处理, 并回退到通用 read/write 循环. 这应能修复 copy_file 在 eCryptFS 及可能其他文件系统上失败的问题. (#184)
  • 自 Linux 内核 4.5 起现在会使用 copy_file_range 系统调用, 而以前只在 5.3 之后才启用. copy_file 实现会回退到 sendfile 或 read/write 循环, 如果 copy_file_range 无法跨文件系统复制给定文件.
  • copy_file 实现 (基于 Linux sendfile 和 copy_file_range 系统调用) 将不会用于已知包含生成内容文件的文件系统. 这些系统调用与此类文件不兼容, 复制它们会产生零大小文件. 将改用通用 read/write 循环. 目前列入黑名单的文件系统有: procfs、sysfs、tracefs 和 debugfs.
  • 在 copy_file 实现 (基于 read/write 循环) 中, 增大了用于临时存储的缓冲区最大尺寸, 并考虑目标文件系统的块大小以获得更优性能.
  • 在 Windows CE 上, 调用 current_path 获取进程的当前路径现在会因错误而失败, 而不是成功返回根路径. 该平台不支持当前目录. 在 Boost.Filesystem 先前的发布中, 更改当前路径已经以类似方式失败.
  • 在 canonical 中, 修复了当较早的符号链接被解析为与原始路径根不同的绝对路径时, 对引用根之上的目录的符号链接的检查.
  • 在 canonical 中, 添加了对调用期间可解析的符号链接最大数量的限制. 该限制目前至少为 40 个符号链接.
  • 在 Windows 上, canonical 和 weakly_canonical 现在会在结果路径中使用 path::preferred_separator 作为根目录分隔符. 这修复了由 Windows API 不处理 UNC 路径及以 Win32 文件系统前缀 ("\\?\") 开头的路径中的通用分隔符而引起的“找不到文件”错误. (#87、#187)
  • 新增: 添加了 weakly_canonical 重载, 接受 base path 作为参数.
  • 在 Windows 上, 如果输入路径包含文件系统中不存在但被后续 dot-dot ("..") 元素抵消的元素, weakly_canonical 不再因错误而失败. 例如, 如果 "C:\a" 目录不存在, weakly_canonical("C:\\a\\..") 以前会失败. (#201)
  • 在 Windows 上的 read_symlink 中, 修正了重解析点处理. 该操作对某些挂载点 (例如由 Box 云存储驱动器创建的) 以及具有空打印名称的目录联接点会返回空路径. 新实现现在会解析重解析点的替代名称 (substitute name), 并尝试据此重构 Win32 路径. (#187)
  • 在 Windows 上, 当标准库支持以宽字符路径打开文件时, boost/filesystem/fstream.hpp 提供的文件流在 libc++ 7.0 及更高版本上将使用宽字符路径. (#181)
  • 在 Windows 上, 如果 Windows 配置为开发者模式, 创建符号链接应不再需要提升的特权.
  • 在某些编译器上, Boost.Filesystem 内部使用的全局对象现在会在用户的全局析构函数被调用之后再销毁. 这使得可以在程序终止阶段调用 Boost.Filesystem 方法. 特别是, 这涉及用于字符编码转换的 path locale, 可通过调用 path::imbue 来安装. 受支持的编译器包括 MSVC、GCC 和 Clang, 以及其他支持通过 #pragma section (针对 MSVC 兼容编译器) 或 __attribute__ ((init_priority)) (针对 GCC 兼容编译器) 自定义程序初始化次序的编译器.

1.58.0

  • 修复 #6124、#6779 和 #10038. 无法把 BOOST_SCOPED_ENUM 传给需编译库的函数, 因为如果库用 -std=c++0x 编译而使用方以 C++03 模式编译 (或反过来), 会导致未定义引用.
  • 重写 temp_directory_path() 的 Windows 实现, 目的是 (1) 在路径长度 > 130 时避免 GetTempPath() 失败 (工单 #5300), (2) 按 boost 邮件列表讨论“[filesystem] temp_directory_path() behavior on Windows”提供比 GetTempPath() 更合理的目录序列. 新序列为:
    1. %TMP%
    2. %TEMP%
    3. %LOCALAPPDATA%/Temp
    4. %USERPROFILE%/Temp
    5. GetWindowsDirectoryW()/Temp

1.57.0

  • 重做类 path 的 locale 与 codecvt 实现, 以提高可靠性. 此变更为 SVN 修订 83021, 本应进入 1.56.0, 但很遗憾合并来得太晚.
  • 修复工单 #8930、#9054、#9219、#10228 和 #10641, 均与 locale 和 codecvt facet 相关.
  • 上述变更与修复的净效果应当是消除 Linux 及其他非 BSD 类 POSIX 系统上虚假的“locale::facet::_S_create_c_locale name not valid”错误. 当在没有有效 C locale 的环境中尝试 char 到 wchar_t 或 wchar_t 到 char 的路径编码转换时, 该错误仍会按预期继续出现 (例如, LANG 环境变量无效或未定义时).
  • 修复 #6124、#6779 和 #10038——当库以 C++03 编译而使用程序以 C++11 编译 (或反之) 时出现的未定义引用. 库的私有接口已改为使用普通的老式 C++03 枚举. 这是 Andy 在 6779 中建议的修复.
  • Windows 实现现在把 NTFS 目录联接 (junction, 也称挂载点) 视为符号链接. 这相当于把目录联接当作目录对待, 从而支持所有适用于目录的操作. 这解决了 #9016. 目录联接与符号链接非常相似, 但在某些情形下可能有性能或其他优势. 它们可以在命令行中用 "mklink /j link target" 创建. 除调用 std::system() 外, Boost.Filesystem 没有计划能直接创建它们.
