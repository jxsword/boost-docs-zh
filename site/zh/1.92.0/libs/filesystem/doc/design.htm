引言

着手开发 Filesystem 库的主要动机是 Boost 管理工具带来的困扰. 脚本分别用 Python、Perl、Bash 和 Windows 命令语言编写. 没有任何一种脚本语言能让所有 Boost 管理员都熟悉并接受. 然而他们都是熟练的 C++ 程序员——为什么不能把 C++ 用作脚本语言呢?

对于类脚本应用而言, C++ 缺少的关键特性是对目录及其内容执行可移植文件系统操作的能力. Filesystem 库正是为填补这一空白而开发的.

其目的并不是与传统脚本语言竞争, 而是为那些已经选择 C++ 作为语言的场合提供一个解决方案..

要求

  • 能够用现代 C++ 编写可移植的脚本风格文件系统操作.

    设计理由: 这是一种常见的编程需求. 无论是当前的 C++ 还是 Boost 库都无法做到这一点, 这既令人尴尬又造成实际困难. 当 C++ 是工具链中唯一允许使用的工具集时, 这种需求尤为迫切. 许多跨平台使用的语言 (如 Perl 和 Python) 以及许多平台特定的脚本语言都提供文件系统操作. 所有操作系统都提供某种形式的文件系统操作 API, 而且即使在通常与 POSIX 无关的操作系统上 (如 Mac、z/OS 或 OS/390), POSIX 绑定也日益普及.
  • 在下文所述的现实情况范围内工作.

    设计理由: 这不是一个研究项目. 我们需要的是能在当今平台上工作的东西, 包括一些文件系统功能受限的嵌入式操作系统. 由于强调可移植性, 这样的库如果能标准化, 将会有用得多. 这意味着能够支持比 Unix、Windows 及其克隆更为广泛得多的平台.
  • 避免危险的编程习惯. 特别是极易被忽略的错误通知以及对全局变量的使用. 如果提供了某个危险特性, 应明确将其标识出来.

    设计理由: 通常这已包含在“通常的 Boost 要求...”之中, 但仍需明确提及, 因为等价的原生平台与脚本语言接口往往依赖于极易被忽略的错误通知以及“当前工作目录”这类全局变量.
  • 对库进行组织, 使得即使某些功能无法很好地映射到给定平台或目录树, 库仍然有用. 特别是, 许多有用的功能应当是可移植的, 甚至可移植到平坦 (非分层) 文件系统.

    设计理由: 许多不需要分层目录结构的功能在平坦结构的文件系统上仍然有用. 有许多系统, 特别是嵌入式系统, 在那里即使功能非常有限也仍然有用.
  • 与当前 C++ 标准库的输入/输出设施平滑衔接. 例如, path 应当能方便地用于 std::basic_fstream 构造函数.

    设计理由: 文件系统功能最常见的用途之一是处理路径, 以便最终用于输入/输出操作. 因此需要与标准库 I/O 平滑衔接.
  • 适合最终标准化. 这一要求意味着接口必须接近最小化, 并且在可移植性方面必须格外小心.

    设计理由: 缺少文件系统操作是当前标准中的一个严重缺口, 而且没有其他已知的候选方案可以填补这一空缺. 接口繁复、规范难以移植的库被接受并标准化的可能性要小得多.
  • 通常的 Boost 要求与准则同样适用.
  • 鼓励但并不要求路径名称具有可移植性.

    设计理由: 对于源自用户输入的路径, 要求其符合可移植的路径语法是不合理的.
  • 在可移植性实际并不存在的地方, 避免制造具有可移植性的假象.

    设计理由: 把重要行为留作未指定或“由实现定义”, 对使用库的程序员危害极大, 因为这会让人以为依赖该行为的代码是可移植的, 而实际上它毫无可移植性可言. 这种规范不足唯一可以接受的情形是: 使用者和实现者都从其他渠道确切知道需要什么行为, 却因某种原因无法将其精确地规范下来.

现实情况

  • 有些操作系统只有单个目录树根, 另一些则有多个根.
  • 有些文件系统同时提供文件名的长短两种形式.
  • 有些文件系统对文件路径与目录路径采用不同的语法.
  • 有些文件系统对有效文件名与有效目录名采用不同的规则.
  • 有些文件系统 (例如 ISO-9660 第 1 级) 使用非常受限的 (即所谓的 8.3) 文件名.
  • 有些操作系统允许把具有不同特性的文件系统“挂载”到一棵目录树之中. 因此, 一个 ISO-9660 或 Windows 文件系统可能最终成为 POSIX 目录树的一个子树.
  • 目录与文件操作的宽字符版本在某些操作系统上可用, 在另一些操作系统上则不可用.
  • 没有任何法则规定目录层级必须按从根开始自左向右下降的方式来指定.
  • 有些文件系统有文件“版本号”或“代数号”的概念, 有些则没有.
  • 并非所有操作系统都在路径名中使用单字符分隔符, 有些采用成对的记号. 一个完整指定的典型 OpenVMS 文件名可能形如:

       DISK$SCRATCH:[GEORGE.PROJECT1.DAT]BIG_DATA_FILE.NTP;5

    OpenVMS 的一般格式为:

    Device:[directories.dot.separated]filename.extension;version_number
  • 对于常见文件系统, 判断两个描述符是否指向同一实体极为困难, 甚至不可能. 例如, 相等的概念对路径的每一部分可能各不相同——有些部分可能区分大小写或区域设置, 另一些则不区分. 大小写敏感性是路径名自身的属性, 而不是平台的属性. 确定排序次序则更加糟糕.
  • 可能出现竞争条件. 目录树、目录、文件与文件属性实际上由所有能访问该文件系统的线程、进程和计算机共享, 其中很可能包括在世界另一端或绕地球轨道上的计算机. 这意味着文件系统操作可能以意外的方式失败. 例如:

         assert( exists("foo") == exists("foo") ); // may fail!
         assert( is_directory("foo") == is_directory("foo"); // may fail!

    在第一个例子中, 文件可能在两次 exists() 调用之间被删除. 在第二个例子中, 文件可能在两次 is_directory() 调用之间先被删除、随后又被一个同名目录取代.
  • 即使应用程序本身是可移植的, 它仍难免偶尔要处理系统特定的路径; 用户提供输入就是一个常见的例子.
  • 符号链接会使某些路径的规范形式与普通形式表示不同的文件或目录. 例如, 给定目录层级 /a/b/c, 在 /a 中有一个名为 x 的符号链接指向 b/c, 那么按照 POSIX Pathname Resolution 规则, 路径 "/a/x/.." 应解析为 "/a/b". 如果先把 "/a/x/.." 规范化为 "/a", 解析结果就会不正确. (案例由 Walter Landry 提供. )

设计理由

上面的要求与现实情况推动了 C++ 接口设计的许多方面. 特别是, 让类脚本代码保持直白的愿望, 促使大量精力投入到确保 exists( "foo" ) 这类看似简单的表达式能按预期工作之上.

许多具体设计决策背后的理由请参见常见问题 (FAQ).

path 类的设计融入了几条关键见解:

  • 将输入格式、内部概念模型 (vector<string> 或其他序列) 与输出格式解耦.
  • 提供两种输入格式 (通用格式与操作系统特定格式) 打破了一个重大的设计僵局.
  • 提供多种输出格式解决了另一组此前难以处理的问题.
  • 要支持可移植代码, 需要若干并不直观的函数 (特别是分解与组合函数). (Peter Dimov、Thomas Witt、Glen Knowles 等. )

错误检查是一个特别困难的领域. 一条关键见解是: 对文件与目录名而言, 可移植性并非普适真理. 相反, 程序员必须认真思考“我希望这个路径能移植到哪些操作系统?”这一问题. Filesystem 库为该问题提供了多种可选答案, 从而提醒程序员首先提出这个问题.

已放弃的设计

operations.hpp

Dietmar Kühl 最初的 directory_iterator 设计与实现支持宽字符文件名和目录名. 库工作组 (Library Working Group) 成员经过大量讨论, 仍无法为不提供原生支持的系统上的宽字符名称确定可移植语义, 因此该设计被放弃. 参见常见问题 (FAQ).

接口设计的先前版本使用显式命名的函数来提供大量便捷操作, 没有编译期或运行期选项. 函数名多到使用起来非常混乱, 接口也大得多. 其好处似乎只停留在理论层面而非实际.

基于编译期 (而非运行期) 标志与选项选择 (通过策略、枚举或 int 模板参数) 的设计变得过于复杂, 在投入大量时间与精力之后往往仍被放弃. 属性或选项名称需要用命名空间 (即便是别名) 来限定, 这使得在模板参数中的使用非常难看; 直到真正编写实际代码时才充分意识到这一点.

又一组便捷函数 (例如带 permissive、prune、recurse 等选项, 以及谓词和其他过滤特性的 remove) 也被放弃, 因为其细节变得既复杂又充满争议.

最终留下的是一套低层操作工具箱, 用户可以在其上构建更复杂的便捷操作; 另有极少数便捷函数, 它们被发现足够有用, 值得纳入库中.

path.hpp

被放弃的 path 设计太多了, 我已经数不清了. 几种风格的基于策略的类模板、由构造函数提供的运行期策略、针对特定操作的运行期策略——这些都被考虑过, 也常常被实现过, 最终都因为过于复杂而收益甚微被放弃.

关于国际化还有额外的设计考量.

错误检查

错误检查机制的许多设计都被放弃, 有些是在尝试实现之后. 其中特别尝试过完全自动的错误检查, 但自动错误检查往往使整个库的设计复杂得多.

有些设计把错误检查机制与路径关联, 有些则与操作函数关联. 一个基于策略的错误检查模板设计曾被部分实现, 随后因对日常类脚本程序而言过于复杂而被放弃.

最终设计部分依赖于显式的错误检查函数调用, 简单直白得多, 尽管它在一定程度上依赖程序员的自律. 但它应当能让关心可移植性的程序员合理地确信, 其程序能在其选定的目标系统上正确运行.
