Boost.Filesystem 的问题 (如缺陷报告或功能请求) 应通过 GitHub 工单报告.

GitHub pull requests 也受到鼓励, 但除真正微不足道的修复之外, 都需要一个工单.

缺陷报告

如果问题能够不经猜测立即复现, 并且回归测试能够轻松创建, 那么你的缺陷报告得到及时响应的可能性会大得多.

你需要提供以下内容:

  1. 一个简单的测试程序, 它:
    • 能够说明问题, 并且
    • 自动产生明确的通过或失败结果 - 最好是通过返回零、失败返回非零, 并且
    • 可以用作向 Boost.Filesystem 回归测试套件添加测试的基础.
  2. 你用于构建和运行测试程序的编译器、标准库、平台和 Boost 版本.
  3. 关于如何构建和运行测试程序的说明.
  4. 测试程序输出的副本 (如有).
  5. 用于后续追问的电子邮件地址.

为什么需要上述内容, 请参见设计理由.

要了解一个能自动完成上述大部分工作的框架, 请继续阅读!

缺陷报告框架

目录 <boost-root>/libs/filesystem/bug> 提供了一个缺陷测试程序 (bug.cpp) 和一个构建文件 (Jamfile.v2). 你需要做的是:

  1. 使用任意文本或程序编辑器向 bug.cpp 添加一个或多个测试用例.
  2. 构建并测试.
  3. 把 测试输出和测试程序的副本附加到 Trac 工单上.

就是这样! 完成这些步骤后, 你就大功告成了!

测试输出提供了关于编译器、标准库、平台、Boost 版本和命令行的全部基本信息, 而你添加的测试用例应当让库维护者能够轻松复现该问题.

使用该框架

bug.cpp

这是随库提供的 bug.cpp. 要报告真实的缺陷, 请使用 BOOST_TEST 和 BOOST_TEST_EQ 宏来构建你自己的测试用例. 你可以删除 bug.cpp 中已有的三个测试:

#include <boost/detail/lightweight_test_report.hpp>
#include <boost/filesystem.hpp>

namespace fs = boost::filesystem;

int test_main(int, char*[])     // note name
{
  BOOST_TEST(2 + 2 == 5);       // one convertible-to-bool argument; this one fails!
  BOOST_TEST_EQ(4 + 4, 9);      // two EqualityComparible arguments; this one fails!
  BOOST_TEST(fs::exists("."));  // should pass, so nothing should be reported

  return ::boost::report_errors();   // required
}

构建并测试

类 POSIX 系统:

cd <boost-root>/libs/filesystem/bug
../../../b2 -a
bin/bug

Windows:

cd <boost-root>\libs\filesystem\bug
..\..\..\b2 -a
bin\bug

测试输出

在 Windows 上运行该测试产生了如下测试输出:

Microsoft Visual C++ version 14.0
Dinkumware standard library version 610
Win32
Boost version 1.58.0
Command line: bin\bug
bug.cpp(10): test '2 + 2 == 5' failed in function
  'int __cdecl test_main(int,char *[])'
bug.cpp(11): test '4 + 4 == 9' failed in function
  'int __cdecl test_main(int,char *[])': '8' != '9'
2 errors detected.

测试框架运行 test_main(), 它位于一个 try 块中, 并带有一个 catch 块, 由后者通过 std::exception what() 报告异常. 因此, 如果抛出异常, 输出将有所不同.

背景信息

现在你应当已掌握足够的信息来提交一份易于复现的缺陷报告. 所以可以跳过本页其余内容, 除非你需要做一些稍微不寻常的事情.

b2 命令行

b2 (原为 bjam) 用法: b2 [options] [properties] [target]

Boost.Build b2 有许多选项、属性和构建目标, 但报告缺陷时大多数都用不到. 以下是一些可能会有帮助的:

选项

-a 重新构建所有内容, 而不仅是过期的构建目标. 上面的示例构建中使用它, 以确保库与测试程序使用相同的配置构建.

属性

address-model=n  n 取 32 或 64. 显式请求 32 位或 64 位代码生成. 这通常要求编译器已作相应配置.

variant=string string 取 debug 或 release.

toolset=string 要使用的 C++ 编译器. 例如, gcc-4.9、clang-3.3、or msvc-14.0.

include=string C 和 C++ 编译器的附加包含路径.

cxxflags=string 传给 C++ 编译器的自定义选项.

define=string C 和 C++ 编译器的附加宏定义. string 应为 SYMBOL 或 SYMBOL=VALUE

设计理由

下面再次列出这份请求清单, 并附上理由:

  1. 一个简单的测试程序, 它:
    • 能够说明问题 [代码比文字更能清楚地传达问题. 如果看起来要花一些时间才能弄清楚问题究竟是什么, 或者更糟, 可能导致白费功夫, 缺陷报告就会被搁置到以后处理, 然后往往被遗忘. ], 并且
    • 自动产生明确的通过或失败结果 - 最好是通过返回零、失败返回非零 [避免沟通误解, 并可用于自动回归测试. ], 并且
    • 可以用作向 Boost.Filesystem 回归测试套件添加测试的基础 [有了好的测试用例, 修复更容易, 回归也更不可能发生].
  2. 你用于构建和运行测试程序的编译器、标准库、平台和 Boost 版本. [实现中包含大量平台相关代码, 并且还依赖于上述其他因素. 预先了解这些内容可以让缺陷报告聚焦, 无需再索取更多信息. ]
  3. 关于如何构建和运行测试程序的说明. [如果使用 b2 (原名 bjam) 作为构建引擎, 这不成问题, 否则就需要多得多的信息. ]
  4. 测试程序输出的副本 (如有). [避免误解结果. ]
  5. 用于后续追问的电子邮件地址. [Trac 评论是主要的答复方式, 但如果 trac 上的问题无人回答, 而又没有附上用于跟进的电子邮件地址, 令人沮丧. ]
