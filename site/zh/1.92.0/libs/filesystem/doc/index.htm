引言

Boost.Filesystem 库提供用于操作文件、目录以及标识它们的路径的设施.

该库的特性包括:

  • 现代的 C++ 接口, 与 C++ 标准库高度兼容.

许多用户表示, 该接口是他们使用 Boost.Filesystem 的主要动机. 他们喜欢它基于标准库容器、迭代器和算法的熟悉惯用法, 也喜欢通过抛出异常来报告错误.

  • 跨操作系统的可移植性.
    • 在 C++ 语法层面, 无论操作系统是什么, 学习并使用同一个接口都很方便.
    • 在语义层面, 代码的行为在不同操作系统之间具有相当好的可移植性.
    • 对通用与原生两种路径格式的双重支持有助于程序可移植性, 同时仍允许以系统特定的格式与用户交互.
  • 通过 C++ 异常 (默认) 或错误码进行错误处理与报告.
    • C++ 异常是多数应用程序首选的错误报告机制. 抛出的异常包含详细的错误码信息, 这对诊断文件系统错误的确切原因非常重要.
    • 通过错误码报告错误, 使需要提供详细错误恢复的用户代码避免因塞满 try-catch 块而变得无法维护.
  • 适用于广泛的应用谱系, 从简单的类脚本操作到极其复杂的生产代码.
    • 在频谱上简单的类脚本一端, 其目的不是与 Python、Perl 或 shell 语言竞争, 而是在 C++ 已经是首选语言时提供文件系统操作.

    • 对操作与错误处理提供更细粒度的控制, 以支持更复杂的应用或其他不希望抛出异常的情形.

  • 构成 ISO/IEC TS 18822 (C++ 标准库 Filesystem 技术规范 (TS)) 的基础.

使用本库

Boost.Filesystem 实现为单独编译的库, 因此必须把二进制文件安装在链接器能够找到的位置. 如果你按照Boost 入门的说明操作, 这一步已经替你完成了.

编码准则

对于新代码, 强烈建议在包含 filesystem 头文件之前先定义 BOOST_FILESYSTEM_NO_DEPRECATED. 这可以防止无意中使用已被取代、将来会被移除的旧特性, 特别是旧式函数名.

注意事项

读完教程之后, 你就可以直接动手编写使用 Filesystem 库的简单类脚本程序了! 不过, 在开始任何正式工作之前, 有几点注意事项需要了解:

存在竞争条件时不保证效果与后置条件

Filesystem 函数的规范遵循 C++ 标准库的形式, 以效果与后置条件来规定行为. 如果存在竞争条件, 那么到函数返回调用者时, 其后置条件可能已不再成立.

解释: 文件与目录的状态通常是全局共享的, 因此可能被其他线程、进程、甚至其他通过网络访问该文件系统的计算机意外改变. 作为这可能造成的困难的例子, 请注意下面的断言可能失败:

assert( exists( "foo" ) == exists( "foo" ) );  // (1)

remove_all( "foo" );
assert( !exists( "foo" ) );  // (2)

assert( is_directory( "foo" ) == is_directory( "foo" ) ); // (3)

(1) 将失败, 如果在第一次与第二次调用 exists() 之间, 一个原本不存在的“foo”出现了, 或者一个已存在的“foo”被移除了. 如果示例代码执行期间另一个线程、进程或计算机也在同一目录中执行操作, 就可能发生这种情况.

(2) 将失败, 如果在调用 remove_all() 与调用 exists() 之间, 另一个线程、进程或计算机创建了一个名为“foo”的新文件或目录.

(3) 将失败, 如果在示例代码两次调用 is_directory() 之间, 另一个线程、进程或计算机删除了已存在的文件“foo”, 然后又创建了一个名为“foo”的目录.

异常

除非另有说明, Boost.Filesystem 函数抛出 basic_filesystem_error 异常来报告诸如 I/O 错误之类的失败. 实现还可能使用会抛出 std::bad_alloc 异常的 C++ 标准库函数来报告内存分配错误. 即使导致异常的错误条件未在函数的“抛出 (Throws)”段落中明确规定, 这些异常也可能被抛出.

为访问外部文件系统的操作函数提供了名义上不抛出异常的版本, 因为它们常用于错误码可能是首选错误报告方式的场景. 即使是名义上不抛出的函数版本, 也会抛出 std::bad_alloc 异常来报告内存分配错误. 不过, 标记为 noexcept 的函数绝不抛出异常.

头文件

Boost.Filesystem 库提供多个头文件:

  • 头文件 <boost/filesystem.hpp> 提供对库中除文件流之外全部特性的访问.
  • 头文件 <boost/filesystem/fstream.hpp> 继承与 C++ 标准库 fstream 头文件相同的组件, 但文件通过 const path& 参数而非 const char* 参数来标识.

实现

当前实现支持提供 POSIX 或 Windows API 的操作系统.

该库在 Apple OS X、HP-UX、IBM AIX、Linux、Microsoft Windows、SGI IRIX 和 Sun Solaris 操作系统上配合多种编译器被常规使用, 也被若干智能手机操作系统使用.

宏

用户可以根据需要定义以下宏. 库提供了合理的默认值, 因此除非有特殊需要, 用户可以忽略这些宏.

宏名称 默认值 定义后的效果
BOOST_FILESYSTEM_VERSION 3 选择 Boost.Filesystem 库版本. 可取值 3 或 4. 定义为 4 也隐含 BOOST_FILESYSTEM_NO_DEPRECATED.
BOOST_FILESYSTEM_NO_DEPRECATED 未定义. 已弃用特性被排除在头文件之外.
BOOST_FILESYSTEM_DYN_LINK 若 BOOST_ALL_DYN_LINK 已定义则定义, 否则未定义. Boost.Filesystem 库动态链接. 若未定义, 则假定静态链接.
BOOST_FILESYSTEM_NO_LIB 若 BOOST_ALL_NO_LIB 已定义则定义, 否则未定义. Boost.Filesystem 库不使用 Boost 自动链接机制.
BOOST_FILESYSTEM_DISABLE_SENDFILE 未定义. 在库构建时检测 sendfile API 是否存在. Boost.Filesystem 库在 Linux 上不使用 sendfile 系统调用. sendfile 系统调用自 Linux 2.6.33 起才开始接受普通文件描述符作为目标.
BOOST_FILESYSTEM_DISABLE_COPY_FILE_RANGE 未定义. 在库构建时检测 copy_file_range API 是否存在. Boost.Filesystem 库在 Linux 上不使用 copy_file_range 系统调用. copy_file_range 系统调用引入于 Linux 内核 4.5, 自 5.3 起开始支持跨文件系统操作.
BOOST_FILESYSTEM_DISABLE_STATX 未定义. 在库构建时检测 statx 是否存在. Boost.Filesystem 库在 Linux 上不使用 statx 系统调用. statx 系统调用引入于 Linux 内核 4.11.
BOOST_FILESYSTEM_DISABLE_GETRANDOM 未定义. 在库构建时检测 getrandom API 是否存在. Boost.Filesystem 库在 Linux 上不使用 getrandom 系统调用. getrandom 系统调用引入于 Linux 内核 3.17.
BOOST_FILESYSTEM_DISABLE_ARC4RANDOM 未定义. 在库构建时检测 arc4random API 是否存在. Boost.Filesystem 库在 BSD 系统上不使用 arc4random_buf 系统调用. arc4random API 引入于 OpenBSD 2.1 和 FreeBSD 8.0.
BOOST_FILESYSTEM_DISABLE_BCRYPT 未定义. 在库构建时检测 BCrypt API 是否存在. Boost.Filesystem 库在 Windows 上不使用 BCrypt API. 对其他平台无影响.

不再支持用户自定义的 BOOST_POSIX_API 和 BOOST_WINDOWS_API 宏.

构建目标库

如果使用 Boost 构建系统, 目标库会被自动构建. 参见入门. 也可以使用目录 libs/filesystem/build 中提供的 Jamfile 手动构建, 或者用户可以自行构造包含目标库源文件的 IDE 工程或 make 文件.

目标库源文件位于src 目录中. 这些源文件为 POSIX 或 Windows 兼容操作系统实现本库; 其他操作系统没有提供实现. 注意, 许多通常不被视为 POSIX 系统的操作系统, 如大型机遗留操作系统或嵌入式操作系统, 也支持 POSIX 兼容文件系统, 因此可以使用 Filesystem 库.

目标库可以构建为静态或动态 (shared/dll) 链接. 这由 BOOST_ALL_DYN_LINK 或 BOOST_FILESYSTEM_DYN_LINK 宏控制. 所用技术的说明参见Separate Compilation页面.

Cygwin 用户须知

需要 Cygwin 1.7 或更高版本, 因为仅支持带宽字符串的 GCC 版本.

本库的实现代码把 Cygwin 当作 POSIX 平台, 因此使用 POSIX API 和 POSIX 路径语法作为原生路径语法.

版本历史

Version 4

开发中 - 提高与 C++17 引入的 std::filesystem 的兼容性 (最初提案: ISO C++ File System Technical Specification). Filesystem TS 基于 Boost.Filesystem Version 3, 仅作了少量修改. 为 Version 3 编写的大多数用户代码应能不加修改地在 Version 4 上运行. 差异见单独章节.

Version 3

Boost 1.44.0 - June, 2010 - 通过单一类 path 实现国际化. 更统一的错误处理.

Peter Dimov 建议使用单一的 path 类, 而不是 basic_path 类模板. 这一想法成为 Version 3 重新设计的基础.

感谢 Robert Stewart, Zach Laine, Peter Dimov, Gregory Peele, Scott McMurray, John Bytheway, Jeff Flinn, Jeffery Bosboom 提出的意见.
