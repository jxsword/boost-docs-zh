本参考文档描述 C++ 程序可用于执行涉及文件系统 (包括路径、普通文件与目录) 的操作的组件.

一致性 [fs.conformance]

ISO/IEC 9945 一致性 [fs.conform.9945]

本参考文档中的某些行为是参照 ISO/IEC 9945 规定的. 这类行为实际如何实现则未作规定.

[注: 这构成实现操作系统相关行为的“仿佛”规则. 实践中, 实现通常会调用原生的操作系统 API. —注结束]

鼓励实现按 ISO/IEC 9945 定义的方式提供此类行为. 实现应当记录与 ISO/IEC 9945 定义的行为不同的任何行为. 对于不支持精确 ISO/IEC 9945 行为的实现, 鼓励其在实际操作系统与文件系统的限制下, 尽可能合理地提供接近 ISO/IEC 9945 的行为. 如果实现无法提供任何合理行为, 则应当以实现定义的方式报告错误.

[注: 这类错误可能通过 #error 指示、一个 static_assert、一个 filesystem_error 异常、特殊的返回值或其他某种方式报告. —注结束]

不要求实现提供特定文件系统不支持的行为.

[示例: 某些存储卡、相机存储器和软盘所使用的 FAT 文件系统不支持硬链接、符号链接以及能力更强的文件系统的许多其他特性. 只要求实现支持宿主操作系统支持的 FAT 特性. —示例结束]

在存在文件系统竞争的情况下, 本参考中描述的函数的行为可能与其规范不同. 不要求诊断.

如果文件系统竞争的可能性使得程序在调用本参考文档所述函数之前测试前置条件变得不可靠, 则不为该条件规定 要求条件, 而是将其规定为 抛出 条件.

[注: 作为设计惯例, 当程序在调用函数之前检测前置条件并不合理时, 就不规定前置条件. —注结束]

操作系统相关一致性 [fs.conform.os]

本参考文档中某些行为被规定为依赖操作系统 ([fs.def.osdep]). 实现所依赖的操作系统由实现定义.

允许实现依赖于操作系统模拟器而非实际操作系统.

[示例: 某个实现使用 Cygwin, 即针对某些 Windows® 操作系统版本的 Linux® API 模拟器. 该实现会把 Cygwin 定义为其操作系统. 用户可以查阅 Cygwin 文档以了解操作系统相关行为的细节. —示例结束]

这样的实现运行在 Cygwin 上是用户和一致性测试都能检测到的事实. 如果实现把 Linux 或 Windows 而不是 Cygwin 定义为其操作系统, 用户会被误导, 一致性测试也会失败, 因为实际行为是两者的混合.

定义 [fs.definitions]

以下定义适用于本参考文档全文:

操作系统相关行为 [fs.def.osdep]

依赖于操作系统的行为与特性的行为. 参见 [fs.conform.os].

文件 [fs.def.file]

可以被写入、读取或两者兼有的对象. 文件具有一定的属性, 包括类型. 文件类型包括普通文件与目录. 实现还可以支持其他类型的文件, 例如符号链接.

文件系统 [fs.def.filesystem]

文件的集合及其某些属性.

文件名 [fs.def.filename]

文件的名称. 文件名 "." 和 ".." 具有特殊含义. 文件名的以下特征依赖操作系统:

  • 允许的字符. 参见 [fs.os.examples].

  • 不允许的特定文件名.

  • 具有特殊含义的其他文件名.

  • 路径解析期间的大小写感知与敏感性.

  • 可能适用于普通文件之外的其他文件类型 (如目录) 的特殊规则.

路径 [fs.def.path]

标识文件在文件系统中位置的元素序列. 这些元素是 root-nameopt、 root-directoryopt 以及可选的文件名序列. [注: 路径名是路径的具体表示. —注结束]

绝对路径 [fs.def.absolute-path]

无需参照其他起始位置即可无歧义地标识文件位置的路径. 路径中决定其是否为绝对的元素依赖操作系统.

相对路径 [fs.def.relative-path]

不是绝对的路径, 因此只有相对于一个隐含的起始位置解析时才能无歧义地标识文件位置. 路径中决定其是否为相对的元素依赖操作系统. [注: 路径 "." 和 ".." 是相对路径. —注结束]

规范路径 [fs.def.canonical-path]

不含符号链接元素、也不含 "." 或 ".." 元素的绝对路径.

路径名 [fs.def.pathname]

表示路径名称的字符串. 路径名按通用路径名文法或依赖操作系统的原生路径名格式进行格式化.

原生路径名格式 [fs.def.native]

宿主操作系统接受的、依赖操作系统的路径名格式.

普通形式路径 [fs.def.normal]

不含冗余目录分隔符、当前目录 (dot) 或父目录 (dot-dot) 元素的路径. 空路径的普通形式是空路径. [v3:对以一个非根目录的 directory-separator 结尾的路径, 其普通形式是在原路径后追加一个当前目录 (dot) 元素. ]

链接 [fs.def.link]

把文件名与文件关联起来的目录项对象. 在某些文件系统上, 多个目录项可以把名称关联到同一个文件.

硬链接 [fs.def.hardlink]

指向已存在文件的链接. 有些文件系统支持对同一文件的多个硬链接. 如果文件的最后一个硬链接被移除, 文件本身也被移除.

[注: 硬链接可以被视为指向文件的共享所有权智能指针. —注结束]

符号链接 [fs.def.symlink]

一种文件类型, 其性质是: 当在路径名解析期间遇到该文件时, 文件存储的一个字符串会被用来修改路径名解析.

[注: 符号链接可以被视为指向文件的裸指针. 如果被指向的文件不存在, 该符号链接就被称为“悬空”符号链接. —注结束]

文件系统竞争 [fs.def.race]

多个线程、进程或计算机交错地访问与修改文件系统中同一对象时出现的状况.

错误报告 [fs.err.report]

Filesystem 库函数通常提供两个重载, 一个抛出异常来报告文件系统错误, 另一个设置 error_code.

[注: 这支持两种常见使用情形:

  • 文件系统错误确实属于异常并表明严重失败的用途. 抛出异常是最恰当的响应. 这是大多数日常编程的首选默认方式.

  • 文件系统错误属于常规情况、不一定代表失败的用途. 返回错误码是最恰当的响应. 这允许应用程序特定的错误处理, 包括简单地忽略错误.

—注结束]

不带 system::error_code& 类型参数的函数按如下方式报告错误, 除非另有规定:

  • 当实现对操作系统或其他底层 API 的调用产生错误, 使函数无法满足其规范时, 抛出 filesystem_error 类型的异常.

  • 存储分配失败按 C++ 标准 17.6.4.10 [res.on.exception.handling] 的描述通过抛出异常来报告.

  • 析构函数不抛出任何异常.

带有 system::error_code& 类型参数的函数按如下方式报告错误, 除非另有规定:

  • 如果实现对操作系统或其他底层 API 的调用产生错误, 使函数无法满足其规范, 则按该特定错误适当设置 system::error_code& 参数. 否则, 调用 clear(), 对象是 system::error_code& 参数.

  • 存储分配失败按 C++ 标准 17.6.4.10 [res.on.exception.handling] 的描述通过抛出异常来报告.

path 使用注意事项 [path.usage]

多线程注意事项

Filesystem 库函数不针对数据竞争提供保护. [修改在线程间共享的 Filesystem 库类型对象, 有引发未定义行为的风险, 除非该类型的对象被明确规定为可无数据竞争共享, 或者用户提供加锁机制. —注结束] [注: 因此 Filesystem 库的行为如同它是标准库的一部分, C++ 标准 17.6.4.10 Shared objects and the library [res.on.objects] 由此适用. —注结束]

Windows 注意事项

至少直到 2012 版本, Visual C++ 都未采用 C++11 风格的静态初始化锁, 因此 path::codecvt() 的初始化可能发生竞争——或是与自身, 或是与 path::imbue() (如果它们从不同线程调用). 一种变通办法是调用:

path::codecvt();  // ensure VC++ does not race during initialization.

(在启动任何附加线程之前在主线程中执行). [注: 由 Filesystem 实现自行加锁这一显而易见的修复方案行不通, 原因是 Microsoft 编译器存在一些不相关的问题; 对于静态链接, 运行时会在 main() 开始之前尝试执行初始化, 但那时不允许调用操作系统加锁函数. —注结束]

POSIX 注意事项

在使用环境变量确定路径编码的 POSIX 系统 (如 Linux, 但不包括 Mac OS X) 上, Filesystem 库的初始化可能抛出异常. 当 std::locale("") 因 LANG 之类的环境变量被设为无效值而抛出异常时, 就会发生这种情况, 因此它可能影响 std::locale("") 的任何使用, 而不只是 Filesystem 库. Filesystem 采用延迟初始化, 因此只在确实需要有效的 std::locale("") 时才抛出异常, 同时也保证异常在 main() 开始之后才抛出.

与其等待某个 Filesystem 库函数在调用 path::codecvt() 时意外触发异常, 需要对环境变量问题高度健壮的程序不妨在 try 块内抢先调用 std::locale(""), 捕获异常, 然后诊断或修复无效的环境变量.

path 迭代器 [path.itr]

路径迭代器 iterator、const_iterator、reverse_iterator 和 const_reverse_iterator 对存储路径名的元素进行迭代.

路径迭代器是满足双向迭代器要求 (C++ 标准, 24.1.4 Bidirectional iterators [lib.bidirectional.iterators]) 的常量迭代器. 迭代器的 value_type 是 path.

[注: 路径迭代器在内部存储其值对象, 解引用时返回对这些内部对象的引用. 它们不能与假设解引用得到的引用所指向的对象寿命长于迭代器本身的迭代器适配器 (如 std::reverse_iterator) 一起使用. —注结束]

调用 path 对象的任何非 const 成员函数, 都会使引用该对象元素的所有迭代器失效.

前向遍历次序如下:

  • root-name 元素 (如果存在).
  • root-directory 元素 (如果存在), 采用通用格式. [注: 要求采用通用格式是为了确保字典序比较正确工作. —注结束]
  • 逐个的 filename 元素 (如果存在).
  • [v3: Dot] [v4: 空路径], 如果存在一个或多个结尾的非根目录分隔符.

[注: 当存在结尾目录分隔符时, 把迭代期间的最后一个元素视为 [v3: dot] [v4: 空路径], 这使得能够在词法 (即语法) 上区分指向目录的路径与指向普通文件的路径. 这种区分在基于 POSIX 和 Windows 的操作系统上通常无关紧要, 但在其他操作系统上可能是必需的. —注结束]

后向遍历次序是前向遍历的逆序.

iterator begin() const;

返回: 前向遍历次序中第一个元素的迭代器. 如果没有元素, 则为尾迭代器.

iterator end() const;

返回: 尾迭代器.

返回: 后向遍历次序中第一个元素的迭代器. 如果没有元素, 则为尾迭代器.

directory_entry 对象存储一个 path 对象, 以及关于该路径所标识文件的若干缓存信息. 目前, 缓存信息包括一个用于非符号链接状态的 file_status 对象和一个用于符号链接状态的 file_status 对象.

[注: 由于对路径名执行 status() 可能是相对昂贵的操作, 某些操作系统把状态信息作为目录迭代的副产品提供. 缓存此类状态信息可以显著节省时间. 在存在文件系统竞争时, 缓存与非缓存的结果可能不同. —注结束]

对包含 15,047 个条目的目录进行迭代的实际冷启动计时: 非缓存状态查询为 6 秒, 而缓存状态查询为 1 秒. 测试环境为 Windows XP, 3.0 GHz 处理器, 配中等速度硬盘. 在以目录迭代副产品形式提供状态的 Linux 及源自 BSD 的系统上, 预期会有类似的提速.

[注: 缓存信息的准确集合可能随 Boost.Filesystem 版本而异, 也随不同操作系统与底层文件系统而异. 用户代码不得依赖某条信息是否被缓存. 这意味着调用 directory_entry 的大多数观察器与修改器可能触发也可能不触发可能失败的文件系统查询. 信息缓存纯粹是一项性能特性, 目的在于减少此类查询的数量. —注结束]

directory_iterator 满足输入迭代器的要求 (C++ 标准, 24.2.1, Input iterators [input.iterators]).

directory_iterator 从构造它所针对的目录读取后续元素, 如同调用 ISO/IEC 9945 的 readdir() or readdir_r(). 在构造 directory_iterator 之后以及每次调用 operator++ 时, 它读取一个目录元素并把有关信息存储到 directory_entry 类型的对象中. operator++ 不保持相等性; 也就是说, i == j 并不蕴含 ++i == ++j.

[注: 不保持相等性的实际后果是, 目录迭代器只能用于单遍算法. —注结束]

如果到达目录元素的末尾, 迭代器应变得等于尾迭代器的值. 无参数的构造函数 directory_iterator() 总是构造一个尾迭代器对象, 它应是唯一对结束条件有效的迭代器. 对尾迭代器执行 operator* 的结果未定义. 对任何其他迭代器值, 返回 const directory_entry&. 对尾迭代器执行 operator-> 是未定义行为. 对任何其他迭代器值, 返回 const directory_entry*.

两个尾迭代器总是相等. 尾迭代器不得与非尾迭代器相等.

上述措辞基于标准库 istream_iterator 的措辞.

调用 path() 成员——其宿主为 directory_entry 对象 (由解引用 directory_iterator 得到)——的结果, 是对一个 path 对象的引用; 该对象由构造迭代器所用的目录参数组成, 并如同通过 operator/= 一样追加了该目录项的文件名.

目录迭代不得为当前 (dot) 与父 (dot dot) 目录产生目录项.

对 directory_iterator 连续递增并解引用所得的目录项的次序未作规定.

[注: 执行目录迭代的程序可能希望测试解引用目录迭代器得到的路径是否确实存在. 它可能是指向不存在文件的符号链接. 出于移除与重命名条目之目的而递归遍历目录树的程序, 可能希望避免跟随符号链接.

如果在为目录构造 directory_iterator 之后, 有文件从该目录中被移除或加入其中, 那么此后对迭代器的递增是否会产生值为被移除或新增目录项的迭代器, 未作规定. 参见 ISO/IEC 9945 readdir_r(). —注结束]

<boost/filesystem/fstream.hpp> 头文件

为 C++ 标准库 <fstream> 头文件中的文件流类提供了替代类. 这些替代类公开继承自标准库类. 在 Boost.Filesystem 版本中, 构造函数与 open 函数接受 const path& 参数而不是 const char* 参数. 在语法或语义上没有其他差别.

namespace boost
{
  namespace filesystem
  {
    template < class charT, class traits = std::char_traits<charT> >
    class basic_filebuf : public std::basic_filebuf<charT,traits>
    {
    public:
      basic_filebuf<charT,traits>*
        open(const path& p, std::ios_base::openmode mode);
    };

    template < class charT, class traits = std::char_traits<charT> >
    class basic_ifstream : public std::basic_ifstream<charT,traits>
    {
    public:
      explicit basic_ifstream(const path& p, std::ios_base::openmode mode=std::ios_base::in)
      void open(const path& p, std::ios_base::openmode mode=std::ios_base::in);
    };

    template < class charT, class traits = std::char_traits<charT> >
    class basic_ofstream : public std::basic_ofstream<charT,traits>
    {
    public:
      explicit basic_ofstream(const path& p, std::ios_base::openmode mode=std::ios_base::out);
      void open(const path& p, std::ios_base::openmode mode=std::ios_base::out);
    };

    template < class charT, class traits = std::char_traits<charT> >
    class basic_fstream : public std::basic_fstream<charT,traits>
    {
    public:
      explicit basic_fstream(const path& p,
        std::ios_base::openmode mode=std::ios_base::in | std::ios_base::out);
      void open(const path& p,
        std::ios_base::openmode mode=std::ios_base::in | std::ios_base::out);
    };

    typedef basic_filebuf<char> filebuf;
    typedef basic_ifstream<char> ifstream;
    typedef basic_ofstream<char> ofstream;
    typedef basic_fstream<char> fstream;

    typedef basic_filebuf<wchar_t> wfilebuf;
    typedef basic_ifstream<wchar_t> wifstream;
    typedef basic_fstream<wchar_t> wfstream;
    typedef basic_ofstream<wchar_t> wofstream;

  }  // namespace filesystem
}  // namespace boost

Windows 长路径与 \\?\ 命名空间前缀

Microsoft Windows 的“最大路径长度限制 (Maximum Path Length Limitation)”规定:

在 Windows API 中 (有少数例外...), 路径的最大长度是 MAX_PATH, 定义为 260 个字符.

Windows API 的许多函数还有 Unicode 版本, 以允许使用扩展长度路径, 最大总路径长度为 32,767 个字符. ... 要指定扩展长度路径, 请使用 "\\?\" 前缀. 例如 "\\?\D:\very long path". [当然, C++ 字符串字面量要求反斜杠写成双份. ]

由于大多数 Boost.Filesystem 操作函数只是把类 path 对象的内容传给 Windows API, 它们确实可以配合扩展长度前缀工作. 但有些不能, 原因是 Windows 施加的限制.

实际上, "\\?\" 前缀告知底层 Windows API 该路径标识 Win32 文件系统命名空间中的一个对象, 并禁用 Windows API 的大多数内部路径处理 (包括规范化). 虽然它解除了长度限制, 但也对可接受的路径施加了许多其他限制, 在下节中列出. 还有许多其他具有不同特殊含义的前缀, 例如 "\\.\" (本地设备命名空间前缀) 和 "\??\" (NT 对象命名空间前缀). 注意, UNC 路径可以通过引用一个特殊的 "UNC" 设备来扩展前缀. 例如, "\\server\share" 可以扩展为 "\\?\UNC\server\share".

就 Boost.Filesystem 而言, 命名空间前缀被视为路径根名称的一部分. 例如, "\\?\c:\foo" 的根名称是 "\\?\c:". 选择这种解释是为了让根路径可以迭代, 即你可以列出 "\\?\c:\" 目录的内容, 只要驱动器 C: 存在且你具有必要的权限. [注意: 你无法列出 "\\?\" 的内容, 因为这样的路径不存在. ]

带命名空间前缀的路径的注意事项

  • 路径的单个组成部分仍然受特定文件系统所支持内容的限制, 通常是 255 个字符.
  • 只有反斜杠可作为目录分隔符. 斜杠不被视为分隔符.
  • 所有路径必须是绝对路径, 且不得包含 "." 或 ".." 组件.
  • 一旦绝对路径超过 260 个字符, 它实际上就被“毒化”了, 所有操作都必须使用扩展长度前缀. 因此, 即使像 create_directory("a") 这样简单的操作, 如果结果目录的绝对路径会超过 260 个字符, 也会失败.
  • 某些把参数路径分解后逐个处理相对目录或文件的 Boost.Filesystem 函数, 在带命名空间前缀的路径上无法正常工作.

Dietmar Kühl 贡献了最初的 Boost Filesystem 库 directory_iterator 设计. Peter Dimov、Walter Landry、Rob Stewart 和 Thomas Witt 在完善该库方面给予了特别的帮助.

create_directories、extension、basename 和 replace_extension 函数由 Vladimir Prus 开发. temp_directory_path 函数由 Jeff Flinn 贡献. David Svoboda 建议了 canonical 函数并提供了伪代码.

Howard Hinnant 和 John Maddock 评审了 version 2 提案的草案, 指出了许多错误或弱点, 使最终文档更加完善.

Peter Dimov 建议使用单一类 path, 并用成员模板适配多种字符串类型. 他的想法成为 version 3 path 设计的基础.
