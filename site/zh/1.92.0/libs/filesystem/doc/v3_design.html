引言

在 Boost.Filesystem.V2 (国际化) 评审期间, Peter Dimov 提出 basic_path 类模板过于笨重, 而能容纳多种字符类型与编码的单一 path 类型会更加灵活. 虽然当时我不愿意停下开发去探索这一想法如何实现, 或偏离 C++ 标准库所用的国际化模式, 但我常常想起 Peter 的建议. 随着 C++0x char16_t 与 char32_t 字符类型的出现, basic_path 类模板方法变得更加笨重, 因此是时候参照 Peter 的建议重新审视这个问题了.

问题

在 Filesystem.V2 中, 要容纳多种字符类型与编码的用户自定义函数的路径参数必须写成模板. 必须采用“正确行事”的重载或模板元编程, 才能允许参数写成字符串字面量. 它看起来是这样的:

template<class Path>
void foo( const Path & p );
inline void foo( const path & p )
{
  return foo<path>( p );
}
inline void foo( const wpath & p )
{
  return foo<wpath>( p );
}

对于如此简单的需求, 这实在难看; 如果函数接受多个 Path 参数且每个都可能是窄或宽字符, 就会出现组合爆炸. 如果要支持 C++0x 的 char16_t 与 char32_t 类型, 情况还会更糟.

解决方案

概览:

  • 单一的非模板 class path.
  • 每个成员函数都是一个模板, 容纳各种适用的字符类型, 包括用户定义的字符类型.
  • 在内部以操作系统 API 使用的类型的字符串保存路径; POSIX 用 std::string, Windows 用 std::wstring.

问题中给出的签名简化为:

void foo( const path & p );

这是代码复杂度的显著降低. 规范也变得更简单. 我相信它将更容易讲授, 并产生灵活得多的用户代码.

其他好处:

  • 所有多态性仍然发生在编译期.
  • 效率得到提高: 如有需要, 编码转换只在创建时发生一次, 而不是每次使用路径时都发生.
  • 实现代码的规模大约减半, 并且变得可读得多.

可能的问题:

  • 成员函数模板与隐式构造函数的组合, 可能在用户犯简单常见编码错误时导致不清晰的错误消息. 有了 C++ concepts 这应当会不成问题, 但在此之前, 通过 enable_if/disable_if 限制过于激进模板的工作仍在继续.

详情

编码 转换

宿主系统

char 字符串路径参数

宽字符串路径参数
以 char 为原生 API 路径字符类型的系统 (即类 POSIX 系统) 无转换. 发生转换, 由当前 path locale 的 codecvt facet 执行.
以 wchar_t 为原生 API 路径字符类型的系统 (即类 Windows 系统). 发生转换, 由当前 path locale 的 codecvt facet 执行. 无转换.

当类 path 函数参数类型与操作系统针对路径的 API 参数类型匹配时, 不执行转换, 而不是转换为指定的编码 (如某种 Unicode 编码). 这避免了意外后果等.

其他变更

统一的混合错误处理: 混合错误处理惯用法已一致地应用于所有适用的函数.
