重入

预处理器中的宏展开完全是函数式的. 因此, 不存在迭代. 遗憾的是, 预处理器也不允许递归. 这意味着库必须通过定义实现方式相似的多组宏来模拟迭代或递归.
为了说明, 下面是一个简单的拼接宏:
#define CONCAT(a, b) CONCAT_D(a, b)
#define CONCAT_D(a, b) a ## b

CONCAT(a, CONCAT(b, c)) // abc
对于上面这样的简单情形, 这没有问题, 但在如下场景中会发生什么:
#define AB(x, y) CONCAT(x, y)

CONCAT(A, B(p, q)) // CONCAT(p, q)
由于没有递归, 上面的示例展开为 CONCAT(p, q) 而不是 pq.
只有两种方法可以“修复”上面的问题. 第一, 可以在文档中说明 AB 使用 CONCAT, 并禁止类似上面的用法. 第二, 可以提供多个拼接宏....
#define CONCAT_1(a, b) CONCAT_1_D(a, b)
#define CONCAT_1_D(a, b) a ## b

#define CONCAT_2(a, b) CONCAT_2_D(a, b)
#define CONCAT_2_D(a, b) a ## b

#define AB(x, y) CONCAT_2(x, y)

CONCAT_1(A, B(p, q)) // pq
这解决了问题. 然而, 现在必须知道 AB 使用的不仅是 某个拼接宏, 而是具体地是 CONCAT_2.
更好的方案是把 使用哪个拼接宏抽象出来....
#define AB(c, x, y) CONCAT_ ## c(x, y)

CONCAT_1(A, B(2, p, q)) // pq
这是 泛型重入的一个示例, 在此例中是重入一组虚构的拼接宏. c 参数表示拼接构造的“状态”, 只要用户跟踪这个状态, AB 就可以在拼接宏内部使用.
库面临同样的选择. 它要么必须禁止一个构造出现在自身内部, 要么提供一个构造的多个等价定义, 并提供一种统一的 重入该构造的方式. 有几个构造 需要递归 (例如 BOOST_PP_WHILE). 因此, 库选择提供多组宏, 并带有在尚未使用过的宏处重入该组的机制.
具体而言, 库必须为 BOOST_PP_FOR、BOOST_PP_REPEAT 和 BOOST_PP_WHILE 提供重入. 有两种机制用于实现这一点: 状态参数 (如上面的拼接示例) 和 自动递归.

状态参数

上述每个构造 (BOOST_PP_FOR、BOOST_PP_REPEAT 和 BOOST_PP_WHILE) 都有一个关联的状态. 该状态提供了重入相应构造的手段.
每个这样的构造都会传入若干用户定义的宏 (用作谓词、操作等). 每当用户定义的宏被调用时, 都会收到调用它的构造的当前状态, 以便该宏在必要时可以重入相应的宏组.
这些状态以两种方式之一使用——要么拼接上去, 要么传给另一个宏.
使用这些状态参数的宏有三类. 第一, 宏组本身, 通过拼接重入. 第二, 表现得像是主宏组一部分的对应宏组. 它们也通过拼接重入. 第三, 在内部使用第一类或第二类宏的宏. 这些宏把状态作为附加实参接受.
BOOST_PP_WHILE 的状态用字母 D 表示. 传给 BOOST_PP_WHILE 的有两个用户定义的宏——一个谓词和一个操作. 当 BOOST_PP_WHILE 展开这些宏时, 它会传递自己的状态, 使这些宏能够重入 BOOST_PP_WHILE 宏组.
考虑下面这个展示该技术的乘法实现:
// The addition interface macro.
// The _D signifies that it reenters
// BOOST_PP_WHILE with concatenation.

#define ADD_D(d, x, y) \
   BOOST_PP_TUPLE_ELEM( \
      2, 0, \
      BOOST_PP_WHILE_ ## d(ADD_P, ADD_O, (x, y)) \
   ) \
   /**/

// The predicate that is passed to BOOST_PP_WHILE.
// It returns "true" until "y" becomes zero.

#define ADD_P(d, xy) BOOST_PP_TUPLE_ELEM(2, 1, xy)

// The operation that is passed to BOOST_PP_WHILE.
// It increments "x" and decrements "y" which will
// eventually cause "y" to equal zero and therefore
// cause the predicate to return "false."

#define ADD_O(d, xy) \
   ( \
      BOOST_PP_INC( \
         BOOST_PP_TUPLE_ELEM(2, 0, xy) \
      ), \
      BOOST_PP_DEC( \
         BOOST_PP_TUPLE_ELEM(2, 1, xy) \
      ) \
   ) \
   /**/

// The multiplication interface macro.

#define MUL(x, y) \
   BOOST_PP_TUPLE_ELEM( \
      3, 0, \
      BOOST_PP_WHILE(MUL_P, MUL_O, (0, x, y)) \
   ) \
   /**/

// The predicate that is passed to BOOST_PP_WHILE.
// It returns "true" until "y" becomes zero.

#define MUL_P(d, rxy) BOOST_PP_TUPLE_ELEM(3, 2, rxy)

// The operation that is passed to BOOST_PP_WHILE.
// It adds "x" to "r" and decrements "y" which will
// eventually cause "y" to equal zero and therefore
// cause the predicate to return "false."

#define MUL_O(d, rxy) \
   ( \
      ADD_D( \
         d, /* pass the state on to ADD_D */ \
         BOOST_PP_TUPLE_ELEM(3, 0, rxy), \
         BOOST_PP_TUPLE_ELEM(3, 1, rxy) \
      ), \
      BOOST_PP_TUPLE_ELEM(3, 1, rxy), \
      BOOST_PP_DEC( \
         BOOST_PP_TUPLE_ELEM(3, 2, rxy) \
      ) \
   ) \
   /**/

MUL(3, 2) // expands to 6
在上面的实现中有几点值得注意. 首先, 注意 ADD_D 如何重入 BOOST_PP_WHILE, 使用 d 状态参数. 其次, 注意 MUL 的操作 (由 BOOST_PP_WHILE 展开) 如何把状态传给 ADD_D. 这展示了通过实参和拼接两种方式进行的状态重入.
库中每个使用 BOOST_PP_WHILE 的宏都有一个状态重入变体. 如果该变体使用实参而非拼接, 它会以后缀 _D 结尾, 以标示其重入方式. 这方面的例子包括库自身的 BOOST_PP_ADD_D 和 BOOST_PP_MUL_D. 如果该变体使用拼接, 它会以下划线结尾, 再通过拼接状态补全. 这包括 BOOST_PP_WHILE 本身 (对应 BOOST_PP_WHILE_ ## d), 例如还有 BOOST_PP_LIST_FOLD_LEFT (对应 BOOST_PP_LIST_FOLD_LEFT_ ## d).
BOOST_PP_FOR 和 BOOST_PP_REPEAT 使用同一套约定, 但分别用字母 R 和 Z 来表示它们的状态.
另请注意, 上面的 MUL 实现虽然一眼看不出来, 却用到了 全部三种重入类型. 它不仅同时使用了两种 状态重入, 还使用了 自动递归....

自动递归

自动递归是一种极大简化可重入构造使用的技术. 使用它的方式就是干脆 不使用任何状态参数.
上面的 MUL 示例在直接使用 BOOST_PP_WHILE 时使用了自动递归. 换言之, MUL 仍然可以在 BOOST_PP_WHILE 内部使用, 即便它没有通过把状态拼接到 BOOST_PP_WHILE_ 来重入 BOOST_PP_WHILE.
为了做到这一点, 库使用了一个“技巧”. 尽管看起来不是这样, 宏 BOOST_PP_WHILE 其实并不接受三个实参. 事实上, 它根本不接受任何实参. 相反, BOOST_PP_WHILE 宏 展开为一个接受三个实参的宏. 它只是检测下一个可用的 BOOST_PP_WHILE_ ## d 宏是什么, 并返回它. 这个检测过程相当复杂, 所以这里我不打算深入 它如何工作, 只需说明它 确实有效.
使用自动递归来重入各组宏显然要简单得多. 它完全隐藏了底层实现细节. 那么, 既然它这么易用, 状态参数为什么仍然存在? 原因同样简单. 使用状态参数时, 状态在任何时刻都是 已知的. 而使用自动递归时并非如此. 自动递归机制必须在每个使用点 推导状态. 这带来了宏复杂度上的代价, 在某些情况下——尤其是在宏嵌套很深时——会使一些预处理器慢如爬行.

结论

为重入选择状态参数还是自动递归, 实际上是一种权衡. 自动递归的优势是易用性和实现封装. 在某些情况下, 这在某些预处理器上要付出性能代价. 而状态参数的主要优势是效率. 使用状态参数是获得 最大效率的唯一途径. 这种效率的代价是代码复杂度和实现细节的暴露.
