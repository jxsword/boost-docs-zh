C/C++ 预处理器的已知问题

预处理器元编程饱受激烈争论. 部分原因是对危险技术的糟糕体验, 例如用宏定义内联函数. 根据经验, 如果你能找到一种不用预处理器来完成某事的干净且可管理的方式, 那么就应当那样做.
让我们以“问题/解决方案”的形式考察一些广为人知的预处理器问题.

问题 #1

预处理器不遵循作用域, 因此宏可能意外地 (有时是无声无息地) 替换代码.
解决方案 A
全大写标识符只用于宏, 且仅用于宏. 这实际上消除了宏意外替换其他种类代码的可能性.
解决方案 B
使用局部宏惯用法:
#define MACRO ...
// use MACRO
#undef MACRO
这确保宏不会意外替换局部宏作用域之外的代码.
这种方案的一个问题是 #undef 无法自动化, 可能被遗忘. 有经验的程序员通常会在写宏定义之前 (时间上紧挨着) 或之后立即写下 #undef.
解决方案 C
使用唯一宏前缀惯用法.
#define UMP_MACRO
// use UMP_MACRO
这使意外替换和命名冲突极不可能发生. 这种方案的问题包括:
  • 在一个大型项目中仍然可能出现命名冲突.
  • 宏仍然会污染全局命名空间.
只要可能就组合使用所有解决方案, 作用域问题就可以在很大程度上避免.

问题 #2

预处理器代码难以阅读. 它要求理解预处理器如何递归展开宏的基本过程: 找到宏定义, 并在头脑中替换宏的参数.
解决方案
任何编程都要求对代码如何执行有基本理解. 任何参数化技术——包括简单的函数和模板——都要求找到定义并在头脑中替换参数.
不过, 了解一些技巧是有益的:
  • 合理地尽量使用局部宏, 就能省去大部分查找过程.
  • 代码浏览器和文本搜索工具使查找定义更容易.
  • 可以用编译器生成预处理后的源代码, 以便查找缺陷.
  • 在把某样东西变成预处理器元程序之前, 先不用预处理器实现它的小规模版本. 然后自底向上工作, 用预处理器替换手工编写的构造. 这样你就可以增量地测试代码. 有经验的程序员常常跳过许多阶段, 但如果某样东西被证明太复杂而难以直接编写, 总是可以退回到增量方法.
  • 如果你在预处理代码中应当换行的地方插入一个特殊符号, 只需使用查找替换工具就能让预处理后的代码变得可读.
尤其要记住的一点是: 把预处理器的使用限制在结构化的、易于理解的、安全的方法上. 结构有助于理解复杂系统 [McConnell].

问题 #3

“我希望看到 Cpp 被废除.”——Bjarne Stroustrup, 见 [Stroustrup].
解决方案
C/C++ 预处理器还会存在很长时间.
在实践中, 预处理器元编程比模板元编程简单得多, 可移植性也强得多 [Czarnecki].
