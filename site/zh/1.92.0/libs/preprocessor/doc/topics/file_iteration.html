文件迭代

文件迭代是一种复杂但强大的纵向重复构造. 它对用户指定范围内的每个数字重复包含一个 文件.

Tutorial

该机制运行需要两条信息: 要迭代的范围, 以及每次迭代要包含的文件. 它还可以可选地接受第三条信息, 表示用于区分同一文件不同迭代的标志. 该机制通过一两个 命名外部实参 获取这些信息. 这些实参被指定为名为 BOOST_PP_ITERATION_PARAMS_x 的用户定义宏, 或者 BOOST_PP_FILENAME_x 与 BOOST_PP_ITERATION_LIMITS 的组合.
BOOST_PP_ITERATION_LIMITS 指定要迭代的值的范围. 它 必须展开为一个包含两个元素——下界和上界——的 元组. 上界和下界都必须是 0 到 BOOST_PP_LIMIT_ITERATION 范围内的数值. 例如, 如果用户希望对从 0 到 10 的数字包含某个文件, 那么 BOOST_PP_ITERATION_LIMITS 应这样定义:
#define BOOST_PP_ITERATION_LIMITS (0, 10)
注意, 宏名之后有一个空白. 该宏 并不接受 两个实参. 在上面的例子中, 如果没有这个空白, 就会发生预处理错误, 因为 0 和 10 不是有效的标识符.
在 BOOST_PP_ITERATION_LIMITS 宏中指定的上界和下界都是 会被求值的形参. 这意味着它们可以包含简单的算术或逻辑表达式. 例如, 上面的定义完全可以写成这样:
#define N() 5
#define BOOST_PP_ITERATION_LIMITS (0, N() + 5)
正因如此, 如果省略宏名后的空白, 该定义在语法上可能是有效的:
#define A 0
#define B 10
#define BOOST_PP_ITERATION_LIMITS(A, B)
   // note:  no whitespace       ^
如果发生这种情况, 该机制在尝试使用这个宏时会在内部产生错误. 由此产生的错误信息可能晦涩难懂, 所以请始终记得加上空白. 上面示例的 正确写法如下:
#define A 0
#define B 10
#define BOOST_PP_ITERATION_LIMITS (A, B)
   // note:  has whitespace      ^
BOOST_PP_FILENAME_x 指定要迭代的文件. x 是迭代维度的占位符. (目前, 我们假定它是 1——即第一维, 因此我们实际处理的是 BOOST_PP_FILENAME_1.) 该宏必须展开为一个有效的文件名——带引号或尖括号, 取决于文件的访问方式:
#define BOOST_PP_FILENAME_1 "file.h"
// -or-
#define BOOST_PP_FILENAME_1 <file.h>
现在, 执行一次简单文件迭代所需要做的就是调用该机制:
??=include BOOST_PP_ITERATE()
(??= 记号是 # 的三字符组 (trigraph). 我使用三字符组是为了清楚地表明我是在 包含一个文件, 而不是定义或展开宏, 但这并非必要. 即使是双字符组 (digraph) 版本 %: 也可以使用. 有些编译器不能顺利接受三字符组和双字符组, 请牢记这一点. 除此之外, 用哪个都可以, 随你喜欢.)
因此, 如果我们想对 "file.h" 从 1 迭代到 10, 只需把这些部件拼在一起:
#define BOOST_PP_ITERATION_LIMITS (1, 10)
#define BOOST_PP_FILENAME_1 "file.h"
??=include BOOST_PP_ITERATE()
上面的代码的效果是连续包含 "file.h" 十次.
或者, 迭代范围和要迭代的文件也可以在同一个宏 BOOST_PP_ITERATION_PARAMS_x 中表达. 同样, x 是迭代维度的占位符——我们假定它是 1. 该宏必须展开为一个 数组, 其中依次包含下界、上界、文件名和可选标志.
#define BOOST_PP_ITERATION_PARAMS_1 (3, (1, 10, "file.h"))
??=include BOOST_PP_ITERATE()
这与前一个版本的效果相同. 这两种指定参数的方式一次只能使用其中一种. (存在两种不同方法的原因与维度抽象有关, 我稍后会讲到.)
把一个文件包含十次并没有什么特别有用的地方. 区别在于当前宏状态每次都会改变. 例如, 当前“迭代值”可以通过 BOOST_PP_ITERATION() 获得. 如果 "file.h" 这样定义...
// file.h
template<> struct sample<BOOST_PP_ITERATION()> { };
...然后如下迭代它...
template<int> struct sample;

#define BOOST_PP_ITERATION_PARAMS_1 (3, (1, 5, "file.h"))
??=include BOOST_PP_ITERATE()
...每次的结果都不同:
template<> struct sample<1> { };
template<> struct sample<2> { };
template<> struct sample<3> { };
template<> struct sample<4> { };
template<> struct sample<5> { };
文件完全可以对自身进行迭代. 这样做的好处是代码可以放在一起. 问题在于, 你必须把文件的“常规”部分与被迭代部分区分开来. 本库提供了 BOOST_PP_IS_ITERATING 宏来帮助解决这个问题. 如果一次迭代正在进行中, 该宏被定义为 1. 例如, 要把 "file.h" 的内容合并到迭代它的文件中:
// sample.h
#if !BOOST_PP_IS_ITERATING

   #ifndef SAMPLE_H
   #define SAMPLE_H

   #include <boost/preprocessor/iteration/iterate.hpp>

   template<int> struct sample;

   #define BOOST_PP_ITERATION_PARAMS_1 (3, (1, 5, "sample.h"))
   ??=include BOOST_PP_ITERATE()

   #endif // SAMPLE_H

#else

   template<> struct sample<BOOST_PP_ITERATION()> { };

#endif
像这样使用同一个文件又引出了另一个问题. 当一个文件对自身执行两次独立的文件迭代时会发生什么? 这就是可选 flags 参数的用途. 它用于区分各次独立的迭代.
// sample.h
#if !BOOST_PP_IS_ITERATING

   #ifndef SAMPLE_H
   #define SAMPLE_H

   #include <boost/preprocessor/iteration/iterate.hpp>
   #include <boost/preprocessor/repetition/enum_params.hpp>
   #include <boost/preprocessor/repetition/enum_shifted_params.hpp>

   template<int> struct sample;

   #define BOOST_PP_ITERATION_PARAMS_1 (4, (1, 5, "sample.h", 1))
   ??=include BOOST_PP_ITERATE()

   template<class T, class U> struct typelist_t {
      typedef T head;
      typedef U tail;
   };

   template<int> struct typelist;
   struct null_t;

   template<> struct typelist<1> {
      template<class T0> struct args {
         typedef typelist_t<T0, null_t> type;
      };
   };

   #ifndef TYPELIST_MAX
   #define TYPELIST_MAX 50
   #endif

   #define BOOST_PP_ITERATION_PARAMS_1 (4, (2, TYPELIST_MAX, "sample.h", 2))
   ??=include BOOST_PP_ITERATE()

   #endif // SAMPLE_H

#elif BOOST_PP_ITERATION_FLAGS() == 1

   template<> struct sample<BOOST_PP_ITERATION()> { };

#elif BOOST_PP_ITERATION_FLAGS() == 2

   #define N BOOST_PP_ITERATION()

   template<> struct typelist<N> {
      template<BOOST_PP_ENUM_PARAMS(N, class T)> struct args {
         typedef typelist_t<
            T0,
            typename typelist<N - 1>::args<BOOST_PP_ENUM_SHIFTED_PARAMS(N, T)>::type
         > type;
      };
   };

   #undef N

#endif
注意 "flags" 参数的用法 (通过 BOOST_PP_ITERATION_FLAGS() 访问). 它区分了我们反复出现的 sample 迭代和 typelist 线性化迭代.
第二次迭代展示了文件迭代机制的威力. 它生成形如 typelist<3>::args<int, double, char>::type 的 typelist 线性化.
实际上, 继续这个 typelist 示例, 借助另一次迭代, 我们可以 完全线性化 typelist 的创建....
// extract.h
#if !BOOST_PP_IS_ITERATING

   #ifndef EXTRACT_H
   #define EXTRACT_H

   #include <boost/preprocessor/iteration/iterate.hpp>
   #include <boost/preprocessor/repetition/enum.hpp>
   #include <boost/preprocessor/repetition/enum_params.hpp>
   #include <boost/preprocessor/repetition/enum_trailing_params.hpp>

   // certain types such as "void" can't be function argument types

   template<class T> struct incomplete {
      typedef T type;
   };

   template<class T> struct strip_incomplete {
      typedef T type;
   };

   template<class T> struct strip_incomplete<incomplete<T> > {
      typedef T type;
   };

   template<template<int> class output, class func_t> struct extract;

   #ifndef EXTRACT_MAX
   #define EXTRACT_MAX 50
   #endif

   #define BOOST_PP_ITERATION_PARAMS_1 (3, (1, EXTRACT_MAX, "extract.h"))
   ??=include BOOST_PP_ITERATE()

   #endif // EXTRACT_H

#else

   #define N BOOST_PP_ITERATION()
   #define STRIP(z, n, _) \
      typename strip_incomplete<T ## n>::type \
      /**/

   template<template<int> class output, class R BOOST_PP_ENUM_TRAILING_PARAMS(N, class T)>
   struct extract<R (BOOST_PP_ENUM_PARAMS(N, T))> {
      typedef typename output<N>::template args<BOOST_PP_ENUM(N, STRIP, nil)>::type type;
   };

   #undef STRIP
   #undef N

#endif
现在我们可以定义一个辅助宏来完成这项工作:
#define TYPELIST(args) extract<typelist, void args>::type

typedef TYPELIST((int, double, incomplete<void>)) xyz;
这个结果有两个小问题. 首先, 像 void 这样的类型不能作为实参的类型, 因此必须用 incomplete<T> 包装. 其次, 必需的双层圆括号很烦人. 有了变参宏, TYPELIST 可以重新定义:
#define TYPELIST(...) extract<typelist, void (__VA_ARGS__)>::type

typedef TYPELIST(int, double, short) xyz;
另请注意, 在迭代内部也可以通过 BOOST_PP_ITERATION_START() 和 BOOST_PP_ITERATION_FINISH() 访问迭代的下界和上界.
希望这里给出的解释和示例展示了文件迭代的威力. 即便如此, 这仅仅是开始. 文件迭代机制还定义了一整套设施来支持多维迭代.

多个维度

文件迭代机制最多支持 BOOST_PP_LIMIT_ITERATION_DIM 个维度. 第一维 (即最外层) 我们在上面已经用过了. 要使用第二维 (在第一维之内), 只需把占位符 x 替换为 2 而不是 1.
#define BOOST_PP_ITERATION_PARAMS_2 /* ... */
                                  ^
...或者...
#define BOOST_PP_FILENAME_2 /* ... */
                          ^
每个维度必须从 1 开始 按顺序使用. 因此, 上面的代码 只能在第一维内部直接使用时才有效.
这里有必要进一步解释 BOOST_PP_ITERATION、BOOST_PP_ITERATION_START 和 BOOST_PP_ITERATION_FINISH. BOOST_PP_ITERATION() 展开为 当前维度的迭代值——不管那是哪个维度. 同样, BOOST_PP_ITERATION_START() 和 BOOST_PP_ITERATION_FINISH() 展开为 当前维度的下界和上界. 以下面的伪代码作参考:
for (int i = start(1); i <= finish(1); ++i) {
   // A
   for (int j = start(2); j <= finish(2); ++j) {
      // B
   }
   // C
}
在点 A 处, BOOST_PP_ITERATION() 引用 i. BOOST_PP_ITERATION_START() 和 BOOST_PP_ITERATION_FINISH() 分别引用 start(1) 和 finish(1). 而在点 B 处, BOOST_PP_ITERATION() 引用 j——即点 B 处的 当前迭代值. BOOST_PP_ITERATION_START() 也是如此, 它引用 start(2), 等等.
如果每个维度使用单独的文件, 那么不会有大的问题, 使用多个维度也很直接. 然而, 如果多个维度位于同一个文件中, 就需要把它们彼此区分开. 文件迭代机制为此提供了宏 BOOST_PP_ITERATION_DEPTH:
// file.h
#if !BOOST_PP_IS_ITERATING

   #ifndef FILE_H
   #define FILE_H

   #include <boost/preprocessor/iteration/iterate.hpp>

   #define BOOST_PP_ITERATION_PARAMS_1 (3, (1, 2, "file.h"))
   ??=include BOOST_PP_ITERATE()

   #endif // FILE_H

#elif BOOST_PP_ITERATION_DEPTH() == 1

   // A
   + BOOST_PP_ITERATION()

   #define BOOST_PP_ITERATION_PARAMS_2 (3, (1, 2, "file.h"))
   ??=include BOOST_PP_ITERATE()

   // C

#elif BOOST_PP_ITERATION_DEPTH() == 2

   // B
   - BOOST_PP_ITERATION()

#endif
这将产生如下结果:
+ 1
- 1
- 2
+ 2
- 1
- 2
多个维度又引出了另一个问题. 如何访问 当前维度以外的维度的状态? 换言之, 如何访问 i, 即它在点 A 处的取值? 由于预处理器的惰性求值, 这样做 行不通....
// ...

#elif BOOST_PP_ITERATION_DEPTH() == 1

   #define I BOOST_PP_ITERATION()

   #define BOOST_PP_ITERATION_PARAMS_2 (3, (1, 2, "file.h"))
   ??=include BOOST_PP_ITERATE()

   #undef I

#elif BOOST_PP_ITERATION_DEPTH() == 2

   #define J BOOST_PP_ITERATION()

   // use I and J

   #undef I

#endif
这里的问题在于, I 引用的是 BOOST_PP_ITERATION(), 而不是 值——即 BOOST_PP_ITERATION() 在 I 定义点处的取值.
本库提供了以两种方式访问这些值的宏——绝对方式或相对方式. 第一种访问特定迭代帧 (即维度) 的值. 要从 任何维度访问第一维的迭代值, 使用 BOOST_PP_FRAME_ITERATION(1). 要访问第二维的迭代值, 使用 BOOST_PP_FRAME_ITERATION(2), 依此类推.
还有帧版本用于访问维度的下界、上界和标志: BOOST_PP_FRAME_START、BOOST_PP_FRAME_FINISH 和 BOOST_PP_FRAME_FLAGS.
于是, 为了修复上一个示例, 我们修改 I 的定义....
// ...

#elif BOOST_PP_ITERATION_DEPTH() == 1

   #define I BOOST_PP_FRAME_ITERATION(1)

// ...
本库还提供了以 相对于当前维度的方式访问维度中值的宏 (例如 前一个维度). 这些宏接受一个实参, 该实参被解释为相对当前帧的偏移量. 例如, BOOST_PP_RELATIVE_ITERATION(1) 总是引用紧邻当前维度之前的外层维度. 实参 0 被解释为偏移量 0, 这使得 BOOST_PP_RELATIVE_ITERATION(0) 等价于 BOOST_PP_ITERATION(). BOOST_PP_RELATIVE_ITERATION(2) 引用紧邻“当前维度的前一维度”之前那个维度的迭代值.
维度的下界和上界也可以用同样方式访问, 分别使用 BOOST_PP_RELATIVE_START 和 BOOST_PP_RELATIVE_FINISH. 相对维度的标志可以用 BOOST_PP_RELATIVE_FLAGS 访问.

相对性

我前面提到过, 存在两种参数化该机制的方式是有原因的. 这个原因就是维度抽象. 在某些情况下, 被迭代的代码并不知道维度——可能因为这段代码在多个不同维度上被复用. 如果这段代码需要再次迭代, 它就必须 (基于维度) 定义正确的参数供该机制使用.
该机制维护的所有宏状态都可以用相对于某个维度的间接方式引用. 这就是 BOOST_PP_RELATIVE_ 访问器的用途.
同样, 用户定义的 命名外部实参 也可以用这种方式定义——例外是要迭代的文件名. 由于下界和上界由该机制 求值, 实现不再需要宏 BOOST_PP_ITERATION_LIMITS, 该标识符可以在每一维迭代中复用.
遗憾的是, 文件名则是另一回事. 本库无法对带引号 (或尖括号) 的文本求值. 因此, 它必须为每个维度使用不同的宏. 这就是 BOOST_PP_FILENAME_x 系列宏的用途. 它们的存在是为了隔离该机制所需的唯一不可抽象化的数据.
要以抽象的方式定义文件名, 你需要这样做:
#define UNIQUE_TO_FILE "some_file.h"

#if BOOST_PP_ITERATION_DEPTH() == 0
   #define BOOST_PP_FILENAME_1 UNIQUE_TO_FILE
#elif BOOST_PP_ITERATION_DEPTH() == 1
   #define BOOST_PP_FILENAME_2 UNIQUE_TO_FILE
#elif BOOST_PP_ITERATION_DEPTH() == 2
   #define BOOST_PP_FILENAME_3 UNIQUE_TO_FILE

// ... up to BOOST_PP_LIMIT_ITERATION_DIM

#endif
其意图是, 除了文件名之外, 不必对任何其他东西这样做. 如果在一个文件中需要多次这样做 (BOOST_PP_FILENAME_x 在被使用后会被该机制取消定义), 可以考虑使用单独的文件来做适当的定义:
# // detail/define_file_h.h
# ifndef FILE_H
#   error FILE_H is not defined
# endif
#
# if BOOST_PP_ITERATION_DEPTH() == 0
#   define BOOST_PP_FILENAME_1 FILE_H
# elif BOOST_PP_ITERATION_DEPTH() == 1
#   define BOOST_PP_FILENAME_2 FILE_H
# elif BOOST_PP_ITERATION_DEPTH() == 2
#   define BOOST_PP_FILENAME_3 FILE_H
# elif BOOST_PP_ITERATION_DEPTH() == 3
#   define BOOST_PP_FILENAME_4 FILE_H
# elif BOOST_PP_ITERATION_DEPTH() == 4
#   define BOOST_PP_FILENAME_5 FILE_H
# else
#   error unsupported iteration dimension
# endif
然后像这样使用它....
// file.h
#if !BOOST_PP_IS_ITERATING

   #ifndef FILE_H
   #define FILE_H "file.h"

   #define BOOST_PP_ITERATION_LIMITS (1, 10)
   #include "detail/define_file_h.h"

   ??=include BOOST_PP_ITERATE()

#endif // FILE_H

#else
   // iterated portion
#endif
像这样稍费一些功夫, 就可以维持抽象, 而无需付出本会需要的代码膨胀代价. 遗憾的是, 这不是一个完全通用的解决方案, 因为对每个唯一的文件名都得这样做, 但聊胜于无.

结论

关于该机制提供的设施, 介绍大致到此为止. 利用这些设施, 我们来实现一个 function_traits 模板, 以演示对该机制的完整运用.

函数特征——一个复杂的示例

实现一个全面的 function_traits 模板元函数需要用到文件迭代机制的每一个主要部分.
(本示例不打算绕过编译器缺陷, 它的存在只是为了说明该机制.)
结果应具有以下特性:
  • 返回类型
  • 参数的数量和类型
  • 该类型是否是函数指针、函数引用、成员函数指针或普通函数类型
  • 该类型是否带有省略号
  • 若不是成员函数指针, 则给出等价的函数指针、函数引用和函数类型
  • 否则, 给出成员指针类型、它所指的类类型, 以及它是否带有 const 和/或 volatile 限定
实现它的方式数不胜数. 这里我简要概述一下下面这个实现中所发生的事情.
该实现必然要处理函数元数 (arity). 因此, 至少我们需要在各个函数元数上迭代, 并定义主模板 function_traits 的偏特化. 变参函数 (即带省略号的函数) 使情况更加复杂. 因此, 对每个元数, 我们还需要一个变参版本.
我们还需要处理成员函数指针. 这意味着我们不仅要处理元数和变参, 还要处理 cv 限定.
为清晰起见, 下面的实现分开处理函数类型和成员函数指针. 它们本可以合并, 但结果会明显更加混乱.
为了处理函数类型, 下面的实现在各个函数元数上迭代. 对每个元数, 它在每个参数上迭代, 以便逐个访问它们. 然后它重新包含自身, 以定义同一元数的变参特化. 它大致执行以下伪代码的等价操作:
void make_spec(int i, bool variadic) {
   :open function_traits<i, variadic>
      for (int j = 0; j < i; ++j) {
         :parameter<j>
      }
   :close
   if (!variadic) {
      make_spec(i, true);
   }
   return;
}

void function_types(int max_arity) {
   for (int i = 0; i <= max_arity; ++i) {
      make_spec(i, false);
   }
   return;
}
成员函数指针的实现稍有不同. 首先, 它在各个 cv 限定符上迭代. 对每个 cv 限定符, 它在各个函数元数上迭代. 对每个函数元数, 它再次在每个参数上迭代. 然后它重新包含自身, 以定义同一元数的变参特化....
void make_spec(int j, const char* cv, bool variadic) {
   :open function_traits<j, cv, variadic>
      for (int k = 0; k < j; ++k) {
         parameter<k>
      }
   :close
   if (!variadic) {
      make_spec(j, cv, true);
   }
   return;
}

void gen_arities(const char* cv, int max_arity) {
   for (int j = 0; j <= max_arity; ++j) {
      make_spec(j, cv, false);
   }
   return;
}

void pointers_to_members(int max_arity) {
   static const char* cv_qualifiers[] = { "", "const", "volatile", "const volatile" };
   for (int i = 0; i < 4; ++i) {
      gen_arities(cv_qualifiers[i], max_arity);
   }
   return;
}
下面是完整的实现. 这个示例展示了文件迭代机制乃至整个库的威力, 所以如果你想完全理解该机制做什么, 请仔细研读....
// function_traits.hpp

#if !BOOST_PP_IS_ITERATING

#ifndef FUNCTION_TRAITS_HPP
#define FUNCTION_TRAITS_HPP

#include <boost/preprocessor/cat.hpp>
#include <boost/preprocessor/facilities/apply.hpp>
#include <boost/preprocessor/iteration/iterate.hpp>
#include <boost/preprocessor/iteration/self.hpp>
#include <boost/preprocessor/repetition/enum_params.hpp>
#include <boost/preprocessor/repetition/enum_trailing_params.hpp>
#include <boost/preprocessor/tuple/elem.hpp>

// enable user-expansion
#ifndef FUNCTION_TRAITS_MAX_ARITY
   #define FUNCTION_TRAITS_MAX_ARITY 15
#endif

namespace detail {

// avoid replication of "default" values
struct function_traits_base {
   static const bool is_plain = false;
   static const bool is_pointer = false;
   static const bool is_reference = false;
   static const bool is_member = false;
};

} // detail

// no definition
template<class> struct function_traits;

// extract ellipsis state
#define ELLIPSIS(n) \
   BOOST_PP_APPLY( \
      BOOST_PP_TUPLE_ELEM(2, n, ELLIPSIS_I) \
   ) \
   /**/

// iterate over function arities for function types
#define BOOST_PP_ITERATION_PARAMS_1 \
   (4, (0, FUNCTION_TRAITS_MAX_ARITY, "function_traits.hpp", 0)) \
   /**/
??=include BOOST_PP_ITERATE()

// obtain a cv-qualifier by index
#define QUALIFIER(n) \
   BOOST_PP_APPLY( \
      BOOST_PP_TUPLE_ELEM( \
         4, n, \
         (BOOST_PP_NIL, (const), (volatile), (const volatile)) \

#define BOOST_PP_ITERATION_PARAMS_1 \

??=include BOOST_PP_ITERATE()

#undef ELLIPSIS

// overriding jumper for pointers-to-functions
template<class T> struct function_traits<T*> : function_traits<T> {
   static const bool is_plain = false;
   static const bool is_pointer = true;
};

// overriding jumper for references-to-functions
template<class T> struct function_traits<T&> : function_traits<T> {
   static const bool is_plain = false;
   static const bool is_reference = true;
};
