A.1 动机

即使我们手中已拥有模板元编程和 Boost 元编程库 的全部能力, 某些 C++ 编码工作仍然需要大量样板式的代码重复. 我们在第 5 章实现 tiny_size 时就见过这样一个例子:

template <class T0, class T1, class T2>
struct tiny_size
  : mpl::int_<3> {};

除了上面主模板形参列表中重复出现的模式之外, 下面还有三个偏特化, 它们同样遵循一种可预测的模式:

template <class T0, class T1>
struct tiny_size<T0,T1,none>
  : mpl::int_<2> {};

template <class T0>
struct tiny_size<T0,none,none>
  : mpl::int_<1> {};

template <>
struct tiny_size<none,none,none>
  : mpl::int_<0> {};

在本例中, 这类带有“机械”味道的代码只有少量, 但如果我们实现的是 large 而不是 tiny, 代码量很容易就会多出许多. 当某个模式的实例数量超过两三个时, 手写它们往往会变得容易出错. 也许更重要的是, 代码会变得难以阅读, 因为代码中真正重要的抽象是模式本身, 而不是各个具体的实例.

A.1.1 代码生成

这类看似机械的代码其实应当以机械方式生成, 而不是手工编写. 编写好一个生成代码模式实例的程序之后, 库作者有两种选择: 一种做法是交付预先生成的源代码文件, 另一种是交付生成器本身. 两种方式都有缺陷. 如果客户只拿到生成的源代码, 他们就被困在库作者已生成的内容上——经验表明, 如果他们今天对某个模式的三个实例感到满意, 明天就会有人需要四个. 另一方面, 如果客户拿到的是生成程序, 他们还需要执行它的资源 (例如解释器), 并且必须把生成器集成到自己的构建过程中……

A.1.2 预处理器登场

……除非生成器本身就是一个预处理器元程序. 虽然并非为此目的而设计, 但 C 和 C++ 预处理器可以在编译的预处理阶段执行复杂的程序. 用户可以通过代码中的预处理器 #define 宏或编译器命令行上的 -D 选项来控制代码生成过程, 使构建集成变得轻而易举. 例如, 我们可以像下面这样为上文的主 tiny_size 模板引入参数:

#include <boost/preprocessor/repetition/enum_params.hpp>

#ifndef TINY_MAX_SIZE
#  define TINY_MAX_SIZE 3  // default maximum size is 3
#endif

template <BOOST_PP_ENUM_PARAMS(TINY_MAX_SIZE, class T)>
struct tiny_size
  : mpl::int_<TINY_MAX_SIZE>
{};

要测试这个元程序, 请让编译器以“预处理”模式 (通常是 -E 选项) 运行, 并把 Boost 根目录加入 #include 搜索路径. 例如:[1]

g++ -P -E -Ipath/to/boost_1_32_0 -I. test.cpp
[1] GCC 的 -P 选项可抑制在预处理输出中生成源文件名与行号标记.

只要有了合适的元程序, 用户不仅能调整 tiny_size 的形参个数, 还能仅通过用 #define 定义 TINY_MAX_SIZE 来调整整个 tiny 实现的最大规模.

Boost Preprocessor 库 [MK04] 在预处理器元编程中扮演的角色, 与 MPL 在模板元编程中的角色类似: 它提供了一套由高层组件 (如 BOOST_PP_ENUM_PARAMS) 组成的框架, 使原本棘手的元编程工作变得易于入手. 在本附录中, 我们不会试图涵盖预处理器工作原理的琐碎细节, 也不会涵盖预处理器元编程的一般原理, 甚至不会详细讨论 Preprocessor 库 本身的工作机制. 我们会以足够的高层视角向你展示相关内容, 使你能够高效地使用这个库, 并自行学习其余部分.

[MK04] Paul Mensonides 与 Vesa Karvonen. 《The Boost Preprocessor Library》. http://www.boost.org/libs/preprocessor.

A.2 预处理器的基本抽象

我们在第 2 章开始讨论模板元编程时, 首先描述了它的元数据 (潜在的模板实参) 和元函数 (类模板). 在这两个基本抽象的基础上, 我们构建了本书其余部分所涵盖的编译期计算的完整图景. 本节将为预处理器元程序员奠定类似的基础. 这里讲述的部分内容对你来说可能是复习, 但在深入细节之前, 先弄清这些基本概念十分重要.

A.2.1 预处理记号

预处理器中数据的基本单位是 预处理记号. 预处理记号大致对应你在 C++ 中惯用的记号, 如标识符、运算符符号和字面量. 严格来说, 预处理记号 与普通的 记号 之间存在一些差别 (详见 C++ 标准第 2 节), 但就本讨论而言可以忽略这些差别. 事实上, 我们在这里将交替使用这两个术语.

A.2.2 宏

预处理器宏有两种形式. 对象式宏可以这样定义:

#define 标识符 替换列表

其中, 标识符命名了被定义的宏, 替换列表则是零个或多个记号的序列. 当 标识符出现在后续程序文本中时, 预处理器会将其 展开为对应的 替换列表.

函数式宏充当“预处理阶段的元函数”, 其定义形式如下:

#define 标识符(a1, a2, ... an) 替换列表

其中每个 ai 都是一个命名 宏形参 的标识符. 当宏名后跟合适的实参列表出现在后续程序文本中时, 宏会被展开为其 替换列表, 只是每个实参都会替换 替换列表 中对应形参出现的位置. [2]

[2] 我们省略了宏展开工作方式的许多细节. 建议你花几分钟研读 C++ 标准的 16.3 节, 该节以简明的术语描述了这一过程.

A.2.3 宏实参

定义

一个 宏实参 是由以下内容构成的非空序列:

  • 逗号或圆括号之外的预处理记号, 和/或
  • 由配对圆括号包围的预处理记号.

这一定义对预处理器元编程的影响不容低估. 首先请注意, 下列记号具有特殊地位:

,  (  )

因此, 一个宏实参永远不可能包含不配对的圆括号, 也不可能包含未被配对圆括号包围的逗号. 例如, 下面 FOO 定义之后的两行都是非法的:

#define FOO(X) X // Unary identity macro
FOO(,)           // un-parenthesized comma or two empty arguments
FOO())           // unmatched parenthesis or missing argument

另请注意, 下列记号不具有特殊地位; 预处理器对配对的花括号、方括号或尖括号一无所知:

{  }  [  ]  <  >

因此, 下面这些行同样是非法的:

FOO(std::pair<int, long>)                // two arguments
FOO({ int x = 1, y = 2; return x+y; })   // two arguments

只要为其加上圆括号, 上面给出的任一记号串是可以作为单个宏实参的一部分来传递的:

FOO((std::pair<int,int>))                 // one argument
FOO(({ int x = 1, y = 2; return x+y; }))  // one argument

然而, 由于逗号的特殊地位, 在不知道宏实参中包含多少个以逗号分隔的记号序列的情况下, 是无法把圆括号从宏实参中剥掉的. [3] 如果你要编写一个需要接受含可变数量逗号的实参的宏, 你的用户要么必须为该实参加上圆括号, 并且把以逗号分隔的记号序列的个数作为附加实参传给你, 要么就必须把同样的信息编码到本附录稍后介绍的某个预处理器数据结构中.

[3] (1, 2) C99 预处理器凭借其变参宏可以做到这一点, 甚至更多. C++ 标准委员会很可能在 C++ 标准的下一个版本中采纳 C99 的预处理器扩展.

A.3 Preprocessor 库的结构

由于深入讲解 Boost Preprocessor 库超出了本书的范围, 我们将在这里尽力为你提供深入理解该库的工具. 为此, 你需要使用 Preprocessor 库的电子版文档, 它从你的 Boost 安装目录中 libs/preprocessor/ 子目录下的 index.html 文件开始.

在浏览器窗口的左侧你会看到一个索引; 如果点击“Headers”链接, 它会展示 boost/preprocessor/ 目录的结构. 库的大多数头文件按相关功能分组到各个子目录中. 顶层目录只包含少数几个提供通用宏的头文件, 另外每个子目录都有一个对应的头文件, 其作用只是 #include 该子目录中的所有头文件. 例如, boost/preprocessor/selection.hpp 所做的无非就是 #include 构成 boost/preprocessor/selection/ 内容的 min.hpp 和 max.hpp 这两个头文件. 名字不对应子目录的头文件通常声明一个宏, 其宏名与头文件名相同 (去掉扩展名) 并加上 BOOST_PP_ 前缀. 例如, boost/preprocessor/selection/max.hpp 声明了 BOOST_PP_MAX.

你还会注意到, 许多头文件还会声明一个带有 _D、_R 或 _Z 后缀的附加宏. [4] 例如, boost/preprocessor/selection/max.hpp 还声明了 BOOST_PP_MAX_D. 就本附录而言, 你应当忽略这些宏. 最终你会想弄清如何利用它们来优化预处理速度; 相关信息请查阅库文档 Topics 部分“reentrancy”小标题下的内容.

[4] 带有 _1ST、_2ND 或 _3RD 后缀的宏如果出现, 则出于另一个原因也应忽略: 它们已被弃用, 很快将从库中移除.

A.4 Preprocessor 库的抽象

本节将讨论 Preprocessor 库的基本抽象, 并为每种抽象给出一些简单示例.

A.4.1 重复

class T0, class T1... class Tn 这种借助于 BOOST_PP_ENUM_PARAMS 实现的重复生成, 是 水平重复 这一一般概念的一个具体实例. 该库还有垂直重复的概念, 我们稍后会讲到. 水平重复宏全部位于库的 repetition/ 子目录中.

A.4.1.1 水平重复

若使用水平重复来生成 tiny_size 的各个特化, 我们可以写出如下代码:

#include <boost/preprocessor/repetition.hpp>
#include <boost/preprocessor/arithmetic/sub.hpp>
#include <boost/preprocessor/punctuation/comma_if.hpp>

#define TINY_print(z, n, data) data

#define TINY_size(z, n, unused)                                 \
  template <BOOST_PP_ENUM_PARAMS(n, class T)>                   \
  struct tiny_size<                                             \
      BOOST_PP_ENUM_PARAMS(n,T)                                 \
      BOOST_PP_COMMA_IF(n)                                      \
      BOOST_PP_ENUM(                                            \
          BOOST_PP_SUB(TINY_MAX_SIZE,n), TINY_print, none)      \
  >                                                             \
    : mpl::int_<n> {};

BOOST_PP_REPEAT(TINY_MAX_SIZE, TINY_size, ~)

#undef TINY_size
#undef TINY_print

代码生成过程由调用 BOOST_PP_REPEAT 启动, 它是一个 高阶宏, 会反复调用由其第二个实参所指定的宏 (TINY_size). 第一个实参指定重复调用的次数, 第三个实参可以是任意数据; 它会原封不动地传递给被调用的宏. 在本例中, TINY_size 并未使用该数据, 因此传入 ~ 只是随意的选择. [5]

[5] ~ 并非完全随意的选择. @ 和 $ 本来也是不错的候选, 只是严格来说它们并不属于 C++ 实现必须支持的基本字符集. 而像 ignored 这样的标识符则可能被宏展开, 从而导致意外的结果.

每当 TINY_size 宏被 BOOST_PP_REPEAT 调用一次, 它就会生成 tiny_size 的一个不同特化. 该宏接受三个形参.

  • z 与我们前面提到的 _Z 宏后缀有关. 除非出于优化目的, 否则你永远不需要使用它, 现在可以放心地忽略.
  • n 是重复索引. 在 TINY_size 的多次调用中, n 依次为 0、1、2 等等.
  • unused 在本例中于每次重复时都是 ~. 一般而言, 被 BOOST_PP_REPEAT 调用的宏所收到的最后一个实参, 总是与调用者自身的最后一个实参相同.

由于它的 替换列表跨越多行, TINY_size 除最后一行外的每一行都以一个反斜杠续行. 其中开头几行只是调用 BOOST_PP_ENUM_PARAMS (我们在主模板中已经用过它) 来生成以逗号分隔的列表, 因此 TINY_size 的每次调用都会产生与下面等价的内容:[6]

template <class T0, class T1, ... class Tn-1>
struct tiny_size<
    T0, T1, ... Tn-1
    ...more... 
> 
  : mpl::int_<n> {};
[6] 请注意, 续行符以及其后的换行符都会被预处理器移除, 因此生成的代码在预处理输出中实际上出现在同一行内.

BOOST_PP_COMMA_IF 在其数值实参不为 0 时会生成一个逗号. 当 n 为 0 时, 前一行生成的列表为空, 此时紧跟在 < 字符之后的前导逗号将是非法的.

下一行使用 BOOST_PP_ENUM 生成 TINY_MAX_SIZE-n 个以逗号分隔的 none 副本. BOOST_PP_ENUM 与 BOOST_PP_REPEAT 的唯一区别在于它会在各次重复之间生成逗号, 因此它的第二个实参 (此处为 TINY_print) 必须与 TINY_size 具有相同的签名. 在本例中, TINY_print 忽略其重复索引 n, 只是简单地返回它的第三个实参 none.

BOOST_PP_SUB 实现了记号减法. 关键要理解: 尽管预处理器本身能够对普通的算术表达式求值:

#define X 3
...
#if X - 1 > 0  // OK
  whatever
#endif

但预处理器元程序只能操作记号. 通常, 当 Preprocessor 库中的宏需要一个数值实参时, 该实参必须作为单个记号传入. 如果我们在上面写的是 TINY_MAX_SIZE-n 而不是 BOOST_PP_SUB(TINY_MAX_SIZE,n), 那么 BOOST_PP_ENUM 的第一个实参在每次调用时将包含三个记号: 先是 3-0, 然后 3-1, 最后 3-2. 而 BOOST_PP_SUB 生成的则是单记号结果: 在相继的各次重复中, 先是 3, 然后 2, 最后 1.

命名约定

请注意, TINY_print 和 TINY_size 在使用之后立即被 #undef 取消定义, 中间没有插入任何 #include. 因此它们可以被视为“局部”宏定义. 由于预处理器不遵循作用域边界, 必须谨慎选择名字以防止冲突. 我们建议局部宏采用 PREFIXED_lower_case 形式的名字, 全局宏采用 PREFIXED_UPPER_CASE 形式的名字. 唯一的例外是单个小写字母的名字, 它们用作局部宏是安全的: 因为其他头文件不太可能 #define 一个全局的单字母小写宏——那样做是非常失礼的行为.

A.4.1.2 垂直重复

如果把上一个例子送入你的预处理器, 你会看到一行很长的输出, 其中包含类似这样的内容:

template <> struct tiny_size< none , none , none > : mpl::int_<0>
 {}; template < class T0> struct tiny_size< T0 , none , none > :
mpl::int_<1> {}; template < class T0 , class T1> struct tiny_size
< T0 , T1 , none > : mpl::int_<2> {};

水平重复的显著特征是: 重复模式的所有实例都生成在预处理输出的同一行上. 对于某些任务, 比如生成主 tiny_size 模板, 这完全没有问题. 然而在本例中, 它至少有两个缺点.

  1. 如果不手工重新排版生成的代码, 就很难验证我们的元程序是否在正确地工作.
  2. 嵌套水平重复的效率在不同预处理器之间差异很大. 通过水平重复生成的每个特化内部还包含三个水平重复: 两次调用 BOOST_PP_ENUM_PARAMS 和一次调用 BOOST_PP_ENUM. 当 TINY_MAX_SIZE 为 3 时你可能永远不会在意, 但在今天仍在使用的至少一种预处理器上, 当 TINY_MAX_SIZE 达到 8 时编译就会明显变慢. [7]
[7] 话虽如此, 其他一些预处理器可以毫无速度问题地处理 256 * 256 的嵌套重复.

解决这些问题的办法自然就是 垂直重复, 它把模式的实例生成在多行上. Preprocessor 库提供了两种垂直重复手段: 局部迭代和文件迭代.

局部迭代

在我们的例子中演示局部迭代最便捷的方式, 是把对 BOOST_PP_REPEAT 的调用替换为如下内容:

#include <boost/preprocessor/iteration/local.hpp>

#define BOOST_PP_LOCAL_MACRO(n)   TINY_size(~, n, ~)
#define BOOST_PP_LOCAL_LIMITS     (0, TINY_MAX_SIZE - 1)
#include BOOST_PP_LOCAL_ITERATE()

局部迭代反复调用一个具有特殊名字 BOOST_PP_LOCAL_MACRO 的用户自定义宏, 传给它的实参是迭代索引. 由于我们手头已有 TINY_size, 所以只是把 BOOST_PP_LOCAL_MACRO 定义为对它的调用. 迭代索引的范围由另一个用户自定义宏 BOOST_PP_LOCAL_LIMITS 给出, 它必须展开为一个带圆括号的整数值对, 表示索引值的闭区间范围, 这些索引值将传递给 BOOST_PP_LOCAL_MACRO. 请注意, 这是库中少数期望数值实参可以为多记号表达式的地方之一.

最后, 通过 #include 引入调用 BOOST_PP_LOCAL_ITERATE 的结果来启动重复, 该结果最终将是 Preprocessor 库自身中的一个文件. 许多预处理器处理重复文件包含的速度比处理嵌套水平重复更快, 你可能觉得意外, 但事实确实如此.

如果把这个新例子送入预处理器, 我们会在输出的三个独立行上看到如下内容:

template <> struct tiny_size< none , none , none > : mpl::int_<0>
 {};

template < class T0> struct tiny_size< T0 , none , none > : mpl::
int_<1> {};

template < class T0 , class T1> struct tiny_size< T0 , T1 , none
> : mpl::int_<2> {};

这在可验证性上是一个巨大的改进, 但仍不理想. 随着 TINY_MAX_SIZE 增大, 越来越难看清该模式是否在生成我们想要的内容. 如果能在输出中获得更多换行, 它就能保持更易辨认的形式.

到目前为止我们用过的两种重复方法还有另一个缺点, 尽管它在本例中没有显露出来. 设想一下, 如果 tiny_size 有一个我们想要调试的成员函数, 会发生什么. 如果你曾试着用调试器单步执行一个由预处理器宏生成的函数, 你就会知道这充其量是一次令人沮丧的体验: 调试器向你显示的行是最初调用宏的那一行, 它通常与生成的代码毫无相似之处. 更糟的是, 在调试器看来, 所生成函数中的每一条语句都占据同一行.

文件迭代

显然, 可调试性取决于在生成的代码与源文件中描述代码模式的那些行之间保持关联. 文件迭代通过反复 #include 同一个源文件来生成模式实例. 文件迭代对可调试性的影响与模板类似: 尽管各个实例在调试器中看起来占据相同的源代码行, 我们确实获得了单步执行该函数源代码的体验.

要在我们的例子中应用文件迭代, 可以把先前的局部迭代代码和 TINY_size 的定义替换为:

#include <boost/preprocessor/iteration/iterate.hpp>
#define BOOST_PP_ITERATION_LIMITS (0, TINY_MAX_SIZE - 1)
#define BOOST_PP_FILENAME_1       "tiny_size_spec.hpp"
#include BOOST_PP_ITERATE()

BOOST_PP_ITERATION_LIMITS 遵循与 BOOST_PP_LOCAL_LIMITS 相同的模式, 允许我们指定一个闭区间的迭代索引范围. BOOST_PP_FILENAME_1 指定要反复 #include 的文件名 (我们稍后会展示该文件). 末尾的 1 表示这是文件迭代的第一层嵌套——如果需要在 tiny_size_spec.hpp 内部再次调用文件迭代, 就得改用 BOOST_PP_FILENAME_2.

tiny_size_spec.hpp 的内容你应当觉得眼熟; 它的大部分与 TINY_size 的 替换列表相同, 只是没有反斜杠:

#define n BOOST_PP_ITERATION()

template <BOOST_PP_ENUM_PARAMS(n, class T)>
struct tiny_size<
    BOOST_PP_ENUM_PARAMS(n,T)
    BOOST_PP_COMMA_IF(n)
    BOOST_PP_ENUM(BOOST_PP_SUB(TINY_MAX_SIZE,n), TINY_print, none)
>
  : mpl::int_<n> {};

#undef n

库通过 BOOST_PP_ITERATION() 的结果把迭代索引传递给我们; n 只是一个用于减少语法噪音的便捷局部宏. 请注意, 我们没有使用 #include 保护宏, 因为我们需要 tiny_size_spec.hpp 被处理多次.

预处理结果现在应能保留模式的行结构, 并且在 TINY_MAX_SIZE 取较大值时更易验证. 例如, 当 TINY_MAX_SIZE 为 8 时, GCC 预处理阶段的输出中会出现如下片段:

...
template < class T0 , class T1 , class T2 , class T3>
struct tiny_size<
    T0 , T1 , T2 , T3
    ,
    none , none , none , none
>
  : mpl::int_<4> {};

template < class T0 , class T1 , class T2 , class T3 , class T4>
struct tiny_size<
    T0 , T1 , T2 , T3 , T4
    ,
    none , none , none
>
  : mpl::int_<5> {};
...etc.

自迭代

每次想为文件重复表达一个琐碎的代码模式时都要创建 tiny_size_spec.hpp 这样一个全新的文件, 可能会很不方便. 幸运的是, 库提供了一个宏, 允许我们把模式直接放在发起迭代的文件中. 只要处于迭代之中, BOOST_PP_IS_ITERATING 就会被定义为一个非零值. 我们可以利用该值在文件中区分发起迭代的部分与提供重复模式的部分. 下面是一个演示自迭代的完整 tiny_size.hpp 文件. 请特别留意 #include 保护宏 TINY_SIZE_HPP_INCLUDED 的位置和用法:

#ifndef BOOST_PP_IS_ITERATING

#  ifndef TINY_SIZE_HPP_INCLUDED
#    define TINY_SIZE_HPP_INCLUDED

#    include <boost/preprocessor/repetition.hpp>
#    include <boost/preprocessor/arithmetic/sub.hpp>
#    include <boost/preprocessor/punctuation/comma_if.hpp>
#    include <boost/preprocessor/iteration/iterate.hpp>

#    ifndef TINY_MAX_SIZE
#      define TINY_MAX_SIZE 3  // default maximum size is 3
#    endif

// primary template
template <BOOST_PP_ENUM_PARAMS(TINY_MAX_SIZE, class T)>
struct tiny_size
  : mpl::int_<TINY_MAX_SIZE>
{};

// generate specializations
#    define BOOST_PP_ITERATION_LIMITS (0, TINY_MAX_SIZE - 1)
#    define BOOST_PP_FILENAME_1       "tiny_size.hpp" // this file
#    include BOOST_PP_ITERATE()

#  endif // TINY_SIZE_HPP_INCLUDED

#else // BOOST_PP_IS_ITERATING

#  define n BOOST_PP_ITERATION()

#  define TINY_print(z, n, data) data

// specialization pattern
template <BOOST_PP_ENUM_PARAMS(n, class T)>
struct tiny_size<
    BOOST_PP_ENUM_PARAMS(n,T)
    BOOST_PP_COMMA_IF(n)
    BOOST_PP_ENUM(BOOST_PP_SUB(TINY_MAX_SIZE,n), TINY_print, none)
>
  : mpl::int_<n> {};

#  undef TINY_print
#  undef n

#endif // BOOST_PP_IS_ITERATING

更多

文件迭代的内容远不止我们在此能展示的这些. 更多细节请深入研读库中关于 BOOST_PP_ITERATE 及相关宏的电子文档. 另外需要注意的是, 没有哪一种重复技术在任何方面都优于其他技术: 你的选择可能取决于便利性、可验证性、可调试性、编译速度, 以及你自己对“逻辑连贯性”的感觉.

A.4.3 控制结构

在其 control/ 目录中, Preprocessor 库提供了一个宏 BOOST_PP_IF(c,t,f), 它扮演着与 mpl::if_ 类似的角色. 为了探究“control”这一组宏, 我们将为一个泛型函数对象框架生成代码: Boost Function 库. [8] boost::function 针对不超过库所支持上限的每种元数的函数类型实参做了偏特化:

template <class Signature> struct function;   // primary template

template <class R>                                   // arity = 0
struct function<R()>
  definition not shown...

template <class R, class A0>                         // arity = 1
struct function<R(A0)>
  definition not shown...

template <class R, class A0, class A1>               // arity = 2
struct function<R(A0,A1)>
  definition not shown...

template <class R, class A0, class A1, class A2>     // arity = 3
struct function<R(A0,A1,A2)>
  definition not shown...

etc.
[8] 在第 9 章讨论类型擦除时, 我们简要谈到了 Boost Function 的设计. 更多信息参见随书附带 CD 中的 Function 库文档 boost_1_32_0/libs/function/index.html.

我们已经介绍过可用于生成上述模式的几种策略, 所以不再赘述这部分问题; 我们为 tiny_size 采用的文件迭代方法在这里就很好用:

#ifndef BOOST_PP_IS_ITERATING

#  ifndef BOOST_FUNCTION_HPP_INCLUDED
#    define BOOST_FUNCTION_HPP_INCLUDED

#    include <boost/preprocessor/repetition.hpp>
#    include <boost/preprocessor/iteration/iterate.hpp>

#    ifndef FUNCTION_MAX_ARITY
#      define FUNCTION_MAX_ARITY 15
#    endif

template <class Signature> struct function;   // primary template

// generate specializations
#    define BOOST_PP_ITERATION_LIMITS (0, FUNCTION_MAX_ARITY)
#    define BOOST_PP_FILENAME_1    "boost/function.hpp" // this file
#    include BOOST_PP_ITERATE()

#  endif // BOOST_FUNCTION_HPP_INCLUDED

#else // BOOST_PP_IS_ITERATING

#  define n BOOST_PP_ITERATION()

// specialization pattern
template <class R BOOST_PP_ENUM_TRAILING_PARAMS(n, class A)>
struct function<R ( BOOST_PP_ENUM_PARAMS(n,A) )>
  definition not shown...

#  undef n

#endif // BOOST_PP_IS_ITERATING

BOOST_PP_ENUM_TRAILING_PARAMS (上面用到过) 与 BOOST_PP_ENUM_PARAMS 几乎一样, 区别在于当它的第一个实参不为 0 时, 它会生成一个前导逗号.

A.4.3.1 实参选择

为了与 C++ 标准库算法互操作, 如果一元或二元的 function 分别派生自 std::unary_function 或 std::binary_function 的相应特化, 也许会更好. [9] BOOST_PP_IF 是处理特例的好工具:

#  include <boost/preprocessor/control/if.hpp>
#  include <boost/preprocessor/comparison/equal.hpp>

// specialization pattern
template <class R BOOST_PP_ENUM_TRAILING_PARAMS(n, class A)>
struct function<R ( BOOST_PP_ENUM_PARAMS(n,A) )>
  BOOST_PP_IF(
      BOOST_PP_EQUAL(n,2), : std::binary_function<A0, A1, R>
    , BOOST_PP_IF(
          BOOST_PP_EQUAL(n,1), : std::unary_function<A0, R>
        , ...empty argument...
      )
  )
{ ...class body omitted... };
[9] 虽然从 std::unary_function 或 std::binary_function 派生对于与某些较旧的库实现互操作可能是必要的, 但当两个这样的派生类同属一个对象时, 它可能妨碍空基类优化 (EBO) 生效. 更多信息见 9.4 节. 一般而言, 更好的做法是直接暴露 first_argument_type、second_argument_type 和 result_type 这些 typedef.

我们第一次尝试就遇到了几个问题. 首先, 不允许向预处理器传递空实参. [3] 其次, 由于尖括号得不到特殊处理, 上面 std::unary_function 和 std::binary_function 特化中的逗号被当作宏实参分隔符, 预处理器会报错说我们在两处给 BOOST_PP_IF 传递了错误数量的实参.

由于它集中体现了所有问题, 我们先聚焦于内层的 BOOST_PP_IF 调用. mpl::eval_if 所用的策略——选择一个零元函数来调用——在这里可以很好地工作. 预处理器没有与 mpl::eval_if 直接对应的东西, 但也确实不需要: 给 BOOST_PP_IF 再加一层圆括号就能获得正确的效果.

#define BOOST_FUNCTION_unary()    : std::unary_function<A0,R>
#define BOOST_FUNCTION_empty()    // nothing

...

    , BOOST_PP_IF(
          BOOST_PP_EQUAL(n,1), BOOST_FUNCTION_unary
        , BOOST_FUNCTION_empty
      )()

#undef BOOST_FUNCTION_empty
#undef BOOST_FUNCTION_unary

“什么也不生成”的零元宏非常常用, 以至于库的“facilities”组提供了一个: BOOST_PP_EMPTY. 为完成这个例子, 我们需要把求值一直延迟到外层的 BOOST_PP_IF 调用, 因为 std::binary_function<A0,A1,R> 同样有“逗号问题”:

#  include <boost/preprocessor/facilities/empty.hpp>

#  define BOOST_FUNCTION_binary() : std::binary_function<A0,A1,R>
#  define BOOST_FUNCTION_unary()  : std::unary_function<A0,R>

// specialization pattern
template <class R BOOST_PP_ENUM_TRAILING_PARAMS(n, class A)>
struct function<R ( BOOST_PP_ENUM_PARAMS(n,A) )>
  BOOST_PP_IF(
      BOOST_PP_EQUAL(n,2), BOOST_FUNCTION_binary
    , BOOST_PP_IF(
          BOOST_PP_EQUAL(n,1), BOOST_FUNCTION_unary
        , BOOST_PP_EMPTY
      )
  )()
{ 
    ...class body omitted...
};

#  undef BOOST_FUNCTION_unary
#  undef BOOST_FUNCTION_binary
#  undef n

请注意, 由于我们恰好在使用文件迭代, 本可以直接对 n 的值使用 #if:

  template <class R BOOST_PP_ENUM_TRAILING_PARAMS(n, class A)>
  struct function<R ( BOOST_PP_ENUM_PARAMS(n,A) )>
#if n == 2
    : std::binary_function<A0, A1, R>
#elif n == 1
    : std::unary_function<A0, R>
#endif

BOOST_PP_IF 的优势在于使我们能够把这一逻辑封装在一个以 n 为参数的可复用宏中, 并与所有重复构造兼容:

#define BOOST_FUNCTION_BASE(n)                                \
    BOOST_PP_IF(BOOST_PP_EQUAL(n,2), BOOST_FUNCTION_binary    \
      , BOOST_PP_IF(BOOST_PP_EQUAL(n,1), BOOST_FUNCTION_unary \
           , BOOST_PP_EMPTY                                   \
        )                                                     \
    )()

A.4.3.2 其他选择构造

BOOST_PP_IDENTITY 同样位于“facilities”组中, 它是 BOOST_PP_EMPTY 一个有趣的近亲:

#define BOOST_PP_IDENTITY(tokens) tokens BOOST_PP_EMPTY

你可以把它看作在创建一个返回 tokens 的零元宏: 当附加了空圆括号后, 尾部的 BOOST_PP_EMPTY 被展开, 只留下 tokens. 如果我们希望在 function 的元数不是一或二时从 mpl::empty_base 继承, 本可以使用 BOOST_PP_IDENTITY:

// specialization pattern
template <class R BOOST_PP_ENUM_TRAILING_PARAMS(n, class A)>
struct function<R ( BOOST_PP_ENUM_PARAMS(n,A) )>
  BOOST_PP_IF(
      BOOST_PP_EQUAL(n,2), BOOST_FUNCTION_binary
    , BOOST_PP_IF(
          BOOST_PP_EQUAL(n,1), BOOST_FUNCTION_unary
        , BOOST_PP_IDENTITY(: mpl::empty_base)
      )
  )()
{ 
    ...class body omitted...
};

另外值得一提的还有 BOOST_PP_EXPR_IF, 它根据第一个实参的布尔值生成第二个实参或者什么也不生成:

#define BOOST_PP_EXPR_IF(c,tokens)                           \
   BOOST_PP_IF(c,BOOST_PP_IDENTITY(tokens),BOOST_PP_EMPTY)()

因此 BOOST_PP_EXPR_IF(1,foo) 展开为 foo, 而 BOOST_PP_EXPR_IF(0,foo) 展开为空.

A.4.4 记号拼接

如果有一种泛型方式可以访问所有函数对象的返回类型和形参类型, 而不仅仅是一元和二元的, 那就太好了. 一个把签名作为 MPL 序列返回的元函数就能做到. 我们可以直接为每个 function 元数特化 signature:

template <class F> struct signature; // primary template

// partial specializations for boost::function
template <class R>
struct signature<function<R()> > 
  : mpl::vector1<R> {};

template <class R, class A0>
struct signature<function<R(A0)> > 
  : mpl::vector2<R,A0> {};

template <class R, class A0, class A1>
struct signature<function<R(A0,A1)> > 
  : mpl::vector3<R,A0,A1> {};

...

为了生成这些特化, 我们可以在模式中加入如下内容:

template <class R BOOST_PP_ENUM_TRAILING_PARAMS(n, class A)>
struct signature<function<R( BOOST_PP_ENUM_PARAMS(n,A) )> >
  : mpl::BOOST_PP_CAT(vector,n)<
      R BOOST_PP_ENUM_TRAILING_PARAMS(n,A)
    > {};

BOOST_PP_CAT 实现记号拼接; 它的两个实参被“粘合”成单个记号. 由于这是一个通用宏, 它位于库目录树顶层的 cat.hpp 中.

尽管预处理器有内建的记号拼接运算符 ##, 但它只能在宏定义内部使用. 如果我们在这里使用它, 它根本不会生效:

template <class R>
struct signature<function<R()> > 
  : mpl::vector##1<R> {};

template <class R, class A0>
struct signature<function<R(A0)> > 
  : mpl::vector##2<R,A0> {};

template <class R, class A0, class A1>
struct signature<function<R(A0,A1)> > 
  : mpl::vector##3<R,A0,A1> {};

...

此外, ## 常常在其实参被展开之前就生效, 从而产生令人意外的结果:

#define N           10
#define VEC(i)      vector##i

VEC(N)           // vectorN

相比之下, BOOST_PP_CAT 会把拼接延迟到其实参被完全求值之后:

#define N           10
#define VEC(i)      BOOST_PP_CAT(vector,i)

VEC(N)           // vector10

A.4.5 数据类型

Preprocessor 库还提供了数据类型, 你可以把它们类比为 MPL 的类型序列. 预处理器数据类型存储的是宏实参而非 C++ 类型.

A.4.5.1 序列

序列 (简称 seq) 是任意一串非空的带圆括号宏实参. 例如, 下面是一个三元素序列:

#define MY_SEQ   (f(12))(a + 1)(foo)

下面展示了如何用序列从 Boost Type Traits 库生成 is_integral 模板的特化 (见第 2 章):

#include <boost/preprocessor/seq.hpp>

template <class T>
struct is_integral : mpl::false_ {}; 

// a seq of integral types with unsigned counterparts
#define BOOST_TT_basic_ints            (char)(short)(int)(long)

// generate a seq containing "signed t" and "unsigned t"
#define BOOST_TT_int_pair(r,data,t)      (signed t)(unsigned t)

// a seq of all the integral types
#define BOOST_TT_ints                                           \
    (bool)(char)                                                \
    BOOST_PP_SEQ_FOR_EACH(BOOST_TT_int_pair, ~, BOOST_TT_basic_ints)

// generate an is_integral specialization for type t
#define BOOST_TT_is_integral_spec(r,data,t) \
   template <>                              \
   struct is_integral<t> : mpl::true_ {}; 

BOOST_PP_SEQ_FOR_EACH(BOOST_TT_is_integral_spec, ~, BOOST_TT_ints)

#undef BOOST_TT_is_integral_spec
#undef BOOST_TT_ints
#undef BOOST_TT_int_pair
#undef BOOST_TT_basic_ints

BOOST_PP_SEQ_FOR_EACH 是一个高阶宏, 类似于 BOOST_PP_REPEAT, 它对其第三个实参的每个元素调用其第一个实参.

序列是这个库的数据结构中最高效、最灵活、也最易用的, 前提是你永远不需要构造空序列: 空序列不含任何记号, 因此无法作为宏实参传递. 这里讲到的其他数据结构都有空表示.

操作序列的工具全部位于库的 seq/ 子目录中. 表 A.5 对它们做了汇总, 其中 t 指序列 (t0)(t1)...(tk). 出现 s、r 和 d 的地方, 它们的作用与我们前面讨论过的 (并建议你暂时忽略的) z 形参类似.

A.4.5.2 元组

元组是一种非常简单的数据结构, 库为它提供了随机访问和少数其他基本操作. 元组的形式是一个带圆括号、以逗号分隔的宏实参列表. 例如, 下面是一个三元素元组:

#define TUPLE3     (f(12), a + 1, foo)

库的 tuple/ 子目录中的运算最多可以处理 25 个元素的元组. 例如, 可以通过 BOOST_PP_TUPLE_ELEM 访问元组的第 N 个元素, 如下所示:

                 // length  index  tuple 
BOOST_PP_TUPLE_ELEM(   3   ,  1  , TUPLE3)   // a + 1

注意, 我们必须把元组的长度作为第二个实参传给 BOOST_PP_TUPLE_ELEM; 事实上, 所有元组运算都要求显式指定元组的长度. "tuple"组中的其他四个运算我们不在此汇总——更多细节请查阅 Preprocessor 库的电子文档. 不过我们要指出, 序列可以用 BOOST_PP_SEQ_TO_TUPLE 转换为元组, 而非空元组可以用 BOOST_PP_TUPLE_TO_SEQ 转换回序列.

元组最大的优势在于它方便地采用了与宏实参列表相同的表示形式:

#define FIRST_OF_THREE(a1,a2,a3)    a1
#define SECOND_OF_THREE(a1,a2,a3)   a2
#define THIRD_OF_THREE(a1,a2,a3)    a3

// uses tuple as an argument list
# define SELECT(selector, tuple)    selector tuple

SELECT(THIRD_OF_THREE, TUPLE3)   // foo

A.4.5.3 数组

数组只是一个包含了非负整数与一个该长度元组的元组:

#define ARRAY3     ( 3, TUPLE3 )

由于数组随身携带着自己的长度, 库中操作数组的接口比操作元组的接口方便得多:

BOOST_PP_ARRAY_ELEM(1, ARRAY3)     // a + 1

操作至多 25 个元素数组的工具全部位于库的 array/ 子目录中. 表 A.6 对它们做了汇总, 其中 a 指数组 (k, (a0,a1,...ak-1)).

A.4.5.4 列表

列表是一个二元素元组, 其第一个元素是列表的首元素, 第二个元素是由其余元素组成的列表; 若没有剩余元素, 则为 BOOST_PP_NIL. 列表的访问特性类似于运行期的链表. 下面是一个三元素列表:

#define LIST3     (f(12), (a + 1, (foo, BOOST_PP_NIL)))

操作列表的工具全部位于库的 list/ 子目录中. 由于这些运算只是序列所提供运算的一个子集, 我们不在此汇总——在了解序列的基础上阅读文档, 应当很容易理解这些列表运算.

与序列一样, 列表没有固定的长度上限. 与序列不同的是, 列表还可以为空. 在预处理器数据结构中很少需要超过 25 个元素, 而列表的操作往往比其他结构更慢、也更难读, 因此通常只应把它们作为最后的手段使用.
