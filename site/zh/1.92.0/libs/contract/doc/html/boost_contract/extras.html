旧值要求 (模板)

旧值需要复制传递给 BOOST_CONTRACT_OLDOF 的表达式, 因此该表达式的类型必须可复制. 更准确地说, 对类型为 boost::contract::old_ptr<T> 的旧值指针解引用, 要求 boost::contract::is_old_value_copyable<T>::value 是 true 的, 否则本库将产生编译期错误.

在某些情况下, 当程序使用不可复制的旧值类型时引发编译期错误是可以接受的, 甚至是可取的 (因为此时无法像使用这些旧值的契约断言所陈述的那样完整检查程序的正确性). 在这些情况下, 程序员可以像前文那样用 boost::contract::old_ptr 声明旧值.

然而, 在另一些情况下, 可能希望当相应旧值类型不可复制时直接跳过使用旧值的断言, 而不引发编译期错误. 程序员可以做到这一点: 使用 boost::contract::old_ptr_if_copyable 而不是 boost::contract::old_ptr, 并在后置条件中解引用旧值指针之前先检查它非空. 例如, 考虑下面这个函数模板, 它一般可以为不可复制构造的类型 T 实例化 (即 boost::contract::is_old_value_copyable<T>::value 为 false 的类型, 参见 old_if_copyable.cpp): [68] 

template<typename T> // T might or might not be copyable.
void offset(T& x, int count) {
    // No compiler error if T has no copy constructor...
    boost::contract::old_ptr_if_copyable<T> old_x = BOOST_CONTRACT_OLDOF(x);
    boost::contract::check c = boost::contract::function()
        .postcondition([&] {
            // ...but old value null if T has no copy constructor.
            if(old_x) BOOST_CONTRACT_ASSERT(x == *old_x + count);
        })
    ;

    x += count;
}

旧值指针 old_x 使用 boost::contract::old_ptr_if_copyable 编写. 当 T 可复制时, boost::contract::old_ptr_if_copyable<T> 的行为如同 boost::contract::old_ptr<T>. 而当 T 不可复制时, boost::contract::old_ptr_if_copyable<T> 只是在运行期不复制 x, 并让 old_x 保持初始化为空指针. 因此, 在把 boost::contract::old_ptr_if_copyable 对象 (如 old_x ) 在后置条件和异常保证中解引用之前, 必须像 if(old_x) ... 中那样检查它们非空 (以避免解引用空指针的运行期错误).

如果上面的示例改用 boost::contract::old_ptr, 那么当 offset 以不可复制构造的类型 T 实例化时, 本库将产生编译期错误 (但仅当 old_x 确实在某处被解引用时, 例如在使用 *old_x ... 或 old_x->... 的契约断言中). [69]

当把 C++11 auto 声明与 BOOST_CONTRACT_OLDOF 一起使用时, 本库总是默认使用 boost::contract::old_ptr 类型 (因为它的类型要求比 boost::contract::old_ptr_if_copyable 更严格). 例如, 以下语句是等价的:

auto old_x = BOOST_CONTRACT_OLDOF(x); // C++11 auto declarations always use `old_ptr` (never `old_ptr_if_copyable`).
boost::contract::old_ptr<decltype(x)> old_x = BOOST_CONTRACT_OLDOF(x);

如果程序员想放宽可复制类型要求, 就必须显式地使用 boost::contract::old_ptr_if_copyable 类型来做到, 而不是使用 auto 声明.

旧值类型特征

本库使用 boost::contract::is_old_value_copyable 来判定旧值类型是否可复制, 然后用 boost::contract::old_value_copy 来实际复制旧值.

默认情况下, boost::contract::is_old_value_copyable<T> 等价于 boost::is_copy_constructible<T>, 而 boost::contract::old_value_copy<T> 使用 T 的复制构造函数实现. 不过, 程序员可以对类型特征进行特化, 例如避免对某些类型做旧值复制 (即使它们有复制构造函数, 也许因为这些复制构造函数代价太高), 或者为没有复制构造函数的类型做旧值复制, 或者满足程序员对相关类型的任何其他特定需要.

例如, 下面对 boost::contract::is_old_value_copyable 的特化有意避免对类型为 w 的所有表达式做旧值复制, 即使该类型有复制构造函数 (参见 old_if_copyable.cpp):

// Copyable type but...
class w {
public:
    w(w const&) { /* Some very expensive copy operation here... */ }

    /* ... */


// ...never copy old values for type `w` (because its copy is too expensive).
namespace boost { namespace contract {
    template<>
    struct is_old_value_copyable<w> : boost::false_type {};
} }

反过来说, 下面这对 boost::contract::is_old_value_copyable 和 boost::contract::old_value_copy 的特化会为类型为 p 的表达式做旧值复制, 即使该类型实际上没有复制构造函数 (参见 old_if_copyable.cpp):

// Non-copyable type but...
class p : private boost::noncopyable {
    int* num_;

    friend struct boost::contract::old_value_copy<p>;

    /* ... */


// ...still copy old values for type `p` (using a deep copy).
namespace boost { namespace contract {
    template<>
    struct old_value_copy<p> {
        explicit old_value_copy(p const& old) {
            *old_.num_ = *old.num_; // Deep copy pointed value.
        }

        p const& old() const { return old_; }

    private:
        p old_;
    };

    template<>
    struct is_old_value_copyable<p> : boost::true_type {};
} }

一般而言, boost::is_copy_constructible 以及 boost::contract::is_old_value_copyable 需要 C++11 的 decltype 和 SFINAE 来自动检测给定类型是否可复制. 在非 C++11 编译器上, 可以让旧值类型继承 boost::noncopyable, 或使用 BOOST_MOVABLE_BUT_NOT_COPYABLE, 或特化 boost::is_copy_constructible (更多信息参见 boost::is_copy_constructible 文档), 或直接特化 boost::contract::is_old_value_copyable. 例如, 对于不可复制的类型 n, 下面的代码在非 C++11 编译器上也能工作 (参见 old_if_copyable.cpp):

class n { // Do not want to use boost::noncopyable but...
    int num_;

private:
    n(n const&); // ...unimplemented private copy constructor (so non-copyable).

    /* ... */


// Specialize `boost::is_copy_constructible` (no need for this on C++11).
namespace boost { namespace contract {
    template<>
    struct is_old_value_copyable<n> : boost::false_type {};
} }

断言要求 (模板)

一般而言, 断言可能对程序所用的类型引入一组新的要求. 其中一些类型要求可能只是检查断言所必需的, 程序本身并不需要它们.

在某些情况下, 当程序使用的类型未提供检查契约断言所需的全部操作时引发编译期错误是可以接受的, 甚至是可取的 (因为此时无法按契约的规定完整检查程序的正确性). 在这些情况下, 程序员可以像前文那样指定契约断言, 如果用户类型未提供检查契约所需的全部操作, 编译将失败.

然而, 在另一些情况下, 可能希望不因契约断言而增加程序的类型要求, 而是在用户类型未提供检查断言所需的全部操作时直接跳过断言, 不引发编译期错误. 程序员可以做到这一点: 在 C++17 编译器上使用 if constexpr, 在非 C++17 编译器上使用 boost::contract::condition_if (或 boost::contract::condition_if_c).

例如, 考虑下面的 vector<T> 类模板, 它等价于 std::vector<T>. C++ std::vector<T> 并不要求其值类型参数 T 具有相等运算符 == (它只要求 T 可复制构造, 参见 std::vector 文档). 然而, vector<T>::push_back(value) 公有函数的契约包含一个后置条件 back() == value, 它引入了新要求: T 也必须具有相等运算符 ==. 程序员可以照常用 BOOST_CONTRACT_ASSERT(back() == value) 指定这个后置条件, 让程序在用户以不提供相等运算符 vector<T> 的类型 T 实例化 == 时编译失败. 或者, 程序员可以用 C++17 的 if constexpr 来守护这个后置条件, 只为具有相等运算符 T 的类型 == 求值被断言的条件, 否则跳过它. [70] 例如:

template<typename T>
class vector {
public:
    void push_back(T const& value) {
        boost::contract::check c = boot::contract::public_function(this)
            .postcondition([&] {
                // Guard with `if constexpr` for T without `==`.
                if constexpr(boost::has_equal_to<T>::value)
                    BOOST_CONTRACT_ASSERT(back() == value);
            })
        ;

        vect_.push_back(value);
    }

    /* ... */

更一般地, if constexpr 可用于同时守护旧值复制和引入特定额外类型要求的契约断言. 例如, 下面的 swap 函数可以在任何可移动的类型 T 上调用, 但其旧值复制和后置条件断言只为同时可复制且具有相等运算符 T 的类型 == 求值 (参见 if_constexpr.cpp):

template<typename T>
void swap(T& x, T& y) {
    constexpr bool b = boost::contract::is_old_value_copyable<T>::value &&
            boost::has_equal_to<T>::value;
    boost::contract::old_ptr<T> old_x, old_y;
    if constexpr(b) { // Contract requires copyable T...
        old_x = BOOST_CONTRACT_OLDOF(x);
        old_y = BOOST_CONTRACT_OLDOF(y);
    }
    boost::contract::check c = boost::contract::function()
        .postcondition([&] {
            if constexpr(b) { // ... and T with `==`...
                BOOST_CONTRACT_ASSERT(x == *old_y);
                BOOST_CONTRACT_ASSERT(y == *old_x);
            }
        })
    ;

    T t = std::move(x); // ...but body only requires movable T.
    x = std::move(y);
    y = std::move(t);
}

不使用 if constexpr (不用 C++17)

在没有 if constexpr 可用的非 C++17 编译器上, 可以使用 boost::contract::condition_if 基于类型要求跳过断言 (尽管这种代码比使用 if constexpr 的可读性差、更冗长). 例如 (参见 condition_if.cpp):

template<typename T>
class vector {
public:
    void push_back(T const& value) {
        boost::contract::check c = boost::contract::public_function(this)
            .postcondition([&] {
                // Instead of `ASSERT(back() == value)` for T without `==`.
                BOOST_CONTRACT_ASSERT(
                    boost::contract::condition_if<boost::has_equal_to<T> >(
                        boost::bind(std::equal_to<T>(),
                            boost::cref(back()),
                            boost::cref(value)
                        )
                    )
                );
            })
        ;

        vect_.push_back(value);
    }

    /* ... */

更一般地, boost::contract::condition_if 的用法如下:

boost::contract::condition_if<Pred>(
    cond
)

其中 Pred 是一个零元布尔元函数, cond 是一个零元布尔仿函数. 如果 Pred::value 在编译期被静态求值为 true, 那么 cond() 会在运行期被调用, 其布尔结果由外围的 boost::contract::condition_if 调用返回. 否则, 如果 Pred::value 在编译期被静态求值为 false, 那么 boost::contract::condition_if 平凡地返回 true. 因此, 如果 cond 是仿函数模板实例化 (而不仅仅是仿函数), 那么包含带有额外类型要求 (如相等运算符 ==) 的断言操作的调用, 除非编译器在编译期判定 Pred::value 为 true, 否则实际上不会被实例化和编译 (以这种方式使用时, std::equal_to 这样的仿函数模板和 C++14 泛型 lambda 可以用来编写 cond, 但 C++11 lambda 不行).

boost::contract::condition_if 函数模板是更一般的 boost::contract::call_if 的特例, 具体而言 boost::contract::condition_if<Pred>(cond) 在逻辑上等价于 boost::contract::call_if<Pred>(cond).else_([] { return true; }). [71] boost::contract::call_if 函数模板还接受若干可选的 else-if 语句和一个可选的 else 语句:

boost::contract::call_if<Pred1>(
    t1
).template else_if<Pred2>(          // Optional.
    t2
)
...                                 // Optionally, other `else_if` statements.
.else_(                             // Optional for `void` functors, otherwise required.
    e
)

其中 Pred1、Pred2 …… 是零元布尔元函数, t1、t2、……、e 是零元仿函数. 仿函数调用 t1()、t2()、……、e() 的返回类型必须要么全部相同 (也可能全部为 void), 要么是可以彼此隐式转换的类型. 在运行期, boost::contract::call_if 会调用仿函数 t1() 或 t2()、……或 e(), 取决于元函数 Pred1::value、Pred2::value、…… 中哪一个在编译期被静态求值为 true 或 false, 并返回被调用仿函数所返回的值. 如果 t1、t2、……、e 是仿函数模板实例化 (而不仅仅是仿函数), 那么只有当编译器判定它们确实需要在运行期被调用时, 它们的代码才会被编译 (即只有当相关的 Pred1::value、Pred2::value、…… 分别在编译期被求值为 true 或 false 时). 所有 else_if<...>(...) 语句都是可选的. 而 else_(...) 语句在仿函数调用返回 void 时是可选的, 否则为必需.

一般而言, boost::contract::call_if 可用于编写契约断言, 根据相关谓词在编译期被静态求值为 true 还是 false 来编译并检查不同的仿函数模板 (但在大多数情况下, 使用 boost::contract::condition_if 就足够了, 而且更简洁). boost::contract::condition_if_c、boost::contract::call_if_c 和 .else_if_c 函数模板的工作方式与此前见到的不带 ..._c 后缀的对应函数模板类似, 但它们的谓词模板参数接受的是静态布尔值, 而不是零元布尔元函数.

在支持 C++17 if constexpr 的编译器上, 应当无需使用 boost::contract::condition_if 或 boost::contract::call_if, 因为可以用 if constexpr 代替 (使代码更易读、更易编写). [72]

volatile 公有函数

本库允许为 volatile 公有函数指定一组不同的类不变式进行检查. 这些volatile 类不变式编写在一个公有 const volatile 函数中, 名为 invariant, 不带参数, 返回 void (参见 BOOST_CONTRACT_INVARIANT_FUNC, 以把不变式函数命名为不同于 invariant 的名字; 以及访问说明符 一节, 以不必把它声明为 public). 对于 volatile 公有函数没有不变式的类, 只需不声明 void invariant() const volatile 函数即可.

一般而言, const volatile 不变式的工作方式与 const 不变式相同 (参见 类不变式), 唯一区别是 volatile 与 const volatile 函数检查 const volatile 不变式, 而非 const (即既非 const 也非 volatile) 的函数以及 const 函数检查 const 不变式. 给定的类可以指定 static、const volatile 和 const 不变式函数的任意组合 (参见 类不变式): [73]

  • 构造函数在入口和出口检查 static 不变式 (即使抛出异常), 另外在出口处按此顺序检查 const volatile 和 const 不变式, 但仅当未抛出异常时.
  • 析构函数在入口和出口检查 static 不变式 (即使抛出异常), 另外在入口处按此顺序检查 const volatile 和 const 不变式 (也在出口处检查, 但仅当抛出异常时——尽管 C++ 中的析构函数通常绝不应抛出异常).
  • 非 const 的公有函数和 const 公有函数都在入口和出口检查 static 和 const 不变式 (即使抛出异常).
  • volatile 公有函数和非 volatile 公有函数都在入口和出口检查 volatile 和 const volatile 不变式 (即使抛出异常). static and const volatile invariants at entry and at exit (even if an exception is thrown).

这些规则保证 volatile 类不变式被正确检查 (参见 构造函数调用、析构函数调用 和 公有函数调用). 例如 (参见 volatile.cpp):

class u {
public:
    static void static_invariant();     // Static invariants.
    void invariant() const volatile;    // Volatile invariants.
    void invariant() const;             // Const invariants.

    u() { // Check static, volatile, and const invariants.
        boost::contract::check c= boost::contract::constructor(this);
    }

    ~u() { // Check static, volatile, and const invariants.
        boost::contract::check c = boost::contract::destructor(this);
    }

    void nc() { // Check static and const invariants.
        boost::contract::check c = boost::contract::public_function(this);
    }

    void c() const { // Check static and const invariants.
        boost::contract::check c = boost::contract::public_function(this);
    }

    void v() volatile { // Check static and volatile invariants.
        boost::contract::check c = boost::contract::public_function(this);
    }

    void cv() const volatile { // Check static and volatile invariants.
        boost::contract::check c = boost::contract::public_function(this);
    }

    static void s() { // Check static invariants only.
        boost::contract::check c = boost::contract::public_function<u>();
    }
};

本库不会为非 const volatile 函数自动检查 volatile 不变式. 不过, 如果契约规约要求如此, 程序员可以从 const volatile 不变式函数中显式调用 const 不变式函数 (最好按该顺序, 以与构造函数和析构函数检查 const volatile 和 const 不变式的顺序保持一致). 这样一来, 所有公有函数——无论是否 volatile——都会检查 const volatile 不变式 (而只有 const 和非 const 的公有函数只检查 const 不变式, 这是正确的, 因为 volatile 限定符不应被剥离): [74] 

class u {
public:
    void invariant() const volatile { ... }                 // Volatile invariants.

    void invariant() const {
        auto const volatile* cv = this; cv->invariant();    // Call `const volatile` invariant function above.
        ...                                                 // Other non-volatile invariants.
    }

    ...
};

(照常, 私有函数和受保护函数不检查任何不变式, 即使它们是 volatile 或 const volatile 也不例外, 参见 私有函数与受保护函数).

移动操作

与类的所有公有操作一样, 公有的移动操作也应维护类不变式 (参见 [Stroustrup13], 第 520 页). 具体而言, C++ 至少要求以下几点:

  • 被移出的对象可以被复制赋值.
  • 被移出的对象可以被移动赋值.
  • 被移出的对象可以被销毁 (即使没有别的原因, 这也要求移动操作维护类不变式, 因为被移出对象的析构函数要求在其入口处类不变式得到满足——析构函数一贯如此, 参见 析构函数调用).

因此, 移动构造函数和移动赋值运算符都需要维护被移出对象的类不变式, 这样它们的契约就可以照常用 boost::contract::constructor 和 boost::contract::public_function 编写. 例如 (参见 move.cpp):

class circular_buffer :
        private boost::contract::constructor_precondition<circular_buffer> {
public:
    void invariant() const {
        if(!moved()) { // Do not check (some) invariants for moved-from objects.
            BOOST_CONTRACT_ASSERT(index() < size());
        }
        // More invariants here that hold also for moved-from objects (e.g.,
        // all assertions necessary to successfully destroy moved-from objects).
    }

    // Move constructor.
    circular_buffer(circular_buffer&& other) :
        boost::contract::constructor_precondition<circular_buffer>([&] {
            BOOST_CONTRACT_ASSERT(!other.moved());
        })
    {
        boost::contract::check c = boost::contract::constructor(this)
            .postcondition([&] {
                BOOST_CONTRACT_ASSERT(!moved());
                BOOST_CONTRACT_ASSERT(other.moved());
            })
        ;

        move(std::forward<circular_buffer>(other));
    }

    // Move assignment.
    circular_buffer& operator=(circular_buffer&& other) {
        // Moved-from can be (move) assigned (so no pre `!moved()` here).
        boost::contract::check c = boost::contract::public_function(this)
            .precondition([&] {
                BOOST_CONTRACT_ASSERT(!other.moved());
            })
            .postcondition([&] {
                BOOST_CONTRACT_ASSERT(!moved());
                BOOST_CONTRACT_ASSERT(other.moved());
            })
        ;

        return move(std::forward<circular_buffer>(other));
    }

    ~circular_buffer() {
        // Moved-from can always be destroyed (in fact no preconditions).
        boost::contract::check c = boost::contract::destructor(this);
    }

    bool moved() const {
        boost::contract::check c = boost::contract::public_function(this);
        return moved_;
    }

private:
    bool moved_;

    /* ... */

本示例假定可以在被移出的对象上调用公有函数 moved(). [75]

注释

由 C++ 生成的默认移动构造函数和移动赋值运算符不会自动检查契约. 因此, 除非移动操作不是公有的, 或者它们没有前置条件、没有后置条件且其类没有不变式, 否则程序员应当用 boost::contract::constructor、boost::contract::constructor_precondition 和 boost::contract::public_function 手动定义它们, 而不是依赖 C++ 生成的默认实现. (对于 C++ 自动实现的所有其他操作同样如此. )

一如既往, 程序员可以决定不为给定类型编写契约. 具体而言, 对于需要被移动的类, 他们可能决定不编写契约, 以避免检查契约断言的运行期开销并最大化性能 (参见 收益与成本).

联合 (union)

C++ 的 union 不能有虚函数、基类, 也不能被用作基类, 因此子契约 (boost::contract::virtual_、BOOST_CONTRACT_OVERRIDE 等) 不适用于联合. 此外, union 不能继承 boost::contract::constructor_precondition (因为它不能有基类), 取而代之, boost::contract::constructor_precondition 用于声明一个检查构造函数前置条件的局部对象 (位于构造函数的最开头、旧值复制和其他契约之前, 参见下面示例中 pre 的声明). 除此之外, 本库照常用于为联合编写契约. 例如 (参见 union.cpp):

union positive {
public:
    static void static_invariant() { // Static class invariants (as usual).
        BOOST_CONTRACT_ASSERT(instances() >= 0);
    }

    void invariant() const { // Class invariants (as usual).
        BOOST_CONTRACT_ASSERT(i_ > 0);
        BOOST_CONTRACT_ASSERT(d_ > 0);
    }

    // Contracts for constructor, as usual but...
    explicit positive(int x) : d_(0) {
        // ...unions cannot have bases so constructor preconditions here.
        boost::contract::constructor_precondition<positive> pre([&] {
            BOOST_CONTRACT_ASSERT(x > 0);
        });
        boost::contract::old_ptr<int> old_instances =
                BOOST_CONTRACT_OLDOF(instances());
        boost::contract::check c = boost::contract::constructor(this)
            .postcondition([&] {
                { int y; get(y); BOOST_CONTRACT_ASSERT(y == x); }
                BOOST_CONTRACT_ASSERT(instances() == *old_instances + 1);
            })
        ;

        i_ = x;
        ++instances_;
    }

    // Contracts for destructor (as usual).
    ~positive() {
        boost::contract::old_ptr<int> old_instances =
                BOOST_CONTRACT_OLDOF(instances());
        boost::contract::check c = boost::contract::destructor(this)
            .postcondition([&] {
                BOOST_CONTRACT_ASSERT(instances() == *old_instances - 1);
            })
        ;

        --instances_;
    }

    // Contracts for public function (as usual, but no virtual or override).
    void get(int& x) const {
        boost::contract::check c = boost::contract::public_function(this)
            .postcondition([&] {
                BOOST_CONTRACT_ASSERT(x > 0);
            })
        ;

        x = i_;
    }

    // Contracts for static public function (as usual).
    static int instances() {
        boost::contract::check c = boost::contract::public_function<positive>();
        return instances_;
    }

private:
    int i_;
    double d_;

    /* ... */

断言级别

本库提供三个预定义的断言级别, 可用于根据断言的计算复杂度有选择地禁用它们: [76]

  • BOOST_CONTRACT_ASSERT 用于断言计算上不昂贵的条件——至少与执行函数体的开销相比不昂贵. 这些断言就是前文所见的那类, 它们总是在运行期被检查, 且不能被禁用.
  • BOOST_CONTRACT_ASSERT_AUDIT 用于断言与执行函数体的开销相比计算上昂贵的条件. 除非程序员显式定义 BOOST_CONTRACT_AUDITS (默认未定义), 这些断言不会在运行期被检查; 但被断言的条件总是会被编译, 因而在语法上得到验证 (即使它们实际并未在运行期被求值和检查).
  • BOOST_CONTRACT_ASSERT_AXIOM 用于断言与执行函数体的开销相比计算上代价高昂到无法承受的条件. 这些断言绝不在运行期被求值或检查, 但被断言的条件总是会被编译, 因而在语法上得到验证 (因此这些断言可以充当代码的形式化注释).

此外, BOOST_CONTRACT_CHECK_AUDIT 和 BOOST_CONTRACT_CHECK_AXIOM 与 BOOST_CONTRACT_ASSERT_AUDIT 和 BOOST_CONTRACT_ASSERT_AXIOM 类似, 但它们用于为实现检查 (而不是断言) 编写 audit 和 axiom 级别 (参见 实现检查).

例如, BOOST_CONTRACT_ASSERT_AUDIT 可用于编写计算上昂贵的断言 (参见 assertion_level.cpp):

template<typename RandomIter, typename T>
RandomIter random_binary_search(RandomIter first, RandomIter last,

    RandomIter result;
    boost::contract::check c = boost::contract::function()
        .precondition([&] {
            BOOST_CONTRACT_ASSERT(first <= last); // Default, not expensive.
            // Expensive O(n) assertion (use AXIOM if prohibitive instead).
            BOOST_CONTRACT_ASSERT_AUDIT(std::is_sorted(first, last));
        })
        .postcondition([&] {
            if(result != last) BOOST_CONTRACT_ASSERT(*result == value);
        })
    ;

类似地, BOOST_CONTRACT_AUDITS 可用于禁用昂贵的旧值复制以及使用这些旧值的相关断言 (参见 assertion_level.cpp):

template<typename T>
class vector {


public:
    void swap(vector& other) {
        boost::contract::old_ptr<vector> old_me, old_other;
        #ifdef BOOST_CONTRACT_AUDITS
            old_me = BOOST_CONTRACT_OLDOF(*this);
            old_other = BOOST_CONTRACT_OLDOF(other);
        #endif // Else, skip old value copies...
        boost::contract::check c = boost::contract::public_function(this)
            .postcondition([&] {
                // ...and also skip related assertions.
                BOOST_CONTRACT_ASSERT_AUDIT(*this == *old_other);
                BOOST_CONTRACT_ASSERT_AUDIT(other == *old_me);
            })
        ;

        vect_.swap(other.vect_);
    }


    /* ... */

private:
    std::vector<T> vect_;
};

传递给 BOOST_CONTRACT_ASSERT_AXIOM 的条件会被编译, 但实际不会在运行期求值, 因此这个宏可用于编写计算上代价高昂到无法承受的断言, 也可用于编写实际上无法在 C++ 中编程的断言——借助声明了但留待未定义的函数. 例如 (参见 assertion_level.cpp):

// If valid iterator range (cannot implement in C++ but OK to use in AXIOM).
template<typename Iter>

template<typename T>

                BOOST_CONTRACT_OLDOF(capacity());

            .postcondition([&] {
                BOOST_CONTRACT_ASSERT(capacity() >= *old_capacity);

                    BOOST_CONTRACT_ASSERT_AXIOM(!valid(where, end()));
                }
            })
        ;

    std::vector<T> vect_;
};

禁用契约检查

检查契约会增加运行期开销, 可能减慢程序执行 (参见 收益与成本). 因此, 程序员可以定义以下宏的任意组合 (在 Clang 和 GCC 上是 -D 选项, 在 MSVC 上是 /D 选项等), 指示本库在运行期不检查特定的契约条件组:

  • 定义 BOOST_CONTRACT_NO_PRECONDITIONS, 以不检查前置条件.
  • 定义 BOOST_CONTRACT_NO_POSTCONDITIONS, 以不检查后置条件.
  • 定义 BOOST_CONTRACT_NO_EXCEPTS, 以不检查异常保证.
  • 定义 BOOST_CONTRACT_NO_ENTRY_INVARIANTS, 以在调用入口不检查类不变式.
  • 定义 BOOST_CONTRACT_NO_EXIT_INVARIANTS, 以在调用出口不检查类不变式.
  • 或者定义 BOOST_CONTRACT_NO_INVARIANTS, 以在调用入口和出口都不检查类不变式. (这是为方便起见提供的, 等同于同时定义 BOOST_CONTRACT_NO_ENTRY_INVARIANTS 和 BOOST_CONTRACT_NO_EXIT_INVARIANTS).
  • 定义 BOOST_CONTRACT_NO_CHECKS, 以不求值实现检查.
注释

旧值可以被后置条件和异常保证两者使用, 因此必须同时定义 BOOST_CONTRACT_NO_POSTCONDITIONS 和 BOOST_CONTRACT_NO_EXCEPTS 才能禁用旧值复制.

默认情况下, 这些宏都未定义, 因此本库检查所有契约. 当用户定义了这些宏时, 本库的实现代码会在内部进行优化, 尽可能减小与检查和编译契约相关的任何运行期和编译期开销 (完全移除与契约代码相关的运行期和编译期开销的技巧参见 禁用契约编译).

例如, 程序员可以决定在早期开发构建中检查所有契约, 而在发布构建中通过定义 BOOST_CONTRACT_NO_POSTCONDITIONS、BOOST_CONTRACT_NO_EXCEPTS、BOOST_CONTRACT_NO_EXIT_INVARIANTS 和 BOOST_CONTRACT_NO_CHECKS 改为只检查前置条件和可能的入口不变式.

禁用契约编译 (宏接口)

本库提供的宏可用于完全消除契约引入的编译期和运行期开销, 但代价是要在契约代码周围手动编写 #ifndef BOOST_CONTRACT_NO_... 语句:

  • 当构造函数的契约检查被禁用时, 本库定义 BOOST_CONTRACT_NO_CONSTRUCTORS.
  • 当析构函数的契约检查被禁用时, 本库定义 BOOST_CONTRACT_NO_DESTRUCTORS.
  • 当公有函数的契约检查被禁用时, 本库定义 BOOST_CONTRACT_NO_PUBLIC_FUNCTIONS.
  • 当 (非公有且非成员) 函数的契约检查被禁用时, 本库定义 BOOST_CONTRACT_NO_FUNCTIONS.
  • 当旧值复制被禁用时, 本库定义 BOOST_CONTRACT_NO_OLDS.
  • 当上述所有契约以及实现检查 (参见 BOOST_CONTRACT_NO_ALL) 都被禁用时, 本库定义 BOOST_CONTRACT_NO_CHECKS.

这些宏不是配置宏, 程序员不应直接定义它们 (否则本库将产生编译期错误). 相反, 当程序员定义 BOOST_CONTRACT_NO_PRECONDITIONS、BOOST_CONTRACT_NO_POSTCONDITIONS、BOOST_CONTRACT_NO_EXCEPTS、BOOST_CONTRACT_NO_INVARIANTS (或 BOOST_CONTRACT_NO_ENTRY_INVARIANTS 与 BOOST_CONTRACT_NO_EXIT_INVARIANTS) 以及 BOOST_CONTRACT_NO_CHECKS (参见 禁用契约检查) 时, 这些宏会由本库自动定义.

另一种做法是, 本库在 boost/contract_macro.hpp 中定义了一个基于宏的接口, 同样可用于完全消除契约引入的编译期和运行期开销, 但无需手动编写 #ifndef BOOST_CONTRACT_NO_... 语句的负担. 例如, 下面的代码展示如何同时使用 boost/contract_macro.hpp 宏接口和 #ifndef BOOST_CONTRACT_NO_... 语句, 来完全消除非成员函数契约的编译期和运行期开销 (参见 ifdef_macro.cpp 与 ifdef.cpp):

宏接口

#ifndef BOOST_CONTRACT_NO_... 语句

 

// Use macro interface to completely disable contract code compilation.
#include <boost/contract_macro.hpp>

int inc(int& x) {
    int result;
    BOOST_CONTRACT_OLD_PTR(int)(old_x, x);
    BOOST_CONTRACT_FUNCTION()
        BOOST_CONTRACT_PRECONDITION([&] {
            BOOST_CONTRACT_ASSERT(x < std::numeric_limits<int>::max());
        })
        BOOST_CONTRACT_POSTCONDITION([&] {
            BOOST_CONTRACT_ASSERT(x == *old_x + 1);
            BOOST_CONTRACT_ASSERT(result == *old_x);
        })
    ;

    return result = x++;
}


// Use #ifdef to completely disable contract code compilation.
#include <boost/contract/core/config.hpp>
#ifndef BOOST_CONTRACT_NO_ALL
    #include <boost/contract.hpp>
#endif

int inc(int& x) {
    int result;
    #ifndef BOOST_CONTRACT_NO_OLDS
        boost::contract::old_ptr<int> old_x = BOOST_CONTRACT_OLDOF(x);
    #endif
    #ifndef BOOST_CONTRACT_NO_FUNCTIONS
        boost::contract::check c = boost::contract::function()
            #ifndef BOOST_CONTRACT_NO_PRECONDITIONS
                .precondition([&] {
                    BOOST_CONTRACT_ASSERT(x < std::numeric_limits<int>::max());
                })
            #endif
            #ifndef BOOST_CONTRACT_NO_POSTCONDITIONS
                .postcondition([&] {
                    BOOST_CONTRACT_ASSERT(x == *old_x + 1);
                    BOOST_CONTRACT_ASSERT(result == *old_x);
                })
            #endif
        ;
    #endif

    return result = x++;
}

对于构造函数、析构函数和公有函数, boost/contract_macro.hpp 宏接口和 #ifndef BOOST_CONTRACT_NO_... 语句可以按如下方式使用 (参见 ifdef_macro.cpp 与 ifdef.cpp):

静态和 volatile 类不变式可以分别用 BOOST_CONTRACT_STATIC_INVARIANT 和 BOOST_CONTRACT_INVARIANT_VOLATILE 编写 (这些宏展开的代码等同于 static void BOOST_CONTRACT_STATIC_INVARIANT_FUNC() 和 void BOOST_CONTRACT_INVARIANT_FUNC() const volatile 函数).

通常更推荐 boost/contract_macro.hpp 宏接口, 因为它比手动编写 #ifndef BOOST_CONTRACT_NO_... 语句更简洁、更易用. 不过, C++ 宏在单行代码上展开, 这会使使用该宏接口时编译器错误信息的作用打折扣, 而且当断言在运行期失败时, 给定的前置条件、后置条件、异常保证和类不变式集合内的所有契约断言都会在错误消息中列出同一个行号 (但错误消息仍会列出断言代码, 这应当仍能让程序员识别出具体失败的断言). 最后, 宏接口会在代码中留下少量契约装饰, 但这不应增加可度量的编译期或运行期开销 (具体而言, 即使契约被禁用, 用户代码中仍会留下额外的 boost::contract::virtual_* 参数、对 boost::contract::constructor_precondition 默认构造函数 (它什么也不做) 的调用、BOOST_CONTRACT_BASE_TYPES typedef 以及 boost::contract::access 友元声明, 除非使用 #ifndef BOOST_CONTRACT_NO_... 语句).

如 禁用契约检查 一节所示禁用契约后, 仍会留下编译契约代码的开销, 外加一些小的运行期开销, 其来源包括旧值指针的初始化 (即使它们全为空且实际不会复制任何旧值)、用于初始化 boost::contract::check 和 boost::contract::constructor_precondition 的契约函数调用 (即使这些调用会被本库在内部优化为基本什么都不做) 等. 对于真正对性能敏感、连这样小的运行期开销都无法接受的代码, 可以使用宏接口 (或 #ifndef BOOST_CONTRACT_NO_... 语句) 来完全消除契约的编译期和运行期开销. 不过, 对于这样的性能敏感代码, 就连检查简单前置条件的开销可能都太大, 因此最好完全不编写契约.

通常, 如果对某应用而言, 检查前置条件和其他断言的开销已被认为可以接受, 那么契约的编译期开销就不应成为问题, 按禁用契约检查 一节所示在运行期禁用契约检查就足够了 (大多数情况下无需真正使用 boost/contract_macro.hpp 宏接口或 #ifndef BOOST_CONTRACT_NO_... 语句).

分离函数体实现

契约是程序规约的一部分, 而不是其实现的一部分 (参见 规约与实现). 然而, 本库使用函数定义来编写契约, 因此契约代码会与函数实现代码出现在一起. 这并不理想 (不过, 用本库编写的契约总是出现在函数定义的最开头, 程序员很容易把契约代码与函数实现代码的其余部分区分开, 所以这在实践中可能不算真正的限制).

在某些情况下, 可能希望把契约代码与函数实现代码完全分开. 例如, 对于只向用户交付头文件和编译后目标文件的软件, 这可能是必要的. 如果契约编写在被编译进目标文件的函数定义中, 用户将无法看到契约代码, 也就无法理解函数的语义和用法 (同样, 这在实践中可能不是真正的问题, 例如, 如果契约已经由某个工具从源代码中提取出来并作为交付软件文档的一部分呈现).

无论如何, 当把契约与函数实现代码分离确实非常重要时, 可以把函数实现编写在额外的函数体函数 (body function)中 (这里命名为 ..._body, 但也可以使用任何其他命名方案), 它们被编译进目标文件. 留在头文件中的函数定义则只包含契约代码, 后跟对额外函数体函数的调用. 这一技巧可以把契约代码保留在头文件中, 同时把实现代码分离到源文件和目标文件. 不过, 这增加了为每个函数体函数手动编写一个额外函数声明的开销 (还有一个限制: 构造函数的成员初始化列表必须编写在头文件中, 因为构造函数需要在那里定义才能列出构造函数契约代码). [77]

例如, 下面的头文件只包含函数声明、契约代码和构造函数成员初始化, 但不包含实现函数体的代码 (参见 separate_body.hpp):

class iarray :
        private boost::contract::constructor_precondition<iarray> {
public:
    void invariant() const {
        BOOST_CONTRACT_ASSERT(size() <= capacity());
    }

    explicit iarray(unsigned max, unsigned count = 0) :
        boost::contract::constructor_precondition<iarray>([&] {
            BOOST_CONTRACT_ASSERT(count <= max);
        }),
        // Still, member initializations must be here.
        values_(new int[max]),
        capacity_(max)
    {
        boost::contract::check c = boost::contract::constructor(this)
            .postcondition([&] {
                BOOST_CONTRACT_ASSERT(capacity() == max);
                BOOST_CONTRACT_ASSERT(size() == count);
            })
        ;
        constructor_body(max, count); // Separate constructor body impl.
    }

    virtual ~iarray() {
        boost::contract::check c = boost::contract::destructor(this); // Inv.
        destructor_body(); // Separate destructor body implementation.
    }

    virtual void push_back(int value, boost::contract::virtual_* v = 0) {
        boost::contract::old_ptr<unsigned> old_size =
                BOOST_CONTRACT_OLDOF(v, size());
        boost::contract::check c = boost::contract::public_function(v, this)
            .precondition([&] {
                BOOST_CONTRACT_ASSERT(size() < capacity());
            })
            .postcondition([&] {
                BOOST_CONTRACT_ASSERT(size() == *old_size + 1);
            })
        ;
        push_back_body(value); // Separate member function body implementation.
    }

private:
    // Contracts in class declaration (above), but body implementations are not.
    void constructor_body(unsigned max, unsigned count);
    void destructor_body();
    void push_back_body(int value);

    /* ... */

而函数体则在单独的源文件中实现 (参见 separate_body.cpp):

void iarray::constructor_body(unsigned max, unsigned count) {
    for(unsigned i = 0; i < count; ++i) values_[i] = int();
    size_ = count;
}

void iarray::destructor_body() { delete[] values_; }

void iarray::push_back_body(int value) { values_[size_++] = value; }

/* ... */

同样的技巧也可用于非成员函数、私有函数和受保护函数等.

注释

当契约只编写在 .cpp 文件中, 且本库的所有头文件也#include 只从 .cpp 文件中被包含, 那么这些 .cpp 文件可以在禁用特定契约检查的情况下编译 (例如 BOOST_CONTRACT_NO_POSTCONDITIONS、BOOST_CONTRACT_NO_EXCEPTS 和 BOOST_CONTRACT_NO_EXIT_INVARIANTS, 参见 禁用契约检查). 这样, 这些 .cpp 文件中的代码将始终禁用此类契约检查, 即使链接到可能以另一组被禁用契约编译的其他用户代码 (即定义了另一组 BOOST_CONTRACT_NO_... 宏) 时也是如此. 这一技巧对于交付编译后的目标文件 (例如某个库的目标文件) 可能有用: 无论用于编译链接到这些交付目标文件的代码的 BOOST_CONTRACT_NO_... 宏如何定义, 这些目标文件都绝不会检查某些契约 (例如后置条件、异常保证和出口不变式).

反过来说, 如果契约只编写在头文件中 (例如使用本节所示的额外 ..._body 函数), 且本库头文件只在交付的这些头文件中被包含, 那么最终用户在把交付的头文件作为其代码一部分编译时, 可以通过定义 #include 宏来启用或禁用交付代码的契约检查. 在另一些情况下这一技巧也可能有用: 交付代码的程序员想让最终用户自行决定交付代码的哪些契约应在运行期检查. BOOST_CONTRACT_NO_... macros when they compile the shipped header files as part of their code. This technique might be useful in other situations when programmers that ship code want to leave it up the their end users to decide which contracts of the shipped code should be checked at run-time.

不使用 lambda 函数 (不用 C++11)

本节展示如何在不使用 C++11 lambda 函数的情况下使用本库. 这有一些优点:

  • 它允许在不支持 C++11 lambda 函数的编译器上使用本库 (在这种情况下, 基本上任何对 SFINAE 有足够支持的 C++03 编译器都可以使用; 另参见 不使用宏 一节以同时避免使用可变参数宏). [78]
  • 契约函数 (即下面示例中的 ..._precondition、..._old 和 ..._postcondition 函数) 可以被编写为在编译期完全强制常量正确性和其他契约要求 (参见 常量正确性). [79]
  • 契约函数的代码与函数体实现相分离 (参见 分离函数体实现).

不过, 不使用 C++11 lambda 函数的显著代价是必须手动编写额外的契约函数及相关样板代码. 例如, 头文件 (参见 no_lambdas.hpp):

class iarray :
        private boost::contract::constructor_precondition<iarray> {
public:
    static void static_invariant() {
        BOOST_CONTRACT_ASSERT(instances() >= 0);
    }

    void invariant() const {
        BOOST_CONTRACT_ASSERT(size() <= capacity());
    }

    explicit iarray(unsigned max, unsigned count = 0);
        static void constructor_precondition(unsigned const max,
                unsigned const count) {
            BOOST_CONTRACT_ASSERT(count <= max);
        }
        static void constructor_old(boost::contract::old_ptr<int>&
                old_instances) {
            old_instances = BOOST_CONTRACT_OLDOF(instances());
        }
        void constructor_postcondition(unsigned const max, unsigned const count,
                boost::contract::old_ptr<int> const old_instances) const {
            BOOST_CONTRACT_ASSERT(capacity() == max);
            BOOST_CONTRACT_ASSERT(size() == count);
            BOOST_CONTRACT_ASSERT(instances() == *old_instances + 1);
        }

    virtual ~iarray();
        void destructor_old(boost::contract::old_ptr<int>& old_instances)
                const {
            old_instances = BOOST_CONTRACT_OLDOF(instances());
        }
        static void destructor_postcondition(boost::contract::old_ptr<int> const
                old_instances) {
            BOOST_CONTRACT_ASSERT(instances() == *old_instances - 1);
        }

    virtual void push_back(int value, boost::contract::virtual_* v = 0);
        void push_back_precondition() const {
            BOOST_CONTRACT_ASSERT(size() < capacity());
        }
        void push_back_old(boost::contract::virtual_* v,
                boost::contract::old_ptr<unsigned>& old_size) const {
            old_size = BOOST_CONTRACT_OLDOF(v, size());
        }
        void push_back_postcondition(
                boost::contract::old_ptr<unsigned> const old_size) const {
            BOOST_CONTRACT_ASSERT(size() == *old_size + 1);
        }

    unsigned capacity() const;
    unsigned size() const;

    static int instances();

private:
    int* values_;
    unsigned capacity_;
    unsigned size_;
    static int instances_;
};

以及源文件 (参见 no_lambdas.cpp):

iarray::iarray(unsigned max, unsigned count) :
    boost::contract::constructor_precondition<iarray>(boost::bind(
            &iarray::constructor_precondition, max, count)),
    values_(new int[max]), // Member initializations can be here.
    capacity_(max)
{
    boost::contract::old_ptr<int> old_instances;
    boost::contract::check c = boost::contract::constructor(this)
        .old(boost::bind(&iarray::constructor_old, boost::ref(old_instances)))
        .postcondition(boost::bind(
            &iarray::constructor_postcondition,
            this,
            boost::cref(max),
            boost::cref(count),
            boost::cref(old_instances)
        ))
    ;

    for(unsigned i = 0; i < count; ++i) values_[i] = int();
    size_ = count;
    ++instances_;
}

iarray::~iarray() {
    boost::contract::old_ptr<int> old_instances;
    boost::contract::check c = boost::contract::destructor(this)
        .old(boost::bind(&iarray::destructor_old, this,
                boost::ref(old_instances)))
        .postcondition(boost::bind(&iarray::destructor_postcondition,
                boost::cref(old_instances)))
    ;

    delete[] values_;
    --instances_;
}

void iarray::push_back(int value, boost::contract::virtual_* v) {
    boost::contract::old_ptr<unsigned> old_size;
    boost::contract::check c = boost::contract::public_function(v, this)
        .precondition(boost::bind(&iarray::push_back_precondition, this))
        .old(boost::bind(&iarray::push_back_old, this, boost::cref(v),
                boost::ref(old_size)))
        .postcondition(boost::bind(&iarray::push_back_postcondition, this,
                boost::cref(old_size)))
    ;

    values_[size_++] = value;
}

unsigned iarray::capacity() const {
    // Check invariants.
    boost::contract::check c = boost::contract::public_function(this);
    return capacity_;
}

unsigned iarray::size() const {
    // Check invariants.
    boost::contract::check c = boost::contract::public_function(this);
    return size_;
}

int iarray::instances() {
    // Check static invariants.
    boost::contract::check c = boost::contract::public_function<iarray>();
    return instances_;
}

int iarray::instances_ = 0;

如果程序员还想在编译期完全强制契约式编程的全部常量正确性要求, 就应在编写契约函数时遵循以下规则 (参见 常量正确性):

  • 前置条件函数 (即上例中的 ..._precondition 函数) 的实参既可以按 const 值接受, 也可以按 const& 接受; 当它们是成员函数时, 应当是 static 或 const 函数.
  • 后置条件函数 (即上例中的 ..._postcondition 函数) 应按 const& 接受其参数; 当它们是成员函数时, 应当是 static 或 const 函数.
  • 类似地, 异常保证函数 (上例未展示) 应按 const& 接受其参数; 当它们是成员函数时, 应当是 static 或 const 函数.
  • 旧值函数 (即上例中的 ..._old 函数) 应按 const& 接受其参数, 但旧值指针应按 & 接受 (这样只有旧值指针可被修改); 当它们是成员函数时, 应当是 static 或 const 函数.
  • 对于构造函数: 前置条件、旧值和异常保证函数应当是 static (因为如果构造函数体没有成功运行, 就不存在有效对象 this, 参见 构造函数调用).
  • 对于析构函数: 后置条件函数应当是 static (因为析构函数体成功运行之后就不存在有效对象 this; 但异常保证函数不必是 static, 因为对象 this 仍然有效——析构函数体没有成功运行; 参见 析构函数调用).

注意, 这些额外的契约函数还允许把契约代码保留在头文件中, 同时把所有函数体实现在单独的源文件中 (包括构造函数成员初始化列表——这是分离函数体实现 一节所示的技巧做不到的). [80] 另需注意, 如果程序员需要精确控制类的公有成员, 契约函数始终可以声明为 private (本示例只是为了简洁而没有这样做).

作者们认为, 本库与 C++11 lambda 函数配合使用时最为有用 (因为如上例所示, 不使用 C++11 lambda 时需要大量样板代码).

不使用宏 (及不使用可变参数宏)

可以不使用本库提供的大多数宏来指定契约, 而是手动编写相关代码 (唯一无法手动编写的宏是 BOOST_CONTRACT_OVERRIDE、BOOST_CONTRACT_OVERRIDES 和 BOOST_CONTRACT_NAMED_OVERRIDE).

注释

本库的宏有些是可变参数宏, 有些不是 (见下文). 可变参数宏在 C++11 中被正式纳入语言, 但大多数编译器早就以扩展形式支持它们, 而且所有支持 C++11 lambda 函数的编译器也都应当支持 C++11 可变参数宏 (何况本库很少会在没有 C++11 lambda 便利的情况下使用, 参见 不使用 lambda 函数 一节). [81] 因此, 本节其余部分主要可以视为趣闻, 因为程序员即使需要, 也很少会在不使用本库宏的情况下使用本库.

覆盖 (Overrides)

如 公有函数覆盖 和 命名覆盖 中所示, 本库提供 BOOST_CONTRACT_OVERRIDE 和 BOOST_CONTRACT_NAMED_OVERRIDE 宏来为覆盖公有函数编写契约 (对于不支持可变参数模板的编译器, 参见 BOOST_CONTRACT_MAX_ARGS). [82] 这些宏无法手动编写, 但它们不是可变参数宏 (因此程序员应当能够在任何对 SFINAE 有健全支持的 C++ 编译器上使用它们). [83] 而 BOOST_CONTRACT_OVERRIDES 宏则是可变参数宏, 但在不支持可变参数宏的编译器上, 程序员可以手动为每个覆盖公有函数名重复使用非可变参数宏 BOOST_CONTRACT_OVERRIDE.

断言 (非可变参数)

如 前置条件、后置条件、异常保证、类不变式 等节所示, 本库提供 BOOST_CONTRACT_ASSERT 宏来断言契约条件. 这不是可变参数宏, 程序员应当能够在所有 C++ 编译器上使用它. 无论如何, 调用 BOOST_CONTRACT_ASSERT(cond) 只是展开为等价于如下所示的代码: [84] 

if(!(cond)) {
    throw boost::contract::assertion_failure(__FILE__, __LINE__,
            BOOST_PP_STRINGIZE(cond));
}

实际上, 本库把从前置条件、后置条件、异常保证和类不变式中抛出的任何异常都视为契约失败, 并通过调用相应的契约失败处理器来报告它 (boost::contract::precondition_failure 等). 如有需要, 程序员始终可以编写抛出特定用户自定义异常的契约断言, 如下所示 (参见 失败时抛出异常):

if(!cond) throw exception-object;

不过, 使用 BOOST_CONTRACT_ASSERT 很方便, 因为出现断言失败时, 它总能使本库显示一条信息丰富的消息, 其中包含断言代码、文件名、行号等.

如 断言级别 一节所示, 本库预定义了 BOOST_CONTRACT_ASSERT_AUDIT 和 BOOST_CONTRACT_ASSERT_AXIOM 断言级别. 这些宏不是可变参数宏, 程序员应当能够在所有 C++ 编译器上使用它们. 无论如何, 它们的实现等价于如下所示:

#ifdef BOOST_CONTRACT_AUDITS
    #define BOOST_CONTRACT_ASSERT_AUDIT(cond) \
        BOOST_CONTRACT_ASSERT(cond)
#else
    #define BOOST_CONTRACT_ASSERT_AUDIT(cond) \
        BOOST_CONTRACT_ASSERT(true || (cond))
#endif

#define BOOST_CONTRACT_ASSERT_AXIOM(cond) \
    BOOST_CONTRACT_ASSERT(true || (cond))
基类型 (可变参数)

如 基类 一节所示, 本库提供可变参数宏 BOOST_CONTRACT_BASE_TYPES 来声明 base_types 成员类型, 该类型会展开为派生类的全部公有基类列表. 程序员也可以不使用 base_types 来声明 BOOST_CONTRACT_BASE_TYPES, 但代价是要多写一些代码并增加维护工作. 例如 (参见 base_types_no_macro.cpp):

#include <boost/mpl/vector.hpp>

class chars :
    private boost::contract::constructor_precondition<chars>,
    public unique_chars,
    public virtual pushable<char>,
    virtual protected has_size,
    private has_empty
{
public:
    // Program `base_types` without macros (list only public bases).
    typedef boost::mpl::vector<unique_chars, pushable<char> > base_types;

    /* ... */

base_types 成员类型必须是一个 boost::mpl::vector, 它必须列出全部且仅有 public 基类 (因为只有公有基类参与子契约, 参见 函数调用), 且顺序与这些公有基类在派生类继承列表中出现的顺序相同. 如果不使用 BOOST_CONTRACT_BASE_TYPES 宏, 那么每当派生类的继承列表发生变化时, 维护 boost::mpl::vector 中正确的基类列表就是程序员的责任 (这可能显著增加维护的复杂度).

一般而言, 建议尽可能使用 BOOST_CONTRACT_BASE_TYPES 宏.

旧值 (可变参数)

如 旧值 一节所示, 本库提供可变参数宏 BOOST_CONTRACT_OLDOF 来赋值旧值副本. 程序员也可以不使用 BOOST_CONTRACT_OLDOF 来赋值旧值, 但代价是要手动多写一些代码. 例如 (参见 old_no_macro.cpp):

template<typename T>
class vector {
public:
    virtual void push_back(T const& value, boost::contract::virtual_* v = 0) {
        // Program old value instead of using `OLD(size())` macro.
        boost::contract::old_ptr<unsigned> old_size =
            boost::contract::make_old(v, boost::contract::copy_old(v) ?
                    size() : boost::contract::null_old())
        ;

        boost::contract::check c = boost::contract::public_function(v, this)
            .postcondition([&] {
                BOOST_CONTRACT_ASSERT(size() == *old_size + 1);
            })
        ;

        vect_.push_back(value);
    }

    /* ... */

此处必须使用三元运算符 boost::contract::copy_old(v) ? size() : boost::contract::null_old(), 以避免在 size() 返回 boost::contract::copy_old 时对旧值表达式 false 求值并复制 (因为在运行期禁用后置条件和异常保证检查时不会复制旧值, 被覆盖的虚函数调用尚未检查后置条件或异常保证, 等等). 外层的 boost::contract::make_old 会复制旧值表达式并创建旧值指针. 否则, boost::contract::null_old 表示应创建空旧值指针.

boost::contract::make_old 与 boost::contract::copy_old 函数的用法与上文所示完全相同, 只是从非虚函数中调用时不带额外的 v 参数 (参见 公有函数覆盖). boost::contract::make_old 返回的旧值指针既可以赋给 boost::contract::old_ptr, 也可以赋给 boost::contract::old_ptr_if_copyable (参见 旧值要求).

一般而言, 建议尽可能使用 BOOST_CONTRACT_OLDOF 宏.

宏接口 (可变参数)

在 boost/contract_macro.hpp 中定义的宏几乎都是可变参数宏. 在不支持可变参数宏的编译器上, 程序员可以用 #ifndef BOOST_CONTRACT_NO_... 语句手动禁用契约代码编译, 如禁用契约编译 一节所示.


[68] 设计理由: [N1962] 以及其他向 C++ 添加契约的提案都没有提供这样一种机制: 只针对不可复制构造的旧值类型有选择地禁用复制. 不过, 本库提供了这样的机制, 以便为模板代码编写契约时, 不必仅仅为了复制旧值而添加额外的可复制构造类型要求 (如果不复制旧值就不会有这些要求) (这样, 带契约编译和不带契约编译就不会必然改变程序的类型要求). 把 C++17 的 if constexpr 与 [N1962] 或 [P0380] 结合起来也可以实现类似效果: 模板代码中的旧值表达式可以用 if constexpr 语句守护, 检查旧值类型是否可复制. 例如, 假定把旧值加入 [P0380] (使用某种 oldof(...) 语法), 并且 C++17 的 if constexpr 可以在 [P0380] 的契约中使用:

template<typename T>
void offset(T& x, int count)
    [[ensures: if constexpr(std::is_copy_constructible<T>::value) x == oldof(x) + count]]
...

[69] 严格来说, 在 C++17 上可以把 boost::contract::old_ptr 与 if constexpr 结合使用来代替 boost::contract::old_ptr_if_copyable, 例如:

template<typename T>
void offset(T& x, int count) {
    boost::contract::old_ptr<T> old_x;
    if constexpr(boost::contract::is_old_value_copyable<T>::value) old_x = BOOST_CONTRACT_OLDOF(x);
    boost::contract::check c = boost::contract::function()
        .postcondition([&] {
            if constexpr(boost::contract::is_old_value_copyable<T>::value) BOOST_CONTRACT_ASSERT(x == *old_x + count);
        })
    ;

    x += count;
}

不过, 作者们觉得这段代码比使用 boost::contract::old_ptr_if_copyable 的等价代码可读性差、更冗长. 当守护条件检查的类型要求比单纯的 if constexpr 更复杂时, 用 boost::contract::is_old_value_copyable 来守护旧值复制和相关断言才有用 (本文档稍后会展示).

[70] 设计理由: [N1962] 以及其他向 C++ 添加契约的提案都没有提供根据类型要求有选择地禁用断言的机制. 不过, 本库提供了这样的机制, 以便为模板代码编写契约时, 不必仅仅因为契约而添加额外的类型要求 (如果没有契约就不会有这些要求) (这样, 带契约编译和不带契约编译不会改变程序的类型要求). 把 C++17 的 if constexpr 与 [N1962] 或 [P0380] 结合起来也可以实现类似效果: 模板代码中的契约断言可以用 if constexpr 语句守护, 检查相关类型要求 ([N1962] 已经允许在契约中使用 if 语句, 称为 select assertions; [P0380] 则不允许, 因此也许也应向 if[P0380] 加入 语句). 例如, 假定 C++17 的 if constexpr 可以在 [P0380] 的契约中使用:

template<typename T>
class vector {
public:
    void push_back(T const& value)
        [[ensures: if constexpr(boost::has_equal_to<T>::value) back() == value]]
    ...
};

[71] 的内部实现经过了优化, boost::contract::condition_if 实际上并不使用 boost::contract::call_if.

[72]

除了在契约中使用之外, boost::contract::call_if 还可以与 C++14 泛型 lambda 结合来模拟 C++17 的 if constexpr (boost::hana::if_ 以及可能还有其他方法也可以与泛型 lambda 结合, 在 C++14 编译器上模拟 C++17 的 if constexpr). 例如, 下面这个 myadvance 的实现自 C++14 起即可编译, 而且比使用标签分派 (tag dispatching) 的 std::advance 常规实现更简洁、更易读、更易维护 (参见 call_if_cxx14.cpp):

template<typename Iter, typename Dist>
void myadvance(Iter& i, Dist n) {
    Iter* p = &i; // So captures change actual pointed iterator value.
    boost::contract::call_if<is_random_access_iterator<Iter> >(
        std::bind([] (auto p, auto n) { // C++14 generic lambda.
            *p += n;
        }, p, n)
    ).template else_if<is_bidirectional_iterator<Iter> >(
        std::bind([] (auto p, auto n) {
            if(n >= 0) while(n--) ++*p;
            else while(n++) --*p;
        }, p, n)
    ).template else_if<is_input_iterator<Iter> >(
        std::bind([] (auto p, auto n) {
            while(n--) ++*p;
        }, p, n)
    ).else_(
        std::bind([] (auto false_) {
            static_assert(false_, "requires at least input iterator");
        }, std::false_type()) // Use constexpr value.
    );
}

当然, 自 C++17 起, 使用 if constexpr 的实现更加易读、简洁:

template<typename Iter, typename Dist>
void myadvance(Iter& i, Dist n) {
    if constexpr(is_random_access_iterator<Iter>::value) {
        i += n;
    } else if constexpr(is_bidirectional_iterator<Iter>::value) {
        if(n >= 0) while(n--) ++i;
        else while(n++) --i;
    } else if constexpr(is_input_iterator<Iter>::value) {
        while(n--) ++i;
    } else {
        static_assert(false, "requires at least input iterator");
    }
}

[73] 设计理由: 构造函数和析构函数按该顺序检查 const volatile 和 const 不变式, 因为可应用于更多调用的限定符先被检查 (注意 const volatile 调用可以在任何对象上进行, 而 const 调用不能在 volatile 对象上进行; 从这个意义上说, const volatile 限定符可比单独的 const 应用于更多调用). 这与 static 类不变式一致——它们甚至在 const volatile 不变式之前被检查 (static 限定符可比 const volatile 应用于更多调用, 事实上进行静态调用甚至不需要对象).

[74] 设计理由: 注意, 虽然可以让所有公有函数检查 const volatile 不变式, 但绝不可能让 volatile 公有函数检查 const 非 volatile 不变式. 这是因为 const 与 volatile 在 C++ 中只能添加、绝不能剥离 (强制通过 const_cast 除外), 而本库为了强制契约常量正确性总是自动添加 const (参见 常量正确性). 话虽如此, 若本库还自动添加 volatile 并要求所有函数检查 const volatile (而不只是 const) 不变式, 那就过于严苛了, 因为只有 volatile 成员才能从 const volatile 不变式中访问, 因此可能存在许多 const (但非 const volatile) 成员, 它们可从 const 不变式中访问, 却不能从 const volatile 不变式中访问. 为避免这种混淆, 本库选择在 const 与 const volatile 不变式之间划出清晰的两分界限: 只有 volatile 公有函数检查 const volatile 不变式, 只有非 volatile 公有函数检查 const (而非 const volatile) 不变式. 这是一个清晰的区分, 应当能满足大多数情况. 如果程序员需要非 volatile 公有函数也检查 const volatile 不变式, 可以像本文档所示那样, 从 const volatile 不变式函数中显式调用 const 不变式函数来做到.

[75] 在本例中, moved() 函数足够简单, 出于优化考虑, 程序员可以决定甚至不从它调用 boost::contract::public_function. 不过, 从 boost::contract::public_function 调用 moved() 并无负面影响 (运行期开销除外), 因为本库会在检查其他契约期间自动禁用契约检查 (所以这一调用不会导致无限递归).

[77] 当用作默认参数值时, lambda 函数允许在函数声明中编写代码语句. 然而, 这些 lambda 无法有效地用于在函数声明 (而非定义) 中编写契约. 这是因为 C++11 标准不允许函数声明中的 lambda 捕获任何变量 (理由很充分: 如何正确定义这类捕获的语义一点也不显而易见). 例如, 下面的代码不是有效的 C++, 无法编译:

// Specifications (in declaration).
int inc(int& x,
    // Error: Lambdas in default parameters cannot capture `this`, `x`, or any other variable.
    std::function<void ()> pre = [&] {
        BOOST_CONTRACT_ASSERT(x < std::numeric_limits<int>::max());
    },
    std::function<void (int const&, boost::contract::old_ptr<int> const&)> post
        = [&] (int const& result, boost::contract::old_ptr<int> const& old_x)
    {
        BOOST_CONTRACT_ASSERT(x == *old_x + 1);
        BOOST_CONTRACT_ASSERT(result == *old_x);
    }
);

// Implementation (in definition).
int inc(int& x,
    std::function<void ()> pre,
    std::function<void (int const&, boost::contract::old_ptr<int> const&)> post
) {
    int result;
    boost::contract::old_ptr<int> old_x = BOOST_CONTRACT_OLDOF(x);
    boost::contract::check c = boost::contract::function()
        .precondition(pre)
        .postcondition(std::bind(post, std::cref(result), std::cref(old_x)))
    ;

    return result = x++; // Function body.
}

无论如何, 即使上面的代码可以编译, 绑定返回值和旧值也需要大量样板代码.
