特性摘要

“在调试运行中, 人们对结果毫无信任, 却煞费苦心地做安全检查; 而在生产运行中, 错误结果可能代价高昂甚至酿成灾难, 这些检查却被移除——这是荒谬的. 如果一个航海爱好者在陆地上训练时穿上救生衣, 一到海上就把它脱掉, 我们会作何感想? ”

-- Charles Antony Richard Hoare (参见 [Hoare73])

本节概述契约式编程 (关于契约式编程更详尽的介绍, 参见 [Meyer97]、[Mitchell02] 和 [N1613]). 已经对契约式编程有基本了解的读者可以跳过本节, 或在读完教程后再回来阅读.

注释

本库的目标不是说服程序员使用契约式编程. 我们假定程序员已经理解契约式编程相关的收益与权衡, 并已决定在其代码中使用这一方法学. 在此前提下, 本库旨在成为 C++ 中最好、最完整的契约式编程库 (不使用 C++ 语言及其预处理器之外的程序和工具).

断言

契约式编程由以下断言机制来刻画:

  • 前置条件: 这些是程序员期望在函数被调用时为真的逻辑条件 (例如, 检查函数实参的约束). 在逻辑上没有前置条件的操作 (即对其输入的整个定义域总是良定义的操作) 也称为具有宽契约 (wide contract). 与之相对, 具有前置条件的操作也称为具有窄契约 (narrow contract) (注意, 真正窄契约的操作也应保证绝不抛出异常, 因为这类操作的实现体在其前置条件被检查为真之后总是预期成功). [6]
  • 后置条件: 这些是程序员期望在函数不抛出异常而退出时为真的逻辑条件 (例如, 检查函数的结果及其可能具有的任何副作用). 后置条件可以访问函数返回值 (对于非 void 函数), 还可以访问旧值 (即表达式在函数实现执行之前所具有的值).
  • 异常保证: 这些是程序员期望在函数抛出异常而退出时为真的逻辑条件. 异常保证可以访问旧值 (但不能访问函数返回值). [7]
  • 类不变式: 这些是程序员期望在构造函数不抛出异常而退出之后、每个非静态公有函数执行之前和之后 (即使它们抛出异常)、析构函数执行之前为真的逻辑条件 (析构函数执行之后也期望为真, 但仅当析构函数抛出异常时). 类不变式为给定类的所有对象定义有效状态. 可以为 volatile 公有函数指定一组不同的类不变式, 即volatile 类不变式. 也可以指定静态类不变式, 它们在任何构造函数、析构函数 (即使它不抛出异常) 和公有函数 (即使是静态的) 执行之前和之后都预期为真. [8]
  • 子契约: 这表示当派生类中的公有函数覆盖其一个或多个基类中的公有函数时, 前置条件不能被加强, 而后置条件和类不变式不能被削弱 (这依照替换原则 作出形式化定义).

处于这些契约断言之外的实际函数实现代码, 在契约式编程中通常称为函数体.

类不变式还可用于为对象指定基本异常安全保证 (因为即使在公有函数抛出异常时, 也会在其出口处检查它们). 异常保证的契约断言可用于为对同一对象的给定操作指定强异常安全保证.

契约式编程的另一个常见要求是: 当已经在检查来自另一个契约的断言时, 自动禁用契约检查 (以避免检查契约断言时发生无限递归).

注释

本库实现了这一要求, 但为了在检查另一个断言时全局禁用断言, 本库实现需要使用某种全局仲裁变量. 本库会自动保护这样的全局变量在多线程程序中免受竞态条件影响, 但这实际上会在程序中引入一个全局锁 (可以定义 BOOST_CONTRACT_DISABLE_THREADS 宏来禁用这个全局锁, 但有引发竞态条件的风险). [9]

一般而言, 建议使用独立的断言语句来指定不同的契约条件, 而不要用逻辑运算符 (&&、|| 等) 把它们归并为单一条件. 这是因为当用逻辑运算符把契约条件编写在同一个断言中时, 如果整个断言在运行期失败, 可能无法弄清实际失败的是哪个条件.

C 风格断言

使用 C 风格的 assert 宏可以实现一种受限形式的契约式编程 (通常是某种形式的前置条件和基本的后置条件检查). 使用 assert 是许多程序员的常见做法, 但它有如下局限:

  • assert 不区分前置条件和后置条件. 在经过充分测试的生产代码中, 后置条件通常可以在信任实现正确性的前提下被禁用, 而前置条件可能仍需保持启用, 因为调用代码可能发生变化 (例如, 某个库的后置条件可以在测试后禁用, 而库的前置条件保持启用, 因为调用该库的用户代码未来的变化无法预料). 使用 assert 无法做到只选择性地禁用后置条件, 所有断言必须一并禁用.
  • assert 需要手动编写额外的代码才能正确检查后置条件 (具体而言, 需要处理具有多个 return 语句的函数、在函数抛出异常时不检查后置条件, 以及实现旧值).
  • assert 需要手动编写额外的代码来检查类不变式 (额外的成员函数、try 块等).
  • assert 不支持子契约.
  • assert 调用通常散布在函数实现的各处, 因此程序员无法一眼看到被断言条件的全貌 (而当断言出现在函数声明中、或至少出现在函数定义的最顶部时, 则可以做到这一点).

契约式编程不存在这些局限.

收益与成本

收益

契约式编程的主要用途是提高软件质量. [Meyer97] 讨论了如何把契约式编程用作编写“正确” 软件的基本工具. [Stroustrup94] 讨论了类不变式的关键重要性以及前置条件和后置条件的优缺点.

以下主要受 [N1613] 启发, 简述与契约式编程相关的收益:

  • 前置条件与后置条件: 使用函数前置条件和后置条件, 程序员可以给出精确的语义描述, 说明函数在入口处要求什么、在出口处保证什么 (如果不抛出异常). 特别是, 借助后置条件旧值, 契约式编程提供了一种机制, 使程序员能够比较表达式在函数体执行前后的值. 这一机制足够强大, 使程序员能够在代码本身中表达许多正确性约束——否则这些约束充其量只能由文档非正式地加以描述.
  • 类不变式: 使用类不变式, 程序员可以描述对一个类的期望以及类成员之间的逻辑依赖关系. 构造函数的职责是确保对象首次创建时类不变式得到满足. 此后, 成员函数的实现可以大大简化, 因为编写它们时可以知道类不变式已得到满足——契约式编程会在每个公有函数执行之前和之后检查类不变式. 最后, 析构函数会在对象析构之前最后一次检查类不变式, 从而确保类不变式在对象的整个生命周期内成立. 类不变式还可以用作衡量良好抽象的标准: 如果无法指定不变式, 可能表明设计抽象较差, 本不应将其做成一个类 (也许用命名空间就足够了).
  • 自文档化代码: 契约是源代码的一部分, 它们在运行期被检查, 因此始终与代码本身保持同步. 因此, 由契约所文档化的程序规约可以始终被信任为与实现保持同步.
  • 更易调试: 契约式编程可以提供强大的调试设施, 因为如果契约编写得当, 缺陷会使契约断言恰好在问题最初出现之处失败, 而不是在程序执行的稍后阶段以表面上无关 (且通常难以调试) 的方式失败. 注意: 前置条件失败指向函数调用者的缺陷, 而后置条件失败则指向函数实现的缺陷. [10]
  • 更易测试: 契约式编程有助于测试, 因为契约天然地规定了测试应当检查什么. 例如, 函数的前置条件说明了哪些输入会导致函数失败, 后置条件说明了函数成功退出时产生哪些输出 (契约式编程应被视为补充和指导测试的工具, 但显然不能取代测试).
  • 形式化设计: 契约式编程以契约断言的形式提供一种精确且无歧义的规约语言, 有助于缩小设计者与程序员之间的差距. 此外, 契约通过阐明代码的部分语义和用法, 可以使代码评审更加容易.
  • 形式化继承: 契约式编程使用子契约将虚函数覆盖机制形式化, 其依据是替换原则. 这使基类程序员保持控制权, 因为覆盖函数始终必须完全满足其基类的契约.
  • 取代防御式编程: 契约式编程断言可以取代防御式编程 检查, 把这些检查局部化到契约中, 并使代码更具可读性.

当然, 并非所有形式化的契约规约都能在 C++ 中断言. 例如, 在一般情况下, C++ 无法断言迭代器范围的有效性 (因为检查两个迭代器是否构成有效范围的唯一办法是不断递增第一个迭代器直到它到达第二个迭代器, 但如果迭代器范围无效, 这样的代码将导致未定义行为或永远运行下去, 而不是令断言失败). 尽管如此, 大量契约断言仍可在 C++ 中成功编写, 本文档中的大量示例以及文献中的示例都说明了这一点 (例如参见使用本库实际上可以在 C++ 中编写多少 STL vector 的契约断言).

成本

一般而言, 契约式编程的收益以性能为代价, [Stroustrup94] 和 [Meyer97] 都对此做了详细讨论. 虽然应根据具体应用领域仔细权衡性能得失, 但软件质量不能牺牲: 很难看出能快速高效地给出错误结果的软件有什么价值.

运行期性能受到契约式编程的负面影响, 主要因为需要额外的时间去:

  • 检查被断言的条件.
  • 在后置条件或异常保证中使用旧值时复制旧值.
  • 调用检查前置条件、后置条件、异常保证、类不变式等的额外仿函数 (在使用子契约时, 这些调用会累积成大量额外调用).
注释

一般而言, 对于任意给定的非成员函数调用, 契约会引入至少三次额外的仿函数调用来检查前置条件、后置条件和异常保证. 公有函数还会引入另外两次函数调用来检查类不变式 (在入口和出口处). 对于子契约, 这些额外的调用 (其中一些会变成虚调用) 会按从基类覆盖的函数数量重复执行 (可能深入继承树). 除此之外, 本库为了正确检查契约, 还在其实现内部引入了若干函数调用.

为减轻运行期性能影响, 程序员可以选择性地禁用部分契约断言的运行期检查. 程序员必须根据其特定应用所需的性能权衡来决定, 但一种常见的合理做法是 (参见 禁用契约检查):

  • 始终编写契约以阐明设计的语义, 把规约直接嵌入代码, 使代码自文档化.
  • 在初始测试期间检查前置条件、后置条件、类不变式, 甚至可以检查异常保证.
  • 在发布测试和最终发布期间只检查前置条件 (以及可能的类不变式, 但不检查后置条件和异常保证).

这种做法通常合理, 因为在经过充分测试的生产代码中, 很少需要用后置条件来验证函数体实现, 因为该函数已在测试中证明自己是“正确” 的. 另一方面, 用前置条件检查函数实参始终是必要的, 因为调用代码可能发生变化 (而被调用代码不必重新测试和重新发布). 此外, 后置条件以及异常保证连同相关的旧值复制, 其检查的计算开销往往高于前置条件和类不变式.

函数调用

非成员函数

对带有契约的非成员函数的调用会执行以下步骤 (参见 boost::contract::function):

  1. 检查函数前置条件.
  2. 执行函数体.
  3. 如果函数体没有抛出异常, 检查函数后置条件.
  4. 否则, 检查函数异常保证.
私有函数与受保护函数

私有函数和受保护函数不必满足类不变式, 因为这些函数属于类的实现而非类的公有接口. 此外, 替换原则 不适用于私有函数和受保护函数, 因为在应用替换原则 的调用点处, 用户无法访问这些函数.

因此, 对带有契约的私有函数和受保护函数的调用会执行与上文针对非成员函数所述相同的步骤 (只检查前置条件和后置条件, 不检查类不变式, 也不进行子契约).

公有函数调用

覆盖公有函数

考虑派生类中的一个公有函数, 它覆盖其公有基类所声明的公有虚函数 (由于 C++ 的多重继承, 该函数可能从不止一个基类覆盖). 我们把派生类中的这个函数称为覆盖函数 (overriding function), 把包含全部被覆盖函数 (overridden functions) 的基类集合称为被覆盖基类 (overridden bases).

进行子契约时, 被覆盖函数会在 (编译期) 深入搜索继承树的所有公有分支 (即不仅检查派生类的直接公有父类, 还检查其所有公有祖父类等). 在多重继承的情况下, 这一搜索还会 (在编译期) 横向扩展到多重继承森林中的所有公有树 (多个公有基类按其在派生类继承列表中的声明顺序被搜索). 与 C++ 多重继承的惯常情况一样, 这一搜索可能得到多个被覆盖函数, 因此会从多个公有基类进行子契约. 注意, 只有公有基类才被纳入子契约的考虑, 因为在使用替换原则 的调用点处, 私有和受保护基类对用户不可访问.

对带有契约的覆盖公有函数的调用会执行以下步骤 (参见 boost::contract::public_function):

  1. 检查所有被覆盖基类的静态类不变式 AND 非静态类不变式, AND 然后检查派生类的静态 AND 非静态不变式.
  2. 在OR 下把来自所有被覆盖基类的被覆盖公有函数的前置条件彼此取或检查, OR 否则检查派生类中覆盖函数的前置条件.
  3. 执行覆盖函数的函数体.
  4. 检查所有被覆盖基类的静态类不变式 AND 非静态类不变式, AND 然后检查派生类的静态 AND 非静态不变式 (即使函数体抛出了异常).
  5. 如果函数体没有抛出异常, 则在AND 下把来自所有被覆盖基类的被覆盖公有函数的后置条件彼此取或检查, AND 然后检查派生类中覆盖函数的后置条件.
  6. 否则, 在AND 下把来自所有被覆盖基类的被覆盖公有函数的异常保证彼此取或检查, AND 然后检查派生类中覆盖函数的异常保证.

而 volatile 公有函数检查的则是静态类不变式 AND volatile 类不变式. volatile 公有函数的前置条件与后置条件以及 volatile 类不变式将对象作为 volatile 来访问.

类不变式先于前置条件和后置条件检查, 因此编写前置条件和后置条件断言时可以假定类不变式已得到满足而加以简化 (例如, 如果类不变式断言某指针不能为空, 那么前置条件和后置条件就可以安全地对该指针解引用而无需额外检查). 类似地, 静态类不变式先于非静态类不变式检查, 因此编写非静态类不变式 (volatile 与非 volatile) 时可以假定静态类不变式已得到满足而加以简化. 此外, 子契约先检查公有基类的契约再检查派生类的契约, 因此编写派生类契约断言时可以假定公有基类契约已得到满足而加以简化.

注释

本文档中 AND 与 OR 表示与 和 或 运算, 以短路 方式求值. 例如: p AND q 为真, 当且仅当 p 和 q 都为真; 但当 q 为假时, p 永远不会被求值; p OR q 为真, 当且仅当 p 或 q 之中至少一者为真; 但当 q 为真时, p 永远不会被求值.

如上述步骤所示, 并依照替换原则, 子契约把前置条件的检查放在OR 中进行, 而类不变式、后置条件和异常保证则在AND 中分别与基类的前置条件、类不变式、后置条件和异常保证一同检查.

非覆盖公有函数

对带有契约的非静态公有函数 (不覆盖其任何公有基类中的函数) 的调用会执行以下步骤 (参见 boost::contract::public_function):

  1. 检查类的静态 AND 非静态不变式 (但不检查基类的任何不变式).
  2. 检查函数前置条件 (但不检查基类中函数的任何前置条件).
  3. 执行函数体.
  4. 检查类的静态 AND 非静态不变式 (即使函数体抛出了异常; 但不检查基类的任何不变式).
  5. 如果函数体没有抛出异常, 检查函数后置条件 (但不检查基类中函数的任何后置条件).
  6. 否则, 检查函数异常保证 (但不检查基类中函数的任何异常保证).

而 volatile 公有函数检查的则是静态类不变式 AND volatile 类不变式. volatile 函数的前置条件和后置条件以及 volatile 类不变式将对象作为 volatile 来访问.

会检查类不变式, 因为该函数属于类的公有接口. 但不会检查基类的任何契约, 因为该函数不覆盖任何公有基类中的任何函数 (所以替换原则 在这种情况下不要求进行子契约).

静态公有函数

对带有契约的静态公有函数的调用会执行以下步骤 (参见 boost::contract::public_function):

  1. 检查静态类不变式 (但不检查非静态不变式, 也不检查基类的任何不变式).
  2. 检查函数前置条件 (但不检查基类中函数的任何前置条件).
  3. 执行函数体.
  4. 检查静态类不变式 (即使函数体抛出了异常; 但不检查非静态不变式, 也不检查基类的任何不变式).
  5. 如果函数体没有抛出异常, 检查函数后置条件 (但不检查基类中函数的任何后置条件).
  6. 否则, 检查函数异常保证 (但不检查基类中函数的任何异常保证).

会检查类不变式, 因为该函数属于类的公有接口, 但只能检查静态类不变式 (因为这是静态函数, 无法访问对象, 而检查非静态类不变式——无论是否 volatile——恰恰需要访问对象). 此外, 静态函数不能覆盖任何函数, 因此替换原则 不适用, 它们也不进行子契约.

静态函数的前置条件和后置条件以及静态类不变式无法访问对象 (因为它们是在 static 成员函数中进行检查的).

构造函数调用

对带有契约的构造函数的调用会执行以下步骤 (参见 boost::contract::constructor_precondition 与 boost::contract::constructor):

  1. 检查构造函数前置条件 (但这些前置条件无法访问对象, 因为对象尚未构造).
  2. 执行构造函数的成员初始化列表 (如果存在).
    1. 按照 C++ 构造机制构造任何基类 (无论公有与否), 并检查这些基类构造函数的契约 (依照与此处所列步骤类似的步骤).
  3. 检查静态类不变式 (但不检查非静态或 volatile 类不变式, 因为对象尚未构造完成).
  4. 执行构造函数体.
  5. 检查静态类不变式 (即使函数体抛出了异常).
  6. 如果函数体没有抛出异常:
    1. 检查非静态 AND volatile 类不变式 (因为对象此时已成功构造).
    2. 检查构造函数后置条件 (但这些后置条件无法访问对象的旧值 oldof(*this), 因为在构造函数体执行之前对象尚不存在).
  7. 否则, 检查构造函数异常保证 (但这些异常保证无法访问对象的旧值 oldof(*this), 因为在构造函数体执行之前对象尚不存在; 而且它们只能访问类的静态成员, 因为在此情况下构造函数体抛出了异常, 对象并未成功构造).

构造函数前置条件在执行成员初始化列表之前检查, 因此编写这些初始化时可以假定构造函数前置条件已得到满足而加以简化 (例如, 构造函数实参可以在用于初始化基类和数据成员之前, 先由构造函数前置条件加以验证).

如上文步骤 2.a. 所示, C++ 的对象构造机制会在初始化这些基类时自动检查基类契约 (此处无需显式的子契约行为).

析构函数调用

对带有契约的析构函数的调用会执行以下步骤 (参见 boost::contract::destructor):

  1. 检查静态类不变式 AND 非静态 AND volatile 类不变式.
  2. 执行析构函数体 (析构函数没有参数, 且可以在对象构造之后的任何时刻被调用, 因此它们没有前置条件).
  3. 检查静态类不变式 (即使函数体抛出了异常).
  4. 如果函数体没有抛出异常:
    1. 检查析构函数后置条件 (但它们只能访问类的静态成员以及对象的旧值 oldof(*this), 因为析构函数体成功执行后对象已被销毁). [11]
    2. 按照 C++ 析构机制析构任何基类 (无论公有与否), 并检查这些基类析构函数的契约 (依照与此处所列步骤类似的步骤).
  5. 否则 (虽然在 C++ 中析构函数即使可以抛异常, 也应极少允许其抛出):
    1. 检查非静态 AND volatile 类不变式 (因为对象未成功析构, 所以它仍然存在, 并应满足其不变式).
    2. 检查析构函数异常保证.

如上文步骤 4.b. 所示, C++ 的对象析构机制会在析构函数不抛出异常而退出时自动检查基类契约 (此处无需显式的子契约行为).

注释

考虑到 C++ 允许析构函数抛出异常, 本库会如上文所述处理析构函数体抛出异常的情况. 不过, 为符合 STL 异常安全保证和良好的 C++ 编程实践, 程序员应实现析构函数体使之极少 (最好从不) 抛出异常 (实际上析构函数在 C++11 中被隐式声明为 noexcept).

常量正确性

不应允许契约修改程序状态, 因为契约只负责检查 (而不是改变) 程序状态, 以验证其是否符合规约. 因此, 契约只应以const 上下文访问对象、函数实参、函数返回值、旧值以及所有其他程序变量 (通过 const&、const* const、const volatile 等).

在可能的情况下 (例如类不变式和后置条件旧值), 本库会自动强制这一常量正确性约束, 方法是利用 const 在编译期进行检查. 然而, 本库无法在所有情况下自动强制这一约束 (例如可变成员函数的前置条件和后置条件、全局变量等情形). 关于在编译期强制常量正确性约束的本库使用方式, 参见 不使用 lambda 函数 (但其代价是需要手动编写大量样板代码, 故一般不推荐).

注释

一般而言, 编写只检查而不修改程序变量的断言是程序员的责任. [12]

规约与实现

契约是程序规约的一部分, 而不是其实现的一部分. 因此, 理想情况下契约应当编写在 C++ 声明之中, 而不是定义之中.

一般而言, 本库无法满足这一要求. 不过, 即使契约与函数体一起编写在函数定义中, 用户仍然相当容易识别并只读函数定义中的契约部分 (因为契约代码必须始终编写在函数定义的最顶部). 关于把契约规约编写在函数体实现之外的本库使用方式, 参见 分离函数体实现 (但其代价是每个函数都要多写一个额外的函数, 故一般不推荐).

此外, 当契约只用公有成员来断言条件时最有用 (在大多数情况下, 需要使用非公有成员来检查契约——尤其是前置条件——表明类设计有误). 例如, 如果前置条件断言使用了调用者无法调用的私有成员, 那么公有函数的调用者通常无法确保函数前置条件得到满足 (因此, 前置条件失败不一定表明调用者有缺陷, 因为调用者本来就无法完整检查前置条件). 不过, 考虑到 C++ 为程序员提供了绕过访问级别限制的手段 (friend、函数指针等), 本库把确保契约断言 (尤其是前置条件) 只使用公有成员的责任留给程序员. ([N1962] 采取同样的做法, 不把契约限制为只能使用公有成员; 而 Eiffel 则在前置条件使用非公有成员断言时产生编译期错误. ) [13]

关于契约失败

如果前置条件、后置条件、异常保证或类不变式在运行期被检查为假, 或者其求值抛出异常, 本库将调用特定的失败处理器函数. [14]

默认情况下, 这些失败处理器函数向标准错误 std::cerr 打印一条消息 (含关于失败的详细信息), 然后调用 std::terminate 终止程序. 不过, 使用 boost::contract::set_precondition_failure、boost::contract::set_postcondition_failure、boost::contract::set_except_failure、boost::contract::set_invariant_failure 等, 程序员可以定义自己的失败处理器函数, 执行任何用户指定的操作 (抛出异常、以错误码退出程序等, 参见 失败时抛出异常). [15]

注释

在 C++ 中, 编写抛出异常而非终止程序的契约失败处理器存在若干问题. 具体而言, 析构函数会检查类不变式, 因此如果程序员把类不变式失败处理器改为抛出异常而不是终止程序, 析构函数就会抛出异常, 但一般而言 C++ 中的析构函数不应抛出异常 (为了符合 STL 异常安全、C++11 对析构函数的隐式 noexcept 声明等). 此外, 把失败处理器编写为在异常保证失败时抛出异常, 会导致在一个已有活动异常 (即最初触发异常保证检查的那个异常) 的情况下再抛出一个异常 (即报告契约失败的异常), 而这将迫使 C++ 无论如何都终止程序.

因此, 建议至少在来自析构函数和异常保证的契约失败时终止程序 (如果不在所有其他契约失败情形下都如此的话——本库默认即为如此). 使用本库编写的契约失败处理器函数带有关于失败契约 (前置条件、后置条件等) 以及正在检查该契约的操作 (构造函数、析构函数等) 的信息, 因此程序员可以细粒度地区分所有情形, 并决定何时适合终止、抛出异常或执行其他用户自定义操作.

[a] 设计理由: 本库的旧版本也会从契约定义宏自动生成 Doxygen 文档. 出于多种原因放弃了这一功能: 本库不再使用宏来编写契约; 甚至在此之前, 本库宏的实现已变得过于复杂, Doxygen 预处理器无法再展开它们; Doxygen 文档只是契约代码的重复 (程序员本可直接查看源代码中的契约); Doxygen 未必是所有 C++ 程序员都在使用的文档工具.

据作者所知, 这是唯一一个完整支持 C++ 全部契约式编程特性的库 (不使用语言本身之外的预处理工具). 概括而言:

  • 在 C++ 中实现前置条件和后置条件并不困难 (例如, 使用某种 RAII 对象).
  • 实现后置条件旧值也不算太难 (通常要求程序员把旧值复制到局部变量中), 但要确保在后置条件被禁用时不执行这些复制, 就已经稍微困难一些了. [16]
  • 实现类不变式则更为复杂 (尤其是要自动完成、不需要程序员手动调用额外函数来检查不变式时). [17] 此外, 作者们审阅过的所有文献似乎都没有考虑静态和 volatile 函数, 因而都不支持静态和 volatile 不变式.
  • 实现子契约涉及相当大的复杂性, 而且除本库外似乎没有任何其他 C++ 库对其提供恰当支持 (尤其是在处理多重继承时, 要沿继承树深处对所有被覆盖契约正确复制后置条件旧值, 并把返回值正确报告给基类中被覆盖虚函数的后置条件). [18]

[6] 宽契约与窄契约的命名法近年来在 C++ 社区获得了不少人气 (出现在若干较新的、向 C++ 标准添加契约式编程的提案中, 参见 参考文献). 这一命名法完全合理, 但本文档中不常使用它, 只是因为作者们通常更愿意直接说 "该操作没有前置条件……" 或 "该操作有前置条件……" (这只是口味问题).

[8] 设计理由: 静态和 volatile 类不变式由本库首创 (只是为了反映 C++ 也支持静态和 volatile 公有函数这一事实), 它们不是 [N1962] 或参考文献 中所列其他文献的一部分.

[9] 设计理由: BOOST_CONTRACT_DISABLE_THREADS 的命名源自 BOOST_DISABLE_THREADS.

[10] 当然, 如果契约本身编写不当, 契约式编程就没什么用处. 不过, 在函数体和契约两处同时出现缺陷的可能性, 低于只在函数体一处出现缺陷的可能性. 例如, 考虑在后置条件中验证结果. 验证返回值看似多余, 但在这种情况下我们恰恰需要这种冗余. 程序员编写函数时, 存在一定的概率在实现函数体时犯错. 程序员在后置条件中指定函数结果时, 也存在一定的概率在编写契约时犯错. 然而, 程序员犯两次错 (在函数体和 契约两处) 的概率, 一般低于只犯一次错 (在函数体或 契约一处) 的概率.

[11] 设计理由: 析构函数的后置条件不是 [N1962] 或参考文献 中所列其他文献的一部分 (不过就 [Meyer97] 而言, 应当指出 Eiffel 不支持静态数据成员, 这可能正是 Eiffel 中析构函数没有后置条件的原因). 然而, 原则上析构函数后置条件可能有用, 因此本库为析构函数提供后置条件 (例如, 一个统计对象实例数的类可以使用析构函数后置条件断言: 由于对象已被析构, 存储在静态数据成员中的实例计数器减少了 1).

[12] 注意, 在使用 C 风格的 assert 时同样如此.

[16] 例如, 下面的伪代码尝试在 [P0380] 中模拟旧值:

struct scope_exit { // RAII.
    template<typename F>
    explicit scope_exit(F f) : f_(f) {}
    ~scope_exit() { f_(); }

    scope_exit(scope_exit const&) = delete;
    scope_exit& operator=(scope_exit const&) = delete;
private:
    std::function<void ()> f_;
};

void fswap(file& x, file& y)
    [[expects: x.closed()]]
    [[expects: y.closed()]]
    // Cannot use [[ensures]] for postconditions so to emulate old values.
{
    file old_x = x; // Emulate old values with local copies (not disabled).
    file old_y = y;
    scope_exit ensures([&] { // Check after local objects destroyed.
        if(std::uncaught_exceptions() == 0) { // Check only if no throw.
            [[assert: x.closed()]]
            [[assert: y.closed()]]
            [[assert: x == old_y]]
            [[assert: y == old_x]]
        }
    });

    x.open();
    scope_exit close_x([&] { x.close(); });
    y.open();
    scope_exit close_y([&] { y.close(); });
    file z = file::temp();
    z.open;
    scope_exit close_z([&] { z.close(); });

    x.mv(z);
    y.mv(x);
    z.mv(y);
}

这需要样板代码来确保: 只有在函数未抛出异常时才检查后置条件, 并且是在所有其他局部对象都销毁之后的 scope_exit RAII 对象中检查 (因为这些析构函数中有一些会参与建立后置条件). 此外, 它从不禁用旧值复制 (即使在发布构建中禁用了后置条件也不禁用, 而要禁用就得使用 #ifdef 等再添加更多样板代码).

[17] 例如, 下面的伪代码尝试在 [P0380] 中模拟类不变式:

template<typename T>
class vector {
    bool invariant() const {        // Check invariants at...
        [[assert: empty() == (size() == 0)]]
        [[assert: size() <= capacity()]]
        return true;
    }

public:
    vector()
        [[ensures: invariant()]]    // ...constructor exit (only if no throw).
    { ... }

    ~vector() noexcept
        [[expects: invariant()]]    // ...destructor entry.
    { ... }

    void push_back(T const& value)
        [[expects: invariant()]]    // ...public function entry.
        [[ensures: invariant()]]    // ...public function exit (if no throw).
    try {
        ... // Function body.
    } catch(...) {
        invariant();                // ...public function exit (if throw).
        throw;
    }

    ...
};

这需要样板代码来手动调用检查不变式的函数 (注意: 不变式会在公有函数出口处检查, 无论是否抛出异常, 而后置条件则不然). 如果析构函数可以抛出异常 (例如, 它被声明为 noexcept(false)), 析构函数还需要一个 try-catch 语句, 与为 push_back 编写的语句类似, 以便在析构函数抛出异常时在出口处检查类不变式. 此外, 如果 empty 和 size 也是被编写为检查类不变式的公有函数, 仍有一个未决问题: 如何避免无限递归 (因为 [P0380] 在检查其他断言期间不会自动禁用断言).
