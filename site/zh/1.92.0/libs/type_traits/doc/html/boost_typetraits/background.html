背景与教程

下文是 John Maddock 与 Steve Cleary 所撰写文章 "C++ Type traits" 的更新版, 刊载于 2000 年 10 月号 Dr Dobb's Journal.

泛型编程 (即编写可作用于任何满足一组需求的数据类型的代码) 已成为提供可复用代码的首选方法. 然而, 泛型编程中 "泛型" 一词有时并不够用——类型之间的差异有时太大, 以至于无法给出高效的泛型实现. 此时, 特征 (traits) 技术便显得尤为重要——把那些需要逐个类型单独考虑的属性封装进特征类 (traits class) 中, 就能将必须随类型而异的代码量降到最少, 并使泛型代码量达到最大.

考虑一个例子: 处理字符串时, 一个常见的操作是求以 null 结尾的字符串的长度. 显然可以编写能做到这一点的泛型代码, 但事实证明有高效得多的方法可用: 例如, C 库函数 strlen 和 wcslen 通常用汇编语言实现, 在适当的硬件支持下, 可以比用 C++ 编写的泛型版本快得多. C++ 标准库的作者们意识到了这一点, 并将 char 和 wchar_t 的属性抽象到了类 char_traits中. 处理字符串的泛型代码只需使用 char_traits<>::length 来求以 null 结尾的字符串的长度, 并确信 char_traits 的特化版本会采用其可用的最合适的方法.

类型特征

类 char_traits 是一个把类型特定属性集封装在单个类中的经典例子——Nathan Myers 称之为 行李类 (baggage class)[1]. 在 Boost type-traits 库中, 我们[2] 编写了一组非常具体的特征类, 其中每一个都封装了 C++ 类型系统中的一个单独的特征 (trait); 例如, 某个类型是指针还是引用类型? 或者某个类型是否具有平凡的构造函数 (trivial constructor), 或 const 限定符? 这些 type-traits 类共享统一的设计: 若类型具有指定的性质, 类就继承自类型 true_type (如果该类型具有指定的性质); 否则继承自 false_type. 我们将会展示, 这些类可用于泛型编程, 以判定给定类型的性质, 并引入适合该情形的优化.

type-traits 库还包含一组对类型执行特定变换的类; 例如, 它们可以从类型中移除顶层 const 或 volatile 限定符. 每个执行变换的类都定义一个单独的 typedef 成员 type 作为变换的结果. 所有 type-traits 类都定义在命名空间 boost中; 为简洁起见, 本文给出的大多数代码示例都省略了命名空间限定.

实现

type-traits 库中包含的独立类太多, 无法在此给出完整实现——完整细节请参阅 Boost 库中的源代码. 不过, 其实现大多相当重复, 因此这里只展示其中一些类的实现方式, 让大家有个大致印象. 从库中可能是最简单的类 is_void<T> 继承自 true_type ——仅当 T 为 void时.

template <typename T>
struct is_void : public false_type{};

template <>
struct is_void<void> : public true_type{};

这里我们定义了模板类 is_void的主版本, 并在 T 为 void时提供其全特化 (full-specialization) 版本. 虽然模板类的全特化是一项重要技术, 但有时我们需要一种介于完全泛型解决方案与全特化之间的方案. 标准委员会定义偏模板类特化 (partial template-class specialization) 正是为了应对这种情形. 作为示例, 考虑类 boost::is_pointer<T>: 这里我们需要一个处理 T 不是指针的所有情形的主版本, 以及一个处理 T 是指针的所有情形的偏特化版本:

template <typename T>
struct is_pointer : public false_type{};

template <typename T>
struct is_pointer<T*> : public true_type{};

偏特化的语法有些晦涩, 其内容本身就足以写成一篇独立的文章; 与全特化一样, 要为类编写偏特化, 必须先声明主模板. 偏特化在类名后包含一个额外的 <...>, 其中存放偏特化参数; 这些参数定义了将绑定到该偏特化 (而非默认模板) 的类型. 关于偏特化中可以出现什么内容的规则有些复杂, 但根据经验, 如果你可以合法地写出如下形式的两个函数重载:

void foo(T);
void foo(U);

那么你还可以写出如下形式的偏特化:

template <typename T>
class c{ /*details*/ };

template <typename T>
class c<U>{ /*details*/ };

这条规则绝非万无一失, 但它相当容易记忆, 且与实际规则足够接近, 对日常使用很有帮助.

作为偏特化的一个更复杂的例子, 考虑类 remove_extent<T>. 该类定义了一个单独的 typedef 成员 type, 其类型与 T 相同, 但移除了所有顶层数组边界; 这是一个对类型执行变换的特征类的例子:

template <typename T>
struct remove_extent
{ typedef T type; };

template <typename T, std::size_t N>
struct remove_extent<T[N]>
{ typedef T type; };

关于 remove_extent 的目的如下: 设想一个以数组类型作为模板参数传入的泛型算法, remove_extent 提供了一种确定该数组底层元素类型的方法. 例如 remove_extent<int[4][5]>::type 会求值为类型 int[5]. 这个例子还表明, 偏特化中的模板参数个数不必与默认模板中的参数个数相同. 然而, 出现在类名之后的那些参数的个数与类型, 必须与默认模板中的参数相匹配.

优化的 copy

作为 type traits 类用法的示例, 考虑标准库算法 copy:

template<typename Iter1, typename Iter2>
Iter2 copy(Iter1 first, Iter1 last, Iter2 out);

显然, 编写一个可作用于所有迭代器类型 Iter1 和 Iter2的泛型版本 copy 并非难事; 然而, 在某些情况下, copy 操作最好通过调用 memcpy来完成. 若要以 memcpy 为基础实现 copy, 必须满足以下所有条件:

  • 迭代器类型 Iter1 和 Iter2 必须都是指针.
  • 要求 Iter1 和 Iter2 必须都指向同一类型——不含 const 和 volatile 限定符.
  • 被 Iter1 所指向的类型必须具有平凡的赋值运算符 (trivial assignment operator).

所谓平凡的赋值运算符, 是指该类型是标量类型 (scalar type)[3], 或者:

  • 该类型没有用户定义的赋值运算符.
  • 该类型没有任何引用类型的数据成员.
  • 所有基类和所有数据成员对象都必须具有平凡的赋值运算符.

如果上述条件全部满足, 则可以使用 memcpy 来复制该类型, 而不必使用编译器生成的赋值运算符. type-traits 库提供了一个类 has_trivial_assign, 使得 has_trivial_assign<T>::value 仅当 T 具有平凡的赋值运算符时才为 true. 该类对标量类型 "直接可用", 但对于那些恰好也具有平凡赋值运算符的 class/struct 类型, 则必须显式特化. 换句话说, 如果 has_trivial_assign 给出了错误的答案, 那么这个错误答案也是 "安全" 的——即判定平凡赋值不可用.

一个在适当之处使用 memcpy 的 copy 优化版本的代码见 示例. 代码首先定义模板函数 do_copy, 其执行 "慢而安全" 的复制. 传给该函数的最后一个参数可以是 true_type 或 false_type. 接着还有一个 do_copy 的重载, 其使用 memcpy: 此时要求迭代器确实是指向同一类型的指针, 且最后一个参数必须是 true_type. 最后, copy 的版本会调用 do_copy, 并把 has_trivial_assign<value_type>() 作为最后一个参数: 这将在适当时机分派到优化版本, 否则将调用 "慢而安全" 的版本.

这样做值得吗?

在这些专栏中, 人们常常反复强调 "过早的优化是万恶之源" [4]. 因此必须提出这样的问题: 我们的优化是否过早? 为了便于直观比较, 表 1 中列出了我们的 copy 版本与传统泛型 copy[5] 相比的计时结果.

显然, 在这个例子中优化确实带来了差别; 但公平地说, 该计时设置偏向于排除缓存未命中的影响——若非如此, 算法之间的准确比较将变得困难. 不过, 对于 "过早优化" 这一准则, 我们或许可以补充以下几点注意事项:

  • 如果一开始就为任务选用正确的算法, 那么就无需再做优化; 在某些情况下, memcpy 就是正确的算法.
  • 如果一个组件将被许多人在许多场合反复使用, 那么优化很可能值得去做, 而在单一使用场景中则未必——换句话说, 优化在某个时间某个场合成为绝对必要的可能性要大得多. 同样重要的是, 标准实现的公认价值也会更高: 如果用户以存在更好、优化程度更高的可用版本为由拒绝某个算法, 那么将其标准化就没有意义.

引用的 pair

优化 copy 的示例展示了如何利用类型特征在编译期作出优化决策. 类型特征的另一项重要用途, 是让原本无法编译 (除非大量使用偏特化) 的代码得以编译. 这可以通过把偏特化委托给类型特征类来实现. 这种用法的一个示例是能够容纳引用的 pair [6].

首先, 让我们考察 std::pair的定义, 为简单起见, 省略比较运算符、默认构造函数和模板拷贝构造函数:

template <typename T1, typename T2>
struct pair
{
typedef T1 first_type;
typedef T2 second_type;

T1 first;
T2 second;

pair(const T1 & nfirst, const T2 & nsecond)
:first(nfirst), second(nsecond) { }
};

按照现状, 这个 "pair" 无法容纳引用, 因为其构造函数需要获取引用的引用, 而这在目前是非法的 [7]. 让我们考虑一下, 要让 "pair" 能够容纳非引用类型、引用和常量引用, 构造函数的参数必须是什么类型:

这使我们可以为 pair 构建一个主模板定义, 使其能够容纳非引用类型、引用类型和常量引用类型:

template <typename T1, typename T2>
struct pair
{
typedef T1 first_type;
typedef T2 second_type;

T1 first;
T2 second;

pair(boost::add_reference<const T1>::type nfirst,
      boost::add_reference<const T2>::type nsecond)
:first(nfirst), second(nsecond) { }
};

把标准比较运算符、默认构造函数和模板拷贝构造函数 (它们都是相同的) 加回去, 就得到一个 std::pair, 它能够容纳引用类型!

同样的扩展本可以借助 pair的偏模板特化来实现, 但以这种方式特化 pair 需要三个偏特化, 外加主模板. 类型特征让我们能够定义一个单一的主模板, 它能自动适配上述任何一种偏特化, 而无需采用暴力的偏特化方案. 以这种方式使用类型特征, 程序员可以把偏特化委托给类型特征类, 从而得到更易维护、更易理解的代码.

结论

我们希望本文能让大家对类型特征 (type-traits) 有所了解. 可用类的更完整清单见 boost 文档, 其中还包含更多使用类型特征的示例. 模板使 C++ 用户得以享受泛型编程带来的代码复用; 希望本文已经表明, 泛型编程不必沦落到只能依赖最小公分母, 模板既可以做到通用, 也可以做到最优.
