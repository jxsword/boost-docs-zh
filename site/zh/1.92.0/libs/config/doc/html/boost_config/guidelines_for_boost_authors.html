修改 Boost 配置头文件

头文件 <boost/config.hpp> 用于把配置信息传递给其他 boost 文件, 使它们能够应对平台依赖, 例如算术字节序、编译器 pragma 或编译器缺陷. 若没有这些配置信息, 许多现有编译器将无法与 Boost 库一起工作.

把配置信息集中在此头文件中, 可减少把库移植到新平台或编译器更新时必须修改的文件数量. 理想情况下, 移植到新平台时无需修改任何其他文件.

配置头文件存在争议, 因为一些人认为它们纵容有缺陷的编译器并助长非标准子集. 为更多平台添加设置以及维护现有设置也可能成为问题. 换言之, 配置头文件是不得已而为之的恶, 而非理想的特性. boost config.hpp 的策略旨在把配置头文件的问题降至最少、收益增至最大.

注意:

  • 不要求 Boost 库实现者 “#include <boost/config.hpp>”, 也不要求他们以任何方式支持不符合 C++ 标准 (ISO/IEC 14882) 的编译器.
  • 若库实现者希望支持某个不符合标准的编译器, 或支持某个平台特定特性, “#include <boost/config.hpp>” 是获取标准头文件 (如 <climits> 等) 中不可得的配置信息的首选方式.
  • 若配置信息可以从标准头文件 (如 <climits>) 推导得出, 则使用那些标准头文件而非 <boost/config.hpp>.
  • 使用 <boost/config.hpp> 应在宏未定义时具有合理的、符合标准的默认行为. 这意味着把 <boost/config.hpp> 移植到新平台的起点就是完全不定义任何特定于该平台的内容. 在极少数没有合理默认行为的情况下, 应使用 #error 消息描述该问题.
  • 若 Boost 库实现者希望向 config.hpp 中添加内容, 请在 Boost 邮件列表上发布请求. 无法保证此类请求会被采纳; 其意图是限制 config.hpp 的复杂度.
  • 其意图是只支持那些正在走向符合 C++ 标准的编译器, 而且只支持这些编译器的近期发布版本.
  • 其意图并不是禁用如今已被大多数编译器充分支持的主流特性, 例如命名空间、异常、RTTI 或模板.

禁用编译器警告

头文件 <boost/config/warning_disable.hpp> 可用于禁用某些难以或无法以其他方式消除的编译器警告.

注意:

  • 此头文件 绝不应被另一个 Boost 头文件包含, 它只应被库源文件或测试用例使用.
  • 应在包含任何其他头文件之前包含该头文件.
  • 此头文件只禁用那些难以或无法以其他方式处理、且通常仅由某一个编译器 (或某一个编译器自己的标准库头文件) 发出的警告.

当前它禁用以下警告:

编译器

警告

Visual C++ 8 及更高版本

C4996: 错误 'function': 已被声明为弃用

Intel C++

警告 1786: 与使用 “已弃用” 标准库函数有关, 类似于 Visual C++ 中的 C4996.

添加新缺陷宏

当你需要添加新的缺陷宏时 — 无论是为了修复现有库的问题, 还是在添加新库时 — 先把问题提炼成简单的测试用例; 通常此时其他 (可能更好的) 变通办法会变得明朗. 其次, 务必将测试用例代码发布到 boost 邮件列表并征求意见; 记住 C++ 很复杂, 有时看似缺陷的东西, 实际可能是作者对标准的理解有问题.

命名该宏时, 请遵循 BOOST_NO_SOMETHING 命名约定, 使其显而易见这是一个报告缺陷的宏.

最后, 把测试程序添加到回归测试中. 你需要把测试用例放入一个 .ipp 文件, 并在靠近顶部处加上以下注释:

//  MACRO:         BOOST_NO_FOO
//  TITLE:         foo
//  DESCRIPTION:   If the compiler fails to support foo

这些注释由 autoconf 脚本处理, 因此务必确保格式与给定格式一致. 文件应命名为 “boost_no_foo.ipp”, 其中 foo 是缺陷描述 — 不过请尽量把文件名保持在 Mac 30 字符文件名限制之内. 你还需要提供函数原型 “int test()”, 它声明在一个与宏同名但全小写的命名空间中, 并在成功时返回零:

namespace boost_no_foo {
int test()
{
    // test code goes here:
    //
    return 0;
}

}

一旦测试代码就位于 libs/config/test 中, 更新配置测试系统的步骤如下:

  • 进入 libs/config/tools 并运行 bjam 这会生成 .cpp 文件测试用例 (取自 .ipp 文件), 并更新 libs/config/test/all/Jamfile.v2config_test.cpp 和 config_info.cpp.

  • 进入 libs/config/test/all 并运行 bjam MACRONAME compiler-list, 其中 MACRONAME 是新宏的名称, 而 compiler-list 是以空格分隔的待测编译器列表.

    xxx_pass_test 和 xxx_fail_test 都应报告 **passed**.

    若 MACRONAME 在应定义时未定义, xxx_pass_test 将不会报告 **passed**. 若 MACRONAME 在不应定义时被定义, xxx_fail_test 将不会报告 **passed**.

  • 进入 libs/config/test 并运行 bjam config_info config_test compiler-list. config_info 对于 compiler-list 中的所有编译器都应干净地构建并运行, 而 config_test 对于有该缺陷的编译器应失败, 对于没有该缺陷的编译器应通过.

然后你应当:

  • 在需要该缺陷宏的那些配置头文件中定义它.
  • 在本文档中记录该宏 (请不要忘记这一步!!)
  • 提交所有改动.
  • 留意回归测试, 关注此添加是否给 Boost.Config 带来新的失败.
  • 开始使用该宏.

添加新特性测试宏

当你需要添加一个描述标准所不要求的特性的宏时, 请遵循添加新缺陷宏的约定 (见上文), 但把宏命名为 BOOST_HAS_FOO, 并把测试文件命名为 “boost_has_foo.ipp”. 尽量不要不必要地添加特性测试宏: 如果已有某个平台特定宏 (例如 _WIN32、__BEOS__ 或 __linux__) 可用于识别该特性, 就使用它. 尽量让宏对应一个特性组或头文件名, 而非某个具体 API (例如 BOOST_HAS_NL_TYPES_H 而非 BOOST_HAS_CATOPEN). 若该宏描述一个 POSIX 特性组, 则向 <boost/config/detail/suffix.hpp> 添加样板代码, 以便在可能处自动检测该特性 (如果你想知道为什么我们不能直接使用 POSIX 特性测试宏, 请记住其中许多特性可以由第三方库添加, 因此不会在 <unistd.h> 内部被识别).

修改 Boost 配置头文件

boost 配置设置的目标是配置头文件应相对稳定 — boost 用户不应仅仅因为自己不关心的某个编译器的配置发生了变化而不得不重新编译其代码. 把配置拆分为独立的编译器/标准库/平台部分提供了部分这种稳定性, 但 boost 作者也需要一定程度的克制, 尤其是:

<boost/config.hpp> 永远不应改变, 不要改动此文件.

<boost/config/user.hpp> 默认被包含, 除非不得已, 不要向此文件添加额外代码. 如果确实要添加, 请记得同时更新 libs/config/tools/configure.in.

<boost/config/detail/suffix.hpp> 总是被包含, 因此修改此文件要小心, 因为它会影响所有人的依赖关系. 此文件应只包含 “样板” 配置代码, 通常只应在添加新宏时才改动.

<boost/config/detail/select_compiler_config.hpp>、<boost/config/detail/select_platform_config.hpp> 和 <boost/config/detail/select_stdlib_config.hpp> 默认被包含, 只应在添加对新编译器/标准库/平台的支持时才改动.

编译器/平台/标准库选择代码的设置方式是: 未知的平台会被忽略并假定为完全符合标准 — 这让未知平台即使不运行 configure 脚本, 也有 “按原样” 工作的合理机会.

在添加或修改各个迷你配置时, 应假定未来的、尚未发布的编译器版本具有当前版本的全部缺陷. 尽管这或许是不必要的悲观, 但它减少了这些文件的维护工作, 而且经验表明在这里悲观比乐观更为妥当!
