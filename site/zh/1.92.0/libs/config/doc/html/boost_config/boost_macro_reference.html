宽泛的 C++ 标准级别检查

它们适用于你只想检查 “该编译器是否符合 C++11” 之类问题的场合.

C++ 标准级别

宏 BOOST_CXX_VERSION 被设置为 C++ 标准版本 — 它与 __cplusplus 的值相同, 条件是 __cplusplus 被设置为合理的值; 否则为当前生效的 C++ 标准级别 (例如对 MSVC 而言, 它被设置为 _MSVC_LANG 的值).

可用的标准值有:

standard

value

2003

199711L

2011

201103L

2014

201402L

2017

201703L

2020

202002L

你应将此宏用作基本合理性检查, 确认编译器至少达到所要求的标准级别 — 仍可能存在缺陷、未实现的特性和/或缺失的头文件. 这些情况应使用单独的特性检查来检测.

严格标准级别检查

以下宏:

BOOST_NO_CXX03
BOOST_NO_CXX11
BOOST_NO_CXX14
BOOST_NO_CXX17

若该标准级别下任意一个缺陷宏被设置, 则这些宏就会被设置, .

注意, 因此这些是非常严格的检查, 结果是, 除最近的 gcc/clang 发布版本外, 许多编译器最终会定义全部这些宏: 即使 BOOST_CXX_VERSION 表明生效的是更新的标准.

严格标准检查头文件

以下头文件:

#include <boost/config/assert_cxx03.hpp>
#include <boost/config/assert_cxx11.hpp>
#include <boost/config/assert_cxx14.hpp>
#include <boost/config/assert_cxx17.hpp>

可用于断言该标准 (或任何更旧的标准) 下没有任何缺陷宏被设置.

这些头文件会提供比仅检查 BOOST_NO_CXX03 之类的做法更有用的错误消息, 因为它们会指出是哪个缺陷宏产生了错误.

如上所述, 这些是非常严格的检查, 因此除近期的 gcc/clang 发布版本外, 许多编译器都会产生 #error (在包含 任意 一个这些头文件时).

SD6 特性测试宏

注意, 上述检查均未考虑任何标准库 SD6 特性测试宏, 因为这样做将要求 #include 几乎整个标准库.

描述 C++03 缺陷的宏

以下宏全部描述 C++03 标准所要求的特性; 若以下某个宏被定义, 则它表示编译器在符合 2003 标准方面存在缺陷.

宏

小节

说明

BOOST_BCB_PARTIAL_SPECIALIZATION_BUG

编译器

编译器表现出某种部分特化缺陷 — 可能是 Borland C++ Builder 特有.

BOOST_FUNCTION_SCOPE_USING_DECLARATION_BREAKS_ADL

编译器

若当前作用域中存在对被查找符号的 using 声明, 则实参相关查找会失败. 例如, using boost::get_pointer; 会阻止 ADL 在 boost 内部嵌套的命名空间中找到 get_pointer 的重载 (但在其他地方不会). 可能是 Borland 特有.

BOOST_NO_ADL_BARRIER

编译器

在执行实参相关查找时, 编译器会定位并搜索它实际上不应搜索的命名空间.

BOOST_NO_ARGUMENT_DEPENDENT_LOOKUP

编译器

编译器未实现实参相关查找 (也称为 Koenig 查找); 见 std::3.4.2 [basic.koenig.lookup]

BOOST_NO_AUTO_PTR

标准库

若编译器/标准库提供了非标准或损坏的 std::auto_ptr.

BOOST_NO_COMPLETE_VALUE_INITIALIZATION

编译器

编译器未完整实现值初始化. 另见 Utility/Value Init 文档

BOOST_NO_CTYPE_FUNCTIONS

平台

平台没有为字符分类操作 <ctype.h> 和 <cctype> 提供函数, 只有宏.

BOOST_NO_CV_SPECIALIZATIONS

编译器

若针对 cv 限定类型的模板特化与针对 cv 未限定类型的特化相冲突.

BOOST_NO_CV_VOID_SPECIALIZATIONS

编译器

若针对 cv void 类型的模板特化与针对 void 的特化相冲突.

BOOST_NO_CWCHAR

平台

平台不提供 <wchar.h> 和 <cwchar>.

BOOST_NO_CWCTYPE

平台

平台不提供 <wctype.h> 和 <cwctype>.

BOOST_NO_FENV_H

平台, 标准库

C 标准库不提供 <fenv.h>. 应包含 <boost/detail/fenv.hpp> 而非 <fenv.h>, 以在确实提供 <fenv.h> 的平台上获得最大可移植性.

BOOST_NO_DEPENDENT_NESTED_DERIVATIONS

编译器

编译器无法编译具有依赖基类的嵌套类:

template<typename T>
struct foo : {
   template<typename U>
   struct bar : public U {};

};

BOOST_NO_DEPENDENT_TYPES_IN_TEMPLATE_VALUE_PARAMETERS

编译器

模板值形参不能具有依赖类型, 例如:

template<class T, typename T::type value>
class X { ... };

BOOST_NO_EXCEPTION_STD_NAMESPACE

标准库

标准库未把 <exception> 的部分或全部内容放入命名空间 std.

BOOST_NO_EXCEPTIONS

编译器

编译器不支持异常处理 (许多面向嵌入式平台的 C++ 编译器通常需要此设置). 注意, 并不要求 boost 库遵守此配置设置 — 实际上在某些情况下这样做可能是不可能的. 遵守此设置的库在发生严重错误时通常会中止 — 已事先警告你!

BOOST_NO_FUNCTION_TEMPLATE_ORDERING

编译器

编译器不执行函数模板排序, 或其函数模板排序不正确.

// #1
template<class T> void f(T);

// #2
template<class T,class U> void f(T(*)(U));

void bar(int);

f(&bar); // should choose #2.

BOOST_NO_INCLASS_MEMBER_INITIALIZATION

编译器

编译器违反 std::9.4.2/4.

BOOST_NO_INTRINSIC_WCHAR_T

编译器

C++ 实现不提供 wchar_t, 或者它实际上是另一个整数类型的同义词. 使用此符号来决定: 若其他整数类型已有特化, 是否适合针对 wchar_t 显式特化一个模板.

BOOST_NO_IOSFWD

标准库

标准库缺少 <iosfwd>.

BOOST_NO_IOSTREAM

标准库

标准库缺少 <iostream>、<istream> 或 <ostream>.

BOOST_NO_IS_ABSTRACT

编译器

C++ 编译器不支持将 SFINAE 用于抽象类型; 这由 Core Language DR337 涵盖, 但不属于当前标准. 幸运的是, 大多数支持 SFINAE 的编译器也支持该 DR. 另见 BOOST_NO_SFINAE 和 BOOST_NO_SFINAE_EXPR

BOOST_NO_LIMITS

标准库

C++ 实现不提供 <limits> 头文件. 绝不要在库代码中检查此符号; 应始终包含 <boost/limits.hpp>, 它保证提供 std::numeric_limits.

BOOST_NO_CXX11_NUMERIC_LIMITS

标准库

std::numeric_limits 的 C++11 新增内容不可用. static function numeric_limits<T>::lowest() 该数值类型可表示的最小有限值. static int const max_digits10 确保该类型的两个不同值具有不同十进制表示所需的十进制位数. template<> class numeric_limits<char16_t>;, 另见 BOOST_NO_CXX11_CHAR16_T; template<> class numeric_limits<char32_t>; 另见 BOOST_NO_CXX11_CHAR32_T. 取代 BOOST_NO_NUMERIC_LIMITS_LOWEST.

BOOST_NO_LIMITS_COMPILE_TIME_CONSTANTS

标准库

诸如 numeric_limits<T>::is_signed 之类的常量在编译期不可用.

BOOST_NO_LONG_LONG_NUMERIC_LIMITS

标准库

不存在针对 numeric_limits<long long> 和 numeric_limits<unsigned long long> 的特化. <boost/limits.hpp> 随后会添加这些特化作为标准库 “修复”, 但仅当编译器支持 long long 数据类型时.

BOOST_NO_MEMBER_FUNCTION_SPECIALIZATIONS

编译器

编译器不支持对模板类的单个成员函数进行特化.

BOOST_NO_MEMBER_TEMPLATE_KEYWORD

编译器

若编译器支持成员模板, 但在访问成员模板类时不支持 template 关键字.

BOOST_NO_MEMBER_TEMPLATE_FRIENDS

编译器

不支持 C++ 标准 14.5.3 中描述的成员模板友元语法 (template<class P> friend class frd;).

BOOST_NO_MEMBER_TEMPLATES

编译器

成员模板函数未受完全支持.

BOOST_NO_MS_INT64_NUMERIC_LIMITS

标准库

不存在针对 numeric_limits<__int64> 和 numeric_limits<unsigned __int64> 的特化. <boost/limits.hpp> 随后会添加这些特化作为标准库 “修复”, 但仅当编译器支持 __int64 数据类型时.

BOOST_NO_NESTED_FRIENDSHIP

编译器

编译器不允许嵌套类访问其外围类的私有成员. 可能是 Borland/CodeGear 特有.

BOOST_NO_OPERATORS_IN_NAMESPACE

编译器

编译器要求继承的运算符友元函数在命名空间作用域中定义, 然后用 using 引入 boost. 可能是 GCC 特有. 示例参见 <boost/operators.hpp>.

BOOST_NO_PARTIAL_SPECIALIZATION_IMPLICIT_DEFAULT_ARGS

编译器

编译器不能正确处理依赖于主模板默认实参的部分特化.

BOOST_NO_POINTER_TO_MEMBER_CONST

编译器

编译器不能正确处理指向 const 成员函数的指针, 导致无法在重载的函数模板中使用它们. 示例参见 <boost/functional.hpp>.

BOOST_NO_POINTER_TO_MEMBER_TEMPLATE_PARAMETERS

编译器

成员指针用作模板形参时无法工作.

BOOST_NO_PRIVATE_IN_AGGREGATE

编译器

编译器误读 8.5.1, 把包含私有或受保护成员函数的类当作非聚合类.

BOOST_NO_RESTRICT_REFERENCES

编译器

编译器特定的 restrict 关键字不能应用于引用.

BOOST_NO_RTTI

编译器

编译器可能具有 (也可能不具有) typeid 运算符, 但不支持对对象动态类型的 RTTI.

BOOST_NO_SFINAE

编译器

编译器不支持 “替换失败不是错误 (Substitution Failure Is Not An Error)” 元编程惯用法. 这是 C++11 之前的 SFINAE 轻量版本.

BOOST_NO_SFINAE_EXPR

编译器

编译器不支持将 SFINAE 用于任意表达式. 这是 C++11 之后的 SFINAE, 但不包括少数特定边角情况, 另见 BOOST_NO_CXX11_SFINAE_EXPR.

BOOST_NO_STD_ALLOCATOR

标准库

C++ 标准库未提供符合标准的 std::allocator.

BOOST_NO_STD_DISTANCE

标准库

平台没有符合标准的 std::distance 版本.

BOOST_NO_STD_ITERATOR

标准库

C++ 实现未能提供 std::iterator 类. 注意, 在 C++17 之后, 此宏被重新用于指示 std::iterator 已被移除或弃用.

BOOST_NO_STD_ITERATOR_TRAITS

标准库

编译器未提供符合标准的 std::iterator_traits 实现. 注意, 编译器可能仍具有非标准的实现.

BOOST_NO_STD_LOCALE

标准库

标准库缺少 std::locale.

BOOST_NO_STD_MESSAGES

标准库

标准库缺少符合标准的 std::messages 刻面.

BOOST_NO_STD_MIN_MAX

标准库

C++ 标准库不提供模板函数 min() 和 max(), 它们应位于 <algorithm> 中.

BOOST_NO_STD_OUTPUT_ITERATOR_ASSIGN

标准库

若标准库的输出迭代器不可赋值, 则定义.

BOOST_NO_STD_TYPEINFO

标准库

头文件 <typeinfo> 在全局命名空间而非命名空间 std 中声明 type_info.

BOOST_NO_STD_USE_FACET

标准库

标准库缺少符合标准的 std::use_facet.

BOOST_NO_STD_WSTREAMBUF

标准库

标准库对 std::basic_streambuf<wchar_t> 的实现要么缺失, 要么不完整, 要么有缺陷.

BOOST_NO_STD_WSTRING

标准库

标准库缺少 std::wstring.

BOOST_NO_STDC_NAMESPACE

编译器, 平台

C 库函数的 C++ 标准头文件 (<c...> 头文件) 的内容尚未放入命名空间 std. 这个测试很困难 — 一些库通过添加 using 声明把它们导入命名空间 std 来 “伪造” std C 函数, 遗憾的是它们不一定能捕获全部...

BOOST_NO_STRINGSTREAM

标准库

C++ 实现不提供 <sstream> 头文件.

BOOST_NO_SWPRINTF

平台

平台没有符合标准的 swprintf 版本.

BOOST_NO_TEMPLATE_PARTIAL_SPECIALIZATION

编译器

不支持类模板部分特化 (14.5.4 [temp.class.spec]).

BOOST_NO_TEMPLATED_IOSTREAMS

标准库

标准库不提供模板化的 iostream 类.

BOOST_NO_TEMPLATED_ITERATOR_CONSTRUCTORS

标准库

标准库未为其容器提供模板化的迭代器构造函数.

BOOST_NO_TEMPLATE_TEMPLATES

编译器

编译器不支持模板模板形参.

BOOST_NO_TYPEID

编译器

编译器完全不支持 typeid 运算符.

BOOST_NO_TYPENAME_WITH_CTOR

编译器

在创建依赖类型的临时对象时不能使用 typename 关键字.

BOOST_NO_UNREACHABLE_RETURN_DETECTION

编译器

若返回不可达, 则不应要求 return 语句, 然而一些编译器坚持要求它, 而另一些编译器在它确实存在时发出一堆警告.

BOOST_NO_USING_DECLARATION_OVERLOADS_FROM_TYPENAME_BASE

编译器

若派生类中存在同名函数, 编译器将不接受把用作基类的类型中的函数引入派生类的 using 声明.

BOOST_NO_USING_TEMPLATE

编译器

编译器不接受从另一个命名空间导入模板类或模板函数的 using 声明. 最初是 Borland 在与全局命名空间之间导入时的特有问题, 后来扩展到 MSVC6, 后者在导入模板类 (但不是函数) 时有特定问题.

BOOST_NO_VOID_RETURNS

编译器

编译器不允许 void 函数返回调用另一个 void 函数的结果.

void f() {}
void g() { return f(); }

BOOST_HAS_MS_INT64

BOOST_HAS_NANOSLEEP

平台

BOOST_HAS_NL_TYPES_H

平台

平台具有 <nl_types.h>.

BOOST_HAS_NRVO

编译器

指示编译器支持命名返回值优化 (NRVO). 用于为某些函数选择最高效的实现. 示例参见 <boost/operators.hpp>.

BOOST_HAS_PARTIAL_STD_ALLOCATOR

标准库

标准库有一个部分符合标准的 std::allocator 类, 但没有任何成员模板.

BOOST_HAS_PRAGMA_ONCE

编译器

编译器识别 #pragma once 指令, 该指令指示在预处理当前翻译单元时其所在的头文件只应被包含一次. 该 pragma 在某些编译器上可能改善大型项目的编译时间.

BOOST_HAS_PRAGMA_DETECT_MISMATCH

编译器

编译器识别 #pragma detect_mismatch("name", "value") 指令, 该指令指示: 若所提供的 "name" 的值不匹配, 链接阶段应以错误终止. 该 pragma 有助于防止 ODR 违规, 并确保不同模块以相同的标志编译.

BOOST_HAS_PTHREAD_DELAY_NP

平台

平台具有 POSIX API pthread_delay_np.

BOOST_HAS_PTHREAD_MUTEXATTR_SETTYPE

平台

平台具有 POSIX API pthread_mutexattr_settype.

BOOST_HAS_PTHREAD_YIELD

平台

平台具有 POSIX API pthread_yield.

BOOST_HAS_PTHREADS

平台

平台支持 POSIX 风格的线程.

BOOST_HAS_SCHED_YIELD

平台

平台具有 POSIX API sched_yield.

BOOST_HAS_SGI_TYPE_TRAITS

编译器, 标准库

编译器对 SGI 风格的类型特征有原生支持.

BOOST_HAS_STDINT_H

平台

平台具有 <stdint.h>

BOOST_HAS_SLIST

标准库

C++ 实现提供 (SGI) slist 类. 定义此宏时, BOOST_SLIST_HEADER 将包含访问 slist 所需头文件的名称, BOOST_STD_EXTENSION_NAMESPACE 将提供 slist 所在的命名空间.

BOOST_HAS_STLP_USE_FACET

标准库

标准库缺少符合标准的 std::use_facet, 但有一个变通的类版本可以完成这项工作. 这主要针对 STLport 标准库.

BOOST_HAS_TR1_ARRAY

标准库

库具有符合 TR1 的 <array> 版本. 仅在包含 Boost.TR1 的某个头文件之后才保证定义此宏. 此外, 此宏现已弃用, 由 BOOST_NO_CXX11_HDR_ARRAY 取代.

BOOST_HAS_TR1_COMPLEX_OVERLOADS

标准库

库具有 <complex> 的一个版本, 支持向复数算法传递标量.

BOOST_HAS_TR1_COMPLEX_INVERSE_TRIG

标准库

库具有 <complex> 的一个版本, 包含来自 TR1 的新的反三角函数.

BOOST_HAS_TR1_REFERENCE_WRAPPER

标准库

库在 <functional> 中具有符合 TR1 的引用包装器. 仅在包含 Boost.TR1 的某个头文件之后才保证定义此宏. 此外, 此宏现已弃用, 由 BOOST_NO_CXX11_HDR_FUNCTIONAL 取代.

BOOST_HAS_TR1_RESULT_OF

标准库

库在 <functional> 中具有符合 TR1 的 result_of 模板. 仅在包含 Boost.TR1 的某个头文件之后才保证定义此宏. 此外, 此宏现已弃用, 由 BOOST_NO_CXX11_HDR_FUNCTIONAL 取代.

BOOST_HAS_TR1_MEM_FN

标准库

库在 <functional> 中具有符合 TR1 的 mem_fn 函数模板. 仅在包含 Boost.TR1 的某个头文件之后才保证定义此宏. 此外, 此宏现已弃用, 由 BOOST_NO_CXX11_HDR_FUNCTIONAL 取代.

BOOST_HAS_TR1_BIND

允许在 C++03 编译器上使用 C++11 特性的宏

以下宏允许在尚未提供符合标准的 C++11 支持的编译器上使用 C++11 特性.

宏

说明

BOOST_ALIGNMENT(X), BOOST_NO_ALIGNMENT

一些编译器不支持 alignas 关键字, 但提供指定对齐的其他手段 (通常通过编译器特定的属性). 若编译器支持, 宏 BOOST_ALIGNMENT(X) 会展开为 alignas(X) 关键字, 否则展开为某种能实现指定对齐的编译器特定属性. 若不知道这样的编译器特定属性, 则 BOOST_ALIGNMENT(X) 会展开为空, 且会定义 BOOST_NO_ALIGNMENT. 与原生 alignas 不同, X 必须始终是编译期整数常量. 该宏可用于指定类型和数据的对齐:

struct BOOST_ALIGNMENT(16) my_data
{
    char c[16];
};
BOOST_ALIGNMENT(8) int arr[32];

BOOST_CONSTEXPR

一些编译器不支持使用 constexpr. 在这些编译器上, 此宏展开为空; 在其他编译器上, 展开为 constexpr. 例如, 在定义 constexpr 函数或构造函数时, 把

constexpr tuple();

其中:

BOOST_CONSTEXPR tuple();

BOOST_CONSTEXPR_OR_CONST

一些编译器不支持使用 constexpr. 在这些编译器上, 此宏展开为 const; 在其他编译器上, 展开为 constexpr. 例如, 在定义 constexpr 变量时, 把

static constexpr UIntType xor_mask = a;

其中:

static BOOST_CONSTEXPR_OR_CONST UIntType xor_mask = a;

BOOST_OVERRIDE

若 BOOST_NO_CXX11_OVERRIDE 未定义 (即符合 C++11 的编译器), 则展开为 override 关键字; 否则展开为空.

BOOST_STATIC_CONSTEXPR

这是 static BOOST_CONSTEXPR_OR_CONST 的快捷方式. 例如, 在定义 constexpr 变量时, 把

static constexpr UIntType xor_mask = a;

其中:

BOOST_STATIC_CONSTEXPR UIntType xor_mask = a;

BOOST_DEFAULTED_FUNCTION(fun, body)

此宏打算在类定义中使用, 用于声明函数 fun 的默认实现. 对于不支持 C++11 默认化函数的编译器, 该宏会展开为一个带有 body 实现的内联函数定义. 例如:

struct my_struct
{
    BOOST_DEFAULTED_FUNCTION(my_struct(), {})
};

等价于:

struct my_struct
{
    my_struct() = default;
};

或者:

struct my_struct
{
    my_struct() {}
};

BOOST_DELETED_FUNCTION(fun)

此宏打算在类定义中使用, 用于声明删除的函数 fun. 对于不支持 C++11 删除函数的编译器, 该宏会展开为一个没有定义的私有函数声明. 由于该宏可能改变访问模式, 建议在类定义的末尾使用它. 例如:

struct noncopyable
{
    BOOST_DELETED_FUNCTION(noncopyable(noncopyable const&))
    BOOST_DELETED_FUNCTION(noncopyable& operator= (noncopyable const&))
};

等价于:

struct noncopyable
{
    noncopyable(noncopyable const&) = delete;
    noncopyable& operator= (noncopyable const&) = delete;
};

或者:

struct noncopyable
{
private:
    noncopyable(noncopyable const&);
    noncopyable& operator= (noncopyable const&);
};


BOOST_NOEXCEPT
BOOST_NOEXCEPT_OR_NOTHROW
BOOST_NOEXCEPT_IF(Predicate)
BOOST_NOEXCEPT_EXPR(Expression)

若 BOOST_NO_CXX11_NOEXCEPT 已定义 (即符合 C++03 的编译器), 这些宏定义为:

#define BOOST_NOEXCEPT
#define BOOST_NOEXCEPT_OR_NOTHROW throw()
#define BOOST_NOEXCEPT_IF(Predicate)
#define BOOST_NOEXCEPT_EXPR(Expression) false

若 BOOST_NO_CXX11_NOEXCEPT 未定义 (即符合 C++11 的编译器), 它们定义为:

#define BOOST_NOEXCEPT noexcept
#define BOOST_NOEXCEPT_OR_NOTHROW noexcept
#define BOOST_NOEXCEPT_IF(Predicate) noexcept((Predicate))
#define BOOST_NOEXCEPT_EXPR(Expression) noexcept((Expression))

BOOST_FINAL

若 BOOST_NO_CXX11_FINAL 未定义 (即符合 C++11 的编译器), 则展开为 final 关键字; 否则展开为空.

BOOST_MSVC_ENABLE_2012_NOV_CTP

对于 Microsoft Visual C++ 2012, 启用 2012 年 11 月社区技术预览版 (CTP) 提供的 C++11 特性. 这些特性不会被自动启用, 因为 CTP 是不受支持的 alpha 代码, 不建议用于生产环境. 此宏必须在包含任何 Boost 头文件之前定义, 并且必须对程序中的所有翻译单元定义, 包括 Boost 库构建. 一旦官方 Microsoft 发布版本支持这些 CTP 特性, 此宏将不再有任何效果.

BOOST_NULLPTR

若 BOOST_NO_CXX11_NULLPTR 未定义 (即符合 C++11 的编译器), 则展开为 nullptr; 否则展开为 0.

Boost 辅助宏

以下宏要么是简单的辅助工具, 要么是为编译器/标准库缺陷提供变通办法的宏.

宏

说明

BOOST_WORKAROUND

此宏用于需要编译器特定变通办法、而其他 Boost.Config 宏均未描述该情况的场合. 要使用此宏, 必须先

#include <boost/config/workaround.hpp>

然后用法为:

#if BOOST_WORKAROUND(MACRONAME, CONDITION)
   // workaround code goes here...
#else
   // Standard conforming code goes here...
#endif

其中 MACRONAME 是一个宏, 通常描述要测试的版本号; CONDITION 是一个比较运算符后跟一个值. 例如, 对 Intel C++ 10.1 及更早版本, BOOST_WORKAROUND(BOOST_INTEL, <= 1010) 的求值结果为 1.

若当前所有编译器版本都表现出该问题, 但预计该问题日后会被修复, 则该宏也可与 BOOST_TESTED_AT 一起使用.

例如, BOOST_WORKAROUND(__BORLANDC__, BOOST_TESTED_AT(0x590)) 通常求值为 1, 对 __BORLANDC__ 的所有值皆然 除非 定义了宏 BOOST_DETECT_OUTDATED_WORKAROUNDS, 此时求值为 (__BORLANDC__ <= 0x590).

注释: 此宏文档的最终来源位于 boost/config/workaround.hpp.

BOOST_PREVENT_MACRO_SUBSTITUTION

有时你会有与 C 宏同名的函数名, 例如 “min” 和 “max” 成员函数, 这时可以用如下方式阻止该函数被宏展开:

someclass.min BOOST_PREVENT_MACRO_SUBSTITUTION(arg1, arg2);

以下方式在大多数 (但并非所有) 语境中同样有效:

(someclass.max)(arg1, arg2);

BOOST_DEDUCED_TYPENAME

一些编译器不支持在推导语境中对依赖类型使用 typename. 在这些编译器上, 此宏展开为空; 在其他编译器上, 展开为 typename. 例如, 把 template <class T> void f(T, typename T::type); 替换为: template <class T> void f(T, BOOST_DEDUCED_TYPENAME T::type);

BOOST_HASH_MAP_HEADER

为获得 SGI hash_map 类而应包含的头文件. 仅当 BOOST_HAS_HASH 已定义时此宏才可用.

BOOST_HASH_SET_HEADER

为获得 SGI hash_set 类而应包含的头文件. 仅当 BOOST_HAS_HASH 已定义时此宏才可用.

BOOST_SLIST_HEADER

为获得 SGI slist 类而应包含的头文件. 仅当 BOOST_HAS_SLIST 已定义时此宏才可用.

BOOST_STD_EXTENSION_NAMESPACE

用于标准库扩展的命名空间 (哈希表类等).

BOOST_STATIC_CONSTANT(Type, assignment)

在不允许类内初始化静态整型常量成员的编译器上, 若希望这些常量在编译期可用, 必须用枚举作为变通办法. 此宏提供了一种声明这类常量的便捷方式. 例如, 不要这样写:

struct foo{
   static const int value = 2;
};

而应这样写:

struct foo{
   BOOST_STATIC_CONSTANT(int, value = 2);
};

BOOST_UNREACHABLE_RETURN(result)

通常求值为空, 但若编译器要求 return (即使它永远不可达), 则求值为 return x;

BOOST_FALLTHROUGH

BOOST_FALLTHROUGH 宏可用于标注 switch 标签之间的隐式贯穿 (fall-through):

switch (x) {
case 40:
case 41:
   if (truth_is_out_there) {
      ++x;
      BOOST_FALLTHROUGH;  // Use instead of/along with annotations in
      // comments.
   } else {
     return x;
   }
   case 42:
      ...

如上面的示例所示, BOOST_FALLTHROUGH 宏后面应跟一个分号. 它的设计旨在模仿诸如 'break;' 之类的控制流语句, 因此可以放在大多数 'break;' 可以出现的位置, 但前提是它与下一个 switch 标签之间的执行路径上没有语句.

在 C++11 模式下用 Clang >3.2 编译时, BOOST_FALLTHROUGH 宏会展开为 [[clang::fallthrough]] 属性, 在执行 switch 标签贯穿诊断 ('-Wimplicit-fallthrough') 时会分析该属性. 详情参见 clang 语言扩展文档.

在不支持的编译器上使用时, BOOST_FALLTHROUGH 宏对诊断没有影响.

无论何种情况, 此宏对代码的运行期行为和性能都没有影响.

BOOST_EXPLICIT_TEMPLATE_TYPE(t)

BOOST_EXPLICIT_TEMPLATE_NON_TYPE(t,v)

BOOST_APPEND_EXPLICIT_TEMPLATE_TYPE(t)

BOOST_APPEND_EXPLICIT_TEMPLATE_NON_TYPE(t,v)

如果某些模板形参没有出现在函数形参列表中, 一些编译器会悄悄地 “折叠” 不同的函数模板实例化. 例如:

#include <iostream>
#include <ostream>
#include <typeinfo>

template <int n>
void f() { std::cout << n << ' '; }

template <typename T>
void g() { std::cout << typeid(T).name() << ' '; }

int main() {
  f<1>();
  f<2>();

  g<int>();
  g<double>();
}

在 VC++ 6 上会错误地输出 2 2 double double. 这些宏用于函数形参列表中, 可在不影响调用语法的情况下修复此问题. 例如, 在上面的情况中应写作:

template <int n>
void f(BOOST_EXPLICIT_TEMPLATE_NON_TYPE(int, n)) { ... }

template <typename T>
void g(BOOST_EXPLICIT_TEMPLATE_TYPE(T)) { ... }

注意, 它们可能会 (对受影响的编译器) 声明一个哑的默认化形参, 因此它们

a) 应始终在形参列表的末尾调用

b) 若你的函数模板被多次声明, 则不能使用.

此外, 为了添加所需的逗号分隔符, 当宏调用出现在普通形参声明之后或同组另一个宏的调用之后时, 必须使用 APPEND_* 版本.

BOOST_USE_FACET(Type, loc)

当标准库没有符合标准的 std::use_facet 时, 有多种可用的变通办法, 但它们因库而异. 此宏提供了一种访问 locale 刻面的一致方式. 例如, 把 std::use_facet<Type>(loc); 替换为: BOOST_USE_FACET(Type, loc); 注意, 不要把 std:: 前缀添加到 BOOST_USE_FACET 的前面.

BOOST_HAS_FACET(Type, loc)

当标准库没有符合标准的 std::has_facet 时, 有多种可用的变通办法, 但它们因库而异. 此宏提供了一种检查 locale 刻面的一致方式. 例如, 把 std::has_facet<Type>(loc); 替换为: BOOST_HAS_FACET(Type, loc); 注意, 不要把 std:: 前缀添加到 BOOST_HAS_FACET 的前面.

BOOST_NESTED_TEMPLATE

一些编译器支持成员模板, 即使它们不能使用 A::template member<U> 语法. 作为变通办法, 把 typedef typename A::template rebind<U> binder; 替换为: typedef typename A::BOOST_NESTED_TEMPLATE rebind<U> binder;

BOOST_STRINGIZE(X)

把实参 X 转换为字符串, 转换发生在对 X 执行宏替换之后.

BOOST_JOIN(X,Y)

这段宏魔法把两个实参连接在一起, 即使其中一个实参本身是宏 (见 C++ 标准 16.3.1). 它通常与 __LINE__ 之类的预定义宏结合使用来创建修饰名.

BOOST_RESTRICT

此宏可替代 C99 restrict 关键字的编译器特定变体, 用于通知编译器: 在被限定指针变量的生存期内, 只有它及其派生的值会被用于访问其所引用的对象. 这限制了指针别名的影响, 并帮助优化器生成更好的代码. 但是, 若违反此条件, 可能发生未定义行为.

用法示例:

void perform_computation( float* BOOST_RESTRICT in, float* BOOST_RESTRICT out )
{
  *out = *in * 0.5f;
}

BOOST_FORCEINLINE

此宏可替代 inline 关键字, 用于指示编译器该函数应始终内联. 过度使用此宏可能导致显著的代码膨胀, 而恰当使用则可在某些情况下提升性能, 例如通过生成式编程技术构建的计算密集型代码.

用法示例:

template<class T>
BOOST_FORCEINLINE T& f(T& t)
{
    return t;
}

注意, 使用此宏在某些编译器上可能导致晦涩难懂的错误消息. 考虑在包含 Boost.Config 头文件之前把它定义为 inline, 以便更容易地调试错误.

BOOST_NOINLINE

此宏可替代 inline 关键字, 用于指示编译器该函数绝不应被内联. 通常应使用此宏标记不太可能被调用的函数, 例如错误处理例程.

用法示例:

BOOST_NOINLINE void handle_error(const char* descr)
{
    // ...
}

BOOST_NORETURN

此宏可用在函数声明或定义之前, 指示编译器该函数不会正常返回 (即不通过 return 语句返回, 若函数返回类型为 void, 也不通过离开函数作用域返回). 该宏可用于标记总是抛出异常或终止应用程序的函数. 支持此标注的编译器可利用该信息专门组织围绕此函数调用的代码, 并抑制外层函数中关于缺少 return 语句的警告.

用法示例:

BOOST_NORETURN void on_error_occurred(const char* descr)
{
    throw std::runtime_error(descr);
}

若编译器不支持此标注, 则 BOOST_NORETURN 被定义为空, 并会定义一个附加宏 BOOST_NO_NORETURN.

BOOST_LIKELY(X)

BOOST_UNLIKELY(X)

这些宏向编译器传达条件表达式 X 可能或不太可能产生肯定结果的信息. 该表达式的结果应为布尔值. 宏的结果是一个等价于 X 结果的整数或布尔值.

这些宏打算用于分支语句中. 它们提供的额外提示可被编译器用来更有效地安排各分支的编译代码.

用法示例:

if (BOOST_UNLIKELY(ptr == NULL))
  handle_error("ptr is NULL");

BOOST_ATTRIBUTE_UNUSED

可用时展开为 __attribute__((unused)) — 可用于禁用与未使用的类型或变量相关的编译器警告.

BOOST_ATTRIBUTE_NODISCARD

可用时展开为 [[nodiscard]] — 可用于在类型或变量未被使用时产生警告.

BOOST_ATTRIBUTE_NO_UNIQUE_ADDRESS

可用时展开为 [[no_unique_address]] — 可用于指示非静态数据成员无需拥有唯一地址 (例如空类).

BOOST_MAY_ALIAS, BOOST_NO_MAY_ALIAS

BOOST_MAY_ALIAS 展开为一个类型属性, 可用于标记可能与其他类型形成别名的类型. 指向这类被标记类型的指针或引用可用于访问其他类型的对象. 若编译器支持此特性, 则不定义 BOOST_NO_MAY_ALIAS. 否则 BOOST_MAY_ALIAS 展开为空, 并定义 BOOST_NO_MAY_ALIAS.

用法示例:

struct BOOST_MAY_ALIAS aliasing_struct;
typedef unsigned int BOOST_MAY_ALIAS aliasing_uint;

BOOST_DEPRECATED(M)

展开为一个符号属性, 当该符号在代码中被使用时会产生警告. 警告中可包含消息 M, 它必须是字符串字面量. 该属性可应用于类型、函数或对象, 通常用于把 API 的某些部分标记为已弃用并建议替代.

示例:

BOOST_DEPRECATED("Use bar() instead.")
void foo();

template< typename T >
class BOOST_DEPRECATED("Use std::unique_ptr instead.") auto_ptr
{
};

BOOST_DEPRECATED("Use std::numeric_limits<int>::max() instead.")
const int max_int = 0x7fffffff;

BOOST_DEPRECATED 发出的警告可通过定义 BOOST_ALLOW_DEPRECATED_SYMBOLS 或 BOOST_ALLOW_DEPRECATED 宏来抑制.

BOOST_PRAGMA_MESSAGE(M)

定义于头文件 <boost/config/pragma_message.hpp>, 此宏展开为等价于 #pragma message(M) 的形式. M 必须是字符串字面量.

示例: BOOST_PRAGMA_MESSAGE("This header is deprecated.")

BOOST_PRAGMA_MESSAGE 发出的消息可通过定义宏 BOOST_DISABLE_PRAGMA_MESSAGE 来抑制.

BOOST_HEADER_DEPRECATED(A)

定义于头文件 <boost/config/header_deprecated.hpp> 此宏发出消息 “This header is deprecated. Use A instead.” (经由 BOOST_PRAGMA_MESSAGE) A 必须是字符串字面量.

示例: BOOST_HEADER_DEPRECATED("<boost/config/workaround.hpp>")

BOOST_HEADER_DEPRECATED 发出的消息可通过定义 BOOST_ALLOW_DEPRECATED_HEADERS 或 BOOST_ALLOW_DEPRECATED 宏来抑制.

面向带独立源代码的库的宏

控制共享库符号可见性的宏
ABI 修正
自动库选择

以下宏和辅助头文件对那些库包含独立源代码的作者有用, 旨在解决以下几个问题:

  • 控制共享库符号可见性
  • 修正需编译库的 ABI
  • 根据编译器设置选择要链接的需编译库

参见 Boost 库独立源代码作者指南

控制共享库符号可见性的宏

一些编译器支持 C++ 扩展, 用于控制哪些符号将从共享库 (如类 Unix 系统上的动态共享对象 (DSO) 或 Windows 上的动态链接库 (DLL)) 中导出.

Microsoft VC++ 编译器早就这样为此提供了 __declspec(dllexport) 和 __declspec(dllimport) 扩展, 面向 Windows 平台的几乎所有其他编译器也是如此.

现代版本的 GNU GCC 编译器提供 __attribute__((visibility("default"))) 扩展来指示某个符号应被导出. 所有其他符号可通过使用 -fvisibility-hidden 或 -fvisibility-ms-compat 编译器开关来隐藏.

Boost 提供了若干宏, 使符号可见性的管理更容易, 且在编译器和操作系统之间可移植.

宏

说明

BOOST_SYMBOL_EXPORT

定义一种 C++ 语言扩展的语法, 该扩展指示某个符号将从共享库导出. 若编译器没有这样的扩展, 则该宏被定义为无替换文本.

BOOST_SYMBOL_IMPORT

定义一种 C++ 语言扩展的语法, 该扩展指示某个符号将从共享库导入. 若编译器没有这样的扩展, 则该宏被定义为无替换文本.

BOOST_SYMBOL_VISIBLE

定义一种 C++ 语言扩展的语法, 该扩展指示某个符号是全局可见的. 若编译器没有这样的扩展, 则该宏被定义为无替换文本. 对于并非以其他方式导出、但会被 RTTI 使用的类, 需要此宏. 例如跨共享库边界抛出异常或用于 dynamic_cast 的对象的类. 例如, 一个仅头文件的异常类可能如下所示:

class BOOST_SYMBOL_VISIBLE my_exception : public std::runtime_error { ... };

若无 BOOST_SYMBOL_VISIBLE, 将无法捕获由以 -fvisibility=hidden 选项编译的 GCC 共享库抛出的 my_exception.

BOOST_HAS_DECLSPEC

编译器具有 C++ 扩展 __declspec(dllexport) 和 __declspec(dllimport) 来控制共享库符号的导出/导入. 已弃用. 由于现已提供 BOOST_SYMBOL_EXPORT 和 BOOST_SYMBOL_IMPORT, 此宏不再必要. 保留它是为了支持遗留代码.

BOOST_DISABLE_EXPLICIT_SYMBOL_VISIBILITY

禁用 BOOST_SYMBOL_EXPORT、BOOST_SYMBOL_IMPORT 和 BOOST_SYMBOL_VISIBLE 宏的效果, 以恢复编译器的默认行为. 注意, 若正在动态链接 Boost 库, 或者正在构建一个在其公共 API 中暴露 Boost 类型的共享库, 则绝不应使用此选项. 不过, 在静态链接 Boost 时建议使用它, 以防止 Boost 符号从二进制文件中泄漏: 例如因为你正在为某个自身可能使用 Boost 的软件构建插件, 这可能造成 ODR 冲突.

典型用法:

boost/foo/config.hpp 

...
#if defined(BOOST_ALL_DYN_LINK) || defined(BOOST_FOO_DYN_LINK)
# if defined(BOOST_FOO_SOURCE)
#   define BOOST_FOO_DECL BOOST_SYMBOL_EXPORT
# else
#   define BOOST_FOO_DECL BOOST_SYMBOL_IMPORT
# endif
#else
# define BOOST_FOO_DECL
#endif
...

boost/foo/foo.hpp 

#include <boost/foo/config.hpp>
...
class BOOST_FOO_DECL bar { ... };
...
void BOOST_FOO_DECL f();
...

boost/libs/foo/src/foo.cpp 

#define BOOST_FOO_SOURCE
#include <boost/foo/foo.hpp>
...
void BOOST_FOO_DECL f()
{
  ...
}
...

ABI 修正

在链接预编译库时, 至关重要的是: 编译器构建该库时使用的 ABI 必须精确匹配使用该库的代码所用的 ABI. 这里的 ABI 指诸如所用的结构体打包方式、所用的名称修饰方案, 或某些类型的大小 (例如枚举类型). 这与线程支持或运行库变体之类的事项是分开的, 后者必须由构建变体来处理. 具体来说, 有一个编译器 (Borland 的) 拥有如此之多会对 ABI 产生细微改变的编译器选项, 以致至少在理论上有 3200 种组合, 这还没有考虑运行库变体. 幸运的是, 这些变体可以由 #pragma 来管理, 它告诉编译器你的库中声明的类型应使用什么 ABI. 为了避免把 #pragma 撒遍 boost 头文件, 有一些前缀和后缀头文件可以完成这项工作. 典型用法如下:

my_library.hpp 

#ifndef MY_INCLUDE_GUARD
#define MY_INCLUDE_GUARD

// all includes go here:
#include <boost/config.hpp>
#include <whatever>

#include <boost/config/abi_prefix.hpp> // must be the last #include

namespace boost {

// your code goes here

}

#include <boost/config/abi_suffix.hpp> // pops abi_prefix.hpp pragmas

#endif // include guard

my_library.cpp 

...
// nothing special need be done in the implementation file
...

用户可以通过定义 BOOST_DISABLE_ABI_HEADERS 来禁用此机制, 或者如果愿意, 可以定义 BOOST_ABI_PREFIX 和/或 BOOST_ABI_SUFFIX 来指向他们自己的前缀/后缀头文件.

自动库选择

用户必须链接到与其应用将要使用的相同运行库所构建的库版本 — 若非如此, 该库将与他们自己的代码不二进制兼容 — 并且他们的应用很可能遭遇运行期崩溃. 这类问题可能极其耗时且难以调试, 常常令用户和作者同样沮丧 (当有 6-8 个库可供选择时, 仅选出要链接的正确库就不像看起来那么容易, 而且一些用户似乎浑然不觉还存在多种不同的运行库可供选择).

为了解决这个问题, 一些编译器允许源代码包含 #pragma 来指示链接器应链接哪个库, 用户只需包含所需的头文件, 把需编译库放入其库搜索路径, 编译器和链接器会完成其余工作. Boost.config 通过头文件 <boost/config/auto_link.hpp> 支持这一点; 在包含此头文件之前, 需要定义以下一个或多个宏:

BOOST_LIB_NAME

必需: 包含库基名 (basename) 的标识符, 例如 'boost_regex'.

BOOST_DYN_LINK

可选: 设置后链接 DLL 而非静态库.

BOOST_LIB_DIAGNOSTIC

可选: 设置后头文件会打印出所选库的名称 (便于调试).

BOOST_AUTO_LINK_NOMANGLE

可选: 设置后指定应链接 BOOST_LIB_NAME.lib, 而非修饰名版本.

BOOST_AUTO_LINK_TAGGED

可选: 指定我们链接以 --layout=tagged 选项构建的库. 这本质上与默认的名称修饰版本相同, 但不含编译器名称和版本, 也不含 Boost 版本, 只有构建选项.

BOOST_AUTO_LINK_SYSTEM

可选: 指定我们链接以 --layout=system 选项构建的库. 这本质上与非名称修饰版本相同, 但带有区分静态库和 DLL 构建的前缀

若编译器支持此机制, 则会指示它链接适当命名的库. 用于修饰库名称的实际算法记录在 <boost/config/auto_link.hpp> 内部, 并且必须与通过 bjam 的安装规则创建库时所用的算法一致.

my_library.hpp 

...
//
// Don't include auto-linking code if the user has disabled it by
// defining BOOST_ALL_NO_LIB, or BOOST_MY_LIBRARY_NO_LIB, or if this 
// is one of our own source files (signified by BOOST_MY_LIBRARY_SOURCE):
//
#if !defined(BOOST_ALL_NO_LIB) && !defined(BOOST_MY_LIBRARY_NO_LIB) && !defined(BOOST_MY_LIBRARY_SOURCE)
#  define BOOST_LIB_NAME boost_my_library
#  ifdef BOOST_MY_LIBRARY_DYN_LINK
#     define BOOST_DYN_LINK
#  endif
#  include <boost/config/auto_link.hpp>
#endif
...

my_library.cpp 

// define BOOST_MY_LIBRARY_SOURCE so that the header knows that the
// library is being built (possibly exporting rather than importing code)
//
#define BOOST_MY_LIBRARY_SOURCE

#include <boost/my_library/my_library.hpp>
...
