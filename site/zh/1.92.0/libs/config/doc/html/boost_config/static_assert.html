头文件 <boost/static_assert.hpp> 提供两个宏:

BOOST_STATIC_ASSERT(x)
BOOST_STATIC_ASSERT_MSG(x, msg)

若整型常量表达式 x 不为真, 两者都会生成编译期错误消息. 换言之, 它们是 assert 宏的编译期等价物; 这有时被称为 “编译期断言 (compile-time-assertion)”, 但在本文档中将称为 “静态断言 (static assertion)”. 注意, 若条件为 true, 这些宏既不生成代码也不生成数据 — 并且这些宏还可在命名空间、类或函数作用域中使用. 在模板中使用时, 静态断言会在模板实例化时求值; 这对校验模板形参特别有用.

若 C++0x 的 static_assert 特性可用, 两个宏都会使用它. 对 BOOST_STATIC_ASSERT(x) 而言, 错误消息将是 x 的字符串化版本. 对 BOOST_STATIC_ASSERT_MSG(x, msg) 而言, 错误消息将是 msg 字符串.

若 C++0x 的 static_assert 特性不可用, BOOST_STATIC_ASSERT_MSG(x, msg) 将被视为 BOOST_STATIC_ASSERT(x).

接下来的内容假定 C++0x 的 static_assert 特性不可用.

BOOST_STATIC_ASSERT 的目标之一是生成可读的错误消息. 这些消息会立即告诉用户: 库正以不受支持的方式被使用. 虽然错误消息显然因编译器而异, 但你应会看到类似下面的内容:

Illegal use of STATIC_ASSERTION_FAILURE<false>

其意图至少是引人注意!

你可以在任何能放置声明的位置使用 BOOST_STATIC_ASSERT, 即类、函数或命名空间作用域, 以下示例说明了这一点:

在命名空间作用域使用

若存在某个必须始终为真的要求, 该宏可在命名空间作用域中使用; 这通常意味着某种平台特定要求. 假设我们要求 int 至少是 32 位整数类型, 且 wchar_t 是无符号类型. 我们可以按如下方式在编译期验证这一点:

#include <climits>
#include <cwchar>
#include <limits>
#include <boost/static_assert.hpp>

namespace my_conditions {

   BOOST_STATIC_ASSERT(std::numeric_limits<int>::digits >= 32);
   BOOST_STATIC_ASSERT(WCHAR_MIN >= 0);

} // namespace my_conditions

这里使用命名空间 my_conditions 需要一些说明. 宏 BOOST_STATIC_ASSERT 的原理是生成一个 typedef 声明, 而 typedef 必须有名字, 因此该宏通过把一个占位名与 __LINE__ 的值修饰组合, 自动生成一个名字. 当 BOOST_STATIC_ASSERT 在类或函数作用域中使用时, 每次 BOOST_STATIC_ASSERT 的使用都保证产生该作用域内唯一的名字 (前提是每行只使用一次该宏). 然而, 当在头文件中的命名空间作用域使用时, 该命名空间可能延续到多个头文件, 每个头文件可能有自己的静态断言, 且位于 “相同” 的行上, 从而产生重复声明. 理论上编译器应默默忽略重复的 typedef 声明, 但许多编译器并不这样做 (即便这样做, 它们也有权在这种情况下发出警告). 为避免潜在问题, 如果你在头文件中、于命名空间作用域使用 BOOST_STATIC_ASSERT, 请把它们放入该头文件独有的命名空间中.

在函数作用域使用

当需要检查模板实参时, 该宏通常在模板函数内的函数作用域中使用. 想象我们有一个基于迭代器的算法, 它要求随机访问迭代器. 若该算法用不满足要求的迭代器实例化, 最终会产生错误, 但它可能深嵌在若干层模板之中, 使用户难以确定问题出在哪里. 一种做法是在模板的顶层添加静态断言, 这样若条件不满足, 产生的错误会让用户相当容易看出模板被误用了.

#include <iterator>
#include <boost/static_assert.hpp>
#include <boost/type_traits.hpp>

template <class RandomAccessIterator >
RandomAccessIterator foo(RandomAccessIterator from,
                         RandomAccessIterator to)
{
   // this template can only be used with
   // random access iterators...
   typedef typename std::iterator_traits<
         RandomAccessIterator >::iterator_category cat;
   BOOST_STATIC_ASSERT(
      (boost::is_convertible<
         cat,
         const std::random_access_iterator_tag&>::value));
   //
   // detail goes here...
   return from;
}

这里需要两条脚注: 断言外面额外的一对括号, 是为了防止 is_convertible 模板内部的逗号被预处理器解释为宏实参分隔符; is_convertible 的目标类型是引用类型, 因为当转换经由用户定义构造函数进行时, 一些编译器在使用 is_convertible 时有问题 (无论如何, 迭代器标签类不保证可拷贝构造).

在类作用域使用

该宏通常在作为模板的类内部使用. 假设我们有一个模板类, 它要求模板实参是精度至少 16 位的无符号整数类型, 我们可以用类似下面这样来做到:

#include <limits>
#include <boost/static_assert.hpp>

template <class UnsignedInt>
class myclass
{
private:
   BOOST_STATIC_ASSERT_MSG(std::numeric_limits<UnsignedInt>::is_specialized, "myclass can only be specialized for types with numeric_limits support.");
   BOOST_STATIC_ASSERT_MSG(std::numeric_limits<UnsignedInt>::digits >= 16, "Template argument UnsignedInt must have at least 16 bits precision.")
   BOOST_STATIC_ASSERT_MSG(std::numeric_limits<UnsignedInt>::is_integer, "Template argument UnsignedInt must be an integer.");
   BOOST_STATIC_ASSERT_MSG(!std::numeric_limits<UnsignedInt>::is_signed, "Template argument UnsignedInt must not be signed.");
public:
   /* details here */
};

在模板中使用

通常, 在类模板或函数模板内部使用的静态断言, 要到使用它的模板被实例化时才会实例化. 不过, 有一个需要提防的潜在问题: 如果静态断言不依赖于一个或多个模板形参, 则编译器被允许在第一次看到它时就对静态断言求值, 而不管该模板是否曾被实例化, 例如:

template <class T>
struct must_not_be_instantiated
{
   BOOST_STATIC_ASSERT(false);
};

在一些编译器 (例如 Intel 8.1 或 gcc 3.4) 上, 无论该模板是否曾被实例化, 这都会产生编译器错误. 这类情况下的变通办法是强制断言依赖于一个模板形参:

template <class T>
struct must_not_be_instantiated
{
   // this will be triggered if this type is instantiated
   BOOST_STATIC_ASSERT(sizeof(T) == 0);
};

How it works

BOOST_STATIC_ASSERT 的工作原理如下. 有一个类 STATIC_ASSERTION_FAILURE, 其定义如下:

namespace boost{

template <bool> struct STATIC_ASSERTION_FAILURE;

template <> struct STATIC_ASSERTION_FAILURE<true>{};

}

关键特性在于: 由未定义表达式 sizeof(STATIC_ASSERTION_FAILURE<0>) 触发的错误消息, 在各种编译器上往往是一致的. BOOST_STATIC_ASSERT 其余的机制只是把 sizeof 表达式喂给 typedef 的一种手段. 这里使用宏有些难看; 然而 boost 成员已花费相当多精力试图发明一种避免宏的静态断言, 都徒劳无功. 总的结论是: 静态断言能在命名空间、函数和类作用域工作的好处, 胜过宏的丑陋.
