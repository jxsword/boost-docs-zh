构建期配置

有时你会希望根据编译器支持的特性来控制某个构建目标是否被构建. 例如, 假设你有一个测试文件 “test_constexpr_128.cpp”, 它需要三个关键特性才能构建:

  • constexpr 关键字, 由 BOOST_NO_CXX11_CONSTEXPR 检测.
  • 用户定义字面量, 由 BOOST_NO_CXX11_USER_DEFINED_LITERALS 检测.
  • __int128 数据类型, 由 BOOST_HAS_INT128 检测.

显然, 如果编译器不支持这些特性, 那么尝试构建测试程序根本没有意义. 主要优点如下:

  • 更快的编译时间 — 构建配置使用轻量级测试, 其结果还会被缓存.
  • 构建输出中更少的噪音 — 既然明知该文件无论如何都无法编译, 就没有理由面对成页的模板实例化回溯.
  • 在线测试结果中更少的噪音 — 在在线测试矩阵中, 该测试将显示为空白, 而非失败.
  • 对于构建整个 Boost 的最终用户来说体验更好: 无法为当前目标编译器构建的库被直接跳过, 而不是生成成页的错误输出.

回到我们的示例, 该测试用例可能在它的 Jamfile 中通过 “run” 规则执行:

run test_constexpr_128.cpp ;

现在我们需要让该目标以必要的特性为条件. 为此, 先在 Jamfile 的开头导入所需的规则:

import path-to-config-lib/checks/config : requires ;

假设该测试用例位于通常的目录中:

libs/yourlib/test

那么 import 规则实际上是:

import ../../config/checks/config : requires ;

然后向该目标的 requirements 区段添加一条 “requires” 规则调用:

run test_constexpr_128.cpp
   : : : #requirements:
   [ requires cxx11_constexpr cxx11_user_defined_literals int128 ] ;

注意, 可以向 requires 规则添加多个实参, 它们始终与 Boost.Config 宏名相同, 只是小写, 并去掉了 boost_no_ 或 boost_has_ 前缀. 也可以使用任何 C++ 标准特性测试宏名, 去掉前导下划线 (详见下文).

构建上面的示例时, 你会在构建过程开始处看到配置的结果, 例如 C++11 模式下的 GCC 给出:

- Boost.Config Feature Check: int128 : yes
- Boost.Config Feature Check: cxx11_constexpr : yes
- Boost.Config Feature Check: cxx11_user_defined_literals : yes

若你想让构建以某个 C++ 标准特性宏为条件, 也可以指定它们, 只需去掉名称的前导下划线. 例如:

[ requires cpp_constexpr ]

要求 C++11 风格的常量表达式. 若想指定来自特定标准的宏, 则附加一个下划线, 后跟该标准的 (两位数) 年份, 例如:

[ requires cpp_constexpr_17 ]

对应 C++17 的 constexpr. 若不指定标准, 则会得到引入该宏的第一个版本. 此外, 只有该宏的每次版本升级才有特定于标准的规则, 因此:

[ requires cpp_if_constexpr_17 ]

这样没问题, 因为该宏在 C++17 中引入, 且与不带版本号的名称相同, 但是:

[ requires cpp_if_constexpr_20 ]

会导致构建错误, 因为 __cpp_if_constexpr 没有 C++20 版本升级.

这个便捷特性就这些. 若任何时候你不确定可以传给 “requires” 规则的特性测试名, 可以在 libs/config/checks/Jamfiles.v2 中搜索你所关心的 Boost.Config 宏, 特性检查的名称会紧跟其后.

最后, 此特性围绕 Boost.Build 内置规则 check-target-builds 构建, 该规则可用于执行更泛化的构建期特性测试. 本库中提供的这些检查是一种便捷的简写, 无需你自己编写测试用例.
