许多传统 “教科书式” 配置头文件实现 (所有配置选项都在单个 “单体” 头文件中) 的问题在于, 它们违反了某些基本的软件工程原则, 其效果是使 boost 更加脆弱、更难维护、更难安全使用. 这些原则的描述见以下文章.

问题所在

设想你在多个平台上并行开发的情形. 再设想添加一个新平台, 或者更改某个现有平台的平台定义. 会发生什么? 所有代码 — 字面意义上的所有代码 — 都会重新编译. 添加一个与先前已有平台毫无关系的新平台, 竟意味着所有现有平台上的所有代码都需要重新编译, 这难道不相当荒谬吗?

实际上, 这在彼此毫无关系的平台之间强加了物理依赖. 从本质上说, 配置头文件所采用的传统方案不符合开闭原则 (Open-Closed Principle):

“模块应对扩展开放, 但对修改关闭.”

扩展传统配置头文件意味着修改现有代码.

此外, 考虑一下平台检测代码的复杂性和脆弱性. 如果一个简单的改动破坏了某个次要平台上的检测怎么办? 如果有人有意或无意 (作为对其他某个问题的变通) 定义了检测代码所使用的某些平台相关宏怎么办? 传统配置头文件是整个库中最不稳定的头文件之一, 而 Boost 中更稳定的部分却要依赖它. 这违反了稳定依赖原则 (Stable Dependencies Principle):

“朝着稳定的方向依赖.”

即使只对某个次要平台上的传统配置头文件做了一个小改动, 如果遵循健全的软件工程实践, 每个平台上几乎所有的东西都应被测试.

另一个重要问题是, 并非总是能够向 <boost/config.hpp> 提交更改. 一些 boost 用户目前正使用受严格保密协议约束的工具和库在平台上工作. 在这种情况下, 无法向传统单体配置头文件提交更改, 因此必须提供某种让用户插入自己的配置代码的方法.

解决方案

boost 配置头文件采取的方法是把配置拆分为三个正交部分: 编译器、标准库和平台. 每个编译器/标准库/平台都有自己的迷你配置头文件, 因此 (例如) 对某个编译器配置的更改不会影响其他编译器. 此外, 还可以采取措施省略编译器/标准库/平台检测代码 (使添加新平台支持不会破坏依赖关系), 或者完全冻结配置; 从而提供几乎完全的防依赖变更保护.
