使用默认 boost 配置

Boost 对最常用的编译器和平台已经预先配置好; 你应能 “按原样” 使用 boost. 由于编译器与标准库是分开配置的, 即使你把编译器的标准库替换为第三方标准库 (如 STLport), 默认配置也应能工作.

推荐的使用 boost 的方法是 “按原样” 使用而不尝试重新配置. 不过, 如果你愿意, 也可以运行 configure 脚本, 并且提供了回归测试, 让你可以用自己特定的编译器设置来测试当前的 boost 配置.

Boost 库用户可以通过访问我们的 Github 并提交支持请求, 来申请对其他编译器或平台的支持.

<boost/config.hpp> 头文件

Boost 库实现通过如下方式访问配置宏:

#include <boost/config.hpp>

虽然不要求 Boost 库用户直接包含该文件或使用那些配置宏, 但这样做也是可以接受的. 这些配置宏就其目的、用法和限制都有文档说明, 因此 Boost 库代码和用户代码都可使用.

Boost 信息性宏和 辅助宏既为 Boost 用户而设计, 也为我们自己的内部使用而设计. 但要注意, 特性测试宏和 缺陷测试宏是为 Boost 库内部使用而设计的, 而非用户代码, 因此它们可能随时变化 (不过不会对它们做无谓的更改). 配置宏更改导致的 Boost 库问题会被 Boost 回归测试捕获, 因此 Boost 库会更新以适应这些更改. 相比之下, Boost 库用户代码可能在毫无警告的情况下受到宏更改的不利影响. 及时了解用户代码所用宏的变化的最佳方式是关注 Boost 开发者邮件列表上的讨论.

使用 configure 脚本

重要

此 configure 脚本只为配合特定编译器使用而设置 Boost 头文件. 它对 Boost.Build 或库的构建方式没有影响.

如果你知道 boost 对你的特定环境配置有误, 并且你在类 UNIX 平台上, 那么可以尝试通过运行 boost configure 脚本来改善. 在 shell 命令提示符下, 你需要 cd 到 <boost-root>/libs/config/ 并输入:

sh ./configure

随着脚本逐步执行回归测试, 你会看到被检查项的列表. 注意, 只有当你的编译器名为 g++、c++ 或 CC 时, configure 脚本才真正自动检测它. 如果你使用其他编译器, 则需要设置以下一个或多个环境变量:

变量

说明

CXX

编译器的名称, 例如 c++.

CXXFLAGS

要使用的编译器标志, 例如 -O2.

LDFLAGS

要使用的链接器标志, 例如 -L/mypath.

LIBS

要链接入的库, 例如 -lpthread.

例如, 要用 HP aCC 运行 configure 脚本, 你可能会使用类似这样的命令:

export CXX="aCC"
export CXXFLAGS="-Aa -DAportable -D__HPACC_THREAD_SAFE_RB_TREE \
   -DRWSTD_MULTI_THREAD -DRW_MULTI_THREAD -D_REENTRANT -D_THREAD_SAFE"
export LDFLAGS="-DAportable"
export LIBS="-lpthread"
sh ./configure

无论你如何运行 configure 脚本, 它完成后你都会找到一个新头文件 -user.hpp- 位于 <boost-root>/libs/config/ 目录中. 注意, configure 默认不会把这个头文件安装到你的 boost include 路径中. 此头文件包含 configure 脚本生成的所有选项, 外加一个头文件区段, 其中包含来自默认版本 <boost/config/user.hpp> (位于 <boost-root>/boost/config/ 下) 的用户可设置选项. 使用此头文件有两种方式:

  • 选项 1: 把该头文件复制到 <boost-root>/boost/config/, 使其替换 boost 提供的默认 user.hpp. 此选项只允许一套 configure 生成的设置; boost 开发者应避免此选项, 因为它有可能把被 configure 修改过的 <boost/config/user.hpp> 意外提交到 svn 仓库 (没人会为此感谢你!).
  • 选项 2: 给该头文件取一个更好记的名字, 并把它放在方便的地方; 然后定义宏 BOOST_USER_CONFIG 指向它. 例如, 创建一个新的子目录 <boost-root>/boost/config/ user/, 并把头文件复制到那里; 例如作为 multithread-gcc-config.hpp. 然后, 编译时添加命令行选项: -DBOOST_USER_CONFIG="<boost/config/user/multithread-gcc-config.hpp>", boost 就会使用新的配置头文件. 此选项允许你生成多个配置头文件, 并把它们与 boost 源码分开保存 — 这样源码的更新就不会干扰你的配置.

用户可设置的选项

有一些配置选项代表用户的选择, 而非编译器缺陷或平台特定选项. 它们列于 <boost/config/user.hpp> 以及 configure 生成的 user.hpp 头文件的开头. 你可以在命令行上定义它们, 或者通过编辑 <boost/config/user.hpp> 来定义, 它们列于下表:

宏

说明

BOOST_USER_CONFIG

定义时, 它应指向要在任何 boost 配置文件之前包含的用户配置文件的名称. 未定义时, 默认为 <boost/config/user.hpp>.

BOOST_COMPILER_CONFIG

定义时, 它应指向要使用的编译器配置文件的名称. 定义它会跳过编译器选择逻辑, 并消除对包含该逻辑的头文件的依赖. 例如, 如果你使用 gcc, 那么可以把 BOOST_COMPILER_CONFIG 定义为 <boost/config/compiler/gcc.hpp>.

BOOST_STDLIB_CONFIG

定义时, 它应指向要使用的标准库配置文件的名称. 定义它会跳过标准库选择逻辑, 并消除对包含该逻辑的头文件的依赖. 例如, 如果你使用 STLport, 那么可以把 BOOST_STDLIB_CONFIG 定义为 <boost/config/stdlib/stlport.hpp>.

BOOST_PLATFORM_CONFIG

定义时, 它应指向要使用的平台配置文件的名称. 定义它会跳过平台选择逻辑, 并消除对包含该逻辑的头文件的依赖. 例如, 如果你在 linux 上编译, 那么可以把 BOOST_PLATFORM_CONFIG 定义为 <boost/config/platform/linux.hpp>.

BOOST_NO_COMPILER_CONFIG

定义后, 不会选择或包含任何编译器配置文件; 当编译器完全符合标准时, 或当用户头文件 (见 BOOST_USER_CONFIG) 已添加所有必需选项时定义它, 例如由 autoconf 生成的 configure 脚本添加.

BOOST_NO_STDLIB_CONFIG

定义后, 不会选择或包含任何标准库配置文件; 当标准库完全符合标准时, 或当用户头文件 (见 BOOST_USER_CONFIG) 已添加所有必需选项时定义它, 例如由 autoconf 生成的 configure 脚本添加.

BOOST_NO_PLATFORM_CONFIG

定义后, 不会选择或包含任何平台配置文件; 当平台完全符合标准 (且没有有用的额外特性) 时, 或当用户头文件 (见 BOOST_USER_CONFIG) 已添加所有必需选项时定义它, 例如由 autoconf 生成的 configure 脚本添加.

BOOST_NO_CONFIG

等价于同时定义 BOOST_NO_COMPILER_CONFIG、BOOST_NO_STDLIB_CONFIG 和 BOOST_NO_PLATFORM_CONFIG.

BOOST_STRICT_CONFIG

对于比最后已知版本更新的编译器版本, 正常行为是假定它们具有与最后已知版本相同的所有缺陷. 通过设置此定义, 比最后已知版本更新的编译器版本将被假定完全符合标准. 这对 boost 开发者或测试者, 以及想用 boost 测试 beta 编译器版本的人可能最为有用.

BOOST_ASSERT_CONFIG

设置此标志后, 如果 config 发现任何未知的东西, 它将以 #error 停止而不是继续. Boost 回归测试者应设置此定义, 任何想快速检查其平台上是否支持 boost 的人也应如此.

BOOST_DISABLE_THREADS

定义后禁用线程支持, 即使编译器在其当前翻译模式下支持多线程.

BOOST_DISABLE_WIN32

定义后禁用 Win32 特定 API 的使用, 即使它们可用. 还会产生设置 BOOST_DISABLE_THREADS 的效果, 除非设置了 BOOST_HAS_PTHREADS. 当 config 系统检测到编译器处于 “严格模式” 时, 可能自动设置此选项.

BOOST_DISABLE_ABI_HEADERS

阻止 boost 头文件包含任何通常控制结构体打包和对齐等事项的前缀/后缀头文件.

BOOST_ABI_PREFIX

用于替代 boost.config 通常所选择的任何前缀头文件; 任何替代品都应按需设置结构体打包和对齐选项.

BOOST_ABI_SUFFIX

用于替代 boost.config 通常所选择的任何后缀头文件; 任何替代品都应撤销前缀头文件的效果.

BOOST_ALL_DYN_LINK

在 Microsoft Windows 上强制所有带独立源码的库以 DLL 而非静态库方式链接 (此宏用于开启 __declspec(dllimport) 修饰符, 使编译器知道应在 DLL 中而非静态库中寻找哪些符号). 注意, 可能有一些库只能静态链接 (例如 Boost.Test), 另一些只能动态链接 (例如 Boost.Thread), 在这些情况下此宏没有效果.

BOOST_WHATEVER_DYN_LINK

在 Microsoft Windows 上强制库 “whatever” 以 DLL 而非静态库方式链接: 把宏名中的 WHATEVER 部分替换为你想动态链接的库的名称, 例如使用 BOOST_DATE_TIME_DYN_LINK 或 BOOST_REGEX_DYN_LINK 等 (此宏用于开启 __declspec(dllimport) 修饰符, 使编译器知道应在 DLL 中而非静态库中寻找哪些符号). 注意, 可能有一些库只能静态链接 (例如 Boost.Test), 另一些只能动态链接 (例如 Boost.Thread), 在这些情况下此宏不受支持.

BOOST_ALL_NO_LIB

告诉 config 系统不要自动选择要链接的库. 通常, 若编译器支持 #pragma lib, 那么只需包含该库的某个头文件, 正确的库构建变体就会被自动选择并链接. 此宏会关闭该特性.

BOOST_WHATEVER_NO_LIB

告诉 config 系统不要为库 “whatever” 自动选择要链接的库, 把宏名中的 WHATEVER 替换为该库的名称; 例如 BOOST_DATE_TIME_NO_LIB 或 BOOST_REGEX_NO_LIB. 通常, 若编译器支持 #pragma lib, 那么只需包含该库的某个头文件, 正确的库构建变体就会被自动选择并链接. 此宏会关闭该特性.

BOOST_LIB_DIAGNOSTIC

使自动链接代码输出诊断消息, 指示被选中进行链接的库的名称.

BOOST_LIB_BUILDID

如果你在构建 Boost 时使用了 --buildid 选项, 那么请把此宏设置为你传给 bjam 的相同值. 例如, 如果你用 bjam address-model=64 --buildid=amd64 构建, 那么编译你的代码时使用 -DBOOST_LIB_BUILDID=amd64, 以确保链接时选择正确的库.

BOOST_LIB_TOOLSET

覆盖被链接库名称中工具集部分的名称; 注意, 若定义, 此宏必须定义为带引号的字符串字面量, 例如 “abc”.

高级配置用法

通过在编译器命令行上设置各种宏, 或者通过编辑 <boost/config/user.hpp>, boost 配置设置可以通过多种方式进行优化.

Boost 的配置结构使得用户配置最先被包含 (默认为 <boost/config/user.hpp>, 条件是 BOOST_USER_CONFIG 未定义). 这会设置任何用户定义的策略, 并让用户配置有机会影响接下来的处理.

接下来包含编译器、标准库和平台配置文件. 它们通过宏包含 (BOOST_COMPILER_CONFIG 等, 参见用户可设置宏), 若对应宏未定义, 则会包含一个单独的头文件来检测正在使用的编译器/标准库/平台, 以便设置这些宏. 若设置了对应的 BOOST_NO_XXX 宏, 可以让 config 完全忽略这些头文件 (例如 BOOST_NO_COMPILER_CONFIG 用于禁用包含任何编译器配置文件 — 参见用户可设置宏).

最后, boost 配置头文件包含 <boost/config/detail/suffix.hpp>; 此头文件包含任何样板配置代码 — 例如某个 boost 宏被设置意味着另一个宏也必须设置的情况.

以下用法示例只代表其中几种可能:

示例 1: 创建我们自己的冻结配置

假设我们正用 Visual C++ 6 和 STLport 4.0 构建 boost. 再假设我们不打算在近期更新编译器或标准库. 为了避免更新 boost 时破坏依赖关系, 我们可能想 “冻结” 我们的配置头文件, 使得只有当 boost 代码本身发生变化时才需要重新构建项目, 而不是因为 boost config 为更新版本的 Visual C++ 或 STLport 做了更新. 我们先弄清正在使用的配置文件: 编译器为 <boost/config/compiler/visualc.hpp>, 标准库为 <boost/config/stdlib/stlport.hpp>, 平台为 <boost/config/platform/win32.hpp>. 接下来创建我们自己的私有配置目录: boost/config/mysetup/, 并把配置文件复制进去. 最后, 打开 <boost/config/user.hpp> 并编辑以下定义:

#define BOOST_COMPILER_CONFIG "boost/config/mysetup/visualc.hpp"
#define BOOST_STDLIB_CONFIG "boost/config/mysetup/stlport.hpp"
#define BOOST_USER_CONFIG "boost/config/mysetup/win32.hpp"

现在使用 boost 时, 其配置头文件会直接使用我们的 “冻结” 版本并忽略默认版本, 更新 boost 时你将不受任何配置变化的影响. 如果你想要修改某些 boost 配置文件, 该技术也很有用; 例如你正在使用一个 boost 尚不支持的 beta 编译器版本时.

示例 2: 跳过你不需要的文件

假设你正在用一个完全符合标准的编译器使用 boost; 你不关心编译器旧版本可能有过缺陷的事实, 因为你知道当前版本不需要设置任何配置宏. 在这种情况下, 你可以定义 BOOST_NO_COMPILER_CONFIG — 无论是在命令行上, 还是在 <boost/config/user.hpp> 中 — 从而完全跳过编译器配置头文件 (实际上你会跳过两个头文件: 一个用于确定编译器是什么, 另一个为它配置 boost). 这有两个后果: 其一是需要编译的代码更少, 其二是你消除了对两个 boost 头文件的依赖.

示例 3: 使用 configure 脚本冻结 boost 配置

如果你在类 unix 平台上工作, 那么可以使用 configure 脚本基于你当前的编译器设置生成 “冻结” 配置 — 详情参见使用 configure 脚本.

测试 boost 配置

boost 配置库在 <boost-root>/boost/config/ test/ 子目录下提供全套回归测试程序:

File

说明

config_info.cpp

打印出你的编译器/标准库/平台设置的详细描述, 以及你当前的 boost 配置. 此程序提供的信息对设置 boost 配置文件很有用. 如果你报告 boost 对你的编译器/库/平台配置有误, 请在报告所需更改时附上此程序的输出.

config_test.cpp

一个包含大部分单独测试用例的单体测试程序. 它可快速检查 boost 是否针对你的编译器/库/平台正确配置.

limits_test.cpp

测试你的标准库的 std::numeric_limits 实现 (若 BOOST_NO_LIMITS 已定义, 则测试 boost 提供的替代实现). 此测试文件在大多数 numeric_limits 版本上都会失败, 主要由于一些编译器处理 NAN 和无穷大的方式.

no_*pass.cpp

单独的编译器缺陷测试文件. 每个都应能编译; 若某个不能编译, 则需要定义对应的 BOOST_NO_XXX 宏 — 具体细节见各测试文件.

no_*fail.cpp

单独的编译器缺陷测试文件. 每个都不应能编译; 若某个能编译, 则对应的 BOOST_NO_XXX 宏在不必定义时被定义了 — 具体细节见各测试文件.

has_*pass.cpp

单独的特性测试文件. 若其中某个不能编译, 则对应的 BOOST_HAS_XXX 宏在不应定义时被定义了 — 具体细节见各测试文件.

has_*fail.cpp

单独的特性测试文件. 若其中某个能编译, 则可以安全地定义对应的 BOOST_HAS_XXX 宏 — 具体细节见各测试文件.

虽然你可以把配置回归测试作为单独的测试文件来运行, 但它们的数量相当多, 因此有几个快捷方式可以帮到你:

或者, 你也可以像这样运行 configure 脚本:

./configure --enable-test

在这种情况下, 脚本会测试当前配置, 而不是从头创建一个新配置.

如果你要为新平台/库/编译器报告这些测试的结果, 请附上完整的编译器输出日志、config_info.cpp 的输出, 以及通过/失败测试结果.
