引言

Boost.Bloom 提供类模板 boost::bloom::filter, 可以配置为实现经典布隆过滤器以及文献中讨论的各种变体, 例如块过滤器、多块过滤器等.

#include <boost/bloom.hpp>
#include <cassert>
#include <iostream>
#include <string>

int main()
{
  // Bloom filter of strings with 5 bits set per insertion
  using filter = boost::bloom::filter<std::string, 5>;

  // create filter with a capacity of 1'000'000 bits
  filter f(1'000'000);

  // insert elements (they can't be erased, Bloom filters are insert-only)
  f.insert("hello");
  f.insert("Boost");

  // elements inserted are always correctly checked as such
  assert(f.may_contain("hello") == true);

  // elements not inserted may incorrectly be identified as such with a
  // false positive rate (FPR) which is a function of the array capacity,
  // the number of bits set per element and generally how the boost::bloom::filter
  // was specified
  if(f.may_contain("bye")) { // likely false
    std::cout << "false positive\n";
  }
  else {
    std::cout << "everything worked as expected\n";
  }
}

所支持的过滤器变体在编译期作为 boost::bloom::filter 实例化定义的一部分指定. Boost.Bloom 的实现以性能为重心; 可以利用 AVX2、Neon 和 SSE2 等 SIMD 技术来加速操作.

入门

关于如何安装整个 Boost 项目或仅安装 Boost.Bloom 及其依赖, 请查阅网站 章节.

Boost.Bloom 是一个仅头文件库, 因此无需额外的构建阶段. 要求 C++11 或更高版本. 本库已验证可在 GCC 4.8、Clang 3.9 和 Visual Studio 2015 (及更新版本) 下工作. 你可以通过编译上面展示的 示例程序 来检查你的环境是否设置正确.

如果你对布隆过滤器总体上并不熟悉, 请参见 入门; 否则, 你可以直接跳到 教程.

布隆过滤器入门

布隆过滤器 (以其发明者 Burton Howard Bloom 命名) 是一种概率型数据结构: 已插入元素可以被 100% 准确地查找, 而查找一个未插入元素则可能以某个概率失败, 该概率称为过滤器的 误报率 (false positive rate) 或 FPR. 这里的权衡是: 在可接受的低 FPR 下, 布隆过滤器占用的空间远小于传统的非概率容器 (通常每元素约 8-20 位). 过滤器的 容量 (以位计的大小) 越大, 所得 FPR 越低.

一般而言, 当精确检索代价高昂和/或无法在主内存中完成时, 布隆过滤器可用于防止/缓解对大型数据集的查询.

示例: 加速对数据库的不成功请求

布隆过滤器及类似数据结构的一个重要应用是: 当昂贵的磁盘/网络访问无法检索到给定信息时, 避免这类访问. 例如, 假设我们在为访问时间 10 ms 的数据库开发前端, 且知道 50% 的请求不会成功 (记录不存在). 插入一个查找时间 200 ns、FPR 0.5% 的布隆过滤器, 将把系统的平均响应时间从 10 ms 降低到

(10 + 0.0002) × 50.25% + 0.0002 × 49.75% ≅ 5.03 ms,

也就是说, 整体加速约 1.99 倍. 若数据库有 10 亿条记录, 一个每元素约 8 位的内存过滤器将占用 0.93 GB, 这完全可以实现.

图 1. 用布隆过滤器改善数据库的否定访问时间.

相关应用已被描述于 web 缓存、词典压缩、网络路由和基因组学等领域. Broder and Mitzenmacher 对用例做了相当广泛的综述, 侧重点在网络.

实现

经典布隆过滤器的实现由一个 m 位数组组成, 初始全部为零. 插入元素 x 归结为伪随机地选取 k 个位置 (借助 k 个独立的哈希函数) 并把它们置一.

图 2. 在使用 k = 6 个不同哈希函数的经典布隆过滤器中插入. 插入 x 归结为把位置 10、14、43、58、1 和 39 处的位按 h1(x)、…​、h6(x) 所示置一.

为检查元素 y 是否在过滤器中, 我们遵循相同的过程, 看所选位是否全部为一. 在示例图中, 有两个位未置一, 这确定地表明 y 未被插入过滤器.

图 3. 经典布隆过滤器中的查找. 值 y 不在过滤器中, 因为位置 20 和 61 的位未被置一.

当被检查的位碰巧因其他不相关的插入而全部为一时, 就发生误报. 误报的概率随向过滤器添加更多元素而增大; 而对于给定的已插入元素数 n , 容量更大 (位数组更大) 的过滤器 FPR 更低. 每次操作所置位的数量 k 也影响 FPR, 但方式更为复杂: 当数组稀疏时, 较大的 k 值会改善 (降低) FPR, 因为命中未置位的机会更多; 然而, 若 k 非常高, 随着新元素插入, 数组中被置一的位会越来越多, 最终会达到一个点: 输给 k 较小、被置位比例较小的过滤器. 对于给定的 n 与 m 值, 最优的 k 是 \(\lfloor k_\\text{opt}}\rfloor\) 或 \(\lceil k_\\text{opt}}\rceil\) , 其中

\(k_\\text{opt}}=\\displaystyle\frac{m\\cdot\ln2}{n},)\)

对应的最小 FPR 接近 \(1/2^{k_\\text{opt}}} \\approx 0.6185^{m/n}\) . 更多细节参见关于 FPR 估计 的附录.

图 4. 两个 m = 105 位过滤器的 FPR 与已插入元素数的关系. 对较小的 n 值, k = 6 (红) 的 FPR 优于 k = 2 (蓝), 但随 n 增长, 其劣化最终更多. 虚线显示对每个 n 值选取最优 k 值所能达到的最小 FPR.

经典过滤器的变体

块过滤器

对布隆过滤器的操作涉及访问内存中 k 个不同位置, 对于大数组, 这导致 k 次 CPU 缓存未命中并影响操作性能. 经典方法的一种称为 块过滤器 的变体试图通过把全部置位/检查集中在从整个数组中伪随机选出的小块 (b 位) 中来最小化缓存未命中. 若块足够小, 它能放入一个 CPU 缓存行, 从而大幅减少缓存未命中次数.

图 5. 块过滤器. 依据 h0(x) 选出 b 位的块, 此后所有置位都被约束在该块内.

缺点是, 对于相同的 n、m 与 k 值, 所得 FPR 比经典过滤器更差. 直观地说, 块过滤器降低了数组中位分布的均匀性, 这最终会损害其概率性能.

图 6. 经典过滤器与块过滤器 (同为 k = 4, m = 105 位) 的 FPR (对数尺度) 与已插入元素数的关系.

这一思想的进一步变体是让操作选取 k 个块, 每块置 k' 个位. 同样, 它的 FPR 会比每次操作置 k·k' 位的经典过滤器更差, 但优于普通的 k·k' 块过滤器.

图 7. 多重插入的块过滤器. 选出 k = 2 个块, 并在每个块中置 k' = 3 个位.

多块过滤器

多块过滤器 把块过滤器的思路更进一步: 置位/检查在 b 大小的连续块序列上进行, 使每个块恰好占用一位. 这仍然保持良好的缓存局部性, 但由于被置一的位更分散于整个数组, 相对于块过滤器改善了 FPR.

图 8. 多块过滤器. 依据 h0(x) 选出 k' = 4 个连续块的范围, 并在每个块中置一位.

多块过滤器也可以与多重插入组合. 一般而言, 在每次操作位数相同且 n 与 m 值相等的情况下, 经典布隆过滤器的 FPR 最好 (最低), 其次是多块过滤器, 然后是块过滤器. 执行速度则大致相反. 考虑带多重插入的块/多块过滤器时, 可用配置的数量会迅速增长, 你需要做一些实验, 才能在 (FPR, 容量, 速度) 权衡空间中找到你偏好的位置.

教程

一个 boost::bloom::filter 可以被视为一个划分为若干 子数组 的位数组: 插入时基于哈希函数伪随机地选取子数组; 每个子数组被交给一个 子过滤器 , 由它按照某种关联策略标记其中的若干位.

注意, 尽管 boost::bloom::filter 模仿容器的接口并提供诸如 insert 之类的操作, 它实际上 并非 容器: 例如, 插入并不把元素真正存储到数据结构中, 而只是基于元素的哈希值在内部数组中设置一些位.

过滤器定义

template<
  typename T, std::size_t K,
  typename Subfilter = block<unsigned char, 1>, std::size_t Stride = 0,
  typename Hash = boost::hash<T>,
  typename Allocator = std::allocator<unsigned char>
>
class filter;

  • T: 插入元素的类型.

  • K: 每次插入所标记的子数组数量.

  • Subfilter: 所使用的子过滤器类型.

  • Stride: 相邻子数组起始位置之间以字节计的距离.

  • Hash: 用于 T 的哈希函数.

  • Allocator: 用于 unsigned char 的分配器.

Subfilter

子过滤器定义在位数组中被选中的子数组内设置或检查位的局部策略. 它决定每次操作修改多少位、这些位在内存中如何排布, 以及如何访问内存. 提供了以下子过滤器:

在上表中, Block 可以是无符号整数类型 (例如 unsigned char 、 uint32_t 、 uint64_t ), 或由 2N 个无符号整数组成的数组 (例如 uint64_t[8] ). 一般而言, Block 越宽, 所得 FPR 越好 (越低), 但缓存局部性变差, 性能可能因此受损.

注意, 一个 boost::bloom::filter<T, K, subfilter<…​, K'>> 设置/检查的总位数为 K * K' . 默认配置 boost::bloom::filter<T, K> = boost::bloom::filter<T, K, block<unsigned char, 1>> (对应于 经典布隆过滤器 ) 在所有每次操作位数相同的过滤器中拥有最好 (最低) 的 FPR, 但也最慢: 每设置/检查一位都要访问一个新的子数组. 有关 FPR 与性能之间的不同权衡, 请查阅 基准测试一节 .

选定子过滤器之后, 若预先知道将要插入的元素数量, 可以把参数 K' 调整到其最优值 (最小 FPR), 如 专门章节 所述; 否则, 只要所得 FPR 处于可接受水平, 较低的 K' 值通常更快, 也更受青睐.

Stride

如前所述, Subfilter 定义了 Block 所使用的子数组 (对于 block<Block, K'> 是 Block[K'] , 对于 multiblock<Block, K'> 是 boost::bloom::filter ): 然后访问底层位数组的连续片段并将其当作这些子数组. Stride 参数控制相邻子数组起始位置之间以字节计的距离.

使用默认值 0 时, 步幅会被自动设为子数组的大小, 因此它们互不重叠. 若把 Stride 设为小于该大小的值, 相邻子数组会相互叠加: Stride 值越小, 重叠程度越大, 当 Stride 为 1 字节时重叠最大.

图 9. Stride 的两种不同配置: (a) 非重叠子数组, (b) 重叠子数组.
每个子数组与相同颜色的步幅相关联.

事实上, 相对于不重叠的情形, 重叠会改善 (降低) 所得 FPR, 代价是子数组在内存中可能不对齐, 这可能对性能产生负面影响.

Hash

与其他要求每次操作使用多个哈希函数的布隆过滤器实现不同, boost::bloom::filter 只使用一个. 默认使用 Boost.ContainerHash . 若你需要为自有类型扩展 , 请查阅该库的 专门章节boost::hash .

当所提供的哈希函数质量足够时, 会原样使用它; 否则, 会对哈希值应用一个位混合后处理, 以改善其统计性质, 使所得 FPR 逼近其理论极限. 哈希函数是否高质量 (更准确地说, 是否具有所谓的 雪崩 (avalanching) 性质) 通过 boost::hash_is_avalanching 特征判定.

容量

过滤器内部数组的大小在构造时指定:

using filter = boost::bloom::filter<std::string, 8>;
filter f(1'000'000); // array of 1'000'000 bits
std::cout << f.capacity(); // >= 1'000'000

注意 boost::bloom::filter 的默认构造函数指定容量为零, 这通常没什么用 —— 分配的数组为空.

我们可以不直接指定数组的容量, 而是让库根据我们计划插入的元素数量和期望的 FPR 来推算它:

// we'll insert 100'000 elements and want a FPR ~ 1%
filter f(100'000, 0.01);

// this is equivalent
filter f2(filter::capacity_for(100'000, 0.01));

当指定的 FPR 非常小时要小心, 因为所得容量可能大到无法放入内存:

// resulting capacity ~ 1.4E12, out of memory std::bad_alloc is thrown
filter f3(100'000, 1E-50);

过滤器一旦构造, 其数组就固定了 (例如, 不会随元素插入而动态增长). 改变它的唯一方式是从另一个过滤器赋值/交换, 或使用 reset :

f.reset(2'000'000); // change to 2'000'000 bits and clears the filter
f.reset(100'000, 0.005); // equivalent to reset(filter::capacity_for(100'000, 0.005));
f.reset(); // null array (capacity == 0)

插入与查找

插入的完成方式与传统容器大致相同:

f.insert("hello");
f.insert(data.begin(), data.end());

当然, 在此语境下 "插入" 并不把元素实际存储进过滤器, 而是依据这些元素的哈希值设置内部数组中的位. 查找如下进行:

bool b1 = f.may_contain("hello"); // b1 is true since we actually inserted "hello"
bool b2 = f.may_contain("bye"); // b2 is most likely false

顾名思义, 即使元素先前未被插入, may_contain 也可能返回 true , 也就是说它可能产生误报 —— 这正是概率型数据结构的本质. fpr_for 提供对误报率的估计:

// we have inserted 100 elements so far, what's our FPR?
std::cout<< filter::fpr_for(100, f.capacity());

注意, 在示例中我们从外部提供了数字 100: boost::bloom::filter 不跟踪已插入元素的数量 —— 换言之, 它没有 size 操作.

一旦插入, 就无法从过滤器中移除特定元素. 只能把过滤器整体清空:

f.clear(); // sets all the bits in the array to zero

批量操作

一般来说, 以下代码:

f.insert(data.begin(), data.end());

比下面这个更快:

for(const auto& x: data) f.insert(x);

这是因为前者使用一些内部精简技术, 以大小为 bulk_insert_size 的块处理范围, 从而缩短执行时间. 类似地, may_contain 可以按如下方式以批量模式执行:

f.may_contain(
  input.begin(), input.end(), // range of elements to do lookup on
  [](value_type& x, bool b) { // called for each of the elements with their lookup result
    if(b) std::cout << x << "likely in the filter";
	else  std::cout << x << "not in the filter";
  });

批量 may_contain 以 bulk_may_contain_size 元素的块处理范围.

批量模式可以把性能提高 2 倍或更多, 但这非常依赖于过滤器配置、所用编译器和环境, 在某些情况下反而导致净性能损失. 一般而言, 数组越大加速越明显. 更多信息请查阅专门的 基准测试一节 与 相关仓库.

过滤器组合

boost::bloom::filter 可以通过对它们数组的位执行 OR 逻辑运算来组合:

filter f2 = ...;
...
f |= f2; // f and f2 must have exactly the same capacity

结果等价于一个 "包含" f 与 f2 元素集合并集的过滤器. 另一方面, AND 组合得到一个持有元素 交集 的过滤器:

filter f3 = ...;
...
f &= f3; // f and f3 must have exactly the same capacity

对于 AND 组合, 要注意所得 FPR 一般会比从头只插入公共元素构造的过滤器更差 (更高) —— 这种情况下不要相信 fpr_for .

直接访问数组

位数组的内容可以通过 array 成员函数直接访问, 这可用于过滤器序列化:

filter f1 = ...;
...

// save filter
std::ofstream out("filter.bin", std::ios::binary);
std::size_t c1=f1.capacity();
out.write(reinterpret_cast<const char*>(&c1), sizeof(c1)); // save capacity (bits)
boost::span<const unsigned char> s1 = f1.array();
out.write(reinterpret_cast<const char*>(s1.data()), s1.size()); // save array
out.close();

// load filter
filter f2;
std::ifstream in("filter.bin", std::ios::binary);
std::size_t c2;
in.read(reinterpret_cast<char*>(&c2), sizeof(c2));
f2.reset(c2); // restore capacity
boost::span<unsigned char> s2 = f2.array();
in.read(reinterpret_cast<char*>(s2.data()), s2.size()); // load array
in.close();

注意, array() 是针对 unsigned char 的 span, 而容量以位计量, 因此 array.size() 是 capacity() / CHAR_BIT . 若在保存过滤器之外的另一台计算机上加载序列化的过滤器, 请注意两端的 CPU 体系结构必须具有相同的 字节序 , 重建才能成功.

  • filter<T, K> → c ≅ 每元素 19 位

  • filter<T, 1, multiblock<uint64_t, K>, 1> → c ≅ 每元素 20 位

  • filter<T, 1, multiblock<uint64_t, K>> → c ≅ 每元素 21 位

  • filter<T, 1, block<uint64_t[8], K>, 1> → c ≅ 每元素 21 位

  • filter<T, 1, multiblock<uint32_t, K>, 1> → c ≅ 每元素 21.5 位

  • filter<T, 1, block<uint64_t[8], K>> → c ≅ 每元素 22 位

  • filter<T, 1, multiblock<uint32_t, K>> → c ≅ 每元素 23 位

using my_filter=filter<std::string, 1, fast_multiblock32<14>, 1>;

所得过滤器可以按以下任一方式构造:

// 1) calculate the capacity from the value of c we got from the chart
my_filter f((std::size_t)(10'000'000 * 21.5));

// 2) let the library calculate the capacity from n and target fpr
// expect some deviation from the capacity in 1)
my_filter f(10'000'000, 1E-4);

// 3) equivalent to 2)
my_filter f(my_filter::capacity_for(10'000'000, 1E-4));

类模板 filter

boost::bloom::filter —— 一种支持元素插入与 概率性 查找的数据结构: 可以高置信度判定元素在过滤器中, 否则可以绝对确定地判定不在. 查找把不存在的元素错误判定为存在的概率称为过滤器的 误报率 (FPR).

boost::bloom::filter 维护一个 m 位的内部数组, 其中 m 是过滤器的 容量 . 与传统容器不同, 插入元素 x 并不在过滤器中存储 x 的副本, 而是使数组中固定数量的位被置一, 位的位置由 x 的哈希值伪随机产生. 对 y 的查找只是检查与 y 关联的所有位是否确实被置位.

  • 对于给定的过滤器, FPR 随新元素插入而增大.

  • 对于给定的已插入元素数量, 容量更高的过滤器 FPR 更低.

按照惯例, 若过滤器的容量为零, 或内部数组中所有位均为零, 我们称该过滤器为 空 的.

说明

模板参数

T

插入到过滤器中的元素的 cv 未限定对象类型.

K

插入或查找时, 每个元素调用相关联子过滤器的次数. K 必须大于零.

Subfilter

一种 subfilter 类型, 提供向过滤器内部数组设置/检查位的精确算法. 每次操作会在 K 个伪随机选中的数组片段 (Ksubarrays ) 上调用子过滤器, 片段宽度为 .used-value-size<Subfilter>

Stride

相邻子数组起始位置之间以字节计的距离. 若 Stride 被指定为零, 实际距离会自动选定为 used-value-size<Subfilter> (子数组不重叠). 否则, Stride 必须不大于 used-value-size<Subfilter> .

Hash

一个 Hash 类型, 针对 T .

Allocator

一个 Allocator , 其值类型为 unsigned char .

内部数组的分配与释放通过所提供分配器的内部副本完成. 若 stride 是 a = alignof(Subfilter::value_type) 的倍数, 数组按字节对齐到 max(64, a ).

若 boost::hash_is_avalanching<Hash>::value 是 true 且 sizeof(std::size_t) >= 8 , 哈希函数将被原样使用; 否则, 会增加一个位混合后处理阶段, 以额外的计算开销换取哈希质量的提升.

异常安全保证

除非明确指出, 所有以非 const 引用接受 boost::bloom::filter 的非 const 成员函数及相关函数都提供 基本异常保证 , 而所有以 const 引用接受 boost::bloom::filter 的 const 成员函数及相关函数都提供 强异常保证 .

除非明确指出, 任何操作都不会抛出异常, 除非该异常由过滤器的 Hash 或 Allocator 对象 (如果存在) 抛出.

类型与常量

static constexpr std::size_t stride;

等于 Stride , 若该参数被指定为非零. 否则, 等于 used-value-size<subfilter> .

后续工作

Boost.Bloom 的评审者和用户所要求的若干特性正被考虑纳入库的未来版本.

try_insert

为避免插入已存在的元素, 现在必须这样做:

已插入元素数的估计

对于经典布隆过滤器, 实际插入的元素数量可以从数组中被置一的位数 \(B\) 估计为

\(n\approx-\displaystyle\frac{m}{k}\ln\left(1-\displaystyle\frac{B}{m}\right),)\

这可用于实现成员函数 estimated_size . 截至撰写本文时, 我们不知道如何把该公式扩展到块过滤器与多块过滤器的情形. 对此问题的任何帮助都将不胜感激.

运行期指定 k

目前, 每次操作设置的位数 k 是在编译期配置的. 可以提供 boost::bloom::filter 的变体 (或扩展), 其中 k 的值在运行期指定, 代价是其性能会比静态情形更差 (初步实验显示执行时间增加约 10-20%).

替代过滤器

我们可以考虑添加其他数据结构, 例如 cuckoo 与 xor 过滤器, 它们更节省空间且可能更快.

附录 A: FPR 估计

对于经典布隆过滤器, 在一些简化假设下, 理论误报率由下式给出

\(\\text{FPR}(n,m,k)=\\left(1 - \\left(1 - \\displaystyle\\frac{1}{m}\\right)^{kn}\\right)^k \\approx \\left(1 - e^{-kn/m}\\right)^k\) 对较大的 \(\m\) ,

其中 \(\n\) 是插入过滤器的元素数量, \(\m\) 是以位计的容量, 而 \(\k\) 是每次插入设置的位数 (该公式的 推导 参见链接). 对于固定的逆负载因子 \(\c=m/n\) , 表达式在

\(\k_\\text{opt}}=c\\cdot\ln2\)

处取得最小值 \(1/2^{k_\\text{opt}}} \\approx 0.6185^{c}\) . 最优的 \(\k\) 必须是整数, 为 \(\\lfloor k_\\text{opt}}\\rfloor\) 或 \(\\lceil k_\\text{opt}}\\rceil\) .

对于形如 boost::bloom::filter<T, K, block<Block, K'>> 的过滤器, 我们可以扩展 Putze et al. 的方法来推导出 (近似但非常精确) 的公式:

\(\\text{FPR}_\\text{block}}(n,m,b,k,k')=\\left(\\displaystyle\\sum_{i=0}^{\\infty} \\text{Pois}(i,nbk/m) \\cdot \\text{FPR}(i,b,k')\\right)^{k},)\

其中

\(\\text{Pois}(i,\\lambda)=\\displaystyle\\frac{\\lambda^i e^{-\\lambda}}{i!}\)

是 Poisson 分布 的概率质量函数, 其均值为 \(\lambda\) ; 而 \(\b\) 是 Block 以位计的大小. 若我们使用 multiblock<Block,K'> , 则有

\(\\text{FPR}_\\text{multiblock}}(n,m,b,k,k')=\\left(\\displaystyle\\sum_{i=0}^{\\infty} \\text{Pois}(i,nbkk'/m) \\cdot \\text{FPR}(i,b,1)^{k'}\\right)^{k}.)\

正如我们 之前 评论过的, 一般而言

\(\\text{FPR}_\\text{block}}(n,m,b,k,k') \\geq \\text{FPR}_\\text{multiblock}}(n,m,b,k,k') \\geq \\text{FPR}(n,m,kk'),)\

也就是说, 对于相同的每次插入置位数, 块过滤器与多块过滤器的 FPR 比经典过滤器更差, 但它们会更快. 我们有特例

\(\\text{FPR}_{\\text{block}}}(n,m,b,k,1)=\\text{FPR}_{\\text{multiblock}}}(n,m,b,k,1)=\\text{FPR}(n,m,k),)\

这直接来自如下观察: 使用 {block|multiblock}<Block, 1> 的行为与经典布隆过滤器完全相同.

我们不知道当 Stride 不是其 "自然" 大小 used-value-size<Subfilter> (即子过滤器子数组相互重叠) 时, 块过滤器与多块过滤器 FPR 的任何封闭、简单的公式. 我们可以使用以下近似 (\(\s\) = Stride , 以位计):

\(\\text{FPR}_{\\text{block}}}(n,m,b,s,k,k')=\\left(\\displaystyle\\sum_{i=0}^{\\infty} \\text{Pois}\\left(i,\\frac{n(2b-s)k}{m}\\right) \\cdot \\text{FPR}(i,2b-s,k')\\right)^{k},)\
\(\\text{FPR}_\\text{multiblock}}(n,m,b,s,k,k')=\\left(\\displaystyle\\sum_{i=0}^{\\infty} \\text{Pois}\\left(i,\\frac{n(2bk'-s)k}{m}\\right) \\cdot \\text{FPR}\\left(i,\\frac{2bk'-s}{k'}\\,1\\right)^{k'}\\right)^{k},)\

其中把 \(\b\) 替换为 \(2b-s) (对多块过滤器则是把 \(bk') 替换为 \(2bk'-s) ) 是为了说明: 由于重叠, 影响特定位的哈希位置窗口会扩散. 注意, 当 \(\s\) 取其默认值 (块为 \(b)\\ , 多块为 \(bk')\) 时, 公式退化为不重叠情形. 这些近似对较低的 \(k') 值是可以接受的, 但随 \(k') 增长, 往往会低估实际 FPR. 一般而言, 对于典型的过滤器配置, 使用重叠会把 FPR 改善 (降低) 0.6 到 0.9 倍不等.

\(\\text{FPR}_{\\text{block}}}(n,m,b,s,k,k')\) 与 \(\\text{FPR}_\\text{multiblock}}(n,m,b,s,k,k')\) 是 boost::filter::fpr_for 的实现所使用的公式.

哈希混合

当哈希函数不具有雪崩性质时, 我们用下面的位混合后处理来改善其统计性质:

\(\m\\leftarrow\\text{mul}(h,C)\) ,
\(\h'\\leftarrow\\text{high}(m)\\text{ xor }\\text{low}(m)\) ,

其中 \(\\text{mul}\) 表示两个 64 位因子的 128 位乘法, \(\\text{high}(m)\) 与 \(\\text{low}(m)\) 分别是 \(\m\) 的高 64 位字与低 64 位字, \(C=\\lfloor 2^{64}/\\varphi \\rfloor\) , 而 \(\\varphi\) 是 黄金比例 .

32 位模式

在内部, 即使在 32 位模式 (用户提供的哈希函数产生 32 位输出) 下, 我们也始终使用 64 位哈希值. 为把 32 位哈希值扩展到 64 位, 我们使用 上文 所述的相同混合过程.

省却多个哈希函数

每次操作 \(\k\) 位的布隆过滤器的直接实现要求 \(\k\) 个不同且相互独立的哈希函数 \(h_i(x)) , 这会带来显著的性能损失, 尤其当对象的哈希代价高昂时 (例如字符串). Kirsch and Mitzenmacher 展示了如何把这一要求放宽到两个不同的哈希函数 \(h_1(x)) 与 \(h_2(x)) , 并按如下方式线性组合:

\(g_i(x)=h_1(x)+ih_2(x).)\

在没有正式论证的情况下, 我们把它进一步放宽为只有一个初始哈希值 \(h_0=h_0(x)) , 新值 \(h_i) 通过非常廉价的混合方案从 \(h_{i-1}) 计算. 下文中, \(\k\) 、 \(k') 是形如 boost::bloom::filter<T, K, {block|multiblock}<Block, K'>> 的过滤器中的同名值, \(\b\) 是 sizeof(Block) * CHAR_BIT , 而 \(\r\) 是过滤器中子数组的数量.

子数组位置

为从 \(h_{i-1}) 产生一个位置 (即 \(\\[0,r)\) 中的数 \(\p\) ), 我们没有使用直接但代价高昂的 \(p\\leftarrow h_{i-1}\\bmod r\) 过程, 而是求助于 Lemire 的 fastrange 技术 :

\(\m\\leftarrow\\text{mul}(h_{i-1},r),)\
\(p\\leftarrow\\lfloor m/2^{64} \\rfloor=\\text{high}(m).)\

为使 \(\p\) 与哈希值的后续使用去相关, 我们按如下方式从 \(h_{i-1}) 产生 \(h_{i}) :

\(h_i\leftarrow c \cdot h_{i-1} \bmod 2^{64}=\text{low}(c \cdot h_{i-1}),)\

其中 \(c=\\text{0xf1357aea2e62a9c5}\) (64 位模式), \(c=\\text{0xe817fb2d}\) (32 位模式) 取自 Steele and Vigna . 变换 \(h_{i-1} \\rightarrow h_i\) 是 \\ ^ {64} 上的一个简单的 乘法同余生成器 . 为了让这个 MCG 产生长周期, \(h_0) 必须为奇数, 因此实现把 \(h_0) 调整为 \(h_0'= (h_0\\text{ or }1)\) , 这使 \(h_i) 的最低有效位不适合用于伪随机化 (它始终为一).

位选择

在子过滤器内部, 我们必须从 \(h_i) 在范围 \([0,b)) 内产生 \(k') 个值 (即 \(k') 个位的位置). 我们通过依次从 \(h_i) 中取出 \(\\log_2b\) 个位来做到这一点, 且不使用包含其最低有效位的部分 (如前所述, 它始终为一). 若位用尽 (发生在 \(k'> 63/\\log_2b\) 时), 我们使用 已经描述过的 混合过程从 \(h_{i}) 产生新的哈希值 \(h_{i+1}) .
