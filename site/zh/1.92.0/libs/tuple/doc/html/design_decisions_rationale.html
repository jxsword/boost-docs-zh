关于命名空间

关于元组应放在单独的命名空间中, 还是直接放在 boost 命名空间中, 曾有过讨论. 通行的原则是: 领域库 (如 graph、python) 应放在单独的子命名空间中, 而工具类库则直接放在 boost 命名空间中. 元组介于两者之间: tuple 模板显然是一种通用工具, 但该库除了 tuple 模板之外还引入了相当多的名字. 元组最初位于子命名空间中. 讨论的结果是, tuple 定义被直接移到了 boost 命名空间之下. 随后讨论的又一个结果是, 子命名空间被重新引入. 最终 (真心希望如此) 的方案是: 所有定义都位于命名空间 ::boost::tuples 中, 同时最常用的名字也进入 ::boost 命名空间. 这通过 using 声明实现 (由 Dave Abrahams 建议):

namespace boost {
  namespace tuples {
      ...
    // All library code
      ...
  }
  using tuples::tuple;
  using tuples::make_tuple;
  using tuples::tie;
  using tuples::get;
}

在这种安排下, 通过直接调用构造函数、make_tuple 或 tie 函数创建元组时, 无需命名空间限定符. 此外, 所有操作元组的函数都能通过 Koenig 查找找到. 唯一的例外是 get<N> 函数, 它们总是以显式限定的模板实参调用, 因此 Koenig 查找不适用. 所以 get 通过 using 声明被提升到 ::boost 命名空间. 因此, 对应用程序员而言, 接口实际上位于命名空间 ::boost 之下.

构成面向库编写者接口的其余名字 (cons 列表、操作 cons 列表的元函数等) 仍留在子命名空间 ::boost::tuples 中. 注意, 名字 ignore、set_open、set_close 和 set_delimiter 被视为应用程序员接口的一部分, 但仍未置于 boost 命名空间之下. 原因在于这些常见名字存在名称冲突的危险. 此外, 这些特性的使用可能并不频繁.

给真正对命名空间感兴趣的读者

子命名空间名 tuples 引起了一些讨论. 不使用最自然的名字 'tuple' 的理由是避免与 tuple 模板重名. 不过, Boost 库中的命名空间名一般不用复数形式. 首先, 没有关于命名空间与类同名的实际麻烦报告, 我们曾考虑把名字 'tuples' 改为 'tuple'. 但后来还是发现了一些麻烦. gcc 和 edg 编译器都拒绝在命名空间名与类名相同时使用 using 声明:

namespace boost {
  namespace tuple {
    ... tie(...);
    class tuple;
      ...
  }
  using tuple::tie; // ok
  using tuple::tuple; // error
    ...
}

不过请注意, 全局命名空间中相应的 using 声明似乎没有问题:

using boost::tuple::tuple; // ok;

cons 列表的结束标记 (nil、null_type、...)

元组在内部表示为 cons 列表:

tuple<int, int>

继承自

cons<int, cons<int, null_type> >

null_type 是列表的结束标记. 最初的提议是 nil, 但该名字在 MacOS 中已被使用, 可能会引起问题, 因此改用 null_type. 曾考虑过的其他名字还有 null_t 和 unit (SML 中的空元组类型).

注意, null_type 是空元组的内部表示: tuple<> 继承自 null_type.

元素索引

关于使用 0 还是 1 作为索引起点, 讨论得极其充分, 得出的观察结论如下:

  • 0 起点的索引是 "C++ 的方式", 数组等使用的就是这种方式.
  • 1 起点的 "命名风格" 索引同样存在, 例如 bind1st、bind2nd、pair::first 等.

形如 get<N>(a) 或 a.get<N>() (其中 a 是元组, N 是索引) 的元组访问语法被认为属于第一类, 因此元组中第一个元素的索引是 0.

曾有人建议提供以 1 为起点的 "命名风格" 索引, 使用 _1st、_2nd、_3rd 等常量. 通过恰当选择常量类型, 这可以支持如下替代语法:

a.get<0>() == a.get(_1st) == a[_1st] == a(_1st);

出于以下原因, 我们选择不提供多于一种的索引方式:

  • 0 起点的索引可能不会让所有人满意, 但一旦固定下来, 就比同时存在两种不同方法的混乱要好 (会有人想为数组提供这样的常量吗?).
  • 添加另一种索引方案并不能真正为库的用户带来任何新东西 (比如新特性).
  • C++ 的变量与常量命名规则几乎没有为定义简短好看的索引常量 (如 _1st 等) 留下多少可能. 还是把这些留给 bind 和 lambda 库去做更有意义的事情吧.
  • a1st (或 a(_1st)) 这样的访问语法很有吸引力, 差一点让我们最终添加了这些索引常量. 然而 0 起点的下标在 C++ 中根深蒂固, 我们担心会造成混淆.
  • 这样的常量很容易添加.

元组比较

比较运算符实现字典序. 其他排序方式也曾被考虑, 主要是支配序 (a < b 当且仅当对每个 i 有 a(i) < b(i)). 我们认为, 字典序虽然在数学上并非最自然, 却是日常编程中最常需要的排序方式.

流式输出

通过元组流操纵符指定的字符存储在 ios_base::xalloc 分配的空间内, 该空间为 long 类型对象分配存储. static_cast 用于在 long 与流的字符类型之间进行转换. 因此, 字符类型无法与 long 相互转换的流将无法编译.

这一点今后可能会重新审视. 两种可能的解决方案是:

  • 只允许使用普通的 char 类型作为元组分隔符, 并使用 widen 和 narrow 在流的实际字符类型之间进行转换. 这样总是可以编译, 但某些设置操纵符的调用可能产生与预期不同的字符 (某个默认字符).
  • 分配足够的空间来容纳流的实际字符类型. 这意味着必须单独分配内存来保存分隔符字符, 而指向该内存的指针则存储在以 ios_base::xalloc 分配的空间中. 有人愿意做吗?
