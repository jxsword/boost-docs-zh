1. 引言

本库根据它能够从 C、C++、Objective C 和 Objective C++ 的预定义宏或普遍可用的头文件中收集到的信息, 定义一组编译器、架构、操作系统、库及其他版本号. 本库的构想源于一项提案, 该提案旨在扩展 Boost Config 库, 使其能提供比其所支持的特征定义更多且一致的信息. 下文是该简短提案经过编辑的版本.

1.1. 提案

构想是定义一组宏来识别编译器并一致地表示其版本. 这包括:

  • 一个唯一的 BOOST_VERSION_NUMBER(major,minor,patch) 宏, 用于指定版本号(遗憾的是, BOOST_VERSION 这个名字已被占用, 用于表示 boost 本身的版本号).

  • 为每个受支持的编译器提供一个编译器识别宏, 适合在 #if/#elif 指令中使用. 无论使用哪个编译器, 所有宏都会被定义. 对应于当前所用编译器的那个宏会以 BOOST_VERSION_NUMBER 的形式定义, 以承载确切的编译器版本. 所有其他宏都会展开为一个求值为 false 的表达式(例如记号 0), 以表明对应的编译器不存在.

  • 可以为所有宏在 boost/config/select_compiler.hpp 中设置"空值"; 然后, 对于每个编译器, 相应的识别宏会在对应的 boost/compiler/(cc).hpp 中被 #undef 并重新 #define; 不过, 在 Boost.Config 基础设施的语境下, 使用"前缀"头文件(稍后介绍)或 boost/config/suffix.hpp 是更好的解决方案.

1.2. 当前的库

当前的 Predef 库现在既是独立的库, 又扩展了范围. 它包括对架构、编译器、语言、库、操作系统以及字节序的检测与定义. 主要优点有:

  • 版本号总是有定义, 因此不必再用 #ifdef 进行守护.

  • 可用于 #ifdef 检查的守护宏.

  • 所有可能的定义都通过单一的 #include <boost/predef.h> 包含进来, 因而对预编译头的使用很友好.

  • 也可以只包含特定的定义, 例如用 #include <boost/predef/os/windows.h> 进行单项检查.

  • 预定义宏可以直接在预处理器表达式和编译器表达式中使用, 与其他以类似方式定义的值进行比较.

  • 这些头文件可以在多种支持 C 预处理器的语言中使用, 特别是 C++、C、Objective C 和 Objective C++.

1.3. 设计抉择

一个重要的设计抉择是如何用一个适合在预处理指令中使用的单一整数来表示编译器版本. 让我们做一些计算. 预处理常量表达式的"基本"有符号类型在 C90(以及 2006 年时的 C++)中是 long, 在 C99 中是 intmax_t. long 类型至少要能表示数 +2 147 483 647. 这意味着最高有效位只能是 0、1 或 2; 如果我们希望所有十进制位都能在 0 到 9 之间变化, 那么可考虑的最大范围是 [0, 999 999 999\]. 均匀分配的话, 这意味着版本号的每个部分各占 3 位十进制数字.

所以我们可以:

  1. 采用不均匀的分配, 或者

  2. 使用更多位(更大的类型), 或者

  3. 使用 3/3/3, 并让具体的编译器/平台/标准库在 3 位数字范围内设置数值.

采用第一种方案并将其定为 2/2/5 看起来相对安全. 它覆盖了 CodeWarrior 等主版本号已达到甚至超过 10 的编译器. 有些编译器用构建号代替补丁号; 五位数字(VC++ 8 已经达到这个数量)即使在这种情况下也算一个合理的上限.

ℹ
 2/2/6 方案可以容纳更大的补丁/构建号, 代价是例如把主版本号限制在 20 以内(或者再加上一些约束, 限制在 21 以内).

读者可以放心的是, 这一决定实际上只编码在代码中的一处: 即 BOOST_VERSION_NUMBER 的定义.

1.4. 后续工作

尽管本库的基础工作已经完成, 仍有许多工作可以做:

  • 目前我们把对库的检测限定于已知的内建预定义宏, 以及保证存在的系统和库头文件. 添加类似自动配置的预定义宏可能会很有意思. 这样我们就能为用户特定的库和特性添加定义.

  • 与上面相辅相成, 最好能增加一些用户控制, 决定顶层头文件包含哪些头文件. 不过在库的当前形态下这已不算什么问题, 因为用户可以只包含自己需要的特定头文件.

  • 此外, 即使没有自动配置风格的选项, 最好也增加可选包含的头文件, 让用户能为自己使用的库获得一致的版本号定义.

  • 显然, 改造现有的 Boost 库以使用 Predef 库还有很多工作要做.

  • 还有为当前及未来的编译器、平台、架构、语言和库添加定义的持续性工作.

2. 使用预定义宏

要使用自动定义的预定义宏, 只需包含唯一的顶层头文件:

#include <boost/predef.h>

这会定义库已知的[*全部]版本宏. 对每个宏而言, 当未检测到特定条目时它会被定义为 零 值表达式, 而当检测到时则被定义为 正 值. 预定义宏分为五个类别, 每个类别带有特定前缀的宏:

  • BOOST_ARCH_ 表示编译所针对的系统/CPU 架构.

  • BOOST_COMP_ 表示正在使用的编译器.

  • BOOST_LANG_ 表示编译所依据的语言标准.

  • BOOST_LIB_C_ 和 BOOST_LIB_STD_ 表示正在使用的 C 和 C++ 标准库.

  • BOOST_OS_ 表示编译目标所在的操作系统.

  • BOOST_PLAT_ 表示位于操作系统或编译器之上的平台.

  • BOOST_ENDIAN_ 表示操作系统与架构组合的字节序.

  • BOOST_HW_ 表示硬件特定特性.

  • BOOST_HW_SIMD 表示 SIMD(单指令多数据)检测.

ℹ
 检测到的定义针对的是编译期间所面向的配置. 特别是在交叉编译中, 这指的是目标系统, 而不是宿主系统.

人们通过与 BOOST_VERSION_NUMBER 宏比较, 使用各个定义来与特定版本进行比较. 例如, 要基于 GCC C++ 编译器的版本做出选择, 可以这样:

#include <boost/predef.h>
#include <iostream>

int main()
{
  if (BOOST_COMP_GNUC >= BOOST_VERSION_NUMBER(4,0,0))
    std::cout << "GCC compiler is at least version 4.0.0" << std::endl;
  else
    std::cout << "GCC compiler is at older than version 4.0.0, or not a GCC compiler" << std::endl;
  return 0;
}

你可能已经注意到, 上面的 else 子句也涵盖了未检测到特定编译器的情况. 但可以让测试同时检测是否被检测到. 所有预定义定义在未检测到时都被定义为零(0)表达式. 因此可以用一个自然的单一条件来同时完成检测. 例如:

#include <boost/predef.h>
#include <iostream>

int main()
{
  if (BOOST_COMP_GNUC)
    std::cout << "This is GNU GCC!" << std::endl;
  else
    std::cout << "Not GNU GCC." << std::endl;
  return 0;
}

而且, 由于预定义宏是预处理器定义, 在预处理器中同样可以做到这一点:

#include <boost/predef.h>
#include <iostream>

#if BOOST_COMP_GNUC
  #if BOOST_COMP_GNUC >= BOOST_VERSION_NUMBER(4,0,0)
    const char * the_compiler = "GNU GCC, of at least version 4."
  #else
    const char * the_compiler = "GNU GCC, less than version 4."
  #endif
#else
  const char * the_compiler = "Not GNU GCC."
#endif

int main()
{
  std::cout << the_compiler << std::endl;
  return 0;
}

此外, 对于每个定义的版本宏, 还有一个 *_AVAILABLE 宏, 它只在检测到特定方面时才被定义. 即一个等价于如下形式的定义:

#if BOOST_PREDEF_ABC
  #define BOOST_PREDEF_ABC_AVAILABLE
#endif

同样, 对于每个方面都有一个以描述性名称定义的宏, 说明检测的内容是什么.

2.1. *_EMULATED 宏

预定义定义保证在一个类别内被唯一地检测到. 但在某些语境下可能出现多个底层检测. 广为人知的例子是 GCC 和 MSVC 编译器的检测, 其他编译器通常通过定义相同的基础宏来模拟它们. 为应对这种情况, 检测头文件允许在检测到这种情形时定义 *_EMULATED 预定义宏. 被模拟的预定义宏将被设置为该检测的版本号, 而不是该检测对应的常规预定义宏. 例如, MSVC 会设置 BOOST_COMP_MSVC_EMULATED 但不设置 BOOST_COMP_MSVC, 同时它还会设置 BOOST_COMP_MSVC_AVAILABLE.

2.2. 使用 BOOST_VERSION_NUMBER 宏

所有预定义宏都被定义为对 BOOST_VERSION_NUMBER 宏的一次使用. 该宏接受各自的 major、minor 和 patch 值表达式:

#define BOOST_VERSION_NUMBER( major, minor, patch ) ...

参数如下:

  1. 主版本号, 范围为 [0,99] 的常量值表达式.

  2. 次版本号, 范围为 [0,99] 的常量值表达式.

  3. 补丁级别版本号, 范围为 [0,99999] 的常量值表达式.

各个参数的范围通过取模("%")(即截断)来"强制", 而不是通过钳制. 因此, 这些上限的强制程度仅足以避免超出范围的问题, 但不足以防止其他种类的问题, 比如超出范围导致错误的检测或漏检. 超出范围保证之外的正确使用, 由各个预定义宏自行负责.

参数的值可以是任何预处理器合法的常量值表达式. 在 BOOST_VERSION_NUMBER 宏的定义以及其他所有预定义宏中, 只使用常量值算术. 这意味着任何允许的进制都可以, 即二进制、八进制、十进制和十六进制. 例如:

#define MY_APPLICATION_VERSION_NUMBER BOOST_VERSION_NUMBER(2,0xA,015)

等价于:

#define MY_APPLICATION_VERSION_NUMBER BOOST_VERSION_NUMBER(2,10,13)

3. 添加新的预定义宏

我们知道, 像这样的库将是一项永无止境的进行中工作. 因此我们期待并欢迎其他人为预定义宏贡献修正与补充. 有鉴于此, 我们需要保持一致的预定义宏定义方式. 因此, 所有现在和将来的预定义宏都遵循相同的结构与要求.

3.1. 头文件的要求

所有预定义宏都需要遵循一组要求:

  • 头文件必须使用 Boost Software License.

  • 预定义宏默认必须定义为 BOOST_VERSION_NUMBER_NOT_AVAILABLE.

  • 一旦检测到, 预定义宏必须被重定义为非零值.

  • 预定义宏在被检测到时默认必须定义为 BOOST_VERSION_NUMBER_AVAILABLE.

  • 如果可能, 预定义宏将被定义为检测到的版本号.

  • 预定义宏必须根据需要定义 *_AVAILABLE 宏.

  • 预定义宏必须定义一个符号常量字符串名称宏.

  • 预定义宏在定义之后必须向测试系统声明自身.

  • 预定义宏必须保证在所属类别中自己是唯一被定义为已检测的.

  • 但预定义宏可以定义 *_EMULATED 宏, 以表明它先前已被另一个头文件检测到, 并且正在被系统"模拟". 注意, 在这种情况下 *_AVAILABLE 宏仍然必须定义.

此外还有一些预定义宏头文件应当遵循的额外准则:

  • 检测应避免包含默认情况下不会被包含的额外头文件.

  • 如果检测必须包含某个头文件, 应尽可能把该包含守护在检测之内.

  • 如果检测必须无条件包含头文件, 并且可以从多个头文件中选择, 应优先选择影响最小的, 即包含定义及其他依赖最少的那一个.

3.2. 头文件的结构

为了保持总体一致性, 建议新的预定义宏头文件像现有的预定义宏头文件一样, 遵循以下结构. 首先是版权与许可声明, 随后是包含守护:

/*
Copyright Jane Doe YYYY
Distributed under the Boost Software License, Version 1.0.
(See accompanying file LICENSE_1_0.txt or copy at
http://www.boost.org/LICENSE_1_0.txt)
*/

#ifndef BOOST_PREDEF_category_tag_H
#define BOOST_PREDEF_category_tag_H

如果检测依赖于对另一个预定义宏的检测, 你应当在这里包含那些头文件.

#include <boost/predef/CATEGORY_TAG/DEPENDENCY.h>

根据你定义预定义宏的方式, 你至少必须包含 version_number.h 头文件. 但你可能还想包含 make.h 头文件, 以获得版本号分解实用宏:

#include <boost/predef/version_number.h>
#include <boost/predef/make.h>

Predef 库使用 Asciidoctor 编写文档. 为了让各个预定义宏出现在参考一节中, 我们添加代码内文档, 随后是预定义宏的零值默认定义. 我们强烈推荐这种文档与默认定义的特定安排, 因为有些开发环境会自动解读它并为宏提供内联帮助. 特别是, 这对流行的 Eclipse IDE 有效:

/* tag::reference[]

= `BOOST_category_tag`

Documentation about what is detected.

*/

#define BOOST_category_tag BOOST_VERSION_NUMBER_NOT_AVAILABLE

接下来是对特定预定义宏的检测与定义. 其结构是先做一个总体检查(condition_a), 并把进一步的版本检测放在其中. 总体检查内的第一个动作是 "#undef BOOST_category_tag", 它会移除零值默认定义. 其余部分由你自行决定如何做检查以定义版本. 但至少必须 "#define BOOST_category_tag BOOST_VERSION_NUMBER_AVAILABLE" 作为后备, 以最低限度表明该预定义宏已被检测到:

#if (condition_a)
#   undef BOOST_category_tag
#   if (condition_b)
#        define BOOST_category_tag BOOST_VERSION_NUMBER(major,minor,patch)
#    else
#        define BOOST_category_tag BOOST_VERSION_NUMBER_AVAILABLE
#    endif
#endif

我们还需要提供该预定义宏的 *_AVAILABLE 版本.

#if BOOST_category_tag
#   define BOOST_category_tag_AVAILABLE
#endif

为了方便, 我们还希望提供一个 *_NAME 宏:

#define BOOST_category_tag_NAME "Name"

此时我们结束包含守护. 我们在测试声明之前这样做, 因为测试系统会多次包含这些头文件以生成所需的测试代码.

#endif

预定义宏的测试是自动化的, 会为所有已定义的预定义宏生成检查, 无论其是否被检测到. 为此, 我们需要向测试系统声明该预定义宏. 这个声明在常规使用中为空, 而在测试程序中它会特殊展开以生成信息性输出:

#include <boost/predef/detail/test.h>
BOOST_PREDEF_DECLARE_TEST(BOOST_category_tag,BOOST_category_tag_NAME)

3.3. 添加排他性预定义宏

对于在检测中需要互斥的预定义宏头文件, 我们需要添加检查和定义, 以检测预定义宏何时被多个头文件检测到.

在内部, 编译器、操作系统和平台分别在预定义宏首次被检测到时定义 BOOST_PREDEF_DETAIL_COMP_DETECTED、BOOST_PREDEF_DEFAIL_OS_DETECTED 和 BOOST_PREDEF_DETAIL_PLAT_DETECTED. 这用于防止后续被包含的头文件对检测进行多重定义. 在这些情况下, 检测应改写为:

#if !BOOST_PREDEF_DETAIL_category_DETECTED && (condition_a)
#   undef BOOST_category_tag
#   if (condition_b)
#        define BOOST_category_tag BOOST_VERSION_NUMBER(major,minor,patch)
#    else
#        define BOOST_category_tag BOOST_VERSION_NUMBER(0,0,1)
#    endif
#endif

并且, 当我们检测到时, 还会包含一个定义 *_DETECTED 宏的头文件:

#if BOOST_category_tag
#   define BOOST_category_tag_AVAILABLE
#   include <boost/predef/detail/CATEGORY_detected.h>
#endif

关于该头文件的其余内容与基本检测头文件相同.

3.4. 添加排他性但以模拟方式实现的预定义宏

由于编译器经常被其他编译器模拟, 我们既要对编译器进行排他性检测, 也要提供已检测到该编译器被模拟的信息. 为此, 我们为编译器检测定义一个局部 *_DETECTION 宏, 并有条件地定义基础编译器预定义宏 BOOST_COMP_compiler 或替代的 BOOST_COMP_compiler_EMULATED 预定义宏.

初始检测如下:

#if (condition_a)
#   if (condition_b)
#        define BOOST_COMP_tag_DETECTION BOOST_VERSION_NUMBER(major,minor,patch)
#    else
#        define BOOST_COMP_tag_DETECTION BOOST_VERSION_NUMBER_AVAILABLE
#    endif
#endif

然后我们就可以有条件地定义基础或被模拟的预定义宏:

#ifdef BOOST_COMP_tag_DETECTION
#   if defined(BOOST_PREDEF_DETAIL_COMP_DETECTED)
#       define BOOST_COMP_tag_EMULATED BOOST_COMP_tag_DETECTION
#   else
#       undef BOOST_COMP_tag
#       define BOOST_COMP_tag BOOST_COMP_tag_DETECTION
#   endif
#   define BOOST_category_tag_AVAILABLE
#   include <boost/predef/detail/comp_detected.h>
#endif

3.5. 使用实用模式宏

通过包含:

#include <boost/predef/make.h>

你会得到一组实用宏, 用于分解编译器所定义的常见版本宏. 例如, EDG 编译器使用一个简单的 3 数字版本宏(M,N,P). 它可以被分解并定义为:

#define BOOST_COMP_EDG BOOST_PREDEF_MAKE_N_N_N(__EDG_VERSION__)

分解宏分为三种类型: 十进制分解、十六进制分解和日期分解. 其命名格式为: 十进制用 "N", 十六进制用 "F", 日期用 "Y"、"M"、"D".

4.7. BOOST_HW 硬件宏

4.7.1. 使用 BOOST_HW_SIMD_* 预定义宏

SIMD 预定义宏依赖于编译器选项. 例如, 要启用 SSE3, 你必须在 clang 或 gcc 中添加选项 -msse3. SIMD 预定义宏也是包含性的. 这意味着如果启用了 SSE3, 那么版本号更低的所有其他扩展都会被隐式启用并被检测到. 但是, 有些扩展是 CPU 特定的, 当更高版本被启用时, 它们可能既不会被检测到也不会被启用.

ℹ
 在使用 x86-64 架构时, SSE(1) 和 SSE2 默认会被自动启用.

要检查是否有任何 SIMD 扩展被启用, 可以使用:

#include <boost/predef/hardware/simd.h>
#include <iostream>

int main()
{
#if defined(BOOST_HW_SIMD_AVAILABLE)
    std::cout << "SIMD detected!" << std::endl;
#endif
    return 0;
}

在编写 SIMD 特定代码时, 你可能想检查是否检测到某个特定扩展. 为此, 你必须使用正确的架构预定义宏并对其进行比较. 这些预定义宏的形式为 BOOST_HW_SIMD_"ARCH" (其中 "ARCH" 可以是 ARM、PPC 或 X86). 例如, 如果你编译面向 x86 架构的代码, 就必须使用 BOOST_HW_SIMD_X86. 它的值将是该架构检测到的最新 SIMD 扩展的版本号.

要检查某个扩展是否已被启用:

#include <boost/predef/hardware/simd.h>
#include <iostream>

int main()
{
#if BOOST_HW_SIMD_X86 >= BOOST_HW_SIMD_X86_SSE3_VERSION
    std::cout << "This is SSE3!" << std::endl;
#endif
    return 0;
}
ℹ
 这些 _VERSION 定义把版本号映射为实际的真实标识符, 这样编写比较时就不必与版本号纠缠.

要 "严格" 检查最近检测到的扩展:

#include <boost/predef/hardware/simd.h>
#include <iostream>

int main()
{
#if BOOST_HW_SIMD_X86 == BOOST_HW_SIMD_X86_SSE3_VERSION
    std::cout << "This is SSE3 and this is the most recent enabled extension!"
        << std::endl;
#endif
    return 0;
}

由于预定义宏的版本体系以及 SIMD 扩展宏的包含性, 你可以轻松检查所支持扩展的范围:

#include <boost/predef/hardware/simd.h>
#include <iostream>

int main()
{
#if BOOST_HW_SIMD_X86 >= BOOST_HW_SIMD_X86_SSE2_VERSION &&\
    BOOST_HW_SIMD_X86 <= BOOST_HW_SIMD_X86_SSSE3_VERSION
    std::cout << "This is SSE2, SSE3 and SSSE3!" << std::endl;
#endif
    return 0;
}
ℹ
 与 gcc 和 clang 不同, Visual Studio 不允许你精确指定想要使用的 SSE 变体, 会进行的检测只有 SSE、SSE2、AVX 和 AVX2. 更多信息, 参见 [@https://msdn.microsoft.com/en-us/library/b0084kay.aspx 此处].

4.8. 其他宏

4.8.1. BOOST_ENDIAN_*

字节序内存排列的检测. 本头文件中有四个被定义的宏, 它们定义了通常可能的各种字节序内存排列:

  • BOOST_ENDIAN_BIG_BYTE, 按字节交换的大端序.

  • BOOST_ENDIAN_BIG_WORD, 按字交换的大端序.

  • BOOST_ENDIAN_LITTLE_BYTE, 按字节交换的小端序.

  • BOOST_ENDIAN_LITTLE_WORD, 按字交换的小端序.

这种检测是保守的, 它只标识它确知的字节序. 特别是双端序不会被标出, 因为除了操作系统提供的头文件之外, 实际上不可能从其他任何途径确定字节序. 而目前已知的一些头文件并未定义程序化的双端序可用性.

本实现汇编了各种公开可得的信息与习得的知识:

  1. "Pre-defined Compiler Macros" 的不可或缺的文档 Endianness.

  2. Wikipedia 计算机架构页面中提供的各种字节序规范.

  3. 对定义字节序的头文件的一般性公开检索.

4.8.2. BOOST_ARCH_WORD_BITS

检测当前架构的本机字长(以位为单位). 这项检测有两种宏:

  • BOOST_ARCH_WORD_BITS, 给出字长的位数(16、32、64).

  • BOOST_ARCH_WORD_BITS_16、BOOST_ARCH_WORD_BITS_32 和 BOOST_ARCH_WORD_BITS_64, 在检测到给定字长时给出指示.

它们既支持单项检查, 也支持在代码中直接使用该字长.

ℹ
 字长是在每种架构上手工确定的. 因此使用 wordsize.h 头文件也会包含所有架构头文件.

4.8.3. BOOST_PREDEF_WORKAROUND

BOOST_PREDEF_WORKAROUND(symbol,comp,major,minor,patch)

用法:

#if BOOST_PREDEF_WORKAROUND(BOOST_COMP_CLANG,<,3,0,0)
    // Workaround for old clang compilers..
#endif

定义对两个版本号的比较, 取决于 BOOST_STRICT_CONFIG 的定义. 当 BOOST_STRICT_CONFIG 已定义时, 这会展开为一个可转换为 false 的值, 其效果是禁用所有由 BOOST_PREDEF_WORKAROUND 条件守护的代码. 当 BOOST_STRICT_CONFIG 未定义时, 这会展开为: 把给定的 symbol 版本值以 comp 比较与 BOOST_VERSION_NUMBER(major,minor,patch) 相对照.

4.8.4. BOOST_PREDEF_TESTED_AT

BOOST_PREDEF_TESTED_AT(symbol,major,minor,patch)

用法:

#if BOOST_PREDEF_TESTED_AT(BOOST_COMP_CLANG,3,5,0)
    // Needed for clang, and last checked for 3.5.0.
#endif

定义对两个版本号的比较, 取决于 BOOST_STRICT_CONFIG 和 BOOST_DETECT_OUTDATED_WORKAROUNDS 的定义. 当 BOOST_STRICT_CONFIG 已定义时, 这会展开为一个可转换为 false 的值, 其效果是禁用所有由 BOOST_PREDEF_TESTED_AT 条件守护的代码. 当 BOOST_STRICT_CONFIG 未定义时, 这会展开为以下两者之一:

  • 可转换为 true 的值 (当 BOOST_DETECT_OUTDATED_WORKAROUNDS 未定义时).

  • 一个可转换为 true 的值, 条件是 BOOST_PREDEF_WORKAROUND(symbol, ⇐, major, minor, patch) 的展开为 true 且 BOOST_DETECT_OUTDATED_WORKAROUNDS 已定义.

  • 当 BOOST_PREDEF_WORKAROUND(symbol, >, major, minor, patch) 的展开为 true 且 BOOST_DETECT_OUTDATED_WORKAROUNDS 已定义时, 为编译错误.

4.9. 版本定义宏

4.9.1. BOOST_VERSION_NUMBER

BOOST_VERSION_NUMBER(major,minor,patch)

定义标准版本号, 具有以下性质:

  • [0,1000000000) 范围内的十进制基整数. 该数值范围的设计允许 (2,2,5) 三元组, 可以放进一个 32 位值中.

  • major 数字可以在 [0,99] 范围内.

  • minor 数字可以在 [0,99] 范围内.

  • patch 数字可以在 [0,99999] 范围内.

  • 值可以用任何进制指定, 因为定义的值是常量表达式.

  • 值可以直接在预处理器表达式和编译器表达式中使用, 与其他以类似方式定义的值进行比较.

  • 实现对 major、minor 和 patch 各自的范围进行了强制. 超出范围的值会被截断(取模).

BOOST_VERSION_NUMBER_MAJOR(N), BOOST_VERSION_NUMBER_MINOR(N), BOOST_VERSION_NUMBER_PATCH(N)

这些宏从格式良好的版本号中提取 major、minor 和 patch 部分, 分别得到 [0,99] 或 [0,99999] 范围内的预处理器表达式.

5. 检查实用工具

predef_check 实用工具提供了一种构建程序的设施, 该程序会把给定的一组表达式与构建它时所检测到的定义进行核对.

5.1. predef_check 程序

尽管只有一个 predef_check 程序, 但针对 Predef 检测到的每种语言都有变体, 以匹配源文件的约定. 对所有这些程序, 都以一组表达式参数调用. 表达式会在特定 predef_check 程序的上下文中求值, 如果它们全部为真, 则返回零(0). 否则返回第一个为假的表达式的下标.

表达式语法很简单:

predef-definition [ relational-operator version-value ]

predef-definition 可以是任何 Predef 定义. 例如 BOOST_COMP_GCC.

relational-operator 可以是以下任意之一: >、<、>=、⇐、== 和 !=.

version-number 可以是完整或部分的版本三元组值. 如果是部分版本三元组, 则以零补全. 即 x.y 等价于 x.y.0, x 等价于 x.0.0.

relations-operator 和 version-number 可以省略. 此时等价于:

predef-definition > 0.0.0

5.2. 在 Boost.Build 中使用

你可以直接从 Boost Build 使用 predef_check 程序来配置目标需求. 这对于基于 Predef 中提供的详细版本信息来控制项目构建哪些内容很有用. 基本用法很简单:

import path-to-predef-src/tools/check/predef
    : check require
    : predef-check predef-require ;

exe my_windows_program : windows_source.cpp
    : [ predef-require "BOOST_OS_WINDOWS" ] ;

这个简单用例会跳过构建 my_windows_program, 除非是在为 Windows 构建. 与直接使用 predef_check 一样, 你可以传入多个使用关系比较的表达式. 例如:

import path-to-predef-src/tools/check/predef
    : check require
    : predef-check predef-require ;

lib my_special_lib : source.cpp
    : [ predef-require "BOOST_OS_WINDOWS != 0" "BOOST_OS_VMS != 0"] ;

在这种情况下, my_special_lib 只有在 OS 不是 Windows 或 VMS 时才会被构建. requires 规则是 check 规则的一个特例, 并且是依据它定义的:

rule require ( expressions + : language ? )
{
    return [ check $(expressions) : $(language) : : <build>no ] ;
}

表达式还可以使用显式的 "and"、"or" 逻辑运算符来进行更复杂的检查:

import path-to-predef-src/tools/check/predef
    : check require
    : predef-check predef-require ;

lib my_special_lib : source.cpp
    : [ predef-require "BOOST_OS_WINDOWS" or "BOOST_OS_VMS"] ;

你可以使用 check 规则获得更多控制, 并实现构建内容控制之外的功能. check 规则的定义是:

rule check ( expressions + : language ? : true-properties * : false-properties * )

当作为 Boost Build 目标的需求被调用时, 该规则会把 true-properties 添加到目标, 条件是所有 expressions 求值为真; 否则会把 false-properties 作为需求添加. 例如, 你可以用它来启用或禁用程序中的特性:

import path-to-predef-src/tools/check/predef
    : check require
    : predef-check predef-require ;

exe my_special_exe : source.cpp
    : [ predef-check "BOOST_OS_WINDOWS == 0"
        : : <define>ENABLE_WMF=0
        : <define>ENABLE_WMF=1 ] ;

对于 check 和 require, language 参数控制使用 predef_check 程序的哪个变体来检查表达式. 它默认为 "c++", 但可以是以下任意之一: "c"、"cpp"、"objc" 和 "objcpp".

  • 修复 MinGW 不正确的包含守护. (来自 Ruslan Baratov)

6.15. 1.4

  • 修复测试警告.

  • 修正 Windows Platform 的 AVAILABLE 宏中的拼写错误. (来自 Vemund Handeland)

6.16. 1.3
