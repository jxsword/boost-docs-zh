唯一资源封装

资源特征
简化资源特征
与 C++ 库基础扩展中定义的 unique_resource 的比较
#include <boost/scope/unique_resource.hpp>

Boost.Scope 提供 unique_resource 类模板. 这是对任意资源的封装, 表示对资源的独占所有权. 该封装提供对所拥有资源的访问, 并在销毁时自动调用删除器函数对象释放资源. 它是 std::unique_ptr 的泛化, 但 std::unique_ptr 仅用于封装指针, 而 unique_resource 也可以封装其他类型的资源.

资源类型必须具有以下属性才能与 unique_resource 兼容:

  • 可移动构造, 且移动构造函数标记为 noexcept; 或
  • 可拷贝构造; 或
  • 对象类型的左值引用.

注意, 若资源类型是引用, 被引用的对象必须存储在 unique_resource 封装之外, 并在封装持有所有权期间始终有效. 用户不应通过 unique_resource 封装以外的方式访问资源对象. 例如, 不允许通过将资源对象置为无效状态或绕过资源封装显式释放资源来修改资源对象, 因为封装仍会对此时已无效的资源调用删除器.

删除器必须是可在资源类型的左值上调用的函数对象类型, 且必须可拷贝构造. 虽然并非严格要求, 但通常强烈建议对资源调用删除器不抛出异常并标记为 noexcept, 因为删除器经常从 unique_resource 的析构函数中被调用.

与 std::unique_ptr 一样, unique_resource 不可拷贝, 并支持许多其他操作, 例如语义相近的移动构造与赋值、reset、release 和 swap. 某些操作对资源和删除器类型施加额外要求; 若不满足这些要求, 相应操作将不可用. 例如, 只有当资源类型和删除器类型都可交换且其中至少一个可无抛出交换时, 才支持 swap (最后一部分是为 强异常保证实现 swap 操作所必需的). 各操作的要求列于 unique_resource 类参考中.

提示

若资源类型可解引用 (即支持一元 operator*), unique_resource 还提供 operator* 和 operator->, 使其表现得更像智能指针.

让我们考虑一个用法示例. 此处我们需要比较两个文件的内容; 若文件内容相等, equal_files 返回 true, 否则返回 false.

// A deleter for POSIX-like file descriptors
struct fd_deleter
{
    void operator() (int fd) const noexcept
    {
        if (fd >= 0)
            close(fd);
    }
};

// Opens a file with the given filename for reading and returns wrapped file descriptor
boost::scope::unique_resource< int, fd_deleter > open_file(std::string const& filename)
{
    boost::scope::unique_resource< int, fd_deleter > file(open(filename.c_str(), O_RDONLY));
    if (file.get() < 0)
    {
        int err = errno;
        throw std::system_error(err, std::generic_category(), "Failed to open file " + filename);
    }

    return file;
}

// Reads contents of a file denoted by fd into buffer and returns the number of read bytes
std::size_t read_file(int fd, unsigned char* buf, std::size_t size)
{
    std::size_t total_read_size = 0;
    while (total_read_size < size)
    {
        ssize_t read_size = read(fd, buf + total_read_size, size - total_read_size);
        if (read_size < 0)
        {
            int err = errno;
            if (err == EINTR)
                continue;
            throw std::system_error(err, std::generic_category(), "Failed to write data");
        }

        if (read_size == 0)
        {
            // End of file
            break;
        }

        total_read_size += read_size;
    }

    return total_read_size;
}

// Compares contents of two files for equality
bool equal_files(std::string const& filename1, std::string const& filename2)
{
    // Create unique resource wrappers for files
    auto file1 = open_file(filename1.c_str());
    auto file2 = open_file(filename2.c_str());

    // Use them to read file contents
    constexpr std::size_t buf_size = 1024;
    unsigned char buf1[buf_size];
    unsigned char buf2[buf_size];
    while (true)
    {
        std::size_t size1 = read_file(file1.get(), buf1, buf_size);
        std::size_t size2 = read_file(file2.get(), buf2, buf_size);

        if (size1 != size2)
        {
            // File sizes are different
            return false;
        }

        if (std::memcmp(buf1, buf2, size1) != 0)
        {
            // File contents are different
            return false;
        }

        if (size1 < buf_size)
        {
            // Files have ended. At this point we know they have equal contents.
            break;
        }
    }

    return true;
}
注释

Windows 上通过 _open、_close、_read、_write 等非标准 API 支持 POSIX 风格的文件描述符. 通过简单重命名, 通常就能把对常规文件和文件描述符执行简单 IO 的程序移植到 Windows. 但此处及下文将使用标准 POSIX 术语.

此示例中有几点需要注意. 首先, fd_deleter 函数对象在把文件描述符传递给 close 之前检查其是否有效. 在这段代码中这是必要的, 因为我们无条件地将 unique_resource 对象初始化为 open 的返回值, 而该值可能是表示错误的 -1. 默认情况下, unique_resource 不区分有效 (即已分配) 资源值与无效 (即未分配) 资源值, 这意味着在它看来, 值 -1 是一个需要通过调用删除器释放的文件描述符. 因此, 删除器必须准备好处理未分配的资源值. 稍后将看到如何缓解此问题.

提示

除资源值之外, 还可以在 unique_resource 构造函数的第二个实参中指定删除器对象. 实际上, 若删除器不可默认构造或其默认构造函数可能抛出异常, 则第二个实参是必需的. 这样一旦资源或删除器的构造抛出异常, 才能对传入的资源值调用删除器. 这确保 unique_resource 初始化失败时资源不会泄漏.

其次, 在使用文件之前仍需检查打开文件是否成功. 由于本示例中的 unique_resource 总是以已分配状态构造, 我们必须检查文件描述符值是否为负. 若要访问资源值, 可以使用 get 这一 unique_resource 方法.

我们可以改进此示例, 让 unique_resource 的初始化自动检查文件描述符的有效性. 这只需要修改 fd_deleter 和 open_file, 其余代码保持不变.

// A deleter for POSIX-like file descriptors
struct fd_deleter
{
    void operator() (int fd) const noexcept
    {
        close(fd);
    }
};

// Opens a file with the given filename for reading and returns wrapped file descriptor
boost::scope::unique_resource< int, fd_deleter > open_file(std::string const& filename)
{
    auto file = boost::scope::make_unique_resource_checked(
        open(filename.c_str(), O_RDONLY)
        -1,
        fd_deleter());
    if (!file.allocated())
    {
        int err = errno;
        throw std::system_error(err, std::generic_category(), "Failed to open file " + filename);
    }

    return file;
}

此处, make_unique_resource_checked 辅助函数执行以下操作:

  1. 若资源值 (第一个实参, 即 open 调用的结果) 等于无效资源值 (第二个实参), 则创建并返回未分配的 unique_resource 对象.
  2. 否则, 创建并返回已分配的 unique_resource 对象, 封装 open 调用的结果.
  3. 在两种情况下, 第三个实参都用于初始化返回的 unique_resource 对象中的删除器.

注意, 若 open 失败并返回 -1, 则保证不会对该资源值调用删除器: make_unique_resource_checked 和 unique_resource 都不会调用, 即使 unique_resource 构造因异常失败也不会. 这使我们能够简化 fd_deleter, 移除对负 fd 值的检查.

提示

若支持 C++17, 可以使用 functor (来自 Boost.Core) 把 close 之类的原始函数封装成一个函数对象, 以便在 unique_resource 中指定为删除器. 例如, 上面示例中的 fd_deleter 可以替换为 boost::core::functor< close >.

此外, 由于返回的 unique_resource 对象现在能正确指示资源是否已分配, 我们可以使用 allocated 成员函数进行测试, 而不必检查资源值. 这使代码更具可读性.

注释

为避免与"unique_resource 对象在以资源值构造后总是已分配"这一点相混淆, 建议始终使用 make_unique_resource_checked 工厂函数, 或更推荐使用下一节所述的资源特征. 资源特征是首选方案, 因为它使 unique_resource 更高效且更不易出错.

资源特征

unique_resource 类模板还支持可选的第三个模板参数, 可用于指定资源特征类. 资源特征为 unique_resource 提供关于资源特性的额外知识, 从而支持更高效的实现. 当存在一个或多个被视为未分配的资源值 (即不标识需要释放的已分配资源的值) 时, 这很有用. 例如, 对指针资源类型, null 通常被视为未分配值; 对 POSIX 风格的文件描述符, 所有负值都是未分配值, 因为有效的文件描述符不可能为负.

若 Resource 是 unique_resource 模板参数中指定的资源类型, 那么在指定资源特征时, 资源特征必须是具有以下公有静态成员函数的类类型:

  • bool is_allocated(Resource const& r) noexcept - 必须返回 true (若资源值 r 是已分配资源值), 否则返回 false.
  • R make_default() noexcept - 必须返回一个值, 使得 std::is_constructible< Resource, R >::value && std::is_nothrow_assignable< Resource&, R >::value 为 true, 且构造 Resource (源为 R) 产生一个未分配资源值, 该值可用于初始化默认构造的 unique_resource 对象.

注意, 所列的所有成员函数都必须不抛出异常. 根据这些定义, 调用 is_allocated 且施于 make_default 所返回的值时, 必须始终返回 false.

当提供了符合要求的资源特征后, unique_resource 的行为发生如下变化:

  • unique_resource 将不再单独跟踪自己是否处于已分配状态, 而是通过对被封装的资源值使用 is_allocated 来判断. 特别是, 这意味着用资源值构造 unique_resource 或用资源值调用 reset 时, 若该资源值是未分配值, 现在可能产生处于未分配状态的封装.
  • 默认构造函数、无实参的 reset, 以及 unique_resource 的移动构造函数和移动赋值, 将使用 make_default 来初始化未分配封装中的资源值 (对移动操作而言, 初始化移动源中的资源值).

使用资源特征可以进一步改进上一节给出的示例. 同样, 我们主要关注 open_file 和 unique_resource 类型的用法, equal_files 实现的其余部分保持不变.

// A deleter for POSIX-like file descriptors
struct fd_deleter
{
    void operator() (int fd) const noexcept
    {
        close(fd);
    }
};

// Resource traits for POSIX-like file descriptors
struct fd_resource_traits
{
    static bool is_allocated(int fd) noexcept
    {
        return fd >= 0;
    }

    static int make_default() noexcept
    {
        // Return any unallocated resource value
        return -1;
    }
};

// A shorthand type alias for unique file descriptor wrappers
using unique_fd = boost::scope::unique_resource< int, fd_deleter, fd_resource_traits >;

// Opens a file with the given filename for reading and returns wrapped file descriptor
unique_fd open_file(std::string const& filename)
{
    unique_fd file(open(filename.c_str(), O_RDONLY));
    if (!file.allocated())
    {
        int err = errno;
        throw std::system_error(err, std::generic_category(), "Failed to open file " + filename);
    }

    return file;
}

在这段代码中, 我们不再需要在每次打开文件 (或以其他方式创建文件描述符) 时使用 make_unique_resource_checked, 因此不必重复无效文件描述符值或删除器: 这些信息由 fd_resource_traits 提供并方便地嵌入 unique_fd 类型中. 与之前一样, 若 open 失败并返回 -1, 构造出的 unique_resource 对象将处于未分配状态, 这意味着我们可以使用 allocated 访问器, 且只有 open 成功时才会调用删除器.

提示

上面示例中展示的 fd_deleter、fd_resource_traits 和 unique_fd 类型由本库在 boost/scope/fd_deleter.hpp、boost/scope/fd_resource_traits.hpp 和 boost/scope/unique_fd.hpp 头文件中开箱即用地提供. 注意, 本库提供的 fd_deleter 支持可能被中断并需要重启的 close 平台. 为简洁起见, 上面的示例省略了这一支持.

简化资源特征

注释

本节描述的组件要求 C++17 编译器支持 auto 非类型模板参数和折叠表达式.

当资源满足以下约束时, 本库提供 unallocated_resource 类模板, 可用于生成与 unique_resource 一起使用的资源特征:

  • C++ 允许将资源值指定为非类型模板参数. 满足此要求的确切类型集合取决于所用的 C++ 标准版本. 例如, 整数、枚举、指针和左值引用自 C++17 起受支持; C++20 增加了对类类型的支持. 注意, 资源值初始化表达式必须是常量表达式. 特别地, 对指针和引用而言, 这意味着资源值初始化表达式必须指代对象或函数, 或者 (对指针而言) 产生空指针.
  • 存在一个或多个可逐一列出的未分配资源值. 所有其他资源值都表示需要释放的已分配资源.
  • 这些未分配资源值之一被视为默认值.
  • 资源类型支持从默认值进行移动构造和赋值, 以及与未分配值的相等和不等比较, 且这些操作都不抛出异常.

满足上述要求后, 可以把未分配资源值指定为 unallocated_resource 的非类型模板参数来生成 unique_resource 的资源特征. 列出的第一个未分配值即为默认值.

例如, 让我们考虑 Windows 句柄 (handle) 的资源特征定义.

struct handle_traits
{
    //! Returns the default resource value
    static HANDLE make_default() noexcept
    {
        return INVALID_HANDLE_VALUE;
    }

    //! Tests if \a res is an allocated resource value
    static bool is_allocated(HANDLE res) noexcept
    {
        return res != INVALID_HANDLE_VALUE && res != (HANDLE)NULL;
    }
};

此处, INVALID_HANDLE_VALUE 是某些 Windows API 函数返回的特殊常量, 表示没有与句柄关联的已分配资源. 但其他函数 (例如 OpenProcess 或 OpenThread) 出错时返回 NULL 句柄, 因此我们还必须测试该值.

提示

好奇的读者可以参阅一篇文章, 其中描述了不同 Windows API 之间这种不一致的原因.

借助 unallocated_resource, 上面的资源特征可以简化为:

using handle_traits = boost::scope::unallocated_resource< INVALID_HANDLE_VALUE, (HANDLE)NULL >;
注释

鉴于 INVALID_HANDLE_VALUE 在 Windows SDK 中定义为 (HANDLE)-1, 且 HANDLE 实际上是指针类型, 在纯 C++ 中本不应能将该值指定为非类型模板参数, 因为该指针并未指代对象. 但 MSVC 将此代码作为扩展接受. 若使用其他编译器, 此情况下仍需实现类似 handle_traits 的正规资源特征.

我们还可以使用 functor 封装用于释放句柄的 CloseHandle Windows API 函数来定义资源删除器. 于是 unique_resource 的完整定义如下:

using unique_handle = boost::scope::unique_resource<
    HANDLE,
    boost::core::functor< CloseHandle >,
    boost::scope::unallocated_resource< INVALID_HANDLE_VALUE, (HANDLE)NULL >
>;

以下章节比较 unique_resource (由 C++ Extensions for Library Fundamentals TS 定义) 与本库.

资源特征

Boost.Scope 为资源特征支持一个额外的可选模板参数. 这使 unique_resource 能够感知资源的细节 (如未分配值和默认值), 有利于易用性和效率. 指定资源特征后, make_unique_resource_checked 工厂函数变得不再必要, 因为 unique_resource 自身就能在构造时判断资源是否已分配. 此外, 这使 unique_resource 无需额外存储一个标志来指示资源是否处于已分配状态以及是否需要在销毁时释放.

使用资源特征可能改变某些 unique_resource API 的含义, 这可以说是向好的变化. 考虑以下示例.

// POSIX file descriptor resource
std::experimental::unique_resource< int, int (*)(int) > fd(-1, &close);

由于此情况下的删除器必须在构造函数实参中指定 (因为默认构造函数会创建值初始化的函数指针, 它为 null 且不可调用), 用户可能倾向于为文件描述符指定 -1 并期望构造出的 unique_resource 处于未分配状态. 这一假设是错误的, 因为此构造函数总是创建已分配的 unique_resource, 这意味着它会在销毁时调用 close(-1). 此情况下构造 fd 的正确方法是使用 make_unique_resource_checked, 如下:

std::experimental::unique_resource< int, int (*)(int) > fd = std::experimental::make_unique_resource_checked(-1, -1, &close);

或者, 可以调用 release, 时间点紧随 unique_resource 的构造之后. 但应注意, 只有在已知 unique_resource 构造不会抛出异常时, 这种做法才有效.

std::experimental::unique_resource< int, int (*)(int) > fd(-1, &close);
fd.release(); // mark the resource unallocated

reset 成员函数存在类似问题.

fd.reset(-1);

与预期相反, 此调用不会使 fd 处于未分配状态, 还会导致 close(-1) 在 fd 销毁时被调用. 正确的做法是调用无参数的 reset 或使用 make_unique_resource_checked.

fd.reset();
// or:
fd = std::experimental::make_unique_resource_checked(-1, -1, &close);
注释

看起来对 reset(-1) 的调用可能是实际中不会发生的人为示例. 但人们常常想直接把另一个调用与 reset 组合 (例如 fd.reset(open(...))) 并期望正确工作. 然而, 由于 open 出错时可能返回 -1, 我们将遇到上述问题.

指定资源特征会改变上述示例的含义. 无论构造函数还是对未分配资源值调用 reset, 都会产生处于未分配状态的 unique_resource 对象.

boost::scope::unique_resource< int, int (*)(int), boost::scope::fd_resource_traits > fd(-1, &close);
assert(!fd.allocated());

fd.reset(-1);
assert(!fd.allocated());
提示

fd_resource_traits 由 Boost.Scope 提供.

资源特征的另一个好处是默认资源值可以不同于值构造的值. 当资源类型不可默认构造 (例如是引用类型) 或值构造的资源不是未分配值时, 这很有用. 例如, fd_resource_traits 将 -1 指定为 POSIX 文件描述符的默认值, 因为值 0 是有效的已分配文件描述符.

Library Fundamentals TS 中没有此特性的直接对应物, 不过如上所示, make_unique_resource_checked 和 release 可用于在某些情况下绕过该限制.

构造函数差异

与 Library Fundamentals TS 不同, 对于 unique_resource 模板参数中指定的删除器, Boost.Scope 不认为函数指针可默认构造. 例如:

std::experimental::unique_resource< int, int (*)(int) > fd1; // compiles, creates unusable unique_resource object
boost::scope::unique_resource< int, int (*)(int) > fd2; // fails to compile, unique_resource is not default-constructible

这是因为默认构造或值构造的函数指针不可调用: 前者是垃圾值, 后者是空指针. unique_resource 没有提供在构造后修改删除器的途径 (移动赋值另一个 unique_resource 对象除外), 这意味着默认构造的 unique_resource 对象将不可用, 并可能在 reset 或销毁时引发未定义行为.

当删除器确实可默认构造且默认构造函数不抛出异常时, Boost.Scope 允许在构造函数实参中省略删除器, 而 TS 要求同时指定资源值和删除器.

std::experimental::unique_resource< int, boost::scope::fd_deleter > fd1(10); // fails to compile, deleter is missing in constructor arguments
boost::scope::unique_resource< int, boost::scope::fd_deleter > fd2(10); // ok, default-constructs fd_deleter
提示

fd_deleter 由 Boost.Scope 提供.

注释

要求删除器默认构造不抛出异常, 是为了确保 unique_resource 构造因异常失败时, 仍能对资源调用删除器. 这防止在资源构造抛出异常或删除器构造函数抛出异常时泄漏资源.

当必须指定删除器时, Boost.Scope 允许在 unique_resource 构造函数实参中省略资源值. 此情况下 default_resource 关键字可用作资源值的占位符:

// Creates an unallocated unique_resource with the specified deleter
boost::scope::unique_resource< int, int (*)(int) > fd(boost::scope::default_resource, &close);

注意, 在上面的示例中, 即使资源值被值初始化 (即零), fd 也处于未分配状态, 销毁时不会调用删除器. default_resource 也可与资源特征配合使用:

boost::scope::unique_resource< int, int (*)(int), boost::scope::fd_resource_traits > fd(boost::scope::default_resource, &close);

在上述情况下, fd 对象将使用资源特征指定的默认值 (fd_resource_traits 情况下即 -1) 来初始化其存储的资源对象. 同样, fd 对象在构造后处于未分配状态.

Library Fundamentals TS 规定, 若资源可无抛出移动构造而删除器不可, 且删除器的拷贝构造函数抛出异常, 则 unique_resource 的移动构造函数必须释放资源. 这是 unique_resource 处于半构造状态的情况: 资源已被移入正在构造的对象 (即不再存储于源对象中), 但删除器拷贝构造失败 (即它只存在于源对象中). TS 所述行为确保资源不会泄漏, 但发生异常时会使源 unique_resource 处于未分配状态, 这意味着移动构造函数只维持基本异常保证. Boost.Scope 在此情况下让源 unique_resource 保持其原有状态, 这同样保证资源不会泄漏, 但提供强异常保证.

检查资源是否已分配

Library Fundamentals TS 有一个明显疏漏: unique_resource 没有提供测试资源是否处于已分配状态的方法. Boost.Scope 通过提供 allocated() 方法以及到 bool 的语境转换弥补了这一点.

boost::scope::unique_resource< int, int (*)(int), boost::scope::fd_resource_traits > fd(-1, &close);
assert(!fd.allocated());
assert(!fd);

fd.reset(10);
assert(fd.allocated());
assert(!!fd);
注释

到 bool 的语境转换 (位于 unique_resource 中) 不测试资源值, 只测试资源是否已分配. 这与其他组件 (例如 std::optional) 一致.

对交换的原生支持

Library Fundamentals TS 将 unique_resource 定义为可移动构造且可移动赋值的类型, 并通过这一属性支持标准 std::swap 算法. 但这种做法有两个问题:

  • 它阻碍了针对资源和删除器类型特化的交换算法的使用. 即使 swap 有特化, 使用的仍是涉及移动或拷贝资源与删除器对象的通用算法.
  • 通用的 swap 实现只提供基本异常保证. 该算法移动构造其中一个源对象的副本, 然后执行两次移动赋值. 若任一赋值失败, 其中一个 unique_resource 对象将处于未分配状态. 还值得注意的是, TS 将 unique_resource 的移动构造函数定义为潜在破坏性的. 若资源类型的移动构造函数不抛出异常而删除器拷贝构造函数抛出异常, 将对移动构造出的资源对象调用删除器以免泄漏. 在 std::swap 的语境下, 这意味着即使移动构造失败, 源对象也会被置为未分配状态而非保持不变.

Boost.Scope 以成员函数和非成员函数 swap 的形式原生支持交换. 若资源类型或删除器类型中至少一个支持无抛出交换 (默认或特化算法), 则支持交换并提供强异常保证. 若资源和删除器类型都支持无抛出交换, unique_resource 交换操作不抛出异常.

boost::scope::unique_resource< int, boost::scope::fd_deleter, boost::scope::fd_resource_traits > fd1, fd2;
fd1.swap(fd2);
swap(fd1, fd2); // found via ADL

更广泛的解引用支持

Library Fundamentals TS 的 unique_resource 仅对指针资源类型支持 operator*() 和 operator->(). Boost.Scope 将此支持扩展到任何支持解引用的资源类型.

// Resource object type
struct my_object
{
    void foo();
};

// Manager for my_object instances
class my_object_manager
{
private:
    // List of allocated objects
    using my_object_list = std::list< my_object >;

    // Resource handle that refers to a my_object element in the list
    class my_handle
    {
    private:
        my_object_list* m_list;
        my_object_list::iterator m_it;

    public:
        my_handle() noexcept : m_list(nullptr), m_it() {}
        explicit my_handle(my_object_list& list, my_object_list::iterator it) noexcept :
            m_list(&list), m_it(it)
        {
        }

        my_object_list::iterator operator-> () const noexcept  
        {
            return m_it;
        }

        my_object& operator* () const noexcept
        {
            return *m_it;
        }

        my_object_list* get_list() const noexcept
        {
            return m_list;
        }

        my_object_list::iterator get_iterator() const noexcept
        {
            return m_it;
        }
    };

    // Resource deleter
    struct my_handle_deleter
    {
        void operator() (my_handle const& res) const noexcept
        {
            res.get_list()->erase(res.get_iterator());
        }
    };

    // Resource traits
    struct my_handle_traits
    {
        static my_handle make_default() noexcept
        {
            return my_handle();
        }

        static bool is_allocated(my_handle const& res) noexcept
        {
            return res.get_list() != nullptr && res.get_iterator() != res.get_list()->end();
        }
    };

public:
    // Unique resource wrapper for my_object instances
    using my_object_handle = boost::scope::unique_resource< my_handle, my_handle_deleter, my_handle_traits >;

private:
    my_object_list m_objects;

public:
    // Allocates a new object and returns a handle to it
    my_object_handle allocate_object()
    {
        return my_object_handle(my_handle(m_objects, m_objects.insert(m_objects.end(), my_object())));
    }
};

void allocate_and_use_object(my_object_manager& mgr)
{
    my_object_manager::my_object_handle handle = mgr.allocate_object();
    if (handle)
        handle->foo(); // invokes my_object::foo on the allocated object
}

该运算符依赖 operator-> 链式调用.

在上面的示例中, 我们使用 unique_resource 引用由 my_object_manager 创建和维护的对象. my_handle 类是资源类型, 支持访问 my_object 成员, 途径是 operator-> 和 operator*. 这使得 operator-> 和 operator* 在 unique_resource 中成为可能, 从而允许使用 unique_resource 的代码访问 my_object 成员.

使用 Library Fundamentals TS 的 unique_resource 时, 可以通过 unique_resource::get 访问器访问存储的资源对象并对其解引用来模拟这一功能.
