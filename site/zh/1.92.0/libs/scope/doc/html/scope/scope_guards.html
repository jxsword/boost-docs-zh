作用域守护是一种在销毁时调用任意 动作 函数对象的对象. 作用域守护适用于实现在控制流离开执行作用域时 (例如从函数返回时) 需要可靠执行的动作, 这对处理异常尤其有帮助.

被封装的动作函数对象在作用域守护构造时指定, 之后不能更改. 其类型必须是以下之一:

  • 具有公有且无参的 operator() 的用户自定义类; 或
  • 指向该类的左值引用; 或
  • 指向无参函数的左值引用或指针.

注意, 若被封装的函数是对某个函数对象的引用, 该对象必须存储在作用域守护之外, 并在作用域守护的整个生命周期内保持有效.

某些作用域守护还支持指定额外的 条件 函数对象, 用于自定义必须调用动作函数对象的条件. 条件函数对象将在后续章节中详细讨论.

在上表中, "失败"一词含义宽泛. 在给定上下文中什么构成失败, 由用户以条件函数对象的形式指定. 最常见的是将抛出的异常视为失败的标志, 但也可以改为例如检查外围函数返回的错误码.

对于 scope_exit, 不存在"成功"或"失败"的概念. 只要条件返回 true, 作用域守护就会调用动作函数对象. 默认情况下, 若用户未指定条件函数对象, 作用域守护如同条件始终返回 true 一样运行, 这意味着无论控制流是正常离开作用域还是因异常离开, 它都会调用动作.

尽管可以指定任意条件函数对象, scope_success 的预期用例是在作用域正常退出时 (即非因失败) 调用其动作, 而 scope_fail 的预期用例是调用其动作处理错误 (包括异常). 因此, 与 scope_fail 一起使用的动作函数通常不允许抛出异常, 否则可能导致程序终止. 这也是 scope_exit 和 defer_guard 等其他作用域守护需要关注的问题, 它们同样可能因异常而调用其动作. 用户有责任确保在另一个异常正在传播时作用域守护的动作不抛出异常. 一般建议使用作用域守护实现不会抛出异常的动作, 并将所有可能失败的操作移入正常代码流程.

条件作用域守护: scope_exit, scope_success 与 scope_fail 

#include <boost/scope/scope_exit.hpp>
#include <boost/scope/scope_success.hpp>
#include <boost/scope/scope_fail.hpp>

scope_exit、scope_success 与 scope_fail 作用域守护在接口和能力上有诸多相似之处, 区别在于调用动作函数对象的条件. 如上表所示, 这些作用域守护支持指定额外的条件函数对象. 默认情况下, scope_success 在正常销毁时调用其动作, scope_fail 在因抛出异常而销毁时调用其动作, 而 scope_exit 默认如同条件始终允许执行动作一样运行.

提示

条件函数对象将在下一节中详细讨论. 注意, 检测是否已抛出异常存在一些注意事项, 也将在下一节讨论.

由于默认条件函数对象不同, 不同的作用域守护类型通常适用于不同目的:

  • scope_exit 适用于一般清理任务, 无论外围函数成功或失败都需要执行.
  • scope_success 可用于在函数成功完成时需要执行的常见收尾代码.
  • scope_fail 用于处理错误, 例如将未完成的操作回退到前一个有效状态.

当存在多个返回点 (包括正常返回和异常返回) 且作用域守护动作不易提取为函数时, 所有作用域守护都特别有用.

让我们考虑一个示例类: 它接收网络请求, 验证请求并将其传递给与每个请求对应的会话对象. 接收到请求后, 该类必须发送响应: 要么是包含请求处理结果的成功响应, 要么是错误.

// A network request receiver
class receiver
{
    // A network connection
    connection m_conn;
    // A collection of sessions, searchable by session id
    std::map< std::string, session > m_sessions;

public:
    // Processes a network request and sends a response
    void process_request(request const& req)
    {
        const auto start_time = std::chrono::steady_clock::now();
        boost::scope::scope_exit time_guard([start_time]
        {
            // Log the amount of time it took to process the request
            const auto finish_time = std::chrono::steady_clock::now();

            std::clog << "Request processed in "
                << std::chrono::duration_cast< std::chrono::milliseconds >(finish_time - start_time).count()
                << " ms" << std::endl;
        });

        response resp;

        boost::scope::scope_fail failure_guard([&]
        {
            // Disconnect in case of exceptions
            m_conn.disconnect(); // doesn't throw
        });

        boost::scope::scope_success success_guard([&]
        {
            // Send a response that was populated while processing the request
            m_conn.send_message(resp);
        });

        // Validate the request and populate the response based on the contents of the request
        if (req.start_line().version > max_supported_version)
        {
            resp.start_line().version = max_supported_version;
            resp.start_line().set_status(protocol_version_not_supported);
            return;
        }

        resp.start_line().version = req.start_line().version;

        auto it_cseq = req.headers().find(cseq_header);
        if (it_cseq == req.headers().end())
        {
            resp.start_line().set_status(bad_request);
            resp.set_body(mime::text_plain, "CSeq not specified");
            return;
        }

        resp.headers().add(cseq_header, *it_cseq);

        auto it_session_id = req.headers().find(session_id_header);
        if (it_session_id == req.headers().end())
        {
            resp.start_line().set_status(bad_request);
            resp.set_body(mime::text_plain, "Session id not specified");
            return;
        }

        resp.headers().add(session_id_header, *it_session_id);

        // Find the session to forward the request to
        auto it_session = m_sessions.find(*it_session_id);
        if (it_session == m_sessions.end())
        {
            resp.start_line().set_status(session_not_found);
            return;
        }

        // Process the request in the session and complete populating the response
        it_session->second.process_request(req, resp);
    }
};

在上面的示例中, 无论 process_request 方法从何处返回, 各作用域守护都会自动执行各自的动作. success_guard 确保发送响应, 无论它是在目标会话对象中处理请求后的成功响应, 还是某个错误响应. failure_guard 处理处理过程因异常失败的情况, 并在这种情况下终止连接. 注意, 由于 failure_guard 在 success_guard 之后销毁, 它还覆盖发送响应期间可能发生的错误. 最后, time_guard 记录处理请求所耗时间 (无论成功还是异常), 以便诊断.

本节描述的每个作用域守护都支持活动和非活动状态. 只有在销毁时处于活动状态, 动作函数对象才会被调用. 默认情况下, 作用域守护以活动状态创建, 但可以通过将 false 作为构造函数的最后一个实参来改变. 在生命周期内也可以调用 set_active 方法来停用或激活作用域守护. 停用作用域守护常用作"提交"作用域守护创建与停用之间代码块效果的手段. 若需要在知道是否要执行作用域守护动作之前就创建守护 (例如守护需要创建在外层作用域, 而是否启用的决定在后面做出), 手动激活作用域守护有时会很有用.

class collection
{
    std::map< int, object > objects;

public:
    // Finds an existing object by key or creates a new one and returns a reference to it
    object& obtain_object(int key)
    {
        // Find the object or the position where it should be
        auto it = objects.lower_bound(key);

        // Create an inactive scope guard initially. Needs to be created
        // at this scope to cover the on_requested() call below.
        boost::scope::scope_fail rollback_guard{[&]
        {
            // Remove the object that was just inserted
            objects.erase(it);
        },
        false};

        if (it == objects.end() || it->first != key)
        {
            // Insert a new object that correspond to the specified key
            it = objects.emplace_hint(it, key, object{});

            // Activate rollback guard to revert the insertion in case of error
            rollback_guard.set_active(true);

            // Initialize the inserted object. May throw.
            it->second.initialize(*this, key);
        }

        // Notify the object that is has been requested. May throw.
        it->second.on_requested();

        return it->second;
    }
};

上面的代码示例依赖 C++17 类模板实参推导 (CTAD), 让作用域守护类型推导函数对象类型 (即 lambda). 若该特性不可用, 可以改用工厂函数重写作用域守护的构造, 如下:

auto rollback_guard = boost::scope::make_scope_fail([&]
{
    objects.erase(it);
},
false);

本节描述的三个作用域守护各自都提供了工厂函数, 且兼容 C++11. 工厂函数命名为 make_<scope_guard>, 接受与相应作用域守护构造函数相同的实参.

本节描述的作用域守护可移动构造 (但不可赋值), 这要求被封装的函数对象也可移动构造或拷贝构造. 移动之后, 被移出的作用域守护变为非活动状态. 若被移出的作用域守护在销毁时仍处于活动状态, 则行为未定义.

作用域守护条件函数 

#include <boost/scope/exception_checker.hpp>
#include <boost/scope/error_code_checker.hpp>

如前所述, scope_exit、scope_success 与 scope_fail 支持指定额外的条件函数对象, 该对象将被调用以决定作用域守护是否应调用动作. 条件函数对象必须满足以下要求:

  • 条件函数对象的类型必须是以下之一:
    • 具有公有且无参的 operator() 的用户自定义类; 或
    • 指向该类的左值引用; 或
    • 指向无参函数的左值引用或指针;
  • 调用条件函数对象必须返回可按语境转换为 bool 的值; 且
  • 调用条件函数对象不得抛出异常.

对这三个作用域守护而言, 条件函数对象都是可选的. 若未指定, scope_exit 如同条件函数对象始终返回 true 一样运行, 只要作用域守护处于活动状态就会调用其动作函数对象. 否则, 作用域守护仅在条件返回 true 时才调用其动作.

对 scope_success 和 scope_fail 而言, 默认使用 exception_checker 条件函数. 它在构造时 (即作用域守护构造之时) 捕获未捕获异常的数量, 然后在其被调用时 (即作用域守护销毁之时) 将捕获的值与未捕获异常的数量进行比较. 若数量增加, 则视为有新异常正在传播, 谓词返回 true; 否则谓词返回 false.

注释

按照设计, exception_checker 针对在栈上创建作用域守护的特定用例. 它与 C++20 协程及类似设施 (如纤程和用户态上下文切换) 不兼容: 在这些场景中, 执行线程可能在谓词捕获未捕获异常数量之后被挂起, 然后在未捕获异常数量已发生变化的其他上下文中恢复. 类似地, 它也与以下使用模式不兼容: 谓词在构造后被缓存, 并在线程离开构造谓词的作用域之后才被调用 (例如谓词或相关作用域守护被存储为类的数据成员或命名空间作用域变量).

scope_success 在条件返回 false 时 (即未检测到失败时) 调用其动作, 而 scope_fail 在条件返回 true 时 (即检测到失败时) 调用其动作. 就这两种作用域守护类型而言, 条件函数对象有时被称为失败条件, 因为它指示是否发生了失败.

你可能注意到, 就条件函数对象的使用方式而言, scope_exit (带有用户指定的条件函数对象) 的行为与 scope_fail 相似, 而与 scope_success 相反. 主要区别在于语义: scope_exit 没有成功/失败的含义, 可与任意条件函数一起使用; 而 scope_success 和 scope_fail 通常对应各自预期的用例, 默认条件函数使它们等效于 <experimental/scope> 中定义的作用域守护.

可以使用 scope_exit 来模拟本节描述的每个作用域守护: 或使用自定义条件函数对象, 或将条件函数嵌入动作函数, 或在构造后激活/停用作用域守护. 例如, 以下四段代码具有相同效果:

在此示例中使用 scope_fail 的主要好处是减少代码规模与复杂度. 可以看到, 在作用域守护动作中加入对未捕获异常数量的检查使其明显更冗长, 且若需要在多个作用域守护中执行此类检查, 这段代码不得不重复. 显式停用作用域守护也有缺点: 若必须在代码的多处执行 (例如存在多个返回点且事务需要在每处提交), 则容易出错. 这违背了作用域守护的初衷, 即自动正确执行其动作, 而无需用户在每个可能的离开作用域之处手动确保这一点.

scope_fail 的另一个好处是提升代码可读性. 对读者而言, scope_fail 立即表明这是错误处理器, 而 scope_exit 没有这种含义, 可能只是一般清理代码.

话虽如此, 仍可能有理由使用上面演示的某种技术来代替 scope_success/scope_fail, 尤其是与 exception_checker 配合使用时. 如上所述, exception_checker 与协程及类似设施不兼容, 因此使用手动管理的 scope_exit 可能是一种解决方案. 另一个考虑因素是性能, 特别是与 exception_checker 相关时. 该谓词必须调用运行时函数来获取未捕获异常的数量, 且必须执行两次: 作用域守护构造和销毁时各一次. 尽管这些函数通常开销很小, 但即使没有抛出异常, 这些调用通常也不会被编译器优化掉, 而停用作用域守护的开销更小. 因此, 若作用域守护用于其性能开销可能显著的紧凑循环中, 优先选择带手动停用的 scope_exit 可能是合理的选择.

scope_exit、scope_success 与 scope_fail 接受条件函数对象作为构造函数或工厂函数的第二个实参, 位于动作函数对象之后. 若条件函数对象可默认构造且默认构造函数不抛出异常, 则可在作用域守护构造函数实参中省略该函数对象.

// Writes a string to a file using a file descriptor, with file locking.
// Reports errors via an error_code parameter.
void locked_write_string(int fd, std::string const& str, std::error_code& ec)
{
    int err = 0;

    // Automatically transform errors to error_code on exit
    boost::scope::scope_fail fail_guard
    {
        // Action function object
        [&] { ec = std::error_code(err, std::generic_category()); },
        // Condition function object
        [&err]() noexcept { return err != 0; }
    };

    // Performs a lock operation on the file descriptor, returns error code or 0 on success
    auto lock_operation = [fd](int operation)
    {
        while (flock(fd, operation) < 0)
        {
            int err = errno;
            if (err != EINTR)
                return err;
        }

        return 0;
    };

    // Lock the file
    err = lock_operation(LOCK_EX);
    if (err != 0)
        return;

    // Unlock the file on exit
    BOOST_SCOPE_DEFER [&] { lock_operation(LOCK_UN); };

    // Write data
    const char* p = str.data();
    std::size_t size_left = str.size();
    while (size_left > 0)
    {
        ssize_t written = write(fd, p, size_left);
        if (written < 0)
        {
            err = errno;
            if (err == EINTR)
            {
                err = 0; // we do not want to report EINTR to the caller
                continue;
            }
            return;
        }

        p += written;
        size_left -= written;
    }
}

除 exception_checker 外, 本库还提供可用作条件函数对象的 error_code_checker. 构造时, error_code_checker 捕获对外部错误码对象的引用, 并在被调用时检查其是否指示错误. 这意味着错误码对象必须在 error_code_checker 谓词的整个生命周期内保持有效.

对象 ec 可用作错误码对象, 若:

  • 表达式 !ec 有效, 绝不抛出异常, 且返回可按语境转换为 bool 的值; 且
  • 表达式 !ec 在无错误时产生可按语境转换为 true 的值, 否则产生 false.

也就是说, 对于错误码对象 ec, 调用 error_code_checker 的结果等同于 !!ec. 这使 error_code_checker 能够兼容多种错误码类型, 包括:

  • std::error_code 或 boost::system::error_code (来自 Boost.System),
  • std::expected、boost::outcome_v2::basic_outcome 或 boost::outcome_v2::basic_result (来自 Boost.Outcome),
  • int, 其中值 0 表示无错误,
  • bool, 其中值 false 表示无错误,
  • T*, 其中空指针表示无错误.

对于 C++11 编译器, 本库还提供工厂函数 check_error_code. 例如, 前面的示例可以这样使用该条件函数对象:

// Writes a string to a file using a file descriptor, with file locking.
// Reports errors via an error_code parameter.

    {
        // Action function object

        // Condition function object
        boost::scope::check_error_code(err)
    };

    // ...
}

无条件作用域守护: defer_guard 

#include <boost/scope/defer.hpp>

在调用动作函数的时机方面, defer_guard 作用域守护类似于不带用户指定条件函数对象的 scope_exit. 但它不支持自定义条件函数, 也缺乏可移动性及激活/停用支持: 该作用域守护在构造后始终处于活动状态. 在不需要这些特性时, 这允许更高效的实现.

注释

defer_guard 是 scope_exit 的更轻量版本, 类似于 std::lock_guard 之于 std::unique_lock 的关系.

由于 defer_guard 在构造之后实际上没有可供交互的接口, 它更适合匿名的"设置后即忘"类作用域守护. 为强调这一亲和性, 本库提供 BOOST_SCOPE_DEFER 宏, 它如同一个关键字, 用于定义具有唯一名称的 defer_guard 对象. 该宏之后应跟随在作用域退出时调用的函数对象.

BOOST_SCOPE_DEFER []
{
    std::cout << "Hello world!" << std::endl;
};
注释

BOOST_SCOPE_DEFER 要求支持 C++17 CTAD. defer_guard 类本身兼容 C++11, 但鉴于它没有工厂函数, 因此非常希望有 C++17 支持.

如你所见, 相比其他作用域守护声明方式, BOOST_SCOPE_DEFER 提供了一些语法改进:

  • 声明不为作用域守护变量命名, 这意味着无需费心取名, 也不会意外遗漏名称或与其他变量冲突.
  • 声明通常键入更短, 也更容易辨认.
  • 函数对象周围没有额外的圆括号或花括号.

但应注意, BOOST_SCOPE_DEFER 宏的使用完全是可选的. 用户可以自由地直接使用 defer_guard.

boost::scope::defer_guard guard{[]
{
    std::cout << "Hello world!" << std::endl;
}};

按引用捕获的注意事项

使用作用域守护时, 用户应确保所有按引用捕获的变量在作用域守护销毁时仍处于有效状态. 这尤其适用于默认按引用捕获变量的 lambda 函数 (即捕获子句以 & 开头的情况). 考虑以下示例:

void bad(std::unique_ptr< int > ptr)
{
    assert(ptr != nullptr);

    boost::scope::scope_exit guard{[&]
    {
        std::cout << "processed: " << *ptr << std::endl;
    }};

    process(std::move(ptr)); // may consume ptr, leaving it null for the scope guard action
}

或者一个不太明显的变体, 涉及返回值的隐式移动:

std::unique_ptr< int > bad(std::unique_ptr< int > ptr)
{
    assert(ptr != nullptr);

    boost::scope::scope_exit guard{[&]
    {
        std::cout << "processed: " << *ptr << std::endl;
    }};

    process(*ptr);

    return ptr; // moves from ptr, leaving it null for the scope guard action
}

在这种情况下, 可考虑在函数对象中按值捕获, 或将作用域守护移到更深层的作用域, 使其在按引用捕获的变量失效之前执行其动作.

std::unique_ptr< int > good(std::unique_ptr< int > ptr)
{
    assert(ptr != nullptr);

    {
        boost::scope::scope_exit guard{[&]
        {
            std::cout << "processed: " << *ptr << std::endl;
        }};

        process(*ptr);
    } // <- scope guard action runs here, before ptr is moved-from

    return ptr;
}

在运行期设置作用域退出动作

可以使用作用域守护类来实现运行期初始化的作用域退出动作. 一种方法是使用函数对象封装器 (如 std::function) 配合作用域守护来安排函数调用. 例如:

using cleanup_func_t = std::function< void() >;
cleanup_func_t cleanup_func;
// Create an inactive scope guard first, since the cleanup function is not set yet
boost::scope::scope_exit< cleanup_func_t& > cleanup(cleanup_func, false);

// Later in the program, initialize the cleanup function with the function selected at run time
if (cond)
{
    cleanup_func = []
    {
        std::cout << "cond is true" << std::endl;
    };
}
else
{
    cleanup_func = []
    {
        std::cout << "cond is false" << std::endl;
    };
}

// Activate the scope guard once the cleanup function is initialized
cleanup.set_active(true);

也可以用 BOOST_SCOPE_DEFER 来做到这一点, 尽管这会失去该宏的优点之一 (即无需费心取名). 另请注意, 一旦构造了作用域守护, 函数封装器就必须始终有效.

// Create a non-empty function wrapper that does nothing
std::function< void() > cleanup_func = [] {};
// Create a scope guard that refers to the function wrapper
BOOST_SCOPE_DEFER std::ref(cleanup_func);

// Later in the program, initialize the function wrapper
if (cond)
{
    cleanup_func = []
    {
        std::cout << "cond is true" << std::endl;
    };
}
else
{
    cleanup_func = []
    {
        std::cout << "cond is false" << std::endl;
    };
}

但用户应注意, 函数封装器通常在内部使用动态内存分配并拷贝函数对象数据, 这可能涉及调用拷贝构造函数, 而后者也可能因异常而失败. 尽管许多标准库实现对 std::function 使用小对象优化, 且 Boost.Function 等其他实现也采用此技术, 但通常无法保证用给定函数对象初始化函数封装器不会抛出异常. 因此, 通常不建议使用 std::function 及类似封装器.

若设置作用域退出动作需要是无抛出操作 (例如作用域守护要回退紧邻的前一个操作的效果), 建议预先初始化非活动的作用域守护, 并在程序稍后的时刻只激活其中一个.

// Create inactive scope guards for both branches
boost::scope::scope_exit cleanup_true([]
{
    std::cout << "cond is true" << std::endl;
},
false);
boost::scope::scope_exit cleanup_false([]
{
    std::cout << "cond is false" << std::endl;
},
false);

// Later in the program, activate one of the scope guards.
// This won't throw.
if (cond)
    cleanup_true.set_active(true);
else
    cleanup_false.set_active(true);

或者, 也可以在作用域守护动作自身内实现选择.

// Create a single inactive scope guard that implements both branches
bool cond;
boost::scope::scope_exit cleanup([&cond]
{
    if (cond)
        std::cout << "cond is true" << std::endl;
    else
        std::cout << "cond is false" << std::endl;
},
false);

// Later in the program, select the branch to perform
// and activate the scope guard.
cond = select_branch();
cleanup.set_active(true);

在上表中你可能注意到, Boost.ScopeExit 与 Boost.Scope 之间相当多的特性对等是通过在前者中使用 BOOST_SCOPE_EXIT_ALL 宏实现的. 该宏内部使用 C++11 lambda 函数实现, 这解释了这种情况下两库的诸多相似之处. 用户也可以定义 BOOST_SCOPE_EXIT_CONFIG_USE_LAMBDAS, 强制其他 Boost.ScopeExit 宏在内部使用 C++11 lambda, 这将相应改变语法和变量捕获规则. 但在此模式下使用该库 (或在任何模式下使用 BOOST_SCOPE_EXIT_ALL 宏) 时, 有几点注意事项需要牢记:

  • 由于依赖 C++11 lambda 函数, 它在 C++03 模式下不可用.
  • 使用 C++11 lambda 实现的 Boost.ScopeExit 作用域守护在内部将 lambda 函数存储于 boost::function 对象中. 这意味着创建作用域守护可能需要动态内存分配, 并可能因异常而失败. Boost.ScopeExit 未对此情况的行为作出文档说明, 但实际上, 截至 Boost 1.83.0, 此时作用域退出块不会被执行. 这意味着此模式下的 Boost.ScopeExit 不能在不抛出上下文中安全使用, 也无法保证作用域退出块的执行. 作用域守护的构造和执行也都存在性能开销.

相比之下, Boost.Scope 作用域守护不使用 boost::function 或 std::function 等函数对象封装器来存储函数对象. 这意味着作用域守护不执行动态内存分配 (除非函数对象自身执行), 也没有相关的异常安全问题与性能开销. 此外, 若作用域守护初始化因异常失败, 作用域守护仍会执行该动作.

C++ Extensions for Library Fundamentals TS 定义了三种作用域守护类型: scope_exit、scope_success 和 scope_fail, 它们与本库提供的同名作用域守护语义相近. 存在一些差异和扩展, 汇总如下.

条件函数

Boost.Scope 提供的 scope_exit、scope_success 和 scope_fail 三种作用域守护都支持可选的条件函数, 用于决定作用域守护是否应调用其封装的动作函数. TS 定义的作用域守护没有此特性, 三种作用域守护各自的行为都由规范预先定义.

Boost.Scope 作用域守护使用的默认条件函数使其行为与 TS 等效, 因此若用户不使用自定义条件函数, 两者中作用域守护的用法是等效的. 若使用自定义条件函数, 则可通过将条件函数嵌入 std::experimental::scope_exit 调用的动作中, 在 TS 作用域守护中模拟. 例如, 若用户代码在 scope_fail 中以错误码作为失败标志, 等效的 TS 代码可能如下:

表 1.5 使用自定义条件函数

Boost.Scope

Library Fundamentals TS 

std::error_code ec;
boost::scope::scope_fail guard
{
    [] { handle_error(); },
    boost::scope::check_error_code(ec)
};

std::error_code ec;

{
    [&ec]
    {
        if (ec)
            handle_error();
    }

注意在 TS 的情况下必须从 scope_fail 切换到 scope_exit.

作用域守护的灵活激活与停用

TS 定义的作用域守护总是以活动状态构造, 且只能通过调用 release() 方法停用. Boost.Scope 支持创建初始为非活动状态的作用域守护, 并可在创建后激活或停用. 这允许在用户代码中更灵活地放置作用域守护, 当是否执行作用域守护动作的决定需要在守护构造之后做出时非常有用.

该特性可在 TS 中通过额外状态来模拟, 由作用域守护动作检查该状态以确定是否需要执行动作.

表 1.6 显式激活作用域守护

Boost.Scope

Library Fundamentals TS 

// Insert value into both containers and call on_inserted() afterwards.
// pv may be null, in which case only insert the value into the set.
// Maintain both containers intact if an exception is thrown.
void insert_two(std::vector< int >* pv, std::set< int >& set, int value)
{
    // Initially inactive scope guard
    boost::scope::scope_fail pv_rollback([pv] { pv->pop_back(); }, false);
    if (pv)
    {
        pv->push_back(value); // may throw
        pv_rollback.set_active(true); // activate the scope guard
    }

    auto [it, inserted] = set.insert(value); // may throw
    // Initially active scope guard, if a new element was inserted, otherwise inactive
    boost::scope::scope_fail set_rollback([&set, &it] { set.erase(it); }, inserted);

    on_inserted(); // may throw
}

// Insert value into both containers and call on_inserted() afterwards.
// pv may be null, in which case only insert the value into the set.
// Maintain both containers intact if an exception is thrown.
void insert_two(std::vector< int >* pv, std::set< int >& set, int value)
{
    bool pv_inserted = false;
    // Initially active scope guard, but blocked by pv_inserted == false
    std::experimental::scope_exit pv_rollback([pv, &pv_inserted]
    {
        if (pv_inserted)
            pv->pop_back();
    });
    if (pv)
    {
        pv->push_back(value); // may throw
        pv_inserted = true; // unblock the scope guard
    }

    auto [it, inserted] = set.insert(value); // may throw
    // Initially active scope guard, which we immediately deactivate if no element was inserted
    std::experimental::scope_exit set_rollback([&set, &it] { set.erase(it); });
    if (!inserted)
        set_rollback.release();

    on_inserted(); // may throw
}

注意 Boost.Scope 守护不提供 release() 成员函数, 而是提供 set_active() (带 bool 实参), 其中 release() 等效于 set_active(false). 这允许对作用域守护既激活又停用. 当是否需要守护处于活动状态的指示以运行期值表达时, bool 实参比两个分开的激活/停用方法更方便. 例如, 上面对 set 的插入可以这样写:

std::set< int >::iterator it;
// Initially create an inactive scope guard to revert the insertion
boost::scope::scope_fail set_rollback([&set, &it] { set.erase(it); }, false);

// Try insering a new element into the set
bool inserted;
std::tie(it, inserted) = set.insert(value); // may throw

// Activate the scope guard only if the element was inserted
set_rollback.set_active(inserted);
注释

在 Boost.Scope 评审期间至少有一人指出, release() 在作用域守护语境中是个不佳的名称. 加之带 bool 实参的方法更灵活且提供相同功能, 这就是 Boost.Scope 不提供 release() 的原因.

除 set_active() 外, 还可以通过 active() 方法查询 Boost.Scope 作用域守护是否处于活动状态. 该特性在 TS 中没有对应物.

析构函数上放宽的 noexcept 规范

在 Library Fundamentals TS 中, 只有 scope_success 的动作允许抛出异常, 而 scope_fail 和 scope_exit 的析构函数被无条件标记为 noexcept. 由于 TS 不支持自定义条件函数, scope_fail 只能在异常正在展开栈时调用其动作, 因此从作用域守护动作中抛出异常会导致程序终止. 就 scope_exit 而言, 理由则不那么确定, 因为该作用域守护可能在无异常传播时调用其动作. 但因异常而调用动作的情况仍然可能发生, TS 采取了保守做法, 禁止动作抛出异常.

Boost.Scope 采取了不同做法. 由于三种作用域守护都支持自定义条件函数, 每一种都可能无论异常是否正在栈上传播都调用其动作. "失败"的概念不再等同于"异常", 因此即使对于带自定义失败条件的 scope_fail 作用域守护, 允许抛出异常也可能是合理的. 因此, 对 Boost.Scope 提供的所有作用域守护, 其析构函数被标记为 noexcept 的前提是其动作和条件函数都标记为 noexcept. 用户有责任确保当另一个异常正在传播时, 作用域守护的动作和条件不抛出异常. 用户甚至可以在需要时用 std::uncaught_exceptions 执行运行期检查. 若用户愿意为自己的作用域守护强制不抛出保证, 他可以通过将动作函数标记为 noexcept 来做到:

boost::scope::scope_exit guard([&]() noexcept { /* I promise I won't throw */ });

虽然这允许更多作用域守护抛出异常, 但当动作在异常传播期间抛出异常时, 行为并无不同. 无论作用域守护的析构函数是否标记为 noexcept, 在这种情况下程序都会终止.

该 Boost.Scope 特性无法用 TS 作用域守护模拟 (除非用例恰好符合 scope_success).
