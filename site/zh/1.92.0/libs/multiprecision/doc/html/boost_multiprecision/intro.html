引言

Multiprecision 库在 C++ 中提供 integer、rational、floating-point 与 complex 类型, 其取值范围与精度均超过 C++ 普通的 基本内建 类型. Multiprecision 中的大数类型可用于丰富的基础数学运算、初等超越函数以及 Boost.Math 中的函数. Multiprecision 类型还可依据明确定义的转换规则, 与 C++ 中任意 基本内建类型 互操作. 这使得 Boost.Multiprecision 可用于各类涉及需要扩展范围与精度的整数、有理数和浮点数类型的数学计算.

Multiprecision 由一个面向大数数学的通用接口以及一组大数后端组成, 支持整数、有理数、浮点数与复数类型. Boost.Multiprecision 提供了一批开箱即用的后端, 包括 GMP、MPFR、MPIR、MPC、TomMath 的接口, 以及自有的、采用 Boost 许可证的仅头文件整数、有理数与浮点数后端集合. 此外, 只要类实现满足必要的 concepts, 用户自定义后端也可以创建并配合 Multiprecision 的接口使用.

依据数值类型的不同, 精度可以是任意大 (仅受可用内存限制), 可以在编译期固定 (例如 50 或 100 位十进制数字), 也可以是由成员函数在运行期控制的变量. 这些类型启用了 expression templates, 因此比朴素的用户自定义类型具有更好的性能.

Multiprecision 库由两个截然不同的部分组成:

  • 一个启用了表达式模板的前端 number, 负责处理全部运算符重载、表达式求值优化以及代码精简.
  • 一组实现实际算术运算的后端, 它们只需满足前端精简后的接口要求.

前端与后端的分离使得在可能的情况下可以使用精良但许可证受限的库, 同时为必须拥有可移植、无约束许可证的用户提供采用 Boost 许可证的替代选择. 也就是说, 某些后端依赖第三方库, 但始终提供采用 Boost 许可证的仅头文件版本 (速度稍慢).

Boost.Multiprecision 入门

如果您只想'直奔主题', 以尽可能简单且可移植的方式获得更大的整数和/或更大、更精确的实数, 作为接近'即插即用'式的 基本内建类型 对应替代品, 那么请使用完全采用 Boost 许可证的数值类型, 并直接跳到以下一项或多项:

  • cpp_int 用于多精度整数,
  • cpp_rational 用于有理数类型,
  • cpp_bin_float 与 cpp_dec_float 用于多精度浮点数类型,
  • cpp_complex 用于复数类型.

本库最常通过某个预定义的便捷 typedef 别名使用, 例如 boost::multiprecision::int128_t 或 boost::multiprecision::cpp_bin_float_quad.

例如, 如果您想要一个有符号的、固定大小的 128 位整数:

#include <boost/multiprecision/cpp_int.hpp>  //  Integer types.

boost::multiprecision::int128_t my_128_bit_int;

或者, 更进一步, 如果您想要一个以 GMP 作为底层实现的 任意精度 整数类型, 那么可以使用:

#include <boost/multiprecision/gmp.hpp>  // Defines the wrappers around the GMP library's types

boost::multiprecision::mpz_int myint;    // Arbitrary precision integer type.

或者, 如果想要一个简单、可移植的 128 位浮点数, 其接近 基本内建类型 的即插即用替代品 (通常为 64 位), 例如 double 

#include <boost/multiprecision/cpp_bin_float.hpp>

boost::multiprecision::cpp_bin_float_quad my_quad_real;

另外, 通过将 number 与某个预定义的后端类型组合, 您可以构造出自己的'定制'多精度类型. 例如, 假设您想要一个基于 MPFR 库的 300 位十进制数字浮点数类型. 这种情况下, 并没有具备该精度的预定义 typedef, 因此我们自行组合一个:

#include <boost/multiprecision/mpfr.hpp>  // Defines the Backend type that wraps MPFR.

namespace mp = boost::multiprecision;     // Reduce the typing a bit later...

typedef mp::number<mp::mpfr_float_backend<300> >  my_float;

my_float a, b, c; // These variables have 300 decimal digits precision.

我们可以在禁用表达式模板的情况下 (编译期更快, 但运行期更慢) 重复上面的示例, 只需向 number 传入第二个模板参数:

#include <boost/multiprecision/mpfr.hpp>  // Defines the Backend type that wraps MPFR.

namespace mp = boost::multiprecision;     // Reduce the typing a bit later...

typedef mp::number<mp::mpfr_float_backend<300>, et_off>  my_float;

my_float a, b, c; // These variables have 300 decimal digits precision

我们还可以在不同类型之间混合算术运算, 只要存在从一个类型到另一个类型的无歧义隐式转换:

#include <boost/multiprecision/cpp_int.hpp>

namespace mp = boost::multiprecision;     // Reduce the typing a bit later...

mp::int128_t a(3), b(4);
mp::int512_t c(50), d;

d = c * a;   // OK, result of mixed arithmetic is an int512_t

转换同样是允许的:

d = a; // OK, widening conversion.
d = a * b;  // OK, can convert from an expression template too.

但本质上会丢失信息的转换要么被声明为 explicit, 要么被完全禁止:

d = 3.14;  // Error, implicit conversion from double not allowed.
d = static_cast<mp::int512_t>(3.14);  // OK, explicit construction is allowed

如果转换有歧义或为 explicit, 混合算术将会失败:

number<cpp_int_backend<>, et_off> a(2);
number<cpp_int_backend<>, et_on>  b(3);

b = a * b; // Error, implicit conversion could go either way.
b = a * 3.14; // Error, no operator overload if the conversion would be explicit.
移动语义

在支持右值引用的编译器上, 如果底层后端支持移动语义, 类 number 也支持移动语义.

此外, 非表达式模板的运算符重载 (见下文) 也支持移动, 并具有形如下式的重载:

template <class B>
number<B, et_off> operator + (number<B, et_off>&& a, const number<B, et_off>& b)
{
    return std::move(a += b);
}

这些运算符重载确保许多表达式可以在不实际生成任何临时对象的情况下求值. 但仍有许多简单表达式, 例如

a = b * c;

它们从移动支持中获益并不明显. 因此, 最优性能来自同时启用移动支持与表达式模板.

注意, 被移出的 (moved-from) 对象虽然处于合理状态, 但其值未指定, 且对其唯一允许的操作是销毁或赋以新值. 任何其他操作都应视为编程错误, 并且只要尝试任何其他操作, 我们的所有后端都会触发断言. 这种行为使移动构造获得最优性能 (即无需分配内存, 我们只是接管既有对象的内部状态), 同时保持其在标准库容器中的可用性.

表达式模板

类 number 是启用表达式模板的: 这意味着它没有形如下式的乘法运算符:

template <class Backend>
number<Backend> operator * (const number<Backend>& a, const number<Backend>& b)
{
   number<Backend> result(a);
   result *= b;
   return result;
}

相反, 该运算符更类似于:

template <class Backend>
unmentionable-type operator * (const number<Backend>& a, const number<Backend>& b);

其中 'unmentionable' 返回类型是一个实现细节: 它并不包含乘法的结果, 而是包含如何计算该结果的指令. 实际上, 它只是一对指向函数实参的引用, 加上一些记录该运算为何种运算的编译期信息.

这种方法的最大优势在于 消除临时对象: 例如, 上面 operator* 的'朴素'实现需要一个临时对象来计算结果, 还至少需要另一个来返回它. 诚然, 有时可以通过移动语义减少这种开销, 但无法将其完全消除. 例如, 假设我们用 Horner 法求多项式的值, 形如下式:

T a[7] = { /* some values */ };
//....
y = (((((a[6] * x + a[5]) * x + a[4]) * x + a[3]) * x + a[2]) * x + a[1]) * x + a[0];

如果类型 T 是某个 number, 那么该表达式的求值 不会创建任何临时值. 相反, 如果我们使用的是 mpfr_class 这一 C++ 封装 (针对 MPFR) - 那么该表达式将产生不少于 11 个临时对象 (即使 mpfr_class 确实使用了表达式模板来在一定程度上减少临时对象的数量). 如果我们改用更简单的 MPFR 封装, 例如 mpreal, 情况会更糟: 这个简单表达式将创建不少于 24 个临时对象 (注意 - 我们实际测量的是所执行的内存分配次数, 而非直接测量临时对象的数量; 另请注意, 随 GMP-5.1 或更高版本提供的 mpf_class 封装几乎将临时对象数量降至零). 注意, 如果我们在编译时禁用表达式模板并启用右值引用支持, 实际上仍然不会有浪费的内存分配, 因为即使创建了临时对象, 其内容也是被移动而非复制. 重要

表达式模板可能从根本上重新排列表达式中的运算顺序, 例如:

a = (b * c) * a;

它会被变换为:

a *= c; a *= b;

如果这对某个特定应用可能构成问题, 则应禁用表达式模板.

本库还将表达式模板支持扩展到标准库函数, 例如 abs 或 sin 这样以 number 为实参的标准库函数. 这意味着, 形如下式的表达式:

y = abs(x);

可以在不计算任何一个临时对象的情况下求值. 甚至像这样的表达式:

y = sin(x);

也会得到同样的处理, 变量 'y' 会在 sin 的实现内部被用作'工作存储', 从而使所用的临时对象数量减少一个. 当然, 如果您写的是:

x = sin(x);

那么显然无法将 x 用作计算过程中的工作存储, 此时就会创建一个临时变量.

鉴于上述注释, 您可能想当然地认为表达式模板是一种万能灵药: 遗憾的是, 这类技巧都有其缺点. 首先, 像这样的表达式模板库往往比其更简单的同类编译得更慢, 也更难调试 (如果您真的想单步调试我们的代码!), 并且需要开启编译器优化才能获得真正良好的性能. 另外, 由于涉及 number 的表达式的返回类型是'不可提及的实现细节', 因此在把表达式传给模板函数时, 您必须小心地将表达式的结果转换为实际的数值类型. 例如, 给定:

template <class T>
void my_proc(const T&);

然后调用

my_proc(a+b);

极有可能在 my_proc 的函数体内部产生晦涩难懂的错误信息 - 因为我们传给它的是表达式模板类型, 而不是数值类型. 相反, 我们可能需要:

my_proc(my_number_type(a+b));

话虽如此, 这种情况并不经常发生 - 对于非模板函数甚至根本不会发生. 此外, Boost.Math 库中的所有函数都会自动把表达式模板实参转换为底层数值类型, 无需您做任何事情, 因此

mpfr_float_100 a(20), delta(0.125);
boost::math::gamma_p(a, a + delta);

也能正常工作, 其中 a + delta 表达式模板实参会被 Boost.Math 库在内部转换为 mpfr_float_100.

注意

在 C++11 中, 绝不应使用如下方式存储表达式模板:

auto my_expression = a + b - c;

除非您绝对确定 a、b 与 c 的生存期都长于 my_expression.

实际上, 将表达式模板与 auto 关键字混用特别容易产生悬垂引用, 例如:

auto val = cpp_dec_float_50("23.1") * 100;

在这种情况下, 整数字面量直接存储在表达式模板中 - 所以这里的使用是安全的 - 但 cpp_dec_float_50 临时对象是按引用存储的, 并在语句结束时被销毁, 从而留下悬垂引用.

如有疑问, 切勿将表达式模板与 auto 关键字混用.

最后... 像这样的表达式模板库带来的性能提升, 往往不如临时对象数量的减少所暗示的那么显著. 例如, 如果我们将本库与 mpfr_class 及 mpreal 进行比较, 三者都使用底层 MPFR 库、精度均为 50 位十进制数字, 那么对于多项式执行可以看到如下典型结果:

如您所见, 执行时间的增长比内存分配次数的增长慢得多. 原因有以下几点:

  • 扩展精度乘法和除法的代价非常大, 以至于这些操作所耗的时间往往淹没了其他一切.
  • 原地乘法 (使用 operator*=) 的代价往往高于非原地运算 operator* (通常 operator *= 必须创建临时工作区来执行乘法, 而 operator* 则可以把目标变量用作工作区). 由于表达式模板的魔力在于把非原地运算符转换为原地运算, 我们必然承受这一损失. 即便如此, 这种变换仍比创建额外的临时变量更高效, 只是幅度不如期望的那么大.

最后, 注意 number 接受第二个模板参数, 当其设置为 et_off 时, 将禁用全部表达式模板机制. 这样编译快得多, 但运行时更慢.
