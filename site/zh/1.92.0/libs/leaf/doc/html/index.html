摘要

Boost LEAF 是一个适用于 C++11 的轻量级错误处理库. 特性:

  • 可移植的单头文件格式, 无依赖.

  • 代码体积极小, 可针对嵌入式开发进行配置.

  • 即使负载 (payload) 非常大, 也无需动态内存分配.

  • 在 "happy" 路径和 "sad" 路径上都具有确定且无偏差的效率.

  • 错误对象以常量时间处理, 与调用栈深度无关.

  • 可以在使用或不使用异常处理的情况下使用.

Tutorial

通常, 错误处理库会定义一个变体结果类型, 例如 result<T, E>. 在 LEAF 中我们舍弃了 E, 只使用 result<T>.

成功时, 对值 T 的访问是即时且直接的, 而失败时我们可以轻松退出 (bail out).

为了处理错误, 我们使用一种特殊语法, 使错误对象能够被直接传递到需要它们的错误处理作用域. 这比把它们保存在 result 类型中更高效, 并且还允许任一处理器访问与同一次失败相关联的多个错误对象.

LEAF 也兼容异常处理, 提供相同的功能, 但无需 result 类型.

报告错误

我们先来介绍基于 result<T> 的接口.

使用 leaf::new_error 报告错误:

enum class api_error { connect_failed, invalid_request, timeout };

leaf::result<connection> connect()
{
  ....
  if( <<connection-failure-detected>> )
    return leaf::new_error( api_error::connect_failed ); // Pass error objects of any type

  // Produce and return a connection object.
}

result | new_error

检查错误

失败时退出, 返回 result::error():

leaf::result<data> connect_and_fetch_data()
{
  leaf::result<connection> cr = connect();
  if( !cr )
    return cr.error();

  connection & c = cr.value();

  // Use c to fetch and return data
}

result

使用 BOOST_LEAF_AUTO 来避免样板式的 if 语句:

leaf::result<data> connect_and_fetch_data()
{
  BOOST_LEAF_AUTO(c, connect()); // Bail out on error

  // Use c to fetch and return data
}

BOOST_LEAF_AUTO

使用 BOOST_LEAF_CHECK 来处理 void 结果:

leaf::result<void> flush(connection & c);
leaf::result<std::size_t> bytes_sent(connection & c);

leaf::result<std::size_t> flush_and_get_bytes_sent(connection & c)
{
  BOOST_LEAF_CHECK(flush(c)); // Bail out on error
  return bytes_sent(c);
}

BOOST_LEAF_CHECK

在定义了 __GNUC__ 的实现 (如 GCC/clang) 上, BOOST_LEAF_CHECK 也兼容非 void 结果:

leaf::result<int> count_rows();

float update_average(int n);

leaf::result<float> average_row_count()
{
  return update_average( BOOST_LEAF_CHECK(count_rows()) );
}

下面是可移植的替代写法:

leaf::result<float> average_row_count()
{
  BOOST_LEAF_AUTO(n, count_rows());
  return update_average(n);
}

错误处理

错误处理作用域使用一种特殊语法来表明它们需要访问错误对象:

leaf::result<data> r = leaf::try_handle_some(

  []() -> leaf::result<data>
  {
    BOOST_LEAF_AUTO(c, connect());
    return fetch(c);
  },

  []( api_error e ) -> leaf::result<data>
  {
    if( e == api_error::connect_failed )
      .... // Handle api_error::connect_failed
    else
      .... // Handle any other api_error value
  } );

try_handle_some | result | BOOST_LEAF_AUTO

首先, try_handle_some 执行传给它的第一个函数; 该函数尝试产生一个 result<data>, 但可能会失败.

第二个 lambda 是一个错误处理器: 仅当第一个 lambda 失败且带有类型为 api_error 的错误对象时, 它才会被调用. 该对象存储在栈上, 是 try_handle_some 函数的局部对象 (LEAF 知道要分配这块存储, 因为我们给它的错误处理器接受一个 api_error). 传给 leaf::try_handle_some 的错误处理器可以返回有效的 leaf::result, 也允许失败.

错误处理器可以声明它只能处理给定错误类型的某些特定值:

leaf::result<data> r = leaf::try_handle_some(

  []() -> leaf::result<data>
  {
    BOOST_LEAF_AUTO(c, connect());
    return fetch(c);
  },

  []( leaf::match<api_error, api_error::connect_failed, api_error::timeout> ) -> leaf::result<data>
  {
    // Handle api_error::connect_failed or api_error::timeout
  },

  []( api_error e ) -> leaf::result<data>
  {
    // Handle any other api_error value
  } );

try_handle_some | result | BOOST_LEAF_AUTO | match

LEAF 按顺序考察所提供的错误处理器, 并根据当前正在传递的错误对象, 调用第一个它能够为之提供实参的处理器. 上例中:

  • 仅当类型为 api_error 的错误对象可用, 且其值为 api_error::connect_failed 或 api_error::timeout 时, 第一个错误处理器才会被调用.

  • 否则, 仅当类型为 api_error 的错误对象可用时 (不论其值如何), 第二个错误处理器才会被调用.

  • 否则, leaf::try_handle_some 无法处理该错误.

错误处理器也可以有条件地不处理某次失败:

leaf::result<data> r = leaf::try_handle_some(

  []() -> leaf::result<data>
  {
    BOOST_LEAF_AUTO(c, connect());
    return fetch(c);
  },

  []( api_error e, leaf::error_info const & ei ) -> leaf::result<data>
  {
    if( e == api_error::timeout )
      return cached_data();
    else
      return ei.error();
  } );

try_handle_some | result | BOOST_LEAF_AUTO | error_info

任何错误处理器都可以接受一个类型为 leaf::error_info const & 的实参, 以访问关于所处理错误的通用信息; 此处我们使用 error 成员函数, 它返回当前错误的唯一 error_id; 我们用它来初始化返回的 leaf::result, 从而有效地将当前错误从 try_handle_some 中传播出去.

如果想发出一个新错误 (而不是传播当前错误), 则应在 return 语句中调用 leaf::new_error 函数.

如果想确保所有可能的失败都得到处理, 则使用 leaf::try_handle_all 而非 leaf::try_handle_some:

data r = leaf::try_handle_all(

  []() -> leaf::result<data>
  {
    BOOST_LEAF_AUTO(c, connect());
    return fetch(c);
  },

  []( leaf::match<api_error, api_error::connect_failed> ) -> data
  {
    // Handle api_error::connect_failed
  },

  []( api_error e ) -> data
  {
    // Handle any other api_error value
  },

  []() -> data
  {
    // Handle any other failure
  } );

try_handle_all

leaf::try_handle_all 函数在编译期强制要求所提供的错误处理器中至少有一个不接受任何实参 (因此能够处理任何失败). 此外, 所有错误处理器都被强制返回有效对象而非 leaf::result, 从而保证 leaf::try_handle_all 一定成功.

处理不同的错误类型

当然也可以为不同的错误类型提供不同的处理器:

enum class api_error { connect_failed, invalid_request, timeout };
enum class auth_error { unauthorized, forbidden };

....

leaf::result<data> r = leaf::try_handle_some(

  []() -> leaf::result<data>
  {
    BOOST_LEAF_AUTO(c, connect());
    return fetch(c);
  },

  []( api_error e ) -> leaf::result<data>
  {
    // Handle errors of type `api_error`.
  },

  []( auth_error e ) -> leaf::result<data>
  {
    // Handle errors of type `auth_error`.
  } );

try_handle_some | result | BOOST_LEAF_AUTO

错误处理器总是按顺序考察:

  • 如果类型为 api_error 的错误对象可用, 则使用第一个错误处理器;

  • 否则, 如果类型为 auth_error 的错误对象可用, 则使用第二个错误处理器;

  • 否则, leaf::try_handle_some 失败.

处理多个错误对象

leaf::new_error 函数可以随多个错误对象一起调用, 例如传递一个错误码以及相关的文件名:

enum class io_error { open_error, read_error, write_error };

struct e_file_name { std::string value; };

leaf::result<File> open_file( char const * name )
{
  ....
  if( open_failed )
    return leaf::new_error(io_error::open_error, e_file_name {name});
  ....
}

result | new_error

类似地, 错误处理器也可以接受多个错误对象作为实参:

leaf::result<T> r = leaf::try_handle_some(

  []() -> leaf::result<T>
  {
    BOOST_LEAF_AUTO(f, open_file(fn));
    ....
  },

  []( io_error ec, e_file_name fn ) -> leaf::result<T>
  {
    // Handle I/O errors when a file name is also available.
  },

  []( io_error ec ) -> leaf::result<T>
  {
    // Handle I/O errors when no file name is available.
  } );

try_handle_some | result | BOOST_LEAF_AUTO

同样, 错误处理器按顺序考察:

  • 如果类型为 io_error 的错误对象和类型为 e_file_name 的错误对象都可用, 则使用第一个错误处理器;

  • 否则, 如果类型为 io_error 的错误对象可用, 则使用第二个错误处理器;

  • 否则, leaf::try_handle_some 失败.

上述代码的另一种写法是提供一个单一的错误处理器, 以指针形式接受 e_file_name 实参:

leaf::result<T> r = leaf::try_handle_some(

  []() -> leaf::result<T>
  {
    BOOST_LEAF_AUTO(f, open_file(fn));
    ....
  },

  []( io_error ec, e_file_name const * fn ) -> leaf::result<T>
  {
    if( fn )
      .... // Handle I/O errors when a file name is also available.
    else
      .... // Handle I/O errors when no file name is available.
  } );

try_handle_some | result | BOOST_LEAF_AUTO

错误处理器绝不会因为缺少其以指针形式接受的类型的错误对象而被丢弃; 此时 LEAF 只是为这些实参传入 nullptr.

当错误处理器以可变引用或指针形式接受实参时, 对其状态的修改会在错误被传递给调用者时得以保留.

增补错误

假设我们有一个函数 parse_line, 它可能因 io_error 或 parse_error 而失败:

enum class io_error { open_error, read_error, write_error };

enum class parse_error { bad_syntax, bad_range };

leaf::result<int> parse_line( FILE * f );

leaf::on_error 函数可用于自动地将额外的错误对象与任何处于 "传递中" (in flight) 的失败相关联:

struct e_line { int value; };

leaf::result<void> process_file( FILE * f )
{
  for( int current_line = 1; current_line != 10; ++current_line )
  {
    auto load = leaf::on_error( e_line {current_line} );

    BOOST_LEAF_AUTO(v, parse_line(f));

    // use v
  }
}

on_error | BOOST_LEAF_AUTO

由于 process_file 并不处理错误, 它对失败保持中立, 只是在出现问题时附加 current_line. on_error 返回的对象持有 current_line 的一份副本, 包装在 struct e_line 中. 若 parse_line 成功, e_line 对象会被直接丢弃; 若失败, e_line 对象将被自动 "附加" 到该失败上.

随后, 这类失败可以这样处理:

leaf::result<void> r = leaf::try_handle_some(

  [&]() -> leaf::result<void>
  {
    BOOST_LEAF_CHECK( process_file(f) );
  },

  []( parse_error e, e_line current_line  )
  {
    std::cerr << "Parse error at line " << current_line.value << std::endl;
  },

  []( io_error e, e_line current_line )
  {
    std::cerr << "I/O error at line " << current_line.value << std::endl;
  },

  []( io_error e )
  {
    std::cerr << "I/O error" << std::endl;
  } );

try_handle_some | BOOST_LEAF_CHECK

下面的写法与之等价, 或许还更简单:

leaf::result<void> r = leaf::try_handle_some(

  []() -> leaf::result<void>
  {
    BOOST_LEAF_CHECK( process_file(f) );
  },

  []( parse_error e, e_line current_line )
  {
    std::cerr << "Parse error at line " << current_line.value << std::endl;
  },

  []( io_error e, e_line const * current_line )
  {
    std::cerr << "I/O error";
    if( current_line )
      std::cerr << " at line " << current_line->value;
    std::cerr << std::endl;
  } );

异常处理

如果某个操作抛出了异常会怎样? try_handle_some 和 try_handle_all 都能捕获异常, 并能将其传给任何兼容的错误处理器:

leaf::result<void> r = leaf::try_handle_some(

  []() -> leaf::result<void>
  {
    BOOST_LEAF_CHECK( process_file(f) );
  },

  []( std::bad_alloc const & )
  {
    std::cerr << "Out of memory!" << std::endl;
  },

  []( parse_error e, e_line l )
  {
    std::cerr << "Parse error at line " << l.value << std::endl;
  },

  []( io_error e, e_line const * l )
  {
    std::cerr << "I/O error";
    if( l )
      std::cerr << " at line " << l.value;
    std::cerr << std::endl;
  } );

try_handle_some | result | BOOST_LEAF_CHECK

这里我们只是添加了一个接受 std::bad_alloc 的错误处理器, 一切便如预期般 "直接可用": 无论失败是通过 leaf::result 传递还是通过异常传递, LEAF 都会正确地分派错误处理器.

当然, 如果我们完全使用异常处理, 就根本不需要 leaf::result. 此时我们使用 leaf::try_catch:

leaf::try_catch(

  []
  {
    process_file(f);
  },

  []( std::bad_alloc const & )
  {
    std::cerr << "Out of memory!" << std::endl;
  },

  []( parse_error e, e_line l )
  {
    std::cerr << "Parse error at line " << l.value << std::endl;
  },

  []( io_error e, e_line const * l )
  {
    std::cerr << "I/O error";
    if( l )
      std::cerr << " at line " << l.value;
    std::cerr << std::endl;
  } );

try_catch

我们无需改动任何错误处理器! 但这是如何做到的? process_file 会抛出什么样的异常?

LEAF 支持一种新颖的异常处理技术, 它不需要异常类型层次结构来对失败进行分类, 也不在异常对象中携带数据. 回想一下, 当失败通过 leaf::result 传递时, 我们调用 leaf::new_error, 它处于一个 return 语句中, 传入任意数量的错误对象, 这些对象会被直接发送到正确的错误处理作用域:

enum class api_error { connect_failed, invalid_request, timeout };
enum class auth_error { unauthorized, forbidden };

....

leaf::result<T> f()
{
  ....
  if( error_detected )
    return leaf::new_error(api_error::connect_failed, auth_error::forbidden);

  // Produce and return a T.
}

result | new_error

使用异常处理时, 上述代码变为:

enum class api_error { connect_failed, invalid_request, timeout };
enum class auth_error { unauthorized, forbidden };

T f()
{
  if( error_detected )
    leaf::throw_exception(api_error::connect_failed, auth_error::forbidden);

  // Produce and return a T.
}

throw_exception

leaf::throw_exception 函数处理传入的错误对象的方式与 leaf::new_error 相同, 然后抛出一个派生自 std::exception 的类型的对象. 采用这种技术时, 异常类型并不重要: leaf::try_catch 捕获所有异常, 然后执行常规的 LEAF 错误处理器选择流程.

反之, 如果我们想遵循通过抛出不同类型来表示不同失败的标准惯例, 只需将一个异常对象 (即派生自 std::exception 的类型的对象) 作为第一个实参传给 leaf::throw_exception:

leaf::throw_exception(std::runtime_error("Error!"), api_error::connect_failed, auth_error::forbidden);

此时抛出的异常对象的类型将派生自 std::runtime_error, 而不是 std::exception.

最后, leaf::on_error 也同样 "直接可用". 下面是我们的 process_file 函数改写为使用异常而非返回 leaf::result 的版本 (参见 增补错误):

int parse_line( FILE * f ); // Throws

struct e_line { int value; };

void process_file( FILE * f )
{
  for( int current_line = 1; current_line != 10; ++current_line )
  {
    auto load = leaf::on_error( e_line {current_line} );
    int v = parse_line(f);

    // use v
  }
}

on_error

使用外部 result 类型

静态类型检查给任何非平凡项目中的错误处理互操作性带来了困难. 使用异常处理可在一定程度上缓解这一问题, 因为此时错误类型不会固化到函数签名中, 错误可以轻松穿透多层 API; 但这总体上无助于 C++, 因为社区在异常处理问题上立场分裂. 抛开这场争论不谈, 现实是 C++ 程序需要处理通过多层 API 以各种错误码、result 类型和异常传递的错误.

LEAF 让应用程序开发者能够把错误对象从每个库各自的 result 类型中原样取出, 并发送到错误处理作用域. 下面是一个例子:

lib1::result<int, lib1::error_code> foo();
lib2::result<int, lib2::error_code> bar();

int g( int a, int b );

leaf::result<int> f()
{
  auto a = foo();
  if( !a )
    return leaf::new_error( a.error() );

  auto b = bar();
  if( !b )
    return leaf::new_error( b.error() );

  return g( a.value(), b.value() );
}

result | new_error

之后我们只需调用 leaf::try_handle_some, 为每个类型传入一个错误处理器:

leaf::result<int> r = leaf::try_handle_some(

  []() -> leaf::result<int>
  {
    return f();
  },

  []( lib1::error_code ec ) -> leaf::result<int>
  {
    // Handle lib1::error_code
  },

  []( lib2::error_code ec ) -> leaf::result<int>
  {
    // Handle lib2::error_code
  } );

try_handle_some | result

一个可能的复杂情况是, 我们也许无法选择 leaf::result<int> 作为 f 的返回类型: 第三方 API 可能对它施加特定的签名, 强制其返回某个库专用的 result 类型. 当 f 要被用作回调时就会出现这种情况:

void register_callback( std::function<lib3::result<int>()> const & callback );

这种情况下还能使用 LEAF 吗? 实际上可以, 只要 lib3::result 能够传递一个 std::error_code. 我们只需通过特化 is_result_type 模板来告知 LEAF:

namespace boost { namespace leaf {

template <class T>
struct is_result_type<lib3::result<T>>: std::true_type;

} }

is_result_type

有了这一设置, f 便照常工作, 即使 lib3::result 无法传递 lib1 错误或 lib2 错误:

lib1::result<int, lib1::error_type> foo();
lib2::result<int, lib2::error_type> bar();

int g( int a, int b );

lib3::result<int> f() // Note: return type is not leaf::result<int>
{
  auto a = foo();
  if( !a )
    return leaf::new_error( a.error() );

  auto b = bar();
  if( !b )
    return leaf::new_error( b.error() );

  return g( a.value(), b.value() );
}

new_error

leaf::new_error 返回的对象可以隐式转换为 std::error_code, 依靠的是 LEAF 专用的 error_category, 这使 lib3::result 与 leaf::try_handle_some (以及 leaf::try_handle_all) 兼容:

lib3::result<int> r = leaf::try_handle_some(

  []() -> lib3::result<int>
  {
    return f();
  },

  []( lib1::error_code ec ) -> lib3::result<int>
  {
    // Handle lib1::error_code
  },

  []( lib2::error_code ec ) -> lib3::result<int>
  {
    // Handle lib2::error_code
  } );

try_handle_some

互操作性

理想情况下, 使用 LEAF 的程序在检测到错误时总是会调用 new_error, 确保遇到的每个失败都被确定地赋予一个唯一的 error_id, 该 ID 随后通过异常或 result<T> 对象被可靠地送达相应的错误处理作用域.

可惜, 这并不总是可行的.

例如, 错误可能需要经由不配合的第三方接口传递. 为便于这种传递, 错误 ID 可以编码在一个 std::error_code 中. 只要第三方接口能够传递一个 std::error_code, 它就可以与 LEAF 兼容.

此外, 有时需要通过一个甚至不使用 std::error_code 的接口来传递错误. 一个例子是外部低层库抛出异常, 该异常不太可能携带 error_id.

为支持这一棘手的使用场景, LEAF 提供了函数 current_error, 它返回最近一次 (在本线程中) 对 new_error 的调用所返回的错误 ID. 解决该问题的一种可能做法是使用如下逻辑 (由 error_monitor 类型实现):

  1. 在调用不配合的 API 之前, 先调用 current_error 并缓存返回值.

  2. 调用该 API, 然后再次调用 current_error:

    1. 如果这次返回的值与之前相同, 则把错误对象传给 new_error, 将它们与一个新的 error_id 相关联;

    2. 否则, 将错误对象与 error_id 值相关联, 该值来自对 current_error 的第二次调用.

注意, 如果上述逻辑发生嵌套 (例如一个函数调用另一个函数), new_error 将只由最内层的函数调用, 因为该调用保证了所有调用方函数都会命中 else 分支.

详细教程参见 使用 error_monitor 报告来自 C 回调的错误.

错误对象的加载

回想一下, 传递给 LEAF 的错误对象存储在栈上, 是用于处理错误的 try_handle_some、try_handle_all 或 try_catch 函数的局部对象. 加载一个错误对象, 指的是把它移入这类存储 (如果可用).

各种 LEAF 函数都接受一个待加载的错误对象列表. 例如, 若一个接受输入文件名和输出文件名作为实参的函数 copy_file 检测到失败, 它可以传递一个错误码 ec, 并通过 new_error 附上两个相关的文件名:

return leaf::new_error(ec, e_input_name{n1}, e_output_name{n2});

或者, 可以通过一个已在传递错误的 result<T> 来加载错误对象. 这样它们便与该错误相关联, 而不是与一个新错误相关联:

leaf::result<int> f() noexcept;

leaf::result<void> g( char const * fn ) noexcept
{
  if( leaf::result<int> r = f() )
  { (1)
    ....;
    return { };
  }
  else
  {
    return r.load( e_file_name{fn} ); (2)
  }
}

result | load

1 成功了! 使用 r.value().
2 f() 已失败; 这里我们把一个额外的 e_file_name 与该错误相关联. 不过, 这种关联只有当通向 g 的调用栈中存在接受 e_file_name 实参的错误处理器时才会发生. 否则, 传给 load 的对象将被丢弃. 换言之, 只有当程序确实使用这些对象来处理错误时, 它们才会被加载.

除错误对象外, load 还可以接受函数实参:

  • 如果我们传入一个不带实参的函数, 该函数会被调用, 其返回的错误对象会被加载.

    考虑一下: 如果传给 load 的错误对象没有被任何错误处理器使用, 它将被丢弃. 而如果我们传入的不是错误对象, 而是一个返回错误对象的函数, 那么只有当它返回的对象会被用到 (即不会被丢弃) 时, 该函数才会被调用. 当错误对象的产生代价较高时, 这一点很有用:

    struct info { .... };

info compute_info() noexcept;

leaf::result<void> operation( char const * file_name ) noexcept
{
  if( leaf::result<int> r = try_something() )
  { (1)
    ....
    return { };
  }
  else
  {
    return r.load( (2)
      [&]
      {
        return compute_info();
      } );
  }
}

    result | load

    1 成功了! 使用 r.value().
    2 try_something 已失败; compute_info 只有在调用栈中存在接受 info 实参的错误处理器时才会被调用.

  • 如果我们传入一个接受单个实参 (某个引用类型 E &) 的函数, LEAF 会用类型为 E 的对象来调用该函数, 该对象当前加载在活动的 context 中并与该错误相关联. 若没有这样的对象可用, 则会默认初始化一个新对象并传给该函数.

    例如, 若一个涉及许多不同文件的操作失败, 程序可以提供一个 e_relevant_file_names 对象来收集所有相关的文件名:

    struct e_relevant_file_names
{
  std::vector<std::string> value;
};

leaf::result<void> operation( char const * file_name ) noexcept
{
  if( leaf::result<int> r = try_something() )
  { (1)
    ....
    return { };
  }
  else
  {
    return r.load( (2)
      [&](e_relevant_file_names & e)
      {
        e.value.push_back(file_name);
      } );
  }
}

    result | load

    1 成功了! 使用 r.value().
    2 try_something 已失败 — 将 file_name 加入 e_relevant_file_names 对象, 与 error_id 相关联, 后者在 r 中传递. 但请注意, 只有当调用栈中存在接受 e_relevant_file_names 对象的错误处理器时, 传入的函数才会被调用.

使用 on_error

错误报告函数通常并不具备提供全部数据的能力, 而合适的错误处理函数需要这些数据才能从失败中恢复. 例如, 报告 FILE 失败的函数可能无法访问文件名, 而错误处理函数却需要文件名才能打印出有用的错误消息.

文件名通常在通向失败的 FILE 操作的调用栈中随时可得. 下例中, parse_info 虽然无法报告文件名, parse_file 却可以并且确实做到了:

leaf::result<info> parse_info( FILE * f ) noexcept; (1)

leaf::result<info> parse_file( char const * file_name ) noexcept
{
  auto load = leaf::on_error(leaf::e_file_name{file_name}); (2)

  if( FILE * f = fopen(file_name,"r") )
  {
    auto r = parse_info(f);
    fclose(f);
    return r;
  }
  else
    return leaf::new_error( error_enum::file_open_error );
}

result | on_error | new_error

1 parse_info 使用 leaf::result 来传递错误.
2 on_error 确保文件名被包含在从 parse_file 报告出的任何错误中. 当 load 对象到期时, 如果正在报告错误, 传入的 e_file_name 值将被自动与之关联.
on_error 与 new_error 一样, 可以接受任意数量的实参.

调用 on_error 时, 我们可以传入三类实参:

  1. 实际的错误对象 (如上例所示);

  2. 不带实参并返回错误对象的函数;

  3. 以可变引用接受单个错误对象的函数.

例如, 如果我们想用 on_error 来捕获 errno, 可以使用 e_errno 类型, 它是一个包装了 int 的简单结构体. 但是, 我们不能直接把 e_errno 传给 on_error, 因为那时 errno 还 (未) 被设置. 作为替代, 我们传入一个返回它的函数:

void read_file(FILE * f) {

  auto load = leaf::on_error([]{ return leaf::e_errno{errno}; });

  ....
  size_t nr1=fread(buf1,1,count1,f);
  if( ferror(f) )
    leaf::throw_exception();

  size_t nr2=fread(buf2,1,count2,f);
  if( ferror(f) )
    leaf::throw_exception();

  size_t nr3=fread(buf3,1,count3,f);
  if( ferror(f) )
    leaf::throw_exception();
  ....
}

上例中, 如果抛出了异常, LEAF 会调用传给 on_error 的函数, 并将返回的 e_errno 对象与该异常相关联.

最后, 如果传给 on_error 的是一个以可变引用接受单个错误对象的函数, 其行为与 load 处理此类函数的方式类似; 参见 错误对象的加载.

使用谓词处理错误

通常, 错误处理器与可用错误对象之间的兼容性是根据处理器所接受实参的类型来判定的. 当错误处理器以谓词类型作为实参时, 处理器选择流程还能够将可用错误对象的值纳入考量.

考虑这个错误码枚举:

enum class validation_error
{
  empty_field = 1,
  invalid_format,
  out_of_range
};

我们可以这样处理 validation_error 错误:

return leaf::try_handle_some(

  []
  {
    return validate_input(); // Returns leaf::result<input>
  },

  []( validation_error e )
  {
    switch(e)
    {
      case validation_error::empty_field:
        ....; // Handle empty_field errors
        break;
      case validation_error::invalid_format:
      case validation_error::out_of_range:
        ....; // Handle invalid_format and out_of_range errors
        break;
      default:
        ....; // Handle unexpected validation_error values
        break;
    }
  } );

如果 validation_error 对象可用, LEAF 会调用我们的错误处理器. 如果不可用, 该失败将被转发给调用者.

可以使用 match 谓词来改写上述代码, 把不同的情况组织到不同的错误处理器中. 下面是等价写法:

return leaf::try_handle_some(

  []
  {
    return validate_input(); // Returns leaf::result<input>
  },

  []( leaf::match<validation_error, validation_error::empty_field> m )
  {
    assert(m.matched == validation_error::empty_field);
    ....;
  },

  []( leaf::match<validation_error, validation_error::invalid_format, validation_error::out_of_range> m )
  {
    assert(m.matched == validation_error::invalid_format || m.matched == validation_error::out_of_range);
    ....;
  },

  []( validation_error e )
  {
    ....;
  } );

match 模板的第一个实参通常指定类型 E, 即错误对象 e 的类型, 只有当该对象可用时, 相应的错误处理器才会被纳入考量. 通常, 其余实参是若干值. 如果 e 与其中任何一个值都不相等, 该错误处理器即被丢弃.

特别是, match 与 std::error_code 配合得非常好. 下面的处理器用于处理 ENOENT 错误:

[]( leaf::match<std::error_code, std::errc::no_such_file_or_directory> )
{
}

不过, 这要求 C++17 或更新标准. LEAF 提供了以下兼容 C++11 的变通方案:

[]( leaf::match<leaf::condition<std::errc>, std::errc::no_such_file_or_directory> )
{
}

也可以基于 std::error_category 来选择处理器. 下面的处理器将匹配任何 std::error_code, 只要它属于 std::generic_category (要求 C++17 或更新标准):

[]( std::error_code, leaf::category<std::errc> )
{
}
更多示例参见 match.

可用的谓词如下:

  • match: 如上所述.

  • match_value: 其中 match<E, V…​> 将对象 e (类型为 E) 与值 V…​ 比较, match_value<E, V…​> 将 e.value 与值 V…​ 比较.

  • match_member: 与 match_value 类似, 但接受一个指向待比较数据成员的指针; 也就是说, match_member<&E::value, V…​> 等价于 match_value<E, V…​>. 但请注意, match_member 要求 C++17 或更新标准, 而 match_value 无此要求.

  • catch_<Ex…​>: 与 match 类似, 但检查捕获的 std::exception 对象能否被 dynamic_cast 到 Ex…​ 类型中的任何一个.

  • if_not 是一个特殊谓词, 它接受任何其他谓词 Pred, 并要求类型为 E 的错误对象可用, 且 Pred 求值为 false. 例如, if_not<match<E, V…​>> 要求对象 e (类型为 E) 可用, 且它与任何指定的 V…​ 都不相等.

谓词系统非常易于扩展, 参见 谓词.

另见 处理 std::error_code 与 std::error_condition.

在线程间传递错误

与异常一样, LEAF 错误对象是线程局部的. 使用并发时, 有时我们需要在一个线程中收集错误对象, 然后在另一个线程中用它们处理错误.

无论是否使用异常处理, LEAF 都支持这一功能. 两种情况下, 错误对象都被捕获并运输于一个 leaf::result<T> 对象中.

不使用异常处理在线程间传递错误

假设我们有一个要异步启动的 task, 它产生一个 task_result 但也可能失败:

leaf::result<task_result> task();

由于任务将异步运行, 失败时我们需要捕获产生的所有错误对象, 但不处理错误. 我们通过调用 try_capture_all 来实现:

std::future<leaf::result<task_result>> launch_task() noexcept
{
  return std::async(
    std::launch::async,
    [&]
    {
      return leaf::try_capture_all(task);
    } );
}

result | try_capture_all

失败时, 从 try_capture_all 返回的 result<T> 对象持有从 task 传递出的所有错误对象, 代价是动态内存分配. 随后, result<T> 对象可以被存放起来或移到另一个线程, 稍后传给错误处理函数以卸载其内容并处理错误:

//std::future<leaf::result<task_result>> fut;
fut.wait();

return leaf::try_handle_some(

  [&]() -> leaf::result<void>
  {
    BOOST_LEAF_AUTO(r, fut.get());
    //Success!
    return { };
  },

  [](E1 e1, E2 e2)
  {
    //Deal with E1, E2
    ....
    return { };
  },

  [](E3 e3)
  {
    //Deal with E3
    ....
    return { };
  } );

try_handle_some | result | BOOST_LEAF_AUTO

失败的分类

接口通常定义一个 enum, 列出该 API 报告的所有可能错误码. 这种做法的好处是列表完整, 且通常有良好的文档:

enum error_code
{
  ....
  read_error,
  size_error,
  eof_error,
  ....
};

这种扁平枚举的缺点在于, 它们不支持对一整类失败的处理. 考虑以下 LEAF 错误处理器:

....
[](leaf::match<error_code, size_error, read_error, eof_error>, leaf::e_file_name const & fn)
{
  std::cerr << "Failed to access " << fn.value << std::endl;
},
....

match | e_file_name

如果随失败一起传递的 error_code 枚举的值是 size_error、read_error 或 eof_error 之一, 该处理器就会被调用. 简而言之, 其意图是处理任何输入错误.

但如果之后我们新增了对一种新输入错误的检测和报告支持, 例如 permissions_error 呢? 把它加进我们的 error_code 枚举很容易; 但这样一来, 我们的输入错误处理器将无法识别这种新的输入错误 — 于是就产生了缺陷.

使用异常是一种改进, 因为异常类型可以组织成层次结构, 以便对失败进行分类:

struct input_error: std::exception { };
struct read_error: input_error { };
struct size_error: input_error { };
struct eof_error: input_error { };

用 LEAF 的术语来说, 我们的输入错误异常处理器现在如下所示:

[](input_error &, leaf::e_file_name const & fn)
{
  std::cerr << "Failed to access " << fn.value << std::endl;
},

这样具有前瞻性, 但仍不理想, 因为在异常对象被抛出之后就无法再细化对该失败的分类了.

LEAF 支持一种新颖的错误处理风格, 其中失败的分类不使用错误码值, 也不使用异常类型层次结构. 我们可以不定义 error_code 枚举, 而是定义:

....
struct input_error { };
struct read_error { };
struct size_error { };
struct eof_error { };
....

有了这一设置, 我们可以定义一个函数 file_read:

leaf::result<void> file_read( FILE & f, void * buf, int size )
{
  int n = fread(buf, 1, size, &f);

  if( ferror(&f) )
    return leaf::new_error(input_error{}, read_error{}, leaf::e_errno{errno}); (1)

  if( n!=size )
    return leaf::new_error(input_error{}, eof_error{}); (2)

  return { };
}

result | new_error | e_errno

1 该错误被分类为 input_error 和 read_error.
2 该错误被分类为 input_error 和 eof_error.

或者, 更好的做法是:

leaf::result<void> file_read( FILE & f, void * buf, int size )
{
  auto load = leaf::on_error(input_error{}); (1)

  int n = fread(buf, 1, size, &f);

  if( ferror(&f) )
    return leaf::new_error(read_error{}, leaf::e_errno{errno}); (2)

  if( n!=size )
    return leaf::new_error(eof_error{}); (3)

  return { };
}

result | on_error | new_error | e_errno

1 任何逃逸出该作用域的错误都将被分类为 input_error
2 此外, 该错误还被分类为 read_error.
3 此外, 该错误还被分类为 eof_error.

如果我们选择使用异常处理, 这一技术同样奏效, 只需调用 leaf::throw_exception 而非 leaf::new_error:

void file_read( FILE & f, void * buf, int size )
{
  auto load = leaf::on_error(input_error{});

  int n = fread(buf, 1, size, &f);

  if( ferror(&f) )
    leaf::throw_exception(read_error{}, leaf::e_errno{errno});

  if( n!=size )
    leaf::throw_exception(eof_error{});
}

on_error | throw_exception | e_errno

如果传给 leaf::throw_exception 的第一个实参的类型派生自 std::exception, 它将用于初始化被抛出的异常对象. 此处情况并非如此, 因此该函数抛出一个默认初始化的 std::exception 对象, 而第一个 (及其他所有) 实参则与该失败相关联.

现在我们可以为任何 input_error 编写具有前瞻性的处理器:

....
[](input_error, leaf::e_file_name const & fn)
{
  std::cerr << "Failed to access " << fn.value << std::endl;
},
....

值得注意的是, 由于失败的分类不依赖错误码或异常类型, 如果我们使用异常处理, 该错误处理器可与 try_catch 配合使用; 如果不使用, 则可与 try_handle_some/try_handle_all 配合使用.

将异常转换为 result<T>

在把一个抛出异常的库集成到使用 result<T> 的代码中时, 可使用 exception_to_result 在边界处转换异常:

struct parse_error: std::exception { };
struct syntax_error: parse_error { };
struct encoding_error: parse_error { };

json_value parse_json(char const * str); // Throws parse_error

leaf::result<json_value> safe_parse_json(char const * str) noexcept
{
  return leaf::exception_to_result<syntax_error, encoding_error>(
    [&]
    {
      return parse_json(str);
    } );
}

result | exception_to_result

模板实参指定要捕获为错误对象的异常类型. 所有异常都会被捕获; 对于列出的每种类型, LEAF 会尝试一次 dynamic_cast 并加载该切片的副本. std::current_exception() 也会被捕获, 因此未列出的异常类型仍然可以得到处理.

之后即可正常处理错误:

leaf::try_handle_all(

  []() -> leaf::result<void>
  {
    BOOST_LEAF_AUTO(doc, safe_parse_json(input));
    process(doc);
    return { };
  },

  [](syntax_error const &)
  {
    std::cerr << "JSON syntax error" << std::endl;
  },

  [](encoding_error const &)
  {
    std::cerr << "Invalid encoding" << std::endl;
  },

  []
  {
    std::cerr << "Unknown error" << std::endl;
  } );

try_handle_all | result | BOOST_LEAF_AUTO

接受异常类型的处理器, 无论对象是被抛出的还是通过 exception_to_result 加载的, 其工作方式都相同.

使用 error_monitor 报告来自 C 回调的错误

C 回调具有固定的签名, 无法返回像 leaf::result<T> 这样的 C++ 类型. error_monitor 类解决了这一问题.

考虑一个调用用户提供的回调的 C 库:

enum class parse_error { unexpected_token, invalid_syntax };

int on_element(void * ctx, char const * data)
{
  if( <<error-detected>> )
  {
    leaf::new_error(parse_error::unexpected_token);
    return -1;
  }
  return 0;
}

new_error

回调调用 new_error 将错误对象与失败相关联, 然后向 C 库返回一个错误码. 包装函数使用 error_monitor 来取回 error_id:

leaf::result<document> parse(char const * input)
{
  leaf::error_monitor cur_err;

  if( c_library_parse(input, &on_element, nullptr) != 0 )
    return cur_err.assigned_error_id();
  else
    return make_document();
}

result | error_monitor

如果回调内部调用过 new_error, assigned_error_id 会返回那个 error_id. 否则, 它会调用 new_error 并返回一个全新的 error_id. 无论哪种情况, 调用者都可以正常处理该失败.

在 diagnostic_details 输出中, Caught: 之下的部分列出错误处理器作为实参接受的对象 — 即存储在栈上的对象. Diagnostic details: 之下的部分列出所有其他被传递的对象. 如果我们没有提供接受 diagnostic_details 的处理器, 这些对象本来会被丢弃.

为了打印每个错误对象, LEAF 会尝试绑定一个对 operator<< 的非限定调用, 传入一个 std::ostream 和该错误对象. 如果失败, 它还会尝试绑定 operator<<, 该调用接受错误类型的 .value. 如果这同样无法通过编译, 该错误对象的值将不会出现在诊断消息中, 但 LEAF 仍会打印其类型.

即使错误类型定义了可打印的 .value, 用户可能仍希望为 operator<< 重载, 以用于其外层的 struct, 例如:

struct e_errno
{
  int value;

  friend std::ostream & operator<<( std::ostream & os, e_errno const & e )
  {
    return os << e.value << ", \"" << strerror(e.value) << '"';
  }
};

上面的 e_errno 类型旨在持有 errno 值. 所定义的 operator<< 重载会自动包含 strerror 的输出, 当打印 e_errno 值的时候 (LEAF 定义了 e_errno, 位于 <boost/leaf/common.hpp> 中, 与其他常用错误类型放在一起).

使用 diagnostic_details 是有代价的. 通常, 当程序试图传递的类型在任何当前调用栈的错误处理作用域中都未被使用时, 这些错误对象会被丢弃, 从而节省开销. 然而, 如果提供的错误处理器接受 diagnostic_details 实参, 这类对象将存储在堆上而不是被丢弃.

序列化

LEAF 提供了一个序列化 API, 可将错误信息导出为不同的格式, 例如 JSON. 这对结构化日志、远程调试或与监控系统集成都很有用. 要序列化错误信息, 请使用以下类型上提供的 serialize_to 成员函数:

  • error_info

  • diagnostic_info

  • diagnostic_details

  • result

LEAF 序列化通过 output 和 output_at 函数调用定义, 经由 ADL 查找:

  • output(e, x) 将 x 直接作为一个值序列化到编码器 e.

  • output_at(e, x, name) 将 x 作为一个具名字段序列化到编码器 e.

LEAF 为以下类型提供了通用 output 重载:

  • error_id

  • e_source_location

  • e_errno

  • std::error_code

  • std::error_condition

  • std::exception

  • std::exception_ptr

  • 任何具有 .value 成员的类型, 只要能通过 ADL 找到合适的 output

#include <boost/exception/diagnostic_information.hpp>

为支持导出到特定格式, 用户需定义一个编码器类, 并为该编码器定义关联的 output 和 output_at 函数模板:

struct my_encoder
{
  template <class T>
  friend void output(my_encoder & e, T const & x)
  {
    // output value x to e
  }

  template <class T>
  friend void output_at(my_encoder & e, T const & x, char const * name)
  {
    // output x to e as a named field
  }
};

output_at 函数通常会创建一个嵌套作用域 (例如 JSON 对象或 XML 元素), 然后对 output 发起非限定调用以输出值. 这会调用经由 ADL 找到的任何兼容重载.

output 函数可能需要用 SFINAE 来定义, 以避免与 LEAF 提供的通用 output 重载产生歧义. 自定义编码器还必须处理不提供 ADL output 重载的类型, 包括 int 和 std::string 这样的内置类型.

要启用序列化到自定义编码器类型, 请定义一个 serialize 函数模板, 置于 boost::leaf::serialization 命名空间中:

namespace boost { namespace leaf {

namespace serialization {

  template <class Handle, class T>
  void serialize(Handle & h, T const & x, char const * name)
  {
    h.dispatch([&](my_encoder & e) {
      output_at(e, x, name);
    });
  }

}

} }

serialize 函数模板接受一个持有编码器的句柄引用 h (类型未指定)、待序列化的错误对象及其类型名. 用单实参函数 F 调用 h.dispatch, 即可根据 F 的实参类型检测编码器类型; 只有当句柄中包含该类型的编码器时, F 才会被调用.

要支持多种输出格式, 向 h.dispatch 传入多个函数:

h.dispatch(
  [&](nlohmann_json_encoder & e) { output_at(e, x, name); },
  [&](xml_encoder & xe) { output_at(xe, x, name); }
);

处理 std::error_code 与 std::error_condition

引言

仅从标准规范来读, std::error_code 与 std::error_condition 之间的关系并不容易理解. 本节解释它们应当如何使用, 以及 LEAF 如何与它们交互.

std::error_code 背后的思想是同时编码一个表示错误码的整数值, 以及该值所属的域. 域由一个 std::error_category 引用表示. 从概念上讲, std::error_code 就像一个 pair<std::error_category const &, int>.

假设我们有这样一个 enum:

enum class file_error
{
  not_found = 1,
  permission_denied,
  disk_full
};

我们希望能把 file_error 值装入 std::error_code 对象中传递. 这会擦除它们的静态类型, 使其能够自由跨越 API 边界. 为此, 我们必须定义一个 std::error_category, 用以代表我们的 file_error 类型:

std::error_category const & file_error_category()
{
  struct category: std::error_category
  {
    char const * name() const noexcept override
    {
      return "file_error";
    }

    std::string message(int code) const override
    {
      switch( file_error(code) )
      {
        case file_error::not_found: return "file not found";
        case file_error::permission_denied: return "permission denied";
        case file_error::disk_full: return "disk full";
        default: return "unknown file error";
      }
    }
  };

  static category c;
  return c;
}

我们还需要告知标准库 file_error 与 std::error_code 兼容, 并提供一个工厂函数, 用来构造 std::error_code 对象, 其原料是 file_error 值:

namespace std
{
  template <>
  struct is_error_code_enum<file_error>: std::true_type
  {
  };
}

std::error_code make_error_code(file_error e)
{
  return std::error_code(int(e), file_error_category());
}

有了这一设置, 如果我们收到一个 std::error_code, 就可以轻松检查它是否表示我们感兴趣的某些 file_error 值:

std::error_code read_file();

....
auto ec = read_file();
if( ec == file_error::not_found || ec == file_error::permission_denied )
{
  // We got either file_error::not_found or file_error::permission_denied
}

之所以可行, 是因为标准库检测到 std::is_error_code_enum<file_error>::value 是 true, 然后使用 make_error_code 创建一个 std::error_code 对象, 并实际用它与 ec 比较.

到目前为止一切顺利, 但请记住, 标准库还定义了另一个类型 std::error_condition. 首先令人困惑的一点是, 就物理表示而言, std::error_condition 与 std::error_code 是完全相同的; 也就是说, 它同样像一对 std::error_category 引用加一个 int. 为什么我们需要两个使用完全相同物理表示的不同类型?

回答这个问题的关键在于理解: std::error_code 对象的设计用途是从函数返回以表示失败. 相反, std::error_condition 对象则绝不应该被传递; 它们的用途是解释正在传递的 std::error_code 值. 其思想是: 在给定的程序中, 可能存在多个不同的 "物理" (也许是平台特定的) std::error_code 值, 它们全都指示同一个 "逻辑" std::error_condition.

由此我们来到关于 std::error_condition 的第二个令人困惑之处: 它使用同样的 std::error_category 类型, 却服务于完全不同的目的: 指定哪些 std::error_code 值等价于哪些 std::error_condition 值.

假设除了 file_error 之外, 我们的程序还使用一个网络库, 该库以另一种错误类别的 std::error_code 来传递失败:

enum class net_error
{
  connection_refused = 1,
  timeout,
  host_unreachable,
  dns_failed
};

// Boilerplate omitted:
// - net_error_category()
// - specialization of std::is_error_code_enum
// - make_error_code factory function for net_error.

现在我们可以用 std::error_condition 来定义逻辑错误条件, 把来自两个库的相关 std::error_code 值归组在一起:

enum class resource_condition (1)
{
  unavailable = 1,
  access_denied
};

std::error_category const & resource_condition_category() (2)
{
  struct category: std::error_category
  {
    char const * name() const noexcept override
    {
      return "resource_condition";
    }

    std::string message(int cond) const override
    {
      switch( resource_condition(cond) )
      {
        case resource_condition::unavailable: return "resource unavailable";
        case resource_condition::access_denied: return "access denied";
        default: return "unknown condition";
      }
    }

    bool equivalent(std::error_code const & code, int cond) const noexcept
    {
      switch( resource_condition(cond) )
      {
        case resource_condition::unavailable: (3)
          return
            code == file_error::not_found ||
            code == net_error::host_unreachable ||
            code == net_error::dns_failed;
        case resource_condition::access_denied: (4)
          return
            code == file_error::permission_denied ||
            code == net_error::connection_refused;
        default:
          return false;
      }
    }
  };

  static category c;
  return c;
}

namespace std
{
  template <> (5)
  struct is_error_condition_enum<resource_condition>: std::true_type
  {
  };
}

std::error_condition make_error_condition(resource_condition e) (6)
{
  return std::error_condition(int(e), resource_condition_category());
}
1 两个逻辑条件的枚举: unavailable 和 access_denied.
2 定义 std::error_category, 用于 std::error_condition 对象, 这些对象表示一个 resource_condition.
3 这里我们指定 file_error::not_found、net_error::host_unreachable 和 net_error::dns_failed 在逻辑上都等价于 resource_condition::unavailable, 以及…​
4 …​file_error::permission_denied 和 net_error::connection_refused 在逻辑上等价于 resource_condition::access_denied.
5 这个特化告知标准库: resource_condition 枚举被设计用于与 std::error_condition 配合.
6 工厂函数, 用于构造 std::error_condition 对象 (由 resource_condition 值而来).

呼!

现在, 如果我们有一个 std::error_code 对象 ec, 就可以像这样轻松检查它是否等价于 resource_condition::unavailable:

if( ec == resource_condition::unavailable )
{
  // The resource is unavailable (file not found, host unreachable, or DNS failed)
}

除了定义 std::error_category, 即用于 std::error_condition 对象 (以 resource_condition 值初始化) 的那一个之外, 我们无需与实际的 std::error_condition 实例交互: 它们是在需要与 std::error_code 比较时创建的, 而这基本上就是它们唯一的用途.

LEAF 中的支持

match 谓词可作为 LEAF 错误处理器的实参, 用于将 std::error_code 与给定的错误条件相匹配. 例如, 要处理 resource_condition::unavailable (见上文), 我们可以使用:

leaf::try_handle_some(

  []
  {
    return open_resource(); // returns leaf::result<resource>
  },

  []( leaf::match<std::error_code, resource_condition::unavailable> m )
  {
    assert(m.matched == resource_condition::unavailable);
    ....
  } );

更多示例参见 match.

Boost Exception 集成

可以不使用 Boost Exception 定义的 boost::get_error_info API, 而直接使用 LEAF 错误处理器. 考虑下面这个 boost::get_error_info 的用法:

typedef boost::error_info<struct my_info_, int> my_info;

void f(); // Throws using boost::throw_exception

void g()
{
  try
  {
    f();
  },
  catch( boost::exception & e )
  {
    if( int const * x = boost::get_error_info<my_info>(e) )
      std::cerr << "Got my_info with value = " << *x;
  } );
}

我们可以改写 g, 使用 LEAF 来访问 my_info:

#include <boost/leaf/handle_errors.hpp>

void g()
{
  leaf::try_catch(

    []
    {
      f();
    },

    []( my_info x )
    {
      std::cerr << "Got my_info with value = " << x.value();
    } );
}

try_catch

接受 my_info 意味着只有当捕获的异常对象携带 my_info 时 (LEAF 经由 boost::get_error_info 访问它), 该处理器才会被选中.

也支持使用 match:

void g()
{
  leaf::try_catch(

    []
    {
      f();
    },

    []( leaf::match_value<my_info, 42> )
    {
      std::cerr << "Got my_info with value = 42";
    } );
}

上例中, 只有当捕获的异常对象携带 my_info 且其 .value() 等于 42 时, 该处理器才会被选中.

本节列出 LEAF 的每个公开头文件, 并说明其提供的定义.

LEAF 的头文件被设计为尽量减少耦合:

  • 仅用于报告或转发 (而非处理) 错误的头文件, 比提供错误处理功能的头文件更轻量.

  • 提供异常处理或抛出功能的头文件, 与提供错误处理或报告但不使用异常的头文件是相互独立的.

也提供独立的单头文件选项; 参见 分发.

效果:

所有 item…​ 对象都会被转发, 与 std::unhandled_exceptions 返回的值一起存储到返回的未指定类型对象中; 该对象应由 auto 捕获, 并在调用作用域中保持存活. 当该对象销毁时, 如果自 on_error 被调用以来发生了错误, LEAF 将处理存储的条目以获得与该失败相关联的错误对象.

发生错误时, LEAF 首先需要推导出一个用于关联错误对象的 error_id 值 err. 这通过以下逻辑完成:

  • 如果 new_error (由调用线程) 曾在 on_error 返回的对象创建之后被调用, 则 err 以 current_error 返回的值初始化;

  • 否则, 如果 std::unhandled_exceptions 返回的值大于其在初始化期间返回的值, 则 err 以 new_error 返回的值初始化;

  • 否则, 所存储的 item…​ 对象被丢弃, 不再采取进一步行动 (没有发生错误).

接下来, LEAF 的处理流程类似于:

err.load(std::forward<Item>(item)...);

区别在于, 与 load 不同, on_error 不会覆盖任何已与 err 相关联的错误对象.

try_handle_some

#include <boost/leaf/handle_errors.hpp>
namespace boost { namespace leaf {

  template <class TryBlock, class... H>
  typename std::decay<decltype(std::declval<TryBlock>()())>::type
  try_handle_some( TryBlock && try_block, H && ... h );

} }
要求:

  • try_block 函数不得接受任何实参.

  • R — 由 try_block 函数返回的类型 — 必须是 result<T> 类型 (参见 is_result_type). try_block 返回 leaf::result<T> 是合法的, 但这并非要求.

  • h…​ 函数中的每一个:

    • 必须返回一个可用于初始化 R 类型对象的类型; 若 R 是一个 result<void> (即成功时不传递值), 则允许返回 void 的处理器. 若选中了这样的处理器, try_handle_some 返回值由 {} 初始化;

    • 可以按值、按 (const) 引用或以指针 (指向 const) 的形式接受任何错误对象;

    • 可以按值接受任何谓词类型的实参: catch_、match、match_value、match_member、if_not, 或任何用户自定义谓词类型 Pred, 只要 is_predicate<Pred>::value 为 true;

    • 可以接受一个 error_info 实参, 按 const & 传递;

    • 可以接受一个 diagnostic_info 实参, 按 const & 传递;

    • 可以接受一个 diagnostic_details 实参, 按 const & 传递.

效果:

  • 创建一个局部 context<E…​> 对象 ctx, 其中 E…​ 类型从 h…​ 中每一个所接受实参的类型自动推导, 保证 ctx 能够存储处理错误所需的全部类型.

  • 调用 try_block:

    • 如果返回的对象 r 指示成功 且 try_block 未抛出异常, 则 r 被转发给调用者.

    • 否则, LEAF 按顺序考察 h…​ 中的每一个处理器, 直到找到一个能够用当前存储在 ctx 中、与 r.error() 相关联的错误对象为其提供实参的处理器. 第一个这样的处理器被调用, 其返回值用于初始化 try_handle_some 的返回值; 若该处理器能够处理该错误, 返回值可指示成功, 否则指示失败.

    • 如果 try_handle_some 无法找到合适的处理器, 它返回 r.

try_handle_some 对异常保持中立: 它自身不抛出异常, 但 try_block 和 h…​ 中的任何一个都允许抛出.
处理器选择流程:

处理器 h 适合处理 r 所报告的失败, 当且仅当 try_handle_some 能够使用当前在 ctx 中可用的、与调用 r.error() 所得错误 ID 相关联的错误对象, 产生其各个实参的值. 一旦确定某个实参值无法产生, 当前处理器即被丢弃, 选择过程继续考察下一个处理器 (如果有的话).

r.error() 的返回值必须可隐式转换为 error_id. 当然, leaf::result 模板满足这一要求. 如果改用外部 result 类型, 通常 r.error() 会返回一个 std::error_code, 它能够传递 LEAF 错误 ID; 参见 互操作性.

如果 err 是 error_id (从 r.error() 获得), 则当前考察的处理器所接受的每个实参 ai 按如下方式产生:

  • 若 ai 的类型为 Ai、Ai const& 或 Ai&:

    • 如果类型为 Ai 且与 err 相关联的错误对象当前存在于 ctx 中, 则 ai 以指向该对象的引用初始化; 否则

    • 若 Ai 派生自 std::exception, 且 try_block 抛出了一个对象 ex (其类型派生自 std::exception), LEAF 会获得 Ai* p = dynamic_cast<Ai*>(&ex). 若 p 为空, 处理器被丢弃; 否则 ai 以 *p 初始化.

    • 否则处理器被丢弃.

    示例:
    ....
auto r = leaf::try_handle_some(

  []() -> leaf::result<int>
  {
    return f();
  },

  [](leaf::e_file_name const & fn) (1)
  {
    std::cerr << "File Name: \"" << fn.value << '"' << std::endl; (2)

    return 1;
  } );

    result | e_file_name

    1 若 try_block 指示失败, 当 ctx 中存储了与该错误相关联的 e_file_name 时, 该处理器将被选中. 由于这是唯一提供的处理器, 若 e_file_name 不可用, try_handle_some 将返回 leaf::result<int>, 即 f 所返回的值.
    2 打印文件名, 处理该错误.

  • 若 ai 的类型为 Ai const* 或 Ai*, 则 try_handle_some 总是能够产生它: 首先尝试按引用接受的方式产生; 若失败, 并不丢弃处理器, 而是 ai 以 0 初始化.

构造函数 | activate | deactivate | is_active | unload | handle_error | context_type_from_handlers

context 类模板为每个指定的 E…​ 类型提供存储. 通常不直接使用 context 对象; 它们在内部被创建, 时机是调用 try_handle_some、try_handle_all 或 try_catch 函数时, 以从传入处理器的实参类型自动推导的类型实例化.

此外, 用户也可以自行创建 context 对象, 如果需要捕获错误对象然后将其传递出去, 办法是移动 context 对象本身.

即便如此, 仍建议用户不要通过显式列出希望 context 模板能够存储的 E…​ 类型来实例化它. 而应使用 context_type_from_handlers 或调用 make_context 函数模板, 它们能从捕获的处理器函数对象列表推导出正确的 E…​ 类型.

要在 context 对象中加载错误对象, 必须先激活它. 激活 context 对象 ctx 会把它绑定到调用线程, 将已存储 E…​ 类型的线程局部指针设置为指向 ctx 中相应的存储. 在任何给定线程中, 完全可能 (甚至很常见) 同时存在多个活动的 context. 此时, 激活/停用必须以 LIFO 方式进行. 因此, 最好使用 context_activator, 它依靠 RAII 来激活和停用 context.

当 context 被停用时, 它与调用线程解绑, 将线程局部指针恢复为 activate 之前的值. 通常, 此时已存储的错误对象 (如果有的话) 要么被丢弃 (默认), 要么被移入调用线程中其他活动的 context 对象的相应存储 (如果可用), 办法是调用 unload.

虽然错误处理通常使用 try_handle_some、try_handle_all 或 try_catch, 但也可以通过调用成员函数 handle_error 来处理错误. 它接受一个 error_id, 并尝试根据存储在 *this 中、与传入的 error_id 相关联的错误对象来选择一个错误处理器.

context 对象可以移动, 只要它们不处于活动状态.
移动活动的 context 会导致未定义行为.

  • 否则, *this 由 new_error 返回的值初始化, 同时 ec 被传给 load, 这使得与 try_handle_some、try_handle_all 或 try_catch 配合使用的处理器能够以 std::error_code 类型的实参接收它.

  };

} }

该类帮助获得一个 error_id 用于关联错误对象, 适用场景是: 通过不使用 LEAF 报告错误 (因此在出错时不返回 error_id) 的不配合 API 传递 LEAF 失败并进行增补时.

该类的常见用法如下:

error_code compute_value( int * out_value ) noexcept; (1)

leaf::result<int> augmenter() noexcept
{
  leaf::error_monitor cur_err; (2)

  int val;
  auto ec = compute_value(&val);

  if( failure(ec) )
    return cur_err.assigned_error_id().load(e1, e2, ...); (3)
  else
    return val; (4)
}
1 不使用 LEAF 的第三方 API, 但可能导致调用一个使用 LEAF 的用户回调. 当我们的回调报告失败时, 我们会用调用作用域中可用的错误对象来增补它, 即使 compute_value 无法传递一个 error_id.
2 初始化一个 error_monitor 对象.
3 对 compute_value 的调用已失败:

  • 如果 new_error 在 augment 对象初始化之后 (由调用线程) 被调用过, assigned_error_id 返回 error_id 的最后一个值, 该值由 new_error 返回. 若失败源于我们的回调 (由 compute_value 在内部调用), 就属于这种情况.

  • 否则, assigned_error_id 调用 new_error 并返回该 error_id.
4 调用成功, 返回计算出的值.

check 函数的工作方式类似, 但它不调用 new_error, 而是返回一个默认初始化的 error_id.

result<T> 类型可由产生 T 类型值但可能失败的函数返回.

要求:

T 必须可移动, 且其移动构造函数不得抛出.

不变式:

result<T> 对象处于三种状态之一:

  • 值状态 (Value state), 此时它包含一个 T 类型的对象, 且可以使用 value / operator* / operator-> 访问所包含的值.

  • 错误状态 (Error state), 此时它包含一个错误 ID, 调用 value 会抛出 leaf::bad_result.

  • 动态捕获状态 (Dynamic capture state), 与错误状态相同, 但除错误 ID 外, 它还持有一个动态捕获的错误对象列表; 参见 try_capture_all.

result<T> 对象可无异常移动, 但不可拷贝.

参考: 谓词

每个参考小节的内容按字母顺序组织.

谓词是一种特殊的错误处理器实参类型, 它使 处理器选择流程能够考虑可用错误对象的值, 而不仅是其类型; 参见 使用谓词处理错误.

可用的谓词如下:

  • match

  • match_value

  • match_member

  • catch_

  • if_not

此外, 任何用户自定义类型 Pred, 只要 is_predicate<Pred>::value 为 true, 就会被视为谓词. 此时要求:

  • Pred 定义一个可访问的成员类型 error_type, 用于指定它所需的错误对象类型;

  • Pred 定义一个可访问的静态成员函数 evaluate, 它返回布尔类型, 且可以用一个 error_type const & 类型的对象调用;

  • 一个 Pred 实例可以用 error_type 类型的对象初始化.

当错误处理器接受一个谓词类型 Pred 的实参时, 处理器选择流程会在错误对象 e (其类型为 Pred::error_type) 不可用时丢弃该处理器. 否则, 若 Pred::evaluate(e) 返回 false, 处理器也被丢弃. 若处理器被调用, Pred 实参以 Pred{e} 初始化.

谓词在错误处理器被调用之前求值, 因此它们不得访问动态状态 (当然, 错误处理器本身可以访问动态状态, 例如通过 lambda 表达式捕获).
示例 1:
enum class my_error { e1 = 1, e2, e3 };

{
  using error_type = my_error; (1)

  static bool evaluate(my_error) noexcept; (2)

  my_error matched; (3)
};

namespace boost { namespace leaf {

  template <>
  struct is_predicate<my_pred>: std::true_type
  {
  };

} }

2 处理器选择流程将以一个 e 对象 (类型为 my_error) 调用此函数来求值该谓词…​
3 …​若求值成功, 则初始化 my_pred 错误处理器实参, 初值为 my_pred{e}.

当错误处理器接受 match<E, V…​> 类型的实参时, 处理器选择流程首先检查错误对象 e (类型为 E) 是否可用. 若不可用, 处理器被丢弃. 否则, 若以下条件不满足, 处理器也被丢弃:

p1 || p2 || …​ pn.

其中 pi 等价于 e == Vi, 除非 Vi 是指向函数的指针

bool (*Vi)(T x).

此时要求 Vi != 0, 且 x 能够以 E const & 初始化, 然后 pi 等价于:

Vi(e).

std::is_error_code_enum<Enum>::value || std::is_error_condition_enum<Enum>::value.

&e.category() == &std::error_code(Enum{}).category().

配置

可识别的配置宏如下:

  • BOOST_LEAF_CFG_DIAGNOSTICS: 把该宏定义为 0 会将 diagnostic_info 和 diagnostic_details 都替换为空桩 (若该宏未定义, LEAF 会将其定义为 1).

  • BOOST_LEAF_CFG_STD_SYSTEM_ERROR: 把该宏定义为 0 会禁用 std::error_code / std::error_condition 集成. 此时 LEAF 不执行 #include <system_error>, 这对嵌入式平台而言可能开销过大 (若该宏未定义, LEAF 会将其定义为 1).

  • BOOST_LEAF_CFG_STD_STRING: 把该宏定义为 0 会禁用 std::string 的一切使用 (这同时要求 BOOST_LEAF_CFG_DIAGNOSTICS=0). 此时 LEAF 不执行 #include <string>, 这对嵌入式平台而言可能开销过大 (若该宏未定义, LEAF 会将其定义为 1).

  • BOOST_LEAF_CFG_CAPTURE: 把该宏定义为 0 会禁用 try_capture_all, 后者 (仅在使用时) 会动态分配内存 (若该宏未定义, LEAF 会将其定义为 1).

  • BOOST_LEAF_CFG_GNUC_STMTEXPR: 该宏控制 BOOST_LEAF_CHECK 是否以 GNU C 语句表达式 的形式定义, 后者使其能够以类似某些语言中问号运算符的方式检查错误 (参见 检查错误). 默认情况下, 该宏被定义为 1 (在 __GNUC__ 之下), 否则定义为 0.

  • BOOST_LEAF_CFG_WIN32: 该宏控制 Win32 API 的使用. 若不定义, LEAF 会将其定义为 0 (即使在 Windows 上也是如此, 因为包含 windows.h 通常并不可取). 可取的值有:

    • 0: 禁用所有 Win32 特有功能.

    • 1: 包含 windows.h 并启用 e_LastError 支持 (否则该支持被替换为空桩).

    • 2: 另外, 还会让 LEAF 改用 Win32 TLS API 而非 C++11 的 thread_local, 使错误对象能够跨 DLL 边界使用.

  • BOOST_LEAF_NO_EXCEPTIONS: 禁用所有异常处理支持. 若不定义, LEAF 会依据编译器配置自动定义它 (例如 -fno-exceptions).

  • BOOST_LEAF_NO_THREADS: 禁用 LEAF 中的全部线程安全机制.

配置线程局部存储 (TLS) 访问

LEAF 需要支持线程局部的 void 指针. 可用的 TLS 实现有:

  • C++11 的 thread_local 关键字 (默认).

  • Win32 TLS API: 通过定义 BOOST_LEAF_CFG_WIN32=2 选择. 这使错误对象能够跨 DLL 边界使用.

  • 自定义 TLS 数组: 通过定义 BOOST_LEAF_USE_TLS_ARRAY 选择. 它面向 嵌入式平台, 即 C++11 的 thread_local 关键字不可用或不适用的场合.

使用 BOOST_LEAF_USE_TLS_ARRAY 时, 用户需要定义以下两个函数来实现所需的 TLS 访问:

namespace boost { namespace leaf {

namespace tls
{
    void * read_void_ptr( int tls_index ) noexcept;
    void write_void_ptr( int tls_index, void * p ) noexcept;
}

} }
为了效率, read_void_ptr 和 write_void_ptr 应当以 inline 方式定义.

在 BOOST_LEAF_USE_TLS_ARRAY 下, 还可识别以下附加配置宏:

  • BOOST_LEAF_CFG_TLS_ARRAY_START_INDEX 指定可供 LEAF 使用的 TLS 数组起始索引 (若该宏未定义, LEAF 会将其定义为 0).

  • BOOST_LEAF_CFG_TLS_ARRAY_SIZE 可以定义用来指定 TLS 数组的大小. 此时 TLS 索引会先经 BOOST_LEAF_ASSERT 校验, 然后才传给 read_void_ptr / write_void_ptr.

  • BOOST_LEAF_CFG_TLS_INDEX_TYPE 可以定义用来指定存储已分配 TLS 索引的整数类型 (若该宏未定义, LEAF 会将其定义为 unsigned char).

TLS 槽位只为错误处理器中使用的类型分配. LEAF 所需的 TLS 指针数组的最小大小是: 用作错误处理器实参的不同类型的总数 (整个程序范围内), 再加一.
当心 read_void_ptr/write_void_ptr 访问超出线程局部指针数组静态边界的线程局部指针; 这很可能导致未定义行为.

设计原理

定义:

携带错误条件信息的对象称为错误对象. 例如, std::error_code 类型的对象就是错误对象.

下面的论述与传递错误对象所用的机制无关, 无论是异常处理还是其他任何机制.
定义:

根据与错误对象的交互方式, 函数可分为以下几类:

  • 错误发起: 通过创建新错误对象来发起错误条件的函数.

  • 错误中立: 把其所调用的低层函数传递出的错误对象转发给调用者的函数.

  • 错误处理: 处置其收到的错误对象、恢复程序正常运行的函数.

一个关键观察是: 错误发起函数通常是缺乏任何上下文的低层函数, 它们无法确定 — 更谈不上规定 — 针对其可能发起的错误, 程序应当如何正确响应. 在某些程序中 (正确地) 导致终止的错误条件, 在另一些程序中可能 (正确地) 被忽略; 还有一些程序可能会从中恢复并继续正常运行.

同样的论述也适用于 错误中立函数, 但此时还有一个额外的问题: 它们需要传递的错误, 一般是由调用链中距其多层之外的函数发起的, 这些函数通常是 — 也应当被视为 — 实现细节. 错误中立函数不应与 错误发起函数所传递的错误对象类型耦合, 理由与其不应与对方接口的任何其他方面耦合相同.

最后, 错误处理函数按定义拥有处理至少部分 (即使不是全部) 失败所需的完整上下文. 在它们的作用域内, 作者必须确切知道低层函数必须传递哪些信息才能从每个错误条件中恢复, 这是绝对必要的. 具体而言, 这些必要信息无一可以作为实现细节对待; 此时, 在 错误中立函数中需要避免的耦合在这里反而是可取的.

现在我们可以定义我们的

设计目标:

  • 错误发起函数应当能够传递它们可获得的、与所报告失败相关的全部信息.

  • 错误中立函数不应与低层 错误发起函数传递的错误类型耦合. 它们应当能够用自己可获得的额外相关信息增补任何失败.

  • 错误处理函数应当能够访问 错误发起或 错误中立函数所传递的、处理失败所需的全部信息.

"错误中立函数不与穿过它们的错误对象的静态类型耦合" 这一设计目标, 似乎要求动态多态, 因而要求动态内存分配 (Boost Exception 库以动态内存分配为代价满足了这一设计目标).

事实证明, 由于以下原因, 动态内存分配并非必要

事实:

  • 错误处理函数 "知道" 错误发起与 错误中立函数能够传递的信息中, 哪些是在特定程序中处理失败实际需要的. 理想情况下, 不应 使用浪费资源去存储或传递当前处理错误并不需要的信息, 即使它与该失败相关.

例如, 如果一个库函数能够传递错误码, 但程序并不需要知道确切的错误码, 那么当该库函数试图传递这一信息时就可以将其忽略. 另一方面, 如果某个 错误处理函数需要该信息, 那么存储它所需的内存可以在其作用域内静态预留.

LEAF 的 try_handle_some、try_handle_all 和 try_catch 函数实现了这一思想. 用户提供错误处理 lambda 函数, 每个函数接受的实参类型就是它从特定错误条件中恢复所需的类型. LEAF 为这些类型预留存储 (使用自动存储期), 直到它们被传给合适的处理器.

报告错误时, LEAF 检查每种错误对象类型是否有可用存储:

  • 若有可用存储, 对象直接存储在错误处理作用域中, 绕过中间的所有 错误中立函数.

  • 若无可用存储, 该错误对象被丢弃, 因为没有任何错误处理函数会用到它 — 从而节省资源.

每次错误发生都会被赋予一个唯一的 error_id, 以防止处理器访问来自先前失败的过时错误对象. 要处理一个失败, LEAF 把可用的错误对象 (按其 error_id) 与每个处理器要求的实参类型相匹配.

LEAF 以 BOOST_LEAF_SYMBOL_VISIBLE 声明以下类型: error_id、error_info、diagnostic_info、diagnostic_details、e_api_function、e_file_name、e_errno、e_type_info_name、e_at_line、e_source_location、bad_result、result<T>.

Windows

要跨 DLL 边界使用错误对象, 请定义 BOOST_LEAF_CFG_WIN32=2. 这会让 LEAF 改用 Win32 TLS API 而非 C++11 的 thread_local. 不支持 DLL 的动态卸载.

链接到不同 CRT 配置 (静态或动态) 的模块可以共享 LEAF 错误对象. 但是, 要让两个模块共享错误对象, 它们必须用相同的编译器编译 (不必是相同的编译器版本). 例如, 如果一个模块用 MSVC 编译, 另一个用 GCC 编译, 错误对象将不会在它们之间共享.

下面我们将 Boost LEAF 与这些替代方案作一比较.

比较: std::expected

std::expected<T, E> 在 C++23 中引入, 是一种词汇类型, 用于返回 T 类型的值或 E 类型的错误的函数. 它的用途与 leaf::result<T> 类似, 但设计不同:

  • std::expected<T, E> 把错误类型 E 编码进函数签名. leaf::result<T> 不指定错误类型; 错误对象单独传递.

  • 使用 std::expected 时, 函数只能返回一个 E 类型的错误对象. LEAF 允许把多个不同类型的错误对象与同一次失败相关联.

  • LEAF 的 on_error 允许中间函数在错误传播时附加额外上下文, 而无需修改函数签名.

二者之间的选择取决于: 是否希望在函数签名中编码错误类型, 以及是否需要把多个错误对象与单次失败相关联.

与 Boost Outcome 的比较

与 LEAF 一样, Boost Outcome 也是为低延迟环境设计的. 它提供 result<T,EC,NVP> 和 outcome<T,EC,EP,NVP>, 其中 EC 是错误码类型 (默认为 std::error_code), EP 是用于附加错误信息的指针类型 (默认为 std::exception_ptr).

关键的设计差异在于错误信息的传递方式:

  • Outcome 通过 EC 和 EP 模板参数把错误类型编码进函数签名, 让调用者明确看到可能的错误类型.

  • LEAF 将 leaf::result<T> 与错误类型完全解耦. 错误对象被单独传递到错误处理作用域, 由处理器决定需要哪些类型.

LEAF 示例中包含对 Boost Outcome result<> 教程中程序的改编. 你可以在 GitHub 上查看.
LEAF 与 outcome::result<T> 兼容; 你不必使用 leaf::result<T>.

互操作性问题

Boost Outcome 文档讨论了集成多个使用不同错误类型的库所面临的挑战:

如果库 A 使用 result<T, libraryA::failure_info>, 库 B 使用 result<T, libraryB::error_info>, 依此类推, 那么对于把这些第三方依赖引入并整合成一个应用程序的应用程序作者而言, 问题就出现了. 一般而言, 每个第三方库作者都不会为未知的其他第三方库内置显式的互操作支持. 因此问题落在应用程序作者身上.

应用编写者有三种选择之一:

  1. 在应用程序中, 使用的 result 形式是 result<T, std::variant<E1, E2, …​>>, 其中 E1, E2 … 是应用程序所用每个第三方库的失败类型. 这样做的好处是精确保留原始信息, 但会带来使用上的不便, 并可能造成高层与实现细节之间过度的耦合.

  2. 可以在失败离开第三方库、进入应用之时, 把第三方的失败类型翻译/映射成应用的失败类型. 比方说, 可以用包住应用对第三方 API 的每次调用的 C 预处理器宏来做. 这种做法可能丢失原始失败细节, 或在两个系统的映射不是一一对应时于特定情形下错误映射.

  3. 一种做法是把第三方的失败类型类型擦除成某个应用程序失败类型, 必要时再重新还原. 这是最干净的方案, 耦合问题最少, 也没有错误映射问题, 但它几乎必然需要使用 malloc, 而前两种方案无需如此.

Boost Outcome 通过在 outcome::convert 命名空间中提供转换器来在错误类型之间转换, 从而解决这一问题 (方案 2).

LEAF 采取不同的方式: 错误对象被直接传递到错误处理作用域, 存储在其中静态分配, 无需动态分配即实现了方案 3.

与 Boost Exception 的比较

LEAF 与 Boost Exception 都允许随异常传递任意错误信息. 关键的设计差异:

  • Boost Exception 把错误对象存储在异常对象本身中 (需要动态分配). LEAF 把错误对象存储在错误处理作用域中, 并丢弃处理器不需要的对象.

  • Boost Exception 只能增补派生自 boost::exception 的异常. LEAF 可以增补任何异常类型.

  • Boost Exception 通过 boost::exception_ptr 自动跨线程边界捕获错误对象. LEAF 需要显式使用 [capture].

LEAF 可以用其错误处理接口访问 Boost Exception 的错误信息. 参见 Boost Exception 集成.
