服务器推送

Redis 服务器可以向客户端发送各种推送消息. Boost.Redis 将它们作为一等操作提供支持. 本页描述如何接收和处理这些消息.

最常见的情况是 Pub/Sub 消息 (由 PUBLISH 触发) . 下面的示例展示了一个典型的接收者:

auto receiver(std::shared_ptr<connection> conn) -> asio::awaitable<void>
{
   generic_flat_response resp;
   conn->set_receive_response(resp);

   // Subscribe to the channel 'mychannel'. You can add any number of channels here.
   request req;
   req.subscribe({"mychannel"});
   co_await conn->async_exec(req);

   // You're now subscribed to 'mychannel'. Pushes sent over this channel will be stored
   // in resp. If the connection encounters a network error and reconnects to the server,
   // it will automatically subscribe to 'mychannel' again. This is transparent to the user.
   // You need to use specialized request::subscribe() function (instead of request::push)
   // to enable this behavior.

   // Loop to read Redis push messages.
   while (conn->will_reconnect()) {
      // Wait for pushes
      auto [ec] = co_await conn->async_receive2(asio::as_tuple);

      // Check for errors and cancellations
      if (ec) {
         std::cerr << "Error during receive: " << ec << std::endl;
         break;
      }

      // This can happen if a SUBSCRIBE command errored (e.g. insufficient permissions)
      if (resp.has_error()) {
         std::cerr << "The receive response contains an error: " << resp.error().diagnostic
                   << std::endl;
         break;
      }

      // The response must be consumed without suspending the
      // coroutine i.e. without the use of async operations.
      for (push_view elem : push_parser(resp.value())) {
         std::cout << "Received message from channel " << elem.channel << ": " << elem.payload
                   << "\n";
      }

      resp.value().clear();
   }
}

步骤概要:

  • 在任何其他与接收相关的调用之前调用 connection::set_receive_response, 使连接将传入的推送存储到给定对象中. 库不会复制响应; 您必须在接收循环期间保持其有效.

  • 用 request::subscribe (或 psubscribe) 构建请求并执行它. 如果连接断开并重新建立, 会自动发送一个等价的 SUBSCRIBE.

  • 在 connection::will_reconnect 为 true 时循环 (即直到连接被取消) .

  • 调用 connection::async_receive2 等待直到至少有一个推送可用. 该函数还参与推送的流量控制 (参见 流量控制) .

  • 完成后, resp 保存收到的推送的原始 RESP3 节点 (resp3::node_view) . 对于由 PUBLISH 产生的 Pub/Sub 消息, 使用 push_parser 来遍历它们. 每条解析后的消息都会暴露频道、载荷, 以及 (对于模式订阅 (PSUBSCRIBE) ) 匹配的模式.

  • 调用 resp.value().clear() 以丢弃当前推送数据, 为下一批腾出空间.

消费所有推送数据时不要挂起当前协程 (也不要以其他方式重新进入事件循环) . 关于必须挂起时的处理方式, 参见 挂起接收者.
您可以对接收推送和普通请求/响应流量使用同一个连接. Boost.Redis 依靠 RESP3 在单个连接上对它们进行多路复用.

动态 Pub/Sub 跟踪

当您执行用 request::subscribe (或 psubscribe、unsubscribe、punsubscribe) 构建的请求时, 连接会对它进行跟踪. 重连后, 连接会重新发出订阅命令, 以恢复重连前处于活动状态的订阅. 您可以动态订阅和取消订阅频道; 跟踪是完全动态的.

流量控制

如果服务器发送推送的速度快于客户端消费的速度, 连接会应用流量控制. 在读取了一定数量尚未消费的推送后, 它会停止读取, 直到应用程序排空接收缓冲区. 这会在 TCP 层面产生背压.

每次 async_receive2 完成时, 未决计数都会重置. 您仍须像示例中那样, 通过对响应调用 resp3::flat_tree::clear() (或等价函数) 来释放内存.

不要在接收循环内调用 async_exec. 您的请求的响应可能排在足够多的推送之后, 足以触发流量控制机制, 从而导致死锁.

订阅确认

每次订阅一个频道时, Redis 都会发送一个推送作为确认. 这些确认会存储在您的接收响应中, 并像其他推送一样使 async_receive2 完成. push_parser 会跳过这些消息, 因为它们不包含应用层信息.

因此, 当只收到确认时, async_receive2 会完成而 push_parser 范围为空. 您的代码应正确处理空范围的情况.

要处理订阅确认或其他推送形态, 请直接使用 generic_flat_response 中的原始节点 (参见 高级场景) .

挂起接收者

在完全消费当前推送数据之前, 不得挂起接收者协程. 如果需要对该数据执行 I/O (例如通过 WebSocket 发送) , 请先在不挂起的情况下将其拷贝或序列化, 然后清除响应, 之后再执行异步操作.

例如, 以下做法是不正确的:

auto [ec] = co_await conn->async_receive2(asio::as_tuple);
// DON'T DO THIS: more pushes may be read while the WebSocket send runs,
// and they are discarded when you clear(), causing a race.
co_await websocket.async_send(push_parser(resp.value()));
resp.value().clear();

正确做法是: 先在没有 I/O 的情况下拷贝或组装消息, 然后清除, 最后发送:

auto [ec] = co_await conn->async_receive2(asio::as_tuple);

// Compose the WebSocket message without any I/O (no suspension).
// msg must not reference resp.
auto msg = compose_websocket_message(push_parser(resp.value()));

resp.value().clear();

// Now it's OK to suspend the coroutine
co_await websocket.async_write(msg);

SUBSCRIBE 错误

SUBSCRIBE 可能失败 (例如由于 ACL 规则) . 由于协议的工作方式, 这类错误可能以类似推送的数据形式送达. 使用 generic_flat_response (adapter::result<resp3::flat_tree> 的别名, 类似于 std::expected) 可以检测到它们: 在遍历之前检查 resp.has_error() 并处理错误. 参见本页顶部的示例.

高级场景

push_parser 只识别标准的 Pub/Sub message 和 pmessage 推送. 其他推送类型会被跳过, 包括:

  • 订阅/取消订阅确认.

  • 客户端缓存 失效消息.

  • MONITOR 命令的输出.

如果需要处理这些, 请直接操作 generic_flat_response 中的节点而不是 push_parser. 整体接收模式 (设置响应、订阅、用 async_receive2 循环、消费、清除) 保持不变.
