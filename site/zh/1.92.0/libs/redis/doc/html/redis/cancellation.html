取消与超时

默认情况下, 使用 async_exec 运行请求时会一直等待, 直到 async_run 建立起与 Redis 服务器的连接. 如果服务器宕机, 这可能耗费很长时间.

因此, 对于 async_exec 操作, 通常最好使用 asio::cancel_after 完成标记设置超时:

using namespace std::chrono_literals;

// Compose a request with a SET command
request req;
req.push("SET", "my_key", 42);

// If the request hasn't completed after 10 seconds, it will be cancelled
// and an exception will be thrown.
co_await conn.async_exec(req, ignore, asio::cancel_after(10s));

完整代码清单参见我们的 超时示例.

您还可以将 cancel_after 与其他完成风格 (如回调与 future) 一起使用.

cancel_after 之所以有效, 是因为 async_exec 支持按操作取消机制. Boost.Asio 使用该机制来实现 cancel_after 与并行组 (parallel groups) 等特性. 库中的所有异步操作都支持这一机制. 更多信息请查阅各个操作的文档.

重试幂等请求

前面提到, async_exec 会等待服务器就绪后再发送请求. 但如果在发送请求之后、接收响应之前发生通信错误, 会发生什么?

在这种情况下, 无法得知服务器是否已处理该请求. 默认情况下, 库会将该请求视为失败, async_exec 将以 asio::error::operation_aborted 错误码完成.

有些请求执行多次与执行一次的结果相同. 我们称这类请求是 幂等的. SET 命令是幂等的, 而 INCR 则不是.

如果您知道 request 对象只包含幂等命令, 可以指示 Boost.Redis 在失败时重试该请求, 即使库不确定服务器是否已处理该请求. 为此, 请将 cancel_if_unresponded 在 request::config 中设置为 false:

// Compose a request
request req;
req.push("SET", "my_key", 42); // idempotent
req.get_config().cancel_if_unresponded = false; // Retry the request even if it was written but not responded

// Makes sure that the key is set, even in the presence of network errors.
// This may suspend for an unspecified period of time if the server is down.
co_await conn.async_exec(req, ignore);
