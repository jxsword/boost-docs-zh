boost::redis::connection::async_receive2

异步等待服务器推送.

概要

声明于 <boost/redis/connection.hpp>

template<class CompletionToken = asio::deferred_t>
auto
async_receive2(CompletionToken&& token = {});

说明

此函数挂起, 直到连接收到至少一个服务器推送. 完成时, 会有数量不定的推送被添加到用 set_receive_response 设置的响应对象中. 使用响应对象中的函数来了解收到了多少条消息并消费它们.

为防止收到无限数量的推送, 当内部累积 256 个推送时, 连接会阻塞套接字上的后续读取操作 (我们不承诺这一确切数字) . 发生这种情况时, 任何 `async_exec` 和健康检查都无法取得进展, 连接最终可能超时. 为避免这种情况, 期望接收服务器推送的应用程序应在循环中持续调用此函数.

应使用此函数替代已弃用的 async_receive. 它与 async_receive 的区别如下:

  • async_receive 被设计为一次消费一条推送消息. 在接收大量服务器推送时这可能效率低下. async_receive2 是面向批量的. 调用 async_receive2 时所有可用的推送都会被标记为已消费.

  • async_receive 在重连发生时 (例如由于网络错误) 会被取消. 这使用户能够在再次等待推送之前使用 async_exec 重新建立订阅. 随着 request::subscribe 等函数的引入, 订阅会在重连时自动重新建立. 因此, async_receive2 不会在重连时被取消.

  • async_receive 传递每条收到的推送消息包含的字节数. 这一信息不可靠也不太有用. 可以使用响应对象中的函数获取等价信息.

  • async_receive 可能会在 async_run 被取消时被取消. async_receive2 则不会发生这种情况.

此函数不会从传递给如下函数的响应对象中移除消息: set_receive_response

  • 请使用响应对象中的函数来实现这一点.

对于给定的连接, 任何时刻只能有一个 async_receive2 实例处于未完成状态. 尝试启动第二个实例将以 error::already_running 失败.

为避免死锁, 调用 async_receive2 的任务 (例如协程) 不应以可能相互阻塞的方式调用 async_exec. 也就是说, 请避免以下模式:

 
asio::awaitable<void> receiver()
{
   // Do NOT do this!!! The receive buffer might get full while
   // async_exec runs, which will block all read operations until async_receive2
   // is called. The two operations end up waiting each other, making the connection unresponsive.
   // If you need to do this, use two connections, instead.
   co_await conn.async_receive2();
   co_await conn.async_exec(req, resp);
}

示例参见 cpp20_subscriber.cpp.

完成标记必须具有以下签名:

void f(system::error_code);

按操作取消

此操作支持以下取消类型:

  • asio::cancellation_type_t::terminal.

  • asio::cancellation_type_t::partial.

  • asio::cancellation_type_t::total.
