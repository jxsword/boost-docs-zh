与其他 Redis 客户端的比较

比较

我开始编写 Boost.Redis 的主要原因是想要一个与 Asio 异步模型兼容的客户端. 随着工作的推进, 我也得以解决我认为其他库中存在的弱点. 由于时间所限, 我无法对 官方列表 中列出的每个客户端进行详细比较. 因此, 我将聚焦于 github 上按星标数计最受欢迎的 C++ 客户端, 即:

https://github.com/sewenew/redis-plus-plus

Boost.Redis 对比 Redis-plus-plus

在开始之前, 有必要提一下 redis-plus-plus 不支持的一些方面

  • 最新版本的通信协议 RESP3. 没有它就无法支持一些重要的 Redis 特性, 例如客户端缓存等.

  • 协程.

  • 直接读入用户数据结构中的响应, 以避免创建临时对象.

  • 带错误码支持的错误处理.

  • 取消.

其余各点将分别讨论. 我们先来看看发送一条命令、一个流水线和一个事务是什么样子

auto redis = Redis("tcp://127.0.0.1:6379");

// Send commands
redis.set("key", "val");
auto val = redis.get("key"); // val is of type OptionalString.
if (val)
    std::cout << *val << std::endl;

// Sending pipelines
auto pipe = redis.pipeline();
auto pipe_replies = pipe.set("key", "value")
                        .get("key")
                        .rename("key", "new-key")
                        .rpush("list", {"a", "b", "c"})
                        .lrange("list", 0, -1)
                        .exec();

// Parse reply with reply type and index.
auto set_cmd_result = pipe_replies.get<bool>(0);
// ...

// Sending a transaction
auto tx = redis.transaction();
auto tx_replies = tx.incr("num0")
                    .incr("num1")
                    .mget({"num0", "num1"})
                    .exec();

auto incr_result0 = tx_replies.get<long long>(0);
// ...

此 API 的一些问题包括

  • 对命令、流水线和事务的处理方式不一致. 这使得自动流水线 (auto-pipelining) 不可能实现.

  • 任何发送单条命令的 API 适用范围都非常有限, 出于性能原因应避免使用.

  • 该 API 强制用户使用异常, 没有提供错误码重载.

  • 无法为新调用 (例如 redis.get) 重用缓冲区, 以避免进一步的动态内存分配.

  • 解析与连接的错误处理不清晰.

在 Boost.Redis 中, 发送一条命令、一个流水线或一个事务没有区别, 因为请求与 I/O 对象是解耦的.

redis-plus-plus 也支持异步接口, 但对 Transaction 和 Subscriber 的异步支持仍在开发中.

其异步接口依赖第三方事件库, 目前仅支持 libuv.

redis-plus-plus 中的异步代码如下所示

auto async_redis = AsyncRedis(opts, pool_opts);

Future<string> ping_res = async_redis.ping();

cout << ping_res.get() << endl;

读者可以看到, 该异步接口基于 future, 而 future 的性能不佳也是众所周知的. 然而这种异步设计最大的问题在于它使正确编写异步程序成为不可能: 它为每条发送的命令启动一个异步操作, 而不是将消息入队并在可以发送时触发写入. 同样不清楚的是, 这种设计如何 (乃至能否) 实现流水线.
