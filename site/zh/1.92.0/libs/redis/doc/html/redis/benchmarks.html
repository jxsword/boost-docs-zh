回显服务器基准测试

本文档对我在不同语言中使用不同 Redis 客户端实现的 TCP 回显服务器的性能进行了基准测试. 选择回显服务器的主要动机如下:

  • 实现简单, 在大多数语言中都不需要专业级的技能.

  • 受 I/O 限制: 回显服务器通常 CPU 占用极低, 因此非常适合用来衡量程序处理并发请求的能力.

  • 在并发方面, 它能很好地模拟典型的后端服务.

我还对实现施加了一些约束

  • 它应当足够简单, 且不需要编写过多代码.

  • 优先使用标准惯用法, 避免需要专家级水平的优化.

  • 避免使用连接和线程池之类的复杂设施.

要复现这些结果, 请在一个终端中运行其中一个回显服务器程序, 在另一个终端中运行 echo-server-client.

不使用 Redis

首先我测试了一个纯 TCP 回显服务器, 即不与 Redis 交互而直接将消息发送给客户端的服务器. 结果如下所示

测试在本机上以 1000 个并发 TCP 连接进行, 本地环回的平均延迟为 0.07ms. 在延迟更高的网络上, 各库之间的差距预计会缩小.

  • 我预期 Libuv 的性能与 Asio 和 Tokio 相近.

  • 考虑到它是 JavaScript 代码, 我确实预期 nodejs 会稍逊一筹. 除此之外, 我预期它与 libuv 性能相近, 因为 libuv 正是其底层框架.

  • Go 确实令我惊讶: 比 nodejs 和 libuv 还快!

读者可以看到, Libuv 与 Rust 的测试并未在图中绘出, 原因如下

  • redis-rs: 该客户端远远落后, 若与其他基准测试画在一起, 其余结果会显得微不足道. 我不确定它为何如此之慢, 我猜想与其缺少自动 流水线 (pipelining) 支持有关. 实际上, 我启动的 TCP 连接越多, 其性能越差.

  • Libuv: 我没有将其绘出, 因为这需要我编写过多的 C 代码. 具体而言, 我将不得不使用 hiredis 并手动实现对流水线的支持.
