常见问题 (FAQ)

Q. 我无法让 regex++ 正确处理转义字符, 这是怎么回事?

A. 如果你在 C++ 代码中嵌入正则表达式, 请记住转义字符会被处理两次: 一次由 C++ 编译器处理, 一次由 Boost.Regex 表达式编译器处理, 因此要把正则表达式 \d+ 传给 Boost.Regex, 你需要在代码中嵌入 "\d+". 同样, 要匹配字面反斜杠, 你需要在代码中嵌入 "\\".

Q. 无论怎么做, regex_match 总是返回 false, 这是怎么回事?

A. 算法 regex_match 只在表达式匹配全部文本时才会成功; 如果你想在文本中查找与表达式匹配的子串, 请改用 regex_search.

Q. 为什么在 POSIX 正则表达式中使用括号会改变匹配结果?

A. 对于 POSIX (扩展和基本) 正则表达式 (但不包括 perl 正则表达式), 括号不仅用于标记, 还用于确定最佳匹配. 当表达式被编译为 POSIX 基本或扩展正则表达式时, Boost.Regex 遵循 POSIX 标准的最左最长规则来确定匹配内容. 因此, 如果在考虑整个表达式之后仍存在多个可能的匹配, 它会接着查看第一个子表达式, 然后是第二个子表达式, 依此类推. 所以...

用 "(0*)([0-9]*)" 匹配 "00123" 将产生 $1 = "00" $2 = "123"

而

用 "0*([0-9])*" 匹配 "00123" 将产生 $1 = "00123"

想一想: 如果 $1 只匹配了 "123", 那么这个匹配就比 "00123" "更差", 因为后者位置更靠左且更长. 如果你希望 $1 只匹配 "123" 部分, 就需要使用类似下面这样的内容:

"0*([1-9][0-9]*)"

作为表达式.

Q. 为什么字符范围不能正常工作 (仅限 POSIX 模式)?

A. POSIX 标准规定字符范围表达式是区分区域设置的 - 例如表达式 [A-Z] 会匹配排列顺序介于 'A' 和 'Z' 之间的任何排序元素. 这意味着对于 "C" 或 "POSIX" 之外的大多数区域设置, [A-Z] 举例来说会匹配单个字符 't', 这不是大多数人所期望的 - 或者至少不是大多数人从正则表达式引擎那里习以为常的预期. 出于这个原因, Boost.Regex 的默认行为 (perl 模式) 是通过不设置 regex_constants::collate 编译期标志来关闭区分区域设置的排序. 但是, 如果你设置了非默认的编译期标志 - 例如 regex_constants::extended 或 regex_constants::basic, 则会启用依赖区域设置的排序; 这同样适用于内部使用 regex_constants::extended 或 regex_constants::basic 的 POSIX API 函数. [注意 - 当 regex_constants::nocollate 生效时, 无论 LC_COLLATE 区域设置类别实际设置为什么, 库的行为都"如同"该类别始终为 "C" - 注释结束].

Q. 为什么这些函数都没有异常抛出规范? 库可能抛出哪些异常?

A. 并非所有编译器都支持 (或遵循) 异常抛出规范, 有些编译器虽支持但效率会降低. 随着编译器对此的处理逐渐改善, 日后可能会加入异常抛出规范. 本库只应抛出三类异常: [boost::regex_error] 可由 basic_regex 在编译正则表达式时抛出; std::runtime_error 可在对 basic_regex::imbue 的调用试图打开一个不存在的消息目录时抛出, 或在对 regex_search 或 regex_match 的调用导致"永无止境"的搜索时抛出, 或在对 RegEx::GrepFiles 或 RegEx::FindFiles 的调用试图打开一个无法打开的文件时抛出; 最后, std::bad_alloc 可由本库中的几乎所有函数抛出.

Q. 为什么我不能使用 regex_match / regex_search / regex_grep / regex_format / regex_merge 的"便捷"版本?

A. 这些版本是否可用取决于编译器的能力; 确定这些函数格式的规则相当复杂 - 帮助文档中只给出了对符合标准的编译器可见的版本. 要了解你的编译器支持哪些, 请将 <boost/regex.hpp> 通过 C++ 预处理器处理, 并在输出文件中搜索你感兴趣的函数. 不过请注意, 目前的编译器中很少有对这些重载函数仍有问题的.
