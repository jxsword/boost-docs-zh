引言

Boost Exception 的目的是简化异常类层次的设计, 并帮助编写异常处理和错误报告代码.

它支持将任意数据传递到捕获点, 否则由于异常类型的抛出要求 (15.5.1), 这一点很难做到. 数据可以被添加到任何异常对象上, 既可以直接在 throw 表达式 (15.1) 中添加, 也可以在异常对象沿调用栈向上传播时再添加.

在异常对象被传给 throw 之后仍能向其添加数据的能力很重要, 因为处理异常所需的部分信息往往在检测到失败的上下文中不可用.

Boost Exception 还支持 N2179 风格的异常对象 复制, 由 boost::throw_exception 函数以非侵入式、自动的方式实现.

Tutorial

将任意数据传递到捕获点

所有派生自 boost::exception 的异常类型都可以用作任意数据对象的类型安全容器, 同时符合 ANSI C++ 标准对异常类型的抛出要求 (15.5.1).

当异常派生自 boost::exception 时, 可以向异常对象添加任意数据:

  • 在抛出点;

  • 或者在异常沿调用栈向上冒泡时再添加.

在抛出点附加任意数据

下面的示例演示如何使用 Boost Exception 将 errno 存入异常对象:

#include <boost/exception/all.hpp>
#include <iostream>

typedef boost::error_info<struct tag_my_info,int> my_info; //(1)

struct my_error: virtual boost::exception, virtual std::exception { }; //(2)

void
f()
    {
    throw my_error() << my_info(42); //(3)
    }

error_info | exception | operator<<

首先, 我们使用唯一标识 —— tag_my_info, 以及它所标识信息的类型 —— int 来实例化 error_info 模板. 这为异常对象中存储的各种值提供了编译期类型安全.

其次, 我们定义类 my_error, 它派生自 boost::exception .

最后, (3) 演示了 (1) 中的 typedef 如何与 operator<< 一起使用, 以在抛出点把值存入异常对象.

存储的 my_info 值可以在稍后这样恢复:

// ...continued

void
g()
    {
    try
        {
        f();
        }
    catch(
    my_error & x )
        {
        if( int const * mi=boost::get_error_info<my_info>(x) )
            std::cerr << "My info: " << *mi;
        }
    }

get_error_info

函数模板 get_error_info 以 (1) 中的 typedef 实例化, 并传入一个多态类型的异常对象. 若该异常对象包含所请求的值, err 将指向它; 否则返回空指针.

向活动异常对象附加任意数据

有时, 抛出点并不具备捕获点为理解出错原因所需的全部信息. 假设我们有一个异常类型 file_read_error, 它的构造函数接受一个文件名. 考虑下面的函数:

void
file_read( FILE * f, void * buffer, size_t size )
    {
    if( size!=fread(buffer,1,size,f) )
        throw file_read_error(????);
    }

file_read 函数如何把文件名传给异常类型的构造函数? 它手头只有一个 FILE 句柄.

使用 boost::exception 可以让 file_read 函数免于在其抛出的异常中存储文件名的负担:

#include <boost/exception/all.hpp>
#include <boost/shared_ptr.hpp>
#include <stdio.h>
#include <errno.h>

struct file_read_error: virtual boost::exception { };

void
file_read( FILE * f, void * buffer, size_t size )
    {
    if( size!=fread(buffer,1,size,f) )
        throw file_read_error() << boost::errinfo_errno(errno);
    }

exception | errinfo_errno

若 file_read 检测到失败, 它抛出一个异常, 其中包含当时可获得的信息, 即 errno. 其他相关信息 (例如文件名) 可以在调用栈更高层的上下文中添加, 在那里它是自然可知的:

#include <boost/exception/all.hpp>
#include <boost/shared_ptr.hpp>
#include <stdio.h>
#include <string>

boost::shared_ptr<FILE> file_open( char const * file_name, char const * mode );
void file_read( FILE * f, void * buffer, size_t size );

void
parse_file( char const * file_name )
    {
    boost::shared_ptr<FILE> f = file_open(file_name,"rb");
    assert(f);
    try
        {
        char buf[1024];
        file_read( f.get(), buf, sizeof(buf) );
        }
    catch(
    boost::exception & e )
        {
        e << boost::errinfo_file_name(file_name);
        throw;
        }
    }

exception | errinfo_file_name

上面的函数是 (几乎) 异常中立的 —— 若 try 块内的任何函数调用抛出异常, parse_file 不需要做任何实际工作, 但它会拦截任何 boost::exception 对象, 存储文件名, 并用无操作数的 throw 表达式 (15.1.6) 重新抛出. 捕获任何 boost::exception 对象的理由是: 文件名与 parse_file 中发生的任何失败都相关, 即使该失败与文件 I/O 无关 .

向异常添加分组数据

下面的代码片段演示如何用 boost::http://www.boost.org/libs/tuple/doc/tuple_users_guide.html[tuple] 把失败函数的名称与报告的 errno 捆绑在一起, 以便更方便地把它们一起添加到异常对象:

#include <boost/exception/info_tuple.hpp>
#include <boost/exception/errinfo_file_name.hpp>
#include <boost/exception/errinfo_api_function.hpp>
#include <boost/exception/errinfo_errno.hpp>
#include <boost/shared_ptr.hpp>
#include <stdio.h>
#include <string>
#include <errno.h>

typedef boost::tuple<boost::errinfo_api_function,boost::errinfo_errno> clib_failure;

struct file_open_error: virtual boost::exception { };

boost::shared_ptr<FILE>
file_open( char const * name, char const * mode )
    {
    if( FILE * f=fopen(name,mode) )
        return boost::shared_ptr<FILE>(f,fclose);
    else
        throw file_open_error() <<
            boost::errinfo_file_name(name) <<
            clib_failure("fopen",errno);
    }

tuple/operator<< | errinfo_file_name | errinfo_api_function | errinfo_errno

注意, boost::http://www.boost.org/libs/tuple/doc/tuple_users_guide.html[tuple] 的成员在异常对象中是分开存储的; 只能用 get_error_info 逐个检索它们.

将 Boost Exception 集成到既有异常类层次中

有些异常层次无法修改为使 boost::exception 成为基类型. 这时, 可以用函数模板 enable_error_info 使异常对象仍然派生自 boost::exception . 下面是一个示例:

#include <boost/exception/all.hpp>
#include <stdexcept>

typedef boost::error_info<struct tag_std_range_min,size_t> std_range_min;
typedef boost::error_info<struct tag_std_range_max,size_t> std_range_max;
typedef boost::error_info<struct tag_std_range_index,size_t> std_range_index;

template <class T>
class
my_container
    {
    public:

    size_t size() const;

    T const &
    operator[]( size_t i ) const
        {
        if( i > size() )
            throw boost::enable_error_info(std::range_error("Index out of range")) <<
                std_range_min(0) <<
                std_range_max(size()) <<
                std_range_index(i);
        //....
        }
    };

enable_error_info | operator<<

调用 enable_error_info<T> 会得到一个 类型未指定 的对象, 保证同时派生自 boost::exception 和 T. 这使得可以用 operator<< 在异常对象中存储附加信息. 该异常可以按 T & 拦截, 因此既有的异常处理不会中断. 它也可以按 boost::exception & 拦截, 以便 在稍后向异常添加更多信息 .

在线程之间传递异常

Boost Exception 通过克隆支持在线程之间传递异常对象. 该系统类似于 N2179 , 但由于 Boost Exception 不能依赖语言支持, 要使用克隆就必须在抛出时使用 enable_current_exception .

熟悉的函数 boost::throw_exception 所抛出的所有异常都保证派生自 boost::exception 并支持克隆.

在抛出时使用 enable_current_exception

下面展示如何在 throw 表达式 (15.1) 中启用克隆:

#include <boost/exception/info.hpp>
#include <boost/exception/errinfo_errno.hpp>
#include <stdio.h>
#include <errno.h>

struct file_read_error: virtual boost::exception { };

void
file_read( FILE * f, void * buffer, size_t size )
    {
    if( size!=fread(buffer,1,size,f) )
        throw boost::enable_current_exception(file_read_error()) <<
            boost::errinfo_errno(errno);
    }

enable_current_exception | errinfo_errno

当然, enable_current_exception 可用于任何异常类型; 不要求它必须派生自 boost::exception .

克隆并重新抛出异常

捕获异常时, 可以调用 current_exception 得到一个 exception_ptr 对象:

#include <boost/exception_ptr.hpp>
#include <boost/thread.hpp>
#include <boost/bind.hpp>

void do_work(); //throws cloning-enabled boost::exceptions

void
worker_thread( boost::exception_ptr & error )
    {
    try
        {
        do_work();
        error = boost::exception_ptr();
        }
    catch(
    ... )
        {
        error = boost::current_exception();
        }
    }

current_exception | exception_ptr

在上面的示例中, 注意 current_exception 捕获了异常对象的原始类型. 可以使用 rethrow_exception 函数再次抛出该异常:

// ...continued

void
work()
    {
    boost::exception_ptr error;
    boost::thread t( boost::bind(worker_thread,boost::ref(error)) );
    t.join();
    if( error )
        boost::rethrow_exception(error);
    }

rethrow_exception | exception_ptr

注意, 在以下情况下 current_exception 可能无法复制原始异常对象:

  • 内存不足, 此时返回的 exception_ptr 指向一个 std::bad_alloc 实例; 或

  • 传给原始 throw 语句的 throw 表达式中未使用 enable_current_exception , 且当前实现不具备自动复制异常所需的编译器特定支持, 此时返回的 exception_ptr 指向一个 unknown_exception 实例.

无论如何, 上面示例中 current_exception 和 rethrow_exception 的使用都是良构的.

作为简单语义标签的异常类型

派生自 boost::exception 实际上把失败的语义与每次以给定语义报告失败时所需的信息解耦了.

换言之: 使用 boost::exception 时, 给定异常对象传递什么数据主要取决于报告失败的上下文 (而不是其类型). 由于异常类型不需要成员, 抛出派生自多个类型以表示多种适当语义的异常就变得非常自然:

struct exception_base: virtual std::exception, virtual boost::exception { };
struct io_error: virtual exception_base { };
struct file_error: virtual io_error { };
struct read_error: virtual io_error { };
struct file_read_error: virtual file_error, virtual read_error { };

exception

采用这种方法, 异常类型变成一个简单的标签系统, 用于对错误分类以及在异常处理器中选择失败.

在异常类型中使用虚继承

异常类型在派生自其他异常类型时应使用虚继承. 这一洞见来自 Andrew Koenig. 使用虚继承可以避免异常处理器中的二义性问题:

#include <iostream>
struct my_exc1 : std::exception { char const* what() const throw(); };
struct my_exc2 : std::exception { char const* what() const throw(); };
struct your_exc3 : my_exc1, my_exc2 {};

int
main()
    {
    try { throw your_exc3(); }
    catch(std::exception const& e) {}
    catch(...) { std::cout << "whoops!" << std::endl; }
    }

上面的程序输出 "whoops!", 因为到 std::exception 的转换有二义性.

虚继承带来的开销在异常处理的上下文中总是可以忽略的. 注意, 虚基类由最终派生类型的构造函数直接初始化 (对异常而言即传给 throw 语句的类型.) 不过, 使用 boost::exception 时通常无需关心这一细节, 因为它使异常类型可以成为没有成员的平凡结构体 (没有什么可初始化的.) 参见 作为简单语义标签的异常类型 .

诊断信息

Boost Exception 提供命名空间级函数 diagnostic_information , 它接受一个 boost::exception . 返回的字符串包含:

  • 所有数据对象的字符串表示, 这些对象是通过 boost::exception 添加到 operator<< 的;

  • std::exception::what 的输出;

  • 附加的平台特定诊断信息.

返回的字符串不适合作为友好的用户消息呈现, 但由于它是自动生成的, 因此对调试或日志记录很有用. 下面是一个示例:

#include <boost/exception/all.hpp>
#include <iostream>

void f(); //throws unknown types that derive from boost::exception.

void
g()
    {
    try
        {
        f();
        }
    catch(
    boost::exception & e )
        {
        std::cerr << diagnostic_information(e);
        }
    }

序列化

Boost Exception 提供一个序列化 API, 支持将诊断信息导出为不同格式 (例如 JSON). 这对结构化日志、远程调试或与监控系统集成都很有用.

要序列化诊断信息, 使用以下函数:

  • serialize_diagnostic_information_to —— 为给定异常序列化诊断信息.

  • serialize_current_exception_diagnostic_information_to —— 为当前异常序列化诊断信息.

序列化系统使用通过 ADL 找到的 output 和 output_at 函数:

  • output(enc, x) 直接把值 x 序列化到编码器 enc .

  • output_at(enc, x, name) 把值 x 作为命名字段序列化到编码器 enc .

#include <boost/exception/diagnostic_information.hpp>

为支持导出到特定格式, 用户定义一个编码器类, 并带上关联的 output 与 output_at 函数模板:

struct my_encoder
{
    template <class T>
    friend void output(my_encoder & enc, T const & x)
    {
        // output value x to enc
    }

    template <class T>
    friend void output_at(my_encoder & enc, T const & x, char const * name)
    {
        // output x to enc as a named field
    }
};

output_at 函数通常创建一个嵌套作用域 (例如 JSON 对象), 然后调用 output 来序列化值.

要启用序列化到自定义编码器类型, 请定义 serialize 函数模板, 位于 boost::exception_serialization 命名空间中:

namespace boost { namespace exception_serialization {

template <class Handle, class T>
void serialize(Handle & h, T const & x, char const * name)
{
    h.dispatch([&](my_encoder & enc) {
        output_at(enc, x, name);
    });
}

} }

函数模板 serialize 接受一个持有一台编码器、待序列化对象及其类型名的句柄引用 h (类型未指定). 用单实参函数 F 调用 h.dispatch 可基于 F 的实参类型检测编码器类型; 仅当句柄包含该类型的编码器时才会调用 F.

要支持多种输出格式, 向 h.dispatch 传入多个函数:

h.dispatch(
    [&](json_encoder & enc) { output_at(enc, x, name); },
    [&](xml_encoder & enc) { output_at(enc, x, name); }
);

JSON 序列化

Boost Exception 提供两个 JSON 编码器:

  • boost_json_encoder , 用于 Boost.JSON

  • nlohmann_json_encoder , 基于对 to_json 的 ADL 调用 (与 nlohmann/json 兼容)

下面是一个把 nlohmann_json_encoder 与 nlohmann/json 一起使用的示例. 我们只需定义所需的 serialize 函数模板 (参见 自定义编码器 ):

#include <boost/exception/serialization/nlohmann_json_encoder.hpp>
#include "nlohmann/json.hpp"

using nlohmann_json_encoder = boost::exception_serialization::nlohmann_json_encoder<nlohmann::json>;

namespace boost { namespace exception_serialization {

template <class Handle, class T>
void serialize(Handle & h, T const & x, char const * name)
{
    h.dispatch([&](nlohmann_json_encoder & enc) {
        output_at(enc, x, name);
    });
}

} }

有了这些准备, 我们就可以把诊断信息输出为 JSON:

#include <boost/exception/diagnostic_information.hpp>
#include <boost/throw_exception.hpp>
#include <iostream>

struct api_response
{
    int status;
    std::string message;

    template <class Json>
    friend void to_json(Json & j, api_response const & e)
    {
        j["status"] = e.status;
        j["message"] = e.message;
    }
};

typedef boost::error_info<struct errinfo_api_response_, api_response> errinfo_api_response;
typedef boost::error_info<struct errinfo_request_url_, std::string> errinfo_request_url;

struct api_error : virtual boost::exception, virtual std::exception { };

....

nlohmann::json j;
try
{
    BOOST_THROW_EXCEPTION(api_error()
        << errinfo_api_response({403, "Access denied"})
        << errinfo_request_url("/api/admin/settings"));
}
catch(boost::exception & e)
{
    nlohmann_json_encoder enc{j};
    boost::serialize_diagnostic_information_to(enc, e);
}
std::cout << j.dump(2) << std::endl;
输出:
{
  "errinfo_api_response_": {
    "status": 403,
    "message": "Access denied"
  },
  "errinfo_request_url_": "/api/admin/settings"
}

serialize_diagnostic_information_to | nlohmann_json_encoder

在上面的示例中, api_response 使用对 to_json 的非限定调用进行序列化. 这是为了演示 nlohmann_json_encoder 会自动处理带有合适 to_json 重载的第三方类型. 若我们改为定义一个与 Boost Exception 序列化 API 兼容的函数 output , 则会使 api_response 与任何 Boost Exception 编码器兼容.

    class error_info

    public:

        typedef T value_type;

        error_info( value_type const & v );

要求:

T 必须具有可访问的复制构造函数, 且不得是引用 (不要求 T 的复制构造函数不抛出.)

此类模板用于把一个 Tag 类型与值类型 T 关联起来. error_info<Tag,T> 类型的对象可以传给 operator<< , 以存储到 boost::exception 类型的对象中.

头文件 <boost/exception/error_info.hpp> 提供 error_info 模板的声明, 这对于为特定 Tag 和 T typedef 一个实例已经足够, 例如:

#include <boost/exception/error_info.hpp>

struct tag_errno;
typedef boost::error_info<tag_errno,int> errno_info;

或者, 更短的等价形式:

#include <boost/exception/error_info.hpp>

typedef boost::error_info<struct tag_errno,int> errno_info;

catch( boost::exception & x )

exception_ptr 类型可用于引用异常对象的一个副本. 它可默认构造、可复制构造、可赋值且可相等比较; exception_ptr 的操作不抛出.

只要还有引用它的 exception_ptr 对象存在, 被引用对象就保持有效.

两个 exception_ptr 实例等价且比较相等, 当且仅当它们引用同一个异常.

exception_ptr 的默认构造函数产生该类型的空值. 空值仅与其自身等价.

线程安全:

exception_ptr 类型 "与内建类型一样线程安全":

  • 一个 exception_ptr 实例可以被多个线程同时 "读取"

  • 不同的 exception_ptr 实例可以被多个线程同时 "写入", 即使这些实例引用同一个异常对象

所有其他并发访问都会导致未定义行为.

  • 若 E 可静态转换为 boost::exception 或 std::exception, 则使用 dynamic_cast 访问 e 的 boost::exception 和 std::exception 两个子对象; 否则 boost::diagnostic_information 模板不可用.

  • 返回值包含通过 error_info 存储在 boost::exception 子对象中的所有 operator<< 对象的字符串表示.

  • 此外, 若 verbose 为 true, 其中还包含与该异常相关的其他诊断信息, 包括 std::exception::what() 返回的字符串.

每个 error_info 对象的字符串表示通过对 to_string(x) 的非限定调用推导, 其中 x 的类型为 error_info<Tag,T> , Boost Exception 为其定义了一个泛型重载. 它把 x.value () 转换为字符串, 尝试按顺序绑定 (在 error_info<Tag,T> 模板实例化时) 以下函数:

  1. 对 to_string(x.value ()) 的非限定调用 (期望返回值类型为 std::string.)

  2. 对 s << x.value () 的非限定调用, 其中 s 是一个 std::ostringstream.

在调用 diagnostic_information 时使用第一个成功绑定的函数; 若两个重载决议都不成功, 系统无法把 error_info 对象转换为字符串, 并且 使用一个未指明的占位字符串值而不产生编译错误.

exception_ptr 的 diagnostic_information 重载等价于:

if( p )
    try
        {
        rethrow_exception(p);
        }
    catch(...)
        {
        return current_exception_diagnostic_information(verbose);
        }
else return <unspecified-string-value>;

设计原理

传统上, 在使用异常报告失败时, 抛出点:

  • 创建一个适当类型的异常对象, 并且

  • 把与检测到的错误相关的数据填入其中.

程序中更高层的上下文包含一个 catch 语句, 它:

  • 基于异常类型选择失败, 并且

  • 检查异常对象以获取处理问题所需的数据.

这种 "传统" 方法的主要问题在于: 抛出点可获得的数据往往不足以让捕获点处理失败.

下面是一个 catch 语句示例:

catch( file_read_error & e )
    {
    std::cerr << e.file_name();
    }

而这里是一个可能匹配的 throw:

void
read_file( FILE * f )
    {
    ....
    size_t nr=fread(buf,1,count,f);
    if( ferror(f) )
        throw file_read_error(???);
    ....
    }

显然, 问题在于处理器需要文件名, 但 read_file 函数没有文件名可放入异常对象; 它手头只有一个 FILE 指针!

为尝试解决这一问题, 我们可以修改 read_file 使其接受一个文件名:

void
read_file( FILE * f, char const * name )
    {
    ....
    size_t nr=fread(buf,1,count,f);
    if( ferror(f) )
        throw file_read_error(name);
    ....
    }

这不是真正的解决方案: 它只是把提供文件名的负担转移给了 read_file 函数的直接调用者.

一般而言, 处理某个库抛出的异常所需的数据取决于链接该库的程序. 抛出与捕获之间的许多上下文可能拥有相关信息, 这些信息必须被传递到异常处理器.

异常包装

异常包装的想法是: 捕获来自较低层函数 (例如上面的 read_file 函数) 的异常, 并抛出一个包含原始异常的新异常对象 (同时还携带文件名.) 这种方法似乎在具有 Java 背景的 C++ 程序员中尤其流行.

异常包装会导致以下问题:

  • 要包装异常对象就必须复制它, 这可能导致切片 (slicing).

  • 包装在泛型上下文中实际上无法使用.

第二点实际上是违反异常中立原则的一个特例. 程序中的大多数上下文无法处理异常; 这样的上下文不应干扰异常处理过程.

boost::exception 解决方案

  • 只需让你的异常类型派生自 boost::exception .

  • 放心地把抛出点限定为只提供自然可获得的数据.

  • 在抛出与捕获之间使用异常中立的上下文, 在异常沿调用栈向上冒泡时为其增补更多相关数据.

例如, 在下面的 throw 语句中我们只添加 errno 代码, 因为这是该上下文中唯一可获得的与失败相关的信息:

struct exception_base: virtual std::exception, virtual boost::exception { };
struct io_error: virtual exception_base { };
struct file_read_error: virtual io_error { };

typedef boost::error_info<struct tag_errno_code,int> errno_code;

void
read_file( FILE * f )
    {
    ....
    size_t nr=fread(buf,1,count,f);
    if( ferror(f) )
        throw file_read_error() << errno_code(errno);
    ....
    }

exception | error_info | operator<<

在更高层的异常中立上下文中, 我们向派生自 的 任何 boost::exception 异常添加文件名:

typedef boost::error_info<struct tag_file_name,std::string> file_name;

....
try
    {
    if( FILE * fp=fopen("foo.txt","rt") )
        {
        shared_ptr<FILE> f(fp,fclose);
        ....
        read_file(fp); //throws types deriving from boost::exception
        do_something();
        ....
        }
    else
        throw file_open_error() << errno_code(errno);
    }
catch( boost::exception & e )
    {
    e << file_name("foo.txt");
    throw;
    }

exception | error_info | operator<<

最后, 下面是处理器从派生自 boost::exception 的异常中检索数据的方式:

catch( io_error & e )
    {
    std::cerr << "I/O Error!\n";

    if( std::string const * fn=get_error_info<file_name>(e) )
        std::cerr << "File name: " << *fn << "\n";

    if( int const * c=get_error_info<errno_code>(e) )
        std::cerr << "OS says: " << strerror(*c) << "\n";
    }

常见问题

调用 boost::throw_exception 的开销是什么?

开销在于: boost::exception 被添加为 boost::throw_exception 所抛出异常的基类 (除非传入的类型已经派生自 boost::exception ).

调用 boost::throw_exception 不会导致动态内存分配.

BOOST_THROW_EXCEPTION 的开销是什么?

除调用 boost::throw_exception 之外, BOOST_THROW_EXCEPTION 还会调用 __FILE__ 与 __LINE__ 宏. 存储该信息所需的空间已包含在 sizeof(boost::exception) 中.

调用 BOOST_THROW_EXCEPTION 不会导致动态内存分配.

应该使用 boost::throw_exception、BOOST_THROW_EXCEPTION 还是直接 throw?

调用 boost::throw_exception 而非直接使用 throw 的好处是: 它确保抛出的异常派生自 boost::exception , 并且与 boost::current_exception 兼容.

BOOST_THROW_EXCEPTION 宏还会导致对 boost::throw_exception 的调用, 但此外它还会在异常对象中记录抛出处的 __FILE__ 与 __LINE__, 以及抛出函数的完整名称. 这使 boost::diagnostic_information 能够合成一条更有用 (尽管对用户不友好) 的消息.

boost::diagnostic_information 的典型用法是:

catch(...)
    {
    std::cerr <<
        "Unexpected exception, diagnostic information follows:\n" <<
        current_exception_diagnostic_information();
    }

这是它可能显示的一条消息 —— 第一行中的信息只有在使用 BOOST_THROW_EXCEPTION 抛出时才可用:

example_io.cpp(70): Throw in function class boost::shared_ptr<struct _iobuf> __cdecl my_fopen(const char *,const char *)
Dynamic exception type: class boost::exception_detail::clone_impl<class fopen_error>
std::exception::what: example_io error
[struct boost::errinfo_api_function_ *] = fopen
[struct boost::errinfo_errno_ *] = 2, "No such file or directory"
[struct boost::errinfo_file_name_ *] = tmp1.txt

在一些开发环境中, 可以点击该消息的第一行在调试器中显示抛出的位置, 因此很容易设置断点并再次运行, 在其调用栈的上下文中查看这个意外的抛出.

为什么 boost::exception 不派生自 std::exception?

尽管 派生自基异常类型时应使用虚继承 , 但异常类型 (包括标准库中定义的那些) 往往并不虚派生自 std::exception.

若 boost::exception 派生自 std::exception, 则将 enable_error_info 函数用于这样的用户自定义类型会引入危险的三义性, 从而破坏所有 catch(std::exception &) 语句.

当然, boost::exception 不应用于替代 std::exception 作为异常类型层次中的基类型. 相反, 它应作为虚基类包含进来, 与 std::exception 并存 (std::exception 或许也应当被虚派生.)

为什么 boost::exception 是抽象类?

为了防止异常中立的上下文在向活动异常对象添加 error_info 时错误地抹除原始异常的类型:

catch( boost::exception & e )
    {
    e << foo_info(foo);
    throw e; //Compile error: boost::exception is abstract
    }

正确的代码是:

catch( boost::exception & e )
    {
    e << foo_info(foo);
    throw; //Okay, re-throwing the original exception object.
    }

为什么用 operator<< 重载向异常添加信息?

在抛出一个派生自 boost::exception 的类型对象之前, 通常希望向其添加一个或多个 error_info 对象. operator<< 提供的语法糖使这可以直接在 throw 表达式中完成:

throw error() << foo_info(foo) << bar_info(bar);

为什么允许 operator<< 抛出异常?

这个问题针对以下议题. 考虑这个 throw 语句示例:

throw file_open_error() << file_name(fn);

这里的意图是抛出 file_open_error, 但若 operator<< 未能复制 file_name error_info 包装器中的 std::string, 则可能传播 std::bad_alloc. 一些程序员认为这种行为不合期望.

"抛出异常需要一个可抛出的对象. C++ 实现必须留有足够的内存余量, 以便在内存耗尽时能够抛出 bad_alloc. 然而, 抛出某个其他异常也可能导致内存耗尽."

—— Bjarne Stroustrup
The C++ Programming Language 3rd Edition p. 371

因此, 语言本身并不保证抛出异常的尝试一定会抛出指定类型的对象; 即使在 Boost Exception 的范围之外, 传播 std::bad_alloc 似乎也是可能的.
