概述

摘要

Boost.Endian 提供用于操作整数和用户自定义类型的 字节序 的设施.

  • 本库支持三种处理字节序的方法. 每种方法都有长期的成功使用历史, 并且每种方法都有其优于其他方法的用例.

  • 主要用途:

    • 数据可移植性. Endian 库支持通过外部介质或网络传输进行二进制数据交换, 而无需考虑平台的字节序.

    • 程序可移植性. 基于 POSIX 和基于 Windows 的操作系统传统上会提供带有不可移植字节序转换函数的库. 常用的互不兼容的函数集至少有四套. Endian 库在所有 C++ 平台上都是可移植的.

  • 次要用途: 通过标准 C++ 整数类型不支持的大小和/或对齐方式来最小化数据体积.

字节序入门

Consider the following code:

int16_t i = 0x0102;
FILE * file = fopen("test.bin", "wb"); // binary file!
fwrite(&i, sizeof(int16_t), 1, file);
fclose(file);

在配备 Intel CPU 的 OS X、Linux 或 Windows 系统上, 对输出文件 "test.bin" 进行十六进制转储会得到:

0201

在配备 PowerPC CPU 的 OS X 系统或配备 SPARC CPU 的 Solaris 系统上, 对输出文件 "test.bin" 进行十六进制转储会得到:

0102

这里发生的情况是: Intel CPU 按最低有效字节在前的顺序排列整数的字节, 而 SPARC CPU 则将最高有效字节放在最前. 一些 CPU (例如 PowerPC) 允许操作系统选择采用哪种排列顺序.

最高有效字节在前的排列顺序传统上称为 "big endian" (大端) 排列, 而最低有效字节在前则传统上称为 "little-endian" (小端) 排列. 这些名称源自 Jonathan Swift 的讽刺小说 Gulliver's Travels (《格列佛游记》), 书中敌对的王国从不同的端头打开他们的溏心蛋.

关于字节序的详尽讨论, 参见 Wikipedia 的 Endianness 条目.

程序员通常可以忽略字节序, 但在小端系统上读取核心转储 (core dump) 时除外. 不过, 在具有不同字节序的计算机系统之间交换二进制整数和二进制浮点值时 (无论是通过物理文件传输还是通过网络), 程序员就必须处理字节序问题了. 此外, 当最小化内部或外部数据体积有利时, 程序员也可能想使用本库.

Boost.Endian 库简介

Boost.Endian 提供三种不同的方法来处理字节序. 这三种方法都支持整数和用户自定义类型 (UDT).

每种方法都有长期的成功使用历史, 并且每种方法都有其优于其他方法的用例. 参见 在转换函数、缓冲类型与算术类型之间做出选择.

Endian 转换函数

应用程序使用内建整数类型保存值, 并调用所提供的转换函数按需转换字节序. 同时提供了修改型 (mutating) 和非修改型 (non-mutating) 转换, 且每种转换都有无条件版和条件版.

Endian 缓冲类型

应用程序使用所提供的 endian 缓冲类型保存值, 并显式地与内建整数类型相互转换. 提供了 8、16、24、32、40、48、56 和 64 位 (即 1、2、3、4、5、6、7 和 8 字节) 的缓冲大小. 所有大小均提供非对齐整数缓冲类型, 16、32 和 64 位大小则提供对齐缓冲类型. 所提供的具体类型是一个泛型类模板的 typedef, 该模板也可直接用于不太常见的用例.

Endian 算术类型

应用程序使用所提供的 endian 算术类型, 它们提供与内建 C++ 算术类型相同的操作. 所有转换都是隐式的. 提供了 8、16、24、32、40、48、56 和 64 位 (即 1、2、3、4、5、6、7 和 8 字节) 的算术大小. 所有大小均提供非对齐整数类型, 16、32 和 64 位大小则提供对齐算术类型. 所提供的具体类型是一个泛型类模板的 typedef, 该模板也可直接用于泛型代码或不太常见的用例.

Boost Endian 是一个仅头文件库, 要求 C++11.

对内建 (Intrinsics) 的支持

包括 GCC、Clang 和 Visual C++ 在内的大多数编译器都提供字节交换 intrinsics 的内建支持. 在可用时, Endian 库会使用这些 intrinsics, 因为它们可能生成更小、更快的代码, 对于优化构建尤其如此.

定义宏 BOOST_ENDIAN_NO_INTRINSICS 将禁止使用 intrinsics. 当编译器没有 intrinsic 支持或找不到相应头文件时 (可能因为它是较旧的版本, 或其支持库非常有限), 这会很有用.

宏 BOOST_ENDIAN_INTRINSIC_MSG 被定义为 "no byte swap intrinsics" , 或被定义为一个描述所使用的特定 intrinsic 集合的字符串. 这有助于排除缺失 intrinsic 这一性能问题的来源.

性能

考虑这个问题:

示例 1

将文件中的一个 big endian 值加上 100, 然后把结果写入文件

Endian 算术类型方法 Endian 转换函数方法

... read into x from a file ...


x += 100;


... write x to a file ...
 
int32_t x;

... read into x from a file ...

native_to_big_inplace(x);

... write x to a file ...

在优化构建中, 无论机器的本机字节序如何, 这两种方法在性能上都不会有差异. 这是因为优化编译器会为两者生成完全相同的代码. 该结论通过研究 GCC 和 Visual C++ 生成的汇编代码得到了证实. 此外, 应用程序的速度将取决于 I/O 所花费的时间.

总体 FAQ

该实现是否仅含头文件?

支持.

是否支持 C++03 编译器?

不支持. 自 1.84 发布版起要求 C++11.

该实现是否使用编译器内建的字节交换 intrinsic?

是的, 如果可用. 参见 Intrinsic 内建支持.

为什么要费心处理字节序?

二进制数据可移植性是最主要的用例.

除了可移植的二进制文件或网络 I/O 格式之外, 字节序还有其他用途吗?

使用大小贴合应用需求的非对齐整数类型是一个较次要的用途, 可节省内部或外部内存空间. 例如, 在大数组中使用 big_int40_buf_t 或 big_int40_t 相比 64 位类型之一可以节省大量空间.

为什么要费心处理二进制 I/O? 为什么不直接使用 C++ 标准库的流插入符和提取符?

  • 数据交换格式通常指定二进制整数数据. 二进制整数数据更小, 因此 I/O 更快, 文件也更小. 系统间的传输成本更低.

  • 此外, 二进制整数数据大小固定, 因此可以生成无需填充的定长磁盘记录, 便于排序并支持随机访问.

  • 其缺点 (例如无法对结果文件使用文本工具) 将其用途限制在二进制 I/O 优势至关重要的应用中.

big-endian 和 little-endian 哪个更好?

在网络环境中, big-endian 往往更受青睐, 并且在某种程度上更是行业标准; 但对于主要运行在 x86、x86-64 及其他 little-endian CPU 上的应用, little-endian 可能更合适. Wikipedia 条目给出了更多优缺点.

为什么只支持 big 和 little 两种本机字节序?

这是当今仅有的具有实用价值的字节序方案. PDP-11 和其他中间字节序 (middle endian) 方式是有趣的奇闻, 但与当今的 C++ 开发者无关. 对于支持运行期字节序切换的体系结构也是如此. 本机序的规范 经过精心设计, 以便将来在需要时能够支持此类字节序. 感谢 Howard Hinnant 的建议.

为什么 buffer 类型和 arithmetic 类型同时存在?

buffer 类型中的转换是显式的, arithmetic 类型中的转换是隐式的. 这一根本差异是有意的设计特性, 若将继承层次合并, 该特性就会丢失. 最初的设计只提供了 arithmetic 类型. buffer 类型是在正式评审期间由希望完全掌控转换发生时机的用户提出的. 他们还认为, 对不熟悉在 endian arithmetic 整数类型上执行大量整数运算的后果的维护型程序员而言, buffer 类型更不容易被误用.

与始终使用 arithmetic 类型相比, 使用 buffer 类型能带来什么?

确保不会执行隐藏转换. 这对追求极致速度的用户来说是最重要的. 对于其他用户而言, "始终使用 arithmetic 类型" 也是可以的. 当需要确保极致速度时, arithmetic 类型可以用在与 buffer 类型相同的设计模式或惯用法中, 从而为两种类型生成相同的代码.

整数支持有哪些限制?

测试仅在采用二进制补码算术的机器上进行. Endian 转换函数仅支持 8、16、32 和 64 位对齐整数. endian 类型仅支持 8、16、24、32、40、48、56 和 64 位非对齐整数, 以及 8、16、32 和 64 位对齐整数.

是否支持浮点数?

曾尝试支持四字节的 float 类型与八字节的 double 类型, 仅限于 IEEE 754 (亦称 ISO/IEC/IEEE 60559) 浮点数, 并进一步限于浮点数字节序与整数字节序相同的系统. 即使有这些限制, 对浮点类型的支持也不可靠, 因此被移除. 例如, 仅仅反转浮点数的字节序就可能得到一个 signaling-NaN.

对 float 和 double 的支持后来已重新提供, 适用于 endian_buffer endian_arithmetic 以及原地反转字节序的转换函数. 按值传入并返回的转换函数由于上述问题仍不支持浮点数; 反转浮点数的字节序未必得到另一个有效的浮点数.

修订历史

1.84.0 中的变更

  • 不再支持 C++03; 要求 C++11 编译器. (包括 GCC 4.6 或更高版本, 以及 MSVC 12.0 (VS 2013) 或更高版本.)

1.75.0 中的变更

  • endian_arithmetic 不再继承自 endian_buffer .

  • 当定义 BOOST_ENDIAN_NO_CTORS 时, 非对齐的 endian_buffer 和 endian_arithmetic 是 C++03 POD, 以支持使用 __attribute__((packed)) .

1.74.0 中的变更

  • 在 endian_reverse 中启用了有作用域枚举类型.

  • 启用了 bool enum float double (在 endian_reverse_inplace 中).

  • 为 endian_reverse_inplace 新增了一个针对数组的重载.

1.72.0 中的变更

  • 在 GCC 和 Clang 上将 endian_reverse conditional_reverse 和 *_to_* 设为 constexpr .

  • 新增了便捷的 load 和 store 函数.

  • 新增了浮点数便捷 typedef.

  • 为 data() 新增了非 const 重载; 并将其返回类型改为 unsigned char* .

  • 在可用时为 __int128 添加了 endian_reverse 支持.

  • 新增了便捷头文件 boost/endian.hpp .

1.71.0 中的变更

  • 澄清了对值类型模板参数的要求.

  • 新增了对 float 与 double 的支持, 受益对象为 endian_buffer 和 endian_arithmetic .

  • Added endian_load, endian_store.

  • 更新了 endian_reverse , 使其正确支持所有非 bool 的整数类型.

  • 将已弃用的名称移入弃用头文件 endian.hpp .

在转换函数、缓冲类型与算术类型之间做出选择

注释
 为一个特定应用确定哪种字节序方法 (转换函数、缓冲类型或算术类型) 最优, 涉及复杂的工程权衡. 若不先了解这些不同的接口, 就很难评估这些权衡, 因此建议在继续阅读之前先阅读 转换函数、缓冲类型 和 算术类型 几页.

对一个特定应用而言, 最合适的字节序方法取决于应用需求与三种方法各自特性之间的相互作用.

建议: 如果你是初次接触字节序、拿不准, 或不想花时间研究工程权衡, 请使用 endian 算术类型. 它们安全、易用且易于维护. 如有需要, 可以在冗长循环等性能热点附近局部使用 预先转换 (anticipating need) 设计模式.

背景

处理字节序通常意味着程序可移植性或数据可移植性需求, 而且往往两者兼有. 这意味着真正处理字节序的程序通常很复杂, 因此这里展示的示例实际会被写成分布在多个翻译单元中的多个函数. 它们会涉及无法修改的接口, 因为这些接口由第三方或标准库提供.

特性

区分这三种字节序方法的特性是: 字节序不变式、转换的显式性、算术运算、可用大小以及对齐要求.

字节序不变式

Endian conversion functions 使用普通的 C++ 算术类型 (如 int 或 unsigned short ) 的对象来保存值. 这破坏了 C++ 语言规则所应用的隐式不变式. 只有当对象的字节序当前被设置为本平台的本机字节序时, 通常的语言规则才适用. 这会使推理控制流变得非常困难, 并导致难以发现的缺陷.

例如:

struct data_t  // big endian
{
  int32_t   v1;  // description ...
  int32_t   v2;  // description ...
  ... additional character data members (i.e. non-endian)
  int32_t   v3;  // description ...
};

data_t data;

read(data);
big_to_native_inplace(data.v1);
big_to_native_inplace(data.v2);

...

++v1;
third_party::func(data.v2);

...

native_to_big_inplace(data.v1);
native_to_big_inplace(data.v2);
write(data);

程序员没有费心把 data.v3 转换为本机字节序, 因为那个成员没有被用到. 后来的维护者需要把 data.v3 传给第三方函数, 于是在代码深处某处添加了 third_party::func(data.v3); . 这会导致静默失败, 因为 "int32_t 类型的对象按 C++ 核心语言描述的那样保存一个值" 这一惯常不变式在此并不适用.

Endian 缓冲与算术类型 在内部将值保存为字符数组, 其不变式是数组的字节序永不改变. 这使得这些类型更易使用, 程序也更易维护.

下面是同一个示例, 改用 endian 算术类型:

struct data_t
{
  big_int32_t   v1;  // description ...
  big_int32_t   v2;  // description ...
  ... additional character data members (i.e. non-endian)
  big_int32_t   v3;  // description ...
};

data_t data;

read(data);

...

++v1;
third_party::func(data.v2);

...

write(data);

后来的维护者可以直接添加 third_party::func(data.v3) , 它会直接正常工作.

转换的显式性

Endian 转换函数 和 缓冲类型 从不执行隐式转换. 这让用户能够显式控制转换发生时机, 并有助于避免不必要的转换.

Endian 算术类型 隐式执行转换. 这使这些类型非常易用, 但可能导致不必要的转换. 若不把转换从内层循环中提升出来, 会带来性能损失.

算术运算

Endian 转换函数 不提供算术运算, 但这不是问题, 因为该方法使用普通的 C++ 算术类型来保存值.

Endian 缓冲类型 不提供算术运算. 虽然这种方法避免了不必要的转换, 但可能导致引入额外的变量, 并给维护程序员带来困扰.

Endian 算术类型 提供算术运算. 若涉及大量算术运算, 它们非常易用.

大小

字节序转换函数 仅支持 1、2、4 和 8 字节整数. 这对许多应用已经足够.

Endian 缓冲与算术类型 支持 1、2、3、4、5、6、7 和 8 字节整数. 对于内存占用或 I/O 速度是限制因素的应用, 使用贴合应用需求的大小会很有用.

对齐

字节序转换函数 仅支持对齐的整数和浮点类型. 这对大多数应用已经足够.

Endian 缓冲与算术类型 同时支持对齐与非对齐的整数和浮点类型. 非对齐类型很少用到, 但一旦需要, 往往非常有用, 而变通办法则很痛苦. 例如:

像这样不可移植的代码:

struct S {
  uint16_t a; // big endian
  uint32_t b; // big endian
} __attribute__ ((packed));

可以替换为像这样可移植的代码:

struct S {
  big_uint16_ut a;
  big_uint32_ut b;
};

设计模式

应用程序经常以记录 (record) 或数据包的形式处理 endian 数据, 其中包含多个 endian 数据元素. 为简单起见, 我们把它们统称为记录.

若所需字节序与本机字节序不同, 则必须执行转换. 这个转换应在何时进行? 实践中形成了三种设计模式.

按需转换 (即惰性转换)

此模式把转换推迟到代码中实际使用该数据元素的位置.

当实际使用哪个 endian 元素随记录内容或其他情况变化很大时, 此模式是合适的.

预先转换

此模式在预见到使用时 (例如读取记录后立即) 执行到本机字节序的转换. 如有需要, 在所有可能的用途都结束之后 (例如写入记录之前) 再执行到输出字节序的转换.

该模式的一种实现是: 在读取函数中创建一个已转换为本机字节序的代理记录, 并只把这个代理暴露给实现的其余部分; 若有写入函数, 则由其处理从本机字节序到所需输出字节序的转换.

当记录中的所有 endian 元素通常都会被用到 (与记录内容或其他情况无关) 时, 此模式是合适的.

按需转换, 但局部预先转换

此模式总体上推迟转换, 但针对特定局部需求进行预先转换. 它与 endian 缓冲类型或算术类型配合使用时尤其合适, 但与转换函数配合也很好.

示例:

struct data_t
{
  big_int32_t   v1;
  big_int32_t   v2;
  big_int32_t   v3;
};

data_t data;

read(data);

...
++v1;
...

int32_t v3_temp = data.v3;  // hoist conversion out of loop

for (int32_t i = 0; i < large-number; ++i)
{
  ... lengthy computation that accesses v3_temp ...
}
data.v3 = v3_temp;

write(data);

一般而言, 上面的伪代码把转换留给 endian 算术类型 big_int32_t . 但为了避免循环内的转换, 在进入循环之前创建一个临时对象, 并在循环结束后用它设置 data.v3 的新值.

问: 编译器的优化器反正会把转换提升到循环之外, 不是吗?

答: VC++ 2015 Preview (可能还有其他编译器) 即使对玩具测试程序也不这样做. 尽管节省不大 (两条寄存器 bswap 指令), 但若循环重复次数足够多, 代价可能很可观. 另一方面, 程序可能被 I/O 时间占主导, 以至于即使是冗长的循环也无关紧要.

移植不感知字节序的代码库

现有代码库运行在 big endian 系统上, 目前不处理字节序. 需要修改该代码库, 使其能在不同操作系统下的小端系统上运行. 为便于过渡并保护既有文件的价值, 外部数据将继续以 big endian 维护.

建议采用 endian 算术类型方法 来满足这些需求. 处理二进制 I/O 布局的少量头文件需要更改类型. 例如, short 或 int16_t 将改为 big_int16_t . .cpp 文件无需任何更改.

移植感知字节序的代码库

现有代码库运行在小端 Linux 系统上, 已经通过 Linux 提供的函数 处理字节序. 由于业务合并, 代码库必须快速改造以支持 Windows 以及可能的其他操作系统, 同时仍要支持 Linux. 代码库可靠, 程序员也都非常清楚字节序问题.

这些因素都支持采用 endian 转换函数方法 : 只需机械性地把对 htobe32 等的调用改为 boost::endian::native_to_big 等, 并把 <endian.h> 替换为 <boost/endian/conversion.hpp> .

可靠性与算术速度

将开发一个新的、复杂的多线程应用, 它必须运行在小端机器上, 但要执行 big endian 的网络 I/O. 开发者认为 endian 变量的计算速度至关重要, 但他们已见识过大量因无法推理字节序转换状态而产生的缺陷. 他们还担心, 若使用完整的 endian 算术类型, 未来的维护性变更可能无意间引入大量缓慢的转换.

采用 endian 缓冲 方法正是为这一用例量身定做的.

可靠性与易用性

将开发一个新的、复杂的多线程应用, 它必须运行在小端机器上, 但要执行 big endian 的网络 I/O. 开发者认为 endian 变量的计算速度 并非至关重要, 但他们已见识过大量因无法推理字节序转换状态而产生的缺陷. 他们还关注开发期间以及长期维护中的易用性.

去掉对转换速度的关注、增加对易用性的关注之后, 天平强烈倒向 endian 算术类型方法.

Endian 转换函数

引言

头文件 boost/endian/conversion.hpp 提供字节序反转及转换函数, 用于在内建整数类型的对象之间在本机序、big endian 与 little endian 字节排列之间转换. 也支持用户自定义类型.

参考

适当时, 函数以 inline 方式实现.

定义

字节序 (Endianness) 指内部或外部整数及其他算术数据中字节的排列顺序. 最高有效字节在前称为 big endian 排列; 最低有效字节在前称为 little endian 排列. 其他排列也是可能的, 一些 CPU 体系结构同时支持 big 与 little 排列.

注释
 这些名称源自 Jonathan Swift 的讽刺小说 Gulliver's Travels (《格列佛游记》), 书中敌对的王国从不同的端头打开他们的溏心蛋. Wikipedia 对 Endianness 有详尽的描述.

除 bool 外的标准整数类型 (C++std [basic.fundamental]) 与有作用域枚举类型 (C++std [dcl.enum]) 统称为 endian 类型 . 在没有填充位的前提下 (这在 Boost.Endian 库支持的平台上成立), endian 类型具有如下性质: 其所有位模式都是有效值, 这意味着当一个 endian 类型对象的组成字节被反转后, 结果仍是另一个有效值. 这使得 endian_reverse 可以按值传入并返回.

其他内建类型, 例如 bool、float 或无作用域枚举, 不具有同样的性质, 这意味着反转其组成字节可能产生无效值, 进而导致未定义行为. 因此这些类型不允许用于 endian_reverse, 但仍允许用于 endian_reverse_inplace. 即使一个对象因字节反转而变为无效, 只要从不读取其值, 就不会有未定义行为.

order::little 与 order::big 的值不得相等.

order::native 的值应为:

  • 若执行环境为 big endian, 则等于 order::big; 否则

  • 若执行环境为 little endian, 则等于 order::little; 否则

  • 既不等于 order::little 也不等于 order::big.

模板实参要求

头文件 boost/endian/conversion.hpp 中的模板定义引用了多个命名要求, 其细节在本小节的表格中给出. 在这些表格中, T 是由实例化模板的 C++ 程序提供的对象或引用类型; x 是 (可能为 const 的) T 类型的一个值; mlx 是 T 类型的可修改左值.

EndianReversible 要求 (除 CopyConstructible 之外)
表达式 Return 要求

endian_reverse(x)

T

T 是 endian 类型或类类型.

若 T 是 endian 类型, 返回 x 的值且字节顺序被反转.

若 T 是类类型, 则该函数:

  • 预期由用户提供, 实现为与 T 位于同一命名空间的非成员函数, 并且可以通过实参依赖查找 (ADL) 找到;

  • 对于类型或类型数组满足 x 要求的全部数据成员, 返回 EndianReversible 的值且字节顺序被反转.
EndianReversibleInplace 要求
表达式 要求

endian_reverse_inplace(mlx)

T 是整数类型、枚举类型、 float 、 double 、类类型或数组类型.

若 T 不是类类型或数组类型, 则反转 mlx 中的字节顺序.

若 T 是类类型, 则该函数:

  • 预期由用户提供, 实现为与 T 位于同一命名空间的非成员函数, 并且可以通过实参依赖查找 (ADL) 找到;

  • 对于 mlx 中类型或类型数组满足 EndianReversible 或 EndianReversibleInplace 要求的全部数据成员, 反转其字节顺序.

若 T 是数组类型, 则对每个元素调用 endian_reverse_inplace .

 由于存在一个针对 endian_reverse_inplace 的函数模板, 会对类类型调用 endian_reverse , 因此用户自定义类型只需提供 endian_reverse 即可满足 EndianReversibleInplace 要求. 虽然用户自定义类型不要求提供 endian_reverse_inplace 函数, 但提供它可能提高效率.

为什么同时提供按值返回和就地修改两种函数?

按值返回结果是 C 和 C++ 中 "由实参计算值的函数" 的标准惯用法. 就地修改函数在许多真实的字节序用例中能得到更整洁的代码, 并且对于含有字符串数据等无需反转的成员的用户自定义类型而言效率更高. 因此同时提供两种形式.

为什么不使用 Linux 的名称 (htobe16, htole16, be16toh, le16toh 等)?

这些名称是非标准的, 甚至在不同的类 POSIX 操作系统之间也不相同. 一个 C++ 库 TS 曾打算使用这些名称, 但发现它们有时被实现为宏. 由于宏不受作用域和命名空间规则的约束, 使用它们极易出错.

Endian 缓冲类型

引言

算术类型的内部字节顺序传统上称为 字节序 (endianness) . 完整探讨参见 Wikipedia 对 endianness 的论述, 包括 big endian 与 little endian 的定义.

头文件 boost/endian/buffers.hpp 提供 endian_buffer , 这是一个可移植的 endian 整数二进制缓冲类模板, 可独立于平台本机字节序控制字节序、值类型、大小和对齐. typedef 为常见配置提供了易用的名称.

用例主要涉及数据可移植性 (通过文件或网络连接), 但这些字节持有者也可用于减少内存占用、文件大小或网络流量, 因为它们提供了其他方式无法获得的二进制数值大小.

类 endian_buffer 面向希望显式控制字节序转换发生时机的用户. 它还作为 endian_arithmetic 类模板的基类, 后者面向希望完全自动的字节序转换以及对所有常规算术运算直接支持的用户.

示例

程序 example/endian_example.cpp 写出一个包含四字节 big-endian 与 little-endian 整数的二进制文件:

#include <iostream>
#include <cstdio>
#include <boost/endian/buffers.hpp>  // see Synopsis below
#include <boost/static_assert.hpp>

using namespace boost::endian;

namespace
{
  //  This is an extract from a very widely used GIS file format.
  //  Why the designer decided to mix big and little endians in
  //  the same file is not known. But this is a real-world format
  //  and users wishing to write low level code manipulating these
  //  files have to deal with the mixed endianness.

  struct header
  {
    big_int32_buf_t     file_code;
    big_int32_buf_t     file_length;
    little_int32_buf_t  version;
    little_int32_buf_t  shape_type;
  };

  const char* filename = "test.dat";
}

int main(int, char* [])
{
  header h;

  BOOST_STATIC_ASSERT(sizeof(h) == 16U);  // reality check

  h.file_code   = 0x01020304;
  h.file_length = sizeof(header);
  h.version     = 1;
  h.shape_type  = 0x01020304;

  //  Low-level I/O such as POSIX read/write or <cstdio>
  //  fread/fwrite is sometimes used for binary file operations
  //  when ultimate efficiency is important. Such I/O is often
  //  performed in some C++ wrapper class, but to drive home the
  //  point that endian integers are often used in fairly
  //  low-level code that does bulk I/O operations, <cstdio>
  //  fopen/fwrite is used for I/O in this example.

  std::FILE* fi = std::fopen(filename, "wb");  // MUST BE BINARY

  if (!fi)
  {
    std::cout << "could not open " << filename << '\n';
    return 1;
  }

  if (std::fwrite(&h, sizeof(header), 1, fi) != 1)
  {
    std::cout << "write failure for " << filename << '\n';
    return 1;
  }

  std::fclose(fi);

  std::cout << "created file " << filename << '\n';

  return 0;
}

编译并执行 example/endian_example.cpp 后, 对 test.dat 进行十六进制转储显示:

注意, 前两个 32 位整数是 big endian, 而后两个是 little endian, 即使编译并运行上述程序的机器是小端机器.

  • 当 sizeof(T) 为 4 时, Nbits 应为 24 或 32;

当 Nbits 小于 sizeof(T)*8 时, T 必须是标准整数类型 (C++std, [basic.fundamental]) 或 enum .

常见问题 (FAQ)

库级 FAQ 参见 概述 FAQ.

为什么不直接使用 Boost.Serialization?

序列化要求 I/O 中涉及的每个对象都进行一次转换. Endian 整数不需要转换或复制. 它们已经处于二进制 I/O 所需的格式, 因此可以批量读写.

endian 类型是 POD 吗?

就 C++11 的 POD 定义而言是; 就 C++03 的 POD 定义而言不是. 不过, 宏 可用于 BOOST_ENDIAN_NO_CTORS 禁用构造函数并强制 C++03 POD 性 (例如 GCC 的 __attribute__((packed)) 扩展就要求这一点.)

本机序 (native endianness) 有什么用?

它提供内建类型所没有的对齐与大小保证, 并简化泛型编程.

为什么要费心使用对齐的 endian 类型?

若类型的字节序与对齐匹配机器的字节序与对齐要求, 对齐整数运算可能更快 (最多快 10 到 20 倍). 但这样的代码可能比使用非对齐类型的代码可移植性略差.

Boost.Endian 缓冲的设计考量

  • 必须适合 I/O —— 换言之, 必须可 memcpy.

  • 必须准确提供所指定的大小与内部字节排列.

  • 当内部整数表示的位数多于外部字节表示的位数之和时, 必须正确工作. 当内部整数表示类型的位数多于外部字节位数之和时, 符号扩展也必须正确工作. 例如, 在内部用 64 位整数表示 40 位 (5 字节) 数, 对正值和负值都必须正确.

  • 无论编译器将 char 视为有符号还是无符号, 都必须正确工作 (包括使用相同的外部表示定义).

  • 非对齐类型不得导致编译器插入填充字节.

  • 实现应当以极大的谨慎提供优化. 经验表明, endian 整数的优化在更换机器或编译器后常会变成负优化. 更换编译器开关、编译器版本或同一体系结构下的 CPU 型号时, 也可能出现负优化.

编译

Boost.Endian 完全在头文件内实现, 无需链接任何 Boost 对象库.

宏 BOOST_ENDIAN_NO_CTORS 在定义时使 class endian_buffer 不带任何构造函数. 其预期用途是保证 endian_buffer 是 C++03 POD. 例如 GCC 的 __attribute__((packed)) 扩展就要求这一点.

引言

头文件 boost/endian/arithmetic.hpp 提供整数二进制类型, 可控制字节序、值类型、大小和对齐. typedef 为常见配置提供了易用的名称.

这些类型为整数数据提供可移植的字节持有者, 与特定计算机体系结构无关. 用例几乎总是涉及 I/O (通过文件或网络连接). 虽然数据可移植性是主要动机, 但这些整数字节持有者也可用于减少内存占用、文件大小或网络流量, 因为它们提供了其他方式无法获得的二进制整数大小.

这类整数字节持有者类型传统上称为 endian 类型. 关于 endianness 的完整探讨 (包括 big endian 与 little endian 的定义) 参见 Wikipedia .

Boost endian 整数提供与 C++ 标准整数类型相同的全套 C++ 赋值、算术和关系运算符, 并具有标准语义.

一元算术运算符是 `, `-`, `~`, `!`, plus both prefix and postfix `--` and `+ . 二元算术运算符是 `, `= - -= * *= / /= & &= | |= ^ ^= << <<= >> 和 >>= . 二元关系运算符是 == != < <= > 和 >= .

提供到底层值类型的隐式转换. 提供从底层值类型转换的隐式构造函数.

示例

程序 endian_example.cpp 写出一个包含四字节 big-endian 与 little-endian 整数的二进制文件:

#include <iostream>
#include <cstdio>
#include <boost/endian/arithmetic.hpp>
#include <boost/static_assert.hpp>

using namespace boost::endian;

namespace
{
  //  This is an extract from a very widely used GIS file format.
  //  Why the designer decided to mix big and little endians in
  //  the same file is not known. But this is a real-world format
  //  and users wishing to write low level code manipulating these
  //  files have to deal with the mixed endianness.

  struct header
  {
    big_int32_t     file_code;
    big_int32_t     file_length;
    little_int32_t  version;
    little_int32_t  shape_type;
  };

  const char* filename = "test.dat";
}

int main(int, char* [])
{
  header h;

  BOOST_STATIC_ASSERT(sizeof(h) == 16U);  // reality check

  h.file_code   = 0x01020304;
  h.file_length = sizeof(header);
  h.version     = 1;
  h.shape_type  = 0x01020304;

  //  Low-level I/O such as POSIX read/write or <cstdio>
  //  fread/fwrite is sometimes used for binary file operations
  //  when ultimate efficiency is important. Such I/O is often
  //  performed in some C++ wrapper class, but to drive home the
  //  point that endian integers are often used in fairly
  //  low-level code that does bulk I/O operations, <cstdio>
  //  fopen/fwrite is used for I/O in this example.

  std::FILE* fi = std::fopen(filename, "wb");  // MUST BE BINARY

  if (!fi)
  {
    std::cout << "could not open " << filename << '\n';
    return 1;
  }

  if (std::fwrite(&h, sizeof(header), 1, fi) != 1)
  {
    std::cout << "write failure for " << filename << '\n';
    return 1;
  }

  std::fclose(fi);

  std::cout << "created file " << filename << '\n';

  return 0;
}

编译并执行 endian_example.cpp 后, 对 test.dat 进行十六进制转储显示:

01020304 00000010 01000000 04030201

注意, 前两个 32 位整数是 big endian, 而后两个是 little endian, 即使编译并运行上述程序的机器是小端机器.

非对齐类型不会导致编译器在类和结构体中插入填充字节. 这是一个重要特性, 可用于最小化内存、文件和网络传输中的空间浪费.

注意
 使用对齐类型的代码可能是不可移植的, 因为对齐要求因硬件体系结构而异, 且对齐可能受编译器开关或 pragma 影响. 例如, 64 位整数的对齐在 32 位机器上可能是 32 位边界. 此外, 对齐类型仅在具有 8、16、32 和 64 位整数类型的体系结构上可用.

注释
 一字节算术类型在所有平台上具有相同的布局, 因此它们实际上从不反转字节序. 提供它们是为了支持泛型代码, 并提高代码的可读性与可检索性.

CHAR_BIT 唯一受支持的值是 8.

Nbits 的有效值如下:

  • 当 sizeof(T) 为 1 时, Nbits 应为 8;

  • 当 sizeof(T) 为 2 时, Nbits 应为 16;

  • 当 sizeof(T) 为 4 时, Nbits 应为 24 或 32;

  • 当 sizeof(T) 为 8 时, Nbits 应为 40、48、56 或 64.

sizeof(T) 的其他值不受支持.

当 Nbits 等于 sizeof(T)*8 时, T 必须是标准算术类型.

当 Nbits 小于 sizeof(T)*8 时, T 必须是 非 bool 的标准整数类型 (C++std, [basic.fundamental]).

常见问题 (FAQ)

库级 FAQ 参见 概述 FAQ.

为什么不直接使用 Boost.Serialization?

序列化要求 I/O 中涉及的每个对象都进行一次转换. Endian 整数不需要转换或复制. 它们已经处于二进制 I/O 所需的格式, 因此可以批量读写.

endian 类型是 POD 吗?

就 C++11 的 POD 定义而言是; 就 C++03 的 POD 定义而言不是. 不过, 宏 可用于 BOOST_ENDIAN_NO_CTORS 禁用构造函数并强制 C++03 POD 性 (例如 GCC 的 __attribute__((packed)) 扩展就要求这一点.)

本机序 (native endianness) 有什么用?

它提供内建类型所没有的对齐与大小保证, 并简化泛型编程.

为什么要费心使用对齐的 endian 类型?

若类型的字节序与对齐匹配机器的字节序与对齐要求, 对齐整数运算可能更快 (最多快 10 到 20 倍). 但这样的代码会比使用非对齐类型的代码可移植性略差.

为什么要提供算术运算?

提供全套运算符可减少程序杂乱, 使代码更易写也更易读. 考虑对记录中的一个变量做递增. 写成下面这样非常方便:

++record.foo;

而不是:

int temp(record.foo);
++temp;
record.foo = temp;

Boost.Endian 类型的设计考量

  • 必须适合 I/O —— 换言之, 必须可 memcpy.

  • 必须准确提供所指定的大小与内部字节排列.

  • 当内部整数表示的位数多于外部字节表示的位数之和时, 必须正确工作. 当内部整数表示类型的位数多于外部字节位数之和时, 符号扩展也必须正确工作. 例如, 在内部用 64 位整数表示 40 位 (5 字节) 数, 对正值和负值都必须正确.

  • 无论编译器将 char 视为有符号还是无符号, 都必须正确工作 (包括使用相同的外部表示定义).

  • 非对齐类型不得导致编译器插入填充字节.

  • 实现应当以极大的谨慎提供优化. 经验表明, endian 整数的优化在更换机器或编译器后常会变成负优化. 更换编译器开关、编译器版本或同一体系结构下的 CPU 型号时, 也可能出现负优化.

编译

Boost.Endian 完全在头文件内实现, 无需链接任何 Boost 对象库.

宏 BOOST_ENDIAN_NO_CTORS 在定义时使 class endian_buffer 不带任何构造函数. 其预期用途是保证 endian_buffer 是 C++03 POD. 例如 GCC 的 __attribute__((packed)) 扩展就要求这一点.

其他被要求的变更.

  • 除命名字节序转换函数外, 现在还提供了执行编译期 (通过模板) 和运行期 (通过函数实参) 分派的函数.

  • order::native 现在根据平台字节序成为 order::big 或 order::little 的同义词. 这减少了所需的模板特化数量.

  • 头文件已重新组织以更易阅读, 概要放前面, 实现跟在后面.

正式评审后的其他变更

  • 头文件 boost/endian/endian.hpp 已重命名为 boost/endian/arithmetic.hpp . 新增了头文件 boost/endian/conversion.hpp 和 boost/endian/buffers.hpp . 基础设施文件名也相应更改.

  • endian 算术类型别名已重命名, 采用对整数和浮点数一致的命名模式, 并为 endian 缓冲类型提供了一组一致的别名.

  • 非对齐类型别名仍带有 _t 后缀, 但对齐类型别名现在带有 _at 后缀.

  • endian_reverse() 重载已被添加, 覆盖 int8_t 和 uint8_t , 以提高泛型性. (Pierre Talbot)

  • endian_reverse_inplace() 的多个重载已被单一的 endian_reverse_inplace() 模板取代. (Pierre Talbot)

  • 对于允许非对齐加载与存储的 X86 和 X64 体系结构, 当大小精确匹配时, 非对齐 little endian 缓冲与算术类型使用常规加载与存储. 这使得非对齐 little endian 缓冲与算术类型在这些体系结构上显著更高效. (Jeremy Maitin-Shepard)

  • 现在使用了影响接口的 C++11 特性, 例如 noexcept . 仍支持 C++03 编译器.

  • 致谢已更新.

与过渡版本的兼容性

在 Boost 正式发布之前, 类模板 endian_arithmetic 以 endian 之名被使用了十多年, 功能相同. 其他名称也在正式发布中发生了变化. 若定义了宏 BOOST_ENDIAN_DEPRECATED_NAMES , 这些现已弃用的旧名称仍然受支持. 但类模板 endian 名称仅为支持 C++11 模板别名的编译器提供; 对 C++03 编译器, 名称必须改为 endian_arithmetic .

为支持向后兼容的头文件, 弃用头文件 boost/endian/endian.hpp 转发到 boost/endian/arithmetic.hpp . 它要求定义 BOOST_ENDIAN_DEPRECATED_NAMES . 它只应在向本库 Boost 正式发布版过渡期间使用, 因为它将在未来的某个版本中被移除.

后续方向

标准化.

计划将 Boost.Endian 提交给 C++ 标准委员会, 以便可能纳入某个技术规范 (TS) 或 C++ 标准本身.

numeric_limits 的特化.

Roger Leigh 要求所有 boost::endian 类型提供 numeric_limits 特化. 参见 GitHub issue 4 .

字符缓冲区支持.

Peter Dimov 在小型评审期间指出, 从无符号 char 数组的某一偏移处读取/写入基本算术类型 (或 <cstdint> 等价物) 是一种常见需求. 参见 Boost.Endian 小型评审帖子 .

越界检测.

Peter Dimov 在小型评审期间建议, 对超出范围的缓冲值抛出异常可能是可取的. 参见 此帖子 末尾及后续回复.
