引言

消息格式化可能是本地化中最重要的部分 - 让你的应用程序说用户的语言.

Boost.Locale 使用 GNU Gettext 本地化模型. 我们建议你阅读 GNU Gettext 的通用 文档, 因为它超出了本文档的范围.

该模型如下:

  • 首先, 我们的应用程序 foo 通过对用户界面中使用的每条消息调用 translate 函数为本地化做好准备.
    例如:
    cout << "Hello World" << endl;
    被改为
    cout << translate("Hello World") << endl;
  • 然后从源码中提取所有消息, 生成一个特殊的 foo.po 文件, 其中包含全部原始英文字符串. 
        ...
    msgid "Hello World"
    msgstr ""
    ...
  • 针对受支持的 locale 翻译 foo.po 文件. 例如, de.po, ar.po, en_CA.po 和 he.po. 
        ...
    msgid "Hello World"
    msgstr "שלום עולם"
    然后编译为二进制 mo 格式, 并存储在以下文件结构中: 
        de
    de/LC_MESSAGES
    de/LC_MESSAGES/foo.mo
    en_CA/
    en_CA/LC_MESSAGES
    en_CA/LC_MESSAGES/foo.mo
    ...

    应用程序启动时加载所需的词典. 之后当 translate 函数被调用且消息写入输出流时, 会执行词典查找, 并写回本地化后的消息.

加载词典

所有词典都由 generator 类加载. 在应用程序中使用本地化字符串需要指定以下参数:

  1. 词典的搜索路径
  2. 应用程序的域 (或名称)

这是通过调用 generator 类的以下成员函数完成的:

  • add_messages_path - 添加词典的根路径.
    例如: 如果词典位于 /usr/share/locale/ar/LC_MESSAGES/foo.mo, 那么路径应为 /usr/share/locale.
  • add_messages_domain - 添加应用程序的域 (名称). 在上例中应为 "foo".
注释
为加载词典, 至少应指定一个域和一个路径.

下面是我们第一个完全本地化程序的示例:

#include <boost/locale.hpp>
#include <iostream>
using namespace boost::locale;
int main()
{
generator gen;
// 指定词典的位置
gen.add_messages_path(".");
gen.add_messages_domain("hello");
// 生成 locale 并注入 iostream
std::locale::global(gen(""));
std::cout.imbue(std::locale());
// 使用当前系统 locale 显示消息
std::cout << translate("Hello World") << std::endl;
}

消息翻译

翻译消息有两种方式:

  • 使用 boost::locale::translate() 函数族:
    这些函数创建一个特殊的代理对象 basic_message, 它可以根据给定 locale 转换为字符串, 或写入 std::ostream 并按 std::ostream's locale 格式化消息.
    它非常便于处理 std::ostream 对象以及推迟消息翻译
  • 使用 boost::locale::gettext() 函数族:
    这些函数用于直接消息翻译: 它们接收原始消息或键作为参数, 并在给定 locale 下将其转换为 std::basic_string.
    这些函数的名称与 GNU Gettext 库中使用的名称相似.

间接消息翻译

让我们能够翻译消息的基本函数是 boost::locale::translate() 函数族.

这些函数以字符类型 CharType 作为模板参数, 并接受 CharType const * 或 std::basic_string<CharType> 作为输入.

这些函数接收一条原始消息并返回一个特殊的代理对象 - basic_message<CharType>. 该对象保存消息格式化所需的全部信息.

当该对象写入输出 ostream 时, 它会根据 iostream 中注入的 locale 对消息执行词典查找.

如果在词典中找到该消息, 就将其写入输出流; 否则将原始字符串写入流.

例如:

// 翻译一条简单消息 "Hello World!"
std::cout << boost::locale::translate("Hello World!") << std::endl;

这使程序可以把消息翻译推迟到真正需要时才进行, 甚至可以面向不同的 locale 目标.

// 多个我们要写入消息的输出流
// 英语、日语、希伯来语等
// 每个流都安装了一个 std::locale 对象,
// 它代表各自特定的 locale
std::ofstream en,ja,he,de,ar;
// 将一条消息发送到多个流
void send_to_all(message const &msg)
{
// 在下面每种情况下
// 消息会被翻译成不同的
// 语言
en << msg;
ja << msg;
he << msg;
de << msg;
ar << msg;
}
int main()
{
...
send_to_all(translate("Hello World"));
}

复数形式

GNU Gettext 消息目录对复数形式提供了简单、健壮而强大的支持. 我们建议阅读 GNU 原始文档 此处.

我们来尝试解决一个简单的问题: 向用户显示一条消息.

if(files == 1)
cout << translate("You have 1 file in the directory") << endl;
else
cout << format(translate("You have {1} files in the directory")) % files << endl;
boost::locale::format
basic_format< char > format
基于 char 的 format 的定义.
定义 format.hpp:418

当处理英语以外的语言时, 这个非常简单的任务变得相当复杂. 许多语言有多于两种复数形式. 例如, 希伯来语对单数、双数、复数以及 10 以上的复数都有特殊形式. 它们无法用 "n 是否为 1" 这种简单规则来区分

正确的解决方案是让翻译者能够自行选择复数形式. 因此 translate 函数可以接收两个附加参数: 英语复数形式和一个数字: translate(single,plural,count)

例如:

cout << format(translate( "You have {1} file in the directory",
"You have {1} files in the directory",
files)) % files << endl;

词典中的一个特殊条目指定在目标语言中选择正确复数形式的规则. 例如, 斯拉夫语族有 3 种复数形式, 可用如下公式选择:

plural=n%10==1 && n%100!=11 ? 0 : n%10>=2 && n%10<=4 && (n%100<10 || n%100>=20) ? 1 : 2;

这样的公式存储在消息目录自身中, 并在翻译期间求值以提供正确的形式.

因此对于 1, 3 和 5 这几个值, 上面的代码会在俄语 locale 下显示 3 种不同的形式:

У вас есть 1 файл в каталоге
У вас есть 3 файла в каталоге
У вас есть 5 файлов в каталоге

而对于完全没有复数形式的日语, 对任何数值都会显示相同的消息.

更多详细信息请参阅 GNU Gettext: 11.2.6 复数形式的附加函数

添加上下文信息

在很多情况下, 仅提供原始英文字符串不足以获得正确的翻译. 有时你需要提供一些上下文信息. 例如在德语中, 标为 "open" 的按钮在"打开文件"的上下文中译为 "öffnen", 在建立互联网连接的上下文中译为 "aufbauen".

在这些情况下, 你必须通过添加注释向原始字符串加入一些上下文信息.

button->setLabel(translate("File","open"));

在单数与复数两种形式中, 上下文信息都作为 translate 函数的第一个参数提供. 翻译者会看到这一上下文信息, 从而能够正确翻译 "open" 字符串.

例如, po 文件的样子如下:

msgctxt "File"
msgid "open"
msgstr "öffnen"
msgctxt "Internet Connection"
msgid "open"
msgstr "aufbauen"
注释
提取字符串和格式化消息目录需要较新版本的 gettext 工具 (>=0.15) 才能支持上下文信息.

使用多个消息域

在某些情况下, 使用多个消息域会很有用.

例如, 如果应用程序由多个独立模块组成, 它可以有多个域 - 每个模块一个独立的域.

例如, 开发 FooBar 办公套件时, 我们可能有:

  • FooBar 文字处理器, 使用 "foobarwriter" 域
  • FooBar 电子表格, 使用 "foobarspreadsheet" 域
  • FooBar 拼写检查器, 使用 "foobarspell" 域
  • FooBar 文件处理器, 使用 "foobarodt" 域

使用非默认域有三种方式:

  • 使用 iostream 时, 可以使用带参数的操纵器 as::domain(std::string const &), 它允许在流中切换域:
    cout << as::domain("foo") << translate("Hello") << as::domain("bar") << translate("Hello");
    // 第一个翻译取自词典 foo, 另一个取自词典 bar

    std::wstring foo_msg = translate(L"Hello World").str("foo");
    std::wstring bar_msg = translate(L"Hello World").str("bar");
  • 可以使用 便捷 接口直接指定域:

直接翻译 (便捷接口)

许多应用程序不把消息直接写入输出流, 或在进程中只使用一个 locale, 因而为单条消息调用 translate("Hello World").str() 会很繁琐. 因此 Boost.Locale 提供了类似 GNU Gettext 的本地化函数, 用于直接翻译消息. 不过, 与 GNU Gettext 函数不同, Boost.Locale 的翻译函数提供一个额外的可选参数 (locale), 并支持宽字符、u16 和 u32 字符串.

类 GNU Gettext 函数的原型见 本节.

这些函数可以为不同形式添加不同的前缀:

  • d - 在特定域中翻译
  • n - 复数形式翻译
  • p - 在特定上下文中翻译
MessageBoxW(0,pgettext(L"File Dialog",L"Open?").c_str(),gettext(L"Question").c_str(),MB_YESNO);

从源码提取消息

有许多工具可以把源码中的消息提取为 .po 文件格式. 最流行且"原生"的工具是 xgettext, 它在大多数 Unix 系统上默认安装, 并且可以在 Windows 上免费下载 (见 在 Windows 上使用 Gettext 工具).

例如, 我们有一个名为 dir.cpp 的源文件, 它输出:

cout << format(translate("Listing of catalog {1}:")) % file_name << endl;
cout << format(translate("Catalog {1} contains 1 file","Catalog {1} contains {2,num} files",files_no))
% file_name % files_no << endl;

现在我们运行:

xgettext --keyword=translate:1,1t --keyword=translate:1,2,3t dir.cpp

随后生成了一个名为 messages.po 的文件, 其内容大致如下:

#: dir.cpp:1
msgid "Listing of catalog {1}:"
msgstr ""
#: dir.cpp:2
msgid "Catalog {1} contains 1 file"
msgid_plural "Catalog {1} contains {2,num} files"
msgstr[0] ""
msgstr[1] ""

该文件可以交给翻译者, 以适配特定语言.

我们使用了 --keyword 这一属于 xgettext 的参数, 使其适合从用 Boost.Locale 本地化的源码中提取消息, 查找 translate() 函数调用而非默认的 gettext() 与 ngettext(). 第一个参数 –keyword=translate:1,1t 为基本消息提供模板: 一个以 1 个参数调用的 translate 函数 (1t), 并把第一条消息作为键. 第二个 –keyword=translate:1,2,3t 用于复数形式. 它告诉 xgettext 使用带 3 个参数的 translate() 函数调用 (3t), 并把第 1 和第 2 个参数作为键. 附加标记 Nc 可用于标注上下文信息.

适用于 Boost.Locale 的完整 xgettext 参数集为:

xgettext --keyword=translate:1,1t --keyword=translate:1c,2,2t \
--keyword=translate:1,2,3t --keyword=translate:1c,2,3,4t \
--keyword=gettext:1 --keyword=pgettext:1c,2 \
--keyword=ngettext:1,2 --keyword=npgettext:1c,2,3 \
source_file_1.cpp ... source_file_N.cpp

自定义文件系统支持

当对实际文件系统的访问受限 (如 ActiveX 控件中), 或开发者想发布一体化可执行文件时, 能够从自定义位置 (自定义文件系统) 加载 gettext 目录会很有用.

Boost.Locale 提供一个选项, 可安装 boost::locale::message_format 刻面, 并使用 boost::locale::gnu_gettext::messages_info 结构中提供的自定义选项.

该结构包含基于 boost::function 的 callback, 允许用户提供加载消息目录文件的自定义功能.

例如:

// 配置消息目录的所有选项
namespace blg = boost::locale::gnu_gettext;
blg::messages_info info;
info.language = "he";
info.country = "IL";
info.encoding="UTF-8";
info.paths.push_back(""); // 需要有路径, 即使是空路径
info.domains.push_back(blg::messages_info::domain("my_app"));
info.callback = some_file_loader; // 提供回调
// 创建不支持消息的基本 locale
boost::locale::generator gen;
std::locale base_locale = gen("he_IL.UTF-8");
// 为 "char" 支持向最终 locale 安装消息目录
// 我们即将使用的
std::locale real_locale(base_locale,blg::create_messages_facet<char>(info));

非 US-ASCII 键

Boost.Locale 假定你使用英文作为原始文本消息. 最佳实践是为原始键使用 US-ASCII 字符.

不过, 在某些情况下在文本中插入一些 Unicode 字符会很有用, 例如版权符号 "©".

只要你的窄字符串编码是 UTF-8, 就无需进一步操作.

Boost.Locale 假定你的源码以 UTF-8 编码, 且输入的窄字符串使用 UTF-8 - 这是当今大多数编译器的默认设置 (Microsoft Visual C++ 是明显的例外).

但如果源文件中窄字符串的编码不是 UTF-8 而是其他编码 (如 windows-1252), 字符串就会被误读.

你可以在为应用程序指定域名时指定原始字符串的字符集.

#include <boost/locale.hpp>
#include <iostream>
using namespace boost::locale;
int main()
{
generator gen;
// 指定词典的位置
gen.add_messages_path(".");
// 指定源字符串的编码
gen.add_messages_domain("copyrighted/windows-1255");
// 生成 locale 并注入 iostream
std::locale::global(gen(""));
std::cout.imbue(std::locale());
// 在 Windows 1255 中 (C) 符号编码为 0xA9
cout << translate("© 2001 All Rights Reserved") << endl;
}

因此, 如果程序运行在 UTF-8 locale 下, 当词典中缺少该键时, 版权符号会自动转换为适当的 UTF-8 序列.

问答

  • 使用 Boost.Locale 需要 GNU Gettext 吗?
    Boost.Locale 提供了加载和使用 GNU Gettext 消息目录的运行时环境, 但它不提供生成、翻译、编译和管理这些目录的工具. Boost.Locale 只重新实现了 GNU Gettext 的 libintl.
    你可能需要:
    1. Boost.Locale 本身 - 用于运行时.
    2. 从源码提取并管理字符串的工具: GNU Gettext 提供了很好的工具, 但也有其他实现可用.
    3. 一个好的翻译程序, 如 Lokalize, Pedit 或 GTranslator.
  • 为什么 Boost.Locale 不提供提取和管理消息目录的工具? 我为什么要使用带 GPL 的软件? 我的程序或消息目录会受其许可证影响吗?
    1. Boost.Locale 不链接也不使用任何 GNU Gettext 代码, 因此你不必为代码担心, 运行时库是完全重新实现的.
    2. 你可以自由使用带 GPL 的软件来提取和管理目录, 就像你可以自由使用带 GPL 的编辑器一样. 这不会影响你的消息目录或代码.
    3. 我看不出有什么理由要重新实现 xgettext, msgfmt, msgmerge 这些调试完善、工作良好且表现出色的工具, 尤其是它们可以免费下载, 并支持几乎所有平台. 所有 Linux 发行版、BSD 变体、Mac OS X 及其他类 Unix 操作系统都把 GNU Gettext 工具作为标准软件包提供.
      Windows 用户可以通过 MinGW 项目获取 GNU Gettext 工具. 见 在 Windows 上使用 Gettext 工具.
  • 与原始 GNU Gettext 运行时库相比, 有什么理由更偏好 Boost.Locale 的实现吗? 无论如何, 我都可能需要一些 GNU 工具.
    GNU Gettext 运行时库与 Boost.Locale 实现之间有两个重要区别:
    1. GNU Gettext 运行时每个进程只支持一个 locale. 在同一进程中使用多个 locale 和编码不是线程安全的. 对于与单个用户直接交互的应用程序 (如大多数 GUI 应用程序) 来说这完全没问题, 但对服务和服务器来说就有问题了.
    2. GNU Gettext API 只支持 8 位编码, 使其在原生使用宽字符串的环境中不适用.
    3. GNU Gettext 运行时库以 LGPL 许可证分发, 这对某些用户来说可能不方便.
