Boost.Locale
建议与迷思

建议

  • 首要也是最重要的建议: 窄字符串优先使用 UTF-8 编码——它表示所有受支持的 Unicode 字符, 并且比 Latin1 之类的编码更便于日常使用.
  • 请记住, 世上有许多不同的文化. 对用户的语言几乎不能做任何假设. 其日历中可能没有 "一月". 可能根本无法用 atoi 把字符串转换为整数, 因为它们可能完全不使用 "普通" 的数字 0..9. 不能假设 "空格" 字符很常见, 因为在中文里空格字符并不分隔单词. 文本可能从右向左书写, 也可能从上向下书写, 等等.
  • 使用消息格式化时, 尽可能提供多的上下文信息. 翻译整句优于翻译单个单词. 翻译单词时, 务必加上一些上下文信息.

迷思

要在我的应用程序中使用 Unicode, 我应该到处使用宽字符串.

Unicode 并不限于宽字符串. std::string 和 std::wstring 都能保存并处理 Unicode 文本. 更重要的是, 在跨平台应用程序中 std::string 的语义要清晰得多, 因为所有 "Unicode" 字符串都是 UTF-8. "宽" 字符串可能随平台不同而被编码为 "UTF-16" 或 "UTF-32", 因此在处理 Unicode 时它们甚至可能不如基于 char 的字符串方便.

UTF-16 是最佳的工作编码.

人们普遍认为 UTF-16 是存储信息的最佳编码, 因为它给出的字符串表示 "最短".

事实上, 它可能是使用起来最容易出错的编码. 最大的问题在于位于 BMP 之外的码点, 它们必须用代理对来表示. 这些字符非常少见, 许多应用程序都没有针对它们做过测试.

例如:

  • Qt3 无法处理 BMP 之外的字符.
  • 编辑码点高于 0xFFFF 的字符时常常暴露出令人不快的缺陷: 例如, 在 Windows 记事本中要删除这样一个字符, 必须按两次退格键.

因此 UTF-16 可以用于 Unicode, 事实上 ICU 和许多其他应用程序都使用 UTF-16 作为其内部 Unicode 表示, 但你必须非常小心, 绝不要假定一个码点 == 一个 UTF-16 字符.
