尽管迭代器接口十分丰富, 但接口中存在一个为全部功能所必需的核心子集. 我们已为迭代器确定出以下核心行为:

  • 解引用
  • 递增
  • 递减
  • 相等比较
  • 随机访问移动
  • 距离测量

除上述行为之外, 核心接口元素还包括通过迭代器特征暴露的关联类型: value_type、reference、difference_type 与 iterator_category.

迭代器外观使用了奇特递归模板模式 (CRTP) [Cop95]_, 使用户能够在派生类中指定 iterator_facade 的行为. 先前的设计使用策略对象来指定行为, 但该方案因若干原因被放弃:

1. 策略对象的创建及最终的拷贝可能产生额外开销, 而当前方案可以避免这种开销.

2. 策略对象方案不允许在所创建的迭代器类型上定义自定义构造函数, 而若 iterator_facade 要用于其他库的实现, 这是必不可少的特性.

3. 若不使用 CRTP, 标准关于迭代器的 operator++ 必须返回迭代器类型本身的要求将意味着: 用本库构建的所有迭代器都不得不成为 iterator_facade<...> 的特化, 而不能是 indirect_iterator<T*> 这样更具描述性的名字. 构建新的参数化迭代器将需要繁琐的类型生成元函数, 而独立的 iterator_adaptor 层也将无从实现.

用法

iterator_facade 的用户从一个 iterator_facade 特化派生自己的迭代器类, 并把派生迭代器类作为 iterator_facade 的第一个模板参数传递. 其余模板参数的顺序经过精心选择, 以便利用有用的默认值. 例如, 在定义一个常量左值迭代器时, 用户可以把该迭代器 value_type 的 const 限定版本作为 iterator_facade 的 Value 参数传入, 并省略紧随其后的 Reference 参数.

除了实现核心接口函数之外, 从 iterator_facade 派生的迭代器通常还会定义若干构造函数. 要模型化任何标准迭代器概念, 该迭代器至少必须有一个拷贝构造函数. 此外, 若迭代器类型 X 预期与另一迭代器类型 Y 自动互操作 (如常量迭代器与可变迭代器那样), 则必须存在从 X 到 Y 或从 Y 到 X 的隐式转换 (但两者不可兼有), 通常以转换构造函数实现. 最后, 若该迭代器要模型化前向遍历迭代器或更精化的迭代器概念, 则需要一个默认构造函数.

迭代器核心访问

iterator_facade 与运算符实现需要能够访问派生类中的核心成员函数. 把核心成员函数设为公有会把实现细节暴露给用户. 这里采用的设计确保实现细节不会出现在派生迭代器类型的公有接口中.

阻止对核心成员函数的直接访问有两个优点. 首先, 用户不可能在本想访问 value_type 的成员时误用迭代器的成员函数. 这在过去曾是智能指针实现的一个问题. 第二个也是主要的优点是, 库实现者可以放心地把手写的迭代器实现替换为基于 iterator_facade 的实现, 而不必担心破坏直接访问公有核心成员函数的代码.

在朴素的实现中, 把派生类的核心成员函数保持为私有, 将要求它向 iterator_facade 以及七个运算符中的每一个授予友元关系. 为了减轻限制访问的负担, 本库提供了 iterator_core_access——一个充当通往派生迭代器类中核心成员函数之网关的类. 派生类的作者只需向 iterator_core_access 授予友元关系, 即可使其核心成员函数对本库可用.

iterator_core_access 通常实现为一个空类, 其中只包含调用迭代器核心成员函数的私有静态成员函数. 不过, 无需对网关协议进行标准化. 注意, 即使 iterator_core_access 使用公有成员函数, 也不会打开安全漏洞, 因为每个核心成员函数都保持迭代器的不变式.

operator[]

泛化迭代器的下标运算符带来特殊的挑战. 随机访问迭代器的 operator[] 只要求返回可转换为其 value_type 的东西. 若要求它返回左值, 将排除当前合法的、把被引用值保存在数据成员中的随机访问迭代器 (例如 |counting|_), 因为 *(p+n) 是指向临时迭代器 p+n 的引用, 而该临时对象在 operator[] 返回时即被销毁.

.. |counting| replace:: counting_iterator

用 iterator_facade 构建的可写迭代器实现了 issue 299_ 的首选决议所要求、并由提案 n1550_ 采纳的语义: p[n] 的结果是一个可转换为迭代器 value_type 的对象, 且 p[n] = x 等价于 *(p + n) = x (注意: 该结果对象可实现为包含 p+n 副本的代理). 无论其实现的其他细节如何, 该方法对任何随机访问迭代器都能正常工作. 对自己迭代器的实现了解更多细节的用户, 可以在派生迭代器类中自行实现一个返回左值的 operator[]; 它会向该迭代器的客户隐藏 iterator_facade 所提供的那个.

.. _n1550: http://www.open-std.org/JTC1/SC22/WG21/docs/papers/2003/n1550.htm

.. _issue 299: http://www.open-std.org/jtc1/sc22/wg21/docs/lwg-active.html#299

operator->

可读迭代器 (以及如今的输入迭代器) 的 reference 类型实际上不必是引用, 只要它可转换为该迭代器的 value_type 即可. 然而, 当 value_type 是类类型时, 仍必须能够通过 operator-> 访问成员. 因此, 其 reference 类型实际上不是引用的迭代器, 必须从其 operator-> 返回一个包含被引用值副本的代理.

iterator_facade 的 operator-> 与 operator[] 的返回类型未被显式指定. 作为替代, 这些类型以一组要求来描述, iterator_facade 的实现必须满足这组要求.

.. [Cop95] [Coplien, 1995] Coplien, J., Curiously Recurring Template Patterns, C++ Report, February 1995, pp. 24-27.

上文使用的 enable_if_interoperable 模板仅用于说明. 只要派生类型 Dr1 与 Dr2 可互操作——即至少其中一个类型可转换为另一个——成员运算符才应进入重载集. enable_if_interoperable 方式使用 SFINAE 在类型不可互操作时把运算符移出重载集. 这些运算符的行为应当 如同 enable_if_interoperable 被定义为:

template <bool, typename> enable_if_interoperable_impl
{};

template <typename T> enable_if_interoperable_impl<true,T>
{ typedef T type; };

template<typename Dr1, typename Dr2, typename T>
struct enable_if_interoperable
  : enable_if_interoperable_impl<
        is_convertible<Dr1,Dr2>::value || is_convertible<Dr2,Dr1>::value
      , T
    >
{};

Tutorial

本节将基于多态对象链表的简单示例, 讲解如何用 iterator_facade 实现几个迭代器. 本示例的灵感来自 Keith Macdonald 发表在 posting 邮件列表 (Boost-Users) 上的一篇文章.

问题所在

假设我们已经写了一个多态链表节点基类:

# include <iostream>

struct node_base
{
    node_base() : m_next(0) {}

    // Each node manages all of its tail nodes
    virtual ~node_base() { delete m_next; }

    // Access the rest of the list
    node_base* next() const { return m_next; }

    // print to the stream
    virtual void print(std::ostream& s) const = 0;

    // double the value
    virtual void double_me() = 0;

    void append(node_base* p)
    {
        if (m_next)
            m_next->append(p);
        else
            m_next = p;
    }

 private:
    node_base* m_next;
};

通过把以下模板的各特化链接起来, 链表可以持有不同类型的对象:

template <class T>
struct node : node_base
{
    node(T x)
      : m_value(x)
    {}

    void print(std::ostream& s) const { s << this->m_value; }
    void double_me() { m_value += m_value; }

 private:
    T m_value;
};

我们可以使用以下流运算符打印任意节点:

inline std::ostream& operator<<(std::ostream& s, node_base const& n)
{
    n.print(s);
    return s;
}

我们的第一个挑战是为这些链表构建一个合适的迭代器.

基本迭代器: 使用 iterator_facade

我们将构造一个 node_iterator 类, 利用从 iterator_facade 的继承来实现该迭代器的大部分操作.

# include "node.hpp"
# include <boost/iterator/iterator_facade.hpp>

class node_iterator
  : public boost::iterator_facade<...>
{
   ...
};

模板实参: iterator_facade

iterator_facade 有若干模板参数, 因此我们必须决定各实参使用什么类型. 这些参数是 Derived、Value、CategoryOrTraversal、Reference 与 Difference.

Derived

由于 iterator_facade 预期与 CRTP [Cop95]_ 一起使用, 第一个参数是迭代器类名本身, 即 node_iterator.

Value

Value 参数决定 node_iterator 的 value_type. 本例中我们遍历的是 node_base 对象, 因此 Value 将为 node_base.

CategoryOrTraversal

现在我们必须确定 iterator traversal concept_ ——我们的 node_iterator 要模型化哪一个. 单向链表只有前向链接, 因此我们的迭代器不能是 bidirectional traversal iterator_. 我们的迭代器应当能够对同一链表进行多遍遍历 (不同于例如 istream_iterator 那样会消耗其遍历的流), 因此它必须是 forward traversal iterator_. 因此, 我们将在此位置传入 boost::forward_traversal_tag _.

.. iterator_facade 也支持旧式类别标签, 因此我们也可以在此传入 std::forward_iterator_tag; 无论如何, 所得迭代器的 iterator_category 最终都会是 std::forward_iterator_tag.

Reference

Reference 实参成为 node_iterator 的解引用操作所返回的类型, 并且也将与 std::iterator_traits<node_iterator>::reference 相同. 库对该参数的默认值为 Value&; 由于 node_base& 对该迭代器的 reference 类型是个好选择, 我们可以省略该实参, 或传入 use_default.

Difference

Difference 实参决定两个 node_iterator 之间的距离如何测量, 并且也将与 std::iterator_traits<node_iterator>::difference_type 相同. 库对 Difference 的默认值为 std::ptrdiff_t——一个适合测量内存中任意两个地址之间距离的类型, 且几乎适用于任何迭代器, 因此我们也可以省略这个实参.

因此 node_iterator 的声明将类似于:

# include "node.hpp"
# include <boost/iterator/iterator_facade.hpp>

class node_iterator
  : public boost::iterator_facade<
        node_iterator
      , node_base
      , boost::forward_traversal_tag
    >
{
   ...
};

构造函数与数据成员

接下来我们需要决定如何表示迭代器的位置. 该表示将以数据成员的形式出现, 因此我们还需要编写构造函数来初始化它们. node_iterator 的位置用指向 node_base 的指针来表示十分自然. 我们需要一个从 node_base* 构造迭代器的构造函数, 以及一个满足 forward traversal iterator_ 要求的默认构造函数 _. 我们的 node_iterator 于是变为:

# include "node.hpp"
# include <boost/iterator/iterator_facade.hpp>

class node_iterator
  : public boost::iterator_facade<
        node_iterator
      , node_base
      , boost::forward_traversal_tag
    >
{
 public:
    node_iterator()
      : m_node(0)
    {}

    explicit node_iterator(node_base* p)
      : m_node(p)
    {}

 private:
    ...
    node_base* m_node;
};

.. 严格来说, C++ 标准对默认构造的迭代器几乎没有任何要求, 因此如果我们真的关心效率, 可以把默认构造函数写成让 m_node 保持未初始化.

实现核心操作

最后一步是实现我们希望迭代器模型化的概念所要求的 core operations_. 参照 table__, 可以看到前三行适用, 因为 node_iterator 需要满足 readable iterator_、single pass iterator_ 与 incrementable iterator_ 的要求.

__ core operations_

因此我们需要提供 dereference、equal 与 increment 成员. 我们不希望这些成员成为 node_iterator 公有接口的一部分, 所以可以把它们设为私有, 并向 boost::iterator_core_access 授予友元关系——它是 iterator_facade 用来访问核心操作的"后门":

# include "node.hpp"
# include <boost/iterator/iterator_facade.hpp>

class node_iterator
  : public boost::iterator_facade<
        node_iterator
      , node_base
      , boost::forward_traversal_tag
    >
{
 public:
    node_iterator()
      : m_node(0) {}

    explicit node_iterator(node_base* p)
      : m_node(p) {}

 private:
    friend class boost::iterator_core_access;

    void increment() { m_node = m_node->next(); }

    bool equal(node_iterator const& other) const
    {
        return this->m_node == other.m_node;
    }

    node_base& dereference() const { return *m_node; }

    node_base* m_node;
};

瞧, 一个完整且符合规范的可读前向遍历迭代器! 关于其使用的可运行示例, 参见 this program.

常量 node_iterator

常量与可变迭代器

术语 **可变迭代器 (mutable iterator)** 指经由它可以修改所引用对象 (其"引用对象") 的迭代器. **常量迭代器 (constant iterator)** 则是不允许修改其引用对象的迭代器.

常量 与 可变 这两个词并不指修改迭代器本身的能力. 例如, int const* 是一个非 const 的 常量迭代器, 它可以递增但不允许修改其引用对象; 而 int* const 是一个 const 的 可变迭代器, 它本身不可修改但允许修改其引用对象.

令人困惑? 我们同意, 但这些是标准术语. 容器的常量迭代器被称为 const_iterator 这一点恐怕也无济于事.

现在, 我们的 node_iterator 让客户既能访问 node 的 print(std::ostream&) const 成员函数, 也能访问其用于修改的 double_me() 成员. 如果我们想构建一个 常量 node_iterator, 只需做三处修改:

class const_node_iterator
  : public boost::iterator_facade<
        const_node_iterator
      , node_base **const**
      , boost::forward_traversal_tag
    >
{
 public:
    const_node_iterator()
      : m_node(0) {}

    explicit const_node_iterator(node_base* p)
      : m_node(p) {}

 private:
    friend class boost::iterator_core_access;

    void increment() { m_node = m_node->next(); }

    bool equal(const_node_iterator const& other) const
    {
        return this->m_node == other.m_node;
    }

    node_base **const**\ & dereference() const { return \*m_node; }

    node_base **const**\ * m_node;
};

const 与迭代器的 value_type

C++ 标准要求迭代器的 value_type 不得 是 const 限定的, 因此 iterator_facade 会从其 const 参数中剥离 Value, 以产生迭代器的 value_type. 把 Value 实参设为 const 会向 iterator_facade 提供一个有用的提示: 该迭代器是 常量迭代器, 而默认的 Reference 实参将对所有左值迭代器都是正确的.

事实上, node_iterator 与 const_node_iterator 如此相似, 以至于把公共代码提取到一个模板中是合理的, 如下所示:

template <class Value>
class node_iter
  : public boost::iterator_facade<
        node_iter<Value>
      , Value
      , boost::forward_traversal_tag
    >
{
 public:
    node_iter()
      : m_node(0) {}

    explicit node_iter(Value* p)
      : m_node(p) {}

 private:
    friend class boost::iterator_core_access;

    bool equal(node_iter<Value> const& other) const
    {
        return this->m_node == other.m_node;
    }

    void increment()
    { m_node = m_node->next(); }

    Value& dereference() const
    { return *m_node; }

    Value* m_node;
};
typedef node_iter<node_base> node_iterator;
typedef node_iter<node_base const> node_const_iterator;

互操作性

我们的 const_node_iterator 单独使用时工作良好, 但与 node_iterator 一起使用时就不太符合预期了. 例如, 我们希望能够把一个 node_iterator 传入期望 node_const_iterator 的地方, 就像 std::list<int> 的 iterator 与 const_iterator 那样. 此外, 给定一个 node_iterator 和一个指向同一链表的 node_const_iterator, 我们应当能够对它们进行相等比较.

这种把两种不同迭代器类型配合使用的预期能力被称为 |interoperability|_. 在我们的情形中, 实现互操作很简单: 把 equal 函数模板化, 并添加一个模板化的转换构造函数 _ _:

template <class Value>
class node_iter
  : public boost::iterator_facade<
        node_iter<Value>
      , Value
      , boost::forward_traversal_tag
    >
{
 public:
    node_iter()
      : m_node(0) {}

    explicit node_iter(Value* p)
      : m_node(p) {}

    template <class OtherValue>
    node_iter(node_iter<OtherValue> const& other)
      : m_node(other.m_node) {}

 private:
    friend class boost::iterator_core_access;
    template <class> friend class node_iter;

    template <class OtherValue>
    bool equal(node_iter<OtherValue> const& other) const
    {
        return this->m_node == other.m_node;
    }

    void increment()
    { m_node = m_node->next(); }

    Value& dereference() const
    { return *m_node; }

    Value* m_node;
};
typedef impl::node_iterator<node_base> node_iterator;
typedef impl::node_iterator<node_base const> node_const_iterator;

说出真相

现在 node_iterator 与 node_const_iterator 的行为完全符合预期……差不多. 我们可以比较它们, 也可以单向转换: 从 node_iterator 到 node_const_iterator. 若尝试从 node_const_iterator 转换到 node_iterator, 转换构造函数尝试初始化 node_iterator 的 m_node (一个 node*) 时——用 node const*——会得到错误. 那么问题出在哪里?

问题在于 boost::|is_convertible|_<node_const_iterator,node_iterator>::value 将为 true, 但它应当为 false. |is_convertible|_ 说谎了, 因为它只能看到 声明 (即 node_iter 转换构造函数的声明), 却无法查看其 定义 来确认它能够编译. 一个完美的方案会让 node_iter 的转换构造函数在 m_node 转换会失败时自动消失.

.. |is_convertible| replace:: is_convertible .. _is_convertible: ../../type_traits/index.html#relationships

事实上, 使用 |enable_if|__ 可以实现这种魔法. 把转换构造函数重写如下, 我们就能在不合适的时候把它从重载集中移除:

#include <boost/type_traits/is_convertible.hpp>
#include <boost/utility/enable_if.hpp>

  ...

private:
  struct enabler {};

public:
  template <class OtherValue>
  node_iter(
      node_iter<OtherValue> const& other
    , typename boost::enable_if<
          boost::is_convertible<OtherValue*,Value*>
        , enabler
      >::type = enabler()
  )
    : m_node(other.m_node) {}
