引言

我们通过研究两个典型用例来介绍 Boost.MultiIndex 的主要概念.

单个集合上的多重排序

STL set 与 multiset 是长度可变的容器, 其中元素按给定的比较谓词高效排序. 当程序员希望按照另一种排序准则高效地排序与查找元素时, 这些容器类在功能上有所不足. 例如考虑:

struct employee
{
  int         id;
  std::string name;

  employee(int id,const std::string& name):id(id),name(name){}

  bool operator<(const employee& e)const{return id<e.id;}
};

每个员工的 ID 唯一这一事实反映在 operator< 的定义方式上, 因此存储 employee 的自然数据结构就是一个 std::set<employee>. 然而, 若想按字母顺序打印所有员工的列表, 可行的方案在存储空间、复杂度或维护便利性方面可能有缺点:

  • 把员工集合复制到 vector 或类似容器中, 并用依赖于 employee::name 的比较仿函数对其排序.
  • 维护一个指向集合元素的次级数据结构, 按名称适当地排序.
其中, 大概第二种方案会被多数关心效率的程序员采纳, 但它带来了令人头疼的负担: 保持两个结构同步. 若还要求代码具备异常安全性, 这种构造很容易变得无法维护.

Boost.MultiIndex 提供了 有序索引, 它按特定的键对元素排序, 旨在帮助需要元素序列且其中 不止一个 排序准则相关的程序员. 我们通过定义一个由多个有序索引构成的 multi_index_container 实例化来做到这一点: 每个索引单独来看, 其行为很像一个有序的 std::set (或 std::multiset), 同时整个数据结构的总体完整性得以保持. 我们的示例问题因此可以用 Boost.MultiIndex 如下解决:

#include <boost/multi_index_container.hpp>
#include <boost/multi_index/ordered_index.hpp>
#include <boost/multi_index/identity.hpp>
#include <boost/multi_index/member.hpp>

// define a multiply indexed set with indices by id and name
typedef multi_index_container<
  employee,
  indexed_by<
    // sort by employee::operator<
    ordered_unique<identity<employee> >,
    
    // sort by less<string> on name
    ordered_non_unique<member<employee,std::string,&employee::name> >
  > 
> employee_set;

void print_out_by_name(const employee_set& es)
{
  // get a view to index #1 (name)
  const employee_set::nth_index<1>::type& name_index=es.get<1>();
  // use name_index as a regular std::set
  std::copy(
    name_index.begin(),name_index.end(),
    std::ostream_iterator<employee>(std::cout));
}

不像 STL 关联容器那样只接受单个比较谓词类型, multi_index_container 被传入一个索引规格的 列表 (indexed_by), 其中每个规格诱导相应的索引. 索引通过 get<N>() 访问, 其中 N 的取值范围是从 0 到比较谓词数目减一. 索引 #0 的功能可以直接从 multi_index_container 对象访问, 无需使用 get<0>(): 例如, es.begin() 等价于 es.get<0>().begin().

注意 get 返回的是指向该索引的 引用, 而不是索引对象. 索引不能作为独立于其所属容器的对象来构造, 因此以下

// Wrong: we forgot the & after employee_set::nth_index<1>::type
const employee_set::nth_index<1>::type name_index=es.get<1>();

无法编译, 因为它试图构造索引对象 name_index. 这是用户代码中常见的错误来源.

支持快速查找的双向列表

这个研究用例让我们得以引入所谓的 序列索引, 以及它们如何与有序索引交互以构造强大的容器. 假设我们把一段文本解析成单词并存储在一个列表中:

typedef std::list<std::string> text_container;

std::string text=
  "Alice was beginning to get very tired of sitting by her sister on the "
  "bank, and of having nothing to do: once or twice she had peeped into the "
  "book her sister was reading, but it had no pictures or conversations in "
  "it, 'and what is the use of a book,' thought Alice 'without pictures or "
  "conversation?'";

// feed the text into the list
text_container tc;
boost::tokenizer<boost::char_separator<char> > tok
  (text,boost::char_separator<char>(" \t\n.,;:!?'\"-"));
std::copy(tok.begin(),tok.end(),std::back_inserter(tc));

如果想统计某个单词在文本中的出现次数, 我们会求助于 std::count:

std::size_t occurrences(const std::string& word)
{
  return std::count(tc.begin(),tc.end(),word);
}

但 occurrences 的这一实现以线性时间运行, 对大量文本而言可能无法接受. 类似地, 其他操作 (如删除选定的单词) 在 std::list 上执行起来代价过高:

void delete_word(const std::string& word)
{
  tc.remove(word); // scans the entire list looking for word
}

当性能成为考虑因素时, 我们需要一个额外的数据结构来对 tc 中的元素建立索引, 大概按字母顺序. Boost.MultiIndex 正是通过序列索引与有序索引的结合来做到这一点:

#include <boost/multi_index_container.hpp>
#include <boost/multi_index/sequenced_index.hpp>
#include <boost/multi_index/ordered_index.hpp>
#include <boost/multi_index/identity.hpp>

// define a multi_index_container with a list-like index and an ordered index
typedef multi_index_container<
  std::string,
  indexed_by<
    sequenced<>, // list-like index
    ordered_non_unique<identity<std::string> > // words by alphabetical order
  >
> text_container;

std::string text=...

// feed the text into the list
text_container tc;
boost::tokenizer<boost::char_separator<char> > tok
  (text,boost::char_separator<char>(" \t\n.,;:!?'\"-"));
std::copy(tok.begin(),tok.end(),std::back_inserter(tc));

到目前为止, 用 multi_index_container 替代 std::list 还看不出任何优势. 把文本插入容器的代码没有改变, 因为序列索引提供了与 std::list 类似的接口 (无需通过 get<0>() 显式访问该索引, 因为 multi_index_container 继承了索引 #0 的功能). 但额外规定一个有序索引使我们能以高效得多的方式实现 occurrences 与 delete_word:

std::size_t occurrences(const std::string& word)
{
  // get a view to index #1
  text_container::nth_index<1>::type& sorted_index=tc.get<1>();

  // use sorted_index as a regular std::set
  return sorted_index.count(word);
}

void delete_word(const std::string& word)
{
  // get a view to index #1
  text_container::nth_index<1>::type& sorted_index=tc.get<1>();

  // use sorted_index as a regular std::set
  sorted_index.erase(word);
}

现在, occurrences 与 delete_word 具有对数复杂度. 程序员可以像使用 std::list 那样使用索引 #0 访问文本, 而在需要对数查找时使用索引 #1.

索引指定

multi_index_container 实例化的索引通过 indexed_by 构造来规定. 例如, 实例化

typedef multi_index_container<
  employee,
  indexed_by<
    ordered_unique<identity<employee> >,
    ordered_non_unique<member<employee,std::string,&employee::name> >
  > 
> employee_set;

由一个 唯一有序索引 与一个 非唯一有序索引 组成, 而

typedef multi_index_container<
  std::string,
  indexed_by<
    sequenced<>,
    ordered_non_unique<identity<std::string> >
  >
> text_container;

中我们规定了两个索引, 第一个为 序列类型, 第二个为非唯一的 有序索引. 一般地, 我们可以规定任意数目的索引: indexed_by 的每个实参称为一个 索引说明符. 依据所规定索引的类型, 相应的说明符需要额外的信息: 例如, 说明符 ordered_unique 与 ordered_non_unique 需要提供一个 键提取器 与一个可选的 比较谓词, 二者共同指示元素排序将如何进行.

multi_index_container 实例化可以在不提供 indexed_by 部分的情况下声明: 此时采用默认的索引值, 使结果类型等价于一个普通的 std::set. 具体而言, 实例化

multi_index_container<(element)>

等价于

multi_index_container<
  (element),
  indexed_by<
    ordered_unique<identity<(element)> >
  >
>

打标签

为了取回给定 multi_index_container 的某个索引的 (引用), 程序员必须提供其序号, 这既麻烦又缺乏自描述性. 或者, 可以为索引指定 标签 (C++ 类型) 作为更方便的助记符. 若提供, 标签必须作为相应索引说明符的第一个参数传递. 以下是 employee_set 的修订版本, 其中加入了标签:

// tags 
struct name{};

typedef multi_index_container<
  employee,
  indexed_by<
    ordered_unique<identity<employee> >,
    ordered_non_unique<tag<name>,member<employee,std::string,&employee::name> >
  >
> employee_set;

标签必须通过 tag 构造传入. 任何类型都可以用作索引的标签, 尽管通常人们会选择能描述其关联索引的名称. 打标签机制使我们能写出如下表达式:

typedef employee_set::index<name>::type employee_set_by_name;
employee_set_by_name::iterator it=es.get<name>().begin();

若未为某个索引提供标签 (如前一示例的索引 #0), 则只能按编号访问该索引. 注意存在两种不同的 typedef——nth_index 与 index——分别用于按编号与按标签引用索引; 例如,

  • employee_set::nth_index<1>::type 是索引 #1 的类型,
  • employee_set::index<name>::type 是以 name 为标签的索引的类型 (本例中同样是索引 #1).
get() 则被重载以同时服务两种访问风格: 

employee_set::index<name>::type& name_index=es.get<name>();
employee_set::nth_index<1>::type& name_index2=es.get<1>(); // same index

此外, tag 类模板可以为一个索引接受多个标签, 我们可以互换使用它们: 例如, 前一示例中索引 #1 的规格可以改写为持有两个不同的标签 name 与 by_name:

// tags
struct name{};
struct by_name{};

typedef multi_index_container<
  ...
    ordered_non_unique<
      tag<name,by_name>,
      member<employee,std::string,&employee::name>
    >
  ...
> employee_set;

迭代器访问

multi_index_container 的每个索引使用自己的迭代器类型, 与其他索引的迭代器不同. 按照 STL 容器的规则, 这些迭代器被定义为索引的嵌套类型:

employee_set::nth_index<1>::type::iterator it=
  es.get<1>().find("Judy Smith");

通过用户自定义的 typedef 可以使这类表达式更具可读性:

typedef employee_set::nth_index<1>::type employee_set_by_name;
employee_set_by_name::iterator it=
  es.get<1>().find("Judy Smith");

每个索引提供的迭代器都是 常量 的, 即它们所指向的元素不能被直接修改. 这遵循有序索引的 std::set 接口, 但对其他类型 (如以 std::list 为模型的序列索引, 在那里没有这一限制) 可能令人意外. 这种看似奇怪的行为是由 multi_index_container 的工作方式所要求的; 若允许随意修改元素, 我们可能会在 multi_index_container 的有序索引中引入不一致, 而容器对此毫无察觉. 元素的修改应通过任一索引上的 更新操作 妥善进行.

索引类型

目前, Boost.MultiIndex 提供以下索引类型:

  • 有序索引像 std::set 那样对元素排序并提供类似的接口. 有 唯一 与 非唯一 变体: 前者不允许重复, 后者允许 (如 std::multiset).
  • 排名索引是有序索引的一个变种, 额外提供基于元素 排名 (它们在索引中所占的数值位置) 的查询与访问能力.
  • 序列索引以 std::list 的语义与接口为模型: 它们像双向列表那样排列元素.
  • 哈希索引通过散列技术提供对元素的快速访问, 方式类似于无序关联容器 std::unordered_set (不允许重复时) 与 std::unordered_multiset (允许重复时).
  • 随机访问索引提供与序列索引类似的接口, 另外还具备随机访问迭代器和按位置访问元素的能力.
引言 一节中的示例演练了有序索引与序列索引——它们最为常用; 其他类型的索引在教程的 索引类型 一节中介绍.

有序索引

有序索引按指定的键与关联的比较谓词对 multi_index_container 中的元素排序. 这些索引可视为标准容器 std::set 的对应物, 实际上它们的确复刻了其接口, 只是因 Boost.MultiIndex 的一般约束而有若干细微差别.

唯一与非唯一变体

有序索引分为 唯一 (禁止两个元素具有相同的键值) 与 非唯一 (允许重复) 两类. 再看一次定义

typedef multi_index_container<
  employee,
  indexed_by<
    ordered_unique<identity<employee> >,
    ordered_non_unique<member<employee,std::string,&employee::name> >
  > 
> employee_set;

在这个 multi_index_container 实例化中, 第一个索引应视为唯一的 (因为 ID 对每个员工是独占的), 因此用 ordered_unique 声明; 而第二个索引是非唯一的 (比如同一家公司可能雇用两个 John Smith), 通过使用 ordered_non_unique 来规定.

有序索引的唯一/非唯一分类影响着哪些元素允许插入给定的 multi_index_container; 简言之, 唯一有序索引模仿 std::set 的行为, 而非唯一有序索引类似于 std::multiset. 例如, 一个 employee_set 可以容纳对象 employee(0,"George Brown") 与 employee(1,"George Brown"), 但不会接受插入一个 ID 与先前插入的某个员工相同的 employee 对象.

可以规定多于一个唯一索引. 例如, 若我们扩充 employee 使其包含社会保险号的额外成员——它被合理地视为唯一——以下定义体现了这一设计:

struct employee
{
  int         id;
  std::string name;
  int         ssnumber;

  employee(int id,const std::string& name,int ssnumber):
    id(id),name(name),ssnumber(ssnumber){}

  bool operator<(const employee& e)const{return id<e.id;}
};

typedef multi_index_container<
  employee,
  indexed_by<
    // sort by employee::operator<
    ordered_unique<identity<employee> >,
    
    // sort by less<string> on name
    ordered_non_unique<member<employee,std::string,&employee::name> >,
    
    // sort by less<int> on ssnumber
    ordered_unique<member<employee,int,&employee::ssnumber> >
  >
> employee_set;

规定

indexed_by 中的有序索引说明符必须符合以下语法之一:

(ordered_unique | ordered_non_unique)
  <[(tag)[,(key extractor)[,(comparison predicate)]]]>

(ordered_unique | ordered_non_unique)
  <[(key extractor)[,(comparison predicate)]]>

第一个可选参数在 标签 与索引关联时使用. 下面我们简要讨论有序索引说明符的其余参数.

键提取

有序索引规格中的第一个模板参数 (若提供标签则为第二个) 提供一个 键提取 谓词. 该谓词接收整个元素 (在我们的示例中, 是对 employee 对象的引用) 并返回执行排序所依据的那部分信息. 在多数情况下, 会出现以下两种情形之一:

  • 整个元素充当键, 如 employee_set 中第一个索引的情形. 预定义的 identity 谓词在此可作键提取器使用; identity 把作为实参传入的同一对象作为键返回.
  • 比较在元素的特定数据成员上进行; 这十分贴近关系数据库中在表的一列上建立索引的做法. Boost.MultiIndex 提供 member, 它把由给定指针所指定的元素成员作为键返回.
作为示例, 再次考虑 employee_set 的定义. 第一个索引的规定: 

ordered_unique<identity<employee> >

通过 identity 规定 element 对象本身充当该索引的键. 另一方面, 第二个索引中:

ordered_non_unique<member<employee,std::string,&employee::name> >

我们用 member 提取 name——它对应 employee 对象的一部分. 该索引的键类型于是为 std::string.

除 identity 与 member 外, Boost.MultiIndex 还提供若干其他预定义键提取器, 以及组合它们的强大方式. 键提取器也可以由用户定义. 关于本主题更详细的阐述, 请查阅教程的 键提取一节.

比较谓词

有序索引规格的最后一部分是关联的 比较谓词, 它必须以小于的方式排列键. 这些比较谓词与 std::set 等 STL 容器所用的没有区别. 默认情况下 (即未提供比较谓词时), 键类型为 key_type 的索引按 std::less<key_type> 对元素排序. 若需要其他比较准则, 可以在索引声明中作为附加参数指定:

// define a multiply indexed set with indices by id and by name
// in reverse alphabetical order
typedef multi_index_container<
  employee,
  indexed_by<
    ordered_unique<identity<employee> >, // as usual
    ordered_non_unique<
      member<employee,std::string,&employee::name>,
      std::greater<std::string>  // default would be std::less<std::string>
    >
  >
> employee_set;

特殊查找操作

给定的有序索引允许基于其键类型 (而非整个元素) 进行查找. 例如, 要在 employee_set 中查找 Veronica Cruz, 可以这样写:

employee_set es;
...
typedef employee_set::index<name>::type employee_set_by_name;
employee_set_by_name::iterator it=es.get<name>().find("Veronica Cruz");

另外, Boost.MultiIndex 提供接受与索引 key_type 不同的搜索键的查找操作——当 key_type 对象的创建代价高昂时, 这是一项特别有用的设施. 有序 STL 容器无法提供此功能, 这常导致不雅的变通办法: 例如考虑确定 ID 落在区间 [0,100] 内的员工这一问题. 鉴于 employee_set 索引 #0 的键就是 employee 本身, 直观的第一种写法如下:

employee_set::iterator p0=es.lower_bound(employee(0,""));
employee_set::iterator p1=es.upper_bound(employee(100,""));

然而注意, std::less<employee> 实际上只取决于员工的 ID, 因此仅仅为了 ID 而创建完整的 employee 对象并不划算. Boost.MultiIndex 允许避免这一点: 定义一个合适的比较谓词

struct comp_id
{
  // compare an ID and an employee
  bool operator()(int x,const employee& e2)const{return x<e2.id;}

  // compare an employee and an ID
  bool operator()(const employee& e1,int x)const{return e1.id<x;}
};

然后这样写查找:

employee_set::iterator p0=es.lower_bound(0,comp_id());
employee_set::iterator p1=es.upper_bound(100,comp_id());

这里我们不仅传入 ID 而不是 employee 对象, 还传入了一个替代的比较谓词. 一般地, 有序索引的查找操作被重载为接受 兼容排序准则. 此语境下兼容性的准确定义见参考文档, 但粗略地说, 我们称比较谓词 C1 与 C2 兼容, 如果任何按 C2 排序的序列相对于 C1 也是有序的. 以下展示兼容谓词的一个更有趣的用法:

// sorting by name's initial
struct comp_initial
{
  bool operator()(char ch,const std::string& s)const{
    if(s.empty())return false;
    return ch<s[0];
  }

  bool operator()(const std::string& s,char ch)const{
    if(s.empty())return true;
    return s[0]<ch;
  }
};

// obtain first employee whose name begins with 'J' (ordered by name)
typedef employee_set::index<name>::type employee_set_by_name;
employee_set_by_name& name_index=es.get<name>(); 
employee_set_by_name::const_iterator it=
  name_index.lower_bound('J',comp_initial());

区间的获取

区间搜索 (即查找给定区间内的所有元素) 是非常频繁的操作, 可以求助于标准的 lower_bound 与 upper_bound, 不过方式笨拙. 例如, 以下代码取回 multi_index_container<double> 中位于区间 [100,200] 内的元素:

typedef multi_index_container<double> double_set;
// note: default template parameters resolve to
// multi_index_container<double,indexed_by<unique<identity<double> > > >.

double_set s;
...
double_set::iterator it0=s.lower_bound(100.0);
double_set::iterator it1=s.upper_bound(200.0);
// range [it0,it1) contains the elements in [100,200]

考虑严格不等式时需要对代码作细微改动. 要取回 大于 100 且 小于 200 的元素, 代码必须改写为

double_set::iterator it0=s.upper_bound(100.0);
double_set::iterator it1=s.lower_bound(200.0);
// range [it0,it1) contains the elements in (100,200)

更为复杂的是, 细心的程序员还必须考虑到所查区间的下界与上界要相互兼容: 例如, 若下界为 200 而上界为 100, 上述代码产生的迭代器 it0 与 it1 将呈相反顺序, 若尝试从 it0 遍历到 it1, 可能造成灾难性后果. 所有这些细节使区间搜索成为一项乏味且易错的任务.

range 成员函数——常与 Boost.Lambda 表达式结合使用——能大大缓解这一情况:

using namespace boost::lambda;

typedef multi_index_container<double> double_set;
double_set s;
...
std::pair<double_set::iterator,double_set::iterator> p=
  s.range(100.0<=_1,_1<=200); // 100<= x <=200
...
p=s.range(100.0<_1,_1<200);   // 100<  x < 200
...
p=s.range(100.0<=_1,_1<200);  // 100<= x < 200

range 只是接受指定所查区间下界与上界的谓词. 有关传给 range 的许可谓词的详细解释, 请查阅参考文档.

可以用特殊的 unbounded 标记省略一个或两个边界:

p=s.range(100.0<=_1,unbounded); // 100 <= x
p=s.range(unbounded,_1<200.0);  //   x <  200
p=s.range(unbounded,unbounded); // equiv. to std::make_pair(s.begin(),s.end())

更新

replace 成员函数对给定元素执行就地替换, 如下例所示:

typedef index<employee_set,name>::type employee_set_by_name;
employee_set_by_name& name_index=es.get<name>();

employee_set_by_name::iterator it=name_index.find("Anna Jones");
employee anna=*it;
anna.name="Anna Smith";      // she just got married to Calvin Smith
name_index.replace(it,anna); // update her record

replace 执行这一替换的方式使得:

  • 若被修改的元素相对于所有索引都保持其原有顺序, 复杂度为常量时间; 否则为对数时间.
  • 迭代器与引用的有效性得到保持.
  • 该操作是强异常安全的, 即若抛出某个异常 (由系统或用户的数据类型引发), multi_index_container 保持不变.
replace 是一个标准 STL 容器未提供的强大操作, 在要求强异常安全性时尤为顺手.

细心的读者可能已注意到, replace 的便利伴随着代价: 即为了执行更新, 整个元素必须被复制 两次 (取回它时以及在 replace 内部). 若元素的复制代价高昂, 仅为修改对象的一小部分而付出这样的计算代价可能相当可观. 为应对这种情况, Boost.MultiIndex 提供了另一种更新机制, 称为 modify:

struct change_name
{
  change_name(const std::string& new_name):new_name(new_name){}

  void operator()(employee& e)
  {
    e.name=new_name;
  }

private:
  std::string new_name;
};
...
typedef employee_set::index<name>::type employee_set_by_name;
employee_set_by_name& name_index=es.get<name>();

employee_set_by_name::iterator it=name_index.find("Anna Jones");
name_index.modify(it,change_name("Anna Smith"));

modify 接受一个仿函数 (或函数指针), 它被传入指向待修改元素的引用, 从而免去多余的复制. 与 replace 一样, modify 确实保持 multi_index_container 所有索引的内部排序. 然而, modify 的语义与 replace 并不完全等价. 考虑若修改元素时发生碰撞会发生什么, 即被修改的元素相对于某个唯一有序索引与另一元素冲突. 对 replace 而言, 原值被保留, 方法在不改动容器的情况下返回; 但 modify 无法采用这样的办法, 因为修改仿函数不会留下元素先前值的任何痕迹. 完整性约束于是导致如下策略: 当调用 modify 的过程中发生碰撞时, 元素被擦除, 方法返回 false. modify 还有一个接受 回滚 仿函数的版本, 用于在碰撞时撤销修改:

struct change_id
{
  change_id(int new_id):new_id(new_id){}

  void operator()(employee& e)
  {
    e.id=new_id;
  }

private:
  int new_id;
};
...
employee_set::iterator it=...

int old_id=it->id; // keep the original id

// try to modify the id, restore it in case of collisions
es.modify(it,change_id(321),change_id(old_id));

示例中, 当修改导致与另一元素碰撞时, 会调用 change_id(old_id) 来恢复原状. replace、modify 与带回滚的 modify 之间的行为差异, 需要程序员逐例考虑以确定最佳的更新机制.

各更新机制的行为.
更新函数 若发生碰撞...
replace(it,x) 替换不发生.
modify(it,mod) 元素被擦除.
modify(it,mod,back) back 用于恢复原状. (若 back 抛出异常, 元素被擦除.)

也提供基于键的 modify 版本, 名为 modify_key. 此时, 修改仿函数被传入元素中 key_type 部分的引用, 而不是整个对象.

struct change_str
{
  change_str(const std::string& new_str):new_str(new_str){}

  // note this is passed a string, not an employee
  void operator()(std::string& str)
  {
    str=new_str;
  }

private:
  std::string new_str;
};
...
typedef employee_set::index<name>::type employee_set_by_name;
employee_set_by_name& name_index=es.get<name>();

employee_set_by_name::iterator it=name_index.find("Anna Jones");
name_index.modify_key(it,change_str("Anna Smith"));

与 modify 一样, modify_key 也有带回滚与不带回滚的版本. modify 与 modify_key 特别适合与 Boost.Lambda 结合使用来定义修改仿函数:

using namespace boost::lambda;

typedef employee_set::index<name>::type employee_set_by_name;
employee_set_by_name& name_index=es.get<name>();

employee_set_by_name::iterator it=name_index.find("Anna Jones");
name_index.modify_key(it,_1="Anna Smith");

modify_key 要求键提取器属于一种称为 读/写 的特殊类型: 情形通常如此, 但并非总是如此.

序列索引

与有序索引不同, 序列索引不对元素强加固定顺序: 相反, 元素可以排列在序列的任意位置, 正如 std::list 所允许的那样. 序列索引的接口因此设计在 std::list 的接口之上; 标准容器提供的几乎所有操作都在此得到复刻, 偶尔在语法和/或语义上有变化, 以应对 Boost.MultiIndex 施加的约束. 一个重要差异——前文 已提及——是序列索引迭代器所指向的值被视为 常量:

multi_index_container<
  int,
  indexed_by<sequenced<> >
> s;            // list-like container

s.push_front(0);
*(s.begin())=1; // ERROR: the element cannot be changed

与其他类型的索引一样, 元素修改仍然可以通过 更新操作 完成.

考虑一个拥有两个或更多索引的 multi_index_container, 其中一个是序列类型. 若元素通过另一个索引插入, 它将被自动追加到序列索引的末尾. 一个例子有助于澄清这一点:

multi_index_container<
  int,
  indexed_by<
    sequenced<>,           // sequenced type
    ordered_unique<identity<int> > // another index
  >
> s;

s.get<1>().insert(1); // insert 1 through index #1
s.get<1>().insert(0); // insert 0 through index #1

// list elements through sequenced index #0
std::copy(s.begin(),s.end(),std::ostream_iterator<int>(std::cout));

// result: 1 0

因此, 当插入不是通过序列索引进行时, 序列索引的行为是保持插入顺序.

规定

序列索引用 sequenced 构造来规定:

sequenced<[(tag)]>

标签 参数是可选的.

列表操作

如前所述, 序列索引模仿 std::list 的接口, 其中的大多数原有操作也都提供. 然而, 这些操作的语义与复杂度并不总是与标准容器一致. 差异主要源于这样一个事实: 向序列索引的插入不保证成功, 因为可能被 multi_index_container 的其他索引禁止. 更多细节请查阅 参考文档.

更新

与有序索引一样, 序列索引提供 replace 与 modify 操作, 功能相同. 但没有类似的 modify_key, 因为序列索引不是基于键的.

迭代器的投影

给定索引 i1 与 i2——二者位于同一 multi_index_container 上——project 可用于取得 i2 迭代器, 对应于给定的 i1 迭代器, 二者指向容器中的同一元素. 这一功能使程序员在执行复杂操作时可以在同一 multi_index_container 的不同索引之间移动:

typedef employee_set::index<name>::type employee_set_by_name;
employee_set_by_name& name_index=es.get<name>();

// list employees by ID starting from Robert Brown's ID

employee_set_by_name::iterator it1=name_index.find("Robert Brown");

// obtain an iterator of index #0 from it1
employee_set::iterator it2=es.project<0>(it1); 

std::copy(it2,es.end(),std::ostream_iterator<employee>(std::cout));

一个稍更有趣的例子:

text_container tc;

// get a view to index #1 (ordered index on the words)
text_container::nth_index<1>::type& sorted_index=tc.get<1>();

// prepend "older" to all occurrences of "sister"

text_container::nth_index<1>::type::iterator it1=
  sorted_index.lower_bound("sister");
  
while(it1!=sorted_index.end()&&*it1=="sister"){
  // convert to an iterator to the sequenced index
  text_container::iterator it2=tc.project<0>(it1);

  tc.insert(it2,"older");
  ++it1;
}

若可用, project 也可以配合 标签 使用.

复杂度与异常安全性

multi_index_container 提供与等价 STL 容器相同的复杂度与异常安全性保证. 面对插入时, 迭代器与引用的有效性得到保持, 即使对于 replace 与 modify 操作亦然.

multi_index_container 的适当实例化实际上可以模拟 std::set、std::multiset 与 (限制更多的) std::list, 如 技术 一节所示. 这些模拟几乎与原 STL 容器一样高效; 关于复杂度保证的更多信息请查阅 参考文档, 效率的实际测量见 性能一节.
