值语义

multi_index_container 具有通常与复制构造和赋值相关联的值语义, 即创建源容器元素的副本并插入目标容器. 更有趣的是, 复制还会为容器的 每个索引 重建元素排列的原有顺序. 这意味着, 在定义了相等性的索引类型上, 所有索引的相等性在复制或赋值下得以保持. 此行为可视为对复制语义一般规则的自然扩展, 该规则说: 若 y 是 x 的副本, 则 y==x.

使用 ctor_args_list

虽然在多数情况下 multi_index_container 会被默认构造 (或从既有的 multi_index_container 复制), 有时需要为所用的内部对象 (键提取器、比较谓词、分配器) 指定特定的值, 例如这些对象中某个没有默认构造函数时. 标准 STL 容器也会遇到同样的情况, 它们允许可选地指定这类对象:

// example of non-default constructed std::set
template<typename IntegralType>
struct modulo_less
{
  modulo_less(IntegralType m):modulo(m){}

  bool operator()(IntegralType x,IntegralType y)const
  {
    return (x%modulo)<(y%modulo);
  }

private:
  IntegralType modulo;
};

typedef std::set<unsigned int,modulo_less<unsigned int> > modulo_set;

modulo_set m(modulo_less<unsigned int>(10));

multi_index_container 同样提供这一功能, 不过方式复杂得多, 因为 multi_index_container 的构造函数必须接受其所有索引的内部对象的值. multi_index_container 构造函数的完整形式为

explicit multi_index_container(
    const ctor_args_list& args_list=ctor_args_list(),
    const allocator_type& al=allocator_type());

分配器对象的规格没有特别的问题; 至于 ctor_args_list, 该对象的设计目的是持有 multi_index_container 中每个索引所需的构造值. 从用户的角度看, ctor_args_list 等价于类型

boost::tuple<C0,...,CI-1>

其中 I 是索引数目, 而 Ci 是

nth_index<i>::type::ctor_args

即嵌套类型 ctor_args (属于第 i 个索引). 每个 ctor_args 类型又是一个元组, 持有其关联索引的构造实参值: 有序索引要求一个键提取器对象与一个比较谓词; 哈希索引接受初始桶数、键提取器、哈希函数与等价谓词; 而序列索引与随机访问索引不需要任何构造实参. 例如, 给定定义

typedef multi_index_container<
  unsigned int,
  indexed_by<
    hashed_unique<identity<unsigned int> >,
    ordered_non_unique<identity<unsigned int>, modulo_less<unsigned int> >,
    sequenced<>,
    random_access<>
  >
> modulo_indexed_set;

相应的 ctor_args_list 类型等价于

boost::tuple<
  // ctr_args of index #0
  boost::tuple<
    std::size_t, // initial number of buckets; 0 if unspecified
    identity<unsigned int>,
    boost::hash<unsigned int>,
    std::equal_to<unsigned int> >,    

  // ctr_args of index #1
  boost::tuple<
    identity<unsigned int>,
    modulo_less<unsigned int> >,
  
  // sequenced indices do not have any construction argument
  boost::tuple<>,

  // neither do random access indices
  boost::tuple<>
>

这样的 modulo_indexed_set 不能默认构造, 因为 modulo_less 不提供默认构造函数. 以下展示构造如何完成:

modulo_indexed_set::ctor_args_list args_list=
  boost::make_tuple(
    // ctor_args for index #0 is default constructible
    modulo_indexed_set::nth_index<0>::type::ctor_args(),
    
    boost::make_tuple(identity<unsigned int>(),modulo_less<unsigned int>(10)),
    
    // these are also default constructible (actually, empty tuples) 
    modulo_indexed_set::nth_index<2>::type::ctor_args(),
    modulo_indexed_set::nth_index<3>::type::ctor_args()
  );

modulo_indexed_set m(args_list);

特殊分配器支持

Boost.MultiIndex 允许使用比 C++ 标准严格要求略更宽的一类分配器, 详见 参考文档. 所支持的一类重要非标准分配器由 Boost Interprocess 库 提供; 这开启了把 multi_index_container 及其迭代器置于共享内存中的可能.

#include <boost/interprocess/allocators/allocator.hpp>
#include <boost/interprocess/managed_shared_memory.hpp>

namespace bip=boost::interprocess;

// a shared memory compatible allocator of ints
typedef bip::allocator<
  int,bip::managed_shared_memory::segment_manager
> shared_int_allocator;

// define a shared memory compatible multi_index_container
// using shared_int_allocator
typedef multi_index_container<
  int,
  indexed_by<
    sequenced<>,
    ordered_unique<identity<int> >
  >,
  shared_int_allocator
> unique_int_list;

...

// create a managed memory segment
bip::managed_shared_memory seg(
  bip::create_only,"SharedMemoryID",65536);

// construct a unique_int_list into the segment
unique_int_list* puil=seg.construct<unique_int_list>
  ("UniqueIntListID") // object identifier within the segment
  // Construction args: first a ctor arg list, then a
  // shared memory allocator obtained from the segment object.
  (unique_int_list::ctor_args_list(),
   unique_int_list::allocator_type(seg.get_segment_manager()));

序列化

multi_index_container 可以借助 Boost Serialization 库 进行存档与取回. 普通档案与 XML 档案均受支持. 用法很直接, 与任何其他可序列化类型没有区别. 例如:

#include <boost/archive/text_oarchive.hpp>
#include <boost/archive/text_iarchive.hpp>
#include <fstream>

...

void save(const employee_set& es)
{
  std::ofstream ofs("data");
  boost::archive::text_oarchive oa(ofs);
  oa<<es;
}

void load(employee_set& es)
{
  std::ifstream ifs("data");
  boost::archive::text_iarchive ia(ifs);
  ia>>es;
}

...

employee_set es;
... // fill it with data
save(es);

...

employee_set restored_es;
load(restored_es);

序列化能力只需链接相应的 Boost.Serialization 库模块即可自动获得: 除了声明该过程中所用档案类型的头文件外, 无需显式包含任何 Boost.Serialization 头文件. 然而, 若不使用, 可以通过全局定义宏 BOOST_MULTI_INDEX_DISABLE_SERIALIZATION 来禁用序列化支持. 为 Boost.MultiIndex 禁用序列化可以小幅改善构建时间, 在那些无法正确处理 Boost.Serialization 头文件的缺陷编译器上也可能是必需的.

按照 Boost.MultiIndex 的 值语义, 取回已存档的 multi_index_container 不仅恢复元素, 还恢复它们在容器每个索引中被排列成的顺序. 不过该规则有一个例外: 对 哈希索引 而言, 不保证元素在恢复后的容器中被迭代的顺序; 一般而言, 依赖哈希索引中元素的顺序是不明智的, 因为它在插入或重哈希期间可能以任意方式改变——这正是哈希索引与 TR1 无序关联容器不定义相等运算符的原因.

指向 multi_index_container 各索引的迭代器也可以序列化. 迭代器的序列化必须在序列化其对应容器之后进行.

示例一节中的 示例 9 展示了 Boost.MultiIndex 的序列化能力.
