分类

Boost.MultiIndex 提供八种不同的索引类型, 可按下表所示进行分类. 有序 与 序列 索引最为常用, 已在基础一节中说明; 其余索引类型可视为前者的变种, 在功能或性能方面提供一些额外的好处.

Boost.MultiIndex 索引.

基于键 有序   ordered_unique  
  ordered_non_unique

基于键的索引 (有序索引是常见例子) 提供基于某条称为 元素键 的信息的高效元素查找: 有一整套 键提取 工具类用于规定这样的键. 快速查找在这些索引上强加了一种由内部管理的顺序, 用户不得修改; 而非基于键的索引可以自由重排, 代价是缺乏查找设施. 序列索引以 std::list 的接口为模型, 是非基于键索引的常见例子.

排名索引

假设我们有一个数字的 std::multiset, 想输出高于 75h 百分位数 的值:

typedef std::multiset<int> int_multiset;

void output_above_75th_percentile(const int_multiset& s)
{
  int_multiset::const_iterator it=s.begin();
  std::advance(it,s.size()*3/4); // linear on s.size();

  std::copy(it,s.end(),std::ostream_iterator<int>(std::cout,"\n"));
}

这段代码的问题在于, 到达目标子序列的开头涉及对容器的线性遍历. 排名索引提供了快得多的机制:

typedef multi_index_container<
  int,
  indexed_by<
    ranked_non_unique<identity<int> >
  >
> int_multiset;

void output_above_75th_percentile(const int_multiset& s)
{
  int_multiset::const_iterator it=s.nth(s.size()*3/4); // logarithmic
  std::copy(it,s.end(),std::ostream_iterator<int>(std::cout,"\n"));
}

nth(n) 返回指向 排名 (即其到索引开头的距离) 为 n 的元素的迭代器, 并以对数时间高效完成. 反过来, rank(it) 以对数时间计算 it 所指向元素的排名, 或 size() (当 it==end() 时).

int_multiset::iterator  it=s.insert(10).first;
int_multiset::size_type r=s.rank(it); // rank of 10;

排名索引提供与有序索引相同的接口, 外加若干与排名相关的操作. 这些额外功能的代价是更高的内存消耗 (每个元素一个机器字的内部附加数据) 以及插入与擦除略长的执行时间——特别是, 擦除一个元素所需的时间与 log(n) 成正比, 其中 n 是索引中的元素数目, 而对有序索引该时间是常量. 参考文档 完整详述了这些索引.

规定

排名索引的规定与 有序索引 完全一样, 只是改用 ranked_unique 与 ranked_non_unique.

(ranked_unique | ranked_non_unique)
  <[(tag)[,(key extractor)[,(comparison predicate)]]]>

(ranked_unique | ranked_non_unique)
  <[(key extractor)[,(comparison predicate)]]>

排名操作

除 nth 与 rank 外, 排名索引还提供成员函数

  • find_rank,
  • lower_bound_rank,
  • upper_bound_rank,
  • equal_range_rank 与
  • range_rank
它们的行为与对应的正常 查找 与 区间获取 操作 (find、 lower_bound 等) 一致, 但返回排名而非迭代器. 

void percentile(int n,const int_multiset& s)
{
  std::cout<<n<<" lies in the "<<
    s.upper_bound_rank(n)*100.0/s.size()<<" percentile\n";
}

你可能认为 upper_bound_rank(n) 只是 rank(upper_bound(n)) 的简写: 但实际上, 你应当优先直接使用 *_rank 操作, 因为它们比替代写法运行得更快.

哈希索引

哈希索引相对于有序索引构成一种权衡: 若使用得当, 它们提供快得多的元素查找, 代价是失去排序信息. 让我们重新审视 employee_set 示例: 假设添加一个存储社会保险号的字段, 要求按此号码的查找尽可能快. 这时可以不用通常的有序索引, 而求助于哈希索引:

#include <boost/multi_index_container.hpp>
#include <boost/multi_index/hashed_index.hpp>
#include <boost/multi_index/ordered_index.hpp>
#include <boost/multi_index/identity.hpp>
#include <boost/multi_index/member.hpp>

struct employee
{
  int         id;
  std::string name;
  int         ssnumber;

  employee(int id,const std::string& name,int ssnumber):
    id(id),name(name),ssnumber(ssnumber){}

  bool operator<(const employee& e)const{return id<e.id;}
};

typedef multi_index_container<
  employee,
  indexed_by<
    // sort by employee::operator<
    ordered_unique<identity<employee> >,
    
    // sort by less<string> on name
    ordered_non_unique<member<employee,std::string,&employee::name> >,
    
    // hashed on ssnumber
    hashed_unique<member<employee,int,&employee::ssnumber> >
  >
> employee_set

注意哈希索引不保证元素的任何特定顺序: 因此, 例如, 我们无法高效地查询 SSN 大于给定数值的员工. 通常, 在判断哈希索引是否优于有序索引时, 必须考虑这些限制.

哈希索引复刻 std::unordered_set 与 std::unordered_multiset 的接口, 仅在 multi_index_container 的一般约束所要求之处有细微差别, 并提供额外的有用能力, 如元素的就地更新. 哈希索引接口的完整规范请查阅 参考文档, 实际应用见 示例 8 与 示例 9.

唯一与非唯一变体

与有序索引一样, 哈希索引有唯一与非唯一变体, 分别由说明符 hashed_unique 与 hashed_non_unique 选择. 在后一种情形下, 键等价的元素被保存在一起, 并可以通过 equal_range 成员函数一起取回.

规定

哈希索引说明符有两种可选语法, 取决于是否提供 标签:

(hashed_unique | hashed_non_unique)
  <[(tag)[,(key extractor)[,(hash function)[,(equality predicate)]]]]>

(hashed_unique | hashed_non_unique)
  <[(key extractor)[,(hash function)[,(equality predicate)]]]>

键提取器参数的工作方式与 有序索引 完全相同; 查找、插入等操作基于提取器返回的键, 而不是整个元素.

哈希函数是这类索引快速查找能力的核心: 哈希器只是一个一元函数对象, 对任意给定的键返回一个 std::size_t 值. 一般而言, 不可能每个键都映射到不同的哈希值, 因为键的空间可能大于许可哈希码的数目: 优秀哈希器的标准是碰撞 (两个不同的键具有相同哈希值) 的概率尽可能接近零. 这是一个统计性质, 取决于给定应用中键的典型分布, 因此不可能有在 每种 可能场景中都表现卓越的通用哈希函数; 该参数的默认值使用 Boost.Hash, 它通常能提供足够好的结果.

等价谓词用于判定两个键是否应视为相同. 默认值 std::equal_to<KeyFromValue::result_type> 在多数情况下正是所需的, 因此极少需要提供自己的谓词. 注意哈希索引要求两个等价的键具有相同的哈希值, 这实际上大大缩小了选择等价谓词的自由.

查找

哈希索引的查找接口由成员函数 find、count、contains 与 equal_range 组成. 注意不提供 lower_bound 与 upper_bound, 因为这类索引中键没有内在顺序.

与有序索引一样, 这些成员函数以键而非整个对象作为搜索实参. 记住有序索引的查找操作还被增强为接受 兼容键——大致可视为“子键”. 对哈希索引, 也支持 兼容键 概念, 但其用处有限得多: 基本上, 兼容键是一个与 key_type 值的原生对象完全等价的对象, 尽管内部表示可能不同:

// US SSN numbering scheme
struct ssn
{
  ssn(int area_no,int group_no,int serial_no):
    area_no(area_no),group_no(group_no),serial_no(serial_no)
  {}

  int to_int()const
  {
    return serial_no+10000*group_no+1000000*area_no;
  }

private:
  int area_no;
  int group_no;
  int serial_no;
};

// interoperability with SSNs in raw int form

struct ssn_equal
{
  bool operator()(const ssn& x,int y)const
  {
    return x.to_int()==y;
  }

  bool operator()(int x,const ssn& y)const
  {
    return x==y.to_int();
  }
};

struct ssn_hash
{
  std::size_t operator()(const ssn& x)const
  {
    return boost::hash<int>()(x.to_int());
  }

  std::size_t operator()(int x)const
  {
    return boost::hash<int>()(x);
  }
};

typedef employee_set::nth_index<2>::type employee_set_by_ssn;

employee_set         es;
employee_set_by_ssn& ssn_index=es.get<2>();
...
// find an employee by ssn
employee e=*(ssn_index.find(ssn(12,1005,20678),ssn_hash(),ssn_equal()));

示例中, 我们提供了哈希仿函数 ssn_hash 与等价谓词 ssn_equal, 使 ssn 对象与原始 int (作为 SSN 存储于 employee_set 中) 之间可以互操作.

到目前为止, 兼容键在哈希索引语境下最有用的应用在于: 它们允许无缝使用 组合键.

更新

哈希索引有 replace、modify 与 modify_key 成员函数, 功能与有序索引中相同.

迭代器有效性与异常安全性的保证

由于 Boost.MultiIndex 框架施加的内部约束, 哈希索引就迭代器有效性与异常安全性所提供的保证, 实际上强于 C++ 标准对无序关联容器的要求:

  • 插入或重哈希期间, 迭代器有效性无论如何都得到保持: C++ 无序关联容器在执行 (隐式或显式) 重哈希时可能使迭代器失效.
  • 经由迭代器擦除一个元素或一段元素从不抛出异常, 因为内部的哈希函数与等价谓词对象实际上并未被调用.
  • rehash 无条件提供强异常安全性保证. 标准只在内部哈希函数与等价谓词对象不抛出异常时才为无序关联容器作此保证. 一个有些令人意外的推论是: 符合标准的 std::unordered_set 可能在重哈希期间抛出异常时擦除元素!
总体而言, 这些更强的保证有利于用户的便利性, 尤其是涉及迭代器稳定性者. 不过, 作为这些好处的交换, 可能会带来 (希望是极小的) 性能下降.

随机访问索引

随机访问索引提供与 序列索引 相同类型的功能, 额外优点是其迭代器为随机访问, 并且提供 operator[] 与 at() 以按元素在索引中的位置访问元素. 让我们重写先前一个 示例 中使用的容器, 用随机访问索引替代序列索引:

#include <boost/multi_index_container.hpp>
#include <boost/multi_index/random_access_index.hpp>
#include <boost/multi_index/ordered_index.hpp>
#include <boost/multi_index/identity.hpp>

// text container with fast lookup based on a random access index
typedef multi_index_container<
  std::string,
  indexed_by<
    random_access<>,
    ordered_non_unique<identity<std::string> >
  >
> text_container;

// global text container object
text_container tc;

随机访问能力使我们能高效地写出如下代码:

void print_page(std::size_t page_num)
{
  static const std::size_t words_per_page=50;

  std::size_t pos0=std::min(tc.size(),page_num*words_per_page);
  std::size_t pos1=std::min(tc.size(),pos0+words_per_page);

  // note random access iterators can be added offsets 
  std::copy(
    tc.begin()+pos0,tc.begin()+pos1,
    std::ostream_iterator<std::string>(std::cout));
}

void print_random_word()
{
  std::cout<<tc[rand()%tc.size()];
}

这种附加的灵活性是有代价的: 在索引末端以外的位置插入与删除具有线性复杂度, 而这些操作对序列索引是常量时间. 这种情况令人想起 std::list 与 std::vector 之间复杂度行为的差异: 不过对随机访问索引而言, 插入与删除从不需要复制任何元素, 因此这些操作的实际性能可以接受, 尽管理论上相对于序列索引处于劣势.

示例一节中的 示例 10 与 示例 11 实际运用了随机访问索引.

规定

随机访问索引用 random_access 构造来规定, 其中 标签 参数照常是可选的:

random_access<[(tag)]>

接口

序列索引提供的所有公开函数也由随机访问索引提供, 因此后者可以直接替代前者 (除其复杂度界限如上所述有所不同之外). 此外, 随机访问索引有用于按位置访问元素的 operator[] 与 at(), 以及成员函数 capacity 与 reserve——它们以与 std::vector 中同名设施类似的方式控制内部重新分配. 详情请查阅 参考文档.

与 std::vector

人们很容易把随机访问索引看作 Boost.MultiIndex 中 std::vector 的对应物, 但这一比喻可能有误导性, 因为二者虽在许多方面相似, 却表现出重要的语义差异. 随机访问索引的一个优点是其迭代器以及指向元素的引用是 稳定的, 即在任何插入或删除之后仍然有效. 另一方面, 随机访问索引相对于 std::vector 有若干缺点:

  • 它们不提供 内存连续性——std::vector 的一项性质, 即元素彼此相邻地存储在单个内存块中.
  • 照常, Boost.MultiIndex 中随机访问索引的元素不可变更, 只能通过成员函数 replace 与 modify 修改. 这妨碍了许多修改型算法的使用, 尽管它们本可适用于 std::vector.
后一缺点可以通过这些索引提供的 重排接口 部分弥补.

一般而言, 更有启发性的看法是把随机访问索引视为提供随机访问语义的序列索引变种, 而不是执着于 std::vector 的类比.

索引重排

按设计, 索引元素不可变更, 即迭代器只授予对它们的 const 访问, 只有通过所提供的更新接口 (replace、modify 与 modify_key) 才能修改元素. 设置这一限制是为了不破坏基于键索引的内部不变量 (例如有序索引中的升序遍历), 但它给非基于键的索引带来重要限制:

typedef multi_index_container<
  int,
  indexed_by<
    random_access<>,
    ordered_unique<identity<int> >
  >
> container;	

container    c;
std::mt19937 rng;
...
// compiler error: assignment to read-only objects
std::shuffle(c.begin(),c.end(),rng);

前一示例的遗憾之处在于, std::shuffle 执行的操作本可能与 multi_index_container 的不变量兼容, 因为其结果可以描述为随机访问索引中元素的一个排列, 而对元素本身没有任何实际修改. C++ 标准库中还有许多此类兼容算法的例子, 例如所有的排序与划分函数.

序列索引与随机访问索引提供了一种利用这类外部算法的手段. 为引入这一设施, 我们需要一个预备概念: 索引的 视图 定义为索引元素上的某个迭代器区间 [first, last), 其所有元素在区间中恰好各出现一次. 继续我们的例子, 我们可以对从容器获得的特设视图应用 std::shuffle:

// note that the elements of the view are not copies of the elements
// in c, but references to them
std::vector<boost::reference_wrapper<const int> > v;
BOOST_FOREACH(const int& i,c)v.push_back(boost::cref(i));

// this compiles OK, as reference_wrappers are swappable
std::shuffle(v.begin(),v.end(),rng);

v 的元素是 reference_wrapper——来自 Boost.Ref——指向多索引容器 (multi_index_container) 中的实际元素. 这些对象仍不允许修改被引用的实体, 但它们可交换, 这正是 std::shuffle 施加的唯一要求. 一旦把所需的重排存入视图, 就可以用以下调用把它转移到容器:

c.rearrange(v.begin());

rearrange 接受一个输入迭代器, 指示外部视图的开头 (无需末端迭代器, 因为视图长度与索引长度相同), 并在内部重定位索引的元素, 使其遍历顺序与视图匹配. 尽管需要一些变通, rearrange 允许把各种算法应用到非基于键的索引. 请注意, 视图概念非常通用, 绝不局限于上面展示的特定实现示例. 例如, multi_index_container 的各索引相对于其非基于键的索引而言确实是视图:

// rearrange as index #1 (ascending order)
c.rearrange(c.get<1>().begin());

// rearrange in descending order
c.rearrange(c.get<1>().rbegin());

对视图施加的唯一重要要求是它们必须是 自由的, 即不受基础索引上重定位的影响: 因此, rearrange 不接受以下做法:

// undefined behavior: [rbegin(),rend()) is not free with respect
// to the base index
c.rearrange(c.rbegin());

视图概念在 参考文档 中有详细定义. 示例一节中的 示例 11 演示了 rearrange 的用法.

iterator_to

Boost.MultiIndex 的所有索引都提供一个名为 iterator_to 的成员函数, 它返回指向容器中给定元素的迭代器:

multi_index_container<
  int,
  indexed_by<sequenced<> >
> c;
...
// convoluted way to do c.pop_back()
c.erase(c.iterator_to(c.back())); 

// The following, though similar to the previous code,
// does not work: iterator_to accepts a reference to
// the element in the container, not a copy.
int x=c.back();
c.erase(c.iterator_to(x)); // run-time failure ensues

iterator_to 提供了一种从指向元素的指针取回指向该元素的迭代器的途径, 从而在许多情形下使迭代器与指针在元素指称上可以互换 (遍历则不然). 尽管如此, iterator_to 的目的并不是提倡用指针替代真正的迭代器: 后者专为处理容器的元素而设计, 不仅受益于容器接口的迭代器导向, 还能在编译期与运行期暴露比原始指针多得多的编程缺陷. 因此, iterator_to 旨在用于经由迭代器访问不合适或不理想的场景:

  • 与基于指针或引用的既有 API 互操作.
  • 发布基于指针的接口 (例如设计兼容 C 的库时).
  • 以指针替代迭代器暴露出去, 可以充当一道 类型擦除 屏障, 有效地把代码使用者与所使用的具体容器这一实现细节解耦. 类似的技术——如著名的 Pimpl 惯用法——在大型项目中用于减少依赖与构建时间.
  • 自引用场景: 元素对其所属容器施加操作, 而又没有指向自身的迭代器可用.

节点处理操作

借助直接的节点操作, 元素可以在 multi_index_container 之间传递而不实际复制:

// move an employee to the retiree archive
void move_to_retirement(int ssnumber,employee_set& es,employee_set& archive)
{
  // assume employee_set has an index on SS number(not shown before)
  // extract the employee with given SS number to a node handle
  employee_set_by_ssn::node_type node=es.get<ssn>().extract(ssnumber);

  if(!node.empty()){ // employee found
    // re-insert into archive (note the use of std::move)
    archive.insert(std::move(node));
  }
}

示例中, 内部节点原样从 es 转移到 archive, 这比从源中擦除再在目标中重建更高效. node_type 是一个只可移动的类, 用于传递节点, 其接口遵循 C++ 关联容器 (set 容器版本) 的 同名类型. Boost.MultiIndex 为所有索引类型提供节点提取与插入操作, 包括序列索引 (相比之下, std::list 没有此类特性):

multi_index_container<
  int,
  indexed_by<
    sequenced<>,
    ordered_unique<identity<int> >
  >
> src;

multi_index_container<
  int,
  indexed_by<
    sequenced<>,
    ordered_non_unique<identity<int>, std::greater<int> >
  >
> dst;

...

// transfer even numbers from src to dst
for(auto first=src.begin(),last=src.end();first!=last;){
  if(*first%2==0) dst.insert(dst.end(),src.extract(first++));
  else            ++first;
}

注意 src 与 dst 类型不同, 但转移是可能的. 两个 multi_index_container 节点兼容 (即使用相同的 node_type), 当且仅当它们具有相同的元素与分配器类型, 且各自的索引一一对应——不论其唯一与否或各自的配置参数: 二者都是有序的, 或都是序列的, 等等.

或者, 无需保留中间的 node_type, 借助 merge (基于键的索引) 与 splice (非基于键的索引) 即可直接在两个容器之间转移节点.

// move older employees to retirement
void move_to_retirement_by_age(
  int max_age,employee_set& es,employee_set& archive)
{
  // assume employee_set has an index on age (not shown before)
  employee_set_by_age& ea=es.get<age>();

  // archive employees with age>max_age
  archive.merge(ea,ea.upper_bound(max_age),ea.end());
}

...

// transfer even numbers from src to dst
for(auto first=src.begin(),last=src.end();first!=last;){
  if(*first%2==0) dst.splice(dst.end(),src,first++);
  else            ++first;
}

merge/splice 有用于转移单个元素、两个迭代器之间的区间以及整个容器的重载: 更多细节请查阅 有序索引 与 序列索引 的参考文档 (其余索引提供其中一种接口). 请注意, 序列索引与随机访问索引也有一个名为 merge 的操作, 但它遵循 std::list::merge 的规范, 行为有所不同 (要求源与目标按同一准则有序). 这是 Boost.MultiIndex 直接从 C++ 标准继承的一个相当令人困惑的命名问题.

有序索引节点压缩

有序索引与排名索引借助一种称为 红黑树 的数据结构实现. 红黑树的节点包含指向父节点与两个子节点的指针, 外加一个 1 位字段——称为 节点颜色 (该结构因此得名). 由于对齐问题, 在多数体系结构上, 颜色字段占据整整一个机器字, 即 32 位系统中的 4 字节、64 位环境中的 8 字节. 这一空间浪费可以避免, 办法是把颜色位嵌入节点指针之一——前提是指针表示的位并非全部含有有用信息: 许多体系结构正是如此, 其中这类节点对齐到偶数地址, 这意味着地址的最低有效位必须总为零.

只要适用, Boost.MultiIndex 有序索引与排名索引就实现这种节点压缩. 与 STL 容器 std::set 的常见实现相比, 节点压缩可使头开销减少 25% (在典型 32 位体系结构上从 16 字节减到 12 字节, 在 64 位系统上从 32 字节减到 24 字节). 经检验, 这一优化对性能的影响在中等规模容器上可忽略不计, 而拥有大量元素 (数十万或更多) 的容器在该优化下运行更快, 极可能源于 L1 与 L2 缓存效应.

节点压缩可以通过全局设置宏 BOOST_MULTI_INDEX_DISABLE_COMPRESSED_ORDERED_INDEX_NODES 来禁用.
