引言

Python 和 Lisp/Scheme、ML 和 Haskell 等其他语言相对 C++ 的一个优势, 是能够拥有可以容纳任意元素类型的异构容器. 标准库中的所有容器都只能容纳特定类型. 一个 vector<int> 只能容纳 int. 一个 list<X> 只能容纳 X 类型的元素, 依此类推.

的确, 你可以用继承让容器容纳通过子类化关联起来的不同类型. 然而, 你必须通过某种指针或智能引用来保存这些对象. 这样做时, 你将不得不依赖虚函数来提供多态行为, 因为一旦把指向派生类的指针存入指向其基类的指针, 实际类型就被擦除了. 所保存的对象必须是相关的: 你无法保存诸如 char、int、class X、float 等不相关类型的对象. 当然, 你可以用 Boost.Any Library 之类的工具来保存任意类型, 但那样你要付出更多的运行期代价, 而且由于实际上擦除了所有类型信息, 你将不得不执行危险的类型转换来取回原始类型.

由 Jaakko Jarvi 编写的 Boost.Tuple 库在 C++ 中提供了异构容器. tuple 是一个可以容纳异构类型的基本数据结构. 这是很好的第一步, 但并不完整. 缺少的是算法. 我们能够向元组存取数据、把元组作为实参和返回类型传递, 这很好. 就其现状而言, Boost.Tuple 设施已经非常有用. 然而, 一旦你更频繁地使用它, 使用模式就会浮现. 最终, 你会把这些模式整理成算法库.

嗯, 这有点让我们想起 STL, 对吧? 没错! 你能想象使用没有算法的 STL 会是什么样子吗? 每个人都不得不重新发明自己的 算法 轮子.

Fusion 是一个与 STL 和 boost MPL 都类似的库和框架. 其结构仿照 MPL, 后者又仿照 STL. 它被命名为 "fusion", 因为这个库让人联想到编译期元编程与运行期编程的"融合". 该库天然带有 MPL 和 STL 的一些有趣的风格与特征. 它生活在编译期元编程与运行期编程之间的晨昏地带. STL 容器处理值, MPL 容器处理类型, 而 Fusion 容器同时处理类型和值.

与 MPL 不同, Fusion 算法是惰性的且不保持序列类型. 这是什么意思? 意思是, 当你通过一个返回序列的 Fusion 算法对序列进行操作时, 返回的序列可能与原序列不是同一类型. 这是有意为之的设计. 运行期效率被赋予很高的优先级. 与 MPL 相同而与 STL 不同的是, fusion 算法在本质上是函数式的, 即算法不修改输入 (无副作用). 然而, 由于返回 vector、list 等完整序列的代价高昂, Fusion 算法改为返回视图. 例如, transform 算法并不实际返回原序列的变换版本, transform 返回一个 transform_view. 该视图持有对原序列的引用以及变换函数. 对 transform_view 的迭代将按需对序列元素应用变换函数. 这种惰性求值方案允许我们任意串联多个算法, 而不会带来高昂的运行期开销.

在算法返回视图的惰性求值方案下, push_back 之类的操作得以完全泛化. 在 Fusion 中, push_back 实际上是一个适用于所有序列的泛型算法. 给定输入序列 s 和值 x, Fusion 的 push_back 算法只是返回一个 joint_view: 一个持有对原序列 s 的引用以及值 x 的视图. 原先针对特定序列、需要在 N 种不同序列上实现 N 次的函数, 现在只需实现一次.

Fusion 提供与 MPL 的全方位兼容. Fusion 序列是完全符合规范的 MPL 序列, MPL 序列也与 Fusion 完全兼容. 如果你只想在类型上工作, 可以在 MPL 中使用 Fusion 序列[1]. 在 MPL 中, Fusion 序列遵循 MPL 的保持序列类型语义 (即算法保持原序列类型, 例如变换 vector 返回 vector). 你也可以把 MPL 序列转换为 Fusion 序列. 例如, 有时先用纯 MPL 序列在 MPL 上工作很方便, 然后在用数据实际实例化真正的运行期对象之前, 作为最后一步把它们转换为 Fusion 序列. 这样你兼得两个世界之长.


[1] 在做纯类型计算时选择 MPL 而非 fusion. 静态类型计算完成后, 你可以为运行期部分实例化一个 fusion 序列 (参见 转换).
