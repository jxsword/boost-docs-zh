引言

源自操作系统或其他低层应用程序接口 (API) 的错误, 通常通过一个表示错误码的整数来报告: 要么由函数直接返回该错误码 (例如 pthread_mutex_init), 要么使用旁路通道, 例如 POSIX 下的 errno 伪变量或 Windows 下的 GetLastError().

然而, 只有在来源已知的情况下, 这些整型错误值才能得到解释. 在 Windows 下, 值 5 表示 ERROR_ACCESS_DENIED (当它由 GetLastError() 返回时), 但表示 EIO (当它从 errno 获取时). 反过来, 同一个错误条件 "拒绝访问" 用值 5 表示 (当它由 GetLastError() 返回时), 而用 13 (EACCES) 表示 (当它从 errno 获取时).

这意味着, 代码若要能够处理来自这两种来源的错误 (例如获取描述该错误的文本消息, 或检查该错误是否意味着 "拒绝访问"), 就需要知道整型错误值来自何处. 为此, 整型错误值需要附带一条标识其来源的信息.

Boost.System 提供了一个可以实现这一点的框架. 错误由类 error_code 表示, 其中既包含错误值, 也包含一个指向其来源 (称为 "类别") 的指针; 来源表示为派生自 error_category 的类.

错误类别提供诸如 message (为特定错误值返回文本消息) 和 equivalent (可用于测试特定错误值是否对应诸如 "拒绝访问" 这样的错误条件) 之类的成员函数. error_code 在其 message 和 operator== 成员函数的实现中使用了这些由类别提供的函数.

Boost.System 包含两个预定义的类别类: 通用类别 (由 generic_category() 返回其引用) 和系统类别 (system_category()). 通用类别表示 POSIX 标准定义的 errno 值中可移植子集的错误值, 而系统类别则依赖于操作系统. 在 POSIX 下, 系统类别表示 OS API 返回的 errno 值 (通用类别中值的超集); 而在 Windows 下, 系统类别表示由 GetLastError() 返回的错误值.

该框架是可扩展的. 用户可以从 error_category 派生一个类, 并实现一个返回其实例引用的函数, 从而定义自己的类别. 这一能力既可用于描述库定义的错误值, 也可用于适配返回整型错误值的既有 C API 库.

对于偏好通过异常报告错误的用户, Boost.System 提供了标准异常类 system_error, 其中存储着一个 error_code.

Boost.System 在 C++11 中被标准化为 <system_error>. 曾有一段时间两者是等价的, 但此后 Boost.System 不断发展, 现在已包含若干超出其标准对应版本的扩展:

  • message 的一个不分配内存的重载;

  • 通过 failed 成员函数支持以非零错误码表示成功;

  • 支持 64 位类别标识符, 以解决有时无法确保类别在程序中只存在一个实例的问题;

  • 支持为错误码附加源位置 (文件/行/函数);

  • 类 result<T>, 可用于从函数返回值或错误码;

  • 其他各种次要改进.

boost::system::error_code 可以转换为 std::error_code, 也可以从后者构造.

用法

以下所有代码片段均假定这些行

#include <boost/system.hpp>
namespace sys = boost::system;

处于生效状态.

在 POSIX 下从 OS API 返回错误

假设我们正在 OS 文件 API 之上实现一个可移植的 file 封装. 其大致轮廓如下:

class file
{
private:

    int fd_;

public:

    // ...

    std::size_t read( void * buffer, std::size_t size, sys::error_code& ec );
    std::size_t write( void const * buffer, std::size_t size, sys::error_code& ec );
};

由于我们实现的是 file 的 POSIX 版本, 其数据成员是一个 POSIX 文件描述符 int fd_;, 不过其他实现会有所不同.

我们的 read 和 write 函数返回传输的字节数, 并通过输出参数 ec (类型为 boost::system::error_code) 报告错误.

file::read 的一种实现可能如下所示:

std::size_t file::read( void * buffer, std::size_t size, sys::error_code& ec )
{
    ssize_t r = ::read( fd_, buffer, size );

    if( r < 0 )
    {
        ec.assign( errno, sys::system_category() );
        return 0;
    }

    ec = {}; // ec.clear(); under C++03
    return r;
}

我们首先调用 POSIX API read; 如果它返回错误, 我们就把 errno 值存入 ec, 采用系统类别, 并返回 0 作为传输的字节数. 否则, 我们清除 ec 以表示成功, 并返回 ::read 的结果.

注释
 在成功返回时清除 ec 是一个重要步骤; 不要省略它.

在 POSIX 下, 系统类别对应于 POSIX 的 errno 值, 这正是我们使用它的原因.

原则上, 由于通用类别在所有平台下也对应于 errno 值, 我们本可以在这里使用它; 然而, 按照 POSIX 下的惯例, 如果 errno 值来自 OS (即 "系统"), 我们就对它使用系统类别. 这是因为系统类别的值可能是通用值 (与平台无关) 的平台特定超集.

file::write 的实现基本相同. 为了完整起见, 我们在这里把它给出:

std::size_t file::write( void const * buffer, std::size_t size, sys::error_code& ec )
{
    ssize_t r = ::write( fd_, buffer, size );

    if( r < 0 )
    {
        ec.assign( errno, sys::system_category() );
        return 0;
    }

    ec = {}; // ec.clear(); under C++03
    return r;
}

在 Windows 下从 OS API 返回错误

在 Windows 下, 我们的 file 对象将存储 HANDLE 而不是 int:

class file
{
private:

    HANDLE fh_;

public:

    // as before
};

而 file::read 的实现则如下所示:

std::size_t file::read( void * buffer, std::size_t size, sys::error_code& ec )
{
    DWORD r = 0;

    if( ::ReadFile( fh_, buffer, size, &r, 0 ) )
    {
        // success
        ec = {}; // ec.clear(); under C++03
    }
    else
    {
        // failure
        ec.assign( ::GetLastError(), sys::system_category() );
    }

    // In both cases, r is bytes transferred
    return r;
}

这里, 系统类别对应于系统头文件 <winerror.h> 中定义、由 GetLastError() 返回的值. 由于我们使用 Win32 API ReadFile 来实现 file::read, 而它通过 GetLastError() 返回错误码, 我们再次把该值作为属于系统类别的值存入 ec.

file::write 的实现同样如此.

std::size_t file::write( void const * buffer, std::size_t size, sys::error_code& ec )
{
    DWORD r = 0;

    if( ::WriteFile( fh_, buffer, size, &r, 0 ) )
    {
        ec = {}; // ec.clear(); under C++03
    }
    else
    {
        ec.assign( ::GetLastError(), sys::system_category() );
    }

    return r;
}

在 POSIX 下返回特定错误

我们的 file::read 实现存在一个问题; 它接受 std::size_t 值作为 size, 但 ::read 在请求的值放不进 ssize_t 时的行为是未指定的. 为了避免依赖未指定的行为, 让我们为这种情况添加一个检查并返回一个错误:

std::size_t file::read( void * buffer, std::size_t size, sys::error_code& ec )
{
    if( size > SSIZE_MAX )
    {
        ec.assign( EINVAL, sys::generic_category() );
        return 0;
    }

    ssize_t r = ::read( fd_, buffer, size );

    if( r < 0 )
    {
        ec.assign( errno, sys::system_category() );
        return 0;
    }

    ec = {}; // ec.clear(); under C++03
    return r;
}

在这里, 由于我们返回的是固定的 errno 值 EINVAL, 它属于通用类别定义的可移植子集, 因此我们把 ec 中的错误值标记为属于通用类别.

也可以使用系统类别, 因为 EINVAL 在 POSIX 下同样是一个系统类别值; 不过, 对于属于可移植 errno 子集的值, 使用通用类别稍微更可取.

我们的 file::write 实现也需要类似的处理. 不过, 在那里我们还要应用另一个改动. 当磁盘上没有剩余空间时, ::write 返回的写入字节数会低于我们通过 size 请求的数量, 但我们的函数不报告任何错误. 我们将让它在这种情况下返回 ENOSPC.

std::size_t file::write( void const * buffer, std::size_t size, sys::error_code& ec )
{
    if( size > SSIZE_MAX )
    {
        ec.assign( EINVAL, sys::generic_category() );
        return 0;
    }

    ssize_t r = ::write( fd_, buffer, size );

    if( r < 0 )
    {
        ec.assign( errno, sys::system_category() );
        return 0;
    }

    if( r < size )
    {
        ec.assign( ENOSPC, sys::system_category() );
    }
    else
    {
        ec = {}; // ec.clear(); under C++03
    }

    return r;
}

我们使用系统类别是为了让 ENOSPC 值看起来像是来自 ::write API, 主要是为了说明这也是一种可行的方法. 使用通用类别的值同样可行.

在 Windows 下返回特定错误

没有太多可说的; Windows 下的情况完全相同. 唯一的区别是, 我们必须使用通用类别来返回 errno 值. 系统类别行不通; 系统类别中的整数值与通用类别中的整数值完全不同.

std::size_t file::read( void * buffer, std::size_t size, sys::error_code& ec )
{
    DWORD r = 0;

    if( size > MAXDWORD )
    {
        ec.assign( EINVAL, sys::generic_category() );
    }
    else if( ::ReadFile( fh_, buffer, size, &r, 0 ) )
    {
        ec = {}; // ec.clear(); under C++03
    }
    else
    {
        ec.assign( ::GetLastError(), sys::system_category() );
    }

    return r;
}

std::size_t file::write( void const * buffer, std::size_t size, sys::error_code& ec )
{
    DWORD r = 0;

    if( size > MAXDWORD )
    {
        ec.assign( EINVAL, sys::generic_category() );
    }
    else if( ::WriteFile( fh_, buffer, size, &r, 0 ) )
    {
        if( r < size )
        {
            ec.assign( ENOSPC, sys::generic_category() );
        }
        else
        {
            ec = {}; // ec.clear(); under C++03
        }
    }
    else
    {
        ec.assign( ::GetLastError(), sys::system_category() );
    }

    return r;
}

为错误码附加源位置

与标准的 <system_error> 不同, Boost.System 允许把源位置 (文件/行/函数) 存储在 error_code 中, 使处理错误的函数能够显示或记录错误发生处的源代码位置. 为了利用这一功能, 我们的 POSIX file::read 函数需要按如下方式增强:

std::size_t file::read( void * buffer, std::size_t size, sys::error_code& ec )
{
    if( size > SSIZE_MAX )
    {
        static constexpr boost::source_location loc = BOOST_CURRENT_LOCATION;
        ec.assign( EINVAL, sys::generic_category(), &loc );
        return 0;
    }

    ssize_t r = ::read( fd_, buffer, size );

    if( r < 0 )
    {
        static constexpr boost::source_location loc = BOOST_CURRENT_LOCATION;
        ec.assign( errno, sys::system_category(), &loc );
        return 0;
    }

    ec = {}; // ec.clear(); under C++03
    return r;
}

也就是说, 在每条 ec.assign 语句之前, 我们需要声明一个保存当前源位置的 static constexpr 变量, 然后把指向它的指针传递给 assign. 由于 error_code 很小, 其中放不下超过一个指针的东西, 所以我们不能按值把 source_location 直接存入其中.

BOOST_CURRENT_LOCATION 是一个展开为当前源位置的宏 (由 __FILE__、__LINE__ 和 BOOST_CURRENT_FUNCTION 组合而成). 它在 Boost.Assert 中定义并配有文档.

在 C++03 下, static constexpr 不可用, 需要改用 static const. 另一个选择是 BOOST_STATIC_CONSTEXPR, 它是 Boost.Config 的一个宏, 会视情况展开为 static constexpr 或 static const.

为了避免每次执行 ec.assign 时都重复这些样板代码, 我们可以定义一个宏:

#define ASSIGN(ec, ...) { \
    BOOST_STATIC_CONSTEXPR boost::source_location loc = BOOST_CURRENT_LOCATION; \
    (ec).assign(__VA_ARGS__, &loc); }

现在我们可以用它来增强 file::write 的 POSIX 实现, 例如:

std::size_t file::write( void const * buffer, std::size_t size, sys::error_code& ec )
{
    if( size > SSIZE_MAX )
    {
        ASSIGN( ec, EINVAL, sys::generic_category() );
        return 0;
    }

    ssize_t r = ::write( fd_, buffer, size );

    if( r < 0 )
    {
        ASSIGN( ec, errno, sys::system_category() );
        return 0;
    }

    if( r < size )
    {
        ASSIGN( ec, ENOSPC, sys::generic_category() );
    }
    else
    {
        ec = {}; // ec.clear(); under C++03
    }

    return r;
}

获取用于日志记录与显示的错误码文本表示

假设我们有一个由某个函数返回给我们的 error_code 实例 ec, 我们有多种手段可以获取其中所表示错误码的文本表示.

ec.to_string() 给出的是把 ec 流插入到 std::ostream 的结果. 例如, 如果 std::cout << ec << std::endl; 输出 system:6, 那么 ec.to_string() 将返回这些内容. (Windows 下, system:6 是 ERROR_INVALID_HANDLE, 来自 <winerror.h>.)

要获得与此错误码对应的人类可读错误消息, 可以使用 ec.message(). 对于 ERROR_INVALID_HANDLE, 它会给出 "The handle is invalid", 可能已本地化.

如果 ec 包含源位置, 我们可以通过 ec.location().to_string() 获取其文本表示. 这会给出类似如下的内容,

C:\Projects\testbed2019\testbed2019.cpp:98 in function 'unsigned __int64 __cdecl file::read(void *,unsigned __int64,class boost::system::error_code &)'

对应于 ec 中存在位置的情况, 而

(unknown source location)

对应于没有位置的情况. (ec.has_location() 为 true 的情况对应于 ec 包含位置.)

最后, ec.what() 会给我们一个包含以上全部内容的字符串, 类似如下

The handle is invalid [system:6 at C:\Projects\testbed2019\testbed2019.cpp:98 in function 'unsigned __int64 __cdecl file::read(void *,unsigned __int64,class boost::system::error_code &)']

大多数并非面向最终用户的日志和诊断输出, 最终大概都会使用 what(). (ec.what() 加上构造时提供的前缀, 也是 boost::system::system_error::what() 会返回的内容.)

组合返回错误码的函数

假设我们需要实现一个文件复制函数, 其接口如下:

std::size_t file_copy( file& src, file& dest, sys::error_code& ec );

file_copy 使用 src.read 从 src 读取字节, 然后把得到的字节写出到 dest, 使用的函数是 dest.write. 这一过程持续进行, 直到其中一个操作报告错误, 或者到达文件末尾为止. 它返回写入的字节数, 并使用 ec 报告错误.

下面是一种可能的实现:

std::size_t file_copy( file& src, file& dest, sys::error_code& ec )
{
    std::size_t r = 0;

    for( ;; )
    {
        unsigned char buffer[ 1024 ];

        std::size_t n = src.read( buffer, sizeof( buffer ), ec );

        // read failed, leave the error in ec and return
        if( ec.failed() ) return r;

        // end of file has been reached, exit loop
        if( n == 0 ) return r;

        r += dest.write( buffer, n, ec );

        // write failed, leave the error in ec and return
        if( ec.failed() ) return r;
    }
}

注意, POSIX 实现与 Windows 实现之间不再有任何区别; 两者的差异都包含在 file::read 和 file::write 中. file_copy 是可移植的, 在任何平台上都能工作.

编写这类更高层函数的一般模式是: 把它们从调用者那里收到的 error_code 类型的输出参数 ec 直接作为输出参数传递给其所依赖的更低层函数. 这样, 当它们通过测试 ec.failed() 在某个中间操作中检测到失败时, 就可以立即返回到调用者, 因为错误码已经位于其应在的位置.

注意, file_copy 甚至不需要在成功时清除 ec, 也就是说不必动用 ec = {};. 由于我们已经测试过 ec.failed(), 因此知道 ec 中包含表示成功的值.

提供双重 (抛出与不抛出) 重载

通过输出参数 error_code& ec 报告错误的函数要求调用者在调用之后检查 ec, 并采取适当的行动 (例如像上面那样立即返回). 忘记检查 ec 会导致逻辑错误.

虽然这是一些人偏好的编码风格, 但另一些人更喜欢异常, 因为异常是无法忘记检查的.

由 Boost.Filesystem 引入 (后来演变为 std::filesystem) 的一种方法是同时提供两种选择: 一种是接受 error_code& ec 的不抛出函数, 如上面的 file_copy; 另一种是不接受 error_code 输出参数、在失败时抛出异常的抛出函数.

第二个抛出函数通常按如下方式实现:

std::size_t file_copy( file& src, file& dest )
{
    sys::error_code ec;
    std::size_t r = file_copy( src, dest, ec );

    if( ec.failed() ) throw sys::system_error( ec, __func__ );

    return r;
}

也就是说, 我们只是简单地调用 file_copy 的不抛出重载, 如果它在 ec 中报告失败, 就抛出一个 system_error 异常.

我们使用自己的函数名 __func__ ("file_copy") 作为前缀, 尽管这纯属品味问题.

注意, 在这种风格下, 接受 error_code& ec 的重载通常会用 noexcept 修饰, 以明确表明它们不会抛出异常 (不过为了保持代码对 C++03 友好, 我们在前面的示例中没有这样做).

以 result<T> 替代双重 API

与其为每个操作提供两个函数, 另一种做法是让函数返回 sys::result<T> 而不是 T. result<T> 是一个要么持有 T、要么持有 error_code 的类, 类似于 variant<T, error_code>.

偏好检查错误而不依赖异常的调用方, 可以测试一个 result<T> r 是否包含值 (通过 if( r ), 或其更冗长的等价形式 if( r.has_value() )), 然后通过 *r 或 r.value() 获取该值. 如果 r 不包含值, 则它所持有的 error_code 可以通过 r.error() 获取.

偏好异常的人则直接调用 r.value(), 无需检查. 在没有值的情况下, 这会自动抛出一个 system_error, 对应的 error_code 正是 r 中所持有的那个.

假设我们的底层 file API 保持不变, 这一变体的 file_copy 将如下所示:

sys::result<std::size_t> file_copy( file& src, file& dest )
{
    std::size_t r = 0;
    sys::error_code ec;

    for( ;; )
    {
        unsigned char buffer[ 1024 ];

        std::size_t n = src.read( buffer, sizeof( buffer ), ec );

        if( ec.failed() ) return ec;
        if( n == 0 ) return r;

        r += dest.write( buffer, n, ec );

        if( ec.failed() ) return ec;
    }
}

这里唯一的区别是, 出错时我们返回 ec, 而不是 r.

但请注意, 我们现在无法同时返回错误码和传输的字节数; 也就是说, 我们无法再表示部分成功. 在较高层次上这通常不成问题, 但像 file::read 和 file::write 这样的低层原语, 用旧风格编写可能更好.

尽管如此, 为了演示返回 result 的 API 如何组合, 我们将展示 file_copy 在 file::read 和 file::write 返回 result<size_t> 的情况下会是什么样子:

class file
{
public:

    // ...

    sys::result<std::size_t> read( void * buffer, std::size_t size );
    sys::result<std::size_t> write( void const * buffer, std::size_t size );
};

sys::result<std::size_t> file_copy( file& src, file& dest )
{
    std::size_t m = 0;

    for( ;; )
    {
        unsigned char buffer[ 1024 ];

        auto r = src.read( buffer, sizeof( buffer ) );
        if( !r ) return r;

        std::size_t n = *r;
        if( n == 0 ) return m;

        auto r2 = dest.write( buffer, n );
        if( !r2 ) return r2;

        std::size_t n2 = *r2;
        m += n2;
    }
}

测试特定错误条件

假设我们调用了一个使用 error_code 报告失败的函数, 向它传入了一个 error_code 变量 ec, 现在出于某种原因想要检查该函数是否因错误码 EINVAL ("无效参数") 而失败.

由于 error_code 可以进行相等比较, 我们的第一直觉可能是 if( ec == error_code( EINVAL, generic_category() ).

这是错误的, 我们绝不应该这样做.

首先, 在 POSIX 下, 该函数可能返回了来自系统类别的 EINVAL (因为该错误可能是由某个 OS API 返回的, 而不是由函数本身返回, 正如我们 read 和 write 实现中的情况那样).

由于 error_code 的比较是精确的, 来自通用类别的 EINVAL 与来自系统类别的 EINVAL 比较起来并不相等.

(在你开始考虑直接把 ec.value() 与 EINVAL 进行比较之前, 请继续往下读.)

其次, 在 Windows 下, 该函数可能返回了 error_code( ERROR_INVALID_PARAMETER, system_category() ). 正如我们已经提到的, Windows 下系统类别中的整型错误值与整型 errno 值完全无关.

正确的做法是, 不把 ec 与具体的错误码比较, 而是与 error_condition( EINVAL, generic_category() ) 比较. 错误条件是一种与平台无关的方式, 用于表示具体错误码的含义. 在我们的例子中, 在 POSIX 和 Windows 下, 所有表示 EINVAL 的错误码都将与 error_condition( EINVAL, generic_category() ) 比较相等.

简而言之, 你永远不应该把错误码与错误码比较, 而应该把它们与错误条件比较. 这正是 error_condition 类的用途所在; 这个类经常遭到误解.

由于

if( ec == sys::error_condition( EINVAL, sys::generic_category() ) )
{
    // handle EINVAL
}

略显冗长, Boost.System 针对 errno 的值提供了枚举量, 错误码可以直接与它们比较.

这些枚举量定义于 <boost/system/errc.hpp> 中, 它们使上面的测试可以写成

if( ec == sys::errc::invalid_argument )
{
    // handle EINVAL
}

作为最佳实践, 测试特定的错误条件时通常应当使用这种写法.

适配既有整型错误值

带有 C (或 extern "C") API 的库通常通过返回库专属的整型错误码来报告失败 (其中 0 通常保留用于表示 "无错误"). 在编写可移植的 C++ 封装时, 我们需要决定如何暴露这些错误码, 而使用 error_code 是一种好办法.

由于这些整型错误码是库专属的, 一般既不匹配 errno 值, 也不匹配系统类别值, 因此我们需要定义一个库专属的错误类别.

适配 SQLite 错误

我们将以 SQLite 为例. 自定义错误类别的大致轮廓如下:

class sqlite3_category_impl: public sys::error_category
{
    // TODO add whatever's needed here
};

sys::error_category const& sqlite3_category()
{
    static const sqlite3_category_impl instance;
    return instance;
}

之后就可以像预定义的通用类别和系统类别一样使用它:

int r = some_sqlite3_function( ... );
ec.assign( r, sqlite3_category() );

如果我们按原样编译上面的类别定义, 编译器会指出我们没有实现两个纯虚成员函数 name 和 message, 因此至少需要添加它们. 此外, 我们还会实现 message 的不分配内存的重载. 它不是纯虚的, 但其默认实现会调用返回 std::string 的那个重载, 而这几乎从来都不是我们想要的. (提供这个默认实现只是为了向后兼容, 以免破坏在该重载加入之前编写的既有用户自定义类别.)

所以, 我们至少需要实现的是:

class sqlite3_category_impl: public sys::error_category
{
public:

    const char * name() const noexcept;
    std::string message( int ev ) const;
    char const * message( int ev, char * buffer, std::size_t len ) const noexcept;
};

name 很简单, 它只返回类别名称:

const char * sqlite3_category_impl::name() const noexcept
{
    return "sqlite3";
}

message 用于在给定整型错误码的情况下取得错误消息. SQLite 为此提供了函数 sqlite3_errstr, 所以我们不需要做任何工作:

std::string sqlite3_category_impl::message( int ev ) const
{
    return sqlite3_errstr( ev );
}

char const * sqlite3_category_impl::message( int ev, char * buffer, std::size_t len ) const noexcept
{
    std::snprintf( buffer, len, "%s", sqlite3_errstr( ev ) );
    return buffer;
}

这样便完成了. sqlite3_category() 现在可以像预定义类别一样使用, 并且我们可以把 SQLite 错误码 int r 放入 Boost.System 的 error_code ec 中, 所用的手段是 ec.assign( r, sqlite3_category() ).

适配 ZLib 错误

另一个被广泛使用的 C 库是 ZLib, zlib.h 中定义其错误码的部分如下所示:

#define Z_OK            0
#define Z_STREAM_END    1
#define Z_NEED_DICT     2
#define Z_ERRNO        (-1)
#define Z_STREAM_ERROR (-2)
#define Z_DATA_ERROR   (-3)
#define Z_MEM_ERROR    (-4)
#define Z_BUF_ERROR    (-5)
#define Z_VERSION_ERROR (-6)
/* Return codes for the compression/decompression functions. Negative values
 * are errors, positive values are used for special but normal events.
 */

与前面的 SQLite 情形相比, 有三个相关差异:

  • SQLite 的所有非零值都是错误 (这是典型情况), 而在这里, 负值是错误, 正值则是 "特殊但正常", 也就是说它们表示成功, 而不是失败;

  • ZLib 不提供针对特定错误码返回对应错误消息的函数;

  • 当返回 Z_ERRNO 时, 错误码应当从 errno 获取.

我们的类别实现将如下所示:

class zlib_category_impl: public sys::error_category
{
public:

    const char * name() const noexcept;

    std::string message( int ev ) const;
    char const * message( int ev, char * buffer, std::size_t len ) const noexcept;

    bool failed( int ev ) const noexcept;
};

sys::error_category const& zlib_category()
{
    static const zlib_category_impl instance;
    return instance;
}

照例, name 的实现很简单:

const char * zlib_category_impl::name() const noexcept
{
    return "zlib";
}

这一次实现 message 需要多花些功夫, 因为没有现成的函数可以依靠:

char const * zlib_category_impl::message( int ev, char * buffer, std::size_t len ) const noexcept
{
    switch( ev )
    {
    case Z_OK:            return "No error";
    case Z_STREAM_END:    return "End of stream";
    case Z_NEED_DICT:     return "A dictionary is needed";
    case Z_ERRNO:         return "OS API error";
    case Z_STREAM_ERROR:  return "Inconsistent stream state or invalid argument";
    case Z_DATA_ERROR:    return "Data error";
    case Z_MEM_ERROR:     return "Out of memory";
    case Z_BUF_ERROR:     return "Insufficient buffer space";
    case Z_VERSION_ERROR: return "Library version mismatch";
    }

    std::snprintf( buffer, len, "Unknown zlib error %d", ev );
    return buffer;
}

这是不抛出的 message 重载的典型实现. 注意, 允许 message 返回与 buffer 不同的东西, 这意味着我们可以直接返回字符字面量, 而不必先把它们复制到所提供的缓冲区中. 这样, 即使缓冲区太小, 我们的函数也能返回正确的消息文本.

std::string 版本的 message 重载现在就非常简单了:

std::string zlib_category_impl::message( int ev ) const
{
    char buffer[ 64 ];
    return this->message( ev, buffer, sizeof( buffer ) );
}

最后, 我们需要实现 failed, 以覆盖其默认行为——对所有非零值返回 true:

bool zlib_category_impl::failed( int ev ) const noexcept
{
    return ev < 0;
}

至此, zlib_category() 的实现已经完成, 上面列表中的前两点也得到了处理, 但第三点还没有解决; 具体而言, 我们需要从 errno 中检索错误 (在 Z_ERRNO 的情况下).

为此, 我们将定义一个辅助函数, 用于把 ZLib 错误码赋给 error_code:

void assign_zlib_error( sys::error_code & ec, int r )
{
    if( r != Z_ERRNO )
    {
        ec.assign( r, zlib_category() );
    }
    else
    {
        ec.assign( errno, sys::generic_category() );
    }
}

这样, 代码将不再直接使用 ec.assign( r, zlib_category() ), 而是执行

int r = some_zlib_function( ... );
assign_zlib_error( ec, r );

我们可以到此为止, 因为这已经涵盖了我们打算做的一切, 但我们还可以更进一步, 为我们的错误码启用源位置. 为此, 我们需要修改 assign_zlib_error, 让它接受一个 source_location:

void assign_zlib_error( sys::error_code & ec, int r, boost::source_location const* loc )
{
    if( r != Z_ERRNO )
    {
        ec.assign( r, zlib_category(), loc );
    }
    else
    {
        ec.assign( errno, sys::generic_category(), loc );
    }
}

定义一个辅助宏, 以避免每次都编写定义 static constexpr 源位置对象的样板代码:

#define ASSIGN_ZLIB_ERROR(ec, r) { \
    BOOST_STATIC_CONSTEXPR boost::source_location loc = BOOST_CURRENT_LOCATION; \
    assign_zlib_error( ec, r, &loc ); }

然后使用该宏而不是函数:

int r = some_zlib_function( ... );
ASSIGN_ZLIB_ERROR( ec, r );

支持与错误条件的比较

我们注意到, 一些 ZLib 错误码对应于可移植的 errno 条件. 例如, Z_STREAM_ERROR 会在 POSIX 函数本会返回 EINVAL 的情况下被返回; Z_MEM_ERROR 即 ENOMEM; 而 Z_BUF_ERROR (输出缓冲区空间不足, 无法存放结果) 大致对应于 ERANGE (结果超出范围).

为了表达这种关系, 我们需要在类别中实现 default_error_condition 或 equivalent. 由于我们的映射是简单的一一对应, 前者就足够了:

class zlib_category_impl: public sys::error_category
{
public:

    const char * name() const noexcept;

    std::string message( int ev ) const;
    char const * message( int ev, char * buffer, std::size_t len ) const noexcept;

    bool failed( int ev ) const noexcept;

    sys::error_condition default_error_condition( int ev ) const noexcept;
};

实现非常直观:

sys::error_condition zlib_category_impl::default_error_condition( int ev ) const noexcept
{
    switch( ev )
    {
    case Z_OK:            return sys::error_condition();
    case Z_STREAM_ERROR:  return sys::errc::invalid_argument;
    case Z_MEM_ERROR:     return sys::errc::not_enough_memory;
    case Z_BUF_ERROR:     return sys::errc::result_out_of_range;
    }

    return sys::error_condition( ev, *this );
}

加入这一实现之后, 我们就能够把 ZLib 的 error_code ec 与 errc 枚举量进行比较:

if( ec == sys::errc::not_enough_memory )
{
    // Z_MEM_ERROR, or ENOMEM
}

定义库特有的错误码

假设我们正在编写一个用于读取某种假想图像格式的库 libmyimg, 并为此定义了如下 API 函数:

namespace libmyimg
{

struct image;

void load_image( file& f, image& im, sys::error_code& ec );

} // namespace libmyimg

(使用前面示例中我们的可移植 file 类.)

我们假想的图像格式很简单, 由一个固定头部加图像数据组成, 因此 load_image 的一种实现可能具有如下结构:

namespace libmyimg
{

struct image_header
{
    uint32_t signature;
    uint32_t width;
    uint32_t height;
    uint32_t bits_per_pixel;
    uint32_t channels;
};

void load_image_header( file& f, image_header& im, sys::error_code& ec );

struct image;

void load_image( file& f, image& im, sys::error_code& ec )
{
    image_header ih = {};
    load_image_header( f, ih, ec );

    if( ec.failed() ) return;

    if( ih.signature != 0xFF0AD71A )
    {
        // return an "invalid signature" error
    }

    if( ih.width == 0 )
    {
        // return an "invalid width" error
    }

    if( ih.height == 0 )
    {
        // return an "invalid height" error
    }

    if( ih.bits_per_pixel != 8 )
    {
        // return an "unsupported bit depth" error
    }

    if( ih.channels != 1 && ih.channels != 3 && ih.channels != 4 )
    {
        // return an "unsupported channel count" error
    }

    // initialize `im` and read image data

    // ...
}

} // namespace libmyimg

可以看到, 我们需要定义五个自己的错误码. (我们的函数也可能在 ec 中返回其他类型的失败——那些失败将来自 file::read, load_image_header 正是用它来读取头部的.)

为了定义这些错误, 我们将使用限定作用域的枚举类型. (本示例将利用 C++11 特性.)

namespace libmyimg
{

enum class error
{
    success = 0,

    invalid_signature,
    invalid_width,
    invalid_height,
    unsupported_bit_depth,
    unsupported_channel_count
};

} // namespace libmyimg

Boost.System 支持告知它某个枚举类型表示错误码, 这会启用该枚举类型与 error_code 之间的隐式转换. 做法是特化 is_error_code_enum 这一类型特征; 与库的其余部分一样, 它位于 namespace boost::system 中:

namespace boost
{
namespace system
{

template<> struct is_error_code_enum< ::libmyimg::error >: std::true_type
{
};

} // namespace system
} // namespace boost

完成这一步之后, 我们就可以把 libmyimg::error 的值赋给 sys::error_code, 从而让 load_image 的实现可以写成下面这样:

void load_image( file& f, image& im, sys::error_code& ec )
{
    image_header ih = {};
    load_image_header( f, ih, ec );

    if( ec.failed() ) return;

    if( ih.signature != 0xFF0AD71A )
    {
        ec = error::invalid_signature;
        return;
    }

    if( ih.width == 0 )
    {
        ec = error::invalid_width;
        return;
    }

    if( ih.height == 0 )
    {
        ec = error::invalid_height;
        return;
    }

    if( ih.bits_per_pixel != 8 )
    {
        ec = error::unsupported_bit_depth;
        return;
    }

    if( ih.channels != 1 && ih.channels != 3 && ih.channels != 4 )
    {
        ec = error::unsupported_channel_count;
        return;
    }

    // initialize `image` and read image data

    // ...
}

然而这还不够; 我们还需要为我们的枚举量定义错误类别, 并将它们与该类别关联.

第一步与我们之前的两个示例非常相似:

namespace libmyimg
{

class myimg_category_impl: public sys::error_category
{
public:

    const char * name() const noexcept;

    std::string message( int ev ) const;
    char const * message( int ev, char * buffer, std::size_t len ) const noexcept;
};

const char * myimg_category_impl::name() const noexcept
{
    return "libmyimg";
}

std::string myimg_category_impl::message( int ev ) const
{
    char buffer[ 64 ];
    return this->message( ev, buffer, sizeof( buffer ) );
}

char const * myimg_category_impl::message( int ev, char * buffer, std::size_t len ) const noexcept
{
    switch( static_cast<error>( ev ) )
    {
    case error::success:                   return "No error";
    case error::invalid_signature:         return "Invalid image signature";
    case error::invalid_width:             return "Invalid image width";
    case error::invalid_height:            return "Invalid image height";
    case error::unsupported_bit_depth:     return "Unsupported bit depth";
    case error::unsupported_channel_count: return "Unsupported number of channels";
    }

    std::snprintf( buffer, len, "Unknown libmyimg error %d", ev );
    return buffer;
}

sys::error_category const& myimg_category()
{
    static const myimg_category_impl instance;
    return instance;
}

} // namespace libmyimg

第二步需要实现一个函数 make_error_code, 它位于我们枚举类型 error 所在的命名空间中, 接受 error 并返回 boost::system::error_code:

namespace libmyimg
{

sys::error_code make_error_code( error e )
{
    return sys::error_code( static_cast<int>( e ), myimg_category() );
}

} // namespace libmyimg

现在 load_image 能够通过编译了, 我们只需在其实现的其余部分填入使用 file::read 读取图像数据的代码.

我们还可以做一点锦上添花的事. 如我们所知, Boost.System 曾被提案并已被 C++11 标准接受, 现在 <system_error> 中已有它的标准实现. 我们还可以让我们的错误枚举类型与 std::error_code 兼容, 办法是特化标准类型特征 std::is_error_code_enum:

namespace std
{

template<> struct is_error_code_enum< ::libmyimg::error >: std::true_type
{
};

} // namespace std

这使我们的枚举量可以转换为 std::error_code.

(之所以可行, 是因为 boost::system::error_code 可以转换为 std::error_code, 因此我们 make_error_code 重载的返回值可以用来初始化 std::error_code.)

定义库特有的错误条件

到目前为止, 我们的 libmyimg::error 错误码全都表示同一个错误条件——无效或不受支持的图像格式. 让用户无需逐一列举全部五个具体错误码就能测试这一条件, 可能是有意义的. 为此, 我们可以定义一个错误条件枚举类型:

namespace libmyimg
{

enum class condition
{
    invalid_format = 1
};

} // namespace libmyimg

我们可以通过特化 is_error_condition_enum 把它标记为表示一个错误条件:

namespace boost
{
namespace system
{

template<> struct is_error_condition_enum< ::libmyimg::condition >: std::true_type
{
};

} // namespace system
} // namespace boost

namespace std
{

template<> struct is_error_condition_enum< ::libmyimg::condition >: std::true_type
{
};

} // namespace std

与需要 make_error_code 重载的错误码枚举类型类似, 这个类型也需要一个 make_error_condition 重载以及一个类别.

原则上可以复用我们已为错误码定义的那个类别, 办法是让条件值从例如 10000 而不是 1 开始. 这能省一些输入, 但更好的做法是为错误条件使用单独的类别. 所以我们就这么做:

namespace libmyimg
{

class myimg_condition_category_impl: public sys::error_category
{
public:

    const char * name() const noexcept;

    std::string message( int ev ) const;
    char const * message( int ev, char * buffer, std::size_t len ) const noexcept;
};

const char * myimg_condition_category_impl::name() const noexcept
{
    return "libmyimg_condition";
}

std::string myimg_condition_category_impl::message( int ev ) const
{
    char buffer[ 64 ];
    return this->message( ev, buffer, sizeof( buffer ) );
}

char const * myimg_condition_category_impl::message( int ev, char * buffer, std::size_t len ) const noexcept
{
    switch( static_cast<condition>( ev ) )
    {
    case condition::invalid_format: return "Invalid or unsupported image format";
    }

    std::snprintf( buffer, len, "Unknown libmyimg condition %d", ev );
    return buffer;
}

我们有了错误条件, 但它还没有任何作用. 要让 libmyimg::condition::invalid_format 能够与我们的错误码比较相等, 需要在错误码类别中实现 default_error_condition:

namespace libmyimg
{

class myimg_category_impl: public sys::error_category
{
public:

    const char * name() const noexcept;

    std::string message( int ev ) const;
    char const * message( int ev, char * buffer, std::size_t len ) const noexcept;

    sys::error_condition default_error_condition( int ev ) const noexcept;
};

sys::error_condition myimg_category_impl::default_error_condition( int ev ) const noexcept
{
    switch( static_cast<error>( ev ) )
    {
    case error::success:

        return {};

    case error::invalid_signature:
    case error::invalid_width:
    case error::invalid_height:
    case error::unsupported_bit_depth:
    case error::unsupported_channel_count:

        return condition::invalid_format;
    }

    return sys::error_condition( ev, *this );

Boost 1.68 中的变更

在 C++14 编译器上, 许多 Boost.System 函数和成员函数现在是 constexpr 的, 而 error_code 和 error_condition 是字面类.

除了能够在常量表达式 (以及 constexpr 函数) 中使用之外, 这还显著提高了生成代码的质量.

然而, 由于这一变更, 现在在 C++14 或 C++17 代码中使用 Boost.System 要求该库也以 C++14 或更高标准构建. 在 GCC 6 及更新版本上这是默认设置, 但在 GCC 5 或 Clang 上不是. 可以通过以 cxxstd=14 选项运行 b2 来为 C++14 构建 Boost.

(以前的版本允许以任何 C++ 标准构建的代码链接以任何 C++ 标准构建的 Boost.System. 在 1.68 中, 使用任何 C++ 标准的代码都可以链接以 C++14 或更高标准构建的 Boost.System; 但如果 Boost.System 是以 C++11 或更低标准构建的, 则只有同样以 C++11 及更低标准构建的代码才能成功链接它.)

Boost 1.65 中的变更

在 C++11 编译器上, Boost.System 现在提供从 boost::system::error_category、error_code 和 error_condition 到 <system_error> 中对应标准版本的隐式转换.

这使得库即使在直接使用 Boost.System 或通过诸如 Boost.ASIO 的依赖使用它时, 也可以对外暴露 C++11 接口并通过 std::error_code 报告错误.

设计原理

error_code 和 error_condition 被设计为值类型, 因此它们可以在不发生切片的情况下复制, 也不需要堆分配, 但仍然具有基于错误类别的多态行为. 这是通过让抽象基类 error_category 提供多态行为, 而 error_code 和 error_condition 持有一个指向派生自 error_category 的类型对象的指针来实现的.

许多具体的设计决策都源于以下要求: 用户能够添加额外的错误类别, 并且编写可移植代码的难度不得高于编写系统专属代码.

operator<< 针对 error_code 的重载消除了向 bool 的误导性转换, 这种转换出现在诸如 cout << ec 的代码中, 其中 ec 的类型为 error_code. 这个重载本身也很有用.

当定义了 BOOST_SYSTEM_ENABLE_DEPRECATED 时, 库会为兼容性提供已弃用的特性. 这些特性最终注定会消失.

throw_exception_from_error

函数 throw_exception_from_error 会在 result 持有错误时被 result<T, E>::value() 调用. 其目的是抛出一个表示 result 所持有错误的异常.

对于 E 为 error_code 这一常见且默认的情况, 已经提供了实现. 它会抛出 system_error(e).

如果 result<T, E> 与其他错误类型一起使用, 用户应提供 throw_exception_from_error 的适当重载, 位置在 E 的命名空间中.

  boost::source_location const & loc );

  boost::source_location const & loc );

    boost::throw_with_location( std::system_error( e ), loc ).

  boost::source_location const & loc );

    仅当 f() 可转换为 T, 或者当 T 为引用时可转换为 std::decay_t<T> 时才会启用.

    示例:
    result<int> get_server_port(); // can fail
int get_default_port();

int get_port()
{
    return get_server_port() | get_default_port;
}

    注意, 右侧是 get_default_port 而不是 get_default_port(). 这一点很重要; 采用这种写法时, 函数 get_default_port 只会在 get_server_port_impl() 失败时才被调用. 如果写成

        return get_server_port() | get_default_port();

    该函数就会被无条件调用.

    另一种等价的方式是使用 lambda

        return get_server_port() | []{ return get_default_port(); };

    在这里这样做并非必要, 但对于更复杂的表达式则需要这样做.

unwrap_and_invoke

template<class F, class... A>
auto unwrap_and_invoke( F&& f, A&&... a ) -> result</*...*/>;

  • 规定:

    a…​ 中的实参至少有一个必须是 result 的实例.

    a…​ 中所有为 result 实例的实参必须具有相同的错误类型.

    效果:

    如果 ai (a…​ 的实参之一) 是一个 result 实例, 且其 has_error() 为 true, 则返回 ai.error().

    否则, 返回 f(b…​), 其中 bi 为 *ai (当 ai 是 result 的实例时), 否则为 ai.

    备注:

    返回类型为 result<R, E>, 其中 R 是应用 f 所得到的类型, E 是 a…​ 中为 result 实例的那些实参的共同错误类型.

历史

N1975 (Filesystem Library Proposal for TR2) 在柏林会议上被接受纳入库技术报告 2 (TR2), 其中包含用于补充标准库诊断条款的额外组件. 此后, 这些错误报告组件经受了更广泛的公众审视, 设计上也得到了增强. 增强后的版本已被 N2054 (Networking Library Proposal for TR2) 使用, 这表明这些错误报告组件在最初的文件系统库之外也很有用.

最初的提案把错误类别视为 errno (即 POSIX 风格) 与操作系统原生错误码之间的二元选择. 现在, 所提议的组件允许按实现者或用户的需要添加任意数量的额外错误类别. 例如, 某些网络库实现就需要支持额外的错误类别, 因为它们构建于 POSIX getaddrinfo API 之上, 而该 API 使用的错误码并不基于 errno.
