eUML 前端 (已弃用)

重要说明: eUML 已不再继续开发, 将逐渐被采用 PlantUML 语法的 Puml 取代.

重要说明: eUML 需要支持 Boost.Typeof 的编译器. 完整的 eUML 具有实验性地位 (但如果仅转移表用 eUML 编写则不然), 因为某些编译器在状态机变得过大时 (通常是在你编写庞大的动作时) 会开始崩溃.

前面的几种前端写起来简单, 但仍然带来不少噪音, 主要是 MPL 类型. 如果能像 UML 设计师喜欢在状态机图上所做的那样, 直接在转移表内部书写看似 C 的代码 (采用 C 动作语言), 那就好了. 如果还能是函数式编程, 那就更好了. 这正是 eUML 的用途.

eUML 是一个基于 Boost.Proto 与 Boost.Typeof 的编译期领域特定嵌入式语言. 它提供的文法允许直接在转移表中定义动作/守卫, 或在状态定义中定义 entry/exit. 动作、守卫、标志、属性、延迟事件、初始状态都有对应的文法.

它还依赖 Boost.Typeof 作为对新的 decltype 这一 C0x 特性的封装, 为所有文法提供编译期求值. 遗憾的是, 并非所有底层 Boost 库都启用了 Typeof, 所以目前你需要一个支持 Typeof 的编译器 (如 VC9-10, g >= 4.3).

后续各节将给出示例. 你需要包含 eUML 的基本特性:

#include <msm/front/euml/euml.hpp>

要添加 STL 支持 (代价可能是编译时间变长), 请包含:

#include <msm/front/euml/stl.hpp>

eUML 定义在命名空间 msm::front::euml 中.

转移表

用 eUML 定义一条转移的方式如下:

source + event [guard] / action == target

或写作

target == source + event [guard] / action

第一种看起来像图中画出的一条转移, 第二种则对 C++ 开发者来说显得更自然.

用 functor front-end 编写的简单转移表现在可以写成:

BOOST_MSM_EUML_TRANSITION_TABLE((
Stopped + play [some_guard] / (some_action , start_playback)  == Playing ,
Stopped + open_close/ open_drawer                             == Open    ,
Stopped + stop                                                == Stopped ,
Open    + open_close / close_drawer                           == Empty   ,
Empty   + open_close / open_drawer                            == Open    ,
Empty   + cd_detected [good_disk_format] / store_cd_info      == Stopped
),transition_table)

或者, 使用另一种记法, 它可以是:

BOOST_MSM_EUML_TRANSITION_TABLE((
Playing  == Stopped + play [some_guard] / (some_action , start_playback) ,
Open     == Stopped + open_close/ open_drawer                            ,
Stopped  == Stopped + stop                                               ,
Empty    == Open    + open_close / close_drawer                          ,
Open     == Empty   + open_close / open_drawer                           ,
Stopped  == Empty   + cd_detected [good_disk_format] / store_cd_info
),transition_table)

转移表现在看起来就像一份 (可读的) 规则列表, 几乎没有噪音.

UML 在 [ ]'' and actions after a /'' 之间定义守卫, 因此所选语法对 UML 设计师而言已经更具可读性. UML 还允许设计师定义顺序执行的多个动作 (即我们之前的 ActionSequence_), 以逗号分隔. 第一条转移正是这样做的: 两个动作以逗号分隔, 并用括号括起以满足 C++ 运算符优先级.

如果这在你看来会带来运行期性能开销, 不必担心, eUML 基于 typeof (或 decltype), 它只对 BOOST_MSM_EUML_TRANSITION_TABLE 的参数求值, 不会产生任何运行期开销. 实际上, eUML 只是位于“标准”MSM 元编程之上的一层元编程, 这第一层会生成前面介绍过的 functor front-end.

UML 还允许设计师定义更复杂的守卫, 例如 [good_disk_format && (some_condition || some_other_condition)]. 用之前定义的仿函数也能做到这一点, 但要使用复杂的模板语法. 而这种语法现在可以完全照原样书写, 也就是说完全不带语法噪音.

一个简单示例: 仅重写我们的转移表

作为 eUML 的入门, 我们将用 eUML 重写教程中的转移表. 依据编译器的不同, 这需要两三处修改:

  • 事件必须继承自 msm::front::euml::euml_event< event_name >

  • 状态必须继承自 msm::front::euml::euml_state< state_name >

  • 使用 VC 时, 状态必须在前端之前声明

现在可以像刚才所示那样书写转移表, 使用 BOOST_MSM_EUML_DECLARE_TRANSITION_TABLE 而非 BOOST_MSM_EUML_TRANSITION_TABLE. 实现非常直白. 唯一必须补充的是: 需要为每个状态声明一个变量, 或在转移表中添加括号 (即默认构造函数调用).

`composite 的实现同样自然:

// front-end like always
struct sub_front_end : public boost::msm::front::state_machine_def<sub_front_end>
{
...
};
// back-end like always
typedef boost::msm::back11::state_machine<sub_front_end> sub_back_end;

sub_back_end const sub; // sub can be used in a transition table.

遗憾的是, VC 存在一个不时出现并导致栈溢出的缺陷. 如果你收到程序在所有路径上递归的警告, 请退回到标准 eUML 或换用其他前端, 因为 Microsoft 似乎不打算修复它.

现在我们有了一个新的、更具可读性的转移表, 而对示例的改动很少. eUML 能做的远不止这些, 请继续跟随本指南.

定义带入口/出口动作的事件、动作与状态

事件

事件必须启用 Proto. 为此, 它们必须继承自一个 Proto 终端 (euml_event<event-name>). eUML 还提供了一个宏来简化这一操作:

BOOST_MSM_EUML_EVENT(play)

这声明了一个事件类型以及该类型的一个名为 play 的实例, 现在即可在状态或转移行为中使用它.

还有第二个宏 BOOST_MSM_EUML_EVENT_WITH_ATTRIBUTES, 它以事件将包含的属性作为第二个参数, 并使用 attribute syntax.

注释: 既然现在事件定义为实例而不仅仅是类型, 我们还能通过现场创建一个事件来处理它吗, 比如: fsm.process_event(play()); 还是必须写成: fsm.process_event(play);

答案是两者皆可. 第二种更简单, 但与其他前端不同, 它使用的是一个已定义的 operator(), 会现场创建事件.

动作

动作 (返回 void) 与守卫 (返回 bool) 的定义方式与之前的仿函数一样, 区别在于它们也必须启用 Proto. 这可以通过继承 euml_action< functor-name > 来实现. eUML 还提供了一个宏:

BOOST_MSM_EUML_ACTION(some_condition)
{
    template <class Fsm,class Evt,class SourceState,class TargetState>
    bool operator()(Evt const& ,Fsm& ,SourceState&,TargetState& )
    { return true; }
};

与事件一样, 该宏声明一个仿函数类型及其一个实例, 供转移或状态行为使用.

可以使用与转移表相同的动作文法定义状态的入口与出口行为. 因此 (action1,action2) 是一个合法的入口或出口行为, 会依次执行这两个动作.

状态仿函数的签名略有不同, 因为这里没有源状态和目标状态, 只有当前状态 (入口/出口动作与转移无关), 例如:

BOOST_MSM_EUML_ACTION(Empty_Entry)
{
    template <class Evt,class Fsm,class State>
    void operator()(Evt const& ,Fsm& ,State& ) { ... }
    };

也可以复用 Functor 前端中的仿函数. 不过语法上稍欠舒适, 因为我们需要为 typeof 假装现场创建一个实例. 例如:

struct start_playback
{
        template <class Fsm,class Evt,class SourceState,class TargetState>
        void operator()(Evt const& ,Fsm&,SourceState& ,TargetState& )
        {
         ...
        }
};
BOOST_MSM_EUML_TRANSITION_TABLE((
Playing   == Stopped  + play        / start_playback() ,
...
),transition_table)

状态

状态也有一个对应的宏. 该宏有 2 个参数: 第一个是定义状态的表达式, 第二个是状态 (实例) 名称:

BOOST_MSM_EUML_STATE((),Paused)

这定义了一个没有入口或出口动作的简单状态. 你可以在表达式参数中用动作文法提供状态行为 (入口与出口), 就像在转移表中那样:

BOOST_MSM_EUML_STATE(((Empty_Entry,Dummy_Entry)/*2 entryactions*/,
                       Empty_Exit/*1 exit action*/ ),
                     Empty)

这表示 Empty 被定义为一个状态, 其入口动作由两个子动作 Empty_Entry 和 Dummy_Entry (用括号括起) 构成, 并有一个出口动作 Empty_Exit.

表达式语法有几种可能的形式:

  • (): 无入口或出口动作的状态.

  • (Expr1): 有入口动作但无出口动作的状态.

  • (Expr1,Expr2): 有入口和出口动作的状态.

  • (Expr1,Expr2,Attributes): 有入口和出口动作的状态, 并定义一些属性 (后文详述).

  • (Expr1,Expr2,Attributes,Configure): 有入口和出口动作的状态, 并定义一些属性 (后文详述) 以及标志 (标准 MSM 标志) 或延迟事件 (标准 MSM 延迟事件).

  • (Expr1,Expr2,Attributes,Configure,Base): 有入口和出口动作的状态, 并定义一些属性 (后文详述)、标志与延迟事件 (普通 msm 延迟事件) 以及一个非默认基状态 (如标准 MSM 中所定义).

另外还定义了 no_action, 它除充当占位符外什么也不做 (例如, 当我们有出口动作却没有入口动作时, 就需要它来充当入口动作). Expr1 和 Expr2 是动作序列, 遵循与转移表中相同的动作文法 (即 ``/'' 符号之后的部分).

BOOST_MSM_EUML_STATE 宏可以让你定义大多数常见状态, 但有时你会需要更多, 例如在状态中提供某些特殊行为. 这时你必须手工完成宏的工作, 这并不十分复杂. 状态需要像任何状态一样继承自 msm::front::state<>, 并且继承 euml_state<state-name> 以启用 Proto. 然后你还需要声明一个实例供转移表使用. 例如:

struct Empty_impl : public msm::front::state<> , public euml_state<Empty_impl>
{
   void activate_empty() {std::cout << "switching to Empty " << std::endl;}
   template <class Event,class Fsm>
   void on_entry(Event const& evt,Fsm&fsm){...}
   template <class Event,class Fsm>
   void on_exit(Event const& evt,Fsm&fsm){...}
};
//instance for use in the transition table
Empty_impl const Empty;

还要注意, 我们定义了一个名为 activate_empty 的方法. 我们希望在某个行为中调用它. 这可以用 BOOST_MSM_EUML_METHOD 宏来实现.

BOOST_MSM_EUML_METHOD(ActivateEmpty_,activate_empty,activate_empty_,void,void)

第一个参数是底层仿函数的名称 (你可以在 Functor 前端中使用它), 第二个是状态方法名, 第三个是 eUML 生成的函数, 第四和第五个是在转移或状态行为中使用时的返回值. 现在你可以在转移中使用它:

Empty == Open + open_close / (close_drawer,activate_empty_(target_))

收尾一个简单的状态机及首批完整示例

你可以复用标准前端的状态机定义方法, 只需把转移表换成新表. 你也可以用 eUML 现场定义一个状态机 (例如, 当你需要以仿函数形式为该状态机提供 on_entry/on_exit 时). 为此还有一个宏 BOOST_MSM_EUML_DECLARE_STATE_MACHINE, 它有 2 个参数: 一个描述状态机的表达式和状态机名称. 该表达式最多可有 8 个参数:

  • (Stt, Init): 最简单的状态机, 仅定义了转移表和初始状态.

  • (Stt, Init, Expr1): 定义了转移表、初始状态和入口动作的状态机.

  • (Stt, Init, Expr1, Expr2): 定义了转移表、初始状态、入口和出口动作的状态机.

  • (Stt, Init, Expr1, Expr2, Attributes): 定义了转移表、初始状态、入口和出口动作的状态机. 此外还添加了一些属性 (后文详述).

  • (Stt, Init, Expr1, Expr2, Attributes, Configure): 定义了转移表、初始状态、入口和出口动作的状态机. 此外还添加了一些属性 (后文详述)、标志、延迟事件和配置能力 (无消息队列 / 不捕获异常).

  • (Stt, Init, Expr1, Expr2, Attributes, Flags, Deferred , Base): 定义了转移表、初始状态、入口和出口动作的状态机. 此外还添加了属性 (后文详述)、标志、延迟事件和配置能力 (无消息队列 / 不捕获异常), 并定义了一个非默认基状态 (见后端说明).

例如, 一个最小的状态机可以定义为:

BOOST_MSM_EUML_TRANSITION_TABLE((
),transition_table)

BOOST_MSM_EUML_DECLARE_STATE_MACHINE((transition_table,init_ << Empty ),
                                     player_)

请看看用 eUML 的第一种语法和第二种语法编写的 player 教程. BOOST_MSM_EUML_DECLARE_ATTRIBUTE 宏 (我们稍后会回到它) 使用 attribute syntax 声明赋予某个 eUML 类型 (状态或事件) 的属性.

定义子状态机

用其他前端定义子状态机 (见教程) 不过是把一个本身是状态机的状态用于另一个状态机的转移表中. eUML 也是如此. 只需定义第二个状态机, 并在包含它的状态机的转移表中引用它.

与状态或事件定义宏不同, BOOST_MSM_EUML_DECLARE_STATE_MACHINE 定义的是类型而非实例, 因为后端需要的是类型. 这意味着你需要自行声明一个实例, 才能在另一个状态机中引用你的子状态机, 例如:

BOOST_MSM_EUML_DECLARE_STATE_MACHINE(...,Playing_)
typedef msm::back11::state_machine<Playing_> Playing_type;
Playing_type const Playing;

现在可以在包含它的状态机的转移表中使用这个实例了:

Paused == Playing + pause / pause_playback

属性 / 函数调用

现在我们想让文法更加实用. 很多时候, 人们只需要非常简单的动作方法, 例如 ++Counter 或 Counter > 5, 其中 Counter 通常定义为包含状态机的类的某个属性. 为这样简单的动作编写一个仿函数似乎是浪费. 此外, MSM 中的状态本身也是类, 因此可以有属性, 我们也希望为它们提供属性.

如果回看我们使用第一种和第二种语法的示例, 你会发现一个 BOOST_MSM_EUML_DECLARE_ATTRIBUTE 宏和一个 BOOST_MSM_EUML_ATTRIBUTES 宏. 第一个声明可能的属性:

BOOST_MSM_EUML_DECLARE_ATTRIBUTE(std::string,cd_name)
BOOST_MSM_EUML_DECLARE_ATTRIBUTE(DiskTypeEnum,cd_type)

这声明了两个属性: std::string 类型的 cd_name 和 DiskTypeEnum 类型的 cd_type. 这些属性并不特定属于任何事件或状态, 我们只是声明了一个名称和一个类型. 现在, 可以用第二个宏给 cd_detected 事件添加属性:

BOOST_MSM_EUML_ATTRIBUTES((attributes_ << cd_name << cd_type ),
                          cd_detected_attributes)

这声明了一个属性列表, 它尚未关联到任何具体对象. 它可以附加到一个状态或一个事件上. 例如, 若我们想让 cd_detected 事件拥有这些已定义的属性, 就这样写:

BOOST_MSM_EUML_EVENT_WITH_ATTRIBUTES(cd_detected,cd_detected_attributes)

对于状态, 我们使用 BOOST_MSM_EUML_STATE 宏, 它有一种可提供属性的表达式形式. 例如:

BOOST_MSM_EUML_STATE((no_action /*entry*/,no_action/*exit*/,
                      attributes_ << cd_detected_attributes),
                     some_state)

好, 很不错, 我们现在有了一种给类添加属性的方法, 而这原本可以更简单地做到, 那么意义何在? 意义在于我们现在可以在转移表中直接引用这些属性, 且是在编译期完成. 例如, 在示例中你会找到这条转移:

Stopped==Empty+cd_detected[good_disk_format&&(event_(cd_type)==Int_<DISK_CD>())]

把 event_(cd_type) 读作 event_→cd_type, 其中 event_ 是事件通用类型, 无论具体事件是什么 (在本例中, 如该转移所示, 它恰好是 cd_detected).

该特性的主要优点是: 你无需定义新的仿函数, 也无需深入仿函数内部去了解它做了什么, 一切都近在眼前.

MSM 为状态机类型提供了更多通用对象:

  • event_: 在任何动作中使用, 即触发该转移的事件

  • state_: 在入口和出口动作中使用, 即进入 / 退出的状态

  • source_: 在转移动作中使用, 即源状态

  • target_: 在转移动作中使用, 即目标状态

  • fsm_: 在任何动作中使用, 即处理该转移的 (最低层) 状态机

  • Int_<int value>: 表示一个 int 的仿函数

  • Char_<value>: 表示一个 char 的仿函数

  • Size_t_<value>: 表示一个 size_t 的仿函数

  • String_<mpl::string> (boost >= 1.40): 表示一个字符串的仿函数.

这些辅助对象可以两种不同的方式使用:

  • helper(attribute_name) 返回名称为 attribute_name 的属性

  • helper 返回状态 / 事件类型本身.

如果你想为状态提供自己的方法, 并且希望在转移表内使用这些方法, 第二种形式就很有用. 在前面的教程中, 我们为 Empty 提供了一个 activate_empty 方法. 我们想创建一个 eUML 仿函数并在转移表内调用它. 这可以用 MSM_EUML_METHOD / MSM_EUML_FUNCTION 宏完成. 第一个宏创建指向方法的仿函数, 第二个创建指向自由函数的仿函数. 在教程中, 我们这样写:

MSM_EUML_METHOD(ActivateEmpty_,activate_empty,activate_empty_,void,void)

第一个参数是仿函数名称, 供 Functor 前端使用. 第二个是要调用的方法的名称. 第三个是供 eUML 使用的函数名, 第四个是当函数用于转移动作上下文时的返回类型, 第五个是当函数用于状态入口 / 出口动作上下文时的结果类型 (第四和第五个通常相同). 现在我们有了一个新的 eUML 函数, 它调用“某物”的方法, 而这个“某物”就是前面展示的五个通用辅助对象之一. 现在我们可以在转移中使用它, 例如:

Empty == Open + open_close / (close_drawer,activate_empty_(target_))

现在动作被定义为两个动作的序列: close_drawer 和 activate_empty, 后者在目标自身上调用. 目标是 Empty (即左边定义的状态), 因此这确实会调用 Empty::activate_empty(). 该方法也可以带一个 (或多个) 参数, 例如事件, 那样我们就可以调用 activate_empty_(target_ , event_).

更多示例见可怕的编译器压力测试、timer 示例或使用 eUML 的 iPodSearch (关于 String_ 及更多内容).

正交区域、标志、事件延迟

定义正交区域实际上就是提供更多初始状态. 要添加更多初始状态, 把它们 `` 左移 '' 即可, 例如, 如果我们有另一个名为 AllOk 的初始状态:

BOOST_MSM_EUML_DECLARE_STATE_MACHINE((transition_table,
                                     init_ << Empty << AllOk ),
                                    player_)

你还记得从 BOOST_MSM_EUML_STATE 和 BOOST_MSM_EUML_DECLARE_STATE_MACHINE 的签名中可以看到, 就在属性之后, 我们可以定义标志, 就像在 MSM 基本前端中那样. 为此我们还有另一个“左移”文法, 例如:

BOOST_MSM_EUML_STATE((no_action,no_action, attributes_ <<no_attributes_,
                      /* flags */ configure_<< PlayingPaused << CDLoaded),
                    Paused)

现在我们用另一个宏定义了 Paused 将获得两个标志: PlayingPaused 和 CDLoaded:

BOOST_MSM_EUML_FLAG(CDLoaded)

这相当于 Paused 的如下基本前端定义:

struct Paused : public msm::front::state<>
{
   typedef mpl::vector2<PlayingPaused,CDLoaded> flag_list;
};

在底层, 你实际得到的是一个 mpl::vector2.

注释: 由于我们使用的是 BOOST_MSM_EUML_STATE 表达式的 4 参数版本, 我们需要告诉 eUML 我们不需要属性. 类似于 cout << endl, 我们需要 attributes_ << no_attributes_ 语法.

可以通过状态机的 is_flag_active 方法使用标志. 你也可以使用提供的辅助函数 is_flag_ (返回 bool) 来处理状态和转移行为. 例如, 在用 eUML 实现的 iPod中, 你会找到如下转移:

ForwardPressed == NoForward + EastPressed[!is_flag_(NoFastFwd)]

该函数还有一个可选的第二个参数, 即调用该函数的状态机. 默认使用 fsm_ (当前状态机), 但你也可以提供一个返回对另一个状态机的引用的仿函数.

eUML 还支持在状态 (状态机) 定义中定义延迟事件. 为此, 我们可以复用标志文法. 例如:

BOOST_MSM_EUML_STATE((Empty_Entry,Empty_Exit, attributes_ << no_attributes_,
                      /* deferred */ configure_<< play ),Empty)

configure_ 左移也负责延迟事件. 向 configure_ 内左移一个标志, 状态就会获得一个标志; 左移一个事件, 它就会获得一个延迟事件. 这替代了如下基本前端定义:

typedef mpl::vector<play> deferred_events;

在该教程中, player 定义了第二个正交区域, 以 AllOk 为初始状态. 状态 Empty 和 Open 也延迟事件 play. Open、Stopped 和 Pause 还支持标志 CDLoaded, 采用的是同样的左移到 configure_ 的方式.

在 Functor 前端中, 我们还可以在转移内部延迟一个事件, 从而实现条件延迟. eUML 通过使用 defer_ 指令也能做到这一点, 如该教程所示. 你会找到如下转移:

Open + play / defer_

这是一个 internal transition. 暂时忽略它. 有意思的是, 当事件 play 被触发且 Open 处于活动状态时, 该事件将被延迟. 现在添加一个守卫, 你就可以有条件地延迟事件, 例如:

Open + play [ some_condition ] / defer_

这类似于我们在 Functor 前端中的做法, 也就是说有同样的约束. 由于使用的是 defer_ 而非状态声明, 我们需要告诉 MSM 这个状态机中存在延迟事件. 我们 (再次) 通过在状态机定义中使用一个 configure_ 声明来做到这一点, 在其中左移 deferred_events 配置标志:

BOOST_MSM_EUML_DECLARE_STATE_MACHINE((transition_table,
                                      init_ << Empty << AllOk,
                                      Entry_Action,
                                      Exit_Action,
                                      attributes_ << no_attributes_,
                                      configure_<< deferred_events ),
                                    player_)

有一个教程展示了这种可能性.

定制状态机 / 获得更快的速度

我们刚刚看到了如何用 configure_ 定义延迟事件或标志. 我们也可以像在其他前端中那样用它来配置状态机:

  • configure_ << no_exception: 禁用异常处理

  • configure_ << no_msg_queue 停用消息队列

  • configure_ << deferred_events 手动启用事件延迟

停用前两个特性, 并且在不需要时不激活第三个, 能大幅提升状态机的事件分发速度. 我们用 eUML 编写的速度测试示例正是这样做的, 以获得最佳性能.

重要说明: 由于出口伪状态要使用消息队列把事件转发到子状态机之外, 含有出口伪状态的状态机不能使用 no_message_queue 选项.

完成 / 匿名转移

匿名转移 (见 UML tutorial) 是没有具名事件的转移, 因此只要守卫允许, 源状态一成为活动状态它们就会立即触发. 由于没有事件, 要定义这样的转移, 只需省略转移的 ``+'' 部分 (即事件), 例如:

State3 == State4 [always_true] / State3ToState4
State4 [always_true] / State3ToState4 == State3

请看看该示例, 它用 eUML 实现了 previously defined 状态机.

内部转移

与其他两个前端一样, eUML 支持两种定义内部转移的方式:

  • 在状态机的转移表中. 这时你需要指定源状态、事件、动作和守卫, 但不指定目标状态, eUML 会将其解释为内部转移. 例如, 下面定义了 Open 内部关于事件 open_close 的一条转移:

    Open + open_close [internal_guard1] / internal_action1

    完整示例. 也提供了一份.

  • 在状态的 internal_transition_table 中. 例如:

    BOOST_MSM_EUML_DECLARE_STATE((Open_Entry,Open_Exit),Open_def)
struct Open_impl : public Open_def
{
   BOOST_MSM_EUML_DECLARE_INTERNAL_TRANSITION_TABLE((
        open_close [internal_guard1] / internal_action1
   ))
};

    注意, 由于我们已经处于 Open 的上下文中, 因此无需再重复该转移源自 Open.

    实现还展示了子状态机获得的一项额外好处: 子状态机可以同时拥有标准 transition_table 和一个 internal_transition_table (后者优先级更高). 如果你决定把一个状态升级为完整的子状态机, 这会让事情更容易. 它也略快于标准替代方案 (添加正交区域), 因为事件分发若被内部表接受, 就不会继续进入子区域. 这带来的是 O(1) 分发而非 O(区域数).

Kleene (任意) 事件

与 Functor 前端一样, eUML 支持 `any` 事件的概念, 但 boost::any 不是可接受的 eUML 终端. 如果你需要 any 事件, 请使用 msm::front::euml::kleene, 它继承自 boost::any. 与使用 boost:any 时相同的转移将是:

State1 + kleene == State2

其他状态类型

我们已经看到了创建简单状态的 build_state 函数. 同样, eUML 为其他类型的状态提供了其他状态构建宏:

  • BOOST_MSM_EUML_TERMINATE_STATE 的参数与 BOOST_MSM_EUML_STATE 相同, 顾名思义, 它定义一个终止状态.

  • BOOST_MSM_EUML_INTERRUPT_STATE 的参数与 BOOST_MSM_EUML_STATE 相同, 定义一个中断状态. 不过, 表达式参数的第一个元素必须是结束中断的事件, 例如: BOOST_MSM_EUML_INTERRUPT_STATE(( end_error /end interrupt event/,ErrorMode_Entry,ErrorMode_Exit ),ErrorMode)

  • BOOST_MSM_EUML_EXIT_STATE 的参数与 BOOST_MSM_EUML_STATE 相同, 定义一个出口伪状态. 不过, 表达式参数的第一个元素必须是从出口点向外传播的事件: BOOST_MSM_EUML_EXIT_STATE(( event6 /propagated event/,PseudoExit1_Entry,PseudoExit1_Exit ),PseudoExit1)

  • BOOST_MSM_EUML_EXPLICIT_ENTRY_STATE 定义一个入口伪状态. 它接受 3 个参数: 要进入的区域索引以 int 参数给出, 随后是像 BOOST_MSM_EUML_STATE 那样的配置表达式, 最后是状态名. 因此 BOOST_MSM_EUML_EXPLICIT_ENTRY_STATE(0 /region index/,( SubState2_Entry,SubState2_Exit ),SubState2) 定义了进入子状态机第一个区域的入口状态.

  • BOOST_MSM_EUML_ENTRY_STATE 定义一个入口伪状态. 它接受 3 个参数: 要进入的区域索引以 int 参数给出, 随后是像 BOOST_MSM_EUML_STATE 那样的配置表达式, 最后是状态名. 因此 BOOST_MSM_EUML_ENTRY_STATE(0,( PseudoEntry1_Entry,PseudoEntry1_Exit ),PseudoEntry1) 定义了进入子状态机第一个区域的伪入口状态.

要在转移表中使用这些状态, eUML 提供了函数 explicit_、exit_pt_ 和 entry_pt_. 例如, 从 SubFsm2 直接进入子状态 SubState2 可以写作:

explicit_(SubFsm2,SubState2) == State1 + event2

分叉是直接入口的列表, eUML 支持一种直观的语法 (state1, state2, …​), 例如:

(explicit_(SubFsm2,SubState2),
 explicit_(SubFsm2,SubState2b),
 explicit_(SubFsm2,SubState2c)) == State1 + event3

进入入口点所用的语法与显式入口相同:

entry_pt_(SubFsm2,PseudoEntry1) == State1 + event4

对于出口点, 语法仍然相同, 只是出口点用作转移的源:

State2 == exit_pt_(SubFsm2,PseudoExit1) + event6

入口教程也有 eUML 版本.

辅助函数

我们已经见过几个辅助对象, 但还有更多, 下面给出更完整的描述:

  • event_: 在任何动作中使用, 即触发该转移的事件

  • state_: 在入口和出口动作中使用, 即进入 / 退出的状态

  • source_: 在转移动作中使用, 即源状态

  • target_: 在转移动作中使用, 即目标状态

  • fsm_: 在任何动作中使用, 即处理该转移的 (最深层) 状态机

  • 这些对象也可以作为函数使用并返回一个属性, 例如 event_(cd_name)

  • Int_<int value>: 表示一个 int 的仿函数

  • Char_<value>: 表示一个 char 的仿函数

  • Size_t_<value>: 表示一个 size_t 的仿函数

  • True_ 和 False_ 仿函数, 分别返回 true 和 false

  • String_<mpl::string> (boost >= 1.40): 表示一个字符串的仿函数.

  • if_then_else_(guard, action, action), 其中 action 可以是动作序列

  • if_then_(guard, action), 其中 action 可以是动作序列

  • while_(guard, action), 其中 action 可以是动作序列

  • do_while_(guard, action), 其中 action 可以是动作序列

  • for_(action, guard, action, action), 其中 action 可以是动作序列

  • process_(some_event [, some state machine] [, some state machine] [, some state machine] [, some state machine]) 会在当前状态机上或在作为第 2、3、4、5 个参数传入的状态机上调用 process_event (some_event). 这允许向多台外部状态机发送事件

  • process_(event_): 重新处理触发该转移的事件

  • reprocess_(): 与上面相同, 但写起来更短

  • process2_(some_event,Value [, some state machine] [, some state machine] [, some state machine]) 会在当前状态机上或在作为第 3、4、5 个参数传入的状态机上调用 process_event (some_event(Value))

  • is_ flag_(some_flag[, some state machine]) 会在当前状态机上或在作为第 2 个参数传入的状态机上调用 is_flag_active

  • Predicate_<some predicate>: 用于 STL 算法. 包装一元/二元函数使其与 eUML 兼容, 从而可用于 STL 算法

这可以相当有趣. 例如,

/( if_then_else_(--fsm_(m_SongIndex) > Int_<0>(),/*if clause*/
                 show_playing_song, /*then clause*/
                 (fsm_(m_SongIndex)=Int_<1>(),process_(EndPlay))/*else clause*/
                 )
  )

表示: 若 (fsm.SongIndex > 0), 则调用 show_playing_song, 否则 \{fsm.SongIndex=1; 在 fsm 上处理 EndPlay;\}

有几个示例用到了这些特性:

  • 在 BoostCon09 上介绍的 iPod 示例已被重写为 eUML 版本 (编译器较弱的读者请跳过…​)

  • 同样在 BoostCon09 上介绍的 iPodSearch 示例也已被重写为 eUML 版本. 在该示例中, 你还会找到一些 STL 仿函数用法示例.

  • 一个更简单的 timer 示例是很好的起点.

遗憾的是有一个小陷阱. 用 MSM_EUML_METHOD 或 MSM_EUML_FUNCTION 定义的仿函数是正确的仿函数. 你按照本节开头所述自行编写的 eUML 仿函数也能正常工作, 但目前在使用 while_、if_then_、if_then_else_ 函数时除外.

类 Phoenix 的 STL 支持

eUML 支持大多数 C 运算符 (取地址除外). 例如可以写 event_(some_attribute) 或 [source_(some_bool) && fsm_(some_other_bool)]. 但程序员在日常编程中需要的不仅仅是运算符, STL 显然是必备品. 因此, eUML 带来了大量仿函数, 进一步减少了你在转移表中对自定义仿函数的需求. STL 的几乎每个算法或容器方法都有对应的 eUML 函数. 与 Boost.Phoenix 一样, .'' And →'' 的对象调用方式被函数式编程范式取代, 例如:

  • begin_(container), end_(container): 返回容器的迭代器

  • empty_(container): 返回 container.empty()

  • clear_(container): container.clear()

  • transform_: std::transform

简而言之, 几乎每个 STL 方法或算法都有一个对应的仿函数, 然后即可在转移表或状态动作中使用. 参考列出了所有 eUML 函数及其底层仿函数 (因此这一能力并非 eUML 独享, 基于仿函数的前端同样可用). 这个类 Phoenix 库的文件结构与 Boost.Phoenix 一致. 所有用于 STL 算法的仿函数位于:

#include <msm/front/euml/algorithm.hpp>

算法还按子头文件划分, 为简单起见与 phoenix 结构对应:

#include < msm/front/euml/iteration.hpp>
#include < msm/front/euml/transformation.hpp>
#include < msm/front/euml/querying.hpp>

容器方法位于:

#include < msm/front/euml/container.hpp>

或者也可以直接包含整套 STL 支持 (你还需要包含 euml.hpp):

#include < msm/front/euml/stl.hpp>

几个示例 (见该教程):

  • push_back_(fsm_(m_tgt_container),event_(m_song)): 状态机有一个 std::vector<OneSong> 类型的属性 m_tgt_container, 事件有一个 OneSong 类型的属性 m_song. 因此这一行把 m_song 推入 m_tgt_container 的末尾

  • if_then_( state_(m_src_it) != end_(fsm_(m_src_container)), process2_(OneSong(),*(state_(m_src_it)++)) ): 当前状态有一个属性 m_src_it (一个迭代器). 如果该迭代器 != fsm.m_src_container.end(), 则在 fsm 上处理 OneSong, 它以 state.m_src_it 复制构造, 随后我们对迭代器做后置递增

用 Boost.Phoenix 编写动作 (开发中)

也可以用 Boost.Phoenix 功能的一个子集来编写动作、守卫以及状态入口和出口动作. 该特性仍处于开发阶段, 所以你可能会时不时遇到一些意外. 不过简单情形应当工作良好. 行不通的是把 eUML 仿函数与 Phoenix 仿函数混用. 不过用一种语言写守卫、用另一种语言写动作是可以的.

Phoenix 支持的语法也比 eUML 所能支持的更大, 因此你只能使用 phoenix 文法的一个子集. 这是由 eUML 的本质决定的. 运行期转移表定义会通过 Boost.Typeof 转换为一个类型. 其结果是一个由仿函数类型构成的“正常”MSM 转移表. 由于 C++ 不允许混用运行期与编译期构造, 这会带来一些限制 (试着实例化一个模板类 MyTemplateClass<i>, 其中 i 是一个 int, 你就会明白). 这意味着以下合法的 Phoenix 构造将无法工作:

  • 字面量

  • 函数指针

  • bind

  • →*

MSM 还提供了一些占位符, 它们在 MSM 的语境中比 arg1 .. argn 更有意义:

  • _event: 触发该转移的事件

  • _fsm: 处理该事件的状态机

  • _source: 该转移的源状态

  • _target: 该转移的目标状态

  • _state: 用于状态入口/出口动作, 即进入/退出的状态

MSM 的未来版本将更好地支持 Phoenix. 你可以通过找出那些本应工作却不能工作的用例来参与贡献, 使它们得以加入.

Phoenix 支持默认不启用. 要启用它, 请在任何 MSM 头文件之前添加: #define BOOST_MSM_EUML_PHOENIX_SUPPORT.
