back & back11 后端

后端包含库的引擎, 并决定了性能与功能之间的取舍. 目前共有三个后端:

  • msm::back 使用 C++03

  • msm::back11 使用 C++11, 如有可能应将其作为默认选择, 因为它消除了一些 C++11 之前的限制 (容量受限的 mpl::vector)

  • msm::backmp11 使用 C++17 (目前仍处于实验阶段, 详见单独页面)

目前可用的后端以非常高的运行期速度实现了 UML 2.0 标准定义的大部分功能, 代价是更长的编译期. 运行期速度得益于恒定时间的双重分发与自适应能力, 使框架能够针对给定具体状态机所使用的特性自行调整. 所有不需要的特性要么自行禁用, 要么可以手动禁用.

创建

MSM 分为前端和后端两部分, 因此需要先定义一个前端. 然后, 要创建一个真正的状态机, 还必须声明后端:

typedef msm::back11::state_machine<my_front_end> my_fsm;

现在我们有了一个功能完备的状态机类型. 后续各节将描述可以用它做什么.

启动与停止状态机

start() 方法启动状态机, 即激活初始状态, 这又意味着将调用初始状态的入口行为. 之所以需要 start 方法, 是因为初始状态的入口行为并非总是需要立即调用, 而是只在状态机准备好处理事件时才调用. 一个典型的例子是: 用状态机编写算法, 每次循环回到初始状态即是一次算法调用. 每调用一次 start, 算法就会运行一次. iPodSearch 示例便利用了这一可能性.

stop() 方法的工作方式相同. 它会导致当前活动状态的出口动作被调用.

其实这两个方法并非绝对必需. 不调用它们只会使第一个入口动作或最后一个出口动作不被调用而已.

事件分发

状态机存在的首要理由就是分发事件. 对 MSM 而言, 事件是某种给定事件类型的对象. 对象本身可以包含数据, 但决定所采取转移的是事件类型. 对 MSM 来说, 如果 some_event 是某个给定类型 (例如一个简单的 struct), 而 e1 和 e2 是 some_event 的两个具体实例, 那么从转移的角度看, e1 与 e2 是等价的. 当然, e1 和 e2 可以有不同的值, 并且可以在动作中使用它们. 事件以 const 引用的方式分发, 因此出于副作用方面的明显考虑, 动作不能修改事件. 要分发一个 some_event 类型的事件, 只需在处理前临时创建或实例化一个即可:

my_fsm fsm; fsm.process_event(some_event());
some_event e1; fsm.process_event(e1)

临时创建事件会被编译器优化, 因此性能不会下降.

活动状态

后端还提供了获知哪个状态处于活动状态的方法, 不过通常只有调试时才需要它. 如果你只是想对活动状态做些操作, internal transitions 或 visitors 是更好的选择. 如果你需要知道哪个状态处于活动状态, const int* current_state() 会返回一个由状态 ID 组成的数组. 状态 ID 的生成方式请参见 internals section.

上层状态机 (仅 msm::back11)

传递给仿函数或入口/出口动作的 FSM 模板参数是当前状态机, 而这未必是你想要的, 因为上层状态机往往更有意义. 后端提供了 get_upper() 函数, 返回指向上层状态机的指针, 这通常才是你想对其调用 process_event 的对象.

序列化

一个常见需求是保存状态机并在之后的某个时刻恢复它. MSM 对 basic 和 functor 前端支持这一特性, 对 eUML 则以更有限的方式支持. MSM 开箱即支持 boost::serialization (通过提供一个 serialize 函数). 实际上, 对于基本序列化, 你几乎不需要做什么, MSM 状态机几乎可以像其他任何类型一样被序列化. 无需任何特殊工作, 就可以让状态机记住自己的状态, 例如:

MyFsm fsm;
// write to archive
std::ofstream ofs("fsm.txt");
// save fsm to archive
{
    boost::archive::text_oarchive oa(ofs);
    // write class instance to archive
    oa << fsm;
}

载回的过程非常相似:

MyFsm fsm;
{
    // create and open an archive for input
    std::ifstream ifs("fsm.txt");
    boost::archive::text_iarchive ia(ifs);
    // read class state from archive
    ia >> fsm;
}

这会 (反) 序列化状态机本身, 但不包括具体状态的数据. 后者可以按状态逐个进行, 以减少所需的输入量. 要允许序列化某个具体状态, 请提供 do_serialize typedef 并实现 serialize 函数:

struct Empty : public msm::front::state<>
{
    // we want Empty to be serialized. First provide the typedef
    typedef int do_serialize;
    // then implement serialize
    template<class Archive>
    void serialize(Archive & ar, const unsigned int /* version */)
    {
        ar & some_dummy_data;
    }
    Empty():some_dummy_data(0){}
    int some_dummy_data;
};

也可以序列化前端类中包含的数据. 同样, 你需要提供 typedef 并实现 serialize:

struct player_ : public msm::front::state_machine_def<player_>
{
    //we might want to serialize some data contained by the front-end
    int front_end_data;
    player_():front_end_data(0){}
    // to achieve this, provide the typedef
    typedef int do_serialize;
    // and implement serialize
    template<class Archive>
    void serialize(Archive & ar, const unsigned int )
    {
        ar & front_end_data;
    }
...
};

对后端数据 (当前状态) 的保存对所有前端均有效, 因此用 eUML 编写的前端也能被序列化. 但是, 要序列化具体状态, 不能使用 BOOST_MSM_EUML_STATE 这类宏, 而必须通过直接继承 front::euml::euml_state 来实现该状态.

唯一的限制是事件队列无法序列化, 因此序列化必须在稳定状态下进行, 即没有事件正在处理的时候. 只是在不使用任何队列 (延迟队列或事件队列) 的情况下, 才能在事件处理过程中进行序列化.

这个示例展示了一个状态机, 我们在处理完一个事件后对它进行序列化. Empty 状态也有一些要序列化的数据.

基状态类型

有时需要自定义状态以避免重复并提供公共功能, 例如以虚方法的形式. 你可能还想让状态具备多态性, 以便可以对其调用 typeid 进行日志记录或调试. 如果你需要访问者, 这也很有用, 下一节将予以展示. 你会注意到, 所有前端都支持添加基类型. 注意, 所有状态和状态机必须使用同一个基状态, 因此这可能降低可复用性. 例如, 使用 basic 前端时, 你需要:

  • 在 msm::front::state<> 定义中添加非默认的基状态, 作为第一个模板参数 (interrupt_states 除外, 对它而言基状态是第二个参数, 第一个参数是结束中断的事件), 例如, 设 my_base_state 是给定状态机中所有状态的新基状态:

    struct Empty : public msm::front::state<my_base_state>

    现在, my_base_state 就是你的新基状态. 如果它含有虚函数, 你的状态就成为多态的. MSM 还提供了一个默认的多态基类型 msm::front::polymorphic_state

  • 在状态机前端定义中添加用户自定义的基状态, 作为第二个模板参数, 例如:

    struct player_ : public msm::front::state_machine<player_,my_base_state>

也可以使用 const base_state* get_state_by_id(int id) const 请求具有给定 id 的状态 (该 id 可能来自 current_state()), 其中 base_state 就是你刚定义的基状态. 现在就可以进行多态操作了.

访问者

在某些情况下, 仅有指向当前活动状态的基类指针还不够. 你可能希望以非虚调用的方式调用当前活动状态的方法. 当然, MSM 绝不会把 virtual 关键字强加给你!

为实现这一目标, MSM 利用前文介绍的用户自定义状态技术, 提供了访问者模式的一种自有变体. 如果你在用户自定义基状态中添加一个给出返回值 (目前未使用) 和参数的 accept_sig typedef, 并提供一个具有该签名的 accept 方法, 那么调用 visit_current_states 将使 accept 在当前活动状态上被调用. 通常, 你还会希望在基状态中提供一个空的默认 accept, 以免强制所有状态都实现 accept. 例如, 你的基状态可以是:

struct my_visitable_state
{
   // signature of the accept function
   typedef args<void> accept_sig;
   // we also want polymorphic states
   virtual ~my_visitable_state() {}
   // default implementation for states who do not need to be visited
   void accept() const {}
};

这使你的状态成为多态且可被访问的. 这里 accept 被声明为 const 且不接收参数. 它也可以写成:

struct SomeVisitor {…};
struct my_visitable_state
{
    // signature of the accept function
    typedef args<void,SomeVisitor&> accept_sig;
    // we also want polymorphic states
    virtual ~my_visitable_state() {}
    // default implementation for states who do not need to be visited
    void accept(SomeVisitor&) const {}
};

现在, accept 将接收一个参数 (也可以是非 const 的). 默认情况下, accept 最多接收 2 个参数. 若需更多参数, 请在包含 state_machine.hpp 之前将 #define BOOST_MSM_VISITOR_ARG_SIZE 设置为其他值. 例如:

#define BOOST_MSM_VISITOR_ARG_SIZE 3
#include <boost/msm/back/state_machine.hpp>

注意, accept 会在所有活动状态上被调用, 同时也会自动在子状态机的子状态上被调用.

重要警告: visit_current_states 方法按值接收其参数, 因此如果 accept 函数的签名中要包含按引用传递的参数, 请用 boost:ref/cref 传递该参数, 以避免不必要的复制或切片. 例如, 对于上面的情形, 应调用:

SomeVisitor vis; sm.visit_current_states(boost::ref(vis));

这个示例使用了带 2 个参数的访问函数.

标志

标志是 MSM 特有的概念, 为所有前端所支持, 各前端都基于以下函数:

template <class Flag> bool is_flag_active()
template <class Flag,class BinaryOp> bool is_flag_active()

如果当前活动状态支持 Flag 属性, 这些函数将返回 true. 当存在多个正交区域时, 第一种变体对结果求或 (OR); 第二种变体则要求传入 OR 或 AND, 例如:

my_fsm.is_flag_active<MyFlag>()
my_fsm.is_flag_active<MyFlag,my_fsm_type::Flag_OR>()

用法示例请参见各前端章节.

获取状态

有时需要让客户端代码能够访问状态的数据. 毕竟, 状态一次性创建后会长期存在, 生命周期与状态机一样长, 何不加以利用呢? 有时你只是需要获取任意状态 (包括非活动状态) 的信息. 例如, 你想编写一个覆盖率工具, 知道某个状态被访问了多少次. 要获取状态, 请使用 get_state 方法并给出状态名, 例如:

player::Stopped* tempstate = p.get_state<player::Stopped*>();

或者

player::Stopped& tempstate2 = p.get_state<player::Stopped&>();

取决于你的个人喜好.

带参数的状态机构造函数

你可能希望为状态机定义一个非默认构造函数. 例如, 你可能想这样写:

struct player_ : public msm::front::state_machine_def<player_>
{
    player_(int some_value){…}
};

这是可行的, 方法是把后端用作转发对象:

typedef msm::back11::state_machine<player_ > player; player p(3);

创建时, 后端会调用相应的前端构造函数.

可以传递的参数数量上限是 BOOST_MSM_CONSTRUCTOR_ARG_SIZE 宏的值 (当前为 5). 如需覆盖默认值, 请在包含任何头文件之前修改该值.

也可以使用 boost::ref (或 boost::cref) 按引用 (或 const 引用) 传递参数:

struct player_ : public msm::front::state_machine_def<player_>
{
   player_(SomeType& t, int some_value){…}
};

typedef msm::back11::state_machine<player_ > player;
SomeType data;
player p(boost::ref(data),3);

通常, MSM 会默认构造其所有状态或子状态机. 但有些情况下你可能不希望如此. 例如, 当你把一个状态机用作子状态机, 而该子状态机使用了上面定义的构造函数时. 你可以在状态机构造函数的第一个参数位置添加一个表达式, 在其中传入并复制已有的状态:

player p( back::states_ << state_1 << ... << state_n , boost::ref(data),3);

其中 state_1..n 是状态机中部分或全部状态的实例. 由于子状态机也是状态机, 这种做法可以递归使用, 例如, 若 Playing 是一个包含状态 Song1 的子状态机, 而 Song1 自身也有一个需要传入一些数据的构造函数:

player p( back::states_ << Playing(back::states_ << Song1(some_Song1_data)) ,
          boost::ref(data),3);

还可以随时使用 set_states() 以相同的语法将某个状态替换为新实例, 例如:

p.set_states( back::states_ << state_1 << ... << state_n );

有一个示例大量使用了这一能力.

以运行期速度换取更优的编译期 / 多 TU 编译 (仅 msm::back)

MSM 为运行期速度而优化, 代价是更长的编译期. 对于较老的编译器和大型状态机, 这可能成为问题, 尤其当你并不特别在意运行期速度, 而只要性能与大多数状态机库大致相当就能满足需求时. MSM 提供了一个后端策略来解决这个问题. 但在尝试之前, 如果你使用的是 VC 编译器, 请先关闭 /Gm 编译器选项 (调试构建默认开启该选项). 该选项可能使构建时间变为原来的 3 倍…​ 如果编译期仍是个问题, 请继续阅读. 在以下两种主要情形下, MSM 提供的策略可加快编译:

  • 大量转移冲突

  • 子状态机

后端 msm::back::state_machine 有一个策略参数 (第一个是前端, 其次是历史策略), 默认值为 favor_runtime_speed. 要切换到 favor_compile_time (在 <msm/back/favor_compile_time.hpp> 中声明), 你需要:

  • 将主状态机 (可能还包括各子状态机) 的策略切换为 favor_compile_time

  • 把子状态机的声明移入各自单独的头文件, 并在其中包含 <msm/back/favor_compile_time.hpp>

  • 为每个子状态机添加一个 cpp 文件, 该文件包含你的头文件并调用一个生成辅助代码的宏, 例如:

    #include "mysubmachine.hpp"
BOOST_MSM_BACK_GENERATE_PROCESS_EVENT(mysubmachine)

  • 将编译器配置为多核编译

现在, 状态机将在与子状态机数量相同的多个核心上编译, 如果把状态机拆分为较小的子状态机, 这将大大加快编译速度.

另外, 转移冲突的消解也会快得多.

该策略在底层使用 boost.any, 这意味着我们将失去 MSM 在默认策略下提供的一项特性, 即事件层级. 下面的示例对 iPod 示例加以改造, 利用这一技术加快编译. 其中包括:

  • 主状态机与 main 函数

  • PlayingMode 移至单独的头文件

  • PlayingMode 的 cpp 文件

  • MenuMode 移至单独的头文件

  • MenuMode 的 cpp 文件

  • 事件移至单独的头文件, 所有状态机都要使用它

编译期状态机分析

MSM 状态机本身就是一个元程序, 因此在编译期检查具体状态机的有效性是顺理成章的. 为此, MSM 使用 Gordon Woodhull 的编译期图库 mpl_graph (目前随 MSM 一起提供), 提供了几项编译期检查:

  • 检查各正交区域是否真正正交.

  • 检查所有状态是否要么可从初始状态到达, 要么是显式入口/伪入口状态.

要使用这一特性, 后端提供了一个策略 (默认不做分析) msm::back::mpl_graph_fsm_check. 例如:

 typedef msm::back11::state_machine< player_,msm::back::mpl_graph_fsm_check> player;

由于 MSM 现在使用 Boost.Parameter 来声明策略, 策略选择可以放在前端类型之后的任意位置 (本例中即 player_).

一旦检测到错误, 将触发一个编译期断言.

该特性默认不启用, 因为它有不可忽视的编译期开销. 如果状态机中没有显式入口状态或伪入口状态, 该算法是线性的; 否则不幸仍是 O(number of states * number of entry states). MSM 的后续版本会对此加以改进.

如果你想在 explicit entry / pseudo entry state 声明中省略区域索引, 也会用到同一算法.

作者的建议是: 在每次修改状态机结构之后启用这些检查, 待分析成功后再将其关闭.

这个示例会在使用转移表前两行之一时触发断言.

将事件入队以便稍后处理

调用 process_event(Event const&) 将立即以 运行至完成 语义处理事件. 你也可以改为调用 enqueue_event(Event const&), 把事件入队并延迟其处理. 之后再调用 execute_queued_events() 将处理所有已入队的事件 (按 FIFO 顺序). 调用 execute_single_queued_event() 将执行最早入队的事件.

可以通过调用 get_message_queue_size() 查询队列大小.

定制消息队列

MSM 默认使用 std::deque 作为其队列 (一个消息队列存放 运行至完成 过程中或通过 enqueue_event 产生的事件, 另一个存放延迟事件). 遗憾的是, 在某些 STL 实现上, 该容器在占用空间和复制时间方面开销很大. 如果这成为问题, MSM 提供了基于 boost::circular_buffer 的替代方案, 对应的策略是 msm::back::queue_container_circular. 要使用它, 需要在后端定义中提供该策略:

 typedef msm::back11::state_machine< player_,msm::back::queue_container_circular> player;

可以通过 get_message_queue 和 get_deferred_queue 访问这两个队列, 两者都返回对队列本身 (const 或非 const) 的引用. Boost::circular_buffer 超出了本文档的范围. 不过, 你需要定义队列容量 (初始为 0), 即你预计队列最多会增长到的大小, 例如 (容量 1 很常见):

 fsm.get_message_queue().set_capacity(1);

用 Boost.Parameter 定义策略

MSM 使用 Boost.Parameter, 使 back11::state_machine<> 的策略参数 (前端以外的所有参数) 更易于定义. 这样, 你可以在任意位置以任意数量定义策略参数 (历史、编译期/运行期、状态机分析、队列所用容器). 例如:

 typedef msm::back11::state_machine< player_,msm::back::mpl_graph_fsm_check> player;
 typedef msm::back11::state_machine< player_,msm::back::AlwaysHistory> player;
 typedef msm::back11::state_machine< player_,msm::back::mpl_graph_fsm_check,msm::back::AlwaysHistory> player;
 typedef msm::back11::state_machine< player_,msm::back::AlwaysHistory,msm::back::mpl_graph_fsm_check> player;

选择何时切换活动状态

UML 标准对一个非常重要的问题未作规定: 当转移触发时, 目标状态究竟在哪个时刻成为状态机的新活动状态? 是在转移结束时? 还是离开源状态之后? 如果抛出异常又如何? 标准认为运行至完成意味着转移几乎在瞬间完成. 但即便如此, 在某些条件下这也可能是非常长的时间. 考虑下面的例子. 我们有一个表示网络连接的状态机, 可处于 Connected 和 Disconnected 状态. 当从一个状态转移到另一个状态时, 我们向另一个实体发送一个 (Boost) Signal. 默认情况下, MSM 在转移完成后才把目标状态设为新状态. 我们希望基于标志 is_connected 来发送信号, 该标志在处于 Connected 状态时为真.

我们处于状态 Disconnected 并收到事件 connect. 转移动作将向状态机询问 is_flag_active<is_connected>, 得到的结果却是…​ false, 因为我们仍处于 Disconnected. 嗯, 怎么办? 我们可以把该动作入队并稍后执行, 但这意味着一个额外的队列、更多的工作量和更高的运行期开销.

MSM 以策略的形式提供了让前端决定目标状态何时成为活动状态的可能性. 它可以是:

  • 在转移触发之前 (前提是守卫允许该转移触发): active_state_switch_before_transition

  • 在调用源状态的出口动作之后: active_state_switch_after_exit

  • 在转移动作执行之后: active_state_switch_after_transition_action

  • 在目标状态的入口动作执行之后 (默认): active_state_switch_after_entry

该问题及其解决办法在 functor 前端 和 eUML 中均有演示. 去掉 active_state_switch_before_transition 即可看到默认状态.

运行至完成

后端实现的运行至完成算法如下:

  • 检查具体状态机的某个区域是否处于终止状态或中断状态. 如果是, 则在该条件持续期间禁用事件处理 (对终止伪状态为永久, 对中断伪状态则在其处于活动状态期间).

  • 如果消息队列特性已启用且状态机已在处理某个事件, 则将当前正在处理的事件推入队列并结束处理. 否则, 记住状态机现在正在处理一个事件, 并继续.

  • 如果状态机检测到未使用延迟事件, 则跳过此步骤. 否则, 将延迟队列中的第一个延迟事件标记为活动.

  • 现在开始事件分发的核心部分. 如果启用了异常处理, 这将发生在 try/catch 块内, 且当异常发生时会调用前端 exception_caught.

  • 事件此时按初始状态前端定义所规定的顺序依次分发到每个区域. 对每个区域, 这将调用相应的前端转移定义 (即转移表中的 "row" 或 "Row" 行).

  • 在没有转移冲突的情况下, 若对给定区域存在可行的转移, 则检查守卫条件. 若其返回 true, 转移处理继续进行: 先调用当前状态的出口动作, 随后执行转移动作行为以及新活动状态的入口行为.

  • 存在转移冲突时 (多个可能的转移, 由互斥的守卫条件消歧), 守卫条件按其在转移表中转移定义的相反顺序依次尝试. 第一个返回 true 的守卫条件所对应的转移即被选中. 注意, 这一点并非由 UML 标准规定; 标准只是说明, 若守卫条件不互斥, 则状态机是不合规范的, 其行为未定义. 依赖这种实现特定的行为, 会加大开发者支持其他状态机框架的难度.

  • 如果至少有一个区域处理了该事件, 则此事件被视为已接受. 否则, 库会对状态机所包含的每个区域调用 no_transition.

  • 如果当前活动状态是一个子状态机, 行为会稍有不同. UML 标准规定必须先尝试内部转移, 因此事件首先被分发到子状态机. 只有当子状态机不接受该事件时, 才会尝试其他 (非内部) 转移.

  • 该后端支持简单状态和子状态机的内部转移. 内部转移在状态的 internal_transition_table 类型中提供. 此表中定义的转移会被添加到主状态机转移表的末尾, 但其优先级低于子状态机的转移 (定义于 transition_table 中). 对简单状态而言, 这意味着这些转移比非内部转移具有更高的优先级, 这符合 UML 标准中更深层级转移优先级更高的规定. 对子状态机而言, 这是一个非标准的扩展, 它让事件处理有机会绕过子区域的处理, 从而加快事件处理. 在标准 UML 下, 必须添加一个子区域才能处理这些内部转移, 那样会更慢.

  • 分发本身完成之后, 第 3 步中标记的延迟事件 (如果有的话) 现在会得到一次处理机会.

  • 然后, 在消息队列中排队的事件也会获得一次分发机会.

  • 最后, 完成转移 / 匿名转移 (如果存在于转移表中) 也会得到各自的分发机会.

该算法体现了后端如何在编译期尽可能完成自身配置. 在给定状态机定义中找不到的每个特性都会被停用, 因而不产生任何运行期开销. 完成事件、延迟事件、终止状态、向多个区域分发、内部转移, 只要未使用就都会被停用. 只有异常处理和消息队列需要用户配置.

已知限制

下面描述目前已知的 back 和 back11 后端的问题与限制.

在正交区域中延迟事件

事件延迟逻辑要求对延迟事件进行分发以作评估. 当延迟事件被分发到多个正交区域时, 每个区域会各自决定是消费该事件还是将其再次延迟. 这可能导致这样的情形: 一个区域延迟了该事件, 而另一个区域处理了它, 从而引发无限递归, 因为事件延迟逻辑需要一遍又一遍地重新评估这种既被延迟又被处理的事件.

根据 UML 标准, 在这种情况下, 只要有一个区域决定延迟该事件, 该事件就应被延迟. 要规避此问题, 可以显式确保 (例如使用守卫) 事件要么被延迟, 要么被处理.

常见问题 (FAQ)

应该在哪里定义状态机?:

为简单起见, 各教程都在一个简单的 cpp 源文件中实现.

我想把一个类的动态行为建模为状态机, 应该如何定义该状态机?

通常你会希望把状态机实现为该类的一个属性. 遗憾的是, 具体状态机是一个 typedef, 无法前向声明. 于是你只有两种选择:

  • 在头文件的类中直接给出状态机定义, 并把一个实例作为属性包含其中. 简单, 但有几个缺点: 不建议使用 using namespace 指令, 且所有包含该头文件的模块都要付出编译期代价.

  • 在类定义中把状态机保存为指向 void 的 (共享) 指针, 而在cpp 文件中实现状态机. 编译期开销最小, 也可以使用 using 指令, 但状态机此时位于堆中.
