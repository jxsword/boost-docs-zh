性能 / 编译器

测试在多台运行 Windows XP 和 Vista 的 PC 上进行, 分别使用 VC9 SP1 编译, 以及在 Ubuntu 上使用 g++ 4.2 和 4.3 编译. 在这些测试中, 使用 Boost.Statechart 编写了同一个播放器状态机, 一为仅含简单状态的状态机, 一为含一个复合状态的状态机. 同样的简单状态机与复合状态机也用 MSM 的标准前端实现 (简单)(复合), 其中简单版本还分别提供了 functors 和 eUML 实现. 由于这些简单状态机不需要终止/中断状态, 不需要消息队列, 且其动作具有不抛出异常保证, 因此 MSM 状态机按最小功能集定义. 测试机为 Q6600 2.4GHz, Vista 64.

速度

VC9:

  • 使用 MSM 时, 简单测试的完成速度比使用 Boost.Statechart 快 90 倍

  • 使用 MSM 时, 复合测试的完成速度快 25 倍

gcc 4.2.3 (同一台 PC 上 VMWare 中的 Ubuntu 8.04):

  • 使用 MSM 时, 简单测试的完成速度快 46 倍

  • 使用 MSM 时, 复合测试的完成速度快 19 倍

可执行文件大小

有人担心 MSM 会生成庞大的代码. 事实如此吗? 我测试的两个编译器都不支持这一说法. 在 VC9 上, 性能一节中使用的测试状态机生成的可执行文件大小为 14kB (simple 与 eUML) 和 21kB (composite). 这包括了测试代码和 iostreams. 相比之下, VC9 生成的带 iostreams 的空可执行文件大小为 7kB. Boost.Statechart 生成的可执行文件为 43kB 和 54kB. 更好的是, eUML 在可执行文件大小方面是 ``免费'' 的, 甚至还能带来速度提升. 在 g++ 4.3 下, 这在很大程度上取决于编译器选项 (比 VC 明显得多). 一个规模可观的状态机在 –O3 下可能生成 600kB 的可执行文件, 使用 eUML 则可达 1.5MB. 改用 –Os –s 后, 测试状态机可降到 18kB 和 30kB, 而 eUML 可降到 1MB (仍然很大), 因此在这种情况下 eUML 不再是免费的.

支持的编译器

最新状态请查看回归测试.

MSM 已在下列编译器上成功通过测试:

  • VC8 (部分), VC9, VC10

  • g++ 4.0.1 及更高版本

  • Intel 10.1 及更高版本

  • Clang 2.9

  • Green Hills Software MULTI for ARM v5.0.5 patch 4416（简单与复合教程配置）

  • 部分支持 IBM 编译器

VC8 以及程度稍轻的 VC9 受一个缺陷困扰. 启用 "Enable Minimal Rebuild" (/Gm) 选项会导致编译期大幅增加 (VC8 上可达 3 倍!). 该选项在 Debug 模式下默认开启, 因此这可能成为大问题.

限制

  • 转移数 > 80 的状态机, 其编译时间会让你直闯 CFO 的办公室, 并确保下周就得到一台配 12GB 内存的崭新八核机器, 除非他乐意付钱请你在旁边看编译器痛苦挣扎几个小时…​ (当然, 顺便务必再要一套双 24" 显示器, 这不会有坏处.)

  • eUML 允许非常长的构造, 但在某些 decltype 支持有缺陷的编译器 (VC9, VC10) 上, 它也会迅速推高编译时间 (我怀疑其中至少存在某些平方级复杂度的算法). 即使是 g++ 4.4, 相比 4.3 也出现了一些退化, 而且当构造过大时会崩溃.

  • 如果状态机中的状态超过 10 个, 需要覆盖 mpl::vector/list 默认的 20 大小上限以及 fusion 默认的向量大小 10

  • Limitation for submachines, 以及需要事件属性的入口动作.

编译器一角

编译器有时充满意外, 开发过程中出现过许多这类奇怪的错误, 我想把其中最有趣的列出来, 供读者消遣.

VC8:

template <class StateType>
typename ::boost::enable_if<
       typename ::boost::mpl::and_<
                typename ::boost::mpl::not_<
                    typename has_exit_pseudo_states<StateType>::type
                >::type,
                typename ::boost::mpl::not_<
                    typename is_pseudo_exit<StateType>::type
                >::type
       >::type,
       BaseState*>::type

我得到如下错误:

error C2770: invalid explicit template argument(s) for '`global namespace'::boost::enable_if<…​>::…​'

如果现在把 ::boost::mpl 中第一个 ``::'' 去掉, 编译器就安静了. 因此在这种情况下, 无法遵循 Boost 的指导原则.

VC9:

  • 这一条是我的最爱. 你知道为什么退出伪状态在转移表中要用 submachine::exit_pt''? Because 来引用吗? ``exit'' 会使编译器崩溃. ``Exit'' 也不可行, 因为它会在一台机器上使编译器崩溃, 而在另一台上却不会 (两台机器的编译器是用同一张盘安装的).

  • 有时, 移除一个策略会使编译器崩溃, 因此某些版本定义了一个名为 WorkaroundVC9 的哑策略.

  • Typeof: 虽然 g++ 和 VC9 编译 ``标准'' 状态机耗时相近, 但 Typeof (尽管两者都原生支持) 在 VC9 和 VC10 上似乎表现出平方级复杂度.

  • eUML: 若发生编译器崩溃, 改变状态定义的顺序 (把没有入口/出口的状态放在前面) 有时能解决问题.

_g 4.x_: 无聊的编译器, 几乎一切都基本按预期工作. 我不是语言律师, 因此对下面的 ``Typeof 问题'' 拿不准. 在能否不经先定义 typedef 就从 BOOST_TYPEOF 生成的类型派生这一点上, VC9 与 g++ 看法不一. 若有人能解答, 我将不胜感激. 我只找到了两种让编译器崩溃的方法:

  • 不断增加 eUML 构造, 直到有什么东西崩溃为止 (g++-4.4 上尤其如此)

  • build_terminate 函数使用 2 个 mpl::push_back 而不是 mpl::insert_range, 因为 g++ 不接受 insert_range.

你可以用下面的压力测试检验编译器的 decltype 实现, 逐步恢复被注释掉的代码, 直到编译器崩溃为止.
