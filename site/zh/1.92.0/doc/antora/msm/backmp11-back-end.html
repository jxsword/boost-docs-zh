Backmp11 后端 (C++17, 实验性)

backmp11 后端要求 C++17, 且与 back 基本向后兼容. 它目前处于 实验性阶段: 功能上已经成熟, 但其 API 的一些细节以及对较少使用功能的兼容性可能还会有变化 (欢迎反馈!). 它以元编程库 Boost.Mp11 命名, 该库是这些优化的主要功臣. 用 Mp11 取代 MPL, 是为了消除 C++03 对变参模板的高成本模拟.

它在运行期和内存占用方面都有显著改进, 以下基准测试可见一斑:

创建

使用 state_machine 类把状态机的前端封装成一个可执行的状态机. 它在 backmp11 中的签名如下:

template<
    typename FrontEnd,
    typename Config = default_state_machine_config,
    typename Derived = no_derived>
class state_machine;

只有 FrontEnd 参数是必需的; using MyStateMachine = msm::backmp11::state_machine<MyStateMachine_>; 是创建状态机的最小声明.

配置

可以通过传入自定义的 Config 参数来调整状态机的配置. 默认配置如下:

struct default_state_machine_config
{
    // Sets up a context accessible by all (sub‐)machines in hierarchical state machines.
    using context = no_context;
    // Optimizes for runtime speed or compile time.
    using compile_policy = favor_runtime_speed;
    // Configures the event pool.
    using event_pool = backmp11::event_pool<std::deque>;
    // Type of the Fsm parameter passed in actions and guards.
    using fsm_parameter = local_transition_owner;
    // Sets up an observer for monitoring state machine activities.
    using observer = no_observer;
    // Identifies the upper‐most machine in hierarchical state machines.
    using root_sm = no_root_sm;
};

using state_machine_config = default_state_machine_config;

继承 state_machine_config 并重写其中的 using 指令, 即可创建自定义配置.

struct MyStateMachineConfig : state_machine_config
{
    using context = MyContext;
    using root_sm = MyRootSm;
    using fsm_parameter = root_sm;
};

状态机配置被设计为可在层次状态机之间共享.

根状态机

设置项 root_sm 定义层次状态机中根状态机的类型. 根 sm 是最上层的状态机.

如果在 config 中定义了 using root_sm = MyRootSm;, 则以下 API 可用于从任何 (子) 状态机访问它:

MyRootSm& state_machine::get_root_sm();

强烈建议在层次状态机中始终配置 root_sm, 即使并不需要访问它. 这可以减少编译时间和内存占用, 因为它使后端只需为根状态机实例化完整的方法与成员集合, 而对子状态机则可省略它们.

上下文

设置项 context 会在状态机中建立一个 context 成员, 用于依赖注入.

如果在 config 中定义了 using context = MyContext;, 则状态机中即可使用以下 API 来访问它:

MyContext& state_machine::get_context();

如果配置了 context, 则必须将其实例的引用作为第一个实参传给 state_machine 构造函数. 在层次状态机中, 还必须设置根状态机.

观察者

设置项 observer 会在状态机中建立一个 observer member, 用于监视状态机的活动. 观察者对日志记录和指标采集尤其有用. 你可以在 Logger example 中找到一个演示用的 logger 实现.

如果在 config 中定义了 using observer = MyObserver;, 则状态机中即可使用以下 API 来访问它:

MyObserver& state_machine::get_observer();

这会创建一个观察者实例, 其生命周期由状态机内部管理. 如果你的实例生命周期由外部管理, 请将观察者包装进 observer_ref:

using observer = observer_ref<MyObserver>;

如果配置了 observer ref, 则必须将其某个实例的引用作为第一个实参 (若同时配置了 context, 则为第二个实参) 传给 state_machine 构造函数. 在层次状态机中, 还必须设置根状态机.

Fsm 动作与守卫的参数

设置项 fsm_parameter 定义在层次状态机中传给动作与守卫的 Fsm& fsm 参数的实例.

默认设置为 local_transition_owner, 其行为与 back 完全相同:

  • 同一转移表中的转移, 其动作与守卫接收拥有该转移的 SM 实例 (即处理该事件的那一个)

  • 入口和出口动作接收从被进入/退出的状态视角而言的 "本地" 转移所有者 (即直接父 SM)

默认设置便于访问子状态机或其前端所包含的成员. 如果不需要访问子状态机成员, 可以改为 using fsm_parameter = root_sm. 此时, 所配置的 root_sm 将作为 Fsm 参数传给所有动作与守卫.

在 UML 中, "转移所有者" 是包含该转移的区域或状态机. "本地转移所有者" 一词扩展了这一 UML 术语, 因为入口和出口动作中的 Fsm 参数未必是包含该转移的状态机, 而是指被进入/退出的状态的直接父状态机, 即从该状态的局部视角看的转移所有者.

示例: 考虑一个带有嵌套状态机的层次状态机:

SM1 (root)
  └─ SM2
      └─ SM3
          └─ State S0 (active)

当 SM1 中定义的一个转移导致 SM2 和 SM3 退出时:

  • S0 的出口动作接收 SM3 作为 Fsm (S0 的直接父状态机)

  • SM3 的出口动作接收 SM2 作为 Fsm (SM3 的直接父状态机)

  • SM2 的出口动作接收 SM1 作为 Fsm (SM2 的直接父状态机)

事件池

设置项 event_pool 配置后端用来存放无法立即处理的工作的容器与内联存储: 入队事件、延迟事件、完成转移以及状态机终止.

template <template <typename> typename Container,
          size_t InlineCapacity = 32,
          size_t InlineAlign = alignof(std::max_align_t)>
struct event_pool;

默认配置使用 std::deque. 每个池化事件占据容器中一个类型擦除的槽位. 为避免每个槽位都做一次堆分配, 后端采用小对象优化: 能放进 InlineCapacity 字节且满足 InlineAlign 对齐的事件直接存储在槽位中; 超出任一限制的事件则回退为堆分配.

调用 push_back 或 push_front 时, 容器不得使既有迭代器失效. 所需接口如下:

  • push_back(const T&) — 用于事件入队与延迟

  • push_front(const T&) — 用于完成转移与状态机终止

  • begin()

  • end()

  • erase(iterator)

  • clear()

把 std::deque 替换为固定容量容器, 并把 InlineCapacity 和 InlineAlign 设置为覆盖所有事件类型, 状态机即可完全无需堆分配运行. 参见无堆状态机示例, 其中演示了 boost::container::static_vector 的用法.

如果不需要事件池, 可用 no_event_pool 将其停用. 该设置会禁用所有相关功能, 提升运行期性能, 并减小状态机的内存占用.

struct MyConfig : state_machine_config
{
    using event_pool = no_event_pool;
};

编译策略

设置项 compile_policy 调整状态机的编译方式, 以针对运行期速度或编译时间进行优化.

favor_runtime_speed

默认编译策略优先考虑运行期速度; 它在编译期评估所有转移并生成分发表. 分发策略可通过继承 favor_runtime_speed 并调整 using dispatch_strategy 指令来选择:

struct favor_runtime_speed
{
    /// Dispatch strategy for processing events.
    using dispatch_strategy = dispatch_strategy::flat_fold;
};

目前支持两种分发策略:

策略 说明

flat_fold (默认)

生成内联比较分支的扁平折叠.
所有转移逻辑对优化器可见.
通常带来最优的运行期性能与可执行文件大小.

function_pointer_array

生成函数指针数组.
保证 O(1) 分发, 但函数指针无法内联.
通常导致较差的运行期性能和更大的可执行文件, 但编译时间略优.

favor_compile_time

该策略以牺牲运行期速度为代价改善编译时间. 它惰性评估各转移, 并在运行期初始化分发表. 与 back 中的对应策略一样, 它不支持事件层级和 Kleene 事件.

事件进入事件处理时会被包装进 std::any. 分发表保存在一个哈希映射中: 以每个事件的类型索引为键, 以指向匹配转移的函数指针数组为值.

采用该策略, 可以把状态机的实现隐藏在接口之后. 参见state machine interface example.

也可以借助一个预处理宏, 把状态机的编译分散到多个翻译单元中进行. 由于后端对大多数状态机的编译都应当非常快, 这是一个可选启用 (opt-in) 的特性:

  • 先定义 BOOST_MSM_BACKMP11_MANUAL_GENERATION 再包含 msm/backmp11/favor_compile_time.hpp

  • 然后生成状态机后端, 所用宏为 BOOST_MSM_BACKMP11_GENERATE_STATE_MACHINE(<sm_type>)

扩展

可以通过继承 state_machine 模板, 并把扩展后的类传递给 Derived 模板参数来扩展状态机.

历史

在 backmp11 中, 历史策略定义在前端而非后端. 在前端定义可确保一个状态机配置能够被层次状态机的多个后端共享.

/// No history (default).
struct no_history {};

/// Shallow history.
/// For deep history use this policy in all contained state machines.
template <typename... Events>
struct shallow_history {};

/// Shallow history for all entry events.
/// For deep history use this policy in all contained state machines.
struct always_shallow_history {};

在状态机定义中配置历史.

struct MyStateMachine_ : public msm::front::state_machine_def<MyStateMachine_>
{
    using history = msm::front::shallow_history<MyEntryEvent>;
    ...
};

启动与停止

新构造的状态机在尚未启动之前不接受事件. 其自身状态由 machine_state 枚举表示, 可以用 machine_state state_machine::get_machine_state() 查询.

void state_machine::start() 方法以 starting 事件激活状态机: 先调用状态机前端的入口动作, 再调用初始状态的入口动作. 重载 void state_machine::start(const auto& initial_event) 允许传入自定义的启动事件.

void state_machine::stop() 方法以 stopping 事件停用状态机: 先调用活动状态的出口动作, 再调用状态机前端的出口动作. 类似的重载 void state_machine::stop(const auto& final_event) 可用于传入自定义的停止事件.

在已启动的状态机上调用 start(…​), 或在未启动的状态机上调用 stop(…​), 均无效果. 注意, 状态机必须已准备好处理事件才能停止.

处理事件

使用 process_result state_machine::process_event(const Event&) 在状态机空闲时触发事件处理. process_result 枚举返回处理尝试的结果.

可以使用 void state_machine::enqueue_event(const Event&) 在动作中把事件入队到事件池以便后续处理. 入队的事件会在当前事件处理完成后立即得到处理. 如果在状态机空闲时入队了事件, 可以用 size_t process_event_pool(size_t max_events = SIZE_MAX) 显式请求状态机处理其事件池中的事件.

后端通过前端的 deferred_events 状态属性支持事件延迟. 延迟事件按其被延迟的顺序求值, 确保 FIFO 处理语义. 它们存储在被请求处理该事件的状态机的事件池中. 在层次状态机中, 这通常是根状态机, 此时所有子状态机都能在分发时收到该事件. 正交区域中的事件延迟行为与 UML 标准描述一致: 只要有一个活动区域决定延迟某事件, 该事件就对所有区域保持延迟.

条件延迟 是 backmp11 对 deferred_events 属性的独有扩展. 通过在状态中定义 bool is_event_deferred(…​) 方法, 可以使延迟成为有条件的:

struct MyState : front::state<>
{
    using deferred_events = mp11::mp_list<MyEvent>;

    template <typename Fsm>
    bool is_event_deferred(const MyEvent& event, Fsm& fsm) const
    {
        // Return true or false to decide
        // whether the event shall be deferred.
        ...
    }
};

也可以在转移中使用 front::Defer 动作来延迟事件. 虽然该机制为事件延迟提供了额外的灵活性, 但它有以下限制:

  • 它使用 Fsm 参数传入的状态机的事件池——如果它不是层次状态机中的根状态机, 层级中更上层的状态机就无法收到该事件.

  • 由动作延迟的事件会先被分发求值, 然后放回事件池. 这带来额外的运行期开销, 并使延迟事件无法按 FIFO 顺序处理.

  • 在正交区域中, 每个区域独立求值该事件, 但各区域共享所属状态机的事件池. 这会导致同一事件被多次分发.

状态机还包含 void state_machine::defer_event(const Event&) 方法, 它把处理推迟到下次调用 process_event(…​) 或 process_event_pool(…​) 时.

检查活动状态

使用 bool state_machine::is_state_active() 检查活动状态:

template <typename State>
bool state_machine::is_state_active() const;

如果该状态类型在层次状态机中出现多次, 只要其中任一状态处于活动状态, 方法就返回 true.

访问状态

使用 void state_machine::visit(Visitor&&) 以访问者仿函数遍历所有当前活动状态. 在层次状态机中, 子状态机会被递归访问.

访问函数可以用 visit_mode 模板参数定制:

  • 仅活动状态或全部状态

  • 非递归或递归

访问者仿函数必须支持以状态机中所有现存状态类型被调用.

template <typename State>
void operator()(State& state);

visitor example 中演示了访问者的用法.

异常

后端是异常中立的; 处理期间抛出的异常会传播给调用者. 它提供基本异常保证: 处理会在执行中途中止, 但状态机仍处于有效状态. 如果处理步骤涉及状态切换, 那么一旦源状态的出口动作执行完毕, 活动状态就会切换到目标状态. 若需了解事件处理期间被中止的状态机活动的确切细节, 请参见运行至完成算法.

反射与序列化

state_machine 通过 void reflect(…​) 自由函数和访问者模式以递归方式提供对其所有成员的访问:

/**
 * @brief Reflects on a state_machine's members with a visitor.
 *
 * The visitor has to implement the methods:
 * - visit_front_end(auto&& front_end)
 * - visit_front_end(auto&& front_end, auto&& reflect)
 * - visit_member(const char* key, auto&& member)
 * - visit_state(size_t state_id, auto&& state)
 * - visit_state(size_t state_id, auto&& state, auto&& reflect)
 */
template <typename FrontEnd, typename Config, typename Derived,
          typename Visitor>
void reflect(state_machine<FrontEnd, Config, Derived>& sm,
             Visitor&& visitor);

不要对 visit 方法的调用顺序和参数细节做任何假设. 反射 API 暴露的是状态机的内部成员, 这些成员可能发生变化.

前端与状态的 visit 方法提供两个重载. 第一个在待访问对象没有反射时被调用, 第二个提供一个 reflect 仿函数参数, 用于把反射更深入地触发到对象内部. 要为前端或状态设置反射, 可以实现 reflect(…​) 成员函数, 或者实现自由函数 (由于 ADL 限制, 在 MSVC 上必须使用成员函数).

struct MyState : front::state<>
{
    // Reflect with a member function.
    template <typename Visitor>
    void reflect(Visitor&& visitor)
    {
        visitor.visit_member("my_member", my_member);
    }
    template <typename Visitor>
    void reflect(Visitor&& visitor) const
    {
        visitor.visit_member("my_member", my_member);
    }

    uint32_t my_member{};
};

// Or reflect with a free function.
template <typename Visitor>
void reflect(MyState& my_state, Visitor&& visitor)
{
    visitor.visit_member("my_member", my_state.my_member);
}
template <typename Visitor>
void reflect(const MyState& my_state, Visitor&& visitor)
{
    visitor.visit_member("my_member", my_state.my_member);
}

反射 API 可用于内省类用例; 最突出的就是状态机的序列化. backmp11 开箱即支持三个序列化库:

  • Boost.Serialization

  • Boost.JSON

  • nlohmann/json

每个序列化库在 boost/msm/backmp11/serialization 下都有对应的头文件, 其中包含序列化器代码. 序列化器要求所有含非静态成员的对象都可序列化, 这可以通过实现 backmp11 的 reflect(…​) API 或库特定的序列化方法来达成. 建议实现 backmp11 后端的反射 API, 因为该机制是通用的, 支持所有序列化库.

把状态机序列化为 JSON 提供了一种以人类可读格式检查它的好方法. 使用 Boost.JSON 和 nlohmann/json 序列化时, 只需包含对应的头文件. 使用 Boost.Serialization 时, 还需要为 (根) 状态机提供一个自由的 serialize(…​) 方法, 或在后端中实现 serialize(…​) 成员. 所有库的用法都在 serialization examples 中演示.

运行至完成

后端使用以下运行至完成算法处理事件:

  • 如果状态机尚未准备好处理该事件, 则直接返回. 已启动且不在处理中即为就绪

  • 如果某个活动状态延迟该事件, 则将其推入事件池末尾并返回

  • 把事件分发到每个区域的转移表, 顺序遵循前端 initial_state

  • 对每一条匹配活动状态与该事件的转移 (按前端转移表的相反顺序):

    • 如果没有守卫或守卫返回 true, 则执行该转移, 否则跳过

    • 如果该转移有目标状态, 调用源状态的出口动作, 然后把活动状态切换为目标状态

    • 如果该转移有转移动作, 调用它

    • 如果该转移有目标状态, 调用目标状态的入口动作

    • 如果目标状态存在完成转移, 则把其执行推入事件池的开头

    • 将该事件视为已处理, 并结束转移执行循环

  • 如果事件尚未被处理且状态机有内部转移表, 则同样把事件分发到内部转移表. 对每一条匹配该事件的内部转移 (按前端内部转移表的相反顺序):

    • 如果没有守卫或守卫返回 true, 则执行该转移, 否则跳过

    • 如果该转移有转移动作, 调用它

    • 将该事件视为已处理, 并结束转移执行循环

  • 如果事件仍未被处理, 调用前端的 no_transition(…​) 处理器

  • 如果状态机有事件池, 开始处理它. 对事件池中的每个事件:

    • 检查它是否已就绪可处理. 就绪的条件是:

      • 它未在同一处理序列中被延迟, 并且

      • 没有活动状态延迟该事件

    • 如果就绪, 处理它并从事件池开头重新开始 (新的活动状态配置可能使之前被延迟的事件得以处理)

    • 当状态机到达事件池末尾时返回

对比 back

backmp11 后端应与使用 back 后端的现有代码基本兼容:

  • 对状态机, 用 backmp11::state_machine 替代 back::state_machine

  • 配置编译策略等, 使用 backmp11::state_machine_config struct

  • 调整在 backmp11 中已变更的公共 API 调用, 或通过继承 state_machine 类编写适配器

以下各节进一步说明 backmp11 与 back 之间的差异.

公共 API: state_machine

以下适配器伪代码说明与 back::state_machine API 的主要差异 (见 full code example).

class back_adapter
{
    template <typename Event>
    back::HandledEnum process_event(const Event& event)
    {
        if (get_machine_state() == machine_state::processing)
        {
            enqueue_event(event);
            return back::HANDLED_DEFERRED;
        }
        else
        {
            try
            {
                return static_cast<back::HandledEnum>(
                    Base::process_event(event));
            }
            catch (std::exception& e)
            {
                exception_caught(event, *this, e);
                return back::HANDLED_FALSE;
            }
        }
    }

    auto& get_message_queue()
    {
        return this->get_event_pool().events;
    }

    size_t get_message_queue_size() const
    {
        return this->get_event_pool().events.size();
    }

    void execute_queued_events()
    {
        this->process_event_pool();
    }

    void execute_single_queued_event()
    {
        this->process_event_pool(1);
    }

    auto& get_deferred_queue()
    {
        return this->get_event_pool().events;
    }

    void clear_deferred_queue()
    {
        this->get_event_pool().events.clear();
    }
};

Kleene 事件

为减少所需的头文件包含, backmp11 使用 std::any 而非 boost::any 来定义 Kleene 事件. 若想选用 boost::any 支持, 请包含 boost/msm/event_traits.h.

此外, 后端转发 Kleene 事件时不会把它们转换为 std::any 或 boost:any. 动作和守卫收到的是原始事件.

移除的特性

中断状态

不支持, 因为中断状态的求值需要访问者来判断某个中断状态是否活动. 一旦定义了中断状态, 这会显著增加状态机的编译期和运行期开销. 如有需要, 可以用状态机扩展来模拟中断状态特性 (见 back 适配器示例).

或者, 你也可以扩展状态机 API 来实现自己的中断机制并按需定制. 参见 interruptible state machine example, 它允许从任何状态发起中断, 并把事件入队以便稍后处理而不是丢弃.

构造函数与 set_states(…​) 方法中的状态初始化

曾有一个构造函数被用于多种不同用例, 这带来一些问题: 一方面, 某些参数会被立即转发给前端的构造函数; 另一方面, 构造函数用流运算符把另一些参数识别为状态, 并把它们复制进状态机. 后者的语法本就相当少见, 而当两者同时进行时, 语法就变得难以理解; 若层次子状态机中的状态也以这种方式初始化, 就更甚了.

为了使构造函数的 API 更简单、更少歧义, 它只支持与 state_machine 配置相关的参数. 状态机的前端必须可默认构造. set_states(…​) API 也已被移除. 如需设置状态, 仍可做到 (方式更繁琐, 但也更直接、更明确): 通过 get_state<State>() 获取目标状态的引用, 然后为其赋一个新的状态对象.

get_state_by_id(…​) 方法

如果需要按 ID 获取状态, 可以用访问者 API 自行实现该功能. state_machine 提供了一个方法, 支持在访问者中获取状态的 ID:

template <typename State>
static constexpr uint16_t state_machine::get_state_id(const State&);

指针重载: get_state<…​>()

类似于 STL 中 tuple 的 std::get<…​>(…​) 方法, get_state<T>() 唯一合理的模板参数是 T, 即返回 T& 的那个. T* 的重载已被移除; T& 的重载虽仍受支持但不建议使用. 如果需要按地址获取状态, 请先按引用取得状态, 再使用取地址运算符.

eUML 前端支持

对 EUML 的支持需要包含 Boost.Proto 头文件并应用 C++03 变参模板模拟, 因而导致更长的编译时间. 如果想使用类 UML 语法, 可以考虑使用新的 PUML 前端.

fsm 检查与区域查找支持

这两个特性的实现依赖 mpl_graph, 导致编译时间较长.

sm_ptr 支持

functor 前端不需要它, 且它此前已被弃用; 因此已在 backmp11 中移除.

弃用信息

下表列出特性与 API 的弃用情况以及其他附带上下文的变更.

特性 弃用 / 移除 说明

事件容器的公共访问

1.90 / 1.91

事件容器可通过公共 API 访问和操作. 在库代码之外操作该容器可能导致未定义行为.

变更: 访问事件容器的公共 API 将改为 protected. 如有需要, 用户可以继承 state_machine 来访问事件容器, 但不保证功能正确性与 API 一致性.

transition_owner 重命名为 local_transition_owner

1.91 / 1.92

Fsm 参数的默认设置名为 transition_owner, 本意是反映与 back 相同的行为. 然而 transition_owner 的行为确实与 back 不同, 而且此前的实现也不正确.

变更: 行为将被修正为与 back 一致, 默认设置将在 1.91 中更名为 local_transition_owner. 原设置名 transition_owner 将在 1.91 中弃用, 并在 1.92 中移除.

移除处理排队事件的 API

1.91 / 1.92

排队事件与延迟事件的事件容器已合并为单一事件池. 处理排队事件的 API 已过时.

变更: API process_queued_events 和 process_single_queued_event 将被移除.

对旧 API 的调用可按如下方式替换:

  • 处理事件池中的单个事件, 使用 process_event_pool(1)

  • 处理事件池中的所有事件, 使用 process_event_pool()

移除 process_event API 中的自动入队

1.91 / 1.92

当状态机已在处理事件时, API process_event 会自动把事件入队. 这要求为每种事件类型实例化 enqueue_event, 尽管大多数实例化从未被调用. 只有在动作中调用 process_event 时才需要它们.

变更: 在事件处理期间调用 API process_event 时, 它将拒绝该事件并返回 HANDLED_FALSE, 而不是自动入队.

动作中对 process_event 的调用必须替换为 enqueue_event.

移除活动状态切换策略

1.92 / 1.93

UML 规范描述了转移中活动状态切换应发生的准确时点. 前端当前的设置 active_state_switch_policy 允许选择规范未定义的取值. 其默认值 "after target entry" 不符合 UML.

变更: 活动状态切换策略将设为 "after source exit", 以符合 UML 规范.

该设置将在 1.93 中移除.
