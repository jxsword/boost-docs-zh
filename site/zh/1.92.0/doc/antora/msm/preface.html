前言

MSM 是一个让你轻松快速地定义高性能状态机的库. 说到这里, 通常很快会出现两个主要问题, 请允许我先行作答.

我什么时候需要状态机?

比你想象的更频繁. 很多时候, 人们在不经意间就已非正式地定义了一个状态机. 例如, 在类中声明某个布尔属性, 比如用来记住某个任务已经完成. 后来这个布尔值实际上需要第三个取值, 于是它变成了 int. 几周后, 又需要第二个属性. 然后是第三个. 很快, 你就发现自己在写:

void incoming_data(data)
{
    if (data = packet_3 && flag1 = work_done && flag2 > step3) ...
}

这看起来开始像是在处理事件 (包含在数据中), 以判断对象生命的某个阶段是否已经完成 (但很丑陋).

这可能是一个协议定义, 而它是状态机的一个常见用例. 另一个常见用例是用户界面. 用户交互所处的阶段决定某个按钮是否激活、某个功能是否可用, 等等.

但只要开始留意, 用例远不止这些. 实际上, 有一整套模型驱动开发方法, 即可执行 UML (http://en.wikipedia.org/wiki/Executable_UML), 它用状态机规定其完整的动态行为. 在可执行 UML 的世界里, 类图、状态机图和一种动作语言就是你绝对需要的全部.

又一个状态机库? 有什么用?

没错, 状态机库确实很多. 这本身就说明, 如果你一个都没用过, 你可能错过了些什么. 为什么要用这一个呢? 遗憾的是, 在寻找一个好的状态机库时, 你通常很快就会撞上以下一个或几个障碍:

  • 速度: “状态机很慢”通常是你最先听到的批评. 它往往是拒绝使用任何库、转而求助于肮脏的手写实现的借口 (当然, 我不是说你的实现肮脏, 我说的是其他开发者的). MSM 让这一通常站不住脚的借口失去立足点, 因为它快得惊人. 大多数手写实现都会被 MSM 击败.

  • 易用性: 好论点. 如果你用过其他库, 你大概是对的. 许多状态机定义看起来都会类似这样:

state s1 = new State;     // a state
state s2 = new State;     // another state
event e = new Event;      // event
s1->addTransition(e, s2); // transition s1 -> s2

转移越多, 可读性就越差. 很久以前, Java 还没有如今这么盛行, 许多电子系统都用由简单转移表定义的状态机构建. 你可以轻松看清整个结构, 并立即发现是否漏掉了一些转移. 随着新的面向对象技术的兴起, 这种易用性不复存在. MSM 把转移表还给你, 并把噪音减到最少.

  • 表现力: MSM 提供多种前端, 并不断尝试改进状态机定义技术. 例如, 你可以用 eUML (MSM 的前端之一) 把一条转移定义为 state1 = state2 + event [condition] / action.

    这不仅仅是语法糖. 这种形式化、可读的结构让与待构建软件的领域专家交流变得容易. 让领域专家看懂你的代码将大大减少缺陷数量.

  • 模型驱动开发: 模型驱动开发的一个常见难点是完成往返 (从模型生成代码, 再从代码生成模型) 的复杂性. 原因在于, 如果状态机结构连你读起来都困难, 那么你的解析工具多半也不好过. MSM 的语法有望为工具作者提供帮助.

  • 特性: 大多数开发者只使用内容丰富的 UML 标准中的 20%. 遗憾的是, 每个人用的那 20% 从不相同. 因此, 你很可能需要标准中尚未实现的某个东西. MSM 提供了标准中的很大一部分, 还在不断补充.

创立初衷

让我们从一个取自《C++ Template Metaprogramming》一书的例子开始:

class player : public state_machine<player>
{
  // The list of FSM states enum states { Empty, Open, Stopped, Playing, Paused , initial_state = Empty };

  // transition actions
  void start_playback(play const&) { std::cout << "player::start_playback\n"; }
  void open_drawer(open_close const&) { std::cout << "player::open_drawer\n"; }
  // more transition actions
  ...
  typedef player p; // makes transition table cleaner
  struct transition_table : mpl::vector11<
  //     Start     Event        Target    Action
  //   +---------+------------+---------+---------------------------+
    row< Stopped , play       , Playing , &p::start_playback        >,
    row< Stopped , open_close , Open    , &::open_drawer            >,
  //   +---------+------------+---------+---------------------------+
    row< Open    , open_close , Empty   , &p::close_drawer          >,
  //   +---------+------------+---------+---------------------------+
    row< Empty   , open_close , Open    , &p::open_drawer           >,
    row< Empty   , cd_detected, Stopped , &p::store_cd_info         >,
  //   +---------+------------+---------+---------------------------+
    row< Playing , stop       , Stopped , &p::stop_playback         >,
    row< Playing , pause      , Paused  , &p::pause_playback        >,
    row< Playing , open_close , Open    , &p::stop_and_open         >,
  //   +---------+------------+---------+---------------------------+
    row< Paused  , play       , Playing , &p::resume_playback       >,
    row< Paused  , stop       , Stopped , &p::stop_playback         >,
    row< Paused  , open_close , Open    , &p::stop_and_open         >
  //   +---------+------------+-----------+-------------------------+
  > {};
  // Replaces the default no-transition response.
  template <class Event>
  int no_transition(int state, Event const& e)
  {
    std::cout << "no transition from state " << state << " on event " << typeid(e).name() << std::endl;
    return state;
  }
};

这个例子是 MSM 背后理念的基础: 一种基于转移表、语法噪音尽可能少的描述性与表现性兼备的语言, 同时尽可能多地提供 UML 2.0 标准的特性. MSM 还提供了几种具有不同取舍的表现性良好的状态机定义语法.

让我们不再等待, 希望你喜欢 MSM, 并从中获得乐趣!
