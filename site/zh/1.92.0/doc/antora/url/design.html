设计原理

本节记录 Boost.URL 设计决策背后、仅从 API 本身难以看出的设计理由. 关于库目标与功能的总体概述, 参见引言.

字符类型

Boost.URL 使用 char 作为其字符类型. 本库不提供以字符类型为参数的类模板 (如 basic_url_view<CharT>) .

按照 RFC 3986 的定义, URL 是 ASCII 八位组的序列. 实践中, URL 总是作为 char 字符串处理: 出现在 HTTP 头、JSON、配置文件以及各大主流编程语言的 URL 库中. 宽字符类型 (wchar_t、char16_t、char32_t) 在任何现实场景中都不用于 URL, 因此支持它们只会增加复杂度而缺乏实际收益.

这也意味着本库不提供 char8_t (C20) 实例化. 虽然 `char8_t` 对 ASCII/UTF-8 文本是可移植正确的, 但它在 C 生态中的采用仍然有限: 标准库在 I/O 或格式化方面对它的支持尚不完整, 也没有主流框架在公开 API 中采用它. 使用 char 意味着 Boost.URL 可以直接与 std::string、std::string_view、字符串字面量以及生态系统的其余部分互操作, 无需转换.

EBCDIC

C++ 标准并不要求 char 使用与 ASCII 兼容的编码. 在 EBCDIC 平台 (主要是 IBM z/OS) 上, 字符字面量 '/' 的值不是 0x2F, 因此将 char 值与 ASCII 常量比较的 URL 解析器会出现故障.

实际上, 这对 Boost.URL 而言并不是问题:

  • z/OS 是唯一还需要在 C++ 编译中考虑 EBCDIC 的平台.

  • z/OS 的 C++ 编译器支持一种 ASCII 编译模式 (-qascii 或 -fzos-le-char-mode=ascii) , 使 char 字面量使用 ASCII 值. 该模式正是为假定 ASCII 的开源软件而设.

  • 在 z/OS 上处理 URL 和 HTTP 的实际 C++ 库 (如 cpp-httplib 和 DuckDB) 都使用这种 ASCII 模式, 而不是增加 EBCDIC 转码.

  • z/OS 上的 REST 与 Web 服务生态几乎完全基于 Java. 目前没有证据表明存在以 EBCDIC char 编码解析 RFC 3986 URI 的 C++ 代码.

  • WG21 (C++ 标准委员会) 也在朝这个方向推进: P3688 (ASCII 字符工具) 提出基于 char 的函数, 无论字面量编码如何都将输入视为 ASCII.

在不使用 ASCII 模式的 EBCDIC 平台上, char8_t 提供了一种可移植的正确替代方案, 因为它保证使用 UTF-8 (ASCII 的超集) . 未来可以通过支持 char8_t 构造函数重载 (作用于基于 char 的具体类型) 来解决这个问题, 而无需引入模板, 因为 char 与 char8_t 都是单字节类型, 对 ASCII 内容而言二者之间的转换非常简单.

默认不进行动态分配

本库的设计使得大多数操作无需动态内存分配.

url_view 不保留底层字符串缓冲区的所有权, 也不分配内存. 与 string_view 类似, 它直接引用原始字符串. 只要原始字符串的内容未被修改, 构造出的 URL 视图就始终包含以正确序列化形式呈现的有效 URL.

访问器函数返回引用底层 URL 子字符串与子范围的视图. 通过在内部引用 URL 字符串的相关部分, 组件可以表示百分号解码后的字符串, 并在无需分配的情况下转换为其他类型. decode_view 及其解码函数不执行任何内存分配, 除非结果需要存入另一个容器. 对象可以被回收以复用其内存, 把分配推迟到应用程序真正需要时进行.

这使得本库适用于对性能敏感的网络程序和嵌入式设备.

错误处理

本库以错误码而非异常作为主要的错误报告机制. 如果输入不符合 URL 文法, 将通过 result 报告错误码而不是抛出异常. 这使得本库可以用于禁用异常的环境 (-fno-exceptions) , 这种环境会被自动检测.

URL 有效性不变式

对 url 的所有修改都会使其处于有效状态. url 不可能持有语法非法的文本. 所有修改函数都会对输入进行验证: 试图把方案或端口设置为无效字符串会抛出异常, 而其他组件则会按需自动进行百分号编码. 所有非 const 操作都提供强异常安全保证.

不支持 IRI

本库不处理 国际化资源标识符 (IRI) . IRI 与 URL 不同: 它来自 Unicode 字符串而非低 ASCII 字符串, 由单独的规范定义.
