Boost.Container 力求完全符合 C++11, 仅保留有充分理由的偏离, 并尽可能为 C++03 向后移植. 显然, 这种一致性仍在完善中, 因此本节说明已实现了哪些 C++ 特性, 以及其中哪些已向后移植到较早的标准符合编译器.

移动与就地构造

对于支持右值引用的编译器, 以及那些使用 Boost.Move 右值引用模拟的 C++03 类型, Boost.Container 支持所有与移动语义相关的 C++11 特性: 容器可移动, 对 value_type 的要求即 C++11 容器所规定的要求.

对于支持变参模板的编译器, Boost.Container 支持 C++11 的就地构造插入 (emplace, ...) 函数. 对于不支持变参模板的编译器, Boost.Container 使用预处理器创建一组最多有限个参数的重载.

有状态分配器与使用分配器协议 (uses-allocator protocol)

C++03 对有状态分配器并不友好. 出于容器对象的紧凑性和简单性, 它不要求容器支持有状态分配器: 分配器对象无需存储在容器对象中. 无法存储带状态的分配器, 例如持有指向分配源的指针的分配器. C++03 允许实现者假定同一类型的两个分配器总是比较相等 (这意味着一个分配器对象分配的内存可以由同类型的另一个实例释放), 并且交换容器时不交换分配器.

C++11 通过以下方式进一步改进有状态分配器支持:

  • std::allocator_traits. std::allocator_traits 是容器与分配器之间的协议, 分配器编写者可以按照下列要求自定义其行为 (容器应在移动构造、swap 等操作中传播分配器吗?): allocator_traits 的要求. Boost.Container 不仅以 C++11 支持该模型, 还将其向后移植到 C++03, 通过 boost::container::allocator_traits 实现, 其中包含一些 C++17 变更. 该类为 C++03 编译器提供了一些变通方法, 以获得与 std::allocator_traits 相同的分配器保证.
  • The uses-allocator protocol 允许类型声明它们可以搭配分配器工作, 即使它们通过不知晓分配器的中间代码构造. Boost.Container 实现了特征 (trait) uses_allocator 并实现了受 C++20 新增内容启发的工具: uninitialized_construct_using_allocator 和 make_obj_using_allocator.

作用域分配器

C++11 通过引入 std::scoped_allocator_adaptor 类模板. scoped_allocator_adaptor 以一个外层分配器和零个或多个内层分配器进行实例化.

作用域分配器是一种以受控方式将分配器状态自动传播到容器子对象的机制. 若仅用一个分配器类型实例化, 内层分配器就成为 scoped_allocator_adaptor 本身, 从而为容器及容器内的每个元素使用相同的分配器资源, 并且若元素本身也是容器, 则递归地用于其每个元素. 若用多于一个分配器实例化, 第一个分配器是供容器使用的外层分配器, 第二个分配器传递给容器元素的构造函数, 并且若元素本身也是容器, 第三个分配器传递给元素的元素, 以此类推.

Boost.Container 实现了自己的 scoped_allocator_adaptor 类, 并且 也将此特性向后移植到 C++03 编译器.

关联容器中的插入提示与等价键元素插入顺序的保持

LWG Issue #233 纠正了 C++98 中的一个缺陷, 并规定了等价键应如何插入关联容器. Boost.Container 实现了 N1780 Comments on LWG issue 233: Insertion hints in associative containers 中规定的 C++11 变更:

  • a_eq.insert(t): 若 a_eq 中存在包含与 t 等价的元素的范围, 则 t 被插入到该范围的末尾.
  • a_eq.insert(p,t): t 被插入到尽可能接近紧邻 p 之前的位置.

初始化列表

在实现该特性的编译器中, Boost.Container 支持从初始化列表进行初始化、赋值和插入.

空前向迭代器

Boost.Container 实现了 C++14 Null Forward Iterators, 这意味着值初始化的迭代器可以与其他同类型的值初始化迭代器进行比较且比较相等. 值初始化的迭代器的行为如同指向同一空序列的末尾之后 (示例取自 N3644):

vector<int> v = { ... };
auto ni = vector<int>::iterator();
auto nd = vector<double>::iterator();
ni == ni; // True.
nd != nd; // False.
v.begin() == ni; // ??? (likely false in practice).
v.end() == ni;   // ??? (likely false in practice).
ni == nd; // Won't compile.

多态内存资源

文档 C++ Extensions for Library Fundamentals (final draft) 包含提供分配器类型擦除和运行期多态的类. 正如该提案的作者 Pablo Halpern 在论文 (N3916 Polymorphic Memory Resources (r2)) 中所解释的:

“C++ 中有效内存管理的一个重大障碍是, 无法在非泛型上下文中使用分配器. 在大型软件系统中, 应用程序的大部分由只编译一次却链接多次的非泛型过程式或面向对象代码组成.”

“然而, C++ 中的分配器历来仅依赖编译期多态, 因此不适合用于在分别编译的模块之间通过接口传递的词汇类型, 因为分配器类型必然影响使用它的对象的类型. 本提案建立在 C++11 对分配器的改进之上, 描述了一组运行期多态内存资源设施, 它们可与现有的编译期多态分配器互操作.”

Fundamentals TS 中的大多数工具已被合并到 C++17, 但 Boost.Container 为 C++03, C++11 和 C++14 编译器提供了它们.

Boost.Container 几乎实现了该提案的所有类, 位于命名空间 boost::container::pmr. 共分两组,

  • 仅头文件的工具 (不需要单独编译的库):
    • memory_resource.
    • resource_adaptor.
  • 需要单独编译库的工具:
    • polymorphic_allocator.
    • monotonic_buffer_resource.
    • unsynchronized_pool_resource.
    • synchronized_pool_resource.
    • 全局资源函数: get_default_resource/ set_default_resource/ new_delete_resource/ null_memory_resource
    • 使用多态分配器的 boost 容器别名 (如 pmr::vector 等)

Boost.Container 的多态资源库可用于 C++03 容器, 并且当 Library Fundamentals 规范所要求的 C++11 特性不可用时, 提供一些替代工具.

最后, Boost.Container 的多态资源库还在较旧的平台上包含对超对齐类型 (C++17 引入) 的动态内存分配支持.

让我们回顾 N3916 中给出的使用示例, 并了解如何使用 Boost.Container 实现它: 假设我们正在处理一系列购物清单, 其中购物清单是字符串的容器, 并将它们存储在购物清单的集合 (一个 list) 中. 每个正在处理的购物清单使用一段有限数量的内存, 且只需存在很短时间, 而购物清单集合使用无限数量的内存, 且将存在更长时间. 为提高效率, 我们可以为临时购物清单使用基于有限缓冲区的、时间上更高效的内存分配器.

让我们看看如何定义 ShoppingList 以支持能够从不同底层机制分配内存的多态内存资源. 最重要的细节是:

  • 它应声明支持定义了 allocator_type typedef 的分配器. 该 allocator_type 的类型将为 memory_resource *, 它是多态资源的基类.
  • 它必须定义接受分配器作为参数的构造函数. 可以通过两种方式实现:
    • ShoppingList 具有以 memory_resource* 作为最后一个参数的构造函数.
    • ShoppingList 具有以 allocator_arg_t 作为第一个参数、memory_resource* 作为第二个参数的构造函数.
//ShoppingList.hpp
#include <boost/container/pmr/vector.hpp>
#include <boost/container/pmr/string.hpp>

class ShoppingList
{
   // A vector of strings using polymorphic allocators. Every element
   // of the vector will use the same allocator as the vector itself.
   boost::container::pmr::vector_of
      <boost::container::pmr::string>::type m_strvec;
   //Alternatively in compilers that support template aliases:
   //    boost::container::pmr::vector<boost::container::pmr::string> m_strvec;
   public:

   // This makes uses_allocator<ShoppingList, memory_resource*>::value true
   typedef boost::container::pmr::memory_resource* allocator_type;

   // If the allocator is not specified, "m_strvec" uses pmr::get_default_resource().
   explicit ShoppingList(allocator_type alloc = 0)
      : m_strvec(alloc) {}

   // Copy constructor. As allocator is not specified,
   // "m_strvec" uses pmr::get_default_resource().
   ShoppingList(const ShoppingList& other)
      : m_strvec(other.m_strvec) {}

   // Copy construct using the given memory_resource.
   ShoppingList(const ShoppingList& other, allocator_type a)
      : m_strvec(other.m_strvec, a) {}

   allocator_type get_allocator() const
   { return m_strvec.get_allocator().resource(); }

   void add_item(const char *item)
   { m_strvec.emplace_back(item); }

   //...
};

然而, 这种时间高效的分配器不适合存在时间较长的购物清单集合. 本示例展示如何使用通用分配器, 将那些使用时间高效分配器的临时购物清单用于填充长寿命的购物清单集合 —— 若没有多态分配器, 这将非常困难.

在 Boost.Container 中, 对于时间高效的分配, 我们可以使用 monotonic_buffer_resource, 提供一个外部缓冲区, 该缓冲区将被使用直到耗尽. 在默认配置中, 当缓冲区耗尽时, 将改用默认内存资源.

#include "ShoppingList.hpp"
#include <cassert>
#include <boost/container/pmr/list.hpp>
#include <boost/container/pmr/monotonic_buffer_resource.hpp>

void processShoppingList(const ShoppingList&)
{  /**/   }

int main()
{
   using namespace boost::container;
   //All memory needed by folder and its contained objects will
   //be allocated from the default memory resource (usually new/delete) 
   pmr::list_of<ShoppingList>::type folder; // Default allocator resource
   //Alternatively in compilers that support template aliases:
   //    boost::container::pmr::list<ShoppingList> folder;
   {
      char buffer[1024];
      pmr::monotonic_buffer_resource buf_rsrc(&buffer, 1024);

      //All memory needed by temporaryShoppingList will be allocated
      //from the local buffer (speeds up "processShoppingList")
      ShoppingList temporaryShoppingList(&buf_rsrc);
      assert(&buf_rsrc == temporaryShoppingList.get_allocator());

      //list nodes, and strings "salt" and "pepper" will be allocated
      //in the stack thanks to "monotonic_buffer_resource".
      temporaryShoppingList.add_item("salt");
      temporaryShoppingList.add_item("pepper");
      //...

      //All modifications and additions to "temporaryShoppingList"
      //will use memory from "buffer" until it's exhausted.
      processShoppingList(temporaryShoppingList);

      //Processing done, now insert it in "folder",
      //which uses the default memory resource
      folder.push_back(temporaryShoppingList);
      assert(pmr::get_default_resource() == folder.back().get_allocator());
      //temporaryShoppingList, buf_rsrc, and buffer go out of scope
   }
   return 0;
}

注意, folder 中的购物清单使用默认分配器资源, 而购物清单 temporaryShoppingList 使用短寿命但非常快的 buf_rsrc. 尽管使用不同的分配器, 你仍可将 temporaryShoppingList 插入 folder, 因为它们具有相同的 ShoppingList 类型. 另外, ShoppingList 直接使用 memory_resource, 而 pmr::list, pmr::vector 和 pmr::string 都使用 polymorphic_allocator.

传递给 ShoppingList 构造函数的资源会传播到 vector 以及该 ShoppingList 中的每个字符串. 类似地, 用于构造 folder 的资源会传播到插入 list 的 ShoppingList 的构造函数 (以及这些 ShoppingLists 中的字符串). polymorphic_allocator 模板的设计几乎可与指向 memory_resource 的指针互换, 从而产生一个 桥接(介于分配器的模板策略风格与多态基类风格之间).

本示例实际上展示了, 即使在 C++03 编译器中, 使用 Boost.Container 编写支持类型擦除分配器的类有多么容易.

forward_list<T>

Boost.Container 尚未提供 C++11 的 forward_list 容器, 但未来的版本中将会提供.

vector 与 std::vector 的异常保证

vector 不支持 std::vector 在 insert, push_back, emplace, emplace_back, resize, reserve 或 shrink_to_fit 等函数中给出的强异常保证, 对可复制类和不抛出移动的类均是如此. 在 C++11 中, move_if_noexcept 用于在结合 C++11 移动语义的同时保持 C++03 的异常安全保证. 这种强异常保证降低了可复制和抛出移动类型的插入性能, 当使用上述成员将这类类型插入 vector 时, 会将移动降级为复制.

这种强异常保证还排除了使用某些原地重分配的可能性, 而这些重分配可进一步提升 vector 的插入性能. 更多有关这些优化的信息参见 扩展分配器 (Extended Allocators).

vector 总是使用移动构造函数/赋值运算符来重新排列 vector 中的元素, 并在分配器支持时使用内存扩展机制, 同时仅提供基本的安全保证. 它以异常保证换取更高的性能.

可被修改的 const 引用参数

多个容器操作使用在函数执行期间可能被修改的 const 引用参数. LWG Issue 526 (标准中的函数修改其参数是否未定义?) 讨论了这些操作:

//Given std::vector<int> v
v.insert(v.begin(), v[2]);
//v[2] can be changed by moving elements of vector

//Given std::list<int> l:
l.remove(*l.begin())
//The operation could delete the first element, and then continue trying to access it.

已采纳的决议 NAD (Not A Defect, 非缺陷) 意味着上述操作必须是良定义的. 这要求代码检测对已插入元素的引用, 并在该情况下进行一次额外复制, 即使未使用对已插入对象的引用也会影响性能. 注意, 接受右值引用或迭代器范围的等价函数要求元素尚未插入容器中.

Boost.Container 优先考虑性能, 未实现 NAD 决议: 在可能修改参数的函数中, 本库要求引用的元素未存储在容器中. 使用对已插入元素的引用会导致未定义行为 (尽管在调试模式下, 可以通过 BOOST_ASSERT 通知此前置条件违规).

vector<bool> 特化

vector<bool> 特化一直很有问题, 曾有多次将其弃用或从标准中移除的尝试, 均未成功. Boost.Container 未实现它, 因为已有更优秀的 Boost.DynamicBitset 方案. 有关 vector<bool> 的问题参见以下论文:

  • 关于 vector<bool>
  • vector<bool>: N1211: More Problems, Better Solutions,
  • N2160: Library Issue 96: Fixing vector<bool>,
  • N2204 A Specification to deprecate vector<bool>.

引文:

  • “遗憾的是, C++ 委员会给这个优秀的数据结构起名 vector<bool>, 并且对需要针对该数据结构优化的关键泛型算法既不提供指导也不给予鼓励. 因此, 很少有 std::lib 实现肯费这个功夫.”
  • “在 1998 年, 承认委员会犯错是有争议的. 此后 Java 不得不弃用其库中如此大的部分, 以至于 C++ 因弃用单个次要模板特化而被嘲笑的想法显得过时了.”
  • “vector<bool> 不是容器, 而 vector<bool>::iterator 也不是随机访问迭代器 (就这一点而言, 甚至连前向或双向迭代器都不是). 这已经在实际中神秘地破坏了用户代码.”
  • “vector<bool> 通过将其写入标准, 向所有用户强加了特定 (且可能糟糕) 的优化选择. 该优化为时过早; 不同用户有不同的需求. 这也已经伤害了那些被迫实现变通方法以禁用该 '优化' 的用户 (例如, 通过使用 vector<char> 并手动与 bool 相互转换).”

因此 boost::container::vector<bool>::iterator 返回真正的 bool 引用, 并作为完全符合标准的容器工作. 如果你需要 boost::container::vector<bool> 的内存优化版本, 请使用 Boost.DynamicBitset.

非标准值初始化: 使用 std::memset

Boost.Container 使用零值的 std::memset 来初始化某些类型, 因为在大多数平台上, 这种初始化以更好的性能产生所需的值初始化.

遵循 C11 标准, Boost.Container 假定 对任何整数类型, 所有位均为零的对象表示都应是该类型中值零的一种表示. 由于 _Bool/wchar_t/char16_t/char32_t 在 C 中也是整数类型, 因此它认为所有 C++ 整数类型都可以通过 std::memset 初始化.

默认情况下, Boost.Container 还认为浮点类型可以通过 std::memset 初始化. 大多数平台与此初始化兼容, 但若不希望此初始化, 用户可以在包含库头文件之前 #define BOOST_CONTAINER_MEMZEROED_FLOATING_POINT_IS_NOT_ZERO.

默认情况下, 它还认为指针类型 (指针和函数指针类型, 不包括成员对象指针和成员函数指针) 可以通过 std::memset 初始化. 大多数平台与此初始化兼容, 但若不希望此初始化, 用户可以在包含库头文件之前 #define BOOST_CONTAINER_MEMZEROED_POINTER_IS_NOT_ZERO.
