类型擦除

不完整类型支持 类型擦除 和 递归数据类型, 多年来 C 和 C++ 程序员一直用它构建复杂的数据结构, 例如节点可以拥有任意数量子节点的树结构.

那么标准容器呢? 不完整类型的容器已经被讨论了很长时间, 如 Matt Austern 的精彩文章 (The Standard Librarian: Containers of Incomplete Types):

“与我大多数专栏不同, 本篇讨论的是 C++ 标准库无法做到的一件事: 将不完整类型放入标准容器之一. 本专栏解释了为什么你可能想这样做, 为什么标准化委员会明知它有用却仍禁止它, 以及你可以做些什么来绕过这一限制.”

“1997 年, 在 C++ 标准即将完成之际, 标准化委员会收到一个提问: 能否用不完整类型创建标准容器? 委员会花了一段时间才理解这个问题. 这样的东西究竟意味着什么, 你到底为什么想要这样做? 委员会最终弄清了问题并给出答案. (为了让你不必跳到结尾, 答案是 "no".) 但这个问题比答案有趣得多: 它指向一种有用却未得到充分讨论的编程技术. 标准库并不直接支持该技术, 但两者可以共存.”

“在 C++ 的未来修订版中, 放宽对以不完整类型实例化标准库模板的限制可能是合理的. 显然, 一般性禁令应当保留 —— 以不完整类型实例化模板是一件微妙的事情, 标准库中有太多类这样做毫无意义. 但也许应该逐个案例地放宽, 而 vector 看起来是这种特殊处理的良好候选: 它是唯一一个有充分理由以不完整类型实例化、且标准库实现者愿意让它工作的标准容器类. 事实上, 如今实现者必须刻意为之才能禁止它!”

C++11 标准对不完整类型与 STL 同样谨慎: “17.6.4.8 其他函数 (...) 2. 在以下情形中效果未定义: (...) 特别地 —— 若在实例化模板组件时将不完整类型 (3.9) 用作模板实参, 除非该组件明确允许”.

最后, C++17 为 std::vector, std::list 和 std::forward_list 添加了对不完整类型的支持 (详情参见 N4510: Minimal incomplete type support for standard containers, revision 4), 但其他容器如 std::set/map/unordered_set/unordered_map,

幸运的是, Boost.Container 容器中除 static_vector, small_vector 和 basic_string 之外的所有容器都设计为支持不完整类型. static_vector 和 small_vector 比较特殊, 因为它们为 value_type 静态分配内存, 这需要完整类型. basic_string 实现了小字符串优化, 这同样需要完整类型.

Boost.Container 支持不完整类型的容器还支持为这些不完整元素实例化迭代器.

递归容器

大多数 Boost.Container 容器都可用于定义递归容器:

#include <boost/container/vector.hpp>
#include <boost/container/stable_vector.hpp>
#include <boost/container/deque.hpp>
#include <boost/container/list.hpp>
#include <boost/container/map.hpp>
#include <boost/container/string.hpp>

using namespace boost::container;

struct data
{
   int               i_;
   //A vector holding still undefined class 'data'
   vector<data>      v_;
   vector<data>::iterator vi_;
   //A stable_vector holding still undefined class 'data'
   stable_vector<data> sv_;
   stable_vector<data>::iterator svi_;
   //A stable_vector holding still undefined class 'data'
   deque<data> d_;
   deque<data>::iterator di_;
   //A list holding still undefined 'data'
   list<data>        l_;
   list<data>::iterator li_;
   //A map holding still undefined 'data'
   map<data, data>   m_;
   map<data, data>::iterator   mi_;

   friend bool operator <(const data &l, const data &r)
   { return l.i_ < r.i_; }
};

struct tree_node
{
   string name;
   string value;

   //children nodes of this node
   list<tree_node>            children_;
   list<tree_node>::iterator  selected_child_;
};



int main()
{
   //a container holding a recursive data type
   stable_vector<data> sv;
   sv.resize(100);

   //Let's build a tree based in
   //a recursive data type
   tree_node root;
   root.name  = "root";
   root.value = "root_value";
   root.children_.resize(7);
   root.selected_child_ = root.children_.begin();
   return 0;
}

类型擦除

不完整类型容器有助于打破头文件依赖并改善编译时间. 使用 Boost.Container, 你可以编写一个头文件, 定义一个以不完整类型容器作为数据成员的类, 只要你小心地把所有需要知道 value_type 大小的实现细节放在实现文件中:

在此头文件中, 我们定义了一个类 (MyClassHolder), 它持有 vector 的不完整类型 (MyClass) 的成员, 该类型仅做了前向声明.

#include <boost/container/vector.hpp>

//MyClassHolder.h

//We don't need to include "MyClass.h"
//to store vector<MyClass>
class MyClass;

class MyClassHolder
{
   public:

   void AddNewObject(const MyClass &o);
   const MyClass & GetLastObject() const;

   private:
   ::boost::container::vector<MyClass> vector_;
};

然后我们可以在它自己的头文件中定义 MyClass.

//MyClass.h

class MyClass
{
   private:
   int value_;

   public:
   MyClass(int val = 0) : value_(val){}

   friend bool operator==(const MyClass &l, const MyClass &r)
   {  return l.value_ == r.value_;  }
   //...
};

包含它的实现文件是 MyClassHolder 

//MyClassHolder.cpp

#include "MyClassHolder.h"

//In the implementation MyClass must be a complete
//type so we include the appropriate header
#include "MyClass.h"

void MyClassHolder::AddNewObject(const MyClass &o)
{  vector_.push_back(o);  }

const MyClass & MyClassHolder::GetLastObject() const
{  return vector_.back();  }

最后, 我们只需编译、链接并运行!

//Main.cpp

#include "MyClassHolder.h"
#include "MyClass.h"

#include <cassert>

int main()
{
   MyClass mc(7);
   MyClassHolder myclassholder;
   myclassholder.AddNewObject(mc);
   return myclassholder.GetLastObject() == mc ? 0 : 1;
}

SCARY 迭代器

题为 SCARY Iterator Assignment and Initialization 的论文 N2913 提出了一项要求: 标准容器的迭代器类型不得依赖除容器的 value_type, difference_type, pointer type 和 const_pointer 类型之外的任何类型实参. 特别地, 按照该提案, 标准容器迭代器的类型不应依赖于容器的 key_compare, hasher, key_equal 或 allocator 类型.

该论文证明了 SCARY 操作对于使用 STL 组件高效实现常见设计模式至关重要. 它表明, 支持 SCARY 操作的实现通过消除迭代器和算法模板的冗余特化来减少目标代码膨胀.

Boost.Container 容器实现了 SCARY 迭代器, 因此容器的迭代器类型仅依赖于 allocator_traits<allocator_type>::pointer 类型 (即要插入容器中的 value_type 的指针类型). 引用类型和所有其他 typedef 都使用 C++11 的 pointer_traits 工具从指针类型推导而来. 这降低了以迭代器为模板的算法和类中的代码膨胀.

C++ 异常处理

在某些环境 (如游戏开发或嵌入式系统) 中, C++ 异常被禁用或需要自定义的错误处理. 根据文档 N2271 EASTL -- Electronic Arts Standard Template Library, 出于若干原因可以禁用异常:

  • “异常处理在所有编译器实现中都会产生某种代价, 包括那些在正常执行期间避免该代价的实现. 然而, 在某些情况下, 这一代价可以说会抵消它所替代的代码的成本.”
  • “人们普遍认为, 异常处理是处理大范围函数返回值的更优方案. 然而, 避免创建需要大范围返回值的函数, 优于使用异常处理来处理这类值.”
  • “在复杂软件的情况下, 正确使用异常处理可能很困难.”
  • “在某些实现中, throw 和 catch 的执行代价可能非常高.”
  • “异常处理违背了 C++ "不为未使用的功能付费" 的设计, 因为它在任何拥有可析构栈对象的非叶函数中都会产生开销, 无论它们是否使用异常处理.”
  • “游戏软件通常采取的方法是尽可能避免需要异常处理的情形; 避免可能出现异常的情况. 例如, 提前验证是否有足够的内存让子系统完成其工作, 而不是在问题发生后试图通过异常处理或其他手段来处理.”
  • “不过, 某些游戏库仍然可以从异常处理中受益. 但最好的做法是让这类库将异常处理保持在内部, 以免把其对异常处理的使用强加给应用程序的其余部分.”

为了支持没有 C++ 异常支持的环境或有特殊错误处理需求的环境, Boost.Container 在定义了 BOOST_CONTAINER_USER_DEFINED_THROW_CALLBACKS 或 BOOST_NO_EXCEPTIONS 时会更改错误通知行为. 前者必须由用户定义, 后者既可以由用户定义, 也可以在编译器以适当标志调用时由 Boost.Confg 隐式定义 (例如 GCC 中的 -fno-exceptions).

在处理用户定义的类时 (例如构造用户定义的类时):

  • 若定义了 BOOST_NO_EXCEPTIONS, 本库将避免使用 try/catch/throw 语句. 类的编写者必须在内部处理并传播错误情形, 因为不会有任何错误通过 Boost.Container 传播.
  • 若 BOOST_NO_EXCEPTIONS 是 未 定义的, 则本库传播异常, 并提供文档中详述的异常保证.

当本库需要抛出异常时 (例如在 out_of_range 中使用了不正确的索引时抛出 vector::at), 本库会调用在 boost/container/throw_exception.hpp 中声明的 throw 回调:

  • 若定义了 BOOST_CONTAINER_USER_DEFINED_THROW_CALLBACKS, 则程序员必须为所有 throw_xxx 函数提供自己的定义. 这些函数不能返回, 它们必须抛出异常或调用 std::exit 或 std::abort.
  • 否则, 若定义了 BOOST_NO_EXCEPTIONS, 则会触发 BOOST_ASSERT_MSG 断言 (更多信息参见 Boost.Assert). 若该断言返回, 则会调用 std::abort.
  • 否则, 会抛出适当的标准库异常 (例如 std::out_of_range).

其他特性

  • 默认构造函数不分配内存, 这提升了性能, 并且通常隐含不抛出保证 (若谓词或分配器的默认构造函数不抛出).
  • 为 basic_string 提供小字符串优化, 内部缓冲区为 11/23 字节 (32/64 位系统), 且 不 增加字符串通常的 sizeof (3 个机器字).
  • [multi]set/map 容器经过大小优化, 将红黑树节点的颜色位嵌入父指针中.
  • [multi]set/map 容器不使用递归函数, 从而避免了栈问题.
