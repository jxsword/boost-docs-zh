在教程部分, 我们已经看到了几个使用本库的示例. 这里我们将描述本库的总体设计, 包括其主要组件及其功能.

本库有三个主要组件:

  • 选项描述组件, 用于描述允许的选项以及如何处理选项的值.

  • 解析器组件, 利用这些信息在输入源中找出选项名和选项值并将其返回.

  • 存储组件, 它提供访问选项值的接口. 它还把解析器返回值的字符串表示转换成所需的 C++ 类型.

具体一点说, options_description 类来自选项描述组件, parse_command_line 函数来自解析器组件, 而 variables_map 类来自存储组件.

在教程中, 我们已经了解了 main 函数如何借助这些组件来解析命令行和配置文件. 在深入探讨每个组件的细节之前, 先就 main 之外的世界作几点说明.

对此外部世界而言, 存储组件最为重要. 它提供一个类来存储所有选项值, 该类的对象可以在程序中自由传递给需要访问选项的模块. 其他所有组件都只能在真正执行解析的地方使用. 不过, 让各个程序模块描述自己的选项并把这些选项传给主模块, 再由主模块合并所有选项, 也可能是有意义的. 当然, 只有在选项数量很大、在一个地方声明所有选项变得麻烦时, 这才值得考虑.

选项描述组件

选项描述组件有三个主要类: option_description、value_semantic 和 options_description. 前两者共同描述单个选项. option_description 类包含选项的名称、描述以及指向 value_semantic 的指针, 后者知道选项值的类型, 并能解析值、应用默认值等等. options_description 类则是 option_description 实例的容器.

对几乎所有库而言, 这些类都可以按常规方式创建: 即用构造函数创建新选项, 然后调用 add 方法把它们加入 options_description. 然而, 对声明二三十个选项来说, 这样写实在过于冗长. 出于这种考虑, 便产生了你已经见过的语法:

options_description desc;
desc.add_options()
    ("help", "produce help")
    ("optimization", value<int>()->default_value(10), "optimization level")
    ;

调用 value 函数会创建一个派生自 value_semantic 类的类的实例: typed_value. 该类包含解析特定类型值的代码, 还包含若干可由用户调用的方法, 用于指定附加信息 (这实质上是在模拟构造函数的命名参数). 对 operator() 的调用作用于 add_options 返回的对象, 它会把实参转发给 option_description 类的构造函数, 并加入新实例.

注意, 除了 value 之外, 本库还提供 bool_switch 函数, 用户也可以编写自己的函数, 返回具有不同行为的 value_semantic 的其他子类. 在本节余下部分, 我们只讨论 value 函数.

关于选项的信息分为语法信息和语义信息. 语法信息包括选项的名称以及可用于指定值的记号数量. 解析器利用这些信息把记号归组成 (名称, 值) 对, 其中值只是一个字符串向量 (std::vector<std::string>). 语义层负责把选项的值转换成更易用的 C++ 类型.

这种分离是本库设计的重要一环. 解析器只使用语法层, 这削减了使用过于复杂结构的自由. 例如, 下面这样的语法就很难解析:

calc --expression=1 + 2/3

因为若不知道它是 C 表达式, 就无法解析

1 + 2/3

. 只需用户稍加帮助, 这项任务就变得轻而易举, 语法也清晰了:

calc --expression="1 + 2/3"

语法信息

描述格式化

语法信息由 boost::program_options::options_description 类以及 boost::program_options::value_semantic 类的一些方法提供, 包括:

  • 选项的名称, 用于在程序内部标识选项,

  • 选项的描述, 可以呈现给用户,

  • 组成选项值的源记号的允许数量, 在解析时使用.

考虑下面的示例:

options_description desc;
desc.add_options()
    ("help", "produce help message")
    ("compression", value<string>(), "compression level")
    ("verbose", value<string>()->implicit_value("0"), "verbosity level")
    ("email", value<string>()->multitoken(), "email to send to")
    ;

对第一个选项, 我们只指定了名称和描述. 解析源中不能为它指定值. 对第二个选项, 用户必须用一个记号指定值. 对第三个选项, 用户可以为一个值提供单个记号, 也可以完全不提供记号. 对最后一个选项, 值可以跨越多个记号. 例如, 下面的命令行是合法的:

          test --help --compression 10 --verbose --email beadle@mars beadle2@mars

描述格式化

有时描述会相当长, 例如当一个选项的多个值需要分别给出文档时. 下面介绍一些可以使用的简单格式化机制.

描述字符串由一个或多个段落组成, 段落之间以换行符 ('\n') 分隔. 输出某个选项时, 本库会为选项描述计算缩进. 每个段落都作为单独的一行输出, 并采用该缩进. 如果一个段落在一行内放不下, 就会折成多行 (各行缩进相同).

可以在段落开头插入空格, 为第一行指定额外的缩进. 例如:

options.add_options()
    ("help", "   A long help msg a long help msg a long help msg a long help
msg a long help msg a long help msg a long help msg a long help msg ")
    ;

将为第一行指定四个空格的缩进. 输出类似于:

  --help                    A long help msg a long
                        help msg a long help msg
                        a long help msg a long
                        help msg a long help msg
                        a long help msg a long
                        help msg

对于发生折行的情况, 你可能希望换行后的文本有额外的缩进. 这可以通过在期望的位置插入制表符 ('\t') 来实现. 例如:

options.add_options()
      ("well_formated", "As you can see this is a very well formatted
option description.\n"
                        "You can do this for example:\n\n"
                        "Values:\n"
                        "  Value1: \tdoes this and that, bla bla bla bla
bla bla bla bla bla bla bla bla bla bla bla\n"
                        "  Value2: \tdoes something else, bla bla bla bla
bla bla bla bla bla bla bla bla bla bla bla\n\n"
                        "    This paragraph has a first line indent only,
bla bla bla bla bla bla bla bla bla bla bla bla bla bla bla");

将产生:

  --well_formated       As you can see this is a
                        very well formatted
                        option description.
                        You can do this for
                        example:

                        Values:
                          Value1: does this and
                                  that, bla bla
                                  bla bla bla bla
                                  bla bla bla bla
                                  bla bla bla bla
                                  bla
                          Value2: does something
                                  else, bla bla
                                  bla bla bla bla
                                  bla bla bla bla
                                  bla bla bla bla
                                  bla

                            This paragraph has a
                        first line indent only,
                        bla bla bla bla bla bla
                        bla bla bla bla bla bla
                        bla bla bla

制表符会在输出前被移除. 每个段落只允许一个制表符, 否则会抛出 program_options::error 类型的异常. 最后, 如果制表符不在段落的第一行上, 或位于第一行最后一个可能的位置, 则会被忽略.

语义信息

语义信息完全由 boost::program_options::value_semantic 类提供. 例如:

options_description desc;
desc.add_options()
    ("compression", value<int>()->default_value(10), "compression level")
    ("email", value< vector<string> >()
        ->composing()->notifier(&your_function), "email")
    ;

这些声明规定: 第一个选项的默认值为 10; 第二个选项可以出现多次, 且所有实例都应被合并; 解析完成后, 本库会调用函数 &your_function, 并把 "email" 选项的值作为实参传入.

位置选项

我们把选项定义为 (名称, 值) 对, 这简单而有用, 但对命令行的一种特殊情况来说, 存在一个问题. 命令行中可以包含 位置选项, 它完全不带任何名称, 例如:

          archiver --compression=9 /etc/passwd

这里, "/etc/passwd" 元素就没有任何选项名.

一种解决办法是让用户自己提取位置选项并随意处理. 不过还有一种更好的做法 -- 提供一种机制, 自动为位置选项指定名称, 使上面的命令行可以按与下面相同的方式解释:

          archiver --compression=9 --input-file=/etc/passwd

positional_options_description 类允许命令行解析器为位置选项指定名称. 该类规定了允许多少个位置选项, 并为每个允许的选项规定名称. 例如:

positional_options_description pd; pd.add("input-file", 1);

规定恰好第一个位置选项的名称为 "input-file".

也可以指定让若干个, 甚至全部位置选项, 都使用同一个名称.

positional_options_description pd;
pd.add("output-file", 2).add("input-file", -1);

在上面的示例中, 前两个位置选项将关联名称 "output-file", 其余的则关联名称 "input-file".

警告

positional_options_description 类只规定从位置到名称的映射, 选项名称仍需注册到 options_description 类的实例中.

解析器组件

解析器组件把输入源切分为 (名称, 值) 对. 每个解析器寻找可能的选项, 并查询选项描述组件, 以确定该选项是否已知以及其值如何指定. 在最简单的情况下, 名称被显式指定, 本库据此判断该选项是否已知. 若已知, value_semantic 实例决定值如何指定. (若未知, 则抛出异常.) 常见情形有两种: 值由用户显式指定; 以及值不能由用户指定, 但选项的出现本身就意味着某个值 (例如 true). 因此, 解析器检查需要值时值已被指定、不需要值时值未被指定, 然后返回新的 (名称, 值) 对.

要调用解析器, 通常的做法是调用一个函数, 向其传入选项描述以及命令行、配置文件或其他内容. 解析结果以 parsed_options 类实例的形式返回. 通常, 该对象会直接传给存储组件. 不过它也可以被直接使用, 或先经过一些额外处理.

上述模型有三个例外 -- 都与命令行的传统用法有关. 它们需要选项描述组件提供一些支持, 由此增加的复杂度尚可接受.

  • 命令行上指定的名称可能与选项名不同 -- 常见的做法是为较长的名称提供一个 "短选项名" 别名. 同样常见的做法是允许在命令行上指定缩写名称.

  • 有时希望把值指定为多个记号. 例如, 选项 "--email-recipient" 后面可以跟多个电子邮件地址, 每个地址都是单独的命令行记号. 这种行为是受支持的, 但它可能导致解析歧义, 因此默认不启用.

  • 命令行中可以包含位置选项 -- 即不带任何名称的元素. 命令行解析器提供了一种为这类选项猜测名称的机制, 我们在教程中已经见过.

存储组件

存储组件负责:

  • 把选项的最终值存入一个专门的类以及普通变量

  • 处理不同来源之间的优先级.

  • 用选项的最终值调用用户指定的 notify 函数.

我们来看一个示例:

variables_map vm;
store(parse_command_line(argc, argv, desc), vm);
store(parse_config_file("example.cfg", desc), vm);
notify(vm);

variables_map 类用于存储选项值. 对 store 函数的两次调用分别加入在命令行和配置文件中找到的值. 最后对 notify 函数的调用会执行用户指定的 notify 函数, 并在需要时把值存入普通变量.

优先级的处理方式很简单: 如果某个选项已被赋值, store 函数就不会再改变它的值. 这样, 如果命令行指定了某选项的值, 配置文件中的任何值都会被忽略.

警告

存完所有解析得到的值之后, 别忘了调用 notify 函数.

配置文件解析器

parse_config_file 函数实现简单的类 INI 配置文件解析. 配置文件语法基于行:

  • 如下形式的行:

    name=value

    为选项赋值.

  • 如下形式的行:

    [section name]

    在配置文件中引入一个新的节.

  • # 字符引出一条延续到行尾的注释.

选项名相对于节名, 所以下面这段配置文件:

[gui.accessibility]
visual_bell=yes

等价于

gui.accessibility.visual_bell=yes

当把选项 "gui.accessibility.visual_bell" 加入选项后

options_description desc;
desc.add_options()
    ("gui.accessibility.visual_bell", value<string>(), "flash screen for bell")
    ;

环境变量解析器

环境变量是通过 C 运行库的 getenv 函数对所有程序都可见的字符串变量. 操作系统允许为给定用户设置初始值, 这些值还可以在命令行上进一步修改. 例如, 在 Windows 上可以使用 autoexec.bat 文件, 或 (在较新的版本上) 使用 Control Panel/System/Advanced/Environment Variables 对话框; 在 Unix 上则使用 /etc/profile、~/.profile 和 ~/.bash_profile 文件. 由于环境变量可以为整个系统设置, 它们特别适用于对所有程序都生效的选项.

环境变量可以用 parse_environment 函数解析. 该函数有多个重载版本. 第一个参数始终是一个 options_description 实例, 第二个参数规定必须处理哪些变量, 以及各变量应对应哪个选项名. 要说明第二个参数, 需要先考虑环境变量的命名约定.

如果你有一个应当通过环境变量指定的选项, 就需要给变量取一个名称. 为避免名称冲突, 建议为环境变量使用足够独特的前缀. 此外, 选项名多半是小写, 而环境变量习惯上使用大写. 因此, 对选项名 proxy 而言, 环境变量可以叫做 BOOST_PROXY. 解析时, 我们需要把名称反向转换. 这可以通过把选定的前缀作为 parse_environment 函数的第二个参数来做到. 比如说, 如果你传入 BOOST_ 作为前缀, 而存在两个变量 CVSROOT 和 BOOST_PROXY, 那么第一个变量会被忽略, 第二个变量则会被转换为选项 proxy.

上述逻辑在许多情况下已经够用, 但也可以向 parse_environment 函数的第二个参数传入任何接受 std::string 并返回 std::string 的函数. 该函数会对每个环境变量被调用, 并应返回对应的选项名; 如果该变量应被忽略, 则返回空字符串. 展示这种方法的示例见 "example/env_options.cpp".

类型

命令行上传入的一切、环境变量以及配置文件中的内容都是字符串. 对于需要以非字符串类型使用的值, variables_map 中的值会尝试把它转换为正确的类型.

整数和浮点值使用 Boost 的 lexical_cast 转换. 它接受 "41" 或 "-42" 这样的整数值, 也接受 "51.1"、"-52.1"、"53.1234567890" (作为 double)、"54"、"55."、".56"、"57.1e5"、"58.1E5"、".591e5"、"60.1e-5"、"-61.1e5"、"-62.1e-5" 等浮点数. 遗憾的是, C++ 字面量中可用的十六进制、八进制和二进制表示不受 lexical_cast 支持, 因而在 program_options 中也无法使用.

布尔类型比较特殊, 因为有多种方式指定它. 与其他值类型一样, 它可以按 ("my-option", value<bool>()) 的形式声明, 然后这样设置:

example --my-option=true

不过, 更典型的情况是布尔值仅由开关的出现与否来设置. 这由 bool_switch 实现, 如 ("other-option", bool_switch()) 所示. 这会使值默认为 false, 并在发现该开关时变为 true:

example --other-switch

当布尔值确实需要参数时, 有几种可选写法. 在 C++ 中求值为 true 的有: "true"、"yes"、"on"、"1". 求值为 false 的有: "false"、"no"、"off"、"0". 此外, 从配置文件读取时, 选项名后跟等号且等号后无值的形式也会求值为 true.
