本节将考察 program_options 库最常见的使用场景, 从最简单的开始. 示例只展示有意思的代码部分, 完整程序见 "BOOST_ROOT/libs/program_options/example" 目录. 在全部示例中, 我们都假定以下命名空间别名已生效:

namespace po = boost::program_options;

入门

第一个示例尽可能简单: 它只处理两个选项. 下面是源代码 (完整程序在 "example/first.cpp" 中):

// Declare the supported options.
po::options_description desc("Allowed options");
desc.add_options()
    ("help", "produce help message")
    ("compression", po::value<int>(), "set compression level")
;

po::variables_map vm;
po::store(po::parse_command_line(ac, av, desc), vm);
po::notify(vm);    

if (vm.count("help")) {
    cout << desc << "\n";
    return 1;
}

if (vm.count("compression")) {
    cout << "Compression level was set to " 
 << vm["compression"].as<int>() << ".\n";
} else {
    cout << "Compression level was not set.\n";
}

我们首先用 options_description 类声明所有允许的选项. 该类的 add_options 方法返回一个定义了 operator() 的特殊代理对象. 对该运算符的调用才真正声明选项. 参数依次是选项名、关于值的信息以及选项描述. 在本示例中, 第一个选项没有值, 第二个选项的值类型为 int.

之后声明一个 variables_map 类的对象. 该类用于存储选项值, 并可存储任意类型的值. 接着, 对 store、parse_command_line 和 notify 函数的调用使 vm 包含在命令行上找到的所有选项.

现在, 我们终于可以随意使用这些选项了. variables_map 类可以像 std::map 一样使用, 只是其中存储的值必须用上面所示的 as 方法取出. (如果调用 as 方法时指定的类型与实际存储的类型不同, 将抛出异常.)

现在正适合亲自尝试编译这段代码; 如果你还没准备好, 下面是一次示例会话:

$ bin/gcc/debug/first
Compression level was not set.
$ bin/gcc/debug/first --help
Allowed options:
  --help                 : produce help message
  --compression arg      : set compression level
$ bin/gcc/debug/first --compression 10
Compression level was set to 10.

选项细节

当然, 选项值可以具有 int 以外的其他类型, 还可以有其他有趣的性质, 我们现在就来讨论. 下面代码片段的完整版本见 example/options_description.cpp.

设想我们正在编写一个编译器. 它应接受优化级别、若干头文件包含路径和若干输入文件, 并完成一些有意思的工作. 我们来描述这些选项:

int opt;
po::options_description desc("Allowed options");
desc.add_options()
    ("help", "produce help message")
    ("optimization", po::value<int>(&opt)->default_value(10), 
  "optimization level")
    ("include-path,I", po::value< vector<string> >(), 
  "include path")
    ("input-file", po::value< vector<string> >(), "input file")
;

"help" 选项应当已在上一示例中见过. 无论如何都建议提供这个选项.

"optimization" 选项展示了两个新特性. 第一, 我们指定了变量的地址 (&opt). 存储值之后, 该变量将持有该选项的值. 第二, 我们指定了默认值 10, 当用户未指定值时将使用它.

"include-path" 选项是唯一一种情形的例子: options_description 类的接口只服务单一来源 -- 命令行. 用户通常喜欢对常用选项使用短选项名, 名称 "include-path,I" 规定短选项名为 "I". 因此, "--include-path" 和 "-I" 都可以使用.

另请注意, "include-path" 选项的类型是 std::vector. 本库为向量提供了特别支持 -- 可以多次指定该选项, 所有指定的值都会被收集到一个向量中.

"input-file" 选项指定要处理的文件列表. 一开始这样还可以, 但当然, 写成下面这样:

compiler --input-file=a.cpp

与下面的写法相比稍显非标准:

compiler a.cpp

我们稍后会解决这个问题.

如上所示, 没有选项名的命令行记号在本库中被称为 "位置选项". 它们同样可以处理. 只需用户稍加帮助, 本库就能判定 "a.cpp" 实际上与 "--input-file=a.cpp" 含义相同. 下面是我们需要的附加代码:

po::positional_options_description p;
p.add("input-file", -1);

po::variables_map vm;
po::store(po::command_line_parser(ac, av).
          options(desc).positional(p).run(), vm);
po::notify(vm);

前两行说明所有位置选项都应转换为 "input-file" 选项. 另请注意, 我们使用 command_line_parser 类来解析命令行, 而不是 parse_command_line 函数. 后者是针对简单情况的便捷封装, 但现在我们需要传入附加信息.

至此, 所有选项都已描述并解析完毕. 剩下的编译器逻辑我们就不费力实现了, 只打印这些选项:

if (vm.count("include-path"))
{
    cout << "Include paths are: " 
         << vm["include-path"].as< vector<string> >() << "\n";
}

if (vm.count("input-file"))
{
    cout << "Input files are: " 
         << vm["input-file"].as< vector<string> >() << "\n";
}

cout << "Optimization level is " << opt << "\n";

下面是一次示例会话:

$ bin/gcc/debug/options_description --help
Usage: options_description [options]
Allowed options:
  --help                 : produce help message
  --optimization arg     : optimization level
  -I [ --include-path ] arg : include path
  --input-file arg       : input file
$ bin/gcc/debug/options_description
Optimization level is 10
$ bin/gcc/debug/options_description --optimization 4 -I foo -I another/path --include-path third/include/path a.cpp b.cpp
Include paths are: foo another/path third/include/path
Input files are: a.cpp b.cpp
Optimization level is 4

哎呀, 有个小问题. 现在仍然可以指定 "--input-file" 选项, 而且用法消息里也这么说, 这可能让用户感到困惑. 把这个信息隐藏起来会更好, 不过我们先留到下一个示例再解决.

多个来源

很可能, 要用户在命令行上为我们的编译器指定所有选项会令其厌烦. 如果用户安装了一个新库, 并希望总是传入一个额外的命令行元素, 怎么办? 如果他做了一些每次运行都应生效的选择, 又怎么办? 比较理想的做法是创建一个包含常用设置的配置文件, 让它与命令行一起使用.

当然, 我们还需要合并来自命令行和配置文件的值. 例如, 命令行上指定的优化级别应覆盖配置文件中的值. 另一方面, 包含路径则应合并.

现在来看代码. 完整程序在 "examples/multiple_sources.cpp" 中. 选项定义有两个值得注意的细节. 第一, 我们声明了 options_description 类的多个实例. 原因在于, 一般来说, 并非所有选项都彼此相同. 有些选项, 比如上面的 "input-file", 不应出现在自动生成的帮助消息中. 有些选项只在配置文件中才有意义. 最后, 帮助消息最好有一些结构, 而不只是一长串选项. 我们来声明几个选项组:

// Declare a group of options that will be 
// allowed only on command line
po::options_description generic("Generic options");
generic.add_options()
    ("version,v", "print version string")
    ("help", "produce help message")    
    ;
    
// Declare a group of options that will be 
// allowed both on command line and in
// config file
po::options_description config("Configuration");
config.add_options()
    ("optimization", po::value<int>(&opt)->default_value(10), 
          "optimization level")
    ("include-path,I", 
         po::value< vector<string> >()->composing(), 
         "include path")
    ;

// Hidden options, will be allowed both on command line and
// in config file, but will not be shown to the user.
po::options_description hidden("Hidden options");
hidden.add_options()
    ("input-file", po::value< vector<string> >(), "input file")
    ;

注意在 "include-path" 选项的声明中对 composing 方法的调用. 它告诉本库: 来自不同来源的值应当合并在一起, 稍后我们会看到这一点.

add 方法属于 options_description 类, 可用于进一步划分选项组:

po::options_description cmdline_options;
cmdline_options.add(generic).add(config).add(hidden);

po::options_description config_file_options;
config_file_options.add(config).add(hidden);

po::options_description visible("Allowed options");
visible.add(generic).add(config);

值的解析和存储遵循常见的模式, 只是我们额外调用了 parse_config_file, 并且调用了两次 store 函数. 但是, 如果同一个值既在命令行上又在配置文件中被指定, 会发生什么? 通常, 先存储的值优先. "--optimization" 选项就是这样处理的. 对于 "composing" 选项, 比如 "include-file", 各个值会被合并.

下面是一次示例会话:

$ bin/gcc/debug/multiple_sources
Include paths are: /opt
Optimization level is 1
$ bin/gcc/debug/multiple_sources --help
Allows options:

Generic options:
  -v [ --version ]       : print version string
  --help                 : produce help message

Configuration:
  --optimization n       : optimization level
  -I [ --include-path ] path : include path

$ bin/gcc/debug/multiple_sources --optimization=4 -I foo a.cpp b.cpp
Include paths are: foo /opt
Input files are: a.cpp b.cpp
Optimization level is 4

第一次运行使用配置文件中的值. 第二次运行还使用了命令行上的值. 如我们所见, 命令行和配置文件中的包含路径被合并了, 而优化级别则取自命令行.
