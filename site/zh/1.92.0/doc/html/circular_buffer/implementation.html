实现

以下几段描述在实现 circular_buffer 时必须考虑的问题:

线程安全

circular_buffer 的线程安全性与大多数 STL 实现中容器的线程安全性相同. 这意味着 circular_buffer 不是完全线程安全的. 线程安全性仅在如下意义上得到保证: 对 circular_buffer 的不同实例的同时访问是安全的, 对共享的 circular_buffer 的同时读访问是安全的.

如果多个线程访问同一个 circular_buffer, 且其中至少一个线程可能进行写操作, 则用户有责任确保各线程在容器访问期间的互斥. 线程间的互斥可以通过用锁的获取与释放包裹底层 circular_buffer 的操作来实现. (参见 circular_buffer_bound_example.cpp 处的有界缓冲区示例代码)

覆写操作

当向一个已满的 circular_buffer 插入元素时, 就会发生覆写 (overwrite) 操作——旧元素被新元素覆写. 在正式评审期间曾讨论过"元素的覆写"到底意味着什么: 它可以是先析构原元素、随后就地构造新元素, 也可以是把新元素赋值到旧元素上. circular_buffer 实现的是赋值, 因为它更高效.

从所存元素的业务逻辑角度看, 析构/构造操作与赋值通常意味着同样的事. 然而, 在极少数情况下 (如果存在的话) 二者可能不同. 如果要求元素必须被析构/构造而不是被赋值, 可以考虑实现一个实现了赋值运算符的元素包装器 (wrapper), 并改为存储这些包装器. 需要指出, 存储这样的包装器有一个缺点: 析构/构造会在每次对包装器赋值时被调用——不仅发生在包装器被覆写时 (缓冲区已满时), 也发生在所存包装器被移位时 (例如作为向容器中部插入的结果).

向已满缓冲区写入

当数据源产生的数据超出定长缓冲区的容量时, 有几种应对方式:

  • 通知数据源等待, 直到缓冲区中有空位 (例如通过抛出上溢异常).
  • 若最旧的数据最重要, 则忽略来自数据源的新数据, 直到缓冲区重新有空位.
  • 若最新的数据最重要, 则覆写最旧的数据.
  • 让生产者负责在写入之前检查缓冲区的大小.

显然, circular_buffer 实现的是第三种方式. 但不太明显的是, 它不实现其他任何方式——尤其是前两种. 有人可能会以为 circular_buffer 应该实现前三种方式, 并提供在它们之间选择的机制. 这种印象是错误的.

circular_buffer 的设计与优化目标就是环形 (即满时覆写最旧的数据). 如果启用这样一种控制机制, 只会把事情复杂化, circular_buffer 的用法很可能不再那么直接了当.

此外, 前两种方式 (第四种也一样) 根本不要求缓冲区是环形的. 如果需要第一种或第二种方式, 可以考虑实现一个适配器, 例如基于 std::vector 的适配器. 在这种情况下 circular_buffer 并不适合用作适配对象, 因为与 std::vector 不同, 它为其环形行为承担着额外开销.

从空缓冲区读取/移除

从空缓冲区读取或移除元素时, 缓冲区应当能够通知数据消费者 (例如通过抛出下溢异常) 其中没有存储任何元素. circular_buffer 没有实现这种行为, 原因有二:

  • 它会带来性能开销.
  • 没有其他 std 容器以这种方式实现它.

从空的 std 容器读取或移除元素 (例如调用 front() 或 pop_back()) 被视为缺陷, 对空的 circular_buffer 亦然. 数据消费者必须在读取/移除之前通过检查 empty() 来确认容器非空. 不过, 从 circular_buffer 读取时, 也可以选择依赖 at() 方法, 它在索引越界时抛出异常.

迭代器失效

如果迭代器所指向的元素被移除或被另一元素覆写, 该迭代器通常被视为已失效. 这一定义由调试支持 (Debug Support) 强制执行, 并在每个方法的文档中说明. 然而, 某些使用 circular_buffer 的应用可能需要较宽松的定义: 只有当迭代器指向未初始化的内存时它才是无效的.

考虑下面的示例:

#define BOOST_CB_ENABLE_DEBUG 0 // The Debug Support has to be disabled, otherwise the code produces a runtime error.

#include <boost/circular_buffer.hpp>
#include <boost/assert.hpp>
#include <assert.h>

int main(int /*argc*/, char* /*argv*/[])
{

  boost::circular_buffer<int> cb(3);

  cb.push_back(1);
  cb.push_back(2);
  cb.push_back(3);

  boost::circular_buffer<int>::iterator it = cb.begin();

  assert(*it == 1);

  cb.push_back(4);

  assert(*it == 4); // The iterator still points to the initialized memory.

  return 0;
}

该迭代器不再指向原来的元素 (从"严格"的角度看已被视为无效), 但它仍指向内存中同一处有效位置. circular_buffer 支持这种迭代器失效的"软"定义, 但应将其视为实现细节而非完整特性. 迭代器何时仍然有效的规则可以从 soft_iterator_invalidation.cpp 中的代码推断.

移动仿真与右值

自 Boost 1.54.0 起, 移动语义的支持用 Boost.Move 库实现. 若右值引用可用, circular_buffer 会使用它们; 否则它使用一种接近但不完美的仿真. 在这类编译器上:

  • 不可复制对象可以存入容器. 它们可以用 emplace 就地构造, 或者 (若支持 Boost.Move) 移动到位.
  • 容器本身不可移动.
  • 实参转发并不完美.

仅当值类型的移动构造函数和移动赋值运算符不抛出异常, 或值类型没有拷贝构造函数时, circular_buffer 才会对该值类型使用右值和移动仿真.

若构造函数会抛出异常, 某些方法将完全不对值类型使用移动构造函数. 这样做是为了保证数据一致性, 并避免异常发生后 circular_buffer 中同时混有已被移走对象与完好对象的情形.

请参阅 is_copy_constructible、is_nothrow_move_assignable 和 is_nothrow_move_constructible 类型特征 (type traits) 的文档. 你会在那里找到如何把类的构造函数声明为 noexcept, 以及如何在 C++03 和 C++98 中创建不可复制类的信息.

若值类型具有 noexcept 移动构造函数和 noexcept 移动赋值运算符, circular_buffer 的性能将 大幅提升.

move_if_noexcept(T&) 的异常

circular_buffer 的参考文档包含诸如 "抛出: 参见 move_if_noexcept(T&) 的异常" 的注释. 该注释的含义是: move_if_noexcept(T& value) 本身不抛出任何异常, 但它以右值引用返回 value, 仅当类 T 具有 noexcept 移动构造函数和 noexcept 移动赋值运算符, 或没有拷贝构造函数. 否则 move_if_noexcept(T& value) 以 const 引用返回 value.

由此我们得到如下情形:

  • 若 value 具有 noexcept 移动构造函数和 noexcept 移动赋值运算符, 则根本不会抛出异常.
  • 若 value 具有会抛出异常的移动构造函数和某个拷贝构造函数, 则该方法可能抛出拷贝构造函数的异常.
  • 若 value 没有拷贝构造函数, 则该方法可能抛出移动构造函数的异常.

move_if_noexcept(T&) 使用 Boost.Move、is_copy_constructible、is_nothrow_move_assignable 和 is_nothrow_move_constructible 类型特征 (type traits).

注意事项

circular_buffer 不应用于存储指向动态分配对象的指针. 当环形缓冲区变满后, 后续插入会覆写已存储的指针——从而导致 内存泄漏. 推荐的替代做法是使用智能指针, 例如 Boost Smart pointers.

std::auto_ptr

注意

任何 std::auto_ptr 的容器都被认为特别危险.

提示

绝不要创建 std::auto_ptr 的环形缓冲区. 详细讨论请参阅 Scott Meyers 的优秀著作 Effective STL. (Meyers S., Effective STL: 50 Specific Ways to Improve Your Use of the Standard Template Library. Addison-Wesley, 2001.)

虽然 circular_buffer 的内部是环形的, 但 迭代器不是. circular_buffer 的迭代器仅在范围 \[begin(), end()\] 内有效, 例如: 迭代器 (begin() - 1) 和 (end() + 1) 都是无效的.

调试支持

为帮助程序员避免和发现常见缺陷, 可以启用 circular_buffer 以提供一种调试支持.

启用调试功能后, circular_buffer 会维护一个有效迭代器的列表. 一旦某个元素被销毁, 所有指向该元素的迭代器都会从该列表中移除并被显式置为无效 (设置失效标志). 调试支持还包括许多断言 (BOOST_ASSERT 宏), 它们确保 circular_buffer 及其迭代器在运行期以正确的方式使用. 若使用了无效迭代器, 断言会报告错误. 显式迭代器失效与断言的结合构成了一种非常稳健的调试技术, 能捕获大多数错误.

此外, 在调试模式下, circular_buffer 分配的未初始化内存会被填充为值 0xcc. 调试代码时, 这可以帮助程序员区分已初始化内存与未初始化内存. 详情请参阅源代码 circular_buffer/debug.hpp.

注意

由于调试代码使 circular_buffer 与其迭代器的关联更加紧密, 启用调试支持时 circular_buffer 的线程安全保证会有所不同. 除容器本身外, 容器跟踪的所有迭代器 (包括其任何副本) 也必须受保护而不被并发访问. 特别是, 这包括从容器复制、销毁或获取迭代器, 即使只是只读访问.

调试支持默认是禁用的. 要启用它, 必须在把宏 BOOST_CB_ENABLE_DEBUG 定义为 1 的同时编译使用 circular_buffer 的代码.

与 Interprocess 库的兼容性

circular_buffer 与用于进程间通信的 Boost.Interprocess 库兼容. 考虑到 circular_buffer 的调试支持依赖"裸"指针 (这是 Interprocess 库不允许的), 代码必须在禁用调试支持的情况下编译 (即不定义 BOOST_CB_ENABLE_DEBUG 宏, 或将其定义为 0). 否则将导致编译失败.
