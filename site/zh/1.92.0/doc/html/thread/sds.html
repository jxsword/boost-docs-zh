互斥量的问题

用互斥量保护共享数据的关键问题在于, 没有简单的方法把互斥量与数据关联起来. 因此, 很容易不小心写出没有锁住正确互斥量——甚至锁错互斥量——的代码, 而编译器不会帮你发现.

std::mutex m1;
int value1;
std::mutex m2;
int value2;

int readValue1()
{
  boost::lock_guard<boost::mutex> lk(m1);
  return value1;
}
int readValue2()
{
  boost::lock_guard<boost::mutex> lk(m1); // oops: wrong mutex
  return value2;
}

此外, 管理互斥量锁还会使源代码变得杂乱, 让人更难看清实际发生了什么.

使用 synchronized_value 可以同时解决这两个问题——互斥量与值紧密绑定, 因此没有加锁就无法访问它, 而访问语义依然简单直接. 对于简单访问, synchronized_value 的行为类似指向 T 的指针; 例如:

boost::synchronized_value<std::string> value3;
std::string readValue3()
{
  return *value3;
}
void setValue3(std::string const& newVal)
{
  *value3=newVal;
}
void appendToValue3(std::string const& extra)
{
  value3->append(extra);
}

两种指针解引用形式都返回代理对象而非真正的引用, 以确保在赋值或方法调用期间持有互斥量上的锁, 但这对用户是透明的.

超越简单访问

指针式语义对于简单访问 (如赋值和成员函数调用) 工作良好. 然而, 有时你需要执行的操作需要在同一把锁的保护下进行多次访问, 这正是 synchronize() 方法所提供的.

调用 synchronize() 会得到一个 strict_lock_ptr 对象, 它持有保护该数据的互斥量上的锁, 并可用于访问受保护的数据. 锁会一直持有到 strict_lock_ptr 对象被销毁, 因此你可以安全地执行多步操作. strict_lock_ptr 对象同样表现得像指向 T 的指针, 与 synchronized_value 一样, 只是这一次锁已被持有. 例如, 下面的函数为保存在 synchronized_value 中的路径添加一个尾部斜杠. strict_lock_ptr 对象的使用确保了在查询与更新之间字符串未被改变.

void addTrailingSlashIfMissing(boost::synchronized_value<std::string> & path)
{
  boost::strict_lock_ptr<std::string> u=path.synchronize();

  if(u->empty() || (*u->rbegin()!='/'))
  {
    *u+='/';
  }
}
跨多个对象的操作

虽然 synchronized_value 对保护单个 T 类型对象工作良好, 但到目前为止我们所见的内容都无法解决需要对多个对象进行原子访问的操作问题, 除非这些对象能被组合进由单个互斥量保护的单个结构中.

保护对两个 synchronized_value 对象的访问的一种方法是, 为每个对象构造一个 strict_lock_ptr 并用它访问各自受保护的值; 例如:

synchronized_value<std::queue<MessageType> > q1,q2;
void transferMessage()
{
  strict_lock_ptr<std::queue<MessageType> > u1 = q1.synchronize();
  strict_lock_ptr<std::queue<MessageType> > u2 = q2.synchronize();

  if(!u1->empty())
  {
    u2->push_back(u1->front());
    u1->pop_front();
  }
}

这在某些场景下可行, 但并非所有场景——如果同样的两个对象在不同代码段中被一起更新, 你就要小心确保 strict_lock_ptr 对象在所有情形下都以相同顺序构造, 否则就有死锁的潜在风险. 这与获取任意两把互斥量时的情况完全相同.

为了能够使用无死锁的加锁算法, 我们需要改用 Lockable 的 unique_lock_ptr.

synchronized_value<std::queue<MessageType> > q1,q2;
void transferMessage()
{
  unique_lock_ptr<std::queue<MessageType> > u1 = q1.unique_synchronize(boost::defer_lock);
  unique_lock_ptr<std::queue<MessageType> > u2 = q2.unique_synchronize(boost::defer_lock);
  boost::lock(u1,u2); // dead-lock free algorithm

  if(!u1->empty())
  {
    u2->push_back(u1->front());
    u1->pop_front();
  }
}

虽然上述做法解决了死锁问题, 但通过 unique_lock_ptr 访问 synchronized_value 所需的锁并不是由接口强制的. 在标准库支持可移动 std::tuple 的编译器上, 另一种做法是使用自由函数 synchronize, 它会锁定与各同步值关联的所有互斥量, 并返回一个 strict_lock_ptr 的 tuple.

synchronized_value<std::queue<MessageType> > q1,q2;
void transferMessage()
{
  auto lks = synchronize(u1,u2); // dead-lock free algorithm

  if(!std::get<1>(lks)->empty())
  {
    std::get<2>(lks)->push_back(u1->front());
    std::get<1>(lks)->pop_front();
  }
}

#include <boost/thread/synchronized_value.hpp>

namespace boost
{

  template<typename T, typename Lockable = mutex>
  class synchronized_value
  {
  public:
    typedef T value_type;
    typedef Lockable mutex_type;

    synchronized_value() noexcept(is_nothrow_default_constructible<T>::value);
    synchronized_value(T const& other) noexcept(is_nothrow_copy_constructible<T>::value);
    synchronized_value(T&& other) noexcept(is_nothrow_move_constructible<T>::value);
    synchronized_value(synchronized_value const& rhs);
    synchronized_value(synchronized_value&& other);

    // mutation
    synchronized_value& operator=(synchronized_value const& rhs);
    synchronized_value& operator=(value_type const& val);
    void swap(synchronized_value & rhs);
    void swap(value_type & rhs);

    //observers
    T get() const;
  #if ! defined(BOOST_NO_CXX11_EXPLICIT_CONVERSION_OPERATORS)
    explicit operator T() const;
  #endif

    strict_lock_ptr<T,Lockable> operator->();
    const_strict_lock_ptr<T,Lockable> operator->() const;
    strict_lock_ptr<T,Lockable> synchronize();
    const_strict_lock_ptr<T,Lockable> synchronize() const;

    deref_value operator*();;
    const_deref_value operator*() const;

  private:
    T value_; // for exposition only
    mutable mutex_type mtx_;  // for exposition only
  };
}

synchronize() 
strict_lock_ptr<T,Lockable> synchronize();

synchronize() 工厂使基于作用域的加锁更容易. 如前所述, operator-> 只能在一次调用的持续时间内加锁, 因此对复杂操作来说不够用. 使用 synchronize(), 你可以在一个作用域内锁定对象, 并在该作用域内直接访问对象.

void fun(synchronized_value<vector<int>> & vec) {
  auto vec2=vec.synchronize();
  vec2.push_back(42);
  assert(vec2.back() == 42);
}

注释

这些特性基于 Lawrence Crowl 与 Chris Mysen 的 C++1y 提案 N3533 - C++ Concurrent Queues 以及 Anthony Williams 的 C++ Concurrency in Action.

引言

队列为系统各组件之间的数据通信提供一种机制.

标准库现有的 deque 本质上是串行数据结构. 其返回引用的元素访问操作无法将元素访问与其他队列操作同步. 因此, 队列上的并发 push 和 pop 需要不同的队列结构接口.

此外, 并发性为性能和语义增加了新的维度. 不同的队列实现必须在无竞争操作成本、有竞争操作成本与元素顺序保证之间进行权衡. 其中一些权衡必然导致语义弱于串行队列.

Tutorial

并发队列是在不同线程之间传递数据的众所周知机制.

并发队列的数据处理操作固有地具有复制/移动语义. 禁止返回引用的接口, 因为对这些引用的多重访问不可能是线程安全的.

有界-无界队列

并发队列的一个主要特性是它是否具有有界-无界容量.

加锁/无锁队列

加锁队列本质上可以阻塞等待队列非空或非满.

无锁队列在等待队列非空或非满时会遇到一些困难. 这类队列无法定义诸如 push (有界队列还包括 pull) 的操作. 也就是说, 它可以有阻塞操作 (推测是用忙等待模拟的) , 但不能有等待操作.

关闭队列

使用队列通信的线程需要某种机制来发出队列不再需要的信号. 通常的做法是添加一个额外的带外信号. 然而, 这种做法有一个缺陷: 当队列不再需要时, 等待队列满或空的线程需要被唤醒. 我们没有要求带外信号, 而是选择在队列本身中直接支持这样的信号, 这大大简化了编码.

为实现这一信号, 线程可以关闭队列. 一旦关闭, 就不能再向队列推入新元素. 在已关闭队列上的 push 操作要么返回 queue_op_status::closed (当它们有 queue_op_status 返回类型时) , 要么设置 closed 参数 (如果有) , 要么抛出 sync_queue::closed (当它们没有时) . 队列中已有的元素仍可被取出. 当队列为空且已关闭时, pull 操作要么返回 queue_op_status::closed (当它们有状态返回时) , 要么设置 closed 参数 (如果有) , 要么抛出 sync_queue::closed (当它们没有时) .

等待队列非空且未关闭. 如果队列为空且已关闭, 则抛出 sync_queue_is_closed. 否则从队列 q 中取出元素并移动该元素.

同步:

同一对象上先前的 pull 类操作与本操作同步.

后置条件:

! q.full().

返回类型:

Q::value_type.

返回:

被取出的元素.

抛出:

复制 e 时抛出的任何异常.

异常安全:

如果抛出异常, 队列状态保持不变.

非等待并发队列操作

ConcurrentQueue 概念刻画带非等待操作的队列.

类型 Q 满足 ConcurrentQueue 要求, 如果它是 BasicConcurrentQueue 的模型, 且下列表达式格式良好并具有规定的语义

  • s = q.try_push_back(e);
  • s = q.try_push_back(rve);
  • s = q.try_pull_front(lre);

其中

  • q 表示 Q 类型的值,
  • e 表示 Q::value_type 类型的值,
  • s 表示 queue_status 类型的值,
  • u 表示 Q::size_type 类型的值,
  • lve 表示一个 Q::value_type 类型的左值引用,
  • rve 表示一个 Q::value_type 类型的右值引用:
s = q.try_push_back(e);

效果:

如果队列 q 未满且未关闭, 则以复制方式把 e push back 到队列.

同步:

当操作成功时, 同一对象上先前的 pull 类操作与本操作同步.

返回类型:

queue_op_status.

返回:

- 如果队列已关闭, 返回 queue_op_status::closed,

- 否则, 如果队列 q 已满, 返回 queue_op_status::full,

- 否则返回 queue_op_status::success;

后置条件:

如果调用返回 queue_op_status::success, 则 ! q.empty().

抛出:

如果队列已关闭, 则抛出 sync_queue_is_closed. 复制 e 时抛出的任何异常.

异常安全:

如果抛出异常, 队列状态保持不变.

s = q.try_push_back(rve);

效果:

如果队列 q 未满且未关闭, 则以移动方式把 e push back 到队列.

同步:

同一对象上先前的 pull 类操作与本操作同步.

返回类型:

返回:

- 否则, 如果队列 q 已满, 返回 queue_op_status::full,

- 否则返回 queue_op_status::success;

复制 e 时抛出的任何异常.

异常安全:

效果:

如果队列非空, 则从队列 q 取出元素, 并把取出的元素移动到 lve (对无界队列可能需要一次分配) .

同步:

- 否则返回 queue_op_status::success;

抛出:

异常安全:

如果抛出异常, 队列状态保持不变.

非阻塞并发队列操作

对于不希望为互斥而阻塞的情形, 我们提供非阻塞操作. 接口与 try 操作相同, 但当操作无法在不阻塞的情况下完成时, 还允许返回 queue_op_status::busy.

非阻塞操作仅对基于锁的队列提供

  • s = q.nonblocking_push_back(nb, e);
  • s = q.nonblocking_push_back(nb, rve);
  • s = q.nonblocking_pull_front(nb, lre);

其中

  • q 表示 Q 类型的值,
  • e 表示 Q::value_type 类型的值,
  • s 表示 queue_status 类型的值,
  • lve 表示一个 Q::value_type 类型的左值引用,
  • rve 表示一个 Q::value_type 类型的右值引用:
s = q.nonblocking_push_back(e);

#include <boost/thread/concurrent_queues/queue_base.hpp>

namespace boost
{
  template <typename ValueType, class SizeType=std::size_t>
  class queue_base
  {
  public:
    typedef ValueType value_type;
    typedef SizeType size_type;

    // Constructors/Assignment/Destructors
    virtual ~queue_base() {};

    // Observers
    virtual bool empty() const = 0;
    virtual bool full() const = 0;
    virtual size_type size() const = 0;
    virtual bool closed() const = 0;

    // Modifiers
    virtual void close() = 0;

    virtual void push_back(const value_type& x) = 0;
    virtual void push_back(BOOST_THREAD_RV_REF(value_type) x) = 0;

    virtual void pull_front(value_type&) = 0;
    virtual value_type pull_front() = 0;

    virtual queue_op_status try_push_back(const value_type& x) = 0;
    virtual queue_op_status try_push_back(BOOST_THREAD_RV_REF(value_type) x) = 0;
    virtual queue_op_status try_pull_front(value_type&) = 0;

    virtual queue_op_status nonblocking_push_back(const value_type& x) = 0;
    virtual queue_op_status nonblocking_push_back(BOOST_THREAD_RV_REF(value_type) x) = 0;
    virtual queue_op_status nonblocking_pull_front(value_type&) = 0;

    virtual queue_op_status wait_push_back(const value_type& x) = 0;
    virtual queue_op_status wait_push_back(BOOST_THREAD_RV_REF(value_type) x) = 0;
    virtual queue_op_status wait_pull_front(value_type& elem) = 0;

  };
}
