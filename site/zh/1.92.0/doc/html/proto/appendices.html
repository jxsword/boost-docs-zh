附录 A: 发布说明

Boost 1.51

解包表达式

Boost 1.51 中, Proto 获得了简单的解包模式. 在使用 Proto 变换时, 解包表达式可用于把表达式的各子节点解包进一次函数调用或一个对象构造中, 同时可选地依次对每个子节点施加某些变换.

更多信息参见 解包表达式 一节.

Boost 1.44

行为变更: proto::and_<>

在 Boost 1.44 中, proto::and_<> 作为变换的行为发生了变化. 此前, 它只应用集合中最后一个文法所关联的变换. 现在, 它会应用所有变换, 但只返回最后一个的结果. 这使其行为类似 C++ 的逗号运算符. 例如, 像这样的文法:

proto::and_< G0, G1, G2 >

当以表达式 e 求值时, 现在的行为如下:

((void)G0()(e), (void)G1()(e), G2()(e))
注释

为什么要有 void 强制转换? 这是为了避免实参依赖查找 (ADL), 它可能找到重载的逗号运算符.

行为变更: proto::as_expr() 与 proto::as_child()

函数 proto::as_expr() 与 proto::as_child() 用于保证一个对象是 Proto 表达式——若它尚不是, 则把它变成一个表达式, 可选用指定的域. 在先前版本中, 当这些函数接收到一个属于另一个域 (与指定域不同) 的 Proto 表达式时, 它们会应用指定域的生成器, 导致表达式被包装两次. 这一行为令一些用户感到意外.

这两个函数的新行为是: 无论表达式的域是什么, 一律不对 Proto 表达式做任何处理.

行为变更: proto::(pod_)generator<> 与 proto::basic_expr<>

熟悉 Proto 扩展机制的用户在定义自己的域时, 可能使用过 proto::generator<> 或 proto::pod_generator<> 搭配一个包装模板. 过去, Proto 会以 proto::expr<> 的实例来实例化你的包装模板. 在 Boost 1.44 中, Proto 现在以一个新类型的实例来实例化你的包装模板: proto::basic_expr<>.

例如:

// An expression wrapper
template<class Expr>
struct my_expr_wrapper;

// A domain
struct my_domain
  : proto::domain< proto::generator< my_expr_wrapper > >
{};

template<class Expr>
struct my_expr_wrapper
  : proto::extends<Expr, my_expr_wrapper<Expr>, my_domain>
{
  // Before 1.44, Expr was an instance of proto::expr<>
  // In 1.44, Expr is an instance of proto::basic_expr<>
};

这一变更的动机是改善编译时间. proto::expr<> 是一个实例化代价很高的类型, 因为它定义了大量成员函数. 当定义自己的表达式包装时, proto::expr<> 的实例作为隐藏数据成员驻留在你的包装中, 而 proto::expr<> 的成员却未被使用. 因此, 这些成员函数的代价被浪费了. 相比之下, proto::basic_expr<> 是一个非常轻量的类型, 没有任何成员函数.

绝大多数程序无需修改源代码即可重新编译. 但是, 如果你在某处假定将获得的一定是 proto::expr<> 的实例, 你的代码将会失效.

新特性: 子域

在 Boost 1.44 中, Proto 引入了一个重要的新特性, 称为"子域" (sub-domain). 它为你提供一种方式来指明一个域与另一个域兼容, 使得一个域中的表达式可以与另一个域中的表达式自由混合. 你可以通过使用 proto::domain<> 的第三个模板参数, 把一个域定义为另一个域的子域.

例如:

// Not shown: define some expression
// generators genA and genB

struct A
  : proto::domain< genA, proto::_ >
{};

// Define a domain B that is the sub-domain
// of domain A.
struct B
  : proto::domain< genB, proto::_, A >
{};

域 A 与 B 中的表达式可以有不同的包装 (因而有不同的接口), 但它们可以组合成更大的表达式. 若没有子域关系, 这将是一个错误. 此时所得表达式的域将是 A.

子域的完整描述见 proto::domain<> 与 proto::deduce_domain 的参考章节.

新特性: 各域专属的 as_expr() 与 as_child()

Proto 一直允许用户在定义自己的域时通过指定一个生成器来事后定制表达式. 但它从未允许用户控制 Proto 一开始如何组装子表达式. 自 Boost 1.44 起, 用户现在拥有了这一能力.

定义自己域的用户现在可以指定 proto::as_expr() 与 proto::as_child() 在其域中如何工作. 他们可以很容易地做到这一点: 在其域类中定义名为 as_expr 和/或 as_child 的嵌套类模板.

例如:

struct my_domain
  : proto::domain< my_generator >
{
  typedef
      proto::domain< my_generator >
  base_domain;

  // For my_domain, as_child does the same as
  // what as_expr does by default.
  template<class T>
  struct as_child
    : base_domain::as_expr<T>
  {};
};

在上面的例子中, my_domain::as_child<> 只是简单地把工作交给 proto::domain::as_expr<>. 这有一个很好的效果: 使所有终结符按值而非按引用捕获, 并同样按值存储子表达式. 其结果是 my_domain 中的表达式可以安全地存入 auto 变量, 因为它们不会有指向中间临时表达式的悬垂引用. (当然, 这也意味着表达式构造带有额外的运行期拷贝开销, 编译器或许能、或许不能把它优化掉.)

Boost 1.43

在 Boost 1.43 中, proto::extends<> 的推荐用法略有变化. 新用法如下:

// my_expr is an expression extension of the Expr parameter
template<typename Expr>
struct my_expr
  : proto::extends<Expr, my_expr<Expr>, my_domain>
{
    my_expr(Expr const &expr = Expr())
      : proto::extends<Expr, my_expr, my_domain>(expr)
    {}

    // NEW: use the following macro to bring
    // proto::extends::operator= into scope.
    BOOST_PROTO_EXTENDS_USING_ASSIGN(my_expr)
};

新东西是 BOOST_PROTO_EXTENDS_USING_ASSIGN() 宏的使用. 为了让赋值运算符能够构建表达式树, proto::extends<> 重载了赋值运算符. 然而, 对 my_expr 模板, 编译器会生成一个默认拷贝赋值运算符, 把 proto::extends<> 中的那些隐藏掉. 这通常不是所期望的 (尽管这取决于你想允许的语法).

此前, 推荐的用法是这样:

// my_expr is an expression extension of the Expr parameter
template<typename Expr>
struct my_expr
  : proto::extends<Expr, my_expr<Expr>, my_domain>
{
    my_expr(Expr const &expr = Expr())
      : proto::extends<Expr, my_expr, my_domain>(expr)
    {}

    // OLD: don't do it like this anymore.
    using proto::extends<Expr, my_expr, my_domain>::operator=;
};

虽然这在大多数情况下可行, 但它仍不能抑制默认赋值运算符的隐式生成. 结果, 形如 a = b 的表达式可能构建表达式模板, 也可能执行拷贝赋值, 取决于 a 与 b 的类型是否恰好相同. 这可能导致微妙的缺陷, 因此行为被改变了.

BOOST_PROTO_EXTENDS_USING_ASSIGN() 把 proto::extends<> 中定义的赋值运算符引入作用域, 同时抑制拷贝赋值运算符的生成.

另请注意, proto::literal<> 类模板 (它使用 proto::extends<>) 已改为使用 BOOST_PROTO_EXTENDS_USING_ASSIGN(). 其影响在下面的示例代码中得到强调:

proto::literal<int> a(1), b(2); // two non-const proto literals
proto::literal<int> const c(3); // a const proto literal

a = b; // No-op. Builds an expression tree and discards it.
       // Same behavior in 1.42 and 1.43.

a = c; // CHANGE! In 1.42, this performed copy assignment, causing
       // a's value to change to 3. In 1.43, the behavior is now
       // the same as above: build and discard an expression tree.

附录 C: 设计理由

静态初始化
为什么不复用 MPL、Fusion 等?

静态初始化

Proto 表达式类型是 POD (Plain Old Data), 没有构造函数. 它们按如下方式以花括号初始化:

terminal<int>::type const _i = {1};

原因是为了让上面 _i 这样的表达式对象能够 静态初始化. 为什么静态初始化很重要? 许多嵌入式领域特定语言的终结符很可能是全局 const 对象, 如 Boost Lambda 库的 _1 与 _2. 若这些对象需要运行期初始化, 就可能在它们初始化之前使用它们. 那会很糟. 静态初始化的对象不会以那种方式被误用.

为什么不复用 MPL、Fusion 等?

任何看过 Proto 源代码的人可能都想过: "为什么要这么多肮脏的预处理器垃圾? 这难道不能在 MPL 和 Fusion 之类的库之上干净地实现吗?" 答案是: Proto 本可以这样实现, 事实上曾有一度就是这样. 问题在于模板元编程 (TMP) 会导致更长的编译时间. 作为其他重 TMP 库将要构建其上的基础, Proto 自身应当尽可能轻量. 这通过优先使用预处理器元编程而非模板元编程来达成. 展开一个宏远比实例化一个模板高效. 在某些情况下, "干净"版本的编译时间比"肮脏"版本长 10 倍.

"干净但慢"的 Proto 版本仍可在 http://svn.boost.org/svn/boost/branches/proto/v3 找到. 任何有兴趣的人都可以下载并验证它编译起来确实慢得不可用. 注意该分支的开发已被放弃, 且它与 Proto 当前接口并非完全一致.

附录 D: 实现说明

快捷而粗糙的类型分类
检测函数对象的元数

快捷而粗糙的类型分类

关于在 C++ 中使用 SFINAE (替换失败不是错误) 技术按类型特征分派, 已经有很多著述. Boost 有一个库 Boost.Enable_if 使该技术成为惯用法. Proto 大量地按类型特征分派, 但它并不常使用 enable_if<>. 相反, 它依据嵌套类型的存在与否来分派——通常是为 void 的 typedef.

考虑 is_expr<> 的实现. 它本可以写成类似这样:

template<typename T>
struct is_expr
  : is_base_and_derived<proto::some_expr_base, T>
{};

而它实际上是这样实现的:

template<typename T, typename Void = void>
struct is_expr
  : mpl::false_
{};

template<typename T>
struct is_expr<T, typename T::proto_is_expr_>
  : mpl::true_
{};

这依赖于如下事实: 若 T 有一个嵌套的 proto_is_expr_, 且它是 void 的 typedef, 则该特化会被优先选择. 所有 Proto 表达式类型都有这样的嵌套 typedef.

Proto 为什么这样做? 原因是, 在为改善编译时间而运行大量基准测试之后, 我发现这种方式编译更快. 它恰好只需要一次模板实例化. 另一种方式至少需要两次: is_expr<> 与 is_base_and_derived<>, 加上 is_base_and_derived<> 可能实例化的任何模板.

检测函数对象的元数

在若干地方, Proto 需要知道函数对象 Fun 是否可以用某些参数调用, 若不能则采取后备动作. 这发生在 proto::callable_context<> 与 proto::call<> 变换中. Proto 如何知道? 这涉及一些巧妙的元编程. 下面是做法.

换一种方式提出这个问题: 尝试实现以下 can_be_called<> 布尔元函数, 它检查函数对象 Fun 是否可以用 A 与 B 类型的参数调用:

template<typename Fun, typename A, typename B>
struct can_be_called;

首先, 我们定义以下 dont_care 结构体, 它有一个从任何东西而来的隐式转换. 而且不是随便什么隐式转换; 它是一个省略号转换——就重载决议而言这是最差的转换:

struct dont_care
{
    dont_care(...);
};

我们还需要一些只有我们自己知道的私有类型, 带有重载的逗号运算符 (!), 以及一些检测该类型存在并返回不同大小类型的函数, 如下:

struct private_type
{
    private_type const &operator,(int) const;
};

typedef char yes_type;      // sizeof(yes_type) == 1
typedef char (&no_type)[2]; // sizeof(no_type)  == 2

template<typename T>
no_type is_private_type(T const &);

yes_type is_private_type(private_type const &);

接下来, 我们实现一个二元函数对象包装, 它带有一个非常奇怪的转换运算符, 其含义稍后会变清楚.

template<typename Fun>
struct funwrap2 : Fun
{
    funwrap2();
    typedef private_type const &(*pointer_to_function)(dont_care, dont_care);
    operator pointer_to_function() const;
};

有了所有这些零件, 我们就可以如下实现 can_be_called<>:

template<typename Fun, typename A, typename B>
struct can_be_called
{
    static funwrap2<Fun> &fun;
    static A &a;
    static B &b;

    static bool const value = (
        sizeof(no_type) == sizeof(is_private_type( (fun(a,b), 0) ))
    );

    typedef mpl::bool_<value> type;
};

想法是: 通过添加我们自己的二元函数重载, 使 fun(a,b) 总能编译, 但要以一种能检测我们的重载是否被选中的方式来做. 而且我们做了手脚, 使我们的重载只在确实没有更好选项时才被选中. 以下描述 can_be_called<> 如何工作.

我们把 Fun 包装在一个可以隐式转换为二元函数指针的类型中. 类类型的对象 fun 若有这样的转换运算符, 就可以像 fun(a, b) 那样被调用, 但由于它涉及用户定义的转换运算符, 它不如重载的 operator() 受青睐——后者不需要这样的转换.

得益于 dont_care 类型, 该函数指针可以接受任何两个实参. 每个实参的转换序列保证是最差的转换序列: 经由省略号的隐式转换, 加上到 dont_care 的用户定义转换. 总体而言, 这意味着 funwrap2<Fun>()(a, b) 总能编译, 但只有确实没有更好选项时才会选中我们的重载.

如果有更好的选项——例如 Fun 有一个像 void operator()(A a, B b) 这样的重载函数调用运算符——则 fun(a, b) 将改为解析到那个. 现在的问题是如何检测重载决议选中了哪个函数.

注意 fun(a, b) 如何出现在 can_be_called<> 中: (fun(a, b), 0). 为什么我们在那里使用逗号运算符? 原因是我们把这个表达式用作函数的实参. 若 fun(a, b) 的返回类型是 void, 它就不能合法地用作函数实参. 逗号运算符绕开了这个问题.

这也应当使 private_type 中重载逗号运算符的用意一目了然. 指向函数的指针的返回类型是 private_type. 若重载决议选中我们的重载, 则 (fun(a, b), 0) 的类型是 private_type. 否则是 int. 这一事实用于分派到 is_private_type() 的两个重载之一, 该重载把答案编码在其返回类型的大小中.

这就是二元函数的工作方式. 现在, 对函数重复上述过程直至某个预定义的函数元数, 就完成了.
