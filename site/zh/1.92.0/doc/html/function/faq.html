常见问题 (FAQ)

1. 为什么不能用 operator== 或 operator!= 比较 boost::function 对象?
2. 我看到 void 指针; 这堆东西是类型安全的吗?
3. 为什么要有针对 void 返回的变通处理? C++ 是允许它们的!
4. 为什么采用 (函数) 克隆?
5. 通过 boost::function 进行调用会产生多少开销?

1.

为什么 boost::function 对象不能与 operator== 或 operator!= 进行比较?

boost::function 对象之间的比较无法 "良好" 实现, 因此不会被实现. 对于 f == g, 在给定的 boost::function 对象 f 和 g 情况下, 典型要求的语义是:

  • 如果 f 和 g 存储的是同一类型的函数对象, 则使用该类型的 operator== 来比较它们.
  • 如果 f 和 g 存储的是不同类型的函数对象, 则返回 false.

当 f 和 g 所存储的函数对象的类型没有 operator== 时, 问题就出现了: 我们希望表达式 f == g 无法通过编译, 就像标准容器那样. 然而, 对 boost::function 来说这无法实现, 因为它在被赋予函数对象后必然 "擦除" 部分类型信息, 因此无法稍后再尝试调用 operator==: 它要么现在就找到调用 operator== 的办法, 要么以后永远无法调用它. 例如, 注意一下当你试图把一个 float 值放入 boost::function 对象时会发生什么: 你会在赋值运算符或构造函数处得到错误, 而不是在 operator() 中, 因为函数调用表达式必须在构造函数或赋值运算符中绑定.

最有希望的方法是找到一种手段来判断是否可以对特定类型调用 operator==, 然后仅在其可用时提供支持; 在其他情况下则抛出异常. 然而, 迄今为止尚无已知方法可以检测任意运算符表达式 f == g 是否被适当地定义. 已知的最佳方案存在以下不理想的性质:

  1. 对于 operator== 不可访问的对象 (例如因为它被声明为 private), 在编译期失败.
  2. 如果调用 operator== 有歧义, 则在编译期失败.
  3. 如果 operator== 声明正确, 即使 operator== 可能无法编译, 看起来也是正确的.

所有这些问题都会转化为 boost::function 构造函数或赋值运算符中的失败, 即使用户从不调用 operator== 也一样. 我们不能这样对待用户.

另一种选择是把负担加在想要使用 operator== 的用户身上, 例如提供一个可供他们特化的 is_equality_comparable 特征. 这是一个可行的方案, 但在实践中很危险, 因为忘记特化该特征会导致 boost::function 的 operator== 抛出意料之外的异常. 这基本上否定了 operator== 在其最被需要的场景中的用处: 多目标回调. Signals 库有绕过该问题的办法.

2.

我看到 void 指针; 这堆东西是类型安全的吗?

是的, boost::function 是类型安全的, 尽管它使用了 void 指针以及指向无参数、返回 void 的函数的指针. 从本质上说, 所有类型信息都编码在管理和调用函数指针与函数对象的那些函数中. 只有这些函数才会以 void 指针或指向 void 函数的指针所指向的精确类型进行实例化. 两者都需要的原因是: 在 void 指针与对象指针之间可以安全地转换, 或在不同类型的函数指针之间转换 (前提是你不会以错误的类型调用函数指针).

3.

为什么要有针对 void 返回的变通处理? C++ 是允许它们的!

C++ 标准允许 void 返回, 如以下代码片段:

void f();
void g() { return f(); }

这是 boost::function 的有效用法, 因为没有使用 void 返回. 如果使用 void 返回, 我们将尝试编译类似于以下的非良构代码:

int f();
void g() { return f(); }

从本质上说, 不使用 void 返回可以让 boost::function 吞掉一个返回值. 这与允许用户赋值并调用参数不完全匹配的函数和函数对象是一致的.

4.

为什么采用 (函数) 克隆?

2000 年 11 月和 12 月, 克隆与引用计数之争经过了深入讨论, 最终决定采用克隆, 因为它提供更可预测的语义. 我不打算在此重述讨论过程, 但如果克隆对某个特定应用不合适, 可以使用引用计数分配器.

5.

通过 boost::function 进行调用会产生多少开销?

在 >2GHz 的现代平台上, 与直接内联代码相比, boost::function 的开销可以相当一致地测得约为 20ns +/- 10 ns.

不过, 应用程序的性能可能因 boost::function 而受益或受损, 这取决于你的 C++ 优化器如何进行优化. 与标准函数指针类似, 根据编译环境的不同, 使用 boost::function 调用包含紧凑循环的函数时, 曾观察到约 10% 量级的性能差异, 有利也有弊.
