用户级连接管理

用户需要对信号到槽的连接及其最终断开有精细的控制. Boost.Signals2 采取的主要做法是返回一个 signals2::connection 对象, 该对象支持已连接/已断开查询、手动断开, 以及析构时自动断开模式 (signals2::scoped_connection). 此外, signal::disconnect 重载方法还支持另外两种接口:

  • 把槽传给 disconnect: 在这一接口模型中, 对用 sig.connect(typeof(sig)::slot_type(slot_func)) 连接的槽的断开通过 sig.disconnect(slot_func) 执行. 内部会使用槽比较进行一次线性搜索, 若找到该槽则将其从列表中移除. 遗憾的是, 查询连接状态最终成为一个线性时间操作.

  • 把令牌传给 disconnect: 这种方法用一个易于比较的令牌 (例如字符串) 来标识槽, 从而允许槽是任意的函数对象. 虽然这种方法在本质上等价于 Boost.Signals2 所采用的连接方式, 但由于以下几个原因, 它可能更容易出错:

    • 连接与断开必须成对出现, 于是问题就变得类似于在动态内存分配中配对 new 和 delete 时遇到的问题. 虽然这类错误对信号槽实现而言并非灾难性的, 但对它们的检测通常并不容易.

    • 如果令牌不唯一, 两个槽可能同名而无法区分. 在会动态建立大量连接的环境中, 名称生成成了用户的额外任务.

    Boost.Signals2 通过槽分组机制以及 signal::disconnect 的重载 (接受信号 Group 类型的实参) 来支持这类接口.

自动连接管理

Signals2 中的自动连接管理依赖于使用 boost::shared_ptr 来管理被跟踪对象的生命期. 这不同于原始的 Boost.Signals 库, 后者依赖的是从 boost::signals::trackable 类派生. 库会通过 boost::signals::trackable 析构函数得到对象销毁的通知.

遗憾的是, 由于析构顺序的原因, boost::signals::trackable 方案无法做到线程安全. 派生自 boost::signals::trackable 的类的析构函数总是在基类 boost::signals::trackable 的析构函数之前被调用. 然而, 为了线程安全, 信号与对象之间的连接需要在对象运行其析构函数之前断开. 否则, 若在一个线程中被销毁的对象连接到一个正在另一线程中并发调用的信号, 该信号可能调用到一个部分销毁的对象.

我们通过要求被跟踪对象由 shared_ptr 管理来解决这个问题. 槽为其依赖的每个对象保留一个 weak_ptr. 当槽所跟踪的任何 weak_ptr 过期时, 与该槽的连接就会断开. 此外, 信号在调用槽之前会为槽的所有被跟踪对象创建自己的临时 shared_ptr. 这确保没有任何被跟踪对象在调用中途析构.

新的连接管理方案具有非侵入式的优点. 任何类型的对象都可以用 shared_ptr/weak_ptr 方案来跟踪. 旧的 boost::signals::trackable 方案要求被跟踪对象派生自 trackable 基类, 而在与第三方库的类交互时这并不总是可行的.

optional_last_value 作为默认合并器

Boost.Signals2 的默认合并器已从原始 Boost.Signals 库默认使用的 last_value 合并器变更而来. 这是因为 last_value 要求在信号被调用时至少连接了 1 个槽 (last_value<void> 特化除外). 在信号调用与槽的连接、断开可能并发发生的多线程环境中, 这一要求难以满足. 使用 optional_last_value 时, 则不要求信号被调用时有槽连接, 因为在这种情况下合并器可以简单地返回一个空的 boost::optional.

合并器接口

选择合并器接口是为了模仿对 C++ 标准库中算法的调用. 我们认为, 把槽调用结果看作仅是由输入迭代器访问的一个值序列, 合并器接口对熟练的 C++ 程序员而言将是最自然的. 相互竞争的接口设计通常要求把合并器构造为遵循一个专为 (且仅限于) Signals2 库定制的接口. 虽然这些接口通常能让信号槽库的实现更直接, 但遗憾的是合并器不可复用 (既不能在其他信号槽库中复用, 也不能在其他泛型算法中复用), 并且学习曲线也因需要学习特定的合并器接口而略微变陡.

Signals2 对合并器的表述基于合并器使用 "拉取" (pull) 式通信, 而不是更复杂的 "推送" (push) 机制. 在 "拉取" 机制下, 合并器的状态可以保存在栈上和程序计数器中, 因为每当需要新数据时 (即调用下一个槽以获取其返回值), 都有一个简单的接口可以立即获取该数据, 而无须从合并器的代码中返回. 与之对比, 在 "推送" 机制下, 合并器必须把所有状态保存在类成员中, 因为每次信号被调用时都会调用合并器的例程. 例如, 比较一个返回调用各槽所得最大元素的合并器: 若最大元素超过 100, 则不再调用更多槽.

推送

 
struct pull_max {
  typedef int result_type;

  template<typename InputIterator>
  result_type operator()(InputIterator first,
                         InputIterator last)
  {
    if (first == last)
      throw std::runtime_error("Empty!");

    int max_value = *first++;
    while(first != last && *first <= 100) {
      if (*first > max_value)
        max_value = *first;
      ++first;
    }

    return max_value;
  }
};

struct push_max {
  typedef int result_type;

  push_max() : max_value(), got_first(false) {}

  // returns false when we want to stop
  bool operator()(int result) {
    if (result > 100)
      return false;

    if (!got_first) {
      got_first = true;
      max_value = result;
      return true;
    }

    if (result > max_value)
      max_value = result;

    return true;
  }

  int get_value() const
  {
    if (!got_first)
      throw std::runtime_error("Empty!");
    return max_value;
  }

private:
  int  max_value;
  bool got_first;
};

这些例子中有几点值得注意. "拉取" 版本是一个可复用的函数对象, 基于带有整数 value_type 的输入迭代器序列, 设计非常直接. 而 "推送" 模型依赖于一个特定于调用方的接口, 一般不可复用. 它还需要额外的状态值来判断, 例如, 是否已经收到任何元素. 虽然代码质量和易用性通常带有主观性, 但 "拉取" 模型显然更短且更可复用, 即使在信号槽库的语境之外, 通常也会被认为更容易编写和理解.

"拉取" 式合并器接口的代价由 Signals2 库自身的实现来支付. 为了正确处理调用期间的槽断开 (例如, 当解引用运算符被调用时), 必须构造能够跳过已断开槽的迭代器. 此外, 迭代器必须随身携带传递给每个槽的实参集合 (尽管使用一个包含这些实参的结构的引用即可), 并且必须缓存调用槽的结果, 以免多次解引用导致多次调用. 这显然需要相当大的开销, 不过若考虑调用槽的整个过程, 就会看到这一开销与 "推送" 模型中的开销几乎等价, 只是我们把控制结构倒了过来, 让迭代和解引用变得复杂 (而不是让合并器状态的确定变得复杂).

连接接口: += 运算符

Boost.Signals2 支持形如 sig.connect(slot) 的连接语法, 但也有人建议使用更简洁的语法 sig += slot (并且已被其他信号槽实现采用). 之所以拒绝这种语法, 有以下几个原因:

  • 没有必要: Boost.Signals2 提供的连接语法在能力上并不逊于 += 运算符所提供的. 少敲几个字 (connect() 与 += 之别) 基本上可以忽略不计. 此外, 可以说调用 connect() 比 += 的重载更具可读性.

  • 返回类型有歧义: += 运算的返回值存在歧义: 它应当是对信号本身的引用 (以便支持 sig += slot1 += slot2), 还是应当为新建的信号/槽连接返回一个 signals2::connection?

  • 通向 -= 和 + 运算符的大门: 一旦增加了连接运算符 +=, 似乎顺理成章地应当有一个断开运算符 -=. 然而, 当库允许任意函数对象隐式成为槽时, 这会带来问题, 因为槽不再可比较.

    有了 operator+= 之后, 第二个显而易见的补充是增加一个支持把多个槽相加、随后赋值给信号的 + 运算符. 然而, 这要求实现 + 使之能接受任意两个函数对象, 这在技术上不可行.

Signals2 互斥量类

Boost.Signals2 库提供了两个互斥量类: boost::signals2::mutex 和 boost::signals2::dummy_mutex. 提供 boost::signals2::mutex 的动机很简单: Boost.Thread 库目前提供的 boost::mutex 类需要链接 libboost_thread. boost::signals2::mutex 类使 Signals2 得以保持为仅头文件库. 如果你愿意, 仍然可以选择使用 boost::mutex, 方法是把它指定为信号的 Mutex 模板类型.

提供 boost::signals2::dummy_mutex 类是为了让对性能敏感的单线程应用能够通过避免不必要的互斥量加锁来把开销降到最低.

与其他信号/槽实现的比较

libsigc++

libsigc++ 是一个 C++ 信号槽库, 最初是一项用 C++ 封装 GTK 库 C 接口的行动的一部分, 后来发展为由 Karl Nelson 维护的独立库. libsigc++ 与 Boost.Signals2 有许多相似之处, 事实上原始的 Boost.Signals 曾深受 Karl Nelson 和 libsigc++ 的影响. 对两个库的粗略考察会发现, 在信号的构造和连接的使用方面有类似的语法. 但在设计上存在一些把这两个库区分开来的重大差异:

  • 槽的定义: libsigc++ 中的槽使用库定义的一组原语来创建. 这些原语允许绑定对象 (作为库的一部分), 并把信号的实参和返回类型显式适配为槽的实参和返回类型 (libsigc++ 默认在类型方面比 Boost.Signals2 更严格).

  • 合并器/编排器接口: libsigc++ 中与 Boost.Signals2 合并器对应的是编排器 (marshaller). 编排器类似于合并器接口一节所述的 "推送" 接口, 对该主题的恰当讨论见该节.

.NET 委托

Microsoft 引入了 .NET Framework 以及一组相关联的语言和语言扩展, 其中之一就是委托 (delegate). 委托与信号槽相似, 但比大多数 C++ 信号槽实现更受限, 因为它们:

  • 要求委托与其调用对象之间精确的类型匹配.

  • 只返回最后被调用的目标的结果, 没有定制选项.

  • 必须调用一个已绑定 this 的方法.
