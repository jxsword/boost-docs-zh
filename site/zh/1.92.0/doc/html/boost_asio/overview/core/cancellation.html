按操作取消

注释

这些类型要求和类是取消机制的底层构件. 对于大多数用例, 请考虑使用更高层的抽象, 例如 experimental::make_parallel_group 或 逻辑运算符 (针对 awaitable) .

套接字和定时器等 I/O 对象通过其 close 或 cancel 成员函数支持对未完成异步操作的对象级取消. 但是, 某些异步操作还支持单个的、有针对性的取消. 这种按操作取消是通过指定完成处理器拥有一个满足 CancellationSlot 类型要求的关联取消槽来启用的. 取消槽是用于传递取消请求的轻量级通道.

给定一个用户自定义 Handler 对象 h 的副本, 如果异步操作支持取消, 它将使用 get_associated_cancellation_slot 函数获取一个取消槽. 例如:

boost::asio::associated_cancellation_slot_t<Handler> s
  = boost::asio::get_associated_cancellation_slot(h);

关联取消槽必须满足 CancellationSlot 类型要求.

默认情况下, 处理器使用默认构造的 cancellation_slot, 这意味着按操作取消被禁用. 可以针对特定的处理器类型定制取消槽, 方法是指定嵌套类型 cancellation_slot_type 和成员函数 get_cancellation_slot():

class my_handler
{
public:
  // Custom implementation of CancellationSlot type requirements.
  typedef my_cancellation_slot cancellation_slot_type;

  // Return a custom cancellation slot implementation.
  cancellation_slot_type get_cancellation_slot() const noexcept
  {
    return my_cancellation_slot(...);
  }

  void operator()() { ... }
};

在更复杂的情况下, 可以直接对 associated_cancellation_slot 模板进行偏特化:

namespace boost { namespace asio {

  template <typename CancellationSlot>
  struct associated_cancellation_slot<my_handler, CancellationSlot>
  {
    // Custom implementation of CancellationSlot type requirements.
    typedef my_cancellation_slot type;

    // Return a custom cancellation_slot implementation.
    static type get(const my_handler&,
        const CancellationSlot& a = CancellationSlot()) noexcept
    {
      return my_cancellation_slot(...);
    }
  };

} } // namespace boost::asio

为方便起见, 可以使用 bind_cancellation_slot 函数把取消槽与处理器关联. 在把取消槽与 lambda 关联时这一做法尤其有用:

boost::asio::async_read(my_socket, my_buffer,
    boost::asio::bind_cancellation_slot(
      my_cancellation_slot,
      [](boost::system::error_code e, std::size_t n)
      {
        ...
      }
    )
  );

Boost.Asio 以 cancellation_slot 及其对应物 cancellation_signal 的形式提供了一个开箱即用的取消槽. 这两个类实现了生产者 (signal) 与消费者 (slot) 接口的一对一配对. 下面的例子展示了其用法:

class session
  : public std::enable_shared_from_this<proxy>
{
  ...

  void do_read()
  {
    auto self = shared_from_this();
    socket_.async_read_some(
        buffer(data_),
        boost::asio::bind_cancellation_slot(
          cancel_signal_.slot(),
          [self](boost::system::error_code error, std::size_t n)
          {
            ...
          }
        )
      );
  }

  ...

  void request_cancel()
  {
    cancel_signal_.emit(boost::asio::cancellation_type::total);
  }

  ...

  boost::asio::cancellation_signal cancel_signal_;
};

cancellation_signal 只包含一个槽, 因此一个取消 signal/slot 对一次至多只能用于一个操作. 不过, 同一个槽可以在后续操作中重复使用.

为支持取消, 异步操作会通过调用槽的 assign 或 emplace 函数, 把一个取消处理器安装到槽中. 当发出取消信号时, 该处理器将被调用. 一个槽一次恰好持有一个处理器, 安装新处理器会覆盖之前安装的任何处理器.

发出取消信号时, 调用者必须指定一个取消类型 (cancellation type) . 该值是一个位掩码, 规定取消目标在成功取消时必须作出哪些保证. 可能的位值按保证从最弱到最强排列如下:

表 1. 取消类型

位

取消成功时的保证

这是所支持的最强保证的示例

terminal

操作有未指明的副作用, 只有关闭或销毁 I/O 对象才是安全的.

消息组帧协议的有状态实现, 其中异步操作发送或接收一条完整消息. 如果在消息正文的中途发生取消, 就不可能向完成处理器报告一个有意义的状态.

partial

操作有明确定义的副作用, 且该操作的完成处理器会指明这些副作用是什么.

诸如 async_read 和 async_write 之类的组合操作. 如果在所有字节传输完成之前发生取消, 完成处理器会收到迄今为止已传输的总字节数. 调用者可以利用这一信息启动另一个操作来传输剩余的字节.

total

操作没有可以通过 API 观察到的副作用.

传输零个或非零个字节的底层系统调用.

等待就绪的操作, 即使成功也没有副作用.

完全缓冲的消息组帧协议实现, 其中部分消息被存储起来以便在下一次操作中复用.

例如, 如果应用程序逻辑要求操作以全有或全无 (all-or-nothing) 的副作用完成, 那么它应当只发出 total 取消类型. 如果目标操作不支持这一类型, 则不会发生取消.

此外, 较强的保证总是满足较弱保证的要求. partial 保证仍然满足 terminal 保证. total 保证同时满足 partial 和 terminal. 这意味着当操作把某个取消类型作为其最强保证加以支持时, 它应当尊重针对任何较弱保证的取消请求.

不应在异步操作的发起函数期间发出取消请求. 在操作开始之前发出的取消请求没有效果; 同样, 在完成之后发出的取消请求也没有效果.

发出取消信号时, 线程安全规则的适用方式就如同在目标操作的 I/O 对象上调用成员函数一样. 对于非组合操作, 这意味着只要没有其他对 I/O 对象的并发调用、也没有其他并发的取消信号请求, 从任何线程发出取消信号都是安全的. 对于组合操作, 必须注意确保取消请求不与操作的中间完成处理器并发发生.

受支持的操作

关于各个异步操作支持哪些取消类型 (如果支持) , 请查阅其文档. 目前支持取消单个操作或组合操作的有:

  • 定时器
  • POSIX 与 Windows 上的套接字
  • POSIX 描述符
  • Windows HANDLE
  • 信号集
  • 串口
  • SSL 流
  • Boost.Asio 提供的所有组合操作, 例如 async_read 和 async_write
  • 基于 async_compose 的组合
  • 使用 awaitable 的 C++20 协程
  • 使用 experimental::coro 的 C++20 协程
  • experimental::parallel_group 操作
  • experimental::promise 类
