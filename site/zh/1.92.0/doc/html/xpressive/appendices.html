附录 3: 与 Boost.Regex 的差异

由于 xpressive 的许多用户很可能已熟悉 Boost.Regex 库, 如果我不指出 xpressive 与 Boost.Regex 之间的一些重要差异, 便是我的疏失. 具体包括:

  • xpressive::basic_regex<> 是以迭代器类型而非字符类型为模板参数的.
  • xpressive::basic_regex<> 不能直接从字符串构造; 相反, 必须使用 basic_regex::compile() 或 regex_compiler<> 来从字符串构建正则对象.
  • xpressive::basic_regex<> 没有 imbue() 成员函数; 相反, imbue() 成员函数位于 xpressive::regex_compiler<> 工厂中.
  • boost::basic_regex<> 拥有 std::basic_string<> 成员的一个子集. xpressive::basic_regex<> 则不然. 缺少的成员有: assign(), operator[](), max_size(), begin(), end(), size(), compare(), 以及 operator=(std::basic_string<>).
  • boost::basic_regex<> 中存在但 xpressive::basic_regex<> 中不存在的其他成员函数有: set_expression(), get_allocator(), imbue(), getloc(), getflags(), 和 str().
  • xpressive::basic_regex<> 没有 RegexTraits 模板参数. 正则语法和本地化行为的定制将由 regex_compiler<> 以及 std::locale 的自定义正则刻面来控制.
  • xpressive::basic_regex<> 和 xpressive::match_results<> 没有 Allocator 模板参数. 这是设计使然.
  • match_not_dot_null 和 match_not_dot_newline 已从 match_flag_type 枚举移至 syntax_option_type 枚举, 并更名为 not_dot_null 和 not_dot_newline.
  • 不支持以下 syntax_option_type 枚举值: escape_in_lists, char_classes, intervals, limited_ops, newline_alt, bk_plus_qm, bk_braces, bk_parens, bk_refs, bk_vbar, use_except, failbit, literal, perlex, basic, extended, emacs, awk, grep, egrep, sed, JavaScript, JScript.
  • 不支持以下 match_flag_type 枚举值: match_not_bob, match_not_eob, match_perl, match_posix, 以及 match_extra.

另外, 在当前实现中, xpressive 的正则算法不会检测病态行为并通过抛出异常而中止. 编写不会出现病态行为的高效模式取决于你自己.

xpressive 的性能与 Boost.Regex 相当. 我在两个平台 (gcc (Cygwin) 和 Visual C++) 上运行了比较静态 xpressive、动态 xpressive 与 Boost.Regex 的性能基准测试. 测试包括短匹配和长搜索. 在两个平台上, xpressive 在短匹配方面表现出色, 在长搜索方面与 Boost.Regex 大致相当.

附录 5: 实现说明

环收集: tracking_ptr<>

环收集: tracking_ptr<>

在 xpressive 中, 正则对象可以按值或按引用相互引用和自引用. 此外, 它们会对所引用的正则进行引用计数以使其保活. 这就可能产生循环的引用计数, 并带来内存泄漏的可能性. xpressive 通过使用一种名为 tracking_ptr<> 的类型来避免泄漏. 本文从较高层面描述 tracking_ptr<> 的工作原理.

约束条件

我们的解决方案必须满足以下设计约束:

  • 无悬空引用: 直接或间接引用的所有对象, 只要有引用存在就必须保活.
  • 无泄漏: 所有对象最终都必须被释放.
  • 无需用户干预: 解决方案不得要求用户显式调用某个环收集例程.
  • 清理不抛出异常: 收集阶段很可能从析构函数中被调用, 因此在任何情况下都不得抛出异常.

Handle-Body 惯用法

要使用 tracking_ptr<>, 必须把你的类型分离为句柄 (handle) 和主体 (body). 在 xpressive 中, 句柄类型名为 basic_regex<>, 主体名为 regex_impl<>. 句柄中将保存一个指向主体的 tracking_ptr<>.

主体类型必须继承自 enable_reference_tracking<>. 这为主体提供了 tracking_ptr<> 将要使用的簿记数据结构. 具体而言, 它为主体提供:

  1. std::set<shared_ptr<body> > refs_ : 本主体所引用的主体的集合, 以及
  2. std::set<weak_ptr<body> > deps_ : 引用本主体的主体的集合.

引用与依赖

我们把上面的 (1) 称为 “引用” (references), 把 (2) 称为 “依赖” (dependencies). 理解 tracking_ptr<> 的关键在于认识到: 引用集合既包括直接引用的对象, 也包括间接引用的对象 (即经由另一个引用). 依赖集合亦然. 换言之, 每个主体都直接持有它所需的每个其他主体的引用计数.

为什么这一点很重要? 因为它意味着, 当某个主体不再有句柄引用它时, 它的所有引用都可以立即释放, 而不必担心产生悬空引用.

引用和依赖会交叉传播. 其工作方式如下:

  1. 当一个对象作为引用获取另一个对象时, 第二个对象便将第一个对象作为依赖获取.
  2. 此外, 第一个对象会获取第二个对象的全部引用, 第二个对象会获取第一个对象的全部依赖.
  3. 当某个对象获得新引用时, 该引用也会被添加到所有依赖对象中.
  4. 当某个对象获得新依赖时, 该依赖也会被添加到所有被引用对象中.
  5. 对象永远不允许把自身作为依赖. 对象可以把自身作为引用, 而且通常正是如此.

考虑如下代码:

sregex expr;
{
    sregex group  = '(' >> by_ref(expr) >> ')';                 // (1)
    sregex fact   = +_d | group;                                // (2)
    sregex term   = fact >> *(('*' >> fact) | ('/' >> fact));   // (3)
    expr          = term >> *(('+' >> term) | ('-' >> term));   // (4)
}                                                               // (5)

fact: cnt=2 refs={expr,group} deps={term}
term: cnt=1 refs={expr,group,fact} deps={}

4) expr = term >> *(('+' >> term) | ('-' >> term));

group: cnt=5 refs={expr,group,fact,term} deps={expr,fact,term}
expr: cnt=5 refs={expr,group,fact,term} deps={group,fact,term}
fact: cnt=5 refs={expr,group,fact,term} deps={expr,group,term}
term: cnt=5 refs={expr,group,fact,term} deps={expr,group,fact}

5) }

expr: cnt=2 refs={expr,group,fact,term} deps={group,fact,term}

这展示了创建对象环时引用和依赖如何传播. 在闭合这个环的第 (4) 行之后, 每个对象对每个其他对象都有一个引用计数, 甚至对自身也是如此. 那么这为什么不会泄漏? 请继续阅读.

打破环

至此, 主体已拥有其引用集合和依赖集合, 最难的部分已经完成. 剩下的只是决定何时何地打破环. 这正是 tracking_ptr<> 的职责, 它是句柄的一部分. tracking_ptr<> 持有 2 个 shared_ptr. 第一个显然是 shared_ptr<body> -- 即指向本句柄所指主体的引用. 另一个 shared_ptr 用于打破环. 它确保当一个主体的所有句柄都离开作用域时, 该主体的引用集合被清空.

这意味着可以有多个句柄指向同一个主体. 实际上, tracking_ptr<> 为你提供写时复制 (copy-on-write) 语义 -- 复制句柄时, 主体是共享的. 这使得复制非常高效. 最终, 指向某个主体的所有句柄都会离开作用域. 此时, 指向该主体的引用计数可能仍大于 0, 因为其他某个主体 (或该主体自身!) 可能仍持有对它的引用. 但是, 我们可以确定环打破者的引用计数会降至 0, 因为环打破者只存在于句柄中. 没有句柄, 就没有环打破者.

环打破者做什么? 回想一下, 主体有一个类型为 std::set<shared_ptr<body> > 的引用集合. 我们把这个类型称为 “references_type”. 环打破者是一个 shared_ptr<references_type>. 它使用一个自定义删除器, 定义如下:

template<typename DerivedT>
struct reference_deleter
{
    void operator ()(std::set<shared_ptr<DerivedT> > *refs) const
    {
        refs->clear();
    }
};

环打破者的职责是确保当指向某个主体的最后一个句柄消失时, 该主体的引用集合被清空. 仅此而已.

我们可以清楚地看到这如何保证所有主体最终都被清理. 一旦每个句柄都离开作用域, 所有主体的引用集合都将被清空, 没有任何主体的引用计数非零. 不会泄漏, 可以保证.

要看出这如何保证没有悬空引用就有点难了. 设想有 3 个主体: A、B 和 C. A 引用 B, B 引用 C. 现在所有指向 B 的句柄都离开作用域, 于是 B 的引用集合被清空. 这是否意味着 C 会被删除, 尽管它正被 A (间接) 使用? 不会的. 这种情况永远不会发生, 因为我们在前面传播引用和依赖时, 已使 A 除持有对 B 的引用外还直接持有对 C 的引用. 当 B 的引用集合被清空时, 不会有任何主体被删除, 因为它们都仍被 A 使用.

后续工作

这么多 std::set、shared_ptr 和 weak_ptr! 效率非常低. 我使用它们只是因为它们很方便. 我大概可以做得更好.

另外, 有些对象存续的时间超过其必要时间. 考虑:

sregex b;
{
    sregex a = _;
    b = by_ref(a);
    b = _;
}
// a is still alive here!

由于引用和依赖的传播方式, 引用的 std::set 只会增长. 即使某些引用不再需要, 它也从不收缩. 对 xpressive 而言这不是问题. 引用型对象的图通常保持很小且相互隔离. 如果有人试图把 tracking_ptr<> 用作通用的引用计数环收集机制, 就必须解决这个问题.
