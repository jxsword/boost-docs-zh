跨编译器的 ABI 可移植性

在讨论本库的过程中, 很多问题都围绕 ABI 稳定性以及库是否应当对此负责. 结论是: 让 ABI 稳定或许是有用的特性, 但会增加大量开销并使库的使用变得不那么简单. 对于不需要跨编译器 ABI 稳定性的用户来说, 这样的特性纯属过度设计.

最终决定把本库做得更简单、更底层, 从而既能为有需要的用户构建 ABI 稳定的插件系统, 又不给其他用户增加开销.

用户的插件 API

现存一些开放的 C++ 插件系统. 它们大多强制用户使用某种预定义的 API. 问题在于, 这些 API 彼此各不相同.

为了更实用, Boost.DLL 不强制任何 API. 由用户自行设计合适的 API.

性能与内存分配

库的某些方法接受 boost::filesystem::path 或返回 std::vector<std::string>. 初看这似乎不优化, 但这样做是有原因的.

boost::filesystem::path 允许以透明方式将 Unicode 字符串与非 Unicode 字符串混用. 采用它为库提供了对用户更友好的接口, 而性能开销并不明显, 因为接受 boost::filesystem::path 的方法中发生的文件系统操作本来就很慢.

std::vector<std::string> 变量由 library_info 方法返回. 查询库本身就是缓慢的过程: 它会随机读取磁盘上文件的部分内容, 并执行复杂度有时随节或导出符号数量呈线性增长的算法. 返回 std::vector<std::string> 可以简化实现, 也不要求用户在查询后保存一个 library_info 实例. 在很少调用的方法中引入不太明显的性能开销, 似乎是合理的.

其他方法被视为热路径, 已尽可能优化.

自加载

通过 shared_library(program_location()) 实现自加载, 而不是提供某种 shared_library::load_self() 成员方法, 有一个很重要的原因: 必须能够从任何位置调用 shared_library(this_line_location()), 甚至从主程序中调用. 我们需要这一点来把插件链接进二进制文件并建立透明的引用计数机制.

提供多个功能完全相同的接口在我看来并不合理, 因此 shared_library(program_location()) 与 shared_library(this_line_location()) 在不使用 shared_library::load_self() 的情况下使用.

别名 vs 修饰名

修饰 (mangling) 取决于源代码, 例如 "boost::foo" 可能是 foo 函数, 也可能是 foo 变量. 依据这一点, 必须以不同方式对其修饰. 若 foo 是接受参数的重载函数, 问题会更多: "boost::foo(variant<int, short>)". 此时必须指明参数的完整名称, 它可能是 boost::variant<int, short> 或 variant<int, short, void_, void_> ...

曾有一个想法: 让用户前置声明函数, 并据此生成修饰名:

namespace boost { void foo(variant<int, short>); }

std::string mangled_name = boost::dll::magic_mangle(boost::foo);

但这个想法彻底失败了, 原因是链接器的问题, 以及在编译期无法从编译器内部可靠地取得修饰符号名.

因此别名被认为是两害相权取其轻的选择:

BOOST_DLL_ALIAS(boost::foo, foo_variant) // in plugin
"foo_variant" // in plugin importer
