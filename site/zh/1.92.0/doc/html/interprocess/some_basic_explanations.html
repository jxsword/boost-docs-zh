进程与线程

Boost.Interprocess 不仅适用于进程, 也适用于线程. Boost.Interprocess 的同步机制既能同步不同进程的线程, 也能同步同一进程的线程.

进程间共享信息

在传统编程模型中, 操作系统上运行着多个进程, 每个进程有自己的地址空间. 要在进程之间共享信息, 我们有几种选择:

  • 两个进程用 文件 共享信息. 访问数据时, 每个进程使用通常的文件读写机制. 更新/读取进程间共享的文件时, 需要某种同步来保护读者免受写者影响.
  • 两个进程共享位于操作系统 内核 中的信息. 传统消息队列就是这种情况. 同步由操作系统内核保证.
  • 两个进程可以共享一个 内存 区域. 经典的共享内存或内存映射文件就是这种情况. 进程建立好内存区域后, 就可以像读写其他内存段一样读写数据, 无需调用操作系统内核. 这同样需要进程之间的某种手动同步.

进程间机制的持久性

进程间通信机制最大的问题之一是机制的生存期. 了解进程间通信机制何时从系统中消失非常重要. 在 Boost.Interprocess 中, 我们可以有 3 种持久性:

  • 进程持久性: 机制一直存在, 直到所有打开该机制的进程关闭它、退出或崩溃.
  • 内核持久性: 机制一直存在, 直到操作系统内核重启或机制被显式删除.
  • 文件系统持久性: 机制一直存在, 直到被显式删除.

一些原生 POSIX 和 Windows IPC 机制具有不同的持久性, 因此很难在 Windows 与 POSIX 原生机制之间做到可移植. Boost.Interprocess 各类具有如下持久性:

如上所示, Boost.Interprocess 定义了一些具有"内核或文件系统"持久性的机制. 这是因为 POSIX 允许原生进程间通信实现具有这种可能性. 例如, 可以用内存映射文件实现共享内存并获得文件系统持久性 (例如, 对使用原生共享内存的 Windows 共享内存, 用户态库没有已知的恰当方法来模拟内核持久性, 对 POSIX 共享内存也没有模拟进程持久性的已知方法, 因此唯一可移植的方式是定义"内核或文件系统"持久性).

进程间机制的命名

一些进程间机制是创建在共享内存或内存映射文件中的匿名对象, 而另一些进程间机制需要名称或标识符, 使两个不相关的进程可以使用同一个进程间机制对象. 共享内存、命名互斥量和命名信号量就是如此 (例如原生的 Windows CreateMutex/CreateSemaphore API 家族).

用于标识进程间机制的名称是不可移植的, 即使在 UNIX 系统之间也是如此. 因此, Boost.Interprocess 把该名称限制为 C++ 变量标识符或关键字:

  • 以字母开头 (大写或小写), 例如 a 到 z 或 A 到 Z 的字母. 示例: Sharedmemory, sharedmemory, sHaReDmEmOrY...
  • 可以包含字母、下划线或数字. 示例: shm1, shm2and3, ShM3plus4...

Interprocess 命名资源的构造函数、析构函数与生存期

命名的 Boost.Interprocess 资源 (共享内存、内存映射文件、命名互斥量/条件变量/信号量) 具有内核或文件系统持久性. 这意味着即使所有打开这些资源的进程都结束了, 资源仍然可以再次打开, 而且只能通过显式调用其静态成员 remove 函数来销毁. 这个行为很容易理解, 因为它与控制文件打开/创建/删除的函数所用机制相同:

权限

由 Boost.Interprocess 提供的命名资源必须应对创建文件时同样存在的平台相关权限问题. 如果程序员想在多个用户之间共享共享内存、内存映射文件或命名同步机制 (互斥量、信号量等), 就有必要指定这些权限. 遗憾的是, 传统 UNIX 和 Windows 的权限差别很大, Boost.Interprocess 不试图标准化权限, 但也不忽视它们.

所有命名资源创建函数都接受一个可选的 permissions object , 可用平台相关的权限进行配置.

由于每种机制可以通过不同机制模拟 (信号量可以用映射文件或原生信号量实现), 当命名资源的实现改变时, 权限类型也可能变化 (例如: 在 Windows 中互斥量需要 synchronize permissions, 但文件并非如此). 为避免这一点, Boost.Interprocess 依赖类文件的权限, 打开命名同步机制 (互斥量、信号量等) 需要文件的读写删除权限, 共享内存则需要适当的读或读写删除权限. 这种做法有两个优点: 它与 UNIX 哲学相似, 而且程序员无需知道命名资源是如何实现的.
