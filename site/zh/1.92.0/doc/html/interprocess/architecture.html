基本指导原则

在构建 Boost.Interprocess 的架构时, 我遵循了一些基本指导原则, 可概括为以下几点:

  • Boost.Interprocess 应当至少在 UNIX 和 Windows 系统上可移植. 这意味着不仅要统一接口, 还要统一行为. 这就是 Boost.Interprocess 为共享内存和命名同步机制选择内核或文件系统生存期的原因. 共享内存的进程生存期也是理想的, 但在 UNIX 系统中难以实现.
  • Boost.Interprocess 的进程间同步原语应当与线程同步原语等同. Boost.Interprocess 的目标是拥有与 C++ 标准线程 API 兼容的接口.
  • Boost.Interprocess 的架构应当模块化、可定制且高效. 这就是 Boost.Interprocess 基于模板的原因: 内存算法、索引类型、互斥量类型和其他类都是可模板化的.
  • Boost.Interprocess 的架构应当允许与基于线程的编程同等的并发能力. 这里定义了不同的互斥级别, 使得一个进程可以在扩展共享内存 vector 时并发分配原始内存, 同时另一个进程可以安全地搜索命名对象.
  • Boost.Interprocess 容器对 Boost.Interprocess 一无所知. 所有特定行为都包含在类 STL 的分配器中. 这使得 STL 厂商只需稍微修改 (或者说泛化) 其标准容器实现, 就能得到完全兼容 std::allocator 和 boost::interprocess::allocator 的容器. 这也使 Boost.Interprocess 容器与标准算法兼容.

Boost.Interprocess 构建于 3 个基本类之上: 一个 内存算法 、一个 段管理器 和一个 托管内存段:

内存算法

内存算法 是一个放置在共享内存/内存映射文件段开头几个字节中的对象. 内存算法 可以把该段的一部分返回给用户并标记为已使用, 用户也可以把这些部分归还给 内存算法 , 由 内存算法 重新标记为空闲. 但有一个例外: 内存算法对象结尾之后的某些字节是保留的, 不能用于这种动态分配. 这个"保留"区将用于在众所周知的位置放置其他附加对象.

总之, 内存算法 的使命与标准 C 库的 malloc/free 相同, 但它只能返回它所在段的部分内存. 内存段的布局如下:

Layout of the memory segment:
 ____________ __________ ____________________________________________
|            |          |                                            |
|   memory   | reserved |  The memory algorithm will return portions |
| algorithm  |          |  of the rest of the segment.               |
|____________|__________|____________________________________________|

内存算法 负责内存同步, 就像 malloc/free 保证两个线程可以同时调用 malloc/free 一样. 这通常通过把一个进程共享互斥量作为内存算法的成员来实现. 请注意, 内存算法对段 一无所知 (不知道它是共享内存、共享内存文件等). 对内存算法而言, 段只是一个固定大小的内存缓冲区.

内存算法 也是 Boost.Interprocess 框架其余部分的配置点, 因为它把两个基本类型定义为成员 typedef:

typedef /*implementation dependent*/ void_pointer;
typedef /*implementation dependent*/ mutex_family;

void_pointer typedef 定义将在 Boost.Interprocess 框架 (段管理器、分配器、容器) 中使用的指针类型. 如果内存算法已准备好放置在以不同基址映射的共享内存/映射文件中, 该指针类型将定义为 offset_ptr<void> 或类似的相对指针. 如果 内存算法 只用于固定地址映射, void_pointer 可以定义为 void*.

Boost.Interprocess 内存算法 的其余接口在 编写新的共享内存分配算法 一节中描述. 作为内存算法的例子, 可以查看 simple_seq_fit 或 rbtree_best_fit 类的实现.

段管理器

段管理器 也是一个放置在托管内存段 (共享内存、内存映射文件) 开头几个字节中的对象, 它在 内存算法 之上提供更复杂的服务. . 段管理器和内存算法怎么能都放在段的开头呢? 这是因为段管理器 拥有 内存算法: 实际上, 内存算法是 内嵌 在段管理器中的:

The layout of managed memory segment:
 _______ _________________
|       |         |       |
| some  | memory  | other |<- The memory algorithm considers
|members|algorithm|members|   "other members" as reserved memory, so
|_______|_________|_______|   it does not use it for dynamic allocation.
|_________________________|____________________________________________
|                         |                                            |
|    segment manager      |  The memory algorithm will return portions |
|                         |  of the rest of the segment.               |
|_________________________|____________________________________________|

段管理器 初始化内存算法, 并告诉内存管理器不要把放置 段管理器 其余成员的内存用于动态分配. 段管理器 的其他成员是 一个递归互斥量 (由内存算法的 mutex_family::recursive_mutex typedef 成员定义), 以及 两个索引 (映射) : 一个用于实现命名分配, 另一个用于实现"唯一实例"分配.

  • 第一个索引是一个映射: 键为指向 C 字符串的指针 (命名对象的名称), 值为包含动态分配对象信息的结构 (最重要的是对象的地址和大小).
  • 第二个索引用于实现"唯一实例", 基本上与第一个索引相同, 只是对象名称来自 typeid(T).name() 操作.

在索引中存储 [名称指针, 对象信息] 对所需的内存也是通过 内存算法 分配的, 因此可以说内部索引就像构建在段中的普通用户对象一样. 存储对象名称、对象本身以及用于析构/释放的元数据所需的其余内存, 则用 内存算法 通过单次 allocate() 调用分配.

如前所述, 段管理器 对共享内存/内存映射文件 一无所知 . 段管理器 自身并不分配段的部分内存, 它只是请求 内存算法 从段的其余部分分配所需的内存. 段管理器 是构建在内存算法之上的类, 提供命名对象构造、唯一实例构造以及许多其他服务.

段管理器 在 Boost.Interprocess 中由 segment_manager 类实现.

template<class CharType
        ,class MemoryAlgorithm
        ,template<class IndexConfig> class IndexType>
class segment_manager;

如前所述, 段管理器相当通用: 我们可以指定用于标识命名对象的字符类型, 可以指定动态控制内存段各部分的内存算法, 还可以指定存储 [名称指针, 对象信息] 映射的索引类型. 我们可以按照 构建自定义索引 一节所述构建自己的索引类型.

Boost.Interprocess 托管内存段

Boost.Interprocess 托管内存段会构建共享内存/内存映射文件, 在其中放置段管理器, 并把用户请求转发给段管理器. 例如, basic_managed_shared_memory 是一个使用共享内存的 Boost.Interprocess 托管内存段. basic_managed_mapped_file 使用内存映射文件, 等等.

基本上, Boost.Interprocess 托管内存段的接口与 段管理器 相同, 但它还提供"打开"、"创建"或"打开或创建"共享内存/内存映射文件段并初始化所有所需资源的函数. 托管内存段类并不构建在共享内存或内存映射文件中, 它们是普通的 C++ 类, 存储一个指向段管理器的指针 (段管理器才构建在共享内存或内存映射文件中).

除此之外, 托管内存段还提供特定函数: managed_mapped_file 提供把内存内容刷新到文件的函数, managed_heap_memory 提供扩展内存的函数, 等等.

Boost.Interprocess 托管内存段的大多数函数可以在所有托管内存段之间共享, 因为它们很多时候只是把函数转发给段管理器. 因此, 在 Boost.Interprocess 中, 所有托管内存段都派生自一个公共类, 该类实现与内存无关的 (共享内存、内存映射文件) 函数: boost::interprocess::ipcdetail::basic_managed_memory_impl

从这个类派生, Boost.Interprocess 针对不同的内存后端实现了几个托管内存类:

  • basic_managed_shared_memory (用于共享内存).
  • basic_managed_mapped_file (用于内存映射文件).
  • basic_managed_heap_memory (用于堆分配内存).
  • basic_managed_external_buffer (用于用户提供的外部缓冲区).

Boost.Interprocess 分配器

Boost.Interprocess 的类 STL 分配器相当简单, 遵循通常的 C++ 分配器方法. 通常, STL 容器的分配器构建在 new/delete 运算符之上, 并在其上实现池、arena 和其他分配技巧.

在 Boost.Interprocess 分配器中, 方法类似, 但所有分配器都基于 段管理器 . 段管理器是唯一一个从简单内存分配到命名对象创建都提供的组件. Boost.Interprocess 分配器始终存储一个指向段管理器的指针, 以便从段中获取内存或在分配器之间共享公共池.

可以想象, 分配器的成员指针不是原始指针, 而是由 segment_manager::void_pointer 类型定义的指针类型. 除此之外, pointer typedef (属于 Boost.Interprocess 分配器) 也与 segment_manager::void_pointer 类型相同.

这意味着, 如果我们的分配算法定义 void_pointer 为 offset_ptr<void>, boost::interprocess::allocator<T> 将存储一个 offset_ptr<segment_manager> 来指向段管理器, 并且 boost::interprocess::allocator<T>::pointer 类型将是 offset_ptr<T> . 这样, Boost.Interprocess 分配器就可以放置在段管理器所管理的内存段中, 即共享内存、内存映射文件等.

Boost.Interprocess 隔离存储池的实现

隔离存储池很简单, 遵循经典的隔离存储算法.

  • 池使用段管理器的原始内存分配函数分配内存块.
  • 块中包含一个指针, 用于形成块的单向链表. 池中保存一个指向第一个块的指针.
  • 块的其余内存被划分为所请求大小的节点, 没有任何内存用作每个节点的负载. 由于空闲节点的内存未被使用, 该内存被用来放置一个指针, 形成空闲节点的单向链表. 池中保存一个指向第一个空闲节点的指针.
  • 分配节点就是从链表中取第一个空闲节点. 如果链表为空, 则分配一个新块, 链入块链表, 并把新的空闲节点链入空闲节点链表.
  • 释放把节点归还给空闲节点链表.
  • 池被销毁时, 会遍历块链表并把内存归还给段管理器.

该池由 private_node_pool 和 shared_node_pool 类实现.

Boost.Interprocess 自适应池的实现

自适应池是隔离链表的一种变体, 但方法更复杂:

  • 池不是使用原始分配, 而是使用段管理器分配 对齐的 内存块. 这是一个 关键 特性, 因为节点只需对地址应用一个简单的掩码就能找到其块信息.
  • 块中包含形成块双向链表的指针, 以及一个附加指针, 用于为放置在该块上的空闲节点创建单向链表. 因此与隔离存储算法不同, 空闲节点链表是 按块 实现的.
  • 池按空闲节点数递增的顺序维护各块. 这改善了局部性, 并尽量减少节点分配在各块之间的分散, 便于产生完全空闲的块.
  • 池保存一个指向空闲节点数最少 (但非零) 的块的指针. 该块称为"活动"块.
  • 分配节点就是返回"活动"块的第一个空闲节点. 块链表会按空闲节点数重新排序. 必要时更新指向"活动"池的指针.
  • 如果池的节点用尽, 则分配一个新块并压入块链表末尾. 必要时更新指向"活动"池的指针.
  • 释放把节点归还给其所在块的空闲节点链表, 并相应地更新"活动"池.
  • 如果完全空闲的块数量超过限制, 块将被归还给段管理器.
  • 池被销毁时, 会遍历块链表并把内存归还给段管理器.

自适应池由 private_adaptive_node_pool 和 adaptive_node_pool 类实现.

Boost.Interprocess 容器

Boost.Interprocess 容器是 boost::interprocess 命名空间中 STL 容器的符合标准的对应版本, 但有以下小细节:

  • Boost.Interprocess STL 容器不假设用一个分配器分配的内存可以用同类型的另一个分配器释放. 它们总是用 operator==() 比较分配器, 以判断是否可行.
  • Boost.Interprocess 容器内部结构的指针与容器的分配器所定义的 pointer 类型相同. 这使容器可以放置在以不同基址映射的托管内存段中.

原始内存分配的性能

使用 Boost.Interprocess 类可以进行两种原始内存分配:

  • 显式: 用户调用托管内存段 (managed_shared_memory/managed_mapped_file 等) 的 allocate() 和 deallocate() 函数. 该调用被转换为 MemoryAlgorithm::allocate() 函数, 这意味着所需时间就是与托管内存段关联的内存算法分配数据所需的时间.
  • 隐式: 例如, 你正在将 boost::interprocess::allocator<...> 与 Boost.Interprocess 容器一起使用. 该分配器调用与显式方法相同的 MemoryAlgorithm::allocate() 函数, 每次 vector/string 需要重新分配其缓冲区时, 以及 每次 向节点容器插入对象时, 都会调用该函数.

如果你发现内存分配是应用程序的瓶颈, 可以考虑以下替代方案:

  • 如果你使用 map/set 关联容器, 且主要进行搜索而插入/删除主要在初始化阶段完成, 可以尝试使用 flat_map 家族代替 map 家族. 此时开销出现在有序 vector 不得不重新分配存储并移动数据时. 如果事先知道要插入多少数据, 也可以调用这些容器的 reserve() 方法. 不过, 这些容器在插入时会使迭代器失效, 因此这种替换只对某些应用程序有效.
  • 为节点容器使用 Boost.Interprocess 池化分配器, 因为池化分配器只在池的节点用尽时才调用 allocate() . 这相当高效 (远胜于当前默认的通用算法), 并且可以节省大量内存. 详见 隔离存储节点分配器 和 自适应节点分配器 .
  • 编写自己的内存算法. 如果你有内存分配算法的经验, 并且认为有比默认算法更适合你的应用程序的算法, 可以在所有 Boost.Interprocess 托管内存段中指定它. 具体做法参见 编写新的共享内存分配算法 一节. 如果你认为它比通用应用程序的默认算法更好, 请大方地把它捐给 Boost.Interprocess 使其成为默认算法!

命名分配的性能

Boost.Interprocess 提供与两个线程写同一公共结构相同的并行性, 只有当用户创建/搜索命名/唯一对象时例外. 创建命名对象的步骤如下:

  • 锁定递归互斥量 (这样就可以在待创建对象的构造函数内进行命名分配).
  • 尝试将 [名称指针, 对象信息] 插入名称/对象索引. 该查找必须确保名称以前未被使用过. 这通过调用索引的 insert() 函数实现. 因此所需时间取决于索引类型 (有序 vector、树、哈希...). 如果索引必须重新分配, 或它是节点分配器、使用池化分配等, 则可能还需要调用内存算法的分配函数.
  • 分配单个缓冲区, 用于容纳对象名称、对象本身以及析构所需的元数据 (对象数量等...).
  • 调用正在创建对象的构造函数. 如果是数组, 则对每个数组元素调用一次构造函数.
  • 解锁递归互斥量.

使用对象名称 (destroy<T>(name)) 销毁命名对象的步骤如下:

  • 锁定递归互斥量 .
  • 在索引中搜索与该名称关联的条目. 复制该信息并擦除索引条目. 这通过索引的 find(const key_type &) 和 erase(iterator) 成员完成. 如果索引是平衡树、有序 vector 等, 可能需要重新排列元素.
  • 调用对象的析构函数 (数组则为多个).
  • 用分配算法释放包含名称、元数据和对象本身的内存缓冲区.
  • 解锁递归互斥量.

使用对象指针 (destroy_ptr(T *ptr)) 销毁命名对象的步骤如下:

  • 锁定递归互斥量 .
  • 根据索引类型, 这可能有所不同:
    • 如果索引是节点索引 (以 boost::interprocess::is_node_index 特化标记): 取出存储在对象附近的迭代器并调用 erase(iterator) . 如果索引是平衡树、有序 vector 等, 可能需要重新排列元素.
    • 如果不是节点索引: 取出存储在对象附近的名称, 调用 `erase(const key &) 擦除索引条目. 如果索引是平衡树、有序 vector 等, 可能需要重新排列元素...
  • 调用对象的析构函数 (数组则为多个).
  • 用分配算法释放包含名称、元数据和对象本身的内存缓冲区.
  • 解锁递归互斥量.

如果你发现性能不够好, 可以考虑以下替代方案:

  • 也许问题在于锁定时间过长, 损害了并行性. 尽量减少全局索引中的命名对象数量; 如果你的应用程序服务多个客户端, 尽量为每个客户端构建一个新的托管内存段, 而不是共用一个.
  • 如果觉得默认索引类型不够快, 可以使用其他 Boost.Interprocess 索引类型. 如果仍不满意, 就编写自己的索引类型. 参见 构建自定义索引 .
  • 通过指针销毁至少与使用对象名称一样快, 甚至可能更快 (例如在节点容器中). 因此, 如果你的问题在于大量命名销毁操作, 请尝试使用指针. 如果索引是节点索引, 可以节省一些时间.
