COM 初始化

Boost.Interprocess 使用 Windows COM 库实现部分功能, 并以并发模型 COINIT_APARTMENTTHREADED. 如果调用线程已以另一个并发模型初始化了 COM 库, Boost.Interprocess 会妥善处理这一情况, 并对已初始化的模型使用 COM 调用. 如果出于某种原因, 你希望 Boost.Interprocess 以另一个模型初始化 COM 库, 请定义宏 BOOST_INTERPROCESS_WINDOWS_COINIT_MODEL, 并在包含 Boost.Interprocess 之前, 将该宏设置为以下值之一:

  • COINIT_APARTMENTTHREADED_BIPC
  • COINIT_MULTITHREADED_BIPC
  • COINIT_DISABLE_OLE1DDE_BIPC
  • COINIT_SPEED_OVER_MEMORY_BIPC

共享内存模拟文件夹

共享内存 (shared_memory_object) 在 Windows 中以内存映射文件实现, 放置在共享文档文件夹 (SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\Shell Folders\Common AppData) 下的一个共享目录中. 该目录名是通过会话管理器 (Session Manager) 的注册表值获得的最近一次启动时间. 自 Boost 1.74 起此行为是默认行为.

旧版 Boost.Interprocess (直到 Boost 1.48) 使用 COM 调用 (通过宏 BOOST_INTERPROCESS_BOOTSTAMP_IS_LASTBOOTUPTIME), 但该时间戳在虚拟机和时间调整的情况下不可靠. 直到 Boost 1.74 的后续版本改用事件日志 (EventLog) 启动事件作为时间戳, 但一些用户发现, 如果系统长时间运行, 该事件可能在事件日志中不存在. 你可以定义 BOOST_INTERPROCESS_BOOTSTAMP_IS_EVENTLOG_BASED 来强制使用这种基于事件日志的时间戳.

在任何错误情况下 (共享文档文件夹未定义或无法获得启动时间), 库都会抛出错误. 你仍然可以使用 Boost.Interprocess , 方法是将你自己的目录定义为共享目录. 如果你的共享目录是编译期常量, 请在使用本库时定义 BOOST_INTERPROCESS_SHARED_DIR_PATH (在 Windows 系统中为 BOOST_INTERPROCESS_SHARED_DIR_WPATH), 该路径将被用于放置共享内存文件. 如果需要在运行期确定共享目录, 请定义 BOOST_INTERPROCESS_SHARED_DIR_FUNC 并实现以下函数

namespace boost {
    namespace interprocess {
        namespace ipcdetail {
            void get_shared_dir(std::string &shared_dir);
            //wstring overload is only needed for Windows systems
            void get_shared_dir(std::wstring &shared_dir);
        }
    }
}

BOOST_USE_WINDOWS_H 支持

如果 BOOST_USE_WINDOWS_H 已定义, 则会包含 <windows.h> 及其他 Windows SDK 文件; 否则库将自行声明所需的函数和结构, 以减轻包含这些庞大头文件的影响.

Cygwin 用户注意事项

本库将 Cygwin 视为类 Unix 操作系统, 在 Cygwin 平台上使用类 Unix 系统调用而非 Windows API. 你可能需要定义 _XOPEN_SOURCE=600 / _POSIX_C_SOURCE=200112L 或更高的值, 以便库能看到最小化的 Unix API.

请注意, 对于 XSI 同步原语 (例如 xsi_shared_memory, managed_xsi_shared_memory), Cygwin 需要启动 Cygserver 程序.

共享内存模拟文件夹

在没有 POSIX 共享内存支持的系统上, 共享内存对象以内存映射文件实现, 使用位于 "/tmp" 下的一个目录, 该目录名可以包含 (若 BOOST_INTERPROCESS_HAS_KERNEL_BOOTTIME 已定义) 最近一次启动时间 (若操作系统支持). 与 Windows 一样, 在获取该目录发生任何错误时库都会抛出错误. 如果你的共享目录是编译期常量, 请在使用本库时定义 BOOST_INTERPROCESS_SHARED_DIR_PATH , 该路径将被用于放置共享内存文件. 如果需要在运行期确定共享目录, 请定义 BOOST_INTERPROCESS_SHARED_DIR_FUNC 并实现函数

namespace boost {

        }
    }

Linux 用户注意事项

过量提交

过量提交

已提交地址空间是指当所有应用程序都决定访问其从内核请求的全部内存时, 内核可能必须供应的虚拟内存总量 (交换空间或物理内存/RAM). 默认情况下, Linux 允许进程提交多于系统可用量的虚拟内存. 如果这些内存未被访问, 则实际上不会占用物理内存 + 交换空间.

这种行为的原因在于 Linux 试图优化 fork 出的进程的内存使用; fork() 会创建进程空间的完整副本, 但在内存过量提交的情况下, 这个新 fork 出的实例中只有被写入过的页才真正需要由内核分配. 如果应用程序访问的内存超过可用量, 内核就必须以强硬方式释放内存: OOM (Out Of Memory) killer 会挑选一些进程将其杀死, 以回收内存.

Boost.Interprocess 无法改变这种行为, 用户在访问共享内存时可能会遭受 OOM-killer. 根据 内核文档, Linux 内核支持若干 overcommit 模式. 如果你的应用程序需要不被杀死的保证, 就应当改变这种过量提交行为.

MacOS 与 BSD 用户注意事项

_POSIX_THREAD_PROCESS_SHARED 的支持不存在 (OpenBSD/NetBSD, 旧版 FreeBSD) 或不完整/有缺陷 (FreeBSD>=11, MacOS). 进程间共享的同步原语以原子操作模拟, 其性能欠佳, 并且当持有锁的进程崩溃时无法恢复.

QNX, Android, Haiku, VxWorks 与 Emscriptem 用户注意事项

沙盒应用程序的限制

Boost.Interprocess 在 MacOS 中使用 POSIX 共享内存来实现 MacOS 的共享内存类.

但沙盒应用无法使用 System V (XSI) 信号量, 且默认情况下 POSIX 信号量和共享内存也不可用. 不过, 通过指定一个申请加入某个应用程序组的 entitlement, 应用可以使用这些技术与该应用程序组的其他成员通信.

请参阅 Apple 文档 中关于在沙盒应用程序上使用进程间通信的限制与指南.

QNX, Android, Haiku, VxWorks 与 Emscriptem 用户注意事项

这些操作系统不提供 XSI IPC 机制支持, 因此相关工具不可用.

Boost 1.91 发布

  • 添加了 uses-allocator 构造 (对于满足 boost::container::uses_allocator<T>::value == true 的类型), 以下工具均提供支持:
    • 段管理器在其 construct 方法中
    • 分配器
  • 实践中不太可能破坏 ABI: 取消定义 BOOST_INTERPROCESS_MSG_QUEUE_CIRCULAR_INDEX (自 2012 年的 Boost 1.52 起这曾是默认值) 的做法不再可用. message_queue 现在只有单一实现, 采用循环队列策略.
  • ABI 破坏性变更: 一些实用工具 (如基于自旋的递归互斥量) 需要使用系统级线程标识符. Unix 系统原先采用基于 pid_t+pthread_t 标识符的方法, 这并不正确 (因为 pthread_t 本不应标识线程, 即使在进程内也是如此). 在本版本中, 多种类 Unix 系统使用了一种专门且正确的全局线程标识符 (gettid() 在 Linux 上为 pthread_getthreadid_np 在 FreeBSD 上为 pthread_threadid_np 在 MacOS 上为 _lwp_self 在 NetBSD 上为 getthrid 在 OpenBSD 上为 thr_self 在 Solaris 上为 GetCurrentThreadId 在 Cygwin 上为 gettid 在 QNX 上, 等等). 程序员可以定义 BOOST_INTERPROCESS_USE_PTHREAD_AS_SYSTEMWIDE_THREAD_ID 以回到旧的基于 pthread_t 的行为, 但该选项已弃用, 并将在几个版本后移除.
  • 在 `<boost/interprocess/containers/*.hpp> 头文件中加入了 BOOST_HEADER_DEPRECATED . 这些头文件在多个版本前已被弃用, 而这条消息会促使现有用户切换到 Boost.Container 头文件.
  • 更改了 多次分配函数 (仍属实验性且 API/ABI 不稳定) 的接口以支持对齐.
  • 在 `<boost/interprocess/containers/*.hpp> 头文件中加入了 BOOST_HEADER_DEPRECATED . 这些头文件在多个版本前已被弃用, 而这条消息会促使现有用户切换到 Boost.Container 头文件.
  • 弃用分配器的 size(), allocate_many 和 deallocate_many, address 和 size 函数. 它们在 Boost.Container 中未被使用, 将来会被移除.
  • 已修复的缺陷:
    • GitHub #242 ("Cygwin 兼容性问题").
    • GitHub #247 ("使用 private_adaptive_pool 的移动构造 map 在析构时触发断言").
    • GitHub #252 ("[回归] 从 1.87.0 起 clang 下 offset_ptr 没有可用的构造函数").
    • GitHub #276 ("boost/interprocess/allocators/allocator.hpp 中的 -Wundef 警告).

  • 优化 vector 以利用 boost::has_trivial_destructor . 该优化避免对具有平凡析构函数的元素调用析构函数.
  • 优化 vector 以利用 has_trivial_destructor_after_move 特征 (trait). 该优化在元素已被移动 (许多可移动类型都属于这种情况) 时, 避免对具有平凡析构函数的元素调用析构函数. 这一技巧由 Howard Hinnant 提供.
  • 添加了安全检查, 以避免分配器和命名构造函数中的整数溢出缺陷.
  • 为向前和向后扩展函数添加了对齐检查.
  • 修复了 PPC 原子函数中的缺陷.
  • 修复了创建和打开托管段时的竞态条件错误.
  • 添加了自适应池.
  • 源码破坏性变更: 更改了节点分配器的模板参数顺序, 使其更易于使用.
  • 添加了对原生 Windows 共享内存的支持.
  • 添加了更多测试.
  • 修正了参考部分中出现的私有函数.
  • 添加了函数 (deallocate_free_chunks()) 用于从节点分配器手动释放完全空闲的块.
  • 实现了针对 LWG 问题 233 的 N1780 提案: 关联容器中的插入提示 , 涉及 interprocess 的 multiset 和 multimap 类.
  • 源码破坏性变更: 现在使用共享内存对象时包含 shared_memory_object.hpp 头文件而非 shared memory.hpp.
  • ABI 破坏性变更: 更改了初始化托管共享内存和内存映射文件时使用的全局互斥量. 此变更试图尽量减少死锁.
  • 源码破坏性变更: 将共享内存、内存映射文件和映射区域的打开模式统一为单一的 mode_t 类型.
  • 在包含 DateTime 头文件之前添加了额外的 WIN32_LEAN_AND_MEAN, 以避免在 Windows 中同时使用 Interprocess 和 Asio 时出现套接字重定义错误.
  • ABI 破坏性变更: mapped_region 构造函数不再要求从 memory_mappable 派生的类, 但类必须满足 MemoryMappable 概念.
  • 为 basic_string 添加了就地重分配能力.
  • ABI 破坏性变更: 重新实现并优化了小字符串优化 (SSO). 窄字符串类在 32 位系统上零字节开销, 内部带有 11 字节缓冲区!
  • 为容器添加了移动语义. 在使用容器的容器时提升性能.
  • ABI 破坏性变更: 节点容器 (list, slist, map/set) 的末端节点现在内嵌于容器中, 而非用分配器分配. 这使得移动构造函数可以不抛异常, 并提升了性能.
  • ABI 破坏性变更: slist 和 list 容器现在具有常数时间的 size() 函数. 容器的大小作为成员加入.

有一些我希望实现的 Interprocess 特性, 也有一些可以做得更好的 Boost.Interprocess 代码. 来看一些想法:

Win32 同步机制过于简陋

Win32 版本的共享互斥量和共享条件变量基于"自旋并等待"的原子指令. 这导致性能不佳, 且不处理优先级反转等问题. 在这方面我们非常需要线程专家的认真帮助. 而且我不确定这在用户态软件中能否实现. 基于 POSIX 的实现使用 PTHREAD_PROCESS_SHARED 属性将互斥量放入共享内存, 因此不存在这些问题. 我不知道有任何为 Win32 模拟 PTHREAD_PROCESS_SHARED 属性的实现. 我们应当能够在内存映射文件中构造这些原语, 从而像 POSIX 原语一样获得文件系统生存期.

在 Boost.Interprocess 基础资源上使用宽字符名称

目前 Interprocess 仅允许对基础命名对象使用基于 char 的名称. 然而, 一些操作系统对资源 (例如映射文件) 使用 wchar_t 名称. 未来 Interprocess 应当尝试提供可移植的窄/宽字符接口. 为此, 拥有一组 boost wstring <-> string 转换工具会很有用, 能以可移植的方式转换资源名称 (转义可能与操作系统名称冲突的字符). 使用 boost::filesystem 路径来避免操作系统特定问题也会很有意思.

安全属性

Boost.Interprocess 不为共享内存和同步对象定义安全属性. 标准 C++ 同样忽略文件的安全属性, 因此添加安全属性需要相当可观的工作.

未来的进程间通信

Boost.Interprocess 提供了基于 Boost.Interprocess 原语 (如互斥量和条件变量) 的进程共享消息队列. 我希望开发更多机制, 例如面向流的命名 fifo, 使我们可以将其与 iostream 接口包装器一起使用 (可以模仿 Unix 管道).

C++ 需要更复杂的机制, 如果 C++ 中有面向流和数据报的类 PF_UNIX 机制就太好了. 而对于极快的进程间远程调用, Solaris doors 是一个值得为 C++ 实现的有趣替代方案. 但实现类 PF_UNIX 套接字和 doors 的工作量巨大 (而且在用户态库中可能很困难). 有网络专家愿意志愿参与吗?
