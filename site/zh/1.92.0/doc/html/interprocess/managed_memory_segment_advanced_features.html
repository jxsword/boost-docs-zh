分配托管内存段的片段

如果需要从托管内存段 (例如托管共享内存) 进行基本的原始字节分配, 以实现顶层的进程间通信, 该类提供了 allocate 和 deallocate 函数. 分配函数有抛出和不抛出两个版本. 抛出版本在没有更多内存时抛出 boost::interprocess::bad_alloc (派生自 std::bad_alloc) , 不抛出版本则返回 0 指针.

#include <boost/interprocess/managed_shared_memory.hpp>

int main()
{
   using namespace boost::interprocess;

   //Remove shared memory on construction and destruction
   struct shm_remove
   {
      shm_remove() { shared_memory_object::remove("MyName"); }
      ~shm_remove(){ shared_memory_object::remove("MyName"); }
   } remover;

   //Managed memory segment that allocates portions of a shared memory
   //segment with the default management algorithm
   managed_shared_memory managed_shm(create_only,"MyName", 65536);

   //Allocate 100 bytes of memory from segment, throwing version
   void *ptr = managed_shm.allocate(100);

   //Deallocate it
   managed_shm.deallocate(ptr);

   //Non throwing version
   ptr = managed_shm.allocate(100, std::nothrow);

   //Deallocate it
   managed_shm.deallocate(ptr);
   return 0;
}

段管理器

所有 Boost.Interprocess 托管内存段类都会在其各自的内存段 (共享内存、内存映射文件、堆内存...) 中构建一些结构, 用于实现内存管理算法、命名分配、同步对象... 所有这些对象都封装在一个称为 段管理器 的单一对象中. 托管内存映射文件和托管共享内存使用相同的 段管理器 来实现所有托管内存段特性, 因为 段管理器 是一个管理固定大小内存缓冲区的类. 由于共享内存和内存映射文件都通过映射区域访问, 而映射区域是固定大小的内存缓冲区, 因此单个 段管理器 类可以管理多种托管内存段类型.

一些 Boost.Interprocess 类在构造函数中需要指向段管理器的指针, 段管理器可以从任何托管内存段用 get_segment_manager 成员获得:

managed_shared_memory::segment_manager *seg_manager =
   managed_shm.get_segment_manager();

获取标识数据的句柄

该类还提供属于托管内存段的绝对地址与句柄之间的转换, 句柄可以用任何进程间机制传递. 该句柄可以用同样包含该对象的托管内存段再转换回绝对地址. 句柄可以在进程之间用作键, 标识托管内存段中已分配的部分或在托管段中构造的对象.

//Process A obtains the offset of the address
managed_shared_memory::handle handle =
   segment.get_handle_from_address(processA_address);

//Process A sends this address using any mechanism to process B

//Process B obtains the handle and transforms it again to an address
managed_shared_memory::handle handle = ...
void * processB_address = segment.get_address_from_handle(handle);

以原子方式执行对象函数

有时程序员必须执行某些代码, 并需要保证在执行该函数对象期间, 没有其他进程或线程会创建或销毁任何命名、唯一或匿名对象. 用户可能想创建多个命名对象并初始化它们, 但这些对象应当立刻对其他进程可用.

为此, 程序员可以使用托管类提供的 atomic_func() 函数:

//This object function will create several named objects
create_several_objects_func func(/**/);

//While executing the function, no other process will be
//able to create or destroy objects
managed_memory.atomic_func(func);

注意, atomic_func 并不阻止其他进程分配原始内存或对已构造对象执行成员函数 (例如: 另一个进程可能正在向段中的 vector 推入元素). 原子函数只阻塞其他进程的命名、唯一和匿名创建、搜索与销毁 (对 construct<>, find<>, find_or_construct<>, destroy<>... 的并发调用).

获取托管段的信息

以下函数可用于获取托管内存段的信息:

获取内存段的大小:

managed_shm.get_size();

获取段的空闲字节数:

managed_shm.get_free_memory();

把空闲内存清零:

managed_shm.zero_free_memory();

获知是否所有内存都已释放, 否则返回 false:

managed_shm.all_memory_deallocated();

测试托管段的内部结构. 未检测到错误时返回 true:

managed_shm.check_sanity();

获取段中已分配的命名对象和唯一对象的数量:

managed_shm.get_num_named_objects();
managed_shm.get_num_unique_objects();

用于名称/对象映射的索引类型

如前所述, 托管内存段在创建命名对象时, 会把名称/对象关联存储在一个索引中. 该索引是一个映射: 键为对象名称, 映射类型为指向对象的指针. 默认特化 managed_shared_memory 和 wmanaged_shared_memory 使用 flat_map_index 作为索引类型.

每种索引都有自己的特性, 如查找时间、插入时间、删除时间、内存使用和内存分配模式. Boost.Interprocess 目前提供 3 种索引类型:

  • boost::interprocess::flat_map_index flat_map_index: 基于 boost::interprocess::flat_map (一种类似 Loki 库 AssocVector 类的有序 vector), 提供出色的查找时间和最小的内存占用. 但 vector 满时必须重新分配, 所有数据都要复制到新缓冲区. 适合插入主要发生在初始化阶段、运行期只需要查找的情况.
  • boost::interprocess::map_index map_index: 基于 boost::interprocess::map (std::map 的托管内存就绪版本). 由于它是基于节点的容器, 没有重新分配, 只是树偶尔需要重新平衡. 与 boost::interprocess::flat_map_index 相比, 每个节点开销更大, 但插入/删除/查找时间均衡. 适合查找/插入/删除随机发生的情况.
  • boost::interprocess::null_index null_index: 该索引适用于只用托管内存段进行原始内存缓冲区分配、不使用命名/唯一分配的用户. 该类是空的, 可节省一些空间和编译时间. 如果在用此索引的托管内存段上尝试命名对象创建, 会得到编译错误.

举例来说, 如果我们想定义新的托管共享内存类, 用 boost::interprocess::map 作为索引类型, 只需把 [boost::interprocess::map_index map_index] 指定为模板参数:

//This managed memory segment can allocate objects with:
// -> a wchar_t string as key
// -> boost::interprocess::rbtree_best_fit with process-shared mutexes
//       as memory allocation algorithm.
// -> boost::interprocess::map<...> as the index to store name/object mappings
//
typedef boost::interprocess::basic_managed_shared_memory
         <  wchar_t
         ,  boost::interprocess::rbtree_best_fit<boost::interprocess::mutex_family, offset_ptr<void> >
         ,  boost::interprocess::map_index
         >  my_managed_shared_memory;

如果这些索引不能满足你的需要, 可以定义自己的索引类型. 具体做法请参见 构建自定义索引 一节.

增长托管段

托管段一旦创建就无法增长. 这一限制不易解决: 每个连接到托管段的进程都需要停下来, 获知新大小, 重新映射托管段再继续工作. 对于不借助操作系统内核的用户态库来说, 这几乎不可能实现.

另一方面, Boost.Interprocess 提供离线段增长. 这是什么意思? 即在没有任何进程映射该托管段时, 段可以被增长. 如果应用程序能找到没有进程连接的时机, 就可以增长或收缩托管段以适应需要.

这里有一个展示如何增长和收缩 managed_shared_memory 的示例:

#include <boost/interprocess/managed_shared_memory.hpp>
#include <boost/interprocess/managed_mapped_file.hpp>
#include <cassert>

class MyClass
{
   //...
};

int main()
{
   using namespace boost::interprocess;
   //Remove shared memory on construction and destruction
   struct shm_remove
   {
      shm_remove() { shared_memory_object::remove("MyName"); }
      ~shm_remove(){ shared_memory_object::remove("MyName"); }
   } remover;

   {
      //Create a managed shared memory
      managed_shared_memory shm(create_only, "MyName", 1000);

      //Check size
      assert(shm.get_size() == 1000);
      //Construct a named object
      MyClass *myclass = shm.construct<MyClass>("MyClass")();
      //The managed segment is unmapped here
   }
   {
      //Now that the segment is not mapped grow it adding extra 500 bytes
      managed_shared_memory::grow("MyName", 500);

      //Map it again
      managed_shared_memory shm(open_only, "MyName");

      //Check size
      assert(shm.get_size() == 1500);
      //Check "MyClass" is still there
      MyClass *myclass = shm.find<MyClass>("MyClass").first;
      assert(myclass != 0);
      //The managed segment is unmapped here
   }
   {
      //Now minimize the size of the segment
      managed_shared_memory::shrink_to_fit("MyName");

      //Map it again
      managed_shared_memory shm(open_only, "MyName");

      //Check size
      assert(shm.get_size() < 1000);
      //Check "MyClass" is still there
      MyClass *myclass = shm.find<MyClass>("MyClass").first;
      assert(myclass != 0);
      //The managed segment is unmapped here
   }
   return 0;
}

managed_mapped_file 还提供了类似的函数来增长或收缩托管文件. 请记住, 在增长/收缩过程执行期间, 不应有任何进程在修改文件/共享内存 , 否则托管段将被破坏.

高级索引函数

如前所述, 托管段把命名对象和唯一对象的信息存储在两个索引中. 根据这些索引的类型, 当进行新的命名或唯一分配时, 索引可能必须重新分配一些辅助结构. 对某些索引, 如果用户知道将要创建多少命名或唯一对象, 可以预分配一些结构以获得更好的性能. (如果索引是有序 vector, 它可以预分配内存以避免重新分配; 如果索引是哈希结构, 它可以预分配桶数组).

以下函数预留内存, 使后续命名或唯一对象的分配更高效. 这些函数只对伪侵入式或非节点索引 (如 flat_map_index, iunordered_set_index) 有用. 对默认索引 (iset_index) 或其他索引 (map_index) 这些函数没有效果:

managed_shm.reserve_named_objects(1000);
managed_shm.reserve_unique_objects(1000);

managed_shm.reserve_named_objects(1000);
managed_shm.reserve_unique_objects(1000);

托管内存段还提供遍历已构造命名对象和唯一对象的功能, 用于调试. 注意: 这种遍历不是线程安全的 , 因此用户应确保没有其他线程正在操纵段中的命名或唯一索引 (创建、擦除、预留...). 不涉及索引的其他操作可以并发执行 (例如原始内存分配/释放).

以下函数返回常量迭代器, 指向托管段中存储的命名对象和唯一对象的范围. 根据索引类型, 迭代器可能在命名或唯一的创建/擦除/预留操作之后失效:

typedef managed_shared_memory::const_named_iterator const_named_it;
const_named_it named_beg = managed_shm.named_begin();
const_named_it named_end = managed_shm.named_end();

typedef managed_shared_memory::const_unique_iterator const_unique_it;
const_unique_it unique_beg = managed_shm.unique_begin();
const_unique_it unique_end = managed_shm.unique_end();

for(; named_beg != named_end; ++named_beg){
   //A pointer to the name of the named object
   const managed_shared_memory::char_type *name = named_beg->name();
   //The length of the name
   std::size_t name_len = named_beg->name_length();
   //A constant void pointer to the named object
   const void *value = named_beg->value();
}

for(; unique_beg != unique_end; ++unique_beg){
   //The typeid(T).name() of the unique object
   const char *typeid_name = unique_beg->name();
   //The length of the name
   std::size_t name_len = unique_beg->name_length();
   //A constant void pointer to the unique object
   const void *value = unique_beg->value();
}

分配对齐的内存部分

由于某些硬件或软件限制, 有时能够分配对齐的内存片段很有用. 有时, 拥有对齐内存是可以用来改进若干内存算法的特性.

这种分配与前面展示的原始内存分配类似, 但多了一个指定对齐的参数. 对齐有一个限制: 对齐值必须是 2 的幂.

如果用户想分配多个对齐块 (例如对齐到 128 字节), 使内存浪费最小的尺寸是接近该对齐倍数的值 (例如 2*128 - 若干字节). 原因在于每次内存分配通常都要在所分配缓冲区的开头占用一些附加元数据. 如果用户能知道"若干字节"的值, 且空闲内存块的头几个字节被用来满足对齐分配, 那么块的其余部分也可以保持对齐, 为下一次对齐分配做好准备. 注意, 请求 对齐值整数倍的大小并非最优 , 因为所需的元数据会使下一个内存块不对齐.

一旦程序员知道了每次内存分配的负载大小, 就可以请求一个最优大小, 以分配对齐的内存块, 同时最大化请求大小 和 未来对齐分配的可能性. 这一信息存储在托管内存段的 PayloadPerAllocation 常量中.

下面的小示例展示了对齐分配的用法:

#include <boost/interprocess/managed_shared_memory.hpp>
#include <cassert>

int main()
{
   using namespace boost::interprocess;

   //Remove shared memory on construction and destruction
   struct shm_remove
   {
      shm_remove() { shared_memory_object::remove("MyName"); }
      ~shm_remove(){ shared_memory_object::remove("MyName"); }
   } remover;

   //Managed memory segment that allocates portions of a shared memory
   //segment with the default management algorithm
   managed_shared_memory managed_shm(create_only, "MyName", 65536);

   const std::size_t Alignment = 128;

   //Allocate 100 bytes aligned to Alignment from segment, throwing version
   void *ptr = managed_shm.allocate_aligned(100, Alignment);

   //Check alignment
   assert(std::size_t(static_cast<char*>(ptr)-static_cast<char*>(0)) % Alignment == 0);

   //Deallocate it
   managed_shm.deallocate(ptr);

   //Non throwing version
   ptr = managed_shm.allocate_aligned(100, Alignment, std::nothrow);

   //Check alignment
   assert(std::size_t(static_cast<char*>(ptr)-static_cast<char*>(0)) % Alignment == 0);

   //Deallocate it
   managed_shm.deallocate(ptr);

   //If we want to efficiently allocate aligned blocks of memory
   //use managed_shared_memory::PayloadPerAllocation value
   assert(Alignment > managed_shared_memory::PayloadPerAllocation);

   //This allocation will maximize the size of the aligned memory
   //and will increase the possibility of finding more aligned memory
   ptr = managed_shm.allocate_aligned
      (3u*Alignment - managed_shared_memory::PayloadPerAllocation, Alignment);

   //Check alignment
   assert(std::size_t(static_cast<char*>(ptr)-static_cast<char*>(0)) % Alignment == 0);

   //Deallocate it
   managed_shm.deallocate(ptr);

   return 0;
}

多次分配函数

注意

该特性是实验性的, API 与 ABI 不稳定

如果应用程序需要分配大量内存缓冲区, 又需要独立地释放它们, 通常只能循环调用 allocate() . 托管内存段提供了一种替代函数, 可以在单次调用中打包多个分配, 得到如下内存缓冲区:

  • 在内存中连续打包 (改善局部性)
  • 可以独立释放.

这种分配方法比在循环中调用 allocate() 快得多. 缺点是段必须提供一块足够大的连续内存来容纳所有分配. 托管内存段通过 allocate_many() 函数提供这一功能. allocate_many 函数有两类:

  • 分配 N 个相同大小的内存缓冲区.
  • 分配 N 个内存缓冲区, 每个大小不同.
//!Allocates n_elements of elem_bytes bytes.
//!Throws bad_alloc on failure. chain.size() is not increased on failure.
void allocate_many(size_type elem_bytes, size_type n_elements, multiallocation_chain &chain);

//!Allocates n_elements, each one of element_lengths[i]*sizeof_element bytes.
//!Throws bad_alloc on failure. chain.size() is not increased on failure.
void allocate_many(const size_type *element_lengths, size_type n_elements, size_type sizeof_element, multiallocation_chain &chain);

//!Allocates n_elements of elem_bytes bytes.
//!Non-throwing version. chain.size() is not increased on failure.
void allocate_many(std::nothrow_t, size_type elem_bytes, size_type n_elements, multiallocation_chain &chain);

//!Allocates n_elements, each one of
//!element_lengths[i]*sizeof_element bytes.
//!Non-throwing version. chain.size() is not increased on failure.
void allocate_many(std::nothrow_t, const size_type *elem_sizes, size_type n_elements, size_type sizeof_element, multiallocation_chain &chain);

//!Deallocates all elements contained in chain.
//!Never throws.
void deallocate_many(multiallocation_chain &chain);

下面的小示例展示了所有这些功能:

#include <boost/interprocess/managed_shared_memory.hpp>
#include <boost/move/utility_core.hpp> //boost::move
#include <cstring>//std::memset
#include <new>    //std::nothrow
#include <vector> //std::vector

int main()
{
   using namespace boost::interprocess;
   typedef managed_shared_memory::multiallocation_chain multiallocation_chain;

   //Remove shared memory on construction and destruction
   struct shm_remove
   {
      shm_remove() { shared_memory_object::remove("MyName"); }
      ~shm_remove(){ shared_memory_object::remove("MyName"); }
   } remover;

   managed_shared_memory managed_shm(create_only,"MyName", 65536);

   //Allocate 16 elements of 100 bytes with a minimal alignment of 4, in a single call. Non-throwing version.
   multiallocation_chain chain;
   managed_shm.allocate_many(std::nothrow, 100, 16, 4u, chain);

   //Check if the memory allocation was successful
   if(chain.empty()) return 1;

   //Allocated buffers
   std::vector<void*> allocated_buffers;

   //Initialize our data
   while(!chain.empty()){
      void *buf = chain.pop_front();
      allocated_buffers.push_back(buf);
      //The iterator must be incremented before overwriting memory
      //because otherwise, the iterator is invalidated.
      std::memset(buf, 0, 100);
   }

   //Now deallocate
   while(!allocated_buffers.empty()){
      managed_shm.deallocate(allocated_buffers.back());
      allocated_buffers.pop_back();
   }

   //Allocate 10 buffers of different sizes in a single call. Throwing version
   managed_shared_memory::size_type sizes[10];
   for(std::size_t i = 0; i < 10; ++i)
      sizes[i] = i*3;

   managed_shm.allocate_many(sizes, 10, 1, 4,  chain);
   managed_shm.deallocate_many(chain);
   return 0;
}

分配 N 个相同大小的缓冲区可以提升池和节点容器 (例如类 STL list) 的性能: 向类 STL list 插入一段前向迭代器范围时, 插入函数可以检测所需元素的数量并在单次调用中完成分配. 节点仍然可以独立释放.

分配 N 个不同大小的缓冲区可用于在必须同时分配多个对象、但在不同时间释放的情况下加速分配. 例如, 一个类可能在构造函数中进行多个初始分配 (例如网络包的头部数据), 同时还要分配将来可能重新分配大小的缓冲区 (要通过网络发送的数据). 构造函数可以不用独立分配所有数据, 而是用 allocate_many() 来加速初始化, 同时仍能释放和扩展可变大小元素的内存.

总体而言, allocate_many 在 N 值较大时才有用. 过度使用 allocate_many 会增加实际内存占用, 因为它无法复用某些元素本可使用的已有的不连续内存片段.

就地扩展内存分配

在编写 vector 之类的数据结构时, 内存重分配成为提升性能的重要工具. 托管内存段提供了一个高级重分配函数, 它提供:

  • 向前扩展: 已分配的缓冲区可以扩展, 使缓冲区末端进一步后移. 新数据可以写在旧末端与新末端之间.
  • 向后扩展: 已分配的缓冲区可以扩展, 使缓冲区开头前移. 新数据可以写在新开头与旧开头之间.
  • 收缩: 已分配的缓冲区可以收缩, 使缓冲区末端前移. 新末端与旧末端之间的内存可用于将来的分配.

如果扩展失败, 扩展还可以与分配新缓冲区结合, 得到具有"先扩展, 失败则分配新缓冲区"语义的函数.

除此之外, 该函数总是返回所分配缓冲区的实际大小, 因为很多时候由于对齐问题, 分配的缓冲区会比请求的大小略大. 这样, 程序员可以用 allocation_command 最大化内存利用率.

下面是该函数的声明:

enum boost::interprocess::allocation_type
{
   //Bitwise OR (|) combinable values
   boost::interprocess::allocate_new        = ...,
   boost::interprocess::expand_fwd          = ...,
   boost::interprocess::expand_bwd          = ...,
   boost::interprocess::shrink_in_place     = ...,
   boost::interprocess::nothrow_allocation  = ...
};


template<class T>
std::pair<T *, bool>
   allocation_command( boost::interprocess::allocation_type command
                     , std::size_t limit_size
                     , size_type &prefer_in_recvd_out_size
                     , T *&reuse_ptr);

该函数的前置条件:

  • 如果参数 command 含有值 boost::interprocess::shrink_in_place , 它就不能含有以下任何值: boost::interprocess::expand_fwd, boost::interprocess::expand_bwd.
  • 如果参数 command 含有 boost::interprocess::expand_fwd 或 boost::interprocess::expand_bwd , 参数 reuse_ptr 必须非空, 且由之前的分配函数返回.
  • 如果参数 command 含有值 boost::interprocess::shrink_in_place, 参数 limit_size 必须大于或等于参数 preferred_size .
  • 如果参数 command 含有以下任何值: boost::interprocess::expand_fwd 或 boost::interprocess::expand_bwd , 参数 limit_size 必须小于或等于参数 preferred_size .

该函数的效果如下:

  • 如果参数 command 含有值 boost::interprocess::shrink_in_place , 函数将尝试把指针 reuse_ptr 所引用内存块的大小缩小到 preferred_size , 只移动块的末端. 如果不可行, 它会尝试尽可能缩小内存块, 只要结果满足 size(p) <= limit_size . 只有当结果同时满足 preferred_size <= size(p) 和 size(p) <= limit_size 时才报告成功.
  • 如果参数 command 只包含值 boost::interprocess::expand_fwd (可附加 boost::interprocess::nothrow_allocation) , 分配器将尝试通过只移动块的末端, 把指针参数 reuse 所引用内存块的大小增大到 preferred_size . 如果不可行, 它会尝试尽可能增大内存块, 只要结果满足 size(p) >= limit_size . 只有当结果满足 limit_size <= size(p) 时才报告成功.
  • 如果参数 command 只包含值 boost::interprocess::expand_bwd (可附加 boost::interprocess::nothrow_allocation) , 分配器将尝试增大指针 reuse_ptr 所引用内存块的大小, 只移动块的起始位置并返回新位置 new_ptr . 如果不可行, 它会尝试尽可能移动块的起始位置, 只要结果满足 size(new_ptr) >= limit_size . 只有当结果满足 limit_size <= size(new_ptr) 时才报告成功.
  • 如果参数 command 只包含值 boost::interprocess::allocate_new (可附加 boost::interprocess::nothrow_allocation) , 分配器将尝试为 preferred_size 个对象分配内存. 如果不可行, 它会尝试至少为 limit_size 个对象分配内存.
  • 如果参数 command 只包含 boost::interprocess::expand_fwd 和 boost::interprocess::allocate_new 的组合 (可附加 boost::interprocess::nothrow_allocation) , 分配器会先尝试向前扩展. 如果失败, 再尝试新的分配.
  • 如果参数 command 只包含 boost::interprocess::expand_bwd 和 boost::interprocess::allocate_new 的组合 (可附加 boost::interprocess::nothrow_allocation) , 分配器会先尝试在必要时用两种方法获得 preferred_size 个对象. 如果失败, 它会再尝试在必要时用两种方法获得 limit_size 个对象.
  • 如果参数 command 只包含 boost::interprocess::expand_fwd 和 boost::interprocess::expand_bwd 的组合 (可附加 boost::interprocess::nothrow_allocation) , 分配器会先尝试向前扩展. 如果失败, 它会尝试用向后扩展或向前向后扩展的组合获得 preferred_size 个对象. 如果仍失败, 它会尝试在必要时用两种方法获得 limit_size 个对象.
  • 如果参数 command 只包含 allocation_new、boost::interprocess::expand_fwd 和 boost::interprocess::expand_bwd 的组合 (可附加 boost::interprocess::nothrow_allocation) , 分配器会先尝试向前扩展. 如果失败, 它会尝试用新分配、向后扩展或向前向后扩展的组合获得 preferred_size 个对象. 如果仍失败, 它会用相同的方法尝试获得 limit_size 个对象.
  • 分配器总是把扩展/分配/收缩后的内存块大小写入 received_size . 失败时, 分配器会在 received_size 中写入一个可能成功的新 limit_size 参数, 供下次调用使用.

在满足以下两个条件时抛出异常:

  • 分配器无法分配/扩展/收缩内存, 或前置条件存在错误
  • 参数 command 不包含 boost::interprocess::nothrow_allocation .

该函数返回:

  • 所分配内存的地址, 或扩展内存的新地址, 作为 pair 的第一个成员. 如果参数 command 含有 boost::interprocess::nothrow_allocation , 当分配/扩展失败或前置条件有误时, 第一个成员为 0.
  • 若内存是分配所得, pair 的第二个成员将为 false; 若内存是扩展所得, 则为 true. 若第一个成员为 0, 第二个成员的值未定义.

备注:

  • 如果用户选择 char 作为模板参数, 返回的缓冲区将对齐到足以容纳任何类型.
  • 如果用户选择 char 作为模板参数并执行了向后扩展, 即使对齐正确, 返回的缓冲区也可能不适用, 因为新开头与旧开头之间的距离可能不是用户要构造类型大小的整数倍, 这是由于内部限制, 扩展可能略大于请求的字节数. 执行向后扩展时, 如果已在旧缓冲区中构造了对象, 请确保正确指定类型.

下面的小示例展示了 allocation_command 的用法:

#include <boost/interprocess/managed_shared_memory.hpp>
#include <cassert>

int main()
{
   using namespace boost::interprocess;

   //Remove shared memory on construction and destruction
   struct shm_remove
   {
      shm_remove() { shared_memory_object::remove("MyName"); }
      ~shm_remove(){ shared_memory_object::remove("MyName"); }
   } remover;

   //Managed memory segment that allocates portions of a shared memory
   //segment with the default management algorithm
   managed_shared_memory managed_shm(create_only, "MyName", 10000*sizeof(std::size_t));

   //Allocate at least 100 bytes, 1000 bytes if possible
   managed_shared_memory::size_type min_size = 100;
   managed_shared_memory::size_type first_received_size = 1000;
   std::size_t *hint = 0;
   std::size_t *ptr = managed_shm.allocation_command<std::size_t>
      (boost::interprocess::allocate_new, min_size, first_received_size, hint);

   //Received size must be bigger than min_size
   assert(first_received_size >= min_size);

   //Get free memory
   managed_shared_memory::size_type free_memory_after_allocation = managed_shm.get_free_memory();

   //Now write the data
   for(std::size_t i = 0; i < first_received_size; ++i) ptr[i] = i;

   //Now try to triplicate the buffer. We won't admit an expansion
   //lower to the double of the original buffer.
   //This "should" be successful since no other class is allocating
   //memory from the segment
   min_size = first_received_size*2;
   managed_shared_memory::size_type expanded_size = first_received_size*3;
   std::size_t * ret = managed_shm.allocation_command
      (boost::interprocess::expand_fwd, min_size, expanded_size, ptr);
   //Check invariants
   assert(ptr != 0);
   assert(ret == ptr);
   assert(expanded_size >= first_received_size*2);

   //Get free memory and compare
   managed_shared_memory::size_type free_memory_after_expansion = managed_shm.get_free_memory();
   assert(free_memory_after_expansion < free_memory_after_allocation);

   //Write new values
   for(std::size_t i = first_received_size; i < expanded_size; ++i)  ptr[i] = i;

   //Try to shrink approximately to min_size, but the new size
   //should be smaller than min_size*2.
   //This "should" be successful since no other class is allocating
   //memory from the segment
   managed_shared_memory::size_type shrunk_size = min_size;
   ret = managed_shm.allocation_command
      (boost::interprocess::shrink_in_place, min_size*2, shrunk_size, ptr);

   //Check invariants
   assert(ptr != 0);
   assert(ret == ptr);
   assert(shrunk_size <= min_size*2);
   assert(shrunk_size >= min_size);

   //Get free memory and compare
   managed_shared_memory::size_type free_memory_after_shrinking = managed_shm.get_free_memory();
   assert(free_memory_after_shrinking > free_memory_after_expansion);

   //Deallocate the buffer
   managed_shm.deallocate(ptr);
   return 0;
}

allocation_command 是一个非常强大的函数, 可以带来可观的性能提升. 它在编写类 vector 数据结构时尤其有用: 程序员可以同时把分配请求的次数和内存浪费降到最低.

以 写时复制 或 只读 模式打开托管共享内存和映射文件

open_copy_on_write 模式
open_read_only 模式

open_copy_on_write 模式

程序员可以使用 open_copy_on_write 选项打开托管共享内存或映射文件. 该选项与 open_only 类似, 但对该托管段所做的所有更改都只保留在本进程内, 不会写入底层设备 (共享内存或文件).

这种写时复制方法可以减少内存消耗:

  • 相同页面共享: 当多个进程使用 open_copy_on_write 时, 操作系统起初让它们共享相同的底层物理内存页. 打开时不会实际复制数据.
  • 仅在修改时复制: 只有当某个进程试图写入托管段的某一部分时, 才会在进程私有内存中创建该部分的私有副本. 大多数时候只读数据的进程继续共享原始部分 (内存页). 这可以带来可观的内存节省, 尤其是在处理大型数据集, 或许多进程需要访问相同数据而只有少数进程修改它时.

open_read_only 模式

用 open_read_only 打开托管共享内存或托管映射文件时, 底层设备会以 read-only 属性映射到内存. 这意味着任何对该内存的写尝试 (包括锁定任何互斥量) 都可能导致操作系统报页面错误 (从而使程序终止).

因此, 在此模式下托管共享内存或托管映射文件的操作相当受限:

  • 只应使用托管共享内存/映射文件的 const 成员函数. 如果程序员取得段管理器并尝试在该对象上使用任何可用操作, 可能导致访问违例.
  • 此外, find<> 成员函数会避免使用内部锁, 可用于查找命名对象和唯一对象.

下面是一个展示这两种模式用法的示例:

#include <boost/interprocess/managed_mapped_file.hpp>
#include <fstream> //std::fstream
#include <iterator>//std::distance


int main()
{
   using namespace boost::interprocess;

   //Define file names
   const char *ManagedFile  = "MyManagedFile";
   const char *ManagedFile2 = "MyManagedFile2";

   //Try to erase any previous managed segment with the same name
   file_mapping::remove(ManagedFile);
   file_mapping::remove(ManagedFile2);
   remove_file_on_destroy destroyer1(ManagedFile);
   remove_file_on_destroy destroyer2(ManagedFile2);

   {
      //Create an named integer in a managed mapped file
      managed_mapped_file managed_file(create_only, ManagedFile, 65536);
      managed_file.construct<int>("MyInt")(0);

      //Now create a copy on write version
      managed_mapped_file managed_file_cow(open_copy_on_write, ManagedFile);

      //Erase the int and create a new one
      if(!managed_file_cow.destroy<int>("MyInt"))
         throw int(0);
      managed_file_cow.construct<int>("MyInt2")();

      //Check changes
      if(managed_file_cow.find<int>("MyInt").first || !managed_file_cow.find<int>("MyInt2").first)
         throw int(0);

      //Check the original is intact
      if(!managed_file.find<int>("MyInt").first || managed_file.find<int>("MyInt2").first)
         throw int(0);

      {  //Dump the modified copy on write segment to a file
         std::fstream file(ManagedFile2, std::ios_base::out | std::ios_base::binary);
         if(!file)
            throw int(0);
       file.write(static_cast<const char *>(managed_file_cow.get_address()), (std::streamsize)managed_file_cow.get_size());
      }

      //Now open the modified file and test changes
      managed_mapped_file managed_file_cow2(open_only, ManagedFile2);
      if(managed_file_cow2.find<int>("MyInt").first && !managed_file_cow2.find<int>("MyInt2").first)
         throw int(0);
   }
   {
      //Now create a read-only version
      managed_mapped_file managed_file_ro(open_read_only, ManagedFile);

      //Check the original is intact
      if(!managed_file_ro.find<int>("MyInt").first && managed_file_ro.find<int>("MyInt2").first)
         throw int(0);

      //Check the number of named objects using the iterators
      if(std::distance(managed_file_ro.named_begin(),  managed_file_ro.named_end())  != 1 &&
         std::distance(managed_file_ro.unique_begin(), managed_file_ro.unique_end()) != 0 )
         throw int(0);
   }
   return 0;
}
