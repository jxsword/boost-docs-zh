术语

首先, 我们来介绍一些贯穿全文将要使用的术语:

语义动作 是与解析器关联的一段任意逻辑, 仅当解析器匹配时才会执行.

较简单的解析器可以组合起来形成更复杂的解析器. 给定某个组合操作 C, 以及解析器 P0、P1、...、PN, 表达式 C(P0, P1, ..., PN) 会创建一个新的解析器 Q. 这就构成了一棵 解析树. Q 是 P1 的父节点, P2 是 Q 的子节点, 以此类推. 各解析器按这种拓扑结构所隐含的自顶向下方式被应用. 当您使用 Q 解析一个字符串时, 它会使用 P0、P1 等来完成实际工作. 如果 P3 正在被用来解析输入, 那就意味着 Q 也在被使用, 因为 Q 进行解析的方式就是把部分或全部工作分派给它的子解析器去做. 在解析的任一时刻, 都恰好有一个没有子节点的解析器正在用于解析输入; 其他所有正在使用的解析器都是它在解析树中的祖先.

子解析器 是作为另一个解析器子节点的解析器.

顶层解析器 是解析器树的根.

当前解析器 或 最底层解析器 是当前正在用于解析输入且没有子节点的解析器.

规则 是一类能让构建大型复杂解析器变得更轻松的解析器. 子规则 是作为某条其他规则子节点的规则. 当前规则 或 最底层规则 是当前正在用于解析输入且没有子规则的那条规则. 注意, 虽然当前解析器始终有且仅有一个, 但当前规则可能存在也可能不存在 —— 规则只是解析器的一种, 在解析的某一时刻您可能正在使用规则, 也可能没有.

顶层解析 是由顶层解析器执行的解析操作. 之所以需要这个术语, 是因为尽管大多数解析失败都只是某个特定解析器的局部失败, 但有些解析失败会导致对 parse() 的调用报告整个解析失败. 对于这些情形, 我们说这种局部失败"导致顶层解析失败".

在整篇 Boost.Parser 文档中, 我都会提到"对 parse() 的调用". 请把它理解为"对 parse() API 一节中所述的任一函数的调用". 这包括 prefix_parse()、callback_parse() 和 callback_prefix_parse().

本文档中会经常遇到一些特殊类型的解析器.

一种是 序列解析器; 您会看到它用 operator>> 创建, 例如 p1 >> p2 >> p3. 序列解析器按顺序逐个尝试让其所有子解析器去匹配输入. 当且仅当其所有子解析器都匹配时, 它才匹配输入.

另一种是 备选解析器; 您会看到它用 operator| 创建, 例如 p1 | p2 | p3. 备选解析器按顺序逐个尝试让其所有子解析器去匹配输入, 在最多匹配一个子解析器后即停止. 当且仅当其中一个子解析器匹配时, 它才匹配输入.

最后还有 排列解析器; 它用 operator|| 创建, 例如 p1 || p2 || p3. 排列解析器会以任意顺序尝试让其所有子解析器去匹配输入. 因此, 解析器 p1 || p2 || p3 等价于 (p1 >> p2 >> p3) | (p1 >> p3 >> p2) | (p2 >> p1 >> p3) | (p2 >> p3 >> p1) | (p3 >> p1 >> p2) | (p3 >> p2 >> p1). 希望其简洁带来的好处是不言自明的. 当且仅当其所有子解析器都匹配时, 它才匹配输入, 且与匹配顺序无关.

每个 Boost.Parser 解析器都有一个与之关联的 属性, 或者明确地没有属性. 属性是解析器在匹配输入时生成的一个值. 例如, 解析器 double_ 在匹配输入时会生成一个 double. ATTR() 是一个概念性的宏, 展开为传给它的解析器的属性类型; ATTR(double_) 就是 double. 这类似于 attribute 类型特征.

接下来, 我们来看几个使用 Boost.Parser 进行解析的简单程序. 我们将从小处着手, 逐步深入.

Hello, Whomever

这几乎是人所能写出的使用 Boost.Parser 的最简化示例. 我们从命令行取一个字符串, 如果未给出则取 "World", 然后解析它:

#include <boost/parser/parser.hpp>

#include <iostream>
#include <string>


namespace bp = boost::parser;

int main(int argc, char const * argv[])
{
    std::string input = "World";
    if (1 < argc)
        input = argv[1];

    std::string result;
    bp::parse(input, *bp::char_, result);
    std::cout << "Hello, " << result << "!\n";
}

表达式 *bp::char_ 是一个解析器表达式. 它使用了 Boost.Parser 提供的众多解析器之一: char_. 与所有 Boost.Parser 解析器一样, 它定义了一些操作. 在这里, *bp::char_ 使用重载的 operator* 作为 Kleene star 运算符的 C++ 版本. 由于 C++ 没有后缀一元 * 运算符, 我们只能使用已有的运算符, 因此它被用作前缀.

因此, *bp::char_ 的意思是"任意数量的字符". 换句话说, 它实际上不可能失败. 即使是空字符串也能匹配它.

解析操作通过调用 parse() 函数来完成, 并把解析器作为参数之一传入:

bp::parse(input, *bp::char_, result);

这里的参数是: input, 要解析的范围; *bp::char_, 用于执行解析的解析器; 以及 result, 用于存放解析结果的出参. 不必过分纠结于这种从 parse() 中取出解析结果的方式; 这样做有多种方法, 我们会在后续章节中逐一介绍.

另外, 请暂时忽略 Boost.Parser 是如何弄清 *bp::char_ 解析器的结果类型是 std::string 这一事实的. 这背后有明确的规则, 我们稍后会介绍.

这次对 parse() 调用的效果并不很有意思 —— 由于我们给它的解析器永远不会失败, 而且我们把输出放进与输入相同的类型中, 它只是把 input 的内容复制到 result.

一个简单的示例

我们来看一个稍微复杂一点的示例, 尽管它仍然很简单. 这次不再接受任意给定的 char, 而是要求有一定的结构. 我们来解析一个或多个以逗号分隔的 double.

用于解析 double 的 Boost.Parser 解析器是 double_. 因此, 要解析单个 double, 直接使用它即可. 如果想连续解析两个 double, 则应使用:

boost::parser::double_ >> boost::parser::double_

表达式中的 operator>> 是序列运算符; 可以把它读作"后跟". 如果把序列运算符与 Kleene star 组合起来, 写出下面的式子就能得到我们想要的解析器:

boost::parser::double_ >> *(',' >> boost::parser::double_)

这是一个至少匹配一个 double 的解析器 —— 因为上面的表达式中有第一个 double_ —— 后跟零个或多个"逗号后跟一个 double"的实例. 注意, 我们可以直接使用 ','. 虽然它不是解析器, 但 operator>> 以及定义在 Boost.Parser 解析器上的其他运算符都有接受"字符/解析器"对参数的重载; 这些运算符重载会创建正确的解析器来识别 ','.

#include <boost/parser/parser.hpp>

#include <iostream>
#include <string>


namespace bp = boost::parser;

int main()
{
    std::cout << "Enter a list of doubles, separated by commas.  No pressure. ";
    std::string input;
    std::getline(std::cin, input);

    auto const result = bp::parse(input, bp::double_ >> *(',' >> bp::double_));

    if (result) {
        std::cout << "Great! It looks like you entered:\n";
        for (double x : *result) {
            std::cout << x << "\n";
        }
    } else {
        std::cout
            << "Good job!  Please proceed to the recovery annex for cake.\n";
    }
}

第一个示例通过填入出参来交付解析结果. 这次对 parse() 的调用则改为返回一个结果. 可以看到, 该结果可按语境转换为 bool, 而 *result 是某种范围. 实际上, 这次对 parse() 调用的返回类型是 std::optional<std::vector<double>>. 自然, 如果解析失败, 则返回 std::nullopt. 稍后我们会看到 Boost.Parser 如何把解析器的类型映射为返回类型或被填入的出参的类型.

注释

有一个类型特征可以告诉您解析器的属性类型, 即 attribute (以及与之关联的别名 attribute_t). 我们会在 属性生成 一节中详细讨论它.

如果我在 shell 中运行它, 结果如下:

$ example/trivial

Great! It looks like you entered:
5.6
8.9
$ example/trivial
Enter a list of doubles, separated by commas.  No pressure. 5.6, 8.9
Good job!  Please proceed to the recovery annex for cake.

它无法识别 "5.6, 8.9". 这是因为它期望一个逗号后紧跟一个 double, 但我在逗号后面插入了一个空格. 如果我在逗号之前插入空格, 或者在 double 列表的前面或后面插入空格, 也会发生同样的解析失败.

还有一点: 有一种更好的方式来编写上面的解析器. 与其重复 double_ 子解析器, 我们本可以这样写:

bp::double_ % ','

这在语义上与 bp::double_ >> *(',' >> bp::double_) 完全相同. "某段输入重复一次或多次, 且每个实例之间有一个分隔符"这种模式非常常见, 以至于专门为它设计了一个运算符 operator%. 从现在起我们会一直使用这个运算符.

一个优雅处理空白的简单示例

我们来修改刚才看到的简单解析器, 让它忽略在 double 和逗号之间可能出现的空格. 要在发现空白的地方跳过它, 我们可以传入一个 跳过解析器 给 parse() 的调用 (我们不需要改动传给 parse() 的解析器). 这里我们使用 ws, 它匹配任何 Unicode 空白字符.

#include <boost/parser/parser.hpp>

#include <iostream>
#include <string>


namespace bp = boost::parser;

int main()
{
    std::cout << "Enter a list of doubles, separated by commas.  No pressure. ";
    std::string input;
    std::getline(std::cin, input);

    auto const result = bp::parse(input, bp::double_ % ',', bp::ws);

    if (result) {
        std::cout << "Great! It looks like you entered:\n";
        for (double x : *result) {
            std::cout << x << "\n";
        }
    } else {
        std::cout
            << "Good job!  Please proceed to the recovery annex for cake.\n";
    }
}

跳过解析器, 即 跳过器, 会在传给 parse() 的解析器内部的各子解析器之间运行. 在本例中, 跳过器会在解析第一个 double 之前、解析后续每个逗号或 double 之前, 以及最后各运行一次. 因此, 本程序对字符串 "3.6,5.9" 和 " 3.6 , \t 5.9 " 的解析结果相同.

跳过是 Boost.Parser 中的一个重要概念. 您可以跳过任何东西, 而不只是空白; 您可能想跳过的东西还有很多. 传给 parse() 的跳过器可以是任意的解析器. 例如, 如果您为某种脚本语言编写解析器, 可以编写一个跳过器来跳过空白、行内注释和行尾注释.

在本文档的其余部分, 我们几乎只会使用跳过解析器. 能够忽略输入中您不关心的部分实在太方便了, 以至于在实践中不做跳过的解析反而很少见.

语义动作

与所有解析系统 (lex & yacc、Boost.Spirit 等) 一样, Boost.Parser 提供了一种把语义动作与解析的各个部分关联起来的机制. 下面这个程序与上一个示例中的程序几乎相同, 区别在于它用语义动作来实现: 由语义动作把每个解析出的 double 追加到结果中, 而不是自动构建并返回结果. 为此, 我们把上一示例中的 double_ 替换为 double_[action]; action 就是我们的语义动作:

#include <boost/parser/parser.hpp>

#include <iostream>
#include <string>


namespace bp = boost::parser;

int main()
{
    std::cout << "Enter a list of doubles, separated by commas. ";
    std::string input;
    std::getline(std::cin, input);

    std::vector<double> result;
    auto const action = [&result](auto & ctx) {
        std::cout << "Got one!\n";
        result.push_back(_attr(ctx));
    };
    auto const action_parser = bp::double_[action];
    auto const success = bp::parse(input, action_parser % ',', bp::ws);

    if (success) {
        std::cout << "You entered:\n";
        for (double x : result) {
            std::cout << x << "\n";
        }
    } else {
        std::cout << "Parse failure.\n";
    }
}

在 shell 中运行, 结果如下:

$ example/semantic_actions
Enter a list of doubles, separated by commas. 4,3
Got one!
Got one!
You entered:
4
3

在 Boost.Parser 中, 语义动作通过可调用对象来实现, 这种可调用对象只接受一个指向解析上下文对象的参数. 解析上下文对象表示解析的当前状态. 在该示例中, 我们使用下面这个 lambda 作为可调用对象:

auto const action = [&result](auto & ctx) {
    std::cout << "Got one!\n";
    result.push_back(_attr(ctx));
};

我们在 lambda 中既向 std::cout 打印了一条消息, 又记录了一个解析结果. 只要您愿意, 它也可以两者都做、只做其一, 或两者都不做. 在 lambda 中获得解析出的 double 的方式是向解析上下文索取. _attr(ctx) 就是向解析上下文索取语义动作所附加的解析器所生成属性的方法. 还有许多类似 _attr() 的函数可用于访问解析上下文中的状态, 我们稍后会介绍其中更多. 解析上下文 一节定义了解析上下文究竟是什么以及它如何工作.

注意, 您不能把一个不加修饰的 lambda 直接用作语义动作. 否则, 编译器会看到两个 '[' 字符, 以为即将开始解析属性. 加上括号即可解决:

p[([](auto & ctx){/*...*/})]

在这样做之前, 请注意: 您作为语义动作编写的 lambda 几乎总是泛型的 (带有 auto & ctx 参数), 因此通常可以复用. 您编写的大多数语义动作 lambda 都应该写成独立命名的形式, 并起一个恰当的名字. 即使它们不会被复用, 具名的 lambda 也能让您的解析器更精简、更易读.

重要

给解析器附加语义动作会移除其属性. 也就是说, ATTR(p[a]) 总是特殊的无属性类型 none, 无论 ATTR(p) 是什么类型.

解析以查找子范围

到目前为止, 我们看到的示例都是解析一些文本并生成相关联的属性. 有时, 您只想找到输入中包含所找内容的某个子范围, 而完全不想生成属性.

有两种 指令 可以影响任何解析器的属性类型, 即 raw[] 和 string_view[]. (我们稍后会在 指令 一节中更详细地介绍指令. 现在, 您只需知道: 指令会包装一个解析器, 并改变其工作方式的某些方面.)

raw[]

raw[] 会把其解析器的属性改为一个 subrange, 其 begin() 和 end() 返回所解析序列中与 p 相匹配部分的边界.

namespace bp = boost::parser;
auto int_parser = bp::int_ % ',';            // ATTR(int_parser) is std::vector<int>
auto subrange_parser = bp::raw[int_parser];  // ATTR(subrange_parser) is a subrange

// Parse using int_parser, generating integers.
auto ints = bp::parse("1, 2, 3, 4", int_parser, bp::ws);
assert(ints);
assert(*ints == std::vector<int>({1, 2, 3, 4}));

// Parse again using int_parser, but this time generating only the
// subrange matched by int_parser.  (prefix_parse() allows matches that
// don't consume the entire input.)
auto const str = std::string("1, 2, 3, 4, a, b, c");
auto first = str.begin();
auto range = bp::prefix_parse(first, str.end(), subrange_parser, bp::ws);
assert(range);
assert(range->begin() == str.begin());
assert(range->end() == str.begin() + 10);

static_assert(std::is_same_v<
              decltype(range),
              std::optional<bp::subrange<std::string::const_iterator>>>);

注意, subrange 的迭代器类型是 std::string::const_iterator, 因为这正是传给 prefix_parse() 的迭代器类型. 如果我们把 char const * 迭代器传给 prefix_parse(), 那么它就会是这里的迭代器类型. 唯一的例外来自支持 Unicode 的解析 (参见 Unicode 支持). 在其中某些情况下, 解析中实际使用的迭代器并不是您传入的那个. 例如, 如果您调用 prefix_parse() 并传入 char8_t * 迭代器, 它会创建一个从 UTF-8 到 UTF-32 的转码视图, 并解析该视图的迭代器. 在这种情况下, 您得到的 subrange 的迭代器类型是转码迭代器. 此时, 您传给 prefix_parse() 的那个底层迭代器可以这样取回: 对每个转码迭代器调用 .base() 成员函数 —— 这里指的是返回的 subrange 中的转码迭代器.

auto const u8str = std::u8string(u8"1, 2, 3, 4, a, b, c");
auto u8first = u8str.begin();
auto u8range = bp::prefix_parse(u8first, u8str.end(), subrange_parser, bp::ws);
assert(u8range);
assert(u8range->begin().base() == u8str.begin());
assert(u8range->end().base() == u8str.begin() + 10);
string_view[]

string_view[] 的语义与 raw[] 非常相似, 区别在于它生成的是 std::basic_string_view<CharT> (其中 CharT 是被解析的底层范围的类型), 而不是 subrange. 要使其工作, 底层范围必须是连续的. 在 C++20 之前无法检测迭代器的连续性, 因此该指令只在 C++20 及更高版本中可用.

namespace bp = boost::parser;
auto int_parser = bp::int_ % ',';              // ATTR(int_parser) is std::vector<int>
auto sv_parser = bp::string_view[int_parser];  // ATTR(sv_parser) is a string_view

auto const str = std::string("1, 2, 3, 4, a, b, c");
auto first = str.begin();
auto sv1 = bp::prefix_parse(first, str.end(), sv_parser, bp::ws);
assert(sv1);
assert(*sv1 == str.substr(0, 10));

static_assert(std::is_same_v<decltype(sv1), std::optional<std::string_view>>);

由于 string_view[] 生成的是 string_view, 它无法像上文针对 raw[] 描述的那样返回转码迭代器. 如果您对 CharT 序列使用 string_view[] 进行解析, 得到的恰好是一个 std::basic_string_view<CharT>. 如果解析在支持 Unicode 的代码路径中使用了转码, string_view[] 会按需分解转码迭代器. 如果您把转码视图传给 parse(), 或把转码迭代器传给 prefix_parse(), string_view[] 仍能毫无问题地看穿这些转码迭代器, 并给您返回底层范围中一部分的 string_view.

auto sv2 = bp::parse("1, 2, 3, 4" | bp::as_utf32, sv_parser, bp::ws);
assert(sv2);
assert(*sv2 == "1, 2, 3, 4");

static_assert(std::is_same_v<decltype(sv2), std::optional<std::string_view>>);

解析上下文

现在是详细介绍解析上下文的好时机. 您编写的任何语义动作都需要使用解析上下文中的状态, 因此您需要了解有哪些可用的东西.

解析上下文是存储解析当前状态的对象 —— 当前迭代器、结束迭代器、错误处理器等. 在解析过程中的不同时刻, 数据看起来像是被"加入"或"移除". 例如, 当解析器 p 带有语义动作 a 并成功时, 上下文会把 p 生成的属性加入解析上下文, 然后调用 a 并把上下文传给它.

尽管上下文对象看起来像是有东西被加入或移除, 实际上并非如此. 现实中并不存在唯一的上下文对象. 上下文在解析过程中的各个时刻形成, 通常是在开始解析一个子解析器时. 每个上下文都是在先前上下文的基础上, 按需增加或修改一些成员而形成的新上下文对象. 当包含新上下文对象的函数返回时, 它的上下文对象 (如果有的话) 会被销毁. 这样做效率很高, 因为解析上下文只有大约十来个数据成员, 且每个数据成员的大小都不超过一个指针. 因此, 在修改上下文时复制整个上下文非常快. 上下文不做任何内存分配.

提示

所有这些以解析上下文作为第一个参数的函数都能通过实参相关查找 (ADL) 找到. 您可能永远不需要用 boost::parser:: 来限定它们.

始终可用的数据的访问器

按照惯例, 所有接受解析上下文的 Boost.Parser 函数 (因而都是打算在语义动作内部使用的函数) 的名称都以下划线开头.

_pass()

_pass() 返回一个对 bool 的引用, 用于指示当前解析的成功或失败. 可以用它来强制当前解析通过或失败:

[](auto & ctx) {
    // If the attribute fails to meet this predicate, fail the parse.
    if (!necessary_condition(_attr(ctx)))
        _pass(ctx) = false;
}

注意, 语义动作要被执行, 其关联的解析器必须已经成功. 因此, 除非您此前已在动作中写过 _pass(ctx) = false, 否则 _pass(ctx) = true 什么也不做; 它是多余的.

_begin(), _end() 和 _where()

_begin() 和 _end() 分别返回您传给 parse() 的范围的开始和结束. _where() 返回一个 subrange, 指示当前解析所匹配输入的边界. 如果您只想解析一些文本并返回一个由某些元素位置组成的结果, 而不生成任何其他属性, _where() 会很有用. _where() 对于跟踪各元素的位置同样至关重要, 这有助于在解析的后续阶段提供良好的诊断信息. 想想 XML 中标签不匹配的情形; 如果您在元素末尾解析到一个结束标签, 而它与开始标签不匹配, 您会希望生成的错误消息同时提及或显示这两个标签. 把 _where(ctx).begin() 存放到结束标签解析器可以访问的地方, 就能做到这一点. 具体示例参见 错误处理与调试.

_error_handler()

_error_handler() 返回与传给 parse() 的解析器相关联的错误处理器的引用. 使用 _error_handler(), 您可以在语义动作内部生成错误和警告. 具体示例参见 错误处理与调试.

仅有时可用的数据的访问器
_attr()

_attr() 返回对当前解析器属性值的引用. 它只在当前解析器的解析成功时可用. 如果解析器没有语义动作, 就不会有任何属性被加入解析上下文. 它可用于读写当前解析器的属性:

[](auto & ctx) { _attr(ctx) = 3; }

如果当前解析器没有属性, 则返回 none.

_val()

_val() 返回对当前用于解析的规则 (如果有的话) 的属性值的引用, 即使在规则的解析尚未成功时也可用. 它可用于设置当前规则的属性, 甚至可以从作为规则内部子解析器的解析器中设置. 假设我们正在编写一个解析器, 它带有一个位于规则内的语义动作. 如果我们想把当前规则的值设置为子解析器属性的某个函数, 就会这样编写语义动作:

[](auto & ctx) { _val(ctx) = some_function(_attr(ctx)); }

如果没有当前规则, 或当前规则没有属性, 则返回 none.

您需要在这样的情况下使用 _val(): rule 的解析器的默认属性与 rule 的属性类型不直接兼容. 在这些情况下, 您需要像上面的示例那样编写一些代码来计算 rule 的属性, 计算依据是 rule 的解析器所生成的属性. 关于 rules 的更多信息, 请参见下一页以及 关于规则的更多内容.

_globals()

_globals() 返回对一个由用户提供的对象的引用, 该对象包含您在解析期间想使用的任何数据. 解析的"全局对象"是一个您交给顶层解析器的对象 —— 通常是一个结构体. 然后您可以在解析期间的任意时刻用 _globals() 来访问它. 我们稍后会在 parse() API 一节中看到全局对象如何与顶层解析器关联. 举例来说, 假设解析的前段需要记录一些黑名单值, 而解析的后段可能需要解析一些值, 一旦看到黑名单中的值就使解析失败. 在解析的前段, 您可以编写类似这样的代码.

[](auto & ctx) {
    // black_list is a std::unordered_set.
    _globals(ctx).black_list.insert(_attr(ctx));
}

在解析的后段, 您随后可以使用 black_list 在值被解析时对其进行检查.

[](auto & ctx) {
    if (_globals(ctx).black_list.contains(_attr(ctx)))
        _pass(ctx) = false;
}
_locals()

_locals() 返回对当前正在解析的规则 (如果有的话) 的一个或多个局部值的引用. 如果有两个或更多局部值, _locals() 返回对 boost::parser::tuple 的引用. 带局部变量的规则我们还没有讲到 (参见 关于规则的更多内容), 但目前您只需知道: 您可以提供一个模板参数 (LocalState) 给 rule, 规则会默认构造一个该类型的对象, 供规则内部使用. 您可以通过 _locals() 来访问它:

[](auto & ctx) {
    auto & local = _locals(ctx);
    // Use local here.  If 'local' is a hana::tuple, access its members like this:
    using namespace hana::literals;
    auto & first_element = local[0_c];
    auto & second_element = local[1_c];
}

如果没有当前规则, 或当前规则没有局部变量, 则返回 none.

_params()

_params() 与 _locals() 一样, 作用于当前正在解析的规则 (如果有的话) (参见 关于规则的更多内容). 如果当前规则只有一个参数, 它同样返回对该值的引用; 如果当前规则有多个参数, 则返回包含多个值的 boost::parser::tuple. 如果没有当前规则, 或当前规则没有参数, 则返回 none.

与 _locals() 不同, 您不向 rule 提供模板参数. 而是调用 rule 的 with() 成员函数 (同样参见 关于规则的更多内容).

注释

none 是 Boost.Parser 中用作解析上下文访问器返回值的一种类型. none 可转换为任何具有默认构造函数的类型, 可从任何类型转换而来, 可从任何类型赋值, 并且对所有可重载的运算符都有模板化重载. 其设计意图是: 对 _val()、_globals() 等的误用应当能够通过编译, 并在运行时产生断言. 经验表明, 用调试器检查导致错误的调用栈, 比在编译器诊断信息中大海捞针的用户体验好得多. 更详细的解释参见 设计理由 一节.

_no_case()

_no_case() 在如下情况下返回 true: 当前解析上下文位于一个或多个 (可能嵌套的) no_case[] 指令内部. 我没有这方面的用例, 但如果不把它暴露出来, 它就会成为上下文中唯一无法从语义动作内部查看的东西. 加上它很容易, 所以我就加了.

规则解析器

这个示例与我们目前看到的其他示例非常相似. 它的不同之处仅在于使用了一个 rule. 打个比方, 可以把 char_ 或 double_ 这样的解析器看作一行单独的代码, 而把 rule 看作一个函数. 与函数一样, rule 有自己的名字, 甚至可以前向声明. 下面是我们定义 rule 的方式, 这类似于前向声明一个函数:

bp::rule<struct doubles, std::vector<double>> doubles = "doubles";

这声明了规则本身. rule 是一个解析器, 我们可以立即在其他解析器中使用它. 这个定义相当紧凑; 请注意以下几点:

  • 第一个模板参数是标签类型 struct doubles. 这里我们一次性声明并使用了该标签类型; 您也可以使用先前声明的标签类型.
  • 第二个模板参数是解析器的属性类型. 如果不提供, 规则将没有属性.
  • 这个规则对象本身名为 doubles.
  • 我们给 doubles 提供了诊断文本 "doubles", 这样 Boost.Parser 在调试期间生成解析器跟踪时就知道如何指代它.

好, 那么如果 doubles 是一个解析器, 它做什么呢? 我们通过定义一个单独的解析器来定义该规则的行为, 到这个阶段它应该看起来相当眼熟了:

auto const doubles_def = bp::double_ % ',';

这类似于为前向声明的函数编写定义. 注意我们使用的名字 doubles_def. 此时, doubles 规则解析器与 doubles_def 非规则解析器之间尚无任何联系. 这是有意为之 —— 我们希望能够分别定义它们. 要把它们连接起来, 我们声明一些具有 Boost.Parser 所能理解的接口的函数, 并使用标签类型 struct doubles 把它们连在一起. 我们用一个宏来做到这一点:

BOOST_PARSER_DEFINE_RULES(doubles);

这个宏展开为让规则 doubles 与其解析器 doubles_def 协同工作所需的代码. _def 后缀是该宏赖以工作的命名约定. 标签类型使得规则解析器 doubles 在作为解析器使用时能够调用这些重载之一.

BOOST_PARSER_DEFINE_RULES 展开为一个名为 parse_rule() 的函数的两个重载. 在上例中, 每个重载都接受一个 struct doubles 参数 (以便把它们与 parse_rule() 针对其他规则的其他重载区分开), 并使用 doubles_def 进行解析. 您永远不需要自己调用 parse_rule() 的任何重载; 它由实现 rules 的解析器 rule_parser 在内部使用.

下面是为每条规则展开的那个宏的定义:

#define BOOST_PARSER_DEFINE_IMPL(_, rule_name_)                                \
    template<                                                                  \
        typename Iter,                                                         \
        typename Sentinel,                                                     \
        typename Context,                                                      \
        typename SkipParser>                                                   \
    decltype(rule_name_)::parser_type::attr_type parse_rule(                   \
        decltype(rule_name_)::parser_type::tag_type *,                         \
        Iter & first,                                                          \
        Sentinel last,                                                         \
        Context const & context,                                               \
        SkipParser const & skip,                                               \
        boost::parser::detail::flags flags,                                    \
        bool & success,                                                        \
        bool & dont_assign)                                                    \
    {                                                                          \
        auto const & parser = BOOST_PARSER_PP_CAT(rule_name_, _def);           \
        using attr_t =                                                         \
            decltype(parser(first, last, context, skip, flags, success));      \
        using attr_type = decltype(rule_name_)::parser_type::attr_type;        \
        if constexpr (boost::parser::detail::is_nope_v<attr_t>) {              \
            dont_assign = true;                                                \
            parser(first, last, context, skip, flags, success);                \
            return {};                                                         \
        } else if constexpr (std::is_same_v<attr_type, attr_t>) {              \
            return parser(first, last, context, skip, flags, success);         \
        } else if constexpr (std::is_constructible_v<attr_type, attr_t>) {     \
            return attr_type(                                                  \
                parser(first, last, context, skip, flags, success));           \
        } else {                                                               \
            attr_type attr{};                                                  \
            parser(first, last, context, skip, flags, success, attr);          \
            return attr;                                                       \
        }                                                                      \
    }                                                                          \
                                                                               \
    template<                                                                  \
        typename Iter,                                                         \
        typename Sentinel,                                                     \
        typename Context,                                                      \
        typename SkipParser,                                                   \
        typename Attribute>                                                    \
    void parse_rule(                                                           \
        decltype(rule_name_)::parser_type::tag_type *,                         \
        Iter & first,                                                          \
        Sentinel last,                                                         \
        Context const & context,                                               \
        SkipParser const & skip,                                               \
        boost::parser::detail::flags flags,                                    \
        bool & success,                                                        \
        bool & /*dont_assign*/,                                                \
        Attribute & retval)                                                    \
    {                                                                          \
        auto const & parser = BOOST_PARSER_PP_CAT(rule_name_, _def);           \
        using attr_t =                                                         \
            decltype(parser(first, last, context, skip, flags, success));      \
        if constexpr (boost::parser::detail::is_nope_v<attr_t>) {              \
            parser(first, last, context, skip, flags, success);                \
        } else {                                                               \
            parser(first, last, context, skip, flags, success, retval);        \
        }                                                                      \
    }

现在我们有了 doubles 解析器, 可以像使用其他任何解析器一样使用它:

auto const result = bp::parse(input, doubles, bp::ws);

完整程序如下:

#include <boost/parser/parser.hpp>

#include <deque>
#include <iostream>
#include <string>


namespace bp = boost::parser;


bp::rule<struct doubles, std::vector<double>> doubles = "doubles";
auto const doubles_def = bp::double_ % ',';
BOOST_PARSER_DEFINE_RULES(doubles);

int main()
{
    std::cout << "Please enter a list of doubles, separated by commas. ";
    std::string input;
    std::getline(std::cin, input);

    auto const result = bp::parse(input, doubles, bp::ws);

    if (result) {
        std::cout << "You entered:\n";
        for (double x : *result) {
            std::cout << x << "\n";
        }
    } else {
        std::cout << "Parse failure.\n";
    }
}

所有这些都是为了引入 rules 的概念. 您究竟为什么想要使用 rules 可能仍不太清楚. 关于 rules 的用例和大量细节将在后面的 关于规则的更多内容 一节中介绍.

注释

rules 的存在意味着您可能永远不需要编写低级解析器. 您只需把现有的解析器组合成 rules 即可.

解析为 struct 和 class

到目前为止, 我们见到的都是重复解析同一个值的简单解析器 (带或不带逗号和空格). 按特定顺序解析几个值也很常见. 假设您想解析一条员工记录. 下面是您可能会编写的解析器:

namespace bp = boost::parser;
auto employee_parser = bp::lit("employee")
    >> '{'
    >> bp::int_ >> ','
    >> quoted_string >> ','
    >> quoted_string >> ','
    >> bp::double_
    >> '}';

employee_parser 的属性类型是 boost::parser::tuple<int, std::string, std::string, double>. 好的一面是, 您无需编写任何语义动作就得到了该记录的全部解析数据. 不太好的一面是, 您现在必须使用 get() 按索引把各个元素取出来. 如果能直接解析到程序最终要使用的数据结构中就好多了. 这通常是一个聚合类型 struct 或 class. Boost.Parser 支持解析到任意的聚合类型 struct 中, 也支持解析到可以由手头的元组构造出来的非聚合类型中.

聚合类型作为属性

如果我们有一个 struct, 其数据成员的类型与 boost::parser::tuple 属性类型 (针对 employee_parser) 中列出的类型相同, 那么直接解析到它里面, 而不是先解析成元组、之后再构造 struct, 会好得多. 幸运的是, 这在 Boost.Parser 中可以直接工作. 下面是一个直接解析到兼容聚合类型的示例.

#include <boost/parser/parser.hpp>

#include <iostream>
#include <string>


struct employee
{
    int age;
    std::string surname;
    std::string forename;
    double salary;
};

namespace bp = boost::parser;

int main()
{
    std::cout << "Enter employee record. ";
    std::string input;
    std::getline(std::cin, input);

    auto quoted_string = bp::lexeme['"' >> +(bp::char_ - '"') >> '"'];
    auto employee_p = bp::lit("employee")
        >> '{'
        >> bp::int_ >> ','
        >> quoted_string >> ','
        >> quoted_string >> ','
        >> bp::double_
        >> '}';

    employee record;
    auto const result = bp::parse(input, employee_p, bp::ws, record);

    if (result) {
        std::cout << "You entered:\nage:      " << record.age
                  << "\nsurname:  " << record.surname
                  << "\nforename: " << record.forename
                  << "\nsalary  : " << record.salary << "\n";
    } else {
        std::cout << "Parse failure.\n";
    }
}

遗憾的是, 这是利用了宽松的属性赋值逻辑; employee_parser 解析器的属性仍然是 boost::parser::tuple. 关于属性出参兼容性的描述, 参见 parse() API.

因此, 更常见的需求是创建一个返回特定类型 (如 employee) 的规则. 只要给规则指定 struct 类型, 我们就能确保该解析器无论出现在解析的哪个位置, 都总是生成一个 employee 结构体作为其属性. 如果我们创建一个简单解析器 P, 它使用 employee_p 规则, 例如 bp::int >> employee_p, 那么 P 的属性类型将是 boost::parser::tuple<int, employee>.

#include <boost/parser/parser.hpp>

#include <iostream>
#include <string>


struct employee
{
    int age;
    std::string surname;
    std::string forename;
    double salary;
};

namespace bp = boost::parser;

bp::rule<struct quoted_string, std::string> quoted_string = "quoted name";
bp::rule<struct employee_p, employee> employee_p = "employee";

auto quoted_string_def = bp::lexeme['"' >> +(bp::char_ - '"') >> '"'];
auto employee_p_def = bp::lit("employee")
    >> '{'
    >> bp::int_ >> ','
    >> quoted_string >> ','
    >> quoted_string >> ','
    >> bp::double_
    >> '}';

BOOST_PARSER_DEFINE_RULES(quoted_string, employee_p);

int main()
{
    std::cout << "Enter employee record. ";
    std::string input;
    std::getline(std::cin, input);

    static_assert(std::is_aggregate_v<std::decay_t<employee &>>);

    auto const result = bp::parse(input, employee_p, bp::ws);

    if (result) {
        std::cout << "You entered:\nage:      " << result->age
                  << "\nsurname:  " << result->surname
                  << "\nforename: " << result->forename
                  << "\nsalary  : " << result->salary << "\n";
    } else {
        std::cout << "Parse failure.\n";
    }
}

正如当解析器的属性类型是元组时, 您可以把一个 struct 作为出参传给 parse(); 当解析器的属性类型是结构体时, 您同样可以把元组作为出参传给 parse():

// Using the employee_p rule from above, with attribute type employee...
boost::parser::tuple<int, std::string, std::string, double> tup;
auto const result = bp::parse(input, employee_p, bp::ws, tup); // Ok!
重要

把 struct 像元组一样自动使用, 依赖于一点元编程. 由于编译器的限制, 检测 struct 数据成员数量的元程序最多只能处理一定数量的成员. 幸运的是, 该上限是可以配置的; 参见 BOOST_PARSER_MAX_AGGREGATE_SIZE.

一般 class 类型作为属性

很多时候, 您并没有一个想从解析中生成的聚合结构体. 如果 Boost.Parser 能检测到作为属性生成的元组的各个成员可以用作某个类型构造函数的实参, 那就比上面的聚合代码更方便了. 所以, Boost.Parser 就是这样做的.

#include <boost/parser/parser.hpp>

#include <iostream>
#include <string>


namespace bp = boost::parser;

int main()
{
    std::cout << "Enter a string followed by two unsigned integers. ";
    std::string input;
    std::getline(std::cin, input);

    constexpr auto string_uint_uint =
        bp::lexeme[+(bp::char_ - ' ')] >> bp::uint_ >> bp::uint_;
    std::string string_from_parse;
    if (parse(input, string_uint_uint, bp::ws, string_from_parse))
        std::cout << "That yields this string: " << string_from_parse << "\n";
    else
        std::cout << "Parse failure.\n";

    std::cout << "Enter an unsigned integer followed by a string. ";
    std::getline(std::cin, input);
    std::cout << input << "\n";

    constexpr auto uint_string = bp::uint_ >> +bp::char_;
    std::vector<std::string> vector_from_parse;
    if (parse(input, uint_string, bp::ws, vector_from_parse)) {
        std::cout << "That yields this vector of strings:\n";
        for (auto && str : vector_from_parse) {
            std::cout << "  '" << str << "'\n";
        }
    } else {
        std::cout << "Parse failure.\n";
    }
}

我们来看第一次解析.

constexpr auto string_uint_uint =
    bp::lexeme[+(bp::char_ - ' ')] >> bp::uint_ >> bp::uint_;
std::string string_from_parse;
if (parse(input, string_uint_uint, bp::ws, string_from_parse))
    std::cout << "That yields this string: " << string_from_parse << "\n";
else
    std::cout << "Parse failure.\n";

这里我们使用解析器 string_uint_uint, 它生成 boost::parser::tuple<std::string, unsigned int, unsigned int> 属性. 当我们尝试把它解析到一个出参 std::string 属性中时, 直接就能工作. 这是因为 std::string 有一个构造函数接受一个 std::string、一个偏移量和一个长度. 下面是另一次解析:

constexpr auto uint_string = bp::uint_ >> +bp::char_;
std::vector<std::string> vector_from_parse;
if (parse(input, uint_string, bp::ws, vector_from_parse)) {
    std::cout << "That yields this vector of strings:\n";
    for (auto && str : vector_from_parse) {
        std::cout << "  '" << str << "'\n";
    }
} else {
    std::cout << "Parse failure.\n";
}

现在我们的解析器是 uint_string, 它生成 boost::parser::tuple<unsigned int, std::string> 属性 —— 末尾的两个 char 合并成了一个 std::string. 这两个值可以用来构造一个 std::vector<std::string> —— 通过接受计数的 T 构造函数.

就像可以用聚合类型代替元组一样, 非聚合的 class 类型在大多数地方也可以代替元组. 这包括把非聚合的 class 类型用作 rule 的属性类型.

然而, 虽然兼容的元组可以代替聚合类型, 但您不能把元组代替某个 class 类型 T, 仅仅因为这个元组本可以用来构造 T. 想一想把上面第二次解析中的替换反过来会怎样. 把 std::vector<std::string> 转换成一个 boost::parser::tuple<unsigned int, std::string> 是毫无意义的.

备选解析器

您经常需要解析可能有多种形式之一的东西. operator| 被重载用于构成备选解析器. 例如:

namespace bp = boost::parser;
auto const parser_1 = bp::int_ | bp::eps;

parser_1 匹配一个整数, 如果失败, 则匹配 epsilon, 即空字符串. 这等价于写:

namespace bp = boost::parser;
auto const parser_2 = -bp::int_;

然而, parser_1 和 parser_2 都不等价于这样写:

namespace bp = boost::parser;
auto const parser_3 = bp::eps | bp::int_; // Does not do what you think.

原因在于, 备选解析器会逐个尝试其子解析器, 并在第一个匹配的子解析器处停止. epsilon 可以匹配任何东西, 因为它长度为零且不消耗输入, 甚至能匹配输入的末尾. 这意味着 parser_3 等价于单独的 eps.

注释

因此, 对任何解析器 p 写出 eps | p 都被视为缺陷. 当调试构建遇到 eps | p 时会触发断言.

警告

当涉及 eps 时, 这类错误非常常见, 而且也很容易检测. 然而, 也可能写出 P1 >> P2 这样的代码, 其中 P1 是 P2 的前缀, 例如 int_ | int >> int_ 或 repeat(4)[hex_digit] | repeat(8)[hex_digit]. 这几乎可以肯定是一个错误, 但在一般情况下无法检测 —— 请记住, rules 可以单独编译, 并考虑一对规则, 其关联的 _def 解析器分别是 int_ 和 int_ >> int_.

解析带引号的字符串

需要解析带引号的字符串是很常见的. 但在使用跳过器时 (而您在 99% 的情况下都应该使用跳过器), 带引号的字符串会有些棘手. 您既不想允许字符串中间出现任意空白, 也不想把字符串中的所有空白都去掉. 使用典型的跳过器 ws 时, 这两种情况都会发生.

下面是大多数人编写带引号字符串解析器的方式:

namespace bp = boost::parser;
const auto string = bp::lexeme['"' >> *(bp::char_ - '"') > '"'];

需要注意几点:

  • 结果是一个字符串;
  • 引号不包含在结果中;
  • 在结束引号之前有一个期望点;
  • lexeme[] 的使用会禁用解析器中的跳过, 并且它必须写在引号外面, 而不是 operator* 表达式外面; 以及
  • 没有办法在字符串中间写一个引号.

这是一个非常常见的模式. 我已经写过几十次这样的带引号字符串解析器. 上面的解析器是快速而粗糙的版本. 更健壮的版本要能处理字符串中被转义的引号, 而这又立刻需要支持被转义的转义字符.

Boost.Parser 提供 quoted_string 来替代这种非常常见的模式. 它支持引号转义和转义字符转义, 使用反斜杠作为转义字符.

namespace bp = boost::parser;

auto result1 = bp::parse("\"some text\"", bp::quoted_string, bp::ws);
assert(result1);
std::cout << *result1 << "\n"; // Prints: some text

auto result2 = bp::parse(R"("some \"text\"")", bp::quoted_string, bp::ws);
assert(result2);
std::cout << *result2 << "\n"; // Prints: some "text"

尽管这个用例很常见, 仍有一些非常相似的用例它没有覆盖. 因此, quoted_string 有一些选项. 如果您用单个字符调用它, 它会返回一个 quoted_string, 并使用该字符作为引号字符.

auto result3 = bp::parse("!some text!", bp::quoted_string('!'), bp::ws);
assert(result3);
std::cout << *result3 << "\n"; // Prints: some text

您也可以提供一个字符范围. 该范围中的同一个字符必须用于字符串的两端; 不允许不匹配. 想想 Python 允许您用 '"' 或 '\'' 来给字符串加引号, 但两边必须使用相同的字符.

auto result4 = bp::parse("'some text'", bp::quoted_string("'\""), bp::ws);
assert(result4);
std::cout << *result4 << "\n"; // Prints: some text

在带引号字符串解析器中, 另一件常见的事是识别转义序列. 如果您有一些不需要真正解析的简单转义序列, 比如说 C++ 的简单转义序列, 您也可以提供一个 symbols 对象. 其模板参数 T (即传给 symbols<T> 的那个) 必须是 char 或 char32_t. 您不需要包含被转义的反斜杠或被转义的引号字符, 因为它们总是有效.

// the c++ simple escapes
bp::symbols<char> const escapes = {
    {"'", '\''},
    {"?", '\?'},
    {"a", '\a'},
    {"b", '\b'},
    {"f", '\f'},
    {"n", '\n'},
    {"r", '\r'},
    {"t", '\t'},
    {"v", '\v'}};
auto result5 =
    bp::parse("\"some text\r\"", bp::quoted_string('"', escapes), bp::ws);
assert(result5);
std::cout << *result5 << "\n"; // Prints (with a CRLF newline): some text

此外, 对于上面所示的每种形式, 您还可以选择提供一个解析器作为最后一个参数, 它将用于解析引号内的每个字符. 这里必须提供一个真正的完整解析器; 不能提供字符或字符串字面量. 如果您不提供字符解析器, 则使用 char_.

auto result6 = bp::parse(
    "'some text'", bp::quoted_string("'\"", bp::char_('g')), bp::ws);
assert(!result6);
result6 =
    bp::parse("'gggg'", bp::quoted_string("'\"", bp::char_('g')), bp::ws);
assert(result6);
std::cout << *result6 << "\n"; // Prints: gggg

解析详解

现在您已经看过一些示例了, 让我们更详细地看看解析是如何工作的. 请看这个示例.

namespace bp = boost::parser;
auto int_pair = bp::int_ >> bp::int_;         // Attribute: tuple<int, int>
auto int_pairs_plus = +int_pair >> bp::int_;  // Attribute: tuple<std::vector<tuple<int, int>>, int>

int_pairs_plus 必须匹配一对 int (使用 int_pair) 一次或多次, 然后还必须再匹配一个 int. 换句话说, 它匹配输入中任何奇数个 (大于 1) 的 int. 我们来看看这次解析是如何进行的.

auto result = bp::parse("1 2 3", int_pairs_plus, bp::ws);

在解析开始时, 顶层解析器使用它的第一个子解析器 (如果有的话) 开始解析. 因此, 作为序列解析器的 int_pairs_plus 会把控制权交给它的第一个解析器 +int_pair. 然后, +int_pair 会使用 int_pair 来进行解析, 而后者又会使用 bp::int_. 这就形成了一个解析器栈, 每个解析器都使用某个特定的子解析器.

步骤 1) 输入是 "1 2 3", 活动解析器的栈是 int_pairs_plus -> +int_pair -> int_pair -> bp::int_. (把 "->" 读作"使用".) 这里解析了 "1", 其后的空白由 bp::ws 跳过. 控制权转交给第二个 bp::int_ 解析器, 它位于 int_pair 中.

步骤 2) 输入是 "2 3", 解析器栈看起来相同, 只是活动解析器变成第二个 bp::int_, 它来自 int_pair. 这个解析器消耗 "2", 然后 bp::ws 跳过其后的空格. 由于 int_pair 的匹配已经完成, 它的 boost::parser::tuple<int, int> 属性也完成了. 它的父节点是 +int_pair, 所以这个元组属性被推入 +int_pair 属性的末尾, 后者的类型是 std::vector<boost::parser::tuple<int, int>>. 控制权向上转交给 int_pair 的父节点 +int_pair. 由于 +int_pair 是一个"一次或多次"解析器, 它开始新一轮迭代; 控制权再次转交给 int_pair.

步骤 3) 输入是 "3", 解析器栈看起来相同, 只是活动解析器再次变成第一个 bp::int_, 它来自 int_pair, 而且我们处于 +int_pair 的第二次迭代中. 这个解析器消耗 "3". 由于这已是输入的末尾, 第二个 bp::int_ (属于 int_pair) 无法匹配. "3" 的这次部分匹配不应计入, 因为它不是完整匹配的一部分. 于是, int_pair 报告自己失败, +int_pair 停止迭代. 由于它已经成功匹配过一次, +int_pair 并不失败; 它是一个"零或多次"解析器; 其子解析器在首次成功之后的失败不会导致它失败. 控制权转交给 int_pairs_plus 序列中的下一个解析器.

步骤 4) 输入再次是 "3", 解析器栈是 int_pairs_plus -> bp::int_. 这里解析了 "3", 解析到达输入末尾. 控制权转交给 int_pairs_plus, 它刚按顺序成功匹配完了其全部解析器. 接着它生成自己的属性 —— boost::parser::tuple<std::vector<boost::parser::tuple<int, int>>, int>, 并从 bp::parse() 返回.

在步骤 3 和步骤 4 之间需要注意一点: 在步骤 4 开始时, 输入位置已经回到了步骤 3 开始时的位置. 这种回溯发生在备选解析器的某个备选项失败时. 下一页会更详细地介绍回溯的语义.

解析器详解

到目前为止, 解析器一直是以较为抽象的实体来介绍的. 您可能想要更多细节. Boost.Parser 解析器 P 是一个带有两个调用运算符重载的可调用对象. 这两个函数非常相似, 在许多解析器中, 一个是以另一个为基础实现的. 第一个函数执行解析并返回解析器的默认属性. 第二个函数执行完全相同的解析, 但接受一个出参并把解析器的属性写入其中. 出参不必与默认属性类型相同, 但两者必须兼容.

兼容意味着默认属性可以以某种方式赋给出参. 这通常指直接赋值, 但也可能指元组到聚合类型或聚合类型到元组的转换. 对于序列类型, 兼容意味着该序列类型具有语义如常的 insert 或 push_back. 这意味着解析器 +boost::parser::int_ 填充一个 std::set<int> 与填充一个 std::vector<int> 一样好.

有些解析器还有执行匹配所需的额外状态. 例如, char_ 解析器可以用要匹配的单个码点来参数化; 该码点的具体值存储在解析器对象中.

没有哪个解析器直接支持在解析器上定义的全部操作 (operator|、operator>> 等). 取而代之的是, 有一个名为 parser_interface 的模板支持所有这些操作. parser_interface 包装每个解析器, 把它存为数据成员, 使其适合一般使用. 您只应该在调试器中看到 parser_interface, 或者可能在某些参考文档中看到它. 您永远不需要在自己的代码中写出它.

回溯

如上一页所述, 当解析尝试匹配当前解析器 P 时, 如果匹配了输入的一部分, 却未能匹配全部 P, 就会发生回溯. 在解析 P 期间消耗的那部分输入基本上被"退还"了.

这是必需的, 因为 P 可能由子解析器组成, 而每个成功的子解析器都会尝试消耗输入、生成属性等. 当后面的某个子解析器失败时, 对 P 的解析就失败了, 此时输入必须回退到 P 开始解析时的位置, 而不是最近一个匹配的子解析器停止的位置.

备选解析器常常会逐个对多个子解析器求值, 前进然后恢复输入位置, 直到某个子解析器成功为止. 请看这个示例.

namespace bp = boost::parser;
auto const parser = repeat(53)[other_parser] | repeat(10)[other_parser];

对 parser 求值意味着尝试让 other_parser 匹配 53 次, 如果失败, 再尝试让 other_parser 匹配 10 次. 假设您解析的输入匹配了 other_parser 11 次. parser 会匹配它, 并且在解析过程中还会对 other_parser 求值 21 次.

repeat(53)[other_parser] 和 repeat(10)[other_parser] 的属性都是 std::vector<ATTR(other_parser)>; 假设 ATTR(other_parser) 是 int. parser 作为整体的属性也是一样的, 即 std::vector<int>. 由于 other_parser 正忙着生成 int —— 准确地说生成了 21 个 —— 您可能想知道: 当 repeat(53)[other_parser] 未能找齐全部 53 个输入时, 期间生成的那些值会怎么样. 那时它的 std::vector<int> 中将含有 11 个 int.

当重复型解析器失败且正在生成属性时, 它会清空自己的容器. 这不仅适用于上面那样的解析器, 也适用于所有其他重复型解析器, 包括用 operator+ 或 operator* 创建的那些.

因此, 当 parser 成功解析 10 个输入后 (因为备选项的右侧只消耗 10 次重复), 属性 std::vector<int> (即 parser 的属性) 将包含 10 个 int.

注释

Boost.Spirit 的用户可能熟悉 hold[] 指令. 由于上面描述的行为, Boost.Parser 中没有这样的指令.

期望点

好, 那么如果所有解析器都尽最大努力去匹配输入, 而且要么全匹配要么全不匹配, 这难道不会给各种坏输入留下被忽略的空间吗? 请看 解析 JSON 示例中的顶层解析器.

auto const value_p_def =
    number | bp::bool_ | null | string | array_p | object_p;

如果我用它来解析 "\"" 会发生什么? 解析尝试 number, 失败. 然后尝试 bp::bool_, 失败. 接着 null 也失败. 最后, 它开始解析 string. 好消息是, 第一个字符是 JSON 字符串的起始引号. 不幸的是, 这也是输入的末尾, 所以 string 也必须失败. 然而, 我们大概不想就此放弃对 string 的解析而转去尝试 array_p, 对吧? 如果用户写了一个起始引号却没有匹配的结束引号, 那它并不是 value_p_def 后面某个备选项的前缀; 这是非良构的 JSON. 下面是 string 规则的解析器:

auto const string_def = bp::lexeme['"' >> *(string_char - '"') > '"'];

注意, 右侧使用的是 operator> 而非 operator>>. 它表示与 operator>> 相同的序列操作, 只是它还代表一个期望. 如果 operator> 之前的解析成功, 那么它后面的内容必须也成功. 否则, 顶层解析失败, 并发出一条诊断信息. 诊断信息会引用发生错误的行, 说一些类似 "Expected '"' here." 的话, 并用插入符指向输入中期望右侧匹配的位置.

选择使用 > 还是 >>, 就是您向 Boost.Parser 表明解析失败是否为硬错误的方式.

符号表

编写解析器时, 经常会遇到这样一组字符串: 它们被解析时与一组值一一对应. 当您必须通过语义动作把每个字符串与一个属性关联起来时, 编写能识别所有可能输入字符串的解析器是很繁琐的. 此时, 我们可以使用符号表.

假设我们想解析罗马数字 —— 这是最常见的与工作相关的解析问题之一. 我们想识别这样的数字: 以任意数量的 "M" 开头 (表示千位), 后跟百位、十位和个位. 这些部分都可以在输入中缺失, 但不能全部缺失. 下面是三个可以分别用于识别个位、十位和百位值的 Boost.Parser 符号表:

bp::symbols<int> const ones = {
    {"I", 1},
    {"II", 2},
    {"III", 3},
    {"IV", 4},
    {"V", 5},
    {"VI", 6},
    {"VII", 7},
    {"VIII", 8},
    {"IX", 9}};

bp::symbols<int> const tens = {
    {"X", 10},
    {"XX", 20},
    {"XXX", 30},
    {"XL", 40},
    {"L", 50},
    {"LX", 60},
    {"LXX", 70},
    {"LXXX", 80},
    {"XC", 90}};

bp::symbols<int> const hundreds = {
    {"C", 100},
    {"CC", 200},
    {"CCC", 300},
    {"CD", 400},
    {"D", 500},
    {"DC", 600},
    {"DCC", 700},
    {"DCCC", 800},
    {"CM", 900}};

symbols 把 char 类型的字符串映射到与之关联的属性. 属性的类型必须作为模板参数提供给 symbols —— 在本例中是 int.

我们遇到的任何 "M" 都应当给结果加上 1000, 而所有其他值都来自符号表. 下面是我们为此需要的语义动作:

int result = 0;
auto const add_1000 = [&result](auto & ctx) { result += 1000; };
auto const add = [&result](auto & ctx) { result += _attr(ctx); };

add_1000 只是把 1000 加到 result 上. add 把其解析器生成的属性加到 result 上.

现在我们只需把这些部件组合起来构成一个解析器:

using namespace bp::literals;
auto const parser =
    *'M'_l[add_1000] >> -hundreds[add] >> -tens[add] >> -ones[add];

这里出现了几个新东西, 让我们把它们拆解开来. 'M'_l 是一个 字面量解析器. 也就是说, 它是解析字面量 char、码点或字符串的解析器. 在本例中, 被解析的是 char 'M'. 末尾的 _l 部分是一个 UDL 后缀, 您可以把它放在任何 char、char32_t 或 char const * 之后来构成字面量解析器. 您也可以通过编写 lit() 并传入前述类型之一的实参来创建字面量解析器.

考虑到我们在上一个示例中刚用过字面量 ',', 为什么还需要这些东西? 原因是 'M' 没有在与其他 Boost.Parser 解析器组合的表达式中使用, 而是用在了 *'M'_l[add_1000] 内部. 如果我们写成 *'M'[add_1000], 那显然是非良构的; char 既没有与之关联的 operator*, 也没有 operator[].

提示

任何时候您想在 Boost.Parser 解析器中使用 char、char32_t 或字符串字面量: 如果它与一个已有的 Boost.Parser 子解析器 p 组合在一起, 例如 'x' >> p, 就按原样书写; 否则, 您需要把它包装在对 lit() 的调用中, 或者使用 _l UDL 后缀.

接下来看下一部分: -hundreds[add]. 到现在为止, 下标运算符的用法应该已经相当熟悉了; 它把语义动作 add 关联到解析器 hundreds. 开头的 operator- 是新出现的. 它意味着被作用的解析器是可选的. 您可以把它读作"零或一". 因此, 如果 hundreds 未能在 *'M'[add_1000] 之后被成功解析, 就什么也不会发生, 因为 hundreds 允许缺失 —— 它是可选的. 如果 hundreds 被成功解析, 比如匹配了 "CC", 那么得到的属性 200 会被加入 result —— 它位于 add 内部.

        {"CD", 400},
        {"D", 500},
        {"DC", 600},
        {"DCC", 700},
        {"DCCC", 800},
        {"CM", 900}};

    int result = 0;
    auto const add_1000 = [&result](auto & ctx) { result += 1000; };
    auto const add = [&result](auto & ctx) { result += _attr(ctx); };

    using namespace bp::literals;
    auto const parser =
        *'M'_l[add_1000] >> -hundreds[add] >> -tens[add] >> -ones[add];

    if (bp::parse(input, parser) && result != 0)
        std::cout << "That's " << result << " in Arabic numerals.\n";
    else
        std::cout << "That's not a Roman number.\n";
}

可变符号表

前面的示例展示了如何把符号表用作固定的查找表. 如果我们想在解析过程中向表中添加内容怎么办? 我们可以做到, 但必须在语义动作中进行. 首先, 这是我们的符号表, 其中已经有一个值:

bp::symbols<int> const symbols = {{"c", 8}};
assert(parse("c", symbols));

不出所料, 把符号表当作解析器来解析符号表中的那一个字符串是可以工作的. 现在, 这是我们的解析器:

auto const parser = (bp::char_ >> bp::int_)[add_symbol] >> symbols;

在这里, 我们把语义动作附加到的不是 double_ 这样的简单解析器, 而是序列解析器 (bp::char_ >> bp::int_). 这个序列解析器包含两个解析器, 每个都有自己的属性, 因此它以元组的形式生成两个属性.

auto const add_symbol = [&symbols](auto & ctx) {
    using namespace bp::literals;
    // symbols::insert() requires a string, not a single character.
    char chars[2] = {_attr(ctx)[0_c], 0};
    symbols.insert(ctx, chars, _attr(ctx)[1_c]);
};

在语义动作内部, 我们可以使用 Boost.Hana 提供的 UDL 和 boost::hana::tuple::operator[]() 来获取属性元组的第一个元素. 第一个属性来自 char_, 是 _attr(ctx)[0_c]; 第二个属性来自 int_, 是 _attr(ctx)[1_c] (如果 boost::parser::tuple 是 std::tuple 的别名, 您就要改用 std::get 或 boost::parser::get). 要把符号加入符号表, 我们调用 insert().

auto const parser = (bp::char_ >> bp::int_)[add_symbol] >> symbols;

在解析期间, ("X", 9) 被解析并加入符号表. 然后, 第二个 'X' 被符号表解析器识别. 然而:

assert(!parse("X", symbols));

如果我们再次解析, 会发现 "X" 并没有留在符号表中. symbols 被声明为 const 这一事实或许已经向您暗示了会出现这种情况.

完整程序如下:

#include <boost/parser/parser.hpp>

#include <iostream>
#include <string>


namespace bp = boost::parser;

int main()
{
    bp::symbols<int> const symbols = {{"c", 8}};
    assert(parse("c", symbols));

    auto const add_symbol = [&symbols](auto & ctx) {
        using namespace bp::literals;
        // symbols::insert() requires a string, not a single character.
        char chars[2] = {_attr(ctx)[0_c], 0};
        symbols.insert(ctx, chars, _attr(ctx)[1_c]);
    };
    auto const parser = (bp::char_ >> bp::int_)[add_symbol] >> symbols;

    auto const result = parse("X 9 X", parser, bp::ws);
    assert(result && *result == 9);
    (void)result;

    assert(!parse("X", symbols));
}

重要

symbols 在内部把它的所有字符串存储为 UTF-32. 如果您进行 Unicode 或 ASCII 解析, 这对您毫无影响. 如果您对并非 Unicode 子集的字符编码 (例如 EBCDIC) 进行非 Unicode 解析, 则可能引发问题. 更多信息参见 Unicode 支持 一节.

可以永久地向 symbols 添加符号. 为此, 您必须使用一个可变的 symbols 对象 s, 并通过调用 s.insert_for_next_parse() (而不是 s.insert()) 来添加符号. 这两个操作是正交的, 因此如果您既想把符号添加到表中用于当前顶层解析, 又想让它留在表中供后续顶层解析使用, 就需要调用这两个函数.

也可以从符号表中擦除单个条目, 或者彻底清空符号表. 与插入一样, erase 和 clear 既有针对当前解析的版本, 也有只作用于后续解析的版本. 完整的操作集合见 symbols 的 API 文档.

注释

symbols 的每个 *_for_next_parse() 函数都有两个版本 —— 一个接受上下文, 一个不接受. 带上下文的版本用于语义动作内部. 不带上下文的版本用于任何解析之外.

解析器及其用途

Boost.Parser 自带了解析任务所需的所有解析器. 每个解析器要么是一个 constexpr 对象, 要么是一个 constexpr 函数. 有些非函数的对象也是可调用的, 例如 char_, 它可以直接使用, 也可以带实参使用, 如 char_('a', 'z'). 从现在起, 任何可调用的解析器 —— 无论是函数还是可调用对象 —— 都将被称为 可调用解析器. 注意, 不存在无参的可调用解析器; 它们都接受一个或多个实参.

每个可调用解析器都接受一个或多个 解析实参. 解析实参可以是一个值, 也可以是接受解析上下文引用的可调用对象. 该引用参数可以是可变的, 也可以是常量的. 例如:

struct get_attribute
{
    template<typename Context>
    auto operator()(Context & ctx)
    {
        return _attr(ctx);
    }
};

它也可以是一个 lambda. 例如:

[](auto const & ctx) { return _attr(ctx); }

从解析实参 (它可以是值, 也可以是接受解析上下文实参的可调用对象) 产生一个值的操作, 被称为对解析实参求值. 如果解析实参 arg 可以用当前上下文调用, 那么 arg 的求值结果就是 arg(ctx); 否则, 求值结果就是 arg 本身.

有些可调用解析器接受一个 解析谓词. 解析谓词与解析实参不完全相同, 因为它必须是可调用对象, 不能是值. 解析谓词的返回类型必须可按语境转换为 bool. 例如:

struct equals_three
{
    template<typename Context>
    bool operator()(Context const & ctx)
    {
        return _attr(ctx) == 3;
    }
};

当然, 它也可以是一个 lambda:

[](auto & ctx) { return _attr(ctx) == 3; }

概念性宏 RESOLVE() 展开为对解析实参或解析谓词求值的结果. 在本文档的其余部分您会看到它的用法.

下面是一个展示解析实参用法的示例:

namespace bp = boost::parser;
// This parser matches one code point that is at least 'a', and at most
// the value of last_char, which comes from the globals.
auto last_char = [](auto & ctx) { return _globals(ctx).last_char; }
auto subparser = bp::char_('a', last_char);

暂时不必关心全局对象是什么; 要点在于: 通过使用解析上下文, 您可以让传给解析器的任何实参依赖于解析的当前状态:

namespace bp = boost::parser;
// This parser parses two code points.  For the parse to succeed, the
// second one must be >= 'a' and <= the first one.
auto set_last_char = [](auto & ctx) { _globals(ctx).last_char = _attr(x); };
auto parser = bp::char_[set_last_char] >> subparser;

std::variant<ATTR(p1), ATTR(p2), ...>

如果您的整数类型 IntType 没有被任何 Boost.Parser 解析器覆盖, 您可以显式指定基数 (base/radix) 或位数界限. 做法是在正确整数类型的现有解析器上调用 base() 和 digits() 成员函数. 因此, 如果 IntType 是无符号的, 您应使用 uint_; 如果是有符号的, 则应使用 int_. 例如:

constexpr auto hex_int = bp::uint_.base<16>();

constexpr auto hex_4_def = bp::uint_.base<16>().digits<8>();

指令

指令是您的解析器中本身没有任何含义的元素. 有些指令是二阶解析器, 需要一阶解析器来完成实际解析. 另一些则以某种方式影响解析. 从词法上看, 您通常可以通过 [] 的使用来辨认指令; 指令总是 []. 非指令也可能使用它, 但只在附加语义动作时才会.

那些作为二阶解析器的指令在技术上是指令, 但由于它们也被用来创建解析器, 只关注这一点更有用. 指令 repeat() 和 if_() 已在解析器一节中描述过; 这里不再多谈.

与序列、备选和排列解析器的交互

序列解析器、备选解析器和排列解析器在大多数情况下不会嵌套. (为了简单起见, 我们只考虑序列解析器, 但其中大部分逻辑同样适用于备选解析器.) a >> b >> c 与 (a >> b) >> c 和 a >> (b >> c) 相同, 它们都表示为一个 seq_parser, 带有三个子解析器 a、b 和 c. 然而, 如果有什么东西阻止了两个 seq_parsers 直接交互, 它们就会嵌套. 例如, lexeme[a >> b] >> c 是一个 seq_parser, 其中包含两个解析器 lexeme[a >> b] 和 c. 这是因为 lexeme[] 会接受给定的解析器并将其包装在一个 lexeme_parser 中. 这进而关闭了序列解析器的合并逻辑, 因为第二个 operator>> (位于 lexeme[a >> b] >> c 中) 的两侧都不是 seq_parsers. 序列解析器有多条规则, 基于其子解析器的位置和属性来决定解析器的整体属性类型 (参见 属性生成). 因此, 知道哪些指令会创建新解析器 (以及创建什么类型) 而哪些不会, 是很重要的; 下文会对每条指令予以说明.

各条指令
repeat()

参见 解析器及其用途. 它创建一个 repeat_parser.

if_()

参见 解析器及其用途. 它创建一个 seq_parser.

omit[]

omit[p] 会禁用解析器 p 的属性生成. 不仅 omit[p] 本身没有属性, 而且通常发生在 p 内部的所有属性生成工作也都会被跳过.

这条指令在如下情形中很有用: 假设您有一个相当复杂的解析器 p, 它会生成一个庞大且构造代价高的属性. 再假设您想编写一个函数, 只统计 p 能匹配一个字符串多少次 (匹配不重叠). 与其直接使用 p 并构建所有那些属性, 或者重写 p 去掉属性生成, 不如使用 omit[].

它创建一个 omit_parser.

raw[]

raw[p] 把属性从 ATTR(p) 改为一个视图, 该视图界定输入中被 p 匹配的子范围. 视图的类型是 subrange<I>, 其中 I 是解析中使用的迭代器类型. 注意, 这可能与传给 parse() 的迭代器类型不同. 例如, 在解析 UTF-8 时, 传给 parse() 的迭代器可能是 char8_t const *, 但在解析内部它将是一个从 UTF-8 到 UTF-32 的转码 (转换) 迭代器. 与 omit[] 一样, raw[] 会使 p 内部的所有属性生成工作都被跳过.

与上面 omit[] 的复用场景类似, raw[] 可用于查找位置 —— 即 p 在一个字符串中所有不重叠匹配的位置.

它创建一个 raw_parser.

string_view[]

string_view[p] 与 raw[p] 非常相似, 区别在于它把 p 的属性改为 std::basic_string_view<C>, 其中 C 是被解析底层范围的字符类型. string_view[] 要求被解析的底层范围是连续的. 由于这一点只能在 C++20 及更高版本中检测, string_view[] 在 C++17 模式下不可用.

与上面 omit[] 的复用场景类似, string_view[] 可用于查找位置 —— 即 p 在一个字符串中所有不重叠匹配的位置. 使用 raw[] 还是 string_view[] 来报告位置更自然, 取决于您的用例, 但两者本质上相同.

它创建一个 string_view_parser.

no_case[]

no_case[p] 会在 p 的解析中启用不区分大小写的解析. 这适用于 char_()、string() 和 bool_ 解析器所解析的文本. 数字解析器本身就是不区分大小写的. 不区分大小写是通过对待解析文本和被匹配解析器中的值执行 Unicode 大小写折叠来实现的 (如果您想进一步了解 Unicode 大小写折叠, 请参见下面的注释). 在非 Unicode 代码路径中, 不会执行完整的 Unicode 大小写折叠, 而是只对小于 0x100 的值进行转换. 示例:

#include <boost/parser/transcode_view.hpp> // For as_utfN.

namespace bp = boost::parser;
auto const street_parser = bp::string(u8"Tobias Straße");
assert(!bp::parse("Tobias Strasse" | bp::as_utf32, street_parser));             // No match.
assert(bp::parse("Tobias Strasse" | bp::as_utf32, bp::no_case[street_parser])); // Match!

auto const alpha_parser = bp::no_case[bp::char_('a', 'z')];
assert(bp::parse("a" | bp::as_utf32, bp::no_case[alpha_parser])); // Match!
assert(bp::parse("B" | bp::as_utf32, bp::no_case[alpha_parser])); // Match!

在 no_case[] 内部, 一切基本都按您朴素预期的那样工作, 唯一例外是 char_ 的双字符范围版本有一个限制. 它只把输入中的一个码点与它的两个实参比较 (例如上面示例中的 'a' 和 'z'). 它不会对多码点大小写折叠展开做任何特殊处理. 例如, char_(U'ß', U'ß') 匹配输入 U"s", 这是合理的, 因为 U'ß' 展开为 U"ss". 然而, 同一个解析器并不能匹配输入 U"ß"! 简而言之, 请坚持使用具有单码点大小写折叠展开的码点对. 如果您需要支持会展开成多个码点的码点, 请使用另一个重载, 例如: char_(U"abcd/*...*/ß").

注释

Unicode 大小写折叠是一种把文本统一成单一大小写的操作; 如果对两段文本 A 和 B 都执行它, 就可以按位比较它们, 看它们除大小写外是否相同. 大小写折叠有时会把一个码点展开成多个码点 (例如, 对 "ẞ" 进行大小写折叠会得到 "ss"). 当发生这种多码点展开时, 展开后的码点处于 NFKC 规范化形式.

它创建一个 no_case_parser.

lexeme[]

lexeme[p] 会禁用跳过器 (如果正在使用跳过器) 在 p 解析中的使用. 例如, 如果您想在解析器的大部分地方启用跳过, 但只在某个不适合跳过的部分禁用它, 这就很有用. 如果您在解析器的大部分地方跳过空白, 但想解析可能包含空格的字符串, 就应当使用 lexeme[]:

namespace bp = boost::parser;
auto const string_parser = bp::lexeme['"' >> *(bp::char_ - '"') >> '"'];

如果没有 lexeme[], 我们的字符串解析器会正确匹配 "foo bar", 但生成的属性将是 "foobar".

它创建一个 lexeme_parser.

skip[]

skip[] 类似于 lexeme[] 的反向操作. 它会在解析中启用跳过, 即使之前没有启用. 例如, 在一个使用跳过器的 parse() 调用中, 假设我们正在使用这些解析器:

namespace bp = boost::parser;
auto const one_or_more = +bp::char_;
auto const skip_or_skip_not_there_is_no_try = bp::lexeme[bp::skip[one_or_more] >> one_or_more];

lexeme[] 的使用禁用了跳过, 但随后 skip[] 的使用又把它打开. 最终结果是, 第一处 one_or_more 会使用传给 parse() 的跳过器; 第二处则不会.

skip[] 还有另一个用途. 您可以用不同的解析器参数化 skip, 从而只在该指令的作用域内更换跳过器. 假设我们把 ws 传给了 parse(), 并且在该 parse() 调用内部的某处使用这些解析器:

namespace bp = boost::parser;
auto const zero_or_more = *bp::char_;
auto const skip_both_ways = zero_or_more >> bp::skip(bp::blank)[zero_or_more];

第一处 zero_or_more 会使用传给 parse() 的跳过器, 即 ws; 第二处将使用 blank 作为它的跳过器.

它创建一个 skip_parser.

merge[]、separate[] 和 transform(f)[]

这些指令会影响属性的生成. 更多细节参见 属性生成 一节.

merge[] 和 separate[] 会创建给定 seq_parser 的一个副本.

transform(f)[] 创建一个 tranform_parser.

delimiter(p)[]

delimiter 指令使排列解析器内部可以使用分隔符. 它只适用于排列解析器, 就像 merge[] 和 separate[] 只适用于序列解析器一样. 请看这个排列解析器.

constexpr auto parser = bp::int_ || bp::string("foo") || bp::char_('g');

它将按任意顺序匹配以下全部内容: 一个整数、"foo" 和 'g' (例如 "foo g 42"). 如果您还想让这三个元素以逗号分隔, 可以改写为这个解析器.

constexpr auto delimited_parser =
    bp::delimiter(bp::lit(','))[bp::int_ || bp::string("foo") || bp::char_('g')];

delimited_parser 会解析与 parser 相同的元素, 但还要求元素之间有逗号 (如 "foo, g, 42" 所示).

上表未涵盖几条特殊规则:

首先, 零次或多次与一次或多次重复 (operator*() 与 operator+()) 在组合时可能发生折叠. 对于任何解析器 p, +(+p) 会折叠为 +p; **p、*+p 和 +*p 各自都会折叠为仅 *p.

其次, 在备选解析器中把 eps 用作最后一个备选项 之外 的任何备选项, 是常见的错误来源; Boost.Parser 不允许这样做. 原因在于, 对任何解析器 p 而言, eps | p 等价于 eps, 因为 eps 总是匹配成功. 对于以条件参数化的 eps 则并非如此. 对于任何条件 cond, eps(cond) 允许出现在备选解析器内的任何位置.

重要

C++ 运算符 > 与 >> 的优先级不同. 这有时会在编译器警告中出现. 无论您是否对由 > 与 >> 分隔的解析器链添加括号, 所得表达式的求值结果都是相同的. 如果编译器有抱怨, 尽可放心添加括号. 更宽泛地说, 编写解析器时请牢记 C++ 的运算符优先级规则 — 最容易写出的形式未必具有您想要的语义.

注释

在调试器中查看 Boost.Parser 解析器, 或查看它们的参考文档时, 您可能会看到对模板 parser_interface 的引用. 这个模板的存在是为了提供上述运算符重载. 它使得解析器本身可以非常简单 —— 大多数解析器只是一个带有两个成员函数的结构体. 在使用 Boost.Parser 时, parser_interface 基本上是不可见的, 您永远不需要在自己的代码中写出这个模板.

属性生成

到目前为止, 我们已经见过来自不同解析器的几种不同类型的属性: int 对应 int_, boost::parser::tuple<char, int> 对应 boost::parser::char_ >> boost::parser::int_, 等等. 让我们更严格地看看这是如何工作的.

注释

有些解析器完全没有属性. 在下面的表中, 这类属性的类型列为 "None.". 每个没有属性的解析器都会返回一个非 void 的类型. 这使逻辑保持简单; 如果必须处理两种情况 —— void 或非 void —— 会让这个库明显更复杂. 与这些解析器关联的这个非 void 属性的类型是一个实现细节. 该类型来自 boost::parser::detail 命名空间, 而且几乎没什么用. 实践中您不应看到这个类型. 在语义动作中, 向不生成属性的解析器索取属性 (使用 _attr(ctx)) 会得到特殊类型 boost::parser::none 的值. 当以返回被解析属性的形式调用 parse() 时, 如果没有属性, 就简单地返回 bool; 它指示解析的成功或失败.

警告

Boost.Parser 假定所有属性都是半正则的 (semi-regular, 参见 std::semiregular). 除了拷贝操作之外几乎满足 std::semiregular 的仅可移动类型也是支持的. 在 Boost.Parser 代码内部, 属性会被移动赋值、移动和默认构造. 不支持不可默认构造的类型.

属性类型特征 attribute

您可以使用 attribute (以及关联的别名 attribute_t) 来确定解析器在被传给 parse() 时会具有的属性. 由于至少有一个解析器 (char_) 具有多态属性类型, attribute 还接受被解析范围的类型. 如果解析器不生成属性, attribute 会给出 none, 而不是 void.

如果您想把一对迭代器/哨兵传给 attribute, 可以像这样从中创建一个范围:

constexpr auto parser = /* ... */;
auto first = /* ... */;
auto const last = /* ... */;

namespace bp = boost::parser;
// You can of course use std::ranges::subrange directly in C++20 and later.
using attr_type = bp::attribute_t<decltype(BOOST_PARSER_SUBRANGE(first, last)), decltype(parser)>;

任何解析器都没有单一的属性类型, 因为解析器可以被放进 omit[] 中, 这会使其属性类型变为 none. 因此, attribute 无法告诉您解析器在所有情况下会生成什么属性; 它只告诉您如果把解析器传给 parse() 会生成什么.

序列解析器的属性规则

序列解析器的属性生成行为在概念上相当简单:

  • 子解析器的属性构成一个值的元组;
  • 不生成属性的子解析器不会对序列的属性有任何贡献;
  • 会生成属性的子解析器通常各自向元组结果贡献一个元素; 除非
  • 当相同元素类型的容器彼此相邻, 或单个元素与其类型的容器相邻时, 相邻的两个属性会合并为一个属性; 而且
  • 如果以上所有步骤的结果是一个退化的元组 boost::parser::tuple<T> (即使 T 是一个表示"无属性"的类型), 属性也会变成 T.

更正式地说, 属性生成算法的工作方式如下. 对于序列解析器 p, 设 p 的子解析器的属性类型列表为 a0, a1, a2, ..., an.

p 的属性是通过对编译期左折叠操作 left-fold({a1, a2, ..., an}, tuple<a0>, OP) 求值得到的. OP 是这样的组合操作: 它接受当前属性类型 (初始为 boost::parser::tuple<a0>) 和下一个属性类型, 并返回新的当前属性类型. 折叠操作结束时的当前属性类型就是 p 的属性类型.

OP 会尝试逐条应用一系列规则. 这些规则记作 X >> Y -> Z, 其中 X 是当前属性的类型, Y 是下一个属性的类型, Z 是新的当前属性类型. 在这些规则中, C<T> 是 T 的容器; none 是表示"无属性"的特殊类型; T 是一个类型; CHAR 是字符类型, 即 char 或 char32_t; 而 Ts... 是由一个或多个类型组成的参数包. 注意, T 可能是特殊类型 none. 当前属性总是一个元组 (记作 Tup), 因此"当前属性 X"指的是 Tup 的最后一个元素, 而不是 Tup 本身 —— 除非某条规则明确把 boost::parser::tuple<> 作为 X 类型的一部分提及.

  • none >> T -> T
  • CHAR >> CHAR -> std::string
  • T >> none -> T
  • C<T> >> T -> C<T>
  • T >> C<T> -> C<T>
  • C<T> >> optional<T> -> C<T>
  • optional<T> >> C<T> -> C<T>
  • boost::parser::tuple<none> >> T -> boost::parser::tuple<T>
  • boost::parser::tuple<Ts...> >> T -> boost::parser::tuple<Ts..., T>

把容器与 (可能可选的) 相邻值组合起来的规则 (例如 C<T> >> optional<T> -> C<T>) 对字符串有一个特例. 如果 C<T> 恰好是 std::string, 且 T 是 char 或 char32_t, 那么组合结果是一个 std::string.

同样, 如果最终结果是属性为 boost::parser::tuple<T>, 那么属性就变成 T.

注释

在上述规则中, 什么构成容器由 container 概念决定:

template<typename T>
concept container = std::ranges::common_range<T> && requires(T t) {
    { t.insert(t.begin(), *t.begin()) }
        -> std::same_as<std::ranges::iterator_t<T>>;
};

序列解析器属性示例

注意, OP 的应用是以左折叠的方式进行的, 因此是贪婪的. 这可能导致一些不直观的结果. 例如, 请看这个程序. 感谢 Duncan Paterson 提供这个非常好的示例!

#include <boost/parser/parser.hpp>
#include <print>

namespace bp = boost::parser;
int main() {
  const auto id_set_action = [](auto &ctx) {
    const auto& [left, right] = _attr(ctx);
    std::println("{} = {}", left, right);
  };

  const auto id_parser = bp::char_('a', 'z') > *bp::char_('a', 'z');

  const auto id_set = (id_parser >> '=' >> id_parser)[id_set_action];
  bp::parse("left=right", id_set);
  return 0;
}

可能令人惊讶的是, 这个程序打印的是 leftr = ight! 为什么? 这是因为 id_parser 看起来施加了结构, 但实际上并没有. id_set 与下面的写法完全等价 (添加了注释以说明各部分).

const auto id_set = (
  /*A*/ bp::char_('a', 'z') > /*B*/ *bp::char_('a', 'z') >>
  /*C*/ '=' >>
  /*D*/ bp::char_('a', 'z') > /*E*/ *bp::char_('a', 'z')
)[id_set_action];

当 Boost.Parser 把 OP 应用到这个序列解析器时, 各个步骤是: A 和 B 被合并成单个 std::string; C 被忽略, 因为它不生成属性; D 被合并进 std::string —— 它是先前由 A 和 B 形成的; 最后, 我们得到 E. E 不会与 D 组合, 因为 D 已被消耗. E 也不会与 std::string 组合 —— 它是我们由 A、B 和 D 形成的 —— 因为我们不组合相邻的容器. 最终, 我们得到一个由 std::string 组成的二元组, 其中第一个元素包含由 A、B 和 D 解析的全部字符, 第二个元素包含由 E 解析的全部字符.

但这显然不是我们在这里想要的. 我们如何得到一个能打印出 left = right 的顶层解析器? 我们使用 rule. 在 rule 内部使用的解析器永远不会与 rule 之外的任何解析器组合. 规则的实例天生就与使用它的所有解析器相互独立, 无论那些解析器是 rules 还是非 rule 解析器. 因此, 请考虑一个 rule, 它等价于上面的 id_parser.

namespace bp = boost::parser;
bp::rule<struct id_parser_tag, std::string> id_parser = "identifier";
auto const id_parser_def = bp::char_('a', 'z') > *bp::char_('a', 'z');
BOOST_PARSER_DEFINE_RULES(id_parser);

稍后, 我们就可以像使用前面的非规则版本那样使用它.

const auto id_set = (id_parser >> '=' >> id_parser)[id_set_action];

这会产生您可能预期的结果, 因为只有 bp::char_('a', 'z') > *bp::char_('a', 'z') 解析器 —— 位于 id_parser rule 内部的那个 —— 才有资格通过 OP 进行组合.

备选解析器的属性规则

备选解析器的规则要简单得多. 对于备选解析器 p, 设 p 的子解析器的属性类型列表为 a0, a1, a2, ..., an. p 的属性是 std::variant<a0, a1, a2, ..., an>, 并按以下步骤处理:

  • 所有 none 属性都被排除在外; 如果确有排除, 属性会被包进一个 std::optional 中, 例如 std::optional<std::variant</*...*/>>;
  • std::variant 模板参数 <T1, T2, ..., Tn> 中的重复项被移除; 出现的每个类型都恰好出现一次;
  • 如果属性是 std::variant<T> 或 std::optional<std::variant<T>>, 那么属性分别变为 T 或 std::optional<T>; 而且
  • 如果属性是 std::variant<> 或 std::optional<std::variant<>>, 结果就相应变为 none.
属性中容器的形成

从非容器形成容器的规则很简单. 您会从任何重复型解析器得到一个向量, 例如 +p、*p、repeat(3)[p] 等. 向量的值类型是 ATTR(p).

序列容器的另一条规则是: 一个值 x 与一个容器 c (其元素类型为 x) 会形成一个单一容器. 然而, x 的类型必须与 c 中的元素完全相同. 上面提到的字符串和字符特例是这条规则的一个例外. 例如, 考虑 char_ >> string("str") 的属性. 在非 Unicode 代码路径中, char_ 的属性类型保证是 char, 因此 ATTR(char_ >> string("str")) 就是 std::string. 如果您在 Unicode 代码路径中解析 UTF-8, char_ 的属性类型是 char32_t, 而这条特殊规则使它还会生成一个 std::string. 否则, ATTR(char_ >> string("str")) 的属性将是 boost::parser::tuple<char32_t, std::string>.

再强调一次, 组合值与容器没有特殊规则. 每种组合要么来自精确匹配, 要么落入"字符串+字符"这一特例.

另一个特例: std::string 赋值

std::string 可以从 char 赋值. 这很愚蠢. 但我们只能接受它. 当您编写一个属性为 char 的解析器, 并试图把它解析到一个 std::string 中时, 您几乎肯定犯了错误. 更重要的是, 如果您写了这样的代码:

namespace bp = boost::parser;
std::string result;
auto b = bp::parse("3", bp::int_, bp::ws, result);

... 那么您犯错的概率就更大了. 尽管这本应可行 —— 因为 std::string s; s = 3; 中的赋值是良构的 —— Boost.Parser 仍禁止它. 如果您编写类似上面代码片段的解析代码, 您会得到一个静态断言. 如果您确实想把 float 或其他什么赋给 std::string, 请在语义动作中做.

用 merge[] 和 separate[] 控制属性生成

正如我们在前面 解析为 struct 和 class 一节中看到的, 如果连续解析两个字符串, 结果属性中会得到两个独立的字符串. 那个示例中的解析器是:

namespace bp = boost::parser;
auto employee_parser = bp::lit("employee")
    >> '{'
    >> bp::int_ >> ','
    >> quoted_string >> ','
    >> quoted_string >> ','
    >> bp::double_
    >> '}';

employee_parser 的属性是 boost::parser::tuple<int, std::string, std::string, double>. 两个 quoted_string 解析器各生成一个 std::string 属性, 而且这些属性不会被合并. 这是默认行为, 也正是本例想要的; 我们不希望名字和姓氏字段被挤在一起, 以至于分不清一个名字在哪里结束、另一个在哪里开始. 如果我们解析的字符串由一个前缀和一个后缀组成, 而且前缀和后缀是分别定义以便在别处复用的, 那该怎么办?

namespace bp = boost::parser;
auto prefix = /* ... */;
auto suffix = /* ... */;
auto special_string = prefix >> suffix;
// Continue to use prefix and suffix to make other parsers....

在这种情况下, 我们可能想使用这些独立的解析器, 但又希望 special_string 生成单个 std::string 作为其属性. merge[] 正是为此而存在的.

namespace bp = boost::parser;
auto prefix = /* ... */;
auto suffix = /* ... */;
auto special_string = bp::merge[prefix >> suffix];

merge[] 只适用于序列解析器 (例如 p1 >> p2), 并强制序列解析器中的所有子解析器对它们的属性使用同一个变量.

另一条指令 separate[] 也只适用于序列解析器, 但它与 merge[] 的作用相反. 它强制序列解析器的子解析器生成的所有属性保持独立, 即使它们本可以合并. 例如, 请看这个解析器.

namespace bp = boost::parser;
auto string_and_char = +bp::char_('a') >> ' ' >> bp::cp;

string_and_char 匹配一个或多个 'a', 后跟某个其他字符. 如上所写, string_and_char 会生成一个 std::string, 并且最后一个字符会被追加到字符串中所有 'a' 之后. 然而, 如果您想把最后一个字符存储为一个独立的值, 就要使用 separate[].

namespace bp = boost::parser;
auto string_and_char = bp::separate[+bp::char_('a') >> ' ' >> bp::cp];

经过这一改动, string_and_char 生成的属性是 boost::parser::tuple<std::string, char32_t>.

merge[] 与 separate[] 详解

如前所述, merge[] 只适用于序列解析器. 所有子解析器必须具有相同的属性, 或完全不生成属性. 至少要有一个子解析器生成属性. 当您使用 merge[] 时, 您创建了一个合并组. 合并组中的每个解析器都使用同一个变量作为其属性. 合并组中的任何解析器都不会与其合并组之外任何解析器的属性交互. 合并组是不相交的; merge[/*...*/] >> merge[/*...*/] 会生成两个属性的元组, 而不是一个.

separate[] 同样只适用于序列解析器. 当您使用 separate[] 时, 您禁用了所有子解析器的属性与相邻属性的交互 —— 无论它们位于 separate[] 指令内部还是外部; 您强制每个子解析器拥有一个独立的属性.

merge[] 和 separate[] 的规则会推翻上面描述的序列解析器属性组合算法的各个步骤. 请看一个示例.

namespace bp = boost::parser;
constexpr auto parser =
    bp::char_ >> bp::merge[(bp::string("abc") >> bp::char_ >> bp::char_) >> bp::string("ghi")];

您可能认为 ATTR(parser) 会是 bp::tuple<char, std::string>. 但它不是. 上面的解析器甚至无法通过编译. 由于我们在上面创建了一个合并组, 我们禁用了默认行为 —— 即 char_ 解析器本会并入它们前面的 string 解析器. 既然它们都被视为独立实体, 且属性类型不同, 使用 merge[] 就是一个错误.

许多指令会用给定的解析器创建一个新解析器. merge[] 和 separate[] 不会. 由于它们只作用于序列解析器, 它们所做的只是创建给定序列解析器的一个副本. seq_parser 模板有一个模板参数 CombiningGroups, 而 merge[] 和 separate[] 所做的只是取得给定的 seq_parser, 并创建一个具有不同 CombiningGroups 模板参数的副本. 这意味着 merge[] 和 separate[] 在 operator>> 表达式中可以像括号一样被忽略. 请看一个示例.

namespace bp = boost::parser;
constexpr auto parser1 = bp::separate[bp::int_ >> bp::int_] >> bp::int_;
constexpr auto parser2 = bp::lexeme[bp::int_ >> ' ' >> bp::int_] >> bp::int_;

注意, separate[] 在这里是一个空操作; 它只是在本示例中这样使用. 这些解析器有不同的属性类型. ATTR(parser1) 是 boost::parser::tuple(int, int, int). ATTR(parser2) 是 boost::parser::tuple(boost::parser::tuple(int, int), int). 这是因为 bp::lexeme[] 会把它给定的解析器包装进一个新解析器, 而 merge[] 不会. 这就是为什么尽管 parser1 和 parser2 在结构上看起来如此相似, 它们的属性却不同.

transform(f)[]

transform(f)[] 是一条指令, 它使用给定的函数 f 来变换解析器的属性. 例如:

auto str_sum = [&](std::string const & s) {
    int retval = 0;
    for (auto ch : s) {
        retval += ch - '0';
    }
    return retval;
};

namespace bp = boost::parser;
constexpr auto parser = +bp::char_;
std::string str = "012345";

auto result = bp::parse(str, bp::transform(str_sum)[parser]);
assert(result);
assert(*result == 15);
static_assert(std::is_same_v<decltype(result), std::optional<int>>);

这里我们有一个函数 str_sum, 用于 f. 它假定给定的 std::string s 中的每个字符都是数字, 并返回 s 中所有数字的和. 我们的解析器 parser 通常会返回一个 std::string. 然而, 由于 str_sum 返回不同的类型 —— int —— 这就是整个解析器的属性类型 bp::transform(by_value_str_sum)[parser], 正如从 static_assert 中可以看到的.

与 Boost.Parser 中所有属性的处理一样, 传给 f 的属性会被移动. 您可以用 const &、&& 或按值来接受它.

解析器有属性与否不作区分, 因为存在一个 Regular 特殊无属性类型, 由无属性的解析器生成. 因此, 您可以写出类似 transform(f)[eps] 的代码, Boost.Parser 会欣然用这个特殊的无属性类型调用 f.

其他影响属性生成的指令

omit[p] 会禁用解析器 p 的属性生成. raw[p] 把属性从 ATTR(p) 改为一个视图, 该视图指示输入中被 p 匹配的子范围. string_view[p] 与 raw[p] 几乎相同, 只是它生成的是 std::basic_string_view. 详情参见 指令.

parse() API

有多个顶层解析函数. 它们有一些共同点:

  • 它们都返回一个可按语境转换为 bool 的值.
  • 它们都至少接受一个要解析的范围和一个解析器. "要解析的范围"可以是一对迭代器/哨兵, 也可以是单个范围对象.
  • 它们都要求要解析的范围可前向迭代.
  • 它们都接受任何元素类型为字符类型的范围. 也就是说, 它们都可以解析 char、wchar_t、char8_t、char16_t 或 char32_t 的范围.
  • 名称中带有 prefix_ 的重载接受一对迭代器/哨兵. 例如 prefix_parse(first, last, p, ws), 它解析范围 [first, last), 并在解析过程中前移 first. 如果解析成功, 整个输入可能匹配了, 也可能没有匹配. first 的值将指示 p 在输入中匹配的最后一个位置. 整个输入被匹配, 当且仅当 first == last 在调用 parse() 之后为真.
  • 当您调用 parse() 的任何范围重载时, 例如 parse(r, p, ws), parse() 只有在全部 r 都被 p 匹配时才指示成功.
注释

wchar_t 是输入可接受的值类型. 请注意, 它在 MSVC 上被解释为 UTF-16, 在其他平台上被解释为 UTF-32.

各个重载

parse() 和 prefix_parse() 合计有八个重载, 因为调用它们的方式有三组二选一的选项.

迭代器/哨兵与范围

您可以给 prefix_parse() 传入一对迭代器和哨兵, 用于界定一个字符值范围. 例如:

namespace bp = boost::parser;
auto const p = /* some parser ... */;

char const * str_1 = /* ... */;
// Using null_sentinel, str_1 can point to three billion characters, and
// we can call prefix_parse() without having to find the end of the string first.
auto result_1 = bp::prefix_parse(str_1, bp::null_sentinel, p, bp::ws);

char str_2[] = /* ... */;
auto result_2 = bp::prefix_parse(std::begin(str_2), std::end(str_2), p, bp::ws);

迭代器/哨兵重载可以在不匹配整个输入的情况下成功解析. 要判断整个输入是否被匹配, 可以检查 first == last 在 prefix_parse() 返回后是否为真.

相比之下, 您给 parse() 传入一个字符值范围. 当范围是对字符数组的引用时, 任何结尾的 0 都会被忽略; 这使得像 parse("str", p) 这样的调用可以自然地工作.

namespace bp = boost::parser;
auto const p = /* some parser ... */;

std::u8string str_1 = "str";
auto result_1 = bp::parse(str_1, p, bp::ws);

// The null terminator is ignored.  This call parses s-t-r, not s-t-r-0.
auto result_2 = bp::parse(U"str", p, bp::ws);

char const * str_3 = "str";
auto result_3 = bp::parse(bp::null_term(str_3) | bp::as_utf16, p, bp::ws);

由于没有办法表示 p 匹配了输入但只匹配了输入的前缀, parse() 的范围 (非迭代器/哨兵) 重载在未匹配整个输入时会指示失败.

带或不带属性出参 
namespace bp = boost::parser;
auto const p = '"' >> *(bp::char_ - '"') >> '"';
char const * str = "\"two words\"" ;

std::string result_1;
bool const success = bp::parse(str, p, result_1);   // success is true; result_1 is "two words"
auto result_2 = bp::parse(str, p);                  // !!result_2 is true; *result_2 is "two words"

当您调用 parse() —— 带属性出参且解析器为 p —— 时, 期望的类型是类似 ATTR(p) 的东西. 它不必恰好如此; 我稍后会解释. 返回类型是 bool.

当您调用 parse() —— 不带属性出参且解析器为 p —— 时, 返回类型是 std::optional<ATTR(p)>. 注意, 当 ATTR(p) 本身是一个 optional 时, 返回类型是 std::optional<std::optional<...>>. 这些 optional 各自告诉您不同的事情. 外层的告诉您解析是否成功. 如果成功, 说明解析器本身成功了, 但它仍然会生成一个本身是 optional 的属性 —— 这就是内层的那个.

带或不带跳过器 
namespace bp = boost::parser;
auto const p = '"' >> *(bp::char_ - '"') >> '"';
char const * str = "\"two words\"" ;

auto result_1 = bp::parse(str, p);         // !!result_1 is true; *result_1 is "two words"
auto result_2 = bp::parse(str, p, bp::ws); // !!result_2 is true; *result_2 is "twowords"
属性出参的兼容性

对于任何接受属性出参的 parse() 调用, 例如 parse("str", p, bp::ws, out), 该调用对多种可能的 out 类型都是良构的; decltype(out) 不必恰好是 ATTR(p).

例如, 下面是良构且不会中止的代码 (记住 string() 的属性类型是 std::string):

namespace bp = boost::parser;
auto const p = bp::string("foo");

std::vector<char> result;
bool const success = bp::parse("foo", p, result);
assert(success && result == std::vector<char>({'f', 'o', 'o'}));

尽管 p 生成 std::string 属性, 但当它实际取得自己生成的数据并写入属性时, 它只假定该属性是一个 container (参见 概念), 而不假定它是某种特定的容器类型. 它会很乐意地把元素 insert() 到 std::string 或 std::vector<char> 中, 一视同仁. std::string 和 std::vector<char> 都是 char 的容器, 但它也会插入元素类型不同的容器. p 只需要能够把它生成的元素插入属性容器即可. 只要隐式转换能让这一切工作, 就没有任何问题:

namespace bp = boost::parser;
auto const p = bp::string("foo");

std::deque<int> result;
bool const success = bp::parse("foo", p, result);
assert(success && result == std::deque<int>({'f', 'o', 'o'}));

这也是可行的, 即使它需要把生成的 char32_t 序列中的元素插入到一个 char 容器中 (记住 +cp 的属性类型是 std::vector<char32_t>):

namespace bp = boost::parser;
auto const p = +bp::cp;

std::string result;
bool const success = bp::parse("foo", p, result);
assert(success && result == "foo");

下一个示例同样可行, 即使对容器的替换不在顶层 —— 它是结果元组的一个元素:

namespace bp = boost::parser;
auto const p = +(bp::cp - ' ') >> ' ' >> string("foo");

using attr_type = decltype(bp::parse(u8"", p));
static_assert(std::is_same_v<
              attr_type,
              std::optional<bp::tuple<std::string, std::string>>>);

using namespace bp::literals;

{
    // This is similar to attr_type, with the first std::string changed to a std::vector<int>.
    bp::tuple<std::vector<int>, std::string> result;
    bool const success = bp::parse(u8"rôle foo" | bp::as_utf8, p, result);
    assert(success);
    assert(bp::get(result, 0_c) == std::vector<int>({'r', U'ô', 'l', 'e'}));
    assert(bp::get(result, 1_c) == "foo");
}
{
    // This time, we have a std::vector<char> instead of a std::vector<int>.
    bp::tuple<std::vector<char>, std::string> result;
    bool const success = bp::parse(u8"rôle foo" | bp::as_utf8, p, result);
    assert(success);
    // The 4 code points "rôle" get transcoded to 5 UTF-8 code points to fit in the std::string.
    assert(bp::get(result, 0_c) == std::vector<char>({'r', (char)0xc3, (char)0xb4, 'l', 'e'}));
    assert(bp::get(result, 1_c) == "foo");
}

如行内注释所示, 从这个示例中可以得到以下几点:

  • 如果您替换一个属性出参 (例如把 std::string 换成 std::vector<int>, 或把 std::vector<char32_t> 换成 std::deque<int>), 对 parse() 的调用通常仍然是良构的.
  • 在替换容器类型时, 如果两个容器都包含字符值, 被移除的容器的元素类型是 char32_t (非 MSVC 构建下是 wchar_t), 而新容器的元素类型是 char 或 char8_t, 那么 Boost.Parser 会假定这是一次从 UTF-32 到 UTF-8 的转换, 并在插入新容器时静默转码数据.

我们来看另一个看似简单的类型替换不起作用的情况. 先看可行的情形:

namespace bp = boost::parser;
auto parser = -(bp::char_ % ',');
std::vector<int> result;
auto b = bp::parse("a, b", parser, bp::ws, result);

ATTR(parser) 是 std::optional<std::string>. 尽管我们传入的是 std::vector<int>, 一切正常. 然而, 如果我们只对这个情形稍作修改, 让 std::optional<std::string> 嵌套在属性内部, 代码就变成非良构的了.

struct S
{
    std::vector<int> chars;
    int i;
};
namespace bp = boost::parser;
auto parser = -(bp::char_ % ',') >> bp::int_;
S result;
auto b = bp::parse("a, b 42", parser, bp::ws, result);

如果我们把 chars 改成 std::vector<char>, 代码仍然是非良构的. 把 chars 改成 std::string 也一样. 我们必须精确地使用 std::optional<std::string>, 才能让代码重新变为良构.

顶层的宽松规则之所以不适用于嵌套解析器, 是因为在代码中的某处, 解析器 -(bp::char_ % ',') 会尝试把一个 std::optional<std::string> —— 即它通常生成的属性类型的元素类型 —— 赋给一个 chars. 如果那里没有隐式转换, 代码就是非良构的.

最后一个示例的要点是: 在传给 parse() 的属性类型内部随意替换数据类型的能力非常灵活, 但也仅限于结构上简单的情形. 当我们在下一节讨论 rules 时, 会看到属性的这种类型灵活性如何在编写复杂解析器时提供帮助.

上面是把一种容器类型换成另一种的示例. 这些是很好的示例, 因为这更容易让人感到意外, 所以这里花了大量篇幅. 您也可以做一些简单得多的事情, 比如用 uint_ 解析, 并把它的属性写入一个 double. 总的来说, 您可以把属性中的任何类型 T 换掉, 只要这种替换不会导致解析内部出现某种非良构的赋值.

下面是另一个也会产生意外结果的示例, 但原因不同.

namespace bp = boost::parser;
constexpr auto parser = bp::char_('a') >> bp::char_('b') >> bp::char_('c') |
                        bp::char_('x') >> bp::char_('y') >> bp::char_('z');
std::string str = "abc";
bp::tuple<char, char, char> chars;
bool b = bp::parse(str, parser, chars);
assert(b);
assert(chars == bp::tuple('c', '\0', '\0'));

这看起来不对, 但这是预期行为. 在解析中每个生成属性的阶段, Boost.Parser 都会尝试把该属性赋给提供给 parse() 的出参属性的某一部分 (如果有出参的话). 注意, ATTR(parser) 是 std::string, 因为每个序列解析器都是三个连续的 char_ 解析器, 构成一个 std::string; 这样的备选项有两个, 所以整体属性也是 std::string. 在解析期间, 当第一个解析器 bp::char_('a') 匹配输入时, 它生成属性 'a' 并需要把它赋给目的地. 序列解析器内部的某些逻辑表明: 如果结果被写入一个元组, 这个 'a' 会贡献给结果元组中第 0 个位置的值. 这里我们传入了一个 bp::tuple<char, char, char>, 所以它把 'a' 写入第一个元素. 后续每个 char_ 解析器都做同样的事情, 覆盖第一个元素. 如果我们改为传入一个 std::string 作为出参, 该逻辑会看到出参属性是一个字符串, 并会把 'a' 追加到它后面. 然后后续每个解析器都会向这个字符串追加内容.

Boost.Parser 从不检查传给 parse() 的元组的元素个数, 即不会相对于解析器期望的属性去判断其中元素是太多还是太少. 在本例中, 有两个多余的元素从未被触及. 如果元组中的元素太少, 您会看到编译错误. Boost.Parser 从不预先做这种类型检查的原因是: 宽松的赋值逻辑分散在各个解析器之中; 顶层解析可以确定期望的属性是什么, 但无法判断传入的另一种类型的属性是否是合适的替身.

variant 属性出参的兼容性

如果默认属性可以赋给 variant, 那么在出参中使用 variant 就是兼容的. 除此之外不做任何其他工作来使赋值兼容. 例如, 下面代码会像您预期的那样工作:

namespace bp = boost::parser;
std::variant<int, double> v;
auto b = bp::parse("42", bp::int_, v);
assert(b);
assert(v.index() == 0);
assert(std::get<0>(v) == 42);

同样, 这能工作是因为 v = 42 是良构的. 然而, 其他类型的替换行不通. 特别是, boost::parser::tuple 到聚合类型或聚合类型到 boost::parser::tuple 的转换行不通. 下面是一个示例.

struct key_value
{
    int key;
    double value;
};

namespace bp = boost::parser;
std::variant<key_value, double> kv_or_d;
key_value kv;
bp::parse("42 13.0", bp::int_ >> bp::double_, kv);      // Ok.
bp::parse("42 13.0", bp::int_ >> bp::double_, kv_or_d); // Error: ill-formed!

在这种情况下, Boost.Parser 本可以轻松查看 variant 覆盖的备选类型并执行转换. 然而, 在很多情况下并不存在明显正确的 variant 备选类型, 或者用户期望的是某个 variant 备选类型而实际得到的是另一个. 请考虑以下几种情形.

struct i_d { int i; double d; };
struct d_i { double d; int i; };
using v1 = std::variant<i_d, d_i>;

struct i_s { int i; short s; };
struct d_d { double d1; double d2; };
using v2 = std::variant<i_s, d_d>;

using tup_t = boost::parser::tuple<short, short>;

如果我们有一个生成 tup_t 的解析器, 又有一个 v1 属性出参, 那么显然不存在正确的 variant 备选类型 —— 这种情况是含糊的, 任何人都看得出两个 variant 备选类型没有哪个是更好的匹配. 如果我们要把 tup_t 赋给 v2, 情况更糟. 同样的含糊性依然存在, 但对用户来说, i_s 显然比 d_d "更接近".

因此, Boost.Parser 只做赋值. 如果某个解析器 P 生成的默认属性无法赋给您想赋给的那个 variant 备选类型, 您可以创建一个 rule, 让它生成精确的 variant 备选类型或 variant 本身, 并把 P 用作您规则的解析器.

Unicode 解析与非 Unicode 解析

对 parse() 的调用要么认为整个输入是某种 UTF 格式 (UTF-8、UTF-16 或 UTF-32), 要么认为整个输入是某种未知编码. 下面是它推断调用属于哪种情形的方式:

  • 如果范围是 char8_t 的序列, 或者输入是一个 boost::parser::utf8_view, 那么输入是 UTF-8.
  • 否则, 如果范围的值类型是 char, 那么输入是某种未知编码.
  • 否则, 输入是某种 UTF 编码.
提示

如果您想以仅 ASCII 模式或某种其他非 Unicode 编码进行解析, 请只使用 char 的序列, 例如 std::string 或 char const *.

提示

如果您想确保所有输入都被当作 Unicode 解析, 请把输入范围 r 作为 r | boost::parser::as_utf32 传入 —— 反正在 Unicode 解析路径中, 这就是它在 parse() 内部经历的第一步处理.

注释

由于传入 boost::parser::utfN_view 是一个特例, 而 char 的序列 r 在其他情况下被视为未知编码, 因此 boost::parser::parse(r | boost::parser::as_utf8, p) 会把 r 当作 UTF-8, 而 boost::parser::parse(r, p) 不会.

parse() 的 trace_mode 参数

解析器一旦达到一定规模, 调试起来就出了名地困难. 要获得解析的详细跟踪, 请把 boost::parser::trace::on 作为最后一个参数传给 parse(). 它会显示当前正在匹配的解析器、接下来要解析的几个字符, 以及生成的任何属性. 详情参见教程的 错误处理与调试 一节.

全局对象与错误处理器

每次对 parse() 的调用都可以选择关联一个全局对象. 要在您的解析器中使用特定的全局对象, 您调用 with_globals() 来创建一个包含该全局对象的新解析器:

struct globals_t
{
    int foo;
    std::string bar;
};
auto const parser = /* ... */;
globals_t globals{42, "yay"};
auto result = boost::parser::parse("str", boost::parser::with_globals(parser, globals));

在该 parse() 调用中的每个语义动作都可以访问同一个 globals_t 对象, 使用的正是 _globals(ctx).

默认错误处理器对大多数需求都很好; 但如果您想更换它, 可以通过调用 with_error_handler() 创建一个新解析器来做到:

auto const parser = /* ... */;
my_error_handler error_handler;
auto result = boost::parser::parse("str", boost::parser::with_error_handler(parser, error_handler));
提示

如果您的解析环境不允许向终端报告错误, 您可能想使用 callback_error_handler 来代替默认错误处理器.

重要

全局对象和错误处理器即使存在, 也会在除顶层解析器之外的任何解析器上被忽略.

关于规则的更多内容

在前一页关于 rules 的内容 (规则解析器) 中, 我把 rules 描述为与函数类似. rules 从根本上说是组织性的. 下面是 rules 的常见用例. 如果您想做到以下几点, 请使用 rule:

  • 把解析器生成的属性类型固定为默认类型之外的其他类型;
  • 控制相邻序列解析器生成的属性;
  • 创建能生成有用诊断文本的解析器;
  • 创建递归规则 (下文详述);
  • 创建一组相互递归的解析器;
  • 进行回调解析.

我们来详细了解这些用例.

固定属性类型

我们在上一节看到了 parse() 在接受何种类型作为属性出参方面的灵活性. 下面是另一个示例.

namespace bp = boost::parser;
auto result = bp::parse(input, bp::int % ',', result);

result 可以是许多不同类型之一. 它可以是 std::vector<int>, 也可以是 std::set<long long>, 还可以是很多东西. 通常这是一个非常有用的性质; 如果您把属性某部分中想要的容器从 std::vector 改成 std::deque, 就不得不重写全部解析器逻辑, 那会很烦人. 然而, 这种灵活性以类型检查为代价. 如果您想编写一个总是生成精确的 std::vector<unsigned int> 而绝不生成其他类型的解析器, 您可能还希望: 万一不小心给该解析器传入 std::set<unsigned int> 属性, 就得到编译错误. 普通解析器无法强制其属性类型只能是唯一固定的类型.

幸运的是, rules 允许您编写具有固定属性类型的解析器. 每条规则都有一个特定的属性类型, 以模板参数的形式提供. 如果不指定, 规则就没有属性. 属性是特定类型这一事实让您可以去掉属性的灵活性. 例如, 假设我们有一条这样定义的规则:

bp::rule<struct doubles, std::vector<double>> doubles = "doubles";
auto const doubles_def = bp::double_ % ',';
BOOST_PARSER_DEFINE_RULES(doubles);

然后您可以在对 parse() 的调用中使用它, parse() 会返回一个 std::optional<std::vector<double>>:

auto const result = bp::parse(input, doubles, bp::ws);

如果您带属性出参调用 parse(), 那么该出参必须恰好是 std::vector<double>:

std::vector<double> vec_result;
bp::parse(input, doubles, bp::ws, vec_result); // Ok.
std::deque<double> deque_result;
bp::parse(input, doubles, bp::ws, deque_result); // Ill-formed!

如果我们想用 std::deque<double> 作为规则的属性类型:

// Attribute changed to std::deque<double>.
bp::rule<struct doubles, std::deque<double>> doubles = "doubles";
auto const doubles_def = bp::double_ % ',';
BOOST_PARSER_DEFINE_RULES(doubles);

int main()
{
    std::deque<double> deque_result;
    bp::parse(input, doubles, bp::ws, deque_result); // Ok.
}

这里的要点是: 属性灵活性仍然可用, 但只在规则内部 —— 解析器 bp::double_ % ',' 可以解析到 std::vector<double> 或 std::deque<double> 中, 但规则 doubles 必须只解析到它被声明生成的那个精确属性.

原因在于, 在规则解析的实现内部, 有类似这样的代码:

using attr_t = ATTR(doubles_def);
attr_t attr;
parse(first, last, parser, attr);
attribute_out_param = std::move(attr);

其中 attribute_out_param 是我们传给 parse() 的属性出参. 如果最后那个移动赋值是非良构的, 那么对 parse() 的调用也是.

您也可以利用规则来实现属性灵活性. 尽管规则降低了它可生成属性的灵活性, 但编写新规则如此容易, 这意味着我们可以用规则本身来在代码中获得想要的属性灵活性:

namespace bp = boost::parser;

// We only need to write the definition once...
auto const generic_doubles_def = bp::double_ % ',';

bp::rule<struct vec_doubles, std::vector<double>> vec_doubles = "vec_doubles";
auto const & vec_doubles_def = generic_doubles_def; // ... and re-use it,
BOOST_PARSER_DEFINE_RULES(vec_doubles);

// Attribute changed to std::deque<double>.
bp::rule<struct deque_doubles, std::deque<double>> deque_doubles = "deque_doubles";
auto const & deque_doubles_def = generic_doubles_def; // ... and re-use it again.
BOOST_PARSER_DEFINE_RULES(deque_doubles);

现在我们两种各有一个, 而且不必复制任何需要两处维护的解析逻辑.

有时, 您需要创建一条规则来强制某种属性类型, 但规则的属性无法从其解析器的属性构造出来. 出现这种情况时, 您需要编写一个语义动作.

struct type_t
{
    type_t() = default;
    explicit type_t(double x) : x_(x) {}
    // etc.

    double x_;
};

namespace bp = boost::parser;

auto doubles_to_type = [](auto & ctx) {
    using namespace bp::literals;
    _val(ctx) = type_t(_attr(ctx)[0_c] * _attr(ctx)[1_c]);
};

bp::rule<struct type_tag, type_t> type = "type";
auto const type_def = (bp::double_ >> bp::double_)[doubles_to_type];
BOOST_PARSER_DEFINE_RULES(type);

对于规则 R 及其解析器 P, 如果满足以下条件之一, 我们就无需编写这样的语义动作:

- ATTR(R) 是聚合体, 且 ATTR(P) 是兼容的元组;

- ATTR(R) 是元组, 且 ATTR(P) 是兼容的聚合体;

- ATTR(R) 是非聚合类类型 C, 且 ATTR(P) 是一个元素可用于构造 C 的元组; 或者

- ATTR(R) 和 ATTR(P) 是兼容的类型.

"兼容"的概念定义在 parse() API 中.

控制生成的属性

详情参见 属性生成 一节中的 序列解析器属性示例.

创建解析器以获得更好的诊断

每条 rule 都有关联的诊断文本, Boost.Parser 可以在该规则失败时使用它. 当解析在期望点处失败时 (参见 期望点), 这很有用. 假设您在某处定义了如下代码.

namespace bp = boost::parser;

bp::rule<struct value_tag> value =
    "an integer, or a list of integers in braces";

auto const ints = '{' > (value % ',') > '}';
auto const value_def = bp::int_ | ints;

BOOST_PARSER_DEFINE_RULES(value);

注意那两个期望点: 一个在 (value % ',') 之前, 一个在最后的 '}' 之前. 稍后, 您解析某个输入:

bp::parse("{ 4, 5 a", value, bp::ws);

这触犯了第二个期望点, 并产生如下输出:

1:7: error: Expected '}' here:
{ 4, 5 a
       ^

这是一个相当不错的错误消息. 下面是违反前面那个期望时的样子:

bp::parse("{ }", value, bp::ws);

1:2: error: Expected an integer, or a list of integers in braces % ',' here:
{ }
  ^

这可差多了. 问题在于期望落在 (value % ',') 上. 因此, 尽管我们给 value 提供了合理的诊断文本, 却把文本放错了对象. 我们可以引入一条新规则, 把诊断文本放到正确的位置.

namespace bp = boost::parser;

bp::rule<struct value_tag> value =
    "an integer, or a list of integers in braces";
bp::rule<struct comma_values_tag> comma_values =
    "a comma-delimited list of integers";

auto const ints = '{' > comma_values > '}';
auto const value_def = bp::int_ | ints;
auto const comma_values_def = (value % ',');

BOOST_PARSER_DEFINE_RULES(value, comma_values);

现在当我们调用 bp::parse("{ }", value, bp::ws) 时, 会得到好得多的消息:

1:2: error: Expected a comma-delimited list of integers here:
{ }
  ^

rule value 在我们代码的其他地方 —— 也许在另一个解析器中 —— 可能也有用. 它的诊断文本适用于那些潜在的用途.

递归规则

在文法中看到包含递归规则的情况相当常见. 请看这条用于匹配配对括号的 EBNF 规则:

<parens> ::= "" | ( "(" <parens> ")" )

我们可以尝试用 Boost.Parser 这样来写:

namespace bp = boost::parser;
auto const parens = '(' >> parens >> ')' | bp::eps;

我们必须把 bp::eps 放在后面, 因为 Boost.Parser 的解析算法是贪婪的. 除此之外, 这只是直接的照搬. 遗憾的是, 它行不通. 代码是非良构的, 因为您不能用变量自身来定义它. 嗯, 您可以这么做, 但不会有任何好结果. 如果我们改为基于一个前向声明的 rule 来构建解析器, 它就能工作.

namespace bp = boost::parser;
bp::rule<struct parens_tag> parens = "matched parentheses";
auto const parens_def = '(' >> parens > ')' | bp::eps;
BOOST_PARSER_DEFINE_RULES(parens);

稍后, 如果我们用它来解析, 它会按我们的期望工作.

assert(bp::parse("(((())))", parens, bp::ws));

当它失败时, 它甚至能生成漂亮的诊断信息.

bp::parse("(((()))", parens, bp::ws);

1:7: error: Expected ')' here (end of input):
(((()))
       ^

递归 rules 在一个方面与其他解析器不同: 当递归地重新进入规则时, 只有属性变量 (在您的语义动作中是 _attr(ctx)) 对该规则实例是唯一的. 该规则最顶层实例的所有其他状态都是共享的, 包括规则的值 (_val(ctx)), 以及规则的局部变量和参数. 换句话说, _val(ctx) 返回对同一对象的引用 —— 这适用于递归 rule 的每个实例. 这是因为规则的每个实例都需要一个地方存放它从解析中生成的属性. 然而, 我们只想要最顶层规则有一个返回值; 如果每个实例在 _val(ctx) 中都有各自独立的值, 那么在递归实例化的求值过程中就无法逐步构建出递归规则的结果.

另外, 请看这条规则:

namespace bp = boost::parser;
bp::rule<struct ints_tag, std::vector<int>> ints = "ints";
auto const ints_def = bp::int_ >> ints | bp::eps;

ints_def 的默认属性类型是什么? 它看起来显然是 std::optional<std::vector<int>>. 在 ints 的求值内部, Boost.Parser 必须对 ints_def 求值, 然后从中产出一个 std::vector<int> —— 即 ints 的返回类型. 怎么做? 您如何把一个 std::optional<std::vector<int>> 变成 std::vector<int>? 对人类来说这似乎显而易见, 但要正确处理这个简单例子和一般情况的元编程, 我自认力不能及.

Boost.Parser 对什么构成递归规则有明确的语义. 每条规则都有一个与之关联的标签类型; 如果 Boost.Parser 进入一条带有某标签 Tag 的规则, 而当前正在求值的规则 (如果有的话) 也带有标签 Tag, 那么被进入的规则实例被视为一次递归. 其他任何情形都不被视为递归. 特别地, 如果您有规则 Ra 和 Rb, 且 Ra 使用 Rb, 而后者又使用 Ra, 那么 Ra 的第二次使用不被视为递归. Ra 和 Rb 当然是相互递归的, 但就获取唯一值、局部变量和参数而言, 两者都不被视为"递归规则".

相互递归的规则

使用规则的好处之一是: 您可以先声明所有规则, 然后立即使用它们. 这让您可以编写相互使用的规则, 而不引入循环:

namespace bp = boost::parser;

// Assume we have some polymorphic type that can be an object/dictionary,
// array, string, or int, called `value_type`.

bp::rule<class string, std::string> const string = "string";
bp::rule<class object_element, bp::tuple<std::string, value_type>> const object_element = "object-element";
bp::rule<class object, value_type> const object = "object";
bp::rule<class array, value_type> const array = "array";
bp::rule<class value_tag, value_type> const value = "value";

auto const string_def = bp::lexeme['"' >> *(bp::char_ - '"') > '"'];
auto const object_element_def = string > ':' > value;
auto const object_def = '{'_l >> -(object_element % ',') > '}';
auto const array_def = '['_l >> -(value % ',') > ']';
auto const value_def = bp::int_ | bp::bool_ | string | array | object;

BOOST_PARSER_DEFINE_RULES(string, object_element, object, array, value);

这里我们有一个针对类似 JavaScript 值类型的解析器 value_type. value_type 可以是一个数组, 而数组本身又可以包含其他数组、对象、字符串等. 由于我们需要能在数组中解析对象, 反之亦然, 所以这两个解析器需要能够相互引用.

回调解析

只有 rules 才能成为回调解析器, 因此如果您想通过回调获得属性, 而不是从代表整个解析结果的庞大属性的中间某处获取属性, 就需要使用 rules. 回调解析的扩展示例参见 使用回调解析 JSON.

规则语义动作中可用的访问器
_val()

在规则的所有语义动作内部, 表达式 _val(ctx) 是对规则所生成属性的引用. 当您想让子解析器以特定方式构建属性时, 这会很有用:

namespace bp = boost::parser;
using namespace bp::literals;

bp::rule<class ints, std::vector<int>> const ints = "ints";
auto twenty_zeros = [](auto & ctx) { _val(ctx).resize(20, 0); };
auto push_back = [](auto & ctx) { _val(ctx).push_back(_attr(ctx)); };
auto const ints_def = "20-zeros"_l[twenty_zeros] | +bp::int_[push_back];
BOOST_PARSER_DEFINE_RULES(ints);
提示

这只是一个示例. 几乎在所有情况下, 不使用语义动作来做这些事都更好. 我们本可以把 ints_def 写成 "20-zeros" >> bp::attr(std::vector<int>(20)) | +bp::int_, 后者语义相同, 可读性好得多, 代码也少得多.

局部变量

rule 模板还有一个我们尚未讨论的模板参数. 您可以传入第三个参数 LocalState 给 rule, 它会由 rule 默认构造, 并在规则中使用的语义动作内以 _locals(ctx) 的形式可用. 如果规则需要, 这会为您的规则提供一些局部状态. LocalState 的类型可以是任何正则类型, 例如单个值、包含多个值的结构体, 或者元组.

struct foo_locals
{
    char first_value = 0;
};

namespace bp = boost::parser;

bp::rule<class foo, int, foo_locals> const foo = "foo";

auto record_first = [](auto & ctx) { _locals(ctx).first_value = _attr(ctx); }
auto check_against_first = [](auto & ctx) {
    char const first = _locals(ctx).first_value;
    char const attr = _attr(ctx);
    if (attr == first)
        _pass(ctx) = false;
    _val(ctx) = (int(first) << 8) | int(attr);
};

auto const foo_def = bp::cu[record_first] >> bp::cu[check_against_first];
BOOST_PARSER_DEFINE_RULES(foo);

foo 在能够连续匹配输入的两个元素时匹配输入, 但前提是这两个元素的值不同. 没有局部变量, 编写需要在解析过程中跟踪状态的解析器会困难得多.

参数

有时, 对解析器进行参数化会很方便. 请看 YAML 1.2 规范中的这几条解析规则:

[80]
s-separate(n,BLOCK-OUT) ::= s-separate-lines(n)
s-separate(n,BLOCK-IN)  ::= s-separate-lines(n)
s-separate(n,FLOW-OUT)  ::= s-separate-lines(n)
s-separate(n,FLOW-IN)   ::= s-separate-lines(n)
s-separate(n,BLOCK-KEY) ::= s-separate-in-line
s-separate(n,FLOW-KEY)  ::= s-separate-in-line

[136]
in-flow(n,FLOW-OUT)  ::= ns-s-flow-seq-entries(n,FLOW-IN)
in-flow(n,FLOW-IN)   ::= ns-s-flow-seq-entries(n,FLOW-IN)
in-flow(n,BLOCK-KEY) ::= ns-s-flow-seq-entries(n,FLOW-KEY)
in-flow(n,FLOW-KEY)  ::= ns-s-flow-seq-entries(n,FLOW-KEY)

[137]
c-flow-sequence(n,c) ::= “[” s-separate(n,c)? in-flow(c)? “]”

YAML [137] 规定解析应进入两条 YAML 子规则, 这两条子规则都带有 n 和 c 参数. 把这些 YAML 解析规则照搬成使用无参数 Boost.Parser rules 的形式当然是可行的, 但这样做相当痛苦. 更好的做法是使用带参数的规则.

您通过调用 rule 的 with() 成员来给它传递参数. 您传给 with() 的值会被用来创建一个 boost::parser::tuple, 它在附加到规则的语义动作中通过 _params(ctx) 可用.

像这样给 rules 传参, 使您可以轻松编写这样的解析器: 它们会根据已解析的上下文数据改变自己的解析方式.

下面是 YAML [137] 的一个实现. 它还实现了 [137] 直接使用的两条 YAML 规则, 即规则 [136] 和 [80]. 那些规则所使用的规则也在下面有所体现, 但只用 eps 实现, 这样我就不必重复 (非常庞大的) YAML 规范的太多内容.

namespace bp = boost::parser;

// A type to represent the YAML parse context.
enum class context {
    block_in,
    block_out,
    block_key,
    flow_in,
    flow_out,
    flow_key
};

// A YAML value; no need to fill it in for this example.
struct value
{
    // ...
};

// YAML [66], just stubbed in here.
auto const s_separate_in_line = bp::eps;

// YAML [137].
bp::rule<struct c_flow_seq_tag, value> c_flow_sequence = "c-flow-sequence";
// YAML [80].
bp::rule<struct s_separate_tag> s_separate = "s-separate";
// YAML [136].
bp::rule<struct in_flow_tag, value> in_flow = "in-flow";
// YAML [138]; just eps below.
bp::rule<struct ns_s_flow_seq_entries_tag, value> ns_s_flow_seq_entries =
    "ns-s-flow-seq-entries";
// YAML [81]; just eps below.
bp::rule<struct s_separate_lines_tag> s_separate_lines = "s-separate-lines";

// Parser for YAML [137].
auto const c_flow_sequence_def =
    '[' >>
    -s_separate.with(bp::_p<0>, bp::_p<1>) >>
    -in_flow.with(bp::_p<0>, bp::_p<1>) >>
    ']';
// Parser for YAML [80].
auto const s_separate_def = bp::switch_(bp::_p<1>)
    (context::block_out, s_separate_lines.with(bp::_p<0>))
    (context::block_in, s_separate_lines.with(bp::_p<0>))
    (context::flow_out, s_separate_lines.with(bp::_p<0>))
    (context::flow_in, s_separate_lines.with(bp::_p<0>))
    (context::block_key, s_separate_in_line)
    (context::flow_key, s_separate_in_line);
// Parser for YAML [136].
auto const in_flow_def = bp::switch_(bp::_p<1>)
    (context::flow_out, ns_s_flow_seq_entries.with(bp::_p<0>, context::flow_in))
    (context::flow_in, ns_s_flow_seq_entries.with(bp::_p<0>, context::flow_in))
    (context::block_out, ns_s_flow_seq_entries.with(bp::_p<0>, context::flow_key))
    (context::flow_key, ns_s_flow_seq_entries.with(bp::_p<0>, context::flow_key));

auto const ns_s_flow_seq_entries_def = bp::eps;
auto const s_separate_lines_def = bp::eps;

BOOST_PARSER_DEFINE_RULES(
    c_flow_sequence,
    s_separate,
    in_flow,
    ns_s_flow_seq_entries,
    s_separate_lines);

YAML [137] (c_flow_sequence) 解析一个列表. 该列表可以为空, 并且必须像您在这里看到的那样被方括号包围. 但是, 根据当前 YAML 上下文 ([137] 的 c 参数), 我们可能要求某些空白由 s-separate 匹配, 而子解析器 in-flow 的行为也取决于当前上下文.

在上面的 s_separate 中, 我们根据 c 的值以不同方式进行解析. 上文是通过在 switch 解析器中使用 s_separate 的第二个参数的值来做到这一点的. 第二个参数通过把 _p 用作解析实参来查询.

in_flow 做了类似的事情. 注意, in_flow 调用其子规则时传入了第一个参数, 但第二个值使用了固定值. s_separate 只是有条件地传入其 n 参数. 关键在于: 规则既可以在有 .with() 的情况下使用, 也可以在没有它的情况下使用; 并且您可以给 .with() 传入常量或解析实参.

定义好这些规则后, 我们可以这样为 YAML [137] 编写单元测试:

auto const test_parser = c_flow_sequence.with(4, context::block_out);
auto result = bp::parse("[]", test_parser);
assert(result);

您可以用不同的 n 和 c 值的测试来扩展它. 显然, 在真实测试中, 如果实现了其他规则 (比如 [138]), 您会解析 "[]" 内部的实际内容.

_p 变量模板

取出规则的一个参数并把它作为实参传给另一个解析器可能非常繁琐. _p 是一个变量模板, 允许您引用当前规则的第 n 个参数, 进而可以把它传给规则的某个子解析器. 使用它, 上面的 foo_def 可以重写为:

auto const foo_def = bp::repeat(bp::_p<0>)[' '_l];

使用 _p 可以让您免于编写一堆 lambda —— 否则每个 lambda 都要用 _params(ctx)[0_c] 或类似方法从解析上下文中取出一个参数.

注意, _p 是一个解析实参 (参见 解析器及其用途), 也就是说它是一个以上下文为唯一参数的可调用对象. 如果您想在语义动作内部使用它, 就必须调用它.

规则内可用的语义动作的特殊形式

本教程中的语义动作通常具有 void (auto & ctx) 这样的签名. 也就是说, 它们按引用接受一个上下文, 并且不返回任何东西. 如果它们返回了什么, 那个返回值也只会被丢弃.

为了从解析器中得到某种特定类型的值 (而您通常无法自动得到它) 而创建一条规则, 是相当常见的模式. 如果我想解析一个 int, int_ 就能做到, 而且解析出的东西也正是我想要的属性. 如果我解析一个 int 后跟一个 double, 我会得到一个 boost::parser::tuple, 其中各含一个这样的值. 但如果我不想要这两个值本身, 而是想要这两个值的某个函数呢? 我大概会这样写:

struct obj_t { /* ... */ };
obj_t to_obj(int i, double d) { /* ... */ }

namespace bp = boost::parser;
bp::rule<struct obj_tag, obj_t> obj = "obj";
auto make_obj = [](auto & ctx) {
    using boost::hana::literals;
    _val(ctx) = to_obj(_attr(ctx)[0_c], _attr(ctx)[1_c]);
};
constexpr auto obj_def = (bp::int_ >> bp::double_)[make_obj];

这没问题, 只是有点冗长. 不过, 您也可以改用这种方式:

namespace bp = boost::parser;
bp::rule<struct obj_tag, obj_t> obj = "obj";
auto make_obj = [](auto & ctx) {
    using boost::hana::literals;
    return to_obj(_attr(ctx)[0_c], _attr(ctx)[1_c]);
};
constexpr auto obj_def = (bp::int_ >> bp::double_)[make_obj];

在上面的代码中, 我们从语义动作返回一个值, 该返回值会被赋给 _val(ctx).

最后, 您可以提供一个函数, 它接受属性的各个元素 (如果属性是元组), 并返回要赋给 _val(ctx) 的值:

namespace bp = boost::parser;
bp::rule<struct obj_tag, obj_t> obj = "obj";
constexpr auto obj_def = (bp::int_ >> bp::double_)[to_obj];

更正式地说, 在规则内部, 语义动作的使用方式由以下规则确定. 假设我们有一个函数 APPLY, 它用元组的元素调用某个函数, 例如 std::apply. 对于某个上下文 ctx、语义动作 action 和属性 attr, action 的使用方式如下:

- _val(ctx) = APPLY(action, std::move(attr)), 如果它是良构的, 且 attr 是大小为 2 或更大的元组;

- 否则, 使用 _val(ctx) = action(ctx), 如果它是良构的;

- 否则, 使用 action(ctx).

第一种情况完全不把上下文传给动作. 最后一种情况是规则之外语义动作的通常用法.

使用解析器的算法与视图

除非另有说明, 所有这些算法和视图的约束方式都与 parse() 的各重载非常相似. 它们接受的范围、解析器等的种类是相同的.

boost::parser::search()

如 parse() API 中所示, Boost.Parser 的两种解析模式是全量解析 (whole-parse) 和前缀解析 (prefix-parse). 当您想在被解析范围的中间查找某个东西时, 并没有相应的 parse API. 当然, 您可以编写一个简单的解析器, 跳过您要找的东西之前的所有内容.

namespace bp = boost::parser;
constexpr auto parser = /* ... */;
constexpr auto middle_parser = bp::omit[*(bp::char_ - parser)] >> parser;

middle_parser 会跳过所有内容, 一次一个 char_, 只要下一个 char_ 不是 parser 成功匹配的开头. 此后, 控制权转交给 parser 本身. 好, 这写起来并不太难. 如果您需要从中间开始解析以生成属性, 这就是您应当使用的方法.

然而, 实际情况往往是您只需要在被解析范围中查找某个子范围. 在这些情况下, 最好按照 std::ranges 中那些算法的模式把它变成一个正式的算法, 因为那样更符合惯用法. boost::parser::search() 就是这样的算法. 它的语义与 std::ranges::search 非常相似, 区别在于它查找的不是与某个精确子范围的匹配, 而是与给定解析器的匹配. 与 std::ranges::search() 一样, 它返回一个子范围 (C++17 中是 boost::parser::subrange, C++20 及更高版本中是 std::ranges::subrange).

namespace bp = boost::parser;
auto result = bp::search("aaXYZq", bp::lit("XYZ"), bp::ws);
assert(!result.empty());
assert(std::string_view(result.begin(), result.end() - result.begin()) == "XYZ");

由于 boost::parser::search() 返回一个子范围, 您给它的任何解析器都不生成属性. 我在上面写的是 bp::lit("XYZ"); 如果我改写为 bp::string("XYZ"), 结果 (以及不构造 std::string 这一点) 也不会改变.

正如您在上面看到的, boost::parser::search() 有一个方面有意不同于 std::ranges 算法的惯例 —— 它接受 C 风格字符串, 并把它们当作真正的范围来对待.

此外, boost::parser::search() 知道如何适配您的迭代器类型. 您可以像上面的示例那样传入 C 风格字符串 "aaXYZq", 或者 "aaXYZq" | bp::as_utf32, 或者 "aaXYZq" | bp::as_utf8, 甚至 "aaXYZq" | bp::as_utf16, 它会返回一个子范围, 其迭代器类型就是您作为输入传入的类型, 即使内部使用的迭代器类型可能不同 (在 Unicode 解析中是 UTF-8 到 UTF-32 的转码迭代器, 上面所有 | bp::as_utfN 示例都是如此). 只要您传入的要解析范围的值类型是 char、char8_t、char32_t, 或者是经过某种 as_utfN 适配器组合适配的范围, 这种适配都会正确工作.

boost::parser::search() 有多个重载. 您可以传入范围或迭代器/哨兵对, 也可以传入或不传入跳过解析器. 这就有四个重载. 此外, 这四个重载都在末尾接受一个可选的 boost::parser::trace 参数. 这对于排查为什么在输入中找不到您期望找到的东西非常方便.

boost::parser::search_all

boost::parser::search_all 创建 boost::parser::search_all_views. boost::parser::search_all_view 是一个 std::views 风格的视图. 它产生一个由子范围组成的范围. 它产生的每个子范围都是给定解析器在被解析范围中的下一个匹配.

namespace bp = boost::parser;
auto r = "XYZaaXYZbaabaXYZXYZ" | bp::search_all(bp::lit("XYZ"));
int count = 0;
// Prints XYZ XYZ XYZ XYZ.
for (auto subrange : r) {
    std::cout << std::string_view(subrange.begin(), subrange.end() - subrange.begin()) << " ";
    ++count;
}
std::cout << "\n";
assert(count == 4);

上面关于 boost::parser::search() 的小节中指出的所有细节同样适用于 boost::parser::search_all: 它的解析器不生成属性; 它接受 C 风格字符串并视其为范围; 在典型情况下, 它知道如何从内部使用的迭代器类型回到给定的迭代器类型.

boost::parser::search_all 调用时可以带或不带跳过解析器, boost::parser::search_all_view 构造时也是如此, 并且您始终可以在它们任何重载的末尾传入 boost::parser::trace.

boost::parser::split

boost::parser::split 创建 boost::parser::split_views. boost::parser::split_view 是一个 std::views 风格的视图. 它产生被解析范围的一个子范围序列, 按给定解析器的匹配进行分割. 您可以把 boost::parser::split_view 看作 boost::parser::search_all_view 的补集: boost::parser::split_view 产生的是 boost::parser::search_all_view 所产生的各子范围之间的子范围. boost::parser::split_view 的语义与 std::views::split_view 非常相似. 与 std::views::split_view 一样, boost::parser::split_view 也会在被解析范围的开头/末尾与相邻匹配之间, 或在相邻匹配之间产生空范围.

namespace bp = boost::parser;
auto r = "XYZaaXYZbaabaXYZXYZ" | bp::split(bp::lit("XYZ"));
int count = 0;
// Prints '' 'aa' 'baaba' '' ''.
for (auto subrange : r) {
    std::cout << "'" << std::string_view(subrange.begin(), subrange.end() - subrange.begin()) << "' ";
    ++count;
}
std::cout << "\n";
assert(count == 5);

上面关于 boost::parser::search() 的小节中指出的所有细节同样适用于 boost::parser::split: 它的解析器不生成属性; 它接受 C 风格字符串并视其为范围; 在典型情况下, 它知道如何从内部使用的迭代器类型回到给定的迭代器类型.

boost::parser::split 调用时可以带或不带跳过解析器, boost::parser::split_view 构造时也是如此, 并且您始终可以在它们任何重载的末尾传入 boost::parser::trace.

boost::parser::replace
重要

boost::parser::replace 和 boost::parser::replace_view 在 MSVC 的 C++17 模式下不可用.

boost::parser::replace 创建 boost::parser::replace_views. boost::parser::replace_view 是一个 std::views 风格的视图. 它从被解析范围 r 和给定的替换范围 replacement 产生一个子范围序列. 在被解析范围中每找到一处与给定解析器 parser 匹配的地方, 产生的子范围就是 replacement. r 中每个不匹配 parser 的子范围也会作为子范围产生. 这些子范围按它们在 r 中出现的顺序产生. 与 boost::parser::split_view 不同, boost::parser::replace_view 不产生空子范围, 除非 replacement 为空.

namespace bp = boost::parser;
auto card_number = bp::int_ >> bp::repeat(3)['-' >> bp::int_];
auto rng = "My credit card number is 1234-5678-9012-3456." | bp::replace(card_number, "XXXX-XXXX-XXXX-XXXX");
int count = 0;
// Prints My credit card number is XXXX-XXXX-XXXX-XXXX.
for (auto subrange : rng) {
    std::cout << std::string_view(subrange.begin(), subrange.end() - subrange.begin());
    ++count;
}
std::cout << "\n";
assert(count == 3);

如果 Ir 和 Ireplacement —— 即传入的 r 和 replacement 范围的迭代器类型 —— 相同 (如上面的示例), 那么产生的子范围的迭代器类型是 Ir. 如果它们不同, 则对迭代器使用实现定义的类型. 该类型在实质上等价于 std::variant<Ir, Ireplacement>. 只要 Ir 与 Ireplacement 兼容, 这就能工作. 要兼容, 它们必须具有公共的引用、值和右值引用类型, 由 std::common_type_t 判定. 这种方案的一个优点是: boost::parser::replace_view 所表示的子范围范围可以轻松地重新连接成单个范围.

namespace bp = boost::parser;
auto card_number = bp::int_ >> bp::repeat(3)['-' >> bp::int_];
auto rng = "My credit card number is 1234-5678-9012-3456." | bp::replace(card_number, "XXXX-XXXX-XXXX-XXXX") | std::views::join;
std::string replace_result;
for (auto ch : rng) {
    replace_result.push_back(ch);
}
assert(replace_result == "My credit card number is XXXX-XXXX-XXXX-XXXX.");

注意, 我们不能写出 std::string replace_result(r.begin(), r.end()). 这是非良构的, 因为 std::string 的范围构造函数接受两个相同类型的迭代器, 而 decltype(rng.end()) 是与 decltype(rng.begin()) 不同的哨兵类型.

虽然范围 r 和 replacement 都可以是 C 风格字符串, 但 boost::parser::replace_view 在做任何工作之前必须知道 replacement 的末尾. 这是因为产生的子范围都是 common 范围, 因此如果 replacement 不是, 就必须由它形成一个 common 范围. 如果您打算把很长的 C 风格字符串传给 boost::parser::replace, 并指望在范围被使用之前不必付出查看其末尾的代价 —— 别这么做.

ReplacementV 的约束与 V 几乎完全相同. V 必须满足 parsable_range 和 std::ranges::viewable_range. ReplacementV 也一样, 区别是它还可以是 std::ranges::input_range, 而 V 必须是 std::ranges::forward_range.

您可能想知道: 如果给 r 传一个 UTF-N 范围, 而给 replacement 传一个 UTF-M 范围, 会发生什么. 此时发生的是 replacement 被静默转码 (从 UTF-M 到 UTF-N), 这是由 boost::parser::replace 范围适配器完成的. 这不需要内存分配; boost::parser::replace 只是把 | boost::parser::as_utfN 套在 replacement 上. 然而, 由于 Boost.Parser 把 char 范围视为未知编码, boost::parser::replace 不会从 char 范围转码. 因此, 像下面这样的调用无法工作:

char const str[] = "some text";
char const replacement_str[] = "some text";
using namespace bp = boost::parser;
auto r = empty_str | bp::replace(parser, replacement_str | bp::as_utf8); // Error: ill-formed!  Can't mix plain-char inputs and UTF replacements.

这无法工作, 尽管 char 与 UTF-8 大小相同. 如果 r 和 replacement 都是 char 的范围, 一切当然都能工作. 无法工作的只是把 char 与 UTF 编码范围混用.

上面关于 boost::parser::search() 的小节中指出的所有细节同样适用于 boost::parser::replace: 它的解析器不生成属性; 对于 r 和 replacement 参数, 它接受 C 风格字符串并视其为范围; 在典型情况下, 它知道如何从内部使用的迭代器类型回到给定的迭代器类型.

boost::parser::replace 调用时可以带或不带跳过解析器, boost::parser::replace_view 构造时也是如此, 并且您始终可以在它们任何重载的末尾传入 boost::parser::trace.

boost::parser::transform_replace
重要

boost::parser::transform_replace 和 boost::parser::transform_replace_view 在 MSVC 的 C++17 模式下不可用.

重要

boost::parser::transform_replace 和 boost::parser::transform_replace_view 在 GCC 12 之前 C++20 模式下的 GCC 上不可用.

boost::parser::transform_replace 创建 boost::parser::transform_replace_views. boost::parser::transform_replace_view 是一个 std::views 风格的视图. 它从被解析范围 r 和给定的可调用对象 f 产生一个子范围序列. 在被解析范围中每找到一处与给定解析器 parser 匹配的地方, 设 parser 的属性为 attr; 产生的子范围就是 f(std::move(attr)). r 中每个不匹配 parser 的子范围也会作为子范围产生. 这些子范围按它们在 r 中出现的顺序产生. 与 boost::parser::split_view 不同, boost::parser::transform_replace_view 不产生空子范围, 除非 f(std::move(attr)) 为空. 下面是一个示例.

auto string_sum = [](std::vector<int> const & ints) {
    return std::to_string(std::accumulate(ints.begin(), ints.end(), 0));
};

auto rng = "There are groups of [1, 2, 3, 4, 5] in the set." |
           bp::transform_replace('[' >> bp::int_ % ',' >> ']', bp::ws, string_sum);
int count = 0;
// Prints "There are groups of 15 in the set".
for (auto subrange : rng) {
    for (auto ch : subrange) {
        std::cout << ch;
    }
    ++count;
}
std::cout << "\n";
assert(count == 3);

设类型 decltype(f(std::move(attr))) 为 Replacement. Replacement 必须是一个范围, 并且必须与 r 兼容. 细节参见上一节中关于 boost::parser::replace_view 迭代器兼容性要求的描述.

与 boost::parser::replace 一样, boost::parser::transform_replace 可以通过管道连接到 std::views::join, 从子范围视图展平为元素视图. 示例参见上面关于 boost::parser::replace 的一节.

与 boost::parser::replace 和 boost::parser::replace_view 一样, boost::parser::transform_replace 和 boost::parser::transform_replace_view 会在适用时把结果静默转码为适当的 UTF. 如果 r 和 f(std::move(attr)) 都是 char 的范围, 或者都是同一种 UTF, 则不发生转码. 如果 r 和 f(std::move(attr)) 中一个是 char 的范围, 而另一个是某种 UTF, 则程序是非良构的.

boost::parser::transform_replace_view 会把每个属性移入 f; f 可以按需从实参移动或拷贝. f 可以返回左值引用. 如果它这样做了, 该引用的地址会被取得并存储在 boost::parser::transform_replace_view 中. 否则, f 返回的值会被移入 boost::parser::transform_replace_view. 无论哪种情况, boost::parser::transform_replace_view 的值类型始终是子范围.

boost::parser::transform_replace 调用时可以带或不带跳过解析器, boost::parser::transform_replace_view 构造时也是如此, 并且您始终可以在它们任何重载的末尾传入 boost::parser::trace.

Unicode 支持

Boost.Parser 从设计之初就考虑了对 Unicode 的友好性. Boost.Parser 文档中多次提到 "Unicode 代码路径"和"非 Unicode 代码路径". 尽管实际上存在分别用于 Unicode 和非 Unicode 解析的两条代码路径, 但两条路径中的代码差异不大, 因为它们是以泛型方式编写的. 唯一的区别是: Unicode 代码路径把输入当作码点范围来解析, 而非 Unicode 路径不是. 实际上, 这意味着在 Unicode 代码路径中, 当您调用 parse(r, p) 并传入某个输入范围 r 和某个解析器 p 时, 解析过程就如同您调用的是 parse(r | boost::parser::as_utf32, p). (当然, r 是一个真正的范围还是一对迭代器/哨兵并无区别; 两者与 boost::parser::as_utf32 配合都能正常工作.)

Boost.Parser 解析器内部对"字符"的匹配被假定为码点匹配. 在 Unicode 路径中, 输入中的一个码点会与每个 char_ 解析器进行匹配. 在非 Unicode 路径中, 编码是未知的, 因此输入的每个元素都被视为输入编码中的一个完整"字符", 类似于码点. 从这里开始, 我将把输入的单个元素一律称为码点.

那么, 假设我们写了这样的解析器:

constexpr auto char8_parser = boost::parser::char_('\xcc');

对任何应当匹配一个或多个值的 char_ 解析器而言, 要匹配的值的类型会被保留. 因此 char8_parser 中保存着一个 char, 它将用于匹配. 如果我们写的是:

constexpr auto char32_parser = boost::parser::char_(U'\xcc');

char32_parser 中保存的就会是一个用于匹配的 char32_t.

因此, 在解析的任何时刻, 如果 char8_parser 正被用来匹配来自输入的码点 next_cp, 我们看到的情况实质上等同于 next_cp == '\xcc'; 而如果 char32_parser 正被用来匹配 next_cp, 我们看到的就是 next_cp == U'\xcc' 的等价形式. 这里的要点是: 您可以编写匹配特定值的 char_ 解析器, 而不必担心输入是否是 Unicode, 因为在底层发生的只是两个整数值之间的简单比较.

注释

Boost.Parser 实际上会在比较之前用 std::common_type 把任意两个值提升为共同类型. 这几乎总是可行的, 因为输入和传给 char_ 的任何参数都必须是字符类型.

由于匹配始终在码点级别进行 (记住, 非 Unicode 路径中的"码点"被假定为单个 char), 在 Unicode 和非 Unicode 代码路径中尝试匹配 UTF-8 输入会得到不同的结果:

namespace bp = boost::parser;

{
    std::string str = (char const *)u8"\xcc\x80"; // encodes the code point U+0300
    auto first = str.begin();

    // Since we've done nothing to indicate that we want to do Unicode
    // parsing, and we've passed a range of char to parse(), this will do
    // non-Unicode parsing.
    std::string chars;
    assert(bp::parse(first, str.end(), *bp::char_('\xcc'), chars));

    // Finds one match of the *char* 0xcc, because the value in the parser
    // (0xcc) was matched against the two code points in the input (0xcc and
    // 0x80), and the first one was a match.
    assert(chars == "\xcc");
}
{
    std::u8string str = u8"\xcc\x80"; // encodes the code point U+0300
    auto first = str.begin();

    // Since the input is a range of char8_t, this will do Unicode
    // parsing.  The same thing would have happened if we passed
    // str | boost::parser::as_utf32 or even str | boost::parser::as_utf8.
    std::string chars;
    assert(bp::parse(first, str.end(), *bp::char_('\xcc'), chars));

    // Finds zero matches of the *code point* 0xcc, because the value in
    // the parser (0xcc) was matched against the single code point in the
    // input, 0x0300.
    assert(chars == "");
}
隐式转码

此外, 预期大多数程序会使用 UTF-8 作为 Unicode 字符串的编码. Boost.Parser 在编写时就考虑了这种典型情形. 这意味着: 如果您解析的是 32 位码点 (在 Unicode 路径中总是如此), 而您想把结果捕获到一个容器 C (由 char 或 char8_t 值组成) 中, Boost.Parser 会静默地从 UTF-32 转码到 UTF-8, 并把属性写入 C. 这意味着 std::string、std::u8string 等都可以用作 *char_ 的属性出参, 结果将是 UTF-8.

注释

不直接支持把 UTF-16 字符串用作属性. 如果您想把 UTF-16 字符串用作属性, 可能需要在语义动作内把 UTF-8 或 UTF-32 属性转码为 UTF-16. 您可以使用 boost::parser::as_utf16 来做到这一点.

在 Boost.Parser 内部, 把字符串当作 UTF-8 来处理的作法几乎无处不在. 例如, 尽管 symbols 的整个接口使用 std::string 或 std::string_view, 内部使用的却是 UTF-32 比较.

显式转码

我在上文提到过, 使用 boost::parser::utf*_view 作为要解析的范围会让您进入 Unicode 解析. 下面进一步介绍这些视图以及如何最好地使用它们.

如果您想做 Unicode 解析, 在解析的每一步都要进行码点比较. 因此, 必要时您会把任何解析输入隐式转换为 UTF-32. 所有解析 API 函数在内部都是这样做的.

然而, 有时您的解析输入是 UTF-8 编码的 char 序列, 而您想做支持 Unicode 的解析. 如前所述, Boost.Parser 对 char 输入有一个特例: 它不会假定 char 序列是 UTF-8. 如果您想让解析 API 仍然对它们做 Unicode 处理, 可以使用 as_utf32 范围适配器. (注意, 您也可以使用任何 as_utf* 适配器, 其语义与下文的语义没有区别.)

namespace bp = boost::parser;

auto const p = '"' >> *(bp::char_ - '"' - 0xb6) >> '"';
char const * str = "\"two wörds\""; // ö is two code units, 0xc3 0xb6

auto result_1 = bp::parse(str, p);                // Treat each char as a code point (typically ASCII).
assert(!result_1);
auto result_2 = bp::parse(str | bp::as_utf32, p); // Unicode-aware parsing on code points.
assert(result_2);

对 parse() 的第一次调用把每个 char 当作一个码点; 由于 "ö" 是由代码单元 0xc3 和 0xb6 组成的一对, 解析会把第二个代码单元与上面解析器的 - 0xb6 部分进行匹配, 从而导致解析失败. 之所以如此, 是因为每个代码单元/char (它们都在 str 中) 都被当作独立的码点.

对 parse() 的第二次调用成功了, 因为当解析到达 'ö' 的码点时, 它是 0xf6 (U+00F6), 与解析器的 - 0xb6 部分不匹配.

另外两个适配器 as_utf8 和 as_utf16 也一并提供, 以保持完整性; 如果您想使用它们也可以. 它们都能对任何字符类型的序列进行转码.

重要

as_utfN 适配器是可选的, 因此它们不随 parser.hpp 一起提供. 要使用它们, 请 #include <boost/parser/transcode_view.hpp>.

(缺乏)规范化

Boost.Parser 不会替您处理的一件事是规范化; Boost.Parser 对规范化完全不加区分. 由于所有解析器都用码点的相等比较来进行匹配, 您应当确保被解析的范围和您的解析器都使用同一种规范化形式.

回调解析

在大多数解析场景中, 能够生成代表解析结果的属性, 或者能够解析到这样的属性中, 就已经足够了. 但有时并不够. 如果您需要解析非常大的一段文本, 生成的属性可能大到无法放进内存. 另一些情况下, 您可能有时想生成属性, 有时不想. callback_rules 就是为这类用途而存在的. callback_rule 与规则几乎一样, 区别在于: 只要解析以调用 callback_parse() (而非 parse()) 开始, 它就允许通过回调把规则的属性返回给调用者. 在对 parse() 的调用中, callback_rule 与普通的 rule 完全相同.

对于没有属性的规则, 回调函数的签名是 void (tag), 其中 tag 是声明规则时使用的标签类型. 对于属性为 attr 的规则, 签名是 void (tag, attr). 例如, 对于这条规则:

boost::parser::callback_rule<struct foo_tag> foo = "foo";

合适的回调函数是这样的:

void foo_callback(foo_tag)
{
    std::cout << "Parsed a 'foo'!\n";
}

对于这条规则:

boost::parser::callback_rule<struct bar_tag, std::string> bar = "bar";

合适的回调函数是这样的:

void bar_callback(bar_tag, std::string const & s)
{
    std::cout << "Parsed a 'bar' containing " << s << "!\n";
}
重要

对于 bar_callback() 的情况, 除了把 s 插入流之外我们不需要对它做任何事, 所以我们把它作为 const 左值引用来接受. Boost.Parser 会把所有属性移入回调, 因此签名也可以是 void bar_callback(bar_tag, std::string s) 或 void bar_callback(bar_tag, std::string && s).

您可以通过用 callback_parse() (而非 parse()) 进行解析来选择回调解析. 如果您把 callback_rules 与 parse() 搭配使用, 它们就只是普通的 rules. 这让您可以选择是用 parse() 做"常规"的属性生成/属性赋值解析, 还是用 callback_parse() 做回调解析, 而几乎不必重写任何解析代码.

所有 rules 之所以并非都是 callback_rules, 唯一的原因是: 您可能希望在一个解析中让某些 rules 使用回调, 而另一些不使用. 例如, 如果您想通过回调报告 callback_rule r1 的属性, r1 的实现可能会使用某条规则 r2 来生成其属性的一部分或全部.

回调解析的扩展示例参见 使用回调解析 JSON.

错误处理与调试

错误处理

Boost.Parser 内置了良好的错误报告. 请考虑当我们在期望点 (用 operator> 创建) 处解析失败时会发生什么. 如果我把 使用回调解析 JSON 示例中的解析器喂给一个名为 sample.json 的文件, 其中包含如下输入 (注意未匹配的 '['):

{
    "key": "value",
    "foo": [, "bar": []
}

下面就是打印到终端的错误消息:

sample.json:3:12: error: Expected ']' here:
    "foo": [, "bar": []
            ^

该消息的格式类似于 Clang 和 GCC 产生的诊断信息. 它引用发生失败的行, 甚至在解析失败的确切位置下面放了一个插入符. 这种错误消息适用于多种最终用户, 并且能与任何支持 Clang 和/或 GCC 诊断信息的东西良好互操作.

Boost.Parser 的大多数错误处理器都按这种方式格式化诊断信息, 但您并不受此约束. 只要满足错误处理器接口, 您可以编写做任何您想做的事情的错误处理器类型.

Boost.Parser 的错误处理器有:

  • default_error_handler: 生成类似上面的格式化诊断信息, 并把它们打印到 std::cerr. default_error_handler 没有关联的文件名, 错误和诊断信息都打印到 std::cerr. 该处理器是 constexpr 友好的.
  • stream_error_handler: 生成格式化的诊断信息. 可以使用一个或两个流. 如果使用两个, 错误进入其中一个流, 警告进入另一个. 可以为解析关联一个文件名; 如果关联了, 该文件名会出现在所有诊断信息中.
  • callback_error_handler: 生成格式化的诊断信息. 它通过用诊断消息调用一个回调来报告诊断, 而不是把诊断信息流式输出. 可以为解析关联一个文件名; 如果关联了, 该文件名会出现在所有诊断信息中. 该处理器适合在内存中记录诊断信息.
  • rethrow_error_handler: 除了重新抛出要求它处理的异常之外什么都不做. 它的 diagnose() 成员函数都是空操作.
  • vs_output_error_handler: 把所有错误和警告导向 Visual Studio 内部的调试输出面板. 仅在 Windows 上可用. 在 Visual Studio 之外执行时, 它可能不会做任何有用或合意的事情.

您可以使用 with_error_handler() 把错误处理器设置为其中任意一个, 或您自己的处理器 (参见 parse() API). 如果您不设置, 将使用 default_error_handler.

诊断信息是如何生成的

Boost.Parser 只在期望点失败处 (例如 a > b: 您已成功解析了 a, 但随后无法成功解析 b) 以及输入意外结束时生成本页所示的这类错误消息. 这在您看来可能很有限. 这实际上已经是我们的最优解了.

要让错误处理发生在期望点之外, 我们必须知道不会再有任何后续处理. 之所以如此, 是因为 Boost.Parser 有 P1 | P2 | ... | Pn 解析器 ("or_parser"). 这些解析器中任何一个 Pi 匹配失败时, 都不允许导致解析失败 —— 因为下一个 (Pi+1) 可能匹配. 如果我们到达 or_parser 各备选项的末尾且 Pn 失败, 我们仍然不能让顶层解析失败, 因为这个 or_parser 可能是某个父 or_parser 内部的子解析器. 唯一的例外是: 我们已完成顶层解析; 顶层解析不是前缀解析; 并且输入范围中仍有一部分剩余. 此时, 存在一个隐含期望: 解析的结束位置与输入的结束位置相同, 而这个隐含期望刚刚被违反了.

注意, 当我们遇到输入末尾时, 不能让顶层解析失败. 不能这样做的原因正是前文所述的原因. 对任何解析器 P 而言, 到达输入末尾对 P 来说是失败, 但对整个解析来说未必是失败.

好, 那么我们还能做哪些其他类型的错误报告呢? 也许我们可以记录解析过程中到达过的最远位置, 并在顶层解析器失败时在顶层报告它. 但如果不知道到达那个位置时哪个解析器是活动的, 这也没什么用. 这还需要某种重复的内存分配, 因为在 Boost.Parser 中, 解析器的进度点只存储在栈上 —— 等到顶层解析失败时, 那些深层的栈帧早已不复存在. 这不是最好的方案.

更糟的是, 知道解析进行到了多远以及哪个解析器是活动的, 也并没有太大用处. 请看这个例子.

namespace bp = boost::parser;
auto a_b = bp::char_('a') >> bp::char_('b');
auto c_b = bp::char_('c') >> bp::char_('b');
auto result = bp::parse("acb", a_b | c_b);

如果我们报告到达最远的解析器及其位置, 那会是 a_b 解析器, 位于输入中的 "bc" 位置. 这真的有启发性吗? 错误究竟出在输入把 'a' 放在了开头, 还是把 'c' 放在了中间? 如果您把 a_b 指给用户作为失败的解析器, 而绝口不提 c_b, 您很可能只是在把用户往错误的方向上引.

所有错误消息都必须来自失败的期望点 (或意外的输入结束). 以解析 JSON 为例. 如果您用 '[' 打开一个列表, 您就知道自己在解析列表; 如果列表是非良构的, 您会得到一条说明这一点的错误消息. 如果您用 '{' 打开一个对象, 同样可行 —— 当缺少匹配的 '}' 时, 您可以告诉用户"这不是一个对象", 这是有用的反馈. 对于部分解析的数字等也是如此. 如果 JSON 解析器没有内置诸如配对花括号和方括号之类的期望, Boost.Parser 怎么能知道缺少 '}' 真的是个问题, 并且即使没有 '}' 也不会有后续解析器匹配输入呢?

重要

结论是: 您应当尽可能多地用 operator> 在解析器中构建期望点.

在语义动作中使用错误处理器

通过调用 _error_handler(ctx), 您可以在任何语义动作内部访问错误处理器 (参见 解析上下文). 任何错误处理器都必须有以下成员函数:

template<typename Context, typename Iter>
void diagnose(
    diagnostic_kind kind,
    std::string_view message,
    Context const & context,
    Iter it) const;


template<typename Context>
void diagnose(
    diagnostic_kind kind,
    std::string_view message,
    Context const & context) const;

如果您调用第二个 (不带迭代器参数的) 重载, 它会以 _where(context).begin() 作为迭代器参数来调用第一个. 不带迭代器的那个是您最常用的. 带显式迭代器参数的那个则在您有彼此相关、关联多个位置的消息时很有用. 例如, 在解析 XML 时, 您可能希望通过显示找到开始标签的行, 来报告某个结束标签与其关联的开始标签不匹配. 当然, 那一行可能离 _where(ctx).begin() 很远. (关于 _globals() 的描述见下文.)

[](auto & ctx) {
    // Assume we have a std::vector of open tags, and another
    // std::vector of iterators to where the open tags were parsed, in our
    // globals.
    if (_attr(ctx) != _globals(ctx).open_tags.back()) {
        std::string open_tag_msg =
            "Previous open-tag \"" + _globals(ctx).open_tags.back() + "\" here:";
        _error_handler(ctx).diagnose(
            boost::parser::diagnostic_kind::error,
            open_tag_msg,
            ctx,
            _globals(ctx).open_tags_position.back());
        std::string close_tag_msg =
            "does not match close-tag \"" + _attr(ctx) + "\" here:";
        _error_handler(ctx).diagnose(
            boost::parser::diagnostic_kind::error,
            close_tag_msg,
            ctx);

        // Explicitly fail the parse.  Diagnostics do not affect parse success.
        _pass(ctx) = false;
    }
}
_report_error() 和 _report_warning()

还有一些便捷函数可以让上面的代码不那么冗长, 即 _report_error() 和 _report_warning():

[](auto & ctx) {
    // Assume we have a std::vector of open tags, and another
    // std::vector of iterators to where the open tags were parsed, in our
    // globals.
    if (_attr(ctx) != _globals(ctx).open_tags.back()) {
        std::string open_tag_msg =
            "Previous open-tag \"" + _globals(ctx).open_tags.back() + "\" here:";
        _report_error(ctx, open_tag_msg, _globals(ctx).open_tag_positions.back());
        std::string close_tag_msg =
            "does not match close-tag \"" + _attr(ctx) + "\" here:";
        _report_error(ctx, close_tag_msg);

        // Explicitly fail the parse.  Diagnostics do not affect parse success.
        _pass(ctx) = false;
    }
}

您几乎总是应当使用这些不那么冗长的函数. 您唯一想直接使用 _error_handler() 的情形是: 您正在使用自定义错误处理器, 并且想访问其接口中除 diagnose() 之外的某些部分.

尽管上面这些函数支持报告警告, 但 Boost.Parser 提供的任何错误处理器都不会报告警告. 警告严格留给用户代码使用.

关于错误处理和诊断 API 其余部分的更多信息, 请参阅 error_handling_fwd.hpp 和 error_handling.hpp 的头文件参考页.

创建自己的错误处理器

创建自己的错误处理器相当简单; 您只需实现三个成员函数. 假设您想要一个把诊断信息写入文件的错误处理器. 下面是可能的实现方式.

struct logging_error_handler
{
    logging_error_handler() {}
    logging_error_handler(std::string_view filename) :
        filename_(filename), ofs_(filename_)
    {
        if (!ofs_)
            throw std::runtime_error("Could not open file.");
    }

    // This is the function called by Boost.Parser after a parser fails the
    // parse at an expectation point and throws a parse_error.  It is expected
    // to create a diagnostic message, and put it where it needs to go.  In
    // this case, we're writing it to a log file.  This function returns a
    // bp::error_handler_result, which is an enum with two enumerators -- fail
    // and rethrow.  Returning fail fails the top-level parse; returning
    // rethrow just re-throws the parse_error exception that got us here in
    // the first place.
    template<typename Iter, typename Sentinel>
    bp::error_handler_result
    operator()(Iter first, Sentinel last, bp::parse_error<Iter> const & e) const
    {
        bp::write_formatted_expectation_failure_error_message(
            ofs_, filename_, first, last, e);
        return bp::error_handler_result::fail;
    }

    // This function is for users to call within a semantic action to produce
    // a diagnostic.
    template<typename Context, typename Iter>
    void diagnose(
        bp::diagnostic_kind kind,
        std::string_view message,
        Context const & context,
        Iter it) const
    {
        bp::write_formatted_message(
            ofs_,
            filename_,
            bp::_begin(context),
            it,
            bp::_end(context),
            message);
    }

    // This is just like the other overload of diagnose(), except that it
    // determines the Iter parameter for the other overload by calling
    // _where(ctx).
    template<typename Context>
    void diagnose(
        bp::diagnostic_kind kind,
        std::string_view message,
        Context const & context) const
    {
        diagnose(kind, message, context, bp::_where(context).begin());
    }

    std::string filename_;
    mutable std::ofstream ofs_;
};

就是这么简单. 您只需在错误处理器的调用运算符中完成其重要工作, 然后实现它必须为语义动作内部使用而提供的 diagnose() 的两个重载. 这些重载的默认实现甚至可以作为自由函数 write_formatted_message() 使用, 所以您可以像上面那样直接调用它. 下面是可能的用法.

int main()
{
    std::cout << "Enter a list of integers, separated by commas. ";
    std::string input;
    std::getline(std::cin, input);

    constexpr auto parser = bp::int_ >> *(',' > bp::int_);
    logging_error_handler error_handler("parse.log");
    auto const result = bp::parse(input, bp::with_error_handler(parser, error_handler));

    if (result) {
        std::cout << "It looks like you entered:\n";
        for (int x : *result) {
            std::cout << x << "\n";
        }
    }
}

我们只需定义一个 logging_error_handler, 并按引用把它传给 with_error_handler(), 后者会用该错误处理器装饰顶层解析器. 我们不能写成 bp::with_error_handler(parser, logging_error_handler("parse.log")), 因为 with_error_handler() 不接受右值. 这是因为错误处理器最终会进入解析上下文. 解析上下文只存储指针和迭代器, 以保持复制成本低廉.

如果我们运行该示例并给它输入 "1,", 日志文件中就会出现如下内容:

parse.log:1:2: error: Expected int_ here (end of input):
1,
  ^
修复非良构代码

在编写解析器的过程中, 您有时会犯一些简单的错误, 而由于从您刚写的代码行到使用点 (通常是对 parse() 的调用) 之间有大量的模板实例化, 诊断结果会非常恐怖. 我说"有时", 意思是"几乎总是, 而且一次又一次". 对于这类情况, Boost.Parser 有一个应对办法: 让非良构代码在尽可能多的情形下变为良构, 然后改用运行时断言.

通常, C++ 程序员会尽一切可能尽早发现错误. 这通常意味着让尽可能多的坏代码成为非良构的. 与直觉相反的是, 在解析器组合子的场景下这并不可行. 关于这两种调试场景在 Boost.Parser 中可能有多么天差地别, 请参阅 none 很奇怪 一节 (位于 设计理由 中) 的很长一段讨论.

如果您在道义上反对这种做法, 或者就是不喜欢乐趣, 好消息是: 您可以通过定义 BOOST_PARSER_NO_RUNTIME_ASSERTIONS 完全关闭这种技术的使用.

运行时调试

调试解析器很难. 任何复杂度超过一定程度的解析器, 仅靠阅读解析器的代码几乎不可能调试. 在调试器中单步跟踪解析更是如此. 为了给调试您的解析器提供合理的机会, Boost.Parser 提供了一种跟踪模式, 只需给 parse() 或 callback_parse() 提供一个额外的参数即可开启:

boost::parser::parse(input, parser, boost::parser::trace::on);

parse() 和 callback_parse() 的每个重载都接受这最后一个参数, 其默认值为 boost::parser::trace::off.

如果我们跟踪一个规模可观的解析器, 就会看到大量输出. 输入的每个码点都必须逐个考虑, 以确定某条规则是否匹配. 作为示例, 让我们用 解析 JSON 中的 JSON 解析器来跟踪一次解析. 输入是 "null". null 是 JavaScript 值可以具有的类型之一; JSON 解析器示例中的顶层解析器是:

auto const value_p_def =
    number | bp::bool_ | null | string | array_p | object_p;

因此, 一个 JSON 值可以是数字、布尔值、null 等. 在解析期间, 每个备选项都会被依次尝试, 直到有一个匹配为止. 我选择 null 是因为它相对接近 value_p_def 备选解析器的开头. 即便如此, 输出还是相当庞大. 让我们边看边分解:

[begin value; input="null"]

每个解析器都被跟踪为 [begin foo; ...], 然后是解析操作本身, 然后是 [end foo; ...]. 规则的名字会用作跟踪中 begin 和 end 部分的名称. 非规则的名称则与您编写解析器时的样子相似. 大多数行都会引用输入接下来的几个码点, 就像我们这里看到的 (input="null").

[begin number | bool_ | null | string | ...; input="null"]

这展示了位于规则 value 之内的解析器的开头 —— 真正完成所有工作的那个解析器. 在示例代码中, 这个解析器名为 value_p_def. 由于它不是规则, 我们没有它的名字, 因此我们按子解析器的构成来展示它的实现. 由于它有点长, 我们不打印全部内容. 那就是那个省略号存在的原因.

查看 Boost.Parser 跟踪输出时需要注意的几点:

  • 有些解析器您并不认识, 因为它们没有被直接写入文档. 例如, p[a] 会构成一个 action_parser, 其中包含解析器 p 和语义动作 a. 这本质上是实现细节, 但遗憾的是, 跟踪输出并不会对您隐藏这一点.
  • 对于解析器 p, 跟踪名称可能与 p 的实际结构有意不同. 例如, 在上面的跟踪中, 您会看到一个简称为 "null" 的解析器. 这个解析器实际上是 boost::parser::omit[boost::parser::string("null")], 但您通常写的只是 "null", 因此就用了这个名字. 这样的特例有两个: 这里描述的 omit[string] 的情形, 以及 omit[char_] 的情形.
  • 由于解析器名称的打印没有其他特例, 您可能会看到与您代码中所写的不同的解析器. 在关于解析器和组合操作的章节中, 您有时会看到用等价解析器来描述某个解析器或组合操作. 例如, if_(pred)[p] 被描述为"等价于 eps(pred) >> p". 在跟踪中, 您不会看到 if_; 您看到的是 eps 和 p.
  • 传给解析器的实参的值会尽可能打印出来. 有时, 解析实参本身不是值, 而是产生该值的可调用对象. 在这些情况下, 您看到的是解析实参的求值结果.
编译期禁用跟踪

虽然跟踪模式对调试非常有用, 但它确实有一些开销. 大多数解析器模板会被实例化两次: 一次启用跟踪, 一次禁用跟踪. 如果您想在编译期完全禁用跟踪功能, 可以在包含任何 Boost.Parser 头文件之前定义 BOOST_PARSER_DISABLE_TRACE:

#define BOOST_PARSER_DISABLE_TRACE
#include <boost/parser/parser.hpp>

设置这个宏定义后, 所有与跟踪相关的代码都会被编译剔除, 从而缩短编译时间.

内存分配

Boost.Parser 很少分配内存. 例外情况如下:

  • symbols 会为它包含的符号/属性对分配内存. 如果在解析期间添加符号, 那时也必须进行分配. symbols 使用的数据结构也是一棵 trie (基于节点的树). 因此, 如果您使用 symbols, 很可能会出现大量分配.
  • 可以接受文件名的那些错误处理器会为文件名分配内存 (如果提供了文件名).
  • 如果通过向顶层解析函数传入 boost::parser::trace::on 来开启跟踪, 解析器的名称会被分配.
  • 当遇到失败的期望时 (使用 operator>), 失败解析器的名称会被放入 std::string 中, 这通常会导致一次分配.
  • string() 的属性是一个 std::string, 其使用意味着分配. 您可以通过为属性显式使用一种不分配内存的其他字符串类型来避免这种分配.
  • repeat(p) 的属性在所有形式下 —— 包括 operator*、operator+ 和 operator% —— 都是 std::vector<ATTR(p)>, 其使用意味着分配. 您可以通过为属性显式使用一种不分配内存的其他序列容器来避免这种分配. boost::container::static_vector 或 C++26 的 std::inplace_vector 可能对此类替换有用.

除了在期望失败的情形下为被期望的解析器名称分配内存之外, Boost.Parser 不会分配内存 —— 除非您通过使用 symbols、使用特定 error_handler、开启跟踪, 或解析到会分配内存的属性中来要求它这样做.

最佳实践

从一开始就解析 Unicode

如果您想解析 ASCII, 使用 Unicode 解析 API 实际上不会让您付出任何代价. 您的输入会被解析, char 逐 char 地进行, 并与作为 Unicode 码点的值进行比较 (它们是 char32_t). 一个需要注意的点是: 如果输入是 UTF-8, 每个字符可能会多一次分支. 如果您的性能要求能容忍这一点, 那么直接从 Unicode 开始并坚持下去, 您的日子会好过得多.

从支持 Unicode 和 UTF-8 输入开始, 您就能毫不费力地正确处理意外的输入, 比如非 ASCII 语言 (大多数语言都是).

编写规则并单独测试

把规则当作解析器中的工作单元. 编写一条规则, 测试它的各种边界情形, 然后用它构建更大的规则或解析器. 这让您能以更少的工作获得更好的覆盖, 因为逐条测试规则的所有代码路径, 可以让贯穿代码的路径组合数量保持在可控范围内.

优先使用自动生成的属性而非语义动作

从解析器中取出属性有多种方式. 您可以:

  • 使用解析器生成的任何属性;
  • 给 parse() 提供一个属性出参, 让解析器来填充;
  • 使用一个或多个语义动作, 把解析器的属性赋给解析器外部的变量;
  • 使用回调解析, 通过回调调用提供属性.

这些方式所需的努力大体相当, 只有语义动作方式例外. 采用语义动作方式时, 您需要有供解析器填充的值, 并让它们在解析期间一直处于作用域内.

让解析器直接在解析结果中产出解析的属性, 要直接得多, 也能带来更可复用的解析器.

这并不意味着您永远不该使用语义动作. 它们有时是必需的. 然而, 您应当默认使用其他非语义动作的方式, 只在有充分理由时才使用语义动作.

如果您的解析器接受最终用户输入, 请给规则起您希望最终用户看到的名字

Boost.Parser 产生的典型错误消息会说类似 "Expected FOO here" 的话, 其中 FOO 是某条规则或某个解析器. 请给您的规则起在这类错误消息中读起来通顺的名字. 例如, JSON 示例中有这些规则:

bp::rule<class escape_seq, uint32_t> const escape_seq =
    "\\uXXXX hexadecimal escape sequence";
bp::rule<class escape_double_seq, uint32_t, double_escape_locals> const
    escape_double_seq = "\\uXXXX hexadecimal escape sequence";
bp::rule<class single_escaped_char, uint32_t> const single_escaped_char =
    "'\"', '\\', '/', 'b', 'f', 'n', 'r', or 't'";

需要注意几点:

- escape_seq 和 escape_double_seq 有相同的名称字符串. 对于想弄清自己的输入为何解析失败的最终用户来说, 解析器规则生成哪种结果并不重要; 他们只想知道如何修正自己的输入. 对这两条规则中的任何一条, 修复方法都一样: 在那里放一个十六进制转义序列.

- single_escaped_char 的名字看起来很糟. 不过, 它实际上并没有被用作名称. 但在错误消息中, 它反而表现良好. 错误消息会是 "Expected '"', '', '/', 'b', 'f', 'n', 'r', or 't' here", 相当有用.

准备一个可运行的简单测试来发现非良构代码转断言的情形

这类错误大多在解析器构造时就能发现, 因此甚至不需要真正执行解析. 例如, 一个测试用例可能是这样:

TEST(my_parser_tests, my_rule_test) {
    my_rule r;
}

编写自己的解析器

您可能永远不需要编写自己的低级解析器. 您有 char_ 这样的原语, 可以用它构建所需的各种解析器. 您不太可能需要做比单个字符更底层的事情.

然而, 有些人执迷于凡事都自己动手实现. 我们把这样的人称为 C++ 程序员. 本节就是为他们准备的. 不过, 本节并不是深入教程; 它是一个基础指引, 让您对编写解析器涉及的各个组成部分足够熟悉, 从而可以通过阅读 Boost.Parser 的代码继续深入学习.

每个解析器都必须提供函数 call() 的两个重载. 其中一个重载执行解析并生成属性 (属性可能是特殊的无属性类型 detail::nope). 另一个重载执行解析并填入给定的属性. 给定属性的类型是一个模板参数, 因此它可以是任何您能构成引用的类型.

我们来看看一个 Boost.Parser 解析器 opt_parser. 它是通过使用 operator- 得到的解析器. 首先, 这是它定义的开头部分.

template<typename Parser>
struct opt_parser
{

它定义的结尾是:

    Parser parser_;
};

如您所见, opt_parser 唯一的数据成员就是它所适配的解析器 parser_. 下面是它生成属性的那个重载, 即 call().

template<
    typename Iter,
    typename Sentinel,
    typename Context,
    typename SkipParser>
auto call(
    Iter & first,
    Sentinel last,
    Context const & context,
    SkipParser const & skip,
    detail::flags flags,
    bool & success) const
{
    using attr_t = decltype(parser_.call(
        first, last, context, skip, flags, success));
    detail::optional_of<attr_t> retval;
    call(first, last, context, skip, flags, success, retval);
    return retval;
}

首先, 我们来看模板参数和函数参数.

  • Iter & first 是迭代器. 它作为出参传入. 当且仅当解析成功时, call() 有责任前移 first.
  • Sentinel last 是哨兵. 如果解析在 call() 内尚未成功, 且 first == last 等于 true, 则 call() 必须失败 (通过把 bool & success 设置为 false).
  • Context const & context 是解析上下文. 它会是 detail::parse_context 的某种特化. 上下文用于对子解析器 call() 的任何调用; 在某些情况下, 应当创建一个新上下文, 并把新上下文传给子解析器 —— 下文会详述.
  • SkipParser const & skip 是当前跳过解析器. skip 应当在解析开始时使用, 并在任何子解析器的任意两次使用之间使用.
  • detail::flags flags 是一组标志, 指示解析当前状态的各种信息. flags 涉及: 是否要生成属性; 是否应用跳过解析器 skip; 是否生成详细跟踪 (例如在顶层传入 boost::parser::trace::on 时); 以及我们当前是否位于工具函数 detail::apply_parser 内部.
  • bool & success 是最后一个函数参数. 解析成功时应把它设为 true, 否则设为 false.

现在来看函数体. 注意, 它只是分派给另一个 call() 重载. 这种做法非常常见, 因为两个重载需要做同样的解析; 只有属性可能不同. 函数体的第一行定义了 attr_t —— 即我们包装的解析器 parser_ 的默认属性类型. 它通过获取 decltype() (即对 parser_.call() 的一次使用的结果) 来做到这一点. (这就是本文档其余部分中 ATTR() 所代表的逻辑.) 由于 opt_parser 表示一个可选值, 其属性的自然类型是 std::optional<ATTR(parser)>. 然而, 这并非对所有情况都适用. 特别是, 它不适用于"无属性"类型 detail::nope, 也不适用于 std::optional<T> —— ATTR(--p) 其实就是 ATTR(-p). 因此, 第二行使用了一个处理这些细节的别名 detail::optional_of<>. 第三行只是调用 call() 的另一个重载, 并把 retval 作为出参传入. 最后, 最后一行返回 retval.

接下来看另一个重载.

        template<
            typename Iter,
            typename Sentinel,
            typename Context,
            typename SkipParser,
            typename Attribute>
        void call(
            Iter & first,
            Sentinel last,
            Context const & context,
            SkipParser const & skip,
            detail::flags flags,
            bool & success,
            Attribute & retval) const
        {
#if BOOST_PARSER_DO_TRACE
            [[maybe_unused]] auto _ = detail::scoped_trace(
                *this, first, last, context, flags, retval);
#endif

            detail::skip(first, last, skip, flags);

            if (!detail::gen_attrs(flags)) {
                parser_.call(first, last, context, skip, flags, success);
                success = true;
                return;
            }

            parser_.call(first, last, context, skip, flags, success, retval);
            if (!success)
                retval = Attribute();
            success = true;
        }

这里的模板参数和函数参数与另一个重载完全相同, 只是多了一个 Attribute & retval —— 我们的出参.

我们逐段来看这个实现.

#if BOOST_PARSER_DO_TRACE
            [[maybe_unused]] auto _ = detail::scoped_trace(
                *this, first, last, context, flags, retval);
#endif

这里定义了一个 RAII 跟踪对象, 如果用户向顶层解析传入了 boost::parser::trace::on, 它就会生成用户请求的详细跟踪. 它只在 detail::enable_trace(flags) 为 true 时才起作用. 如果启用了跟踪, 它会在定义之处显示解析的状态, 并在其离开作用域时再次显示. 通过定义 BOOST_PARSER_DISABLE_TRACE, 可以在编译期全局禁用跟踪功能.

重要

要让跟踪代码工作, 您必须为新的解析器类型/模板定义一个 detail::print_parser 的重载. 示例参见 <boost/parser/detail/printing.hpp>.

detail::skip(first, last, skip, flags);

这一段相当简单; 它只是应用跳过解析器. opt_parser 只有一个子解析器; 但如果它有多个子解析器, 或者有一个子解析器被应用了多次, 它就需要重复这一行, 并在任意子解析器的每两次使用之间使用 skip.

if (!detail::gen_attrs(flags)) {
    parser_.call(first, last, context, skip, flags, success);
    success = true;
    return;
}

这个分支处理我们完全不想生成属性的情形 —— 也许是因为这个解析器位于 omit[] 指令内部.

parser_.call(first, last, context, skip, flags, success, retval);
if (!success)
    retval = Attribute();
success = true;

这是另一个典型分支. 这里我们确实想生成属性, 因此同样调用 parser_.call(), 只是还要传入 retval.

注意, 在两个代码分支中, 我们都在把 success 设置为 true 之后调用 parser_.call(). 由于 opt_parser 是"零或一", 即使子解析器失败, opt_parse 仍会成功.

何时创建新的解析上下文

有时, 您需要在调用子解析器之前修改解析上下文的某些内容. 例如, rule_parser 会设置该规则可用的值、局部变量等. action_parser 会把生成的属性加入上下文 (即 _attr(ctx)). 在 Boost.Parser 中上下文是不可变的. 要为子解析器"修改"上下文, 您需要通过适当调用 detail::make_context() 来创建一个新的上下文.

detail::apply_parser()

有时, 解析器需要操作一个与其默认属性不完全相同、但在某种意义上兼容的出参. 为此, 让解析器以略有不同的参数调用自己往往很有用. detail::apply_parser() 有助于做到这一点. 示例参见 repeat_parser::call() 的出参重载. 注意, 由于这会为替代解析器创建一个新作用域, scoped_trace 对象需要知道我们当前是否位于 detail::apply_parser 内部.
