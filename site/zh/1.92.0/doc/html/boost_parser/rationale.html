设计理由

char_ 的属性类型是多态的

使用 Boost.Parser 解析的主要用例是支持 Unicode 的解析. 这些用户应当能够简单地使用 char_, 并让它 "开箱即用". 就 Unicode 而言, "开箱即用" 意味着输入范围的每个元素都应当是一个码点.

有些用户会坚持认为他们的解析需求完全是 ASCII 的. 还有些用户无法使用 Unicode, 因为他们使用的编码不是 Unicode 编码的子集, 例如 EBCDIC. 对于这些用户, 他们可以直接解析 char 类型的输入序列, 这对他们来说也会 "开箱即用". 对他们而言, 这意味着被解析的输入范围的每个元素都应当是一个 char.

这正是 char_ 所做的事情, 也是它这样做的原因.

none 很奇怪

是的, 使用如此宽松的类型 (任何东西都可以赋给它, 它可以隐式转换为任何东西, 等等) 通常不是好的编程实践. 不过, 它比其他替代方案要好. 请看这个语义动作:

[](auto & ctx) { _attr(ctx) = 42; }

如果附加到一个 int 解析器上, 这没有问题. 如果附加到一个 epsilon 解析器 (它没有属性) 上, 这会静默地什么也不做. 但在调试模式下, 这个语义动作中的赋值会触发 BOOST_ASSERT(false), 并引导用户去看一大段内联注释, 说明他们是如何走到这里的. 对大多数程序员来说, 这种失败模式要比下面这种情况容易理解得多: 任意深度的模板实例化栈, 以及令人困惑的 ctx 类型 — 那是当表达式 _attr(ctx) 非良构时会导致的结果.

使用 none 会把一个纯粹的编译期调试操作变成运行期调试操作. 通常, 这与 C++ 用户所想要的恰恰相反. 考虑到解析器组合子库产生的错误信息何等晦涩难懂, 用您喜欢的调试器单步跟踪调用栈来诊断问题, 是一种 快得多 的修复问题的方式.

属性类型非常灵活

这就是在属性生成中获得泛型性的方式. 在 STL 中, 算法之所以能搭配多种类型的容器使用, 是因为迭代器充当了连接算法与容器的粘合剂. 而在属性生成中, 则是任意类型的对象被构造出来并插入容器. 允许对满足 container 概念的任意类型执行插入操作, 正是让不同容器得以泛型使用的关键.

字符类型的序列会被特殊处理

Boost.Parser 尽量让属性生成的规则保持简单. 然而, 属性生成中有一些规则只适用于 char 和 char32_t 这类字符类型. 这些类型的序列会生成 std::string 属性, 而其他所有类型的序列则会生成 std::vector. 这样做有几个原因.

首先, 字符串和向量并不相同. 我们知道字符串本质上就是数字数组, 但我们为它单独准备了一种完全不同的类型 std::string. 它有一套不同的 API, 而且其他处理文本的代码期望得到的是字符串而非其他容器. 字符数组已经被标准库和 C++ 的惯常做法视为特殊类型.

其次, 当您编写一个连续解析多个字符的解析器时, 通常是想生成一个字符串属性, 而不是若干个单独的字符值. 当您连续使用多个非字符解析器时, 通常则是想生成多个值. 例如:

namespace bp = boost::parser;
auto parser_1 = bp::char_ >> bp::char_ >> -bp::char_;
auto parser_2 = +(bp::char_ - ' ') >> ' ' >> +(bp::char_ - ' ');

我不知道您的情况如何, 但我很少在写出 parser_1 这样的解析器后还想要生成一个 boost::parser::tuple<char, char, std::optional<char>>. 同样, 我也很少在写出 parser_2 这样的解析器后还想要一个 std::vector<std::string>.

因此, Boost.Parser 把常见情形作为默认行为, 并提供 merge[] 和 separate[] 指令, 让您可以选择生成较少见的属性.

属性兼容规则比 Spirit 更严格

请考虑这个解析器.

namespace bp = boost::parser;
auto parser = -(bp::char_ % ',');

但 Boost.Parser 和 Spirit 都认为该解析器的属性类型是 optional<SEQ-OF<char>>. 不过, Spirit 允许您把它解析到一个 std::vector<char> 或 std::string 中, 而 Boost.Parser 不允许. Boost.Parser 要求您把它解析到一个 std::optional<std::string> 中, 或者把解析器改为 -(bp::char_ % ',') | bp::attr(std::string{}). 换句话说, Spirit 把"由一个或多个元素组成的序列"的可选值视为与序列本身等价, 因为序列的空状态就代表可选值的空状态. Boost.Parser 不这样认为. 为什么要如此严格?

我理解 Spirit 为什么那样做 —— 这样不会丢失任何信息, 何乐而不为呢? 然而, 我并不认同这种做法.

当我写下 operator- 时, 我得到的就是一个 std::optional. 这是一条简单的规则.

如果我确实写出了 operator-, 那就是我主动选择了要得到一个 std::optional. 代码表达了这一意图. 如果库要改变我写下的意图, 那最好有一个非常充分的理由.

当然, 上面的"简单规则"有一个例外 —— 如果我写下 -p1 >> *p2, 且 ATTR(p1) 与 ATTR(p2) 相同, 那么两者的属性就是相同的, 可选值会被吸收进容器. 我认为这就属于"非常充分的理由", 因为这是非常常见的用例. 对于其他较少见的情形, 可以使用 separate[] 来保持属性互不合并. 因此, separate[-int_ >> *int_] 的属性是 boost::parser::tuple<std::optional<int>, std::vector<int>>. 这使得退出该例外非常容易, 而且意图在代码中依然清晰可见.

相比之下, "我写了 -+int_, 但我真正想要的是一个 std::vector<int> 而不是 std::optional<std::vector<int>>"并不是一个很常见的用例.

此外, Spirit 式的宽松处理比上面 parser 所展示的更加复杂. 请记住, int_ | eps 和 -int_ 应当在语义上等价. 若不如此, 就会严重违背最小惊讶原则. 因此, 如果它们等价, 我们就需要把同样的规则应用于 int_ | eps. 这需要记住的东西太多, 实现和维护起来也很复杂.

从 Spirit 1 发布起我就在使用它, 后来又一直使用 Spirit 2. 我甚至不知道这里讨论的这种特殊宽松行为; 是一位用户在 GitHub 上指出来的. 在使用这些库的许多年里, 我从未完全掌握全部属性兼容规则, 而且常常被它们弄得措手不及.

拥有一套用户能够内化的小规则集至关重要; 如果生成的属性与我表达的意图不一致, 那就是问题. 要让它不成为问题, 我必须能够理解这些规则, 这样我才能表达自己的意图, 而不会感到意外.

传递给 parse() 的出参属性在解析失败时会被清空

对任何接受属性出参的 parse() 重载 (包括 callback_parse() 等变体) 的调用结束时, 解析要么成功, 要么失败. 如果调用失败, 该属性会被显式地"清空", 即被赋为其默认构造的值.

这样做是因为它是两个选项中危害较小的一个. 先来看看另一个选项.

// Without explicit clearing.
namespace bp = boost::parser;
std::vector<int> result;
auto b = bp::parse("3 4 c", +bp::int_, bp::ws, result);
assert(!b);
assert(result == std::vector<int>({3, 4}));

这很奇怪 —— 解析失败了, 但出参中却仍然留有部分结果. 之所以如此, 是因为解析器 +bp::int_ 只有在连一次 bp::int_ 都无法匹配时才会失败. 上例中它匹配了两次, 也就是说它成功了 (如果它失败了, 它就会清空自己的属性). 它并不知道后面已经没有内容可以继续解析, 也不知道自己正被用来执行一次全量解析. 因此, 整体解析失败了, 但填充出参属性的那部分解析并不知道要清空自己的属性.

这就是为什么显式清空行为发生在 parse() 的末尾. 不过这也不是没有缺点. 请看这个例子.

// With explicit clearing.
namespace bp = boost::parser;
std::string str = "-42";
int i = 3;
bool b = parse(str, bp::uint_, i);
assert(!b);
assert(i == 0);

在这里, 显式清空替换了 3 原有的值, 尽管解析器根本没有碰过这个值! 不必要地破坏用户变量的状态看起来似乎是个坏主意, 但请考虑另一种做法 —— 在前面的示例中, 出参属性中留下了虚假的值; 而在这里, 如果不清空, 出参属性中也会留下一个值, 但这并不是解析产生的部分结果, 而是因为解析根本没有碰过它. 这样的行为必定令人困惑, 至少也会令人意外. 我认为让解析失败的情形保持一致更好, 以减少困惑. 类型为 A 的出参属性在解析器失败时总是等于 A(); 解析成功时, 它等于解析器设置的值 —— 如果解析器没有修改它, 则保持其原有值.

没有 Boost.Spirit 风格的字符类解析器

Boost.Spirit 提供了一些字符类解析器, 它们识别的字符集合与 C 标准库的字符类函数相同. 例如, Boost.Spirit 的 alnum 识别 std::isalnum() 所识别的字符, 它的 punct 识别 std::ispunct() 所识别的字符, 等等.

问题在于, 这些 std::is*() 函数存在严重缺陷. 它们甚至连 ASCII 值都无法正确处理. 这是因为它们使用 C 标准库的 locale 机制, 该机制可以被设置为当前平台支持的任何值, 而且程序中任何位置的任何代码都可以设置它; locale 是可变的全局状态. 因此, 即使您的程序使用默认的 C locale, 只要您链接的某个库把 locale 设置成了会破坏 ASCII 字符识别的值 (例如 EBCDIC locale), 您的程序就不再正确, 无论您自己写的代码是什么.

鉴于此, 我坚信任何人在任何地方都不应在生产代码中使用那些 C 函数, 我也不会通过 Boost.Parser 支持它们的使用.
