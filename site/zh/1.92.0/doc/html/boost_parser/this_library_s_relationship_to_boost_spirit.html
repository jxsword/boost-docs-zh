本库与 Boost.Spirit 的关系

注释

如果您熟悉 Spirit 2 和/或 Spirit X3, 可能会对本节感兴趣. 如果您不熟悉, 而且还没读过 Boost.Parser 的教程, 那么本节内容对您来说几乎难以理解.

Boost.Spirit 是 Boost 中已有的一库, 已经存在很长时间了.

然而, 它在某些方面无法满足用户的需求.

  • Spirit 2 的编译时间非常长.
  • Spirit 2 的错误报告需要用户做大量干预才能工作.
  • Spirit 2 需要用户干预 (包括一次漫长的重新编译) 才能启用解析跟踪.
  • Spirit X3 的规则组合性不佳 —— 规则生成的属性会随使用该规则的上下文而变化.
  • Spirit X3 缺少 Spirit 2 曾提供的许多便捷的解析器接口. 例如, 您无法为解析器添加参数 (关于 _locals() 的描述参见 关于规则的更多内容).
  • 所有版本的 Spirit 都支持 Unicode, 但要让它正常工作相当困难.

我想要一个不受上述任何限制困扰的库. 需要指出, 尽管 Spirit X3 只存在上面列表中的几个缺陷, 但与规则相关的那一条就是一票否决的问题. 能够编写规则、单独测试它们, 然后在整个复杂解析器中复用它们, 这是不可或缺的能力.

虽然 Boost.Spirit 的任何版本 (Spirit 2 或 Spirit X3) 都没有集所有这些限制于一身, 但也不存在能完全避开所有这些限制的版本. Boost.Parser 做到了. 不过, Boost.Spirit 中有许多出色的设计思想在 Boost.Parser 中得以保留. 两个库都:

  • 使用相同的运算符重载来组合解析器;
  • 使用大致相同的一组指令来影响解析 (例如 lexeme[]);
  • 都围绕一个灵活的解析上下文对象构建, 解析过程中会向其加入或移除状态 (此处同样以 Spirit X3 作比较).

Spirit X3 的规则问题

有些读者希望看到能佐证 Spirit X3 规则组合性不佳这一论断的具体示例. 请看这个程序.

#include <boost/spirit/home/x3.hpp>

#include <iostream>
#include <set>
#include <string>
#include <vector>


namespace x3 = boost::spirit::x3;
using ints_type = x3::rule<class ints, std::vector<int>>;
BOOST_SPIRIT_DECLARE(ints_type);

x3::rule<class ints, std::vector<int>> ints = "ints";
constexpr auto ints_def = x3::int_ % ',';
BOOST_SPIRIT_DEFINE(ints);

#define FIXED_ATTRIBUTE 0


int main()
{
    std::string input = "43, 42";
    auto first = input.begin();
    auto const last = input.end();
#if FIXED_ATTRIBUTE
    std::vector<int> result;
#else
    std::set<int> result;
#endif
    bool success = x3::phrase_parse(first, last, ints, x3::space, result);
    if (success) {
        // We want this to print "43 42\n".
        for (auto x : result) {
            std::cout << x << ' ';
        }
        std::cout << "\n";
    }

    return 0;
}

把 FIXED_ATTRIBUTE 定义为 1 会得到一个良构的程序, 但它打印出的是 "42 43\n" 而非期望的结果. 这里的问题在于, 如果您把一个属性出参传给 x3::phrase_parse(), 就会得到 Spirit X3 与 Boost.Parser 都有的那种宽松匹配语义. 这是个问题, 因为用户已经明确断言 ints 规则的属性类型应当是 std::vector<int>. 在我看来, 采用 FIXED_ATTRIBUTE == 1 时这段代码应当被视为非良构. 要让它重新成为良构代码, 用户可以直接使用 ints_def, 因为它并未指定属性类型.

当用户明确声明某个类型是某个固定的 T 时, 库不应忽略这一点. 作为 X3 的用户, 我曾被这个问题坑过, 以至于我认为 X3 对我的用途来说不是一个可行的选择. 我遇到过一个问题: X3 忽略了我的一条或多条规则的属性, 导致解析产生了错误的结果, 而我找不到任何修复办法.

当库通过泛型性提供更广泛的使用场景时, 我们通常认为这是好事. 如果它的语义过于宽松, 我们通常会说它是类型不安全的. 使用 rules 来锁定类型灵活性, 是 Boost.Parser 尝试在需要泛型性的地方启用泛型、在不需要的地方让用户将其关闭的方式之一.
