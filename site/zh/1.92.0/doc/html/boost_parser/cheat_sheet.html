速查表

此处汇集了包含各种 Boost.Parser 解析器、示例等的全部表格, 一并集中于此. 这些表格也会在本教程其他章节中重复出现.

解析器

本表列出所有 Boost.Parser 解析器. 对于可调用的解析器, 每种可能的参数数量都单独有一个条目. 对于解析器 p, 如果不存在不带参数的 p 条目, 则 p 是一个函数, 其本身不能用作解析器; 必须先调用它. 下表中:

  • 除非另有说明, 每个条目都是一个全局对象, 可直接在您的解析器中使用;
  • "码点" 用于指代输入范围的元素, 这假定解析是在支持 Unicode 的代码路径中进行的 (如果解析是在非 Unicode 代码路径中进行的, 请将 "码点" 读作 "char");
  • RESOLVE() 是一个概念性的宏, 展开为解析实参的求值结果或解析谓词的求值结果 (参见 解析器及其用途);
  • "RESOLVE(pred) == true" 是 "RESOLVE(pred) 可按语境转换为 bool 与 true" 的简写形式; false 同理;
  • c 是类型为 char、char8_t 或 char32_t 的字符;
  • str 是类型为 char const[]、char8_t const [] 或 char32_t const [] 的字符串字面量;
  • pred 是一个解析谓词;
  • arg0、arg1、arg2、... 是解析实参;
  • a 是一个语义动作;
  • r 是一个类型满足 parsable_range 的对象;
  • p、p1、p2、... 都是解析器;
  • escapes 是一个 symbols<T> 对象, 其中 T 为 char 或 char32_t.
注释

parsable_range 的定义如下:

template<typename T>
concept parsable_range = std::ranges::forward_range<T> &&
    code_unit<std::ranges::range_value_t<T>>;

repeat(arg0)[p]

当且仅当 p 恰好匹配 RESOLVE(arg0) 次时匹配.

std::string, 当 ATTR(p) 为 char 或 char32_t 时; 否则为 std::vector<ATTR(p)>

可以使用特殊值 Inf; 它表示无限重复. decltype(RESOLVE(arg0)) 必须可隐式转换为 int64_t. 无限次匹配 eps 会造成无限循环, 这在 C++ 中是未定义行为. 当遇到 repeat(Inf)[eps] 时, Boost.Parser 会在调试模式下断言失败 (这仅适用于无条件的 eps).

repeat(arg0, arg1)[p]

当且仅当 p 匹配的次数介于 RESOLVE(arg0) 与 RESOLVE(arg1) 之间 (含边界) 时匹配.

std::string, 当 ATTR(p) 为 char 或 char32_t 时; 否则为 std::vector<ATTR(p)>

上界可以使用特殊值 Inf; 它表示无限重复. decltype(RESOLVE(arg0)) 与 decltype(RESOLVE(arg1)) 都必须可隐式转换为 int64_t. 无限次匹配 eps 会造成无限循环, 这在 C++ 中是未定义行为. 当遇到 repeat(n, Inf)[eps] 时, Boost.Parser 会在调试模式下断言失败 (这仅适用于无条件的 eps).

repeat(arg0, p1)[p2]

当且仅当 p2 恰好匹配 RESOLVE(arg0) 次, 且 p1 会在 p2 的每对相邻匹配之间被匹配时. 等价于: eps (当 RESOLVE(arg0) <= 0 时), 以及 repeat(RESOLVE(arg0) - 1)[p2 >> p1] >> p2 (其他情况).

std::string, 当 ATTR(p2) 为 char 或 char32_t 时; 否则为 std::vector<ATTR(p2)>

可以使用特殊值 Inf; 它表示无限重复. decltype(RESOLVE(arg0)) 必须可隐式转换为 int64_t. 无限次匹配 eps 会造成无限循环, 这在 C++ 中是未定义行为. 当遇到 repeat(Inf)[eps] 时, Boost.Parser 会在调试模式下断言失败 (这仅适用于无条件的 eps).

repeat(arg0, arg1, p1)[p2]

当且仅当 p2 匹配的次数介于 RESOLVE(arg0) 与 RESOLVE(arg1) 之间 (含边界), 且 p1 会在 p2 的每对相邻匹配之间被匹配时. 等价于: eps (当 RESOLVE(arg1) <= 0 时), 以及 repeat(RESOLVE(arg0) - 1, RESOLVE(arg1) - 1)[p2 >> p1] >> p2 (其他情况).

std::string, 当 ATTR(p2) 为 char 或 char32_t 时; 否则为 std::vector<ATTR(p2)>

上界可以使用特殊值 Inf; 它表示无限重复. decltype(RESOLVE(arg0)) 与 decltype(RESOLVE(arg1)) 都必须可隐式转换为 int64_t. 无限次匹配 eps 会造成无限循环, 这在 C++ 中是未定义行为. 当遇到 repeat(n, Inf)[eps] 时, Boost.Parser 会在调试模式下断言失败 (这仅适用于无条件的 eps).

if_(pred)[p]

等价于 eps(pred) >> p.

ATTR(p)

写 if_(pred) 是错误的. 也就是说, 省略按条件匹配的解析器 p 是错误的.

switch_(arg0)(arg1, p1)(arg2, p2) ...

等价于 p1 (当 RESOLVE(arg0) == RESOLVE(arg1) 时), p2 (当 RESOLVE(arg0) == RESOLVE(arg2) 时), 以此类推. 如果不存在这样的 argN, 则 switch_() 的行为是未定义的.

std::variant<ATTR(p1), ATTR(p2), ...>

写 switch_(arg0) 是错误的. 也就是说, 省略按条件匹配的解析器 p1、p2、... 是错误的.

symbols<T>

symbols 是一个由键值对组成的关联容器. 每个键都是一个 std::string, 每个值的类型为 T. 在 Unicode 解析路径中, 这些字符串被视为 UTF-8 编码; 在非 Unicode 路径中, 不假定任何编码. symbols 匹配输入的最长前缀 pre, 该前缀等于键 k 之一. 如果长度 len (即 pre 的长度) 为零, 且不存在零长度的键, 则不匹配输入. 如果 len 为正, 则生成的属性是与 k 相关联的值.

T

与本表中其他条目不同, symbols 是一个类型而非对象. 在跳过器内部, 所有 symbols 都会呈现为空.

quoted_string

匹配 '"', 后跟零个或多个字符, 再后跟 '"'.

std::string

结果不包含引号. 字符串中的引号可以通过反斜杠转义来书写. 字符串中的反斜杠可以通过连续写两个反斜杠来书写. 反斜杠的其他任何用法都会导致解析失败. 在解析整个字符串期间, 跳过被禁用, 就像使用了 lexeme[] 一样.

重要

所有字符解析器, 如 char_、cp 和 cu, 产生的属性要么是 char, 要么是 char32_t. 因此, 当您在上表中看到 "std::string 当 ATTR(p) 为 char 或 char32_t 时; 否则为 std::vector<ATTR(p)>" 时, 这实际上意味着所有字符属性序列都会被转换成一个 std::string. 唯一不发生这种情况的情形是: 您引入了自己的带属性的规则且使用了其他字符类型 (或使用 attribute 来做到这一点).

重要

所有字符解析器, 如 char_、cp 和 cu, 产生的属性要么是 char, 要么是 char32_t. 因此, 当您在上表中看到 "std::string 当 ATTR(p) 为 char 或 char32_t 时; 否则为 std::vector<ATTR(p)>" 时, 这实际上意味着所有字符属性序列都会被转换成一个 std::string. 唯一不发生这种情况的情形是: 您引入了自己的带属性的规则且使用了其他字符类型 (或使用 attribute 来做到这一点).

上表未涵盖几条特殊规则:

首先, 零次或多次与一次或多次重复 (operator*() 与 operator+()) 在组合时可能发生折叠. 对于任何解析器 p, +(+p) 会折叠为 +p; **p、*+p 和 +*p 各自都会折叠为仅 *p.

其次, 在备选解析器中把 eps 用作最后一个备选项 之外 的任何备选项, 是常见的错误来源; Boost.Parser 不允许这样做. 原因在于, 对任何解析器 p 而言, eps | p 等价于 eps, 因为 eps 总是匹配成功. 对于以条件参数化的 eps 则并非如此. 对于任何条件 cond, eps(cond) 允许出现在备选解析器内的任何位置.

重要

C++ 运算符 > 与 >> 的优先级不同. 这有时会在编译器警告中出现. 无论您是否对由 > 与 >> 分隔的解析器链添加括号, 所得表达式的求值结果都是相同的. 如果编译器有抱怨, 尽可放心添加括号. 更宽泛地说, 编写解析器时请牢记 C++ 的运算符优先级规则 — 最容易写出的形式未必具有您想要的语义.

char_ 有点特殊, 因为其属性类型是多态的. 当您在非 Unicode 代码路径中使用 char_ 解析文本 (即 char 类型的字符串) 时, 属性是 char. 当您使用完全相同的 char_ 在支持 Unicode 的代码路径中解析时, 所有匹配都以码点为基础, 因此属性类型是用于表示码点的类型 char32_t. 所有对 UTF-8 的解析都属于这种情况.

这里我们解析的是普通 char, 也就是说解析处于非 Unicode 代码路径中, char_ 的属性是 char:

auto result = parse("some text", boost::parser::char_);
static_assert(std::is_same_v<decltype(result), std::optional<char>>));

解析 UTF-8 时, 匹配以码点为基础进行, 因此属性类型是 char32_t:

auto result = parse("some text" | boost::parser::as_utf8, boost::parser::char_);
static_assert(std::is_same_v<decltype(result), std::optional<char32_t>>));

好消息是, 通常您不会单独解析字符. 使用 char_ 解析时, 您通常解析的是字符的重复, 这会产生一个 std::string, 无论您是否处于 Unicode 解析模式. 如果您确实需要解析单个字符, 并且希望固定其属性类型, 可以使用 cp 和/或 cu 来强制使用非多态的属性类型.
