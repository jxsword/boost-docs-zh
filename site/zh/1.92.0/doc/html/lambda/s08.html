Boost Function

有时把 lambda 仿函数存入变量会很方便. 然而, 即使是最简单的 lambda 仿函数, 其类型也很冗长难用, 一般来说用 lambda 仿函数类型声明变量是不可行的. Boost Function 库 [function] 为任意函数对象 (例如 lambda 仿函数) 定义了包装器, 而且这些包装器的类型容易写出. 例如:

boost::function<int(int, int)> f = _1 + _2;
boost::function<int&(int&)> g = (_1 += 10);
int i = 1, j = 2;
f(i, j); // returns 3
g(i);    // sets i to = 11;

被包装函数对象的返回类型和参数类型必须显式地写成包装器模板 boost::function的模板实参; 即使被包装的是本来具有泛型参数的 lambda 仿函数也是如此. 用 boost::function 包装函数对象会带来可与虚函数分派相比的性能开销, 尽管实际上并未使用虚函数. 注意, 把 lambda 仿函数存入 boost::function 会引入危险. 某些类型的 lambda 仿函数可能存储对绑定实参的引用, 而不是对 lambda 表达式实参取副本. 当临时 lambda 仿函数对象用于 STL 算法调用时, 这总是安全的, 因为 lambda 仿函数会在 STL 算法调用完成后立即析构. 然而, 包在 boost::function 里的 lambda 仿函数可能存活得更久, 从而产生悬垂引用的可能. 例如:

int* sum = new int();
*sum = 0;
boost::function<int&(int)> counter = *sum += _1;
counter(5); // ok, *sum = 5;
delete sum; 
counter(3); // error, *sum does not exist anymore

Boost Bind

绑定表达式的第一个实参

The Boost Bind [bind] 库与 BLL 的功能部分重叠. 基本上, Boost Bind 库 (下文简称 BB) 实现的是 BLL 的绑定表达式部分. 不过, 两者存在一些语义差异.

BLL 和 BB 是分别演化的, 实现不同. 这意味着 BB 的绑定表达式不能用在 BLL 的绑定表达式中, 也不能用在 BLL 其他类型的 lambda 表达式中. 在 BB 中使用 BLL 的绑定表达式同样如此. 不过两个库可以共存, 因为 BB 库的名字位于 boost 命名空间, 而 BLL 的名字位于 boost::lambda 命名空间.

BLL 要求编译器相当符合 C++ 标准, 而 BB 库可移植性更好, 可在更大的一组编译器上工作.

下面两节描述 BB 与 BLL 中绑定表达式之间的语义差异.

绑定表达式的第一个实参

在 BB 中, 绑定表达式的第一个实参——目标函数——被区别对待, 因为不会在该实参内进行实参替换. 在 BLL 中, 第一个实参在这方面并非特殊情况. 例如: 
template<class F>
int foo(const F& f) {
  int x;
  ..
  bind(f, _1)(x);
  ...
}

int bar(int, int);
nested(bind(bar, 1, _1));
中 foo 内的绑定表达式变成: 
bind(bind(bar, 1, _1), _1)(x)
BLL 把它解释为: 
bar(1, x)(x)
而 BB 库解释为: 
bar(1, x)
要在 BLL 中获得这一功能, 可以把 foo 函数内的绑定表达式写成: 
bind(unlambda(f), _1)(x);
, 如 "Unlambda"一节所解释.

BB 库支持最多九个占位符, 而 BLL 只定义三个占位符. 不提供更多占位符的理由是: 任何 STL 算法接受的函数对象的最高元数是二. 在 BB 库中增加占位符数量很容易. 在 BLL 中也可以, 但更费力. BLL 目前在内部把实际实参原样传给 lambda 仿函数, 不把它们包在 tuple 对象里. 原因是一些广泛使用的编译器无法把中间 tuple 对象优化掉. 创建中间 tuple 会导致显著的性能损失, 尤其对最简单 (因此也最常见) 的 lambda 仿函数而言. 我们正在研究一种混合方法, 它将允许更多占位符, 同时不损害简单 lambda 仿函数的性能.
