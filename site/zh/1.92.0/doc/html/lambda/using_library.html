本节的目的在于介绍本库的基本功能. 有相当多的例外和特殊情况, 但对它们的讨论推迟到后面的各节.

入门示例

在本节中, 我们给出在 STL 算法调用中使用 BLL lambda 表达式的基本示例. 我们从一些简单的表达式开始并逐步深入. 首先, 我们把容器 (比如 list) 的元素初始化为值 1:

list<int> v(10);
for_each(v.begin(), v.end(), _1 = 1);

表达式 _1 = 1 创建一个 lambda 仿函数, 它把值 1 赋给 v中的每个元素. [6]

接下来, 我们创建一个指针容器, 并让它们指向第一个容器 v的元素:

vector<int*> vp(10); 
transform(v.begin(), v.end(), vp.begin(), &_1);

表达式 &_1 创建一个函数对象, 用于取得 v中每个元素的地址. 这些地址被赋给 vp中对应的元素.

下一段代码改变 v中的值. 对每个元素, 调用函数 foo . 元素的原始值作为实参传给 foo. foo 的结果被赋回该元素:

int foo(int);
for_each(v.begin(), v.end(), _1 = bind(foo, _1));

下一步是对 vp的元素排序:

sort(vp.begin(), vp.end(), *_1 > *_2);

在这个对 sort的调用中, 我们按元素内容以降序排序.

最后, 下面的 for_each 调用输出 vp 排好序的内容, 以换行分隔:

for_each(vp.begin(), vp.end(), cout << *_1 << '\n');

注意, 作为 lambda 表达式子表达式的普通 (非 lambda) 表达式会被立即求值. 这可能引起意外. 例如, 如果把前面的例子改写成

for_each(vp.begin(), vp.end(), cout << '\n' << *_1);

子表达式 cout << '\n' 会被立即求值, 效果是输出单个换行, 随后输出 vp的元素. BLL 提供函数 constant 以及 var 分别把常量和变量转换为 lambda 表达式, 可用于阻止子表达式被立即求值:

for_each(vp.begin(), vp.end(), cout << constant('\n') << *_1);

这些函数在 "延迟常量与变量"一节中有更详尽的描述

lambda 仿函数的参数与返回类型

在 lambda 仿函数的调用过程中, 实际实参被替换到占位符上. 占位符并不规定这些实际实参的类型. 基本规则是: lambda 函数可以用任何类型的实参调用, 只要完成替换后的 lambda 表达式是合法的 C++ 表达式. 举例来说, 表达式 _1 + _2 创建一个二元 lambda 仿函数. 它可以用任何类型 A 以及 B 的两个对象来调用, 只要对它们定义了 operator+(A,B) (并且 BLL 知道该运算符的返回类型, 见下文) .

C++ 缺少查询表达式类型的机制. 然而, 这一精确机制对实现 C++ lambda 表达式至关重要. 因此, BLL 包含一个稍显复杂的类型推导系统, 它使用一组特征类来推导 lambda 函数的结果类型. 它能处理操作数为内建类型的表达式, 以及许多操作数为标准库类型的表达式. 许多用户自定义类型也被覆盖, 特别是当用户自定义运算符在定义返回类型时遵循常规约定的情况下.

不过, 存在返回类型无法推导的情况. 例如, 假设你定义了:

C operator+(A, B);

下面的 lambda 函数调用会失败, 因为返回类型无法推导:

A a; B b; (_1 + _2)(a, b);

对此有两种可选的解决方案. 第一种是扩展 BLL 类型推导系统以覆盖你自己的类型 (参见 "扩展返回类型推导系统"一节) . 第二种是使用一种特殊的 lambda 表达式 (ret) , 它在原地定义返回类型 (参见 "覆盖推导出的返回类型"一节) :

A a; B b; ret<C>(_1 + _2)(a, b);

对于绑定表达式, 返回类型也可以定义为 bind 函数的模板实参:

bind<int>(foo, _1, _2);

关于 lambda 仿函数的实际实参

对实际实参的一个普遍限制是它们不能是非 const 右值. 例如:

int i = 1; int j = 2; 
(_1 + _2)(i, j); // ok
(_1 + _2)(1, 2); // error (!)

这一限制并不像看上去那么糟. 由于 lambda 仿函数最常在 STL 算法内部被调用, 实参来自对迭代器的解引用, 而解引用运算符很少返回右值. 即便它们返回右值, "右值作为 lambda 仿函数的实际实参"一节中也讨论了一些应对办法.

在 lambda 函数中存储绑定实参

默认情况下, 绑定实参的临时 const 副本被存储在 lambda 仿函数中. 这意味着绑定实参的值在 lambda 函数创建时即被固定, 并在 lambda 函数对象的生命期内保持不变. 例如:

int i = 1;
(_1 = 2, _1 + i)(i);

逗号运算符被重载以把 lambda 表达式组合成序列; 所得的一元 lambda 仿函数先把 2 赋给其实参, 再把 i 的值加上. 最后一行表达式的值是 3, 而不是 4. 换句话说, 创建出的 lambda 表达式是 lambda x.(x = 2, x + 1) 而非 lambda x.(x = 2, x + i).

如前所述, 这是默认行为, 但也存在例外. 确切规则如下:

  • 程序员可以用 ref 以及 cref 包装器 [ref]控制存储机制. 用 ref或 cref包装实参会指示库分别以引用或 const 引用存储该实参. 例如, 如果我们重写前一个例子, 把变量 i 用 ref包装, 我们创建的 lambda 表达式是 lambda x.(x = 2, x + i) , 最后一行表达式的值将是 4:

    i = 1;
(_1 = 2, _1 + ref(i))(i);

    注意, ref 和 cref 不同于 var 以及 constant. 后者创建 lambda 仿函数, 前者则不会. 例如:

    int i; 
var(i) = 1; // ok
ref(i) = 1; // not ok, ref(i) is not a lambda functor

    函数 ref 以及 cref 的存在主要是历史原因, ref 总是可以用 var替代, cref 可以用 constant_ref替代. 详情参见 "延迟常量与变量"一节 . 函数 ref 和 cref 是 Boost 中的通用实用函数, 因此直接定义在 boost 命名空间中.

  • 数组类型无法被复制, 因此默认以 const 引用存储.

  • 对某些表达式来说, 把实参存储为引用更合理. 例如, lambda 表达式 i += _1 的明显意图是: 对 lambda 仿函数的调用影响变量 i的值, 而不是其某个临时副本的值. 再举一例, 流运算符把最左边的实参作为非 const 引用接受. 确切规则如下:

    • 复合赋值运算符 (+=、 *=等) 的左实参以非 const 引用存储.

    • 如果 << 或者 >> 运算符的左实参派生自 basic_ostream 的实例化 (或分别派生自 basic_istream) , 该实参以非 const 引用存储. 对所有其他类型, 实参以副本存储.

    • 在指针算术表达式中, 非 const 数组类型以非 const 引用存储. 这是为了防止指针算术把非 const 数组变成 const.


[6] 严格来说, C++ 标准把 for_each 定义为 非修改序列操作 (non-modifying sequence operation) , 传给 for_each 的函数对象不应修改其实参. for_each 对实参的要求过于严格, 因为只要迭代器是 可变的 (mutable) , for_each 就接受可以对其实参产生副作用的函数对象. 尽管如此, 提供另一个具有std::for_each 功能、但对实参要求更细粒度的函数模板是直截了当的.
