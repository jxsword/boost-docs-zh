有关什么是解析器的解释, 请参阅 解析器 一节 (见 参考).

解析器的输入

解析器接受一个 string 作为输入, 它为模板元程序表示一个字符串. 例如, 字符串 "Hello World!" 可以按如下方式定义:

string<'H','e','l','l','o',' ','W','o','r','l','d','!'>

这种语法使解析器的输入难以阅读. Metaparse 可以在使用 C++98 的编译器下工作, 但解析器的输入必须按上面描述的方式定义.

基于 constexpr (C++11 提供的一项特性), Metaparse 提供了一个用于定义字符串的宏 BOOST_METAPARSE_STRING:

BOOST_METAPARSE_STRING("Hello World!")

这同样定义了一个 string , 不过它更易读. 用这种方式可定义的字符串最大长度是受限的, 但这个限制是可配置的. 它由 BOOST_METAPARSE_LIMIT_STRING_SIZE 宏指定.

源位置

源位置用一个编译期数据结构描述. 以下函数可用于查询它:

  • get_col
  • get_line

输入的开头是 start , 它要求包含 <boost/metaparse/start.hpp>.

错误处理

错误用一个编译期数据结构描述. 它包含检测到错误时的源位置信息, 以及关于该错误的一些描述 信息. debug_parsing_error 可用于显示错误消息. Metaparse 提供了 BOOST_METAPARSE_DEFINE_ERROR 宏, 用于定义简单的 解析错误消息 .

简单解析器的一些示例

  • 一个什么都不解析、总是成功的解析器是 return_.
  • 总是失败的解析器是 fail.
  • 解析一个字符并返回被解析字符作为结果的解析器是 one_char.

组合解析器

复杂解析器可以通过组合简单解析器来构建. 解析器库包含许多解析器组合子, 用于从已有解析器构建新解析器.

accept_when<Parser, Predicate, RejectErrorMsg> 是一个解析器. 它用 Parser 解析输入. 当 Parser 拒绝输入时, 该组合子返回 Parser 失败时产生的错误. 当 Parser 成功时, 该组合子会用 Predicate 校验结果. 如果谓词返回真, 组合子接受输入; 否则它会生成一条错误, 消息为 RejectErrorMsg.

有了 accept_when , one_char 可以用来构建只接受数字字符、只接受空白字符等的解析器. 例如 digit 只接受数字字符:

typedef
  boost::metaparse::accept_when<
    boost::metaparse::one_char,
    boost::metaparse::util::is_digit,
    boost::metaparse::errors::digit_expected
  >
  digit;

序列

成功解析的结果是一个值以及未解析的剩余字符串. 剩余字符串可以交给另一个解析器处理. 解析器库提供了一个解析器组合子 sequence , 它接受若干解析器作为实参, 并由它们构建一个新解析器, 该解析器:

  • 用第一个解析器解析输入
  • 如果解析成功, 它用第二个解析器解析剩余字符串
  • 只要解析器成功, 它就继续按顺序应用各解析器
  • 如果它们全部成功, 它返回结果列表
  • 如果任何一个解析器失败, 该组合子也随之失败, 并返回第一个失败的解析器所产生的错误

找到合适的折叠解析器组合子

解析未知长度的列表是很常见的需求. 举个例子, 我们从简单的东西开始: 文本是一个数字列表. 例如:

11 13 3 21

我们希望解析结果是这些值的和. Metaparse 提供了 int_ 解析器, 可以用它解析其中一个数字. Metaparse 还提供了 token 组合子来消耗数字后面的空白字符. 因此, 下面的解析器解析一个数字及其后的空白字符:

using int_token = token<int_>;

解析的结果是一个装箱整数值: 即被解析数字的值. 例如, 解析 BOOST_METAPARSE_STRING("13 ") 会得到 boost::mpl::int_<13> 作为结果.

这张图展示了反复应用 int_token 可以解析示例输入. Metaparse 提供了 repeated 解析器, 可以轻松实现这一点. 解析结果是一个 typelist: 即各个数字组成的列表.

这张图展示了 repeated<int_token> 的工作方式. 它反复使用 int_token 解析器, 并用它提供的结果构建一个 boost::mpl::vector .

但我们需要的这些值的和, 所以需要对结果求和. 为此, 我们可以把解析器 repeated<int_token> 用 transform 加以包装. 这让我们有机会指定一个函数, 把这个 typelist 转换为其他某个值 —— 在我们的例子中就是元素的和. 暂且不管如何对 vector 中的元素求和. 我们假定它可以用一个 lambda 表达式实现, 并用 boost::mpl::lambda<...>::type 来表示该 lambda 表达式. 下面是一个使用 transform 与这个 lambda 表达式的示例:

using sum_parser =
  transform<
    repeated<int_token>,
    boost::mpl::lambda<...>::type
  >;

transform<> 解析器组合子把 repeated<int_token> 包装起来, 构建出我们需要的解析器. 下面是一张展示其工作方式的图:

transform<repeated<int_token>, ...> 解析器用 repeated<int_token> 解析输入, 然后对解析结果做一些处理.

transform 如何转换来自 repeated<int_token> 的结果. 我们可以用 Boost.MPL 的 fold 或 accumulate . 下面是一个这样做的示例:

using sum_op = mpl::lambda<mpl::plus<mpl::_1, mpl::_2>>::type;

using sum_parser =
  transform<
    repeated<int_token>,
    mpl::lambda<
      mpl::fold<mpl::_1, mpl::int_<0>, sum_op>
    >::type
  >;

这个示例解析输入, 构建数字列表, 然后遍历列表并对值求和. 它从 fold 的第二个实参 int_<0> 开始, 并把数字列表 (它是解析器 repeated<int_token> 的结果) 中的每一项逐个相加.

注释

注意, transform 在这里包装了另一个解析器 repeated<int_token> . 它用那个解析器解析输入, 得到解析结果并对其进行转换. transform 本身将是一个返回更新后结果的解析器.

介绍 foldl

它能工作, 但效率相当低: 它有一个循环逐个解析整数并构建 typelist, 然后再遍历这个 typelist 对结果求和. 在应用程序中使用模板元程序可能对编译器的内存使用和编译速度产生严重影响, 因此我建议谨慎对待这些东西.

Metaparse 提供了更高效的方式来达到同样的结果. 你不需要两个循环: 可以把它们合并起来, 在解析每个数字之后立即把它加到汇总值中. Metaparse 提供了 foldl 来实现.

使用 foldl , 你要指定:

  • 用于解析列表中各个元素的解析器 (在我们的示例中是 int_token)
  • 用于折叠的初始值 (在我们的示例中是 int_<0>)
  • 把目前得到的子结果与上一次解析器应用所产生的值合并起来的前向操作 (在我们的示例中这是 sum_op)

我们的解析器可以这样实现:

using better_sum_parser = foldl<int_token, mpl::int_<0>, sum_op>;

介绍 foldl_start_with_parser

让我们改一下我们这个小语言的文法. 不再是数字列表, 而是期望由 + 符号分隔的数字. 我们的示例输入变成如下:

BOOST_METAPARSE_STRING("11 + 13 + 3 + 21")

foldl 或 repeated 来解析它是困难的: 在除+第一个 元素之外的每个元素之前都必须有一个 符号. 前面已介绍的重复构造没有一个提供以不同方式处理第一个元素的方法.

如果暂时忽略第一个数字, 输入的其余部分就是 "+ 13 + 3 + 21" 可以轻松地用 foldl (或用 repeated ) 来解析:

using plus_token = token<lit_c<'+'>>;
using plus_int = last_of<plus_token, int_token>;

using sum_parser2 = foldl<plus_int, int_<0>, sum_op>;

它使用 plus_int , 即 last_of<plus_token, int_token> , 作为反复用来获取数字的解析器. 它做以下事情:

  • 用 plus_token 解析 + 符号以及其后可能出现的空白字符.
  • 然后用 int_token 解析数字
  • 用 last_of 把上面两个组合起来, 按顺序使用两个解析器, 且只保留第二个的使用结果 (解析 + 符号的结果被丢弃 —— 我们不关心它).

这样, last_of<plus_token, int_token> 会返回数字的值作为解析结果, 与我们之前的解析器 int_token 一样. 因此, 在前面的示例中, 它可以用作 int_token 的直接替代品, 从而我们得到一个针对更新后语言的解析器. 或者说, 至少对除第一个数字之外的所有数字是如此.

foldl 无法解析第一个元素, 因为它期望每个数字之前都有一个 + 符号. 你可能想在上面这种方法中把 + 符号变为可选 —— 别这么做. 这会让解析器把 "11 + 13 3 21" 也接受下来, 因为 + 符号现在处处都是可选的.

你可以做的是: 用 int_token 解析第一个元素, 用上面基于 foldl 的方案解析其余元素, 然后把两个结果相加. 这留作读者的练习.

foldl_start_with_parser 来实现这一点. foldl_start_with_parser 与 foldl 相同. 区别在于: 它接受的不是一个用于与列表元素结合的初始值, 而是一个初始解析器:

using plus_token = token<lit_c<'+'>>;
using plus_int = last_of<plus_token, int_token>;

using sum_parser3 = foldl_start_with_parser<plus_int, int_token, sum_op>;

foldl_start_with_parser 会先应用那个初始解析器, 并把它返回的结果用作折叠的初始值. 之后它的行为与 foldl 相同. 下图展示如何用它来解析由 + 符号分隔的数字列表:

如图所示, 它从 int_token 开始解析数字列表, 并把它的值用作折叠的起始值 (之前的方案用的是值 int_<0> 作为该起始值). 然后它通过多次使用 plus_int 来解析列表的所有元素.

介绍 foldl_reject_incomplete_start_with_parser

使用用 foldl_start_with_parser 构建的解析器, 当输入正确时我们可以解析输入. 然而, 情况并非总是如此. 例如考虑以下输入:

BOOST_METAPARSE_STRING("11 + 13 + 3 + 21 +")

这是一个无效的表达式. 然而, 如果我们用先前介绍的基于 foldl_start_with_parser (即 sum_parser3 ) 的解析器来解析它, 它会接受该输入, 结果为 48 . 这是因为 foldl_start_with_parser 解析输入尽可能远 . 它先解析第一个 int_token (11), 然后开始解析 plus_int 元素 (+ 13, + 3, + 21). 在解析完所有这些之后, 它尝试用 " +" 解析剩余的 plus_int 输入, 但失败了, 因此 foldl_start_with_parser 在 + 21 之后停止.

问题在于: 解析器会从开头解析出最长的、表示有效表达式的子表达式, 其余部分被忽略. 可以用 entire_input 来包装解析器, 确保拒绝末尾带有无效多余字符的表达式, 但这不会让错误消息变得有用. (entire_input 只能告诉无效表达式的作者: 在 + 21 之后有问题).

foldl_reject_incomplete_start_with_parser , 它做的与 foldl_start_with_parser 相同, 区别在于: 一旦找不到更多重复, 它会检查重复解析器 (在我们的例子中是 ) 在哪里plus_int 失败. 当它能取得任何进展时 (例如它找到了一个 + 符号), foldl_reject_incomplete_start_with_parser 就会假定表达式的作者本想让重复更长, 但犯了错误, 并传播来自最后一个损坏表达式的错误消息.

上图展示了 foldl_reject_incomplete_start_with_parser 解析示例无效输入以及它如何失败. 这可以用于改进解析器的错误报告.

其他折叠解析器也各有其 f 版本. (例如 foldr_reject_incomplete 、 foldl_reject_incomplete1 等).

从编译期字符串能构建出什么?

用 Metaparse 构建的解析器是在编译期解析文本 (或代码) 的模板元程序. 下面列出可以作为解析"结果"的东西:

  • 一个类型 . 一个例子是: 解析 printf 格式字符串并返回期望实参的 typelist (例如 boost::mpl::vector) 的解析器.
  • 常量值 . 一个例子是计算器语言的结果. 更多细节请参阅 入门 一节.
  • 运行期对象 . 可以生成一个可能在运行期使用的静态运行期对象. 一个例子是: 在编译期解析正则表达式并构建 boost::xpressive::sregex 对象. 具体示例参见 Metaparse 的 regex 示例.
  • 函数 , 它可能在运行期被调用. 可以生成一个能在运行期调用的 C++ 函数. 这适合于从 EDSL 生成原生 (且经优化的) 代码. 具体示例参见 Metaparse 的 compile_to_native_code 示例.
  • 模板元函数类 . 解析的结果可以是一个类型, 而该类型是一个模板元函数类 . 这适合于为模板元编程构建 EDSL. 具体示例参见 Metaparse 的 meta_hs 示例.

文法

Metaparse 提供了一种以类似 EBNF 的语法定义文法的方法. grammar 模板可用于定义文法. 它可以按如下方式使用:

grammar<BOOST_METAPARSE_STRING("plus_exp")>
  ::import<BOOST_METAPARSE_STRING("int_token"), token<int_>>::type

  ::rule<BOOST_METAPARSE_STRING("ws ::= (' ' | '\n' | '\r' | '\t')*")>::type
  ::rule<BOOST_METAPARSE_STRING("plus_token ::= '+' ws"), front<_1>>::type
  ::rule<BOOST_METAPARSE_STRING("plus_exp ::= int_token (plus_token int_token)*"), plus_action>::type

上面的代码从文法定义创建了一个解析器. 文法的起始符号是 plus_exp . 以 ::rule 开头的行定义规则. 规则可以带有一个语义动作, 它是一个元函数类, 在规则被应用之后转换解析结果. 通过导入, 现有解析器可以绑定到名称并在规则中使用. 以 ::import 开头的行把现有解析器绑定到名称.

文法定义的结果是一个解析器, 它可以交给其他解析器组合子, 也可以直接使用. 鉴于文法可以导入现有解析器并构建新的解析器, 它们本身也是解析器组合子.

基于 constexpr

Metaparse 基于模板元编程, 不过 C++11 提供了 constexpr , 它同样可以用于编译期解析. 对 C++ 开发者而言, 基于 constexpr 实现解析器更容易, 因为其语法类似于语言的常规语法, 但解析结果必须是一个 constexpr 值. 基于模板元编程的解析器可以把类型作为解析结果来构建. 这些类型可以是装箱的 constexpr 值, 但也可以是元函数类、带有可在运行期调用的静态函数的类, 等等.

当用 Metaparse 构建的解析器需要一个子解析器来处理输入文本的一部分, 并生成作为解析结果的 constexpr 值时, 可以基于 constexpr 函数来实现该子解析器. Metaparse 可以与它们集成, 并把其结果提升到 C++ 模板元编程中. 在示例中可以找到一个演示此功能的示例 (constexpr_parser ). 这一能力使 Metaparse 可以与基于 constexpr 的解析库集成.

可以使用哪些类型的文法?

上下文无关文法 . 然而, 这并不是可使用的最一般的文法类别. 由于 Metaparse 是一个高度可扩展的框架, 什么应当被视为 Metaparse 本身的界限并不明确. 例如, Metaparse 提供了 accept_when 解析器组合子 . 它可用于为启用/禁用某条特定规则提供任意谓词. 甚至可以提供整个文法的图灵机 (作为一个元函数) 作为谓词, 这样就可以为能够用图灵机解析的无限制文法 构建解析器. 注意, 这样的解析器不会被算作用 Metaparse 构建的解析器, 不过一个解决方案能走多远还仍然算是使用 Metaparse, 这并不明确.

Metaparse 假定解析器是确定性的 , 因为它们只有"一个"结果. 当然, 也可以编写返回一个结果集合 (或列表或其他容器) 作为那个"一个"结果的解析器和组合子, 但那可以被视为在构建一个新的解析器库. Metaparse 没有清晰的边界.

自顶向下的解析器 , 而左递归 不受支持, 因为它会导致无限递归. 右递归 是受支持的, 不过在大多数情况下, 迭代解析器组合子 提供了更好的替代方案.
