该保证

所有实例 v (其类型为 variant<T1,T2,...,TN>) 都保证 v 具有已构造的内容, 其类型属于 Ti 之一, 即使先前对 v 的某个操作已经失败.

这意味着 variant 可以被精确地视为其 全部 有界类型的联合 (union). 这种 "永不空" 特性使用户免于出现未定义 variant 内容的可能性, 以及随之而来的显著额外使用复杂度.

实现问题

虽然 never-empty 保证 初看似乎"显而易见", 但事实上如何在一般情形下实现它 (即不对 有界类型 施加不合理地苛刻的附加要求) 甚至都不是一件直接了当的事.

核心难点出现在 variant 赋值的细节中. 给定同一具体类型的两个实例 v1 与 v2 (该类型为 variant), 对于赋值 v1 = v2, 我们必须考虑两种不同的基本情况.

首先考虑 v1 与 v2 各自包含同类型值的情形. 称该类型为 T. 此时赋值完全直接了当: 使用 T::operator=.

然而, 我们还必须考虑 v1 与 v2 包含 不同类型 值的情形. 称这些类型为 T 与 U. 此时, 由于 variant 在栈上管理其内容, 赋值的左侧 (即 v1) 必须销毁其内容, 以便允许就右侧内容 (即 v2) 进行就地拷贝构造. 最终, 虽然 v1 开始时内容类型为 T, 但结束时其内容类型为 U, 即 v2 内容的一份拷贝.

于是问题的症结在于: 若 v2 内容的拷贝构造失败, v1 如何维持其 "永不空" 保证? 当尝试从 v2 进行拷贝构造时, v1 已经销毁了它的内容!

"理想"解法: 虚假的希望

得知这一两难困境后, 聪明的人可能会提出以下方案试图解决问题:

  1. 提供一些适当对齐的"备份"存储, 能够容纳左侧所含类型的值.
  2. 把左侧存储的内存 (例如使用 memcpy) 复制到备份存储.
  3. 尝试把右侧内容拷贝到 (现已复制的) 左侧存储.
  4. 若拷贝抛出异常, 则恢复备份 (即把内存从备份存储复制回左侧存储).
  5. 否则, 若拷贝成功, 则把左侧存储的内存复制到另一块"临时"对齐存储.
  6. 现在把备份恢复 (即再次复制内存) 到左侧存储; 在"旧"内容恢复之后, 对左侧存储调用所含类型的析构函数.
  7. 最后, 把临时存储的内存复制到 (现已为空的) 左侧存储.

虽然复杂, 但这样的方案似乎能以相对高效的方式提供所需的安全性. 实际上, 本库的几个早期迭代版本正是实现了这一方案.

遗憾的是, 正如 Dave Abraham 最早指出的, 该方案会导致未定义行为:

"这段代码读起来很长, 但如果它做的是我认为它在做的事, 那么这就是未定义行为.

"诀窍是不是把现有对象的比特移入缓冲区, 以便我们可以在那块内存中试验性地构造一个新对象, 之后再把旧比特临时移回去以销毁旧对象?

"标准不允许这样做: 同一时间只能有一个对象拥有给定地址. 参见 3.8, 特别是第 4 段.

此外, 细察即可发现, 该方案有可能在并发环境中造成无法调和的竞态条件.

归根结底, 即使上述方案能在某些平台上配合特定编译器工作, 仍然需要找到一个可移植的解决方案.

初始解法: 双重存储

在得知上述方案不可行之后, Anthony Williams 在 [Wil02] 中提出了一个方案, 它成为 variant 某些预发布实现中可移植解决方案的基础.

这一方案 (下称"双重存储"方案) 的核心思想是在 variant 内部提供足够的空间, 以容纳任意有界类型的两个独立值.

有了辅助存储, 就可以在不先销毁左侧内容的情况下尝试拷贝右侧; 因此, 即使发生异常, 左侧内容仍然可用.

因此, 采用这一方案, variant 实现只需跟踪哪个存储包含内容——并据此分派所有访问 (visitation) 请求、查询等.

这一方案最明显的缺陷是带来的空间开销. 虽然在某些特殊情形下可以应用优化来消除双重存储的必要——对某些有界类型, 甚至在某些情形下完全消除 (更多细节见 "启用优化"一节)——但 Boost 邮件列表上的许多用户强烈反对使用双重存储. 特别有人指出, 双重存储的开销将始终存在——即使从未发生对 variant 的赋值. 出于这一原因及其他原因, 人们开发了一种新方案.

当前方案: 临时堆备份

尽管对双重存储方案有很多反对意见, 但人们意识到任何替代方案都不会没有缺点. 因此, 需要一种折衷.

为此, Dave Abrahams 建议在 variant 赋值的行为规范中加入以下内容: "variant 从一种类型到另一种类型的赋值可能引发动态分配." 也就是说, 虽然 variant 在构造之后以及涉及相同所含类型的赋值之后仍会 就地 存储其内容, 但在涉及不同所含类型的赋值之后, variant 会把内容存储在堆上.

赋值算法将按如下进行:

  1. 把右侧的内容拷贝构造到堆上; 称指向该数据的指针为 p.
  2. 销毁左侧的内容.
  3. 把 p 拷贝到左侧存储.

由于对指针的所有操作都不抛出异常, 该方案能让 variant 满足其 never-empty 保证.

这一方案最明显的问题是: 虽然它确实消除了双重存储的空间开销, 但它给 variant 赋值引入了动态分配的开销——不仅是初始分配的开销, 还有内容持续存储在堆上的开销. 前一个问题不可避免, 但后一个问题可以用以下"临时堆备份"技术来避免:

  1. 把 左侧的内容拷贝构造到堆上; 称指向该数据的指针为 backup.
  2. 销毁左侧的内容.
  3. 在 (现已为空的) 左侧存储中拷贝构造右侧的内容.
  4. 若失败, 把 backup 拷贝到左侧存储.
  5. 若成功, 释放 backup 所指向的数据.

采用这一技术: 1) 只使用单一存储; 2) 只有在赋值失败时, 内容才长期存于堆上; 3) 在任何 成功 的赋值之后, variant 内的存储是有保证的. 就本库的初始发布而言, 这些特性被认为是令人满意的折衷方案.

不过, 仍存在明显的不足. 特别是, 有些用户可能必须不惜一切代价避免堆分配; 另一些用户的任何分配都可能需要通过用户提供的分配器进行. 这些问题将在未来解决 (见 "未来方向: 基于策略的实现"一节). 不过目前, 本库把其内容的存储视为实现细节. 尽管如此, 如下一节所述, 用户 确实 可以做一些事情来确保 variant 实例获得最大效率 (详见 "启用优化"一节).

启用优化

如 "实现问题"一节 所述, 实现 never-empty 保证的核心困难是 variant 赋值期间拷贝构造失败的可能性. 然而, 具有不抛异常拷贝构造函数的类型显然永远不会面临这种可能性. 类似地, 若 variant 的某个有界类型可无异常默认构造, 则在拷贝构造失败时可以用这种类型作为安全的"后备"类型.

因此, 一旦其有界类型满足以下判据, variant 的设计就会启用以下优化:

  • 对于每个有界类型 T, 若其可无异常拷贝构造 (由 boost::has_nothrow_copy 指示), 本库保证 variant 对 T 只使用单一存储和就地构造.
  • 若 任何 有界类型可无异常默认构造 (由 boost::has_nothrow_constructor 指示), 本库保证 variant 对 每个 有界类型 (属于 variant) 都只使用单一存储和就地构造. 但请注意, 若赋值失败, 会在左侧操作数中默认构造某个未指定的可无异常默认构造的有界类型, 以维持 never-empty 保证.

实现注释: 为了让 variant 在异常发生后的行为更可预测, 当前实现优先默认构造 boost::blank (若它被指定为有界类型), 而不是其他可无异常默认构造的有界类型. (若这一特性被认为有用, 它将成为 variant 规范的一部分; 否则可能会被废弃. 请向 Boost 邮件列表提供反馈.)

未来方向: 基于策略的实现

如前几节所示, 人们已经投入了大量努力, 试图在性能、数据大小和堆使用之间取得平衡. 此外, variant 可以基于其有界类型的某些特征启用显著的优化.

然而, 有些用户会对所选的折衷不满意 (例如: 必须不惜一切代价避免堆分配; 若使用堆分配, 则必须使用自定义分配器; 等等). 出于这一原因, 本库的未来版本将支持基于策略的 variant 实现. 虽然这不会消除前几节所述的问题, 但它将允许由用户而不是库设计者来决定各种权衡.
