高效的多态数据结构

假设我们有一个抽象基类 base, 它有 derived1、derived2 和 derived3 几个实现类. std::vector<base*> (或类似的构造, 如 std::vector<std::unique_ptr<base>> 或 boost::ptr_vector<base>) 的内存布局如下所示:

向量中相邻的元素不一定是连续分配的, 如果向量经历过中途插入和删除, 就更加不是如此. 一个典型的处理操作

std::vector<base*> v;
...
for(base* b: v){
  ... // access base's virtual interface
}

会受到以下两个因素的负面影响:

  • 元素散布于整个内存之中会降低 CPU 缓存效率, 而 CPU 缓存通常有利于对连续内存区域的常规访问循环.
  • 分支预测 试图通过根据历史记录投机地执行某个给定分支, 来尽量减小运行条件代码 (如 if-else 语句或对 base 虚函数的调用) 所产生的影响. 当 derived1、derived2 和 derived3 元素毫无确定模式地散布于序列之中时, 这一机制便基本失效.

这些限制源于动态多态的本质: 由于通过 base 的接口所访问元素的确切类型是未知的, 因此必须借助 base* (类型擦除 的一种特定形式) 进行间接访问. 然而存在一个关键观察: 即便在遍历 std::vector<base*> 时派生类型是未知的, 该信息通常在向向量插入之点即已于编译期可知:

std::vector<base*> v;
...
v.insert(new derived2{...}); // the type derived2 is "forgotten" by v

一个经过恰当设计的容器可以利用这一信息, 按照元素的确切类型将它们连续排列, 其结果是一个内部数据结构 (实际上是一个指向 std::type_info 对象的指针映射表), 其中包含与派生类数目相同的多个向量或段 (segment):

遍历这种结构就简化为逐个循环访问所有段: 无论在缓存还是分支预测方面, 这都极为高效. 不过在这一过程中, 我们失去了 std::vector<base*> 的自由排序能力 (自由排序只能在段这一层级上保留), 但如果这对用户的应用无关紧要, 改用这种结构所能带来的潜在性能收益是巨大的.

以上讨论集中于基类/派生类编程 (也称为 OOP), 但它同样适用于其他形式的动态多态:

  • std::function 以一个共同接口来抽象具有同一给定签名的可调用实体. 其内部使用指针间接和类虚函数调用. 不过, 其内存碎片预计会低于 OOP, 因为其实现通常带有所谓的 小缓冲区优化, 以在某些情况下避免堆分配.
  • std::function 的情况可以看作是更一般的多态形式——鸭子类型 (duck typing)——的一个具体例子: 只要类型符合同一给定的接口 (一组指定的成员函数和/或操作), 不相关的类型就会被统一对待. 鸭子类型在提供 OOP 能力的同时允许更大的灵活性, 因为多态类型无需派生自某个预先存在的基类, 也无须在总体上为任何特定接口而设计——事实上, 同一个对象可以被鸭子类型化为不同的接口. 在众多库之中, Boost.TypeErasure 为 C++ 提供了鸭子类型. 在底层, 鸭子类型需要使用与 OOP 类似的指针间接和虚调用实现技术, 因此同样存在我们前面所述的高效容器数据结构的机会.
  • 封闭多态 是指可接受的类型在编译期即被指定的情形. std::variant 和 Boost.Variant2 是封闭多态的两个突出例子, 其底层类型 (称为备选类型, alternatives) 通过 访问 (visitation) 来存取. 封闭多态的典型实现不涉及动态分配 (各备选类型以 union 的方式存储于共享存储中), 但把同类型对象分组存放仍然能带来性能和空间上的优势.

Boost.PolyCollection 提供了四个不同的容器类模板, 分别用于处理 OOP、std::function 风格的多态、由 Boost.TypeErasure 实现的鸭子类型, 以及秉持 std::variant 精神的封闭多态:

  • boost::base_collection
  • boost::function_collection
  • boost::any_collection
  • boost::variant_collection

这些容器的接口大体相同, 并遵循标准库容器的惯用约定.
