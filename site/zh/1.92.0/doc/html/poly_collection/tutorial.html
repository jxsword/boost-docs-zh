boost::base_collection

(代码示例来自 basic_base.cpp.)

设想我们正在用 C++ 开发一个角色扮演游戏, 其中的精灵 (sprite) 会渲染到屏幕上; 出于说明的目的, 我们可以简单地把渲染建模为向某个 std::ostream 输出一些信息:

struct sprite
{
  sprite(int id):id{id}{}
  virtual ~sprite()=default;
  virtual void render(std::ostream& os)const=0;

  int id;
};

游戏中有战士 (warrior)、重装兵 (juggernaut, 一种特殊类型的战士) 和哥布林 (goblin), 每个都由自己的类表示, 这些类 (直接或间接地) 派生自 sprite:

struct warrior:sprite
{
  using sprite::sprite;
  warrior(std::string rank,int id):sprite{id},rank{std::move(rank)}{}

  void render(std::ostream& os)const override{os<<rank<<" "<<id;}

  std::string rank="warrior";
};

struct juggernaut:warrior
{
  juggernaut(int id):warrior{"juggernaut",id}{}
};

struct goblin:sprite
{
  using sprite::sprite;
  void render(std::ostream& os)const override{os<<"goblin "<<id;}
};

让我们用一个由各种精灵组成的组合来填充一个多态集合:

#include <boost/poly_collection/base_collection.hpp>
...

boost::base_collection<sprite> c;

std::mt19937                 gen{92748}; // some arbitrary random seed
std::discrete_distribution<> rnd{{1,1,1}};
for(int i=0;i<8;++i){        // assign each type with 1/3 probability
  switch(rnd(gen)){
    case 0: c.insert(warrior{i});break;
    case 1: c.insert(juggernaut{i});break;
    case 2: c.insert(goblin{i});break;
  }
}

这里有两点需要注意:

  • boost::base_collection 没有 push_back 成员函数, 比如说不像 std::vector 那样, 因为元素存储的顺序无法由用户代码自由选择——这一点我们稍后会进一步讨论. 其插入机制更接近于 std::unordered_multiset 之类容器的机制, 即 insert 和 emplace, 可带或不带位置提示.
  • 元素并非用 new 创建, 而是在栈上构造并直接传入, 就像使用标准非多态容器时所做的那样.
重要

插入到 boost::base_collection (或 Boost.PolyCollection 的其他容器) 中的元素必须可拷贝且可赋值; 严格说来, 它们至少必须模拟 MoveConstructible, 并且要么是 MoveAssignable, 要么在移动构造时不抛出异常. 这可能迫使你重新审视自己的代码, 因为习惯上会在虚层次结构的基类层级显式禁止拷贝以避免 切片 (slicing).

现在可以用一个简单的 for 循环遍历 c 来实现渲染:

const char* comma="";
for(const sprite& s:c){
  std::cout<<comma;
  s.render(std::cout);
  comma=",";
}
std::cout<<"\n";

输出为:

juggernaut 0,juggernaut 4,juggernaut 7,goblin 1,goblin 3,goblin 5,warrior 2,warrior 6

正如我们事先提醒的, 遍历顺序与插入顺序并不对应. 相反, 元素按其具体类型分组为段. 这里我们看到重装兵排在最前, 其后是哥布林和战士. 一般而言, 不应对段的顺序做任何假设——在你的环境中, 就这个示例本身而言段顺序可能就有所不同. 另一方面, 插入到已存在段中的元素总是位于末尾 (除非提供了提示). 例如, 用 id==8 插入一个迟到的哥布林之后:

c.insert(goblin{8});

渲染循环输出 (新元素以红色显示):

juggernaut 0,juggernaut 4,juggernaut 7,goblin 1,goblin 3,goblin 5,goblin 8,warrior 2,warrior 6

删除可以按常规方式进行:

// find element with id==7 and remove it
auto it=std::find_if(c.begin(),c.end(),[](const sprite& s){return s.id==7;});
c.erase(it);

现在渲染输出:

juggernaut 0,juggernaut 4,goblin 1,goblin 3,goblin 5,goblin 8,warrior 2,warrior 6

boost::function_collection

(代码示例来自 basic_function.cpp. 使用了 C++14 的 std::make_unique.)

在游戏开发进行到相当程度时, 产品经理要求在渲染循环中新增两类实体:

  • 叠加显示的消息, 如得分, 建模为 std::string.
  • 来自第三方库的弹出窗口, 遗憾的是它们不派生自 sprite, 并且使用自己的 display 成员函数进行渲染:
struct window
{
  window(std::string caption):caption{std::move(caption)}{}

  void display(std::ostream& os)const{os<<"["<<caption<<"]";}

  std::string caption;
};

于是我们决定重构代码, 让精灵、消息和窗口分别存储在专属容器中:

std::vector<std::unique_ptr<sprite>> sprs;
std::vector<std::string>             msgs;
std::vector<window>                  wnds;

并将我们的渲染容器定义为一个 boost::function_collection, 其元素为可调用实体——即函数指针或带有函数调用 operator() 的对象——接受 std::ostream& 作为参数

#include <boost/poly_collection/function_collection.hpp>
...

// function signature accepting std::ostream& and returning nothing
using render_callback=void(std::ostream&);

boost::function_collection<render_callback> c;

我们为 sprite、std::string 和 window 分别填入合适的适配器. Lambda 函数可以写出特别简洁的代码.

auto render_sprite(const sprite& s){
  return [&](std::ostream& os){s.render(os);};
}

auto render_message(const std::string& m){
  return [&](std::ostream& os){os<<m;};
}

auto render_window(const window& w){
  return [&](std::ostream& os){w.display(os);};
}
...

for(const auto& ps:sprs)c.insert(render_sprite(*ps));
for(const auto& m:msgs)c.insert(render_message(m));
for(const auto& w:wnds)c.insert(render_window(w));

渲染循环现在看起来像这样:

const char* comma="";
for(const auto& cbk:c){
  std::cout<<comma;
  cbk(std::cout);
  comma=",";
}
std::cout<<"\n";

对于精灵、消息和窗口的某个特定场景, 其产出如下:

juggernaut 0,goblin 1,warrior 2,goblin 3,"stamina: 10,000","game over",[pop-up 1],[pop-up 2]

我们刚创建的容器在许多方面都像 std::vector<std::function<render_callback>> 一样工作, 主要区别在于: 使用 boost::function_collection 时, 同类型的可调用实体在内存中打包在一起 [11], 从而提高性能 (这正是使用 Boost.PolyCollection 的全部意义所在); 而 std::function 的向量则会为每个存储的实体单独分配 [12]. 事实上, value_type 元素 (由 boost::function_collection 持有) 实际上并非 std::function, 尽管它们的行为类似, 并且在需要时可转换为 std::function:

auto cbk=*c.begin();
cbk(std::cout); // renders first element to std::cout
std::function<render_callback> f=cbk;
f(std::cout);   // exactly the same

这是有原因的: 多态集合的元素不能由用户随意赋值, 因为这最终可能试图把一个对象插入到不同类型的段中. 所以, 与 std::function 不同, 以下代码无法工作:

*c.begin()=render_message("last minute message"); // compile-time error

boost::any_collection

(代码示例来自 basic_any.cpp.)

注释

这里我们仅触及展示 Boost.TypeErasure 所需的最基本要点, 以便介绍 boost::any_collection. 建议读者阅读 Boost.TypeErasure 文档以了解更多信息.

在测量了最新更改的性能之后, 我们发现渲染太慢, 于是决定再次重构: 如果能把所有实体——精灵、消息和窗口——存储到一个单一容器中, 就能消除一层间接. 问题在于这些类型彼此完全无关.

Boost.TypeErasure 提供了一个类模板 boost::type_erasure::any<Concept>, 只要对象符合 Concept 所指定的接口, 它就能持有任何类型的对象. 在我们的情形中, 我们发现通过提供 operator<< 的重载来实现一个用于渲染的公共接口特别容易

std::ostream& operator<<(std::ostream& os,const sprite& s)
{
  s.render(os);
  return os;
}

// std::string already has a suitable operator<<

std::ostream& operator<<(std::ostream& os,const window& w)
{
  w.display(os);
  return os;
}

这样我们就可以用它来指定所有实体都必须遵循的接口:

#include <boost/poly_collection/any_collection.hpp>
#include <boost/type_erasure/operators.hpp>
...

using renderable=boost::type_erasure::ostreamable<>;
boost::any_collection<renderable> c;

刚创建的集合欣然接受插入异构实体 (因为接口符合性在编译期被静默检查)

// populate with sprites
std::mt19937                 gen{92748}; // some arbitrary random seed
std::discrete_distribution<> rnd{{1,1,1}};
for(int i=0;i<4;++i){        // assign each type with 1/3 probability
  switch(rnd(gen)){
    case 0: c.insert(warrior{i});break;
    case 1: c.insert(juggernaut{i});break;
    case 2: c.insert(goblin{i});break;
  }
}

// populate with messages
c.insert(std::string{"\"stamina: 10,000\""});
c.insert(std::string{"\"game over\""});

// populate with windows
c.insert(window{"pop-up 1"});
c.insert(window{"pop-up 2"});

渲染于是变为

const char* comma="";
for(const auto& r:c){
  std::cout<<comma<<r;
  comma=",";
}
std::cout<<"\n";

输出为

[pop-up 1],[pop-up 2],juggernaut 0,goblin 1,goblin 3,warrior 2,"stamina: 10,000","game over"

与 boost::function_collection 的情况一样, 此容器类似于 std::vector<boost::type_erasure::any<Concept>>, 但由于同类型元素的打包而具有更好的性能. 此外, value_type (就 boost::any_collection<Concept> 而言) 并非 boost::type_erasure::any<Concept>, 而是一个行为类似的实体 [13]. 无论如何, 我们不再通过抽象的 sprite& 访问精灵, 因此原则上我们可以拆除虚层次结构, 并让每个类型自主实现: 这留作读者的练习.

boost::variant_collection

(代码示例来自 basic_variant.cpp. overloaded 工具使用了 C++17.)

既然此时我们已有这样一个由无关类型组成的异构列表, 不妨在编译期指定它们:

#include <boost/poly_collection/variant_collection.hpp>
...

boost::variant_collection<
  boost::mp11::mp_list<warrior,juggernaut,goblin,elf,std::string,window>
> c;

需要 boost::mp11::mp_list 来在语法上区分进入集合的类型与随后的 (默认的) 分配器实参. 如果未指定特殊分配器, 别名模板 variant_collection_of 提供了稍微更便利的语法:

boost::variant_collection_of<
  warrior,juggernaut,goblin,elf,std::string,window
> c;

boost::variant_collection 的行为如同 std::vector, 其元素为 std::variant, 区别在于同类型的对象被分组在一起. 对对象的访问通过访问 (visitation) 完成:

// usual utility to construct a visitor
template<typename... Ts>
struct overloaded:Ts...{using Ts::operator()...;};
template<class... Ts>
overloaded(Ts...)->overloaded<Ts...>;

const char* comma="";
for(const auto& r:c){
  std::cout<<comma;
  visit(overloaded{
    [](const sprite& s)       { s.render(std::cout); },
    [](const std::string& str){ std::cout<<str; },
    [](const window& w)       { w.display(std::cout); }
  },r);
  comma=",";
}
std::cout<<"\n";

输出:

warrior 1,warrior 4,juggernaut 2,goblin 0,elf 3,"stamina: 10,000","game over",[pop-up 1],[pop-up 2]

备选的访问函数 visit_by_index 可能更方便, 因为它不要求我们构建重载的访问器:

auto print_sprite=[](const sprite& s)       { s.render(std::cout); };
auto print_string=[](const std::string& str){ std::cout<<str; };
auto print_window=[](const window& w)       { w.display(std::cout); };

const char* comma="";
for(const auto& r:c){
  std::cout<<comma;
  visit_by_index(
    r,
    print_sprite,  // type #0: warrior
    print_sprite,  // type #1: juggernaut
    print_sprite,  // type #2: goblin
    print_sprite,  // type #3: elf
    print_string,  // type #4
    print_window); // type #5
  comma=",";
}
std::cout<<"\n";

注意, 类型按指定的精确顺序遍历. value_type (属于 boost::variant_collection<boost::mp11:mp_list<Ts..>>) 的行为如同 std::variant<Ts..>, 但带有一些明显的限制, 例如无法更改所含对象的类型 (例如, 不提供等价于 std::variant::emplace 的功能).

类型注册

回到我们的 boost::base_collection 示例, 假设我们想按如下方式重构填充代码:

std::unique_ptr<sprite> make_sprite()
{
  static std::mt19937                 gen{92748};
  static std::discrete_distribution<> rnd{{1,1,1}};
  static int                          id=0;

  switch(rnd(gen)){
    case 0: return std::make_unique<warrior>(id++);break;
    case 1: return std::make_unique<juggernaut>(id++);break;
    case 2: return std::make_unique<goblin>(id++);break;
  }
}
...

for(int i=0;i<8;++i)c.insert(*make_sprite());
// throws boost::poly_collection::unregistered_type

出乎意料的是, 这段代码抛出了一个 boost::poly_collection::unregistered_type 类型的异常. 与最初的代码相比, 什么改变了?

假设一个 warrior 已由 make_sprite 创建. 语句 c.insert(*make_sprite()) 把该对象作为 sprite& 传入: 尽管 boost::base_collection 足够聪明, 能知道该对象实际上派生自 sprite (通过使用 typeid()) 且应当避免 切片 (slicing), 但若不访问类型 warrior——这一访问须在编译期进行——以便实例化相应的内部类模板, 就无法为它创建段 [14]. 在重构前的代码中不会发生这种情况, 因为对象是以其真实类型的引用传入的.

如果为某个类型创建了一个 (可能为空的) 段, 则称该类型已被注册到多态集合中. 可以用以下方式检查:

std::cout<<c.is_registered<warrior>()<<"\n";       // prints 0
std::cout<<c.is_registered(typeid(warrior))<<"\n"; // alternate syntax

当对象以其真实类型的引用传入或被 emplace 时, 注册会自动发生; 也可以通过 register_types 显式注册:

c.register_types<warrior,juggernaut,goblin>();
// everything works fine now
for(int i=0;i<8;++i)c.insert(*make_sprite());

一旦 T 被注册到多态集合中, 无论是否存储了 T 类型的对象, 它都会保持注册状态, 除非集合被移动、被赋值或被交换.

由于切片主要是 OOP 的问题, 预计 unregistered_type 异常在使用 boost::function_collection 和 boost::any_collection 时会少见得多. 不过也能找到牵强的例子:

boost::any_collection<renderable> c1,c2;
... // populate c2

c1.insert(*c2.begin()); // throws: actual type of *c2.begin() not known by c1
注释

boost::variant_collection 以不同的方式处理类型注册: 由于可接受类型在编译期即被指定, 其关联的段会在集合构造时自动创建; 因此, 不提供 is_registered 和 register_types.

段专属接口

对于多态集合接口的大部分内容, 可以只通过提供元素的类型或 typeid() 来引用给定段的元素. 例如:

... // populate c with 8 assorted entities

std::cout<<c.size()<<"\n";                    // 8 sprites
std::cout<<c.size<juggernaut>()<<"\n";        // 2 juggernauts
std::cout<<c.size(typeid(juggernaut))<<"\n";  // alternate syntax
c.clear<juggernaut>();                        // remove juggenauts only
std::cout<<c.empty<juggernaut>()<<"\n";       // 1 (no juggernauts left)
std::cout<<c.size()<<"\n";                    // 6 sprites remaining

注意, 若类型未注册, 其中任何一种 (reserve 除外) 都会抛出 boost::poly_collection::unregistered_type. 在 boost::variant_collection 的情况下, 我们使用该类型的索引号而非 typeid():

boost::variant_collection<
  boost::mp11::mp_list<warrior,juggernaut,goblin,elf,std::string,window>
> c3;
... // populate c3 some entities

std::cout<<c3.size<warrior>()<<"\n"; // same as with other collections
std::cout<<c3.size(0)<<"\n";         // list number of warriors (type #0 in the list of types)

段专属寻址还包括遍历:

局部迭代器

以下代码只在集合的 warrior 之上运行:

const char* comma="";
for(auto first=c.begin(typeid(warrior)),last=c.end(typeid(warrior));
    first!=last;++first){
  std::cout<<comma;
  first->render(std::cout);
  comma=",";
}
std::cout<<"\n";

输出:

warrior 2,warrior 6

begin|end(typeid(T)) 返回 local_base_iterator 类型的对象, 关联到 T 的段. 这些迭代器解引用得到的值与常规迭代器相同 (对于 boost::base_collection<base>, 即 base&), 但只能用于遍历给定的段 (例如, 来自不同段的 local_base_iterator 之间不能相互比较). 作为交换, local_base_iterator 是 RandomAccessIterator, 而整集合迭代器只模拟 ForwardIterator.

基于范围的 for 循环配合便利的 segment 成员函数可以写得更简洁:

const char* comma="";
for(const auto& x:c.segment(typeid(warrior))){
  std::cout<<comma;
  x.render(std::cout);
  comma=",";
}
std::cout<<"\n";

比 local_base_iterator 更强大的是 local_iterator<T>:

const char* comma="";
for(auto first=c.begin<warrior>(),last=c.end<warrior>();
    first!=last;++first){
  first->rank.insert(0,"super");
  std::cout<<comma;
  first->render(std::cout);
  comma=",";
}
std::cout<<"\n";

// range-based for loop alternative

const char* comma="";
for(auto& x:c.segment<warrior>()){
  x.rank.insert(0,"super");
  std::cout<<comma;
  x.render(std::cout);
  comma=",";
}
std::cout<<"\n";

这会追加一个 "super" 前缀到现有战士的 rank 数据成员:

superwarrior 2,superwarrior 6

细心的读者会注意到, 为了访问 rank——它是 warrior 的成员而非其基类 sprite 的成员——first (或 x, 在 range for 循环版本中) 必须引用一个 warrior&, 而这正是 local_iterator<warrior> (由 begin<warrior>() 返回的类型) 与 local_base_iterator 之间的区别. local_iterator<warrior> 也是一个 RandomAccessIterator: 在大多数方面, [begin<T>(), end<T>()) 可以看作是一个 T 对象数组上的范围. local_iterator<T> 可显式转换为 local_base_iterator. 反过来, 若一个 local_base_iterator 关联到 T 的段, 则它可显式转换为 local_iterator<T> (否则该转换是未定义行为).

local_iterator<T> 直接引用一个 T 对象这一事实, 在我们使用 boost::variant_collection 时更为明显:

// traverse all windows in our variant_collection

for(auto& x:c3.segment<window>()){
  // visitation not required: we're accessing window directly
  x.display(std::cout);
}

该图显示与多态集合关联的所有迭代器的作用范围 (不包括 const_ 版本):

图中底部部分我们尚未描述. segment(typeid(T)) 用于遍历特定段的元素, 而 segment_traversal() 返回一个用于遍历段的对象, 这样整个集合就可以用如下嵌套的段-元素 for 循环来处理:

const char* comma="";
for(auto seg:c.segment_traversal()){
  for(sprite& s:seg){
    std::cout<<comma;
    s.render(std::cout);
    comma=",";
  }
}
std::cout<<"\n";

遍历循环的段分解构成了 提升性能的算法 的基础.

Reserve

与 std::vector 很相似, 可以让段预先保留内存以尽量减少重新分配:

c.reserve<goblin>(100); // no reallocation till we exceed 100 goblins
std::cout<<c.capacity<goblin>()<<"\n"; // prints 100

若所指示类型 (此处为 goblin) 没有段, 则会自动创建一个. 这与其他段专属成员函数形成对比, 后者会抛出 boost::poly_collection::unregistered_type.

reserve 可以一次性处理所有段. 以下代码

c.reserve(1000); // reserve(1000) for each segment
std::cout<<c.capacity<warrior>()<<", "
         <<c.capacity<juggernaut>()<<", "
         <<c.capacity<goblin>()<<"\n"; // prints 1000, 1000, 1000

指示每个现有段预留 1,000 个元素. 如果段是稍后创建的 (通过元素插入或 类型注册), 其容量将会不同.

注释

与标准容器不同, 不提供集合级的 capacity() 和 max_size(), 因为其惯常语义无法应用于 Boost.PolyCollection: 例如, capacity() 通常用于检查在不重新分配的情况下可以插入多少元素, 但在分段结构中, 这取决于元素的确切类型以及它们是否已注册.

插入与原地构造

(代码示例来自 insertion_emplacement.cpp.)

我们已经知道, insert(x) 在没有进一步位置信息时, 会把 x 存储到其关联段的末尾. 当提供了常规迭代器 it 时, 若 it 和 x 属于同一个段, 插入会发生在所指示的位置; 否则, it 会被忽略. 例如, 若我们的精灵集合有以下实体:

juggernaut 0,juggernaut 4,juggernaut 7,goblin 1,goblin 3,goblin 5,warrior 2,warrior 6

那么以下代码:

c.insert(c.begin(),juggernaut{8});

会把新的 juggernaut 放在开头:

juggernaut 8,juggernaut 0,juggernaut 4,juggernaut 7,goblin 1,...

而以下代码中的位置提示

c.insert(c.begin(),goblin{9});

会被忽略, 新的 goblin 将被插入到其段的末尾:

juggernaut 8,...,juggernaut 7,goblin 1,goblin 3,goblin 5,goblin 9,warrior 2,...

也可以使用 局部迭代器 来指示插入位置:

c.insert(c.begin<juggernaut>()+2,juggernaut{10});
                           // ^^ remember local iterators are random access

juggernaut 8,juggernaut 0,juggernaut 10,juggernaut 4,juggernaut 7,goblin 1,...

不过有一个注意事项: 使用局部迭代器时, 插入的元素必须属于所指示的段:

c.insert(c.begin(typeid(warrior)),juggernaut{11}); // undefined behavior!!

为范围插入提供了成员函数, 分为带位置提示和不带位置提示两种:

boost::base_collection<sprite> c2;

c2.insert(c.begin(),c.end()); // read below

// add some more warriors
std::array<warrior,3> aw={{11,12,13}};
c2.insert(aw.begin(),aw.end());

// add some goblins at the beginning of their segment
std::array<goblin,3> ag={{14,15,16}};
c2.insert(c2.begin<goblin>(),ag.begin(),ag.end());

正如前面已经解释过的, 如果类型不是以其真实类型的引用传入, 就必须注意将其预先注册到集合中. 那么, 为什么下面这一行

c2.insert(c.begin(),c.end());

没有抛出 boost::poly_collection::unregistered_type? 碰巧的是, 在插入的范围属于同一类型的多态集合这一特殊情况下, 注册会自动完成 [15].

对于 Boost.PolyCollection 而言, 原地构造 (emplacement) 与标准容器略有不同. 考虑以下尝试原地构造一个 goblin 的代码:

c.emplace(11); // does not compile

如果仔细审视, 上面这段代码无法编译是很自然的: Boost.PolyCollection 不可能知道我们想原地构造的恰好是一个 goblin, 而不是某个可以从 int 构造的其他类型 (如 warrior、juggernaut 或某个无关的类). 因此, 必须显式指定被原地构造元素的类型:

c.emplace<goblin>(11); // now it works

与 insert 一样, 原地构造时也可以指示一个位置:

c.emplace_hint<juggernaut>(c.begin(),12); // at the beginning if possible
c.emplace_pos<goblin>(c.begin<goblin>()+2,13); // amidst the goblins
c.emplace_pos<warrior>(c.begin(typeid(warrior)),14); // local_base_iterator

注意这里的命名: 当位置用常规迭代器指示时使用 emplace_hint, 而对于局部迭代器则使用 emplace_pos.

异常

(代码示例来自 exceptions.cpp.)

除了 std::bad_alloc 之类的常规异常以及用户提供的类型所产生的异常之外, 多态集合还可能抛出以下异常:

  • boost::poly_collection::unregistered_type
  • boost::poly_collection::not_copy_constructible
  • boost::poly_collection::not_equality_comparable

引发第一种异常的情形已在前面讨论过; 让我们把注意力放在另外两种上.

我们的游戏中有一类新的精灵, 由不可拷贝的类 elf 定义:

struct elf:sprite
{
  using sprite::sprite;
  elf(const elf&)=delete; // not copyable
  elf(elf&&)=default;     // but moveable
  void render(std::ostream& os)const override{os<<"elf "<<id;}
};

我们毫无问题地使用它, 直到写出以下代码:

c.insert(elf{0}); // no problem
...

c2=c; // throws boost::poly_collection::not_copy_constructible

第一次插入能成功, 因为传入的 elf 对象是临时对象, 可以被移动进容器; 但第二条语句实际上需要拷贝 elf 元素 (位于 c 中) 到 c2, 于是抛出了异常.

这种行为可能令人意外之处在于, 标准容器会以编译期失败的方式报告这类问题. 在这里我们无法享受这种便利, 因为多态集合所含的确切类型要到运行期才能知道 (例如, 若 elf 元素在把 c 拷贝到 c2 之前已被擦除, 那么一切本可以正常工作): 从根本上说, 把错误从编译期推迟到运行期是动态多态的固有特征.

同理, 相等比较要求元素本身可进行相等比较:

c.clear<elf>(); // get rid of non-copyable elfs
c2=c;           // now it works
// check that the two are indeed equal
std::cout<<(c==c2)<<"\n";
                // throws boost::poly_collection::not_equality_comparable

一旦注意到我们没有定义 operator== (用于任何 sprite), 上面的内容就不足为奇了. 然而, 这个问题可能长时间不被察觉, 因为判定两个多态集合相等 (即其所有非空段都相等) 可以在不比较任何东西的情况下返回 false (例如, 若段大小不同), 此时不会抛出异常.

注释

不提供用于 <、<=、> 和 >= 比较的运算符, 因为段顺序不是固定的, 在其他方面完全相同的集合之间也可能不同. 这种情况类似于标准 无序关联容器.

这三种就是 Boost.PolyCollection 抛出的全部内在异常. 其含义是: 如果一个类型是 CopyConstructible、MoveAssignable (或移动构造不抛出异常) 且 EqualityComparable, 那么 Boost.PolyCollection 的整个接口都可以无限制地用于它 [16].

算法

类型恢复

(代码示例来自 algorithms.cpp. 使用了 C++14 泛型 lambda 表达式. overloaded 工具使用了 C++17.)

Boost.PolyCollection 的根本目的在于加速对大量多态实体的处理, 尤其是那些涉及以 for 循环实现的线性遍历, 或使用典型的 std::for_each 算法的操作.

const char* comma="";
std::for_each(c.begin(),c.end(),[&](const sprite& s){
  std::cout<<comma;
  s.render(std::cout);
  comma=",";
});
std::cout<<"\n";

把程序中使用的容器从经典替代品替换为 Boost.PolyCollection:

  • std::vector<base*> (或类似容器) → boost::base_collection<base>
  • std::vector<std::function<signature>> → boost::function_collection<signature>
  • std::vector<boost::type_erasure::any<concept_>> → boost::any_collection<concept_>
  • std::vector<std::variant<Ts...>> → boost::any_collection<boost::mp11::mp_list<Ts...>>

由于更好的缓存和分支预测行为, 预期性能会得到提升. 但仍有改进空间.

考虑用双重段-元素循环 (基于 Boost.PolyCollection 的 局部迭代器 能力) 对上面的代码做如下改写:

const char* comma="";
for(auto seg_info:c.segment_traversal()){
  for(const sprite& s:seg_info){
    std::cout<<comma;
    s.render(std::cout);
    comma=",";
  }
}
std::cout<<"\n";

虽然乍看之下并不明显, 但同一基本操作的这一版本实际上比第一个更快: 对于 Boost.PolyCollection 所使用的分段结构, 传给 std::for_each 的非局部迭代器的每次迭代都涉及:

  1. 跳到段中的下一个位置,
  2. 检查是否到达段末尾 (总是),
  3. 若已到末尾 (不常见), 选择下一个段,
  4. 检查是否到达范围末尾 (总是),

而在第二个版本中, 大部分处理所在的内层循环上的迭代只是一个简单的递增加检查操作, 也就是说少了一次检查 (这次检查发生在外层循环上, 而外层循环要短得多). 当算法的工作量 (对元素本身实际做的有用工作) 相对较轻时, 循环的开销可能非常可观.

为了让用户更容易利用更快的段-元素循环, Boost.PolyCollection 基于该技术提供了自己的 for_each 版本:

#include <boost/poly_collection/algorithm.hpp>
...

const char* comma="";
boost::poly_collection::for_each(c.begin(),c.end(),[&](const sprite& s){
  std::cout<<comma;
  s.render(std::cout);
  comma=",";
});
std::cout<<"\n";

boost::poly_collection::for_each 具有与 std::for_each 相同的接口和行为, 区别在于它只适用于多态集合的 (非局部) 迭代器 [17]. 也提供了其他标准算法的版本:

auto n=boost::poly_collection::count_if(
  c.begin(),c.end(),[](const sprite& s){return s.id%2==0;});
std::cout<<n<<" sprites with even id\n";

事实上, 对于 <algorithm> 中与多态集合兼容的那些算法 (并非全部), 其中的大多数都提供了变体 [18]. 详情请查阅 参考.

类型恢复

所谓类型恢复, 我们指的是通过提供缺失的类型信息、从抽象实体获得具体实体的通用过程:

sprite*  ps=new warrior{5};
// sprite -> warrior
warrior* pw=static_cast<warrior*>(ps);

boost::type_erasure::any<renderable> r=std::string{"hello"};
// renderable -> std::string
std::string& str=boost::type_erasure::any_cast<std::string&>(r);

类型恢复有提升性能的潜力. 例如考虑以下代码:

// render r with std::string restitution
if(boost::type_erasure::typeid_of(r)==typeid(std::string)){
  std::string& str=boost::type_erasure::any_cast<std::string&>(r);
  std::cout<<str<<"\n";
}
else{
  std::cout<<r<<"\n";
}

从行为上看, 这段代码等价于简单地执行 std::cout<<r<<"\n", 但当类型恢复成功时, 语句 std::cout<<str<<"\n" 跳过了一次本会在使用 r 时发生的类虚调用. 从一般的角度看, 向编译器提供额外的类型信息使其能够执行比抽象情形更多的优化, 内联就是最主要的例子.

所有 Boost.PolyCollection 算法都接受一个可选的类型列表用于恢复. 让我们用 boost::any_collection 场景来说明这一点:

const char* comma="";
boost::poly_collection::for_each
  <warrior,juggernaut,goblin>( // restituted types
  c.begin(),c.end(),[&](const auto& x){ // loop traverses *all* elements
    std::cout<<comma<<x;
    comma=",";
  });
std::cout<<"\n";

输出:

warrior 2,warrior 6,[pop-up 1],[pop-up 2],juggernaut 0,juggernaut 4,
juggernaut 7,goblin 1,goblin 3,goblin 5,"stamina: 10,000","game over"

这个渲染循环与非恢复版本在两个方面有所不同:

  • 一个类型列表作为模板实参提供给了算法. 这表示这些类型可能实际存在于集合中, 而不是一种承诺. 此外, 类型列表不必是穷尽的, 即某些未列出的类型也可能存在于集合中——在上面的例子中, 该循环遍历 所有元素 (包括 std::string 和 window), 而不仅仅是与被恢复类型对应的那些元素. 一般而言, 被恢复的类型越多, 潜在的性能提升就越大.
  • 传入的 lambda 函数是泛型的, 以 const auto& 接受其参数 [19].

在内部, boost::poly_collection::for_each 会检查每个段的类型 (设为 T) 是否属于类型恢复列表: 若是这种情况, 则传给 lambda 函数的是一个 const T&, 而不是通用的 const boost::any_collection::value_type&. 对每个被恢复的类型, 我们都省去了间接调用, 并可能获得内联优化等. 正如我们在 性能一节 中所看到的, 加速效果可能非常显著.

类型恢复对 Boost.PolyCollection 的其余集合同样有效. 不过, 使用 boost::base_collection 时, 性能提升的情形更为微妙:

const char* comma="";
boost::poly_collection::for_each<warrior,juggernaut,goblin>(
  c.begin(),c.end(),[&](const auto& s){
    std::cout<<comma;
    s.render(std::cout);
    comma=",";
  });
std::cout<<"\n";

这里的问题在于, 即使传给 lambda 函数的参数 (在适当的情况下) 会被恢复为 warrior&、juggernaut& 或 goblin&, 使用它仍然涉及在 s.render(std::cout) 中执行一次虚函数调用. 这次调用能否被解析为非虚调用, 取决于编译器的实现质量:

  • 如果具体类被标记为 final, 那么编译器原则上拥有足够的信息来消除虚函数调用.
  • 除此之外, 去虚化 (devirtualization) 能力可能能够推断出类型恢复场景实际上是把元素转换为其真实类型, 在这种情况下, 同样不需要虚调用.

使用 boost::variant_collection 时, 便利标记 all_types 请求恢复所有类型而无须显式写出它们. 这当然是可行的, 因为这些类型 (同样) 在编译期是已知的. 注意, 由于元素按其类型被直接访问, 示例中不会进行 visit 调用 [20].

boost::variant_collection<
  boost::mp11::mp_list<warrior,juggernaut,goblin,elf,std::string,window>
> c;
...

auto print_sprite=[](const sprite& s)       { s.render(std::cout); };
auto print_string=[](const std::string& str){ std::cout<<str; };
auto print_window=[](const window& w)       { w.display(std::cout); };
auto print=overloaded{print_sprite,print_string,print_window};

const char* comma="";
boost::poly_collection::for_each<boost::poly_collection::all_types>(
  c.begin(),c.end(),[&](const auto& r){
    std::cout<<comma;
    print(r);
    comma=",";
});
std::cout<<"\n";
