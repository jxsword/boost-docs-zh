计算

时间点 -- 时长 -- 区间 (时段) -- 特殊值处理

时间点

本节介绍可对时间点执行的一些基本算术规则. 总体而言, 时间点支持与时长配合进行的基本算术运算, 如下所示:

      Timepoint + Duration  --> Timepoint
      Timepoint - Duration  --> Timepoint
      Timepoint - Timepoint --> Duration

与常规数值类型不同, 以下运算是未定义的:

      Duration + Timepoint  --> Undefined
      Duration - Timepoint  --> Undefined
      Timepoint + Timepoint --> Undefined

时长

时长表示一段时间长度, 可以取正值和负值. 能够与其他时长以及简单整数值进行计算往往很有用. 下面对这些计算加以说明:

      Duration + Duration  --> Duration
      Duration - Duration  --> Duration
      
      Duration * Integer   --> Duration
      Integer  * Duration  --> Duration
      Duration / Integer   --> Duration  (Integer Division rules)

区间 (时段)

区间逻辑对于简化日期和时间的许多"计算"极为有用. 下面描述基于半开区间的时段所提供的运算. 以下运算基于两个输入时间段计算新的时间段:

Timeperiod intersection Timeperiod --> Timeperiod 
  (null interval if no intersection)
Timeperiod merge Timeperiod        --> Timeperiod 
  (null interval if no intersection)
Timeperiod shift Duration          --> Timeperiod 
  (shift start and end by duration amount)

此外, 时段支持各种返回布尔结果的查询. 第一组是与其他时间段进行的计算:

  Timeperiod == Timeperiod           --> bool
  Timeperiod < Timeperiod            --> bool (true if lhs.last <= rhs.begin)
  Timeperiod intersects Timeperiod   --> bool
  Timeperiod contains Timeperiod     --> bool
  Timeperiod is_adjacent Timeperiod  --> bool

以下计算针对时间点 (Timepoint) 执行.

  Timeperiod contains Timepoint      --> bool
  Timeperiod is_before Timepoint     --> bool
  Timeperiod is_after Timepoint      --> bool

特殊值处理

对于许多时间相关的问题, 让时长和时间点类型支持特殊值 (例如非日期时间 (NADT, Not A Date Time) 和无穷大) 是很有用的. 总体而言, 非日期时间 (NADT) 和无穷大这类特殊值应当遵循与浮点值类似的规则. 注意, 应当可以将基于 NADT 的系统配置为抛出异常而不是产生 NADT.

  Timepoint(NADT) + Duration --> Timepoint(NADT)
  Timepoint(∞) + Duration    --> Timepoint(∞)
  Timepoint + Duration(∞)    --> Timepoint(∞)
  Timepoint - Duration(∞)    --> Timepoint(-∞)

当对正无穷和负无穷执行运算时, 库将产生与下表一致的结果.

  Timepoint(+∞) + Duration(-∞) --> NADT
  Duration(+∞) + Duration(-∞)  --> NADT
  Duration(±∞) * Zero          --> NADT
  
  Duration(∞) * Integer(Not Zero) --> Duration(∞)
  Duration(+∞) * -Integer         --> Duration(-∞)
  Duration(∞) / Integer           --> Duration(∞)

权衡: 稳定性、可预测性与近似

不可避免的权衡

库尽力提供用户想要的一切, 但存在某些固有限制, 制约着任何时间库所能做到的事情. 具体而言, 在任何特定应用中, 用户必须在以下三种能力中舍弃其一、选择其二:

  • 与墙上时钟时间 (wall-clock time) 精确一致
  • 精确的数学运算, 例如时长计算
  • 处理未来时间点的能力

有些库可能会隐含地承诺三者兼得, 但若真正加以检验, 三者中只有两个能同时成立. 这一局限并非任何特定库在设计或实现上的缺陷, 而是国际标准定义不同时间系统的方式所导致的结果. 下面分别考察这三种情形:

若要与墙上时钟时间精确一致, 就必须使用 UTC 或本地时间. 若要通过两个 UTC 时间相减计算时长并希望答案精确到秒, 那么这两个时间不能距离现在太远, 因为闰秒会影响计数, 而闰秒只能提前约 6 个月确定. 对于本地时间, 未来的时长计算可能偏差整整一小时, 因为立法机构可以 (而且确实会) 随意修改夏令时 (DST) 规则.

若要处理未来的墙上时钟时间, 那么 (一般情况下) 将无法计算精确的时长, 原因如上所述.

若要对未来时间进行精确计算, 就必须使用 TAI 或等效的时间标准, 但 TAI 到 UTC 或本地时间的映射取决于闰秒, 因此将无法与墙上时钟时间精确一致.

稳定性、可预测性与近似

下面是一些有助于解释其中缘由的基础理论. 记住, 时间类型同任何抽象数据类型 (ADT) 一样, 是一个值集合以及对这些值的运算.

稳定性

如果与给定值关联的位模式不随时间变化, 则该类型的表示是稳定的. 表示不稳定的类型对任何人都没什么用处, 因此我们将坚持要求任何时间库只使用稳定的表示.

如果对特定操作数应用某个运算的结果不随时间变化, 则该运算是稳定的.

可预测性

集合通常分为两类: 良定义 (well-defined) 与劣定义 (ill-defined) . 由于类型即集合, 我们可以将这些定义扩展到类型上. 对于任何类型 T, 必须存在谓词 is_member( x ), 用于判定值 x 是否为类型 T 的成员. 该谓词必须返回 true、false 或 dont_know.

如果对所有 x, is_member( x ) 都返回 true 或 false, 我们称集合 T 是良定义的.

如果对任何 x, is_member( x ) 返回 dont_know, 我们称集合 T 是劣定义的.

这是数学中通常使用的规则. 然而, 由于时间类型的特殊性质, 有必要细化这一观点并创建第三个类别, 如下所示:

对于任何时间类型 T, 必须存在谓词 is_member( x, t ), 用于判定值 x 是否为 T 的成员. 参数 t 表示谓词求值的时间. 对每个 xi, 必须存在时间 ti 和值 v, 使得:

  • v = true 或 v = false, 且
  • 对所有 t < ti, is_member( xi, t ) 返回 dont_know, 且
  • 对所有 t >= ti, is_member( xi, t ) 返回 v.

ti 由此就是我们"查明"xi 是否为 T 成员的时间. 现在可以定义三类时间类型:

如果对所有 xi 都有 ti = 负无穷, 我们称类型 T 是可预测的.

如果对某个 xi 有 ti = 正无穷, 我们称类型 T 是畸形的 (ill-formed) .

否则我们称类型 T 是不可预测的 (这意味着对某个 xi, ti 是有限的) .

畸形集合没有多少实用价值, 因此不再进一步讨论. 用通俗的话说, 上述内容只是在讲: 可预测类型的所有值都可以提前知晓, 而不可预测类型的某些值要到某个特定时刻才能知晓.

运算的稳定性

可预测类型具有两个重要性质:

  • 其元素到一组连续整数存在保序映射, 且
  • 对其值进行的时长运算是稳定的

其实际效果是, 时长计算可以用简单的整数减法实现. 可预测类型的例子有 TAI 时间点和格里高利历日期.

不可预测类型恰好具有相反的性质:

  • 其元素到一组连续整数不存在保序映射, 且
  • 对其值进行的时长运算是不稳定的.

不可预测类型的例子有 UTC 时间点和本地时间时间点.

我们可以稍加细化: 不可预测类型中的某个范围可以是可预测的, 且完全在该范围内的值上执行的运算将是稳定的. 例如, 从 1970-01-01 至今的 UTC 时间点范围是可预测的, 因此该范围内的时长计算将是稳定的.

近似

这些限制带来了问题, 因为 UTC 和本地时间这类重要的时间类型实际上是不可预测的, 因此对其执行的运算有时并不稳定. 然而从实践角度看, 我们经常希望执行这类运算, 例如计算以本地时间指定的两个未来时间点之间的时长.

库所能做的最好办法是提供一个近似值, 这通常是可行的, 而且对大多数用途而言足够好了. 当然, 文档必须说明答案何时是近似的 (因而也是不稳定的) 以及误差可能有多大. 在许多方面, 对不可预测集合进行计算类似于使用浮点数——其结果只被期望近似正确; 而对可预测集合进行计算则类似于使用整数——其结果被期望精确.

对于需要精确答案或不能容忍不稳定性的情形, 用户必须能够明确指定这一点; 此后若用户请求的计算无法得到精确且稳定的答案, 库应当抛出异常.

术语

以下是若干与日期时间领域相关的术语.

时间类型的一种分类:

  • Timepoint (时间点) —— 时间连续体中某个位置的指定符. 类似于直尺上的一个数字.
  • Timelength (时间长度) —— 不依附于时间连续体上任何点的时间段.
  • Timeinterval (时间区间) —— 依附于时间连续体中特定点的时间段.

还有一些其他术语:

  • Accuracy (准确度) —— 误差的度量, 即时钟读数与真实时间之间的差异.
  • Calendar System (历法系统) —— 以日级分辨率标记时间点的系统.
  • Clock Device (时钟设备) —— (与某些硬件绑定的) 软件组件, 相对于某个历法或时钟系统提供当前日期或时间.
  • Precision (精密度) —— 时钟可重复性的度量.
  • Resolution (分辨率) —— 时钟/历法系统或时间类型可表示的最小时长的规格 (例如: 1 秒、1 个世纪) .
  • Stability (稳定性) —— 类的一种性质, 表示与特定 (抽象) 值相关联的底层表示 (实现) 永远不会改变.
  • Time System (时间系统) —— 以高于日级的分辨率标记时间点的系统.

一些标准的日期时间术语:

  • Epoch (纪元) —— 历法或时钟系统的起始时间点.
  • DST (夏令时) —— 某些地区在夏季进行的本地时间调整, 用于移动白昼时段的时钟时间
  • Time zone (时区) —— 地球上提供"本地时间"的区域, 本地时间由 DST 规则和 UT 偏移定义.
  • UTC Time (协调世界时) —— 在经度零处测量的民用时间系统. 通过使用闰秒进行调整以匹配地球自转. 也称为 Zulu Time. 取代了类似的格林尼治平均时 (Greenwich Mean Time) 系统. 更多信息见 http://aa.usno.navy.mil/faq/docs/UT.html
  • TAI Time (国际原子时) —— 一种高精度单调 (术语有待改进) 时间系统, 由世界各地的原子钟以 0.1 微秒的分辨率测量. 不随地球自转调整. 更多信息见 http://www.bipm.fr/enus/5_Scientific/c_time/time_server.html

一些更具实验性的术语:

  • Local Time (本地时间) —— 在宇宙中特定位置测量的时间.
  • Time Label (时间标签) —— 完整或部分地指定相对于某个历法或时钟系统的特定日期时间的元组. 即年-月-日表示法.
  • Adjusting Time Length (可调整时间长度) —— 表示随时刻变化而不同的物理时长的时间段. 例如, 1 个月的时长通常不是固定的天数, 其实际长度取决于从哪个日期开始度量.

以下是一些设计层面的术语:

  • Generation function (生成函数) —— 基于一个或多个参数生成一组特定时间点、长度或区间的函数.

构建-编译器信息

概述 -- 编译选项 -- 编译器/可移植性说明 -- 目录结构 -- 所需的 Boost 库

概述

本库有少数几个函数需要创建库文件 (主要是 to_string、from_string 函数) . 大多数库用户无需构建该库即可有效使用它——只需包含所需的头文件即可. 如果需要该库, build 目录中的 Jamfile 会生成包含这些函数的"静态"库 (libboost_date_time) 和"动态/共享"库 (boost_date_time) . 注意, 在不用库文件的情况下使用本库 (尤其在 Windows 上) 可能需要在编译选项中使用 BOOST_DATE_TIME_NO_LIB 标志.

编译选项

默认情况下, posix_time 系统内部使用单个 64 位整数来提供微秒级分辨率. 或者, 可以使用 64 位整数与 32 位整数的组合 (96 位分辨率) 来提供纳秒级分辨率. 对于许多不需要纳秒分辨率的应用, 默认实现可以提供更好的性能和更紧凑的内存占用.

要使用替代分辨率 (96 位纳秒) , 必须在库用户的项目文件 (如 Makefile、Jamfile 等) 中定义变量 BOOST_DATE_TIME_POSIX_TIME_STD_CONFIG. 格里高利历系统不使用该宏, 因此在构建该库时它不产生任何影响.

自 1.33 版起, date_time 库引入了新的 IO 流系统. 某些编译器无法使用这套新系统. 对这些编译器而言, 较早的 ("legacy") IO 系统仍然可用. 不受支持的编译器会自动选择旧系统, 但用户也可以通过定义 USE_DATE_TIME_PRE_1_33_FACET_IO 强制使用旧系统.

为方便起见, date_time 提供了一些 额外的时长类型. 由于"贴合到月末" (snap-to-end-of-month) 行为, 使用这些类型可能产生意外结果 (完整细节与示例见 运算可逆性陷阱) . 这些类型默认启用. 要禁用它们, 只需在项目文件中取消定义 BOOST_DATE_TIME_OPTIONAL_GREGORIAN_TYPES.

另一项便利是 date 和 ptime 的默认构造函数. 这些构造函数默认启用. 要禁用它们, 只需在项目文件中定义 DATE_TIME_NO_DEFAULT_CONSTRUCTOR.

编译器/可移植性说明

Boost Date-Time 库已在许多编译器和平台上构建并测试过. 不过, 某些编译器和标准库存在问题. 其中一些问题可以绕过, 另一些则难以绕过. 以下编译器已知可完全支持库的各个方面:

  • Codewarrior 9.4 Windows
  • GCC 3.2 - 3.4, 4.x on Linux
  • GCC 3.3, 4.x on Darwin
  • GCC 3.3 - 3.4, 4.x on Solaris
  • GCC 3.3, 4.x on HP-UX
  • QCC 3.3.5 on QNX
  • MSVC 7.1 Windows
  • Intel 8.1-9.x Linux and Windows

遗憾的是, VC8 编译器在日期时间代码上存在一些问题. 最严重的问题是 VC8 标准库 basic_stream 代码中引入的内存泄漏. date_time 的代码已尽可能加以修改以避开该问题, 但如果使用旧式 IO 选项 (VC8 下这不是默认项) , 问题仍可能出现. 更多细节见 邮件列表存档.

除上述问题外, 某些版本的 VC8 库将 std::tm 结构中允许的值范围限制为正值. 这是 VC8 新增的限制. 其影响是 1900 年之前的日期会导致异常. 遗憾的是, 该问题没有简单的解决办法. 注意, VC8 编译器的新 64 位版本似乎没有这一限制.

这些编译器支持库的除 wstring/wstream 输出外的所有方面.

  • MinGW 3.2, 3.4, 3.5 *
  • GCC 3.2 (cygwin) *

具体而言, 缺乏对标准 locale 的支持限制了库支持基于 iostream 的输入输出的能力. 对这些编译器, 提供了一套功能较为有限的基于字符串的输入输出. 具有这一限制的部分编译器/标准库包括:

  • Borland 5.6

对一些较旧编译器的官方支持现已停止. 这包括:

  • GCC 2.9x
  • Borland 5.1.1

Visual Studio 与 STLPort

Visual Studio (7.0 和 7.1) 与 STLPort 存在一个已知问题. 构建错误通常涉及类型问题或"no acceptable conversion", 并试图用 wchar_t 实例化模板. STLPort 的默认构建不支持 wchar_t. 该问题有两种可能的解决办法. 最简单的一种是用户可以构建不带宽流/宽字符串等的 date_time. 另一种是重新构建带 wchar_t 支持的 STLPort.

要以不带宽流/宽字符串等的方式构建 date_time, 请从 $BOOST_ROOT 执行以下命令:

bjam -a "-sTOOLS=vc-7_1-stlport" "-sSTLPORT_PATH=..." \
     "-sBUILD=<define>BOOST_NO_STD_WSTRING"           \
     --stagedir=... --with-date_time stage

(将省略号替换为构建系统的正确路径, 并在必要时将 TOOLS 调整为正确的工具集)

重新构建带 wchar_t 支持的 STLPort 需要在 STLPort 的 makefile 中放入 /Zc:wchar_t. 然后应从 $BOOST_ROOT 执行以下命令构建 date_time:

bjam -a "-sTOOLS=vc-7_1-stlport" "-sSTLPORT_PATH=..." \
     "-sBUILD=&native-wchar_t>on"                     \
     --stagedir=... --with-date_time stage

(将省略号替换为构建系统的正确路径, 并在必要时将 TOOLS 调整为正确的工具集)

缺陷修复 修复了 time_duration_traits 的计算缺陷, 该缺陷曾导致时长被限制在 32 位范围内, 即使 64 位可用. 感谢 Joe de Guzman 查明此问题.
缺陷修复 为时长类型 (例如 date_duration、time_duration) 提供了额外的运算符. 这包括可被整数除, 以及允许 +=、-= 运算符的修复. 感谢 Bart Garst 编写这些代码. 此外, 计算 的文档也得到改进.
缺陷修复 在 boost::gregorian gregorian_types.hpp 中为各种 date_generator 函数类加入了 typedef.
特性 加入了 from_time_t 函数, 用于将 time_t 转换为 ptime.
特性 加入了用于组合时段的 span 函数. 见 date period 和 time period 文档.
特性 为 time_duration 加入了获取时长中总秒数的函数 (截断任何小数秒) . 此外, 还加入了其他分辨率以便于转换. 例如 
seconds(1).total_milliseconds() == 1000
seconds(1).total_microseconds() == 1000000
hours(1).total_milliseconds() == 3600*1000 //3600 sec/hour
seconds(1).total_nanoseconds() == 1000000000
特性 为 日期生成器 类加入了输出流运算符——partial_date、first_kday_after、first_kday_before 等. 感谢 Bart Garst 完成这项工作.
特性 为时长加入了一元负号运算符, 用于反转时长的符号. 例如: 
time_duration td(5,0,0); //5 hours
td = -td; //-5 hours
感谢 Bart Garst 完成这项工作.
特性 加入了对解析含"月份名"字符串的支持. 因此从字符串创建 date 对象现在接受多种格式 ("2003-10-31"、"2003-Oct-31" 和 "2003-October-31") . 因此, date d = from_simple_string("2003-Feb-27") 现在是允许的. 错误的月份名字符串 (from_simple_string("2003-SomeBogusMonthName-27")) 会导致 bad_month 异常. 在大多数编译器上字符串比较不区分大小写. 感谢 Bart Garst 完成这项工作.
特性 除了支持月份名或数字之外, 还加入了从多顺序日期字符串创建 date 对象的函数. 例如: "January-21-2002"、"2002-Jan-21" 和 "21-Jan-2003". 更多细节见 Date 类.
缺陷修复 各种文档修复. 感谢 Bart Garst 的更新.

Boost 1.29 到 1.30 (date_time 1.00 到 1.01) 的变更

注意: partial_date 类的接口 (见 date_algorithms) 发生了变更. 构造参数的顺序被改变, 这会导致一些代码执行失败. 做出这一变更是为了便于实现更通用的本地时间调整代码. 因此, 原来写 partial_date pd(Dec,25) 的代码需要改为 partial_date pd(25, Dec);
