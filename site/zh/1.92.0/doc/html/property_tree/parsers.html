XML 解析器

XML 格式 是以文本形式存储信息的行业标准. 遗憾的是, 撰写本文时 Boost 中尚无 XML 解析器. 因此本库内置了快速而小巧的 RapidXML 解析器(当前版本 1.13)以提供 XML 解析支持. RapidXML 并不完全支持 XML 标准, 它无法解析 DTD, 因此不能做完整的实体替换.

默认情况下, 解析器会保留大部分空白, 但移除仅由空白组成的元素内容. 经编码的空白(如 &#32;)不在此列. 若希望去除全部首尾空白并把连续空白折叠为单个空格, 可传入 trim_whitespace 标志.

请注意 RapidXML 不理解编码规范. 若传入字符缓冲区, 它假定数据已正确编码; 若传入文件名, 它会按你给定的 locale (未给定则用全局 locale)的字符转换来读取文件. 这意味着要把 UTF-8 编码的 XML 文件解析进 wptree, 必须直接提供或通过替换全局 locale 提供一个替代 locale.

XML / 属性树转换模式 (read_xml 和 write_xml):

  • 每个 XML 元素对应一个属性树节点, 子元素对应该节点的子节点.
  • XML 元素的属性存储在子键 <xmlattr> 中, 属性节点中每个属性各有一个子节点. 无属性时不保证也不需要存在 <xmlattr> 节点.
  • XML 注释存储在名为 <xmlcomment> 的节点中, 除非通过标志启用了注释忽略.
  • 文本内容按标志以两种方式之一存储. 默认方式把所有文本节点拼接后存为元素节点的数据, 这样可以方便地读取全部内容, 但文本与子元素的相对顺序会丢失. 另一种方式把每段文本内容存为独立节点, 都命名为 <xmltext>.

XML 存储编码不能完美往返. 一次读取-写入周期会丢失被裁剪的空白、低层格式信息, 以及普通数据与 CDATA 节点的区分. 注释仅在启用时保留. 一次写入-读取周期会丢失被裁剪的空白, 即若原树的字符串数据以空白开头或结尾, 这些空白会丢失.

JSON 解析器

JSON 格式 是一种由 JavaScript 对象字面量记法衍生而来的数据交换格式. (JSON 即 JavaScript Object Notation.) JSON 是一种简单、紧凑的格式, 适用于任意深度的松散结构节点树, 与属性树数据集非常相似. 它比 XML 的结构化程度低且不支持 schema, 但优点是更简单、更小巧, 并且无需复杂 schema 即可带类型.

属性树数据集不带类型, 也不直接支持数组. 因此采用如下 JSON / 属性树映射:

  • JSON 对象映射为节点, 每个属性是一个子节点.
  • JSON 数组映射为节点, 每个元素是一个名为空的子节点. 若节点同时具有有名和无名子节点, 则无法映射为 JSON 表示.
  • JSON 值映射为包含该值的节点. 但所有类型信息都会丢失; 数字以及字面量 "null"、"true"、"false" 都只映射为其字符串形式.
  • 同时包含子节点和数据的属性树节点无法映射.

除类型信息丢失外, JSON 可完整往返.

例如下面这段 JSON:

{
   "menu":
   {
      "foo": true,
      "bar": "true",
      "value": 102.3E+06,
      "popup":
      [
         {"value": "New", "onclick": "CreateNewDoc()"},
         {"value": "Open", "onclick": "OpenDoc()"},
      ]
   }
}

将被转换为如下属性树:

menu
{
   foo true
   bar true
   value 102.3E+06
   popup
   {
      ""
      {
         value New
         onclick CreateNewDoc()
      }
      ""
      {
         value Open
         onclick OpenDoc()
      }
   }
}

INI 解析器

INI 格式 曾在 Windows 世界广泛使用. 如今它已过时, 但仍有数量惊人的应用程序在使用它. 原因大概是它的简单性, 再加上微软推荐改用注册表, 而并非所有开发者都愿意这样做.

INI 是一种只有单层分节的简单键值格式, 因此不如属性树数据集丰富, 这意味着并非所有属性树都能序列化为 INI 文件.

INI 解析器为每个节创建一个树节点, 并为该节中的每个属性创建一个子节点. 不属于任何节的属性直接加入根节点. 空节被忽略.(如前所述, 它们无法往返.)

INI 序列化器执行相反的过程. 它先把根中所有含数据但无子节点的子级作为属性写出, 然后为每个含子节点但无数据的子级创建一个节. 节的子级只能包含数据. 若根节点含有数据, 或根的任何子级同时含有数据与内容, 或层级超过三层, 均为错误. 还不得存在重复键.

空的树节点被视为空属性. 无法创建空节.

由于 Windows INI 解析器丢弃尾部空格且不支持引号, 属性树解析器沿袭此例. 这意味着以空白结尾的属性值无法往返.

INFO 解析器

INFO 格式是专为属性树库设计的. 它提供一种简单、高效的格式, 可用于序列化原本只存在于内存中的属性树. 它当然也可用于其他目的, 尽管缺乏广泛使用的先例可能是个障碍.

INFO 提供了一些让 C++ 程序员感到熟悉、并对中等规模数据集(尤其是测试输入数据)高效利用的特性. 它支持 C 风格字符转义、通过花括号的嵌套, 以及通过 #include 的文件包含.

本文档中的属性树可视化也使用 INFO.

一个典型的 INFO 文件大致如下:

key1 value1
key2
{
   key3 value3
   {
      key4 "value4 with spaces"
   }
   key5 value5
}

下面这个更复杂的文件演示了 INFO 的全部特性:

; A comment
key1 value1   ; Another comment
key2 "value with special characters in it {};#\n\t\"\0"
{
   subkey "value split "\
          "over three"\
          "lines"
   {
      a_key_without_value ""
      "a key with special characters in it {};#\n\t\"\0" ""
      "" value    ; Empty key with a value
      "" ""       ; Empty key with empty value!
   }
}
#include "file.info"    ; included file

除注释与 include 指令丢失外, INFO 可完整往返.
